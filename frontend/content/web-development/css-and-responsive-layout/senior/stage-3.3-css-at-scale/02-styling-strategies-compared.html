Styling Strategies Compared

CSS Modules, CSS-in-JS, utility CSS, and plain CSS solve the same problems, scoping, reuse, and dynamic values, with different costs, and the right choice depends on your constraints.

§1The Problems Every Strategy Solves

  • Scoping: avoid global name collisions.
  • Co-location: keep styles near the component that uses them.
  • Dynamic values: change styles from props or state.
  • Dead code removal: delete styles safely when components go.
  • Performance: small output, no runtime penalty, and streaming-friendly.
  • Tooling: types, linting, editor support, and design token integration.

§2Comparing the Options

ApproachStrengthsCosts
Plain CSS + convention (BEM, layers)Zero runtime, standard, great caching, no lock-inDiscipline required; global namespace
CSS ModulesLocal class names by default, plain CSS syntax, no runtimeDynamic values need custom properties; build step
Utility-first (Tailwind)Fast, consistent, tiny CSS, no namingVerbose markup; vocabulary lock-in
Runtime CSS-in-JS (styled-components, Emotion)Dynamic props, full co-locationRuntime cost, harder with server components and streaming, larger bundles
Zero-runtime CSS-in-JS (vanilla-extract, Panda, StyleX)Typed, co-located, extracted at build timeToolchain complexity, ecosystem maturity

Runtime CSS-in-JS lost ground as frameworks moved toward server rendering and React Server Components, since styles computed at runtime in the browser conflict with that model. The extraction-based approaches try to keep co-location without the runtime.

§3Choosing

Decide from constraints, not fashion.

  1. Rendering model: server-rendered or streamed pages favor static, extracted CSS.
  2. Team: how comfortable is everyone with CSS? Tools with guardrails help mixed-skill teams.
  3. Design system: if CSS must be consumed by many frameworks, standard CSS plus custom properties travels best.
  4. Dynamic styling needs: most dynamic values can be expressed as custom properties set by the component.
  5. Migration cost: switching strategies mid-project is expensive, so choose what you can sustain.
/* dynamic value without runtime CSS-in-JS: pass data through a custom property */
<div class="progress" style="--value: 72%"></div>
.progress::after { content: ""; display: block; width: var(--value); height: 100%; background: var(--accent); }
Native CSS got much better Nesting, layers, scope, container queries, and custom properties cover many reasons teams adopted tools. Re-evaluate old choices when the platform moves.

§4Common Mistakes

MistakeWhat HappensFix
Picking a tool because it is trendyMismatch with rendering model and team skillsDecide from constraints and a short prototype
Mixing three strategies in one codebase without rulesInconsistent and hard to maintainDefine where each is allowed
Runtime CSS-in-JS in a server-streamed app without checking supportHydration and performance issuesCheck the framework's guidance, or use extracted CSS
Practice
  1. Build the same small component with CSS Modules, utility classes, and plain CSS with layers, and compare bundle size and developer experience.
  2. Write a one-page decision record choosing a strategy for a specific project, with the constraints that drove it.
Key takeaways
  • All strategies address scoping, co-location, dynamic values, and dead-code removal.
  • Extracted, static CSS suits server rendering; runtime CSS-in-JS has real costs.
  • Choose from constraints, and recheck as native CSS evolves.
