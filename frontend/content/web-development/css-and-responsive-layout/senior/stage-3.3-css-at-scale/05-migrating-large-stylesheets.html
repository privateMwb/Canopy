Migrating Large Stylesheets

Migrating a huge stylesheet is a series of small, reversible, measured steps, with screenshots and metrics proving that nothing changed visually.

§1Understand What You Have

Before moving anything, collect facts about the current stylesheet.

  • Size and shape: lines, rules, selectors; use cssstats or similar tools.
  • Specificity graph: spikes of high-specificity selectors and !important count.
  • Duplication and dead code: find unused CSS with Coverage on key journeys, and duplicate declarations with a tool like jscpd.
  • Hot spots: which files change most often and cause the most bugs (use version control history).
  • Ownership: who owns each area, and what tests exist.

§2The Safety Net

A refactor with no safety net is a rewrite in disguise. Build the net first.

  1. Visual regression tests for key pages and components, at several widths and themes.
  2. Lint ratchet: a baseline of current violations that may only shrink.
  3. Feature flags or scoped rollouts so a change can be turned off.
  4. Metrics dashboard: CSS size, specificity, !important count, Core Web Vitals.
  5. A rollback plan: every step reversible by a single revert.

§3Strategies for Moving

StrategyHowFits when
StranglerBuild new components in the new system, replace old ones graduallyLarge, long-lived products
Layer wrappingWrap legacy CSS in a low-priority @layer so new rules win without specificity fightsSpecificity wars are the main pain
Scoped islandsMigrate by route, page, or component, behind flagsClear ownership boundaries
CodemodsAutomate mechanical changes: class renames, token substitutionRepetitive, rule-based edits
@layer legacy, system;

@layer legacy { @import url("old-site.css"); }   /* everything old, lowest priority */
@layer system { /* new tokens, components, utilities */ }

Work in small pull requests that each pass visual tests, and track burn-down: the number of legacy selectors or files remaining. Celebrate deleting code.

Delete as you go Each migrated area should end with deletion of the old CSS. Otherwise you're adding a second system on top of the first, and the codebase gets bigger and slower.

§4Common Mistakes

MistakeWhat HappensFix
Rewriting everything on a branch for monthsMerge conflicts, no value delivered, high riskMigrate incrementally behind flags
Migrating without visual regression testsRegressions are found by usersBuild the safety net first
Leaving the old CSS in place after migrationGrowing bundle and confusionDelete legacy rules as each area is done
Practice
  1. Run a coverage and specificity analysis on a real stylesheet and list its three biggest problems with numbers.
  2. Wrap a legacy stylesheet in a lower-priority @layer, add one new component in the higher layer, and show that it wins without raising specificity.
Key takeaways
  • Measure the current state before changing it.
  • Build the safety net: visual tests, lint ratchet, flags, metrics, rollback.
  • Migrate incrementally with layers and the strangler pattern, and delete as you go.
