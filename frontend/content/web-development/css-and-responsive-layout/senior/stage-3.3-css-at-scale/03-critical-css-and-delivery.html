Critical CSS & Delivery

CSS is render-blocking, so how you split, inline, and load it directly sets how soon users see content.

§1Why Delivery Matters

The browser won't paint until it has the CSS needed for the first render. A big single stylesheet delays First Contentful Paint (FCP), and may delay Largest Contentful Paint (LCP) too. Goals: ship less CSS, ship it earlier, and don't block on what isn't needed yet.

  • Reduce: remove unused rules, minify, compress with Brotli or gzip.
  • Split: separate critical, per-route, and rarely used styles.
  • Prioritize: load critical CSS first and defer the rest.
  • Cache: use long-lived, hashed filenames for static assets.

§2Critical CSS

Critical CSS is the minimum needed to render the above-the-fold content. Inline it in the <head> to avoid a request, then load the full stylesheet without blocking.

<head>
  <style>/* critical rules for header, hero, first paragraph */</style>

  <link rel="preload" href="/css/site.css" as="style" onload="this.onload=null;this.rel='stylesheet'">
  <noscript><link rel="stylesheet" href="/css/site.css"></noscript>
</head>

Tools like critical or Critters can extract above-the-fold CSS automatically at build time. Keep the inlined part small (roughly under 14KB, which fits in the first TCP packets), and test that it doesn't cause a flash of unstyled content below the fold.

§3Splitting and Loading Strategy

TechniqueHowNotes
Per-route CSSBundler outputs a CSS file per page or routeStandard in most frameworks
Media-scoped CSS<link media="print"> or (min-width: 60em)Non-matching sheets don't block rendering
Component-level loadingLoad CSS with the component's JS or on demandWatch for late-loaded layout shift
@import in CSSAvoid in productionSerial requests; bundle instead
FontsPreload key fonts, use font-displaySee metrics-adjusted fallbacks to prevent shift

Check results with Lighthouse and the Network panel: look at the Coverage tab for unused CSS, and the waterfall for chained or late stylesheets. Also check the cost in the field with real user monitoring, not just lab tests.

Less CSS beats clever loading Before inlining and splitting, delete unused styles. A smaller stylesheet is faster to download, parse, and match, and needs no tricks.

§4Common Mistakes

MistakeWhat HappensFix
Inlining hundreds of KB of CSSBloats every HTML response and defeats cachingInline only a small critical subset
Using @import chainsSerial downloads delay renderingBundle or use parallel <link> tags
Deferring CSS without a fallbackFlash of unstyled content, or no styles without JSAdd <noscript> and test the loading state
Practice
  1. Run the Coverage tool on a page and record the percentage of unused CSS, then remove or split what you can.
  2. Extract critical CSS for one page, inline it, and compare First Contentful Paint before and after.
Key takeaways
  • CSS is render-blocking: send less, send it earlier, defer the rest.
  • Inline a small critical subset, and load the full stylesheet without blocking.
  • Measure with Coverage, Lighthouse, and field data.
