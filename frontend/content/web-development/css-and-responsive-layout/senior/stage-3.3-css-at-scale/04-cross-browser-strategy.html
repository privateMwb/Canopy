Cross-Browser Strategy

A cross-browser strategy is a written policy for who you support and how, built on progressive enhancement, so you stop guessing and start deciding.

§1Define a Support Policy

Decide, with data, which browsers get which level of experience, and write it down.

  • Start from analytics: which browsers and versions do your users actually use?
  • Use a browserslist query such as defaults and last 2 versions and not dead, shared by every build tool.
  • Define tiers: full support for current evergreen browsers, functional (usable, less polished) for older ones, unsupported below a cut-off.
  • Revisit regularly; policies drift as usage changes.

Evergreen browsers update automatically, so the real compatibility work is mostly about features that are new, partially implemented, or differently implemented.

§2Progressive Enhancement for CSS

Write a baseline that works everywhere, and layer newer features on top, using feature queries.

.layout { display: block; }                    /* baseline */

@supports (display: grid) {
  .layout { display: grid; grid-template-columns: 1fr 2fr; }
}

@supports (container-type: inline-size) {
  .card-wrap { container-type: inline-size; }
}

.box { width: 90%; width: min(90%, 60rem); }     /* later value wins where supported */

Unknown properties and invalid values are dropped, so the cascade naturally falls back to the previous declaration. This makes the "write the safe value first" pattern reliable.

§3Tooling and Verification

ToolUse
MDN compatibility tables, caniuse, BaselineCheck support before adopting a feature
browserslist + Autoprefixer / Lightning CSSPrefix and down-level syntax such as nesting
@supports and feature queriesConditional enhancement in CSS
BrowserStack, Playwright (Chromium, Firefox, WebKit)Test across engines in CI
stylelint-no-unsupported-browser-featuresWarn about unsupported features against your targets

Polyfills for CSS are rare and expensive because they run in JavaScript. Prefer graceful degradation: a design that is simpler but fully functional in an older browser is a success.

Baseline as a shortcut The Baseline label marks features that work across all major current browsers. A policy of "use Baseline widely available features freely, enhance with newer ones" is easy to explain and defend.

§4Common Mistakes

MistakeWhat HappensFix
Testing only in your own browserWebKit and Firefox differences surface in productionRun tests across Chromium, Firefox, and WebKit
No written support policyEndless debates and inconsistent decisionsDocument tiers and a review cadence
Reaching for polyfills firstHeavy JavaScript to replicate CSSDegrade gracefully with feature queries
Practice
  1. Write a one-page browser support policy for a real project, with tiers and the data behind them.
  2. Take a newer CSS feature, write a baseline, and layer the feature using @supports.
Key takeaways
  • Base the support policy on your analytics, and write it down.
  • Write safe baselines and enhance with @supports and cascade fallbacks.
  • Test across engines in CI, and prefer degradation to polyfills.
