Reading Performance Traces

A performance trace shows exactly where frames spend their time, and learning to read it turns "it feels janky" into a specific, fixable cause.

§1Recording a Useful Trace

  1. Open DevTools → Performance, and set CPU throttling (4x or 6x) and, for load issues, network throttling.
  2. Click Record, perform one interaction or reload the page, then stop.
  3. Use the Screenshots option to correlate what users saw with the activity.
  4. Look at the Frames and Main tracks first.

Record short traces. A focused 3-second recording of the problem is much easier to read than a 60-second tour.

§2Reading the Flame Chart

Color / EventMeaningCommon cause
Scripting (yellow)JavaScript runningHeavy handlers, long tasks
Recalculate Style (purple)Style matchingLarge DOM changes, broad class toggles
Layout (purple)Geometry computationLayout-affecting changes, forced reflow
Paint (green)PaintingLarge shadows, filters, repaints
Composite Layers (green)Layer assemblyMany layers, transforms

Red markers over a task flag long tasks (over 50ms) that block the main thread. Red corners on frames indicate dropped frames. A trace showing many small Layout events interleaved with Scripting often means layout thrashing: reading and writing layout in alternation.

§3From Symptom to Fix

// layout thrash: each loop iteration reads then writes
for (const el of items) {
  el.style.width = el.parentNode.offsetWidth + "px";   // read forces layout after each write
}

// fix: batch reads, then writes
const widths = items.map((el) => el.parentNode.offsetWidth);
items.forEach((el, i) => { el.style.width = widths[i] + "px"; });
  • Click an event and read the Summary tab: it shows the element count, the triggering stack, and "Layout forced" warnings with a link to the source.
  • Use the Rendering panel's Paint Flashing and Layout Shift Regions to see what repaints and shifts.
  • Compare traces before and after a change, using the same throttling, and report frame time and long-task numbers.

Always measure on realistic hardware settings. A fix that is invisible on a developer's laptop may be vital on a mid-range phone.

Evidence, not intuition Before changing code, write down the specific number you intend to improve (for example, 'frame time during scroll'). Re-measure after each change, and stop when the target is met.

§4Common Mistakes

MistakeWhat HappensFix
Recording long, noisy tracesThe cause is lost in the noiseRecord one short interaction
Profiling without CPU throttlingProblems on real devices stay hiddenThrottle to simulate mid-range hardware
Changing several things between measurementsYou don't know what helpedChange one variable at a time
Practice
  1. Record a trace of a janky interaction, identify the longest task, and trace it to a source line.
  2. Reproduce a layout thrash loop, record it, then fix it with batched reads and writes and compare traces.
Key takeaways
  • Record short, throttled traces of a single interaction.
  • Read Scripting, Style, Layout, Paint, and Composite events and long-task markers.
  • Make one change at a time and compare before and after numbers.
