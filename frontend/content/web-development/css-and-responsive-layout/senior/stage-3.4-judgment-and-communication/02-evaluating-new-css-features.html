Evaluating New CSS Features

CSS gains features constantly, so a repeatable framework, with support data, fallback cost, and user benefit, tells you when to adopt, polyfill, or wait.

§1Gather the Facts

  • Support: check MDN, caniuse, and Baseline status. Is it widely available, newly available, or limited to one engine?
  • Your users: what share of your traffic would get the fallback?
  • Spec status: is it stable, or still changing? Look at the spec maturity and open issues.
  • Standards positions: are the other engines supportive, neutral, or opposed?
  • Fallback: can the page work acceptably without it?

Baseline marks features that are available in the current stable versions of all the major browsers; "newly available" means they just landed, and "widely available" means they've been there for about 30 months.

§2A Decision Framework

SituationDecisionExample
Widely availableAdopt nowGrid, custom properties, :is()
Newly available, with a safe fallbackAdopt as an enhancement with @supportsContainer style queries, new color functions
Limited support, with benefit only on some browsersEnhance progressively; don't depend on it@scope or scroll-driven animations in some contexts
Limited support and essential for layoutWait, or use an established alternativeA layout that breaks without it
Polyfill exists but costs JavaScriptUsually avoid; degrade insteadCSS-heavy polyfills

§3Make the Decision Visible

Record decisions so the team doesn't relitigate them.

Decision record: CSS Anchor Positioning for tooltips
Status:    Evaluate / Adopt as enhancement / Wait
Support:   <engines and versions>; Baseline: <status>
Fallback:  absolute positioning with JS flip logic (existing)
Benefit:   removes ~2KB of positioning JS, fixes overflow bugs
Risk:      spec still changing; limited Firefox support
Review:    revisit in 6 months, or when Baseline is reached

A review date matters: a "wait" decision is only valid until support changes. Subscribing to browser release notes or a feature-tracking dashboard keeps decisions current.

Early isn't always better Adopting a feature early can earn real wins, or years of fallback code. Choose based on user benefit and fallback cost, not novelty.

§4Common Mistakes

MistakeWhat HappensFix
Adopting a feature because a demo looked impressiveBreaks for users without supportCheck Baseline and write a fallback
Never revisiting a "wait" decisionMissing features that have since become safeSet review dates
Relying on a feature that only one engine shipsThe spec may never reach othersCheck standards positions
Practice
  1. Pick one new CSS feature, gather the evidence, and write a decision record like the one above.
  2. Review your project's @supports blocks and remove those whose features are now Baseline widely available.
Key takeaways
  • Evaluate support, users, stability, standards positions, and fallbacks.
  • Adopt widely available features, enhance with newer ones, and wait on risky ones.
  • Record decisions with review dates.
