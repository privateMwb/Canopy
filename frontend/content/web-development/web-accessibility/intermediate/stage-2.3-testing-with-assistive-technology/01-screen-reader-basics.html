Screen Reader Basics

You cannot judge how a page sounds by looking at it. Spending an hour with a screen reader teaches more about accessibility than any checklist, and you only need a handful of commands to start.

§1Pick One and Learn It

Every major platform ships a screen reader, and one is free on Windows. Start with one that matches how your users reach your product, and learn a small core of commands rather than all of them.

Screen readerPlatformStart it with
NVDAWindows (free download)Install, then launch NVDA. Press NVDA+Q to quit
VoiceOvermacOSPress Cmd+F5
VoiceOveriOSSettings > Accessibility > VoiceOver, or the shortcut you set up
TalkBackAndroidSettings > Accessibility > TalkBack
NarratorWindows (built in)Press Win+Ctrl+Enter

Pair a screen reader with a sensible browser: NVDA with Firefox or Chrome, VoiceOver with Safari. Turn the volume down at first, since speech is fast, or turn on a speech viewer so you can read what is spoken.

§2The Commands That Matter

Screen reader users rarely read from top to bottom. They navigate by element type. In NVDA's browse mode, single letters jump to the next item of a kind, and the same keys with Shift go backward.

On a phone, swipe right or left to move to the next or previous item, and double-tap to activate. On iOS, the rotor (a two-finger twist) switches the navigation unit to headings, links, and more.

§3What to Listen For

For every interactive thing, a screen reader should tell you four things: its name, its role, its state, and its value. When any one is missing or wrong, you have found a bug.

  • Does the page title make sense when you arrive?
  • Can you reach the main content and the navigation by landmarks?
  • Does the heading list read like a table of contents?
  • Does each link and button have a name that makes sense out of context?
  • Does each form field announce its label, hints, errors, and required state?
  • Are updates (errors, search results, confirmations) announced?
What you should hear, and what signals a bug
"Subscribe, button"                         good: name + role
"button"                                    bug: no accessible name
"Email address, edit text, required"        good: name, role, state
"edit text"                                 bug: no label
"Menu, button, collapsed"                   good: state is announced
"Menu, button"                              bug: aria-expanded is missing

NVDA has two modes. Browse mode lets you move through the page with single-letter keys. Focus mode passes keys straight to form fields so you can type. It switches automatically on most form controls, and Insert+Space (NVDA+Space) toggles it by hand. If a widget behaves oddly, the mode is often the reason.

The key insight You are not trying to become an expert user. You are checking that name, role, state, and value come through, and that the page can be navigated by structure. That alone catches most serious problems.

§4Common Mistakes

MistakeWhat HappensFix
Testing only by reading the whole page top to bottomMisses how real users navigate, by headings, landmarks, and linksPractice navigating by element type, as users do
Running the screen reader at full speed on day oneYou cannot follow what it says and learn nothingSlow the speech rate, or use a speech viewer while learning
Judging a widget in the wrong modeKeys appear to fail because the screen reader intercepted themKnow when NVDA is in browse mode and when it is in focus mode
Practice
  1. Install NVDA, or turn on VoiceOver, and navigate a news site from the top using only headings, landmarks, and links. Note what you could not find.
  2. Fill in a login form with a screen reader on. Write down what was announced for each field and each button.
Key takeaways
  • Learn a few commands for headings, landmarks, links, form fields, and element lists, on one screen reader to start.
  • For every control, check that name, role, state, and value are announced.
  • Know the difference between browse mode and focus mode when testing with NVDA.
