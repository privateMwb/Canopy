Browser & Screen Reader Differences

The same HTML can sound different in different screen readers and browsers. Good testing accepts this, plans for it, and avoids coding around quirks that will not last.

§1Why Combinations Matter

A screen reader does not read your page directly. It reads what a browser exposes through the operating system's accessibility APIs. So the combination of screen reader, browser, and platform decides what a user hears. Each pair has its own support gaps and bugs.

Surveys such as the WebAIM screen reader user survey show which tools people actually use, and are a good guide to what to test first. Revisit them periodically, because usage shifts.

§2Where Behavior Diverges

Most core features behave consistently: native buttons, links, headings, landmarks, and labeled form controls. Differences tend to appear in more complex areas.

  • Live regions. Timing, repeated messages, and politeness handling vary.
  • Custom widgets. Support for newer ARIA roles and properties is uneven, especially on mobile.
  • Tables and lists. Verbosity differs, such as whether "list, 5 items" is announced.
  • Focus and reading modes. How each tool switches between reading and interacting with controls differs.
  • Hidden content. Subtle differences with aria-hidden, hidden, and visually hidden text.

WCAG uses the idea of accessibility support: a technique counts only if it works with the assistive technologies your users actually have. Sites like a11ysupport.io publish community test results for HTML and ARIA features across screen reader and browser pairs, which can answer "does this work?" before you build.

§3Strategies for Coping

You will never test every combination, so aim for resilience.

  1. Prefer native HTML. It is the best-supported path everywhere.
  2. Use well-supported ARIA patterns from the Authoring Practices Guide rather than exotic attributes.
  3. Test a priority matrix. Choose a core set (for example NVDA with Firefox, VoiceOver with Safari, TalkBack with Chrome), and add more as risk demands.
  4. Do not code around one tool's bug. A workaround that fixes one screen reader can break another, or break when the bug is fixed.
  5. Report bugs upstream. Browser and screen reader vendors take accessibility bug reports.

Notes: VO+Safari does not announce the chosen date. Filed as issue #482.
The key insight When a behavior differs, return to first principles: is your markup correct and well supported? If so, the difference is probably a tool bug, and the right response is to record it and report it, not to hack around it.

§4Common Mistakes

MistakeWhat HappensFix
Testing with one screen reader and calling it doneBugs that only appear in another pairing ship to real usersTest a small matrix that reflects your audience
Adding hacks for one tool's quirkBreaks other tools, or breaks when the bug is fixedUse standard markup, document the quirk, and report it
Assuming ARIA support is universalNewer attributes silently do nothing in some toolsCheck accessibility support data before relying on a feature
Practice
  1. Take one custom component and test it with two different screen reader and browser pairs. Record any differences in a matrix like the one above.
  2. Look up an ARIA feature you use on a support-data site. In which screen reader and browser pairs does it work?
Key takeaways
  • What users hear depends on the screen reader, the browser, and the platform together.
  • Native HTML and well-established ARIA patterns are the most reliable across combinations.
  • Test a priority matrix, document differences, and report bugs rather than coding around them.
