Widgets from the ARIA Authoring Practices

When no native element fits, you do not invent a pattern. The ARIA Authoring Practices Guide documents the roles, states, and keyboard behavior for common widgets, so your design matches what users already know.

§1Using the Authoring Practices Guide

The ARIA Authoring Practices Guide (APG) from the W3C describes patterns for tabs, accordions, menu buttons, comboboxes, dialogs, listboxes, trees, and more. Each pattern lists the required roles, states and properties, plus the keyboard model. The guide is advice rather than a formal standard, but following it makes your widget behave the way screen reader users expect.

PatternKey behavior
TabsArrow keys move between tabs. Tab moves into the panel
AccordionEach header is a button. Enter or Space toggles the section
Menu buttonEnter or Space opens. Arrows move. Escape closes and returns focus
DialogFocus moves in and is contained. Escape closes
ComboboxTyping filters. Arrows move through options. Enter selects

One common trap: role="menu" is for application-style menus, such as the menus in a desktop app. A website's navigation is not one. Use a list of links, with a disclosure button for submenus, instead.

§2Example: Tabs

Tabs show how the pieces fit together: roles that describe the structure, states that track selection, and keyboard handling that moves between tabs. Only the active tab sits in the Tab order (called a roving tabindex), and the arrow keys move between the others.

<div role="tablist" aria-label="Account sections">
  <button role="tab" id="t1" aria-selected="true"  aria-controls="p1">Profile</button>
  <button role="tab" id="t2" aria-selected="false" aria-controls="p2" tabindex="-1">Security</button>
  <button role="tab" id="t3" aria-selected="false" aria-controls="p3" tabindex="-1">Billing</button>
</div>

<div role="tabpanel" id="p1" aria-labelledby="t1" tabindex="0">Profile settings…</div>
<div role="tabpanel" id="p2" aria-labelledby="t2" tabindex="0" hidden>Security settings…</div>
<div role="tabpanel" id="p3" aria-labelledby="t3" tabindex="0" hidden>Billing settings…</div>

§3The Keyboard Handling

Without this script, the markup above only announces tabs and does not behave like them.

const tabs = [...document.querySelectorAll('[role="tab"]')];

function select(tab) {
  tabs.forEach((t) => {
    const on = t === tab;
    t.setAttribute('aria-selected', String(on));
    t.tabIndex = on ? 0 : -1;                       // roving tabindex
    document.getElementById(t.getAttribute('aria-controls')).hidden = !on;
  });
  tab.focus();
}

tabs.forEach((tab, i) => {
  tab.addEventListener('click', () => select(tab));
  tab.addEventListener('keydown', (e) => {
    let next;
    if (e.key === 'ArrowRight') next = tabs[(i + 1) % tabs.length];
    if (e.key === 'ArrowLeft')  next = tabs[(i - 1 + tabs.length) % tabs.length];
    if (e.key === 'Home')       next = tabs[0];
    if (e.key === 'End')        next = tabs[tabs.length - 1];
    if (next) { e.preventDefault(); select(next); }
  });
});

Notice what was needed: roles, an accessible name from content, state, a roving tabindex, four keys, and a relationship between each tab and its panel. This is the real cost of a custom widget, and it is why you should check whether a simpler design, such as a set of headings or an accordion, can do the job.

The key insight Copy the pattern, not just the markup. A widget that has the right roles but the wrong keys is worse than a plain one, because it promises behavior it does not deliver.

§4Common Mistakes

MistakeWhat HappensFix
Using role="menu" for site navigationScreen readers switch to an application mode that breaks normal navigationUse a list of links with a disclosure button for submenus
Implementing roles but not the keyboard modelThe widget announces correctly and cannot be operatedFollow the APG keyboard behavior for the pattern
Putting every tab in the Tab orderUsers must tab through every tab before reaching the panelUse a roving tabindex so only the active tab is a Tab stop
Practice
  1. Build the tabs example above, and test it with a screen reader. Does it announce the tab names, the selected state, and the panel?
  2. Read the APG page for an accordion. List the roles, states, and keys it specifies, and compare with an accordion you have built.
Key takeaways
  • Follow the ARIA Authoring Practices Guide for roles, states, and keyboard behavior when building custom widgets.
  • Use roving tabindex and arrow keys for tabs, and keep aria-selected in sync.
  • Avoid role="menu" for site navigation, and prefer simpler native patterns whenever they fit.
