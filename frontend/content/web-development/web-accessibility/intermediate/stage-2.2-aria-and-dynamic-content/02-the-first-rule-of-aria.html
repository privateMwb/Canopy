The First Rule of ARIA

The most useful advice about ARIA is about when not to use it. Bad ARIA is often worse than none, so there is a short set of rules to check before adding any attribute.

§1The Rules

The W3C's guidance on using ARIA reduces to five rules. The first is the one that matters most.

  1. If you can use a native HTML element or attribute with the semantics and behavior you need, do that instead.
  2. Do not change native semantics unless you really have to.
  3. All interactive ARIA controls must be usable with the keyboard.
  4. Do not use role="presentation" or aria-hidden="true" on a visible, focusable element.
  5. All interactive elements must have an accessible name.

Studies of large numbers of home pages (the annual WebAIM Million) have repeatedly found that pages using ARIA tend to have more detectable accessibility errors than pages without it. That does not mean ARIA is bad. It means it is often applied where HTML would have been enough, and misapplied when it is not.

§2Native Beats ARIA

Each of these pairs does the same job. The native version is shorter, more robust, and works everywhere.

<!-- Bad: ARIA rebuilds a button -->
<div role="button" tabindex="0" onclick="save()" onkeydown="...">Save</div>
<!-- Good -->
<button type="button" onclick="save()">Save</button>

<!-- Bad: ARIA rebuilds a heading and a link -->
<div role="heading" aria-level="2">Our story</div>
<span role="link" tabindex="0" onclick="go()">Read more</span>
<!-- Good -->
<h2>Our story</h2>
<a href="/story">Read more</a>

<!-- Bad: ARIA for a required field -->
<input aria-required="true">
<!-- Good: the native attribute also enables browser validation -->
<input required>

§3Do Not Fight the Native Semantics

Rule 2 stops you from making elements say something false. Overriding native semantics usually creates confusion.

<!-- Bad: changes what a heading is, breaking the outline -->
<h2 role="tab">Settings</h2>

<!-- Good: keep the heading, and put the interactive control inside it -->
<h2><button type="button" aria-expanded="false" aria-controls="settings-panel">Settings</button></h2>

When you do have to use ARIA, treat it as a full package: the role, the states, the accessible name, and the keyboard behavior. Leaving any of them out is how widgets end up announced as one thing and behaving as another.

No ARIA is better than bad ARIA Before adding any ARIA attribute, ask: is there an HTML element or attribute that already does this? If so, use it. If not, make sure you can deliver the role, name, state, and keyboard behavior as a set.

§4Common Mistakes

MistakeWhat HappensFix
Reaching for role="button" on a divExtra code, easy bugs, and missing behaviorUse button, or an a href for navigation
Overriding native roles, such as role="tab" on a headingThe outline and announcements become wrongKeep native semantics, or wrap them in an element with the new role
Interactive ARIA elements with no accessible nameAnnounced as "button" or "link" with no purposeGive every interactive element a name from content, aria-label, or aria-labelledby
Practice
  1. Search a codebase for role="button". For each hit, decide whether a native button could replace it, and rewrite one.
  2. Pick one ARIA attribute you use often, and look it up in the ARIA specification. Check that every use gives the matching role, name, state, and keyboard support.
Key takeaways
  • Use native HTML first. ARIA is for what HTML cannot express.
  • Do not override native semantics, and never hide visible, focusable elements from assistive technology.
  • Every interactive ARIA control needs a name and full keyboard support.
