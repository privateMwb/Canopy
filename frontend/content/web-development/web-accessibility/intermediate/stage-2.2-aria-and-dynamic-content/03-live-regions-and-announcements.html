Live Regions & Announcements

When content changes without a page load, such as a search that updates, a message that appears, or an item added to a cart, sighted users notice. Screen reader users only find out if you tell them.

§1How Live Regions Work

A live region is an area of the page that assistive technology watches. When its content changes, the screen reader announces the change without moving focus. This is what WCAG 4.1.3 Status Messages (Level AA) requires for updates that do not take focus.

Attribute or roleBehaviorUse for
role="status"Polite. Waits until the user is idleSaved confirmations, result counts, cart updates
role="alert"Assertive. Interrupts immediatelyErrors and urgent messages
aria-live="polite"Same politeness as status, on any elementCustom regions
aria-live="assertive"Interrupts speechRarely. Truly urgent only
role="log"Polite, for an ordered streamChat transcripts, activity feeds

Use polite for almost everything. Assertive announcements cut off whatever the user is hearing, which is jarring and should be saved for real emergencies.

§2Using a Live Region Correctly

The most common mistake is timing. Browsers and screen readers only announce changes to a live region that already exists. If you insert the region and its message in the same step, it may be silent. Put the empty container in the page from the start, then fill it with text.

<div id="status" role="status"></div>   <!-- present from page load, empty -->

<button id="add">Add to cart</button>

<script>
  const status = document.getElementById('status');
  document.getElementById('add').addEventListener('click', () => {
    addToCart();
    status.textContent = 'Blue backpack added to cart. 3 items in cart.';
  });
</script>
  • Keep messages short and specific. "3 results found" is better than a paragraph.
  • To repeat the same message, clear the region first and then set the text again, so the change is detected.
  • aria-atomic="true" makes the whole region read as one unit when only part of it changes.
  • Do not make every small update live. Constant announcements are exhausting.

§3Common Cases

A few situations call for a live region almost every time:

<!-- 1. Search results count after filtering -->
<p role="status" id="count">12 results</p>

<!-- 2. A form-level error on submit, assertive because it blocks progress -->
<div role="alert" id="form-error"></div>

<!-- 3. A toast that stays long enough to be read -->
<div role="status" id="toast"></div>
<script>
  toast.textContent = 'Settings saved';
  setTimeout(() => { toast.textContent = ''; }, 8000);   // not 2 seconds
</script>

Toasts that vanish quickly are a barrier even to sighted users with low reading speed or attention differences. Give people time, and consider an alternative that does not time out.

The key insight Think of a live region as speaking on the user's behalf: "something changed, and here is what you would otherwise see." If sighted users get feedback, announce an equivalent one.

§4Common Mistakes

MistakeWhat HappensFix
Creating the live region and its message at the same momentThe announcement is skipped by many screen readersRender the empty region first, then update its text
Marking too much as aria-live="assertive"Speech is interrupted constantlyUse polite for most messages, and alert only for urgent errors
Toasts that disappear in two secondsSlow readers, and screen reader users, miss the messageKeep messages visible long enough, and consider letting users dismiss them
Practice
  1. Add a role="status" message to a filtering interface that announces how many results match. Test it with a screen reader.
  2. Find a toast or inline notification in an app you use. Does it reach screen reader users? Write the live region markup that would.
Key takeaways
  • Live regions announce changes without moving focus. Use role="status" (polite) for most updates and role="alert" for urgent ones.
  • Render the region empty first, then change its text. Announcements fire on change.
  • Keep announcements brief, rare, and visible long enough to read.
