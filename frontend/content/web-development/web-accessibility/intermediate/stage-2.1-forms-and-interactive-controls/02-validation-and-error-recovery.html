Validation & Error Recovery

Everyone makes mistakes on forms. A good error tells the person that something went wrong, where, why, and how to fix it, and it reaches people who cannot see the page.

§1What WCAG Asks For

Several criteria shape error handling:

CriterionLevelRequirement
3.3.1 Error IdentificationADetected errors are identified and described in text
3.3.3 Error SuggestionAAIf a fix is known, suggest it
3.3.4 Error PreventionAAFor legal, financial, or data-changing submissions: allow reversal, checking, or confirmation
4.1.3 Status MessagesAAStatus messages are announced without moving focus

Notice what is missing: nothing says errors must be red. Color can help sighted users, but the message must exist as text and must be connected to the field.

§2Inline Errors

For each field with a problem, show a clear message near it, and connect it with aria-describedby while marking the field aria-invalid.

<label for="dob">Date of birth</label>
<input id="dob" aria-invalid="true" aria-describedby="dob-err dob-hint">
<p id="dob-hint">Use the format DD/MM/YYYY.</p>
<p id="dob-err" class="error">
  Error: enter a date in the format DD/MM/YYYY, for example 07/03/1990.
</p>
  • Say what is wrong and how to fix it. "Invalid input" helps no one.
  • Begin the message with a word like "Error" so it is clear in text, without relying on an icon or color.
  • Do not clear what the user typed. Keep their input so they can correct it.
  • Validate when the user finishes a field (on blur) or on submit. Validating on every keystroke interrupts typing and floods screen readers.

§3Error Summaries and Focus

On submit, several errors can occur at once. A common and effective pattern is an error summary at the top of the form that lists each problem with a link to its field, and receives focus so assistive technology announces it.

<div id="summary" role="alert" tabindex="-1" hidden>
  <h2>There are 2 problems with your form</h2>
  <ul>
    <li><a href="#email">Enter an email address</a></li>
    <li><a href="#dob">Enter a date of birth in the format DD/MM/YYYY</a></li>
  </ul>
</div>

<script>
  form.addEventListener('submit', (e) => {
    const errors = validate(form);
    if (errors.length) {
      e.preventDefault();
      renderSummary(errors);          // fill the list, then...
      summary.hidden = false;
      summary.focus();                // ...move focus so it is announced
    }
  });
</script>

Each summary link moves the user to the problem field. For high-stakes forms such as payments or legal agreements, also offer a review step before final submission, which satisfies 3.3.4.

The key insight Good error handling is a recovery path, not a rejection. Tell people what happened, where it is, and what to do, then keep their work intact.

§4Common Mistakes

MistakeWhat HappensFix
Showing errors only as a red borderUsers who cannot see color, or use a screen reader, miss the problemAdd text messages and link them with aria-describedby
Vague messages like "Invalid input"Users cannot tell what to fixState the problem and give an example or fix
Clearing the form after an errorUsers must retype everything and often give upPreserve entered values and focus the first problem
Practice
  1. Take a form you know and submit it empty. Rewrite each error message so it says what is wrong and how to fix it.
  2. Add an error summary with links to a form, and verify that a screen reader announces it on submit and that each link moves to the right field.
Key takeaways
  • Identify errors in text, suggest fixes, and add confirmation for legal, financial, or data-changing actions.
  • Connect errors to fields with aria-describedby and aria-invalid, and never use color alone.
  • On submit, move focus to an error summary with links to each field, and keep the user's input.
