Custom Controls & Native First

The most accessible control is the one the browser already built. Native elements bring roles, keyboard behavior, and states for free, and building your own means taking responsibility for all of it.

§1Why Native First

A native button, input, select, or details comes with a role, an accessible name, state, keyboard support, and focus handling that is tested across browsers and assistive technology. A custom div widget has none of that until you rebuild it.

Every custom control must answer five questions: role (what is it?), name (what is it called?), state (on or off, open or closed?), keyboard (how do I operate it?), and focus (can I reach it and see it?). Skip one and some users are locked out.

§2Style Native Controls Instead of Replacing Them

You can often change the look without losing the behavior. For checkboxes and radios, modern CSS goes a long way, and the accent-color property tints them to match your brand.

input[type="checkbox"], input[type="radio"] {
  accent-color: #1D4ED8;
  width: 1.5rem;
  height: 1.5rem;
}

When you need a fully custom look, the safest pattern keeps the real input in the page and styles the visual around it. The input stays focusable and operable, and the custom visuals follow its state.

<label class="switch">
  <input type="checkbox" role="switch">
  <span class="track" aria-hidden="true"></span>
  Email notifications
</label>

.switch input {
  position: absolute;
  opacity: 0;              /* hidden visually but still focusable */
  width: 1.5rem; height: 1.5rem;
}
.switch input:focus-visible + .track { outline: 3px solid #1D4ED8; }
.switch input:checked + .track      { background: #15803D; }

§3When You Must Build Your Own

Sometimes no native element fits, such as a rich combobox or a tree view. In that case follow the ARIA Authoring Practices Guide patterns, which document the expected roles, states, and keys for each widget. A custom toggle button, for instance, needs a role, a state, and key handling.

<button type="button" role="switch" aria-checked="false" id="dark-toggle">
  Dark mode
</button>

<script>
  const t = document.getElementById('dark-toggle');
  t.addEventListener('click', () => {
    const on = t.getAttribute('aria-checked') === 'true';
    t.setAttribute('aria-checked', String(!on));
    document.documentElement.classList.toggle('dark', !on);
  });
</script>

Using a real button as the base means Enter, Space, focus, and the name are already handled. You add only the state. The next stage covers ARIA in depth.

The key insight If you cannot name the role, name, state, keyboard behavior, and focus behavior of a custom control, it is not ready to ship. Prefer a native element, or a native element with a small addition.

§4Common Mistakes

MistakeWhat HappensFix
Replacing select or button with div widgetsLost keyboard support, roles, and screen reader behaviorUse native elements, and style them with CSS
Hiding the native input with display: noneThe control is removed from the Tab order and the accessibility treeHide it visually with opacity or clipping, and keep it focusable
Adding ARIA roles without behaviorA role promises behavior that does not existImplement the full keyboard and state pattern, or use native HTML
Practice
  1. Find a custom dropdown or toggle on a site you use. List which of role, name, state, keyboard, and focus it supports, and which are missing.
  2. Build an accessible toggle two ways: a styled native checkbox, and a button with role="switch". Compare how much code each needed.
Key takeaways
  • Native elements supply role, name, state, keyboard support, and focus for free. Use them first.
  • Style native controls instead of replacing them, and keep real inputs focusable.
  • When you must build custom, follow ARIA Authoring Practices patterns for roles, states, and keys.
