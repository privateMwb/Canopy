Accessibility in Design Systems

A design system is the place where accessibility pays off the most. Fix a button once, and every product that uses it improves. Neglect it, and the same bug ships to a hundred screens.

§1Accessibility as Part of the Component

If accessibility is optional in a component, many teams will skip it. The strongest design systems make the accessible way the default, and the inaccessible way hard or impossible. Aim to build four things into every component.

Built inExample
SemanticsA Button always renders a real button, never a div
NamesAn IconButton will not render without a required label
Keyboard and focusEvery component has a tested keyboard model and a visible focus style
Design tokensOnly approved color pairs that already meet contrast requirements are offered

§2APIs That Prevent Mistakes

Good component APIs make the right choice the easy one. A form field component, for example, can wire up the label, hint, and error relationships automatically, so no one has to remember for, id, and aria-describedby.

import { useId } from 'react';

export function TextField({ label, hint, error, ...props }) {
  const id = useId();
  const hintId = hint ? id + '-hint' : undefined;
  const errId = error ? id + '-err' : undefined;
  const describedBy = [hintId, errId].filter(Boolean).join(' ') || undefined;

  return (
    <div>
      <label htmlFor={id}>{label}</label>
      {hint && <p id={hintId}>{hint}</p>}
      <input id={id} aria-invalid={!!error} aria-describedby={describedBy} {...props} />
      {error && <p id={errId}>Error: {error}</p>}
    </div>
  );
}

// IconButton: the label is required, so there is no unnamed icon button
export function IconButton({ label, icon, ...props }) {
  return <button type="button" aria-label={label} {...props}>{icon}</button>;
}

Type checking and lint rules back this up: make label a required prop, and flag raw div onClick patterns in review.

§3Documentation and Testing

Components are used by people who are not accessibility experts, so document the details for them.

  • Accessibility notes on every component page: roles, keyboard behavior, focus management, and screen reader announcements.
  • Do and don't examples, such as how to write a good label or when to use a link instead of a button.
  • Automated checks in the component test suite and in Storybook, covering each state and variant.
  • Manual checks with a keyboard and a screen reader before a component ships, recorded in a checklist.
  • A changelog that notes accessibility fixes, so product teams know why to upgrade.

Accessible components do not guarantee accessible products. Teams can still combine them badly, with a skipped heading level, a confusing page layout, or unclear copy. Pair the system with guidance on page-level patterns, and test the assembled result.

The key insight A design system multiplies your effort. Each accessibility improvement to a shared component is inherited by every product, and each missing one is inherited too.

§4Common Mistakes

MistakeWhat HappensFix
Making accessibility props optionalUnnamed icon buttons and unlabeled fields ship by defaultRequire labels and other essentials in the component API
Documenting only the visualsDevelopers rebuild keyboard behavior wrongly or skip itDocument roles, keys, focus, and announcements for each component
Assuming accessible components make accessible pagesPage-level problems such as heading order and copy go unnoticedTest assembled pages, and provide page-level guidance
Practice
  1. Pick one component in a library you use. List its role, name source, keyboard model, and focus behavior, and note any gaps.
  2. Redesign the API of a form field or icon button so that the inaccessible usage is impossible or raises a warning.
Key takeaways
  • Build semantics, names, keyboard support, and approved colors into every component.
  • Design APIs where the accessible choice is the default, and required props prevent common mistakes.
  • Document and test each component for accessibility, and also test the pages built from them.
