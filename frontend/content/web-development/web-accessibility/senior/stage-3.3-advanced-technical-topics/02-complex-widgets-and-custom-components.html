Complex Widgets & Custom Components

Grids, trees, comboboxes, and rich text editors are the hardest things to make accessible. Doing it well takes a careful keyboard model, a deliberate focus strategy, and a lot of testing.

§1Composite Widgets and Focus Strategy

A composite widget is one Tab stop that contains many items you move between with arrow keys. There are two techniques for tracking the current item, and you must pick one deliberately.

TechniqueHow it worksTrade-offs
Roving tabindexReal DOM focus moves. The active item has tabindex="0", and the rest have -1Robust and simple. Items must be focusable, and scrolling follows focus
aria-activedescendantFocus stays on the container, and an attribute points at the "current" itemGood for comboboxes, where focus must stay in the text field. Requires careful support testing

Use roving tabindex by default. Use aria-activedescendant when focus has to remain on an input, as in a combobox.

§2Example: A Data Grid

A grid is an interactive table, where users move between cells and may edit them. It needs the right roles and a clear keyboard model.

<div role="grid" aria-label="Team members" aria-rowcount="200" aria-colcount="3">
  <div role="row" aria-rowindex="1">
    <div role="columnheader" aria-colindex="1">Name</div>
    <div role="columnheader" aria-colindex="2">Role</div>
    <div role="columnheader" aria-colindex="3">Start date</div>
  </div>
  <div role="row" aria-rowindex="2">
    <div role="gridcell" aria-colindex="1" tabindex="0">Maria Lopez</div>
    <div role="gridcell" aria-colindex="2" tabindex="-1">Engineer</div>
    <div role="gridcell" aria-colindex="3" tabindex="-1">2024-03-04</div>
  </div>
</div>
  • Arrow keys move between cells. Home and End go to the row's start or end. Ctrl+Home and Ctrl+End go to the first or last cell of the grid.
  • Page Up and Page Down move by a screen of rows.
  • Enter or F2 may start editing a cell, and Escape cancels the edit.
  • For virtualized grids, where only some rows exist in the DOM, set aria-rowcount and aria-rowindex so users know where they are in the full set.
  • If the grid is not truly interactive, a plain table is better, and simpler for everyone.

§3Trees, Comboboxes, and Rich Text

Other complex widgets share the same needs: a documented keyboard model, a focus strategy, and correct state.

WidgetKey points
Tree viewrole="tree" and treeitem, with aria-expanded and aria-level. Right arrow expands, left collapses, up and down move
ComboboxText input with a popup list. Focus stays in the input, aria-activedescendant marks the highlighted option, and aria-expanded and aria-controls track the popup
Toolbarrole="toolbar" with a roving tabindex, so the whole toolbar is one Tab stop
Rich text editorNeeds a labeled editing area, a keyboard-operable toolbar, announcements for formatting changes, and reliable undo

Rich text editors are the hardest of all. A contenteditable region behaves differently across browsers, and the editor must expose formatting, selection, and structure to assistive technology. For this reason, prefer a mature, well-tested editor framework that documents its accessibility, and test it with several screen readers rather than building your own.

Whatever you build, write the keyboard model before you code it, as a table, and review it with someone who uses a screen reader daily. That document becomes the specification, the test plan, and the user documentation.

The key insight The hard part of a complex widget is not the ARIA attributes. It is the focus strategy and keyboard model. Decide those first, write them down, and implement ARIA to match.

§4Common Mistakes

MistakeWhat HappensFix
Making every cell or item a Tab stopUsers must press Tab dozens of times to cross the widgetUse a roving tabindex so the whole widget is one Tab stop
Using role="grid" for a read-only tablePromises interaction that does not exist, and changes screen reader navigationUse a plain table unless cells are interactive
Building a rich text editor from scratchBrowser and assistive technology differences cause endless bugsAdopt a tested editor framework, and verify its accessibility
Practice
  1. Write the complete keyboard model, as a table, for a tree view or a data grid, before any code.
  2. Take a combobox or autocomplete you use, and check whether focus stays in the input and the highlighted option is exposed.
Key takeaways
  • Choose a focus strategy deliberately: roving tabindex by default, aria-activedescendant when focus must stay on an input.
  • Grids, trees, and comboboxes each need specific roles, states, and keyboard models. Document them first.
  • Prefer simpler native structures when the interaction is not truly needed, and adopt tested libraries for rich editing.
