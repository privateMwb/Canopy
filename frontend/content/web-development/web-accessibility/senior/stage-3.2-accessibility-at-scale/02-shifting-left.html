Shifting Left

The cost of an accessibility bug grows at every stage after it is created. Catching it in design costs a conversation, and catching it after launch costs a retrofit, a complaint, and a rushed release.

§1Why Earlier Is Cheaper

"Shifting left" means moving checks toward the start of the lifecycle. A missing heading hierarchy found on a wireframe is a one-minute fix. The same problem found in a production audit means changing templates, tests, and documentation, and perhaps a release.

StageAccessibility activity
Research and planningInclude disabled users in research, and add accessibility to requirements
DesignAnnotate headings, landmarks, focus order, and alt text. Check color contrast and target sizes
DevelopmentUse semantic HTML, linters, and accessible components from the design system
Pull requestReview with an accessibility checklist, and run automated tests
QA and releaseKeyboard and screen reader checks of acceptance criteria
ProductionMonitoring, feedback channel, and regular audits

§2Requirements and Design Reviews

The earliest lever is the requirement itself. If accessibility acceptance criteria are written into the story, they are discussed in planning, estimated, and tested.

User story: As a shopper, I can apply a discount code at checkout.

Acceptance criteria
- A visible label and instructions describe the discount code field.
- Errors are shown in text, linked to the field, and announced on submit.
- The whole flow works with the keyboard alone, with visible focus.
- Success and failure are announced to screen reader users without moving focus.
- Contrast and target size meet WCAG 2.2 AA.

In design, add accessibility annotations to the specs, such as which element is the h1, the tab order, the accessible name of each icon, and how errors appear. A short design review checklist catches layout and contrast issues before any code is written.

§3Code, Review, and Automation

In code, make the right thing easy. A linter catches common mistakes as you type, and tests stop regressions.

eslint.config.js: lint accessibility issues in JSX
import jsxA11y from 'eslint-plugin-jsx-a11y';

export default [
  jsxA11y.flatConfigs.recommended,
  { rules: { 'jsx-a11y/no-autofocus': 'error' } },
];

A component test with jest-axe
import { render } from '@testing-library/react';
import { axe, toHaveNoViolations } from 'jest-axe';
expect.extend(toHaveNoViolations);

test('Dialog has no detectable violations', async () => {
  const { container } = render(<Dialog open title="Delete?">...</Dialog>);
  expect(await axe(container)).toHaveNoViolations();
});
  • Add accessibility to the definition of done, so a story is not finished until its keyboard and screen reader checks pass.
  • Put a short accessibility checklist in the pull request template.
  • Run automated checks in CI, and fail the build on new violations.
  • Keep manual checks, such as a keyboard pass and a screen reader skim, for anything interactive.
The key insight Shifting left is not only about tools. It is about timing. The best accessibility check is a good question in a planning meeting: "How will someone use this without a mouse, or without seeing it?"

§4Common Mistakes

MistakeWhat HappensFix
Leaving accessibility testing until the endLate discoveries are expensive and tempt teams to ship with known defectsAdd criteria to stories, and check at every stage
Relying on a linter and nothing elseLinters find only static, code-level issuesCombine linting with component tests, reviews, and manual checks
A checklist nobody readsBox-ticking without thoughtKeep it short, specific to the change, and reviewed by someone who cares
Practice
  1. Rewrite a story from your backlog with five accessibility acceptance criteria.
  2. Add an accessibility linter and a component-level axe test to a small project, and see which issues each one finds.
Key takeaways
  • Moving accessibility earlier lowers the cost of fixes at every stage.
  • Write accessibility into requirements and acceptance criteria, annotate designs, and review them before code.
  • Use linting, component tests, CI checks, and a definition of done together.
