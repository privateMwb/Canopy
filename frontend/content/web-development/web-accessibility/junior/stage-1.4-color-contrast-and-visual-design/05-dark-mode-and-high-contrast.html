Dark Mode & High Contrast

People set up their devices for how they see best. Some prefer dark themes, some need strong contrast, and some run a mode that replaces your colors entirely. A robust page cooperates with all of them.

§1Supporting Dark Mode

Dark mode is a comfort and, for some people with light sensitivity, a necessity. The prefers-color-scheme media query reads the user's system setting. The easiest implementation is to define colors as variables and swap the values.

:root {
  color-scheme: light dark;   /* tells the browser to style form controls and scrollbars */
  --bg: #FFFFFF;
  --text: #1C1F26;
  --link: #1D4ED8;
}

@media (prefers-color-scheme: dark) {
  :root {
    --bg: #14171A;
    --text: #E8E6DF;
    --link: #93B4FF;
  }
}

body { background: var(--bg); color: var(--text); }
a { color: var(--link); }
  • Check contrast in both themes. Passing in light mode says nothing about dark.
  • Avoid pure white on pure black. It can cause glare and halation for some readers. Slightly softer values are often more comfortable.
  • Check images, logos, and icons. A dark logo can vanish on a dark background.

§2Forced Colors and High Contrast Modes

Some users, particularly on Windows, turn on a forced colors mode (often called high contrast). The system replaces your colors with a small palette, so text and backgrounds are guaranteed to contrast. This is a strong accessibility feature that your CSS should not fight.

  • Box shadows and some decorative effects are removed, so never use them as the only indicator of state or boundaries.
  • Use real borders and outlines for edges and focus, since they remain visible.
  • Use SVG icons with fill: currentColor so they pick up the forced text color.
  • Use system colors such as CanvasText, LinkText, and ButtonText when you must style inside this mode.
/* A button defined only by background color vanishes in forced colors */
.btn { background: #1D4ED8; border: 2px solid transparent; }

/* A transparent border turns into a visible one in forced colors mode */

@media (forced-colors: active) {
  .badge { border: 1px solid CanvasText; }
}

svg { fill: currentColor; }

Use forced-color-adjust: none very sparingly, and only for things like a color picker where the real color is the content.

§3Other User Preferences

The same idea extends to other media queries that read system settings. Honor them where they apply.

QueryUser preference
prefers-color-schemeLight or dark theme
prefers-reduced-motionLess animation
prefers-contrast: moreStronger contrast between colors
forced-colors: activeSystem-enforced palette

Test by turning these on in your operating system or DevTools rendering panel, which lets you emulate them without changing your settings.

The key insight Respect the user's choices. You do not need to design a separate high contrast theme for every system. You need markup and CSS that adapt gracefully when the user's settings take over.

§4Common Mistakes

MistakeWhat HappensFix
Checking contrast in light mode onlyDark theme text and links fail the ratioVerify every color pair in each theme
Boundaries and state shown only with box-shadow or background colorThey disappear in forced colors modeAdd real borders or outlines, and use currentColor for icons
Overriding forced colors widelyDefeats the system settings people rely onUse forced-color-adjust: none only where color is the content
Practice
  1. Add a dark theme to a small page with CSS variables, then verify the contrast of text, links, and borders in both themes.
  2. Emulate forced-colors: active in DevTools on a page you built. List what disappears, and fix one issue using borders or system colors.
Key takeaways
  • Use prefers-color-scheme and CSS variables for dark mode, and check contrast in each theme.
  • In forced colors mode, shadows and background-only cues vanish, so rely on real borders, outlines, and currentColor.
  • Read and respect user preferences rather than overriding them.
