Links, Buttons & Names

Every control on a page needs a name that tells people what it does. Choosing the right element, and writing a clear name for it, is one of the highest-impact habits in accessible development.

§1Links Go Places, Buttons Do Things

Links and buttons look similar but mean different things, and assistive technology announces them differently. Pick the element that matches the behavior.

ElementUse it toKeyboard
a href="..."Navigate to another page or locationEnter activates
buttonPerform an action: submit, open a dialog, toggle somethingEnter and Space activate
<!-- Navigation: a link -->
<a href="/pricing">See pricing</a>

<!-- Action: a button -->
<button type="button" id="open-menu">Open menu</button>

<!-- Avoid: a link that is really a button, or a div pretending -->
<a href="#" onclick="openMenu()">Open menu</a>
<div class="btn" onclick="openMenu()">Open menu</div>

§2The Accessible Name

Assistive technology identifies each control by its accessible name, which the browser computes. For most controls, the best source is simply visible text inside or beside it.

SourceExampleWhen to use
Content<button>Save</button>Best choice. Visible and reliable
Label element<label for="e">Email</label>For form fields
aria-labelledbyPoints to visible text elsewhereWhen the name is already on the page
aria-labelaria-label="Close"When no visible text exists, such as an icon button
<!-- Icon-only button: needs an invisible name -->
<button type="button" aria-label="Close dialog">
  <svg aria-hidden="true" focusable="false">...</svg>
</button>

<!-- Better still when space allows: visible text -->
<button type="button">
  <svg aria-hidden="true" focusable="false">...</svg>
  Close
</button>

The title attribute is a weak last resort. It is not reliably announced, and touch and keyboard users often never see it.

§3Names That Make Sense Out of Context

Screen reader users often pull up a list of all links on a page, which strips each one of its surroundings. A list that reads "Read more, Read more, Click here, Read more" is useless.

<!-- Bad: unclear out of context -->
<a href="/report">Click here</a> to download the annual report.
<a href="/post-1">Read more</a>

<!-- Good: self-describing -->
<a href="/report">Download the annual report (PDF, 2 MB)</a>

<!-- Keep the visible design, extend the name for assistive tech -->
<a href="/post-1">Read more<span class="visually-hidden"> about trail shoes</span></a>

Two more rules matter. The accessible name must contain the visible label (so a voice user who says "click Search" succeeds), and links that behave in surprising ways, such as opening a new tab or downloading a file, should say so in their text.

The key insight If a control's visible text and accessible name are the same, almost everything works. Problems start when they differ, or when the name is missing and a screen reader reads only "button".

§4Common Mistakes

MistakeWhat HappensFix
Using div or span as buttonsNo keyboard focus, role, or key supportUse a real button, or a href for navigation
Icon buttons with no nameScreen readers announce just "button" or "unlabeled"Add aria-label or visible text
Links like "Click here" or "Read more"Meaningless in a list of linksWrite names that describe the destination
Practice
  1. List every link and button on a page with a screen reader's links list or an extension. Rewrite any name that is unclear out of context.
  2. Find an icon-only button in a site you use and write the markup that would give it a correct accessible name.
Key takeaways
  • Use links to navigate and buttons to act, and let native elements supply the behavior.
  • The accessible name comes best from visible content. Use aria-label only when no visible text exists.
  • Link text should make sense on its own, and the accessible name should contain the visible label.
