Git Workflow & Preview Deployments

Branches, pull requests, and reviewing live previews.

§1Branches Are the Unit of Work

A simple, reliable workflow is to keep main always deployable and do all work on short-lived branches. Each branch becomes a pull request (PR) that teammates review before it merges.

git switch -c feature/task-filters     # new branch
git add -A && git commit -m "Add status filter to task list"
git push -u origin feature/task-filters   # opens the door for a PR

§2Preview Deployments

When the PR opens, the platform builds the branch and posts a unique URL. Reviewers can click it and use the real change, rather than imagining it from a diff. Each push to the branch updates the same preview.

  • Designers and product managers can approve visual changes without cloning the repo.
  • Bugs that only appear in a production build are caught before merge.
  • Previews use the Preview environment's variables, so keep them pointed at safe test data.

§3Good Pull Requests

Small PRs are reviewed faster and break less. Aim for one idea per PR, a title that says what changed, and a description that says *why* and how to verify it. Link the preview, and include a screenshot for visual changes.

HabitWhy it helps
Rebase or merge main before openingFewer surprise conflicts
Keep commits meaningfulHistory explains intent and eases debugging
Delete merged branchesA clean branch list stays navigable
Previews are cheap insurance A bug found on a preview URL costs minutes. The same bug found by customers in production costs a rollback, an incident, and trust.

§4Common Mistakes

MistakeWhat HappensFix
Committing directly to mainUntested code goes live and breaks everyone's baselineProtect main and require PRs
Huge, multi-topic pull requestsReviews are shallow and bugs slip throughSplit work into small, focused PRs
Pointing previews at production dataReviewers' clicks modify real recordsGive previews their own database and keys
Practice
  1. Create a branch, change a page, open a pull request, and review it using only its preview URL.
  2. Write a PR description that explains why the change was made and how a reviewer can verify it.
Key takeaways
  • Keep main deployable and do work on short-lived branches reviewed through pull requests.
  • Preview deployments let anyone test a change on a real URL before it merges.
  • Small, well-described PRs are reviewed faster and ship more safely.
