Threat Modeling Full-Stack Apps

Finding where the trust boundaries sit.

§1Think Like the Attacker Before They Do

Threat modeling is a structured way of asking four questions: What are we building? What can go wrong? What will we do about it? Did we do a good enough job? Doing it on a whiteboard during design costs far less than discovering the answers in an incident.

§2Map Assets and Trust Boundaries

Start with a data-flow diagram: the actors, components, data stores, and the arrows between them. Then draw trust boundaries where data crosses from a less-trusted to a more-trusted zone. Bugs cluster at those lines, because that's where input must be validated and identity verified.

Boundary in a full-stack appWhat crosses itMust be checked
Browser → server (requests, forms, Server Actions)Any user-controlled inputAuthentication, authorization, validation, CSRF
Third party → server (webhooks, OAuth callbacks)Claims made by another systemSignature, state, replay protection
Server → databaseQueries built from inputsParameterization, least-privilege credentials, tenant scoping
Server → third-party APIsSecrets and user dataSecret handling, allowlisted destinations, timeouts
Client bundle ← serverProps, env variables, payloadsNo secrets or excess data in what ships

§3Enumerate Threats with STRIDE

ThreatMeaningExample
SpoofingPretending to be someoneStolen session cookie, forged webhook
TamperingModifying dataChanging an id or price in a request
RepudiationDenying an actionNo audit log of an admin deletion
Information disclosureLeaking dataIDOR, verbose errors, secrets in the bundle
Denial of serviceExhausting resourcesUnbounded queries, no rate limits
Elevation of privilegeGaining unauthorised rightsMissing role check on a Server Action

For each boundary, walk through STRIDE and note the plausible threats. Then rank by likelihood and impact, decide to mitigate, accept, transfer, or avoid each one, and write down why.

Model the app you have A threat model is only useful if it matches reality. Update it when you add a payment provider, a file upload, a new tenant model, or an admin panel, because each adds assets and boundaries.

§4Common Mistakes

MistakeWhat HappensFix
Treating threat modeling as a one-off documentIt goes stale as the system changesRevisit it for every significant feature
Focusing only on external attackersInsider misuse and compromised dependencies go unconsideredInclude malicious users, insiders, and supply-chain risks
Listing threats without deciding what to doA long list that nobody acts onAssign each threat a mitigation or a documented acceptance
Practice
  1. Draw a data-flow diagram for an app you know, mark the trust boundaries, and list three STRIDE threats at its riskiest boundary.
  2. For each threat, pick a mitigation and name the test or control that would show it works.
Key takeaways
  • Threat modeling asks what we're building, what can go wrong, what we'll do, and whether it was enough.
  • Trust boundaries are where validation and authentication must happen.
  • Use STRIDE to enumerate threats, then prioritise and decide on mitigations explicitly.
