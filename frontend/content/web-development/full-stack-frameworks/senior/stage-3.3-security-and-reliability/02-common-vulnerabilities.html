Common Vulnerabilities

XSS, CSRF, SSRF, and injection in framework apps.

§1The Classics Still Apply

Frameworks remove some vulnerability classes by default, but not all. Knowing what the framework protects and what it leaves to you is the core skill here.

VulnerabilityWhat it isFramework helps byStill your job
XSSAttacker script runs in a victim's browserEscaping rendered text by defaultNever use dangerouslySetInnerHTML on untrusted HTML; sanitize it; set a CSP
CSRFA malicious site makes the browser send a state-changing requestServer Actions check origin headers; SameSite cookiesProtect custom route handlers that use cookie auth
SSRFServer is tricked into requesting internal URLsNothingAllowlist outbound destinations; block private IP ranges
InjectionInput is interpreted as code (SQL, shell)ORMs parameterize queriesAvoid raw SQL and shell calls built from input
IDOR / broken access controlAccess to others' records by changing an idNothingAuthorize every record access (lesson 2.1.3)
Open redirectA redirect target comes from user inputNothingAllowlist or validate redirect destinations

§2XSS and CSP

// Dangerous: untrusted HTML rendered as markup
<div dangerouslySetInnerHTML={{ __html: userBio }} />

// Safer: render text, or sanitize with a vetted library first
<div>{userBio}</div>
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(userBio) }} />

A Content Security Policy is a second layer: it tells the browser which script sources are allowed, so injected inline scripts fail to run. Use nonces for the scripts you trust, and treat CSP as defence in depth rather than a replacement for escaping.

§3SSRF in Practice

Any feature that fetches a URL on a user's behalf (link previews, image import, webhooks, PDF rendering) is an SSRF candidate. An attacker supplies http://169.254.169.254/ or an internal hostname to reach cloud metadata or private services.

const url = new URL(input);
if (url.protocol !== "https:") throw new Error("blocked");
const ip = await resolveToIp(url.hostname);          // resolve, then check the IP
if (isPrivateOrLinkLocal(ip)) throw new Error("blocked");
const res = await fetch(url, { redirect: "manual", signal: AbortSignal.timeout(5000) });

Re-check after redirects and DNS resolution, because an attacker can change what a name points to. Better still, run such fetches in an isolated network segment with no access to internal systems.

§4Server Actions Are Public Endpoints

Server Actions are reachable by direct HTTP, not just from your forms. Validate input, authenticate, and authorize inside every action. Don't assume that unreferenced actions are unreachable; they should be treated as endpoints regardless of where they're used in the UI.

Use the OWASP Top 10 as a checklist It names the most common web risks, such as broken access control, injection, and security misconfiguration. Walk through it for your own app. Broken access control tops the list for a reason.

§5Common Mistakes

MistakeWhat HappensFix
Rendering user HTML with dangerouslySetInnerHTML unsanitisedStored XSS that steals sessionsRender as text, or sanitize with a vetted library and add a CSP
Fetching user-supplied URLs from the server without restrictionsSSRF reaches internal services and cloud metadataAllowlist destinations, block private ranges, and limit redirects
Building SQL with string concatenationSQL injectionUse parameterized queries or ORM APIs
Practice
  1. Audit a project for dangerouslySetInnerHTML, raw SQL, user-controlled redirects, and server-side fetch of user URLs, and list findings.
  2. Write the validation function for a 'fetch this URL' feature that defends against SSRF, and list what it can't protect against.
Key takeaways
  • Frameworks mitigate XSS and SQL injection by default, but not SSRF, IDOR, or open redirects.
  • Treat Server Actions as public endpoints, and defend in depth with sanitization and CSP.
  • Walk through the OWASP Top 10 against your own application.
