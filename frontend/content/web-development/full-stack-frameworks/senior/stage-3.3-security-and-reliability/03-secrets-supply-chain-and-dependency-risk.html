Secrets, Supply Chain & Dependency Risk

Locking down what you ship.

§1Most of Your Code Isn't Yours

A typical full-stack project depends on hundreds or thousands of packages, directly and transitively. Each is code you run with your app's privileges, so a compromised or vulnerable dependency can read your environment variables, your database, and your users' data. Recent years have seen malicious versions published to popular registries, so this risk is concrete.

§2Controlling What You Install

  • Commit the lockfile and install with npm ci in CI, so builds use exactly the reviewed versions.
  • Pin and review updates instead of auto-merging them blindly. Consider a delay of a few days on brand-new releases, since malicious versions are often caught quickly.
  • Run an audit (npm audit, Dependabot, Renovate, or a scanning service) and triage by actual exploitability in your context.
  • Be wary of install scripts. Dependencies can run code at install time; consider --ignore-scripts where feasible, or an allowlist.
  • Guard against typosquatting and dependency confusion: verify package names and use scoped, private-registry configuration for internal packages.
  • Prefer fewer, well-maintained dependencies. Replace a tiny package with ten lines of your own code when sensible.
npm ci                      # install exactly what the lockfile says
npm audit --omit=dev        # known vulnerabilities in production deps
npm ls --all | wc -l        # how big is the tree, really?

§3Protecting Secrets

  • Least privilege: each environment and service gets its own narrowly scoped keys, such as a read-only database role for the reporting job.
  • Keep secrets out of git and scan for them: pre-commit hooks and CI scanners such as gitleaks catch leaks early.
  • Rotate on a schedule and on suspicion. A secret that has appeared in a log, a chat, or a commit is burned.
  • Use a secrets manager (the platform's, or Vault, AWS Secrets Manager, and similar) rather than sharing .env files.
  • Restrict CI: don't expose production secrets to pull requests from forks, and pin third-party CI actions to a commit hash.

§4Know What You Ship

Generate a software bill of materials (SBOM) so you can answer 'are we affected?' within minutes when a new vulnerability is announced. Enable alerts on your dependency graph, and have a documented process for emergency patching.

Your build pipeline is a target Attackers increasingly compromise CI systems, build scripts, and publishing tokens, because those reach everything downstream. Protect the pipeline with the same rigour as production.

§5Common Mistakes

MistakeWhat HappensFix
Updating all dependencies automatically without reviewA malicious or broken release flows straight to productionReview updates, use lockfiles, and delay brand-new versions
Using one powerful key for every environmentA leak anywhere compromises everythingIssue separate, least-privilege credentials
Deleting a leaked secret from git and moving onIt stays in history, forks, and cachesRotate the secret immediately
Practice
  1. Run an audit on a real project, triage the findings by whether the vulnerable code path is reachable, and write down what you would fix first.
  2. Add secret scanning to a repository's CI and test it with a fake key.
Key takeaways
  • Dependencies run with your app's privileges, so install, update, and audit them deliberately.
  • Use least-privilege, separate, rotatable secrets kept out of git and scanned for leaks.
  • Secure your CI and build pipeline, and keep an inventory so you can react quickly to new advisories.
