Resilience & Failure Modes

Timeouts, retries, and graceful degradation.

§1Everything Fails Eventually

Your app depends on databases, APIs, DNS, networks, and platform services, and every one of them will slow down or fail at some point. Resilience is designing so that the failure of a part degrades the experience instead of destroying it.

§2Timeouts, Retries, and Backoff

  • Always set timeouts on outbound calls. Without one, a hung dependency ties up your capacity indefinitely.
  • Retry only safe operations: idempotent reads, or writes protected by idempotency keys.
  • Use exponential backoff with jitter, so that thousands of clients don't retry in lockstep and overwhelm a recovering service.
  • Cap total retry time, since the user won't wait forever, and your platform has duration limits.
async function withRetry<T>(fn: () => Promise<T>, attempts = 3) {
  for (let i = 0; ; i++) {
    try { return await fn(); }
    catch (err) {
      if (i >= attempts - 1 || !isRetryable(err)) throw err;
      const delay = Math.min(2000, 200 * 2 ** i) * (0.5 + Math.random());   // backoff + jitter
      await new Promise((r) => setTimeout(r, delay));
    }
  }
}
// ...and every fetch gets: signal: AbortSignal.timeout(3000)

§3Protecting the System

PatternWhat it doesExample
Circuit breakerStops calling a failing dependency for a whileAfter repeated payment-API failures, fail fast for 30 seconds
BulkheadIsolates resources so one failure can't consume them allSeparate connection pools for reporting and checkout
Load sheddingRejects excess work to protect core functionsReturn 503 for low-priority endpoints under load
Graceful degradationServes a reduced experienceShow cached recommendations when the recommender is down
Fallbacks and defaultsSubstitutes a safe valueUse the last known exchange rate

Retries without limits can make outages worse. If every layer retries three times, one failure becomes dozens of calls (a retry storm). Retry at one layer, and combine retries with circuit breakers.

§4Practising Failure

Resilience that hasn't been tested is a hypothesis. Rehearse: kill a dependency in staging, inject latency, restore a backup into a clean environment, and run game days. Define SLOs, keep runbooks for common failures, and write blameless postmortems after incidents, focusing on how the system allowed the failure rather than who caused it.

Decide what 'degraded' means in advance For each dependency, decide ahead of time what the app does when it's down: fail, show cached data, queue the work, or hide the feature. Making that choice during an outage is the worst time to do it.

§5Common Mistakes

MistakeWhat HappensFix
Outbound calls with no timeoutHung requests exhaust workers and take everything downSet explicit timeouts on every call
Retrying immediately and indefinitelyA retry storm that prevents the dependency recoveringUse capped exponential backoff with jitter plus a circuit breaker
Never testing failure scenarios or restoresBackups and fallbacks fail when finally neededRun regular failure drills and restore tests
Practice
  1. Choose a third-party dependency in an app and write down, for a total outage, what the user sees and what you'd change to degrade more gracefully.
  2. Add a timeout, a bounded retry with jitter, and a fallback to one outbound call, then test it by simulating failures.
Key takeaways
  • Always set timeouts, and retry only safe operations with capped, jittered backoff.
  • Circuit breakers, bulkheads, and graceful degradation keep partial failures contained.
  • Rehearse failures, define SLOs and runbooks, and learn from blameless postmortems.
