Queues, Events & Eventual Consistency

Designing workflows that tolerate delay.

§1Don't Do It All Inside the Request

A checkout that charges a card, updates inventory, sends an email, and notifies a warehouse inside one request is slow and fragile: any step can fail after others succeeded. Asynchronous designs break the work into steps connected by queues and events, trading immediacy for resilience.

StyleExampleGood forCost
SynchronousCall the payment API, wait for the resultSteps whose result the user needs nowLatency and cascading failures
Queue (work)Enqueue 'send receipt'; a worker does itTasks needing retries and rate controlDelay; need for monitoring

§2Eventual Consistency

When data is updated through asynchronous steps, different parts of the system briefly disagree. The order is saved but the receipt hasn't been sent, or the search index lags the database. This is eventual consistency: given time and no new changes, everything converges. Your job is to design the UI and logic so the delay is acceptable and visible, for example showing 'Processing…' instead of pretending the work is complete.

§3The Dual-Write Problem and the Outbox

If you save to the database and then publish an event, a crash between the two leaves them inconsistent: data saved, event lost. The transactional outbox pattern fixes this by writing the event into an outbox table in the same transaction as the data. A separate process reads the outbox and publishes reliably.

await db.$transaction(async (tx) => {
  const order = await tx.order.create({ data });
  await tx.outbox.create({
    data: { type: "OrderPlaced", payload: { orderId: order.id }, idempotencyKey: order.id },
  });
});
// A relay job polls `outbox`, publishes to the queue, and marks rows as sent

§4Reliability Rules for Async Work

  • At-least-once delivery is the realistic default, so every consumer must be idempotent.
  • Retries with exponential backoff and jitter, and a limit on attempts.
  • Dead-letter queue for messages that keep failing, so they can be inspected rather than lost or retried forever.
  • Compensating actions (sagas) for multi-step workflows: if step 3 fails, run actions that undo steps 1 and 2.
  • Visibility: metrics on queue depth, age of the oldest message, and failure rate, with alerts.
Exactly-once is mostly a myth Networks fail in ways that make exactly-once delivery impractical. The robust approach is at-least-once delivery combined with idempotent handlers, which gives exactly-once *effects*.

Practice
  1. Design an order-placement flow with a queue for email and inventory, showing where idempotency keys and the outbox are used.
  2. Describe what the user sees at each step while eventual consistency is in play, and how the UI communicates it.
Key takeaways
  • Queues and events decouple work from the request, trading immediacy for resilience.
  • Eventual consistency is a design constraint to expose in the UI, not hide.
  • Use the outbox, idempotent consumers, bounded retries, and dead-letter queues for reliable async workflows.
