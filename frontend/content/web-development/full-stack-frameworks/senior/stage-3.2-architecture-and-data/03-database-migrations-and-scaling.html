Database Migrations & Scaling

Schema changes without downtime.

§1Schema Changes Are Deployments Too

A migration alters a live database that code is actively using. During a rolling deploy, old and new application versions run at the same time against the same schema. So every migration must be compatible with both versions, and some operations can lock a table and take the app down.

§2Expand, Migrate, Contract

The safe pattern splits one risky change into several backwards-compatible steps. Example: renaming name to full_name.

  1. Expand: add the new full_name column (nullable). Old code keeps working.
  2. Dual write: deploy code that writes both columns and reads the new one with a fallback.
  3. Backfill: copy existing data to the new column in small batches.
  4. Switch: deploy code that uses only full_name.
  5. Contract: drop name once nothing reads it, and after you're sure you won't roll back.
-- Step 1: safe, additive
ALTER TABLE users ADD COLUMN full_name text;

-- Step 3: backfill in batches to avoid long locks
UPDATE users SET full_name = name
 WHERE id IN (SELECT id FROM users WHERE full_name IS NULL LIMIT 5000);

-- Step 5: only after all code stops using it
ALTER TABLE users DROP COLUMN name;

§3Operations That Hurt

OperationRiskSafer approach
Add a column with a volatile default (older Postgres)Rewrites the whole table under a lockAdd nullable, backfill, then add default and constraint
Create an indexBlocks writes while it buildsCREATE INDEX CONCURRENTLY in Postgres
Add NOT NULL or a foreign keyFull-table validation under lockAdd as NOT VALID, then VALIDATE separately
Rename or drop a columnBreaks running code instantlyUse expand and contract
Change a column typeRewrite plus code mismatchAdd a new column, migrate data, swap

Set a lock_timeout on migrations so one that can't acquire a lock fails fast rather than queuing behind a long transaction and blocking everyone behind it. Behaviour of specific operations differs by database and version, so check yours.

§4Scaling the Database

As load grows, the usual ladder is: fix queries and indexes first, add connection pooling, scale the instance vertically, add read replicas for read-heavy traffic (accepting replication lag), cache hot reads, then partition or shard very large tables. Each step adds complexity, so climb only as far as measurements demand.

Never couple a migration to a deploy you can't undo Application code can be rolled back in seconds, but a dropped column can't. Keep destructive steps separate, delayed, and deliberate, so rollbacks stay possible.

§5Common Mistakes

MistakeWhat HappensFix
Renaming or dropping a column in one deployOld instances crash during the rolloutUse expand, migrate, contract over several deploys
Building a large index without CONCURRENTLYWrites block and the app stallsUse the online index-build option
Running untested migrations on production firstSurprises like long locks appear on real data volumesRehearse on a production-sized copy, with timing
Practice
  1. Plan the expand-migrate-contract sequence for splitting a name column into first_name and last_name, listing what each deploy contains.
  2. Time an index build with and without CONCURRENTLY on a large test table and observe the effect on concurrent writes.
Key takeaways
  • Old and new code run together during deploys, so migrations must be backwards compatible.
  • Use expand, migrate, contract, and avoid locking operations on hot tables.
  • Scale the database stepwise, from query tuning through pooling and replicas, only as data demands.
