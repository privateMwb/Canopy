Observability

Logs, traces, metrics, and alerts for full-stack apps.

§1Seeing Inside a Running System

Monitoring tells you something is wrong; observability lets you work out *why*, including for problems you didn't predict. In a full-stack app one user action crosses the browser, edge, server components, database, and third-party APIs, so you need telemetry that follows it across all of them.

SignalAnswersExample
LogsWhat happened, in detailpayment_failed with order id and error code
MetricsHow much, how often, how fastp95 latency, error rate, queue depth
TracesWhere time went across services in one requestA span tree: handler → database → payment API
Errors / exceptionsWhat broke, with a stack trace and contextSentry-style grouped exceptions

§2Structured Logs and Correlation

Log as structured JSON with consistent fields so you can filter and aggregate. Include a request or trace id in every line so that all logs for one request can be found together. Never log secrets, tokens, or unnecessary personal data.

logger.info({
  event: "checkout_completed",
  requestId, tenantId, userId,          // correlation and context
  orderId, amountCents, durationMs,
});

§3Tracing with OpenTelemetry

OpenTelemetry is the vendor-neutral standard for traces, metrics, and logs. Next.js supports it through an instrumentation.ts hook, and many frameworks have equivalents. Auto-instrumentation records spans for incoming requests, fetch, and database calls, and you add custom spans around important business steps. Propagate the trace context to downstream services so the trace stays connected.

§4Alerting That Humans Can Live With

  • Alert on symptoms users feel (error rate, latency, failed checkouts), not on every internal cause.
  • Define SLOs, such as 99.9% of requests succeeding under 500 ms, and alert on burn rate of the error budget.
  • Every alert should be actionable and link to a runbook; otherwise delete or tune it.
  • Watch the frontend too: real-user Web Vitals and client errors.
  • Add synthetic checks for critical journeys such as login and checkout.
Alert fatigue kills on-call If alerts fire constantly and are usually ignorable, people stop responding, and the one real incident is missed. Fewer, higher-quality alerts beat comprehensive noisy ones.

§5Common Mistakes

MistakeWhat HappensFix
Unstructured console.log stringsImpossible to filter or aggregate at scaleEmit structured logs with consistent fields and ids
Logging secrets or full personal dataA logging breach becomes a data breachRedact sensitive fields and log identifiers instead
Alerting on CPU spikes and other causesNoise that doesn't reflect user impactAlert on user-facing symptoms and SLO burn
Practice
  1. Add a request id to every log line in a project and trace a single request through your logs.
  2. Define two SLOs for your app (availability and latency) and write the alert conditions that would protect them.
Key takeaways
  • Observability combines logs, metrics, traces, and error tracking, linked by correlation ids.
  • Use structured logs, OpenTelemetry tracing, and careful redaction of sensitive data.
  • Alert on symptoms and SLO burn, and keep every alert actionable.
