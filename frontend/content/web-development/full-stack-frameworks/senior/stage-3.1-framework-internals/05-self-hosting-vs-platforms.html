Self-Hosting vs. Platforms

What a managed platform does that you would have to rebuild.

§1What a Platform Does for You

next start runs your app on a single Node server. A managed platform such as Vercel does much more, and some framework features assume it. When you self-host you must supply the missing pieces yourself.

CapabilityOn a managed platformWhen self-hosting
Global CDN and static assetsAutomaticPut a CDN in front; configure cache headers
Serverless scalingPer-request, scales to zeroRun and autoscale containers or VMs yourself
Shared data cache / ISR across instancesBuilt inConfigure a shared cache handler (Redis, object storage), or each instance caches separately
Image optimizationManaged and cachedRuns in your server; needs CPU and caching
Preview deploymentsPer branch, automaticBuild your own pipeline
TLS, DDoS protection, WAFIncludedAdd a proxy or provider (Cloudflare, load balancer)
Zero-downtime deploys and rollbacksImmutable deploymentsBlue/green or rolling deploys; keep old assets available

§2Self-Hosting Patterns

  • Container: build a Docker image (Next.js supports a standalone output that bundles only what's needed) and run it on a container platform or Kubernetes.
  • Node process on a VM: simplest, with a process manager and reverse proxy; you handle scaling and updates.
  • Static export: if the site needs no server features, export static files and host them anywhere, but you lose server rendering, actions, and route handlers.
  • Other adapters: Cloudflare, Netlify, AWS, and others run the framework via adapters with differing feature support.
# next.config.ts → output: "standalone"
docker build -t acme-web .
docker run -p 3000:3000 -e DATABASE_URL=... acme-web

§3Multi-Instance Gotchas

The classic self-hosting bug is running several instances behind a load balancer, each with its own in-memory cache and local files. A revalidation reaches only one instance, so users see inconsistent content depending on which they hit. Fix this with a shared cache store, consistent build ids, and keeping prior deployment assets available during rollouts so open browser tabs don't request deleted chunks.

It's a build-versus-buy decision Platforms charge for convenience, and self-hosting charges in engineering time and on-call burden. The right answer depends on traffic, team skill, compliance needs, and costs. Decide with numbers, as lesson 3.4.2 explores.

§4Common Mistakes

MistakeWhat HappensFix
Running multiple instances with per-instance cachesInconsistent content and invalidation missesUse a shared cache handler
Deleting old build assets immediately on deployUsers with open tabs hit 404s for old chunksKeep previous assets for a grace period
Assuming every framework feature works on every hostFeatures break or silently degrade after migrationCheck the adapter's supported-features list before choosing
Practice
  1. Build a Docker image of a Next.js app with standalone output and run it locally with environment variables.
  2. List ten things Vercel provides that your container deployment would need, and note who would own each.
Key takeaways
  • Managed platforms bundle CDN, scaling, caching, previews, and security that self-hosting must replace.
  • Multi-instance deployments need a shared cache and careful handling of old assets.
  • Choose between platform and self-hosting by weighing cost, control, and operational burden.
