Routing, Rendering & the RSC Payload

How the server and client exchange UI.

§1What the Server Actually Sends

When a React Server Component tree renders, the server doesn't send finished HTML only. It produces the RSC payload: a compact, streamable description of the rendered tree. Server Components appear as already-rendered output, Client Components appear as references to JavaScript chunks plus their serialized props, and Suspense boundaries appear as placeholders that fill in later.

# A simplified, illustrative shape of an RSC payload
0:["$","div",null,{"children":[
  ["$","h1",null,{"children":"Products"}],
  ["$","$L1",null,{"productId":42}],      # $L1 = reference to a client component chunk
  ["$","$Sa",null,{"fallback":"Loading"}] # Suspense boundary, content streams later
]}]
1:I["chunk-abc.js",["LikeButton"]]        # import instruction for client code

The format is an implementation detail and changes between versions, so don't depend on it. The shape of the idea is what matters.

§2Two Paths to the Screen

MomentWhat is sentWhy
First loadHTML (for fast paint) plus the RSC payload (for hydration)HTML shows content immediately; the payload lets React take over without re-fetching
Client-side navigationOnly the RSC payload for the new routeReact merges it into the existing tree, preserving layouts and client state

On navigation the browser requests the next route's payload (often prefetched), and React reconciles it into the live page. Shared layouts aren't re-sent or re-rendered, which is why they keep state.

§3Hydration and Its Costs

Hydration attaches event handlers and state to the server-rendered HTML for Client Components. Only client boundaries hydrate, not the whole page, which is the performance win of Server Components. Costs remain: client JavaScript still downloads and executes, and props crossing the boundary are serialized into the payload, so passing a huge object as a prop literally increases page weight.

// Don't pass more than the client component needs
<ProductCard product={entireDatabaseRow} />              // serializes everything
<ProductCard name={p.name} price={p.price} />           // serializes only what's used
Props are part of your payload Everything you pass from a Server Component to a Client Component is serialized and sent to every visitor. That includes accidental fields. Pass narrow, purpose-built props, and never pass secrets.

§4Common Mistakes

MistakeWhat HappensFix
Passing entire database records to client componentsLarger payloads and leaked internal fieldsSelect and pass only the needed fields
Assuming hydration errors are randomServer and client rendered different output (time, random, locale)Make rendering deterministic or defer the difference to an effect
Parsing or relying on the payload formatBreaks on framework upgradesTreat it as an internal protocol
Practice
  1. Open the network tab during a client-side navigation and identify the request that carries the next route's payload. What does it contain?
  2. Reduce a Server-to-Client prop from a whole object to three fields and compare page weight.
Key takeaways
  • The RSC payload describes the rendered tree, with references to client component chunks.
  • First load sends HTML plus payload; later navigations send only the payload.
  • Only client boundaries hydrate, and props across them are serialized, so keep them lean.
