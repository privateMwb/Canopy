Caching Internals

How each cache layer decides what is fresh.

§1How a Cache Decides

Lesson 2.3.2 mapped the cache layers. Here we look at how each one decides whether its stored copy is still valid, because staleness bugs come from misunderstanding that decision. Details vary by version, so use this as a mental model and confirm specifics in the docs and in your own build output.

§3Stale-While-Revalidate in Practice

Most layers use stale-while-revalidate: when an entry expires, the next request is served the old copy immediately while a regeneration runs in the background. The following request gets the fresh version. So after a change, one unlucky visitor may still see old content, and a rarely visited page may stay stale for a long time, because nothing triggered the refresh.

  1. Request 1 arrives after expiry: the stale copy is returned and a background regeneration starts.
  2. Regeneration succeeds and replaces the entry.
  3. Request 2 receives the fresh copy.
  4. If regeneration fails, the old entry normally stays, so an upstream outage can mean serving old content longer than intended.

§4Reading the Evidence

Don't guess whether a response came from cache. Check headers and logs.

curl -sI https://acme.com/blog | grep -iE 'cache|age|x-vercel|x-nextjs'
# x-nextjs-cache: HIT | MISS | STALE         (framework-level, where exposed)
# age: 120                                    (seconds in a shared cache)
# cache-control: s-maxage=60, stale-while-revalidate

A STALE value means a regeneration was just triggered; a HIT with a growing age means the CDN is serving without involving your origin. Header names vary by host, so check what yours emits.

Keys decide correctness A cache returns whatever is stored under the key. If the key omits something that changes the output (a user id, a locale, a feature flag), different users or states collide and one sees another's content. Always ask: what does this output depend on?

§5Common Mistakes

MistakeWhat HappensFix
Caching output that depends on the user without keying on the userOne person's data is served to anotherDon't cache personalised output, or include the identity in the key and scope
Expecting rarely visited pages to refresh automaticallyThey stay stale because nothing triggers regenerationUse on-demand invalidation or scheduled revalidation
Ignoring failed regenerationsStale data is served silently during an upstream outageAlert on regeneration errors and set sensible maximum staleness
Practice
  1. Use curl -I repeatedly on a revalidated route and record the cache headers across expiry. Can you observe the MISS, HIT, and STALE transitions?
  2. For one cached function in an app you know, list every input its output depends on and check whether each is part of the key.
Key takeaways
  • Every cache decides freshness from a key, a lifetime, and invalidation signals.
  • Stale-while-revalidate serves old content once while regenerating, and pages with no traffic never refresh.
  • Verify behaviour with response headers rather than assumptions, and make sure cache keys include everything the output depends on.
