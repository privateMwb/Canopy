Protecting Routes & Data

Middleware and server-side checks.

§1Authentication Is Not Enough

A route being hidden from the navigation is not protection. Every request must be checked on the server. There are three layers, and a secure app uses more than one.

LayerGood atLimit
Middleware / proxyFast, broad redirects (send logged-out users to /login)Runs before rendering; shouldn't be your only check
Page / layout checkGating whole sectionsLayouts don't re-run on every navigation, so don't rely on them alone
Data layer checkAuthorizing each record accessMust be applied consistently

§2Check Close to the Data

The safest pattern is a data access function that authorizes every read and write. Whatever calls it, a page, an action, or an API route, gets the same protection, so a missed check in one place can't expose data.

// lib/data/tasks.ts
import "server-only";

export async function getTask(id: string) {
  const user = await requireUser();                    // throws or redirects if signed out
  const task = await db.task.findUnique({ where: { id } });
  if (!task || task.ownerId !== user.id) notFound();   // authorize the record
  return task;
}

// Server Action: authorize again, it is a public endpoint
export async function deleteTask(id: string) {
  const user = await requireUser();
  await db.task.deleteMany({ where: { id, ownerId: user.id } });
}

§3Middleware as a First Gate

Middleware (called proxy in the newest Next.js versions) is great for cheap, early redirects, such as sending visitors without a session cookie to the login page. Treat it as a convenience layer: a 2025 Next.js middleware vulnerability showed that relying on middleware as the only barrier is risky. Always re-check in the data layer.

IDOR: the most common authorization bug Insecure direct object reference means a user changes an id in a URL or request and reads someone else's record. The fix is always the same: verify ownership on the server for every record access.

§4Common Mistakes

MistakeWhat HappensFix
Hiding links instead of enforcing accessAnyone can still request the URL or call the actionCheck permissions on the server for every request
Protecting only the page, not the action or APIData can still be read or changed via direct callsPut checks in shared data-access functions
Trusting an id from the client for ownershipUsers edit or read other people's dataAlways include the user's id in the query or verify ownership
Practice
  1. Add middleware that redirects signed-out users from /dashboard to /login, then add a second, independent check in the data layer.
  2. Try to read or delete another user's record by changing an id. Make your code return not-found or forbidden.
Key takeaways
  • Hiding UI isn't security; every request needs a server-side check.
  • Centralise authorization in data-access functions so every caller is protected.
  • Middleware is a good first gate, but never the only one.
