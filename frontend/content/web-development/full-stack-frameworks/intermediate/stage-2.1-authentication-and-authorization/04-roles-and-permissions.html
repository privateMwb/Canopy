Roles & Permissions

Modeling access control.

§1Authentication vs. Authorization

Authentication answers 'who are you?'. Authorization answers 'what are you allowed to do?'. This lesson is about the second question, and about modelling it so it stays manageable as the app grows.

§2Common Models

ModelHow it worksGood for
Roles (RBAC)Users have roles (admin, editor); roles grant permissionsMost apps; simple and understandable
Attributes (ABAC)Rules over properties (department, record owner, time)Complex, context-dependent policies
Relationships (ReBAC)Access follows relationships (member of team, owner of folder)Collaboration apps such as docs and projects

Start with roles. Add ownership checks ('only the author can edit') on top. Move to heavier models only when real requirements demand it.

§3Implementing Permissions

Check permissions, not role names, in code. Roles map to permissions in one central place, so changing what an editor can do is a single edit.

const permissions = {
  admin:  ["post:create", "post:edit:any", "post:delete:any", "user:manage"],
  editor: ["post:create", "post:edit:own"],
  viewer: [],
} as const;

export function can(user: User, action: string, post?: Post) {
  const perms = permissions[user.role] ?? [];
  if (perms.includes(action as never)) return true;
  if (action === "post:edit" && post?.authorId === user.id)
    return perms.includes("post:edit:own");
  return false;
}

// Usage, in an action or data function
if (!can(user, "post:delete", post)) throw new ForbiddenError();

§4Multi-Tenant Considerations

In apps where users belong to organizations, a role usually applies within a tenant: someone may be an admin of one workspace and a viewer in another. Store roles on the membership, not on the user, and always scope queries by tenant.

Default to deny If no rule explicitly allows an action, refuse it. New features then start locked down instead of accidentally open.

§5Common Mistakes

MistakeWhat HappensFix
Scattering if (user.role === 'admin') through the codeRules become inconsistent and impossible to auditCentralise in a can() function or policy module
Putting the role only in the client UIUsers can call the endpoint directlyEnforce on the server for each action
Storing a global role in a multi-tenant appA user gets admin rights in organizations where they shouldn'tAttach roles to the membership and scope by tenant
Practice
  1. Define three roles and a permission map for a blog app, then write can() and use it in a Server Action.
  2. Write a test table listing each role and action with the expected allow or deny result.
Key takeaways
  • Authentication identifies the user; authorization decides what they can do.
  • Start with roles plus ownership checks, and centralise rules in one place.
  • Default to deny, enforce on the server, and scope roles to the tenant when relevant.
