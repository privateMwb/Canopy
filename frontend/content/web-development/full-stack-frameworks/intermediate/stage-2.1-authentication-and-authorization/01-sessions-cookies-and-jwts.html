Sessions, Cookies & JWTs

How logins actually persist.

§1Why Logins Need State

HTTP is stateless, so once a user signs in the server has to recognise them on every later request. There are two main designs: the server remembers the user (a session), or the browser carries a signed proof (a token). Both ride on a cookie or a header.

§2Cookie-Backed Sessions

On login the server creates a random session id, stores the session data (user id, expiry) in a database or cache such as Redis, and sends the id to the browser in a cookie. Each request returns the cookie, and the server looks the session up. Revoking access is easy: delete the record.

import { cookies } from "next/headers";

(await cookies()).set("session", sessionId, {
  httpOnly: true,       // JavaScript cannot read it (blocks XSS theft)
  secure: true,         // only sent over HTTPS
  sameSite: "lax",      // not sent on most cross-site requests (CSRF defence)
  path: "/",
  maxAge: 60 * 60 * 24 * 7,
});

§3JWTs

A JSON Web Token is a signed blob containing claims such as the user id and expiry. The server verifies the signature without a database lookup, which is attractive for stateless services. The catch is that a valid token stays valid until it expires: you can't easily revoke one without keeping a server-side denylist, which reintroduces state.

Server sessionsJWTs
State livesOn the serverIn the token on the client
RevocationImmediate (delete the session)Hard until expiry
Per-request costA lookupA signature check
Best forMost web apps with a browser UIService-to-service calls and short-lived access tokens

A common hybrid is a short-lived access token (minutes) plus a long-lived refresh token that can be revoked. For a typical browser app, a httpOnly session cookie is the simpler and safer default.

Where the token lives matters Tokens in localStorage can be stolen by any injected script. An httpOnly cookie can't be read by JavaScript, which removes a whole class of theft. The trade-off is that cookies need CSRF protection, which SameSite and tokens provide.

§4Common Mistakes

MistakeWhat HappensFix
Storing a session or JWT in localStorageAny XSS bug lets an attacker steal itUse an httpOnly, secure cookie
Putting sensitive data in a JWT payloadTokens are encoded, not encrypted, so anyone can read themKeep claims minimal; look up details on the server
Using long-lived JWTs with no revocation planA stolen token works for days or weeksUse short expiry plus refresh tokens, or server sessions
Practice
  1. Decode a JWT with a tool and list what any holder of it can read. What does that imply for what you put in it?
  2. Set a session cookie with the right flags and inspect it in the browser's storage panel.
Key takeaways
  • Sessions store state on the server; JWTs carry signed state on the client.
  • Cookies should be httpOnly, secure, and SameSite to resist theft and CSRF.
  • JWTs are hard to revoke, so keep them short-lived or choose server sessions.
