Testing Server Actions & APIs

Contract and integration tests.

§1Server Code Needs Direct Tests

Server Actions and route handlers hold your most sensitive logic: validation, authorization, and writes. Testing them through the browser is slow, so test them directly. The goal is to verify the contract: for given input and user, what response and side effects occur?

§2Testing Route Handlers

A route handler is a function from Request to Response, so you can call it in a test with no server running.

import { POST } from "@/app/api/tasks/route";

test("rejects an empty title with 400", async () => {
  const req = new Request("http://test/api/tasks", {
    method: "POST",
    body: JSON.stringify({ title: "" }),
  });
  const res = await POST(req);
  expect(res.status).toBe(400);
  expect((await res.json()).error).toBeDefined();
});

§3Testing Server Actions

Server Actions are ordinary async functions in tests, but they depend on request context such as cookies and the session. Make that dependency injectable or mock just that boundary. Then assert on both return values and database state.

vi.mock("@/lib/auth", () => ({ requireUser: async () => ({ id: "alice" }) }));

test("createTask stores a task for the current user", async () => {
  const fd = new FormData();
  fd.set("title", "Ship it");
  await createTask(fd);
  expect(await db.task.findMany({ where: { ownerId: "alice" } })).toHaveLength(1);
});

§4Contract and Security Tests

  • Authorization matrix: for each role and endpoint, assert allow or deny.
  • Validation cases: missing, malformed, oversized, and unexpected fields.
  • Idempotency and duplicates: the same request twice should not double-write.
  • Schema contracts: verify response shapes against a shared schema, so clients don't break silently.

Each past security bug is a good regression test: write the test that reproduces it before fixing it.

Test the unhappy paths Most production incidents come from invalid input, missing permissions, and failed dependencies, not the happy path. A good API test suite is mostly 'what happens when this goes wrong?'

§5Common Mistakes

MistakeWhat HappensFix
Only testing successful requestsAuthorization and validation bugs ship unnoticedAdd cases for denied, invalid, and missing data
Mocking the database in action testsTests pass despite broken queries or constraintsUse a real test database, reset between tests
Testing one role onlyA permission hole for another role goes undetectedLoop through a role-by-action matrix
Practice
  1. Test a route handler for success, invalid input, and unauthorized access, calling it directly with Request objects.
  2. Write an authorization matrix test for three roles and four actions.
Key takeaways
  • Route handlers and Server Actions can be tested directly without a browser.
  • Assert on both responses and database state, using a real test database.
  • Test the failure paths and the full role-by-action matrix, not just success.
