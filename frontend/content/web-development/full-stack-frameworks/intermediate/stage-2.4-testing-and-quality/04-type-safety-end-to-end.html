Type Safety End to End

Shared types from database to UI.

§1One Source of Truth for Types

In a full-stack TypeScript app a single concept, say a Task, appears in the database, the API, validation, and the UI. If each layer defines its own copy, they drift apart and bugs hide in the gaps. End-to-end type safety means the types flow from one source through every layer.

LayerWhere the type comes from
DatabaseSchema (Prisma or Drizzle) generates row types
ValidationZod schema; z.infer gives the input type
Server logicFunctions accept and return those types
UIComponents import the same types

§2Deriving Instead of Duplicating

// db schema defines Task; derive everything else from it
import type { Task } from "@prisma/client";

export const CreateTask = z.object({ title: z.string().min(1) });
export type CreateTaskInput = z.infer<typeof CreateTask>;

// A view model that never exposes internal columns
export type TaskView = Pick<Task, "id" | "title" | "done">;

async function listTasks(userId: string): Promise<TaskView[]> {
  return db.task.findMany({
    where: { ownerId: userId },
    select: { id: true, title: true, done: true },
  });
}

Changing a column then produces compile errors everywhere that depended on it, which is exactly what you want: the compiler finds all the places to update.

§3Typed Boundaries and Their Limits

Server Actions and Server Components share types naturally, since they're called as functions. For external HTTP boundaries, tools such as tRPC, or OpenAPI-generated clients, carry types across the network. Typed route helpers can also check your <Link> hrefs.

Types are not validation. TypeScript is erased at runtime. z.infer types are only trustworthy because the data was actually parsed. A type annotation on await req.json() proves nothing about what a client sent.

Use strict mode, avoid any, and treat type errors as build failures in CI.

Parse at the edge, trust inside Validate untrusted data once where it enters your system (forms, requests, webhooks) and let the parsed, typed value flow inward. Everything inside can then rely on the types.

§4Common Mistakes

MistakeWhat HappensFix
Casting with as Task on parsed JSONThe compiler is silenced while the runtime data may be wrongParse with a schema; infer the type from it
Hand-writing the same interface in several filesTypes drift and bugs appear at the seamsDerive from the schema or the database types
Returning full database rows to the UIInternal fields leak and the UI couples to the table shapeSelect only needed fields into a view type
Practice
  1. Replace two duplicated type definitions in a project with types derived from the database schema and a Zod schema.
  2. Rename a database column and use the compiler's errors to find every place that needs updating.
Key takeaways
  • Derive types from one source, such as the schema, instead of duplicating them per layer.
  • Types give compile-time safety; schemas give runtime safety, and you need both at boundaries.
  • Enable strict, avoid any and unsafe casts, and fail CI on type errors.
