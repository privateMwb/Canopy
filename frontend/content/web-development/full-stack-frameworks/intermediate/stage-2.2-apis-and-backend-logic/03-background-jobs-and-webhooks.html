Background Jobs & Webhooks

Handling work that outlives a request.

§1Work That Outlives a Request

Some tasks shouldn't block a response: sending email, generating a PDF, resizing images, syncing with a third party. On serverless platforms there's a bigger reason: the function is frozen or killed shortly after the response returns, and it has a maximum duration. Long work needs a background job design.

§2Options for Background Work

ApproachHowUse when
after() / waitUntilRun a short task after the response is sentQuick fire-and-forget work such as logging or analytics
Queue + workerEnqueue a message; a worker processes itReliable work with retries, such as email and exports
Workflow serviceDurable, multi-step jobs (Inngest, Trigger.dev, Vercel Workflow, Temporal)Long or multi-stage processes that must survive failures
Scheduled job (cron)Run on a scheduleNightly cleanup, digests, syncs
import { after } from "next/server";

export async function POST(req: Request) {
  const order = await createOrder(await req.json());
  after(async () => {                 // runs after the response is sent
    await sendConfirmationEmail(order);
  });
  return Response.json({ id: order.id }, { status: 201 });
}

after() is best-effort and bound by the function's time limit. Anything that must not be lost belongs in a durable queue.

§3Webhooks

A webhook is the reverse of an API call: another service (Stripe, GitHub, a CMS) sends an HTTP POST to your endpoint when something happens. The rules are strict because anyone on the internet can hit your URL.

  1. Verify the signature using the raw request body and the shared secret. Reject anything that doesn't match.
  2. Respond quickly with a 2xx, doing minimal work inline and handing the rest to a queue.
  3. Be idempotent. Providers retry, so the same event may arrive more than once. Record processed event ids and ignore duplicates.
  4. Don't rely on order. Events can arrive late or out of sequence; fetch current state when it matters.
const raw = await req.text();                   // raw body, NOT req.json()
const event = stripe.webhooks.constructEvent(
  raw, req.headers.get("stripe-signature")!, process.env.STRIPE_WEBHOOK_SECRET!
);
if (await alreadyProcessed(event.id)) return new Response("ok");
await enqueue(event);                          // handle asynchronously
return new Response("ok");
Assume at-least-once delivery Retries mean your handler will sometimes run twice for one event. If processing the same message twice would double-charge or double-email, you have a bug waiting for a bad network day.

§4Common Mistakes

MistakeWhat HappensFix
Parsing the body before verifying the signatureThe signature check fails, or is skipped entirelyRead the raw body, verify, then parse
Doing slow work inside the webhook handlerThe provider times out and retries, creating duplicatesAcknowledge fast and process in the background
Assuming each webhook arrives exactly onceDuplicate side effectsStore event ids and make handlers idempotent
Practice
  1. Create a webhook endpoint that verifies a signature, rejects a tampered payload, and ignores a duplicate event id.
  2. Move a slow task (sending an email) out of a request handler using after(), then explain what would be lost if the function were killed early.
Key takeaways
  • Serverless functions are short-lived, so long or critical work needs queues or workflows.
  • Verify webhook signatures against the raw body before trusting a payload.
  • Design for retries: acknowledge fast, process asynchronously, and be idempotent.
