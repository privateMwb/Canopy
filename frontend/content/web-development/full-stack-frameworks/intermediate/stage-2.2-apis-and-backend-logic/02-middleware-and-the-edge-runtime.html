Middleware & the Edge Runtime

Running code before a request and near the user.

§1Code That Runs Before the Request

Middleware runs before a request reaches a route. It can redirect, rewrite, set headers, or respond directly. It is ideal for work that applies broadly and cheaply: redirects, locale detection, simple auth gating, and A/B bucketing.

// middleware.ts (named proxy.ts in the newest Next.js versions)
import { NextResponse, type NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  const hasSession = request.cookies.has("session");
  if (!hasSession && request.nextUrl.pathname.startsWith("/dashboard")) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  return NextResponse.next();
}

export const config = { matcher: ["/dashboard/:path*"] };   // limit where it runs

Use matcher to avoid running middleware on static assets and unrelated routes. Because it sits in front of every matching request, slow middleware slows everything.

§2The Edge Runtime

Middleware traditionally runs on the edge runtime: a lightweight environment deployed in many locations, so code executes physically near the user with very low startup time. The cost is a restricted API surface.

Edge runtimeNode.js runtime
StartupVery fast, minimal cold startSlower cold start
LocationMany regions, near usersUsually a chosen region
APIsWeb-standard APIs only (fetch, Request, Web Crypto)Full Node API (fs, native modules, most npm packages)
Database driversNeeds HTTP-based or edge-compatible driversAny driver
Best forRedirects, header logic, light auth checksHeavy logic, database access, large dependencies

Newer Next.js versions let middleware run on the Node.js runtime as well, which relaxes some limits. Check the current docs for your version, and pick the runtime that matches the work.

§3Keep It Thin

Middleware executes on a hot path and can't easily share work with your pages. Do fast checks there, such as reading a cookie or a header, and leave real authorization and data work to server code, where it can be tested and where runtime limits don't apply.

Edge isn't automatically faster Running near the user helps only if the code doesn't then call a distant database. An edge function that makes a cross-ocean query to a single-region database can be slower than a function placed beside the data.

§4Common Mistakes

MistakeWhat HappensFix
Importing a Node-only library into edge codeBuild or runtime errors about unsupported APIsUse web-standard alternatives, or switch the runtime
Matching every route including static filesNeedless latency and cost on each asset requestNarrow the matcher
Doing database queries or heavy logic in middlewareSlow requests and fragile limitsKeep it to quick checks; do the rest in server code
Practice
  1. Write middleware that redirects unauthenticated visitors and add a matcher that excludes static assets.
  2. List three tasks you would place in middleware and three you would keep out, with reasons.
Key takeaways
  • Middleware runs before routes and suits broad, cheap tasks such as redirects and header logic.
  • The edge runtime offers low latency and fast starts, but a limited API surface.
  • Keep middleware thin and place data-heavy work close to your data.
