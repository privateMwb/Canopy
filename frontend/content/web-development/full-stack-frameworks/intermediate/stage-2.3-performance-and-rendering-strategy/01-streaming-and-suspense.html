Streaming & Suspense

Showing useful content as soon as it's ready.

§1The Problem Streaming Solves

Traditional server rendering is all-or-nothing: the server waits for every query to finish, then sends the whole page. One slow query delays everything, including content that was ready instantly. Streaming sends the HTML in pieces: the fast parts arrive first, and slow parts fill in as they finish.

§2Suspense Boundaries

React's <Suspense> marks a region that may not be ready. The server immediately sends the surrounding page plus the fallback, then streams the real content into place when its data resolves.

export default function Dashboard() {
  return (
    <>
      <Header />                                   {/* instant */}
      <Suspense fallback={<StatsSkeleton />}>
        <Stats />                                  {/* slow query, async component */}
      </Suspense>
      <Suspense fallback={<FeedSkeleton />}>
        <ActivityFeed />                           {/* different slow query */}
      </Suspense>
    </>
  );
}

Each boundary resolves independently, so a slow feed never holds up the stats. The browser can show and even hydrate parts of the page before the rest arrives.

§3Designing Good Boundaries

  • Put boundaries around independent, slow data, not around everything.
  • Make fallbacks the same size as the final content to avoid layout shift.
  • Start the fetches early and in parallel; sibling boundaries load concurrently.
  • Keep critical content (the thing the user came for, and your LCP element) outside a slow boundary where possible.

A route-level loading.tsx is simply an automatic boundary around the whole page. Use finer boundaries when different parts of the page have very different speeds.

§4Trade-offs

Streaming improves perceived performance and time to first byte, but the total work is the same. It also complicates a few things: the status code and headers are sent before later parts finish, so a late failure can't change the HTTP status, and some crawlers and tools see only the initial HTML. Frameworks handle the common cases, but test what your SEO-critical pages actually return.

Streaming doesn't make queries faster It makes the page useful sooner. If a query itself is slow, fix it. Streaming just ensures it no longer blocks everything else.

§5Common Mistakes

MistakeWhat HappensFix
One Suspense boundary around the whole pageNo benefit; nothing shows until the slowest part is doneWrap independent slow regions separately
Fallbacks that differ in size from the contentThe page jumps when content arrives (layout shift)Build skeletons that match the final layout
Hiding the main content behind a boundaryPoor LCP and weak SEORender the primary content outside slow boundaries
Practice
  1. Add a two-second delay to two separate data sources on a page and wrap each in its own <Suspense>. Confirm that the fast parts appear first.
  2. Compare the first paint of the streamed version with one that awaits both queries before rendering anything.
Key takeaways
  • Streaming sends the fast parts of a page immediately and fills in slow parts as they resolve.
  • Place Suspense boundaries around independent slow data, with fallbacks matching the final layout.
  • Streaming improves perceived speed and doesn't reduce total work.
