HTTP/2, HTTP/3 & Connection Costs

Newer HTTP versions change which tricks help and which hurt. Know what each protocol fixes so you stop applying 2012 advice to a 2026 stack.

§1What Each Version Changed

VersionKey changeEffect on performance work
HTTP/1.1One request at a time per connectionBrowsers open ~6 connections; head-of-line blocking; bundling and sharding were common tricks
HTTP/2Many requests multiplexed on one TCP connection; header compressionMore, smaller files are cheaper; sharding hurts
HTTP/3Runs on QUIC over UDP; streams are independent; faster setupPacket loss on one stream no longer stalls the others; better on bad networks

HTTP/2 fixed head-of-line blocking at the HTTP layer but still ran on TCP, so one lost packet stalls every stream on that connection. HTTP/3 moves to QUIC, where streams are independent, and combines transport and TLS setup into fewer round trips.

§2The Cost of Connections

Whatever the version, a new connection to a new origin costs round trips, and a connection starts slow.

  • Setup: DNS, plus transport and TLS handshakes. TLS 1.3 and QUIC cut this down, and resumption makes repeat connections cheaper still.
  • Slow start: a new connection begins with a small congestion window, so the first transfers on it are slow.
  • Many origins: each new origin pays setup and starts slow again.

That is why fewer origins and reusing one connection is the lasting advice. Hosting your own assets on the same origin lets HTTP/2 or HTTP/3 share one warm connection, which can beat a separate asset domain.

§3Practical Consequences

  • Enable HTTP/2 or HTTP/3 at your CDN or server. It is usually a setting, and most CDNs support both.
  • Stop domain sharding. It was a workaround for HTTP/1.1 and now costs extra connections.
  • Don't over-bundle. Smaller, cacheable chunks work well on HTTP/2 and HTTP/3. Don't go to thousands of tiny files either, as there is still per-request overhead and discovery delay.
  • Server push is gone. Browsers removed HTTP/2 push. Use preload and 103 Early Hints instead.
  • preconnect remains valuable for third-party origins you can't avoid.
# Check which protocol a site uses
curl -sI --http3 https://example.com -o /dev/null -w '%{http_version}\n'
# or in DevTools: Network -> right-click header row -> enable 'Protocol'

Don't expect HTTP/3 to fix everything. It helps most on lossy and high-latency links, such as mobile networks. On a clean wired link, the difference may be small.

The key insight Protocol upgrades make parallelism cheap, but they don't make bytes or round trips to new origins free. The fundamentals of fewer origins and smaller payloads still apply.

§4Common Mistakes

MistakeWhat HappensFix
Keeping domain sharding after moving to HTTP/2Extra connections and handshakesServe assets from one origin
Concatenating everything into one giant filePoor caching and unneeded code on every pageUse sensible chunking and fingerprinting
Relying on HTTP/2 server pushBrowsers have removed itUse preload and Early Hints
Practice
  1. Enable the Protocol column in DevTools for a site and list which origins use HTTP/1.1, HTTP/2, and HTTP/3.
  2. Move a page's assets from a separate asset domain to the main origin, and compare the waterfall.
Key takeaways
  • HTTP/2 multiplexes requests on one connection, and HTTP/3 over QUIC also removes TCP head-of-line blocking.
  • New connections still cost round trips and start slow, so fewer origins is lasting advice.
  • Drop HTTP/1.1-era tricks such as sharding, and use preload and Early Hints instead of push.
