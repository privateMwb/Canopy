Framework Performance Pitfalls

Frameworks make big apps manageable, and add their own costs. Most framework slowness comes from a handful of repeating patterns.

§1Where Framework Costs Come From

A framework adds JavaScript to download and run, work to render and update the UI, and often a second pass to make server-rendered HTML interactive. Understanding the stages helps you find which one hurts.

CostWhat happensSymptom
Bundle sizeFramework plus your components plus librariesSlow load, long parse and execution
HydrationClient re-runs components to attach events to server HTMLPage looks ready but ignores input (high INP)
Re-renderingState changes re-run many componentsLaggy typing, slow interactions
Client-side data fetchingFetch begins only after JS loads and runsLate content, spinners, request waterfalls

§2Hydration and Rendering Choices

Hydration means the browser receives server-rendered HTML, shows it quickly, then downloads the JavaScript and re-executes the component tree to make it interactive. Until that finishes, buttons may not respond. The larger the tree, the longer the gap.

  • Send less JavaScript. Smaller bundles hydrate sooner. Split by route and by interaction.
  • Hydrate less. Techniques such as islands architecture and server components keep static parts out of the client bundle and hydrate only interactive pieces.
  • Stream and hydrate in parts, so important areas become interactive first.
  • Avoid client-only rendering for content that could be rendered ahead of time. It delays LCP.

The details vary by framework, but the principle is the same everywhere: the less code that must run on the client, the faster the page becomes interactive.

§3Common Pitfalls and Fixes

  • State too high in the tree. A change in a parent re-renders every child. Keep state close to where it is used.
  • Unstable props. Creating new objects, arrays, or functions on each render defeats memoization. Stabilize them where it matters.
  • Expensive work in render. Move heavy calculations out of the render path, or memoize them.
  • Huge lists. Virtualize them (earlier lesson).
  • Request waterfalls. Components that fetch inside children fetch one after another. Fetch in parallel, or at the route level.
  • Too many global listeners and subscriptions that re-render large parts of the app.
// React example: avoid recomputing and re-rendering needlessly
const filtered = useMemo(() => items.filter(matches(query)), [items, query]);
const onSelect = useCallback(id => setSelected(id), []);

const Row = memo(function Row({ item, onSelect }) {
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});

Don't sprinkle memo everywhere. Profile first. The framework's devtools profiler shows which components re-render and how long they take, and fixes belong where the profiler points.

The key insight Framework performance is mostly about doing less on the client: ship less code, hydrate less, and re-render less. Measure with the profiler before optimizing.

§4Common Mistakes

MistakeWhat HappensFix
Wrapping everything in memo by habitAdds complexity and sometimes slows thingsProfile and optimize the hot spots
Rendering main content only on the clientLate LCP and an empty first loadRender on the server or ahead of time
Nested components each fetching their own dataSequential request waterfallsFetch in parallel at a higher level
Practice
  1. Use your framework's profiler on a slow interaction and list the components that re-render. Identify one that did not need to.
  2. Move one piece of state lower in the tree and confirm fewer components re-render.
Key takeaways
  • Framework costs come from bundle size, hydration, re-rendering, and client-side data fetching.
  • Ship less JavaScript, hydrate less, and keep state close to where it is used.
  • Profile first, and fix the specific component the profiler identifies.
