Tree Shaking & Dependency Choices

Tree shaking removes code you imported but never used, but only when your code and your dependencies cooperate. Choosing dependencies well matters more.

§1How Tree Shaking Works

Tree shaking is dead-code elimination for modules. The bundler analyses which exports are actually used and drops the rest. It relies on the static structure of ES modules (import and export), because it can tell at build time what is referenced.

// math.js
export function add(a, b) { return a + b; }
export function multiply(a, b) { return a * b; }   // never imported anywhere

// app.js
import { add } from './math.js';
console.log(add(1, 2));

// The production bundle contains add() and drops multiply()

CommonJS (require) is dynamic, so it generally can't be tree shaken. Prefer libraries that publish ES module builds.

§2What Defeats It

ProblemWhy it blocks shaking
CommonJS dependenciesExports can't be analyzed statically
Side effects at import timeThe bundler can't safely drop a module that does work when loaded
Barrel files (index.js re-exporting everything)Can pull in a whole package if side effects aren't declared
Importing a default object (import _ from "lodash")Brings the entire object along
Dynamic access (obj[name])The bundler can't tell what is used

Libraries can mark themselves safe to prune by setting "sideEffects": false in package.json, which tells the bundler that unused modules can be removed without changing behavior. Only set this if it is true.

// package.json of a well-behaved library
{
  "name": "my-lib",
  "type": "module",
  "sideEffects": false,
  "exports": { ".": "./dist/index.js" }
}

§3Choosing Dependencies Wisely

Tree shaking helps, but the biggest lever is what you depend on in the first place.

  • Check size before installing, including transitive dependencies, with bundlephobia or your analyzer.
  • Prefer modular, ESM-first libraries: date-fns over moment, individual imports over whole-library defaults.
  • Use the platform. Native fetch, Intl, URL, structuredClone, and CSS often replace a library.
  • Don't import a utility library for one function. Write it, or import it narrowly.
  • Audit periodically. Remove packages that are no longer used.
// Narrow imports so the bundler can drop the rest
import { format } from 'date-fns';       // shaken to just format()
import debounce from 'lodash-es/debounce';   // one function from an ESM build

Always verify with the analyzer. Whether something was actually shaken is a measurable fact, not an assumption.

Gotcha Marking a package sideEffects: false when it does have side effects, such as registering styles or polyfills, can silently delete code your app needs. Declare it accurately.

§4Common Mistakes

MistakeWhat HappensFix
Using a CommonJS-only libraryThe whole library is bundled, whatever you useChoose an ESM build or an alternative
Importing the whole library by defaultLarge bundle for one functionUse named or per-function imports
Assuming tree shaking workedDead code is still shippedConfirm in the bundle analyzer
Practice
  1. Import one function from a library two different ways and compare the bundle size of each in an analyzer.
  2. Replace a heavy dependency with a lighter one or a native API, and record the saving.
Key takeaways
  • Tree shaking removes unused exports, but relies on static ES modules and side-effect-free code.
  • CommonJS, barrel files, and import-time side effects can all defeat it.
  • Choose small, modular dependencies, prefer native APIs, and verify with an analyzer.
