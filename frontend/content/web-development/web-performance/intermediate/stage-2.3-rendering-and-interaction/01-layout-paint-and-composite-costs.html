Layout, Paint & Composite Costs

Every visual change pays for some mix of style, layout, paint, and composite. Knowing which one a change triggers tells you how expensive it is.

§1The Rendering Pipeline

After JavaScript changes something, the browser may need to redo several steps, in order. Later steps are cheaper, so the goal is to trigger as few and as late as possible.

StageWhat it doesRelative cost
StyleWorks out which CSS rules apply to each elementLow to medium
LayoutComputes size and position of every affected elementHigh, can cascade to the whole page
PaintFills in pixels: text, colors, borders, shadowsMedium to high
CompositeCombines layers on the GPULowest

Changing a property that affects geometry, such as width, top, margin, or font-size, triggers layout, then paint and composite. Changing only color or background skips layout but still paints. Changing transform or opacity on its own layer can skip both and go straight to composite.

§2Layout Thrashing

Layout is expensive, and it is easy to force it repeatedly. Reading a layout property such as offsetHeight forces the browser to calculate layout now if anything is pending. If you alternate reads and writes in a loop, you force layout on every iteration.

// Bad: read, write, read, write... forces layout every iteration
for (const el of items) {
  el.style.width = el.parentNode.offsetWidth / 2 + 'px';
}

// Better: batch all reads first, then all writes
const widths = items.map(el => el.parentNode.offsetWidth);
items.forEach((el, i) => { el.style.width = widths[i] / 2 + 'px'; });

In DevTools, a purple Layout block that repeats many times inside one task, often with a warning about forced reflow, is the signature of thrashing.

§3Reducing the Work

  • Prefer transform and opacity for movement and fades, since they can run on the compositor.
  • Limit the scope of layout with CSS contain: layout paint or content-visibility: auto on large offscreen sections, so changes there don't affect the rest.
  • Keep the DOM small. Layout and style cost grow with the number of elements.
  • Avoid deep, complex selectors and huge numbers of rules touching many elements.
  • Batch DOM updates, and write with requestAnimationFrame so changes happen once per frame.
/* Skip rendering work for sections far offscreen */
.article-section {
  content-visibility: auto;
  contain-intrinsic-size: auto 600px;   /* reserve space so scroll bar doesn't jump */
}

Use CSS Triggers style references, or the Performance panel itself, to see which stage a property touches. Verify in a trace rather than trusting a rule of thumb.

The key insight The cheapest frame is the one where only composite runs. Each step up the pipeline, composite to paint to layout, costs more, and layout can cascade across the page.

§4Common Mistakes

MistakeWhat HappensFix
Reading layout properties inside a write loopForced layout on every iterationRead everything first, then write
Animating top, left, or widthLayout and paint on every frameAnimate transform
Keeping tens of thousands of DOM nodesStyle and layout get expensive for any changeVirtualize, or use content-visibility
Practice
  1. Write a loop that reads and writes layout alternately, then fix it by batching. Compare the traces.
  2. Apply content-visibility: auto to long offscreen sections and measure the change in initial rendering time.
Key takeaways
  • Style, layout, paint, and composite run in order and cost more the earlier they are.
  • Alternating layout reads and writes causes forced reflow, so batch reads then writes.
  • Prefer compositor-friendly properties, keep the DOM small, and use containment to limit scope.
