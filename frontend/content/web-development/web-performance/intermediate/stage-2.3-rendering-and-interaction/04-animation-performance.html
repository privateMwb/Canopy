Animation Performance

Smooth animation means producing a new frame every 16 ms. Choosing the right properties decides whether the browser has the time.

§1The Frame Budget

To look smooth at 60 frames per second, every frame must be ready in about 16.7 ms, and less on 120 Hz screens. That budget has to cover your JavaScript, style, layout, paint, and compositing. Miss it and frames are dropped, which the eye sees as jank.

The trick is to animate properties that don't need the main thread. The compositor runs on a separate thread, so animations that only need it keep running smoothly even when the main thread is busy.

Property you animateWork requiredSmooth?
transform, opacityComposite only (when on its own layer)Yes: can run off the main thread
background-color, box-shadowPaint every frameMedium: depends on area
width, height, top, left, marginLayout, paint, and composite every frameNo: expensive

§2Writing Animations the Cheap Way

/* Move with transform, not left/top */
.panel { transform: translateX(-100%); transition: transform 250ms ease; }
.panel.open { transform: translateX(0); }

/* Fade with opacity */
.toast { opacity: 0; transition: opacity 200ms; }
.toast.show { opacity: 1; }
  • Prefer CSS transitions and animations for simple motion. The browser can optimize them.
  • Use the Web Animations API (element.animate) when you need JavaScript control over the same optimized path.
  • When you must use JavaScript per frame, use requestAnimationFrame, not setTimeout, so updates align with the display.
  • Use will-change: transform sparingly, only on elements about to animate. Each promoted layer costs GPU memory.
el.animate(
  [{ transform: 'translateY(20px)', opacity: 0 }, { transform: 'none', opacity: 1 }],
  { duration: 300, easing: 'ease-out', fill: 'both' }
);

§3Finding and Fixing Jank

  • The Performance panel's Frames track shows dropped frames. Look at what ran in them.
  • The Rendering tab can display paint flashing, layer borders, and an FPS meter.
  • On weak hardware, test with CPU throttling, since a smooth animation on your laptop can stutter on a phone.
  • Honor prefers-reduced-motion. Many users want less motion, and it saves battery.
@media (prefers-reduced-motion: reduce) {
  * { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; }
}

Also consider scroll-driven animations in CSS, which tie animation progress to scroll position without JavaScript scroll listeners. They are the modern replacement for many scroll handlers that caused jank.

Gotcha Overusing will-change or promoting too many layers can slow things down and burn memory. Promote only what actually animates, and remove the hint when it is done.

§4Common Mistakes

MistakeWhat HappensFix
Animating left, top, or widthLayout every frame causes dropped framesUse transform and opacity
Applying will-change to many elementsGPU memory use balloonsUse it only on elements about to animate
Driving animation with setTimeoutUpdates drift out of sync with the displayUse CSS, WAAPI, or requestAnimationFrame
Practice
  1. Convert an animation that changes left into one that uses transform. Compare the Frames track before and after.
  2. Add a prefers-reduced-motion rule for your site's animations and test it.
Key takeaways
  • You have about 16.7 ms per frame, and layout-triggering animation burns that budget.
  • Animate transform and opacity with CSS or the Web Animations API, and use will-change sparingly.
  • Find jank with the Frames track and CPU throttling, and respect reduced-motion preferences.
