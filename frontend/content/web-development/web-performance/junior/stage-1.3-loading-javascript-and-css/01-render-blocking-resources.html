Render-Blocking Resources

The browser won't paint until it knows what the page looks like. CSS and some JavaScript hold it back, and that wait is your first-paint time.

§1What Blocks Rendering

A resource is render-blocking when the browser refuses to show anything until it has been downloaded and processed. Two kinds matter.

  • CSS is render-blocking by default. The browser needs the styles to know what to draw, so it waits for stylesheets in the <head>.
  • Synchronous scripts are parser-blocking. A plain <script src> stops HTML parsing while it downloads and runs, and scripts can also wait for CSS that comes before them.
<head>
  <link rel="stylesheet" href="/all-styles.css">   <!-- blocks render -->
  <script src="/analytics.js"></script>            <!-- blocks parsing AND is blocked by the CSS above -->
</head>

Every blocking file adds at least a network round trip before first paint. On a slow connection, a few of them can mean seconds of blank screen.

§2Reducing the Blocking

You can't remove all blocking, since the page needs some CSS to look right. The aim is to block on as little as possible, and make that small.

TechniqueHow it helps
Inline critical CSSThe above-the-fold styles are in the HTML, so no extra request is needed
Load the rest asynchronouslyBelow-the-fold styles don't delay first paint
Split CSS by mediamedia="print" or a breakpoint stylesheet isn't blocking for other cases
defer or move scriptsScripts stop blocking the parser (next lesson)
Ship less CSSSmaller files download faster and parse faster
<style>/* critical, above-the-fold rules */ header{...} .hero{...}</style>

<!-- non-critical stylesheet: does not block first paint -->
<link rel="stylesheet" href="/rest.css" media="print" onload="this.media='all'">
<noscript><link rel="stylesheet" href="/rest.css"></noscript>

Inlining too much CSS bloats every HTML response and can't be cached on its own, so inline only what the first screen needs.

§3Finding Render-Blocking Resources

Lighthouse lists them under Eliminate render-blocking resources. In DevTools, the Performance panel shows when the first paint happens relative to when each stylesheet and script finished.

  1. Run Lighthouse and note the blocking requests it flags.
  2. In the Network tab, check the Priority column. Blocking CSS shows as Highest.
  3. Ask of each: is it needed for the first screen? If not, defer or delay it.
  4. Re-measure first paint and LCP after each change.
The key insight The question for every resource in the head is: does the first screen need this to render? If not, it shouldn't block.

§4Common Mistakes

MistakeWhat HappensFix
Many separate stylesheets in the headSeveral blocking requests before first paintCombine, and defer what isn't critical
Putting synchronous scripts at the top of the headParsing stops and the page stays blankUse defer, or place scripts at the end of the body
Inlining the entire stylesheetHTML grows and the CSS can't be cachedInline only the critical rules
Practice
  1. Run Lighthouse on a page and list its render-blocking resources. Decide which, if any, the first screen truly needs.
  2. Add defer to one script and compare the time of first paint before and after.
Key takeaways
  • CSS blocks rendering, and synchronous scripts block parsing.
  • Inline the critical CSS, load the rest without blocking, and defer scripts.
  • Judge every head resource by whether the first screen needs it.
