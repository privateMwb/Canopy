Measuring Cache Hits

Setting caching headers isn't the same as caching working. Learn to verify that repeat visits are actually served from cache, and to spot why they aren't.

§1Checking in the Browser

DevTools tells you exactly where each response came from. Open the Network tab, load the page, then reload it normally and look at the Size column.

What you seeMeaning
(memory cache) or (disk cache)Served from the browser cache with no network request
A size such as 0 B with status 304Revalidated, and the server said it hasn't changed
A full size with status 200Downloaded again: not served from cache
  • Untick Disable cache while testing caching. It's often on while DevTools is open.
  • A hard reload (Ctrl or Cmd + Shift + R) bypasses the cache on purpose, so test with a normal reload and with a fresh navigation.
  • The Timing and Headers tabs show the headers the server sent.

§2Checking the Headers and the CDN

# Inspect what the server and CDN say about a response
curl -sI https://example.com/app.3f9a1c.js

cache-control: public, max-age=31536000, immutable
age: 5120                  # seconds it has been in a shared cache
x-cache: HIT               # name varies by provider
etag: "3f9a1c"

A rising Age and a hit indicator mean the CDN is serving from cache. A missing Age or constant misses mean it isn't. Run the request twice, because the first may legitimately be a miss that fills the cache.

§3Measuring Over Time and Debugging Misses

For a service you run, your CDN's dashboard or logs report a cache hit ratio: the share of requests served from the edge. Aim for a high ratio on static assets, and investigate drops.

SymptomLikely cause
Static assets always MISSNo Cache-Control, or private or no-store set by mistake
Different cache keys per requestQuery strings, cookies, or Vary headers splitting the cache
Repeat visits re-download everythingShort max-age, or filenames that change every build
Stale content after deployHTML cached too long, or assets not fingerprinted
// In the field: see whether real loads came from cache
const nav = performance.getEntriesByType('resource');
for (const r of nav) {
  const fromCache = r.transferSize === 0 && r.decodedBodySize > 0;
  console.log(r.name, fromCache ? 'cache' : 'network');
}
Gotcha A transferSize of 0 can mean a cache hit, but cross-origin resources hide size details unless the server sends Timing-Allow-Origin. Use it as a hint, not proof.

§4Common Mistakes

MistakeWhat HappensFix
Testing caching with 'Disable cache' tickedEverything looks uncachedUntick it and use a normal reload
Judging a CDN from a single requestThe first request fills the cache and is a missRequest twice and compare
Ignoring cache hit ratio after launchSilent misconfigurations erode the benefitMonitor it and alert on drops
Practice
  1. Load a page, reload normally, and list which requests come from (disk cache) and which hit the network. Explain two of the differences.
  2. Find one asset that is not being cached well, and fix its headers.
Key takeaways
  • DevTools shows cache hits as memory or disk cache, and 304 responses mean revalidation.
  • Age and the CDN's hit header show whether shared caches are serving a response.
  • Monitor hit ratios and know the common causes of misses: headers, cookies, query strings, and unstable filenames.
