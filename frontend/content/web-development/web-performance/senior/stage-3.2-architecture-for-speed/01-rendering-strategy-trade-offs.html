Rendering Strategy Trade-offs

Where and when HTML gets produced, on the server, at build time, in the browser, or in pieces, shapes almost every performance number. There is no best strategy, only trade-offs.

§1The Main Strategies

StrategyHTML is producedStrengthWeakness
CSR (client-side rendering)In the browser, by JavaScriptRich interactivity, simple hostingEmpty first load, late LCP, heavy JS, weaker for crawlers
SSR (server-side rendering)On the server, per requestFresh and personalized, fast first paintServer cost and TTFB, hydration needed
SSG (static generation)At build timeFastest delivery from a CDN, cheap, resilientStale until rebuilt, build time grows with page count
ISR / revalidationAt build time, then regenerated in the backgroundStatic speed with bounded stalenessMore moving parts, cache invalidation
Streaming SSROn the server, sent in chunksEarly first bytes, slow parts do not block the restComplexity, careful handling of errors and status codes
Islands / partial hydrationStatic HTML plus small interactive piecesLittle JavaScript, fast interactivityNeeds framework support, state sharing is harder

Real sites mix them. A marketing page is static, a product page is regenerated every few minutes, a dashboard is client-rendered behind a login, and checkout is server-rendered and personalized.

§2Choosing by Constraint

Start from what must be true about the page, not from what the framework defaults to. A few questions decide most cases.

  1. How personalized is it? If the HTML is the same for everyone, it can be cached at the edge, so prefer static or revalidated.
  2. How fresh must it be? Seconds, minutes, or days? Freshness requirement sets the revalidation window.
  3. Does a crawler or a first-time visitor need the content? Then it must be in the initial HTML.
  4. How interactive is it? Mostly reading means ship little JavaScript. Mostly app-like means a larger client is justified.
  5. What does the audience's device look like? Slow phones punish heavy hydration.

§3Measuring the Trade-offs

Each strategy moves cost to a different place, so judge it with the metric that cost lands on.

MetricCSR tends toSSR tends toSSG tends to
TTFBExcellent (static shell)Worse, depends on server workExcellent (edge cache)
LCPPoor, waits on JS and dataGood if the server is fastBest
INPDepends on JS sizeHydration can delay first inputGood with little JS
Server costLowHigh, scales with trafficLow

These are tendencies, not laws. A badly cached SSR page can be slower than a lean CSR one, and a huge static page can still hydrate slowly. Prototype the real page, and compare field metrics for the strategies you are choosing between.

The key insight Rendering strategy is a decision about where to pay: build time, server time, or the user's device. Pay as early and as far from the user's CPU as the content's freshness and personalization allow.

§4Common Mistakes

MistakeWhat HappensFix
Choosing CSR for content-heavy public pagesSlow LCP, poor discoverabilityRender the content on the server or at build time
Using SSR for pages that are identical for everyonePays server cost on every request for no benefitGenerate statically and cache at the edge
Picking a strategy from framework defaultsMisfit with the actual content and trafficDecide from personalization, freshness, and interactivity
Practice
  1. Take a site with five page types and assign each a rendering strategy. Justify each in terms of freshness, personalization, and interactivity.
  2. Choose one page and describe which metric you would watch to confirm your choice was right.
Key takeaways
  • CSR, SSR, SSG, ISR, streaming, and islands each shift cost between build, server, and client.
  • Decide per page type, from personalization, freshness, crawler needs, and interactivity.
  • Verify with field metrics, because the tendencies differ in practice.
