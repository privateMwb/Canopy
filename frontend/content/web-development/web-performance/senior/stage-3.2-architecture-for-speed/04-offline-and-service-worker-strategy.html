Offline & Service Worker Strategy

A service worker is a programmable network proxy in the browser. It can make repeat visits instant and keep an app working offline, and a bad one can strand users on a broken version.

§1What a Service Worker Does

A service worker is a script that sits between your page and the network. It intercepts fetch requests and decides how to answer: from a cache, from the network, or a mix. It runs separately from pages, has a lifecycle of its own, and works only over HTTPS.

// register.js
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js');
}

// sw.js: lifecycle
self.addEventListener('install', e => e.waitUntil(precache()));
self.addEventListener('activate', e => e.waitUntil(cleanOldCaches()));
self.addEventListener('fetch', e => e.respondWith(handle(e.request)));

Be clear about the goal. A service worker can speed up repeat visits and provide offline support, but it does nothing for a first visit, and it adds a layer that must be maintained.

§2Caching Strategies

StrategyBehaviorGood for
Cache firstServe from cache, fall back to networkVersioned static assets, fonts, icons
Network firstTry the network, fall back to cacheContent where freshness matters but offline should still work
Stale-while-revalidateServe cache immediately, update it in the backgroundAvatars, feeds, and API data that can be briefly stale
Network onlyNever cachePayments and anything that must be live
Cache onlyOnly from cachePrecached app shell, offline pages
// Stale-while-revalidate for API reads
async function swr(request) {
  const cache = await caches.open('api-v1');
  const cached = await cache.match(request);
  const network = fetch(request).then(res => {
    if (res.ok) cache.put(request, res.clone());
    return res;
  });
  return cached ?? network;
}

Use a library such as Workbox to implement these patterns, because the edge cases are numerous: opaque responses, range requests, quota limits, and cache expiry.

§3The Update Problem

The hard part is updating. A new service worker installs in the background, then waits until all tabs using the old one are closed before it takes over. Users can run an old version for days, and a worker that caches HTML and assets together can serve a stale page forever.

  • Version your caches and delete old ones in activate.
  • Don't cache the service worker file itself aggressively. Serve sw.js with Cache-Control: no-cache, so updates are noticed.
  • Decide an update policy. Use skipWaiting() and clients.claim() to activate immediately, but know that it can mix old pages with new assets. Or prompt the user to reload when an update is ready.
  • Never cache HTML with cache-first without a revalidation path.
  • Ship a kill switch. Be able to deploy a worker that unregisters itself and clears caches if something goes wrong.
  • Watch quota and eviction. Storage can be cleared by the browser, so don't treat it as durable.
// An emergency escape hatch
self.addEventListener('install', () => self.skipWaiting());
self.addEventListener('activate', async () => {
  await self.registration.unregister();
  const keys = await caches.keys();
  await Promise.all(keys.map(k => caches.delete(k)));
});
Gotcha A buggy service worker is hard to remove, because it controls the very requests you'd use to replace it. Always keep sw.js uncached and have a tested kill switch before you ship.

§4Common Mistakes

MistakeWhat HappensFix
Caching HTML cache-first with no update pathUsers are stuck on an old versionUse network first or revalidation for documents
Serving sw.js with a long cache lifetimeThe new worker is never foundServe it no-cache
Never cleaning old cachesStorage grows and stale files lingerVersion caches and delete old ones on activate
Practice
  1. Write a service worker that precaches an app shell and uses stale-while-revalidate for API reads. Test going offline.
  2. Deploy a change and observe the update lifecycle in DevTools' Application panel. Describe when the new worker activates.
Key takeaways
  • Service workers intercept requests and enable instant repeat visits and offline use, but not faster first loads.
  • Choose a strategy per resource type, and use a library to avoid edge-case bugs.
  • Plan updates and a kill switch up front, because stale workers are the main risk.
