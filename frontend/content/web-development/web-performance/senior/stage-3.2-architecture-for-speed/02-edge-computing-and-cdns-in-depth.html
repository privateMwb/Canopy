Edge Computing & CDNs in Depth

A CDN is more than file hosting. At its best it is a programmable cache and compute layer close to every user, and designing it well is an architecture skill.

§1Cache Design

A cache hit depends on the cache key: the set of request properties the CDN uses to decide two requests want the same response. A key that is too narrow splits identical content into many entries, and one that is too wide serves the wrong content.

Key ingredientEffect
URL pathAlways part of the key
Query stringEvery distinct value is a separate entry. Ignore irrelevant parameters (tracking tags) or sort them.
CookiesIf included, every user gets a separate entry. Exclude them for cacheable content.
Vary headersEach distinct value of a listed header creates a variant
Device or countryUseful for real differences, but multiplies entries
  • Normalize the key. Strip tracking parameters, lowercase hostnames, and collapse variants that produce the same response.
  • Tier the cache. A shield or origin-shield layer lets many edges share a regional cache, so your origin sees one miss rather than one per edge.
  • Coalesce requests. When many users request the same uncached object at once, the CDN should send one request to origin and fan out the answer.

§2Freshness and Invalidation

Long lifetimes give high hit ratios, and short ones give freshness. Good designs avoid choosing between them.

Cache-Control: public, s-maxage=300, stale-while-revalidate=86400, stale-if-error=86400
# Fresh for 5 min at the edge. After that, serve stale instantly while refreshing,
# for up to a day. If the origin is failing, keep serving stale rather than erroring.
  • Surrogate keys (cache tags): tag responses with logical keys such as product-123, and purge by tag when that product changes, instead of guessing URLs.
  • Event-driven purge: trigger invalidation from your content system on publish, so long lifetimes stay safe.
  • Versioned URLs remain the most reliable approach for static assets.
  • Plan for purge propagation delay. It is fast but not instant, and can fail, so don't build correctness on it alone.

§3Compute at the Edge

Many CDNs run your code in lightweight runtimes in their points of presence. This moves logic to where latency is lowest.

Good usesPoor uses
Redirects, rewrites, and A/B bucketing without an origin tripHeavy computation or long-running jobs
Authentication checks and header manipulationChatty access to a single central database
Personalizing a cached page shell (geo, language)Large dependencies, since runtimes limit size and APIs
Assembling responses from multiple cached fragmentsLogic that needs strong consistency across regions
// Edge function sketch: serve a cached page, vary by country, no origin call
export default async function handler(request) {
  const country = request.headers.get('x-country') ?? 'US';
  const page = await cache.match(`/home?c=${country}`);
  return page ?? fetchFromOrigin(request);
}

The recurring pitfall is data gravity: code at the edge is fast, but if it must call a database in one region, the round trip erases the gain. Replicate or cache the data, or keep that logic at the origin.

The key insight Edge performance comes from hit ratio and proximity of both code and data. Normalize cache keys, layer your caches, and put computation where its data already is.

§4Common Mistakes

MistakeWhat HappensFix
Including cookies in the cache key for public pagesEvery visitor gets a separate entry and nothing hitsExclude cookies and vary only on what truly differs
Running edge code that calls a distant databaseThe round trip erases the benefitCache or replicate the data, or run it at the origin
Relying solely on purge for correctnessPurges can be delayed or failCombine with short s-maxage or stale-while-revalidate
Practice
  1. Audit a CDN configuration for cache-key problems: list query parameters and cookies that fragment the cache and propose a normalized key.
  2. Design a purge strategy using surrogate keys for a catalog where individual products update at random.
Key takeaways
  • The cache key decides hit ratio, so normalize it and avoid cookies and noisy parameters.
  • Use stale-while-revalidate, stale-if-error, tags, and event-driven purges to get freshness without losing hits.
  • Edge compute is fastest when its data is also nearby, so beware data gravity.
