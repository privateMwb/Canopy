Memory & Garbage Collection

Pages that stay open for hours, such as dashboards, editors, and single-page apps, can slow down and crash from memory growth. Finding leaks is its own discipline.

§1How Memory Is Managed

JavaScript is garbage collected. The engine periodically finds objects that are no longer reachable from the roots (global scope, the call stack, live closures) and frees them. You don't free memory manually, but you can accidentally keep things reachable forever.

Collection has a cost. Modern engines are generational and incremental, so they do most work in small pauses, but heavy allocation produces frequent collections, and a very large heap produces longer pauses. Both show up as jank.

SymptomLikely meaning
Memory climbs steadily and never fallsA leak: objects are being kept reachable
Sawtooth: rises, drops, rises, dropsHealthy allocation and collection
Frequent short pauses during animationHigh allocation rate producing garbage
Tab crashes or reloads on mobileMemory pressure; devices have less headroom

§2Common Leak Patterns

  • Forgotten event listeners: adding listeners to long-lived objects, such as window, without removing them when a component unmounts.
  • Timers and intervals that keep running and hold references in their callbacks.
  • Detached DOM nodes: elements removed from the page but still referenced from a JavaScript variable or cache.
  • Unbounded caches and maps: a cache that never evicts, or a Map keyed by objects that are never deleted.
  • Closures capturing large objects that outlive their purpose.
  • Growing global state such as logs or history arrays.
// Leaks: the listener keeps `component` (and its DOM) alive forever
function mount(component) {
  window.addEventListener('resize', () => component.update());
}

// Fixed: remove on teardown, or use AbortController
function mount(component) {
  const ac = new AbortController();
  window.addEventListener('resize', () => component.update(), { signal: ac.signal });
  return () => ac.abort();
}

// Caches keyed by object: WeakMap lets entries be collected with their key
const meta = new WeakMap();

§3Finding Leaks With DevTools

  1. Open the Memory panel and take a heap snapshot at a stable state.
  2. Perform the suspected leaking action several times, such as opening and closing a dialog.
  3. Force garbage collection (the trash can icon) and take a second snapshot.
  4. Use the Comparison view to see which object types grew. Detached DOM nodes and large counts of the same class are the clues.
  5. Select a leaked object and read its Retainers to see what path keeps it alive.

The Performance panel's memory option records heap size over time, and the allocation timeline shows where objects are created. Use performance.measureUserAgentSpecificMemory() where available to track memory in the field, and watch for gradual growth across long sessions.

The key insight A leak is an unwanted reference path. The retainers view shows that path, which is the thing to cut, whether it is a listener, a timer, or a cache.

§4Common Mistakes

MistakeWhat HappensFix
Adding listeners and never removing themComponents and DOM stay alive after removalClean up on teardown, or use AbortController
Using an unbounded cacheMemory grows with every unique keySet a size limit, or use a WeakMap
Taking one snapshot and guessingYou can't tell what grewCompare snapshots before and after the action
Practice
  1. Write a component that leaks via an event listener. Find it with a heap snapshot comparison, and read its retainers.
  2. Fix the leak and confirm the comparison no longer shows growth after repeating the action.
Key takeaways
  • Memory is freed only when objects become unreachable, so leaks are references you didn't mean to keep.
  • Common causes are listeners, timers, detached DOM, unbounded caches, and captured closures.
  • Compare heap snapshots and follow the retainers to find and cut the reference path.
