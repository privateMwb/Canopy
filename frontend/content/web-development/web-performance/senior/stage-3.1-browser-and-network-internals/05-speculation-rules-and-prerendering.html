Speculation Rules & Prerendering

The fastest page load is one that already happened. Speculation rules let the browser fetch or fully render the next page before the user clicks.

§1Prefetch and Prerender

Two techniques anticipate the next navigation. Prefetch downloads the next page's HTML ahead of time, so the request itself is instant. Prerender goes further: the browser loads the page, runs its JavaScript, and renders it in a hidden state. When the user navigates, it is swapped in, often appearing instantly.

TechniqueDoesSavesCost
PrefetchFetches the document (and optionally its subresources)Network time for the HTMLBandwidth, low CPU
PrerenderFetches, parses, executes, and renders the pageNearly all load timeBandwidth, CPU, and memory

Both are guesses. If the user doesn't navigate there, the work is wasted, which is the central trade-off.

§2Speculation Rules

The Speculation Rules API replaces older <link rel="prefetch"> and prerender hints. You declare rules in JSON, and the browser decides when to act, based on the eagerness you choose.

<script type="speculationrules">
{
  "prerender": [{
    "where": { "and": [
      { "href_matches": "/products/*" },
      { "not": { "selector_matches": "[rel~=nofollow]" } }
    ]},
    "eagerness": "moderate"
  }],
  "prefetch": [{
    "urls": ["/pricing"],
    "eagerness": "eager"
  }]
}
</script>
EagernessWhen the browser acts
immediateAs soon as the rules are seen
eagerShortly after, on very light signals
moderateTypically on hover (or pointer down on mobile)
conservativeOn pointer or touch down, right before the click

Browser support and exact behavior differ and are changing. Check current documentation, and treat it as a progressive enhancement: where it is unsupported, navigation simply behaves normally.

§3Making Prerendering Safe

A prerendered page runs your code before the user has actually visited it. That creates hazards you must design around.

  • Analytics: don't count a page view until the page is activated. Listen for the prerenderingchange event or check document.prerendering.
  • Side effects: don't start timers, modals, autoplay media, or write to storage on load without checking.
  • Personalized or stateful pages: avoid prerendering pages that change server-side state on load, such as logout or add-to-cart URLs.
  • Cost: prerender only likely targets. Wasted prerenders burn user bandwidth, battery, and your server capacity.
  • Same-site constraints: cross-origin prerendering is restricted, and credentials and cookies are handled carefully.
if (document.prerendering) {
  document.addEventListener('prerenderingchange', startRealPageView, { once: true });
} else {
  startRealPageView();
}

Measure the effect: Chrome DevTools has an Application > Speculative loads panel, and your real-user metrics will show activation-time LCP values near zero for prerendered navigations. Segment them, so they don't skew the rest of your analysis.

The key insight Speculation trades wasted work for instant navigations. Use it where prediction is reliable, such as a product list to a product page, and moderate eagerness keeps the waste low.

§4Common Mistakes

MistakeWhat HappensFix
Prerendering with immediate for many linksWasted bandwidth, CPU, and server loadUse moderate or conservative for broad rules
Counting a page view when the prerender loadsAnalytics inflated by pages never seenWait for activation before tracking
Prerendering URLs with side effectsActions run without the user's intentExclude them, and keep GET requests safe
Practice
  1. Add a speculation rule with moderate eagerness for links on a list page, and confirm in DevTools that a hover triggers a prerender.
  2. Adjust one analytics call so it only fires after the prerendered page is activated.
Key takeaways
  • Prefetch downloads the next page and prerender renders it ahead, so navigation can feel instant.
  • Speculation Rules declare targets and eagerness, and degrade gracefully where unsupported.
  • Guard against side effects and analytics during prerender, and keep wasted speculation low.
