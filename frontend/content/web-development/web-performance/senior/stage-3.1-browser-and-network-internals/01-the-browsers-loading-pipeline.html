The Browser's Loading Pipeline

The browser is not a passive renderer. It runs a parser, a speculative scanner, and a scheduler that decide what loads when. Working with them, not against them, is the senior skill.

§1Two Parsers, One Page

When HTML arrives, the main parser builds the DOM and runs scripts. If it hits a synchronous script, it stops, because the script might change the document. That could waste seconds if the page's remaining resources can't be discovered until it resumes.

To avoid this, browsers run a second, lightweight scanner called the preload scanner. While the main parser is blocked, it races ahead through the raw HTML looking for resources such as <img src>, <link rel="stylesheet">, and <script src>, and starts fetching them early.

Can the preload scanner see it?Resource
Yes<img src> and srcset in the HTML
Yes<link rel="stylesheet"> and <script src> in the HTML
Yes<link rel="preload"> hints
NoAn image set from JavaScript after load
NoA CSS background-image (found only once the CSS is parsed)
NoAn image with data-src swapped in by a lazy-loading script

This is why 'put the hero image in the HTML' is such durable advice. It makes the resource visible to a scanner that works even when the main thread is stuck.

§2From Bytes to Priority

Once a resource is discovered, the browser assigns it a priority and the network stack schedules it. Priority comes from the type of resource, its position, and hints such as fetchpriority, async, defer, and loading. HTTP/2 and HTTP/3 send that priority to the server, which can order the response bytes accordingly.

  • Highest: the document, render-blocking CSS, and often fonts used by visible text.
  • High: scripts in the head, the LCP image if the browser detects it or you hint it.
  • Low: images that start offscreen, async scripts, and prefetch.

Chrome may begin with an image at low priority, and raise it after layout when it turns out to be in the viewport. That delay is why an LCP image can start late. A fetchpriority="high" hint tells it up front.

§3Reasoning About a Load

With this model, a slow load becomes a puzzle you can solve from a trace. Ask a fixed set of questions in order.

  1. When did the HTML arrive, and was it streamed? Delays here delay discovery of everything.
  2. When did the browser first learn about each critical resource? Look for late discovery: JS-inserted, CSS-referenced, or chained behind other files.
  3. What priority did it get, and was that right? Check the Priority column, and compare with what matters.
  4. What blocked rendering? CSS and parser-blocking scripts.
  5. What happened between 'resource arrived' and 'pixels painted'? Main-thread work and render delay.

The key insight Most loading problems are discovery problems. A resource the browser doesn't know about can't be prioritized, however good your hints are, so make critical resources visible in the HTML.

§4Common Mistakes

MistakeWhat HappensFix
Inserting the LCP image from JavaScriptThe scanner can't see it, so it's fetched lateRender the <img> in the initial HTML
Relying on preload to rescue hidden resourcesYou added a hint to compensate for a structural problemFix discovery first, and use hints on top
Judging a load by total timeHides when critical things were foundRead initiator and start time per request
Practice
  1. Take a trace of a page and for the LCP resource, record when the HTML arrived, when the request started, and its initiator. Explain the gap.
  2. Change how the LCP image is referenced so the scanner can see it, and measure the difference.
Key takeaways
  • The preload scanner finds resources in raw HTML while the main parser is blocked, but cannot see JavaScript- or CSS-referenced ones.
  • Priority comes from resource type, position, and hints, and HTTP/2 and HTTP/3 pass it to the server.
  • Debug loads by asking about discovery, priority, blocking, and render delay, in that order.
