Why Server State Is Different

Data that lives on a server behaves nothing like state that lives in a component. It is shared, it can change without you knowing, and it is always slightly out of date. Treating it as a cache, not as state, changes how you build.

§1Client State vs. Server State

Client state is owned by the browser: whether a menu is open, what is typed in a field. You control it completely, and it is always current. Server state is owned by someone else and only borrowed: your component holds a snapshot of data that lives in a database, and the real thing can change at any moment.

Client stateServer state
OwnerThe appA remote database
Always up to date?YesNo: it is a snapshot that goes stale
AccessSynchronousAsynchronous: can be slow or fail
Shared with others?RarelyOften: other users and devices change it
NeedsLocal updatesCaching, refetching, invalidation, retries

When you put server data in useState and fetch it in useEffect, you take responsibility for all the problems in the right-hand column, and you will rediscover each of them as a bug.

§2The Problems You Inherit

  • Caching: if two components need /api/user, do you fetch twice? If the user returns to a page, do you show the old data instantly, or a spinner again?
  • Staleness: how old can data be before it is wrong? When should it refresh: on a timer, when the window regains focus, when the network reconnects?
  • Deduplication: ten components mounting at once should cause one request, not ten.
  • Race conditions: out-of-order responses and cancelled requests.
  • Background updates: show the cached data immediately and update it quietly (stale-while-revalidate).
  • Invalidation: after the user changes something (a mutation), which cached data is now wrong and needs refetching?
  • Retries and errors: transient failures should retry; permanent ones should show a useful message.
  • Pagination, prefetching, and garbage collection of data no one is using any more.
// the hand-rolled version handles almost none of the above
function useUser(id) {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetch(`/api/users/${id}`).then((r) => r.json()).then(setUser);
  }, [id]);
  return user;                                  // no cache, no error state, no dedupe, race condition
}

§3A New Mental Model: A Cache with Keys

The shift is to see server data as a cache that your UI subscribes to. Each piece of data is stored under a key (such as ["user", 42]). Components ask for a key; a library returns the cached value (if any), fetches or refreshes it when necessary, and tells every subscriber when it changes.

// the shape of the idea (a library does the work)
const { data, isPending, error, isFetching } = useQuery({
  queryKey: ["user", id],                   // identifies the data
  queryFn: () => getUser(id),               // how to get it
  staleTime: 60_000,                        // treat it as fresh for a minute
});
  • Fresh data is served from cache without a request; stale data is served from cache and refetched in the background.
  • Your component no longer manages loading flags, effects, or cleanup; it declares which data it needs.
  • After a mutation, you invalidate the affected keys and the library refetches whatever is on screen.
  • Server state is not a replacement for client state: keep UI state (modals, form drafts) in components or a small client store.

In the next lesson you will use TanStack Query, the most widely used library for this. Others (SWR, RTK Query, Apollo for GraphQL, and framework loaders) follow the same model.

You are caching, whether you admit it or not Every useState holding fetched data is a hand-written cache with no invalidation strategy. Naming it a cache is the first step to managing it properly.

§4Common Mistakes

MistakeWhat HappensFix
Copying fetched data into useState and treating it as local stateIt goes stale and diverges from the serverRead it from a query cache and invalidate on change
Refetching on every mount with a spinner each timeSlow, flickering UICache and show stale data while refreshing
Fetching the same endpoint independently in many componentsDuplicate requests and inconsistent viewsShare one cached query by key
Ignoring what happens after a mutationThe screen shows pre-change dataInvalidate or update the affected cache entries
Practice
  1. List every data fetch in an app and, for each, write how fresh it must be and what should refresh it.
  2. Open two components that fetch the same endpoint with raw effects and count the requests in the Network panel.
  3. Describe in your own words what "stale" means and why showing stale data while refetching can be good UX.
Key takeaways
  • Server state is borrowed, asynchronous, shared, and always potentially stale; client state is not.
  • Hand-rolling it means reimplementing caching, deduplication, invalidation, and retries.
  • Treat it as a keyed cache your UI subscribes to, and let a library manage freshness.
