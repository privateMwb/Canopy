Optimistic Updates

Waiting for the server before showing a change makes an app feel sluggish. Optimistic updates show the result immediately and quietly undo it if the request fails.

§1The Idea

An optimistic update assumes the server will accept the change, so the UI updates right away. If the request later fails, you roll back to the previous state and tell the user. It suits actions that almost always succeed and where the result is easy to predict: toggling a like, ticking a to-do, reordering a list.

Use optimistic updates forAvoid them for
Likes, favorites, checkboxes, togglesPayments, orders, anything irreversible
Adding or removing a simple list itemActions with complex server-side validation or results you cannot predict
Drag-and-drop reorderingOperations where failure is common
Inline edits of simple fieldsAnything that must show server-generated data (totals, ids) before continuing

§2The Cache-Based Pattern

With TanStack Query, you edit the cache before the request completes. The pattern has four steps: cancel in-flight fetches, snapshot the current data, write the optimistic value, and restore the snapshot on error. Always refetch at the end so the cache matches the server.

const toggle = useMutation({
  mutationFn: (todo) => api.updateTodo(todo.id, { done: !todo.done }),

  onMutate: async (todo) => {
    await queryClient.cancelQueries({ queryKey: ["todos"] });       // stop a refetch from overwriting us
    const previous = queryClient.getQueryData(["todos"]);            // snapshot for rollback

    queryClient.setQueryData(["todos"], (old) =>
      old.map((t) => (t.id === todo.id ? { ...t, done: !t.done } : t))
    );
    return { previous };                                             // passed to onError as context
  },

  onError: (err, todo, context) => {
    queryClient.setQueryData(["todos"], context.previous);          // roll back
    toast.error("Could not update. Your change was undone.");
  },

  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ["todos"] });         // sync with the server either way
  },
});

<input type="checkbox" checked={todo.done} onChange={() => toggle.mutate(todo)} />

cancelQueries matters: without it, a background refetch that was already running could return old data and overwrite your optimistic update, causing a flicker. Return the snapshot from onMutate so onError can restore it.

§3Simpler Option and Edge Cases

For a simple, single-place update you can skip cache surgery and use the mutation's own variables to render the pending value. React 19 also provides useOptimistic for this pattern with forms and actions.

// render pending state from the mutation itself
const { mutate, variables, isPending } = useMutation({ mutationFn: addTodo, onSettled: refetchList });

<ul>
  {todos.map((t) => <li key={t.id}>{t.title}</li>)}
  {isPending && <li style={{ opacity: 0.5 }}>{variables.title}</li>}   {/* shown until it settles */}
</ul>

// React 19: useOptimistic
const [optimisticTodos, addOptimistic] = useOptimistic(todos, (list, title) => [...list, { id: "tmp", title, pending: true }]);
  • Always tell the user on failure; silently reverting looks like a bug.
  • Mark optimistic items visually when it helps (reduced opacity, a small spinner), and avoid letting users act on temporary ids.
  • Replace temporary ids with server ids after success (the final refetch does this).
  • Handle rapid repeated actions: either disable the control while pending, or make sure rollbacks do not clobber later optimistic changes.
  • Keep a way to retry a failed action when it matters.
  • Test the failure path deliberately (force the API to return 500) so you know the rollback works.
Fast when it works, honest when it does not The optimistic path is only half the feature. The rollback and the message are what keep users trusting an interface that moves ahead of the server.

§4Common Mistakes

MistakeWhat HappensFix
Skipping cancelQueries before the optimistic writeA refetch in flight overwrites the update and the UI flickersCancel related queries first
Not storing a snapshot for rollbackNo way to undo on errorReturn the previous data from onMutate
Optimistically updating irreversible or unpredictable actionsUI shows success that never happensWait for the server on payments and complex operations
Reverting silently on failureUsers think the app lost their changeShow an error and offer retry
Practice
  1. Add an optimistic toggle to a to-do list with snapshot, rollback, and a final invalidate.
  2. Force the API to fail 50% of the time and verify the rollback and the error message.
  3. Rewrite a simple add-item mutation to render the pending item from variables without touching the cache.
Key takeaways
  • Optimistic updates show the expected result immediately and roll back on failure.
  • Cancel in-flight queries, snapshot, write optimistically, restore on error, and invalidate when settled.
  • Use them for likely-to-succeed, reversible actions, and always handle and explain failure.
