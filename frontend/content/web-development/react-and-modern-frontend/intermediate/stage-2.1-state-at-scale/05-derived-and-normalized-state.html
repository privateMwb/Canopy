Derived & Normalized State

Two copies of the same fact will eventually disagree. Deriving values instead of storing them, and normalizing nested data so each entity lives in exactly one place, keeps the UI consistent as the app grows.

§1Derive, Do Not Duplicate

Store the minimum state needed to describe the UI, and compute everything else during render. Every extra copy is a chance for the two to drift apart when only one gets updated.

// duplicated: selectedItem is a copy that goes stale
const [items, setItems] = useState(initialItems);
const [selectedItem, setSelectedItem] = useState(items[0]);
// rename items[0] in setItems and selectedItem still shows the old name

// minimal: store the id, derive the object
const [items, setItems] = useState(initialItems);
const [selectedId, setSelectedId] = useState(items[0].id);
const selected = items.find((i) => i.id === selectedId);

// other derived values: counts, filtered lists, totals, validity
const doneCount = todos.filter((t) => t.done).length;
const visible = todos.filter(matchesFilter(filter));
const isValid = email.includes("@") && password.length >= 8;

Ask of every piece of state: *can I calculate this from other state or props?* If yes, it should not be state. If calculating it is expensive, cache it with useMemo (or let the React Compiler do it), but do not move it into state.

§2Normalizing Nested Data

APIs often return nested data: a list of posts, each with its author and comments. If the same author appears in many posts and you store each copy inside its post, updating the author means finding and changing every copy, and missing one leaves the UI inconsistent.

// nested: the same author is duplicated in every post
const posts = [
  { id: 1, title: "A", author: { id: 7, name: "Ada" } },
  { id: 2, title: "B", author: { id: 7, name: "Ada" } },
];

// normalized: each entity once, referenced by id
const state = {
  users: { 7: { id: 7, name: "Ada" } },
  posts: { 1: { id: 1, title: "A", authorId: 7 }, 2: { id: 2, title: "B", authorId: 7 } },
  postIds: [1, 2],                              // order
};

// update the name once and every post shows it
const renameUser = (state, id, name) => ({
  ...state,
  users: { ...state.users, [id]: { ...state.users[id], name } },
});

// join at read time
const postView = (id) => ({ ...state.posts[id], author: state.users[state.posts[id].authorId] });

Normalized state looks like a small database: tables keyed by id, with foreign keys instead of embedded copies. Updates become simple and local, and lookups are O(1). It also makes deep updates in nested arrays much simpler than copy-spreading through many levels.

§3When to Normalize (and When Not To)

  • Normalize when entities are shared across places, edited frequently, or deeply nested.
  • Do not normalize read-only data you display once and never update, or small, flat lists; the extra bookkeeping is not worth it.
  • Server data usually lives in a query cache, where TanStack Query already deduplicates by key. Normalize in the cache only if you have clear cross-list consistency problems. Libraries such as RTK Query and Apollo offer normalization for that.
  • Redux Toolkit's createEntityAdapter provides ready-made normalized state with selectors and CRUD reducers.
  • Prefer Map or plain objects keyed by id, and keep a separate array of ids when order matters.
  • Keep UI state (which row is expanded, what is selected) separate from entity data, and reference entities by id.
import { createEntityAdapter, createSlice } from "@reduxjs/toolkit";

const usersAdapter = createEntityAdapter();       // { ids: [], entities: {} } plus helpers
const usersSlice = createSlice({
  name: "users",
  initialState: usersAdapter.getInitialState(),
  reducers: {
    loaded: usersAdapter.setAll,
    renamed: (state, { payload }) => usersAdapter.updateOne(state, { id: payload.id, changes: { name: payload.name } }),
  },
});
One fact, one place Whenever the same data exists twice, ask which is the source of truth, and delete the other. Store ids, derive objects, and keep each entity in exactly one spot.

§4Common Mistakes

MistakeWhat HappensFix
Storing the selected object instead of its idSelection shows stale data after the item is editedStore selectedId and derive the item
Keeping filteredItems in state alongside items and filterLists get out of syncCompute the filtered list during render
Updating a duplicated entity in only one placeDifferent parts of the UI disagreeNormalize so each entity is stored once
Normalizing small read-only dataMore code and complexity with no benefitNormalize only shared, frequently updated data
Practice
  1. Refactor a component that stores selectedItem and filteredItems in state so that it stores only selectedId and filter and derives the rest.
  2. Normalize a posts-with-authors array into users and posts maps, and write a function that renames a user once.
  3. Identify one place in a project where two copies of the same data could disagree, and describe the fix.
Key takeaways
  • Store the minimal state; derive selections, counts, filters, and validity during render.
  • Normalize shared nested data into id-keyed tables so each entity is stored once.
  • Normalize where it removes real duplication, and keep UI state separate from entity data.
