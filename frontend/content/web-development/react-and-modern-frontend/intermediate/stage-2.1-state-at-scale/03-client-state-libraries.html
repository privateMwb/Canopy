Client State Libraries

Some state is shared widely and changes often: a shopping cart, UI panels, editor settings. Libraries like Zustand and Redux Toolkit manage that state outside components and let each component subscribe to only what it needs.

§1What They Add Over Context

A client-state library keeps state in a store outside the React tree. Components read it through a hook with a selector, and React re-renders a component only when its selected slice changes. Updates are written as plain functions you can call from anywhere, including outside components.

NeedContext + useStateState library
Read one field without re-rendering on othersNo (all consumers re-render)Yes, via selectors
Update from outside React (an event listener, a WebSocket)AwkwardEasy: call the store
DevTools, time travel, middleware, persistenceBuild yourselfOften built in
Small, local, or infrequent statePerfectOverkill

§2Zustand: Minimal and Direct

Zustand is a tiny store with almost no boilerplate. You define state and actions together in one function, and consume them with a hook.

import { create } from "zustand";

const useCart = create((set, get) => ({
  items: [],
  add: (product) =>
    set((s) => {
      const existing = s.items.find((i) => i.id === product.id);
      return existing
        ? { items: s.items.map((i) => (i.id === product.id ? { ...i, qty: i.qty + 1 } : i)) }
        : { items: [...s.items, { ...product, qty: 1 }] };
    }),
  remove: (id) => set((s) => ({ items: s.items.filter((i) => i.id !== id) })),
  total: () => get().items.reduce((sum, i) => sum + i.price * i.qty, 0),
}));

function CartBadge() {
  const count = useCart((s) => s.items.length);        // re-renders only when this changes
  return <span>{count}</span>;
}

function AddButton({ product }) {
  const add = useCart((s) => s.add);                    // functions are stable
  return <button onClick={() => add(product)}>Add</button>;
}

Always pass a selector. Calling useCart() with no selector subscribes to the whole store, and the component re-renders on every change. To select several values, use useShallow from zustand/react/shallow so a new object with equal fields does not trigger a render.

§3Redux Toolkit: Structure for Big Teams

Redux Toolkit (RTK) is the modern, official way to use Redux. It reduces the old boilerplate with createSlice, which generates actions and a reducer together, and lets you write "mutating" code that Immer turns into immutable updates behind the scenes.

import { configureStore, createSlice } from "@reduxjs/toolkit";
import { Provider, useSelector, useDispatch } from "react-redux";

const cartSlice = createSlice({
  name: "cart",
  initialState: { items: [] },
  reducers: {
    added(state, action) {                              // Immer: this "mutation" is safe
      const item = state.items.find((i) => i.id === action.payload.id);
      if (item) item.qty += 1;
      else state.items.push({ ...action.payload, qty: 1 });
    },
    removed(state, action) {
      state.items = state.items.filter((i) => i.id !== action.payload);
    },
  },
});

export const { added, removed } = cartSlice.actions;
export const store = configureStore({ reducer: { cart: cartSlice.reducer } });

function CartBadge() {
  const count = useSelector((s) => s.cart.items.length);
  return <span>{count}</span>;
}
// <Provider store={store}><App /></Provider>

RTK gives you strict conventions, excellent DevTools (every action is logged and replayable), middleware, and RTK Query for server data. That structure pays off in large codebases with many contributors, and costs ceremony in small ones.

§4Choosing

  • Start without a library. useState, useReducer, lifted state, and a little context cover most apps.
  • Server data does not belong here. Use TanStack Query (next stage); it removes most of what people used global stores for.
  • Reach for a library when the same client state is needed by distant components, changes often, or must be updated from outside React.
  • Zustand for small-to-medium apps and quick wins; Redux Toolkit when you want strict structure, strong tooling, and team conventions.
  • Keep stores small and domain-focused (a cart store, a UI store) rather than one global blob.
  • Do not put form field state, or state used by only one component, in a global store.
Server data is not client state Most state that people put in Redux is really a cache of server data. Move that to a query library first, and you may find you need very little global client state at all.

§5Common Mistakes

MistakeWhat HappensFix
Subscribing to the whole store without a selectorComponent re-renders on every store changeSelect only what you need
Putting server responses in a client storeYou reimplement caching, staleness, and refetching badlyUse TanStack Query or RTK Query
Mutating state in Zustand setNo re-render; subtle bugsReturn new objects (or use the immer middleware)
Adding a state library to a small app out of habitExtra concepts and bundle for nothingStart with local state and add a library when pain appears
Practice
  1. Build a cart store in Zustand with add, remove, and a derived total, and prove with logs that a badge re-renders only when the count changes.
  2. Rebuild the same cart with Redux Toolkit and compare the amount of code and the DevTools experience.
  3. List the pieces of state in an app you know and classify each as local, shared client, or server state.
Key takeaways
  • State libraries store state outside React and let components subscribe to slices with selectors.
  • Zustand is minimal; Redux Toolkit adds structure, tooling, and conventions for larger teams.
  • Reach for them only for widely shared client state; keep server data in a query library.
