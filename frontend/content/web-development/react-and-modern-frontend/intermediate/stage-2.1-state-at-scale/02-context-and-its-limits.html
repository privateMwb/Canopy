Context & Its Limits

Context passes data to deep components without threading props through every layer. It is the right tool for a few kinds of data, and a surprisingly common source of slow apps when used for everything.

§1Creating and Using Context

Context has three parts: create it, provide a value near the top of the tree, and consume it in any descendant with useContext. Components in between do not need to know about it.

import { createContext, useContext, useState } from "react";

const ThemeContext = createContext("light");           // default if there is no provider

export function ThemeProvider({ children }) {
  const [theme, setTheme] = useState("light");
  return (
    <ThemeContext value={{ theme, setTheme }}>        {/* React 19: render the context directly */}
      {children}
    </ThemeContext>
  );
}

export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx || typeof ctx === "string") throw new Error("useTheme must be used inside ThemeProvider");
  return ctx;
}

function ThemeToggle() {
  const { theme, setTheme } = useTheme();
  return <button onClick={() => setTheme(theme === "light" ? "dark" : "light")}>{theme}</button>;
}

Wrapping useContext in a custom hook like useTheme gives a clear error when the provider is missing and hides the context object from the rest of the app. (In React 18 and earlier, you write <ThemeContext.Provider value={...}>.)

§2The Re-render Cost

Whenever the value passed to a provider changes, every component that calls useContext for it re-renders, even if it uses only a part of the value. And an object literal like value={{ theme, setTheme }} is a new object on every render of the provider, so consumers re-render whenever the provider does.

// the value object is recreated each render of the provider
<ThemeContext value={{ theme, setTheme }}>

// stabilize it (the React Compiler can often do this for you)
const value = useMemo(() => ({ theme, setTheme }), [theme]);
<ThemeContext value={value}>

// split contexts by how often they change and who needs them
<UserContext value={user}>                // changes rarely
  <ThemeContext value={theme}>            // changes sometimes
    <NotificationsContext value={unread}> {/* changes often */}
  • Context does not provide selectors: a consumer cannot subscribe to just one field. If different parts of the value change at different rates, split them into separate contexts.
  • Keep the provider's children stable: state inside the provider re-renders the provider, but children passed from above are the same element objects, so they skip re-rendering unless they consume the context.
  • Put the state and the provider in one component and receive children; do not render big subtrees inside the same component that holds frequently changing state.

§3When Context Is the Right Tool

Context is best for data that is read widely, changes infrequently, and is conceptually global to a subtree.

Good fitPoor fit
Theme, locale, color modeFast-changing values (mouse position, a form's fields)
The current user / auth sessionLarge, frequently updated application state
Feature flags, configServer data (use a query library: it handles caching and refetching)
A compound component's shared stateState used by only a parent and its direct children (just pass props)

Before reaching for context to avoid prop drilling, try composition: pass the lower component itself as children or a prop, so intermediate layers never see the data. Many cases of "drilling" disappear that way. For genuinely global, frequently changing client state, a dedicated library (next lesson) with selectors will serve you better than a large context.

// instead of drilling `user` through Layout -> Header -> Menu
function Page({ user }) {
  return <Layout header={<Header menu={<UserMenu user={user} />} />} />;
}
// Layout and Header never touch `user`
Context is for reading, not for performance Context avoids passing props. It does not make updates cheaper, and a changing value re-renders every consumer. Use it for slow-changing, widely read data, and split it when parts change at different speeds.

§4Common Mistakes

MistakeWhat HappensFix
Putting all app state in one big contextEvery change re-renders every consumerSplit by update frequency, or use a state library with selectors
Passing value={{ a, b }} inline without stabilizingConsumers re-render whenever the provider rendersMemoize the value (or rely on the React Compiler)
Using context for server dataHand-rolled caching and refetching bugsUse TanStack Query or framework loaders
Reading context without a providerSilent defaults and confusing bugsThrow an error in a custom useX hook when missing
Practice
  1. Build a theme context with a useTheme hook that throws if used outside the provider.
  2. Make a context whose value changes every second, add console.log to consumers, and observe the re-renders. Then split the context to confine them.
  3. Remove a prop-drilled prop by restructuring with children instead of context.
Key takeaways
  • Context shares data with descendants without prop threading; wrap it in a custom hook.
  • A changed value re-renders all consumers, with no selectors, so split contexts by update rate.
  • Use it for slow-changing global data; prefer composition for drilling and libraries for heavy state.
