Mocking the Network

Components that fetch data need a fake server to test against. Mock Service Worker intercepts real requests at the network level, so your components run unchanged and your tests exercise the real fetching code.

§1Why Not Mock fetch Directly

You can replace fetch with vi.fn() and return canned responses, but that couples the test to how the code calls the network (which function, which arguments). Switch from fetch to Axios, or add a query library, and every test breaks even though behavior is identical. Mock Service Worker (MSW) intercepts requests outside your code, as a stand-in for the server, so the app code under test is exactly what ships.

ApproachStrengthWeakness
vi.fn() replacing fetchQuick for one functionTied to implementation; hides real request/response handling
MSW handlersRealistic: tests the real fetching code; reusable in dev, tests, and StorybookSome setup
Real test backendHighest fidelitySlow, flaky, needs data management

§2Setting Up MSW

Define handlers that describe the API, start a server in your test setup, reset handlers between tests, and override handlers inside a test to simulate errors or edge cases.

// src/test/handlers.ts
import { http, HttpResponse } from "msw";

export const handlers = [
  http.get("/api/todos", () =>
    HttpResponse.json([{ id: 1, title: "Write tests", done: false }])
  ),
  http.post("/api/todos", async ({ request }) => {
    const body = (await request.json()) as { title: string };
    return HttpResponse.json({ id: 2, title: body.title, done: false }, { status: 201 });
  }),
];

// src/test/server.ts
import { setupServer } from "msw/node";
import { handlers } from "./handlers";
export const server = setupServer(...handlers);

// src/test/setup.ts
import { beforeAll, afterEach, afterAll } from "vitest";
import { server } from "./server";

beforeAll(() => server.listen({ onUnhandledRequest: "error" }));   // fail on requests you forgot to mock
afterEach(() => server.resetHandlers());                           // undo per-test overrides
afterAll(() => server.close());

onUnhandledRequest: "error" is valuable: a test that makes an unmocked request fails loudly instead of silently hitting the real network.

§3Testing Loading, Success, Error, and Mutations

test("shows todos from the API", async () => {
  renderWithProviders(<Todos />);

  expect(screen.getByText(/loading/i)).toBeInTheDocument();
  expect(await screen.findByText("Write tests")).toBeInTheDocument();
});

test("shows an error when the API fails", async () => {
  server.use(http.get("/api/todos", () => new HttpResponse(null, { status: 500 })));   // override for this test
  renderWithProviders(<Todos />);

  expect(await screen.findByRole("alert")).toHaveTextContent(/could not load/i);
});

test("adds a todo and shows it", async () => {
  const user = userEvent.setup();
  renderWithProviders(<Todos />);
  await screen.findByText("Write tests");

  await user.type(screen.getByLabelText(/new todo/i), "Ship it");
  await user.click(screen.getByRole("button", { name: /add/i }));

  expect(await screen.findByText("Ship it")).toBeInTheDocument();
});
  • Test the error and empty paths, not just success: they are where UI bugs hide.
  • Make handlers stateful when needed (an in-memory array) so a POST followed by a GET returns the new item.
  • Simulate slowness with await delay(200) from msw to test loading states and race conditions.
  • Create a fresh QueryClient per test with retries disabled, or failures retry and tests time out.
  • Reuse the same handlers in the browser (setupWorker) to develop against a fake API, and in Storybook.
  • Keep handler data realistic and typed; share types or schemas with the real API client.
Mock the server, not your code Intercepting at the network boundary means your fetching, parsing, and error handling are all under test. Only the thing you do not control, the server, is faked.

§4Common Mistakes

MistakeWhat HappensFix
Mocking fetch with vi.fn() in every testTests break when the implementation changesUse MSW handlers at the network layer
Not resetting handlers between testsAn error override leaks into later testsserver.resetHandlers() in afterEach
Letting unmocked requests throughTests secretly hit a real networkonUnhandledRequest: "error"
Reusing one QueryClient across tests, with retries onCached data leaks; failure tests hangNew client per test with retry: false
Practice
  1. Set up MSW and write tests for a list's loading, success, and error states.
  2. Add a stateful handler so that creating an item and then reloading shows it.
  3. Use delay to test that a spinner appears, and that a stale response never overwrites a newer one.
Key takeaways
  • MSW intercepts requests at the network layer, so tests exercise your real data-fetching code.
  • Set onUnhandledRequest: "error", reset handlers each test, and override per test for error cases.
  • Test loading, success, empty, and error states, with a fresh query client per test.
