Linting, CI & Code Quality

Automated checks catch bugs and keep a team's code consistent without anyone arguing in review. A small set of tools, run on every commit and pull request, is worth far more than a long list of rules.

§1ESLint for React

ESLint reports likely bugs. The two React plugins matter most: eslint-plugin-react-hooks enforces the Rules of Hooks and checks effect dependencies, and eslint-plugin-jsx-a11y flags accessibility problems. Vite's templates include a starting configuration.

// eslint.config.js (flat config)
import js from "@eslint/js";
import tseslint from "typescript-eslint";
import reactHooks from "eslint-plugin-react-hooks";
import jsxA11y from "eslint-plugin-jsx-a11y";

export default tseslint.config(
  js.configs.recommended,
  ...tseslint.configs.recommended,
  jsxA11y.flatConfigs.recommended,
  {
    plugins: { "react-hooks": reactHooks },
    rules: {
      "react-hooks/rules-of-hooks": "error",          // hooks only at the top level
      "react-hooks/exhaustive-deps": "error",         // complete dependency arrays
      "@typescript-eslint/no-explicit-any": "warn",
      "no-console": ["warn", { allow: ["warn", "error"] }],
    },
  }
);
  • Treat exhaustive-deps as an error. Disabling it for a line almost always hides a stale-closure bug; restructure the code instead.
  • Use Prettier for formatting and keep formatting rules out of ESLint, so the two tools do not conflict.
  • Add rules for mistakes your team actually makes, not every rule available. Noise teaches people to ignore the linter.
  • Run npx eslint . locally and in CI, and use --fix for safe automatic fixes.

§2Automating Checks: Hooks and CI

Checks only help if they always run. Run fast ones before each commit, and the full set on every pull request so nothing broken reaches the main branch.

// package.json
{
  "scripts": {
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "e2e": "playwright test",
    "build": "vite build"
  },
  "lint-staged": { "*.{ts,tsx,js,jsx}": ["eslint --fix", "prettier --write"] }
}

# .github/workflows/ci.yml
name: CI
on: [pull_request]
jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm test
      - run: npm run build
  • Pre-commit (husky plus lint-staged) runs lint and format on changed files only, so it stays fast.
  • CI runs the complete suite: lint, type check, tests, and build. Make it a required check for merging.
  • Use npm ci (not npm install) for exact, reproducible installs from the lockfile.
  • Run slower E2E tests in a separate job, and cache dependencies and browsers to keep CI quick.
  • Keep the pipeline fast (aim for minutes, not tens of minutes) or people will route around it.

§3Quality Beyond Linting

Tools cannot judge design, but they can reduce what humans have to look at in review, so reviewers spend time on the important questions.

Tool or habitWhat it catches
TypeScript strictWrong props, null errors, impossible states
react-hooks lint rulesStale closures, conditional hooks
Bundle size check (size-limit)Accidental large dependencies
Dependabot / RenovateOutdated and vulnerable packages
npm audit, Socket, SnykKnown vulnerabilities and suspicious packages
Lighthouse CIPerformance, accessibility, and SEO regressions
Coverage reportUntested code (as a guide, never a goal)
Pull request template and review checklistMissing tests, accessibility, and states
  • Fix warnings or remove the rule. A codebase with hundreds of ignored warnings has no working linter.
  • Prefer fast, deterministic checks. Flaky checks erode trust in all of them.
  • Do not chase 100% coverage; test behavior that matters, including error states.
  • Document how to run each check locally, so a new teammate gets the same results as CI.
Automate the arguments Style, hook rules, types, and tests should be settled by machines on every commit. That leaves code review for what only people can judge: design, naming, and whether the change is the right one.

§4Common Mistakes

MistakeWhat HappensFix
Disabling react-hooks/exhaustive-deps to silence itStale values and subtle bugsFix the dependencies or restructure the effect
Checks that run only on a developer's machineBroken code reaches the main branchRun them in CI as required checks
Enabling every lint ruleNoise leads people to ignore all warningsKeep a small set aimed at real bugs
Slow CI that nobody waits forPeople merge without results or skip checksCache, parallelize, and split slow jobs
Practice
  1. Add eslint-plugin-react-hooks and jsx-a11y to a project and fix every finding without disabling rules.
  2. Set up a pre-commit hook with lint-staged that lints and formats only staged files.
  3. Write a CI workflow that runs lint, type check, tests, and build on pull requests, and make it required for merging.
Key takeaways
  • ESLint with the hooks and accessibility plugins catches real React bugs; treat exhaustive-deps as an error.
  • Run fast checks on commit and the full suite in CI as a required gate.
  • Keep rules few and meaningful, fix warnings, and keep the pipeline fast.
