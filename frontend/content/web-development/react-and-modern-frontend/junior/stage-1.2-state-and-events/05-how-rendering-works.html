How Rendering Works

Knowing what "render" means, and when React does it, explains why state updates look asynchronous and why your component runs more often than you expect.

§1Render and Commit

In React, rendering means calling your component function to find out what UI it describes. It is not the same as drawing to the screen. A state change goes through three steps:

  1. Trigger: something asks for an update, either the first mount or a state setter call.
  2. Render: React calls your components to compute the new UI description, from the changed component downward.
  3. Commit: React applies the differences to the real DOM, then the browser paints.

If the rendered output is identical to last time, React makes no DOM changes at all. Rendering is cheap and ordinary: your components may run many times, and that is by design. This is why component bodies must be pure, with no side effects such as changing outside variables or fetching data directly.

§2Why State Updates Look Asynchronous

Calling a setter does not run your component immediately. It schedules a render. Until then, your code continues to see the old snapshot of state. React also batches multiple setter calls from the same event into one render, which saves work.

function Form() {
  const [first, setFirst] = useState("");
  const [count, setCount] = useState(0);

  function handleClick() {
    setFirst("Ada");
    setCount(count + 1);
    console.log(first, count);      // still the OLD values: "", 0
  }                                 // one render happens after the handler finishes

  console.log("render", first, count);   // runs once per batch, with the new values
  return <button onClick={handleClick}>Go</button>;
}

Batching applies everywhere in modern React, including inside promises, timeouts, and native event handlers. If you need the next value inside the same handler, compute it into a variable and use that variable.

function handleSubmit() {
  const next = count + 1;
  setCount(next);
  save(next);               // use the computed value, not `count`
}

§3What Causes a Re-render

A component re-renders when its own state changes, when its parent re-renders, or when a context it reads changes. Notice that changing props is not the trigger: if a parent re-renders, every child re-renders by default, even if the props are the same.

CauseRe-renders
setState with a different valueThat component and its descendants
setState with the same value (Object.is)Usually nothing
Parent re-rendersAll children, even with unchanged props
Context value changesEvery component using that context
  • Plain variables are recreated each render and do not trigger one: only state does.
  • In development, StrictMode renders components twice to help you find impure code. This is expected, and does not happen in production.
  • Do not optimize re-renders early. Most are fast. Measure with the React DevTools Profiler first (you will learn this in the next stages).
  • Each render gets its own props, state, and handlers, a *snapshot*. A handler created in one render keeps seeing that render's values.
function Counter() {
  const [n, setN] = useState(0);

  function handleAlert() {
    setTimeout(() => alert(n), 3000);   // shows the value from the render where you clicked
  }

  return (
    <>
      <button onClick={() => setN(n + 1)}>+1 ({n})</button>
      <button onClick={handleAlert}>Alert in 3s</button>
    </>
  );
}
Render is calculating, commit is changing React may call your component many times to work out what the screen should be. Only the commit touches the DOM. Keep render functions pure and cheap, and let React decide when to commit.

§4Common Mistakes

MistakeWhat HappensFix
Reading state right after calling the setter and expecting the new valueYou see the old value in the same handlerCompute the next value in a variable and use it
Fetching data or changing globals inside the component bodyRuns on every render, including extra StrictMode onesPut side effects in event handlers or useEffect
Assuming a child only re-renders when its props changeUnexpected re-renders when the parent updatesKnow the default; profile before reaching for memo
Storing a mutable value in a plain let and expecting it to persistIt resets every renderUse state (or a ref for non-visual values)
Practice
  1. Add console.log("render") to a component, click a button that sets state to the same value, and observe whether it logs.
  2. Write a handler that calls three setters and confirm the component renders once, using a log in the body.
  3. Reproduce the "alert shows an old number" example and explain the result using the snapshot idea.
Key takeaways
  • Rendering calls your component to compute UI; committing applies the DOM changes.
  • State updates are scheduled and batched, so the current snapshot does not change mid-handler.
  • Components re-render on state changes, parent renders, and context changes; keep render pure.
