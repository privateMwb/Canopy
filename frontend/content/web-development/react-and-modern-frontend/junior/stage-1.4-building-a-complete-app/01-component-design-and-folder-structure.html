Component Design & Folder Structure

The hardest part of a growing React app is rarely any single hook. It is deciding what each component should be responsible for, and where its files live, so that the next change is easy.

§1Splitting Components

Start from the design. Draw a box around each piece of the UI, and name it. Each box that has one clear job becomes a component. A reliable way to split is by asking three questions: is this piece repeated? Does it have its own state or logic? Is the parent getting too long to read?

// before: one component doing everything
function ProductPage() { /* 300 lines: header, filters, list, cart */ }

// after: each piece has a name and a job
function ProductPage() {
  const [query, setQuery] = useState("");
  const products = useProducts();                 // data logic is separate
  const visible = filterProducts(products, query);

  return (
    <>
      <PageHeader title="Shop" />
      <SearchBox value={query} onChange={setQuery} />
      <ProductGrid products={visible} />
    </>
  );
}
  • A component should be describable in one sentence without the word "and".
  • Prefer many small components over deeply nested JSX, but do not split into fragments with no meaning (DivWrapper, Section2).
  • Presentational components receive data and render it; container-style components fetch and hold state. Keeping them separate makes both easier to reuse and test.
  • Do not copy-paste a component to change one thing; add a prop or use composition.

§2Naming Things

Good names make code readable without comments. Follow the conventions React developers expect.

ThingConventionExample
ComponentPascalCase, named for what it isProductCard, UserMenu
Component fileSame as the componentProductCard.jsx
HookuseCamelCase, starts with useuseProducts, useDebounced
Event handler (inside)handleXhandleSubmit
Event handler (prop)onXonSubmit, onSelect
BooleanisX, hasX, canXisOpen, hasError

§3Folder Structure

There is no required structure, and the best one changes as the app grows. A small app can be organized by type; once it has several features, organize by feature so related files live together.

// small app: by type
src/
  components/    Button.jsx  Card.jsx  Navbar.jsx
  pages/         Home.jsx  Movie.jsx
  hooks/         useMovies.js
  api/           movies.js
  main.jsx  App.jsx

// growing app: by feature, with shared pieces separate
src/
  features/
    movies/
      MovieList.jsx
      MovieCard.jsx
      useMovies.js
      api.js
      movies.test.jsx
    cart/
      ...
  components/    // shared UI used by many features
  lib/           // helpers (formatters, constants)
  • Colocate: keep a component's styles, tests, and helpers next to it. Things that change together should live together.
  • Promote code to a shared folder only when a second place needs it.
  • Avoid very deep nesting and avoid circular imports (feature A importing from feature B and back).
  • Use an index.js sparingly: barrel files can slow builds and make imports harder to trace.
  • Do not agonize: moving files later is cheap with a good editor. Start simple.
Organize for the next change A good structure is one where adding a feature touches a few files in one place, and deleting a feature means deleting one folder.

§4Common Mistakes

MistakeWhat HappensFix
One giant component with everything in itImpossible to read, test, or reuseSplit by responsibility; name each piece
Over-splitting into meaningless wrappersIndirection with no benefitSplit when there is a clear job, repetition, or length
Putting every file in one flat components/ folder foreverHard to find related code as the app growsMove to feature folders and colocate
Importing across features in both directionsCircular dependencies and fragile buildsExtract the shared piece to a common folder
Practice
  1. Take a long component and split it into at least four named components, each describable in one sentence.
  2. Reorganize a small app from type-based folders into feature folders, and note what became easier or harder.
  3. Rename five things (components, handlers, booleans) in your code to follow the conventions above.
Key takeaways
  • Split components by clear responsibility, repetition, and readability.
  • Follow naming conventions: PascalCase components, useX hooks, handleX/onX handlers.
  • Organize by type when small and by feature as you grow; colocate files that change together.
