Fetching Data

Almost every app loads data from a server. The pattern is the same each time: start in a loading state, end in either success or error, and make sure the screen shows each of the three honestly.

§1Three States, Not One

A request is not "data or no data". It is loading, then success or error. If you only handle success, users see a blank screen while waiting and nothing at all when the request fails. Model all three explicitly in state.

function Users() {
  const [users, setUsers] = useState([]);
  const [status, setStatus] = useState("loading");   // "loading" | "error" | "success"
  const [error, setError] = useState(null);

  useEffect(() => {
    async function load() {
      try {
        const res = await fetch("https://jsonplaceholder.typicode.com/users");
        if (!res.ok) throw new Error(`HTTP ${res.status}`);   // fetch does not reject on 404/500
        setUsers(await res.json());
        setStatus("success");
      } catch (err) {
        setError(err.message);
        setStatus("error");
      }
    }
    load();
  }, []);

  if (status === "loading") return <p>Loading...</p>;
  if (status === "error") return <p role="alert">Could not load users: {error}</p>;
  return <ul>{users.map((u) => <li key={u.id}>{u.name}</li>)}</ul>;
}

Remember that fetch only rejects on network failure. A 404 or 500 still fulfills the promise, so check res.ok yourself. Using a single status value (instead of separate loading and error booleans) prevents impossible combinations such as being both loading and in error.

§2Fetching When Inputs Change

When the request depends on a prop or state (a user id, a search term), put that value in the dependency array. The effect runs again whenever it changes. Reset to loading at the start so the user does not see data from the previous request.

function UserProfile({ id }) {
  const [state, setState] = useState({ status: "loading", data: null, error: null });

  useEffect(() => {
    setState({ status: "loading", data: null, error: null });

    async function load() {
      try {
        const res = await fetch(`/api/users/${id}`);
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const data = await res.json();
        setState({ status: "success", data, error: null });
      } catch (err) {
        setState({ status: "error", data: null, error: err.message });
      }
    }
    load();
  }, [id]);                                       // refetch when id changes

  if (state.status === "loading") return <p>Loading...</p>;
  if (state.status === "error") return <p role="alert">{state.error}</p>;
  return <h2>{state.data.name}</h2>;
}

This works for the happy path, but it has a flaw: if id changes quickly, responses can arrive out of order. The next lesson fixes that with cleanup.

§3Fetching Well in Practice

  • Do not fetch in event-less places by habit. Data needed because a user clicked belongs in the click handler. Data needed because a component appeared belongs in an effect (or, better, a data library).
  • Keep the URL and parsing in one place, such as an api.js module, so components stay about UI.
  • Show something useful in each state: skeleton or spinner for loading, a retry button for errors, and a clear message for empty results.
  • Never trust the response shape: handle missing fields and empty arrays.
  • Raw effects are the beginner way. Production apps usually use a library such as TanStack Query, which gives caching, deduplication, retries, and background refresh for free (covered in the intermediate level), or the framework's data loading.
// api.js: one place for network code
export async function getUsers(signal) {
  const res = await fetch("/api/users", { signal });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}
Always design the three states Before you write any fetch code, decide what the user sees while loading, after a failure, and when the result is empty. A feature that only works on the happy path is not finished.

§4Common Mistakes

MistakeWhat HappensFix
Forgetting to check res.okA 404 page is parsed as if it were dataThrow when !res.ok
Tracking loading and error as separate booleansImpossible states like both trueUse one status value
Leaving old data on screen while the new request loadsUsers read the wrong item's dataReset to loading when inputs change
Fetching inside the component bodyA request on every render and likely an infinite loopFetch inside useEffect or an event handler
Practice
  1. Load a list of posts from a public API with loading, error, and success states, and test the error state by breaking the URL.
  2. Add a user-id input; refetch the user whenever the id changes, and show Loading between requests.
  3. Move the fetch logic into an api.js file and keep the component free of URLs.
Key takeaways
  • Model loading, error, and success explicitly, ideally with a single status value.
  • Check res.ok; put the inputs a request depends on in the effect's dependency array.
  • Raw fetch in effects is the foundation; real apps usually add a data library.
