Code Review & Mentoring

Code review is where a team's standards are taught and where trust is built or lost. Good reviews catch problems that matter and help the author grow; poor ones nitpick style and slow everyone down.

§1What to Look For in React Code

Automate the mechanical checks (formatting, lint, types, tests) so that review time goes to what only people can judge. Review in this order, from most to least costly to change later.

LevelQuestions to ask
Design and behaviorDoes this solve the right problem? Is it the simplest approach? Are loading, empty, error, and edge states handled?
Component designDoes each component have one job? Are props minimal and well named? Is state owned at the right level? Composition over flags?
State and dataIs derived data computed rather than stored? Is server data in a query layer? Anything duplicated or mutated?
Effects and hooksDoes every effect sync with something external? Are dependencies complete? Is there cleanup? Could it be an event handler or derived value?
AccessibilitySemantic elements, labels, keyboard use, focus, contrast, announced changes?
PerformanceObvious waste (rendering huge lists, heavy work in render, large imports)? Evidence for any optimization?
SecurityUntrusted HTML or URLs, secrets, authorization, input validation?
TestsDo they check behavior a user would notice? Do they fail if the feature breaks?
ReadabilityClear names, small functions, comments only where intent is not obvious?
// a review comment that teaches, not just corrects
// "This effect copies `items` into `filtered` state. Since `filtered` can be computed
//  from `items` and `query`, storing it risks the two drifting apart and adds an extra render.
//  Could we derive it during render (and memoize if it is expensive)?
//  See: react.dev/learn/you-might-not-need-an-effect"
const filtered = items.filter((i) => i.name.includes(query));

§2How to Give Feedback

  • Review the code, not the person. "This function does two things" lands better than "you wrote this badly".
  • Ask questions when you are not sure ("What happens if the request fails here?"). You may be missing context, and questions invite explanation rather than defense.
  • Explain why, and link to docs or examples. A reason lets the author apply the lesson next time; a bare instruction teaches only compliance.
  • Label the weight: blocking: for must-fix, suggestion: or nit: for optional, question: for curiosity, and praise: for what is good. Authors should never have to guess what is required.
  • Offer an alternative with a snippet when it saves time, and distinguish preference from principle; where reasonable people differ, defer to the author.
  • Be timely and proportionate. Review within a working day; keep pull requests small (a few hundred lines) by encouraging the author to split large changes; do not hold up merging for trivia.
  • Say what is good. Specific praise reinforces practices you want repeated.
  • Move to a call when a thread goes past two rounds, and write down the outcome.

§3As an Author, and as a Mentor

Good reviews start before the reviewer opens the diff. Authors can make review easier and mentors can use review to grow people.

  • Authors: keep the change focused, write a description that explains why and how to test, add screenshots for UI changes, self-review first, and respond to every comment (done, or a reasoned disagreement).
  • Receive feedback well: treat comments as information about how the code reads to someone else, assume good intent, and separate the code from your identity.
  • Mentoring through review: tailor the depth to the person. For newer engineers, explain the principle and link a resource; for senior peers, raise the question and trust their judgment.
  • Teach the underlying mental model, not just the fix: "state should live in one place" applies to the next hundred cases.
  • Pair on hard problems and show your own process, including mistakes and how you debug, so people see how decisions are really made.
  • Delegate real ownership with support: let people lead a small feature or a migration step, and make it safe to ask questions and to fail.
  • Build shared standards in writing: a short style guide, a PR template and checklist, and examples of good components. Standards that exist only in your head do not scale.
  • Watch for patterns: if the same comment appears repeatedly, fix it with a lint rule, a template, a doc, or a team conversation rather than repeating it in every review.
Review for what machines cannot check Let tools handle style and rules. Spend human attention on design, behavior, and teaching, and phrase feedback so that the author leaves knowing both what to change and why.

§4Common Mistakes

MistakeWhat HappensFix
Commenting mostly on style and formattingWastes time that automation could save; hides real issuesAutomate with Prettier and ESLint; review design and behavior
Unlabeled comments of mixed importanceAuthors cannot tell what blocks mergingMark blocking, suggestion, nit, and question
Giving instructions without reasonsAuthor complies but does not learnExplain the principle and link a resource
Reviewing huge pull requestsSuperficial review; bugs slip throughAsk for smaller, focused changes
Practice
  1. Review a real pull request using the checklist in section 1 and write five comments, each with a reason and a weight label.
  2. Turn a comment you often repeat into a lint rule, template item, or short team doc.
  3. Rewrite three blunt review comments into questions or suggestions that explain why.
Key takeaways
  • Automate mechanical checks; review design, state, effects, accessibility, security, and tests.
  • Give feedback about the code with reasons, labeled weight, and questions, and say what is good.
  • Mentor through review by teaching principles, building written standards, and turning repeated comments into tooling.
