Upgrading & Migrating Large React Apps

Large migrations fail because they are planned as a single heroic project. Treat them as a series of small, reversible, shippable steps that run alongside normal feature work, with a measurable finish line.

§1Kinds of Change and Their Risk

ChangeExampleTypical risk
Dependency upgradeReact 18 to 19, router or query library major versionsBreaking API changes, subtle behavior shifts
Tooling migrationWebpack/CRA to Vite, Jest to Vitest, JS to TypeScriptBuild, test, and CI disruption; configuration drift
Pattern migrationClass components to hooks, Redux to Query + ZustandLong coexistence; inconsistent code
Architecture migrationCSR to SSR/Server Components, monolith to modular, new frameworkHighest: touches routing, data, deployment, and team workflow

The risk is not just breakage. It is time: a migration that takes a year while the old code keeps changing will never finish unless you plan for coexistence, and teams that pause features for it rarely get permission twice.

§2Strategies That Work

  • Incremental over big-bang. Make old and new coexist: run both routers, both state libraries, or both build tools, and move one slice at a time. The strangler fig pattern wraps the old app and replaces routes or features gradually.
  • Upgrade one thing at a time, in small steps (one major version at a time), with the test suite green between steps. Read the official upgrade guide and codemods first; React and major libraries ship them.
  • Automate the repetitive parts with codemods (jscodeshift, ts-morph, official codemods) and lint rules that forbid the old pattern in new code, so the problem stops growing while you shrink it.
  • Get a safety net first: raise test coverage on critical paths (component tests, a few Playwright journeys) before the risky changes, so regressions show up in CI, not in production.
  • Ship behind flags: feature flags or gradual rollouts (1%, 10%, 100%) with the old path still deployable, and a tested rollback at every step.
  • Measure the migration: track a simple number (files still using the old API, percent of routes on the new stack), and watch error rates, Web Vitals, and bundle size throughout.
  • Keep shipping value: interleave migration work with features, assign owners, and timebox. Make progress visible so the effort stays funded.

§3Planning, Communicating, and Finishing

  1. State the reason and the goal in terms the business understands (reduce build time from 12 to 2 minutes, unblock React 19 features, cut security risk), with a measurable finish line.
  2. Inventory what is affected: dependencies, routes, shared components, tests, and infrastructure, and rank by risk and value.
  3. Spike the riskiest piece first to find the real problems early, before committing to a schedule.
  4. Define the steps and the exit criteria for each: what ships, how it is verified, how to roll back.
  5. Communicate the plan, the coexistence rules ("new code uses X"), and status regularly; unexplained migrations breed resistance.
  6. Finish: delete the old code, remove the compatibility layers and flags, and update docs. A migration that never removes the old path has doubled your complexity.
  • Expect the long tail: the last 10% of files takes as long as the first 90%. Plan for it, or declare an explicit cut-off.
  • Know when to not migrate: if the old system works, is secure, and is not blocking anything, the cost may not be worth it. Say so with evidence.
  • Document what you learned and the decisions made, in an ADR, so the next migration starts better.
A migration is finished when the old thing is deleted Coexistence is a tool, not a destination. Every step should ship, be reversible, and move a visible number, and the last step is always removing the scaffolding.

§4Common Mistakes

MistakeWhat HappensFix
Planning a single big-bang rewriteLong freeze, high risk, often abandonedMigrate incrementally with coexistence and flags
Starting without a test safety netRegressions found by usersAdd critical-path tests before the risky changes
No rule to stop new uses of the old patternThe migration never catches upAdd lint rules that forbid the old approach in new code
Never deleting the old code and flagsPermanent double complexitySchedule the cleanup as part of the plan
Practice
  1. Write a migration plan for moving a Redux-based app to a query library plus a small store, with steps, coexistence rules, rollback, and a progress metric.
  2. Write a lint rule configuration that forbids the old pattern and a script that counts remaining usages.
  3. List the risks of a React major upgrade for an app you know, and the tests you would add first.
Key takeaways
  • Migrate in small, shippable, reversible steps with old and new coexisting, not as a big-bang rewrite.
  • Build a safety net first, automate with codemods, stop new uses with lint rules, and ship behind flags.
  • Measure progress, communicate the plan, and finish by deleting the old code.
