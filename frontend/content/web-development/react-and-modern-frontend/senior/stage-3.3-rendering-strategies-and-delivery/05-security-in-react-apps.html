Security in React Apps

React escapes output by default, which prevents many injection bugs, but security does not end there. The risky spots are the escape hatches, untrusted URLs, where credentials live, server boundaries, and the dependencies you install.

§1XSS and the Escape Hatches

Values placed in JSX with {} are escaped, so {userInput} is rendered as text, not as HTML. Cross-site scripting (XSS) in React almost always comes through a small set of escape hatches and unsafe URLs.

// safe: escaped text
<p>{comment.body}</p>

// dangerous: renders raw HTML
<div dangerouslySetInnerHTML={{ __html: comment.html }} />

// if you must render user HTML, sanitize with an allow-list library first
import DOMPurify from "dompurify";
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(comment.html) }} />

// dangerous: a user-controlled URL can be `javascript:alert(1)`
<a href={profile.website}>Website</a>

function safeHref(url) {
  try {
    const u = new URL(url, window.location.origin);
    return ["https:", "http:", "mailto:"].includes(u.protocol) ? u.href : "#";
  } catch { return "#"; }
}
<a href={safeHref(profile.website)} rel="noopener noreferrer">Website</a>
  • Treat dangerouslySetInnerHTML, innerHTML via refs, eval, new Function, and setTimeout(string) as review triggers.
  • Validate URL schemes for href, src, and redirects. Never put untrusted values into a javascript: or data: URL.
  • Do not spread untrusted objects as props (<div {...userProps} />): an attacker may supply dangerouslySetInnerHTML or event handlers.
  • Add a Content Security Policy (with nonces, no unsafe-inline for scripts) as defense in depth, and consider Trusted Types.
  • Markdown and rich-text renderers need an allow-list sanitizer; do not write your own with regexes.

§2Credentials, Server Boundaries, and Requests

  • Where tokens live matters: a token in localStorage is readable by any script that runs on the page, including injected XSS and compromised dependencies. Prefer an HttpOnly; Secure; SameSite session cookie for browser apps, with CSRF protection for state-changing requests.
  • Never put secrets in client code or VITE_/NEXT_PUBLIC_ environment variables: everything in the bundle is public. Keep API keys and database credentials on the server.
  • Authorization happens on the server. Hiding a button or route in React is a UI courtesy, not security. Every endpoint must check permissions itself.
  • Server Components and Server Actions: treat actions as public endpoints: authenticate, authorize, and validate input inside each one. Use server-only to keep server modules out of client bundles.
  • Validate all input (forms, URL params, API responses) with a schema, on the client for usability and on the server for security.
  • CSRF and CORS: use SameSite cookies and anti-CSRF tokens; configure CORS to allow only the origins you intend, and never * with credentials.
  • Open redirects (?next=...): allow only relative paths or an allow-list of hosts after login.
// server action: authorize and validate every time
"use server";
export async function deletePost(formData) {
  const session = await getSession();
  if (!session) throw new Error("Unauthorized");
  const id = z.string().uuid().parse(formData.get("id"));
  const post = await db.post.findUnique({ where: { id } });
  if (!post || post.authorId !== session.userId) throw new Error("Forbidden");   // ownership check
  await db.post.delete({ where: { id } });
}

§3Dependencies and the Supply Chain

A typical React app pulls in hundreds of transitive packages, each one a place where malicious or vulnerable code can arrive. These attacks have included hijacked maintainer accounts, typosquatted names, and malicious install scripts.

  • Commit the lockfile and install with npm ci in CI so builds are reproducible. Avoid floating versions for anything that ships.
  • Scan continuously: npm audit, Dependabot or Renovate, and tools like Socket or Snyk. Review changelogs and diffs of updates, especially for packages with install scripts.
  • Reduce the surface: remove unused dependencies, prefer well-maintained packages with few sub-dependencies, and replace trivial packages with a few lines of code.
  • Harden the pipeline: require 2FA, give CI least-privilege tokens, consider --ignore-scripts for installs, and use package provenance where available.
  • Third-party scripts (analytics, chat) run with full page authority: load them deliberately, use SRI for static files, sandbox in iframes, and restrict with CSP.
  • Follow framework security advisories and update promptly: framework-level vulnerabilities have affected server-rendering features in the past.
  • Run a threat model for new features: what is untrusted, what can an attacker control, and what is the worst thing that could happen?
React protects the default path, so audit the exceptions Search the codebase for the escape hatches, untrusted URLs, secrets in the bundle, unprotected server actions, and unreviewed dependencies. That short list is where almost all real React vulnerabilities live.

§4Common Mistakes

MistakeWhat HappensFix
Using dangerouslySetInnerHTML with unsanitized contentStored or reflected XSSSanitize with DOMPurify, or render as text
Rendering <a href={userUrl}> uncheckedjavascript: URLs run script on clickAllow only https:/mailto: schemes
Putting API secrets in VITE_ or NEXT_PUBLIC_ variablesSecrets are public in the bundleKeep secrets on the server
Relying on hidden UI for authorizationAnyone can call the endpoint directlyEnforce permissions on the server for every request
Practice
  1. Search a codebase for dangerouslySetInnerHTML, innerHTML, and href={, and assess each use for XSS risk.
  2. Write a Server Action that authenticates, validates with a schema, and checks ownership, then try to bypass each check.
  3. Run npm audit and a dependency review on a project, and write down what you would remove or replace.
Key takeaways
  • React escapes JSX output; XSS arrives through escape hatches, unsafe URLs, and spread untrusted props.
  • Keep secrets and authorization on the server, prefer HttpOnly cookies, and treat server actions as public APIs.
  • Manage the supply chain: lockfiles, scanning, fewer dependencies, a hardened pipeline, and CSP.
