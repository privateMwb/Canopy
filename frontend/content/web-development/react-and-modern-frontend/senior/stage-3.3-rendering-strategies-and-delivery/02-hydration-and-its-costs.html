Hydration & Its Costs

Server-rendered HTML is only a picture until React attaches behavior to it. Hydration is that step, it costs real time on real devices, and most modern rendering techniques exist to reduce it.

§1What Hydration Does

With SSR or SSG, the browser receives finished HTML and shows it quickly. But buttons do nothing yet. Hydration is React downloading the component code, re-running your components in the browser to rebuild the tree, matching it to the existing DOM, and attaching event handlers and state. Only then does the page become interactive.

import { hydrateRoot } from "react-dom/client";

// attach React to HTML the server already produced (instead of createRoot().render)
hydrateRoot(document.getElementById("root"), <App />);

The page therefore passes through an uncanny valley: it looks ready but ignores taps. The browser pays for it three times: downloading the JavaScript, executing every component to rebuild the tree, and the work of attaching listeners. On a mid-range phone this can take seconds and directly damages INP.

§2Why It Is Expensive, and Mismatches

  • Duplicate work: the server rendered every component, and the client renders them all again just to rebuild state, even for parts that never change.
  • Bundle size: all components you hydrate must ship as JavaScript, including static content like headings and footers.
  • All or nothing (classic): before React 18, nothing was interactive until the whole tree was hydrated.
  • Main-thread blocking: a long hydration task freezes input.

React also requires the client render to match the server HTML. Differences cause hydration mismatch errors and can force React to discard server HTML and re-render on the client, losing the benefit.

// mismatch: different output on server and client
function Clock() { return <p>{new Date().toLocaleTimeString()}</p>; }   // times differ
function Width() { return <p>{window.innerWidth}</p>; }                  // window does not exist on the server

// fix: render a stable value first, then update after hydration
function Clock() {
  const [now, setNow] = useState(null);
  useEffect(() => { setNow(new Date()); }, []);                         // effects run only on the client
  return <p>{now ? now.toLocaleTimeString() : "..."}</p>;
}

// intentional, tiny differences (a timestamp) can be marked
<time suppressHydrationWarning>{formatted}</time>

§3Reducing the Cost

TechniqueHow it helps
Server ComponentsComponents that never need interactivity ship no JS and are never hydrated
Selective hydration (React 18+)Suspense boundaries hydrate independently; React prioritizes what the user interacts with
Less client JavaScriptCode-split, lazy load, and drop heavy libraries
Islands architecture (Astro, Qwik-style ideas)Hydrate only small interactive islands; the rest stays static HTML
Defer non-critical hydrationHydrate below-the-fold or hidden components on visibility or idle
Avoid hydration entirelyFor static content, ship plain HTML (SSG with no client JS)
// lazy hydrate a heavy widget only when it scrolls into view
const Comments = lazy(() => import("./Comments"));

function LazyOnVisible({ children }) {
  const [visible, setVisible] = useState(false);
  const ref = useRef(null);
  useEffect(() => {
    const io = new IntersectionObserver(([e]) => e.isIntersecting && setVisible(true));
    io.observe(ref.current);
    return () => io.disconnect();
  }, []);
  return <div ref={ref}>{visible ? children : <CommentsPlaceholder />}</div>;
}
  • Measure with the Performance panel: look for long tasks right after load, and check INP and Total Blocking Time on throttled CPU.
  • Use the React DevTools Profiler to see how long hydration takes per component.
  • Prefer solutions that remove work (server components, islands, static HTML) to ones that only reschedule it.
Hydration is duplicate work you pay for in time Every component you hydrate costs bytes, CPU, and delay before interaction. The best fix is to ship less JavaScript, by not hydrating what never changes.

§4Common Mistakes

MistakeWhat HappensFix
Rendering Date.now(), Math.random(), or window values during render in SSR appsHydration mismatch and discarded server HTMLCompute client-only values in useEffect
Hydrating static content like footers and articlesNeedless JS and CPUUse Server Components, islands, or static HTML
Assuming SSR means the page is interactiveUsers tap before hydration and nothing happensReduce hydration cost; measure INP on slow devices
One giant client bundle for the whole pageLong hydration blocks inputSplit, defer, and use selective hydration
Practice
  1. Cause a hydration mismatch with the current time, read the warning, and fix it with an effect.
  2. Measure time-to-interactive of a server-rendered page on 4x CPU throttling and identify the hydration long task.
  3. Move one non-interactive section to a Server Component (or static HTML) and compare client bundle size and hydration time.
Key takeaways
  • Hydration re-runs components in the browser to attach behavior to server HTML, a cost in bytes, CPU, and delay.
  • Client output must match server HTML; compute client-only values in effects.
  • Reduce the cost by hydrating less: Server Components, selective hydration, islands, and lazy hydration.
