CSR, SSR, SSG & Streaming

Where and when HTML gets produced decides how fast a page appears, how well it ranks, and what it costs to run. The four strategies are tools, and most real products mix them route by route.

§1The Four Strategies

Each strategy answers the same question differently: *who builds the HTML, and when?*

StrategyHTML builtFirst paintServer costFits
CSR (client-side rendering)In the browser, after JS loadsSlow: blank until JS runsLowest (static files)Logged-in apps, dashboards, tools
SSG (static generation)At build timeFastest: prebuilt HTML on a CDNLowestDocs, marketing, blogs, rarely changing pages
SSR (server rendering)On the server, per requestFast, but waits on the server and dataHighestPersonalized or frequently changing public pages
ISR / revalidationAt build, regenerated in the backgroundFast, bounded stalenessLowCatalogs, news: mostly static with periodic change

A client-rendered page ships an almost empty HTML file; the user sees nothing until the JavaScript downloads, runs, and fetches data. Server rendering sends real content immediately, which helps users on slow devices and search engines, but the page is not interactive until the JavaScript hydrates it (next lesson).

§2Streaming and Mixed Strategies

Classic SSR is all-or-nothing: the server waits for all data before sending any HTML, so the slowest query delays everything. Streaming SSR sends the HTML in pieces: the shell goes out immediately, and slower sections arrive later, replacing their Suspense fallbacks as they resolve.

export default async function ProductPage({ params }) {
  const product = await getProduct(params.id);            // fast and essential: awaited before sending

  return (
    <>
      <ProductHeader product={product} />                  {/* in the first chunk */}
      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews productId={params.id} />                  {/* slow: streamed in when ready */}
      </Suspense>
      <Suspense fallback={<RecsSkeleton />}>
        <Recommendations productId={params.id} />
      </Suspense>
    </>
  );
}

Modern frameworks (Next.js, React Router framework mode, Remix, Astro) let you choose per route, or even per component: a static marketing page, a server-rendered product page, a client-rendered account dashboard, all in one app. Caching rules and revalidation differ by framework and change between versions, so read your framework's current documentation.

§3Choosing

  1. Does it need to be indexed or shared with a rich preview? Then HTML must contain the content: SSG, ISR, or SSR.
  2. Is it the same for every visitor? Prefer SSG/ISR plus a CDN: the cheapest and fastest option.
  3. Is it personalized or real-time? SSR with streaming, or a static shell with client-fetched personalized parts.
  4. Is it behind a login and highly interactive? CSR is often fine; SEO does not matter and server cost is lower.
  5. What is the data latency? Slow data favors streaming so that it never blocks the shell.
  • Time to first byte (TTFB) rises with SSR because the server does work per request; cache at the CDN where you can (Cache-Control: s-maxage, stale-while-revalidate).
  • Edge rendering runs SSR close to users to cut latency, with constraints on runtime APIs and database access.
  • SEO is not magic: crawlers do run JavaScript, but server HTML is faster, more reliable, and measured by real users' speed too.
  • Rendering strategy interacts with Core Web Vitals: SSR/SSG improve LCP, but heavy hydration can hurt INP.
  • Do not switch strategies by fashion: measure LCP, TTFB, and cost for your pages.
Choose per page, not per app A product is a mix: static for what never changes, streamed server rendering for what is personal or fresh, client rendering for tools behind a login. Pick by who sees the page and how often it changes.

§4Common Mistakes

MistakeWhat HappensFix
Client-rendering public content that needs SEO or fast first paintBlank page until JS runs; weaker crawling and sharingUse SSG, ISR, or SSR for public pages
SSR for everything, including identical-for-all pagesNeedless server cost and slower TTFBPrebuild static pages and cache at the CDN
Awaiting all data before sending any HTMLThe slowest query delays the whole pageStream with Suspense boundaries
Ignoring cache headers on server-rendered pagesEvery request hits the originSet CDN caching and revalidation deliberately
Practice
  1. Classify ten pages of a real product into CSR, SSG, ISR, or SSR with a one-line reason each.
  2. Convert a slow server-rendered page to stream its slowest section behind Suspense, and compare time to first content.
  3. Measure TTFB and LCP for the same page rendered statically and with SSR.
Key takeaways
  • CSR, SSG, ISR, and SSR differ in who builds HTML and when; each trades speed, freshness, and cost.
  • Streaming sends the shell first and slow sections later, so slow data does not block the page.
  • Choose per route from audience, personalization, freshness, and SEO needs, and measure the result.
