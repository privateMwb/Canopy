Design Systems & Component Libraries

A design system is shared UI plus the decisions behind it. Building one as a versioned package gives teams consistent, accessible components, and also gives you a long-term maintenance commitment worth planning for.

§1What a Design System Includes

A design system is more than a component folder. It has three layers that build on each other, and the lowest layer carries the most leverage.

LayerContentsExample
Design tokensNamed values for color, spacing, type, radius, motion, elevation--color-text, --space-4, --radius-md
ComponentsAccessible, tested building blocks that use the tokensButton, Dialog, Select, Tabs
Patterns and guidanceHow to combine components; content and accessibility rulesForm layout, empty states, error messages
/* tokens: one source of truth; themes override the same names */
:root {
  --color-bg: #ffffff;       --color-text: #1c1f26;     --color-accent: #15803d;
  --space-2: 0.5rem;         --space-4: 1rem;           --radius-md: 8px;
  --font-body: system-ui, sans-serif;
}
[data-theme="dark"] { --color-bg: #12151a; --color-text: #e8eaee; --color-accent: #4ade80; }

/* components use tokens only, never raw values */
.button { background: var(--color-accent); color: var(--color-bg); padding: var(--space-2) var(--space-4); border-radius: var(--radius-md); }

Because components consume tokens, not hard-coded values, re-theming, dark mode, and even rebranding become changes to one file. Store tokens in a platform-neutral format (such as the W3C design tokens JSON) when design tools or native apps need them too.

§2Building Components That Last

  • Accessibility is built in, not optional: roles, keyboard behavior, focus management, and contrast are part of each component's definition of done. Consider building on headless primitives (Radix UI, React Aria, Ariakit) that supply behavior and accessibility, and add your own styling.
  • API design matters more than looks: prefer composition (<Dialog><Dialog.Title />...) and a small number of well-named props; forward className and native props with ...rest.
  • Variants as data: use a helper like cva to define variants (size, tone) so combinations are explicit and typed.
  • Document with examples: Storybook (or similar) shows each component's states, props, and accessibility checks, and doubles as a visual test bed.
  • Test at three levels: unit/component tests for behavior, accessibility checks (axe), and visual regression (Chromatic, Playwright screenshots) for appearance.
  • Keep it free of product logic: a Button knows nothing about checkout. Business components belong in features, built from design system parts.
import { cva, type VariantProps } from "class-variance-authority";

const button = cva("button", {
  variants: {
    tone: { primary: "button--primary", neutral: "button--neutral", danger: "button--danger" },
    size: { sm: "button--sm", md: "button--md" },
  },
  defaultVariants: { tone: "primary", size: "md" },
});

type Props = React.ComponentProps<"button"> & VariantProps<typeof button>;

export function Button({ tone, size, className, ...rest }: Props) {
  return <button className={button({ tone, size, className })} {...rest} />;
}

§3Packaging, Versioning, and Governance

Once other teams depend on your components, changes become a compatibility problem. Treat the design system as a product with consumers.

  • Publish as a package (internal registry or npm) using semantic versioning: patch for fixes, minor for backward-compatible additions, major for breaking changes. Automate releases and changelogs with Changesets.
  • Define what is breaking: removed props, changed defaults, DOM structure that consumers style, and visual changes that affect layouts all count.
  • Deprecate before removing: mark APIs deprecated, warn in development, document the migration, and keep them for at least one major version. Offer codemods for large changes.
  • Support tree-shaking: ship ES modules with "sideEffects": false and per-component exports, so consumers do not pay for what they do not use.
  • Decide who contributes: a small core team, with a clear process for others to propose or add components, avoids both bottlenecks and a free-for-all.
  • Measure adoption and consistency (how many one-off buttons remain?), and gather feedback; a design system nobody uses is a cost with no return.
  • Know when not to build one: with one app and a small team, a good headless library plus your own tokens may be enough. Full design systems carry real, ongoing staffing costs.
A design system is a product, and the teams using it are its customers It needs versioning, documentation, support, and a deprecation policy, or it becomes the thing everyone works around. Start with tokens and the five components you use most, and grow from real demand.

§4Common Mistakes

MistakeWhat HappensFix
Hard-coding colors and spacing inside componentsTheming and rebranding require touching every componentUse design tokens everywhere
Making breaking changes in minor or patch releasesConsuming apps break unexpectedly; trust erodesFollow semver and use Changesets; deprecate before removing
Putting business logic in shared componentsComponents become coupled to one productKeep the system presentational; compose business components in features
Building a large system before demand existsCostly components nobody adoptsStart small from real, repeated needs
Practice
  1. Define a token set (color, space, radius, type) and rebuild a Button using only tokens, then add a dark theme by overriding the tokens.
  2. Build a Dialog on a headless primitive, add a Storybook story for each state, and an accessibility check.
  3. Write a deprecation plan for renaming a prop: warnings, documentation, version bump, and removal timeline.
Key takeaways
  • A design system layers tokens, accessible components, and guidance; tokens carry the most leverage.
  • Build on headless primitives, design composable APIs, and test behavior, accessibility, and visuals.
  • Version it like a product: semver, changesets, deprecation, and clear governance.
