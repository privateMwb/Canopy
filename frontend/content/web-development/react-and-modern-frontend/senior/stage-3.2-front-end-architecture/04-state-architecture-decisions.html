State Architecture Decisions

Most state-management debates dissolve once you recognize that there are different kinds of state, each with a natural home. The architecture question is not which library, but where each piece of state belongs.

§1A Taxonomy of State

Before choosing a tool, classify the state. Mixing categories in one store is the main reason state becomes hard to reason about.

KindDescriptionNatural home
Server stateData owned by a backend; cached, can go staleA query cache (TanStack Query, RTK Query, framework loaders)
URL stateWhat the user is looking at: route, filters, sort, page, selected tabThe URL (path and search params)
Form stateValues, errors, and touched fields while editingA form library or local state; submit to the server
Local UI stateOpen/closed, hover, current input, ephemeral view stateuseState / useReducer in the component
Shared client stateClient-only data needed by distant components (cart draft, editor selection)Lifted state, context, or a small store (Zustand/RTK)
Persistent client statePreferences that survive reloadslocalStorage/IndexedDB behind a hook or store middleware

Server state is the largest category in most apps, and it is not client state: when you move it into a query cache, much of the rest simplifies, and the amount of true global client state that remains is usually small.

§2Rules for Deciding Where State Lives

  1. Can it live in the URL? If a user would want to bookmark, share, or reload and see the same view, put it in the URL. It gives you Back/Forward and deep links for free.
  2. Is it server data? Use a query/caching layer. Do not copy it into useState or a global store.
  3. Is it derived? Compute it from existing state during render; never store it.
  4. Does only one component care? Keep it local, as low in the tree as possible.
  5. Do a few nearby components care? Lift it to the closest common parent.
  6. Do distant components care, or does it change often? Use a store with selectors; use context only for rarely changing values.
  7. Does it need to survive a reload or sync across tabs? Persist it deliberately, with a versioned schema.
// state, each in its natural home
const [params, setParams] = useSearchParams();                // URL: filters, page, sort
const { data: products } = useProducts({ ...filters });       // server: cached query keyed by filters
const [isFilterOpen, setFilterOpen] = useState(false);        // local UI
const cartCount = useCart((s) => s.items.length);             // shared client: selector on a small store
const visible = useMemo(() => products?.filter(inStock), [products]);   // derived: not stored

§3Boundaries, Costs, and Evolving the Design

  • One source of truth per fact. If two places hold the same data, decide which owns it and delete the other; synchronize through ids, not copies.
  • Keep stores small and domain-scoped (a cart store, a UI preferences store) rather than a single global tree that every feature reads and writes.
  • Hide the implementation behind hooks (useCart(), useUser()), so you can change the underlying tool without touching components.
  • Make impossible states unrepresentable: model modes with discriminated unions or state machines (idle | loading | success | error), not several independent booleans.
  • Plan for failure and staleness of server state: loading, empty, error, and retry states are part of the design, not afterthoughts.
  • Optimistic updates, offline support, and real-time data raise the stakes: decide ahead of time who wins on conflict and how the UI recovers.
  • Watch for re-render fan-out: a store or context read by hundreds of components needs selectors, splitting, or restructuring.
  • Write the decision down in an ADR: where each class of state lives and why. New engineers will otherwise add a fifth way to do it.

Choose the home before the tool Ask what kind of state it is first: server, URL, form, local, shared, or persistent. The right place usually follows from the answer, and the library debate becomes much smaller.

§4Common Mistakes

MistakeWhat HappensFix
Storing API responses in a global client storeHand-built caching with staleness and sync bugsUse a query cache for server state
Keeping filters and pagination in useStateLost on refresh, not shareable, Back breaksStore them in the URL
One giant global store or context for everythingWide re-renders and tangled dependenciesSplit by domain and use selectors
No written convention for where state livesEach developer picks a different approachRecord the decision in an ADR and review against it
Practice
  1. Take a feature in a real app and label each piece of state by kind, then identify any that live in the wrong place.
  2. Move a filter and pagination state from useState to the URL, and confirm Back, refresh, and sharing work.
  3. Write a one-page state-architecture ADR for a project: each category, its home, and the rules for adding new state.
Key takeaways
  • Classify state as server, URL, form, local, shared client, or persistent, and give each its natural home.
  • Prefer the URL for view state, a query cache for server data, and the smallest scope for everything else.
  • Keep one source of truth, hide tools behind hooks, and write the conventions down.
