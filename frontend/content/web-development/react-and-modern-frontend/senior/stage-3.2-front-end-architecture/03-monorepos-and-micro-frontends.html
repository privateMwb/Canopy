Monorepos & Micro-Frontends

Once several teams and apps share code, you have to decide how to arrange repositories and how to deploy. Monorepos and micro-frontends solve different problems, and micro-frontends in particular are often adopted far earlier than they should be.

§1Monorepos

A monorepo keeps many projects (apps and packages) in one repository. It is a source-control and tooling choice, not an architecture: your apps can still be independent. The main benefits are atomic changes across packages (update a shared component and every consumer in one commit), easy code sharing, a single dependency policy, and consistent tooling.

repo/
  apps/
    web/            # customer app
    admin/          # internal tool
  packages/
    ui/             # design system
    api-client/     # typed API access
    config/         # eslint, tsconfig, prettier
  package.json      # workspaces: ["apps/*", "packages/*"]
  turbo.json        # or nx.json: task graph and caching

// apps/web/package.json
{ "dependencies": { "@acme/ui": "workspace:*", "@acme/api-client": "workspace:*" } }
  • Workspaces (npm, pnpm, Yarn) link local packages without publishing them. pnpm is popular for its strict, efficient installs.
  • Build orchestration (Turborepo, Nx) understands the dependency graph, runs tasks in the right order and in parallel, and caches results so unchanged packages are not rebuilt (including remote caches shared with CI).
  • Run only what changed in CI (turbo run test --filter=...[origin/main]) or builds will become unbearably slow as the repo grows.
  • Enforce boundaries between packages with lint rules or Nx tags, and use CODEOWNERS so each area has owners.
  • Costs: tooling complexity, larger clones, CI that needs careful caching, and access control is repo-wide (everyone sees everything).

§2Micro-Frontends

Micro-frontends split one product's UI into independently built and deployed pieces, usually owned by separate teams, and compose them in the browser or at the edge. The goal is team and deployment independence: team A ships its section without coordinating a release with team B.

TechniqueHow pieces are combinedTrade-off
Links between separate appsEach section is a full app; navigate between themSimplest; full page loads between sections
IframesEmbed one app inside anotherStrong isolation; poor UX, sizing, and accessibility
Module Federation / runtime compositionHost loads remote bundles at runtime and shares librariesFlexible; version mismatches and complexity
Server-side or edge compositionFragments assembled into one HTML responseFast first load; infrastructure complexity
Web Components as the contractTeams expose custom elementsFramework-neutral; styling and state sharing are manual

The costs are substantial: duplicated dependencies and larger bundles, inconsistent UX unless a shared design system is enforced, cross-app communication (state, auth, routing, events) that must be designed, harder end-to-end testing, more complicated local development, and performance and accessibility regressions from loading several runtimes.

§3Choosing, and When Not To

These are organizational solutions to organizational problems. If one team can ship the whole product, a micro-frontend architecture adds cost and no benefit.

  • Start with a modular monolith (one app, feature folders, enforced boundaries) inside a monorepo. You get most of the code-ownership benefits with none of the runtime complexity.
  • Consider micro-frontends only when many teams (rough guide: several, not two) are blocked on a shared release process, and independent deployment is worth the runtime and consistency costs.
  • Decide the shared contracts first: routing, authentication, design system, error handling, observability, and how pieces communicate (URL, events, a narrow shared store).
  • Keep shared dependencies (React) singleton and version-aligned, or accept duplication deliberately.
  • Invest in a shared design system and performance budgets per fragment, or the combined page will be slow and inconsistent.
  • Migrating legacy apps incrementally (strangler pattern, replacing one route at a time) is a legitimate reason for a composition layer.
  • Always ask: *what problem do we have, and is there a cheaper way to solve it?* Many teams adopted micro-frontends and later consolidated.
Match architecture to org structure, not to fashion Monorepos help teams share code. Micro-frontends help teams deploy independently. If you do not have the second problem, do not pay for the second solution.

§4Common Mistakes

MistakeWhat HappensFix
Adopting micro-frontends for one or two teamsRuntime complexity, duplication, and inconsistent UX with no benefitUse a modular monolith with enforced boundaries
A monorepo with no task caching or affected-only CIBuilds and tests get slower with every packageUse Turborepo/Nx caching and run only affected tasks
No shared design system across fragmentsThe product looks and behaves like several different appsShare tokens and components, enforced in review
Letting packages import each other freelyA tangled dependency graphEnforce boundaries with lint rules and tags
Practice
  1. Create a small pnpm workspace with an app and a shared ui package, and run a build with Turborepo caching.
  2. List the cross-cutting concerns (routing, auth, theming, errors, analytics) you would have to solve for a micro-frontend split, and decide which team owns each.
  3. Write a one-page recommendation for a hypothetical company with 3 front-end teams: monolith, monorepo, or micro-frontends, and why.
Key takeaways
  • Monorepos share code and tooling; they are a repository choice, and need caching and affected-only CI.
  • Micro-frontends buy independent deployment at the cost of duplication, inconsistency, and complexity.
  • Default to a modular monolith in a monorepo, and split only when org scale and delivery pain demand it.
