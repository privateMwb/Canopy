Concurrent Rendering

Concurrent rendering lets React work on an update in the background and interrupt it for something more urgent. Transitions and deferred values are how you tell React which updates can wait.

§1The Problem: One Update Blocks the Rest

Without concurrency, once React starts rendering it finishes before the browser can respond. If typing in a search box triggers rendering a 5,000-row list, each keystroke waits for the list, and the input feels broken. The cause is that all updates are treated as equally urgent.

Concurrent rendering makes rendering interruptible. React assigns updates a priority (internally, lanes): discrete user input like typing and clicks is urgent, while updates you mark as transitions are not. It can start the low-priority render, pause to handle an urgent update, throw away the stale work, and restart. Rendering is sliced into small units that yield back to the browser (time slicing), so input and paint are never starved for long.

This only works because render is pure: React can abandon a half-finished render with no consequences. Concurrent features are opt-in: you use them through startTransition, useTransition, useDeferredValue, and Suspense.

§2Transitions and Deferred Values

startTransition marks a state update as non-urgent. The urgent update (the input's text) renders immediately; the transition update (the filtered results) renders in the background and can be interrupted by further typing. useTransition adds an isPending flag so you can show feedback.

function Search({ items }) {
  const [query, setQuery] = useState("");              // urgent: the input
  const [filter, setFilter] = useState("");            // non-urgent: the expensive result
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    setQuery(e.target.value);                           // renders immediately
    startTransition(() => {
      setFilter(e.target.value);                        // can wait and be interrupted
    });
  }

  return (
    <>
      <input value={query} onChange={handleChange} />
      <div style={{ opacity: isPending ? 0.6 : 1 }}>
        <SlowList items={items} filter={filter} />
      </div>
    </>
  );
}

When you cannot wrap the setter (the value arrives as a prop), useDeferredValue gives you a lagging copy of a value: React first renders with the old value, then re-renders in the background with the new one.

function Results({ query }) {
  const deferred = useDeferredValue(query);             // trails behind during heavy work
  const stale = deferred !== query;

  return (
    <div style={{ opacity: stale ? 0.6 : 1 }}>
      <SlowList filter={deferred} />                    // memoize this child so the old value skips work
    </div>
  );
}

§3Transitions with Suspense, and Limits

Transitions interact with Suspense: if a transition causes something to suspend, React keeps showing the old UI (with isPending true) instead of replacing it with a loading fallback. This is how navigation can feel smooth, as the current page stays until the next is ready.

function Tabs() {
  const [tab, setTab] = useState("posts");
  const [isPending, startTransition] = useTransition();

  return (
    <>
      <nav aria-busy={isPending}>
        {["posts", "photos"].map((t) => (
          <button key={t} onClick={() => startTransition(() => setTab(t))} aria-current={tab === t}>{t}</button>
        ))}
      </nav>
      <Suspense fallback={<Spinner />}>      {/* shown only on first load, not on later tab switches */}
        {tab === "posts" ? <Posts /> : <Photos />}
      </Suspense>
    </>
  );
}
  • Transitions do not make slow code fast. They keep the app responsive while slow work happens elsewhere in time. Reduce the work itself with virtualization and good structure.
  • A transition update must be a state update; you cannot wrap controlled input value changes in one (that makes typing lag).
  • Code in the startTransition callback must be synchronous: await inside it does not extend the transition (React 19's Actions, with startTransition(async () => ...), handle async work and pending state).
  • Use isPending for subtle feedback (dim, small indicator), not full spinners, so the UI does not flash.
  • Combine with memo/the React Compiler so the deferred child can skip rendering when its input has not yet changed.
Urgent versus can-wait Concurrent rendering is a way to say which updates matter now. Typing, clicking, and focus are urgent; filtering, tab content, and navigation can wait, and React keeps the interface alive while they finish.

§4Common Mistakes

MistakeWhat HappensFix
Wrapping a controlled input's own state in startTransitionTyping lags or characters appear lateKeep the input urgent; transition the derived/heavy state
Expecting transitions to speed up a slow renderTotal work is the same; only responsiveness improvesReduce render cost; use transitions for responsiveness
Using await inside a transition callback and expecting it to spanPending state ends earlyUse Actions (async startTransition) or manage state explicitly
Showing a full-page spinner for every transitionFlash of fallback on every navigationUse isPending to dim, and let Suspense keep old UI
Practice
  1. Build a search over 5,000 items that lags with plain state, and fix responsiveness with useTransition.
  2. Do the same using useDeferredValue on a prop, and add memo to the slow child.
  3. Implement tab navigation where switching tabs keeps the old tab visible until the new data is ready.
Key takeaways
  • Concurrent rendering makes rendering interruptible, with urgent updates preempting transitions.
  • useTransition and useDeferredValue mark work as non-urgent; transitions keep old UI during Suspense.
  • They improve responsiveness, not raw speed: reduce work, then defer what is left.
