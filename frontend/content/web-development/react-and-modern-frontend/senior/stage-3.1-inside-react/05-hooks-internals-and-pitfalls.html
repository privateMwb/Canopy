Hooks Internals & Pitfalls

Hooks look like ordinary function calls, yet they keep state between renders without any names. That works because of one strict rule about call order, and understanding the mechanism makes the rules of hooks obvious instead of arbitrary.

§1How Hooks Are Stored

Each component instance has a fiber, React's internal record for it. The fiber holds a linked list of hook records, one per hook call, in the order the component called them. There are no names or keys: React identifies useState number 1, useState number 2, and useEffect number 3 purely by position in that list.

function Form() {
  const [name, setName] = useState("");      // hook #1: first node in the list
  const [age, setAge] = useState(0);         // hook #2
  const ref = useRef(null);                  // hook #3
  useEffect(() => { /* ... */ }, [name]);    // hook #4: stores deps for comparison
  // ...
}

// a simplified model of what React keeps for this fiber
// fiber.memoizedState -> { value: "", queue }
//                         -> { value: 0, queue }
//                              -> { current: null }
//                                   -> { effect, deps: ["..."] }

On each render React walks the list in step with your calls: the first useState call gets the first node, the second gets the second, and so on. That is why useState can return the right value without knowing anything about your variable names.

§2Why the Rules Exist

The two Rules of Hooks follow directly from the position-based list:

  1. Call hooks at the top level, never inside conditions, loops, or nested functions.
  2. Call hooks only from React functions: components and custom hooks.
function Broken({ loggedIn }) {
  if (loggedIn) {
    const [user, setUser] = useState(null);   // hook #1 only on some renders
  }
  const [theme, setTheme] = useState("light");   // hook #1 or #2 depending on the render
  // On a render where loggedIn flips, call positions shift: `theme` receives the user's state,
  // or React throws "Rendered more hooks than during the previous render"
}

// fix: always call the hook; put the condition inside
function Fixed({ loggedIn }) {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState("light");
  if (!loggedIn) return <Login />;               // early return AFTER all hooks
  return <Dashboard user={user} theme={theme} />;
}

Early returns before a hook are the same violation. Custom hooks follow the same rules, since they are just a grouping of calls that end up in the host component's list. The ESLint rule react-hooks/rules-of-hooks enforces these statically.

§3Closures, Dependencies, and Other Pitfalls

Every render creates new functions that close over that render's props and state. Effects and handlers see the values from the render in which they were created, a *snapshot*. Most hook bugs are really stale closures, where a callback uses an old value because it was not re-created, or the dependency list did not include what it reads.

function Ticker() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1);                 // closes over count = 0 forever: stuck at 1
    }, 1000);
    return () => clearInterval(id);
  }, []);                                    // lint warns: count is missing

  // fix 1: updater form needs no dependency on count
  useEffect(() => {
    const id = setInterval(() => setCount((c) => c + 1), 1000);
    return () => clearInterval(id);
  }, []);
}

// latest-value pattern: a ref always holds the newest callback without re-subscribing
function useEvent(fn) {
  const ref = useRef(fn);
  useLayoutEffect(() => { ref.current = fn; });
  return useCallback((...args) => ref.current(...args), []);
}

  • useState's initializer runs every render unless you pass a function: useState(() => expensive()).
  • State updates are replaced, not merged: setObj({ a: 1 }) drops other fields.
  • In React 19, use(promise) and use(context) are the exceptions that can be called conditionally, since they do not rely on the hook list.
  • The React Compiler relies on these rules: code that follows them can be memoized automatically.
Hooks are a list indexed by call order Everything strange about hooks, no conditionals, no loops, stale closures, resets on remount, follows from that one fact. If you can picture the linked list, you can predict the behavior.

§4Common Mistakes

Practice
  1. Draw the hook list for a component with two useState, one useRef, and one useEffect, and show what changes if you move one hook into an if.
  2. Reproduce the stale-interval bug, then fix it with an updater function and again with a useEvent-style ref.
  3. Find three effects in a codebase with workarounds for dependency warnings and restructure each so the warning is satisfied properly.
Key takeaways
  • Hooks live in a per-fiber linked list identified only by call order.
  • The Rules of Hooks (top level only) keep that order identical every render.
  • Most hook bugs are stale closures: refresh dependencies, use updaters, or the latest-value ref pattern.
