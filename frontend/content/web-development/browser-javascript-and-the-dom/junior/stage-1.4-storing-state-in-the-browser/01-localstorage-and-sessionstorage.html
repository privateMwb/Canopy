localStorage & sessionStorage

Web Storage gives a page a simple place to keep small pieces of data between visits. It is easy to use, and it has limits worth understanding before you rely on it.

§1The Storage API

localStorage keeps data until it is cleared, across tabs and browser restarts, for one origin. sessionStorage is the same API but its data lives only for that tab and is discarded when the tab closes. Both store strings as key-value pairs.

localStorage.setItem("theme", "dark");
localStorage.getItem("theme");        // "dark"
localStorage.getItem("missing");      // null
localStorage.removeItem("theme");
localStorage.clear();                 // removes everything for this origin

localStorage.length;
localStorage.key(0);                  // name of the first key

Because values are always strings, localStorage.setItem("count", 5) stores "5", and reading it back gives you a string. That is a source of bugs such as "5" + 1 === "51".

§2Storing Objects Safely

To store anything other than a string, serialize it with JSON, and wrap parsing in try/catch because stored data can be missing, edited by the user, or written by an older version of your app.

function save(key, value) {
  try {
    localStorage.setItem(key, JSON.stringify(value));
  } catch (err) {
    console.warn("could not save", err);   // quota exceeded or storage blocked
  }
}

function load(key, fallback) {
  try {
    const raw = localStorage.getItem(key);
    return raw === null ? fallback : JSON.parse(raw);
  } catch {
    return fallback;                       // corrupted or blocked
  }
}

save("settings", { theme: "dark", fontSize: 16 });
const settings = load("settings", { theme: "light", fontSize: 14 });

The storage event fires in other tabs of the same origin when storage changes, which is handy for keeping several tabs in sync, for example logging out everywhere.

window.addEventListener("storage", (e) => {
  if (e.key === "theme") applyTheme(e.newValue);
});

§3Limits and What Not to Store

  • Size: roughly 5 MB per origin, and exceeding it throws an error.
  • Synchronous: reads and writes block the main thread, so avoid large values or many calls in hot paths.
  • Strings only: no binary, no structured data without serialization.
  • Not secure: any script on your page, including third-party scripts and XSS payloads, can read it, and the user can edit it. Never store passwords, session tokens, or secrets.
  • May be unavailable: private modes, blocked storage settings, and quota errors can all make it fail.

Use it for preferences, drafts, and non-sensitive caches. For larger or structured data, IndexedDB (covered later) is the right tool, and for anything that must be trusted, keep it on the server.

Treat storage as untrusted input Data you read from localStorage came from outside your current code: an old version, a user edit, or an attacker. Validate and fall back to defaults rather than assuming its shape.

§4Common Mistakes

MistakeWhat HappensFix
Storing an object directlySaved as "[object Object]"Use JSON.stringify and JSON.parse
Calling JSON.parse without try/catchCorrupt data crashes startupWrap in try/catch and use a fallback
Storing auth tokens or secretsAny script (including XSS) can steal themUse HttpOnly cookies or keep secrets server-side
Treating numbers as numbers after reading"5" + 1 becomes "51"Convert with Number() or store JSON
Practice
  1. Make a dark-mode toggle that remembers its setting across reloads using localStorage.
  2. Write load/save helpers with JSON and fallbacks, then deliberately corrupt the stored value in DevTools and confirm the app still starts.
  3. Open the same page in two tabs and use the storage event to update one when the other changes a value.
Key takeaways
  • localStorage persists across sessions; sessionStorage lasts for one tab. Both hold only strings.
  • Serialize with JSON, guard parsing with try/catch, and handle quota errors.
  • Never store secrets in Web Storage; it is readable by every script on the page.
