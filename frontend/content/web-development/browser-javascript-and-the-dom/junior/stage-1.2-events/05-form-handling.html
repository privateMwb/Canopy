Form Handling

Forms are the main way users give your page data. Reading values, listening for the right events, and validating in script come together in a pattern you will use constantly.

§1Reading Values

Form controls expose their current state as properties: value for text inputs and selects, checked for checkboxes and radios, files for file inputs. The FormData object collects every named field in a form at once.

const form = document.querySelector("#signup");
const email = form.elements.email;         // by the field's name
console.log(email.value);
console.log(form.elements.agree.checked);  // checkbox: true or false

const data = new FormData(form);
data.get("email");                          // one field
Object.fromEntries(data);                   // all fields as a plain object

FormData only includes fields that have a name attribute and are not disabled. Unchecked checkboxes are omitted, which is a frequent source of confusion.

§2Submitting

Listen for the form's submit event, not a click on the button. The submit event also fires when the user presses Enter inside a field, so it covers both. Cancel the default to handle it in script.

form.addEventListener("submit", async (e) => {
  e.preventDefault();
  const payload = Object.fromEntries(new FormData(form));

  const res = await fetch("/api/signup", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(payload),
  });
  if (!res.ok) showError("Could not sign up");
});

Two other events matter while typing: input fires on every change to the value (use it for live feedback), and change fires when the user commits the change (on blur for text, immediately for checkboxes and selects).

§3Validating

Start with the browser's built-in validation: attributes like required, type="email", minlength, pattern, and min/max give you checks, error bubbles, and CSS pseudo-classes (:invalid) for free. Script can query and extend it with the Constraint Validation API.

const pw = form.elements.password;
const confirm = form.elements.confirm;

confirm.addEventListener("input", () => {
  confirm.setCustomValidity(
    confirm.value === pw.value ? "" : "Passwords do not match"
  );
});

form.addEventListener("submit", (e) => {
  if (!form.checkValidity()) {
    e.preventDefault();
    form.reportValidity();        // shows the browser's messages
  }
});

An empty string passed to setCustomValidity clears the error. Any other string marks the field invalid with that message. Remember that client-side validation is for user experience only: the server must always validate again, because anyone can bypass your script.

Validate twice Client-side checks make forms pleasant; server-side checks make them safe. Never rely on the first one alone.

§4Common Mistakes

MistakeWhat HappensFix
Listening for click on the submit buttonMisses submits triggered by pressing EnterListen for the form's submit event
Fields with no name attributeThey are silently missing from FormDataGive each control a name
Forgetting to clear setCustomValidityThe field stays invalid foreverCall setCustomValidity("") when the value is valid
Trusting client-side validationAnyone can send bad data directlyValidate on the server too
Practice
  1. Build a sign-up form that shows a live character count using the input event.
  2. Add a password-confirmation check using setCustomValidity and style :invalid fields in CSS.
  3. On submit, convert the form to JSON with FormData and log it; confirm unchecked checkboxes are missing.
Key takeaways
  • Read values from properties or collect them with FormData; fields need a name to be included.
  • Handle submit on the form, call preventDefault(), and use input for live feedback.
  • Use built-in validation plus the Constraint Validation API, and always validate again on the server.
