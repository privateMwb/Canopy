Scripts in the Browser

A script tag is how your JavaScript gets into a page. Where you put it, and which attributes you give it, decides whether it runs before or after the HTML it needs.

§1Running Code in a Page

The browser reads HTML top to bottom and builds the page as it goes. When it meets a classic <script> tag it stops parsing, downloads the file if there is one, runs it, and only then continues. That is why a script in the <head> that looks for an element further down finds nothing: the element does not exist yet.

<!-- inline -->
<script>
  console.log("hello from the page");
</script>

<!-- external file -->
<script src="app.js"></script>

Scripts run in a single shared global scope, in the order they appear. A variable declared with var or a function declaration at the top level of a classic script becomes visible to every script after it.

§2defer, async, and Modules

Three attributes change the timing. All three let the HTML keep parsing while the file downloads.

FormRuns whenOrder kept?
<script src>Immediately, blocking the parserYes
<script defer src>After parsing finishes, before DOMContentLoadedYes
<script async src>As soon as it downloads, whenever that isNo
<script type="module" src>Deferred by defaultYes (dependencies first)

For your own application code, defer or type="module" is almost always the right choice. Use async only for independent scripts such as analytics, where order does not matter.

<script type="module" src="main.js"></script>

// main.js
import { render } from "./render.js";   // modules can import other modules
render(document.body);                   // the DOM is ready here

Module scripts also run in strict mode, have their own scope (top-level variables do not leak onto window), and are fetched only once even if several files import them.

§3The Console

Every browser has a console (open DevTools with F12 or Cmd/Ctrl+Shift+I). It shows errors and console.log output, and it is also a live prompt: type an expression and it runs against the current page.

console.log("plain message");
console.warn("something looks off");
console.error("something broke");
console.table([{ id: 1, name: "Ada" }, { id: 2, name: "Lin" }]);

document.title            // try this in the console prompt
document.body.children    // an HTMLCollection of the body's child elements

Read the red error text carefully. It names the file and line, and the most common first errors are Uncaught ReferenceError (a name that is not defined, often a typo or script order) and Cannot read properties of null (you used an element that was not found).

The key insight If your script needs the DOM, make sure it runs after the DOM exists. defer or type="module" does this with no extra code. Wrapping everything in a DOMContentLoaded listener is the older way to get the same result.

§4Common Mistakes

MistakeWhat HappensFix
Classic script in <head> that queries the pagequerySelector returns null; later code throwsAdd defer or use type="module"
Using async for scripts that depend on each otherThey run in a random order and sometimes failUse defer, which preserves order
Putting code in a <script src> tag that also has inline codeThe inline code is ignoredUse two separate script tags
Opening a module page via file://Browser blocks the import with a CORS errorServe the folder over http://localhost
Practice
  1. Create an HTML page with a heading and a script in the <head> that logs document.querySelector("h1"). Observe null, then fix it with defer.
  2. Move the code into main.js loaded with type="module", and export a function from a second file that you import and call.
  3. In the console, run document.title = "Changed" and watch the tab title update.
Key takeaways
  • A classic script blocks parsing; defer and modules wait for the DOM, async runs in no guaranteed order.
  • Prefer type="module" for application code: deferred, strict, and scoped.
  • The console is both a log and a live prompt: use it to explore the page.
