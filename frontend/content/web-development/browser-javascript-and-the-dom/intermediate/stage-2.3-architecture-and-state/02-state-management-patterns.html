State Management Patterns

Most UI bugs are state bugs: two parts of the screen disagree about the truth. A single source of truth and one-way data flow make behavior predictable, and you can build both in a few lines.

§1A Single Source of Truth

State is the data that describes what the UI should look like right now: the list of items, the selected tab, whether a request is loading. The key rule is to keep each fact in one place and derive everything else from it. Copies drift apart, and derived values should be computed, not stored.

// duplicated truth: the count and the list can disagree
let todos = [];
let doneCount = 0;

// single truth: derive the count
const state = { todos: [{ id: 1, text: "Write", done: false }], filter: "all" };
const doneCount2 = state.todos.filter((t) => t.done).length;

Where possible, do not read values back from the DOM. If the checkbox says one thing and your array says another, which one is right? Make the data authoritative and let the DOM reflect it.

§2One-Way Data Flow

In one-way data flow, user actions do not edit the DOM directly. They produce an action, a function (the reducer) computes the next state from the old state and the action, and the view is redrawn from the new state. The cycle is always: action, state, view.

function reducer(state, action) {
  switch (action.type) {
    case "add":
      return { ...state, todos: [...state.todos, { id: Date.now(), text: action.text, done: false }] };
    case "toggle":
      return { ...state, todos: state.todos.map((t) => t.id === action.id ? { ...t, done: !t.done } : t) };
    case "setFilter":
      return { ...state, filter: action.filter };
    default:
      return state;
  }
}

function createStore(reducer, initial) {
  let state = initial;
  const listeners = new Set();
  return {
    getState: () => state,
    dispatch(action) {
      state = reducer(state, action);
      listeners.forEach((fn) => fn(state));
    },
    subscribe(fn) { listeners.add(fn); return () => listeners.delete(fn); },
  };
}

The reducer never mutates the old state; it returns a new object. That makes changes easy to detect (compare references), easy to log, and easy to replay or undo. The store is about twenty lines, and this is essentially what Redux does.

§3Rendering from State

The view subscribes to the store and renders whenever state changes. Events dispatch actions and never touch the DOM themselves.

const store = createStore(reducer, { todos: [], filter: "all" });

function render(state) {
  const visible = state.todos.filter((t) =>
    state.filter === "all" ? true : state.filter === "done" ? t.done : !t.done);
  list.replaceChildren(...visible.map(todoItem));
  remaining.textContent = state.todos.filter((t) => !t.done).length;
}
store.subscribe(render);
render(store.getState());

list.addEventListener("change", (e) => {
  store.dispatch({ type: "toggle", id: Number(e.target.closest("li").dataset.id) });
});
form.addEventListener("submit", (e) => {
  e.preventDefault();
  store.dispatch({ type: "add", text: input.value });
  input.value = "";
});

Keep UI state (which dropdown is open) separate from domain state (the todos), and keep server data in mind as its own category: it is a cache of remote truth that can be stale, loading, or failed. Putting { status: "loading" | "error" | "ready", data, error } in state makes every case explicit.

State in, UI out If you can say "the screen is a function of the state", bugs shrink: to find out why the screen looks wrong, inspect the state, and to change the screen, change the state.

§4Common Mistakes

MistakeWhat HappensFix
Mutating state in place (state.todos.push(x))Change detection and undo breakReturn a new object or array
Storing derived values (counts, filtered lists)They go stale and disagreeCompute them when rendering
Event handlers editing the DOM and the stateTwo sources of truth that driftDispatch an action and render from state
One global blob for every kind of stateEverything re-renders; hard to reason aboutSeparate local UI state from shared domain state
Practice
  1. Implement the store above and build a to-do app that renders purely from state.
  2. Add a status field for loading, error, and ready states to a fetch-driven list and render each case.
  3. Add an undo feature by keeping an array of previous states, and explain why immutability makes it easy.
Key takeaways
  • Keep one authoritative copy of each fact and derive everything else.
  • Actions flow to a reducer, state is replaced (not mutated), and the view re-renders from it.
  • Model loading and error as explicit states, and keep UI state separate from domain state.
