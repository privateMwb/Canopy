End-to-End Tests with Playwright

End-to-end (E2E) tests drive a real browser through a real user journey. They are slower and fewer than unit tests, and they catch the integration problems nothing else can.

§1Writing a Playwright Test

Playwright launches Chromium, Firefox, and WebKit, loads your app, and interacts with it as a user would. Its locators auto-wait for elements to be ready, which removes most of the flakiness that older tools had.

npm init playwright@latest

// tests/todo.spec.js
import { test, expect } from "@playwright/test";

test("a user can add and complete a task", async ({ page }) => {
  await page.goto("/");

  await page.getByLabel("New task").fill("Buy milk");
  await page.getByRole("button", { name: "Add" }).click();

  const item = page.getByRole("listitem").filter({ hasText: "Buy milk" });
  await expect(item).toBeVisible();

  await item.getByRole("checkbox").check();
  await expect(item).toHaveClass(/done/);
});

// playwright.config.js: start the app automatically
// webServer: { command: "npm run dev", url: "http://localhost:5173", reuseExistingServer: true }

Locators mirror Testing Library's philosophy: getByRole, getByLabel, getByText. The expect(locator) assertions retry until they pass or a timeout elapses, so you almost never need manual sleep calls.

§2Isolation, Network, and Debugging

Each test runs in a fresh browser context (clean cookies and storage), so tests do not leak into each other. You can intercept network requests to make tests fast and deterministic, instead of hitting real servers.

test("shows an error when the API fails", async ({ page }) => {
  await page.route("**/api/todos", (route) => route.fulfill({ status: 500, body: "nope" }));
  await page.goto("/");
  await expect(page.getByRole("alert")).toContainText("Could not load");
});

test("works on a phone", async ({ browser }) => {
  const ctx = await browser.newContext({ viewport: { width: 390, height: 844 }, hasTouch: true });
  const page = await ctx.newPage();
  await page.goto("/");
});
  • npx playwright test --ui opens a time-travel debugger with DOM snapshots at every step.
  • npx playwright codegen http://localhost:5173 records your clicks as test code.
  • Traces, screenshots, and videos on failure make CI failures debuggable.
  • Run tests in parallel across browsers and viewport sizes with projects in the config.

§3Where E2E Fits

E2E tests are the top of the testing pyramid: few, slow, and valuable. They verify that the pieces really work together: routing, the server, the database, and the UI. They are also the most expensive to maintain, so reserve them for the critical journeys (sign up, checkout, core workflow) and keep detailed logic checks in faster unit and DOM tests.

LayerSpeedCatchesHow many
UnitMillisecondsLogic errorsMany
DOM / componentTens of msUI behaviorSome
End-to-endSecondsIntegration, real browser bugsFew, critical paths

To keep E2E tests reliable: control test data (seed it, or intercept the network), avoid depending on third-party sites, use stable locators, and run them in CI on every pull request. A flaky test, one that fails randomly, is worse than no test, because people stop trusting the suite.

Never sleep Playwright locators and expect assertions wait and retry on their own. Adding a fixed waitForTimeout makes tests slow *and* still flaky. Wait for a visible condition instead.

§4Common Mistakes

MistakeWhat HappensFix
Using fixed sleeps like waitForTimeout(2000)Slow and still flakyRely on auto-waiting locators and expect
Locating by brittle CSS or XPathBreaks on markup changesUse getByRole, getByLabel, getByText
Testing against live third-party servicesRandom failures outside your controlIntercept with page.route or use a test backend
Putting every check into E2ESlow suite that nobody runsKeep logic in unit tests, E2E for critical journeys
Practice
  1. Write an E2E test for a core journey in your app, using only role- and label-based locators.
  2. Stub a failing API with page.route and assert that the error message appears.
  3. Run with --ui, step through a failing test, and identify the exact action where it diverged.
Key takeaways
  • Playwright drives real browsers with auto-waiting locators and retrying assertions.
  • Isolate tests with fresh contexts and control the network so results are deterministic.
  • Keep E2E tests few and focused on critical journeys; avoid flakiness above all.
