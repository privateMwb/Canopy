Testing the DOM

DOM tests check what a user would experience, not how your code is structured. Testing Library's principle, query by what users see and use, gives tests that survive refactors and also push you toward accessible markup.

§1Test Like a User

The guiding principle of Testing Library is: *the more your tests resemble the way your software is used, the more confidence they give.* Users do not look for .btn-primary; they find a button named "Save". So the tests should too.

npm install -D vitest jsdom @testing-library/dom @testing-library/user-event @testing-library/jest-dom

// vite.config.js
export default { test: { environment: "jsdom", setupFiles: ["./test/setup.js"] } };

// test/setup.js
import "@testing-library/jest-dom/vitest";

jsdom is a simulated browser DOM that runs in Node. It is fast, and good for most component logic, but it does not do layout or painting, so it cannot test CSS, scroll position, or visual rendering. Real-browser tests (next lesson) cover those.

§2Querying by Role

Queries are listed in priority order. Prefer the ones that reflect how users and assistive technology find things: role and accessible name first, then label text, then visible text. Use data-testid only as a last resort.

PriorityQueryExample
1getByRolegetByRole("button", { name: /save/i })
2getByLabelTextgetByLabelText("Email")
3getByPlaceholderText, getByTextgetByText("No results")
4getByAltText, getByTitlegetByAltText("Profile photo")
lastgetByTestIdgetByTestId("cart-badge")

There are three families: getBy* throws if there is not exactly one match, queryBy* returns null when absent (use it to assert something is not there), and findBy* waits asynchronously for an element to appear. Because role queries rely on proper semantics, a test that cannot find your button by role is often telling you the markup is wrong.

§3Interacting and Asserting

Use user-event to simulate real interaction (focus, typing, clicking with the right events in order) rather than firing a bare click event. Then assert on what the user would see.

import { describe, test, expect } from "vitest";
import { screen, within } from "@testing-library/dom";
import userEvent from "@testing-library/user-event";
import { mountTodoApp } from "./todo.js";

describe("todo app", () => {
  test("adds an item and clears the field", async () => {
    document.body.innerHTML = "<div id=app></div>";
    mountTodoApp(document.querySelector("#app"));
    const user = userEvent.setup();

    await user.type(screen.getByLabelText(/new task/i), "Write tests");
    await user.click(screen.getByRole("button", { name: /add/i }));

    const list = screen.getByRole("list");
    expect(within(list).getByText("Write tests")).toBeInTheDocument();
    expect(screen.getByLabelText(/new task/i)).toHaveValue("");
  });

  test("shows an error when the request fails", async () => {
    // arrange a failing fetch, then act...
    expect(await screen.findByRole("alert")).toHaveTextContent(/could not load/i);
  });
});

Avoid asserting on implementation details such as class names, internal function calls, or exact DOM structure. If you can rename a CSS class or reorganize wrappers without the test noticing, the test is well written.

Accessibility and testing reinforce each other Queries by role and label only work if the page exposes proper roles and labels. Writing tests this way quietly pushes your markup toward being accessible.

§4Common Mistakes

MistakeWhat HappensFix
Selecting by CSS class or DOM positionTests break on harmless refactorsQuery by role, label, or visible text
Using getBy* to assert something is absentThrows instead of assertingUse queryBy* and not.toBeInTheDocument()
Firing raw click events instead of user-eventSkips focus and key events users produceUse userEvent.setup() and await its calls
Expecting jsdom to test layout or CSSNo layout engine: sizes are 0Use a real browser test for visual behavior
Practice
  1. Test a form: type into a labeled input, submit, and assert on the displayed result using only role/label queries.
  2. Test an error state by stubbing a failing fetch and using findByRole("alert").
  3. Deliberately remove an aria-label from a button and observe which query stops working and why that matters.
Key takeaways
  • Test through the user's eyes: query by role, label, and visible text, not classes or structure.
  • getBy throws, queryBy returns null, findBy waits; user-event simulates real interaction.
  • jsdom is fast but has no layout; use real browsers for anything visual.
