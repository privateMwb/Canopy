Service Workers & Offline-First

A service worker is a programmable proxy between your page and the network. It makes offline apps and instant repeat loads possible, and it is the one browser feature where a mistake can keep users on a broken version.

§1What a Service Worker Is

A service worker is a script that the browser runs in the background, separate from any page. It has no DOM access, requires HTTPS (or localhost), and is event-driven: the browser starts it when needed and stops it when idle, so it must not rely on global variables surviving. Its most important event is fetch, which fires for every request from pages it controls, letting it answer from a cache or the network.

// page: register it
if ("serviceWorker" in navigator) {
  window.addEventListener("load", () => {
    navigator.serviceWorker.register("/sw.js").catch(console.error);
  });
}

// sw.js: the lifecycle events
self.addEventListener("install", (e) => {
  e.waitUntil(caches.open("shell-v3").then((c) => c.addAll(["/", "/app.css", "/app.js", "/offline.html"])));
});
self.addEventListener("activate", (e) => {
  e.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(keys.filter((k) => k !== "shell-v3").map((k) => caches.delete(k))))
  );
});

The scope of a service worker is the path it is served from: /sw.js can control the whole site, /app/sw.js only /app/. Place it at the root unless you have a reason not to.

§2Caching Strategies

The fetch handler decides, per request, where the response comes from. Choose the strategy based on the type of resource, not one for everything.

StrategyHow it worksBest for
Cache firstServe from cache; fall back to networkVersioned static assets (hashed JS/CSS, fonts, images)
Network firstTry network; fall back to cache when offlineHTML pages and data that should be fresh
Stale-while-revalidateServe cache immediately, update it in the backgroundContent where speed matters and slight staleness is fine
Network only / cache onlyNo caching / precached onlyAnalytics, non-GET requests / app shell
self.addEventListener("fetch", (e) => {
  const req = e.request;
  if (req.method !== "GET") return;                       // never cache writes

  const url = new URL(req.url);
  if (url.origin !== location.origin) return;             // leave cross-origin alone

  if (req.mode === "navigate") {                          // network first for pages
    e.respondWith(
      fetch(req).catch(() => caches.match("/offline.html"))
    );
    return;
  }

  e.respondWith(                                          // stale-while-revalidate for the rest
    caches.open("assets-v3").then(async (cache) => {
      const cached = await cache.match(req);
      const network = fetch(req).then((res) => {
        if (res.ok) cache.put(req, res.clone());
        return res;
      });
      return cached || network;
    })
  );
});

§3Updates and the Lifecycle

A new sw.js is detected by the browser (it byte-compares the file, checking at least every 24 hours and on navigation), installs beside the old one, and then waits until no open tab is using the old version. This is deliberate, so that one page never mixes two versions of its cache, but it surprises developers who see "my changes don't show up".

// sw.js: opt in to taking over immediately, only if your app tolerates it
self.addEventListener("install", () => self.skipWaiting());
self.addEventListener("activate", (e) => e.waitUntil(self.clients.claim()));

// page: tell users a new version is ready, and let them choose
navigator.serviceWorker.register("/sw.js").then((reg) => {
  reg.addEventListener("updatefound", () => {
    const sw = reg.installing;
    sw.addEventListener("statechange", () => {
      if (sw.state === "installed" && navigator.serviceWorker.controller) {
        showToast("Update available", () => sw.postMessage({ type: "SKIP_WAITING" }));
      }
    });
  });
});
navigator.serviceWorker.addEventListener("controllerchange", () => location.reload());
  • Version your caches (shell-v3) and delete old ones in activate.
  • Never cache the service worker file itself aggressively: serve sw.js with Cache-Control: no-cache.
  • Have a kill switch: a bad service worker can trap users on a broken page, so plan how you would ship a replacement that unregisters itself.
  • Use Workbox for production work; it implements these strategies and precaching correctly.
  • Debug in DevTools Application → Service Workers, with *Update on reload* and *Offline* checkboxes.
A service worker is a deployment, not a feature Because it controls every request and persists between visits, a faulty service worker can outlive a bad release. Version your caches, avoid caching sw.js, and know your rollback path before you ship.

§4Common Mistakes

MistakeWhat HappensFix
Caching sw.js or index.html with a long max-ageUsers cannot receive updatesServe sw.js with no-cache; revalidate HTML
Caching every request with one strategyStale pages or API data; broken POSTsChoose by resource type; only cache GET
Never deleting old cachesStorage grows and stale assets lingerClean up in activate by cache name
Relying on global variables in the workerIt is stopped and restarted; state vanishesPersist in IndexedDB or the Cache
Practice
  1. Precache an app shell and an offline page, then confirm the page loads with DevTools set to Offline.
  2. Implement stale-while-revalidate for images and cache-first for hashed assets, and verify each in the Network panel.
  3. Ship a second version of your service worker and build a "refresh to update" prompt using the lifecycle events.
Key takeaways
  • A service worker is an event-driven network proxy that enables offline use and fast repeat loads.
  • Pick a caching strategy per resource type; version caches and clean them up on activate.
  • Plan the update flow and a kill switch: service workers persist and can strand users on bad releases.
