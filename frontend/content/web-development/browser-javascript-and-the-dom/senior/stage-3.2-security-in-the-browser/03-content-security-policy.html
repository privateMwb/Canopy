Content Security Policy

A Content Security Policy tells the browser which sources of script, style, and other resources are allowed. A strict CSP can stop an XSS bug from becoming an incident, but only if you roll it out carefully.

§1What CSP Does

CSP is a response header that sets rules for what a page may load and execute. When injected script violates the policy, the browser refuses to run it, so CSP reduces the damage of XSS bugs you have not found. It is defense in depth, not a replacement for escaping.

Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  base-uri 'none';
  object-src 'none'
DirectiveControls
default-srcFallback for any fetch directive not listed
script-srcWhere JavaScript may come from, and whether inline scripts run
style-srcStylesheets and inline styles
connect-srcfetch, XMLHttpRequest, WebSocket, EventSource targets
img-src, font-src, media-srcThose resource types
frame-src / frame-ancestorsWhat you may embed / who may embed you
base-uri, form-action, object-srcClose off less obvious injection routes

An allow-list of hosts such as https://cdn.example.com looks simple but is weak in practice: many CDNs and JSONP endpoints host content an attacker can abuse to run script from an "allowed" host. Modern guidance is a nonce- or hash-based strict CSP.

§2Strict CSP with Nonces

With a nonce, the server generates a fresh random value for every response, puts it in the header, and adds the same value to each legitimate <script>. The browser runs only scripts carrying the matching nonce, so an injected script, which cannot know the nonce, is blocked. 'strict-dynamic' lets those trusted scripts load further scripts.

Content-Security-Policy:
  script-src 'nonce-r4nd0mPerResponse' 'strict-dynamic' https: 'unsafe-inline';
  object-src 'none';
  base-uri 'none'

<script nonce="r4nd0mPerResponse" src="/app.js"></script>
<script nonce="r4nd0mPerResponse">window.__CONFIG__ = { api: "/v1" };</script>
<script>alert("injected: has no nonce, blocked")</script>

// the nonce must be unguessable and different on every response
// (in Node: crypto.randomBytes(16).toString("base64"))

Older browsers ignore 'nonce-…' and 'strict-dynamic' and fall back to the https: 'unsafe-inline' tokens, which is why they are included. Nonces need server-rendered HTML; for static sites, use hashes ('sha256-…') of each inline script instead. Avoid 'unsafe-inline' and 'unsafe-eval' for scripts: they remove most of CSP's protection.

§3Rolling Out Safely

Adding CSP to an existing app tends to break things: inline handlers (onclick=), inline <script> blocks, third-party widgets, and eval in libraries. Roll out in stages.

  1. Report only: send Content-Security-Policy-Report-Only with a report-to endpoint. Nothing is blocked, but you collect every violation.
  2. Clean up the findings: move inline handlers to addEventListener, replace eval-using libraries, add nonces to legitimate inline scripts.
  3. Tighten gradually: start with object-src 'none'; base-uri 'none', then script-src, then the rest.
  4. Enforce with Content-Security-Policy, keeping a report endpoint to catch regressions. Keep the report-only header to test the *next*, stricter policy.
Content-Security-Policy-Report-Only:
  script-src 'nonce-abc' 'strict-dynamic'; object-src 'none'; base-uri 'none';
  report-to csp-endpoint
Reporting-Endpoints: csp-endpoint="https://example.com/csp-reports"

// listen for violations during testing
document.addEventListener("securitypolicyviolation", (e) => {
  console.warn("CSP blocked", e.violatedDirective, e.blockedURI, e.sourceFile, e.lineNumber);
});

Pair CSP with other headers: X-Content-Type-Options: nosniff, Referrer-Policy, and Permissions-Policy. Evaluate your draft policy with Google's CSP Evaluator before shipping.

Allow-lists age badly, nonces do not Host allow-lists tend to include endpoints that an attacker can abuse. A per-response nonce with strict-dynamic ties trust to *your* scripts, not to whole domains.

§4Common Mistakes

MistakeWhat HappensFix
Adding 'unsafe-inline' to script-src to "make it work"Injected inline scripts run again; CSP loses its valueUse nonces or hashes for legitimate inline scripts
Reusing one static nonceAttackers can read it from earlier responses and reuse itGenerate a fresh random nonce per response
Deploying an enforcing policy straight to productionPages and widgets break for real usersStart with Report-Only and fix violations first
Allow-listing broad CDNs like https://*.googleapis.comAbusable hosted scripts bypass the policyPrefer nonces plus strict-dynamic
Practice
  1. Add a report-only CSP to a small app and collect the violations it generates; categorize them.
  2. Convert an inline onclick attribute and an inline script block so the page works under a nonce-based CSP.
  3. Run your policy through the CSP Evaluator and fix every high-severity finding.
Key takeaways
  • CSP limits what the browser will load and run, reducing the impact of XSS.
  • Prefer a nonce or hash with 'strict-dynamic' over host allow-lists; avoid 'unsafe-inline' for scripts.
  • Roll out with report-only, clean up violations, then enforce and keep monitoring.
