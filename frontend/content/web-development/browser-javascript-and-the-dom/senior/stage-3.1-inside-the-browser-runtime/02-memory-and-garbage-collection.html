Memory & Garbage Collection

JavaScript frees memory automatically, but only for things that can no longer be reached. Most leaks in real apps are things you forgot you still hold: a listener, a closure, or a detached piece of the DOM.

§1Reachability

A garbage collector frees objects that are unreachable from the roots: global variables, the current call stack, and active listeners and timers. If anything reachable still holds a reference, the object stays alive, even if you will never use it again. A leak, in a garbage-collected language, is unwanted reachability.

let cache = new Map();

function lookup(user) {
  if (!cache.has(user.id)) cache.set(user.id, expensive(user));  // grows forever
  return cache.get(user.id);
}
// every user ever seen stays in memory; the Map is reachable from the module

// bounded alternatives
const weak = new WeakMap();      // keys held weakly: entry vanishes when the key is collected
function remember(obj, value) { weak.set(obj, value); }

WeakMap and WeakSet hold their keys weakly (and WeakRef holds a weak reference), so they do not keep objects alive. They are the right tool for attaching extra data to objects you do not own.

function showModal(content) {
  const modal = document.createElement("div");
  modal.append(content);
  document.body.append(modal);

  const onKey = (e) => e.key === "Escape" && close();
  window.addEventListener("keydown", onKey);            // window outlives the modal

  function close() {
    window.removeEventListener("keydown", onKey);       // without this, modal leaks
    modal.remove();
  }
  return close;
}

// tidier: tie all listeners to one signal
const ctrl = new AbortController();
window.addEventListener("keydown", onKey, { signal: ctrl.signal });
window.addEventListener("resize", onResize, { signal: ctrl.signal });
ctrl.abort();                                           // removes both

§3Finding Leaks with DevTools

The Memory panel shows what is alive. The most reliable technique is the three-snapshot or comparison approach: do the suspect action repeatedly and see what keeps growing.

  1. Open the Memory panel and click the trash can icon (or run the page's cleanup) to force a garbage collection.
  2. Take a heap snapshot as a baseline.
  3. Perform the action (open and close the modal) 10 times, force GC, and take a second snapshot.
  4. Switch the second snapshot to Comparison view; sort by # Delta and look for counts that grew by 10, such as HTMLDivElement or your own classes.
  5. Search for "Detached" to find DOM nodes no longer in the page but still referenced, then open Retainers to see what holds each one.

The Retainers panel is the key: it shows the chain of references from a root to the leaked object, and the last link is usually the thing you forgot to clean up. The Performance panel's memory graph is useful for spotting a sawtooth (healthy: grows, then drops after GC) versus a staircase (leak: never returns to baseline).

Follow the retainer chain A heap snapshot tells you *what* is alive, but the retainers tell you *why*. Find the reference that keeps it alive and break it: remove the listener, clear the timer, or drop the variable.

§4Common Mistakes

MistakeWhat HappensFix
Adding listeners to window without removalEvery instance of a component stays alive foreverRemove on teardown or use an AbortSignal
Keeping element references after remove()Detached DOM trees remain in memorySet references to null or avoid holding them
Caching without a boundMemory grows with use until the tab slows or crashesAdd a size limit, eviction, or use WeakMap
Judging a leak from one readingGC timing makes single numbers misleadingCompare snapshots after forced GC across repeated actions
Practice
  1. Write a modal that leaks through a window listener, find it with snapshot comparison and the Retainers panel, and fix it.
  2. Replace an unbounded Map cache with a size-limited LRU, and show the memory stays flat.
  3. Record a memory timeline while repeating an action and identify the sawtooth versus staircase pattern.
Key takeaways
  • A leak is something unwanted that is still reachable: listeners, timers, detached DOM, closures, and caches.
  • Tie listeners and timers to a lifecycle and clean up; use WeakMap and bounded caches.
  • Find leaks by comparing heap snapshots across repeated actions and reading the retainers.
