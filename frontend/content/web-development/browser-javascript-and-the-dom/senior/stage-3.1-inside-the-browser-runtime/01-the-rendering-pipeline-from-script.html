The Rendering Pipeline from Script

Every visual change goes through the same stages: style, layout, paint, and composite. Knowing which stage your JavaScript triggers tells you why one animation is smooth and another stutters.

§1The Pipeline

After your script runs, the browser turns the DOM and CSS into pixels in a series of steps. Each step depends on the one before it, and changing something early forces all the later steps to repeat.

StageWhat it doesTriggered by changing
StyleMatch CSS rules to elements; compute final valuesClasses, attributes, stylesheets
LayoutCompute size and position of every boxwidth, height, margin, top, text, font size
PaintFill in pixels: text, colors, borders, shadowscolor, background, box-shadow, border-radius
CompositeCombine layers on the GPU in the right ordertransform, opacity

Layout is the most expensive stage for most pages, because moving one box can move many others. Paint is cheaper, and compositing is the cheapest of all, because it only rearranges layers that are already painted.

§2What Your Script Triggers

Changing a property that affects layout makes the browser re-run layout (and then paint and composite). Animating left or width therefore does heavy work on every frame, while animating transform and opacity can often skip layout and paint entirely and run on the compositor.

// expensive: layout + paint + composite on every frame
function slideBad(el, x) { el.style.left = x + "px"; }

// cheap: composite only, can run off the main thread
function slideGood(el, x) { el.style.transform = `translateX(${x}px)`; }

// let the browser prepare a layer for something that will animate
/* .moving { will-change: transform; } */   // use sparingly: each layer uses memory

Resist adding will-change everywhere. Each promoted layer costs GPU memory, and too many layers slow things down instead of speeding them up. Apply it only to elements that really are about to animate, and remove it afterward.

§3Forced Synchronous Layout

The browser normally batches style and layout work until the end of the frame. But if you read a layout-dependent value (such as offsetHeight, getBoundingClientRect(), or getComputedStyle(el).width) after a write, it must stop and compute layout right now so the answer is correct. This is a forced synchronous layout, and doing it in a loop is layout thrashing.

// thrashing: each iteration writes, then reads, forcing a layout
for (const card of cards) {
  card.style.width = list.offsetWidth / 3 + "px";   // read forces layout, write dirties it
}

// fix: batch reads, then writes
const w = list.offsetWidth / 3;                      // one read
for (const card of cards) card.style.width = w + "px";   // then all writes

// or schedule reads/writes around the frame
requestAnimationFrame(() => {
  const heights = items.map((el) => el.offsetHeight);       // reads
  items.forEach((el, i) => (el.style.minHeight = heights[i] + "px"));  // writes
});

You can see this in the DevTools Performance panel: purple "Recalculate Style" and "Layout" blocks, often with a warning about forced reflow, repeating inside a single function. The call stack under the block shows exactly which line forced it.

Ask which stage you are paying for Before optimizing an animation or update, decide whether it needs layout, paint, or only compositing. Moving work to transform and opacity, and batching reads before writes, solves most rendering performance problems.

§4Common Mistakes

MistakeWhat HappensFix
Animating top, left, width, or heightLayout runs every frame; dropped framesAnimate transform and opacity instead
Alternating reads and writes of layout propertiesForced synchronous layout, thrashingRead everything first, then write
Adding will-change to many elementsExcess layers and GPU memory useApply only to elements about to animate
Changing a class on <body> for a tiny updateStyle recalculation across the whole pageScope changes to the smallest container
Practice
  1. Record the same animation twice in the Performance panel, once with left and once with transform, and compare the layout and paint costs.
  2. Reproduce layout thrashing on a list of 1,000 items and fix it by batching, measuring before and after.
  3. Find the property that triggers only compositing, then check a site you like with the Rendering tools' "Paint flashing" option.
Key takeaways
  • Style, layout, paint, and composite run in order; earlier changes re-run later stages.
  • transform and opacity can skip layout and paint; animate those where possible.
  • Reading layout values right after writes forces synchronous layout: batch reads before writes.
