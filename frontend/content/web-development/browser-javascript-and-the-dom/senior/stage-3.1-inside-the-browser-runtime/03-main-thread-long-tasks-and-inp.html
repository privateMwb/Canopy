Main Thread, Long Tasks & INP

Users judge your app by how quickly it responds when they touch it. Interaction to Next Paint (INP) measures that, and nearly every bad INP is the main thread being busy when the user acts.

§1Responsiveness and INP

Interaction to Next Paint (INP) is a Core Web Vital that measures the delay between a user interaction (click, tap, key press) and the next frame the browser paints in response. Over a page visit it reports roughly the worst interaction. It replaced First Input Delay because it captures the whole page lifetime and the full response, not just the start.

INPRating (at the 75th percentile of real users)
≤ 200 msGood
200 – 500 msNeeds improvement
> 500 msPoor

Each interaction has three parts: input delay (waiting for the main thread to be free), processing time (your event handlers), and presentation delay (rendering the result). Any of them can dominate, and the fix differs for each.

§2Long Tasks

A long task is any task that occupies the main thread for more than 50 ms. While it runs, the browser cannot respond to input or paint. You can observe them directly:

new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.warn("long task", Math.round(entry.duration) + "ms", entry.attribution?.[0]?.containerSrc);
  }
}).observe({ type: "longtask", buffered: true });

// measure your own work
performance.mark("filter-start");
filterRows();
performance.mark("filter-end");
performance.measure("filter", "filter-start", "filter-end");
console.table(performance.getEntriesByName("filter"));

In the DevTools Performance panel, long tasks appear as grey blocks with a red corner. Expand one to see its call tree and find which function takes the time. Common culprits are large JSON parsing, rendering thousands of nodes, expensive event handlers, and third-party scripts.

§3Breaking Up Work

You cannot make a long task shorter by wishing; you split it so that the browser can handle input and paint between the pieces. This is called yielding.

// modern: scheduler.yield() resumes with priority after the browser handles input
async function processItems(items) {
  for (const item of items) {
    handle(item);
    if (navigator.scheduling?.isInputPending?.() || shouldYield()) {
      await (globalThis.scheduler?.yield?.() ?? new Promise((r) => setTimeout(r)));
    }
  }
}

// time-sliced loop: yield about every 40ms
let deadline = performance.now() + 40;
const shouldYield = () => performance.now() > deadline && ((deadline = performance.now() + 40), true);

// give instant feedback, then do the heavy part
button.addEventListener("click", () => {
  spinner.hidden = false;                       // cheap, shows up in the next frame
  setTimeout(() => { heavy(); spinner.hidden = true; });
});
  • Do the minimum in the event handler: update visible state first, defer the rest.
  • Move pure computation to a Web Worker so it is off the main thread completely.
  • Render less: virtualize long lists, paginate, and avoid touching thousands of nodes at once.
  • Defer or lazy-load third-party scripts; they often account for a large share of long tasks.
  • Debounce or throttle high-frequency handlers (input, scroll, pointermove).
Visible response first Users forgive work that takes time, but not silence. Acknowledge the interaction in the next frame (a pressed state, a spinner), then do the heavy work in smaller pieces or in a worker.

§4Common Mistakes

MistakeWhat HappensFix
Running heavy work directly inside a click handlerLong processing time delays the next paint; poor INPUpdate the UI first, then defer or chunk the work
Assuming async makes code non-blockingSynchronous CPU work inside an async function still blocksYield, or move CPU work to a worker
Optimizing average timings onlyINP reflects the worst interactionsLook at slow percentiles and field data
Ignoring third-party scriptsThey are a frequent source of long tasks you cannot see in your own codeAttribute tasks in the profiler; defer or remove them
Practice
  1. Add a PerformanceObserver for longtask and trigger one deliberately; find it in the Performance panel's call tree.
  2. Rewrite a 300 ms click handler to show feedback immediately and yield during the heavy processing, and compare INP in the Web Vitals extension.
  3. Identify which part of INP (input delay, processing, presentation) dominates in a slow interaction on a real page.
Key takeaways
  • INP measures how long users wait to see a response to their input; under 200 ms is good.
  • Any task over 50 ms blocks input and painting: find them with the profiler and longtask observer.
  • Respond visibly first, then break up, defer, or offload the work to keep the main thread free.
