Frameworks vs. the Platform

Frameworks solve real problems, and the browser has quietly absorbed many of them. Choosing between them is a judgment about cost, team, and time horizon, not a loyalty test.

§1What a Framework Actually Earns You

Before deciding, name the specific problems a framework would solve for you. Most of the value falls into a few categories:

ProblemWhat frameworks provideWhat the platform offers now
Keeping UI in sync with stateDeclarative rendering, efficient diffing, reactivity<template>, custom elements, manual rendering; no built-in reactivity
Component model and reuseComponents with props, slots, lifecycleCustom elements, Shadow DOM, slots
Routing and navigationClient routers, nested layouts, data loadingHistory API, Navigation API, View Transitions, multi-page navigation
Team conventionsA shared mental model, docs, ecosystem, hiring poolStandards, but few conventions
Server rendering and dataSSR, streaming, code splitting, build integrationStreaming HTML, fetch; no built-in orchestration
Tooling and devtoolsDev servers, HMR, testing integrations, component devtoolsDevTools and Vite-style tools

The honest summary: frameworks are strongest at state-driven UI at scale with a team, and the platform has caught up substantially on components, routing, animation, forms, dialogs, and layout. A great deal of what once justified a framework is now a few lines of HTML, CSS, or platform JavaScript.

§2What the Platform Gives You Now

Many features that people once reached for libraries to get are built in. Knowing them lets you remove dependencies and write less code.

<!-- a modal with focus trapping, Esc to close, backdrop: no library -->
<dialog id="d"><form method="dialog"><p>Delete this?</p><button value="ok">Delete</button><button value="cancel">Cancel</button></form></dialog>

<!-- disclosure, popovers, and form validation without JavaScript -->
<details><summary>More</summary>...</details>
<button popovertarget="menu">Menu</button><div id="menu" popover>...</div>
<input type="email" required>

// native dialog, animated page transitions, and container queries
d.showModal();
document.startViewTransition(() => updateDOM());          // cross-fade between states
/* @container (min-width: 400px) { .card { display: grid; } } */

// the platform's own components and reactivity primitives you can build on
customElements.define("x-counter", class extends HTMLElement { /* ... */ });
const abort = new AbortController();                      // cancellation and cleanup for listeners and fetch

That said, the platform still has gaps: no declarative, reactive templating built in; no standard for server-rendered hydration; and ergonomics for large-scale state and data fetching are left to you. These are exactly the gaps frameworks fill.

§3Making the Call

A good decision weighs the costs of both sides against the specific situation, rather than defaulting to what is familiar or fashionable.

  • Complexity of the UI: a mostly static site with some interactivity needs little; a dense, stateful app (editors, dashboards, real-time collaboration) benefits greatly.
  • Team: size, experience, and turnover matter. A framework is a shared language, and a convention that new hires may already know. A homegrown solution needs documentation and discipline.
  • Lifespan: a campaign page that lives three months favors the lightest tools. A product maintained for a decade favors the choice with the strongest long-term support and the fewest sharp edges.
  • Performance budget: frameworks add JavaScript to download, parse, and run. On low-end devices, that cost is real; measure it (and consider server rendering, islands, or lighter frameworks).
  • Lock-in and churn: weigh upgrade costs, ecosystem health, and how hard migration would be. Platform features are the most durable code you can write.
  • A middle path: use the platform by default, and add a small, focused library (or a lightweight framework) where the pain is demonstrable, without adopting a whole stack for one problem.

Whatever you choose, write down why, including the alternatives you rejected and the conditions under which you would revisit the decision (the next lessons cover how). "Everyone uses it" and "frameworks are bloat" are both reasons that will not survive a thoughtful reviewer.

Decide from the problem, not the tool Start by listing the concrete problems you have (state sync, routing, SSR, team onboarding). Then ask which solution addresses them at the lowest long-term cost. The answer is sometimes a framework, and sometimes a <dialog>.

§4Common Mistakes

MistakeWhat HappensFix
Adopting a framework for a mostly static pageLarge JavaScript cost with little benefitUse HTML, CSS, and a little platform JavaScript
Rebuilding a framework by hand on a big teamUndocumented conventions and re-solved problemsAdopt an established framework and its conventions
Choosing by popularity or preference alonePoor fit; costs discovered lateEvaluate against concrete requirements and constraints
Ignoring platform features that replace dependenciesExtra code and bundle size for no gainAudit for built-ins like dialog, popovers, and view transitions
Practice
  1. List five libraries in a project and, for each, decide whether a current platform feature could replace it, with evidence.
  2. Rebuild one small interactive piece with plain platform APIs and with a framework; compare code size, bundle cost, and clarity.
  3. Write a half-page recommendation for a hypothetical project (static marketing site vs. collaborative editor) with your reasoning.
Key takeaways
  • Frameworks earn their cost in state-driven UI, conventions, and tooling at scale; the platform now covers a lot more than it used to.
  • Decide from concrete problems, team, lifespan, and performance budget, not preference.
  • Prefer the platform by default, add focused tools where pain is demonstrated, and record the reasoning.
