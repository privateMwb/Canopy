Performance Budgets & Real-User Monitoring

A site does not stay fast by accident. Performance budgets turn "be fast" into limits a build can enforce, and real-user monitoring tells you what people actually experience, which is rarely what your laptop shows.

§1Measuring What Users Feel

Pick metrics that reflect real experience. Google's Core Web Vitals are the common baseline, and they are measured at the 75th percentile of real page loads, because averages hide the slow experiences that matter most.

MetricMeasuresGood
LCP Largest Contentful PaintWhen the main content is visible≤ 2.5 s
INP Interaction to Next PaintResponsiveness to input across the visit≤ 200 ms
CLS Cumulative Layout ShiftVisual stability (unexpected movement)≤ 0.1

Supporting metrics help diagnosis: TTFB (server and network start), FCP (first paint), total JavaScript bytes, and number of requests. A metric you cannot connect to a user-visible experience is probably not worth a budget.

§2Budgets You Can Enforce

A performance budget is a set of limits the team agrees on and enforces automatically, so regressions are caught in review rather than discovered by users. Budgets work best when they are few, specific, and tied to the user experience.

// budgets.json: limits checked in CI
{
  "initialRouteJsKb": 170,        // compressed JavaScript for the first route
  "totalImagesKb": 500,
  "lcpMs": 2500,                   // lab value on a throttled mid-range profile
  "clsMax": 0.1,
  "thirdPartyRequests": 8
}

// Lighthouse CI assertion example
{
  "ci": { "assert": { "assertions": {
    "largest-contentful-paint": ["error", { "maxNumericValue": 2500 }],
    "cumulative-layout-shift": ["error", { "maxNumericValue": 0.1 }],
    "resource-summary:script:size": ["error", { "maxNumericValue": 174080 }]
  } } }
}
  • Set the first budget from what you measure today and your competitors, then ratchet it down; an impossible number gets ignored.
  • Fail the build (or block the merge) when a budget is exceeded, with a clear message about which change caused it.
  • Budget in user-facing terms where possible (seconds to interactive on a mid-range phone), not only file sizes.
  • Use bundle analysis in each pull request to show what a change added.
  • Allow a deliberate exception process: someone must justify and sign off on exceeding the budget.

§3Real-User Monitoring

Lab data (Lighthouse, DevTools) is controlled and repeatable, which is good for catching regressions and diagnosing causes. Field data from real users, called RUM, tells you whether it actually matters to them: real devices, real networks, real geographies. You need both, and they often disagree.

import { onLCP, onINP, onCLS, onTTFB } from "web-vitals";

function send(metric) {
  const body = JSON.stringify({
    name: metric.name,
    value: metric.value,
    rating: metric.rating,                 // "good" | "needs-improvement" | "poor"
    id: metric.id,
    page: location.pathname,               // group by route, not full URL
    nav: metric.navigationType,
    conn: navigator.connection?.effectiveType,
    release: "2026.10.3",
  });
  navigator.sendBeacon("/rum", body) || fetch("/rum", { method: "POST", body, keepalive: true });
}
onLCP(send); onINP(send); onCLS(send); onTTFB(send);
  • Analyze by percentile (p75, p95), and segment by route, device class, country, and connection type; the problem is usually in a segment.
  • Tag with a release so you can see whether a deploy moved a metric, and set alerts on regressions rather than staring at dashboards.
  • Combine with the public Chrome UX Report (CrUX) for a free field baseline and competitor comparisons.
  • Respect privacy: collect performance data without personal information, and follow your consent obligations.
  • Turn insight into action: a slow p75 LCP on product pages becomes a prioritized, measurable ticket.
Averages lie, percentiles tell the truth If your median is great but your p95 is terrible, a large number of real users are having a bad time. Budget and alert on the percentile that represents your slower users.

§4Common Mistakes

MistakeWhat HappensFix
Tracking only lab scores from a fast laptopReal users on phones are much slowerAdd RUM and test with CPU and network throttling
Reporting averagesSlow experiences are hiddenUse p75/p95 and segment by device and route
Setting budgets nobody enforcesThey become decoration; performance decaysFail the build or block the merge
Choosing too many metricsNobody knows what to prioritizePick a few tied to user experience
Practice
  1. Add web-vitals to a page, send metrics to a simple endpoint, and chart p75 by route.
  2. Define a three-item budget for a project and wire it into CI so a deliberately bloated PR fails.
  3. Compare Lighthouse numbers with CrUX field data for a public site and write down why they differ.
Key takeaways
  • Measure what users feel (LCP, INP, CLS) at the 75th percentile of real page loads.
  • Budgets only work if they are few, user-relevant, and enforced automatically in CI.
  • Use lab data to diagnose and field data to decide what matters; segment and alert on regressions.
