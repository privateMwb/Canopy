Migrating Legacy Markup

Modernizing a large site without a rewrite means measuring first, fixing in small safe steps, and using automation to keep progress from slipping backward.

§1Audit and Prioritize

Start with data, not opinions. Crawl the site and gather counts: validation errors, missing alt, tables used for layout, inline styles, non-semantic click handlers, and accessibility violations per template.

ImpactEffortExample
HighLowAdd lang, doctype, and viewport; label form fields
HighMediumReplace div onclick with button; fix heading structure
MediumMediumReplace layout tables with CSS Grid
LowHighRemove inline styles site-wide

Fix templates and shared components first. One change in a layout improves thousands of pages.

§2The Strangler Pattern

Rather than a big-bang rewrite, replace pieces gradually. New and updated components use modern markup, old ones stay until they're touched, and a boundary keeps them from clashing.

<!-- before: layout table and a click handler on a div -->
<table width="100%"><tr><td class="nav">...</td><td>...</td></tr></table>
<div onclick="go('/pricing')">Pricing</div>

<!-- after -->
<div class="layout"><nav aria-label="Primary">...</nav><main>...</main></div>
<a href="/pricing/">Pricing</a>

Where CSS depends on the old structure, add the new markup behind a feature flag or ship both and switch gradually, comparing screenshots as you go.

§3Guardrails and Metrics

  • Add linters and axe checks to CI for new code first, with a baseline of known violations that can only shrink.
  • Track metrics over time: violations per page, Lighthouse accessibility score, and HTML payload size.
  • Use automated codemods for mechanical changes such as self-closing tags or removing deprecated attributes.
  • Test with real assistive technology on the top user journeys after each phase.
  • Communicate progress in terms people care about: fewer support tickets, better conversion, easier maintenance.

A migration succeeds when it is boring: small reversible changes, measured before and after.

Ratchet, don't reset Set a baseline of today's violations and fail CI only on new ones. Lower the baseline as you fix old issues, so you never regress while you improve.

§4Common Mistakes

MistakeWhat HappensFix
Proposing a total rewriteHigh risk, long delay, no incremental valueMigrate template by template with measurable goals
Fixing individual pages instead of templatesThe same bugs reappear everywhereFix shared layouts and components first
No guardrails after the cleanupNew violations creep inEnforce linting and accessibility checks in CI
Practice
  1. Crawl a sample site or your own project and build a table of the top ten markup problems by count.
  2. Define a CI ratchet: a baseline file of current violations that the build is not allowed to exceed.
Key takeaways
  • Audit with data and prioritize by impact and effort.
  • Migrate gradually, starting with templates and shared components.
  • Use CI guardrails and metrics to lock in progress.
