How the Web Delivers a Page

Every page starts as a text response to a request; knowing the round trip tells you what your HTML is, who reads it, and where things can go wrong.

§1The Request and the Response

When you type a URL and press Enter, the browser opens a connection to a server and sends an HTTP request. The server answers with a response: a status line, headers, and a body. For a web page, the body is HTML — plain text that describes the page.

GET /index.html HTTP/1.1
Host: example.com
Accept: text/html

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1256

<!DOCTYPE html>
<html lang="en"> ... </html>

The Content-Type header is what tells the browser to treat the body as HTML. A file named index.html served with the wrong type may be shown as raw text or offered as a download.

§2From Bytes to a Rendered Page

The browser reads the HTML as it arrives and builds an in-memory tree called the DOM (Document Object Model). While parsing, it finds more resources — stylesheets, scripts, images — and requests each one with its own request.

  1. Request the HTML document and start parsing it.
  2. Discover linked CSS, JavaScript, and images, and fetch them.
  3. Combine the DOM with the styles to work out layout.
  4. Paint pixels to the screen.

HTML itself has no colors or layout; it describes structure and meaning. CSS handles presentation and JavaScript handles behavior. Keeping those three jobs separate is the foundation of everything in this path.

§3Where the Page Comes From

A URL such as https://example.com/about/ maps to a file or to a program that builds HTML on request. A static site serves ready-made files; a dynamic site runs code on each request and returns generated HTML. Either way, the browser sees the same thing: HTML text.

PieceExampleRole
ProtocolhttpsHow the browser talks to the server
Hostexample.comWhich server to contact (found via DNS)
Path/about/Which resource the server should return
The key insight HTML is just text delivered over HTTP. You can always right-click and view source to see exactly what the server sent, before any scripts changed the page.

§4Common Mistakes

MistakeWhat HappensFix
Thinking the browser shows the file you wrote byte for byteThe browser parses it into a DOM; error recovery and scripts can change what ends up on screenCompare View Source (what was sent) with the Elements panel (the live DOM)
Opening file:/// paths and expecting server behaviorRedirects, headers, and root-relative links behave differently without a serverUse a local server such as python3 -m http.server when testing
Serving HTML with the wrong Content-TypeThe page displays as plain text or downloadsMake sure the server sends text/html; charset=utf-8
Practice
  1. Open any site, view its source, and find the <title>. Then open DevTools and see whether the Elements panel matches.
  2. In the Network tab, reload a page and list every request it makes. Which one is the HTML document?
Key takeaways
  • A page is an HTTP response whose body is HTML text.
  • The browser parses HTML into the DOM and then fetches the other resources it discovers.
  • HTML describes structure; CSS handles looks and JavaScript handles behavior.
