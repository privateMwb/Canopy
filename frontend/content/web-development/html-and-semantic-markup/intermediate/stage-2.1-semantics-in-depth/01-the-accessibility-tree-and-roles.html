The Accessibility Tree & Roles

Browsers turn your DOM into a second tree of roles, names, and states for assistive technology; seeing that tree shows whether your markup means what you think.

§1From DOM to Accessibility Tree

For each element, the browser computes an accessibility object with four key properties: role (what it is), name (what it's called), state (checked, expanded, disabled), and description. Screen readers, voice control, and switch devices all consume this tree rather than your pixels.

<button>Save</button>
<!-- role: button   name: "Save" -->

<input type="checkbox" id="news" checked>
<label for="news">Newsletter</label>
<!-- role: checkbox   name: "Newsletter"   state: checked -->

<div class="btn">Save</div>
<!-- role: generic   name: none — nothing here says "button" -->

Open the Accessibility panel in Chrome or Firefox DevTools to inspect any element's computed role and name.

§2How a Name Is Computed

The accessible name comes from the first available source, roughly in this order: aria-labelledby, aria-label, native content such as an associated <label>, alt, or the element's text, and finally title.

<!-- name from content -->
<a href="/cart/">Cart (3)</a>

<!-- name from aria-label, when no visible text exists -->
<button aria-label="Close dialog">✕</button>

<!-- name from another element -->
<h2 id="t">Billing</h2>
<section aria-labelledby="t">...</section>

Prefer visible text as the name. Voice-control users say what they see on screen, so a name that differs from visible text makes the control hard to activate.

§3Roles, States, and ARIA

Native elements get implicit roles: <nav> is navigation, <ul> is list. ARIA attributes can add or override them when HTML has no equivalent.

<button aria-expanded="false" aria-controls="menu">Menu</button>
<ul id="menu" hidden>...</ul>

ARIA changes only what is *announced*, never what the element *does*. role="button" on a div doesn't add keyboard handling or focus; you still have to build all of it.

Five rules of ARIA, abridged Use a native element if one exists. Don't change native semantics without a reason. Every interactive ARIA control must work with the keyboard. Don't hide a focusable element from the tree. Every interactive element needs an accessible name.

§4Common Mistakes

MistakeWhat HappensFix
Adding role="button" to a div and stopping thereAnnounced as a button but not focusable or operableUse <button>
Using aria-label that contradicts visible textVoice control users can't activate it by nameMake the name start with, or match, the visible label
Putting aria-hidden="true" on a focusable elementKeyboard users land on something screen readers can't seeRemove it from focus order too, or don't hide it
Setting redundant roles such as <nav role="navigation">Noise and maintenance burdenRely on the implicit role
Practice
  1. Open a site in DevTools' Accessibility panel and find three elements whose role or name is wrong or missing.
  2. Add an accessible name to an icon-only button three different ways and compare the results.
Key takeaways
  • Assistive technology reads the accessibility tree: role, name, state, description.
  • Native elements fill the tree correctly; ARIA only adjusts what is announced.
  • Every interactive control needs an accessible name that matches what users see.
