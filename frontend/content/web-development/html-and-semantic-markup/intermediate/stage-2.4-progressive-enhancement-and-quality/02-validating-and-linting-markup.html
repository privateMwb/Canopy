Validating & Linting Markup

Validators and linters catch invalid and inaccessible markup early, and running them automatically in CI keeps quality from drifting.

§1Validators vs. Linters

A validator checks your HTML against the specification: unclosed tags, bad nesting, invalid attributes. A linter goes further, enforcing team conventions and best practices: missing alt, duplicate ids, inline styles.

ToolChecksWhere it runs
Nu Html Checker (validator.w3.org/nu)Spec conformanceWeb, CLI, or Java jar
html-validateSpec plus configurable rulesnpm, CLI, editor, CI
htmlhintConvention-based rulesnpm, editor, CI
axe-core, Pa11yAccessibility rules on rendered pagesBrowser, CLI, CI

§2Running a Check Locally

Install a linter and run it on your files as part of development.

npm install --save-dev html-validate
npx html-validate "src/**/*.html"
# .htmlvalidate.json
# { "extends": ["html-validate:recommended"] }

Editor integrations show the same errors inline, so you fix them as you type rather than at the end.

§3Automating in CI

Add the check to your continuous integration so that an invalid or inaccessible page fails the build before it ships.

# .github/workflows/html.yml
name: html
on: [pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: npm ci
      - run: npx html-validate "src/**/*.html"

Automated tools can detect only a portion of accessibility problems. They complement manual testing with a keyboard and a screen reader; they do not replace it.

Fix the cause, not the count One unclosed tag can produce dozens of errors. Fix errors from the top down and re-run, rather than chasing every line in the report.

§4Common Mistakes

MistakeWhat HappensFix
Validating only once at the endA mountain of errors piles upRun checks continuously in the editor and CI
Silencing rules without understanding themReal problems stay hiddenDisable a rule only with a written reason
Treating a clean report as proof of accessibilityTools can't judge alt text quality or reading orderAdd manual and assistive-technology testing
Practice
  1. Install a linter in a project and fix everything it reports on your pages.
  2. Add a CI step that fails on any validation error.
Key takeaways
  • Validators check the spec; linters add conventions and best practice.
  • Run checks in the editor and automate them in CI.
  • Tooling catches only part of the problems; test manually too.
