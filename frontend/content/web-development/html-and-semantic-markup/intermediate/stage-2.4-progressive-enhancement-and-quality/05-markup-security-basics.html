Markup Security Basics

Safe markup means isolating third-party content, preventing opener leaks, and never trusting HTML that came from a user.

§1Links and rel

A page opened with target="_blank" can historically access the opener through window.opener. Modern browsers now treat _blank links as noopener by default, but being explicit is harmless and protects older ones.

<a href="https://partner.example" target="_blank" rel="noopener noreferrer">Partner</a>

<!-- user-generated links: tell search engines you don't vouch for them -->
<a href="https://user-site.example" rel="ugc nofollow noopener">User link</a>

noreferrer also withholds the Referer header, which can matter for privacy. ugc, sponsored, and nofollow are search signals and not security features.

§2Sandboxing Third-Party Content

An <iframe> with sandbox runs with restrictions: no scripts, forms, popups, or same-origin access unless you grant them one by one.

<iframe src="https://widget.example/embed"
        title="Weather widget"
        sandbox="allow-scripts"
        referrerpolicy="no-referrer"
        loading="lazy"></iframe>

Be careful combining allow-scripts with allow-same-origin for content on your own origin; together they let the frame remove its own sandbox.

§3Never Trust User HTML

If you insert user-supplied text as HTML, anything they type can become executable markup. This is cross-site scripting (XSS).

// DANGEROUS: runs <img onerror=...> or <script> from user input
el.innerHTML = userInput;

// SAFE for plain text
el.textContent = userInput;

If you must allow some HTML (for example, comments with bold and links), sanitize it with a well-maintained library and an allowlist, never with a hand-written regular expression. Add a Content-Security-Policy header as a second line of defense. Both topics return in the Senior level.

Escape on output Treat all user input as text. Where HTML is created from it, the output must be escaped or sanitized for the context it lands in.

§4Common Mistakes

MistakeWhat HappensFix
Using innerHTML with unsanitized inputScript injection and account takeoverUse textContent, or sanitize with an allowlist
Embedding an iframe with no sandboxThird-party content runs with full page privilegesAdd sandbox and grant only what is needed
Assuming rel="nofollow" improves securityIt only affects search enginesUse noopener and a sandbox for real isolation
Practice
  1. Write a form that echoes a comment back to the page using textContent, then try it with <img src=x onerror=alert(1)> as input.
  2. Add a sandbox to an iframe and loosen it one token at a time until the widget works.
Key takeaways
  • Use rel="noopener" with target="_blank".
  • Sandbox third-party iframes and grant minimal permissions.
  • Treat user input as text; sanitize any HTML with a proven library.
