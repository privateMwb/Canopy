Event-Driven Architecture

Queues, streams, and eventual consistency.

§1Announcing Facts Instead of Giving Orders

In a synchronous design, the Orders service calls Email, Inventory, Analytics, and Loyalty in turn. It knows about all of them, waits for each, and fails if any fails. In an event-driven design, Orders simply publishes a fact, OrderPlaced, and any interested service subscribes and reacts on its own schedule. The publisher no longer knows or cares who is listening.

Events travel through a broker such as RabbitMQ, Amazon SNS/SQS, Google Pub/Sub, or Apache Kafka (a durable, replayable log). Queues deliver each message to one consumer in a group; topics and logs fan out to many.

§2What You Gain

  • Decoupling: add a new reaction (fraud scoring, analytics) without touching the publisher.
  • Resilience: if Email is down, events wait in the broker and are processed on recovery, rather than failing the order.
  • Load smoothing and independent scaling of consumers.
  • An audit trail: with a durable log, you can replay history to rebuild a read model or backfill a new service.

§3What You Pay

  • Eventual consistency. After an order is placed, the inventory count, search index, and email are updated later. The UI and the business must be designed for "not yet visible."
  • Harder reasoning and debugging. Control flow is implicit: nothing in one place shows what happens when an order is placed. Invest in tracing, event catalogs, and correlation ids.
  • At-least-once delivery. Duplicates happen, so consumers must be idempotent.
  • Ordering is limited. Order is generally guaranteed only within a partition or key (for example, per order id), not globally.

§4Publishing Reliably: The Outbox Pattern

A classic bug: you save the order to the database and then publish to the broker. If the process dies between the two, the order exists but no one was told (or, in reverse order, the event exists but the order does not). You cannot make a database commit and a broker publish atomic. The fix is the transactional outbox: write the event to an outbox table in the same transaction as the business change, and let a separate relay publish it.

// One transaction: the state change and the event commit together or not at all
await db.transaction(async tx => {
  await tx.query("INSERT INTO orders (id, customer_id, total) VALUES ($1, $2, $3)", [id, customerId, total]);
  await tx.query(
    "INSERT INTO outbox (id, type, aggregate_id, payload) VALUES ($1, 'OrderPlaced', $2, $3)",
    [crypto.randomUUID(), id, JSON.stringify({ orderId: id, customerId, total })]
  );
});

// Relay (separate process): poll unpublished rows, publish, mark as published.
// Delivery is at-least-once: a crash after publish but before marking means a re-send.
// Consumers therefore dedupe by event id.

§5Designing Consumers

async function handleOrderPlaced(event) {
  const already = await db.query(
    "INSERT INTO processed_events (consumer, event_id) VALUES ('inventory', $1) ON CONFLICT DO NOTHING RETURNING 1",
    [event.id]);
  if (already.rowCount === 0) return;                // duplicate delivery: safe no-op

  await reserveStock(event.payload.orderId);         // ideally in the same transaction as the dedupe insert
}
  • Make events self-describing and versioned (type, version, id, occurredAt, payload). Evolve them additively, like any public API, since you cannot update every consumer at once.
  • Prefer events that carry the facts consumers need ("event-carried state transfer") over thin events that force every consumer to call back for details.
  • Handle poison messages with bounded retries and a dead-letter queue, and alert on it.

§6Long-Running Workflows: Sagas

Without distributed transactions, a multi-step business process (reserve stock, charge card, schedule shipping) is coordinated as a saga: a sequence of local transactions where each step publishes an event triggering the next, and a failure triggers compensating actions that undo earlier steps (release the stock, refund the card). Sagas can be choreographed (services react to each other's events) or orchestrated (a coordinator directs each step); orchestration is easier to follow and monitor as flows grow.

Events are not free decoupling Services coupled through event meaning are still coupled: changing an event's shape or semantics can break unknown consumers. Treat events as published contracts with owners, schemas, and compatibility rules, not as internal implementation details.

§7Common Mistakes

Assuming global orderingConsumers see updates out of order and corrupt statePartition by the entity key, and design handlers to tolerate reordering using versions
Practice
  1. Implement an outbox table and a relay for one event in a sample app, then kill the relay mid-publish and verify consumers handle the duplicate.
  2. Write the event schema (with version and id) for OrderPlaced and state two backward-compatible changes and one breaking change.
  3. Design a saga for "place order" with three steps and write the compensating action for each.
Key takeaways
  • Events announce facts; publishers stay decoupled, at the price of eventual consistency and implicit control flow.
  • Use the transactional outbox to publish reliably and make every consumer idempotent.
  • Version events like public APIs, bound retries with dead-letter queues, and use sagas with compensation for multi-step workflows.
