Multi-Tenancy & Data Isolation

Serving many customers safely.

§1Many Customers, One System

A SaaS product serves many tenants (companies, workspaces, organizations), and each expects its data to be private. Multi-tenancy is the architecture that serves them all from shared infrastructure while keeping them isolated. The central risk is stark: a single missing filter and Tenant A sees Tenant B's data, which is often a company-ending incident. The central trade-off is between isolation strength and operational cost.

§2Three Isolation Models

ModelHowIsolationCost and operations
Pool (shared tables)All tenants in the same tables, every row carries a tenant_idLogical; relies on correct filteringCheapest; simplest to operate and migrate; noisy-neighbor risk
Bridge (schema per tenant)One database, one schema per tenantStronger; separate namespacesModerate; migrations run N times; thousands of schemas strain the catalog
Silo (database or stack per tenant)Dedicated database (or whole deployment) per tenantStrongest; per-tenant backups, encryption keys, and regionsHighest cost and operational load; best for large or regulated customers

Many products use a hybrid: pooled by default, with a silo for enterprise customers who require dedicated infrastructure or data residency. Design the code so the tenant's "home" (which database holds their data) is resolved in one place.

§3Pooled Isolation: Make Leaks Impossible, Not Unlikely

With shared tables, relying on every developer to remember WHERE tenant_id = ... in every query will eventually fail. Push enforcement into the database with row-level security (RLS) in PostgreSQL, so even a buggy query cannot cross tenants.

-- Every tenant-owned table has tenant_id, and RLS enforces it
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;
ALTER TABLE notes FORCE ROW LEVEL SECURITY;           -- apply even to the table owner

CREATE POLICY tenant_isolation ON notes
  USING (tenant_id = current_setting('app.tenant_id')::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

-- The app connects as a role WITHOUT the BYPASSRLS attribute and is not a superuser
// Per request, inside a transaction: bind the tenant, then run queries normally
async function withTenant(tenantId, fn) {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    await client.query("SELECT set_config('app.tenant_id', $1, true)", [tenantId]);   // true = local to this transaction
    const result = await fn(client);                 // every query here is filtered by RLS automatically
    await client.query("COMMIT");
    return result;
  } catch (e) { await client.query("ROLLBACK"); throw e; }
  finally { client.release(); }
}

// Tenant comes from the verified token or session, NEVER from a client-supplied header or body field
app.use((req, res, next) => { req.tenantId = req.auth.tenantId; next(); });

§4Carry the Tenant Everywhere

  • Caches: include the tenant in every key (t:{tenantId}:product:42), or tenants will read each other's cached data.
  • Queues and background jobs: put tenantId in the message and re-establish the tenant context in the worker.
  • Search indexes, files, and logs: prefix object-storage paths, filter search queries, and tag log lines by tenant (while keeping personal data out of logs).
  • Unique constraints and indexes become composite: UNIQUE (tenant_id, email), and tenant_id usually leads composite indexes.

§5Noisy Neighbors and Fairness

In shared infrastructure, one tenant's heavy export or load test can degrade everyone. Defend with per-tenant rate limits and quotas, fair job scheduling (separate queues or concurrency caps per tenant), query timeouts, and monitoring broken down by tenant so you can spot who is consuming what. Tiers (free, pro, enterprise) can map to different limits or to dedicated capacity.

§6Operations at Tenant Granularity

  • Onboarding and offboarding: provisioning a tenant and, at the end of a contract, deleting all of its data across the database, caches, files, backups, and search indexes.
  • Backup and restore: restoring one tenant after their accidental deletion is trivial in a silo and a custom project in a pool; decide in advance.
  • Migrations: a pooled schema migrates once; schema-per-tenant migrates thousands of times and must handle partial failure.
  • Compliance and residency: some customers require their data to stay in a region or be encrypted with their own keys, pushing toward silos.
Test isolation as a first-class feature Write automated tests that create two tenants, then attempt every read, update, and delete from one against the other's ids, through the API, the background workers, and the cache. Run them in CI on every change; leaks are the failures you can least afford to find in production.

§7Common Mistakes

MistakeWhat HappensFix
Relying on developers to add WHERE tenant_id to every queryOne missed filter leaks data across customersEnforce with row-level security or a mandatory data-access layer
Taking the tenant id from a request header or bodyAny user can claim to be any tenantDerive it from the verified identity
Forgetting tenant in cache keys and job payloadsCross-tenant data appears in cached pages or background workInclude the tenant in every key, message, and file path
Practice
  1. Add RLS to a pooled table in a local Postgres, connect as a non-owner role, and show that a query with no tenant filter still returns only the current tenant's rows.
  2. Write a test with two tenants that tries to read, update, and delete the other's data through every endpoint.
  3. Choose an isolation model for a product with 5,000 small customers and 10 regulated enterprise customers, and justify a hybrid approach.
Key takeaways
  • Pool, bridge, and silo models trade cost against isolation strength; hybrids are common.
  • Enforce tenant isolation in the database (row-level security) and derive the tenant from verified identity, never from client input.
  • Carry the tenant through caches, queues, files, and logs, and guard against noisy neighbors with per-tenant limits.
