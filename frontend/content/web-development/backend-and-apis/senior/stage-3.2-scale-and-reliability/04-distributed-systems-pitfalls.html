Distributed Systems Pitfalls

Clocks, partial failure, and consistency trade-offs.

§1The Network Is Not a Function Call

Distributed systems fail in ways single programs do not. The classic "fallacies of distributed computing" are assumptions that seem true and are not: the network is reliable, latency is zero, bandwidth is infinite, the network is secure, topology does not change, there is one administrator, transport cost is zero, and the network is homogeneous. Almost every outage in this area traces back to forgetting one of them.

§2Partial Failure and Ambiguity

In one process, a call either returns or throws. Across a network there is a third outcome: you do not know. You send a request and hear nothing. The server may have crashed before processing it, processed it and crashed before replying, or the reply may be delayed or lost. From the caller, all of these look identical. Consequences:

  • A timeout is not a failure; it is an unknown. The operation may still happen.
  • You cannot get "exactly once" delivery end to end. You get at-most-once (do not retry; may be lost) or at-least-once (retry; may duplicate). Practical systems pair at-least-once delivery with idempotent handlers, which achieves exactly-once effect.
  • Failure detection is only a guess: a slow node is indistinguishable from a dead one, so detectors use timeouts and can be wrong in either direction.

§3Clocks Lie

Every machine has its own clock, and they disagree (clock skew), jump when synced (NTP can step time backward), and drift. Bugs follow whenever code assumes clocks agree:

  • Do not order events across machines by timestamp. "Last write wins" by wall-clock time silently discards the newer write when its server's clock runs slow.
  • Measure durations with a monotonic clock (performance.now(), process.hrtime), never by subtracting two wall-clock times.
  • Use logical ordering where order matters: version numbers, sequence numbers, or vector/Lamport clocks, or let a single database assign order.
  • Treat leases and token expiry carefully. A process that believes it holds a lease may have paused (garbage collection, VM migration) past its expiry.

§4Consistency Trade-offs

When data is replicated and the network can partition, you must choose between consistency (every read sees the latest write) and availability (every request gets a response). This is the CAP theorem: during a partition, you cannot have both. Even without a partition there is a latency-versus-consistency trade-off (PACELC). In practice this is a spectrum, and different data in the same product deserves different choices:

ModelGuaranteeTypical use
Strong / linearizableReads always see the latest committed writeAccount balances, inventory reservations, unique usernames
Read-your-writes / sessionYou see your own changesUser profile edits
EventualReplicas converge given timeLike counts, feeds, caches, search indexes

§5Split Brain and Fencing

If a cluster loses contact between two halves, both may believe they are the leader and both accept writes: split brain, which corrupts data. Safe leader election uses a majority quorum (a minority side cannot make progress) via consensus systems such as etcd, ZooKeeper, or Raft-based stores, and uses fencing tokens so that a delayed old leader is rejected.

// A lock service hands out a monotonically increasing token with every grant.
// The storage layer rejects any write carrying a token older than one it has already seen.

lease = lockService.acquire("report-job")      // -> { token: 34 }
// ...process pauses for 30 s (GC, VM freeze); the lease expires; another node gets token 35...
storage.write(data, { fencingToken: lease.token })
// storage has seen 35, so token 34 is rejected: the zombie cannot corrupt state

§6Practical Defenses

  • Make operations idempotent and carry request ids end to end.
  • Prefer asynchronous, durable messaging over long chains of synchronous calls.
  • Avoid distributed transactions; use sagas with compensation, or keep related data in one database.
  • Let one component own each fact (a single writer per piece of data) and replicate it for reads.
  • Use proven coordination tools (a database, etcd, a managed lock service) rather than writing your own consensus.
The three questions For any cross-service operation, ask: (1) what happens if the request is lost, (2) what happens if it succeeds but the reply is lost, and (3) what happens if it is delivered twice? A design that has an answer to all three is most of the way to correct.

§7Common Mistakes

MistakeWhat HappensFix
Ordering events across servers by wall-clock timestampsNewer data is overwritten by older data with a faster clockUse version numbers, sequences, or a single ordering authority
Treating a timeout as a definite failureOperations execute anyway; retries duplicate themMake operations idempotent and check state before assuming
Writing your own leader election or locking from scratchSubtle split-brain and lease bugsUse a consensus-backed service and fencing tokens
Practice
  1. For "transfer money between accounts in two services", walk through the three questions above and design idempotency and compensation to answer each.
  2. Show how last-write-wins by timestamp can lose an update when one server's clock is five seconds behind, using a small simulation.
  3. Classify five pieces of data in a product (such as inventory, likes, profile, balance, search index) by the consistency each really needs.
Key takeaways
  • Across a network, a timeout means unknown, so design for retries, duplicates, and loss with idempotent operations.
  • Never trust clocks for ordering across machines; use monotonic clocks for durations and logical versions for order.
  • Choose consistency per piece of data, use consensus systems and fencing for leadership, and avoid inventing your own.
