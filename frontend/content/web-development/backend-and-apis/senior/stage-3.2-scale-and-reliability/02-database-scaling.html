Database Scaling

Replication, partitioning, and sharding.

§1Climb the Ladder in Order

The database is usually the first component that cannot just be cloned. Each step up in complexity solves a real problem and creates new ones, so work through them in order and stop as soon as the problem is solved:

  1. Fix the queries. Indexes, query plans, N+1 removal. This alone often buys 10x to 100x.
  2. Pool connections (PgBouncer or your driver's pool) so many app instances do not exhaust the server.
  3. Cache the hot, repeatable reads.
  4. Scale up the machine: more CPU, RAM, and faster disks. Cheap in engineering time and reaches surprisingly far.
  5. Add read replicas to spread read traffic.
  6. Partition large tables within one database.
  7. Shard across databases as a last resort, when writes or data volume exceed a single primary.

§2Read Replicas and Replication Lag

A read replica is a copy that continuously receives changes from the primary. Send writes to the primary and spread reads across replicas. It scales read-heavy workloads and adds a failover candidate. The catch is replication lag: replicas are slightly behind, from milliseconds to much longer under load, so a read right after a write may not see it.

// Route by intent: writes and read-your-own-writes go to the primary
async function query(sql, params, { consistent = false } = {}) {
  const target = consistent ? primary : pickReplica();
  return target.query(sql, params);
}

// After a user changes something, read from the primary for a short window
app.patch("/profile", async (req, res) => {
  await primary.query("UPDATE users SET bio = $1 WHERE id = $2", [req.body.bio, req.user.id]);
  res.cookie("read_primary_until", Date.now() + 5000, { httpOnly: true });   // "read-your-writes" window
  res.sendStatus(204);
});
// Reports, search, feeds, and anything tolerant of a few seconds of staleness use replicas.
// Monitor replica lag and fall back to the primary (or stop serving) when it exceeds a threshold.

§3Partitioning

Partitioning splits one huge logical table into smaller physical pieces inside the same database, usually by time or a key. Queries that filter on the partition key touch only the relevant pieces (partition pruning), and dropping an old partition is instant compared with deleting millions of rows.

CREATE TABLE events (
  id          BIGINT GENERATED ALWAYS AS IDENTITY,
  tenant_id   BIGINT NOT NULL,
  occurred_at TIMESTAMPTZ NOT NULL,
  payload     JSONB,
  PRIMARY KEY (id, occurred_at)                      -- the partition key must be part of the primary key
) PARTITION BY RANGE (occurred_at);

CREATE TABLE events_2026_01 PARTITION OF events FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE events_2026_02 PARTITION OF events FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
-- Retention: DROP TABLE events_2025_01;  (instant, no vacuum pressure)

§4Sharding

Sharding spreads data across multiple independent databases, each holding a subset, so writes and storage scale beyond one machine. It is powerful and expensive, and it changes how your whole application works:

  • The shard key decides everything. Choose a key (tenant id, user id) that spreads load evenly and keeps most queries within one shard. A bad key creates "hot" shards.
  • Cross-shard operations get hard. Joins, global unique constraints, and multi-shard transactions are costly or impossible; aggregate queries must fan out and merge.
  • Resharding is painful. Moving data when you add shards needs careful tooling (consistent hashing and many small logical shards help).
  • Alternatives first: managed distributed SQL (such as CockroachDB, Spanner, Citus, Vitess) can shard for you; use them if you have real scale needs.

§5Separating Reads From Writes

When read and write needs diverge sharply (a normalized write model, a denormalized read model for dashboards or search), you can maintain separate read models fed by events or change-data-capture. This is CQRS (command query responsibility segregation) in practical form. It trades simplicity and immediate consistency for speed and independent scaling.

Most systems never need to shard A well-indexed single PostgreSQL primary on modern hardware serves very large workloads. Teams that shard early pay a permanent complexity tax for scale they may never reach. Measure, climb the ladder one rung at a time, and shard only when a single primary's write throughput or storage is genuinely exhausted.

§6Common Mistakes

MistakeWhat HappensFix
Sending read-after-write queries to a lagging replicaUsers do not see their own changes and report "lost data"Read from the primary after writes, and monitor replica lag
Sharding before exhausting simpler optionsHuge complexity for a problem an index or bigger box would solveClimb the ladder: queries, pooling, cache, scale up, replicas, partition, then shard
Choosing a shard key with skew (such as country or creation date)One shard takes most of the loadPick a high-cardinality, evenly distributed key aligned with query patterns
Practice
  1. Set up a Postgres primary and a streaming replica (Docker Compose is fine). Write to the primary and measure how quickly the replica reflects the change.
  2. Partition an events table by month, run a query with and without the partition key in the filter, and compare the plans.
  3. For a multi-tenant SaaS, propose a shard key and list three queries that become hard under that choice.
Key takeaways
  • Scale the database in order: queries, pooling, caching, bigger hardware, replicas, partitioning, and only then sharding.
  • Read replicas scale reads but introduce replication lag, so handle read-your-writes explicitly.
  • Sharding requires a good shard key and makes cross-shard queries and resharding difficult; use it last, or use a distributed database.
