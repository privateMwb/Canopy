Horizontal Scaling & Load Balancing

Stateless services, and where state hides.

§1Scaling Up vs Scaling Out

When one server runs out of capacity you have two options. Vertical scaling (scaling up) means a bigger machine: simple, no code changes, but with a ceiling, rising cost per unit of capacity, and a single point of failure. Horizontal scaling (scaling out) means more machines behind a load balancer: it has no hard ceiling and improves availability, but it works only if any instance can serve any request.

That requirement has a name: stateless services. If instance A holds something that instance B needs, the next request that lands on B breaks. Horizontal scaling is mostly the work of finding and removing hidden state.

§2Where State Hides

Hidden stateWhat goes wrong when you add instancesWhere it should live
In-memory sessionsUser is logged out when the next request hits a different instanceShared store (Redis, database) or a signed token
In-process cacheEach instance caches separately; invalidation reaches only oneShared cache such as Redis, or accept per-instance TTL staleness
Files on local diskUpload lands on A, download is requested from BObject storage (S3-compatible)
In-process rate-limit countersEffective limit is multiplied by the number of instancesShared counters in Redis
WebSocket connectionsMessages published on one instance miss users on anotherPub/sub backplane between instances
Scheduled jobs (setInterval, cron)Every instance runs the job, so emails go out N timesA single scheduler, or a distributed lock / leader election

§3What a Load Balancer Does

  • Distributes requests across healthy instances and removes unhealthy ones, using the readiness checks from stage 2.4.
  • Terminates TLS and can add routing, compression, and timeouts.
  • Enables rolling deploys by draining an instance (finishing in-flight requests) before replacing it.
AlgorithmBehaviorBest when
Round robinTake turnsRequests are similar in cost
Least connections / least loadPick the instance with the fewest active requestsRequest cost varies widely, or connections are long-lived
Consistent hashingSame key (user, tenant) goes to the same instance, and only a few keys move when instances changePer-instance caches or locality matter
WeightedSend more to bigger instancesMixed instance sizes, or gradual canary traffic

Layer 4 balancers route raw TCP connections quickly and with little inspection; layer 7 balancers understand HTTP and can route by path, header, or cookie, at the cost of more processing. Most web APIs use layer 7.

# nginx: a layer-7 load balancer with passive failure detection
upstream api {
    least_conn;
    server 10.0.1.11:3000 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:3000 max_fails=3 fail_timeout=10s;
    server 10.0.1.13:3000 max_fails=3 fail_timeout=10s;
    keepalive 64;                                    # reuse upstream connections
}

server {
    listen 443 ssl;
    location / {
        proxy_pass http://api;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header X-Request-Id $request_id;
        proxy_next_upstream error timeout http_502 http_503;   # retry idempotent failures elsewhere
        proxy_read_timeout 30s;
    }
}

§4Sticky Sessions: A Crutch

A balancer can pin each client to one instance (via a cookie or hash). That papers over in-memory state, but it unbalances load, loses the session when that instance dies, and complicates deploys. Treat stickiness as a temporary workaround while you externalize state, with the exception of protocols such as WebSockets where a connection naturally stays on one instance.

§5Autoscaling

Autoscalers add and remove instances based on a signal: CPU utilization, requests per instance, queue depth, or latency. Good practice: scale on a signal that reflects real saturation (queue depth for workers; concurrency or latency for APIs), set sensible minimums for availability, allow warm-up time before sending traffic, and remember that the database usually does not scale out as easily, so 50 new instances can overwhelm it with connections (see the next lesson).

Statelessness is a property you test Do not assume it. Run two or three instances locally behind a balancer, click through the app, kill instances at random, and see what breaks. The bugs this finds (a missing session, a vanished upload, a double-run cron) are exactly the ones that appear on the day you scale.

§6Common Mistakes

MistakeWhat HappensFix
Keeping sessions or uploads on the instanceUsers get logged out or lose files when balanced to another instanceExternalize to Redis, the database, or object storage
Running scheduled jobs on every instanceDuplicate emails and double processingUse one scheduler or a distributed lock with a lease
Scaling the app tier without watching the databaseMore instances exhaust database connections and make things worsePool connections, limit per-instance pools, and scale the data tier deliberately
Practice
  1. Run three copies of your API behind nginx or Caddy and find every feature that breaks. Fix each by moving state out of the process.
  2. Create a cron-like job with setInterval, run two instances, observe the duplicate, then protect it with a Redis or Postgres advisory lock.
  3. Pick an autoscaling signal for (a) a queue worker and (b) a public API, and justify each choice.
Key takeaways
  • Horizontal scaling requires stateless instances; find and externalize hidden state such as sessions, files, caches, and jobs.
  • Load balancers distribute traffic, remove unhealthy instances, and enable draining and rolling deploys; choose the algorithm to fit your workload.
  • Scaling the app tier shifts the bottleneck, often to the database, so plan connection limits and the data tier too.
