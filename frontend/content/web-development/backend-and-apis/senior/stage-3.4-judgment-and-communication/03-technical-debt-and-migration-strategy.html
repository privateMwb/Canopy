Technical Debt & Migration Strategy

Paying down risk deliberately.

§1Debt Is a Loan, Not a Sin

Technical debt is the future cost you accept by choosing a quicker or simpler solution now. Like financial debt, it can be a smart tool: shipping a prototype fast to learn something is often right. What matters is whether the debt was taken deliberately, whether it is tracked, and whether the interest (the ongoing slowdown it causes) is being paid or growing.

§2Make Debt Visible and Prioritize It

"The code is messy" is not a compelling case to a product manager. Describe debt in terms of its cost and risk: how it slows delivery, causes incidents, blocks a strategic goal, or creates security exposure.

  • Keep a debt register with a short description, the pain it causes, a rough cost to fix, and who is affected.
  • Prioritize by interest, not ugliness. Debt in code that changes weekly and causes incidents costs far more than a hideous module nobody has touched in three years. Leave stable ugly code alone.
  • Evidence beats opinion: use incident history, change-failure rates, how long features in that area take, and survey data on where engineers lose time.
  • Tie it to goals. "This blocks the multi-region launch" or "this accounts for 40% of our incidents" earns time; "this offends me" does not.

§3Paying It Down Deliberately

  • Boy-scout rule: leave code a little better than you found it, in small increments attached to feature work.
  • Reserve capacity: for example 15 to 20 percent of each cycle for maintenance and improvement, so debt work does not depend on winning a debate every sprint.
  • Make refactoring safe first: add characterization tests that pin current behavior before changing it. Changing untested code is how debt payments cause outages.
  • Prefer small, continuous steps over the rewrite. Total rewrites usually take longer than expected, freeze feature work, and reintroduce old bugs the old code had already fixed.

§4Migration Strategy: Changing the Engine While Flying

Large changes (a new database, a new framework, splitting a service) fail when treated as a big bang. The reliable pattern is incremental migration: keep the system working at every step, move traffic gradually, and make each step reversible. The strangler fig pattern wraps the old system with a routing layer and replaces pieces one at a time until the old one withers away.

# A migration plan skeleton
1. Goal & success criteria   What does "done" mean? What problem does this fix? Metrics to prove it.
2. Inventory                 What exists? Consumers, data volumes, hidden dependencies, owners.
3. Seam & routing            Introduce a facade/proxy so traffic can be steered per tenant / endpoint / percentage.
4. Build new path            Behind the seam, with feature flags; no user impact yet.
5. Shadow / dual-run         Send copies of real traffic to the new path; compare results; fix differences.
6. Migrate data              Backfill; dual-write; verify with checksums and row counts; reconcile continuously.
7. Shift traffic gradually   Internal -> 1% -> 10% -> 50% -> 100%, with automatic rollback on SLO regressions.
8. Hold, then decommission   Keep the old path (read-only) for a safety period; then delete it AND its infrastructure.
9. Communicate               Dated milestones, owners, and customer-facing notices throughout.
  • Define the rollback for every step before taking it, and rehearse it.
  • Verify with data, not hope: comparison jobs, shadow traffic diffs, and reconciliation reports tell you whether the new system is equivalent.
  • Beware the long tail. The last 10 percent (odd consumers, edge cases, forgotten cron jobs) takes disproportionate time, and migrations that stall at 90 percent leave you running both systems, the worst outcome. Plan, staff, and set a date for decommissioning.
  • Do not mix goals. Changing the platform and redesigning the behavior in one move makes failures impossible to attribute. Migrate behavior-for-behavior first, then improve.
Finish what you start A migration is not complete until the old system is gone and its costs stop. Half-finished migrations create the most expensive kind of debt: two systems to maintain, two sets of knowledge, and confusion about which is the source of truth. Make decommissioning an explicit, scheduled deliverable.

Practice
  1. Write a debt register for a system you know with five items, each with the pain it causes, a cost estimate, and a priority argument aimed at a product manager.
  2. Draft a migration plan, using the skeleton above, for moving one service's data from a single database into its own database. Include rollback for each step.
  3. Choose a module you want to refactor and write down which characterization tests you would add first.
Key takeaways
  • Technical debt is a tradeoff; make it visible, describe it as cost and risk, and prioritize by interest paid.
  • Pay it down continuously with reserved capacity and safe, test-backed refactoring rather than big rewrites.
  • Migrate incrementally with a seam, shadow traffic, verification, gradual cutover, rollback, and a firm decommissioning date.
