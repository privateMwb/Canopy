GraphQL Fundamentals

Schemas, resolvers, and when GraphQL fits.

§1Ask for Exactly What You Need

With REST, the server decides each endpoint's shape. A mobile screen that needs a note's title and its author's name may need two calls, or one call that returns far more data than it uses (under-fetching and over-fetching). GraphQL flips control: the server publishes a typed schema, and the client sends a query naming exactly the fields it wants, usually through a single endpoint (POST /graphql).

# The schema (SDL): the contract
type User {
  id: ID!
  name: String!
  notes: [Note!]!
}

type Note {
  id: ID!
  title: String!
  body: String
  author: User!
}

type Query {
  note(id: ID!): Note
  notes(limit: Int = 20): [Note!]!
}

type Mutation {
  createNote(title: String!, body: String): Note!
}
# A query: ask for exactly these fields, nested, in one round trip
query {
  note(id: "7") {
    title
    author { name }
  }
}

# Response mirrors the shape of the query
# { "data": { "note": { "title": "SQL basics", "author": { "name": "Ada" } } } }

The ! means non-null. Queries read data and mutations change it; both are validated against the schema before any code runs, so malformed or unknown fields are rejected automatically.

§2Resolvers: Where the Data Comes From

Each field in the schema is backed by a resolver, a function that produces its value. The engine walks the query and calls the resolvers it needs.

import { createSchema, createYoga } from "graphql-yoga";

const schema = createSchema({
  typeDefs,                                          // the SDL above
  resolvers: {
    Query: {
      note: (_, { id }, ctx) => ctx.db.notes.findById(id),
      notes: (_, { limit }, ctx) => ctx.db.notes.list(limit),
    },
    Note: {
      author: (note, _, ctx) => ctx.loaders.userById.load(note.userId),   // batched, see below
    },
    Mutation: {
      createNote: (_, args, ctx) => ctx.db.notes.create({ ...args, userId: ctx.user.id }),
    },
  },
});

§3The N+1 Problem Returns

Ask for 50 notes with their authors and the author resolver runs 50 times. If each does a query, that is 51 queries. The standard fix is DataLoader, which collects all the ids requested during one tick and loads them in a single batched query.

import DataLoader from "dataloader";

// Created per request (so caches do not leak between users)
const userById = new DataLoader(async ids => {
  const { rows } = await pool.query("SELECT * FROM users WHERE id = ANY($1)", [ids]);
  const byId = new Map(rows.map(u => [String(u.id), u]));
  return ids.map(id => byId.get(String(id)));        // results MUST match the order of ids
});

§4Trade-Offs to Weigh

StrengthCost
Clients fetch exactly what they need, in one requestHTTP caching is harder: everything is a POST to one URL
Strongly typed schema, introspection, great toolingQueries can be arbitrarily deep and expensive; you need depth and cost limits
Evolves without versions by adding fields and deprecating old onesAuthorization must be enforced per field and per resolver, not just per route
Excellent for varied clients (web, mobile, partners)More moving parts than a simple CRUD API; file uploads and errors need extra conventions
GraphQL always returns 200 Errors usually arrive in an errors array alongside partial data with HTTP status 200. Monitoring that only watches status codes will miss failures; track GraphQL errors explicitly.

§5Common Mistakes

MistakeWhat HappensFix
Writing resolvers that query per itemN+1 queries and slow responsesUse DataLoader (per request) or join in the parent resolver
Exposing an unbounded, deeply nestable schemaA single query can take down the databaseLimit depth, cost, and page sizes; consider persisted queries
Checking auth only at the top-level queryNested fields leak data the caller should not seeEnforce authorization in the resolvers (or a shared layer) that fetch each type
Practice
  1. Define a schema for users and notes, then run a query against a GraphQL server and compare the request count with a REST equivalent.
  2. Create an N+1 on purpose with a naive author resolver, count queries in the log, then fix it with DataLoader.
  3. Write down two situations where you would choose GraphQL and two where plain REST is the better fit.
Key takeaways
  • GraphQL exposes a typed schema; clients send queries naming exactly the fields they need.
  • Resolvers back each field, and DataLoader batching prevents N+1 query explosions.
  • Flexibility costs you simple caching and requires query limits and per-field authorization.
