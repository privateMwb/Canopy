gRPC & Internal APIs

Contracts between services.

§1A Different Contract for Service-to-Service Calls

Public APIs favor human-readable JSON over HTTP because strangers need to understand them. Inside your own system, between services you control, you can trade some readability for speed, strictness, and generated code. gRPC is a widely used framework for that: you define services and messages in a .proto file using Protocol Buffers, and tooling generates typed clients and servers in many languages.

// notes.proto
syntax = "proto3";
package notes.v1;

service NoteService {
  rpc GetNote (GetNoteRequest) returns (Note);                      // unary
  rpc ListNotes (ListNotesRequest) returns (stream Note);           // server streaming
}

message GetNoteRequest { int64 id = 1; }
message ListNotesRequest { int64 user_id = 1; int32 limit = 2; }

message Note {
  int64  id      = 1;
  string title   = 2;
  string body    = 3;
  int64  user_id = 4;
}

Those numbers are field tags, and they are the wire identity of each field. Messages are encoded into a compact binary format that is smaller and faster to parse than JSON, and the generated code removes whole classes of mistakes (a misspelled field is a compile error, not a runtime surprise).

§2What gRPC Provides

  • HTTP/2 transport: multiplexed requests over one connection, with header compression.
  • Four call types: unary (one request, one response), server streaming, client streaming, and bidirectional streaming.
  • Deadlines and cancellation built in: callers state how long they will wait, and the deadline propagates through chains of services.
  • Standard status codes (such as NOT_FOUND, UNAVAILABLE, DEADLINE_EXCEEDED) with interceptors for auth, logging, and retries.
import grpc from "@grpc/grpc-js";
import * as loader from "@grpc/proto-loader";

const def = loader.loadSync("notes.proto", { keepCase: true });
const { notes } = grpc.loadPackageDefinition(def);

const client = new notes.v1.NoteService("notes.internal:50051", grpc.credentials.createInsecure()); // use TLS in production

client.GetNote({ id: 7 }, { deadline: Date.now() + 500 }, (err, note) => {   // 500 ms budget
  if (err) return console.error(err.code, err.details);
  console.log(note.title);
});

§3Evolving Protobuf Schemas Safely

  • Never change or reuse a field number. Old and new binaries would disagree about what the bytes mean.
  • Adding fields is safe; old readers ignore tags they do not know.
  • When removing a field, mark its number and name reserved so no one reuses it later.

§4REST or gRPC?

REST/JSONgRPC
ReadabilityHuman-readable; easy to debug with curlBinary; needs tooling such as grpcurl
Browser supportNativeNeeds gRPC-Web or a gateway
PerformanceGoodSmaller payloads and streaming; usually faster
ContractOptional (OpenAPI)Mandatory, generated, strongly typed
Best fitPublic and partner APIsInternal service-to-service calls and streaming
Choose by audience A common pattern is gRPC between internal services and a REST or GraphQL layer facing outside clients. Adopting gRPC for a two-service system with a few endpoints is often needless complexity; the benefits grow with the number of services and languages.

§5Common Mistakes

MistakeWhat HappensFix
Renumbering or reusing protobuf field numbersData is silently misread by older clientsTreat numbers as permanent; use reserved for removed fields
Calling services with no deadlineOne slow dependency stalls every callerSet a deadline on every call and propagate it downstream
Exposing gRPC directly to browsers or third partiesPoor tooling and compatibility for external developersPut a REST/GraphQL gateway in front for external consumers
Practice
  1. Write a .proto with one unary and one server-streaming method, then implement a server and call it from a client.
  2. Add a new field to a message and verify an older client still works. Then mark a removed field as reserved.
  3. Give the client a 100 ms deadline against a handler that sleeps 1 second, and read the resulting error code.
Key takeaways
  • gRPC defines services in .proto files and generates typed, efficient clients and servers over HTTP/2.
  • Field numbers are permanent identities; add fields freely but never reuse or renumber them.
  • Use gRPC for internal service calls, keep REST or GraphQL for public ones, and always set deadlines.
