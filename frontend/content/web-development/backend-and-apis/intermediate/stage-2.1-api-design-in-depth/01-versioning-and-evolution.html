Versioning & Evolution

Changing an API without breaking clients.

§1Your API Is a Promise to Strangers

Once someone else's code calls your API, you no longer control when they update. A mobile app released last year may still be in use, and a partner's integration may not change for a decade. Evolving an API means changing it without breaking those callers, and the best versioning strategy is the one you rarely need to use.

§2Breaking vs Non-Breaking Changes

Usually safe (additive)Breaking
Adding a new endpointRemoving or renaming an endpoint, field, or enum value
Adding an optional request fieldMaking an optional field required
Adding a response fieldChanging a field's type or meaning (price from dollars to cents)
Adding a new optional query parameterTightening validation so previously valid input is rejected
Adding a new error code for a new situationChanging status codes, error shapes, or default sort order

Even "safe" changes break fragile clients that, for example, crash on unknown fields. Document the expectation that clients must follow the tolerant reader principle: ignore what you do not understand. Never reuse an old field name with a new meaning, because that is the most dangerous change of all.

§3Versioning Strategies

StrategyExampleNotes
URL path/v1/notes, /v2/notesMost visible and easy to route and test; the most common choice
HeaderAccept: application/vnd.example.v2+jsonCleaner URLs, but harder to try in a browser and to cache correctly
Date-basedApi-Version: 2026-01-15Accounts pin a version; used by Stripe-style APIs for many small, frequent changes
Query parameter/notes?version=2Simple, but easy to omit by accident

Whichever you choose, version the whole contract rarely and deliberately. A new major version means maintaining two behaviors, two sets of docs, and two sets of tests until the old one is gone.

// Routing two versions side by side, sharing what hasn't changed
const v1 = express.Router();
const v2 = express.Router();

v1.get("/notes/:id", async (req, res) => res.json(toV1(await getNote(req.params.id))));
v2.get("/notes/:id", async (req, res) => res.json(toV2(await getNote(req.params.id))));

app.use("/v1", v1);
app.use("/v2", v2);

// Keep one internal model; each version is a thin translation layer ("serializer")
const toV1 = n => ({ id: n.id, title: n.title, price: n.priceCents / 100 });
const toV2 = n => ({ id: n.id, title: n.title, price: { amount: n.priceCents, currency: "USD" } });

§4Deprecating Gracefully

  • Announce early with a changelog, email to registered developers, and a migration guide.
  • Signal in the response using the Deprecation header (RFC 9745) and a Sunset header (RFC 8594) giving the retirement date, plus a Link to the replacement.
  • Measure usage per version and per client, so you know who is still on the old one and can contact them.
  • Turn it off in stages: warn, throttle, brown-out for short periods, then remove.
HTTP/1.1 200 OK
Deprecation: @1767225600
Sunset: Thu, 01 Jul 2027 00:00:00 GMT
Link: <https://api.example.com/docs/migrate-to-v2>; rel="deprecation"
The best version strategy is additive change Design so that growth happens by adding optional fields and endpoints. Teams that do this well may run a single major version for years. Reserve a new version for changes that truly cannot be made compatibly.

§5Common Mistakes

MistakeWhat HappensFix
Changing a field's meaning but keeping its nameClients silently compute wrong resultsAdd a new field and deprecate the old one
Shipping v2 with no plan to retire v1You maintain both foreverSet and publish a sunset date, and track usage per version
Removing a field without checking who uses itProduction clients crash with no warningLog field and endpoint usage, and warn before removing
Practice
  1. Classify each change as breaking or non-breaking: renaming userName to username; adding avatarUrl to a response; making phone required; adding a new enum value archived to status.
  2. Implement the v1/v2 routers above for a resource that changes shape, using a shared internal model.
  3. Add Deprecation and Sunset headers to a v1 route and write the migration note a client would see.
Key takeaways
  • Prefer additive, backward-compatible change; most evolution should not need a new version.
  • Never change the meaning or type of an existing field; clients should ignore unknown fields.
  • When you must break, version deliberately, signal deprecation in headers and docs, and measure usage before retiring.
