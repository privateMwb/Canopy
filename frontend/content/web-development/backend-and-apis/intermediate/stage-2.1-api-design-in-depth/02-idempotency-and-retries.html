Idempotency & Retries

Making unsafe operations safe to retry.

§1Networks Fail in the Middle

A client sends POST /payments and the connection drops. Did the server process it? The client cannot know. If it retries, it may charge the customer twice; if it does not, the payment may never happen. Because timeouts, dropped connections, and crashed servers are normal, clients will retry, so your API must make retries safe.

An operation is idempotent if performing it multiple times has the same effect as once. GET, PUT, and DELETE are idempotent by definition (setting the same value twice, or deleting something already gone). POST is not: each call creates something new. The fix is to let clients make a POST idempotent by attaching a unique key.

§2Idempotency Keys

The client generates a unique value (such as a UUID) per logical operation and sends it as a header. The server records the key with the result of the first execution. A retry carrying the same key gets the stored response back instead of running the operation again.

POST /payments HTTP/1.1
Idempotency-Key: 8f14e45f-ceea-467a-9f3c-5b2d1e0a7c11
Content-Type: application/json

{"amount": 5000, "currency": "usd", "customer": "cus_123"}
-- Persist keys with a uniqueness guarantee
CREATE TABLE idempotency_keys (
  key           TEXT NOT NULL,
  user_id       INTEGER NOT NULL,
  request_hash  TEXT NOT NULL,         -- detect the same key reused with a different body
  status        TEXT NOT NULL,         -- 'in_progress' | 'completed'
  response_code INTEGER,
  response_body JSONB,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, key)
);
async function idempotent(req, res, next) {
  const key = req.get("Idempotency-Key");
  if (!key) return next();                           // or require it for payment-like endpoints
  const hash = sha256(JSON.stringify(req.body));

  // Atomically claim the key; only one concurrent request can insert it
  const claim = await pool.query(
    `INSERT INTO idempotency_keys (key, user_id, request_hash, status)
     VALUES ($1, $2, $3, 'in_progress') ON CONFLICT DO NOTHING RETURNING key`,
    [key, req.user.id, hash]);

  if (claim.rowCount === 0) {                        // seen before
    const { rows: [saved] } = await pool.query(
      "SELECT * FROM idempotency_keys WHERE user_id = $1 AND key = $2", [req.user.id, key]);
    if (saved.request_hash !== hash) return res.status(422).json({ error: "Key reused with different request" });
    if (saved.status === "in_progress") return res.status(409).json({ error: "Request in progress" });
    return res.status(saved.response_code).json(saved.response_body);   // replay the stored result
  }
  // ...run the handler, then UPDATE the row to 'completed' with the response
  next();
}
  • The atomic insert (unique key) is what handles two simultaneous retries; checking first and inserting second would race.
  • Store the request hash so a key accidentally reused for a different request is rejected.
  • Expire keys after a window such as 24 hours to bound storage.
  • For side effects outside your database (charging a card), pass the key through to that provider as well.

§3Retrying Well on the Client

Idempotency makes retrying safe; backoff makes it polite. Retrying instantly in a tight loop turns a brief outage into a self-inflicted attack on a recovering server. Wait longer after each failure and add randomness (jitter) so thousands of clients do not all retry on the same beat.

async function withRetry(fn, { retries = 5, base = 200, cap = 10_000 } = {}) {
  for (let attempt = 0; ; attempt++) {
    try { return await fn(); }
    catch (err) {
      const retryable = err.status === 429 || err.status >= 500 || err.code === "ECONNRESET";
      if (!retryable || attempt >= retries) throw err;
      const delay = Math.random() * Math.min(cap, base * 2 ** attempt);   // "full jitter"
      await new Promise(r => setTimeout(r, delay));
    }
  }
}

Retry only transient failures (network errors, 429, 502/503/504) and honor a Retry-After header when present. Never retry 4xx errors like 400 or 404; the same request will fail the same way.

Idempotent does not mean identical response The first call might return 201 and a replay might return 200 with the same body. What must be identical is the effect: one payment, one email, one order.

§4Common Mistakes

MistakeWhat HappensFix
Retrying non-idempotent POSTs without a keyDuplicate charges, orders, or emailsRequire Idempotency-Key on creation endpoints that cost money
Retrying immediately in a loopOverloads a recovering server and prolongs the outageExponential backoff with jitter, and a retry cap
Check-then-insert for keysTwo concurrent retries both pass the check and both executeUse an atomic insert with a unique constraint
Practice
  1. Add idempotency-key handling to a POST /orders endpoint, then send the same request ten times in parallel and verify only one order exists.
  2. Reuse a key with a different body and confirm the API refuses it.
  3. Make the retry helper honor Retry-After and test it against an endpoint that returns 429 twice, then 200.
Key takeaways
  • Clients retry, so unsafe operations need idempotency keys backed by an atomic uniqueness check.
  • Store the result of the first execution and replay it for duplicates; reject key reuse with a different body.
  • Retry only transient failures, with exponential backoff, jitter, and a limit.
