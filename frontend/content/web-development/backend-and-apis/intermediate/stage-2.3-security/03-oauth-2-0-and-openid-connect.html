OAuth 2.0 & OpenID Connect

Delegated login and tokens done right.

§1Delegated Login Without Sharing Passwords

"Sign in with Google" and "Allow this app to read your calendar" are both OAuth 2.0. OAuth is an authorization framework: it lets a user grant an application limited access to their account at another service without handing over their password. OpenID Connect (OIDC) is a thin identity layer on top of OAuth that adds authentication: a standard way to learn who the user is.

§2The Players

RoleExample
Resource ownerThe user
ClientYour application

§3Authorization Code Flow with PKCE

This is the recommended flow for web apps, mobile apps, and single-page apps. Its key idea: the browser only ever carries a short-lived code, and your backend exchanges it for tokens over a direct, secure channel.

1. Your app generates a random `state` and a PKCE `code_verifier`; sends only its hash (`code_challenge`).
2. Redirect the user to the provider:
   https://accounts.example.com/authorize?response_type=code&client_id=APP_ID
     &redirect_uri=https://app.example.com/callback&scope=openid%20email%20profile
     &state=abc123&code_challenge=HASH&code_challenge_method=S256
3. The user logs in and consents at the provider (not on your site).
4. Provider redirects back:  https://app.example.com/callback?code=XYZ&state=abc123
5. Your server checks `state` matches, then POSTs to the token endpoint:
   code=XYZ + code_verifier (+ client_secret for confidential clients)
6. Provider returns:  access_token, id_token (OIDC), and maybe refresh_token.
  • state is a random value that you verify on return, which defeats CSRF against your callback.
  • PKCE (Proof Key for Code Exchange) binds the code to the client that started the flow, so a stolen code is useless. It is now recommended for all clients, not just public ones.
  • Exact redirect URI matching stops attackers redirecting the code to their own site.
  • Avoid the old implicit flow (tokens in the URL) and the password grant; current best practice has deprecated both.

§4The Tokens

TokenPurposeWho reads it
Access tokenProves permission to call an API, limited by scopes (calendar.readonly)The resource server
ID token (OIDC)A signed JWT stating who the user is (sub, email, iss, aud, exp)Your app, to log the user in
Refresh tokenGets new access tokens without re-prompting the userOnly the authorization server; store securely

When you receive an ID token you must validate it: the signature (against the provider's published keys), that iss is the expected issuer, that aud is your client id, that it has not expired, and that the nonce matches if you sent one. Use a maintained library rather than writing this yourself.

import * as client from "openid-client";

const config = await client.discovery(new URL("https://accounts.example.com"), CLIENT_ID, CLIENT_SECRET);

// Start login: the library generates state, nonce, and PKCE parameters for you
const codeVerifier = client.randomPKCECodeVerifier();
const authUrl = client.buildAuthorizationUrl(config, {
  redirect_uri: REDIRECT_URI, scope: "openid email profile",
  code_challenge: await client.calculatePKCECodeChallenge(codeVerifier), code_challenge_method: "S256",
  state: client.randomState(),
});
// ...store state + verifier in the user's session, redirect to authUrl...
// In the callback: client.authorizationCodeGrant(config, currentUrl, { pkceCodeVerifier, expectedState })
// then create or look up your OWN user keyed by (issuer, sub), and start your own session

§5Machine-to-Machine

When no user is involved (a backend job calling another service), use the client credentials grant: the service authenticates with its own id and secret and receives a short-lived access token for specific scopes.

OAuth is not authentication by itself An access token says "this bearer may do X", not "this user is Ada." For login, use OIDC and the validated ID token. Key your users on the stable (issuer, sub) pair, not on email, which can change or be reassigned.

§6Common Mistakes

MistakeWhat HappensFix
Using the implicit flow or skipping PKCETokens or codes can be intercepted and replayedUse authorization code with PKCE
Not verifying state, aud, or issLogin CSRF and token-substitution attacksUse a certified library and validate every claim
Matching users by email aloneAccount takeover when emails are reused or unverifiedLink accounts on (iss, sub) and require verified email for linking
Practice
  1. Add "Sign in with Google" or GitHub to a small app using a standard library, and log the claims you receive in the ID token.
  2. Remove the state check in a throwaway copy and write down how an attacker could exploit it.
  3. Draw the sequence diagram for authorization code with PKCE and label what the browser sees versus what only your server sees.
Key takeaways
  • OAuth 2.0 delegates access; OpenID Connect adds a validated ID token to establish who the user is.
  • Use the authorization code flow with PKCE, a verified state, and exact redirect URIs.
  • Rely on maintained libraries, validate tokens fully, and key users on issuer plus subject.
