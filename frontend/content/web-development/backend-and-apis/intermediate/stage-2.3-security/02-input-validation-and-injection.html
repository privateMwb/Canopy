Input Validation & Injection

SQL injection, command injection, and safe handling.

§1Injection Is Data Becoming Code

Every injection attack has the same shape: untrusted input is mixed into something an interpreter will execute (SQL, a shell command, a query document, a template, a file path), and the interpreter cannot tell the data from the instructions. The universal fix is to keep them separate, using structured APIs that pass data as data, and to validate the shape of input before it goes anywhere.

§2SQL Injection

You met this in stage 1.2: concatenating input into SQL lets attackers rewrite the query. The defense is parameterized queries everywhere, including inside ORMs' raw-query escape hatches. Identifiers (table and column names) cannot be parameters, so allow-list them.

// Injection: email = "x' OR '1'='1" returns every user
db.query(`SELECT * FROM users WHERE email = '${email}'`);

// Safe
db.query("SELECT * FROM users WHERE email = $1", [email]);

// Raw escape hatches in ORMs need the same care (Prisma's tagged template parameterizes safely)
await prisma.$queryRaw`SELECT * FROM users WHERE email = ${email}`;

§3NoSQL and Operator Injection

Document databases are vulnerable too. If you pass a parsed JSON body straight into a MongoDB query, an attacker can send an object where you expected a string:

// Body: {"email": "ada@example.com", "password": {"$ne": null}}
const user = await users.findOne({ email: req.body.email, password: req.body.password });
// {"$ne": null} means "password not equal to null": matches any account with a password

// Fix: validate types first so objects can't smuggle in operators
const Login = z.object({ email: z.string().email(), password: z.string() });
const { email, password } = Login.parse(req.body);

§4Command Injection

Shelling out with user input is dangerous because the shell interprets metacharacters such as ;, |, and $(). Prefer a library over a subprocess. If you must run one, use the variants that take an argument array and bypass the shell.

import { exec, execFile } from "node:child_process";

// Dangerous: filename = "a.png; rm -rf /" runs a second command
exec(`convert ${filename} out.jpg`);

// Safer: no shell, arguments are passed as separate values
execFile("convert", [filename, "out.jpg"]);        // still validate filename; a leading "-" can look like an option

§5Path Traversal

If a file name from the user is joined onto a directory, ../../etc/passwd walks out of it. Resolve the final path and confirm it is still inside the intended directory, or better, never use client-supplied names as paths (generate ids and store the mapping).

import path from "node:path";

const base = path.resolve("/var/app/uploads");
const target = path.resolve(base, userSuppliedName);
if (!target.startsWith(base + path.sep)) {
  return res.status(400).json({ error: "Invalid file name" });
}

§6Validation Principles

  • Validate on the server, always. Client-side validation is a convenience, not a control.
  • Allow-list, do not deny-list. Define exactly what is acceptable (type, length, format, range) rather than trying to enumerate bad input.
  • Validate type, not just content. A field you expect to be a string might arrive as an array, an object, or null.
  • Set size limits on bodies, strings, and arrays, and beware of regular expressions with catastrophic backtracking (ReDoS) on user input.
  • Encode on output for the destination: JSON APIs should send Content-Type: application/json and X-Content-Type-Options: nosniff; anything rendered into HTML must be escaped by the template engine or framework.
Validation is not a substitute for safe APIs Validation reduces risk, but the primary defense is using interfaces that cannot mix data and code: parameterized queries, argument arrays, resolved-and-checked paths. Use both layers.

§7Common Mistakes

MistakeWhat HappensFix
Interpolating input into SQL, shell, or file pathsAttackers run their own queries, commands, or read arbitrary filesParameters, argument arrays, and resolved-path checks
Trusting that a field is a stringObjects and arrays smuggle in operators and break logicSchema-validate types at the boundary
Deny-list filtering (blocking ' or ;)Attackers find encodings and characters you did not listAllow-list the exact acceptable format
Practice
  1. Build a deliberately vulnerable login endpoint using string-built SQL, exploit it with ' OR 1=1 --, then fix it with parameters.
  2. Write a file-download endpoint, exploit it with ../, then add a resolved-path check.
  3. Use a schema validator to ensure each field in a request is the expected type, with length limits, and test with arrays and objects as values.
Key takeaways
  • Injection happens when untrusted data is executed as code; keep data and instructions separate.
  • Use parameterized queries, argument-array subprocess calls, and resolved-path checks.
  • Validate with allow-lists at the boundary, including types and sizes, as a second layer of defense.
