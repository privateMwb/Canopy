Rate Limiting, CORS & Hardening

Protecting a public API.

§1Public Means Hostile

Once an API is reachable from the internet, someone will probe it, hammer it, and try to embed it where you did not expect. Three inexpensive defenses address most of that: rate limits, a deliberate CORS policy, and a hardened default configuration.

§2Rate Limiting

A rate limit caps how many requests a client may make per time window, protecting you from brute-force logins, scraping, runaway scripts, and cost abuse. Decide who to count (API key, user id, IP), what to count (per endpoint; stricter for login and password reset), and how to count (fixed window, sliding window, or token bucket, which allows controlled bursts while enforcing an average).

import rateLimit from "express-rate-limit";
import { RedisStore } from "rate-limit-redis";

const apiLimiter = rateLimit({
  windowMs: 60_000,
  limit: 120,                                        // 120 requests per minute per key
  standardHeaders: "draft-7",                        // emits RateLimit-* headers
  keyGenerator: req => req.user?.id ?? req.ip,       // prefer the account over the IP when known
  store: new RedisStore({ sendCommand: (...args) => redis.call(...args) }),   // shared across instances
});

const loginLimiter = rateLimit({ windowMs: 15 * 60_000, limit: 10, skipSuccessfulRequests: true });

app.use("/api", apiLimiter);
app.post("/auth/login", loginLimiter, loginHandler);
  • Respond with 429 Too Many Requests and a Retry-After header so good clients back off.
  • Use a shared store such as Redis once you run more than one instance; in-memory counters are per process.
  • Behind a proxy or load balancer, configure trust proxy correctly, or every client will appear to share the proxy's IP.
  • Limiting is also about cost: unauthenticated endpoints that trigger expensive work deserve the tightest limits.

§3CORS: A Browser Rule, Not a Firewall

Browsers enforce the same-origin policy: JavaScript on app.example.com may not read responses from api.example.com unless the API opts in. CORS (Cross-Origin Resource Sharing) is that opt-in, expressed in response headers. For "non-simple" requests the browser first sends a preflight OPTIONS request asking permission.

import cors from "cors";

const allowed = new Set(["https://app.example.com", "https://admin.example.com"]);

app.use(cors({
  origin: (origin, cb) => cb(null, !origin || allowed.has(origin)),   // allow-list, never "*" with credentials
  methods: ["GET", "POST", "PATCH", "DELETE"],
  allowedHeaders: ["Content-Type", "Authorization"],
  credentials: true,                                 // allow cookies; requires an explicit origin
  maxAge: 600,                                       // cache preflight results for 10 minutes
}));
  • CORS protects users' browsers, not your server. curl, scripts, and other servers ignore it completely, so it is never a substitute for authentication.
  • Never reflect arbitrary Origin values back with credentials enabled; that lets any website act as your logged-in user.
  • A public, credential-free API (open data) can reasonably use Access-Control-Allow-Origin: *.

§4Hardening Defaults

  • Security headers: the helmet middleware sets sensible ones (Strict-Transport-Security, X-Content-Type-Options, and more). Call app.disable("x-powered-by") to stop advertising your framework.
  • HTTPS everywhere, with HSTS so browsers refuse plain HTTP, usually terminated at your load balancer or reverse proxy.
  • Limits: cap body sizes, header sizes, request timeouts, and pagination page sizes.
  • Quiet errors: no stack traces or debug pages in production; set NODE_ENV=production.
  • Minimal surface: disable unused routes, methods, and old versions; keep dependencies patched.
Rate limit before you authenticate Brute-force and credential-stuffing attacks target your login endpoint, so apply limits there first, and key them on both IP and the account being attacked. Locking accounts outright can be abused to lock out legitimate users; prefer progressive delays.

§5Common Mistakes

MistakeWhat HappensFix
Access-Control-Allow-Origin: * together with credentials, or reflecting any originAny site can make authenticated requests as your userAllow-list exact origins
In-memory rate limiting across several instancesEach instance counts separately, so the effective limit is multipliedUse a shared store such as Redis
Believing CORS blocks attackersScripts and servers bypass CORS entirelyAuthenticate and authorize every request regardless of CORS
Practice
  1. Add a global limiter and a stricter login limiter, then hammer them with a loop and observe the 429s and headers.
  2. Make a page on a different origin call your API with fetch; watch the preflight in dev tools, then fix it with an origin allow-list.
  3. Add helmet, run your API through an online or CLI header scanner, and note what remains.
Key takeaways
  • Rate limit by meaningful keys, stricter on sensitive endpoints, with a shared store and clear 429 responses.
  • CORS is a browser-enforced opt-in: allow-list exact origins and never treat it as authentication.
  • Harden defaults: security headers, HTTPS and HSTS, size and time limits, and no verbose errors.
