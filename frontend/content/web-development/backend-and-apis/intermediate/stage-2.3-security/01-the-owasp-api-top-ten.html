The OWASP API Top Ten

The most common API vulnerabilities.

§1A Shared Map of What Goes Wrong

The OWASP API Security Top 10 is a community-maintained ranking of the most common and damaging API vulnerabilities. It is not a complete security program, but it is an excellent checklist: most real-world API breaches are variations of items on this list. The list below follows the 2023 edition; OWASP revises it periodically, so check owasp.org for the current version.

RiskWhat it meansCore defense
API1: Broken Object Level AuthorizationChanging an id in a request exposes someone else's object (the IDOR bug from stage 1.4)Check access to every object on every request
API2: Broken AuthenticationWeak login, credential stuffing, bad token handlingStrong hashing, rate limits, MFA, careful token validation
API3: Broken Object Property Level AuthorizationExposing or accepting fields the caller should not touch (excessive data exposure, mass assignment)Allow-list response and request fields
API4: Unrestricted Resource ConsumptionNo limits on request rate, size, or costRate limits, quotas, pagination caps, timeouts
API5: Broken Function Level AuthorizationA normal user can call admin endpointsDeny by default; explicit role checks on every function
API6: Unrestricted Access to Sensitive Business FlowsAutomated abuse of legitimate flows (ticket scalping, mass signup)Detect and throttle automation; bot protection
API7: Server-Side Request ForgeryYour server fetches a URL the attacker chose, reaching internal systemsAllow-list destinations; block private address ranges
API8: Security MisconfigurationDebug mode, verbose errors, default credentials, open CORSHardened, reviewed, automated configuration
API9: Improper Inventory ManagementForgotten old versions, test endpoints, and undocumented APIs still exposedKeep an inventory; retire what you no longer need
API10: Unsafe Consumption of APIsBlindly trusting data from third-party APIsValidate upstream data like any other input

§2Mass Assignment in Practice

API3 is easy to introduce by accident. Spreading the whole request body into a database update lets clients set fields they should never control.

// VULNERABLE: client sends {"title": "x", "role": "admin"} and promotes themselves
await db.users.update(req.user.id, req.body);

// SAFE: validate against an explicit schema, accept ONLY known, permitted fields
const UpdateProfile = z.object({ displayName: z.string().max(60).optional(), bio: z.string().max(500).optional() }).strict();
await db.users.update(req.user.id, UpdateProfile.parse(req.body));

// Same idea for responses: build the output explicitly, never return the raw row
const toPublic = u => ({ id: u.id, displayName: u.displayName, avatarUrl: u.avatarUrl });   // no email, hash, or role
res.json(toPublic(user));

§3SSRF: When Your Server Is the Attacker's Proxy

Features like "import from URL", webhooks, or link previews make your server issue requests to user-supplied addresses. An attacker supplies http://169.254.169.254/latest/meta-data/ (a cloud metadata service) or an internal admin URL, and your server fetches it from inside your network. Defend by allow-listing hosts where possible, resolving the hostname and rejecting private, loopback, and link-local addresses, disabling redirects, and running such fetches from a network segment with no internal access.

§4Using the List

  • Threat-model each endpoint by asking which of the ten could apply.
  • Turn each risk into tests: a user cannot read another's object, a member cannot call an admin route, an oversized request is rejected.
  • Automate where possible: dependency scanners, DAST/API scanners, and linting of the OpenAPI spec for missing auth on endpoints.
Authorization dominates the list Three of the top five (BOLA, property-level, and function-level authorization) are variations of "the server checked who you are but not what you may touch." Centralize and test your authorization logic; it pays off more than any other single security investment.

§5Common Mistakes

MistakeWhat HappensFix
Treating the Top 10 as a one-time auditNew endpoints reintroduce old bugsBake the checks into code review, tests, and CI
Returning whole database rowsHashes, emails, and internal flags leakMap rows to explicit response objects
Leaving old API versions and test routes runningUnpatched, forgotten attack surfaceMaintain an inventory and decommission what is unused
Practice
  1. Walk through your API and, for each of the ten risks, write one sentence on whether it applies and what currently protects you.
  2. Find an endpoint that accepts req.body directly and rewrite it with a strict allow-list schema.
  3. Write tests proving that user B cannot read user A's resource and a member cannot call an admin endpoint.
Key takeaways
  • The OWASP API Top 10 is a practical checklist; most breaches map to one of its items.
  • Authorization failures (object, property, function level) are the most common and most damaging.
  • Use allow-lists for inputs, outputs, and outbound requests, and turn each risk into an automated test.
