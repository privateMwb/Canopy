Caching with Redis

Cache-aside, TTLs, and invalidation.

§1Remember Expensive Answers

Some work is slow and repeated: a heavy aggregation, a call to a rate-limited API, rendering the same popular page. A cache stores the result of that work in fast memory so later requests skip it. Redis is the most common choice: an in-memory key-value store with rich data types, built-in expiry, and shared access across all your server instances (unlike a per-process JavaScript object).

§2The Cache-Aside Pattern

The application manages the cache explicitly: check the cache, and on a miss load from the source of truth, store the result, and return it.

import Redis from "ioredis";
const redis = new Redis(process.env.REDIS_URL);

async function getProduct(id) {
  const key = `product:v1:${id}`;                    // namespaced, versioned key

  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);             // HIT

  const { rows: [product] } = await pool.query("SELECT * FROM products WHERE id = $1", [id]);   // MISS
  if (product) {
    await redis.set(key, JSON.stringify(product), "EX", 300);   // expire after 5 minutes
  }
  return product;
}
  • Always set a TTL (time to live) so stale or forgotten entries clean themselves up.
  • Namespace and version keys (product:v1:42). Bumping v1 to v2 invalidates every entry when the data shape changes.
  • Treat the cache as disposable. If Redis is down or empty, the app should still work, just slower. The database remains the source of truth.

§3Invalidation: The Hard Part

The saying goes that there are two hard problems in computer science: cache invalidation and naming things. When the underlying data changes, cached copies become wrong. Your options:

StrategyHowTrade-off
TTL onlyLet entries expire naturallySimple; data can be stale up to the TTL
Delete on writeWhen data changes, DEL the keyFresher; you must find every key affected by a change
Write-throughUpdate the cache and database togetherAlways fresh; more complex and slower writes
async function updateProduct(id, fields) {
  await pool.query("UPDATE products SET name = $1 WHERE id = $2", [fields.name, id]);
  await redis.del(`product:v1:${id}`);               // invalidate AFTER the database commit
}

§4Failure Modes to Plan For

  • Cache stampede: a popular key expires and hundreds of requests all miss at once and hammer the database. Mitigate with a short lock around recomputation, request coalescing, or jittered TTLs so keys do not expire together.
  • Caching the wrong thing: never cache per-user data under a shared key. Include the user (or tenant) in the key, or you will serve one person's data to another.
  • Caching errors and misses: deliberately caching "not found" for a short time (negative caching) protects the database from repeated lookups of nonexistent ids; caching a transient error does the opposite.
  • Memory limits: configure a max memory and an eviction policy (such as allkeys-lru) so Redis evicts old entries instead of failing.
Cache after you've measured Caching adds complexity and a new way for data to be wrong. First fix the query with an index (the previous lesson); add a cache when profiling shows a specific expensive, frequently repeated, tolerably stale computation.

§5Common Mistakes

MistakeWhat HappensFix
No TTL on cached entriesMemory grows without bound and stale data lives foreverAlways set an expiry
Shared key for user-specific dataOne user sees another user's dataInclude user or tenant id in the key
Letting the app fail when Redis is downA cache outage becomes a full outageCatch cache errors and fall back to the database
Practice
  1. Wrap a slow query with cache-aside, log hits and misses, and measure latency for cold and warm requests.
  2. Invalidate on update and prove with a test that a read after a write returns the new value.
  3. Simulate a stampede with 50 concurrent requests for an expired key and count database queries; then add a lock to reduce them.
Key takeaways
  • Cache-aside (check, load on miss, store with a TTL) is the default Redis pattern.
  • Invalidation is the hard part: combine TTLs with deletes on write, and namespace keys.
  • Treat the cache as disposable, protect against stampedes, and never share user-specific data between users.
