CI/CD & Deployments

Automated releases with rollbacks.

§1Automate the Path to Production

Continuous Integration (CI) automatically builds and tests every change, so problems are found within minutes of being introduced. Continuous Delivery/Deployment (CD) extends that to packaging and releasing the change, so shipping is a routine, low-drama action rather than a risky weekend event. The goal is small, frequent, reversible releases.

§2A CI Pipeline

# .github/workflows/ci.yml
name: CI
on:
  pull_request:
  push: { branches: [main] }

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17
        env: { POSTGRES_PASSWORD: test, POSTGRES_DB: notes_test }
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U postgres" --health-interval 5s --health-retries 10
    env:
      TEST_DATABASE_URL: postgres://postgres:test@localhost:5432/notes_test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm audit --audit-level=high      # fail on serious known-vulnerable dependencies
  • Fast feedback: keep the pipeline to a few minutes; slow pipelines get ignored.
  • Required checks: protect main so nothing merges until the pipeline is green.
  • Same steps locally and in CI (npm scripts), so "it fails only in CI" is rare.
  • Secrets live in the CI system's secret store, never in the repository, and are exposed only to the jobs that need them.

§3The Deployment Pipeline

After tests pass on main, the pipeline builds a container image, tags it with the commit SHA, pushes it to a registry, and deploys it to staging and then production. The crucial rule is build once, deploy the same artifact everywhere: what you tested is exactly what runs in production, with only configuration differing.

StrategyHow it worksTrade-off
RollingReplace instances a few at a timeSimple; old and new versions briefly coexist
Blue/greenRun a full new environment, switch traffic over, keep the old one for rollbackInstant rollback; double the capacity during switch
CanarySend a small percentage of traffic to the new version and watch metricsLimits blast radius; needs good observability

§4Health Checks and Rollbacks

Orchestrators and load balancers decide whether to send traffic to an instance, or restart it, by probing health endpoints. Provide two with different meanings:

app.get("/healthz", (req, res) => res.sendStatus(200));           // liveness: the process is up and not deadlocked

app.get("/readyz", async (req, res) => {                          // readiness: able to serve real traffic right now
  try {
    await pool.query("SELECT 1");
    res.sendStatus(200);
  } catch {
    res.sendStatus(503);                                          // load balancer stops routing here
  }
});
  • A deployment is not done until the health checks pass, and a failing rollout should roll back automatically.
  • Keep the previous image available and make rollback a single command or button.
  • Run database migrations carefully: apply them as a separate, early step, and keep changes backward compatible so the old code still works against the new schema during the rollout and during a rollback.
  • Use feature flags to ship code dark and enable it gradually, separating deploying from releasing.
Make deploys boring Teams that deploy many small changes daily have fewer outages than teams that deploy large batches monthly: each change is easy to reason about and easy to undo. If deploys feel scary, the fix is more automation and smaller steps, not more ceremony.

§5Common Mistakes

MistakeWhat HappensFix
Rebuilding separately for each environmentWhat you tested is not what you deployedBuild one immutable image and promote it through environments
Migrations that break the currently running versionRollout or rollback fails partwayMake schema changes backward compatible (expand, then contract)
No readiness check, or one that always returns 200Traffic goes to instances that cannot serve itCheck real dependencies in readiness and fail the rollout when it does not pass
Practice
  1. Create a CI workflow that runs lint and tests against a Postgres service on every pull request, and make it a required check.
  2. Add /healthz and /readyz endpoints, then stop the database and watch readiness fail while liveness stays green.
  3. Write down your rollback procedure for a bad release in five steps. Then try it on a staging copy.
Key takeaways
  • CI runs tests on every change; CD builds one artifact and promotes it through environments.
  • Use health checks, gradual rollout strategies, and fast rollback to make releases low-risk.
  • Keep migrations backward compatible and separate deploying code from releasing features.
