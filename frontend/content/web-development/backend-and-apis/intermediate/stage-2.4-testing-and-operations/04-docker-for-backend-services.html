Docker for Backend Services

Packaging and running consistently.

§1"It Works on My Machine"

A backend depends on a specific runtime version, operating-system libraries, and configuration. Docker packages your app and everything it needs into an image, a portable, immutable snapshot, which runs as an isolated container that behaves the same on your laptop, in CI, and in production.

§2A Production-Minded Dockerfile

# syntax=docker/dockerfile:1
FROM node:22-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev                                # reproducible install from the lockfile

FROM node:22-slim AS runtime
ENV NODE_ENV=production
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY src ./src
COPY package.json ./
USER node                                            # don't run as root
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s CMD node -e "fetch('http://localhost:3000/healthz').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
CMD ["node", "src/server.js"]                        # exec form: Node receives signals directly
  • Layer caching: copy package*.json and install before copying source, so editing code does not reinstall dependencies.
  • Multi-stage builds keep build tools and dev dependencies out of the final image, making it smaller and with less attack surface.
  • Pin versions of base images (a specific tag, ideally a digest) so builds are repeatable.
  • Run as a non-root user so a compromised process has fewer privileges.
  • .dockerignore should list node_modules, .git, .env, and test files so secrets and clutter never enter the build context.

§3Configuration and Secrets

Images must be environment-agnostic: the same image runs in staging and production, with differences injected at runtime through environment variables or mounted secrets. Never bake .env files or credentials into an image; anyone with the image can extract them.

§4Graceful Shutdown

When a container is stopped or replaced, the orchestrator sends SIGTERM and, after a grace period, SIGKILL. Handle SIGTERM by stopping new connections, letting in-flight requests finish, closing database pools, and then exiting. Without this, deploys drop requests.

const server = app.listen(config.PORT);

process.on("SIGTERM", () => {
  server.close(async () => {                         // stop accepting; wait for in-flight requests
    await pool.end();
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 10_000).unref(); // safety net if something hangs
});

§5Running the Whole Stack Locally

Docker Compose describes multi-container setups, such as your API plus Postgres and Redis, in a single file, so a new teammate can run docker compose up and have a working environment.

# compose.yaml
services:
  api:
    build: .
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgres://app:devpass@db:5432/notes
      REDIS_URL: redis://cache:6379
    depends_on:
      db: { condition: service_healthy }
  db:
    image: postgres:17
    environment: { POSTGRES_USER: app, POSTGRES_PASSWORD: devpass, POSTGRES_DB: notes }
    volumes: ["pgdata:/var/lib/postgresql/data"]    # data survives container restarts
    healthcheck: { test: ["CMD-SHELL", "pg_isready -U app"], interval: 5s, retries: 10 }
  cache:
    image: redis:7
volumes:
  pgdata:
Containers are disposable; state is not A container's filesystem disappears when it is replaced. Keep durable state in volumes or managed services (databases, object storage), and keep the container itself stateless so it can be killed and restarted freely.

§6Common Mistakes

MistakeWhat HappensFix
Copying all source before installing dependenciesEvery code change reinstalls everything and builds slowlyCopy manifests first, install, then copy source
Running as root and baking in secretsA breach gets root, and secrets can be pulled from the imageUse a non-root user and inject config at runtime
Ignoring SIGTERM (or using shell-form CMD)Deploys kill in-flight requests after a hard timeoutUse exec-form CMD and handle graceful shutdown
Practice
  1. Write a Dockerfile for your API, build it, and compare the image size with and without a multi-stage build.
  2. Create a compose.yaml that brings up the API with Postgres, and verify that data persists after docker compose down and up.
  3. Start the container, run docker stop, and confirm via logs that your SIGTERM handler ran.
Key takeaways
  • Docker packages the app and its dependencies into an immutable image that runs the same everywhere.
  • Use multi-stage builds, layer caching, a non-root user, and runtime-injected configuration.
  • Handle SIGTERM for graceful shutdown, and keep containers stateless with Compose for local stacks.
