Logging, Metrics & Tracing

Seeing inside a running service.

§1Seeing Inside a Running Service

In production you cannot attach a debugger. Observability is the ability to understand what a system is doing from the signals it emits. Three kinds of signal complement each other:

SignalAnswersExample
LogsWhat happened, in detail, for one event?"Payment 918 failed: card declined"
MetricsHow is the system behaving overall, over time?Requests per second, error rate, p95 latency
TracesWhere did the time go in one request across services?A 900 ms request: 20 ms API, 700 ms database, 150 ms payment call

§2Structured Logging

Free-text logs are hard to search at scale. Structured logs emit one JSON object per event with consistent fields, which log systems can filter and aggregate. Include a request id on every line so you can pull up everything that happened during one request.

import pino from "pino";
import { randomUUID } from "node:crypto";

const logger = pino({ level: process.env.LOG_LEVEL ?? "info", redact: ["req.headers.authorization", "*.password"] });

app.use((req, res, next) => {
  req.id = req.get("x-request-id") ?? randomUUID();
  req.log = logger.child({ requestId: req.id, userId: req.user?.id });
  res.set("x-request-id", req.id);                   // clients can quote this in bug reports
  const start = process.hrtime.bigint();
  res.on("finish", () => {
    req.log.info({
      method: req.method, route: req.route?.path, status: res.statusCode,
      durationMs: Number(process.hrtime.bigint() - start) / 1e6,
    }, "request completed");
  });
  next();
});

// {"level":30,"requestId":"3c1...","method":"POST","route":"/notes","status":201,"durationMs":12.4,"msg":"request completed"}
  • Use levels deliberately: error for things needing attention, warn for odd but handled, info for key events, debug only when investigating.
  • Redact secrets and personal data. Never log passwords, tokens, or full payment details.
  • Write to stdout and let the platform collect and ship logs; do not manage log files in the app.

§3Metrics: The Four Numbers to Start With

For any request-driven service, begin with the RED method: Rate (requests per second), Errors (failed fraction), and Duration (latency distribution). Track latency as a histogram and read percentiles (p50, p95, p99) rather than averages, because averages hide the slow tail that real users feel.

import client from "prom-client";
client.collectDefaultMetrics();                      // CPU, memory, event loop lag, GC...

const httpDuration = new client.Histogram({
  name: "http_request_duration_seconds",
  help: "Request duration",
  labelNames: ["method", "route", "status"],
  buckets: [0.01, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
});

// in the finish handler:  httpDuration.labels(req.method, req.route?.path ?? "unmatched", res.statusCode).observe(seconds);

app.get("/metrics", async (req, res) => {            // scraped by Prometheus (keep it off the public internet)
  res.type(client.register.contentType).send(await client.register.metrics());
});

Label with the route pattern (/notes/:id), never the raw URL or user id, because each distinct label value creates a new time series. Unbounded labels ("high cardinality") can overwhelm a metrics system.

§4Tracing

When one request touches several services, a trace records each step as a span with timing, linked by a trace id propagated in request headers (the W3C traceparent header). OpenTelemetry is the vendor-neutral standard: its Node SDK can auto-instrument HTTP, Express, and database clients, then export to Jaeger, Tempo, or a commercial backend. Put the trace id in your logs and you can jump from a slow trace straight to its log lines.

Instrument before you need it The incident is the worst time to discover you cannot answer "what changed, and where is it slow?" Add request logging, RED metrics, and tracing early; they are cheap compared with a blind outage.

§5Common Mistakes

MistakeWhat HappensFix
Plain-text, unstructured logs with no request idCannot correlate lines or filter reliablyEmit JSON with a request id on every line
Logging secrets or full request bodiesCredentials and personal data leak into log systemsRedact sensitive fields and log only what you need
Labeling metrics with user ids or raw URLsCardinality explosion crashes or bankrupts the metrics backendUse bounded labels such as method, route pattern, and status
Practice
  1. Add a request-logging middleware that emits one structured line per request with a request id, status, and duration, and redacts the Authorization header.
  2. Expose a /metrics endpoint with a latency histogram, generate load, and read the p95 from the data.
  3. Add OpenTelemetry auto-instrumentation and view a trace of a request that hits the database.
Key takeaways
  • Logs, metrics, and traces answer different questions; use all three together.
  • Emit structured JSON logs with request ids, and track rate, errors, and duration (RED) with histograms.
  • Keep metric labels bounded, redact secrets, and propagate trace ids across services.
