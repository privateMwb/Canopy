Tokens & JWTs

Stateless auth and its trade-offs.

§1Stateless Authentication

Instead of looking up a session on every request, the server can issue a token that contains the user's identity and is cryptographically signed. On each request the server only checks the signature; no database call is required. The most common format is the JWT (JSON Web Token, pronounced "jot").

A JWT is three base64url-encoded parts separated by dots: header.payload.signature. The payload holds claims, statements about the user and the token itself.

// Decoded payload
{
  "sub": "user_42",                  // subject: whose token this is
  "role": "member",
  "iat": 1767225600,                 // issued at
  "exp": 1767226500                  // expires at (15 minutes later)
}
import { SignJWT, jwtVerify } from "jose";           // npm install jose

const secret = new TextEncoder().encode(process.env.JWT_SECRET);   // long random value

const token = await new SignJWT({ role: user.role })
  .setProtectedHeader({ alg: "HS256" })
  .setSubject(String(user.id))
  .setIssuedAt()
  .setExpirationTime("15m")
  .sign(secret);

// On each request
try {
  const { payload } = await jwtVerify(token, secret, { algorithms: ["HS256"] });
  req.user = { id: payload.sub, role: payload.role };
} catch {
  return res.status(401).json({ error: "Invalid or expired token" });
}

§2Signed Is Not Secret

The signature proves the token was not tampered with and was issued by someone who holds the key. It does not hide the contents: anyone can base64-decode the payload and read it. Never put passwords, secrets, or sensitive personal data in a JWT.

§3The Trade-Offs

Server-side sessionsJWTs
Lookup per requestYes (store hit)No (signature check only)
Revoke a user instantlyEasy: delete the rowHard: valid until it expires
Scales across servicesNeeds shared storeAny service with the key can verify
Token contentsOpaque random idReadable claims, can go stale

The central weakness is revocation. Once issued, a JWT is valid until exp, even if the user is banned or changes their password. The usual compromise is a short-lived access token (about 5 to 15 minutes) paired with a longer-lived, revocable refresh token stored server-side, which the client exchanges for new access tokens. Rotating refresh tokens on each use, and detecting reuse, adds protection against theft.

  • Always verify: signature, expiry, and (for production systems) issuer and audience claims.
  • Pin the algorithm in the verify call. Accepting whatever the header says has caused real vulnerabilities, such as the alg: none attack.
  • Store tokens carefully in browsers. A token in localStorage is readable by any injected script; an HttpOnly cookie is not. Many teams therefore keep refresh tokens in HttpOnly cookies.
Sessions are not obsolete "Stateless" sounds modern, but for a typical web app with a single backend, a server-side session is simpler, safer, and easier to revoke. Reach for JWTs when you genuinely need to verify identity across independent services or from mobile and third-party clients.

§4Common Mistakes

MistakeWhat HappensFix
Putting sensitive data in the payloadAnyone holding the token can read itKeep claims minimal and non-sensitive
Long-lived access tokens (days or weeks)A stolen token works for the whole period and cannot be revokedUse 5 to 15 minute access tokens with refresh tokens
Not restricting accepted algorithms, or using a weak shared secretToken forgeryPin algorithms and use a long random secret (or an asymmetric key pair)
Practice
  1. Issue a 15-minute JWT at login and write middleware that verifies it from the Authorization: Bearer header.
  2. Decode a token you issued at a JWT inspector (or with atob on the middle part) to see that the payload is readable. Change one character of the payload and watch verification fail.
  3. Sketch the refresh-token flow: where is the refresh token stored, and what happens when a user logs out?
Key takeaways
  • A JWT is a signed, readable set of claims that servers can verify without a database lookup.
  • Signing prevents tampering, not reading; keep payloads small and non-sensitive.
  • Statelessness makes revocation hard, so use short-lived access tokens plus revocable refresh tokens.
