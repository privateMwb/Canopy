Environment Config & Secrets

Keeping credentials out of code.

§1Config Belongs Outside the Code

Your app needs values that differ between environments or must stay private: database URLs, API keys, JWT signing secrets, the port to listen on. Hardcoding them means you cannot run the same code in development, staging, and production, and it means anyone who can read your repository can read your credentials. The widely used guideline (from the Twelve-Factor App methodology) is to keep config in environment variables.

# .env  (local development only: NEVER commit this file)
DATABASE_URL=postgres://app:devpass@localhost:5432/notes
JWT_SECRET=replace-with-a-long-random-value
STRIPE_API_KEY=sk_test_...
PORT=3000
// Node 20.6+ can load it natively:   node --env-file=.env server.js
// or use the dotenv package:         import "dotenv/config";

const dbUrl = process.env.DATABASE_URL;

In production you do not ship a .env file. The hosting platform, container orchestrator, or CI system injects the variables when it starts your process.

§2Protect the Repository

  • Add .env to .gitignore before the first commit, and commit a .env.example containing the names (not the values) so teammates know what to set.
  • Remember that git remembers: deleting a secret from the latest commit does not remove it from history.
  • Use secret-scanning tools (GitHub secret scanning, gitleaks, or a pre-commit hook) to catch accidental commits.
If a secret leaks, rotate it Assume it is compromised the moment it appears in a public repo, a log, or a screenshot. Revoke and replace it at the provider first; cleaning git history is secondary, because bots scrape public repositories within minutes.

§3Validate Config at Startup

A missing or malformed variable should stop the app immediately with a clear message, not surface as a confusing crash an hour later. Parse the environment once, with a schema, and export a typed config object that the rest of the code imports.

import { z } from "zod";

const Env = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  PORT: z.coerce.number().int().default(3000),
  DATABASE_URL: z.string().url(),
  JWT_SECRET: z.string().min(32, "JWT_SECRET must be at least 32 characters"),
});

export const config = Env.parse(process.env);       // throws with a readable error if invalid

§4Secrets vs Ordinary Config

Not every setting is secret. A port or a feature flag is plain config; a database password or signing key is a secret and deserves stricter handling: never log it, never send it to the client, limit who can read it, and rotate it periodically. For larger systems, a dedicated secrets manager (cloud providers' secret stores, HashiCorp Vault, Doppler, and similar) adds access control, audit logs, and automated rotation. Stage 2.3 covers these in depth.

§5Common Mistakes

MistakeWhat HappensFix
Committing .env or hardcoding keysCredentials leak publicly and are scraped quicklyGitignore .env, use scanning, and rotate any exposed secret
Reading process.env everywhere with no validationTypos and missing values cause late, confusing failuresValidate once at startup and import a typed config object
Logging config objects or sending them to the browserSecrets appear in logs and client bundlesNever log secrets; expose to clients only values designed to be public
Practice
  1. Move every hardcoded value in your project into environment variables, add a .env.example, and confirm .env is gitignored.
  2. Write a Zod config schema, then delete JWT_SECRET and confirm the app refuses to start with a helpful message.
  3. Run git log -p or a scanner such as gitleaks over a practice repo to see how secrets in history are found.
Key takeaways
  • Keep secrets and per-environment settings in environment variables, never in source code.
  • Gitignore .env, commit only a .env.example, and rotate any secret that was ever exposed.
  • Validate configuration at startup so mistakes fail fast with clear errors.
