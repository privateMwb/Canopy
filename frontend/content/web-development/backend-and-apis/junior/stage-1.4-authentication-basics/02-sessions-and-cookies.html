Sessions & Cookies

Server-side sessions and secure cookie settings.

§1Remembering Who Is Logged In

HTTP is stateless, so after a successful login the server needs a way to recognize the same user on later requests. The classic solution is a session: the server creates a random, unguessable session id, stores it with the user's identity, and sends the id to the browser in a cookie. The browser then attaches that cookie automatically to every request to your site.

import crypto from "node:crypto";

// On successful login
const sessionId = crypto.randomBytes(32).toString("base64url");     // 256 bits of randomness
await pool.query(
  "INSERT INTO sessions (id, user_id, expires_at) VALUES ($1, $2, now() + interval '7 days')",
  [sessionId, user.id]
);
res.cookie("sid", sessionId, {
  httpOnly: true,                                    // JavaScript cannot read it (limits XSS theft)
  secure: true,                                      // only sent over HTTPS
  sameSite: "lax",                                   // not sent on most cross-site requests (CSRF defense)
  maxAge: 7 * 24 * 60 * 60 * 1000,
  path: "/",
});
res.json({ ok: true });
// Middleware: turn the cookie into req.user on every request
async function loadSession(req, res, next) {
  const sid = req.cookies?.sid;                      // needs the cookie-parser middleware
  if (!sid) return next();
  const { rows } = await pool.query(
    `SELECT u.id, u.email FROM sessions s JOIN users u ON u.id = s.user_id
      WHERE s.id = $1 AND s.expires_at > now()`, [sid]);
  req.user = rows[0];                                // undefined if invalid or expired
  next();
}

// Logout: destroy it on the server, then clear the cookie
await pool.query("DELETE FROM sessions WHERE id = $1", [req.cookies.sid]);
res.clearCookie("sid");

§2What the Cookie Flags Do

FlagPurpose
HttpOnlyHides the cookie from document.cookie, so injected scripts cannot steal it
SecureSends the cookie only over HTTPS, so it cannot be sniffed on plain HTTP
SameSiteLax or Strict stops the browser attaching it to most cross-site requests, which blunts CSRF
Max-Age / ExpiresBounds the cookie's lifetime; omit for a session-only cookie
__Host- name prefixForces Secure, no Domain, and path /, preventing subdomain tricks

§3Why Server-Side Sessions Are Good

  • Revocation is trivial. Delete the row and the user is logged out everywhere, immediately. That matters when an account is compromised.
  • The cookie holds nothing sensitive, only a random id that means nothing without your database.
  • You can see and manage active sessions, for example a "log out other devices" feature.

The cost is a lookup on every request, which is why sessions usually live in a fast store such as Redis (or an indexed database table at modest scale). Two more rules: generate a new session id at login (never reuse one that existed before authentication, to prevent session fixation), and expire sessions on both an idle and an absolute timeout.

Cookies and CSRF Because browsers attach cookies automatically, a malicious site can try to make your user's browser send a request to your API. SameSite=Lax blocks most of that; for state-changing requests also consider CSRF tokens or checking the Origin header. Bearer tokens in the Authorization header (next lesson) are not attached automatically, which is part of their appeal for APIs.

§4Common Mistakes

MistakeWhat HappensFix
Cookie without HttpOnly and SecureXSS or network sniffing steals sessionsAlways set httpOnly, secure in production, and sameSite
Using predictable session ids (counters, timestamps)Attackers guess other users' sessionsUse at least 128 bits from a cryptographic random source
Keeping the same session id across loginSession fixation: an attacker plants a known id before the victim logs inIssue a fresh id when privilege changes
Practice
  1. Implement login, an authenticated GET /me route, and logout using a sessions table. Confirm that after logout the old cookie no longer works.
  2. Open the browser dev tools, find your cookie, and check each flag. Try reading it with document.cookie in the console.
  3. Add an idle timeout: extend expires_at on activity, but cap total lifetime at 30 days.
Key takeaways
  • A session is a random id in a cookie that maps, on the server, to a logged-in user.
  • Set HttpOnly, Secure, and SameSite; regenerate the id at login and expire it sensibly.
  • Server-side sessions are easy to revoke, at the cost of a lookup per request.
