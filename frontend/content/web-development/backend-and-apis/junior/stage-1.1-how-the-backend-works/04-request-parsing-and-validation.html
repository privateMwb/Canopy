Request Parsing & Validation

Query strings, JSON bodies, and rejecting bad input.

§1Input Arrives in Three Places

Clients send data to your server through the URL path, the query string, and the body. Each arrives as untyped text until you parse it, and each can contain anything a malicious or careless client decides to send.

SourceExampleExpress accessTypical use
Path/books/42req.params.idIdentify one resource
Query string/books?genre=scifi&limit=10req.queryFilter, sort, paginate
Body{"title": "Dune"}req.bodyCreate or update data
import express from "express";
const app = express();

app.use(express.json());                             // parses JSON bodies into req.body

app.get("/books", (req, res) => {
  const limit = Number(req.query.limit ?? 20);       // query values are strings (or arrays!)
  res.json({ limit });
});

app.post("/books", (req, res) => {
  console.log(req.body);                             // undefined/{} if no JSON parser or wrong Content-Type
  res.status(201).json(req.body);
});

§2Never Trust the Client

Your server cannot control what arrives. A missing field, a string where you expected a number, a 5 MB title, or an unexpected extra field are all normal. Validation checks input against the shape you expect before any of it touches your logic or database, and rejects the rest with a clear 4xx response.

Hand-written if chains get long and inconsistent. Schema libraries such as Zod (or Valibot, Joi, and Ajv for JSON Schema) describe the shape once and give you parsed, typed data in return.

import { z } from "zod";

const CreateBook = z.object({
  title: z.string().trim().min(1).max(200),
  year: z.number().int().min(0).max(2100).optional(),
  tags: z.array(z.string().max(30)).max(10).default([]),
});

app.post("/books", (req, res) => {
  const result = CreateBook.safeParse(req.body);
  if (!result.success) {
    return res.status(400).json({
      error: "Invalid request body",
      details: result.error.issues.map(i => ({ field: i.path.join("."), message: i.message })),
    });
  }
  const book = result.data;                          // trusted from here on
  res.status(201).json(book);
});

§3Choosing the Status Code

  • 400 Bad Request: malformed input, such as invalid JSON or wrong types. It is the common default for validation failures.
  • 422 Unprocessable Content: well-formed but semantically invalid. Many APIs use it for validation errors; pick one convention and apply it everywhere.
  • 413 Content Too Large: the body exceeds your limit. Set a size cap with express.json({ limit: "100kb" }).
Validate at the boundary Do validation once, at the edge where data enters, and pass only validated values inward. Code deeper in the system can then assume the data is well-formed instead of re-checking it in a dozen places.

§4Common Mistakes

MistakeWhat HappensFix
Skipping the JSON parserreq.body is empty and every create call looks brokenRegister express.json() before routes that read bodies
Trusting Number(req.query.limit) blindlyNaN, negative, or enormous values reach your database layerValidate and clamp: integer, minimum 1, sensible maximum
Spreading req.body straight into a database callClients set fields they should never control, like isAdminPick only the fields your schema allows
Practice
  1. Write a Zod schema for a user signup (email, password of at least 12 characters, optional display name) and return field-level error details.
  2. Send a request with a body that is not valid JSON and observe what Express returns. Then make that response a clean JSON error.
  3. Add a limit and offset to GET /books with validated bounds, rejecting limit=100000.
Key takeaways
  • Input comes from the path, the query string, and the body, and always starts life as untrusted text.
  • Validate with a schema at the boundary, reject early with a clear 4xx, and use only the parsed result.
  • Set body size limits and allow-list fields so clients cannot send more than you intended.
