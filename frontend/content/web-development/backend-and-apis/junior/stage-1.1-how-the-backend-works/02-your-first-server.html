Your First Server

Building a server in Node.js and handling routes.

§1A Server Is a Program That Listens

Node.js ships with an HTTP server in its standard library. You give it a function that runs for every incoming request; it hands you a request object (what the client sent) and a response object (what you will send back). No framework is needed to see how it works, and understanding this layer makes every framework less magical.

// server.js  (run with: node server.js)
import { createServer } from "node:http";

const server = createServer((req, res) => {
  res.statusCode = 200;
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.end("Hello from my first server\n");
});

const port = process.env.PORT ?? 3000;
server.listen(port, () => {
  console.log(`Listening on http://localhost:${port}`);
});

Save this as server.js in a folder whose package.json contains "type": "module" (so import works), run node server.js, and visit the URL. Stop it with Ctrl+C.

§2Handling Routes by Hand

The request object tells you the method and URL. Branching on them is the simplest possible router. It gets tedious quickly, which is exactly why frameworks exist, but writing it once shows what a router actually does.

import { createServer } from "node:http";

const books = [{ id: 1, title: "Dune" }, { id: 2, title: "Neuromancer" }];

function sendJson(res, status, data) {
  res.writeHead(status, { "Content-Type": "application/json" });
  res.end(JSON.stringify(data));
}

const server = createServer((req, res) => {
  const url = new URL(req.url, `http://${req.headers.host}`);

  if (req.method === "GET" && url.pathname === "/health") {
    return sendJson(res, 200, { status: "ok" });
  }
  if (req.method === "GET" && url.pathname === "/books") {
    return sendJson(res, 200, books);
  }
  sendJson(res, 404, { error: "Not found" });   // fallthrough: nothing matched
});

server.listen(3000);

§3Things Worth Noticing

  • The server stays running. Unlike a script, it does not exit; it waits for events. The process is the server.
  • Every request must end. If a code path never calls res.end(), the client hangs until it times out.
  • Ports are addresses. Only one process can listen on a given port, so a second copy fails with EADDRINUSE.
  • The fallthrough matters. Without the final 404, unknown URLs would hang rather than fail clearly.
Read the port from the environment process.env.PORT ?? 3000 costs nothing and means the same code runs on your laptop and on a hosting platform that assigns the port for you. This habit returns in the secrets-and-config lesson.

§4Common Mistakes

MistakeWhat HappensFix
Forgetting res.end() on one branchThe request hangs with no response until the client times outReturn after every response and add a default 404 branch
Calling res.end() twice, or writing headers after the body startsAn error such as ERR_HTTP_HEADERS_SENT and a crashed or garbled responseUse return after sending, and set status and headers before the body
Hardcoding the portDeploys fail or collide on platforms that assign portsRead process.env.PORT with a local default
Practice
  1. Add a GET /books/1 route that returns one book, parsing the id from the path by hand, and a 404 when it does not exist.
  2. Add a route that returns the current time as JSON. Verify the Content-Type header in your browser's network tab.
  3. Start the server twice in two terminals and read the error. What does it tell you about ports?
Key takeaways
  • A server is a long-running process that runs your function once per request.
  • Every request needs exactly one complete response: status, headers, then body.
  • Hand-written routing works, and its limits motivate the framework you meet next.
