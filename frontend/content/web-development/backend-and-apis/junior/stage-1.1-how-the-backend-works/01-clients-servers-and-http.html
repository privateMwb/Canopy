Clients, Servers & HTTP

Requests, responses, methods, status codes, and headers.

§1The Conversation Behind Every Page

A client (a browser, a mobile app, another server) asks for something; a server is a program that listens for those asks and answers them. The language they speak is HTTP: a text-based, request/response protocol that runs on top of TCP (and, with HTTP/3, QUIC). Each exchange is independent: the server does not inherently remember the previous request, which is why things like sessions and tokens exist later in this course.

Here is a complete request and response as they travel over the wire. Everything you build in the backend is, in the end, a program that turns the first block into the second.

GET /api/books/42?expand=author HTTP/1.1
Host: library.example.com
Accept: application/json
Authorization: Bearer eyJhbGciOi...

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: max-age=60

{"id": 42, "title": "Dune", "author": {"id": 7, "name": "Frank Herbert"}}

§2Anatomy of a Request and Response

  • Request line / status line: method, path (plus query string), and protocol version on the way in; protocol version, status code, and reason phrase on the way out.
  • Headers: key-value metadata such as Content-Type, Authorization, Accept, Cache-Control, and Set-Cookie.
  • Body: optional payload, usually JSON for APIs. GET requests normally have none; POST, PUT, and PATCH usually do.

§3Methods Carry Meaning

The method states the intent. Two properties matter for correctness: a safe method does not change server state, and an idempotent method has the same effect whether you send it once or five times. Browsers, proxies, and retry logic all rely on these promises.

MethodTypical useSafeIdempotent
GETRead a resourceYesYes
POSTCreate a resource or trigger an actionNoNo
PUTReplace a resource entirelyNoYes
PATCHPartially update a resourceNoNot guaranteed
DELETERemove a resourceNoYes

§4Status Codes by Family

The first digit tells the client what kind of outcome occurred, which lets generic tooling react sensibly even to codes it has never seen.

FamilyMeaningExamples
2xxSuccess200 OK, 201 Created, 204 No Content
3xxRedirection301 Moved Permanently, 304 Not Modified
4xxThe client made a mistake400 Bad Request, 401 Unauthorized, 404 Not Found
5xxThe server failed500 Internal Server Error, 503 Service Unavailable
The key insight Responsibility is split by the first digit. A 4xx says "fix your request and try again"; a 5xx says "I broke, and retrying later might work." Returning 500 for a bad input, or 200 for a failure, misleads every client and monitoring tool that depends on the family.

§5Common Mistakes

MistakeWhat HappensFix
Returning 200 with {"error": ...} in the bodyClients, caches, and monitors treat the call as a success, so failures go unnoticedUse a real 4xx or 5xx status and put the details in the body
Using GET for actions that change dataCrawlers, prefetchers, and retries trigger the change unintentionallyUse POST, PUT, PATCH, or DELETE for mutations
Ignoring Content-TypeThe receiver guesses how to parse the body and often guesses wrongAlways set it on responses and send it on requests with bodies
Practice
  1. Open your browser's network tab, load any page, and pick one request. Write down its method, status, and three headers, and say what each header is for.
  2. For each of these, choose a method and a success status: fetch a user, create an order, replace a profile, delete a comment.
  3. Explain in two sentences why a client may safely retry a PUT but should be careful retrying a POST.
Key takeaways
  • HTTP is a stateless request/response protocol: a start line, headers, and an optional body.
  • Methods express intent, and safe and idempotent are promises other software relies on.
  • Status code families (2xx, 3xx, 4xx, 5xx) tell the client who needs to act next.
