Connecting from Code

Drivers, connection pools, and parameterized queries.

§1A Driver Speaks the Database's Protocol

Your Node process talks to PostgreSQL over a network connection using a driver. The standard one is pg (node-postgres); other databases have equivalents (mysql2, better-sqlite3). You hand the driver a connection string, then send SQL and receive rows back as JavaScript objects.

import pg from "pg";

const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,        // postgres://user:pass@host:5432/dbname
  max: 10,                                           // at most 10 simultaneous connections
});

const { rows } = await pool.query("SELECT id, title FROM notes WHERE user_id = $1", [userId]);
console.log(rows);                                   // [{ id: 1, title: "..." }, ...]

§2Why a Pool?

Opening a database connection is slow (a network handshake, authentication, and server-side setup), and databases only allow a limited number of them. A connection pool opens a handful once and lends them out: pool.query() borrows a connection, runs your query, and returns it. Create one pool when the app starts and share it everywhere. Creating a pool per request defeats its purpose and can exhaust the database.

When several statements must run on the same connection (as in a transaction), check one out explicitly and always give it back:

const client = await pool.connect();
try {
  await client.query("BEGIN");
  await client.query("UPDATE accounts SET balance = balance - $1 WHERE id = $2", [50, 1]);
  await client.query("UPDATE accounts SET balance = balance + $1 WHERE id = $2", [50, 2]);
  await client.query("COMMIT");
} catch (err) {
  await client.query("ROLLBACK");
  throw err;
} finally {
  client.release();                                  // forgetting this leaks the connection
}

§3Parameterized Queries Stop SQL Injection

Never build SQL by gluing user input into a string. If a user submits x'; DROP TABLE notes; -- as a title, string concatenation turns their text into commands. Parameterized queries send the SQL and the values separately, so the database treats values purely as data.

// DANGEROUS: input becomes part of the SQL
await pool.query(`SELECT * FROM users WHERE email = '${email}'`);

// SAFE: $1 is a placeholder; the value travels separately
await pool.query("SELECT * FROM users WHERE email = $1", [email]);
Placeholders only work for values You can parameterize values ($1) but not identifiers like table or column names. If a column name must be dynamic (say, for sorting), check it against a hard-coded allow-list, never pass it through from the client.

§4Common Mistakes

MistakeWhat HappensFix
Building SQL with template strings and user inputSQL injection: attackers read, modify, or destroy dataUse $1 placeholders for every value
Creating a new pool (or client) per requestConnections pile up until the database refuses new onesCreate one pool at startup and reuse it
Not calling client.release() in a finallyThe pool slowly runs dry and requests hangRelease in finally so it runs on success and on error
Practice
  1. Connect a script to your database with pg, insert a user using placeholders, and read it back.
  2. Write a deliberately injectable query, then craft an input that returns every row. Fix it with a parameter.
  3. Set the pool's max to 2, fire 10 slow queries at once (for example SELECT pg_sleep(1)), and observe how they queue.
Key takeaways
  • A driver sends SQL over a network connection; a pool reuses a small set of connections for speed and safety.
  • Create one pool per process, and always release explicitly checked-out clients in a finally block.
  • Pass user input only through parameter placeholders, never by string concatenation.
