Encryption Strategy & Key Management at Scale

At scale, encryption is a governance problem: who owns keys, who can use them, who can delete them, and how that stays true across hundreds of accounts.

§1Key Policies and Grants

A KMS key policy is the primary access control for a key; IAM policies work only if the key policy allows it (typically by delegating to the account). Grants give temporary, narrow permissions, used heavily by AWS services.

{
  "Sid": "AllowUseByAppRole",
  "Effect": "Allow",
  "Principal": {"AWS": "arn:aws:iam::111111111111:role/app"},
  "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
  "Resource": "*",
  "Condition": {"StringEquals": {"kms:ViaService": "s3.eu-west-1.amazonaws.com"}}
}

§2Separation of Duties

RoleCanCannot
Key administratorManage, rotate, schedule deletionUse the key to decrypt data
Key user (application)Encrypt and decryptChange policy or delete the key
AuditorRead key metadata and logsUse or manage the key

Use kms:ViaService and encryption-context conditions so keys are used only through intended services and for intended data.

§3Rotation, Scale, and Recovery

  • Enable automatic rotation on customer managed symmetric keys; old key material is retained so existing data stays decryptable.
  • Use a key per data class and environment, not one global key, to limit blast radius and make revocation meaningful.
  • Multi-Region keys let you decrypt in another region for DR and global tables.
  • Deleting a key has a 7 to 30 day waiting period; disabling a key is the reversible emergency brake.
  • Alarm on ScheduleKeyDeletion and DisableKey events in CloudTrail.
  • Decide deliberately between AWS managed keys (simple) and customer managed keys (control, audit, cross-account sharing).
Admins should not read the data Key administration and key usage are different powers. Separating them means the people who manage keys cannot silently decrypt the data.

§4Common Mistakes

MistakeWhat HappensFix
One KMS key for every workloadBig blast radius, no meaningful revocationUse keys per environment and data class
Key admins also able to decryptNo separation of dutiesSplit administrator and user permissions
No alert on key deletion or disableDestructive changes go unnoticedAlarm on those CloudTrail events
Practice
  1. Write a key policy separating administrators from application users.
  2. Create a CloudTrail-based alarm for scheduled key deletion.
Key takeaways
  • Key policies control access first; use conditions and grants for precision.
  • Separate key administration from key usage.
  • Use keys per data class, enable rotation, and alarm on dangerous key events.
