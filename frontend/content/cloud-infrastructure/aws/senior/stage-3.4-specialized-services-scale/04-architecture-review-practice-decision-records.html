Architecture Review Practice & Decision Records

Architecture is the sum of decisions, and teams stay healthy when those decisions are reviewed openly and written down with their reasons.

§1Running a Useful Review

  • Define the workload, goals, constraints, and non-goals before the meeting.
  • Use a framework (Well-Architected pillars) to ensure coverage, but focus on risks that matter.
  • Ask for failure scenarios: what happens when X is down, slow, or wrong?
  • Give evidence: diagrams, metrics, test results, not opinions.
  • Run it blamelessly; the aim is better systems, not a verdict on people.
  • End with prioritized findings, each with an owner, a deadline, and a decision to fix, accept, or defer.

§2Architecture Decision Records

An ADR is a short document capturing one decision: the context, the options considered, the choice, and the consequences. It lets future engineers understand why, and decide when conditions have changed.

# ADR-014: Use SQS between checkout and fulfillment

Status: Accepted (2026-10-12)

Context: Fulfillment is slow and fails intermittently; checkout must stay fast.
Options: (1) synchronous call (2) SQS + worker (3) EventBridge
Decision: SQS with DLQ and idempotent worker.
Consequences: + decoupled, absorbs spikes  - eventual consistency, DLQ ops burden
Revisit if: more than three consumers need the event

§3Keeping It Alive

  • Store ADRs in the repository next to the code, numbered and never deleted; supersede instead.
  • Link decisions from the architecture diagram and the runbooks.
  • Revisit decisions with explicit triggers ("revisit if...").
  • Track findings to closure, with a visible list and regular follow-up.
  • Accepting a risk is a valid outcome if someone owns it and writes it down.
Write the why, not just the what Code shows what was built. Only a decision record shows what was rejected and why, which is exactly what you need when requirements change.

§4Common Mistakes

MistakeWhat HappensFix
Reviews without owners or deadlinesFindings never get fixedAssign owner and date for every finding
Undocumented decisionsRe-litigated or blindly reversed laterWrite ADRs in the repository
Reviewing only the happy pathFailures surprise youWalk through failure scenarios explicitly
Practice
  1. Write an ADR for a real architectural decision from a recent project.
  2. Run a 45-minute review of a small system and produce a prioritized findings list.
Key takeaways
  • Good reviews are evidence-based, blameless, and end in owned, dated findings.
  • ADRs capture context, options, decision, and consequences.
  • Keep records in the repository and revisit them on defined triggers.
