Event-Driven & Serverless Architecture Patterns

Event-driven systems trade the simplicity of direct calls for resilience and loose coupling, and they demand discipline about ordering, duplicates, and failure.

§1Choreography vs. Orchestration

ChoreographyOrchestration
ControlEach service reacts to eventsA central workflow directs steps
VisibilityHard to see the whole flowExplicit state machine, easy to trace
CouplingVery looseWorkflow knows the participants
AWS toolEventBridge, SNS, SQSStep Functions

Use choreography for simple fan-out, and orchestration (Step Functions) when a business process has ordering, branching, retries, compensation, and needs an audit trail.

§2Idempotency and Duplicates

Most AWS messaging is at least once, so a handler may see the same event twice. Make handlers idempotent: processing again gives the same result.

def handle(event):
    key = event['id']
    try:
        table.put_item(Item={'pk': key}, ConditionExpression='attribute_not_exists(pk)')
    except ConditionalCheckFailedException:
        return   # already processed
    do_work(event)

Powertools for AWS Lambda includes an idempotency utility built on this idea.

§3Failure Handling and Sagas

  • Give every queue a dead-letter queue and alarm on its depth.
  • Distributed workflows cannot use one transaction; use the saga pattern with compensating actions (refund the payment if shipping fails).
  • Use the transactional outbox pattern to publish events reliably alongside a database write.
  • Version event schemas and use the EventBridge schema registry; consumers must tolerate additive changes.
  • Propagate a correlation id and use X-Ray for tracing across hops.
Assume every message arrives twice If a duplicate would cause harm, the design is incomplete. Idempotency keys, conditional writes, and compensating steps are not extras; they are the architecture.

§4Common Mistakes

MistakeWhat HappensFix
Non-idempotent consumersDouble charges, duplicate emailsUse idempotency keys and conditional writes
Silent failures without DLQsLost work nobody seesDLQ plus alarms on depth
Breaking event schemasConsumers crash after a producer deployVersion and evolve schemas compatibly
Practice
  1. Model an order workflow in Step Functions with a compensating step for payment failure.
  2. Make a Lambda consumer idempotent and prove it by replaying a message.
Key takeaways
  • Choreography fits loose fan-out; orchestration fits multi-step processes.
  • At-least-once delivery requires idempotent consumers.
  • Sagas, DLQs, and schema versioning handle failure in distributed flows.
