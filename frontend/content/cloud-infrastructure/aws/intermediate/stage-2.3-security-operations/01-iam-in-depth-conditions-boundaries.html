IAM in Depth: Conditions & Boundaries

Beyond simple allow statements, IAM offers conditions, permission boundaries, and a precise evaluation order that explains every access decision.

§1How a Request Is Evaluated

  1. Everything starts as an implicit deny.
  2. An explicit Deny in any applicable policy ends the evaluation: denied.
  3. Organization SCPs and permission boundaries must allow the action, since they set the maximum.
  4. An Allow in an identity policy or resource policy is required to grant access.
  5. Session policies, when present, further limit what the session can do.

For cross-account access, both the identity policy in the caller's account and the resource policy in the target account must allow it.

§2Conditions

{
  "Effect": "Allow",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::uploads/*",
  "Condition": {
    "StringEquals": {"s3:x-amz-server-side-encryption": "aws:kms"},
    "Bool": {"aws:SecureTransport": "true"},
    "IpAddress": {"aws:SourceIp": "203.0.113.0/24"}
  }
}

Common condition keys include aws:PrincipalTag, aws:ResourceTag, aws:MultiFactorAuthPresent, aws:SourceIp, and aws:PrincipalOrgID. Tag-based conditions give you attribute-based access control that scales without a policy per team.

§3Permission Boundaries

A permission boundary is a policy attached to a user or role that defines the maximum permissions its identity policies can ever grant. It lets you delegate: developers may create roles, but only roles carrying the boundary, so they cannot grant themselves more than you allow.

Effective permissions = identity policy  ∩  permission boundary  ∩  SCP
Boundaries cap, they do not grant A boundary never gives access on its own. It only trims what other policies would allow, which is exactly why it is safe to delegate role creation under one.

Practice
  1. Write a policy requiring MFA for ec2:TerminateInstances and test it in the policy simulator.
  2. Create a role with a permission boundary and show an allowed action being blocked by it.
Key takeaways
  • Evaluation order: implicit deny, explicit deny wins, boundaries and SCPs cap, allows grant.
  • Conditions on tags, networks, encryption, and MFA make policies precise and scalable.
  • Boundaries safely delegate role creation by capping maximum permissions.
