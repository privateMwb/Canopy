API Objects, Versions & Declarative Management

Kubernetes objects are records in the API; you manage them by applying files that describe what should exist, not by issuing a chain of commands.

§1Everything Is an API Object

Pods, Deployments, Services, ConfigMaps: each is a kind of object stored through the API server. You can list every kind your cluster supports and read its documentation from the terminal.

kubectl api-resources                 # all kinds, short names, and whether namespaced
kubectl explain pod.spec.containers   # field-by-field documentation
kubectl explain deployment.spec --recursive | head -40

kubectl explain is the fastest way to remember a field name without leaving the terminal, and it matches your cluster's version exactly.

§2API Groups and Versions

The apiVersion field has the form group/version, or just version for the original "core" group.

apiVersionExample kinds
v1Pod, Service, ConfigMap, Secret, Namespace
apps/v1Deployment, StatefulSet, DaemonSet, ReplicaSet
batch/v1Job, CronJob
networking.k8s.io/v1Ingress, NetworkPolicy

Versions such as v1beta1 signal features that may change; stable APIs use plain v1. When Kubernetes removes an old version, manifests using it stop working, so a version bump is something to check when you upgrade a cluster.

§3Imperative vs. Declarative

There are two ways to work:

# Imperative: you issue steps and must remember the order
kubectl create deployment web --image=nginx
kubectl scale deployment web --replicas=3
kubectl set image deployment/web nginx=nginx:1.27

# Declarative: you keep the end state in a file and apply it
kubectl apply -f web-deployment.yaml

The declarative style wins for real work. The file is the record: it can be reviewed, stored in Git, repeated on another cluster, and re-applied after a mistake. apply compares your file with the live object and changes only the difference, so applying the same file twice is safe.

Git as the source of truth If the cluster can be rebuilt from files in a repository, you can review changes, see history, and recover from disasters. Later stages build on this idea with Helm, Kustomize, and GitOps.

§4Useful Companions to apply

kubectl diff -f web.yaml          # what would change?
kubectl get deploy web -o yaml    # the live object, including status
kubectl apply -f ./manifests/     # apply every file in a directory

§5Common Mistakes

MistakeWhat HappensFix
Mixing create/edit with applyLater applies can overwrite or conflict with manual changesPick one workflow per object, preferably apply from files
Using a removed apiVersionThe API server rejects the file after an upgradeCheck kubectl explain and release notes; update manifests before upgrading
Editing live objects with kubectl editThe change exists only in the cluster, not in GitEdit the file and re-apply
Practice
  1. Use kubectl explain to find what spec.restartPolicy of a pod accepts, then check the default.
  2. Apply a manifest, change one field in the file, run kubectl diff, then apply again.
Key takeaways
  • Every Kubernetes thing is a versioned API object with a kind and apiVersion.
  • Declarative apply from files is repeatable, reviewable, and safe to re-run.
  • kubectl explain and kubectl diff keep you out of guesswork.
