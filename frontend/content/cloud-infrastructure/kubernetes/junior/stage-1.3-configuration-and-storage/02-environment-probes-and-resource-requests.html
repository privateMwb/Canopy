Environment, Probes & Resource Requests

Probes tell Kubernetes whether a container is alive and ready, and resource requests tell the scheduler how much room a pod needs.

§1Health Probes

By default Kubernetes only knows whether a container's process is running. A probe checks something more useful. There are three kinds:

ProbeQuestion it answersWhat happens on failure
startupProbeHas the app finished starting?Container is restarted if it never passes
readinessProbeCan it serve traffic right now?Removed from Service endpoints, not restarted
livenessProbeIs it stuck beyond recovery?Container is restarted
containers:
  - name: api
    image: myorg/api:2.1
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 10
      failureThreshold: 3
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      periodSeconds: 20

Probes can be an HTTP GET, a TCP socket check, a command run inside the container (exec), or gRPC.

Keep liveness simple A liveness probe that checks the database turns a database outage into a restart storm across every replica. Liveness should answer "is this process wedged?" Use readiness for "are my dependencies available?"

§2Requests and Limits

Every container should declare how much CPU and memory it needs:

resources:
  requests:
    cpu: "250m"        # 0.25 of a CPU core
    memory: "256Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
  • Requests are what the scheduler reserves. A pod is placed only on a node with that much unreserved capacity.
  • Limits are the ceiling enforced at runtime. Exceed the memory limit and the container is killed (OOMKilled). Exceed the CPU limit and it is throttled, not killed.

CPU is measured in cores, where 1000m (millicores) is one core. Memory uses Mi and Gi (powers of two).

§3Environment Variables From the Pod Itself

The Downward API exposes pod details to the container without calling the API:

env:
  - name: POD_NAME
    valueFrom:
      fieldRef:
        fieldPath: metadata.name

If you set no requests, the scheduler assumes the pod needs nothing and may overpack a node, which later causes evictions and noisy-neighbor problems.

§4Common Mistakes

MistakeWhat HappensFix
No readiness probeTraffic reaches pods before they can serve itAdd a readiness probe that checks real ability to serve
Liveness probe too aggressiveSlow starts trigger restart loopsUse a startup probe and generous thresholds
No requests setScheduler overpacks nodes and pods get evictedSet requests from observed usage; Intermediate lessons cover tuning
Practice
  1. Add a readiness probe pointing at a path that returns 404 and observe the pod stay 0/1 Ready.
  2. Set a memory limit lower than the app needs and find OOMKilled in kubectl describe pod.
Key takeaways
  • Readiness gates traffic, liveness triggers restarts, and startup protects slow boots.
  • Requests drive scheduling; limits cap usage, with memory overuse killing the container.
  • Always set requests, and keep liveness checks narrow.
