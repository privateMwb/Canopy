Debugging a Broken Deployment

Most broken deployments fail in a few recognizable ways, and describe, logs, and events will tell you which one.

§1A Method, Not a Guess

Work from the outside in: is the pod scheduled, did the image pull, did the container start, did it stay up? Each question maps to a status and a command.

kubectl get pods                                  # status column is your first clue
kubectl describe pod <pod>                        # Events at the bottom explain most problems
kubectl logs <pod>                                # current container output
kubectl logs <pod> --previous                     # output from the last crashed run
kubectl logs <pod> -c <container>                 # a specific container
kubectl get events --sort-by=.lastTimestamp       # recent cluster activity

§2The Big Three

StatusUsual causesWhere to look
PendingNo node has enough CPU or memory; unbound PVC; taints or node selectors that match nothingdescribe pod Events: FailedScheduling with the reason
ImagePullBackOff / ErrImagePullWrong image name or tag; private registry with no pull secretdescribe pod Events: the exact pull error
CrashLoopBackOffApp crashes at startup: bad config, missing env var, failing dependency, wrong commandlogs --previous, then the exit code in describe

Other statuses to recognize: CreateContainerConfigError (a referenced ConfigMap or Secret is missing), OOMKilled with exit code 137 (memory limit exceeded), Init:Error (an init container failed), and Running but 0/1 Ready (readiness probe failing).

§3Worked Example

$ kubectl get pods
web-5d8c   0/1   ImagePullBackOff   0   2m

$ kubectl describe pod web-5d8c
...
Events:
  Warning  Failed  kubelet  Failed to pull image "myorg/web:1.4":
           manifest unknown

The message points straight at a tag that does not exist. Fix the image reference in the manifest, apply it, and the Deployment replaces the pod.

§4Looking Inside a Running Pod

kubectl exec -it <pod> -- sh
kubectl debug -it <pod> --image=busybox --target=<container>   # ephemeral debug container
kubectl port-forward <pod> 8080:8080

Minimal images often contain no shell. kubectl debug attaches a temporary container with tools next to the one you are investigating.

Read the Events first Before guessing, run kubectl describe and read the bottom. The scheduler and kubelet record why they could not do something, in plain language, and the answer is usually right there.

§5Common Mistakes

MistakeWhat HappensFix
Looking only at logsA pod that never started has no logsStart with describe; use logs once a container has run
Deleting the pod to "fix" itThe Deployment recreates the same problemChange the manifest, not the pod
Forgetting --previousYou see only the fresh restart's empty outputUse --previous for crash loops
Practice
  1. Deploy an image with a misspelled tag and diagnose it from Events alone.
  2. Deploy a container with command: ["false"], then use logs --previous and the exit code to describe what happened.
Key takeaways
  • Check status, then describe Events, then logs, in that order.
  • Pending, ImagePullBackOff, and CrashLoopBackOff each have distinct usual causes.
  • Fix the manifest, not the pod, because controllers recreate what the manifest says.
