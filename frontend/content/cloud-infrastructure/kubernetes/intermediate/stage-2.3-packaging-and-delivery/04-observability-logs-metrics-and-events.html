Observability: Logs, Metrics & Events

Observability is how you learn what a cluster and its apps are doing, built from logs, metrics, events, and the habit of knowing what normal looks like.

§1The Pillars

LogsWhat happened, in detailLoki, Elasticsearch/OpenSearch, a cloud logging service

§2Logs

Containers write to stdout and stderr, and the node keeps those logs only while the pod exists and within size limits. kubectl logs is for the present; anything you need later has to be shipped off the node. A common pattern is a DaemonSet log agent (Fluent Bit, Vector, or the OpenTelemetry Collector) that reads node log files and forwards them to central storage. Emit structured JSON logs with fields such as request ID, so they can be searched.

§3Metrics

Prometheus pulls metrics from endpoints at a regular interval. The kube-prometheus-stack Helm chart installs Prometheus, Alertmanager, Grafana, and ready-made dashboards. Sources include:

  • kube-state-metrics: the state of objects (desired vs. available replicas, pod phases).
  • node-exporter: node CPU, memory, disk, and network.
  • cAdvisor (in the kubelet): container resource use.
  • Your app: expose /metrics and describe it with a ServiceMonitor or PodMonitor.

§4Events and What to Watch

Events are short-lived records of scheduling, pulling, killing, and failing. They expire in about an hour by default, so export them if you want history.

A good starting set of signals follows the RED method for services (Rate, Errors, Duration) and the USE method for resources (Utilization, Saturation, Errors). Practical alerts for a cluster:

  • Pods in CrashLoopBackOff, or Pending for more than a few minutes.
  • Deployments whose available replicas are below desired.
  • Node NotReady, or disk and memory pressure.
  • Error rate or latency above a service-level objective.
  • Persistent volumes nearly full.
Alert on symptoms Page people when users are affected (errors, latency), not on every high CPU number. Use cause-level signals as dashboards and ticket-level alerts.

§5Common Mistakes

No application metricsYou see node health but not request healthExpose RED metrics from each service
Practice
  1. Install kube-prometheus-stack on a local cluster and find the pod CPU dashboard in Grafana.
  2. Write an alert rule that fires when a Deployment has fewer available replicas than desired for five minutes.
Key takeaways
  • Logs, metrics, traces, and events each answer different questions.
  • Log shipping and Prometheus are standard building blocks on Kubernetes.
  • Alert on symptoms users feel, using RED for services and USE for resources.
