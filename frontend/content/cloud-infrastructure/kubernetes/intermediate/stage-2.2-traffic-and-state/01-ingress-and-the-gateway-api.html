Ingress & the Gateway API

Ingress and the Gateway API route external HTTP and HTTPS traffic to Services, so many apps can share one load balancer and one set of hostnames.

§1Why Not One LoadBalancer Per App

A LoadBalancer Service creates a cloud load balancer, which costs money and gives one IP per service. HTTP routing by hostname and path, and TLS certificates, are better handled in one shared layer. That layer has two parts: rules that describe routes, and a controller that implements them.

§2Ingress

An Ingress object declares routes; an ingress controller (a pod running NGINX, HAProxy, Traefik, or a cloud load balancer integration) watches those objects and configures itself. An Ingress does nothing without a controller installed.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
spec:
  ingressClassName: nginx
  tls:
    - hosts: ["shop.example.com"]
      secretName: shop-tls
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api
                port: { number: 80 }
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port: { number: 80 }

TLS certificates are commonly issued and renewed automatically by cert-manager using Let's Encrypt.

The Ingress API is stable but limited: advanced behavior such as header matching, traffic splitting, or timeouts is expressed through controller-specific annotations that are not portable. Note also that the widely used community ingress-nginx controller was announced to be retired in 2026, so check the current status before choosing a controller for new clusters.

§3The Gateway API

The Gateway API is the newer, more expressive successor, built around roles:

ObjectOwned byPurpose
GatewayClassInfrastructure providerWhich implementation handles gateways
GatewayCluster operatorListeners: ports, protocols, TLS
HTTPRouteApplication developerHostnames, paths, headers, backends
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop
spec:
  parentRefs:
    - name: public-gateway
  hostnames: ["shop.example.com"]
  rules:
    - matches:
        - path: { type: PathPrefix, value: /api }
      backendRefs:
        - name: api
          port: 80
          weight: 90
        - name: api-canary
          port: 80
          weight: 10

Weighted backends, header matches, and redirects are part of the spec, not annotations. Gateway API CRDs are installed separately, and it also covers TCP, gRPC, and TLS routes.

Pick by need Ingress is simple and everywhere. Gateway API fits teams that want a shared gateway, delegated routing, and portable traffic features. Many clusters run both during migration.

§4Common Mistakes

MistakeWhat HappensFix
Creating an Ingress with no controllerNothing serves traffic and no address appearsInstall a controller and set ingressClassName
Backend Service name or port wrongGateway returns 502 or 404Check kubectl get endpoints and the controller's logs
Leaning on controller-specific annotationsConfig does not move between controllersPrefer Gateway API fields where they exist
Practice
  1. Install an ingress controller on a local cluster, route two paths to two Services, and test with curl -H "Host: ...".
  2. Rewrite your Ingress as an HTTPRoute and compare how a 90/10 split is expressed.
Key takeaways
  • Ingress and Gateway API describe routes; a controller implements them.
  • One shared entry point serves many apps by host and path, with TLS handled centrally.
  • Gateway API adds roles and portable features such as weighted routing.
