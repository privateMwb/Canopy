Jobs, CronJobs & DaemonSets

Jobs, CronJobs, and DaemonSets cover work that is not a long-running replicated service: tasks that finish, tasks on a schedule, and agents that run on every node.

§1Jobs in Practice

The Junior stage introduced Jobs. Production use adds more controls:

spec:
  completions: 20
  parallelism: 4
  completionMode: Indexed         # each pod receives JOB_COMPLETION_INDEX
  backoffLimit: 2
  activeDeadlineSeconds: 3600     # fail the whole Job after an hour
  ttlSecondsAfterFinished: 86400

Indexed Jobs hand each pod a unique index, so a pod can pick its own slice of data without a work queue. activeDeadlineSeconds is a hard time limit; backoffLimit caps retries; backoffLimitPerIndex retries each index separately on newer clusters.

§2CronJobs in Practice

spec:
  schedule: "*/15 * * * *"
  timeZone: "Europe/Berlin"       # without it, the controller's time zone is used
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 300
  suspend: false

Handy operations:

kubectl create job manual-run --from=cronjob/nightly-cleanup   # trigger one now
kubectl patch cronjob nightly-cleanup -p '{"spec":{"suspend":true}}'

If a CronJob misses too many runs (for example, the controller was down), it may stop scheduling and log an error; startingDeadlineSeconds bounds how far back it looks.

§3DaemonSets

A DaemonSet runs one pod on every node (or on a chosen subset). New nodes get a pod automatically, and removed nodes lose theirs.

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-agent
spec:
  selector:
    matchLabels: { app: log-agent }
  template:
    metadata:
      labels: { app: log-agent }
    spec:
      tolerations:
        - operator: Exists          # run even on tainted nodes
      containers:
        - name: agent
          image: fluent/fluent-bit:3.0
          volumeMounts:
            - name: varlog
              mountPath: /var/log
              readOnly: true
      volumes:
        - name: varlog
          hostPath: { path: /var/log }

Typical uses are log shippers, metrics exporters, node-level networking (CNI plugins), storage drivers, and security agents. Limit them with nodeSelector or affinity. DaemonSet updates roll out node by node under updateStrategy with maxUnavailable.

ControllerRunsTypical workload
DeploymentN interchangeable replicasStateless services
StatefulSetN pods with identity and storageDatabases, brokers
Job / CronJobUntil success, once or on a scheduleBatch, reports, cleanup

Agents consume every node A DaemonSet's requests are paid on all nodes. A heavy agent on fifty nodes is fifty heavy pods, so size them carefully.

§4Common Mistakes

MistakeWhat HappensFix
Skipping startingDeadlineSeconds and a concurrency policyRuns pile up after downtime or overlapSet both deliberately
DaemonSet missing tolerationsIt skips tainted nodes, leaving gaps in logging or security coverageAdd tolerations for the taints you want covered
Heavy per-node agentsLarge cost across every nodeSet tight requests and measure
Practice
  1. Create an Indexed Job where each pod prints its index.
  2. Deploy a DaemonSet and confirm one pod per node with kubectl get pods -o wide.
Key takeaways
  • Indexed Jobs and deadlines make batch work controllable.
  • CronJobs need a time zone, concurrency policy, and a deadline.
  • DaemonSets place one pod per node for agents and node-level services.
