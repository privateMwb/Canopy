Vertical Scaling, Node Autoscaling & Right-Sizing

Pod autoscaling and node autoscaling solve different problems, and right-sizing requests is what makes both of them effective.

§1The Layers of Scaling

LayerToolWhat it changes
Pod countHPANumber of replicas
Pod sizeVertical Pod Autoscaler (VPA)CPU and memory requests of each pod
Node countCluster Autoscaler or KarpenterNumber (and kind) of machines

They stack: the HPA adds pods, pods that do not fit become Pending, and the node autoscaler adds machines to host them.

§2Vertical Pod Autoscaler

VPA is an add-on that observes usage and recommends, or applies, better requests.

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: web
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  updatePolicy:
    updateMode: "Off"        # recommend only; "Auto" applies changes

In Auto mode VPA traditionally restarts pods to apply new values, though newer Kubernetes releases add in-place pod resizing in some setups. Do not let an HPA and VPA both act on the same CPU or memory metric; they will fight. A common safe pattern is VPA in recommendation mode, or VPA on memory with HPA on a custom metric.

§3Node Autoscaling

  • The Cluster Autoscaler adds nodes when pods are Pending due to insufficient resources, and removes nodes that stay underused, working with pre-defined node groups.
  • Karpenter (on AWS, with other providers emerging) chooses instance types directly based on pending pod requirements, which can pack workloads more tightly and react faster.
  • Managed modes like GKE Autopilot take over node management entirely.

Scale-down is where waste hides. Nodes with pods that cannot move (local storage, restrictive PDBs, system pods without budgets) are not removed.

§4Right-Sizing

Right-sizing means setting requests close to what workloads really use over time.

kubectl top pods -n shop --containers
# compare against requests; check a week of Prometheus data, not one moment

A request far above usage wastes capacity; one below usage causes throttling and evictions. Look at percentiles (for example p95) over days, include peak periods, and revisit after major releases. Recommendations from VPA in Off mode are a good data source.

Autoscaling amplifies bad requests If every pod requests twice what it needs, the node autoscaler happily buys twice the machines. Fix sizing first, then trust the scalers.

§5Common Mistakes

MistakeWhat HappensFix
HPA and VPA both scaling on CPUThey oscillate against each otherUse VPA recommendations only, or split metrics between them
Copying requests from a template and never revisitingLarge, silent over-provisioningReview usage versus requests on a schedule
Expecting nodes to scale instantlyPods stay Pending for minutes during a spikeKeep headroom, or use overprovisioning pods
Practice
  1. Run VPA in Off mode on a test workload and compare its recommendation with your current requests.
  2. Explain why a pod with a restrictive PDB might stop a node from being removed.
Key takeaways
  • HPA scales pod count, VPA scales pod size, and node autoscalers scale machines.
  • Do not let two autoscalers drive the same metric.
  • Right-sized requests, based on real data, make every layer of scaling cheaper and more accurate.
