Blue-Green & Canary Rollouts

Blue-green and canary releases expose a new version gradually or in parallel, so a bad release is caught and reversed before it reaches everyone.

§1Why Go Beyond Rolling Updates

A rolling update replaces pods gradually, but it has no opinion about whether the new version is *good*. It only waits for readiness. Progressive delivery adds a decision: send a controlled share of real traffic to the new version, measure, then proceed or reverse.

§2Blue-Green

Run two full environments: blue (current) and green (new). Test green while no users see it, then flip traffic all at once by switching a selector or route.

# Switch the Service from blue to green by changing one selector
kubectl patch service web -p '{"spec":{"selector":{"app":"web","version":"green"}}}'
ProsCons
Instant switch and instant rollbackNeeds double capacity during the release
Green can be fully tested firstAll users move at once; no gradual evidence
Simple to understandDatabase changes must work with both versions

§3Canary

Send a small percentage of traffic to the new version, watch metrics, then increase.

Without extra tools, a crude canary uses replica ratios behind one Service: 9 stable pods and 1 canary pod give roughly 10% to the canary. For precise weights, use traffic-aware routing: a Gateway API HTTPRoute with weighted backends, an ingress controller's canary feature, or a service mesh.

§4Argo Rollouts and Flagger

These controllers automate the process. Argo Rollouts replaces Deployment with a Rollout object:

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: web
spec:
  replicas: 10
  strategy:
    canary:
      steps:
        - setWeight: 10
        - pause: { duration: 5m }
        - analysis:
            templates:
              - templateName: error-rate
        - setWeight: 50
        - pause: { duration: 10m }

The analysis step queries Prometheus (or another provider) and aborts and rolls back automatically when a metric such as error rate crosses a threshold. Flagger offers a similar loop on top of a Deployment and an existing mesh or ingress.

§5Deciding When to Roll Back

Define in advance what bad looks like: error rate above a number, p99 latency above a limit, a drop in a business metric. Compare canary to baseline, not to an absolute number, to account for normal daily variation.

A canary only protects you if you watch it Traffic percentage without automated analysis is just a slower outage. Wire the rollback to metrics.

§6Common Mistakes

MistakeWhat HappensFix
Canary with no success criteriaNobody knows whether to proceedDefine metrics and thresholds before starting
Incompatible database changesOld and new versions break each otherMake schema changes backward compatible, in separate steps
Judging a canary on too little trafficNoise looks like a signalUse sufficient traffic and duration, and compare to baseline
Practice
  1. Implement a blue-green switch with two Deployments and one Service, and flip back.
  2. Write down three metrics and thresholds that would automatically abort a canary for your service.
Key takeaways
  • Blue-green flips whole environments; canaries shift traffic in measured steps.
  • Argo Rollouts and Flagger automate analysis and rollback.
  • Releases need predefined success criteria and compatible data changes.
