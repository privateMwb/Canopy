Configuration Patterns & Secret Rotation

Changing configuration and credentials safely means treating config as versioned input to a rollout, and having a way to rotate secrets without downtime.

§1Config Changes Do Not Restart Pods

Updating a ConfigMap or Secret does not restart pods that read it through environment variables, and file-based updates only help if the app rereads files. Left alone, different pods can end up running different effective configuration.

§2Pattern 1: Immutable, Versioned Config

Treat config like an image: a change creates a new object with a new name, and the Deployment references it, which triggers a normal rolling update.

configMapGenerator:           # Kustomize appends a content hash to the name
  - name: app-config
    files: [app.properties]

The rendered name looks like app-config-7k9d2h5f4m. Changing the file changes the name, which changes the pod template, which rolls the Deployment. A bad config rolls back exactly like a bad image. Setting immutable: true on ConfigMaps and Secrets enforces this.

§3Pattern 2: Checksum Annotation (Helm)

template:
  metadata:
    annotations:
      checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}

When the ConfigMap content changes, the annotation changes, and pods restart.

§4Pattern 3: Reloaders

Stakater Reloader watches ConfigMaps and Secrets and triggers a rollout of workloads that use them. Some apps can reload their own config on a signal or by watching mounted files, which avoids restarts for settings that can change live.

§5Rotating Secrets

Rotation is the regular replacement of a credential. Do it without downtime:

  1. Store secrets in an external system (Vault, AWS Secrets Manager, and similar) and sync them with External Secrets Operator or the Secrets Store CSI Driver, which can refresh on an interval.
  2. For credentials a service accepts only one of, use a dual-credential window: add the new credential, deploy consumers using it, then revoke the old one.
  3. Prefer short-lived, dynamically issued credentials where possible, such as database users generated per pod, or cloud identity instead of static keys.
  4. Roll the workloads (via a reloader or a controlled restart) when the app reads secrets only at startup.
kubectl rollout restart deployment/web          # a manual forced rollout
kubectl rollout status deployment/web
Make rotation boring A credential you can only rotate during an outage will never be rotated. Practice it on a schedule so that an emergency rotation is routine.

§6Common Mistakes

MistakeWhat HappensFix
Editing a ConfigMap and assuming pods updatedPods run stale values until restartUse hashed names, checksum annotations, or a reloader
Revoking the old secret before consumers switchInstant outageUse an overlap window and verify before revoking
Secrets that never expireA leak remains valid indefinitelyRotate regularly and prefer short-lived credentials
Practice
  1. Use a Kustomize configMapGenerator, change a value, and watch the Deployment roll.
  2. Write a numbered procedure for rotating a database password with no downtime.
Key takeaways
  • Config changes should trigger rollouts through versioned names or checksums.
  • Reloaders and live-reload apps handle changes without manual restarts.
  • Rotate secrets with an overlap window and short-lived credentials.
