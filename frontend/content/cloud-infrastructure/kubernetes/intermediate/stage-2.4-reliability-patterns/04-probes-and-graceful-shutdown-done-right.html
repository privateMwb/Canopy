Probes & Graceful Shutdown Done Right

Readiness, liveness, and startup probes control traffic and restarts, and graceful shutdown makes sure terminating pods finish their work instead of dropping requests.

§1Using the Three Probes Well

ProbeUse it toTypical mistake
startupProbeAllow slow starts without loosening other probes; others wait until it succeedsOmitting it and raising initialDelaySeconds everywhere
readinessProbeControl whether the pod receives trafficChecking too little, so unready pods get traffic
livenessProbeRestart a wedged processChecking dependencies, causing restart cascades
startupProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 5
  failureThreshold: 30          # allows up to 150 seconds to start
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
  failureThreshold: 2
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3

Make /ready reflect whether the app can serve right now (warmed caches, connections up, not overloaded). Make /healthz cheap and internal only.

§2What Happens on Termination

When a pod is deleted, two things occur at roughly the same time:

  1. The pod is removed from Service endpoints, and proxies and load balancers learn this gradually.
  2. The container receives SIGTERM.

Because step 1 takes time to propagate, the app may still receive new requests after SIGTERM. If it exits immediately, those requests fail. This race is the cause of many errors seen during deployments.

§3A Graceful Shutdown Recipe

spec:
  terminationGracePeriodSeconds: 45
  containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: ["sleep", "10"]     # keep serving while endpoints update

In the application, on SIGTERM:

  1. Stop accepting new connections and fail the readiness check.
  2. Finish in-flight requests (with a timeout).
  3. Close connections to databases and queues, flush buffers.
  4. Exit with code 0.

Timing must fit inside terminationGracePeriodSeconds: the preStop sleep plus the app's drain time. If time runs out, SIGKILL arrives.

§4Common Traps

  • A shell-form CMD or a wrapper script that does not forward signals, so the app never sees SIGTERM. Use exec in scripts and the exec form in Dockerfiles.
  • Long-lived connections (WebSockets, streams) need a deliberate drain strategy, such as telling clients to reconnect.
  • Rolling updates with maxUnavailable: 0 plus correct readiness and shutdown gives zero-downtime deploys.
Test it under load Run a load generator while you roll out a new version. Dropped requests during the rollout point to probe or shutdown problems that a quiet test never shows.

§5Common Mistakes

MistakeWhat HappensFix
Liveness probe that checks the databaseA database blip restarts every podKeep liveness internal; put dependencies in readiness
Exiting immediately on SIGTERMIn-flight and just-routed requests failDrain, with a short preStop delay for endpoint propagation
Signals not reaching the appThe pod is always force-killed after the grace periodUse exec-form entrypoints and exec in wrapper scripts
Practice
  1. Roll out a Deployment while running a constant stream of requests and count errors, then add preStop and a drain handler and compare.
  2. Verify your app receives SIGTERM by logging it, and fix any wrapper script that hides it.
Key takeaways
  • Startup, readiness, and liveness probes each have a distinct job; keep liveness narrow.
  • Endpoint removal and SIGTERM race, so delay shutdown briefly and drain gracefully.
  • Test deployments under load to confirm zero dropped requests.
