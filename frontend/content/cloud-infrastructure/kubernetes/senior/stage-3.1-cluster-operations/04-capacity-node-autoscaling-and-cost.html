Capacity, Node Autoscaling & Cost

Capacity planning is about packing pods onto nodes efficiently and adding or removing nodes at the right moments, which is where most of a cluster's money is won or lost.

§1Allocatable, Not Capacity

A node's capacity is its raw CPU and memory. Its allocatable amount is what remains after reserving space for the OS, the kubelet, the runtime, and the eviction threshold.

kubectl describe node worker-1
# Capacity:     cpu: 4   memory: 16Gi
# Allocatable:  cpu: 3920m  memory: 14.7Gi
# Allocated resources:  cpu 3100m (79%)  memory 9Gi (62%)

The scheduler fills nodes by requests against allocatable. When one resource runs out first (often CPU), the other is stranded, which is fragmentation. Choosing node shapes whose CPU-to-memory ratio matches your workloads reduces stranding.

§2Bin Packing and Node Sizing

  • Big nodes waste less on per-node overhead (daemons, system reservations) and pack large pods well, but a single node failure affects more pods, and each upgrade drain moves more.
  • Small nodes limit the blast radius and scale in finer steps, but overhead is a larger share and large pods may not fit.
  • Mixing pod sizes on a uniform node type tends to waste more than a few node pools tuned to workload classes.

Scheduler scoring can be tuned (for example, favor MostAllocated to pack tightly on autoscaled clusters, versus the default spreading behavior), which lets the autoscaler remove emptied nodes.

§3Scaling Nodes

  • Cluster Autoscaler works against fixed node groups: it adds a node when a pod is Pending for lack of resources and removes nodes that are underused for some time (default around ten minutes), after checking that their pods can move elsewhere.
  • Karpenter and similar provisioners look at pending pods directly, choose a fitting instance from many types, and consolidate workloads onto fewer or cheaper nodes.
  • Scale-down is blocked by pods with local storage, restrictive PDBs, anti-affinity that cannot be satisfied elsewhere, or the annotation cluster-autoscaler.kubernetes.io/safe-to-evict: "false".

§4Headroom and Overprovisioning

A new node takes minutes to appear, so a spike can leave pods Pending. Keep headroom by running low-priority "placeholder" pods that reserve capacity:

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: overprovisioning
value: -10          # lower than any real workload

Real pods preempt the placeholders instantly, and the displaced placeholders go Pending, which triggers the autoscaler to add nodes in the background.

§5Finding Waste

  • Compare requested to used resources per workload and per node.
  • Look for nodes with low allocation that cannot be consolidated.
  • Use spot or preemptible capacity for interruption-tolerant workloads, with correct tolerations, PDBs, and graceful termination.
  • Watch for zone imbalance and cross-zone traffic costs.
  • Set ResourceQuota and LimitRange so no team can request unlimited resources.
Efficiency is a product of three things Request accuracy (what pods ask for), packing (how well nodes are filled), and node pricing (instance choice and commitments). Improving only one leaves the others as the bottleneck.

§6Common Mistakes

MistakeWhat HappensFix
Planning from capacity instead of allocatableOverestimates what fitsPlan from allocatable minus headroom
Autoscaler blocked by unmovable podsIdle nodes stay foreverReview blockers and set PDBs and eviction annotations deliberately
Spot nodes for stateful or critical podsSudden interruption causes outagesUse spot only for tolerant, replicated workloads
Practice
  1. Compute requested versus allocatable for each node in a cluster and identify the most stranded resource.
  2. Design an overprovisioning setup that keeps 10% headroom and explain what happens during a spike.
Key takeaways
  • Plan with allocatable resources and match node shapes to workload ratios.
  • Cluster autoscalers add nodes for Pending pods and remove underused ones, subject to blockers.
  • Overprovisioning, spot capacity, and request accuracy together control cost without hurting availability.
