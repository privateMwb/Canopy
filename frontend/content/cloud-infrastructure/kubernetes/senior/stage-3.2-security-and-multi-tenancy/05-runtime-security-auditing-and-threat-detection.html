Runtime Security, Auditing & Threat Detection

Prevention eventually fails, so clusters also need records of what happened, monitoring of what workloads actually do, and the ability to recognize a compromised pod.

§1Audit Logs

The API server can record who did what to which object. An audit policy sets how much detail each request gets:

LevelRecords
NoneNothing
MetadataUser, verb, resource, and timing, without bodies
RequestMetadata plus the request body
RequestResponseMetadata, request, and response bodies
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
  - level: None
    users: ["system:kube-proxy"]
  - level: Metadata
    resources:
      - group: ""
        resources: ["secrets", "configmaps"]    # never log secret bodies
  - level: RequestResponse
    resources:
      - group: "rbac.authorization.k8s.io"
  - level: Metadata                               # default for everything else

Managed services expose audit logs through their cloud logging. Ship them off the cluster, and alert on high-value events: exec or attach into pods, creation of privileged pods, changes to RBAC, access to Secrets by unexpected identities, and use of system:masters.

§2Runtime Security

Admission checks a pod's declaration; runtime tools watch behavior. They use kernel features (eBPF, syscall tracing) to see what processes actually do.

ToolWhat it does
FalcoRules over syscalls and Kubernetes audit events, such as "shell spawned in a container" or "write below /etc"
Tetragon / CiliumeBPF-based observability and optional enforcement of process, file, and network behavior
seccompRestricts which system calls a container may make; RuntimeDefault is a good baseline
AppArmor / SELinuxMandatory access control profiles for files and capabilities

Typical detections:

  • An interactive shell in a production container.
  • A process reading /var/run/secrets/kubernetes.io/serviceaccount and calling the API unexpectedly.
  • Outbound connections to unusual addresses, or crypto-mining behavior.
  • Writes to binaries or package manager use inside a running container (read-only root filesystems make this fail).

§3Spotting a Compromised Pod

Signs: unexpected network connections, new processes, CPU spikes, files created in odd places, and API calls from a workload that never used the API. A response plan:

  1. Isolate: apply a deny-all NetworkPolicy or a quarantine label, rather than deleting immediately, so evidence survives.
  2. Capture: preserve logs, record the image digest, and snapshot the pod's filesystem or node as your tooling allows.
  3. Contain scope: revoke the ServiceAccount's permissions and rotate any credentials the pod could read.
  4. Remove and rebuild: replace the workload from a known-good image, and fix the entry point.
  5. Review: use audit logs to see what the identity did, then run a blameless postmortem.
Layers, not a single wall Admission lowers the chance of a bad pod; read-only filesystems, dropped capabilities, and network policy limit the damage; audit and runtime detection tell you when the first three failed.

§4Common Mistakes

MistakeWhat HappensFix
No audit logging, or logs kept only on the nodeAn attacker erases evidence and you cannot reconstruct eventsShip audit logs off-cluster to write-once storage
Logging Secret request bodiesThe audit log becomes a credential leakUse Metadata level for secrets
Deleting a suspect pod immediatelyEvidence is lostIsolate with network policy, capture, then remove
Practice
  1. Write three Falco-style rules in plain words for behavior that should never happen in your production pods.
  2. Draft an audit policy that records Secret access at Metadata and RBAC changes at RequestResponse.
Key takeaways
  • Audit logs record API activity; set levels carefully and ship them off the cluster.
  • Runtime tools such as Falco and Tetragon detect behavior that admission cannot see.
  • Respond to compromise by isolating, capturing evidence, revoking identity, and rebuilding.
