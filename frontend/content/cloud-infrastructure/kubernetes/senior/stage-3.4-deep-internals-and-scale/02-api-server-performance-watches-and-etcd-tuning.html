API Server Performance, Watches & etcd Tuning

At scale, cluster slowness usually traces to what clients ask of the API server and how etcd handles it, so you measure and then tune.

§1What Makes a Large Cluster Slow

Control plane load scales with objects (how many), watchers (how many clients are listening), and churn (how fast things change). Typical culprits:

  • A controller or script listing all pods or secrets repeatedly rather than using a watch or informer.
  • Thousands of Services causing large EndpointSlice and kube-proxy churn.
  • Large objects (huge ConfigMaps or CRDs) and frequent updates to them.
  • A flood of events or status updates from a misbehaving operator.
  • etcd on slow disks, or a database near its size quota.

§2The API Server's Mechanics

  • The watch cache serves most reads and watches from memory, protecting etcd. Reads with certain consistency options bypass it, which is more expensive.
  • resourceVersion semantics matter: a list with resourceVersion=0 can be served from cache (possibly stale), while a "most recent" read goes to etcd.
  • Pagination (limit and continue) bounds the size of list responses, and newer versions can stream initial state for watches rather than build one giant list.
  • API Priority and Fairness (APF) classifies requests into priority levels and flow queues, so one noisy client cannot starve system components. Throttled requests return HTTP 429.

§4Tuning etcd

  • Fast dedicated SSDs and low network latency between members.
  • Compaction (automatic, by revision or time) and occasional defragmentation to reclaim space; a defrag blocks the member briefly, so do it one member at a time.
  • Keep the database well under its quota, and raise the quota deliberately rather than as a first response.
  • Consider separating events into their own etcd cluster in very large deployments.

§5Reducing Load

  • Make clients use informers, field and label selectors, and pagination.
  • Prefer EndpointSlices and reduce churn from frequently flapping pods.
  • Set sensible TTLs for Jobs and clean up old objects.
  • Scale the API server horizontally, and give heavy controllers their own APF flow schema.
  • Split very large clusters when per-cluster limits (objects, nodes, pods) are approached, since published scalability thresholds guide what is tested and supported.
Measure before tuning Find the slow verb and resource, then find the client responsible, then fix the client. Raising limits on the server usually hides the problem for a while and makes it worse later.

§6Common Mistakes

MistakeWhat HappensFix
Raising API server limits to fix slownessThe noisy client keeps growing and hurts everyoneIdentify the client and fix its access pattern
Never defragmenting or compacting etcdThe database hits its quota and writes stopEnable auto-compaction, defragment on schedule, alert on size
Running etcd on shared network disksHigh fsync latency destabilizes leader electionUse local SSDs and monitor fsync p99
Practice
  1. Find the top three request types by latency in a cluster's API server metrics.
  2. Describe how an operator that lists all Secrets every second would affect the API server and etcd.
Key takeaways
  • Large-cluster pain is usually objects, watchers, and churn, concentrated in a few clients.
  • The watch cache, pagination, and API Priority and Fairness protect the control plane.
  • Measure request latency, etcd fsync, and object counts before changing any limit.
