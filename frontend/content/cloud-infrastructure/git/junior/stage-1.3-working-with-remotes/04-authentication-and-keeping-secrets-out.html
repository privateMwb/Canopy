Authentication & Keeping Secrets Out

Hosting sites need proof of who you are, and the safest habit is to use SSH keys or tokens and keep secrets out of your repository entirely.

§1Two Ways to Authenticate

Hosts no longer accept account passwords for Git operations. The two common options:

MethodHow it worksURL form
SSH keyA key pair: the private key stays on your machine, the public key is registered with the hostgit@github.com:me/repo.git
HTTPS + tokenA personal access token acts as the password; a credential helper stores ithttps://github.com/me/repo.git
ssh-keygen -t ed25519 -C "ada@example.com"   # create a key pair
cat ~/.ssh/id_ed25519.pub                       # copy this public key to the host
ssh -T git@github.com                           # test the connection
git config --global credential.helper store     # or use your OS keychain helper

Never share the private key (the file without .pub). Protect it with a passphrase and use an agent so you type it once per session. Give tokens the minimum permissions they need and set an expiry.

§2Keeping Secrets Out of Git

Passwords, API keys, tokens, and private keys must not be committed. History is permanent: deleting the file in a later commit does not remove it from earlier ones, and anyone with the repository can recover it. Keep secrets in environment variables or a secrets manager, and list local files such as .env in .gitignore.

echo ".env" >> .gitignore
git add .gitignore && git commit -m "Ignore local environment file"
git status                                       # confirm .env is not listed

§3If You Commit a Secret

Assume it is compromised the moment it is pushed. In order:

  1. Revoke and rotate the credential at its provider immediately. This is the step that actually fixes the problem.
  2. Remove it from the current code and load it from the environment.
  3. Optionally rewrite history to remove it (an advanced task, covered in the Senior level), though the rotated secret is already safe.
Rotate first, clean up second Rewriting history does not un-leak a secret: bots scrape public pushes within minutes, and others may already have cloned it. Rotating makes the old value worthless, and that is what protects you.

§4Common Mistakes

MistakeWhat HappensFix
Committing a .env or key fileCredentials are exposed permanently in historyIgnore secret files from the start; rotate if one leaks
Deleting the secret in a later commit and moving onIt remains in every earlier commitRevoke and rotate the credential first
Sharing or emailing the private SSH keyAnyone with it can act as youShare only the .pub file; generate a new key if exposed
Practice
  1. Generate an ed25519 key, register the public key with a host, and verify with ssh -T.
  2. Add .env and *.pem to a .gitignore and prove with git status that a sample file of each type is ignored.
Key takeaways
  • Use SSH keys or tokens, and keep private keys and tokens private.
  • Never commit secrets; keep them in the environment and ignored files.
  • If a secret is committed, rotate it first; deleting it from history is secondary.
