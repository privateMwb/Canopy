Pull Requests & Code Review

A pull request proposes merging your branch into another and gives teammates a place to review it, so learning to open, give, and respond to review is a core team skill.

§1The Basic Flow

A pull request (PR; called a merge request on GitLab) is a feature of the hosting site, not of Git itself. It asks, "please review and merge my branch." The standard cycle:

git switch -c fix/empty-cart
# ...edit, test, commit...
git push -u origin fix/empty-cart
# open the pull request in the browser, base: main, compare: fix/empty-cart
# reviewers comment; you push more commits to the same branch
# approve, then merge

Pushing more commits to the branch updates the open PR automatically, so there is no need to open a new one.

§2Writing a Good Pull Request

  • A clear title that reads like a commit subject
  • A description of what changed and why, plus how to test it
  • A link to the issue it addresses
  • A small change: reviewers read 200 lines carefully and 2,000 lines barely at all

§3Giving and Receiving Review

As a reviewer, read the intent first, then the code; ask questions rather than issue commands; separate must-fix problems from preferences ("nit: ..."); and say what is good as well as what is wrong. As an author, respond to every comment, push fixes as new commits, and thank people for catching things. Disagree with reasons, not with defensiveness.

Merge optionResulting history
Merge commitKeeps all commits plus a merge commit
Squash and mergeCollapses the PR into one commit on the target
Rebase and mergeReplays the commits as a straight line
Review the change, not the person Comments should describe the code and its effects ("this loop can skip the last item"), never the author. A review culture that feels safe catches more bugs.

§4Common Mistakes

MistakeWhat HappensFix
Opening one giant PR with many unrelated changesSlow, shallow reviews and hard revertsKeep each PR to one purpose and a reviewable size
Force-pushing during review without saying soReviewers lose track of what changedPush new commits, or announce any history rewrite
Leaving the description emptyReviewers must guess the intentExplain what, why, and how to verify
Practice
  1. Open a pull request in a practice repository with a proper description, then merge it using the squash option.
  2. Review a partner's PR with two questions, one "nit", and one genuine praise comment.
Key takeaways
  • A pull request is a hosted conversation about merging one branch into another.
  • Small PRs with clear descriptions get faster, better reviews.
  • Critique the code, respond to every comment, and push fixes to the same branch.
