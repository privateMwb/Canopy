Rebase vs. Merge

Rebasing replays your commits on a new base to produce straight-line history, and merging preserves what actually happened; choosing between them is mostly about shared versus private branches.

§1What Rebase Does

git rebase takes the commits unique to your branch, sets them aside, moves the branch to a new base, and replays them one by one. The replayed commits have the same changes but are new commits with new IDs, since their parent changed.

Before:   A---B---C   <- main
               \
                D---E   <- feature

git switch feature
git rebase main

After:    A---B---C   <- main
                   \
                    D'--E'   <- feature   (new commits, same changes)

After the rebase, merging feature into main is a clean fast-forward and the history is one straight line.

§2Merge vs. Rebase

MergeRebase
HistoryPreserves true branching and timingLinear and tidy; rewrites commits
Commit IDsUnchangedChanged for every replayed commit
ConflictsResolved once, in the merge commitMay need resolving at each replayed commit
Safe on shared branchesYesNo
TraceabilityMerge commit shows where work joinedContext of the original branch is lost

§3The Golden Rule

Never rebase commits that other people have already based work on. Rewriting published commits gives teammates duplicated and diverging histories to untangle. Rebasing your own private branch is safe, and you may need --force-with-lease to update your own remote copy afterward.

git fetch origin
git rebase origin/main            # update my branch onto the latest main
git rebase --continue            # after resolving a conflict in the middle
git rebase --abort               # back to exactly where I started
git push --force-with-lease      # update my own branch; refuses if someone else pushed
A common team policy Rebase your own local branch freely to keep it current and clean. Merge, or squash-merge, into shared branches. You get tidy pull requests without rewriting history others depend on.

§4Common Mistakes

MistakeWhat HappensFix
Rebasing a branch teammates have pulledDuplicate commits and painful divergence for everyoneRebase only private work; merge shared branches
Using plain --force after a rebaseOverwrites commits someone else pushed to that branchUse --force-with-lease, which checks first
Rebasing main onto a feature branchRewrites shared history upside downAlways rebase the feature onto main, never the reverse
Practice
  1. Build a feature branch that has fallen behind main, then bring it up to date once with merge and once with rebase (resetting in between), and compare the graphs.
  2. Cause a conflict during a rebase, resolve it, continue, and then try once more and abort with git rebase --abort.
Key takeaways
  • Rebase replays commits as new ones on a new base; merge preserves history as it happened.
  • Never rebase commits that others already depend on.
  • After rebasing a pushed private branch, update it with --force-with-lease.
