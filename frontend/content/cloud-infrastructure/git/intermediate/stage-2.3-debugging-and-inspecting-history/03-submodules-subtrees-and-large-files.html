Submodules, Subtrees & Large Files

Git offers several ways to include other repositories and to handle big binaries, each with trade-offs worth knowing before you commit to one.

§1Submodules: A Pinned Pointer

A submodule embeds another repository at a path. Your repository stores only a pointer to a specific commit of it, plus a .gitmodules file. The dependency stays a separate repository with its own history.

git submodule add https://github.com/org/lib.git vendor/lib
git commit -m "Add lib as a submodule"
git clone --recurse-submodules <url>           # clone including submodules
git submodule update --init --recursive        # fix a clone that lacks them
git submodule update --remote vendor/lib       # move the pointer to the latest upstream

The usual gotcha: updating a submodule changes your pointer, so you must commit the new pointer and push the submodule's own commits first, or teammates will not be able to fetch that commit.

§2Subtrees: Copy With History

A subtree merges another repository's content into a folder of your own history. Clones need no special steps, which is its main advantage over submodules, at the cost of a larger history and less obvious boundaries.

git subtree add --prefix=vendor/lib https://github.com/org/lib.git main --squash
git subtree pull --prefix=vendor/lib https://github.com/org/lib.git main --squash
git subtree push --prefix=vendor/lib <lib-remote-url> my-change

§3Large Files

Git stores every version of every file forever, so large binaries such as videos, datasets, and design files bloat every clone. Git LFS keeps small pointer files in Git and stores the real content on a separate server.

git lfs install
git lfs track "*.psd" "*.mp4"      # writes rules to .gitattributes
git add .gitattributes
git lfs ls-files                  # what LFS is managing
OptionBest whenCost
SubmoduleYou need an exact, separate, versioned dependencyExtra commands and easy mistakes
SubtreeYou want a simple clone and rarely edit the vendored codeLarger history
Package managerA library has releasesUsually the best choice; no repo embedding at all
Git LFSLarge binaries that changeNeeds server support; history already containing big files needs rewriting
Prefer a package manager when you can If the dependency publishes releases, npm, pip, Maven, or similar is usually simpler than submodules or subtrees. Embed repositories only when you truly need their source at an exact commit.

§4Common Mistakes

MistakeWhat HappensFix
Cloning without --recurse-submodulesEmpty submodule folders and broken buildsUse the flag, or run git submodule update --init --recursive
Moving a submodule pointer without pushing the submoduleTeammates cannot fetch the referenced commitPush the submodule first, then commit the new pointer
Committing a large binary directlyEvery clone downloads it foreverTrack it with Git LFS before the first commit
Practice
  1. Add a small public repository as a submodule, clone your project fresh with --recurse-submodules, and verify the files appear.
  2. Configure Git LFS for *.zip files in a practice repository and verify with git lfs ls-files.
Key takeaways
  • A submodule pins another repository at an exact commit; subtrees copy it into your history.
  • Push a submodule's commits before committing the new pointer to it.
  • Use Git LFS for large binaries, and prefer package managers for libraries.
