Bisect: Finding the Commit That Broke It

git bisect binary-searches history to find the exact commit that introduced a bug, taking a handful of steps even across thousands of commits.

§1The Idea

If a bug exists now but did not in an older version, the culprit commit is somewhere between them. Bisect checks out the midpoint and asks whether the bug is present, halves the range each time, and finishes in about log2(N) steps: roughly 10 tests for 1,000 commits.

§2Manual Bisect

git bisect start
git bisect bad                  # the current commit is broken
git bisect good v2.3.0         # this old tag was fine
# Git checks out a commit in the middle. Build, test, then report:
git bisect good                # or: git bisect bad
# ...repeat until Git prints: a1b2c3d is the first bad commit
git bisect log                 # the record of your answers
git bisect reset               # return to where you started

Use git bisect skip when a midpoint cannot be tested, for example because it does not build for an unrelated reason.

§3Automated Bisect

If you can write a script that exits 0 when the code is good and 1 to 127 (except 125) when it is bad, Git runs the whole search for you.

git bisect start HEAD v2.3.0
git bisect run ./test-bug.sh          # or: git bisect run npm test -- search.test.js
# ...Git reports the first bad commit with no further input
git bisect reset
#!/bin/sh
# test-bug.sh: exit 0 = good, 1 = bad, 125 = cannot test, skip
make build >/dev/null 2>&1 || exit 125
./run-checkout-test || exit 1

§4Making Bisect Work Well

  • It depends on atomic, buildable commits; a commit that fails to build wastes steps
  • A reproducible test is everything: write the failing test first, then bisect
  • Bisect finds the commit, but you still need the commit message and diff to understand the cause
Automate the question The fastest bisects are the automated ones. Writing a small script that reproduces the bug is useful anyway, because it later becomes your regression test.

§5Common Mistakes

MistakeWhat HappensFix
Marking a commit good or bad by guessworkThe search converges on a wrong commitTest each step with the same reproducible check
Forgetting git bisect resetYou stay on a detached, old commitAlways reset to return to your branch
Bisecting a history full of broken buildsMany skipped steps and an ambiguous resultKeep commits buildable; use skip or 125 for unbuildable ones
Practice
  1. In a practice repository, deliberately introduce a bug in the middle of twenty commits, and find it with manual bisect.
  2. Write a script and repeat the search with git bisect run, comparing the steps taken.
Key takeaways
  • Bisect halves the suspect range each step to find the first bad commit.
  • git bisect run automates the search with a script's exit code.
  • It relies on buildable, atomic commits and a reproducible test.
