Shallow, Partial & Sparse Clones

You do not always need every commit, every blob, or every directory of a huge repository, and Git has three separate ways to download and check out less.

§1Shallow Clones: Less History

A shallow clone truncates history to the most recent commits. It is ideal for CI jobs that only need to build the latest code.

git clone --depth 1 https://example.com/big.git      # only the newest commit
git fetch --deepen 50                                     # later, get 50 more commits
git fetch --unshallow                                     # convert to a full clone
git clone --depth 1 --single-branch --branch main <url>   # one branch only

Shallow clones cannot answer questions about older history, so blame, bisect, and log are limited, and some merge operations fail without a common ancestor.

§2Partial Clones: Less Data

A partial clone downloads all commits and trees but fetches file contents (blobs) lazily, only when you check them out or need them.

git clone --filter=blob:none <url>              # no file contents until needed
git clone --filter=blob:limit=1m <url>          # skip blobs larger than 1 MB
git clone --filter=tree:0 <url>                 # even trees on demand (best for CI)

You keep complete history, so log and blame still work, though some commands trigger a fetch from the server and need network access. This is usually the better trade-off than a shallow clone for developers.

§3Sparse Checkout: Fewer Directories

Sparse checkout limits which paths appear in your working tree, which is useful in a monorepo where you work on one service.

git clone --filter=blob:none --sparse <url>
cd big
git sparse-checkout set services/billing libs/common    # only these directories
git sparse-checkout add docs
git sparse-checkout disable                              # back to everything
TechniqueReducesKeeps full history?
Shallow (--depth)Commits downloadedNo
Partial (--filter)Objects downloadedYes
Sparse checkoutFiles in your working treeYes

The three can be combined: partial plus sparse is a common setup for large monorepos.

Choose by what you need to do CI that only builds: shallow or tree:0. Daily work in one part of a monorepo: partial plus sparse. Anything involving history archaeology: a full or partial clone, not a shallow one.

§4Common Mistakes

MistakeWhat HappensFix
Using --depth 1 and then running git bisect or blameMissing history produces errors or wrong resultsDeepen or unshallow first, or use a partial clone
Expecting a partial clone to work fully offlineCommands stall when they need a missing blobFetch what you need beforehand, or stay online
Forgetting that sparse checkout hides filesSearches miss code outside the selected foldersAdd paths with sparse-checkout add
Practice
  1. Clone a large public repository three ways (--depth 1, --filter=blob:none, and sparse) and compare the sizes of the resulting .git folders.
  2. Use git sparse-checkout set to check out only one folder, then add a second folder and list the working tree.
Key takeaways
  • Shallow clones cut history, partial clones defer file contents, sparse checkout limits the working tree.
  • Partial clones keep history, so they suit developers better than shallow clones.
  • Combine partial and sparse for work inside a monorepo.
