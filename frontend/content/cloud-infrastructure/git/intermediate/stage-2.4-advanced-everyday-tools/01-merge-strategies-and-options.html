Merge Strategies & Options

Git merges with the ort strategy by default, and a few strategy options let you steer stubborn merges, but the difference between a strategy and an option matters.

§1Strategies

A merge strategy is the algorithm used to combine histories. You rarely choose one, because the default does the right thing.

StrategyWhat it doesUse
ortDefault three-way merge, handles renames and is fastAlmost always
recursiveThe older default; ort replaced it and is now the name usedLegacy scripts
octopusMerges more than two branches at once; refuses if conflicts occurCombining several clean topic branches
oursRecords a merge but keeps your tree entirely, ignoring the other branch's changesMarking a branch as merged without taking its content
subtreeMerge where one side is a subdirectory of the otherSubtree workflows
git merge -s ours obsolete-branch     # history says merged, content untouched
git merge feature-a feature-b feature-c   # octopus merge

§2Strategy Options (-X)

Options adjust how the default strategy resolves conflicts. They apply only to the conflicting hunks; everything else still merges normally.

git merge -X ours feature          # on conflicting lines, prefer MY side
git merge -X theirs feature        # on conflicting lines, prefer THEIR side
git merge -X ignore-space-change feature
git merge -X find-renames=70 feature   # lower the similarity needed to detect a rename

Do not confuse the two. -s ours discards the other branch's changes entirely; -X ours only prefers your version where there is a conflict and still takes their non-conflicting changes.

§3Choosing a Side for Whole Files

During a conflicted merge, ours is the branch you are on, and theirs is the one being merged. In a rebase the meaning flips, because your commits are the ones being replayed.

git checkout --ours -- config.yaml      # take my version of the file
git checkout --theirs -- config.yaml    # take the incoming version
git add config.yaml
git merge --continue

Turn on rerere so Git remembers how you resolved a conflict and reuses it next time: git config --global rerere.enabled true.

-X theirs is not a conflict solver It silently picks one side wherever both changed the same lines, without checking whether the result makes sense. Use it only when you know one side is simply right, and always run the tests.

§4Common Mistakes

MistakeWhat HappensFix
Confusing -s ours with -X oursAnother branch's changes are discarded completelyUse -X ours to resolve only conflicting hunks
Mixing up ours and theirs during a rebaseYou keep the wrong sideRemember: in a rebase, ours is the branch being rebased onto
Using -X theirs to make a conflict go awaySilent loss of intended changesRead the conflict; resolve it deliberately
Practice
  1. Create a conflict and resolve it three times, using -X ours, -X theirs, and manual editing, then compare the resulting files.
  2. Use git merge -s ours and git log to explain why the merged branch's content is absent although it appears merged.
Key takeaways
  • ort is the default; strategies (-s) differ from strategy options (-X).
  • -s ours ignores the other branch; -X ours only breaks conflicts in your favor.
  • In a rebase, ours and theirs are reversed relative to a merge.
