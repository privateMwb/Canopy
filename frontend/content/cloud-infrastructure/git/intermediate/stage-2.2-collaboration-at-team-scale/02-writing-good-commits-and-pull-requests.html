Writing Good Commits & Pull Requests

Atomic commits, useful messages, and reviewable change sizes make a team's history searchable and its reviews fast, and they are habits you can build one commit at a time.

§1Atomic Commits

An atomic commit makes one logical change and leaves the project in a working state: the build passes and the tests pass. Refactoring, formatting, and behavior changes belong in separate commits, so a reviewer can read each on its own and a bad one can be reverted alone.

Refactor: extract tax calculation into its own function
Add tax exemption for educational customers
Update tax rate table for 2026

Tests belong with the code they test, in the same commit, so every commit stays green.

§2Messages Teams Can Use

Agree on a style. A popular one is Conventional Commits, which prefixes each subject with a type that tools can read for changelogs and version bumps.

feat(cart): allow promo codes at checkout
fix(auth): reject expired refresh tokens
docs: explain local database setup
refactor(search): split query parser from ranker
feat!: drop support for API v1    # '!' marks a breaking change

Whatever the format, the body explains why. Link the issue or ticket in a trailer so tools can connect them: Fixes #214.

§3Reviewable Pull Requests

PracticeWhy it helps
Under ~400 changed linesReview quality drops sharply on larger changes
One purpose per PREasier to approve, revert, and understand later
Description with context and test stepsReviewers do not have to reverse-engineer intent
Self-review before requestingYou catch debug code and stray files first
Draft PRs for early feedbackCheap course correction before the work is polished
git diff --stat origin/main...HEAD     # how big is this really?
git log --oneline origin/main..HEAD    # do these commits tell a story?

If a change is inherently large, split it into a series: preparatory refactors first, then the feature in steps, each of which can land safely on its own.

Optimize for the reader A commit is written once and read many times. Each extra minute spent on a clear message or a smaller diff saves reviewers and future debuggers far more than it costs you.

§4Common Mistakes

MistakeWhat HappensFix
Mixing formatting changes with logic changesReviewers cannot see the real change in the noiseCommit pure formatting separately, or land it first
Commits that break the build mid-branchgit bisect and reverts become unreliableMake every commit pass the tests
Giant pull requestsRubber-stamp approvals and missed bugsSplit into reviewable pieces
Practice
  1. Take a recent branch of yours and list its commits; rewrite any vague subjects and note where one commit should have been split.
  2. Break an imaginary 1,200-line change into a series of five pull requests, each with a purpose and a safe order.
Key takeaways
  • Atomic commits do one thing and keep the build green.
  • Agree on a message convention and explain why, not just what.
  • Small, single-purpose pull requests are reviewed faster and more carefully.
