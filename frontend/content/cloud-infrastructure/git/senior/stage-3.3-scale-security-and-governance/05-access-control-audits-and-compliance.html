Access Control, Audits & Compliance

Regulated or security-sensitive teams must show who can change what and prove it afterward, which Git hosting supports through permissions, protected branches, and audit logs.

§1Least-Privilege Access

Give each person and system only the access they need, at the narrowest scope. Use teams or groups rather than individuals, and review membership regularly.

RoleTypical permission
ReaderClone and read, comment on issues
ContributorPush to branches and open pull requests
MaintainerMerge, manage settings of the repository
AdminChange protection rules, add people, delete the repository (keep this group small)
CI / botsScoped tokens or apps, never a person's personal token

Enforce SSO and multi-factor authentication at the organization level, expire unused tokens and SSH keys, and prefer short-lived credentials for automation.

§2Separation of Duties and Protected Changes

Compliance frameworks (SOC 2, ISO 27001, PCI DSS, HIPAA and others) commonly expect that no one can push their own change to production unreviewed. In Git terms:

  • Protected branches that require pull requests and approvals from someone other than the author
  • Required status checks, and restrictions on who can bypass them (with bypasses recorded)
  • Signed commits and protected tags for release provenance
  • CODEOWNERS for sensitive paths such as payment or infrastructure code

§3Audit Trails

A good audit trail answers: who did what, when, from where, and with whose approval. Git history gives authorship and ordering, but authorship is only trustworthy with signing. The hosting platform's audit log records the rest: permission changes, setting changes, deploy key use, forced pushes, and repository deletion.

git log --show-signature --format='%H %an %ad %G?' main   # %G? = signature status per commit
# export the organization audit log (via the host's API or SIEM integration)
# keep it somewhere tamper-resistant and retain it for the required period

Stream audit logs to a central system, alert on risky events (force pushes to protected branches, admin changes, new deploy keys), and keep evidence of reviews, since compliance asks you to prove the control worked.

§4Doing It Without Slowing Teams Down

Automate the evidence: let branch protection and CI produce the records, rather than asking engineers to fill in forms. Use pre-approved low-risk change categories, and make controls the default path in repository templates.

Controls you can demonstrate are the ones that count An auditor wants to see the setting, the log showing it was enforced, and the exception record. Prefer controls that leave evidence automatically.

§5Common Mistakes

MistakeWhat HappensFix
Using personal tokens for automationAccess disappears with the person, and actions are misattributedUse a bot account or app with a scoped token
Too many administratorsA larger attack surface and weak accountabilityKeep admin rights to a few reviewed people
Allowing unrecorded bypasses of protectionNo evidence for auditors, and silent riskLog and review every bypass
Practice
  1. Design a permission model with four roles for a company with 40 developers, and name who can approve changes to a payment service.
  2. Write the list of audit events you would alert on and the person or team who would receive each alert.
Key takeaways
  • Apply least privilege through teams, SSO, MFA, and scoped automation credentials.
  • Separation of duties maps to required reviews, status checks, and signed, protected releases.
  • Automate evidence from audit logs so compliance does not slow teams down.
