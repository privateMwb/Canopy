Repository Security & Secret Response

A repository is part of your supply chain, so you need scanning to prevent leaks, a rehearsed response when one happens, and defenses against malicious changes.

§1Preventing Leaks

  • Pre-commit scanning with gitleaks, trufflehog, or detect-secrets catches secrets before they are committed
  • Server-side push protection (such as GitHub secret scanning) blocks pushes that contain recognizable credentials
  • Ignore rules for .env, key files, and local config
  • Prefer short-lived, scoped credentials (OIDC tokens in CI, workload identity) over long-lived keys, since a leaked token that expires in an hour is a smaller incident
gitleaks detect --source . --log-opts="--all"      # scan the full history
gitleaks protect --staged                         # scan what you are about to commit

§2Responding When a Secret Leaks

Assume it is compromised the moment it was pushed anywhere others can read it.

  1. Revoke and rotate the credential at its provider, then check the provider's audit logs for any use of the old one.
  2. Assess the scope: which systems, what data, how long it was exposed.
  3. Remove it from history if required, as a clean-up step, using git filter-repo --replace-text. Then force-push, and have every collaborator re-clone, since old clones still contain it.
  4. Ask the host to purge cached views and any forks or pull request refs that still reference the objects.
  5. Add prevention (scanning, push protection) and write a short post-incident note.
echo 'AKIAEXAMPLEKEY==>***REMOVED***' > replacements.txt
git filter-repo --replace-text replacements.txt   # rewrites every commit

§3Supply-Chain Risks

RiskDefense
Malicious or compromised dependencyLockfiles, pinned versions, review of updates, SCA scanning
Unreviewed change reaching mainBranch protection, required reviews, CODEOWNERS
Forged author on a commitSigned commits, required on protected branches
Compromised CI or workflow edit from a PRLeast-privilege tokens; careful use of pull_request_target; pin actions to a commit SHA
Malicious hooks or config in a cloned repoDo not run unfamiliar repository scripts blindly; hooks are not cloned by default
Rotation is the cure; history rewriting is cosmetic Cleaning history makes a repository tidier but cannot recall copies that already exist. Only revoking the credential makes the leaked value harmless.

§4Common Mistakes

MistakeWhat HappensFix
Rewriting history without rotating the secretThe leaked credential still works for anyone who copied itRotate first, always
Pinning CI actions to mutable tagsA compromised tag changes what runs in your pipelinePin to a full commit SHA
Scanning only new commitsOld secrets in history are missedRun a full-history scan once, then scan on every push
Practice
  1. Install a secret scanner, plant a fake key in a scratch repository, and watch the scanner catch it both before commit and in history.
  2. Write a one-page incident checklist for a leaked cloud key: who does what, in what order, in the first hour.
Key takeaways
  • Prevent with pre-commit scanning, push protection, and short-lived credentials.
  • On a leak: revoke and rotate first, then clean history and add prevention.
  • Protect the supply chain with review, signing, and pinned, least-privilege automation.
