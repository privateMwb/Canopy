How Merge, Diff & Rebase Actually Work

Merge, diff, and rebase are algorithms over the commit graph, and knowing their inputs explains their surprises.

§1Merge Base and Three-Way Merge

To merge A into B, Git finds the merge base, the best common ancestor, and compares both sides against it. For each region, if only one side changed it, that change wins. If both changed it identically, fine. If both changed it differently, conflict.

git merge-base main feature          # the common ancestor
git diff $(git merge-base main feature) feature   # what feature changed
git merge-tree --write-tree main feature          # test a merge without touching the working tree

With criss-cross histories there may be several best ancestors. The default ort strategy merges them recursively, and it handles renames by similarity detection.

§2Diff Algorithms

Diff computes a minimal set of added and removed lines. Different algorithms give differently readable results.

git diff --diff-algorithm=histogram
git config --global diff.algorithm histogram
git diff -M --stat                   # detect renames
git diff --word-diff                 # compare words, not lines

Renames are not stored: Git infers them by comparing content similarity, which is why a rename plus heavy edits may look like delete and add.

§3Rebase as Replay

Rebase is a series of cherry-picks, each a three-way merge using the commit's parent as the base. That is why conflicts can reappear at every replayed commit.

§4Rerere: Reuse Recorded Resolution

git config --global rerere.enabled true

Git remembers how you resolved a conflict and applies the same fix automatically if the same conflict appears again, such as during repeated rebases.

The key insight A merge compares each side with the common ancestor, not with each other. Most strange conflicts come from an unexpected merge base.

§5Common Mistakes

MistakeWhat HappensFix
Assuming Git tracks renamesHeavy edits break rename detectionRename in a separate commit from large edits
Resolving the same conflict repeatedly in a long rebaseWasted time and inconsistent resultsEnable rerere
Never checking the merge baseA surprising merge base causes unexpected resultsRun git merge-base when a merge looks wrong
Practice
  1. Create a criss-cross history and examine the merge base and the result.
  2. Enable rerere, resolve a conflict, abort, and redo the merge to see it reapply the resolution.
Key takeaways
  • Merges compare each side with the merge base.
  • Renames are inferred from similarity, not recorded.
  • rerere reuses recorded conflict resolutions.
