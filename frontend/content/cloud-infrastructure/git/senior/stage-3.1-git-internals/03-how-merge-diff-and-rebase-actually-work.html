How Merge, Diff & Rebase Actually Work

Diffs are computed on demand, merges compare two tips against their common ancestor, and rebase is repeated cherry-picking, so none of them is magic.

§1Diff Is Computed, Not Stored

Since commits are snapshots, a diff is calculated by comparing two trees and running a line-difference algorithm on files that differ. The algorithm choice changes how a diff reads, but not what the final content is.

git diff --diff-algorithm=myers      # default: fast, good general results
git diff --diff-algorithm=patience   # better on code with many repeated lines
git diff --diff-algorithm=histogram  # patience-like, often fastest and cleanest
git config --global diff.algorithm histogram

Rename detection is also inferred, not recorded: Git compares content similarity (50% by default) between deleted and added files. That is why a rename plus heavy edits in one commit can look like a delete and an add.

§2Merge: Two Tips and a Base

A three-way merge needs the merge base, the best common ancestor of the two tips. Git diffs base-to-ours and base-to-theirs and combines them: a change made on only one side is taken, and the same change on both sides is taken once. A change to the same region on both sides is a conflict.

git merge-base main feature           # the common ancestor commit
git diff $(git merge-base main feature) feature   # what the feature changed
git log main...feature --left-right --oneline   # commits unique to each side

With criss-cross histories there can be multiple merge bases. The ort strategy merges those bases first to build a virtual one, which is why it handles them more gracefully than older approaches.

§3Rebase: Repeated Cherry-Pick

git rebase main computes the commits on your branch that are not on main, checks out main, and applies each commit's changes in order, with each commit being a three-way merge whose base is the commit's own parent. That explains why a rebase can conflict at each step and why the new commits have new hashes.

git rev-list --reverse main..feature       # the commits that will be replayed
git rebase --onto main old-base feature   # replay commits after old-base onto main
git cherry-pick $(git rev-list --reverse main..feature)   # roughly equivalent by hand

§4Rerere: Reusing Recorded Resolution

With rerere.enabled, Git records how you resolved each conflict and replays that resolution when the same conflict reappears, for example when you repeatedly rebase a long-lived branch.

git config --global rerere.enabled true
git rerere status                    # conflicts it has recorded
git rerere diff                      # what it would apply
Rebase conflicts repeat because every commit merges separately If a ten-commit branch conflicts on the same lines in three of them, you will resolve it three times. Squashing first, or enabling rerere, reduces that repeated work.

§5Common Mistakes

MistakeWhat HappensFix
Expecting renames to be tracked as eventsA heavily edited rename shows as delete and addCommit pure renames separately from big edits
Assuming one merge base always existsSurprise results in criss-cross mergesCheck with git merge-base --all
Choosing diff algorithm by habitConfusing diffs in code with repetitive structureTry histogram or patience when diffs look odd
Practice
  1. Create a criss-cross merge scenario or a simple branch pair, and use git merge-base and git diff to predict what a merge will change before running it.
  2. Turn on rerere, resolve a conflict, abort, repeat the merge, and observe Git reapplying your resolution.
Key takeaways
  • Diffs and renames are computed on demand from snapshots.
  • A merge combines two tips relative to their merge base; rebase is repeated three-way application.
  • rerere remembers conflict resolutions so repeated conflicts are solved once.
