Objects: Blobs, Trees, Commits & Tags

Underneath every command, Git is a content-addressable database of four object types, each named by a hash of its own contents.

§1A Key-Value Store Named by Content

Inside .git/objects, Git stores everything as an object. Each object's name is a hash (SHA-1 by default, SHA-256 optionally) of its type and content. The same content always produces the same name, so identical files are stored once, and any change to content changes the name.

echo "hello" | git hash-object --stdin        # compute the hash, store nothing
echo "hello" | git hash-object -w --stdin     # -w: actually write it
git cat-file -t ce013625030ba8dba906f756967f9e9ca394464a   # type: blob
git cat-file -p ce013625030ba8dba906f756967f9e9ca394464a   # print contents

§2The Four Object Types

ObjectHoldsAnalogy
blobThe contents of one file (no name, no mode)A file's bytes
treeA directory: names, modes, and pointers to blobs and other treesA folder listing
commitA pointer to a top-level tree, parent commit(s), author, committer, messageA snapshot with metadata
tagAn annotated tag: a pointer to an object, plus tagger and messageA signed label
git cat-file -p HEAD                    # a commit object
# tree 9f2c...   <- snapshot of the root directory
# parent 4be1... <- previous commit
# author Ada <ada@example.com> 1767225600 +0000
# committer Ada <ada@example.com> 1767225600 +0000
#
# Add search endpoint
git cat-file -p HEAD^{tree}              # the root tree: its entries
git ls-tree -r HEAD                      # every file with its blob hash

§3Why This Design Matters

  • Integrity: a commit's hash covers its tree, its parents, and its message, so it fixes the entire history behind it. Altering any old commit changes every later hash.
  • Efficiency: an unchanged file or folder reuses the same blob or tree, so a snapshot costs space only for what changed.
  • Rewriting is replacing: rebase and amend do not edit commits; they create new objects and move a pointer, and the old objects linger until garbage collection.
Commits are immutable A "rewritten" commit is a different commit with a different hash. This single fact explains force pushes, why rebasing shared branches hurts, and why the reflog can restore old states.

§4Common Mistakes

MistakeWhat HappensFix
Thinking Git stores diffs between versionsMisjudging storage and performanceLogically it stores whole snapshots; packfiles compress them later
Believing a hash identifies only a file's nameConfusion about renamesA blob has no name; names live in trees
Treating amend as editing in placeSurprise at diverging histories after pushingRemember it creates a new commit object
Practice
  1. Make a commit in a scratch repository and use git cat-file -p to walk from the commit to its tree to a blob, noting each hash.
  2. Change one file and commit again; use git ls-tree -r on both commits to show which blobs are shared and which are new.
Key takeaways
  • Git is a content-addressable store of blobs, trees, commits, and tags.
  • An object's hash covers its content, so history is tamper-evident.
  • Rewriting history creates new objects; it never modifies old ones.
