Versioning, Changelogs & Release Automation

Semantic versions, annotated tags, and conventional commits let a pipeline compute the next version, write the changelog, and publish a release with no manual steps.

§1Semantic Versioning

SemVer numbers a release MAJOR.MINOR.PATCH and communicates risk to users:

PartBump whenExample
MAJORYou make an incompatible, breaking change2.4.1 to 3.0.0
MINORYou add functionality in a backward-compatible way2.4.1 to 2.5.0
PATCHYou make backward-compatible bug fixes2.4.1 to 2.4.2

Pre-release and build labels extend it: 2.5.0-rc.1, 2.5.0+build.7. SemVer works best for libraries and APIs; applications often use calendar versions such as 2026.11.1 instead.

§2Tags Mark Releases

git tag -a v2.5.0 -m "Release 2.5.0"        # annotated (or -s to sign)
git push origin v2.5.0
git describe --tags                         # v2.5.0-14-g9c8b7a6  (14 commits after the tag)
git log v2.4.0..v2.5.0 --oneline            # everything in the release
git tag --sort=-v:refname | head            # newest versions first

§3Changelogs From Commits

A changelog is for humans: what changed, grouped by kind, with breaking changes visible. If commits follow Conventional Commits, tools can generate it and decide the version:

Commit prefixVersion effectChangelog section
fix:PatchBug Fixes
feat:MinorFeatures
feat!: or BREAKING CHANGE: footerMajorBreaking Changes
docs:, chore:, refactor:NoneUsually omitted

§4Automating the Release

Tools such as release-please, semantic-release, and changesets read the commits since the last tag, compute the next version, update the changelog, create the tag, and publish. A typical flow runs on every merge to main:

# CI on merge to main
npx semantic-release
#  1. analyze commits since the last tag  ->  next version 2.5.0
#  2. generate release notes and update CHANGELOG.md
#  3. create tag v2.5.0 and a GitHub Release
#  4. publish the package

Protect the release step: only CI may create release tags, tags should be immutable (never move or re-tag a published version), and credentials for publishing must be scoped and stored as CI secrets.

Never move a published tag Once users or package registries have seen v2.5.0, it must forever mean the same commit. If it is wrong, ship v2.5.1. Re-tagging breaks caches, builds, and trust.

§5Common Mistakes

MistakeWhat HappensFix
Bumping the wrong part of the versionUsers upgrade blindly into a breaking changeDerive the bump from commit types, and review breaking changes
Dumping git log as the changelogNoise that no user can readWrite or generate grouped, human-oriented notes
Re-tagging a released version to fix a mistakeDifferent consumers have different code under one versionRelease a new patch version
Practice
  1. Given ten Conventional Commit messages you invent, decide the next version from 1.8.3 and write the changelog entries.
  2. Sketch a CI job that, on each merge to main, computes the version, tags it, and publishes, listing the secrets it needs.
Key takeaways
  • SemVer encodes risk: major breaks, minor adds, patch fixes.
  • Conventional Commits let tools compute versions and changelogs.
  • Automate releases in CI, and never move a published tag.
