Trunk-Based Development vs. Git Flow

Branching models are bets about what a team needs most: continuous integration speed, or structured control over parallel releases.

§1Git Flow: Structured Parallel Lines

Git Flow uses long-lived branches with defined roles: main holds released code, develop collects finished features, and short-lived feature/*, release/*, and hotfix/* branches move work between them.

feature/login ──┐
feature/search ─┤
                ▼
develop ───────●────────●──────►
                         \ release/2.1 (stabilize)
main ───────────────────────●──► tag v2.1

It suits products with scheduled, versioned releases and several supported versions at once, such as desktop software, firmware, or libraries with long-term support. The cost is long-lived branches that drift apart, painful merges, and slow feedback.

§2Trunk-Based Development: Integrate Constantly

In trunk-based development, everyone integrates into one branch (main, the trunk) at least daily. Branches live hours or a day or two; unfinished work is hidden behind feature flags rather than kept on a branch. Releases are cut from trunk, or trunk is deployed continuously.

git switch -c small-change main
# ...a few hours of work, tests passing...
git push -u origin small-change   # open a PR, review within hours
# merge to main, which is always releasable

It demands strong automated tests, fast CI, and quick review, and in return it nearly eliminates merge pain and keeps changes small and low-risk.

§3Comparing What Each Optimizes

Git FlowTrunk-based
Optimizes forControl of parallel releasesSpeed of integration and delivery
Branch lifetimeDays to monthsHours to a couple of days
ReleaseCut from a release/* branchFrom trunk, often continuous
NeedsDiscipline in mergingTests, CI, feature flags
Hurts whenTeams want to ship oftenYou cannot test automatically or must support many versions

Related simpler models sit between them: GitHub Flow (short branches and pull requests off main, deploy from main) and release branching off trunk, which keeps trunk-based speed while allowing stabilization of a versioned release.

The research favors short-lived branches Industry research on delivery performance (DORA) consistently links frequent integration and small batches with better outcomes. Use Git Flow only if you genuinely need to maintain several released versions in parallel.

§4Common Mistakes

MistakeWhat HappensFix
Adopting Git Flow for a web service deployed dailyCeremony and merge pain with no benefitUse trunk-based or GitHub Flow with feature flags
Going trunk-based with weak testsBroken trunk and fear of mergingInvest in CI, tests, and fast rollback first
Calling any long-lived feature branch "trunk-based"Delayed integration, which is the real problemKeep branches short; flag unfinished work
Practice
  1. For a mobile app with versions in the app store, a SaaS dashboard deployed hourly, and a library with three supported majors, pick a model for each and justify it in two sentences.
  2. List the three biggest risks of a branch that lives for six weeks, and the practice that removes each in a trunk-based approach.
Key takeaways
  • Git Flow gives structure for parallel versioned releases at the cost of long-lived branches.
  • Trunk-based development integrates constantly and relies on tests and feature flags.
  • Choose by release needs and test maturity, not by fashion.
