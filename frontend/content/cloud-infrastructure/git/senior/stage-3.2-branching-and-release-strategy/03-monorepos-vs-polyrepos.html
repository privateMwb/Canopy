Monorepos vs. Polyrepos

Keeping all code in one repository or in many is a trade-off between atomic change and independence, and Git has features that make large monorepos workable.

§1The Two Shapes

A monorepo holds many projects, services, and libraries in one repository. Polyrepos give each project its own. The common mistake is to treat this as a Git question, when it is really about how your teams, builds, and dependencies work.

MonorepoPolyrepo
Cross-project changeOne atomic commit and PRCoordinated PRs across repos and a release order
Dependency versionsEveryone on one version ("one version policy")Each project pins its own, drifts apart
Code sharing and discoveryEasy: it is all in one placeHarder; needs packages and registries
Access controlCoarser (CODEOWNERS, path rules)Natural per-repo permissions
Build and CINeeds path-aware tooling to stay fastSimple, small, independent pipelines
Clone size and speedLarge; needs partial and sparse clonesSmall

§2Making a Monorepo Workable

  • Partial and sparse clones so developers fetch only what they need
  • Path-based CI: build and test only what a change affects, using a build tool with a dependency graph (Bazel, Nx, Turborepo, Pants)
  • CODEOWNERS and path-scoped protection rules for review and security boundaries
  • Commit graph, fsmonitor, and git maintenance to keep status and log fast
  • A merge queue to keep trunk green when many people merge at once
git sparse-checkout set services/billing libs/common
git config core.fsmonitor true
git config core.untrackedCache true
git maintenance start                    # background prefetch, commit-graph, gc

§3Choosing

Monorepos shine when projects change together and share code, and when you want one set of tools and standards. Polyrepos fit teams that release independently, need strict access separation, or have unrelated tech stacks.

Migration is possible in both directions, and git subtree split and git filter-repo can preserve history, but it is costly. Decide on need rather than trend, and remember that a hybrid is normal: a few repositories, each a monorepo for a product area.

Tooling decides whether a monorepo works A monorepo without path-aware builds, ownership rules, and sparse checkouts becomes slow and painful. A polyrepo without good package tooling becomes a maze of version mismatches. The structure needs its supporting tools.

§4Common Mistakes

MistakeWhat HappensFix
Choosing a monorepo without build toolingCI rebuilds everything on every changeAdopt a dependency-aware build and path filters
Splitting into many repos for tiny shared codeVersion drift and painful cross-repo changesKeep tightly coupled code together
Ignoring access needsSensitive code exposed to everyone in a monorepoDecide on boundaries early; use path rules or separate repos
Practice
  1. For a company with a web app, a mobile app, and a shared design library, argue for monorepo or polyrepo in a paragraph and name the tooling each choice needs.
  2. List what you would configure in Git to keep a 20 GB monorepo usable on a laptop.
Key takeaways
  • Monorepos give atomic cross-project changes; polyrepos give independence and simple access control.
  • Sparse and partial clones, path-aware CI, and merge queues make monorepos scale.
  • Choose by how your teams and releases actually work.
