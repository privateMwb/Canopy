Performance: Parallelism, Refresh & Large States

Large configurations get slow because every plan reads every resource. Most speedups come from doing less work, not from tuning flags.

§1Why Plans Are Slow

Refresh issues at least one API call per resource, and data sources add more. Thousands of resources in one state mean thousands of calls, and cloud APIs rate-limit you. Locking, state download, and provider startup add fixed cost on top.

§2Measure Before Tuning

export TF_LOG=INFO
time terraform plan

Look for which provider calls dominate, and whether you are being throttled (retries and 429 responses).

§3What Helps

  • Split state. Smaller stacks mean smaller graphs and faster refresh. This is also the best fix for blast radius (stage 3.2).
  • Parallelism. -parallelism=N changes how many graph nodes run at once (default 10). Raising it helps until you hit API rate limits, after which it makes things worse.
  • Skip refresh when safe. -refresh=false speeds up plans, at the cost of missing drift. It suits tight development loops, not pipelines you trust.
  • Target narrowly, rarely. -target plans only a resource and its dependencies. It is a diagnostic tool and a recovery tool, not a workflow, because it can leave the rest of the stack out of date.
  • Cache providers. Set TF_PLUGIN_CACHE_DIR so CI does not download large providers on every run.
  • Reduce data source calls. Look up shared values once, in one place, and pass them in.
export TF_PLUGIN_CACHE_DIR="$HOME/.terraform.d/plugin-cache"
terraform plan -parallelism=20
Slow plans are a design smell If a plan takes twenty minutes, nobody runs it before pushing, and the feedback loop breaks. Treat plan time as a quality metric for stack design and split before it becomes painful.

§4Common Mistakes

MistakeWhat HappensFix
Cranking parallelism up blindlyRate limiting and more retries slow things downMeasure and increase gradually
Living on -targetState and reality drift apart, and surprises accumulateUse it for emergencies, and plan the whole stack afterwards
Keeping one huge state for everythingSlow plans, risky applies, and long lock timesSplit along ownership and change-rate boundaries
Practice
  1. Time a plan for a large configuration with several -parallelism values and chart the results.
  2. Identify five data sources in a stack that could be looked up once and passed in as inputs.
Key takeaways
  • Plan time scales with the number of resources and API calls.
  • Splitting state is the most effective improvement; parallelism and caching help at the margins.
  • Use -target and -refresh=false sparingly, and never as a routine workflow.
