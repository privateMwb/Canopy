How Terraform Plans: Graph, Refresh & Diff

A plan is not a diff of text files. Terraform builds a graph, refreshes real objects, and asks each provider what must change. Knowing that sequence explains most surprising plans.

§1From Files to Graph

Terraform's core does roughly this on every plan:

  1. Load all .tf files, variables, and modules into one configuration.
  2. Read state, the record of what it created.
  3. Build a graph whose nodes are resources, data sources, providers, variables, locals, and outputs, and whose edges are references and depends_on.
  4. Walk the graph in dependency order, running independent nodes in parallel (default -parallelism=10).
  5. Refresh each existing resource by asking its provider to read the real object, updating the in-memory state.
  6. Diff each resource: Terraform sends the provider the prior state, the configuration, and the proposed new state, and the provider returns the planned result, including which changes require replacement.

The apply step walks the same graph again and calls the provider to create, update, or delete.

§2Unknown Values

Some values cannot be known until apply, such as a generated ID. The plan marks them (known after apply), and anything derived from them is unknown too. This is why for_each keys and count must be known at plan time: Terraform needs to know how many nodes the graph has before it can walk it.

terraform plan -out=tfplan
terraform show -json tfplan | jq '.resource_changes[] | {address, actions: .change.actions}'

The plan file records the prior state, the planned changes, and a snapshot of the configuration, which is why applying it needs no re-planning.

§3Refresh Behavior

Normal plans refresh first, so they notice drift. You can control it.

terraform plan -refresh=false        # skip the read of real objects (faster, may be stale)
terraform plan -refresh-only         # show only what changed in the real world
Providers decide replacement, not Terraform The # forces replacement flag comes from the provider's schema for each argument. Core only orchestrates. When a plan surprises you, the answer is usually in that resource's schema and docs, not in Terraform itself.

§4Common Mistakes

MistakeWhat HappensFix
Assuming plan shows only your code's changesOut-of-band changes also appear after refreshUse -refresh-only to separate drift from code changes
Using -refresh=false as a habitPlans miss drift and can be wrongReserve it for speed in controlled cases
Expecting for_each keys from apply-time values"Invalid for_each argument"Derive keys from values known during plan
Practice
  1. Save a plan and use terraform show -json with jq to list each resource and its planned action.
  2. Compare plan with plan -refresh-only after changing a resource by hand in the console.
Key takeaways
  • Plans come from a dependency graph, a refresh, and a provider-computed diff.
  • Unknown values explain (known after apply) and the limits on count and for_each.
  • Providers decide what forces replacement; core coordinates.
