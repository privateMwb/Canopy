Zero-Downtime Changes & Migrations

A -/+ in the plan is an outage unless you design around it. Zero-downtime changes mean building the new before removing the old.

§1Create Before Destroy

By default Terraform destroys the old resource, then creates the new one. For things that serve traffic, reverse that.

resource "aws_launch_template" "app" {
  name_prefix   = "app-"          # unique names allow two to exist at once
  image_id      = var.ami_id
  instance_type = "t3.medium"

  lifecycle { create_before_destroy = true }
}

This only works when the resource's identifying name does not collide. Fixed names (name = "app") block it, so use name_prefix or include a random suffix. The setting also propagates to dependencies, which can surprise you.

§2Rolling Out Instances

Replacing an auto-scaling group's template should roll gradually, not all at once.

resource "aws_autoscaling_group" "app" {
  # ...
  launch_template {
    id      = aws_launch_template.app.id
    version = aws_launch_template.app.latest_version
  }
  instance_refresh {
    strategy = "Rolling"
    preferences { min_healthy_percentage = 90 }
  }
}

§3Blue/Green and Traffic Shifting

For bigger changes, stand up the new version alongside the old and move traffic with weighted DNS or load balancer target groups, then remove the old after it proves healthy.

resource "aws_lb_listener_rule" "app" {
  # ...
  action {
    type = "forward"
    forward {
      target_group {
        arn    = aws_lb_target_group.blue.arn
        weight = 90
      }
      target_group {
        arn    = aws_lb_target_group.green.arn
        weight = 10
      }
    }
  }
}

§4Data and Migrations

Replacing stateful resources needs a data plan: snapshots and restores, replication, or provider-supported blue/green for managed databases. Use the expand and contract pattern for schema changes, which adds new structure, migrates, then removes the old, with each step compatible with the version before and after it.

§5Moving Resources Without Recreating

Use moved blocks to rename or restructure, and removed plus import to move something between states without touching the real object.

Rehearse the plan, not just the code For risky changes, apply to a staging copy first and read the plan on the real stack closely. The question is never "will the code work" but "what happens to live traffic between the first and last step".

§6Common Mistakes

MistakeWhat HappensFix
Using fixed names on resources that must be replacedcreate_before_destroy fails on a name conflictUse name_prefix or generated suffixes
Replacing a database in placeData loss and downtimeUse snapshots, replication, or provider blue/green features
Changing everything in one applyA failure leaves a half-migrated systemBreak migrations into small, individually safe steps
Practice
  1. Convert a launch template to use name_prefix and create_before_destroy, and confirm in the plan that the new one is created first.
  2. Write the sequence of steps to rename a database column using expand and contract, with each step independently safe.
Key takeaways
  • Build new before removing old, and make names unique enough to allow both to exist.
  • Roll instances gradually and shift traffic in measured steps.
  • Treat stateful replacement as a data migration, not a resource swap.
