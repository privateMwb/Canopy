Multi-Account & Multi-Region Patterns

Organizations run on many accounts and regions. A repeatable pattern keeps that sprawl consistent, auditable, and secure.

§1Why Many Accounts

Accounts (or subscriptions and projects, on other clouds) are the strongest isolation boundary the cloud offers: separate permissions, billing, quotas, and failure domains. Typical structures separate environments, workloads, security tooling, logging, and shared networking.

§2Layers of Configuration

  • Organization level. Accounts, organizational units, service control policies, and central logging. Few people may change this.
  • Account baseline. Settings every new account gets: logging, security tooling, budget alerts, base IAM roles.
  • Shared services. Networking hubs, DNS, container registries, identity providers.
  • Workloads. Application stacks per account and environment.

Each layer has its own state and its own pipeline, with credentials scoped to its level.

§3Reaching Many Accounts

A pipeline assumes a role in each target account, usually with a provider that is chosen per stack.

provider "aws" {
  region = var.region
  assume_role {
    role_arn = "arn:aws:iam::${var.account_id}:role/terraform-deploy"
  }
  default_tags { tags = { Environment = var.environment } }
}

The same module and the same code run for every account, with only variables changing. Account vending (AWS Control Tower with Account Factory for Terraform, or your own automation) creates and baselines new accounts from code, rather than by ticket.

§4Regions

Multi-region adds choices: which resources are global (IAM, some DNS) and which are regional, how data replicates, and how failover works. Keep a stack per region for anything you apply independently, and keep region as a variable, not a hard-coded value.

Make the account a parameter, not a copy When every account needs the same baseline, one module applied N times beats N copies of code. Differences go in variables, and a new account becomes a new variable file and a pipeline run.

§5Common Mistakes

MistakeWhat HappensFix
Hard-coding account IDs and regions in modulesCannot reuse the code for another accountPass them as variables and configure the provider in the root
Giving every pipeline organization-level accessA workload bug can alter org-wide policySeparate layers with separate roles
Manually creating accountsInconsistent baselinesAutomate account creation and baselining
Practice
  1. Design the account structure and baseline layers for a company with dev, staging, prod, security, and logging needs.
  2. Write a provider block that assumes a role from a variable, and list what must exist in the target account for it to work.
Key takeaways
  • Accounts are the strongest isolation boundary; use them to separate environments and concerns.
  • Apply the same baseline modules to every account, varying only inputs.
  • Automate account vending so every new account starts correctly configured.
