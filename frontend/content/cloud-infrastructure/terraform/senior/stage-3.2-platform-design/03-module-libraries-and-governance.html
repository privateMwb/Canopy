Module Libraries & Governance

A shared module becomes a product with users. Versioning, ownership, and deprecation decide whether it helps your organization or slows it down.

§1Treat Modules as Products

Once several teams depend on a module, changes affect all of them. Give each module:

  • An owner. A team named in CODEOWNERS who reviews every change.
  • Semantic versions. Tag releases v1.4.0. Patch for fixes, minor for backward-compatible additions, major for anything that can change existing plans.
  • A changelog and upgrade notes. Callers must know what a bump will do before they run it.
  • Tests. terraform test and example configurations that run in CI on every change.
  • Documentation generated from code. Tools such as terraform-docs keep input and output tables accurate.
module "service" {
  source  = "app.terraform.io/acme/service/aws"   # private registry
  version = "~> 2.3"
}

A private registry (in HCP Terraform, or a git tag convention) gives teams one discoverable place to find approved modules.

§2Breaking Changes

What counts as breaking in Terraform is broader than API changes. Renaming a resource inside a module, changing a default, or tightening a validation can all make an existing caller's plan show destroys or errors.

moved {
  from = aws_s3_bucket.logs
  to   = aws_s3_bucket.this
}

Ship moved blocks with renames, keep old variable names working for a deprecation period, and announce the removal date.

§3Deprecation

Mark a variable or output as deprecated in its description, support it for a stated period, and then remove it in a major release. Track which stacks still use old versions, so you know when removal is safe.

Governance should reduce friction The goal is paved roads people want to use. A module library with no owners becomes abandoned; one with heavy process becomes a bottleneck and teams copy code. Aim for clear ownership and a fast, predictable release path.

§4Common Mistakes

MistakeWhat HappensFix
Publishing a changed default as a patch releaseExisting stacks start planning destroysTreat default changes as breaking and bump the major version
Removing a variable without noticeCallers' plans failDeprecate first, remove later in a major release
No tests on shared modulesBugs reach every consumer at onceRun tests and example plans in CI before release
Practice
  1. Write a release checklist for a shared module covering tests, changelog, tag, and announcement.
  2. List three changes to a module that you would classify as major, and explain how each could break a caller.
Key takeaways
  • Shared modules need owners, semantic versions, tests, and a changelog.
  • Defaults, names, and validations can all be breaking changes.
  • Deprecate before you remove, and track who still uses old versions.
