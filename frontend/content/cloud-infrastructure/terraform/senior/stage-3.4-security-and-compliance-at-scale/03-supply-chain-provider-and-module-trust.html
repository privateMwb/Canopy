Supply Chain: Provider & Module Trust

Every provider and module is third-party code that runs with your cloud credentials. The supply chain deserves the same scrutiny as application dependencies.

§1What You Are Trusting

When you run terraform init, you download provider binaries and modules from the internet and execute them. A malicious or compromised provider could read credentials from its environment and access anything Terraform can. Modules can create backdoor IAM roles or open networks.

§2Providers

  • Pin and lock. Use version constraints and commit .terraform.lock.hcl, which records the exact version and checksums so a tampered download fails verification.
  • Verify publishers. The registry signs providers, and tiers (official, partner, community) tell you who stands behind them. Prefer official and partner providers, and review community ones.
  • Mirror. Run a network or filesystem mirror so CI installs from a source you control instead of reaching the public registry.
# ~/.terraformrc or CI config
provider_installation {
  network_mirror {
    url = "https://mirror.example.com/terraform/providers/"
  }
}
terraform providers mirror ./mirror          # download providers for a mirror
terraform providers lock -platform=linux_amd64 -platform=darwin_arm64

Lock files should include checksums for every platform your team and CI use, or developers on different machines will see "checksum mismatch" and reach for workarounds.

§3Modules

  • Pin to a version or commit SHA, not a branch. Tags can be moved; a commit hash cannot.
  • Review the diff when upgrading, since modules run with your permissions.
  • Prefer a vendored or private-registry copy of third-party modules you rely on, so upstream deletion or tampering cannot affect you.
  • Check who maintains it, how active it is, and how many people use it.

§4Keeping Current Without Surprises

Automated update tools (Renovate, Dependabot) open pull requests when new provider and module versions appear. They turn upgrades into reviewed changes with a plan attached, rather than silent drift.

Upgrades are changes too A dependency bump can alter plans and run new code. Treat every upgrade like a deploy: read the changelog, run the plan in a test environment, and only then promote it.

§5Common Mistakes

MistakeWhat HappensFix
Deleting the lock file when it complainsVerification is bypassed and builds are no longer reproducibleUpdate it deliberately with init -upgrade and fix platform hashes
Referencing a module by branchContents change without any change on your sidePin to a version tag or commit SHA
Installing directly from the public registry in CIExposure to outages and tamperingUse a mirror or private registry
Practice
  1. Run terraform providers lock for your team's platforms and commit the result.
  2. Pick one third-party module you use, read every resource it creates, and decide whether to pin, vendor, or replace it.
Key takeaways
  • Providers and modules execute with your credentials, so treat them as trusted code that must be earned.
  • Lock files, signed registries, mirrors, and pinned refs reduce supply-chain risk.
  • Review upgrades like deployments, and automate the pull requests that propose them.
