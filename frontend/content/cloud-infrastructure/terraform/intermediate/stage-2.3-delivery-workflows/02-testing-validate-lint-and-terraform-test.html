Testing: Validate, Lint & terraform test

Infrastructure code can be tested like any other. Layer cheap checks first and run expensive ones sparingly.

§1The Cheap Layer

Run these on every commit. They need no cloud account.

terraform fmt -check -recursive
terraform validate
tflint --recursive            # provider-aware linting, catches invalid instance types and more
trivy config .                # security misconfiguration scanning (tfsec's rules now live here)

checkov is another popular scanner for the same job. Static analysis catches unencrypted storage, open ports, and invalid values before any plan runs.

§2terraform test

Terraform has a built-in test framework. Test files end in .tftest.hcl and contain run blocks that execute a plan or apply and check assertions.

# tests/bucket.tftest.hcl
variables {
  name = "test-bucket"
}

run "creates_private_bucket" {
  command = plan

  assert {
    condition     = aws_s3_bucket.this.bucket == "test-bucket"
    error_message = "Bucket name did not match the input."
  }
}

run "rejects_bad_name" {
  command = plan
  variables { name = "Bad Name" }
  expect_failures = [var.name]
}

Tests with command = plan run quickly and create nothing. Tests with command = apply create real resources and then destroy them. Mock providers let a test run without calling a real API at all.

mock_provider "aws" {}

§3Higher Layers

For full integration tests, tools such as Terratest deploy a module into a sandbox account, check that it works, and destroy it. They are slow and cost money, so run them on module changes or nightly, not on every commit.

Test the contract, not the provider You do not need to assert that AWS can create a bucket. Test your own logic: validations, conditionals, naming, and the outputs your callers depend on.

§4Common Mistakes

MistakeWhat HappensFix
Relying only on validateValid-looking code that is insecure or wrong in practiceAdd linting, scanning, and plan-level tests
Running full apply tests on every commitSlow pipelines and real costUse plan tests and mocks for most checks, and keep apply tests for key modules
Tests in a shared accountLeftover resources and name collisionsUse a dedicated sandbox account and unique names
Practice
  1. Write a terraform test with one passing assertion and one expect_failures case for a validated variable.
  2. Run tflint and trivy config on a module and fix the first finding of each.
Key takeaways
  • Layer checks: format, validate, lint, scan, test, then integration.
  • terraform test supports plan-only runs, applies, and mocked providers.
  • Test your own logic and interface, not the cloud's behavior.
