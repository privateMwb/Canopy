Terraform in CI/CD

Running Terraform from laptops does not scale. A pipeline that plans on every pull request and applies on merge makes changes reviewed, repeatable, and recorded.

§1The Standard Flow

  1. A developer opens a pull request with a configuration change.
  2. CI runs fmt, validate, and plan, and posts the plan to the pull request.
  3. Reviewers read the plan alongside the code.
  4. After approval and merge, CI applies the change, ideally the exact plan that was reviewed.
# .github/workflows/terraform.yml (abridged)
name: terraform
on:
  pull_request:
  push:
    branches: [main]

permissions:
  id-token: write       # for OIDC to the cloud
  contents: read
  pull-requests: write

jobs:
  plan:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init -input=false
      - run: terraform fmt -check
      - run: terraform validate
      - run: terraform plan -input=false -out=tfplan -no-color

Pin third-party actions to a version or commit, and prefer short-lived cloud credentials through OIDC (lesson 2.3.4) over stored keys.

§2Applying Safely

terraform apply -input=false tfplan

-input=false stops Terraform from waiting for a prompt that nobody will answer. Gate the apply job behind a protected branch and a required approval, using an environment with reviewers. Use a concurrency group so two pipeline runs never apply against the same state at once, in addition to state locking.

concurrency:
  group: terraform-prod
  cancel-in-progress: false

§3Detecting Changes With Exit Codes

terraform plan -detailed-exitcode returns 0 for no changes, 1 for an error, and 2 when changes are present. That makes scheduled drift checks (stage 3.1) easy to script.

Show the plan where reviewers look A plan nobody reads is just a log. Post it as a pull-request comment or a summary so reviewers see precisely what will change. Truncate or collapse very long plans, but never hide destroys.

§4Common Mistakes

MistakeWhat HappensFix
Applying from a fresh plan after mergeWhat runs differs from what was reviewedSave the plan as an artifact, or re-plan and require a second look
Long-lived cloud keys in CI secretsA leaked secret gives lasting accessUse OIDC to obtain short-lived credentials
No concurrency controlTwo pipelines race on the same stateUse a concurrency group per state and keep locking enabled
Practice
  1. Write a workflow that runs fmt -check, validate, and plan on every pull request.
  2. Add -detailed-exitcode and make a scheduled job fail when the plan is not empty.
Key takeaways
  • Plan on pull requests, apply on merge, and review the plan with the code.
  • Use -input=false, saved plans, and concurrency groups in pipelines.
  • Short-lived credentials beat stored keys.
