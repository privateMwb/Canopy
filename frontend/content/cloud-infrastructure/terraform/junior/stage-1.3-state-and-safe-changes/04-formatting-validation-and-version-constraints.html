Formatting, Validation & Version Constraints

Format, validate, and pin your versions. These small habits keep a team's runs identical and catch mistakes before they cost anything.

§1fmt and validate

terraform fmt              # rewrite files to canonical style
terraform fmt -check       # exit non-zero if anything needs formatting (for CI)
terraform validate         # check syntax and internal consistency, no API calls

validate catches typos, wrong argument names, and bad references without credentials, which makes it a good first gate in any pipeline. It does not check whether values are valid for the real cloud.

§2Version Constraints

Pin the Terraform CLI and every provider so a teammate or a CI runner does not silently get something different.

terraform {
  required_version = ">= 1.9, < 2.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"      # >= 5.0 and < 6.0
    }
  }
}

The pessimistic operator ~> allows only the rightmost version component to increase: ~> 5.2 means >= 5.2, < 6.0, while ~> 5.2.1 means >= 5.2.1, < 5.3.0.

§3The Lock File

terraform init writes .terraform.lock.hcl, recording the exact provider versions and checksums chosen. Commit this file. It makes every machine install the identical build, and it detects tampering. To move forward on purpose, run terraform init -upgrade, review the diff to the lock file, and commit it.

Constraints say what is allowed, the lock says what is used A constraint like ~> 5.0 permits many versions; the lock file picks one. Teams that gitignore the lock file get "works on my machine" provider bugs.

§4Common Mistakes

MistakeWhat HappensFix
Gitignoring .terraform.lock.hclDifferent machines resolve different provider versionsCommit it, and update it deliberately with init -upgrade
No version constraint on providersA new major release breaks plans unexpectedlyConstrain to the major version you tested
Skipping fmt in reviewNoisy, whitespace-only diffsRun fmt -check in CI
Practice
  1. Add required_version and a provider constraint, run terraform init, and inspect the generated lock file.
  2. Introduce a typo in an argument name and see which command catches it: fmt, validate, or plan.
Key takeaways
  • fmt and validate are free, fast gates to run on every change.
  • Constrain Terraform and provider versions, and commit the lock file.
  • Upgrade providers on purpose with init -upgrade, never by accident.
