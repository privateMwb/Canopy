Reading Plans Carefully

The plan is where mistakes are cheap. Learn to read each kind of change, and to spot the one that destroys data.

§1The Symbols

  # aws_s3_bucket.logs will be created
  + resource "aws_s3_bucket" "logs" { ... }

  # aws_instance.web will be updated in-place
  ~ resource "aws_instance" "web" {
      ~ instance_type = "t3.micro" -> "t3.small"
    }

  # aws_db_instance.main must be replaced
-/+ resource "aws_db_instance" "main" {
      ~ identifier = "app-db" -> "app-database" # forces replacement
    }
  • + create
  • ~ update in place, nothing destroyed
  • - destroy
  • -/+ replace: destroy then create (or +/- for create first, when create_before_destroy is set)

§2Finding the Dangerous Line

A replacement is the plan item to slow down on. Look for the annotation # forces replacement next to an argument: that argument cannot be changed in place, so the provider must delete and recreate the resource. For a stateless server that may be fine. For a database or a volume, replacement means the data is gone.

Also notice (known after apply). It means the value (an ID, an IP address) does not exist yet and will be filled in during apply. It is normal for new resources and for anything that depends on one.

§3Save the Plan You Reviewed

terraform plan -out=tfplan          # write the plan to a file
terraform show tfplan               # read it again
terraform apply tfplan              # apply exactly this, no re-planning

Applying a saved plan guarantees what runs is what you approved, even if the cloud or code changed in between.

Count the totals The last line, such as Plan: 1 to add, 2 to change, 1 to destroy, is your sanity check. If you expected a one-line edit and see a destroy, stop and find out why before typing yes.

§4Common Mistakes

MistakeWhat HappensFix
Approving a plan without scrollingA hidden -/+ replaces a databaseRead every resource line, and search for forces replacement
Assuming ~ is always safeSome in-place updates still cause brief disruptionCheck the provider docs for what an update does
Re-planning before apply in a pipelineThe applied change differs from the reviewed oneApply the saved plan file
Practice
  1. Change an immutable argument (like an RDS identifier or EC2 availability_zone) and find the forces replacement line in the plan.
  2. Save a plan to a file, change the code, then apply the file. Which version ran?
Key takeaways
  • +, ~, -, and -/+ tell you exactly what will happen to each resource.
  • # forces replacement marks the change that can destroy data.
  • Save and apply a reviewed plan so approval and execution match.
