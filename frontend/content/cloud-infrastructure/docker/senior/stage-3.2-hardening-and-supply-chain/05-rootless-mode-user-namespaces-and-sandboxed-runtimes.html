Rootless Mode, User Namespaces & Sandboxed Runtimes

Rootless mode and user namespaces shrink what a breakout can do, and sandboxed runtimes add a second boundary for code you do not trust.

§1Rootless Docker and User Namespaces

In normal Docker, the daemon runs as root and container root is host UID 0, so a breakout lands as root. Two mitigations change that:

  • User namespace remapping (userns-remap in daemon.json) maps container UIDs to an unprivileged range on the host, so container root is just an unprivileged user outside.
  • Rootless mode runs the daemon and containers entirely as an ordinary user, with no root daemon at all.
dockerd-rootless-setuptool.sh install
export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/docker.sock
docker run --rm alpine id            # root inside, your user outside
cat /proc/self/uid_map

Trade-offs: privileged ports, some networking features, certain storage drivers, and cgroup limits may need extra setup, and performance of rootless networking is lower. Podman is rootless by default, which makes it a popular option here.

§2Sandboxed Runtimes

When kernel sharing is not acceptable, put another boundary between the workload and the host kernel:

RuntimeApproachTrade-off
runc (default)Namespaces and cgroups on the host kernelFastest; shared kernel
gVisor (runsc)A user-space kernel intercepts syscallsSmaller host attack surface; some syscall and I/O overhead, incomplete compatibility
Kata ContainersEach container (or pod) runs in a lightweight VMStrong isolation; higher memory and startup cost
Firecracker-style microVMsMinimal VMs with a stripped device modelStrong isolation, fast boots; more integration work
docker run --rm --runtime=runsc alpine uname -a      # kernel the app sees is gVisor's

Register the alternate runtime in daemon.json and choose it per container or per workload class. Test applications first, since unusual syscalls, filesystem features, or device access may not work.

§3Choosing the Boundary

  • Your own services, trusted code: hardened runc with non-root, seccomp, dropped capabilities.
  • Third-party plugins, customer-supplied code, CI jobs running unreviewed code, or multi-tenant platforms: a sandboxed runtime or a VM per tenant.
  • Highly regulated or hostile workloads: dedicated hosts or accounts in addition to a sandbox.
Isolation costs, so spend it where the threat is Applying VM-grade isolation to everything is expensive; applying none to untrusted code is dangerous. Classify workloads by trust and give each class the cheapest boundary that meets the threat.

§4Common Mistakes

MistakeWhat HappensFix
Enabling rootless and assuming it is a sandboxKernel is still sharedAdd sandboxed runtimes for untrusted code
Moving everything to gVisor without testingCompatibility and performance failuresPilot per workload and measure
Running third-party code in plain runc containersOne kernel bug exposes the hostUse Kata, gVisor, or per-tenant VMs
Practice
  1. Install rootless Docker (or Podman) and compare the host UID of a container's process with ps, then explain what a breakout would gain.
  2. Run a simple workload under gVisor or Kata if available, and note any syscall or performance differences.
Key takeaways
  • Rootless mode and user namespaces make container root unprivileged on the host.
  • gVisor and Kata add a boundary between workload and host kernel at some cost.
  • Pick the boundary according to how much you trust the code.
