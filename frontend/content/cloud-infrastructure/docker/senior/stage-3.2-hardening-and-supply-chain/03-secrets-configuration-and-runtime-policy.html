Secrets, Configuration & Runtime Policy

A platform delivers secrets by short-lived, identity-based means and enforces policy automatically, because relying on each team to configure everything correctly does not scale.

§1Secrets Delivery Patterns

PatternHow it worksWeakness
Environment variablesSet at startVisible in inspect and /proc, inherited by children
Mounted file (tmpfs)Platform writes a secret fileNeeds a delivery mechanism
Secrets manager fetchApp or sidecar pulls with its identityNeeds a bootstrap credential
Workload identityPlatform issues a short-lived token (OIDC, cloud IAM role)Platform setup effort

The strongest pattern minimizes standing secrets: the workload proves who it is, and a manager issues a short-lived credential. Rotation then becomes routine, and a leaked token expires soon after.

# file-based secret read at startup, never logged
DB_PASSWORD="$(cat /run/secrets/db_password)"
# short-lived credentials from an agent/sidecar
vault read -field=password database/creds/api    # example: dynamic DB creds

§2Enforcing Policy on Docker Hosts

Policy should be checked by machines before containers run. Typical rules:

  • No --privileged, host namespaces, or Docker socket mounts.
  • Must run as non-root, with a read-only root filesystem and dropped capabilities.
  • Images must come from approved registries, be pinned by digest, and carry a valid signature.
  • Resource limits and log rotation must be set.

Enforcement points include CI checks on Compose files and Dockerfiles (linters such as Hadolint, config scanners such as Trivy config, and policy engines such as Open Policy Agent with Conftest), Docker authorization plugins or an enterprise access layer for the daemon, and, on Kubernetes, admission controllers.

hadolint Dockerfile
conftest test compose.yaml -p policy/
trivy config .

§3Making Compliance the Easy Path

Provide templates: a base Dockerfile, a Compose skeleton, and a CI pipeline that already satisfy the policy. Let teams request time-boxed exceptions with an owner and expiry. Measure compliance continuously, report it, and fail builds for hard rules while warning on soft ones.

A rule nobody can follow becomes a workaround Policies that block routine work without a documented alternative get bypassed through shadow infrastructure. Pair every restriction with a supported way to achieve the goal.

§4Common Mistakes

MistakeWhat HappensFix
Same long-lived secret in every environmentOne leak compromises all of themUse per-environment, short-lived, scoped credentials
Policy documented but not enforcedDrift and silent violationsCheck automatically in CI and at deploy
Exceptions with no owner or expiryTemporary exceptions become permanentRecord an owner and an end date for each
Practice
  1. Write a policy that rejects a Compose file mounting the Docker socket or running privileged, and test it against a good and a bad file.
  2. Replace a static database password with a file mounted from a secret source and describe how you would rotate it.
Key takeaways
  • Prefer identity-based, short-lived credentials delivered as files to static environment secrets.
  • Express platform rules as automated checks in CI and at deploy.
  • Provide secure templates and managed exceptions so compliance is the easy path.
