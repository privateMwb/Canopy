Storage Drivers, Volumes & I/O Performance

The copy-on-write layers that make images efficient add overhead for write-heavy workloads, which is why data belongs in volumes and why the filesystem choice matters.

§1Where the Bytes Live

On Linux, Docker's data lives under /var/lib/docker:

sudo du -sh /var/lib/docker/*
# overlay2/   image layers and container writable layers
# volumes/    named volumes (_data directories)
# containers/ logs and config per container

Writes into the container's own filesystem go through overlayfs: reads of unchanged files are near-native, but the first write to a lower-layer file triggers a copy-up of the entire file, and metadata-heavy workloads pay extra for the union lookup. Volumes bypass the union entirely, giving native filesystem performance.

§2Storage Drivers and Filesystems

ChoiceNotes
overlay2The default and recommended driver on modern Linux; requires a supported backing filesystem (ext4, or xfs with d_type)
btrfs, zfsSnapshot-native drivers, useful when you already operate those filesystems
fuse-overlayfsUsed for rootless mode when native overlay is unavailable
containerd snapshottersThe newer image store uses containerd snapshotters such as overlayfs

Put /var/lib/docker on fast, dedicated storage with enough inodes, and monitor both space and inode use, because many small layers consume inodes quickly. Avoid network filesystems for the layer store.

§3Volume Performance in Practice

  • Databases and write-heavy data: always a named volume or a bind mount to fast local disk.
  • Bind mounts on macOS and Windows: cross a VM boundary and can be several times slower; use volumes for dependency directories.
  • tmpfs: memory-backed and very fast for scratch data, lost on stop, and counted against memory limits.
  • Volume drivers can place data on NFS, cloud block storage, or other backends, with the latency and consistency characteristics of the backend.
docker run --rm -v testvol:/data alpine sh -c \
  'dd if=/dev/zero of=/data/f bs=1M count=1024 oflag=direct'
docker run --rm alpine sh -c \
  'dd if=/dev/zero of=/f bs=1M count=1024 oflag=direct'      # writable layer
docker run --rm --tmpfs /data:rw,size=1g alpine sh -c \
  'dd if=/dev/zero of=/data/f bs=1M count=1024'

Use fio for serious benchmarks, and also limit I/O fairly with --device-write-bps and --blkio-weight where noisy neighbors matter.

Measure on the real storage path Benchmarks on a laptop bind mount say nothing about a cloud volume under production load. Test on the same storage class, filesystem, and mount type that production uses, with realistic block sizes and concurrency.

§4Common Mistakes

MistakeWhat HappensFix
Running a database on the writable layerSlow writes, lost data on removalMount a volume on its data directory
Ignoring inode exhaustion"No space left on device" with free blocksMonitor df -i for /var/lib/docker
Using NFS for the layer storePoor performance and locking problemsKeep layers local; use NFS only for application data if needed
Practice
  1. Compare write throughput for the container writable layer, a named volume, and tmpfs with dd or fio.
  2. Find a container's data under /var/lib/docker/overlay2 and a volume under /var/lib/docker/volumes.
Key takeaways
  • Overlay copy-on-write adds overhead; volumes give native speed and persistence.
  • Choose the filesystem, driver, and mount type deliberately, and watch inodes as well as bytes.
  • Benchmark on the real storage path before drawing conclusions.
