Container Networking Internals

Container networking is a Linux bridge, pairs of virtual ethernet devices, and firewall rules for NAT, nothing more exotic than that.

§1veth Pairs and the Bridge

Each container gets its own network namespace. Docker connects it to the host with a veth pair, a virtual cable with one end inside the container (eth0) and the other attached to a bridge on the host (docker0 for the default network, br-<id> for user-defined ones).

ip link show type bridge
ip link show type veth                       # one host-side end per container
docker exec web ip addr show eth0
bridge link                                  # which veths are on which bridge
sudo nsenter -t $(docker inspect -f '{{.State.Pid}}' web) -n ip route

The bridge acts as a layer-2 switch among its attached containers and as the default gateway for traffic leaving them. Containers on different user-defined networks sit on different bridges and are isolated from each other by firewall rules.

§2NAT and Port Publishing

Outbound traffic is masqueraded: the host rewrites the container's private source address to its own. Inbound published ports use DNAT, which rewrites the destination from the host's address and port to the container's.

sudo iptables -t nat -L POSTROUTING -n | grep MASQUERADE
sudo iptables -t nat -L DOCKER -n            # DNAT rules for published ports
sudo iptables -L DOCKER-USER -n              # your own filtering hook
sudo nft list ruleset | grep -i docker       # on nftables-based systems

-p 8080:80 adds a DNAT rule from host port 8080 to container IP port 80. Docker also has a userland docker-proxy process for some cases such as loopback access. Because Docker inserts its rules ahead of typical firewall front ends, a published port can be reachable even if your host firewall appears to deny it; place restrictions in the DOCKER-USER chain.

§3Embedded DNS and Service Discovery

On user-defined networks, containers use Docker's embedded DNS resolver at 127.0.0.11, which Docker intercepts and answers from its knowledge of container names, aliases, and service names, forwarding other queries to the host's resolvers.

docker exec web cat /etc/resolv.conf         # nameserver 127.0.0.11
docker exec web nslookup db
sudo tcpdump -ni docker0 port 8080           # watch traffic on the bridge
Debug networking like Linux, because it is There is no special container networking tool required: ip, ss, tcpdump, and the firewall listings from the host and from nsenter will explain nearly any issue. Start by finding which namespace and which interface a packet should cross.

§4Common Mistakes

MistakeWhat HappensFix
Relying on a host firewall to block published portsDocker's rules bypass itFilter in DOCKER-USER or avoid publishing the port
Overlapping subnets with a VPN or LANContainers cannot reach the real networkConfigure default-address-pools or the network's subnet
Assuming docker-proxy handles everythingMissing the NAT rules that do the real workInspect the nat table and bridge state
Practice
  1. Find the veth interface on the host for a running container and prove its pairing by comparing interface indexes with ip link inside and outside.
  2. List the DNAT rule created by -p, then remove the container and confirm the rule disappears.
Key takeaways
  • Bridges, veth pairs, and routing connect containers; NAT and DNAT connect them to the outside.
  • Docker's firewall rules take precedence, so use DOCKER-USER for your own restrictions.
  • Standard Linux tools in the right namespace diagnose container networking.
