Observability & Performance of Containers

Container metrics come from cgroups, and the signals that explain most production problems are CPU throttling, memory pressure, I/O waits, and restarts.

§1What to Measure

SignalWhere it comes fromWhat it tells you
CPU usagecpu.stat usage_usecWork actually done
CPU throttlingcpu.stat nr_throttled, throttled_usecTime the app was denied CPU by its quota
Memory working setmemory.current minus inactive file cacheWhat would be hard to reclaim

Restarts and exitsEngine state and eventsCrash loops and exit codes
Network and block I/OInterface and io.stat countersSaturation and slow storage
docker stats --no-stream
cat /sys/fs/cgroup/system.slice/docker-<id>.scope/cpu.stat
cat /sys/fs/cgroup/system.slice/docker-<id>.scope/memory.events

Collectors such as cAdvisor, the Prometheus node exporter, and OpenTelemetry agents scrape these and expose them to dashboards. Pair infrastructure metrics with application metrics (latency, errors, saturation) and logs and traces.

§2Throttling and Memory Pitfalls

CPU throttling causes latency spikes even when average CPU looks low: with a quota of 1 CPU, a multithreaded app can burn its whole 100 ms period budget in 20 ms of wall time on several cores, then stall for the remaining 80 ms. Watch the throttled period ratio, and consider raising or removing CPU limits for latency-sensitive services while keeping reservations or shares. Memory is hard-limited: working set approaching memory.max leads to reclaim, then OOM kills. Page cache counts against the limit but is reclaimable, so do not alarm on raw usage; alarm on working set and on oom_kill events. Runtimes with their own heaps (JVM, Go, Node) need limits tuned to the container so total process memory stays under the cgroup limit.

dmesg -T | grep -i 'killed process'          # host-side evidence of OOM kills
docker events --filter event=oom --since 1h

§3Noisy Neighbors and Fairness

Containers on a host share CPU caches, memory bandwidth, disk, and network. One heavy batch job can slow a latency-critical service. Mitigate with CPU shares or pinning (--cpuset-cpus), I/O weights, per-container PID limits, separate hosts for critical and batch workloads, and by monitoring host-level saturation (load, pressure stall information in /proc/pressure) alongside container metrics.

Averages hide the problem Mean CPU of 30% can coexist with severe throttling and bad p99 latency. Alert on throttling ratio, working-set-to-limit ratio, OOM kills, and restart counts, and always look at percentiles, not averages.

§4Common Mistakes

MistakeWhat HappensFix
Setting tight CPU limits on latency-sensitive servicesThrottling and slow tail latencyRaise or remove CPU limits, and use requests or shares
Alerting on raw memory usage including cacheFalse alarmsAlert on working set and OOM events
Watching only container metricsHost contention goes unseenAdd host pressure and saturation metrics
Practice
  1. Run a multi-threaded CPU load with --cpus 1 and read nr_throttled from cpu.stat before and after.
  2. Produce an OOM kill on purpose and find the evidence in memory.events, docker events, and dmesg.
Key takeaways
  • Container metrics come from cgroup files; throttling and working set matter most.
  • Limits cause two failure modes: CPU throttling (slow) and OOM kills (dead).
  • Monitor host saturation to catch noisy neighbors.
