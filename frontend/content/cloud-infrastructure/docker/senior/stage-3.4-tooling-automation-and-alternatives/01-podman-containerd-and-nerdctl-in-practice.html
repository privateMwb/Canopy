Podman, containerd & nerdctl in Practice

Because images and runtimes follow OCI standards, the same container can run under Podman, nerdctl on containerd, or Docker, with differences mostly in daemon design and tooling.

§1Podman: Daemonless and Rootless

Podman runs containers as child processes of the command that starts them, with no central root daemon. It is rootless by default, uses a Docker-compatible CLI, and understands pods (groups of containers sharing a network namespace, like Kubernetes pods).

podman run -d --name web -p 8080:80 docker.io/library/nginx
podman ps
podman generate kube web > web.yaml      # export as Kubernetes YAML
podman play kube web.yaml                # run Kubernetes YAML locally
podman compose up -d                     # uses a Compose provider

Podman integrates with systemd: Quadlet files describe containers as systemd units, so they start at boot and restart on failure without any daemon of their own.

# ~/.config/containers/systemd/web.container
[Container]
Image=docker.io/library/nginx
PublishPort=8080:80

[Service]
Restart=always

[Install]
WantedBy=default.target

Differences to expect: fully qualified image names are advised (no implicit Docker Hub in every configuration), rootless networking uses a user-space stack with some limits, and Compose support depends on which provider you configure.

§2containerd and nerdctl

containerd is the runtime Kubernetes commonly uses. Its own CLI ctr is low-level, so nerdctl provides a Docker-like experience on top of it, with additions such as lazy-pulling image formats and rootless mode:

sudo nerdctl run -d --name web -p 8080:80 nginx
sudo nerdctl compose up -d
sudo nerdctl -n k8s.io ps               # containers in Kubernetes' namespace
sudo crictl ps                          # Kubernetes-oriented view of the same runtime

containerd uses namespaces to separate clients (moby for Docker, k8s.io for Kubernetes, default for nerdctl), which is why one tool does not automatically see another's containers.

§3Choosing and Migrating

OptionStrengthConsider when
Docker EngineMature ecosystem, best tooling and docsDefault for development and single hosts
PodmanRootless, daemonless, systemd-nativeSecurity-focused hosts, RHEL-family systems
containerd + nerdctlSame runtime as KubernetesDebugging nodes, minimal installs

To migrate, verify image compatibility (OCI), replace Docker-specific socket assumptions (tools that mount /var/run/docker.sock may need Podman's compatible socket), and test Compose files, networking, volumes, and build behavior on the target engine.

Test the whole workflow, not just run podman run working proves little. Check builds, Compose, volume ownership, ports below 1024, and every tool in your pipeline that talks to the daemon socket.

§4Common Mistakes

MistakeWhat HappensFix
Assuming perfect Docker compatibilityA flag or Compose feature behaves differentlyRun your actual workflows on the target engine
Looking for containers in the wrong containerd namespaceThey appear to be missingPass -n with the right namespace
Tools hardcoded to docker.sockFailures under Podman or nerdctlUse the compatible socket or update the tools
Practice
  1. Run the same Compose application under Docker and under Podman, and list every difference you hit.
  2. Convert a container into a Quadlet unit and confirm it restarts after you kill its process.
Key takeaways
  • OCI standards make images portable across Docker, Podman, and containerd.
  • Podman is daemonless and rootless with systemd integration; nerdctl brings a Docker-like CLI to containerd.
  • Migration risk lives in tooling that assumes the Docker daemon, so test complete workflows.
