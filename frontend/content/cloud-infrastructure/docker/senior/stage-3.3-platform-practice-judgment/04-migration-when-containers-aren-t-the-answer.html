Migration & When Containers Aren't the Answer

Moving legacy software into containers goes best when you pick the right candidates, and some workloads should not be containerized at all.

§1Good Candidates

Stateless services, twelve-factor style applications, batch jobs, tools with complex dependencies, and anything you need to run identically in many places.

§2Containerizing a Legacy App

1. Run it as is: wrap the existing install in a container to learn its needs.

2. Externalize configuration: move settings to environment variables or mounted files.

3. Log to stdout.

4. Separate state: move data to volumes or managed services.

5. Handle signals and health: graceful shutdown and a health endpoint.

6. Remove hidden dependencies: hard-coded paths, local files, IP addresses, cron on the host.

7. Slim it down with multi-stage builds and a proper base.

FROM eclipse-temurin:21-jre AS runtime
COPY app.jar /opt/app/app.jar
USER 10001
ENTRYPOINT ["java", "-jar", "/opt/app/app.jar"]

§3Poor Fits

  • Heavy, stateful databases with demanding I/O may be better as managed services or on dedicated hosts, though containerized databases are common in Kubernetes with care.
  • GUI desktop applications and hardware-dependent software.
  • Workloads needing a different kernel or strong isolation may need VMs.
  • Tiny scripts where a container adds ceremony without value.
  • Licensing or support terms that forbid containers.

§4Migrating Safely

Run old and new side by side, move traffic gradually, compare results, and keep a rollback path. Migrate one service at a time and learn from each.

§5Know When to Stop

Containerization is a means. If an application is stable, rarely changes, and runs well on a VM, the benefit of migrating may not justify the effort.

The key insight Containerize to gain portability, repeatability, or density, and be able to say which one you are after.

§6Common Mistakes

MistakeWhat HappensFix
Lifting a stateful legacy system into a container with state insideData lost on the first redeployExternalize state first
Migrating everything at onceFailures are hard to isolateMove one service at a time with rollback
Containerizing because it is expectedCost with no benefitState the goal and measure the result
Practice
  1. Take a legacy-style app and list the changes needed before it is container-ready.
  2. Write a one-page migration plan with rollback steps for moving one service.
Key takeaways
  • Stateless, configurable, log-to-stdout applications containerize best.
  • Some workloads are better on managed services or VMs.
  • Migrate gradually, with a clear goal and a way back.
