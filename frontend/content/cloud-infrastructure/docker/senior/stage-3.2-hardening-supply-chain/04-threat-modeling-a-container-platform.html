Threat Modeling a Container Platform

Threat modeling asks what can go wrong, so you spend effort on the controls that matter instead of all of them.

§1A Simple Method

1. Draw the system: registry, CI, hosts, containers, networks, secrets, people.

2. List assets: customer data, credentials, build pipeline, production access.

3. Walk the boundaries and ask what an attacker could do at each (a framework such as STRIDE helps).

4. Rate by likelihood and impact.

5. Choose controls and decide what you accept.

§2Typical Attack Paths

  • Vulnerable application inside the container leads to code execution, then to secrets in the environment and access to the cluster or cloud.
  • Compromised dependency or base image leads to malicious code in your build.
  • Stolen CI credential leads to pushing a malicious image.
  • Exposed Docker socket or daemon port leads to full host control.
  • Misconfigured container (privileged, host mounts) leads to host escape.
  • Overly broad cloud role attached to the host leads to damage far beyond the container.
internet → app flaw → container shell → env secrets → cloud role → customer database

§3Controls That Break the Chain

For the path above, any one of these helps: fix the flaw (scanning), remove the shell (distroless), keep secrets out of the environment, narrow the role, and restrict database access by network. Layers matter because one will fail.

§4Prioritizing

Rank by how much each control reduces the most likely, most damaging paths. Often the top list is: non-root and least privilege, patched minimal images, narrow cloud identities, secrets management, network segmentation, and image provenance for production.

§5Keep It Alive

Repeat the exercise when architecture changes, after incidents, and when new attack techniques appear. A threat model on a shelf decays.

The key insight Security work is choosing what to do first. A short ranked list beats a long unprioritized checklist.

§6Common Mistakes

MistakeWhat HappensFix
Listing every possible threat with equal weightNothing gets doneRank by likelihood and impact
Focusing on the container and ignoring the cloud role and CIAttackers go around the controlInclude the whole chain
Doing it onceThe system changes and the model goes staleRevisit it regularly
Practice
  1. Threat-model a small platform (CI, registry, three services, a database) and rank the top five risks.
  2. For one attack path, name three different controls that would each break it.
Key takeaways
  • Threat modeling draws the system, finds attack paths, and ranks the risks.
  • Real attacks chain container flaws to cloud identities, CI, and secrets.
  • Use layers, prioritize, and revisit the model.
