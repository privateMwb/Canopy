The Container Security Model & Isolation Limits

Containers share the host kernel, so their isolation is a stack of layered controls rather than a single strong wall.

§1What Provides Isolation

  • Namespaces and cgroups separate views and resources.
  • Linux capabilities split root's power into pieces that can be dropped.
  • seccomp filters which system calls a process may make. Docker applies a default profile that blocks dozens of risky calls.
  • AppArmor or SELinux add mandatory access control on files, networks, and more.
  • User namespaces and rootless mode make container root map to an unprivileged host user.
docker run --security-opt seccomp=profile.json --security-opt apparmor=my-profile myapp
docker run --userns=host --cap-drop ALL --cap-add NET_BIND_SERVICE myapp
dockerd-rootless-setuptool.sh install        # Docker without root on the host

§2Where It Breaks

Container escapes have come from kernel vulnerabilities, runtime bugs (such as runc flaws), and misconfiguration: privileged mode, the Docker socket, host mounts, and excess capabilities. With a shared kernel, one kernel exploit reaches every container on the host.

§3Stronger Isolation

  • gVisor intercepts system calls in a user-space kernel.
  • Kata Containers and Firecracker run each container or pod in a lightweight VM.
  • Separate hosts or nodes for workloads of different trust levels.
docker run --runtime=runsc myapp             # gVisor, if installed

Stronger isolation costs performance and compatibility, and fits untrusted or multi-tenant code.

§4Matching Controls to Threats

Your own code running in your own cluster needs sensible defaults. Running other people's code (CI for strangers, a hosting platform, plugins) needs sandboxes or VMs, not plain containers.

The key insight Containers are a packaging and resource-control tool that happens to give some isolation. For hostile code, add a VM boundary.

§5Common Mistakes

MistakeWhat HappensFix
Treating containers as a security boundary against hostile codeOne kernel bug escapes to the hostUse gVisor, Kata, or VMs for untrusted workloads
Disabling seccomp or AppArmor to fix an errorDefenses are removed for everythingAdd the specific permission needed
Running everything on the same hosts regardless of sensitivityA compromise spreadsSeparate workloads by trust level
Practice
  1. List the isolation layers a default Docker container has and which attack each one addresses.
  2. Decide what isolation you would use to run customer-submitted code, and defend the choice.
Key takeaways
  • Isolation comes from namespaces, capabilities, seccomp, MAC policies, and user namespaces.
  • Kernel bugs, runtime bugs, and misconfiguration cause escapes.
  • Use sandboxes or VMs when workloads are untrusted.
