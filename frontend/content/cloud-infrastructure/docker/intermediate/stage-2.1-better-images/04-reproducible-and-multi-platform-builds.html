Reproducible & Multi-Platform Builds

A reproducible build gives the same result from the same inputs, and a multi-platform build produces one image reference that works on both Intel and ARM machines.

§1Pin Your Inputs

Reproducibility means controlling everything that can change between builds:

  • Base image: pin to an exact tag, and for strict control a digest: FROM python:3.12.7-slim@sha256:<digest>.
  • Language dependencies: install from a lockfile (npm ci, pip install -r with pinned hashes, go.sum).
  • OS packages: apt-get install curl=<version> is brittle but exact; at minimum, rebuild and scan on a schedule.
  • Downloads: verify checksums when fetching binaries with curl.
RUN curl -fsSLo /tmp/tool.tgz https://example.com/tool-1.4.2.tgz \
 && echo "<sha256>  /tmp/tool.tgz" | sha256sum -c - \
 && tar -xzf /tmp/tool.tgz -C /usr/local/bin

Pinning has a cost: you must update deliberately, so pair it with a tool such as Renovate or Dependabot to propose version bumps.

§2Multi-Platform Images

An image is built for one CPU architecture. A manifest list (also called an image index) groups several, and the client automatically pulls the right one. Buildx builds them:

docker buildx create --use --name multi
docker buildx build --platform linux/amd64,linux/arm64 \
  -t myorg/app:1.0 --push .
docker buildx imagetools inspect myorg/app:1.0

Multi-platform results must be pushed to a registry (or exported), because the local image store traditionally holds one platform at a time. Non-native architectures are built by emulation (QEMU), which is slow, or by native builders for each architecture, which is fast.

§3Writing Portable Dockerfiles

BuildKit provides the build platform and target in variables, so a cross-compiling stage can run natively and still output the right binary:

FROM --platform=$BUILDPLATFORM golang:1.23 AS build
ARG TARGETOS TARGETARCH
RUN GOOS=$TARGETOS GOARCH=$TARGETARCH go build -o /out/app .
FROM gcr.io/distroless/static-debian12
COPY --from=build /out/app /app
Same inputs is not the same bytes Even with pinned inputs, timestamps and file ordering can make image digests differ between builds. True bit-for-bit reproducibility needs extra controls such as SOURCE_DATE_EPOCH; for most teams, pinned inputs plus a lockfile are the practical goal.

§4Common Mistakes

MistakeWhat HappensFix
Building on an M-series Mac and deploying to amd64exec format error on the serverBuild with --platform linux/amd64 or use a multi-platform build
Pinning once and never updatingBase image accumulates unpatched vulnerabilitiesAutomate version-bump pull requests
Downloading binaries without a checksumA compromised or changed download goes unnoticedVerify a pinned SHA-256
Practice
  1. Pin the base image of a project by digest, rebuild, and note what changes when the upstream tag moves.
  2. Build an image for two platforms with buildx and inspect the manifest list.
Key takeaways
  • Pin base images, dependencies, and downloads, and update them on purpose.
  • Multi-platform images are manifest lists built with buildx --platform.
  • Cross-compile on the build platform where you can; emulation works but is slow.
