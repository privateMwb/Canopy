Image Size Forensics

Reducing an image is a measurement exercise: find which layers are large, learn why, and change one thing at a time.

§1Measure Before Changing

Start with the layer breakdown:

docker images myapp                       # total size
docker history myapp:1.0                  # size contributed by each instruction
docker history --no-trunc --format '{{.Size}}\t{{.CreatedBy}}' myapp:1.0

For an interactive view, tools like dive show the contents of each layer and estimate wasted space. Docker's own docker scout can also summarize image composition. Record the starting size so you can prove each change helped.

§2The Usual Culprits

CulpritCauseRemedy
Build toolchain in the final imageSingle-stage buildMulti-stage build
Package manager cachesapt lists, pip and npm cachesClean in the same RUN, or use cache mounts
Dev dependenciesInstalling everythingnpm ci --omit=dev, separate stages
Copied junkCOPY . . with a weak .dockerignoreIgnore .git, tests, docs, and build output
Files deleted in a later layerLayers are append-onlyDelete in the same RUN that created them
Heavy baseFull OS imageSlim, Alpine, or distroless
Large assets and dataModels or datasets baked into the imageMount or download at run time

§3A Methodical Slimming Pass

# apt: install only what's needed and clean in the same layer
RUN apt-get update \
 && apt-get install -y --no-install-recommends ca-certificates curl \
 && rm -rf /var/lib/apt/lists/*

# remove build leftovers in the layer that made them
RUN pip install --no-cache-dir -r requirements.txt \
 && find /usr/local -name '__pycache__' -type d -exec rm -rf {} +

After each change, rebuild, compare with docker images, and check the image still works. An aggressive cleanup that deletes something the app needs at run time is worse than a larger image.

Total size is not transfer size Layers are compressed and shared. Two images that share a base only download the base once, and registries report compressed sizes that are smaller than docker images shows. Optimize what changes often into small layers for fast pulls.

§4Common Mistakes

MistakeWhat HappensFix
Slimming by guessworkChanges with no measurable effect, or broken imagesMeasure with docker history and dive first
rm in a separate later RUNImage does not shrinkCombine creation and cleanup into one layer
Stripping files the app needsRuntime crash that only appears in productionRun the app's tests and smoke test against the slimmed image
Practice
  1. Take a bloated image, list its three biggest layers, and reduce each one, recording the size after every change.
  2. Compare the compressed size shown in a registry with the size in docker images for the same image.
Key takeaways
  • Use docker history and layer inspection to find where the bytes are.
  • The big wins are multi-stage builds, a smaller base, ignoring junk, and cleaning in the same layer.
  • Verify the slimmed image still works; size is only one goal.
