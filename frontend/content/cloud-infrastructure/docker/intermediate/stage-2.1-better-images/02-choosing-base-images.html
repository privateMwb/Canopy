Choosing Base Images

The base image sets your size, your compatibility, and your attack surface, so the right choice depends on what you must debug and what you must run.

§1The Common Families

BaseSize (rough)What you getTrade-off
Full Debian/Ubuntu (python:3.12)Hundreds of MBCompilers, many toolsLarge, many packages to patch
Slim (python:3.12-slim)Tens to ~150 MBDebian without extrasMissing build tools; add what you need
Alpine (python:3.12-alpine)Under ~60 MBmusl libc and BusyBoxCompatibility surprises
DistrolessA few to tens of MBApp runtime only, no shellHard to debug interactively
scratch0 MBLiterally emptyOnly for static binaries

Sizes vary by version and architecture, so measure your own images with docker images.

§2Alpine Is Not Always Smaller in Practice

Alpine uses musl instead of glibc. Many prebuilt wheels and binaries (notably some Python and Node native packages) expect glibc, so you end up compiling from source, which takes longer, needs build tools, and can erase the size benefit or cause subtle runtime differences. Use Alpine when your stack supports it cleanly, such as Go, many Node apps, and nginx; for Python data and native-extension work, -slim is usually the smoother choice.

§3Distroless and Debuggability

Distroless images contain your runtime and its libraries but no shell or package manager, which removes most tools an attacker would use. The cost is that docker exec -it app sh does not work. Debugging options include a :debug variant (which adds BusyBox), an ephemeral debug container sharing the target's namespaces, or docker debug where available:

docker run --rm -it --pid=container:app --net=container:app \
  --cap-add=SYS_PTRACE busybox sh        # a sidecar in the same namespaces
Choose the smallest base you can still debug A 5 MB image you cannot diagnose at 3 a.m. is not a win. Many teams ship distroless or slim in production and keep a full-featured variant of the same image for development and debugging.

§4Common Mistakes

MistakeWhat HappensFix
Switching to Alpine for size without testingNative packages fail to install or behave differentlyTry -slim first, and test thoroughly if you pick Alpine
Using scratch for a dynamically linked binary"no such file or directory" at startBuild a static binary or use a base with libc
Using floating tags like python:3The base changes underneath youPin a full version and update on purpose
Practice
  1. Build the same app on a full, slim, and Alpine base and tabulate size and build time.
  2. Run an app on a distroless image and try to exec a shell, then attach a debug sidecar instead.
Key takeaways
  • Full images are convenient, slim is the safe default, Alpine and distroless trade compatibility and debuggability for size and attack surface.
  • Alpine's musl libc can break native dependencies; test before committing.
  • Pick the smallest base your team can still operate and debug.
