Health Checks & Graceful Shutdown

A health check tells Docker whether the app works, and graceful shutdown lets it finish in-flight work when the container is told to stop.

§1Defining a Health Check

HEALTHCHECK --interval=15s --timeout=3s --start-period=20s --retries=3 \
  CMD curl -fsS http://localhost:3000/health || exit 1
services:
  api:
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost:3000/health"]
      interval: 15s
      timeout: 3s
      start_period: 20s
      retries: 3

Status moves between starting, healthy, and unhealthy. start_period gives slow apps time to boot without counting failures. The command must exist inside the image; a minimal image with no curl needs a built-in check mode in your own binary. Plain Docker (outside orchestrators) reports unhealthiness but does not restart on it by itself, so use it with Compose conditions, a supervisor, or monitoring.

§2Signals and PID 1

docker stop sends SIGTERM to the container's main process (PID 1), waits for the grace period (default 10 seconds), then sends SIGKILL. Two things commonly break this:

  • Shell-form commands make /bin/sh PID 1, which does not forward signals. Use the exec form.
  • PID 1 has special rules in Linux: it ignores signals it has no handler for, and it must reap zombie child processes. Many apps are not written to be PID 1.
docker run --init myapp          # adds a tiny init (tini) as PID 1

In Compose, set init: true. Alternatively, install tini and use ENTRYPOINT ["tini", "--"].

§3Handling SIGTERM

The application must act on the signal: stop accepting new connections, finish current requests, close database connections, then exit.

// Node
process.on('SIGTERM', () => {
  server.close(() => process.exit(0));
});
docker stop -t 30 api        # allow 30 seconds before SIGKILL

Test it: if docker stop consistently takes exactly 10 seconds, your app is not receiving or handling SIGTERM and is being killed.

Test shutdown as a feature Graceful shutdown is rarely noticed until a deploy drops requests. Make docker stop timing and exit code a routine check: a clean stop exits quickly with code 0 (or 143 if the runtime reports the signal).

§4Common Mistakes

MistakeWhat HappensFix
Health endpoint that always returns 200Reports healthy while the database is unreachableCheck real dependencies, but keep it cheap
No start_period for a slow appMarked unhealthy during normal startupAdd a start period sized to normal boot time
Shell-form CMDSIGTERM never reaches the app; 10-second stops and dropped requestsExec form, plus --init when needed
Practice
  1. Time docker stop for a service started with shell-form and with exec-form CMD, and explain the difference.
  2. Add a health check to a Compose service and watch the status change when you break the endpoint.
Key takeaways
  • Health checks report state; something else must act on it.
  • SIGTERM must reach your app, so use the exec form and consider an init process.
  • Handle SIGTERM by draining work and exiting before the grace period ends.
