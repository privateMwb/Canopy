Single-Host Production: Reverse Proxy & TLS

A reverse proxy container terminates TLS, obtains certificates automatically, and routes hostnames to the right services, letting one server host several apps safely.

§1The Shape

Only the proxy publishes ports 80 and 443. Applications sit on an internal network and are reached by name:

internet -> :443 proxy (TLS) -> app:3000 / api:8000   (private network)

Everything else, including the database, publishes nothing. Point your DNS records at the server before starting, because certificate issuance needs the domain to resolve to this machine and ports 80 or 443 to be reachable.

§2Caddy: The Simplest Setup

Caddy obtains and renews Let's Encrypt certificates on its own:

services:
  caddy:
    image: caddy:2
    restart: unless-stopped
    ports: ["80:80", "443:443"]
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data         # certificates: persist this!
      - caddy_config:/config
  web:
    image: ghcr.io/myorg/web:1.4.2
    restart: unless-stopped
volumes: { caddy_data: , caddy_config: }
app.example.com {
    reverse_proxy web:3000
}
api.example.com {
    reverse_proxy api:8000
}

Persisting /data matters: if certificates are lost on each restart you can hit Let's Encrypt rate limits. Traefik is the alternative that reads labels on containers to discover routes automatically, which suits setups where services change often:

  web:
    labels:
      - traefik.http.routers.web.rule=Host(`app.example.com`)
      - traefik.http.routers.web.tls.certresolver=le
      - traefik.http.services.web.loadbalancer.server.port=3000

§3Production Hygiene on One Host

  • restart: unless-stopped on every service so the stack returns after a reboot (and enable Docker at boot).
  • Resource limits, log rotation, and health checks on each service.
  • A host firewall allowing only 22, 80, and 443; remember that published Docker ports can bypass some firewall front-ends, so publish as little as possible.
  • Backups of named volumes and the database, plus a tested restore.
  • Pin image tags, and update with docker compose pull && docker compose up -d.
A single host is a single point of failure This setup is genuinely fine for many small services, but a reboot, disk failure, or bad deploy takes everything down. Know the downtime you can tolerate, and have a rebuild-from-scratch plan.

§4Common Mistakes

MistakeWhat HappensFix
Not persisting certificate storageCertificates re-requested and rate-limited after restartsMount a volume for /data (Caddy) or acme.json (Traefik)
Publishing app ports alongside the proxyApps reachable without TLSPublish only the proxy's ports
DNS not pointing at the server before launchCertificate issuance failsCreate DNS records and wait for them to resolve first
Practice
  1. Put two sample apps behind Caddy on two hostnames (or local hostnames using a local CA) and confirm only ports 80 and 443 are published.
  2. Restart the proxy and verify it reuses stored certificates instead of requesting new ones.
Key takeaways
  • One proxy publishes 80 and 443; everything else stays on private networks.
  • Caddy and Traefik automate certificates, and the certificate store must be persistent.
  • Add restart policies, limits, backups, and a firewall before calling it production.
