Compose Profiles, Overrides & Multiple Files

Profiles, override files, and the extends and include features let one Compose project describe several environments without copy-pasted files.

§1Profiles: Optional Services

A service with a profiles list starts only when one of its profiles is enabled. Services without profiles always start.

services:
  web:
    build: .
  db:
    image: postgres:16
  adminer:
    image: adminer
    profiles: [ debug ]
  mailpit:
    image: axllent/mailpit
    profiles: [ dev ]
docker compose up -d                       # web and db only
docker compose --profile debug up -d       # adds adminer
COMPOSE_PROFILES=dev,debug docker compose up -d

Use profiles for developer tools, seed jobs, and test dependencies that production never needs.

§2Override Files and Merging

Compose merges files in order, with later files overriding earlier ones. Scalars are replaced, mappings are merged, and lists such as ports are generally concatenated:

# compose.yaml            (base, valid on its own)
# compose.override.yaml   (auto-applied in development)
# compose.prod.yaml       (explicit, for production)
docker compose -f compose.yaml -f compose.prod.yaml up -d
docker compose -f compose.yaml -f compose.prod.yaml config   # preview the merged result
# compose.prod.yaml
services:
  web:
    image: ghcr.io/myorg/web:${TAG}
    restart: unless-stopped
    deploy:
      resources:
        limits: { memory: 512M }

A common split: the base defines services and wiring, the development override adds bind mounts and published debug ports, and production swaps build: for a pinned image: plus restart policies and limits. Always preview with docker compose config, because merge rules for lists and special cases sometimes surprise people.

§3Reuse Across Projects

  • include: pulls another Compose file into this project, handy for shared infrastructure such as a common database stack.
  • extends: reuses a single service definition from another file.
  • YAML anchors (x-common: &common) share snippets inside one file: x-logging: &logging then logging: *logging.
x-defaults: &defaults
  restart: unless-stopped
  logging:
    driver: local
services:
  web:
    <<: *defaults
    image: myorg/web:1.4.2
  worker:
    <<: *defaults
    image: myorg/worker:1.4.2
One file per concern, not per environment Resist a separate full Compose file for every environment. Keep a valid base and thin overrides containing only the differences, so a change to the base reaches everyone.

§4Common Mistakes

MistakeWhat HappensFix
Overrides that only work with the baseHard to read and debugAlways test with docker compose config and keep overrides small
Expecting ports in an override to replace the basePorts are appended, causing conflictsUse !override / !reset tags where supported, or restructure
Starting profile-only services by name onlyService is not enabledPass --profile, or name the service explicitly with up adminer
Practice
  1. Split a Compose file into a base, a dev override, and a production file, and print the merged result for each.
  2. Add an optional debug profile and start it only when needed.
Key takeaways
  • Profiles make services optional; overrides layer environment differences on a valid base.
  • docker compose config shows the real merged result.
  • Use anchors, include, and extends to avoid repeating definitions.
