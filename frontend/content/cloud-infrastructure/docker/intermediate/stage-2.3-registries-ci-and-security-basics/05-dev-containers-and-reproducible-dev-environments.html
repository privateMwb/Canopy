Dev Containers & Reproducible Dev Environments

A dev container defines the tools, runtime, and editor settings for a project in a file, so a new teammate gets a working environment in minutes.

§1What a Dev Container Is

The Dev Containers specification describes a development environment as a container. Editors such as VS Code, JetBrains products, and GitHub Codespaces read a .devcontainer/devcontainer.json file, build or pull the image, and open your project inside it, with your editor's server running in the container.

{
  "name": "api",
  "image": "mcr.microsoft.com/devcontainers/python:3.12",
  "features": {
    "ghcr.io/devcontainers/features/node:1": {}
  },
  "forwardPorts": [8000],
  "postCreateCommand": "pip install -r requirements.txt",
  "customizations": {
    "vscode": { "extensions": ["ms-python.python"] }
  }
}

Because .devcontainer/ is committed with the code, the environment is versioned alongside it, and "it works on my machine" mostly goes away.

§2Using Compose for Dependencies

When the project needs a database or cache, point the dev container at a Compose file so the whole stack comes up together:

{
  "name": "api",
  "dockerComposeFile": "docker-compose.yml",
  "service": "app",
  "workspaceFolder": "/workspaces/${localWorkspaceFolderBasename}",
  "shutdownAction": "stopCompose"
}

The app service holds your tools and mounts the source; db and cache run as ordinary services alongside it. Reuse the same Dockerfile base for CI so local and pipeline environments match.

§3Trade-offs

  • Pros: fast onboarding, identical toolchains, a clean machine, and easy switching between projects with conflicting requirements.
  • Cons: file-sharing slowness on macOS and Windows (keep the repo in a volume or in WSL), more RAM use, and editor integrations that behave slightly differently.
  • Security: a dev container runs your code with your credentials; limit mounts, and avoid mounting your home directory or SSH keys when you can forward an agent instead.
Treat the dev image like production code Pin versions, rebuild regularly, and keep the image small enough to pull in a minute. A stale, slow dev container is quickly abandoned.

§4Common Mistakes

MistakeWhat HappensFix
Installing tools by hand inside the running containerChanges vanish on rebuildPut them in the Dockerfile, features, or postCreateCommand
Differing toolchains between dev container and CI"Works in the editor, fails in CI"Share the same base image and versions
Mounting the whole home directoryCredentials and files exposed to project codeMount only the workspace and forward the SSH agent
Practice
  1. Add a .devcontainer/devcontainer.json to a small project and open it in a dev container-capable editor.
  2. Extend it with a Compose-managed database and confirm the app connects by service name.
Key takeaways
  • Dev containers store the development environment in the repository.
  • Compose integration brings dependencies up with the workspace.
  • Keep them pinned, lean, and as narrowly mounted as you can.
