Registries & Image Promotion

A registry stores your images, and a good tagging strategy lets you promote the exact same image from test to production instead of rebuilding it.

§1Pushing to a Registry

docker login ghcr.io
docker tag myapp:1.0 ghcr.io/myorg/myapp:1.0
docker push ghcr.io/myorg/myapp:1.0
docker pull ghcr.io/myorg/myapp:1.0

A tag is just another name for an image ID; docker tag adds a name and docker push uploads the layers the registry does not already have. Common choices are Docker Hub, GitHub Container Registry, Amazon ECR, Google Artifact Registry, Azure Container Registry, and self-hosted options such as Harbor or the open-source registry image. Store credentials with a credential helper rather than plain text in ~/.docker/config.json.

§2A Tagging Strategy

TagExamplePurpose
Git commit SHAmyapp:3f2a9c1Unique, traceable, immutable by convention
Semantic versionmyapp:1.4.2Human-readable releases
Branch or channelmyapp:main, myapp:stagingMoving pointers for environments
latestmyapp:latestConvenience only; avoid in deployments

Tag the same build with several names at once: the commit SHA for traceability and a version for humans. Deploy by SHA or digest, never by a moving tag, so you always know what is running. Some registries support immutable tags, which stop a tag from being overwritten.

§3Promotion: Build Once, Move the Image

Rebuilding the "same" code for production can produce a different image, so what you tested is not what you ship. Promotion moves one built image through environments by retagging, with no rebuild:

docker pull ghcr.io/myorg/myapp:3f2a9c1
docker tag  ghcr.io/myorg/myapp:3f2a9c1 ghcr.io/myorg/myapp:staging
docker push ghcr.io/myorg/myapp:staging
# after tests pass:
docker tag  ghcr.io/myorg/myapp:3f2a9c1 ghcr.io/myorg/myapp:1.4.2
docker push ghcr.io/myorg/myapp:1.4.2

With docker buildx imagetools create --tag new old you can retag directly in the registry without pulling. Configure retention policies so old untagged images are cleaned up, since registries bill for storage.

The digest is the identity Tags describe intent; the digest proves identity. Log the digest at deploy time. If production and staging report the same digest, they are running the same bytes.

§4Common Mistakes

MistakeWhat HappensFix
Deploying latestNo record of what runs, and surprise upgradesDeploy by SHA or digest
Rebuilding for each environmentThe production image differs from the tested oneBuild once, promote by retagging
No cleanup policyRegistry storage and cost grow foreverSet retention rules for untagged and old images
Practice
  1. Push an image to a registry under both a commit SHA and a version tag, then retag it as staging without rebuilding.
  2. Compare the digests of the three tags to confirm they point to the same image.
Key takeaways
  • Tag with a commit SHA for traceability and a version for people, and deploy by SHA or digest.
  • Promote one built image through environments; do not rebuild per environment.
  • Use registry retention and immutability features to control cost and risk.
