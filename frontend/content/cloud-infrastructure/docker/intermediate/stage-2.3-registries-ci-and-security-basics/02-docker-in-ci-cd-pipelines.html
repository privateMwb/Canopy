Docker in CI/CD Pipelines

A CI pipeline builds the image once, tests it, and pushes it, and the main challenge is keeping builds fast on runners that start with an empty cache.

§1The Standard Pipeline Shape

checkout -> build image -> run tests against it -> scan -> push (main only)

In GitHub Actions, the official Docker actions wrap this:

name: build
on: { push: { branches: [main] }, pull_request: {} }
jobs:
  image:
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write }
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        if: github.event_name != 'pull_request'
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: ${{ github.event_name != 'pull_request' }}
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

Check each action's current major version before copying, as they are updated regularly. The same ideas apply in GitLab CI, Jenkins, CircleCI, and others.

§2Caching on Ephemeral Runners

Fresh runners have no local layer cache, so every build starts cold. Export and import the BuildKit cache:

Cache typeWhere it livesNotes
ghaGitHub's cache serviceEasy in GitHub Actions, size-limited
registryA tag in your registryWorks on any CI; slower to restore
localA directory you persistGood with CI cache features
docker buildx build \
  --cache-from type=registry,ref=ghcr.io/myorg/myapp:buildcache \
  --cache-to   type=registry,ref=ghcr.io/myorg/myapp:buildcache,mode=max \
  -t ghcr.io/myorg/myapp:$SHA --push .

mode=max also caches intermediate stages, which matters for multi-stage builds. A well-ordered Dockerfile still matters most: the cache only helps if the dependency layer is stable.

§3Testing and Security in the Pipeline

  • Run tests in the image you will ship, or in a test stage built from the same Dockerfile, so you test what you deploy.
  • Push only from trusted branches; pull requests, especially from forks, should build but not receive credentials.
  • Use short-lived credentials (OIDC to your cloud or registry) rather than long-lived tokens stored as secrets where possible.
  • Avoid mounting the Docker socket into CI containers; it gives root-equivalent control of the host. Prefer rootless builders or dedicated build services.
A pipeline is a production system Whoever can change the pipeline can ship to production. Review pipeline changes like code, scope tokens narrowly, and never print secrets in logs.

§4Common Mistakes

MistakeWhat HappensFix
Cold cache on every runTen-minute builds for one-line changesExport and import cache with cache-from and cache-to
Pushing from pull requestsUntrusted code gets registry credentialsRestrict push to protected branches
Mounting /var/run/docker.sock into a jobThe job can control the whole hostUse rootless or isolated build runners
Practice
  1. Write a pipeline that builds on every pull request but pushes only from main, and tags images with the commit SHA.
  2. Compare build times with and without registry caching over three successive commits.
Key takeaways
  • Build once in CI, test the same image, and push only from trusted branches.
  • Export BuildKit cache because runners start empty.
  • Treat CI credentials and the Docker socket as high-value targets.
