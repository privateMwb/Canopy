Build Context & .dockerignore

The build context is the set of files docker build sends to the builder, and anything you do not need in it slows builds and may leak into your image.

§1What the Context Is

When you run docker build -t app ., the final . is the context: the directory whose contents the builder can COPY from. Paths in COPY are relative to the context, and a Dockerfile cannot reach outside it (COPY ../secrets.txt . fails). If your project folder contains a 2 GB node_modules, a .git directory, and test data, all of it is candidate material for transfer. Large contexts make every build start slowly, and COPY . . can pull things into the image you never meant to ship.

§2The .dockerignore File

A .dockerignore file in the context root works like .gitignore: matching paths are excluded from the context entirely.

.git
node_modules
dist
*.log
.env
.env.*
Dockerfile
.dockerignore
coverage/
**/__pycache__

Excluding node_modules matters twice: it keeps the context small, and it prevents your host's compiled packages (possibly for a different OS or CPU) from overwriting the ones the image installs for itself. Patterns are matched from the context root. Prefix with ! to re-include something: *.md followed by !README.md ignores all Markdown except the README.

§3Choosing a Context

The context does not have to be the Dockerfile's folder. In a monorepo you can point at a subdirectory and name the Dockerfile separately:

docker build -f services/api/Dockerfile -t api services/api
docker build -f docker/Dockerfile.prod -t app .

Modern BuildKit builds print the amount transferred at the start (look for a line about transferring context). If it is hundreds of megabytes for a small app, your ignore file is missing something.

Treat the context as published If a file is in the context and a COPY or ADD can reach it, it can end up in a layer, and layers are readable by anyone who can pull the image. Always ignore .env files, private keys, and credentials.

§4Common Mistakes

MistakeWhat HappensFix
No .dockerignore at allSlow builds and accidental copying of .git or .envAdd one before your first real build
Copying host node_modules into the imageBinary mismatch, "wrong ELF class" or similar errorsIgnore it and let RUN install dependencies
Assuming ignored files can still be COPYed"file not found" in the buildRemove it from the ignore list, or restructure the context
Practice
  1. Build a project twice, once without and once with a .dockerignore, and compare the context transfer size and time.
  2. Place a fake .env in a project and prove it does not appear in the image by listing the directory with docker run --rm myimage ls -la /app.
Key takeaways
  • The context is everything the builder may read, and COPY cannot go outside it.
  • .dockerignore keeps the context small and keeps secrets and host artifacts out of images.
  • Choose the context and Dockerfile explicitly in monorepos with -f and the final path.
