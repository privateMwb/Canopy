Volumes & Bind Mounts

A container's writable layer dies with the container, so anything you want to keep has to live in a volume or a bind mount.

§1Why Data Disappears

Every container gets a thin writable layer on top of its image. It is deleted with the container, and it is slower than a mounted volume for heavy writes. Run a database without a volume, remove the container, and the data is gone. Docker offers three ways to give a container storage that outlives it or reaches the host:

TypeManaged byTypical use
Named volumeDockerDatabases and app data you want Docker to manage
Bind mountYou (a host path)Source code during development, config files
tmpfsMemory onlyScratch data that must never touch disk

§2Named Volumes

docker volume create pgdata
docker run -d --name db -e POSTGRES_PASSWORD=devpass \
  -v pgdata:/var/lib/postgresql/data postgres:16
docker rm -f db
docker run -d --name db2 -e POSTGRES_PASSWORD=devpass \
  -v pgdata:/var/lib/postgresql/data postgres:16     # same data is back
docker volume ls
docker volume inspect pgdata

The left side of -v name:/path is the volume name, and the right side is where it appears inside the container. If the volume does not exist, Docker creates it, and an empty named volume is populated from whatever the image already has at that path.

§3Bind Mounts

A bind mount maps a specific host path into the container, so edits on either side are visible immediately:

docker run --rm -v "$(pwd)":/app -w /app node:22-slim node script.js
docker run --rm -v "$(pwd)"/conf:/etc/app:ro myimage     # read-only
docker run --rm --mount type=bind,src="$(pwd)",dst=/app myimage   # explicit form

Add :ro when the container only needs to read. A bind mount hides whatever the image had at that path, which is a frequent source of "my files vanished" confusion.

Volumes persist until you delete them deliberately docker rm does not remove volumes, and docker rm -v removes only anonymous ones. Backup before docker volume rm or docker volume prune, and give important data a name so you can find it later.

§4Common Mistakes

MistakeWhat HappensFix
Running a database with no volumeAll data lost when the container is replacedMount a named volume at the data directory
Bind-mounting over a populated image directoryThe image's files are hiddenMount to an empty path or a more specific subfolder
Relative host path in -vTreated as a volume name, not a pathUse an absolute path or $(pwd)/path
Practice
  1. Create a Postgres container with a named volume, add a table, remove the container, start a new one on the same volume, and confirm the table survived.
  2. Bind-mount a folder of HTML files into nginx at /usr/share/nginx/html and edit a file while it runs.
Key takeaways
  • The container's writable layer is temporary; volumes and bind mounts persist.
  • Use named volumes for managed data and bind mounts for host files such as source code.
  • Mounts hide whatever the image had at that path, and :ro protects the host side.
