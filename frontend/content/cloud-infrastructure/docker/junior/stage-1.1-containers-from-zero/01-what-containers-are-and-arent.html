What Containers Are (and Aren't)

A container is an ordinary process on your machine that has been given its own isolated view of the filesystem, network, and process list; it is not a tiny virtual machine.

§1The Problem Containers Solve

"It works on my machine" usually means the app depends on something that differs elsewhere: a language version, a system library, an environment variable, a config file. A container packages the app together with everything it needs to run (except the kernel), so the same package behaves the same on a laptop, a CI server, and production.

Two words you will use constantly:

  • Image: a read-only package containing a filesystem snapshot plus metadata (default command, environment, ports). Think of it as the recipe and ingredients.
  • Container: a running (or stopped) instance created from an image. Think of it as the meal. You can start many containers from one image.

§2Containers vs. Virtual Machines

A virtual machine emulates hardware and boots a full guest operating system on top of a hypervisor. A container skips all of that: it runs directly on the host's kernel, with the kernel hiding everything except what the container is meant to see.

Virtual machineContainer
IncludesFull guest OS and kernelApp, libraries, and files; shares the host kernel
StartupSeconds to minutesTypically milliseconds to a second
Typical sizeGigabytesMegabytes to a few hundred MB
IsolationStrong (separate kernel)Weaker (shared kernel)
DensityHandfuls per hostDozens to hundreds per host

§3What Is Actually Happening

On Linux, "container" is not a single kernel feature. It is a process started with namespaces (which limit what it can see) and cgroups (which limit what it can use). From the host, a containerized process shows up in the normal process list.

docker run -d --name web nginx
ps aux | grep nginx      # on a Linux host: the nginx processes are right there

You will build this understanding up slowly; Senior-level lessons take the mechanism apart by hand. For now, hold one idea: a container is a process with boundaries, not a machine.

The shared-kernel catch A Linux container needs a Linux kernel. On macOS and Windows, Docker quietly runs a small Linux VM and puts your containers inside it. That is why containers are lightweight on Linux but you still see a VM in the Docker Desktop settings on other platforms.

§4Common Mistakes

MistakeWhat HappensFix
Thinking a container is a lightweight VMExpecting to ssh in, install an init system, and run many servicesRun one main process per container and treat it as disposable
Assuming containers are a security boundary equal to VMsUntrusted code shares your host kernelUse VMs or sandboxed runtimes for hostile workloads; see the Senior level
Storing important data inside a containerData vanishes when the container is removedKeep state in volumes, which a later stage covers
Practice
  1. In your own words, explain the difference between an image and a container, using one analogy that is not a recipe.
  2. Name two things a container shares with its host and two things it has to itself.
Key takeaways
  • A container is an isolated process that shares the host kernel, not a miniature virtual machine.
  • An image is the read-only package; a container is a running instance of it.
  • Containers trade some isolation strength for speed, size, and density.
