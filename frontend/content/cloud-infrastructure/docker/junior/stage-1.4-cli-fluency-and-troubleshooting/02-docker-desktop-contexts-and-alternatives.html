Docker Desktop, Contexts & Alternatives

The docker command is only a client, so you can point it at Docker Desktop, a lightweight alternative, or a remote machine and switch between them with contexts.

§1Client, Engine, and Contexts

The CLI talks to an engine (the daemon) over a socket. A context stores which engine to talk to, so one terminal can control several:

docker context ls
docker context create remote-box --docker "host=ssh://deploy@build-server"
docker context use remote-box
docker ps                    # now lists containers on the remote server
docker --context default ps  # one-off use of another context

Remote contexts over SSH are a simple way to manage a single server without logging in to it.

§2Choosing an Engine

OptionWhat it isNotes
Docker DesktopOfficial GUI app with engine, Compose, and extrasEasiest start; licensing terms apply to larger companies
Docker Engine (Linux)The daemon installed nativelyBest performance; no VM
ColimaLightweight Linux VM running Docker on macOS or LinuxFree, scriptable, uses the same CLI
PodmanDaemonless, rootless-by-default engine with a Docker-compatible CLIWorks with most Dockerfiles; slightly different for Compose and networking
Rancher DesktopGUI alternative with a choice of enginesCross-platform

Check Docker's current licensing page if you work for a company with many employees, since Docker Desktop's free tier has size limits.

§3Switching Safely

Different engines have separate images, containers, and volumes. Switching engines does not carry your existing containers along. With Colima, for example:

colima start --cpu 4 --memory 8
docker context use colima
docker run --rm hello-world

Podman can mimic the CLI (alias docker=podman), and many tools accept a DOCKER_HOST environment variable pointing at the socket they should use.

The CLI is not the engine When a command seems to have "lost" all your containers, check docker context ls first. You are probably talking to a different engine than yesterday.

§4Common Mistakes

MistakeWhat HappensFix
Switching engines and expecting old imagesEverything appears missingUnderstand each engine has its own storage; re-pull or re-build
Leaving a remote context activeCommands run on the wrong machineCheck docker context ls before destructive commands
Assuming Podman and Docker are identicalA few flags and Compose features differTest your workflows on the engine you will use
Practice
  1. Run docker context ls, then create a context that targets a second engine or machine and switch back and forth.
  2. List which socket your current client is using, and identify which engine is serving it.
Key takeaways
  • The Docker CLI is a client; contexts choose which engine it controls.
  • Desktop, Colima, Podman, and others each have their own storage and trade-offs.
  • Always know which context is active before running something destructive.
