Docker on Windows, macOS & Linux

Linux containers need a Linux kernel, so on Windows and macOS there is a hidden VM, and where your files live determines how fast things run.

§1What Is Different on Each Platform

  • Linux: containers run directly on the host kernel. Bind mounts and networking are native and fast.
  • macOS: Docker runs a Linux VM. Bind mounts cross a file-sharing layer between macOS and the VM.
  • Windows: Docker Desktop normally uses WSL2, a lightweight Linux VM integrated with Windows. Windows containers (running Windows applications) also exist but are a separate mode and a niche.

Knowing that VM exists explains most platform oddities: memory limits are set for the VM, not per container, and localhost and file paths behave differently across the boundary.

§2File-Sharing Performance

Bind mounts from a macOS or Windows host into the VM are much slower than native Linux, especially for tools that touch thousands of small files, such as node_modules, package managers, and test watchers.

  • On Windows with WSL2, keep your project inside the WSL filesystem (\\wsl$\Ubuntu\home\you\project) rather than under C:\. Cross-OS file access is the slow path.
  • On macOS, use Docker Desktop's recommended file-sharing implementation, keep heavy directories like node_modules inside the container (as a volume), and mount only your source.
  • Named volumes live inside the VM and avoid the slow boundary entirely.

§3Other Platform Gotchas

  • CPU architecture: Apple Silicon Macs are arm64; many servers are amd64. Images built on your Mac may not run on an amd64 server unless built for it (--platform linux/amd64). The Intermediate level covers multi-platform builds.
  • Line endings: a shell script saved with Windows CRLF line endings fails in a Linux container with confusing "not found" errors. Configure your editor and Git to use LF for scripts.
  • Paths: on Windows, mount paths and quoting differ between PowerShell, cmd, and Git Bash. Use ${PWD} in PowerShell and $(pwd) in bash.
  • Case sensitivity: Linux filesystems are case-sensitive; macOS and Windows usually are not, so Config.js vs config.js bugs appear only inside the container.
docker run --rm alpine uname -m                  # aarch64 on Apple Silicon, x86_64 on Intel/AMD
docker run --rm --platform linux/amd64 alpine uname -m   # emulated: works, but slower
printf '*.sh text eol=lf\n' >> .gitattributes     # keep shell scripts on LF endings
docker run --rm -v "${PWD}:/src" -w /src alpine ls    # PowerShell path form
Resources belong to the VM On macOS and Windows, a container can only use the CPU and memory you allocated to Docker Desktop's VM. If builds crash or are slow, check those settings before blaming the container.

§4Common Mistakes

MistakeWhat HappensFix
Mounting a Windows C:\ project into WSL2 containersVery slow file accessKeep the project inside the WSL filesystem
Building on Apple Silicon and deploying to amd64"exec format error" on the serverBuild with --platform linux/amd64 or multi-platform images
Editing scripts with CRLF line endings/bin/sh^M: bad interpreter or "not found"Use LF endings, set .gitattributes for *.sh
Practice
  1. Check which architecture your machine reports with docker version and docker run --rm alpine uname -m.
  2. Time npm install (or similar) once on a bind mount and once inside a named volume, and compare.
Key takeaways
  • Linux containers on macOS and Windows run inside a Linux VM, whose resources you configure.
  • Keep heavy file access inside the VM (WSL filesystem or volumes) for speed.
  • Watch for architecture, line-ending, path, and case-sensitivity differences.
