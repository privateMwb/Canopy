Scoping ML Problems

The most senior ML skill isn't building models — it's correctly deciding when not to.

§1Not Every Problem Needs ML

A simple rule-based system, a lookup table, or basic statistics can solve many problems that initially look like they need a model — more reliably, more cheaply, and far more easily explained to stakeholders. Reaching for ML by default, rather than by necessity, is a common and costly mistake.

§2Questions Worth Asking First

  • Is there a pattern to learn at all? If the relationship between inputs and outputs is simple and well-understood, a rule often beats a model.
  • Is there enough data? ML needs examples to learn from; a handful of cases is better served by explicit logic.
  • Can errors be tolerated? ML predictions are probabilistic — if a wrong answer is unacceptable in some critical case, a model might not be the right tool at all, or needs to be paired with strict guardrails.
  • What's the cost of being wrong, vs. the cost of building and maintaining a model?

§3A Concrete Example

"Should we use ML to flag transactions over $10,000 for review?" — No; that's a simple threshold rule, not a learning problem. "Should we use ML to predict which transactions are fraudulent based on subtle patterns across dozens of signals?" — Plausibly yes, since the pattern is genuinely complex and not reducible to a simple rule.

A useful default Start with the simplest possible solution — a rule, a heuristic, a lookup table. Only reach for ML once that simple baseline has been tried and genuinely falls short. This also gives you a baseline to measure the ML approach against.

§4Common Mistakes

MistakeWhat HappensFix
Defaulting to ML because it's the more exciting/current technologyOverbuilt, hard-to-maintain solution to a simple problemTry the simplest solution first; justify ML by genuine necessity
Not establishing a simple baseline before building a modelNo way to tell if the model is actually adding valueAlways compare the model against a simple baseline (a rule, the majority class, etc.)
Practice
  1. For "predicting next month's office supply orders," argue whether this needs ML or a simpler approach.
  2. Describe one question you'd ask a stakeholder before agreeing to build a model for their problem.
Key takeaways
  • Many problems that look like they need ML are better solved by simple rules or statistics.
  • Check for a genuine pattern, sufficient data, and tolerable error rates before committing to ML.
  • Always establish a simple baseline — it's the only way to know if a model is actually earning its complexity.
