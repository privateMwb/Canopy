Signals & Exit Status

Signals are small asynchronous notifications sent to a process, and exit status is how a process reports how it ended.

§1What a Signal Is

A signal interrupts a process to tell it something happened. The kernel delivers signals for events like a bad memory access, and other processes or users can send them on purpose.

SignalTypical causeCan be caught?
SIGINTCtrl-C at the terminalYes
SIGTERMPolite request to terminate (kill)Yes
SIGKILLForced termination (kill -9)No
SIGSEGVInvalid memory accessYes, but rarely useful
SIGCHLDA child changed state or exitedYes

Each signal has a default action, usually terminate. A process can install a handler to run its own code instead, except for SIGKILL and SIGSTOP, which can never be caught or ignored.

§2Handling a Signal

#include <signal.h>
#include <unistd.h>

volatile sig_atomic_t stop = 0;

void on_int(int sig) { stop = 1; }   // do almost nothing in a handler

int main(void) {
    struct sigaction sa = { .sa_handler = on_int };
    sigaction(SIGINT, &sa, NULL);
    while (!stop) pause();           // sleep until a signal arrives
    write(1, "cleaning up\n", 12);    // real work happens outside the handler
    return 0;
}

A handler can interrupt the program at almost any point, so it must be extremely careful. Set a flag and return; do the real cleanup in the main loop. Many library functions, including printf and malloc, are unsafe inside handlers.

§3Exit Status, Zombies, and Orphans

A process ends by returning from main or calling exit(code). By convention, 0 means success and non-zero means failure. A parent reads it with waitpid; shells expose it as $?.

false; echo $?    # 1
true;  echo $?    # 0
sh -c 'kill -9 $$'; echo $?   # 137 = 128 + signal 9

A zombie is a child that exited but hasn't been reaped. An orphan is a child whose parent exited first; the kernel reassigns it to PID 1, which reaps it when it finishes.

Gotcha A handler that calls non-async-signal-safe functions can deadlock. If the signal arrives while malloc holds an internal lock, a handler that calls malloc will wait forever on that same lock.

§4Common Mistakes

MistakeWhat HappensFix
Doing complex work inside a signal handlerDeadlocks and corrupted state at random momentsSet a volatile sig_atomic_t flag and handle it in normal code
Using kill -9 as the first resortThe process can't clean up temp files or flush dataSend SIGTERM first; use SIGKILL only if it ignores that
Ignoring SIGCHLD and never waitingZombies pile upReap in a SIGCHLD handler with waitpid(-1, NULL, WNOHANG) in a loop
Practice
  1. Write a program that prints a message and exits cleanly on Ctrl-C instead of dying immediately.
  2. Create a zombie on purpose by having the parent sleep without waiting. Find it with ps and explain the Z state.
Key takeaways
  • Signals are asynchronous notifications; SIGKILL and SIGSTOP can't be caught.
  • Keep signal handlers tiny: set a flag and return.
  • Exit status 0 means success, and unreaped children become zombies.
