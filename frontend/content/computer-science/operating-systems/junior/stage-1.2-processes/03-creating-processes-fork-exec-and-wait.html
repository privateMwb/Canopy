Creating Processes: fork, exec & wait

Unix creates a process by cloning the caller with fork, replacing the clone's program with exec, and collecting its result with wait.

§1fork: Make a Copy

fork() creates a child that is a near-exact copy of the caller: same code, same variables, same open file descriptors, and the same next instruction. The call returns twice: 0 in the child, and the child's PID in the parent.

#include <stdio.h>
#include <unistd.h>

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {
        printf("child: pid %d\n", getpid());
    } else if (pid > 0) {
        printf("parent: child is %d\n", pid);
    } else {
        perror("fork");   // pid < 0: fork failed
    }
    return 0;
}

After the fork, the two processes run independently and their memory diverges when either writes. Output order between them isn't guaranteed.

§2exec: Become Something Else

exec replaces the current process's program with a new one. The PID stays the same, but code, stack, and heap are replaced. If exec succeeds, it never returns.

if (fork() == 0) {
    execlp("ls", "ls", "-l", NULL);   // replace child with ls
    perror("execlp");                 // only reached if exec failed
    _exit(127);
}

Why two steps? Between fork and exec, the child can rearrange its own descriptors, which is exactly how shells set up redirection and pipes.

§3wait: Collect the Result

When a child exits, it leaves a small record holding its exit status. The parent must wait to read it and let the kernel free the record.

int status;
pid_t done = waitpid(pid, &status, 0);
if (WIFEXITED(status))
    printf("exit code %d\n", WEXITSTATUS(status));

A child that exited but hasn't been waited on is a zombie: it uses no CPU or memory, but still occupies a process table entry.

The key insight Unix separates 'create a process' (fork) from 'choose its program' (exec). That gap is where shells do all their setup work, and it's why the design has lasted decades.

§4Common Mistakes

MistakeWhat HappensFix
Not checking fork's return valueChild code runs in the parent too, or errors go unnoticedBranch on pid == 0, pid > 0, and pid < 0
Calling fork in a loop without exiting the childChild processes keep forking, producing exponential growth (a fork bomb)Make sure each child calls exec or _exit
Never calling waitZombie processes accumulateReap every child with wait or waitpid
Practice
  1. Write a program that forks three children, each printing its PID, and a parent that waits for all of them.
  2. Write a program that runs date through fork and exec, then prints the child's exit code.
Key takeaways
  • fork clones the process and returns twice, once in each copy.
  • exec replaces the process's program but keeps its PID and open descriptors.
  • The parent must wait for children to read their status and avoid zombies.
