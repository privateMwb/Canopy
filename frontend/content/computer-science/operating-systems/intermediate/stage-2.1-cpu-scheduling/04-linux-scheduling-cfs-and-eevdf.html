Linux Scheduling: CFS & EEVDF

Linux's general-purpose scheduler tracks how much CPU each task has received and always runs the task that's owed the most.

§1Virtual Runtime

The Completely Fair Scheduler (CFS), the default from Linux 2.6.23, gives each runnable task a counter called vruntime, the amount of CPU time it has received, scaled by its weight. The scheduler always picks the task with the smallest vruntime, the one that has had the least.

# Conceptual pick-next logic
next = task with min(vruntime)     # kept in a red-black tree, O(log n)
run(next)
next.vruntime += elapsed * (1024 / next.weight)

A high-weight (low nice) task accumulates vruntime more slowly, so it's chosen more often and receives a larger share of CPU.

§2Nice Values and Weights

Each nice level changes a task's weight so that one step corresponds to roughly a 10% change in CPU share relative to a neighbor. Two always-runnable tasks at nice 0 split the CPU evenly; a nice 0 and a nice 5 task split it roughly 75/25.

# Two CPU hogs: compare their shares in top
nice -n 0  sh -c 'while :; do :; done' &
nice -n 10 sh -c 'while :; do :; done' &
top

A task that sleeps a lot builds up credit, because its vruntime lags behind. When it wakes, it has the smallest vruntime and runs promptly, which is why interactive tasks feel responsive without explicit priorities.

§3From CFS to EEVDF

Linux 6.6 replaced CFS's task-selection logic with EEVDF (Earliest Eligible Virtual Deadline First). Each task has a lag measuring how much CPU it's owed or has overused. Only tasks with non-negative lag are eligible, and among those, the scheduler runs the one with the earliest virtual deadline.

  • Fairness still comes from tracking each task's share of CPU
  • Latency is handled explicitly: a task requesting a shorter time slice gets an earlier deadline
  • This removes several heuristics that CFS used to give sleeping tasks a latency boost

Real-time tasks use separate scheduling classes (SCHED_FIFO, SCHED_RR) that always take priority over normal tasks.

The key insight Both CFS and EEVDF are fair-share schedulers: they track how much CPU each task has received relative to what it's owed, and always run the one that is most behind.

§4Common Mistakes

MistakeWhat HappensFix
Thinking nice sets strict priorityA nice 19 task still gets some CPU when others are runnableNice adjusts the share of CPU, not absolute precedence
Assuming Linux uses a fixed time sliceSlice length adapts to the number of runnable tasksTreat the slice as a dynamic outcome of fairness and load
Using SCHED_FIFO for ordinary workA busy real-time task can monopolize a CPU and freeze other tasksReserve real-time classes for genuinely latency-critical work
Practice
  1. Run two CPU-bound loops at nice 0 and nice 10. Use top to see the ratio and compare it with the weight table.
  2. Explain in a sentence why a task that sleeps often gets prompt service when it wakes up under CFS.
Key takeaways
  • CFS runs the task with the smallest virtual runtime, weighted by nice value.
  • Sleeping tasks stay near the front of the line because their vruntime lags.
  • EEVDF, in Linux 6.6 and later, adds explicit eligibility and deadlines for latency.
