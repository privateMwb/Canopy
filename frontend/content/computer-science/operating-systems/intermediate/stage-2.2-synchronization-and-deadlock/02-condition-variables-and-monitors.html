Condition Variables & Monitors

A condition variable lets a thread sleep until some shared state becomes true, and the rule that matters most is to always wait inside a loop.

§1Waiting for a Condition

A mutex protects data, but it can't wait for the data to change. If a consumer needs the queue to be non-empty, spinning on it wastes CPU. A condition variable pairs with a mutex: pthread_cond_wait atomically releases the mutex and sleeps, then reacquires the mutex before returning.

pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  c = PTHREAD_COND_INITIALIZER;
int ready = 0;

// Waiter
pthread_mutex_lock(&m);
while (!ready)                     // a loop, never a plain if
    pthread_cond_wait(&c, &m);     // unlock, sleep, relock
// ready is true and we hold the lock
pthread_mutex_unlock(&m);

// Signaler
pthread_mutex_lock(&m);
ready = 1;
pthread_cond_signal(&c);           // wake one waiter
pthread_mutex_unlock(&m);

§2Why the while Loop

Three things can wake a waiter with the condition still false. Spurious wakeups are allowed by the specification. Another thread may take the item first between the signal and the waiter reacquiring the lock. And with broadcast, several waiters wake for one item. Re-checking the condition in a loop makes all of these harmless.

// Wrong: assumes the signal means the condition holds
if (queue_empty()) pthread_cond_wait(&c, &m);
item = pop();                      // may pop from an empty queue

// Right
while (queue_empty()) pthread_cond_wait(&c, &m);
item = pop();

The condition lives in your shared state, such as ready above. The condition variable is only the mechanism for sleeping and waking; it holds no information itself.

§3Signal vs. Broadcast, and Monitors

signal wakes one waiter, and broadcast wakes all. Use broadcast when different waiters wait for different conditions on one variable, or when the change might satisfy many of them.

A monitor bundles shared data, the lock that protects it, and the condition variables into one unit, with every operation running under the lock. Java's synchronized with wait/notify and Python's threading.Condition follow this pattern. In C you build one by hand with a struct.

Gotcha: lost wakeups If you signal before the waiter begins waiting and the waiter doesn't check the condition first, the wakeup is lost and the waiter sleeps forever. Checking shared state under the mutex before waiting prevents this.

§4Common Mistakes

MistakeWhat HappensFix
Using if instead of while around cond_waitProceeds on a spurious wakeup with the condition falseAlways re-check the condition in a loop
Calling cond_wait without holding the mutexUndefined behavior and race conditionsHold the mutex before waiting; it releases it for you while asleep
Changing the shared state without the mutexA waiter can miss the change and sleep foreverUpdate the condition's state while holding the same mutex the waiter uses
Practice
  1. Implement a thread-safe queue with a blocking pop that waits while the queue is empty.
  2. Explain a scenario where replacing while with if produces a wrong result even without spurious wakeups.
Key takeaways
  • A condition variable lets a thread sleep atomically while releasing its mutex.
  • Always wait in a while loop re-checking the condition.
  • The condition is your shared state; the variable is just the sleep and wake mechanism.
