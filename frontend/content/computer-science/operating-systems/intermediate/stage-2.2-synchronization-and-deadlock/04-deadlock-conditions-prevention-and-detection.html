Deadlock: Conditions, Prevention & Detection

Deadlock needs four conditions to hold at once, so removing any one of them makes it impossible.

§1The Four Conditions

Deadlock means a set of threads each wait for something another in the set holds. It can only occur when all four of these hold (the Coffman conditions):

ConditionMeaningBreak it by
Mutual exclusionA resource can be held by only one threadMaking resources shareable (rarely possible)
Hold and waitA thread holds one resource while waiting for anotherAcquiring everything at once, or releasing before waiting
No preemptionA held resource can't be forcibly takenUsing trylock and backing off
Circular waitA cycle of threads each waiting on the nextImposing a global lock order
// Thread 1          // Thread 2
lock(A);             lock(B);
lock(B);             lock(A);      // each waits for the lock the other holds

§2Prevention in Practice: Lock Ordering

The most practical fix is a global lock order: every thread acquires locks in the same sequence, so a cycle can't form.

void transfer(Account *from, Account *to, long amt) {
    Account *first  = from->id < to->id ? from : to;
    Account *second = from->id < to->id ? to   : from;
    lock(&first->m);
    lock(&second->m);       // always lower id first, regardless of direction
    from->bal -= amt;  to->bal += amt;
    unlock(&second->m);
    unlock(&first->m);
}

Where ordering is impractical, use pthread_mutex_trylock: if the second lock isn't available, release the first, wait briefly, and retry.

§3Detection and Recovery

Some systems allow deadlock and detect it. Build a wait-for graph, with an edge from each thread to the thread holding what it wants. A cycle means deadlock. Databases do this, then abort one transaction as the victim to break the cycle.

  • Avoidance (the banker's algorithm) grants a request only if the system stays in a safe state, but it needs advance knowledge of maximum needs
  • Prevention removes a condition by design, as with lock ordering
  • Detection plus recovery allows deadlock and cleans up afterward
  • Ignoring it is what most general-purpose OSes do for user-level locks, leaving the programmer responsible
Connection to later lessons In Stage 3.4 you'll diagnose live deadlocks from thread dumps by finding the cycle: look for threads waiting on locks held by each other.

§4Common Mistakes

MistakeWhat HappensFix
Taking locks in different orders in different code pathsRare, load-dependent deadlocksDocument one global lock order and enforce it in review
Calling unknown code while holding a lockThe callee may take another lock and complete a cycleRelease locks before calling callbacks or external code
Retrying trylock in a tight loopLivelock: threads keep backing off in lockstepAdd randomized backoff between retries
Practice
  1. Write a two-thread program that reliably deadlocks, then fix it with lock ordering.
  2. Draw the wait-for graph for three threads T1 holds A wants B, T2 holds B wants C, T3 holds C wants A. Which edge would you remove, and how?
Key takeaways
  • Deadlock requires mutual exclusion, hold and wait, no preemption, and circular wait.
  • A global lock ordering breaks circular wait and is the standard practical fix.
  • Databases detect cycles and abort a victim; most application code must prevent deadlock by design.
