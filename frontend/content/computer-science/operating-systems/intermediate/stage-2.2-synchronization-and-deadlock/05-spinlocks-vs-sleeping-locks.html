Spinlocks vs. Sleeping Locks

A lock can wait by burning CPU or by sleeping, and the right choice depends on how long the lock is held compared with the cost of a context switch.

§1Two Ways to Wait

A spinlock loops, repeatedly testing the lock until it becomes free. It uses CPU while waiting, but reacts immediately when the lock is released. A sleeping lock (the standard mutex) puts the waiter to sleep and has the kernel wake it later. It uses no CPU while waiting, but sleeping and waking cost a pair of context switches.

// A minimal spinlock using an atomic exchange
#include <stdatomic.h>
atomic_flag lock = ATOMIC_FLAG_INIT;

void spin_lock(void)   { while (atomic_flag_test_and_set(&lock)) ; }
void spin_unlock(void) { atomic_flag_clear(&lock); }

test_and_set atomically sets the flag and returns its old value, so exactly one spinner sees false and gets the lock.

§2When Each Wins

SituationBetter choiceWhy
Critical section is a few instructionsSpinlockWaiting is shorter than a context switch
Critical section does I/O or runs longSleeping mutexSpinners would waste whole time slices
Single CPU coreNever spin in user spaceThe lock holder can't run while you spin
Inside an interrupt handlerSpinlockHandlers can't sleep

A spinning thread occupies a core doing nothing useful. If the lock holder is descheduled by the OS, spinners can burn an entire time slice waiting for it.

§3Hybrid Locks in Practice

Production mutexes often spin briefly and then sleep. Linux's kernel mutex and glibc's adaptive mutex try for a short time first, betting that the holder will release quickly, and block only if it doesn't.

// pthread spinlock API, for very short critical sections only
pthread_spinlock_t sl;
pthread_spin_init(&sl, PTHREAD_PROCESS_PRIVATE);
pthread_spin_lock(&sl);
counter++;
pthread_spin_unlock(&sl);

Heavy contention on one lock makes the cache line holding it bounce between cores, costing performance even if the critical section is tiny.

The key insight The decision is arithmetic: spin if the expected wait is shorter than two context switches, sleep otherwise. When you don't know, use the default mutex, which already hedges.

§4Common Mistakes

MistakeWhat HappensFix
Using a spinlock around code that can block or do I/OOther threads burn CPU while the holder sleepsUse a sleeping mutex whenever the critical section can wait
Spinning on a single-core machineThe holder can't run, so the spinner just wastes its sliceUse sleeping locks, or yield, on one core
Assuming a spinlock is always fasterHeavy contention causes cache-line bouncingBenchmark under realistic contention
Practice
  1. Time a counter protected by a spinlock versus a mutex with 2 threads and with 16 threads on your machine. Explain the difference.
  2. Argue whether a lock protecting a hash table lookup should be a spinlock or a mutex, and what would change your answer.
Key takeaways
  • Spinlocks burn CPU while waiting but avoid context switches; sleeping locks do the opposite.
  • Spin only for very short critical sections on multicore systems.
  • Real mutexes are hybrids that spin briefly and then sleep.
