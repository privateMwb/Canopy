Memory Management Across Languages

Every language decides who frees memory and when, and each choice moves cost between the programmer, the compiler, and the runtime.

§1Four Strategies

StrategyExamplesWho frees memoryCost
ManualCThe programmer, via freeBugs: leaks, use-after-free
Scope-based (RAII/ownership)C++, RustThe compiler inserts frees when owners go out of scopeDesign effort; Rust enforces it at compile time
Reference countingPython (CPython), SwiftFreed when the count reaches zeroCounting on every copy; cycles leak
Tracing garbage collectionJava, Go, C#, JavaScriptA runtime collector finds unreachable objectsPauses and extra memory headroom

No strategy is free. They differ in whether the cost is paid at compile time, spread across every operation, or paid in bursts.

§2How Each One Fails

# Reference counting: a cycle is never freed
a = {}; b = {}
a["other"] = b
b["other"] = a     # each holds the other; counts never reach zero
# CPython adds a cycle detector for this; plain refcounting does not.

A tracing GC starts from known roots, such as stacks and globals, and keeps everything reachable, so cycles aren't a problem. Its costs are pauses while it works, though modern collectors do most of the work concurrently, and the need for spare memory, often a significant multiple of live data, so it can run without constantly collecting.

§3What the OS Sees

From the kernel's view, all of these are ordinary programs requesting pages. Language runtimes have visible effects on memory behavior.

  • A GC'd process often grows its heap, then keeps it; RSS can stay high even when live data is small
  • A moving collector touches many pages while compacting, causing bursts of page faults
  • Containers with a memory limit can kill a GC'd process whose heap grows beyond the limit before it collects
  • Tuning options such as -Xmx for Java or GOMEMLIMIT for Go tell the runtime the budget it must respect
# Rust: the compiler inserts the free; no runtime collector needed
{
    let v = vec![1, 2, 3];   // allocated on the heap
}                            // v goes out of scope: freed here, deterministically
Connection to later lessons The container memory limits and OOM-kill behavior that make GC tuning important are covered in Stages 3.2 and 3.3.

§4Common Mistakes

MistakeWhat HappensFix
Believing a garbage-collected language can't leakObjects held by a forgotten cache or listener stay reachableProfile heap contents and remove references you no longer need
Relying on reference counting with cyclic structuresCycles never reach zeroUse weak references for back-pointers, or a runtime with a cycle collector
Ignoring runtime memory settings in containersThe runtime assumes more memory than the limit allows and gets OOM-killedConfigure the heap limit to fit inside the container limit
Practice
  1. Write a Python reference cycle, use the gc module to count collected objects, and then break the cycle with a weak reference.
  2. For a service you know, identify its strategy and one way its memory behavior could surprise an operator.
Key takeaways
  • Languages manage memory manually, by scope, by reference count, or by tracing GC.
  • Each strategy puts its cost somewhere different: bugs, compile effort, per-operation overhead, or pauses and headroom.
  • The OS sees only pages, so runtime settings determine how a process behaves under memory limits.
