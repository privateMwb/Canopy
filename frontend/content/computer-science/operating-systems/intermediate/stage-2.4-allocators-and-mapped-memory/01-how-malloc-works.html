How malloc Works

malloc is a user-space library that manages memory it borrows from the kernel in large pieces, which is why its behavior often surprises people.

§1Two Sources of Memory

malloc doesn't ask the kernel for memory on every call, because system calls are expensive and the kernel only deals in whole pages. glibc's allocator gets memory in two ways:

  • The heap (brk/sbrk): one region that grows upward; the allocator extends it as needed and carves it into blocks
  • Anonymous mmap: a separate mapping, used for large requests (the default threshold is 128 KiB, and it adjusts dynamically)
# Watch the system calls behind malloc
strace -e trace=brk,mmap,munmap ./prog

// malloc(100)        -> carved from the heap, usually no syscall
// malloc(1 << 20)    -> mmap of its own region
// free of the large block -> munmap, memory returns to the OS immediately

Large blocks are mapped separately so they can be returned to the OS the instant they're freed, without leaving a hole in the heap.

§2Chunks and Headers

Each allocation is a chunk: a small header recording the size, then the memory handed to you. When you call free(p), the allocator finds the header just before p, which is how free knows the size without being told.

         ┌──────────┬───────────────────────┐
 chunk:  │ header   │ user data (what       │
         │ size|flags│ malloc returned)     │
         └──────────┴───────────────────────┘
              ▲              ▲
          p - 16            p

This is also why overflowing a buffer is so dangerous: the bytes after your block are often the next chunk's header, and corrupting them breaks the allocator's bookkeeping, not just your data.

§3Bins, Caches, and Arenas

Freed chunks go onto lists called bins, organized by size, so the next request of that size can reuse one quickly. glibc keeps a small per-thread cache (tcache) for the fastest path with no locking. In multithreaded programs, glibc also creates several arenas, each its own heap with its own lock, so threads don't all contend for one.

# Inspect the allocator's state from inside a program
malloc_stats();      // prints arena and in-use totals to stderr
malloc_trim(0);      // ask glibc to return free memory at the top of the heap

Alternative allocators such as jemalloc, tcmalloc, and mimalloc make different tradeoffs on speed, fragmentation, and thread scaling, and are often swapped in for long-running servers.

Why RSS doesn't shrink Calling free usually puts a block back on a list for reuse; it does not return memory to the OS. A heap block in the middle can't be released while higher blocks are in use, so a process's RSS can stay high after you free a lot.

§4Common Mistakes

MistakeWhat HappensFix
Expecting free to lower the process's memory in topThe memory is retained for reuseUse malloc_trim, an allocator tuned for returning memory, or measure live bytes
Writing even one byte before or after a blockCorrupts neighboring headers and crashes laterRun AddressSanitizer, which places guard zones around allocations
Assuming malloc is cheap in hot pathsLocks and bin searches add up under contentionReuse buffers, use pools, or choose a scalable allocator
Practice
  1. Use strace to find the size at which your system switches from brk to mmap for a single malloc.
  2. Allocate and free a million small blocks, then check RSS. Does it drop? Try malloc_trim(0) and compare.
Key takeaways
  • malloc gets memory from the kernel in bulk using brk and mmap, then subdivides it.
  • Each chunk has a header, so overflows can damage the allocator's own bookkeeping.
  • Freed memory typically stays in the process until trimmed.
