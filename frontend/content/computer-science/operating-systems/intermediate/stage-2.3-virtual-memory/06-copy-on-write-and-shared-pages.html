Copy-on-Write & Shared Pages

Because mappings are just table entries, two processes can share one physical page until one of them writes, and that makes fork cheap.

§1Why fork Is Cheap

A naive fork would copy the parent's entire memory, gigabytes in some programs, even though the child usually calls exec right away and discards it. Instead, the kernel copies only the page tables and marks all writable pages read-only in both processes. Both share the same physical frames.

parent: virtual page 7 ──┐
                         ├──> frame 42   (marked read-only in both)
child:  virtual page 7 ──┘

Reads proceed normally. Fork costs time proportional to the page tables, not to the data.

§2The Copy Happens on Write

When either process writes to a shared page, the read-only permission triggers a page fault. The handler allocates a new frame, copies the page, maps the new copy as writable for the writer, and restarts the instruction. The other process keeps the original.

int *data = malloc(100 << 20);    // 100 MiB, touched so it is resident
memset(data, 1, 100 << 20);

pid_t pid = fork();               // near-instant despite 100 MiB
if (pid == 0) {
    data[0] = 2;                  // copies exactly one 4 KiB page
    _exit(0);
}

This is copy-on-write (COW). Memory is duplicated only for pages that are actually modified, and often nothing is ever copied.

§3Other Kinds of Sharing

  • Shared libraries: the code pages of libc are mapped by every process but exist in RAM once
  • The zero page: newly allocated memory initially maps to a single shared page of zeros, copied on first write
  • File-backed pages: the page cache holds file data once, mapped into any process that opens it
  • Same-binary processes: two copies of a program share the same read-only code pages
# RSS counts shared pages fully; PSS divides shared pages among sharers
grep -E 'Rss|Pss' /proc/self/smaps_rollup

Because shared pages are counted in each process's RSS, adding up RSS across processes overstates real memory use. PSS gives a fairer total.

The key insight Copy-on-write is a bet that most copied memory will never be written. When the bet is right, you get the semantics of a full copy at nearly zero cost.

§4Common Mistakes

MistakeWhat HappensFix
Adding up RSS across processes to find memory usedShared pages are counted multiple timesUse PSS, or total system memory figures
Assuming fork copy cost is zero for big processesPage-table copying and later COW faults still cost timeUse posix_spawn or vfork followed by exec when you only want to run another program
Writing to a large inherited buffer in the childTriggers many COW copies and memory growthMinimize writes to inherited data, or let the child exec instead
Practice
  1. Fork a process holding 200 MiB, then have the child write to every page. Watch system memory use before and after.
  2. Compare Rss and Pss in /proc/<pid>/smaps_rollup for two processes of the same program.
Key takeaways
  • fork shares frames and marks them read-only, deferring copies until a write.
  • A write to a shared page faults, and the kernel copies just that page.
  • Shared libraries, the zero page, and the page cache all rely on shared mappings.
