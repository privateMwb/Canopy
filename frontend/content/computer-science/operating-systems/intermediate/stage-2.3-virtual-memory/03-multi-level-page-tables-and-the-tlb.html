Multi-Level Page Tables & the TLB

Real systems shrink page tables with a tree structure and hide the cost of walking it with a small cache called the TLB.

§1Multi-Level Page Tables

Instead of one giant table, the page table becomes a tree. The top-level table points to second-level tables, and so on. Entire branches for unused regions of the address space simply don't exist, so a small process needs only a few tables.

On x86-64, the 48 bits of virtual address are split as shown below. Each table is exactly one 4 KiB page holding 512 eight-byte entries, so 9 bits index each level.

47      39 38      30 29      21 20      12 11         0
[ L4 index ][ L3 index ][ L2 index ][ L1 index ][  offset  ]
   9 bits      9 bits      9 bits      9 bits     12 bits

# A register (CR3) holds the physical address of the top-level table.
# Each level's entry points to the next table; the last gives the frame.

Newer hardware supports a fifth level for 57-bit addresses. The price of the tree is that a translation, called a page walk, now needs up to four memory reads.

§2The Translation Lookaside Buffer

Four extra memory accesses per load would be disastrous, so the CPU caches recent translations in the TLB, a small, very fast cache from virtual page number to frame. On a TLB hit, translation is nearly free. On a miss, hardware walks the page tables and fills the TLB.

# Effective access time with a 99% TLB hit rate (illustrative numbers):
#   hit : 1 ns translation + 100 ns memory         = 101 ns
#   miss: ~4 table reads (400 ns) + 100 ns memory  = 500 ns
#   average = 0.99*101 + 0.01*500 = ~105 ns

Programs work well with a TLB because of locality: they reuse the same few pages repeatedly.

§3TLB Reach and Context Switches

TLB reach is entries multiplied by page size. A 64-entry TLB with 4 KiB pages covers just 256 KiB, so a program that jumps across a larger working set misses constantly. Larger pages, covered in Stage 3.2, extend reach.

When the OS switches to another process, the old translations are wrong. Options: flush the whole TLB, which is costly, or tag entries with an address-space ID (ASID, called PCID on x86) so entries from different processes coexist.

# Count TLB-related events with perf, if available
perf stat -e dTLB-load-misses,dTLB-loads ./myprogram
Gotcha A page table walk is itself made of memory accesses, which can hit the CPU caches. A TLB miss isn't always 400 ns; it depends heavily on whether the table entries are cached.

§4Common Mistakes

MistakeWhat HappensFix
Ignoring TLB behavior when striding across a large arrayEach access lands on a new page and misses the TLBAccess data sequentially, or restructure to improve locality
Assuming a multi-level table makes translation cheaperIt saves memory, at the cost of a longer walkThe TLB is what keeps the common case fast
Forgetting TLB invalidation after changing a mappingThe CPU keeps using a stale translationThe OS must flush or invalidate affected entries (a 'TLB shootdown' on multicore)
Practice
  1. With a 4-level table, how many memory accesses does a full page walk need? How many would be needed with 5 levels?
  2. Compute the TLB reach of a 1,536-entry TLB with 4 KiB pages, and with 2 MiB pages.
Key takeaways
  • Multi-level page tables store only the parts of the address space in use.
  • The TLB caches translations so most accesses avoid the page walk.
  • TLB reach is entries × page size; poor locality causes misses.
