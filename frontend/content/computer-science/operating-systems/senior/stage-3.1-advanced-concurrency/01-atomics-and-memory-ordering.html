Atomics & Memory Ordering

Compilers and CPUs reorder memory operations for speed, and atomics with explicit ordering are how you tell them which orderings you depend on.

§1Atomic Operations

An atomic operation completes as one indivisible step from the point of view of every other thread. C11 provides these in <stdatomic.h>, and C++ in <atomic>. The workhorse is compare-and-swap (CAS): set a variable to a new value only if it still holds an expected one, and report whether it did.

#include <stdatomic.h>

atomic_long counter = 0;
atomic_fetch_add(&counter, 1);          // lock-free increment, no mutex

// CAS loop: atomically double the value
long old = atomic_load(&counter);
while (!atomic_compare_exchange_weak(&counter, &old, old * 2))
    ;                                   // on failure, old is refreshed; retry

Atomic operations fix the lost-update race, but they say nothing by default about the order in which other memory becomes visible.

§2Why Ordering Matters

Both the compiler and the CPU may reorder independent loads and stores, and store buffers let a core's writes become visible to others later than program order suggests. Consider publishing data with a flag:

int data;  atomic_int ready = 0;

// Thread 1                          // Thread 2
data = 42;                            while (!atomic_load_explicit(&ready,
atomic_store_explicit(&ready, 1,                 memory_order_acquire)) ;
        memory_order_release);        print(data);   // guaranteed to be 42

The release store guarantees that all writes before it, including data = 42, are visible to any thread that performs an acquire load that sees the flag. With relaxed ordering, Thread 2 could see ready == 1 and still read the old data.

§3The Memory Orders

OrderGuaranteeTypical use
relaxedAtomicity only; no ordering with other memoryCounters and statistics
acquire (loads)Later operations can't move before this loadTaking a lock, reading a published flag
release (stores)Earlier operations can't move after this storeReleasing a lock, publishing data
acq_relBoth, on read-modify-write operationsReference counts, CAS in lock-free structures
seq_cstOne global order of all such operations (the default)When in doubt

x86 is strongly ordered, so many bugs are invisible there and appear only on ARM, which reorders far more aggressively. Passing tests on x86 is not evidence of correct ordering.

The key insight A lock operation is an acquire and an unlock is a release. That's why data protected by a mutex is safely visible to the next holder, and why hand-rolled atomics must replicate those guarantees deliberately.

§4Common Mistakes

MistakeWhat HappensFix
Using relaxed for a flag that publishes other dataThe reader sees the flag but stale data on weak-memory CPUsUse release on the store and acquire on the load
Testing atomics only on x86Ordering bugs are hidden by its strong memory modelTest on ARM, and use ThreadSanitizer
Defaulting to the weakest ordering for speedSubtle bugs for a tiny gainStart with seq_cst; relax only with a proven, measured need
Practice
  1. Write the flag-and-data example with relaxed ordering and run it millions of times on ARM hardware if available. Does the reader ever see stale data?
  2. Implement a spinlock with acquire on lock and release on unlock, and explain why each ordering is needed.
Key takeaways
  • Atomic operations prevent torn or lost updates; memory orders control visibility of surrounding memory.
  • Release-store with acquire-load is the standard pattern to publish data.
  • Weak-memory CPUs expose ordering bugs that x86 hides; default to seq_cst.
