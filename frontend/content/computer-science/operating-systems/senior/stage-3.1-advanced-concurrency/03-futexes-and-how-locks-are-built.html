Futexes & How Locks Are Built

A futex lets a lock stay entirely in user space when uncontended and ask the kernel to sleep or wake threads only when contention occurs.

§1The Idea

Calling into the kernel for every lock operation would be slow, since most locks are uncontended most of the time. A futex (fast user-space mutex) splits the work. The lock state is an integer in user memory. Locking and unlocking try an atomic operation first. Only if the lock is taken does the thread invoke the futex system call to sleep, and only if someone is sleeping does the unlocker invoke it to wake one.

PathWhat happensCost
Fast pathOne atomic instruction in user spaceA few nanoseconds
Slow pathfutex(WAIT) sleeps; futex(WAKE) wakesA syscall plus a context switch

§2A Three-State Mutex

A classic design uses three values: 0 unlocked, 1 locked with no waiters, 2 locked with possible waiters. The unlocker only needs a syscall if the state was 2.

// cmpxchg(addr, expected, new) returns the old value
void lock(int *v) {
    int c = cmpxchg(v, 0, 1);
    if (c != 0) {                      // contended
        do {
            if (c == 2 || cmpxchg(v, 1, 2) != 0)
                futex_wait(v, 2);      // sleep while *v == 2
        } while ((c = cmpxchg(v, 0, 2)) != 0);
    }
}

void unlock(int *v) {
    if (atomic_fetch_sub(v, 1) != 1) { // there were waiters (state was 2)
        *v = 0;
        futex_wake(v, 1);              // wake exactly one
    }
}

futex_wait(addr, val) sleeps only if *addr still equals val, checked atomically inside the kernel. That check is what prevents a lost wakeup between 'I saw it locked' and 'I went to sleep'.

§3Where Futexes Show Up

pthread mutexes, condition variables, semaphores, and read-write locks on Linux are all built on futexes. When you see many futex calls in a trace, you're seeing lock contention: threads sleeping and waking.

strace -f -c -e trace=futex ./server       # count futex calls across all threads
strace -f -T -e trace=futex -p PID         # time spent in each wait

Futexes are keyed by address, so processes can synchronize through shared memory too, as long as the lock lives in a shared mapping.

Connection to earlier lessons This is the hybrid lock from Stage 2.2 in concrete form: an atomic fast path in user space, then sleep in the kernel. The release and acquire semantics from the atomics lesson are what make the lock's critical section safe.

§4Common Mistakes

MistakeWhat HappensFix
Making a syscall on every unlockUncontended locks become slowTrack waiter state so unlock only calls the kernel when someone sleeps
Sleeping without the atomic value checkA lost wakeup leaves a thread asleep foreverPass the expected value to futex_wait, as the kernel rechecks it
Assuming many futex calls mean slow syscallsThe real problem is contentionReduce sharing, shorten critical sections, or shard the lock
Practice
  1. Trace a multi-threaded program with strace -f -c. Which syscall dominates, and what does it say about contention?
  2. Explain why state 2 exists. What breaks if unlock always calls futex_wake, and what breaks if it never does?
Key takeaways
  • A futex keeps uncontended locking in user space and uses the kernel only to sleep and wake.
  • The kernel's atomic value check inside futex_wait prevents lost wakeups.
  • Frequent futex calls in a trace are a sign of lock contention.
