Observing a Live System: strace, perf, /proc & eBPF

Good diagnosis starts with picking the tool that answers your specific question at a cost the production system can tolerate.

§1Match the Tool to the Question

QuestionToolOverhead
What is this process asking the kernel for?straceHigh: it slows the target noticeably
Where is CPU time being spent?perf record / perf topLow: samples the stack periodically
What are its memory, threads, and open files?/proc/<pid>/ filesNegligible: reads kernel counters
Why is it blocked or off-CPU?perf sched, eBPF toolsLow to moderate
Who opens files, runs programs, or hits the disk?eBPF (bpftrace, bcc tools)Low, and filtered inside the kernel

The most common mistake is reaching for strace on a busy production process, where its overhead can itself cause the outage you're investigating.

§2The Everyday Tools

# Syscalls: summary first, then drill in
strace -f -c -p PID               # counts and time per syscall (Ctrl-C to print)
strace -f -T -e trace=file ./prog # only file syscalls, with durations

# CPU profile with call stacks
perf record -F 99 -g -p PID -- sleep 30
perf report

# The kernel's own bookkeeping
cat /proc/PID/status              # threads, memory, context switches
ls -l /proc/PID/fd | wc -l        # open descriptors
cat /proc/PID/smaps_rollup        # Rss, Pss, swap
cat /proc/PID/stack               # where a blocked task is waiting in the kernel

A sampling profiler such as perf interrupts the CPU ~99 times a second and records the stack. Functions that appear in many samples are where time goes. Turn the output into a flame graph to see the whole picture at once.

§3eBPF: Programmable Kernel Tracing

eBPF lets you load small, verified programs into the kernel to collect exactly the data you want, attached to system calls, kernel functions, or events. Because filtering and aggregating happen in the kernel, it's cheap enough for production.

sudo opensnoop-bpfcc                 # who is opening which files, live
sudo execsnoop-bpfcc                 # every new process started
sudo biolatency-bpfcc                # histogram of disk I/O latency
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'

Start with questions, not tools: what do I expect, what do I observe, and which measurement would separate the possible explanations?

The key insight Each tool changes the system it measures. Choose by the question and by the overhead you can afford, and prefer sampling and in-kernel aggregation over tracing every event.

§4Common Mistakes

MistakeWhat HappensFix
Attaching strace to a busy production serviceOverhead slows requests or causes timeoutsUse perf or eBPF with filters, or strace -c briefly on one process
Profiling for a few seconds during a quiet periodThe problem doesn't appear in the sampleCapture during the incident, long enough to include rare events
Looking only at on-CPU timeThreads that are blocked aren't visibleAlso check off-CPU time: I/O, locks, and scheduling delays
Practice
  1. Run strace -f -c on a short command such as ls -R /usr. Which syscalls dominate, and what does that tell you?
  2. Record a 30-second perf profile of a busy process, and identify the top three functions by sample count.
Key takeaways
  • Pick tools by the question asked and the overhead tolerable.
  • /proc is free; perf samples cheaply; strace is powerful but heavy.
  • eBPF provides low-overhead, targeted tracing suitable for production.
