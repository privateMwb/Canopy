Debugging Deadlocks, Leaks & Crashes

The hardest bugs are the ones you can't reproduce on demand, so the skill is capturing enough evidence from a single occurrence.

§1Deadlocks: Read the Thread Stacks

A hung process is often a deadlock. Attach a debugger and dump every thread's stack. Threads waiting inside lock calls reveal who holds what.

gdb -p PID
(gdb) thread apply all bt          # a stack for every thread
(gdb) detach

# Without a debugger: kernel-side view of each thread
for t in /proc/PID/task/*; do echo $t; cat $t/stack; done

Look for threads blocked in pthread_mutex_lock or futex_wait, then find which thread owns each mutex. In glibc you can inspect the lock's __owner field in the debugger. A cycle among the waiters is the deadlock. Fix it by establishing a global lock order from Stage 2.2.

§2Crashes: Core Dumps

A core dump is a snapshot of a crashed process's memory. It lets you inspect the state after the fact, which is essential when the crash is rare.

ulimit -c unlimited                 # allow core files in this shell
coredumpctl list                    # on systemd systems, dumps are captured here
gdb ./prog core                     # open the dump
(gdb) bt                            # where it crashed
(gdb) info threads
(gdb) frame 3
(gdb) print *ptr

Build with symbols (-g) and keep the exact binary that crashed, since the core can't be decoded without it. A crash far from the root cause usually means memory corruption, so reproduce under AddressSanitizer.

§3Leaks and Races

Leaks show up as RSS growing over time. Confirm the trend, then find the allocation sites.

watch -n 5 'grep -E "VmRSS" /proc/PID/status'   # is it growing without bound?
valgrind --leak-check=full ./prog                # slow; good for short test runs
heaptrack ./prog                                 # lower overhead; shows growth by call stack
gcc -fsanitize=thread -g prog.c                  # races; run the stress test under it

For bugs that only occur under load, increase the odds: run with many threads, add random delays at suspect points, and run in loops under stress-ng. Enable core dumps in production so that the next occurrence leaves evidence.

The key insight Collect evidence at the time of failure, because an intermittent bug may not recur. Thread stacks for hangs, core dumps for crashes, and heap profiles for growth are your three standard captures.

§4Common Mistakes

MistakeWhat HappensFix
Restarting a hung process without capturing stateEvidence is lost, and the bug returnsTake a thread dump or core first, then restart
Debugging a core with a different binarySymbols and addresses don't matchArchive the exact build that's deployed
Concluding it's fixed after one clean runA race may simply not have triggeredStress test under ThreadSanitizer and repeat many times
Practice
  1. Create a two-lock deadlock, attach gdb, and identify from the stacks which thread holds which lock.
  2. Make a program that segfaults, produce a core dump, and use gdb to find the line and the variable that caused it.
Key takeaways
  • For hangs, dump all thread stacks and look for a cycle of waiting.
  • For crashes, enable core dumps and keep the matching binary with symbols.
  • For leaks and races, use sampling heap profilers and ThreadSanitizer, and stress the code.
