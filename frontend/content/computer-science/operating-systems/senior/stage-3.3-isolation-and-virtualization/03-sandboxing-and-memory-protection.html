Sandboxing & Memory Protection

Security comes from stacking layers, each limiting what a compromised process can do or what an attacker can predict about its memory.

§1Limiting What a Process May Ask For

A process that's compromised can still make system calls. Two mechanisms shrink its options.

  • Capabilities split root's powers into pieces, such as CAP_NET_BIND_SERVICE for low ports or CAP_SYS_TIME for the clock. A service needs only the few it uses; drop the rest.
  • seccomp-bpf installs a filter that allows or blocks system calls by number and arguments. A web server doesn't need mount or ptrace, so the filter kills it if it tries.
# See and drop capabilities
capsh --print
setpriv --no-new-privs --bounding-set=-all ./untrusted

# Docker's default seccomp profile blocks dozens of risky syscalls

no_new_privs prevents a process and its descendants from gaining privileges through setuid binaries, so a sandbox can't be undone from inside.

§2Making Memory Hard to Exploit

Most exploits depend on predictable memory. Several defenses, each from the memory lessons you've covered, target that:

DefenseWhat it doesWhat it stops
NX / DEPMarks data pages non-executable (the NX bit in the page table)Running injected code from the stack or heap
ASLRRandomizes addresses of stack, heap, and librariesHard-coded addresses in an exploit
PIERandomizes the executable's own base addressFixed addresses inside the program itself
Stack canariesA secret value placed before the return address and checked on returnLinear stack buffer overflows
RELROMakes relocation tables read-only after startupOverwriting function pointers in the GOT
# Check which protections a binary was built with
checksec --file=./prog
gcc -fstack-protector-strong -fPIE -pie -Wl,-z,relro,-z,now prog.c

Each defense can be bypassed individually, for example, by an information leak that reveals randomized addresses, which is why they're combined.

§3Defense in Depth and W^X

A sound design assumes some layer will fail. A web server might run unprivileged, in its own namespaces, with a tight seccomp profile and read-only filesystem, so that a memory bug yields little. Follow W^X (write xor execute): a page should be writable or executable, never both. JIT compilers handle this by writing code to a writable page, then switching it to executable with mprotect.

void *p = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
// ... write machine code into p ...
mprotect(p, 4096, PROT_READ | PROT_EXEC);   // now executable, no longer writable
The key insight No single defense stops a determined attacker. The goal is to raise the cost of each step and to limit the damage when one step succeeds. Memory-safe languages remove whole classes of bugs these defenses exist to contain.

§4Common Mistakes

MistakeWhat HappensFix
Running a service as root 'for convenience'Any compromise gains full privilegesDrop to an unprivileged user and keep only needed capabilities
Relying on ASLR aloneA single address leak defeats itCombine with NX, canaries, PIE, and least privilege
Mapping memory as read-write-executeGives attackers a place to run injected codeFollow W^X; make code pages non-writable
Practice
  1. Compile a small program with and without stack protection, PIE, and RELRO, and compare the checksec output.
  2. Write a seccomp filter (or use bwrap/Docker's profile) that blocks socket, and show a program being killed when it tries to open one.
Key takeaways
  • Capabilities and seccomp restrict what a compromised process can request from the kernel.
  • NX, ASLR, PIE, canaries, and RELRO make memory exploitation harder, and each can be bypassed alone.
  • Layer defenses and follow W^X so that one failure doesn't mean total compromise.
