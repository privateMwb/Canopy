Namespaces: What a Container Really Is

A container is an ordinary process whose view of the system has been restricted by kernel namespaces, with no separate kernel involved.

§1Namespaces Restrict What a Process Can See

A namespace gives a process its own private view of one kind of system resource. Processes in the same namespace share that view; those in different namespaces can't see each other's. Linux has several kinds:

NamespaceIsolates
PIDProcess IDs: the first process inside sees itself as PID 1
MountThe filesystem tree and mount points
NetworkInterfaces, IP addresses, routing, ports
UTSHostname and domain name
IPCSystem V IPC and POSIX message queues
UserUser and group IDs (root inside can map to an unprivileged user outside)
CgroupThe view of the cgroup hierarchy
ls -l /proc/self/ns                        # the namespaces your process belongs to
sudo unshare --pid --fork --mount-proc bash
ps aux                                      # only a handful of processes, bash is PID 1

§2Assembling a Container

A container runtime combines several pieces and calls it a container:

  1. Namespaces to restrict what the process can see
  2. cgroups to restrict how much it can use (next lesson)
  3. A root filesystem from an image, mounted using pivot_root or chroot
  4. Security layers such as dropped capabilities and a seccomp filter
  5. The process itself, started with exec
// Namespaces are created with clone() or unshare() flags
clone(child_fn, stack_top,
      CLONE_NEWPID | CLONE_NEWNS | CLONE_NEWNET | CLONE_NEWUTS | SIGCHLD, NULL);

From the host, the 'container' is visible as a normal process in ps, with a different PID than the one it sees for itself.

§3What Namespaces Don't Do

All containers on a host share one kernel. A kernel vulnerability, or an escape through a misconfigured capability, can break out of every namespace. Namespaces also say nothing about resource limits, so by themselves they don't stop a container from using all the CPU or memory.

PropertyContainerVirtual machine
KernelShared with the hostIts own guest kernel
StartupMilliseconds, just a processSeconds, boots an OS
OverheadVery lowHigher, but better isolated
Isolation strengthWeaker: shared kernel attack surfaceStronger: hypervisor boundary
The key insight 'Container' is not a kernel feature. It's a convention built on namespaces, cgroups, and a root filesystem. Once you see the parts, debugging container behavior becomes ordinary process debugging.

§4Common Mistakes

MistakeWhat HappensFix
Treating a container as a lightweight VMAssuming a separate kernel and strong isolationRemember the shared kernel and limit privileges accordingly
Running containers as root with extra capabilitiesAn escape yields root on the hostUse user namespaces, drop capabilities, and avoid privileged mode
Believing PID 1 in a container is just another processSignals and zombies aren't handled as expectedUse a proper init process, such as --init or tini, to forward signals and reap children
Practice
  1. Use unshare to start a shell with new PID and UTS namespaces. Change the hostname inside it and confirm the host's is unchanged.
  2. Find a containerized process from the host with ps, compare its PID with the one it sees inside, and inspect /proc/<pid>/ns.
Key takeaways
  • Namespaces give a process its own view of PIDs, mounts, network, and more.
  • A container is namespaces, cgroups, a root filesystem, and security filters around a normal process.
  • Containers share the host kernel, so their isolation is weaker than a VM's.
