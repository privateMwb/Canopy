NUMA & Memory Placement

On large machines, memory attached to another socket is slower to reach, so where a thread runs and where its memory lives both matter.

§1What NUMA Is

In a non-uniform memory access (NUMA) system, each CPU socket has its own directly attached memory, called a node. A core can reach all memory, but its own node's memory is faster than a remote node's, often by 1.5 to 2 times in latency, with lower bandwidth across the interconnect.

numactl --hardware          # nodes, their CPUs, memory sizes, and distances
lscpu | grep -i numa
numastat -p PID             # per-node memory use of one process

A single-socket desktop is typically one node, but multi-socket servers and some large single-socket chips expose several.

§2First-Touch and Placement Policy

By default, Linux allocates a page on the node where the thread first touched it. A common bug is a main thread that initializes a huge array, placing all pages on its node, and then many worker threads on other nodes read it remotely.

// Bad: main thread touches everything first -> all pages on one node
memset(big, 0, SIZE);
spawn_workers_on_all_nodes(big);

// Better: each worker initializes the slice it will use
worker(i) { memset(big + i*CHUNK, 0, CHUNK); compute(big + i*CHUNK); }

This is demand paging from Stage 2.3 interacting with scheduling: where the page fault happens decides where the page lives.

§3Controlling Placement

numactl --cpunodebind=0 --membind=0 ./app     # run on node 0, allocate from node 0
numactl --interleave=all ./db                 # spread pages round-robin across nodes
  • Bind a process and its memory to one node when it fits, for the lowest latency
  • Interleave when data is shared by threads on all nodes and bandwidth matters more than latency
  • Automatic NUMA balancing in Linux can migrate pages toward the threads using them, at the cost of extra page faults to track access

Moving a thread to another node with taskset while its memory stays behind makes it slower, so pin CPU and memory together.

Connection to earlier lessons Per-core run queues and affinity from Stage 2.1 pull threads toward warm caches. NUMA adds a second reason to keep a thread in place: its memory is on a particular node.

§4Common Mistakes

MistakeWhat HappensFix
Initializing all data in one threadAll pages land on one node, and other nodes access remotelyInitialize in the threads that will use the data, or interleave
Pinning CPUs but not memoryThreads run locally against remote memoryUse --membind or --localalloc along with CPU binding
Ignoring NUMA on multi-socket serversThroughput plateaus while remote accesses climbCheck numastat and measure both bandwidth and latency
Practice
  1. On a multi-node machine, run a memory-bound benchmark bound to node 0 CPUs with memory on node 0, then with memory on node 1. Compare times.
  2. Explain how first-touch could make a parallel program slower after you 'optimized' its initialization into a single thread.
Key takeaways
  • NUMA machines have per-socket memory; remote access is slower with less bandwidth.
  • Linux places a page where it's first touched, so initialization strategy matters.
  • Use numactl to bind CPUs and memory together, or interleave for shared data.
