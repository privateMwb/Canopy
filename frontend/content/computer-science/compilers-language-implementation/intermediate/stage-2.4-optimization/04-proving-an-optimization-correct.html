Proving an Optimization Correct

An optimization is only worth having if it preserves what the program means, and the only way to trust that is to test it against an unoptimized baseline.

§1What 'correct' means

An optimization is semantics-preserving if the optimized program has the same observable behaviour as the original for every input. 'Observable' needs a definition: for Twig, it's the sequence of print outputs, the final exit status, and any runtime errors (including *which* error).

# allowed: removing unobservable work
t = a * b            # t unused, no side effects  →  removed

# not allowed: changing observable behaviour
print f();           # reordering these two calls changes output order
print g();

Compilers often have wiggle room the language grants, such as unspecified evaluation order in some languages. Twig doesn't: it fixes left-to-right order, so reordering calls would be a bug.

§2Undefined behaviour and the contract

Some languages say certain programs have undefined behaviour, and the optimizer may assume they never happen. That makes optimization easier and bugs much nastier.

Twig makes the opposite choice: every error is a defined runtime error. That limits some optimizations, such as hoisting a possible division by zero, but makes the optimizer's job well defined. Whichever you choose, write it down. The optimizer and the programmer must share one contract.

Twig contract (excerpt):
- Integer overflow wraps (two's complement, 64-bit).
- Division by zero is a runtime error at that operation, in program order.
- Out-of-range indexing is a runtime error at that operation.

§3Testing optimizations

The most effective test is differential: run each program with and without the optimization and compare observable output.

for program in all_test_programs:
    for pass_set in [none, fold, fold+dce, all]:
        assert run(compile(program, passes=pass_set)) == run(compile(program, passes=none))

More tools to add:

  • A verifier run after every pass (all blocks end in terminators, every use is dominated by its definition, phis match predecessors) to catch malformed IR immediately.
  • Per-pass flags so a failing program can be bisected: which pass breaks it?
  • Benchmarks that show the optimization actually helps. An optimization that gives no speedup is just a risk.
$ twigc --passes=fold,dce,inline --verify-each prog.twig
$ twigc --bisect prog.twig       # find the first pass whose output differs
The key insight An optimizer is a program that rewrites programs, so its bugs silently change other people's results. The unoptimized path is both your fallback and your test oracle.

§4Common Mistakes

MistakeWhat HappensFix
Optimizing without a reference implementationA wrong optimization looks like normal outputKeep the unoptimized path and compare against it in tests
Not verifying IR between passesA bug in one pass shows up as a crash three passes laterRun the verifier after every pass in testing
Assuming an optimization helpsIt adds risk with no gain, or even slows things downBenchmark before and after on realistic programs
Practice
  1. Write down five clauses of the Twig semantic contract that an optimizer must respect, and for each, name a tempting optimization that would violate it.
  2. Design a --bisect option: given a program that gives different output with all passes enabled, how would you find the guilty pass automatically?
Key takeaways
  • Semantics-preserving means the same observable behaviour: output, errors, and their order.
  • A written contract, including how errors and overflow behave, is the reference for every pass.
  • Differential testing, a verifier after each pass, and benchmarks keep optimization honest.
