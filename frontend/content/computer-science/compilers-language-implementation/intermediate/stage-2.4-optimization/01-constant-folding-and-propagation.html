Constant Folding & Propagation

Constant folding computes at compile time whatever is already known, and constant propagation spreads those known values to where they are used.

§1Folding

If every operand of an instruction is a constant, the compiler can do the arithmetic itself and replace the instruction with the result.

before:   t1 = 60 * 60
          t2 = t1 * 24
after:    t1 = 3600
          t2 = 86400

Folding is local and simple: look at one instruction, check that its operands are constants, and evaluate.

def fold(ins):
    if ins.op in ARITH and is_const(ins.a) and is_const(ins.b):
        return Const(apply(ins.op, ins.a.value, ins.b.value))
    return ins

§2Propagation

Folding exposes more opportunities. If x1 = 5 and x1 is used later, we can substitute 5 for x1, which may make the next instruction foldable too.

x1 = 5                      x1 = 5
y1 = x1 * 2        ──►      y1 = 10
z1 = y1 + x1                z1 = 15

In SSA this is trivial, since every name has exactly one definition (Stage 2.2). A worklist keeps going until nothing changes.

def propagate(func):
    changed = true
    while changed:
        changed = false
        for ins in func.instructions():
            new = fold(substitute_known_constants(ins))
            if new != ins: replace(ins, new); changed = true

Without SSA, propagation has to check that the variable hasn't been reassigned on any path between the definition and the use. That's exactly the complexity SSA removes.

§3Where folding is unsafe

Folding must produce exactly what the program would have computed. Edge cases matter.

t = 1 / 0              # don't fold: it must be a runtime error, and only if executed
t = a + 0              # fine to simplify to 'a' only if a is known to be an int
t = 9223372036854775807 + 1     # fold with the same overflow rule the VM uses

Rules for safe folding:

  • Use the same arithmetic the VM or hardware would, including overflow behaviour.
  • Never fold something that would raise a runtime error, or the error moves from run time to compile time (or disappears).
  • Beware of types: in a dynamic language, a + 0 might be string concatenation, not the identity.
The key insight Compile-time evaluation is only correct if it exactly mimics run-time evaluation, including the edge cases. Every folding rule is a small proof obligation.

§4Common Mistakes

MistakeWhat HappensFix
Folding x / 0A runtime error becomes a compile-time crash, or the error is silently droppedLeave it for run time
Using the host language's arithmetic when it differs from the VM'sFolded and unfolded programs give different results on overflowShare the arithmetic implementation between the folder and the VM
Simplifying x * 0 to 0 in a dynamic languageA string or nil times zero should be an error, and is no longerOnly apply identities when types are known
Practice
  1. Write the folding rules for comparisons and for not, then list one case for each where folding is not allowed.
  2. Show a three-instruction SSA sequence where propagating one constant lets two later instructions fold.
Key takeaways
  • Constant folding evaluates instructions whose operands are all known.
  • Propagation substitutes known values, enabling more folding; SSA makes it simple.
  • Folding must mirror run-time behaviour exactly, including overflow and errors.
