Static Single Assignment

In static single assignment form every variable is defined exactly once, which makes 'where did this value come from?' a lookup instead of an analysis.

§1One definition per name

In ordinary IR a variable like x can be assigned many times, so at any use you need to work out which assignment reached it. SSA removes the question by renaming: every assignment creates a new name, and every use refers to exactly one definition.

before:             after (SSA):
x = 1               x1 = 1
x = x + 2           x2 = x1 + 2
y = x * 3           y1 = x2 * 3

Now x2 is defined once, at one place, and everything that uses it can find that definition directly. Facts like 'x1 is the constant 1' stay true forever, because x1 can never change.

§2Phi nodes

Straight-line code renames easily. The problem is joins, where two paths merge and a variable might have come from either.

if (c) { x = 1; } else { x = 2; }
print x;

In SSA each branch defines its own version, and the join needs a way to pick one. A phi (φ) instruction does it, choosing a value based on which block control came from.

 entry:   branch c, then, else
 then:    x1 = 1;  jump join
 else:    x2 = 2;  jump join
 join:    x3 = phi [x1, then], [x2, else]
          print x3

phi isn't a real machine instruction. It is a notation meaning 'x3 is x1 if we came from then, and x2 if we came from else.' Back ends eventually replace phis with copies on the incoming edges.

§3Where to put phis

You don't need a phi for every variable at every join, only where different definitions actually meet. The standard algorithm uses dominance frontiers: for each variable, put a phi at the blocks just beyond the region where a definition dominates.

# outline of SSA construction
1. Compute dominators and dominance frontiers for the CFG.
2. For each variable v, for each block that defines v:
       place a phi for v at every block in its dominance frontier
       (repeat, since a phi is itself a new definition)
3. Walk the dominator tree, renaming:
       each definition gets a fresh version;
       each use refers to the latest version on the current path.

Simpler compilers can skip this and put phis for every variable at every join, then clean up. The result is correct but larger.

SSA pays off in optimization. Constant propagation becomes 'replace uses of x1 with 1.' Dead code elimination becomes 'delete a definition with no uses.' Both are simple because each name has exactly one definition.

The key insight SSA turns the question 'which assignment reached this use?' into a lookup, because every use points at one definition. Most classic optimizations get simpler as a result.

§4Common Mistakes

MistakeWhat HappensFix
Renaming in straight-line code but forgetting loopsA loop-carried variable has no phi, and uses of its previous value become wrongPut a phi at the loop header for each variable assigned in the loop
Treating phi as an ordinary instruction in the middle of a blockThe 'which predecessor' meaning breaksKeep all phis at the start of a block, with one entry per predecessor
Assuming phis cost something at run timeYou avoid SSA for fear of overheadPhis are eliminated before code generation, usually by copies on edges
Practice
  1. Convert i = 0; while (i < 3) { i = i + 1; } to SSA by hand, including the phi at the loop header.
  2. Write the phi for a variable assigned in only one arm of an if, and say what its other incoming value is.
Key takeaways
  • SSA gives each variable exactly one definition by renaming on every assignment.
  • Phi nodes merge values at control-flow joins, selecting by which block control came from.
  • Single definitions make constant propagation and dead code elimination simple.
