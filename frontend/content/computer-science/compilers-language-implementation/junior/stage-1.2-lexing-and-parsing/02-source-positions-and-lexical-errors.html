Source Positions & Lexical Errors

Every token should remember where it came from, and the lexer should turn bad input into clear errors instead of crashing.

§1Tracking positions

An error message that says 'something went wrong' is not much use. One that says line 4, column 12 is. Store a position on every token as it is created.

struct Token { type, lexeme, value, line, col }

# the scanner keeps these as it advances
def advance():
    c = source[current]; current += 1
    if c == '\n': line += 1; col = 1
    else:         col += 1
    return c

Some implementations store only a byte offset in each token and compute line and col on demand by scanning for newlines. That keeps tokens smaller and works well for tools that re-map positions after edits.

§2Comments and strings

Comments are skipped, but the scanner must still count newlines inside them. Strings are trickier because they have their own mini-syntax.

def string():
    start_line = line
    while peek() != '"' and not at_end():
        if peek() == '\\':             # escape sequence
            advance()
            match advance():
                'n': buf.append('\n')
                '"': buf.append('"')
                '\\': buf.append('\\')
                else: error("unknown escape")
        else:
            buf.append(advance())
    if at_end():
        error("unterminated string", start_line)
    advance()                          # closing quote
    add(STRING, buf.join())

Report an unterminated string at the line where it began, not where the file ended. The place the string started is where the programmer's mistake is.

§3Reporting errors without stopping

When the scanner sees something it cannot use, it should record an error, skip that character, and keep going. That way one run reports every lexical problem instead of only the first.

error: unexpected character '@'
  --> program.twig:7:14
   |
 7 | let a = 5 @ 3;
   |             ^

Collect errors in a list. The driver decides after scanning whether to stop or continue to the parser.

Connection to later stages The position you store here is what the type checker, the interpreter, and even a debugger will point at much later. Retrofitting positions onto an existing lexer is far harder than carrying them from the start.

§4Common Mistakes

MistakeWhat HappensFix
Recording positions only on errorsLater stages have no locations to reportPut line and column (or offset) in every token
Not counting newlines inside comments and stringsEvery line number after a multi-line string is wrongUpdate the line counter in advance(), so every path goes through it
Aborting on the first bad characterProgrammers fix one error per runRecord the error, skip the character, keep scanning
Practice
  1. Write the scanner code for /* ... */ block comments that keeps line numbers correct and reports an unterminated comment where it began.
  2. Given a list of newline offsets, write a function that turns a byte offset into a line and column.
Key takeaways
  • Store a line and column, or an offset, on every token.
  • Strings need escape handling and an unterminated-string error reported at the opening quote.
  • Collect lexical errors and keep scanning so one run shows them all.
