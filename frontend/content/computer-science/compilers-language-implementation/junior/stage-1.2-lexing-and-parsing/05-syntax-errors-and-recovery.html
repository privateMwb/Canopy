Syntax Errors & Recovery

Real programs contain mistakes, so a parser must report the first error clearly and then recover, so it can find the next one instead of giving up.

§1What a good syntax error says

The easiest error to produce is syntax error. The most useful says what was expected, what was found, and where.

error: expected ')' after condition, found '{'
  --> game.twig:12:18
   |
12 | if (score > 10 {
   |                ^

Our expect(type, message) helper already gives us this. Pass a message that describes the rule being parsed ('after condition'), and the token the parser actually saw is available from peek().

§2Panic-mode recovery

After the first error the parser's position is meaningless: it does not know how much of the bad statement is left. If it carries on, it reports a pile of nonsense errors caused by the first one. The standard fix is panic mode: throw away tokens until we reach a place that is likely to be the start of a new statement, then resume.

def synchronize():
    advance()
    while not check(EOF):
        if previous().type == SEMICOLON: return      # statement just ended
        if peek().type in (LET, FN, IF, WHILE, FOR, PRINT, RETURN):
            return                                   # a statement is starting
        advance()

def declaration():
    try:
        return parse_declaration()
    catch ParseError:
        synchronize()
        return nil

The parser records the error in a list, synchronizes, and continues. At the end it reports every error found, and does not run the program.

§3Cascading errors

Recovery is a heuristic, not a guarantee. A missing } can still make the parser misread what follows. Good habits limit the damage.

  • Report only the first error inside a single statement; discard errors until synchronization.
  • Cap the number of errors shown (for example, 20).
  • Test with deliberately broken programs and check that the second error is a real one, not an echo.
let x = ;        // error 1: expected expression
let y = 5 + ;    // error 2: still reported, because we resynchronized at ';'
print x          // error 3: expected ';' after value
The key insight The goal of recovery is not to fix the program. It is to make sure the second error message you show is as trustworthy as the first.

§4Common Mistakes

MistakeWhat HappensFix
Throwing an exception and stopping at the first errorProgrammers fix one problem per runCatch at the statement level, synchronize, and continue
Resynchronizing on any tokenThe parser stops in the middle of an expression and emits false errorsSkip to a ; or to a keyword that begins a statement
Running the program after a parse errorThe tree is incomplete and execution behaves unpredictablyReport all errors and exit before the next stage
Practice
  1. Write three small broken Twig programs and write down, for each, the error list you would want the parser to produce.
  2. Add } as a synchronization point so a block with a missing statement does not swallow the rest of the file.
Key takeaways
  • A good syntax error names what was expected, what was found, and where.
  • Panic mode skips tokens to a statement boundary, then keeps parsing.
  • Recovery is a heuristic, so test that follow-up errors are real.
