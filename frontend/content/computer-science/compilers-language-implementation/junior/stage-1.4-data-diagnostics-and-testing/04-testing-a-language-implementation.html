Testing a Language Implementation

A language implementation is only as trustworthy as its tests, and the best ones are plain files of Twig code with their expected output next to them.

§1Golden-file tests

Rather than writing a unit test per function, keep a directory of small Twig programs and the output each should produce. This is called golden-file (or snapshot) testing.

tests/
  arithmetic/precedence.twig         print 1 + 2 * 3;
  arithmetic/precedence.expected     7
  closures/counter.twig              ...
  closures/counter.expected          1
                                     2
  errors/undefined_var.twig          print y;
  errors/undefined_var.expected      error: undefined variable 'y' ...

A test runner runs each .twig file through the implementation and compares the output to the .expected file. A new bug becomes a new pair of files.

§2One feature per test

Small, focused programs make failures obvious. A test called shadowing.twig that fails tells you where to look. A single 200-line program that fails does not.

// closures/shared_variable.twig
fn pair() {
  let x = 0;
  return rec { inc: fn() { x = x + 1; }, get: fn() { return x; } };
}
let p = pair();
p.inc(); p.inc();
print p.get();        // expect 2

Cover each rule in the spec, the boundaries (empty arrays, index 0 and last, division by zero), and each error path. Errors are features, so test the exact message and the position too.

§3Keeping tests meaningful

Golden files are easy to update, which is also their weakness. A runner that can 'accept new output' makes it easy to bless a bug.

$ twig-test            # run all, show diffs for failures
$ twig-test --accept   # overwrite .expected files — review the diff first!

Good habits: review every changed .expected file in version control, never accept output you have not read, and keep a test for every bug you fix so it can never silently come back. Later, when you add a second implementation (a bytecode VM), the same files test both of them.

Connection to later stages In Stage 2.3 the bytecode VM must produce the same output as this interpreter on every test. A thorough golden suite written now is what makes that rewrite safe.

§4Common Mistakes

MistakeWhat HappensFix
Blessing new output without reading itA bug is recorded as the correct behaviourReview .expected diffs like code
Testing only programs that should workError handling is untested and regresses firstAdd tests for every error message and span
Giant test programsOne failure hides others and is hard to diagnoseWrite many small programs, one feature each
Practice
  1. Write five golden tests for closures, including one that checks two counters don't share state.
  2. Add a test runner that runs every .twig file and prints a diff for failures, and a flag to update expected files.
Key takeaways
  • Golden-file tests pair a small Twig program with its expected output.
  • Test each rule, boundary, and error message, one feature per file.
  • A thorough suite lets you replace the implementation (tree-walker to VM) and still trust the result.
