Values, Truthiness & Dynamic Typing

Every Twig value has a runtime type, and the rules for equality and truthiness have to be decided and written down before the interpreter can be correct.

§1Representing values

A dynamically typed interpreter needs one host type that can hold any Twig value, and a way to ask 'what is this?'. A tagged union does both.

# pseudocode
Value = Int(i64)
      | Bool(b)
      | Str(s)
      | Nil
      | Array(ref to list of Value)
      | Record(ref to map of name → Value)
      | Function(ref to function object)

Small values (ints, bools, nil) can be stored inline. Larger ones (strings, arrays, records) live on the heap and the value holds a reference. That split matters later: heap values are what a garbage collector has to track.

§2Truthiness and equality

Two questions come up on every if and every ==, and Twig answers them with fixed rules.

def truthy(v):
    return not (v is Nil or v == Bool(false))

def values_equal(a, b):
    if type(a) != type(b): return false     # 1 == "1" is false, no coercion
    match a:
        Int, Bool, Str:  return a.value == b.value
        Nil:             return true
        Array, Record, Function: return same_object(a, b)   # identity

Twig does not coerce between types. 1 == "1" is false rather than an error or true, and arrays compare by identity: two arrays with the same contents are still different arrays.

§3Why choose strict rules

Languages that coerce quietly (turning "5" into 5 to make + work) are convenient until a typo hides inside the convenience. Strictness trades a little typing for errors that show up near their cause.

print 1 + "2";        // runtime error: '+' needs two numbers or two strings
print "a" + "b";      // "ab"
print nil == false;   // false: different types
print not nil;        // true: nil is falsy

Whatever rules you choose, choose them once, test them, and make the interpreter, the VM, and any optimizer agree. Disagreements between stages here are some of the nastiest bugs to find later.

The key insight Truthiness, equality, and coercion are part of the language definition, not implementation details. An optimizer that changes them has changed the language.

§4Common Mistakes

MistakeWhat HappensFix
Using the host language's equality on every valueArrays compare by contents in one place and identity in anotherWrite values_equal once and use it everywhere
Borrowing the host's truthiness rules0 or "" behave differently from the Twig specImplement truthy explicitly
Coercing types to avoid errorsTypos like "5" + 1 produce surprising values instead of failingReject mismatched types with a clear runtime error
Practice
  1. Write a table of what each of 0, "", nil, [], and false does in an if, and in == against each other.
  2. Implement a type_name(v) function and use it so runtime errors say "got string" rather than just "bad operand".
Key takeaways
  • Values are tagged unions; small ones inline, large ones as heap references.
  • Truthiness and equality have exact, written rules and no hidden coercion.
  • Every later stage must reproduce the same rules, or it changes the language.
