Meet Twig

Twig is a small dynamically typed language with just enough features to need every stage of a real implementation, and nothing more.

§1A tour of Twig

Twig looks like a small member of the curly-brace family, but it is invented for this course. Nothing about it is meant to match a production language, which keeps us focused on the machinery rather than on any one language's quirks.

// Twig: a function, a loop, and printing
fn fib(n) {
  if (n < 2) { return n; }
  return fib(n - 1) + fib(n - 2);
}

let i = 0;
while (i < 10) {
  print fib(i);
  i = i + 1;
}

Statements end in ;. Blocks use braces. let declares a variable; plain = assigns to an existing one. Comments start with //.

§2What is in the language

Twig has a deliberately short feature list:

  • Values: integers, booleans (true, false), strings, nil, arrays, records, and functions.
  • Operators: + - * / %, comparisons, == and !=, and the short-circuiting and, or, and not.
  • Control flow: if/else, while, for, break, and return.
  • Functions: named with fn name(...), anonymous with fn(...), and they can capture variables from where they are defined.
  • Compound data: [1, 2, 3], indexing with a[0], and records like rec { x: 1, y: 2 } with p.x.

Types are checked at run time at first. In Stage 2.1 we add optional annotations such as let n: int = 3; and a static checker.

§3What is left out, on purpose

No classes, no modules, no floating point, no standard library beyond print and a few helpers, no exceptions, no concurrency. Each missing feature is something a real language needs, but each would add a chapter without adding a new idea until the Senior level, where several come back on purpose.

Twig's semantics are fixed by a few plain rules that every later stage must preserve:

1. Evaluation order is left to right.
2. Arguments are evaluated before the call.
3. 'and' / 'or' skip their right side when the left decides the answer.
4. Only false and nil are falsy; everything else is truthy.
5. Variables are lexically scoped: a name means the nearest enclosing let.

Whatever we build next, interpreter or compiler, optimized or not, must print the same output for the same Twig program. That is our definition of correct.

The key insight A language is a specification before it is a program. Writing the rules down, like the five above, is what lets you decide later whether an optimization is a bug or a feature.

§4Common Mistakes

MistakeWhat HappensFix
Leaving evaluation order unspecifiedDifferent stages or targets evaluate f() + g() in different orders, and output changesFix an order in the spec (Twig uses left to right) and test it
Adding features before the core worksEvery later stage carries complexity it did not need yetGrow the language in small steps, each with tests
Defining semantics only by what your interpreter doesInterpreter bugs become 'the language', and a second implementation disagreesWrite the intended rules down separately and test against them
Practice
  1. Write a Twig program that prints the first ten squares using a for loop.
  2. Write a Twig function max3(a, b, c) using only if and return, then say which of the five semantic rules your program relies on.
Key takeaways
  • Twig is a small dynamic language, invented so no production language's quirks get in the way.
  • Its few features are chosen to need every pipeline stage.
  • Written semantic rules define correctness for every later interpreter and compiler.
