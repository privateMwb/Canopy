Targeting an Existing Backend

You rarely need to write a back end from scratch: targeting an existing one like an LLVM-style IR or WebAssembly gets you optimization and many targets for the price of one translation.

§1Why reuse a back end

Everything in this stage, from selection to linking, is real work, repeated for each architecture. A shared back end gives you all of it. You lower your language to the backend's IR, and it does optimization, register allocation, and machine code generation for every target it supports.

Twig ─► Twig IR ─► translate ─► [LLVM-style IR] ─► many CPU targets
                               [WebAssembly]   ─► any runtime that supports it
                               [C source]      ─► any C compiler

The tradeoff is control. You inherit the backend's assumptions, such as its calling conventions, its memory model, and how it handles garbage collection, and fighting them is harder than adopting them.

§2What the translation looks like

LLVM-style IR is typed, in SSA form, and organized into basic blocks, so Twig's SSA IR from Stage 2.2 maps onto it closely.

; Twig:   fn add(a, b) { return a + b; }   (with int annotations)
define i64 @add(i64 %a, i64 %b) {
entry:
  %sum = add i64 %a, %b
  ret i64 %sum
}

Instruction for instruction it is close to what you already have: typed values, explicit blocks, phi nodes. Your job is to translate Twig's types and runtime operations: integers become i64, arrays become pointers plus lengths, and operations that can fail become explicit checks and branches to error handlers.

; array index with bounds check
%ok = icmp ult i64 %idx, %len
br i1 %ok, label %load, label %out_of_range

§3WebAssembly and other targets

WebAssembly is a compact, portable, stack-based instruction format designed to run safely in browsers and standalone runtimes. It is a good target when you want your language to run anywhere.

(func $add (param $a i64) (param $b i64) (result i64)
  local.get $a
  local.get $b
  i64.add)

It has structured control flow (blocks and loops, not arbitrary jumps), which constrains how you lower branch and jump. It also has no built-in garbage collector for the plain core language, so your runtime must manage the heap in linear memory unless you use newer GC-aware proposals.

Emitting C source is the simplest backend of all, and a surprisingly practical one. Every platform has a C compiler, and the output is readable, at the cost of less control over low-level details.

The key insight A backend is a big, reusable asset. Choose the one whose assumptions match your language's needs, since adapting your runtime to it is cheaper than adapting it to you.

§4Common Mistakes

MistakeWhat HappensFix
Ignoring how the backend handles garbage collectionRoots are missed, and live objects are freedUse the backend's stack-map or shadow-stack mechanism, or keep your own root stack
Translating each Twig operation without keeping type informationThe backend can't optimize, and bugs appear as invalid IRCarry types through lowering and run the backend's verifier
Expecting arbitrary jumps in WebAssemblyYour CFG can't be emitted directlyConvert to structured control flow, or use a relooper-style algorithm
Practice
  1. Translate the Twig function fn abs(x) { if (x < 0) { return -x; } return x; } into LLVM-style IR with explicit blocks and a phi or a return in each branch.
  2. List three things about Twig's runtime (strings, arrays, errors) that you'd have to implement as library functions if you targeted WebAssembly.
Key takeaways
  • Targeting an existing backend gives optimization and many targets for one translation.
  • SSA-based IR with explicit blocks maps closely onto LLVM-style IR.
  • WebAssembly and C are practical targets with different tradeoffs in control.
