Object Files, Linking & Loading

Compilers produce object files containing code, data, and symbols; the linker joins them, and the loader maps the result into memory to run.

§1Object files

A compiler rarely produces a finished program. It produces an object file for each source unit, containing machine code and data with some details left blank.

sections:
  .text     machine code
  .data     initialized global data
  .rodata   constants such as string literals
  .bss      zero-initialized data (just a size)
symbols:
  main      defined, in .text at offset 0
  print_int undefined — provided by another file or library
relocations:
  at .text+0x14: patch in the address of print_int

The compiler can't know final addresses, since they depend on what else is linked. So it leaves relocations: notes saying 'fill in the address of symbol X here.'

§2Linking

The linker combines object files into one executable.

1. Collects sections: all .text parts together, all .data together, and so on. 2. Resolves symbols: matches each undefined symbol to a definition in some file or library, or reports undefined reference. 3. Applies relocations: assigns final addresses and patches every placeholder.

def link(objects):
    layout = assign_addresses(merge_sections(objects))
    for obj in objects:
        for reloc in obj.relocations:
            target = symbol_table[reloc.symbol].final_address
            patch(obj.section(reloc.section), reloc.offset, target)

Static linking copies library code into the executable. Dynamic linking leaves some symbols for the loader to resolve at program start (or on first call), so many programs can share one copy of a library.

§3Loading

The loader (part of the operating system) prepares a program to run. It maps the executable's segments into a new address space, giving each the right permissions, then sets up the stack and jumps to the entry point.

segment    permissions   contents
text       r-x           code (readable, executable, not writable)
rodata     r--           constants
data/bss   rw-           mutable globals
stack      rw-           grows downward
heap       rw-           grows upward as needed

These permissions are a security feature: code can't be overwritten, and data can't be executed. Dynamic loading adds another step: the loader finds the needed shared libraries and fills in a table of function addresses that calls go through.

For Twig, the language runtime (garbage collector, print, array helpers) is a library the generated code links against. Your compiler emits calls to its functions, and the linker joins them.

The key insight Separate compilation is possible because object files carry 'blanks' (relocations) and names (symbols). Linking is simply filling in the blanks once every name has a definition.

§4Common Mistakes

MistakeWhat HappensFix
Forgetting to export a symbolOther files report undefined referencesMark functions and globals that need to be visible as external
Defining the same symbol in two object filesThe linker reports duplicate definitions, or silently picks oneKeep one definition per symbol, or use explicit weak symbols
Assuming addresses are fixed at compile timeCode breaks when loaded at a different address (position independence)Use relative addressing and relocations, and generate position-independent code when required
Practice
  1. List the sections, symbols, and relocations the compiler should emit for a Twig program that calls a runtime function rt_print.
  2. Explain what the linker does when two object files both define helper, and one defines it as weak.
Key takeaways
  • Object files hold sections, symbols, and relocations, with addresses left blank.
  • The linker merges sections, resolves symbols, and patches relocations.
  • The loader maps segments with the right permissions and starts the program.
