Writing & Defending a Design Document

A design document records a decision's problem, alternatives, and risks, so reviewers can disagree with specific parts instead of with the whole.

§1Why write it down

A design that lives only in someone's head can't be reviewed, only trusted. Writing it down forces you to find the gaps in your own thinking, and it lets others find the ones you missed, before the feature is built, when changing it is cheap.

A design document also outlives the discussion. Months later, when someone asks 'why does it work this way?', the document holds the reasons, and the rejected alternatives, so the same debate isn't repeated.

§2A structure that works

Good design documents for language and compiler changes share a shape.

Title and status           (draft / accepted / rejected / implemented)
1. Problem                 what's painful today, with a concrete example
2. Goals and non-goals     what this must do, and what it deliberately won't
3. Proposal                syntax, semantics, and edge cases, with examples
4. Implementation plan     changes to each stage, and a testing plan
5. Alternatives considered what else could solve it, and why not
6. Risks and open questions what could go wrong, and what you don't yet know
7. Compatibility           effect on existing programs and tools

The non-goals and alternatives sections do the most for review quality. A reader who knows what you ruled out, and why, argues with your reasoning instead of repeating options you already considered.

Example, proposed 'defer' statement for Twig:
  Problem:     cleanup code is far from the code that needs it, and missed on early return
  Non-goal:    full exception support
  Alternative: try/finally  (rejected: heavier syntax, needs exceptions first)
  Risk:        interacts with 'return' values and with loops that 'break'

§3Defending a design

Review is not an attack, but it will find weaknesses. Prepare for the questions reviewers always ask.

  • 'Why not just...?' Have the alternative and the reason ready.
  • 'What about this edge case?' Keep a list of edge cases and their answers in the document.
  • 'How will you test it?' Say which tests, which fuzz generators, and which existing programs.
  • 'What does this cost?' Give numbers where possible: code size, compile-time, performance.
  • 'What if we're wrong?' Describe how you'd back it out, or limit the damage.

When a reviewer finds a real flaw, change the document, and record the change and the reason. A design that survives honest challenge is stronger, and one that was never challenged is only untested. Explaining tradeoffs plainly, including what's uncertain, builds more trust than claiming everything is settled.

The key insight A design document is a tool for being wrong cheaply. It moves disagreement from after the code is written to before, and gives it something precise to point at.

§4Common Mistakes

MistakeWhat HappensFix
Writing only the proposalReviewers re-propose the alternatives you already rejectedInclude goals, non-goals, and alternatives with reasons
Hiding open questionsReviewers find them and trust the rest lessList what you don't know yet, with a plan for each
Treating review feedback as oppositionReal flaws get defended instead of fixedTreat each objection as a test of the design and update the document
Practice
  1. Write the one-page design document for adding defer or pattern matching to Twig, using the seven-part structure.
  2. Pair up, or imagine a skeptical reviewer, and list the five hardest questions about your document, then answer each in writing.
Key takeaways
  • A design document states the problem, goals, proposal, plan, alternatives, and risks.
  • Non-goals and rejected alternatives improve review more than anything else.
  • Defend a design with prepared answers, and change the document when a flaw is real.
