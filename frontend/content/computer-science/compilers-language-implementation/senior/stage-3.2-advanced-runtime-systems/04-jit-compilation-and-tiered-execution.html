JIT Compilation & Tiered Execution

A JIT compiler watches a program run, compiles the code that matters while it's running, and falls back to the interpreter when its assumptions turn out to be wrong.

§1Why compile at run time

An interpreter starts instantly but runs slowly. An ahead-of-time compiler runs fast but knows nothing about how the program will actually behave. A JIT (just-in-time) compiler gets some of both: it begins by interpreting, and compiles code to machine instructions while the program runs.

It has one big advantage: it can observe. It knows which functions are hot, which types actually flow through them, and which branches are taken. An AOT compiler can only guess.

§2Tiered execution

JITs usually use tiers: cheap execution first, expensive compilation only where it pays.

tier 0: interpreter           starts immediately; collects profile data
tier 1: quick compiler        compiles functions called often; little optimization
tier 2: optimizing compiler   compiles the hottest code with heavy optimization

Counters trigger promotion between tiers.

def call(func):
    func.call_count += 1
    if func.tier == 0 and func.call_count > HOT_THRESHOLD:
        func.code = quick_compile(func); func.tier = 1
    if func.tier == 1 and func.call_count > VERY_HOT and func.profile_stable:
        func.code = optimizing_compile(func); func.tier = 2
    return execute(func.code)

Loops are counted too, using back-edge counters, so a long-running loop in a function called once still gets compiled (this is called on-stack replacement: switching from interpreted to compiled code in the middle of a running function).

§3Speculation and deoptimization

The optimizing tier uses profile data to speculate. If add(a, b) has always seen integers, the compiled code assumes it will, and skips the type checks, with a cheap guard to confirm the assumption.

compiled add, speculating on ints:
    guard a is int   ── fail ─► deoptimize
    guard b is int   ── fail ─► deoptimize
    result = a + b                  # no tag checks, no dispatch

When a guard fails, the JIT must deoptimize: reconstruct the interpreter's state (locals, stack, instruction pointer) from the machine state, and continue in the interpreter as if the optimized code had never run. Doing this correctly in every possible guard location is the hardest part of building a JIT.

on guard failure:
    state = rebuild_interpreter_frame(machine_registers, deopt_map[guard_id])
    func.profile.record(unexpected_type)       # remember, so we don't speculate again
    resume_in_interpreter(state)

JITs also pay costs: compile time is spent during execution, memory holds generated code, and bugs in the JIT cause strange miscompilations. This is why correctness testing (Stage 3.4) matters more here than anywhere.

The key insight A JIT's power is that it can bet on what it has seen, and its safety is that every bet comes with an escape hatch. Deoptimization is what makes aggressive speculation affordable.

§4Common Mistakes

MistakeWhat HappensFix
Compiling every function immediatelyStartup is slow, and memory fills with code that never runs hotInterpret first and compile only past a threshold
Speculating without a guardA wrong assumption silently corrupts resultsInsert a guard for every assumption and deoptimize on failure
Keeping speculating after a guard keeps failingThe program bounces endlessly between compiled and interpreted codeRecord the failure and recompile without that assumption
Practice
  1. Design the tier counters for Twig: what thresholds would you start with, and what would you measure to tune them?
  2. For a compiled a[i] + b[i] speculating on arrays of integers, list every guard you need and what state deoptimization has to rebuild.
Key takeaways
  • A JIT can profile real behaviour and compile only what matters.
  • Tiered execution balances start-up speed against peak speed using counters.
  • Speculation uses guards, and deoptimization restores interpreter state when they fail.
