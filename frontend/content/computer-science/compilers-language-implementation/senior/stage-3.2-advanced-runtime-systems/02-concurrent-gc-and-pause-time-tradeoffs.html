Concurrent GC & Pause-Time Tradeoffs

Concurrent and incremental collectors trade total throughput for shorter pauses, using tri-color marking and barriers to let the program keep running during collection.

§1Pauses matter

A stop-the-world collector halts the program while it collects. For a batch job that's fine. For an interactive app or a server with latency targets, a 200 ms pause is a visible failure.

throughput:  how much work gets done per second
latency:     how long the program is paused at once

stop-the-world:   high throughput, long pauses
incremental:      slice the work into small steps between program steps
concurrent:       collector threads run alongside the program

You can't improve both for free: doing collection work while the program runs needs extra coordination, and that costs total throughput.

§2Tri-color marking

Concurrent marking is tricky because the program changes the object graph while the collector is traversing it. Tri-color marking gives a precise way to reason about it.

  • White: not yet reached. If it stays white at the end, it is garbage.
  • Grey: reached, but its references haven't all been scanned yet.
  • Black: reached and fully scanned.
roots → grey.  Repeat: take a grey object, mark its white children grey, make it black.
When no grey remain: everything white is garbage.

The tri-color invariant says that a black object never points to a white one. If it did, the collector would never scan that white object, because it has already finished with the black one, and live data would be freed.

collector:  A is black (scanned), B is white.
program:    A.field = B ; remove the other reference to B
result:     B is reachable only through A, but A won't be scanned again → B freed. Bug!

§3Barriers keep the invariant

To preserve the invariant while the program runs, the program executes a write barrier on pointer stores during marking. There are two common designs.

# incremental-update barrier: when storing white B into black A, make A grey again
def barrier(A, B):
    if A.color == BLACK and B.color == WHITE: A.color = GREY; grey_set.add(A)

# snapshot-at-the-beginning barrier: before overwriting a reference, grey the old target
def barrier(A, field, new):
    old = A.fields[field]
    if marking and old.color == WHITE: old.color = GREY; grey_set.add(old)
    A.fields[field] = new

Both keep the collector correct while the program mutates the graph. The first rescans what the program touches; the second preserves a snapshot of the graph as it was when marking began.

Real concurrent collectors also handle moving objects while the program runs, using read barriers or forwarding pointers. They achieve pauses of a millisecond or less on huge heaps, at a throughput cost, which is why collectors come in flavours: throughput-oriented batch collectors versus low-latency ones.

The key insight Concurrent collection is mostly about one invariant: a fully scanned object must never point at an unscanned one. Everything else, barriers included, is bookkeeping to maintain it.

§4Common Mistakes

MistakeWhat HappensFix
Letting the program write pointers without a barrier during markingA live object stays white and is freedRun the barrier on every pointer store while a collection is in progress
Choosing a low-latency collector for a batch jobYou lose throughput and gain nothingMatch the collector to the latency and throughput goals
Forgetting to rescan roots at the end of concurrent markingReferences created during marking are missedFinish with a short stop-the-world step that re-scans roots and grey objects
Practice
  1. Construct a scenario with two objects and a mutation during marking where, without a barrier, a live object is freed. Then show how each barrier prevents it.
  2. Compare which kinds of program would prefer a stop-the-world collector, an incremental one, and a concurrent one, and justify each.
Key takeaways
  • Stop-the-world pauses hurt latency, and shorter pauses cost throughput.
  • Tri-color marking reasons about collection with white, grey, and black objects and one invariant.
  • Write barriers during marking keep a scanned object from hiding an unscanned one.
