Exceptions & Non-Local Control Flow

Exceptions let an error jump out of many nested calls to a handler, and the compiler has to decide how to make that jump correct, with the happy path as cheap as possible.

§1Non-local control flow

A normal return goes back one frame. An exception can leave several frames at once, and run cleanup code (like closing a file) on the way.

// hypothetical Twig extension
fn read_config(path) {
  let f = open(path);
  try {
    return parse(f);          // may throw
  } finally {
    close(f);                  // must run on every exit path
  }
}

Each frame between the throw and the matching catch must be unwound: its locals discarded, its cleanup actions run, then control moves one frame up, until a handler is found.

§2Two implementation strategies

Setjmp-style (table of handlers at run time): entering a try pushes a handler record onto a handler stack; leaving it pops. A throw looks at the top handler and jumps there.

try_begin:   push Handler(catch_label, saved_stack_depth, saved_frame)
body...
try_end:     pop Handler
throw e:     h = handlers.top(); restore(h.frame, h.stack_depth); push(e); jump h.catch_label

This is simple and fast to throw, but every try costs a push and pop even if nothing is ever thrown.

Table-driven ("zero-cost"): the compiler emits no code on entry to a try. Instead it generates tables, keyed by instruction address, that say which handler covers each range of code and what cleanup each frame owns. A throw consults the tables, walks the stack frame by frame, and runs cleanups.

exception table for read_config:
  range [0x40, 0x68)  handler 0x80   cleanup: close(f)

The happy path pays nothing. Throwing is expensive, since it needs table lookups and a stack walk, so this design suits languages where exceptions are for exceptional cases.

§3Interaction with other features

Exceptions touch everything else in the implementation.

  • Optimizations: any call can now exit early by exception, so moving code across a call needs care. The IR needs exceptional edges from calls to handlers, so the CFG (Stage 2.2) stays accurate.
  • Cleanup: finally code has to be duplicated or entered from multiple paths: normal exit, return, break, and throw.
  • Garbage collection: unwinding must keep roots correct, so frames being discarded aren't scanned as live.
  • Resource safety: cleanup that itself throws needs a defined rule.
# IR with exceptional edges
 t = call f(x)  normal → B2   unwind → H1

Many languages that skip exceptions use explicit result values (a value that is either a success or an error) to get the same expressiveness with ordinary control flow, trading convenience for visible, optimizable paths.

The key insight Exceptions are control flow the call graph doesn't show. Whatever strategy you pick, every stage from the optimizer to the garbage collector has to know that any call might not return normally.

§4Common Mistakes

MistakeWhat HappensFix
Forgetting exceptional edges in the CFGOptimizations move code past a call that might throw, changing behaviourModel each call as having an unwind edge to the handler
Running finally only on normal exitResources leak on return, break, or throwRoute every exit path through the cleanup code
Using exceptions for ordinary control flowThrowing is slow in table-driven implementationsReserve exceptions for rare errors, and use results for expected ones
Practice
  1. Write the handler-stack bytecode for a try/catch that wraps a call, showing what is pushed on entry, popped on exit, and restored on throw.
  2. List what the optimizer must know about a call that can throw before it may reorder a store past that call.
Key takeaways
  • Exceptions unwind several frames, running cleanup on each.
  • Runtime handler stacks are simple; table-driven designs make the happy path free but throwing costly.
  • Every stage of the compiler must treat a call as possibly exiting early.
