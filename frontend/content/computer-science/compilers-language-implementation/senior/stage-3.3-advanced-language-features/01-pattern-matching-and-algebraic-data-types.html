Pattern Matching & Algebraic Data Types

Pattern matching lets a program take data apart and choose a branch in one step, and the compiler's job is to turn many patterns into few efficient tests.

§1Algebraic data types and match

An algebraic data type is a value that is exactly one of several named variants, each carrying its own fields. match inspects which variant it is and extracts the fields.

// hypothetical Twig extension
type Shape = Circle(r) | Rect(w, h) | Point

fn area(s) {
  return match s {
    Circle(r)  => 3 * r * r,
    Rect(w, h) => w * h,
    Point      => 0,
  };
}

Compared to a chain of ifs checking a tag field, match states intent directly: each arm names the variant and binds its fields in one place.

§2Compiling to decision trees

A naive compiler tests each arm in order, repeating work. With nested patterns that gets wasteful.

match pair {
  (Circle(r), Circle(s)) => ...
  (Circle(r), _)         => ...
  (_, Circle(s))         => ...
  (_, _)                 => ...
}

A decision tree compiles the match into a tree of tests in which each value is inspected at most once.

test pair.0 tag
├─ Circle: test pair.1 tag
│          ├─ Circle: arm 1 (r = pair.0.r, s = pair.1.r)
│          └─ else:   arm 2
└─ else:   test pair.1 tag
           ├─ Circle: arm 3
           └─ else:   arm 4

The standard algorithm works on a pattern matrix: pick a column to test, split the rows by the constructor found there, and recurse on each group with the rest of the matrix. The choice of column affects tree size, and a poor choice can duplicate code. The alternative, backtracking automata, shares code but may test a value more than once.

§3Exhaustiveness and redundancy

A big advantage of compiling patterns is that the compiler can check them.

  • Exhaustiveness: does every possible value match some arm? If not, the program can fail at run time with no matching case.
  • Redundancy: is any arm unreachable because earlier arms already cover it?
match s {
  Circle(r) => 1,
  Rect(w, h) => 2,
}                       // warning: non-exhaustive, missing Point

match n {
  _ => 1,
  0 => 2,               // warning: unreachable arm
}

The check uses the same pattern matrix: if the algorithm reaches an empty matrix with values still to cover, those values are missing, and the compiler can report an example of an unmatched value. That error message is one of the most useful things a type system gives programmers, because adding a variant later points at every match that needs updating.

The key insight Pattern matching is a declaration of intent that the compiler can both optimize and verify. The same matrix algorithm gives you efficient code and the exhaustiveness check.

§4Common Mistakes

MistakeWhat HappensFix
Testing arms top to bottom with no sharingThe same field is tested over and over, so nested matches get slowCompile to a decision tree or a matching automaton
Skipping the exhaustiveness checkA missing variant crashes at run timeReport non-exhaustive matches, with an example of a missing case
Choosing columns left to right alwaysTrees can grow exponentially for some pattern setsUse a heuristic (such as testing the column with the most distinct constructors) and measure
Practice
  1. Write the decision tree for matching on a pair of booleans with four patterns, including (true, _) and (_, true).
  2. Describe how the compiler detects that match s { Circle(_) => 1, _ => 2, Point => 3 } has a redundant arm.
Key takeaways
  • Algebraic data types and match combine inspecting a variant with extracting its fields.
  • Decision trees compile many patterns into tests that look at each value once.
  • The same pattern matrix drives exhaustiveness and redundancy checks.
