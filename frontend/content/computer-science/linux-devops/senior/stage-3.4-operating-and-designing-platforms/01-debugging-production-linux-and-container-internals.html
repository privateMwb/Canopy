Debugging Production: Linux & Container Internals

When a container misbehaves, the fastest way to find out why is to look from the host with ordinary Linux tools, since a container is just a process with namespaces and cgroups.

§1Get Inside Without Changing It

Minimal images often have no shell and no tools. You can still inspect them. kubectl debug attaches a temporary ephemeral container with tools to a running pod, sharing its namespaces. On the host, nsenter joins a container's namespaces using its PID, so your host tools run in its network or mount view.

# Kubernetes: add a debug container beside the app (shares the process namespace)
kubectl debug -it pod/shop-7d9f-abcde --image=busybox:1.36 --target=shop

# Host: find the PID, then enter its network namespace with host tools
PID=$(docker inspect -f '{{.State.Pid}}' shop)
sudo nsenter -t "$PID" -n ss -tlnp          # listening sockets as the container sees them
sudo nsenter -t "$PID" -n ip addr

§2Read the Process Like Any Other

Everything from the OS track applies. /proc/<pid> shows open files, memory maps, environment, and limits. strace shows system calls and which one is slow or failing. lsof and ss show files and connections.

sudo ls -l /proc/$PID/fd | head            # open files and sockets
sudo cat /proc/$PID/limits                 # max open files, etc.
sudo strace -f -tt -T -p "$PID" -e trace=network,file 2>&1 | head -40
sudo lsof -p "$PID" | grep -c ESTABLISHED
sudo tcpdump -i any -nn port 5432 -c 20    # is the database even answering?

Attaching strace slows the target, so use it briefly and with filters on a busy production process.

§3Check the Limits: cgroup Files

Many "mysterious" container failures are limits. The cgroup files record exactly what happened: how many times memory was exhausted, and how much CPU time was throttled.

CG=/sys/fs/cgroup/$(cut -d: -f3 /proc/$PID/cgroup)
cat $CG/memory.current $CG/memory.max      # use vs. ceiling
cat $CG/memory.events                      # includes oom_kill count
cat $CG/cpu.stat                           # nr_throttled, throttled_usec
dmesg -T | grep -i "killed process"        # kernel OOM kill messages
A method, not a bag of tools Form a hypothesis from the symptom, pick the cheapest observation that would prove or disprove it, and change one thing at a time. "Is it the app, the network, or the limits?" narrows quickly when you check each layer in turn.

§4Common Mistakes

MistakeWhat HappensFix
Restarting first and investigating neverEvidence is destroyed, and the problem returnsCapture state (logs, /proc, cgroup stats) before restarting
Running heavy tools on a hot production processThe diagnosis worsens the incidentUse filtered, short-lived probes and read-only checks first
Guessing instead of checking limitsThrottling and OOM kills are blamed on the appRead memory.events and cpu.stat directly
Practice
  1. Start a container that gets OOM-killed, then prove it from memory.events and dmesg.
  2. Use nsenter to list the listening sockets of a distroless container that has no shell.
Key takeaways
  • A container is a process, so host tools like strace, ss, and /proc work on it.
  • kubectl debug and nsenter let you inspect minimal images without rebuilding them.
  • cgroup files show OOM kills and CPU throttling as hard evidence.
