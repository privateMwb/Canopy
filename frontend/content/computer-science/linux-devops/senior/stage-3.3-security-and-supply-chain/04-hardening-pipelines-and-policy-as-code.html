Hardening Pipelines & Policy as Code

A CI/CD system holds your code, your secrets, and your deploy rights, so it needs the same hardening as production, and rules enforced by machines, not memory.

§1CI Is an Attack Surface

Attackers target pipelines because one foothold yields credentials and a path into production. Common routes are untrusted pull requests, compromised third-party actions or dependencies, over-permissive tokens, and leaked secrets in logs. Harden each: least-privilege tokens, pinned actions, protected branches, required reviews, and isolation for untrusted code.

permissions:
  contents: read                 # default everything to read-only
jobs:
  build:
    steps:
      - uses: actions/checkout@v4   # pin to a full commit SHA for sensitive workflows
      # an untrusted PR title in a shell command is an injection risk:
      # BAD:  run: echo "${{ github.event.pull_request.title }}"
      - run: echo "$TITLE"
        env:
          TITLE: ${{ github.event.pull_request.title }}

§2Branch Protection and Ownership

Require pull requests, approvals, and passing checks on protected branches. Use CODEOWNERS so changes to sensitive paths, such as the pipeline definitions, infrastructure code, and security settings, require review from the right team.

# CODEOWNERS
/.github/workflows/   @acme/platform-team
/infra/               @acme/platform-team @acme/security
/deploy/              @acme/platform-team
# branch protection on main: required reviews, required checks,
#   no force pushes, signed commits (optional), admins included

§3Policy as Code

Rules written in a document are forgotten. Rules written as policy code run automatically on every change, in CI and at the cluster's front door. Tools like Open Policy Agent (OPA) with Conftest, or Kyverno in Kubernetes, check configuration against your standards and reject violations.

# a Rego policy checked in CI with Conftest
package main
deny[msg] {
  input.kind == "Deployment"
  c := input.spec.template.spec.containers[_]
  not c.securityContext.runAsNonRoot
  msg := sprintf("container %s must set runAsNonRoot", [c.name])
}
# conftest test deployment.yaml
# the same rule, enforced again by the cluster's admission controller
Make the secure path the easy path People bypass friction. If the paved road, with a standard pipeline, hardened base images, and pre-approved templates, is also the fastest way to ship, most teams will take it, and policy only has to catch the exceptions.

§4Common Mistakes

MistakeWhat HappensFix
Interpolating untrusted input into shell commandsScript injection can run attacker code with your secretsPass values through environment variables, not inline expressions
Letting anyone change workflow filesAn attacker or mistake can add a step that exfiltrates secretsProtect .github/workflows with CODEOWNERS and review
Relying on a wiki page of rulesNobody checks them, and violations slip throughEncode rules as policy and enforce them in CI and admission
Practice
  1. Audit one workflow for broad token permissions, unpinned actions, and untrusted input in shell commands, and fix each.
  2. Write a policy that rejects any Deployment without resource limits, and run it against a sample manifest.
Key takeaways
  • Treat CI/CD as a high-value attack surface: least-privilege tokens, pinned actions, protected branches.
  • CODEOWNERS and required reviews guard the pipeline definitions and infrastructure code.
  • Policy as code enforces standards automatically, both in CI and at cluster admission.
