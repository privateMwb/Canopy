Least Privilege for Hosts & Containers

Least privilege means every process, container, and credential gets only the access its job needs, so a single compromise stays small.

§1Hardening a Container

By default a container often runs as root with more capabilities than it needs. Tighten it: run as a non-root user, make the filesystem read-only, drop all Linux capabilities and add back only what is required, and block privilege escalation. These map onto the kernel features covered in the OS track.

docker run -d --name shop \
  --user 10001:10001 \
  --read-only --tmpfs /tmp \
  --cap-drop=ALL \
  --security-opt no-new-privileges:true \
  --pids-limit=200 --memory=512m \
  ghcr.io/acme/shop:1.4.2

Never use --privileged or mount the Docker socket (/var/run/docker.sock) into a container. Either one effectively hands over the host.

§2The Same Ideas in Kubernetes

A securityContext expresses the same rules, and Pod Security Standards can enforce them for a whole namespace. Also restrict what the pod's own service account may do through RBAC, since a compromised pod inherits that identity.

securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities: { drop: ["ALL"] }
  seccompProfile: { type: RuntimeDefault }
automountServiceAccountToken: false     # unless the app calls the API
kubectl label ns prod pod-security.kubernetes.io/enforce=restricted
kubectl auth can-i --list --as=system:serviceaccount:prod:shop

§3Hosts and IAM

Apply the same principle one level out. On hosts, use unprivileged service users, minimal packages, key-only SSH, and no shared accounts. In the cloud, write IAM policies naming exact actions and resources instead of wildcards, and review who and what holds broad roles.

# policy review questions
#   Does this role need "*" on actions or resources?
#   Is it assumed by one workload, or shared by many?
#   When was it last used? (unused permissions should be removed)
#   What is the worst an attacker can do with this identity?
Assume breach Do not design for "nothing will ever be compromised". Design so that when one component is, the attacker is stuck in a read-only, non-root, network-restricted box with a narrow identity.

§4Common Mistakes

MistakeWhat HappensFix
Running containers as rootA container escape lands as root on the hostUse a non-root user and drop capabilities
Mounting the Docker socket or using --privilegedEquivalent to root on the hostAvoid them; use purpose-built tooling
Wildcard IAM policies like Action: *One stolen credential controls everythingGrant specific actions on specific resources
Practice
  1. Harden a container until it still works with --read-only, --cap-drop=ALL, and a non-root user, noting what you had to allow back.
  2. Use kubectl auth can-i --list to see what a pod's service account can do, and remove what it does not need.
Key takeaways
  • Least privilege limits the damage of any single compromise.
  • Non-root, read-only, no extra capabilities, and no privilege escalation are the container baseline.
  • Apply the same minimalism to host accounts, Kubernetes RBAC, and cloud IAM.
