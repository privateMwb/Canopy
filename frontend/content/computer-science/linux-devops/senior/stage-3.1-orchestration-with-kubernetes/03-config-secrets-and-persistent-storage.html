Config, Secrets & Persistent Storage

Applications need configuration, credentials, and sometimes durable storage, and Kubernetes separates each from the container image.

§1ConfigMaps and Secrets

A ConfigMap holds non-sensitive settings and a Secret holds sensitive ones. Both can be injected as environment variables or mounted as files. Secrets are only base64-encoded by default, not encrypted, so restrict access with RBAC, enable encryption at rest, or sync them from an external secrets manager.

apiVersion: v1
kind: ConfigMap
metadata:
  name: shop-config
data:
  LOG_LEVEL: info
---
apiVersion: v1
kind: Secret
metadata:
  name: shop-db
type: Opaque
stringData:
  DATABASE_URL: postgres://app:CHANGEME@db:5432/app
# in the container spec
envFrom:
  - configMapRef: { name: shop-config }
env:
  - name: DATABASE_URL
    valueFrom:
      secretKeyRef: { name: shop-db, key: DATABASE_URL }

Environment variables are read at container start, so changing a ConfigMap does not update a running pod. Mounted files do update eventually, and a rollout restart picks up either.

§2Persistent Storage

Container filesystems are disposable. For durable data, a pod claims storage with a PersistentVolumeClaim (PVC), and the cluster provisions a volume through a StorageClass. The volume outlives any one pod.

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: shop-uploads
spec:
  accessModes: ["ReadWriteOnce"]     # mountable read-write by one node
  resources:
    requests:
      storage: 10Gi
# in the pod spec
volumes:
  - name: uploads
    persistentVolumeClaim: { claimName: shop-uploads }
# and in the container
volumeMounts:
  - name: uploads
    mountPath: /var/uploads

§3Stateful Workloads

Databases and other stateful systems need stable identity and their own storage per replica. A StatefulSet gives each pod a fixed name (db-0, db-1) and its own PVC that follows it across restarts. Running a database well on Kubernetes also needs backups and careful operations, so many teams use a managed database instead.

kubectl get pvc,pv
kubectl get statefulset
kubectl rollout restart deploy/shop       # restart pods so they re-read config
Config out of the image, state out of the pod The image stays identical across environments, and the cluster injects settings and storage at run time. It is the twelve-factor principle again, now enforced by the platform.

§4Common Mistakes

MistakeWhat HappensFix
Treating Secrets as encryptedAnyone who can read the Secret can decode itRestrict RBAC, encrypt at rest, or use an external secrets manager
Editing a ConfigMap and expecting env vars to changeRunning pods keep the old valuesRestart the Deployment to pick up changes
Storing data in the container filesystemData is lost when the pod is replacedUse a PVC, or an external managed database
Practice
  1. Inject one setting from a ConfigMap and one credential from a Secret, then verify both inside the pod with kubectl exec.
  2. Create a PVC, write a file into it from a pod, delete the pod, and confirm the file persists.
Key takeaways
  • ConfigMaps and Secrets keep configuration out of images, but Secrets need real protection.
  • A PVC gives pods durable storage that outlives the pod.
  • StatefulSets give stable identity and per-replica storage, and stateful systems need careful operation.
