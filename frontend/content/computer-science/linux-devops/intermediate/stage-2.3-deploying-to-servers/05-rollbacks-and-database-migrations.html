Rollbacks & Database Migrations

Code rolls back easily because you can redeploy the old version, but data does not, so schema changes need a safer pattern.

§1Rolling Back Code

A rollback should be a routine, practiced operation: redeploy the previous known-good image tag or digest. This works only if you kept the old artifact and deployments are scripted. Decide the rollback trigger in advance, such as "error rate above 2 percent for 5 minutes", instead of debating it during an incident.

./deploy.sh 1.4.1                         # roll back = deploy the previous tag
docker compose ps                         # confirm which version is running
git revert a1b2c3d && git push            # or revert the change and let CI ship it

§2Why Databases Are Different

A migration that drops a column or rewrites a table cannot be undone by redeploying old code. During a rolling or canary release, old and new code also run against the same database at once. So every migration must work with both the version before it and the version after it.

-- risky: breaks the old code the moment it runs
ALTER TABLE users DROP COLUMN fullname;

-- safe order: new code stops using the column FIRST,
-- a later release then removes it

§3Expand and Contract

The safe pattern splits a breaking change into compatible steps. Expand: add the new structure without removing the old. Migrate: write to both and backfill existing data. Contract: after all code uses the new structure, remove the old one in a later release.

-- Release 1 (expand): add the new column, nullable
ALTER TABLE users ADD COLUMN display_name text;

-- Release 2: code writes both columns; backfill old rows
UPDATE users SET display_name = fullname WHERE display_name IS NULL;

-- Release 3: code reads only display_name
-- Release 4 (contract): drop the old column
ALTER TABLE users DROP COLUMN fullname;
Make every migration reversible in practice Before running a migration, ask "if the new code has to roll back, will the old code still work against this schema?" If not, split the change until the answer is yes. Take a backup first for anything destructive.

§4Common Mistakes

MistakeWhat HappensFix
Dropping or renaming columns in one releaseRollback and mixed-version periods breakUse expand and contract across several releases
Running a long, locking migration at peak trafficThe table is locked and requests time outUse online techniques, batches, and off-peak windows
Never practicing rollbackThe first attempt happens during an outageRehearse rollbacks in staging regularly
Practice
  1. Plan a column rename as an expand-and-contract sequence across four releases.
  2. Write down the rollback trigger and the exact rollback commands for a service you run.
Key takeaways
  • Rolling back code means redeploying a known-good artifact, so keep old versions available.
  • Schema changes must be compatible with both the old and new code versions.
  • Use expand and contract so each release can be rolled back safely.
