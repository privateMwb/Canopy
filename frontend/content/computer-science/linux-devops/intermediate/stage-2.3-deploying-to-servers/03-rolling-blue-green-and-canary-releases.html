Rolling, Blue-Green & Canary Releases

There are three standard ways to replace a running version, and each trades risk against cost differently.

§1Rolling Deployments

A rolling release replaces instances a few at a time. Capacity stays up and extra infrastructure cost is minimal. The catch is that old and new versions run side by side for a while, so they must be compatible with each other and with the database.

# conceptual: 4 instances, replace 1 at a time
v1 v1 v1 v1
v2 v1 v1 v1      # take one out of the proxy, update, health check, add back
v2 v2 v1 v1
v2 v2 v2 v1
v2 v2 v2 v2

§2Blue-Green Deployments

Blue-green runs two full environments. Blue serves traffic while you deploy to green and test it. Then you switch the router, and rollback is a switch back. It is clean and fast but needs double capacity for a while.

upstream app { server 127.0.0.1:8001; }   # blue is live on 8001
# deploy v2 to 8002 and verify it, then change the line to 8002 and reload:
#   upstream app { server 127.0.0.1:8002; }
sudo nginx -t && sudo systemctl reload nginx
# rollback: change back to 8001 and reload

§3Canary Releases

A canary sends a small share of real traffic, such as 1 to 5 percent, to the new version first. You watch errors and latency, and widen the rollout only if it looks healthy. It limits the blast radius of a bad release but needs good monitoring and traffic-splitting support.

upstream app {
    server 10.0.1.11:8000 weight=19;   # v1
    server 10.0.1.20:8000 weight=1;    # v2 canary: about 5% of requests
}
# watch error rate and p99 latency; if healthy, shift weights step by step
Compatibility is the real work Every strategy runs two versions at once, even if only briefly. Code and schema changes must be backward compatible across that window, or the strategy cannot save you.

§4Common Mistakes

MistakeWhat HappensFix
Rolling out without health checksA broken instance receives traffic and fails usersGate each step on a passing health check
Assuming blue-green is freeYou pay for double capacity and still must manage shared dataPlan the capacity and keep the database compatible
Running a canary with no monitoringYou cannot tell whether the canary is healthyDefine the metrics and thresholds before the release
Practice
  1. Implement a blue-green switch with two local containers and an nginx upstream, and perform a rollback.
  2. For a service you know, choose rolling, blue-green, or canary, and justify the choice in three sentences.
Key takeaways
  • Rolling updates instances gradually, blue-green swaps whole environments, and canary exposes a small slice first.
  • Each approach trades infrastructure cost against risk and rollback speed.
  • Old and new versions overlap, so changes must be backward compatible.
