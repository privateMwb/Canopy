Terraform Basics: Providers, Resources & Variables

Terraform lets you declare the infrastructure you want in text files, then works out and applies the changes to get there.

§1Declarative Configuration

You describe the desired end state, not the steps. Terraform compares it to reality and computes the difference. Providers are plugins that talk to a platform's API, and resources are the things you create.

# main.tf
terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region = var.region
}

variable "region" {
  type    = string
  default = "eu-west-1"
}

resource "aws_s3_bucket" "backups" {
  bucket = "acme-backups-${var.env}"
  tags   = { env = var.env }
}

§2The Core Workflow

Four commands cover daily use. init downloads providers, plan previews changes, apply makes them, and destroy removes everything. Always read the plan before applying it.

terraform init
terraform fmt -recursive             # standard formatting
terraform validate                   # catch syntax and type errors
terraform plan -var env=staging -out=tfplan
terraform apply tfplan               # apply exactly what you reviewed
terraform destroy -var env=staging

§3Variables, Outputs, and References

Values flow between resources through references, such as aws_instance.web.id, and Terraform builds a dependency graph from them. Outputs expose results, and variables make a configuration reusable.

resource "aws_security_group" "web" {
  name   = "web"
  vpc_id = aws_vpc.main.id            # reference creates a dependency
  ingress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

output "web_sg_id" {
  value = aws_security_group.web.id
}
Code review for infrastructure Because infrastructure is now text, you get everything software already has: version control, pull requests, review, history, and rollback. A plan posted in the pull request shows reviewers exactly what will change.

§4Common Mistakes

MistakeWhat HappensFix
Applying without reading the planA change can destroy and recreate a databaseReview the plan, and look carefully for destroy and replace
Hard-coding values in resourcesThe config cannot be reused across environmentsUse variables and per-environment values
Mixing console clicks with TerraformThe real world drifts from the codeMake all changes through the code
Practice
  1. Write a configuration for one storage bucket, then plan, apply, and destroy it.
  2. Change a tag, run plan, and explain why Terraform shows an in-place update rather than a replacement.
Key takeaways
  • Terraform is declarative: you describe the end state, and it computes the changes.
  • The workflow is init, plan, apply, with the plan always reviewed.
  • References build the dependency graph, and variables make configurations reusable.
