Secrets & Credentials in Pipelines

Pipelines need credentials to push images and deploy, and every secret you give a pipeline is a secret an attacker can try to steal from it.

§1Storing and Using Secrets

CI systems store encrypted secrets that are masked in logs and exposed only to jobs that reference them. Reference a secret through an environment variable instead of pasting it into a command.

- name: Deploy
  run: ./deploy.sh
  env:
    DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}   # available to this step only
# never:  run: curl -H "Authorization: $TOKEN" ...  with the value inline

Masking only hides exact matches. A secret that is transformed (base64-encoded, split, echoed with set -x on) can still leak into logs, so avoid printing anything derived from one.

§2Scope: Who Can See What

Secrets should be as narrow as possible: per environment (staging vs. production) rather than global, with protection rules such as required reviewers on production. Workflows triggered by pull requests from forks do not receive secrets, which is intentional, since the PR author controls the code that would run.

jobs:
  deploy-prod:
    runs-on: ubuntu-latest
    environment: production        # secrets and approval rules scoped here
    steps:
      - run: ./deploy.sh
        env:
          TOKEN: ${{ secrets.PROD_TOKEN }}

Be very careful with triggers that run untrusted code with secrets, such as pull_request_target. Never check out and execute a fork's code in that context.

§3Limiting the Damage

Assume a secret will eventually leak and plan for it. Use credentials with the smallest possible permissions, rotate them on a schedule and after any suspicion, and prefer short-lived credentials issued per run. The Senior track covers OIDC, which removes stored cloud keys entirely.

# a deploy token should be able to do one thing:
#   push to ONE registry repository, not manage the whole account
# rotate:  create new -> update the secret -> delete old
git log -p | grep -i "AKIA"            # hunt for accidentally committed keys
Treat the pipeline as production A CI system can read your code, your secrets, and often deploy to production, which makes it one of the most valuable targets you own. Review workflow changes as carefully as application code.

§4Common Mistakes

MistakeWhat HappensFix
Committing secrets to the repoThey stay in Git history even after deletionRotate immediately and use secret scanning
One shared production token for everythingA single leak compromises every systemScope tokens per environment and per purpose
Running fork PR code with secretsAn attacker's code can read and send them outNever expose secrets to untrusted code
Practice
  1. Move a hard-coded token out of a workflow into an environment-scoped secret.
  2. List every secret your pipeline uses, what it can do, and how you would rotate it.
Key takeaways
  • Pass secrets as environment variables from the secret store, and never inline or print them.
  • Scope secrets per environment and require approval for production.
  • Prefer narrow, short-lived, rotatable credentials, and never run untrusted code with secrets.
