Tests, Caching & Artifacts in CI

Caches make pipelines fast, artifacts carry results between jobs, and tests are only valuable if the pipeline trusts and reports them.

§1Caching Dependencies

Downloading dependencies on every run wastes minutes. A cache stores them under a key, usually derived from the lockfile hash, so it refreshes exactly when dependencies change.

- uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    key: pip-${{ runner.os }}-${{ hashFiles('requirements.txt') }}
    restore-keys: |
      pip-${{ runner.os }}-
- run: pip install -r requirements.txt

A cache is an optimization, never a dependency. The pipeline must still pass on a cold cache, and a cache must never hold secrets or build output you rely on for correctness.

§2Artifacts Between Jobs

Jobs run on separate machines, so hand results forward as artifacts. Upload from the producing job, download in the consuming one. You also use artifacts to keep reports and logs after a run.

build:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - run: make build
    - uses: actions/upload-artifact@v4
      with:
        name: dist
        path: dist/
deploy:
  needs: build
  runs-on: ubuntu-latest
  steps:
    - uses: actions/download-artifact@v4
      with:
        name: dist

§3Tests You Can Trust

A pipeline is only as good as its tests. Keep fast unit tests early, slower integration tests later, and make failures obvious with readable output and saved reports. A flaky test, one that passes and fails without code changes, is a bug in the pipeline: fix it or quarantine it, because retries just hide it.

- run: pytest --junitxml=reports/junit.xml
- uses: actions/upload-artifact@v4
  if: always()                     # keep the report even when tests fail
  with:
    name: test-report
    path: reports/
- run: docker compose -f compose.test.yaml up --abort-on-container-exit
Fail fast, report clearly Order jobs so the cheapest checks fail first, and use if: always() on steps that save diagnostics. A red build you can diagnose in 30 seconds is worth more than a green one you cannot trust.

§4Common Mistakes

MistakeWhat HappensFix
A cache key that never changesStale dependencies are used foreverInclude the lockfile hash in the key
Relying on the cache to passThe pipeline breaks on a cold cacheTreat caches as optional speedups only
Auto-retrying flaky testsThe flakiness stays hidden and growsInvestigate or quarantine, and track the failures
Practice
  1. Add dependency caching to a workflow and compare the run time before and after.
  2. Make a failing test run still upload its report, and open the report from the run page.
Key takeaways
  • Cache keys should derive from the lockfile hash, and a pipeline must pass without the cache.
  • Artifacts are how jobs on different machines share files and keep reports.
  • Fix flaky tests rather than retrying them away.
