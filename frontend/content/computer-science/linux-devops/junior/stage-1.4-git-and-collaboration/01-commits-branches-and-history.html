Commits, Branches & History

Git stores your project as a chain of snapshots called commits, and you move work through three areas: the working tree, the staging area, and the repository.

§1The Three Areas

You edit files in the working tree, choose what goes into the next snapshot by staging it, and then commit to record it permanently. The staging area lets you build a commit deliberately instead of saving everything at once.

git init                         # start a repository
git status                       # what changed, what is staged
git add app.py                   # stage one file
git add -p                       # stage chosen hunks interactively
git commit -m "Add health check endpoint"
git diff                         # working tree vs. staged
git diff --staged                # staged vs. last commit

Each commit has an ID (a SHA hash), an author, a message, and a pointer to its parent. Write messages that explain why, in the imperative mood, such as "Fix race in cache refresh".

§2Branches

A branch is just a movable label pointing at a commit. Creating one is nearly free, so the normal workflow is one branch per change. HEAD marks the branch you are on.

git switch -c fix-login-timeout  # create and move to a new branch
git branch                       # list branches
git switch main                  # go back
git branch -d fix-login-timeout  # delete after merging

§3Reading History

History is only useful if you can read it. git log shows commits, git show shows one in detail, and git blame shows who last changed each line.

git log --oneline --graph --decorate --all
git log -p -- path/to/file       # history of one file, with diffs
git show a1b2c3d                 # one commit
git blame -L 10,20 app.py        # who last touched lines 10-20
git log --grep="timeout"         # search commit messages
The key insight Commits are immutable snapshots linked by parent pointers, and branches are only labels on them. Almost every confusing Git behavior becomes clear once you picture that graph.

§4Common Mistakes

MistakeWhat HappensFix
Using git add . blindlyCommits secrets, build output, or unrelated changesReview with git status and git diff --staged, and use .gitignore
Writing vague messages like "fix stuff"Nobody, including you, can understand the history laterDescribe what changed and why
Committing directly to mainUntested changes land in the shared branchWork on a branch and merge by review
Practice
  1. Create a repo, make three commits on a branch, and draw the commit graph by hand, then compare with git log --graph.
  2. Stage only part of a file's changes with git add -p and confirm with git diff --staged.
Key takeaways
  • Work flows from the working tree to the staging area to a commit.
  • A branch is a lightweight label on a commit, so branching per change is cheap.
  • Good history relies on small, focused commits with clear messages.
