Merging vs. Rebasing

Merging and rebasing both combine work from two branches, but they leave different histories behind.

§1Merging

git merge joins another branch into your current one. If your branch has diverged, Git creates a merge commit with two parents, preserving exactly what happened. If nothing has diverged, it simply moves the label forward, a fast-forward.

git switch main
git merge feature/search         # fast-forward or a merge commit
git merge --no-ff feature/search # always create a merge commit
git merge --abort                # back out of a conflicted merge

§2Rebasing

git rebase replays your commits on top of another base, producing a straight line of new commits with new IDs. The history reads cleanly, but it rewrites commits.

git switch feature/search
git fetch origin
git rebase origin/main           # replay my commits onto the latest main
git rebase -i HEAD~4             # reorder, squash, or reword the last 4

The golden rule: never rebase commits that others have already pulled. Rewriting shared history forces everyone else to untangle duplicated commits.

§3Resolving Conflicts

A conflict appears when both sides changed the same lines. Git marks the file, and you choose the final content, then continue.

<<<<<<< HEAD
timeout = 30
=======
timeout = 60
>>>>>>> feature/search
# edit the file to the correct result and delete the markers, then:
git add config.py
git merge --continue             # or: git rebase --continue
git rebase --abort               # give up and return to the start
A common team policy Rebase your own local branch freely to keep it tidy and current. Merge (or squash-merge) into the shared branch. This gives you clean pull requests without ever rewriting history others depend on.

§4Common Mistakes

MistakeWhat HappensFix
Rebasing a branch others are usingDuplicated and diverging commits for everyoneRebase only local work; merge shared branches
Committing the conflict markersBroken code with <<<<<<< lines checked inSearch for markers and run the tests before --continue
Resolving a conflict by choosing a side without readingSilently drops someone's changeRead both sides, and understand what each intended
Practice
  1. Create two branches that edit the same line, merge them, and resolve the conflict.
  2. Make five messy commits, then use git rebase -i to squash them into two clean ones.
Key takeaways
  • Merge preserves true history with a merge commit; rebase rewrites it into a straight line.
  • Never rebase commits that other people have already pulled.
  • Resolve conflicts by reading both sides, removing markers, and testing before continuing.
