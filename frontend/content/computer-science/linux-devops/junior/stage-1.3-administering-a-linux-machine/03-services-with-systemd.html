Services with systemd

On modern Linux, systemd starts the system, supervises long-running services, and restarts them when they fail.

§1Managing Services

A service is described by a unit. systemctl starts and stops units now, and enables them to start at boot. These are two separate switches, and mixing them up is a common beginner trap.

sudo systemctl start nginx       # run now
sudo systemctl stop nginx
sudo systemctl restart nginx
sudo systemctl reload nginx      # re-read config without dropping connections
sudo systemctl enable nginx      # start at boot
sudo systemctl enable --now nginx   # both at once
systemctl status nginx           # state, PID, and recent logs
systemctl is-active nginx; systemctl is-enabled nginx

§2Writing a Unit File

Custom units live in /etc/systemd/system/. A service unit says what to run, as whom, and what to do if it dies. After creating or editing a unit, reload systemd so it re-reads the files.

# /etc/systemd/system/myapp.service
[Unit]
Description=My application
After=network-online.target
Wants=network-online.target

[Service]
User=myapp
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/bin/server --port 8080
Environment=APP_ENV=production
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload     # pick up the new/changed unit
sudo systemctl enable --now myapp
systemctl cat myapp              # show the effective unit

§3Dependencies and Targets

After= controls ordering only, and Wants= or Requires= pull other units in. Targets such as multi-user.target are named groups of units, roughly the old "runlevels". WantedBy=multi-user.target means "start this in normal multi-user boot".

systemctl list-units --type=service --state=failed
systemctl list-dependencies multi-user.target | head
systemd-analyze blame | head     # what slowed down boot?
Why Restart= matters With Restart=on-failure, systemd is your first line of defense: a crashed process is relaunched automatically. It is also the same supervision idea that container orchestrators later generalize across many machines.

§4Common Mistakes

MistakeWhat HappensFix
Editing a unit and not running daemon-reloadsystemd keeps using the old definitionRun systemctl daemon-reload after every change
Running start and expecting it to survive a rebootService is gone after restartAlso enable it, or use enable --now
Using After= alone to require a dependencyOrdering only; the other unit may never startAdd Wants= or Requires= as well
Practice
  1. Write a unit for a simple script that runs forever, enable it, then kill -9 the process and watch systemd restart it.
  2. Use systemctl list-units --state=failed to find any failed service on your machine and read why it failed.
Key takeaways
  • start runs a service now, and enable makes it start at boot; they are separate.
  • A unit file defines the command, the user, and the restart policy; reload systemd after editing it.
  • Ordering (After=) and requirement (Wants=, Requires=) are different settings.
