SSH & Key-Based Access

SSH gives you an encrypted shell on a remote machine, and key-based login is both more secure and more convenient than passwords.

§1Connecting and Copying

ssh user@host opens a remote shell, or runs a single command and returns. scp and rsync copy files over the same connection, and rsync only transfers what changed.

ssh alice@server.example.com
ssh alice@server.example.com "df -h /"   # run one command and exit
scp report.pdf alice@server:/home/alice/
rsync -avz --delete ./site/ alice@server:/var/www/site/
ssh -p 2222 alice@server                 # non-default port

The first connection shows the server's host key fingerprint and stores it in ~/.ssh/known_hosts. If the key later changes unexpectedly, SSH warns loudly, because that can mean someone is intercepting your connection.

§2Key Pairs

A key pair has a private key, which never leaves your machine, and a public key you place on servers in ~/.ssh/authorized_keys. The server proves you own the private key without ever seeing it. Protect the private key with a passphrase and use an agent to avoid retyping it.

ssh-keygen -t ed25519 -C "alice@laptop"  # creates ~/.ssh/id_ed25519(.pub)
ssh-copy-id alice@server                 # install the public key
eval "$(ssh-agent -s)" && ssh-add        # cache the unlocked key
chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys

SSH refuses keys when the permissions are too open. The ~/.ssh directory should be 700, and private keys and authorized_keys should be 600.

§3Config and Hardening

~/.ssh/config gives hosts short names and per-host settings. On the server, /etc/ssh/sshd_config controls policy. Once key login works, turn off passwords and root login.

# ~/.ssh/config
Host prod
    HostName 203.0.113.10
    User deploy
    IdentityFile ~/.ssh/id_ed25519
    ProxyJump bastion

# /etc/ssh/sshd_config (on the server)
PasswordAuthentication no
PermitRootLogin no
sudo sshd -t                             # validate config before reloading
sudo systemctl reload ssh                # the unit is "sshd" on RHEL systems
ssh prod                                 # now just works
Keep a session open while changing sshd Before you disable passwords or change the port, keep your current SSH session open and test a second connection. If the new config is wrong, the open session is your way back in.

§4Common Mistakes

MistakeWhat HappensFix
Sharing or copying private keys aroundAnyone with the file is you, everywhereGenerate one key per device and share only the .pub
Disabling password login before testing key loginYou lock yourself out of the serverTest a new key session first, and keep the old one open
Ignoring a changed host key warningYou may be talking to an impostorVerify with the server owner before updating known_hosts
Practice
  1. Generate a key pair, install it on a test machine, and log in without a password.
  2. Add a Host entry in ~/.ssh/config and connect using just the short name.
Key takeaways
  • Key-based SSH proves your identity with a private key that never leaves your machine.
  • Use rsync or scp for secure copies, and ~/.ssh/config to shorten everything.
  • Once keys work, disable password and root login, and validate with sshd -t.
