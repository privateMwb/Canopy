Secure-by-Default Design & Paved Roads

The most effective security work builds the safe way into the default way, so whole classes of bugs disappear instead of being found and fixed one at a time.

§1Eliminate Bug Classes, Don't Hunt Instances

If a vulnerability keeps recurring, ask what API or framework design makes it easy to write, and change that. Examples that worked:

Recurring bugSystemic fix
SQL injectionA data-access layer that only accepts parameterized queries; raw SQL requires an explicit, reviewable escape hatch
XSSA UI framework that escapes by default, plus Trusted Types and CSP
Missing authorization checksA framework where every route requires a declared policy, denying by default
Memory-safety bugsMemory-safe languages for new components
Hard-coded secretsWorkload identity and a secrets manager, with scanning in CI

§2Paved Roads

A paved road is the well-supported default path that makes the secure choice also the easy one: a standard service template with authentication, logging, and TLS already wired in; an approved crypto library with a high-level API; a shared login component. Teams that follow it get security for free, and teams that leave it must justify and own the risk. Developers choose the easy path, so make that the safe one.

§3Misuse-Resistant APIs

Design interfaces so the dangerous mistake is hard or impossible. Compare:

# Easy to misuse: caller picks mode, IV, and padding
encrypt(key, data, mode="CBC", iv=iv, padding="PKCS7")

# Misuse-resistant: one safe operation, nonce handled internally
box.encrypt(plaintext)      # authenticated, fresh nonce, no choices to get wrong

Libraries like libsodium and Tink follow this approach. The same thinking applies to your own internal APIs: make unsafe operations explicit (unsafe_raw_html, dangerously...) so they stand out in review and in search.

§4Guardrails in the Pipeline

Enforce defaults automatically: linters that ban dangerous functions, CI checks for secrets and vulnerable dependencies, and policy-as-code (from the DevOps track) that blocks insecure configurations. Automated guardrails scale better than reminders and reviews.

The leverage One framework fix can remove a vulnerability class from hundreds of services. That is how a small security team protects a large organization.

§5Common Mistakes

MistakeWhat HappensFix
Relying on developers to remember every ruleOne lapse across a large codebase causes a breachBuild the rule into the framework or pipeline
Offering secure options that are harder to useTeams route around themMake the safe path the easiest path
Fixing each instance of a bug class individuallyThe same bug keeps returningChange the API or tool that allowed it
Practice
  1. Pick a vulnerability class that recurs in a codebase you know, and propose a framework or API change that prevents it.
  2. Design the interface for an internal encrypt function that cannot be called unsafely.
Key takeaways
  • Remove bug classes with secure defaults, not one-off fixes.
  • Paved roads make the secure choice the easy choice.
  • Back defaults with automated guardrails in tooling and CI.
