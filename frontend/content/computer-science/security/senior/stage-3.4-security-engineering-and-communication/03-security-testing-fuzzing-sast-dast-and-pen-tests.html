Security Testing: Fuzzing, SAST, DAST & Pen Tests

Each testing technique finds a different slice of bugs, and a mature program uses several because none of them sees everything.

§1What Each Technique Finds

TechniqueWhat it doesGood atMisses
SAST (static analysis)Analyzes source code without running itInjection patterns, dangerous APIs, early in developmentRuntime and configuration issues; many false positives
DAST (dynamic testing)Probes a running app from outsideMisconfigurations, exposed endpoints, some injectionCode paths it can't reach; logic flaws
SCA (dependency scanning)Matches dependencies to known vulnerabilitiesKnown-vulnerable librariesUnknown flaws; whether the vulnerable code is reachable
FuzzingFeeds large volumes of mutated input to find crashesParsers and memory-safety bugsLogic and authorization flaws
Penetration testSkilled humans try to break inChained flaws, logic and authorization bugs, realistic pathsBroad coverage; findings are a point-in-time snapshot

§2Fuzzing, a Closer Look

A fuzzer generates inputs, feeds them to a parser or function, and watches for crashes, hangs, or sanitizer errors. Coverage-guided fuzzers (such as AFL++ or libFuzzer) mutate inputs that reach new code paths, so they explore deeply. Fuzzing is especially effective for file-format parsers, protocol decoders, and any code written in a memory-unsafe language. Run it in CI and keep the crashing inputs as regression tests.

§3Commissioning a Penetration Test

  • Scope: which systems, environments, and techniques are in or out (and get written authorization).
  • Goals: a general assessment, a specific feature before launch, or an attack simulation.
  • Provide access: test accounts of different roles, documentation, and a staging environment make the time more productive.
  • Act on the report: triage findings by risk (Stage 3.1), assign owners, fix, and retest. A report nobody follows up on is wasted money.

§4Reducing the Noise

Automated tools produce false positives, and a flood of low-value alerts trains developers to ignore them. Tune rules, suppress known-safe findings with documented reasons, gate builds only on high-confidence issues, and track the signal that matters: time to fix serious findings.

Tools find patterns, humans find intent Scanners match known shapes. Whether a coupon should work twice, or whether user A may see user B's invoice, is something only a person who understands the product will test.

§5Common Mistakes

MistakeWhat HappensFix
Treating a clean scan as proof of securityLogic and authorization flaws remainCombine tools with code review, threat modeling, and testing by humans
Commissioning a pen test without scope or accessTime is wasted on setup and shallow findingsDefine scope and goals, and provide accounts and docs
Not retesting after fixesFixes that don't work go unnoticedVerify every serious finding is closed
Practice
  1. Run a fuzzer on a small parsing function you've written and record what it finds in 10 minutes.
  2. Draft a scope document for a penetration test of one feature, including access and rules of engagement.
Key takeaways
  • SAST, DAST, SCA, fuzzing, and pen tests each find different bugs.
  • Fuzz parsers in CI and keep crashing inputs as regression tests.
  • Scope pen tests clearly, triage by risk, and retest the fixes.
