Randomness Failures & Key Compromise

Weak randomness and leaked keys have broken real systems far more often than weak algorithms, and the response plan for a lost key should exist before you need it.

§1When Randomness Fails

  • Debian OpenSSL (2006 to 2008): a code change removed nearly all entropy, leaving only about 32,000 possible keys per key type and architecture. Every key generated on affected systems was guessable and had to be replaced.
  • Repeated ECDSA nonces: a weak random generator on Android in 2013 caused some Bitcoin wallets to reuse a signature nonce, allowing private keys to be recovered. This is the failure mode from Stage 2.1.
  • Cloned virtual machines and forked processes that share generator state produce identical "random" values unless reseeded.
  • Backdoor concerns: the Dual_EC_DRBG generator was standardized and later withdrawn amid evidence it could be backdoored, a reason to use well-reviewed designs.

Always use the OS CSPRNG, verify that forked or restored processes reseed, and be wary of custom randomness code.

§2How Keys Actually Leak

  • Committed to source repositories, including in history.
  • Printed in logs, error pages, and crash dumps.
  • Embedded in mobile apps and client-side bundles, where anyone can extract them.
  • Left in backups, build artifacts, and container images.
  • Shared in chat, tickets, and documents.

The DevOps track's secrets-management lesson covers prevention. The senior skill is recovering when prevention failed.

§3Responding to a Compromised Key

  1. Revoke or rotate the credential immediately, and stop trusting the old key.
  2. Assess use: check logs for use of the key since the earliest possible exposure, not since you noticed.
  3. Re-issue anything derived from or protected by it, such as certificates, tokens, and encrypted data keys.
  4. Remove the leak from the source (scrub history if appropriate) and find how it got there.
  5. Fix the process: add secret scanning, shorter lifetimes, and per-service keys to reduce the blast radius.

Systems designed for rotation, with key versions, short lifetimes, and automated reissue, turn this from a crisis into a routine. Canary credentials that alert when used also detect theft early.

Plan the day you lose a key If rotating a key would take a week of manual work, you won't do it quickly enough during an incident. Practice rotation before you need it.

§4Common Mistakes

MistakeWhat HappensFix
Deleting a leaked secret from the repo and calling it fixedIt remains in history and clones, and may already be copiedRotate first, then clean up
Checking key use only from the date you noticedEarlier abuse goes unseenReview activity from the earliest possible exposure
Sharing one key across many servicesA single leak affects everythingUse per-service keys with narrow scope
Practice
  1. Scan a repository (including history) with a secret-scanning tool and list what it finds.
  2. Write a step-by-step rotation runbook for one API key, with who does what and how long each step takes.
Key takeaways
  • Weak randomness and repeated nonces have broken real systems.
  • Keys leak through repos, logs, client apps, and artifacts, so assume it will happen.
  • Rotate first, investigate from the earliest exposure, and design for painless rotation.
