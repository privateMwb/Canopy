Timing & Side Channels in Application Code

The side-channel lessons in the Architecture track showed timing leaking through hardware; the same idea shows up in ordinary application code, where the leak is often a branch or a comparison.

§1Where Software Timing Leaks

In the Architecture track, cache state and timing revealed secrets across a shared processor. Software has its own versions: anything that takes different time depending on a secret can be measured, remotely too. Researchers have shown timing differences of microseconds can be detected over a network with enough samples, so "it's only a few microseconds" is not a defense.

  • Early-exit comparisons: == on strings stops at the first mismatch, so a longer correct prefix takes longer.
  • Secret-dependent branches or table lookups in cryptographic code.
  • Different work for different outcomes in authentication, which reveals *which* check failed.

§2Enumeration by Response Time

A classic login leak: if the user doesn't exist, the server returns immediately, but if the user exists, it first runs a slow password hash. An attacker measuring response time learns which emails are registered, even when the messages are identical.

# Leaky: unknown users return fast
user = db.find(email)
if user is None:
    return fail()                     # no hash computed
if not verify(user.hash, password):
    return fail()                     # slow path

# Uniform: do the same work either way
user = db.find(email)
stored = user.hash if user else DUMMY_HASH     # a valid hash of a random value
ok = verify(stored, password) and user is not None
return success() if ok else fail()

§3Constant-Time Habits

  • Compare secrets (tokens, MACs, API keys) with a constant-time function, such as hmac.compare_digest, never ==.
  • Don't write your own cryptographic primitives. Constant-time implementation is hard, and compilers can quietly reintroduce branches. Use maintained libraries and their hardware-accelerated paths.
  • Equalize observable work in authentication and error paths, including response size.
  • Rate limiting and noise make measurement harder but don't eliminate leaks, so treat them as a supplement.
Connection to the Architecture track That track's defensive habits, constant-time code and reduced timer precision, apply here at the application layer. The difference is that the observer might be a remote client, not a co-resident process.

§4Common Mistakes

MistakeWhat HappensFix
Comparing tokens with ==Matching prefix length is measurableUse a constant-time comparison function
Skipping the password hash for unknown accountsResponse timing reveals which accounts existRun a dummy hash so both paths cost the same
Assuming network noise hides small timing differencesStatistical averaging recovers themRemove the secret-dependent difference at the source
Practice
  1. Time a login endpoint for existing and nonexistent users in a test app over 200 requests each, and compare the averages.
  2. Replace a token comparison in your code with a constant-time function and say what the old one leaked.
Key takeaways
  • Anything whose running time depends on a secret can leak it, even over a network.
  • Make authentication paths do equal work, and compare secrets in constant time.
  • Use vetted crypto libraries; don't hand-write constant-time primitives.
