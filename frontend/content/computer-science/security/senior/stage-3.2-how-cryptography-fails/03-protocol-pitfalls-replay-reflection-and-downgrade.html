Protocol Pitfalls: Replay, Reflection & Downgrade

A protocol can break even when every primitive in it is secure, because the flaws live in what is authenticated, what is bound together, and what the receiver accepts twice.

§1Replay, Reflection, and Downgrade

AttackWhat the attacker doesDefense
ReplayResends a valid captured message laterNonces, timestamps with a window, sequence numbers, one-time tokens
ReflectionSends a party's own message back to it as if from the peerInclude direction or role in what is authenticated
DowngradeForces both sides onto a weaker version or algorithmAuthenticate the negotiation transcript, and disable weak options
Cross-protocol or key reuseUses a message or key from one context in anotherDomain separation: distinct keys and labels per purpose

§2Bind Everything That Matters

A valid tag or signature proves only that *some* message was authenticated, and it's up to you to include what gives it meaning: the sender and receiver identities, the purpose ("password reset" versus "email verification"), the version, and a freshness value. Otherwise a token minted for one use can be redeemed for another.

# Weak: the tag covers only the user ID
tag = HMAC(key, user_id)

# Better: covers purpose, identity, and expiry, in an unambiguous encoding
tag = HMAC(key, encode(purpose="reset", user=user_id, expires=ts, version=1))

§3Ambiguous Encodings

If you authenticate by concatenating fields, different inputs can produce the same bytes: "ab" + "c" and "a" + "bc" both give "abc". An attacker shifts content between fields and keeps the tag valid. Use a canonical, unambiguous encoding: length-prefixed fields or a structured format with a fixed field order, and verify against the exact bytes you signed, not a re-serialized version.

§4Don't Compose Your Own

The safest path is a well-studied protocol or a high-level library (TLS, Noise-based designs, libsodium's constructions) rather than combining primitives yourself. If you must design one, get it reviewed by a cryptographer, write down the security goals and the attacker model first, and test it against the attacks above.

The pattern behind the table Each attack works because the receiver accepted something it shouldn't: a second copy, a message from itself, a weaker version, or a token made for another purpose. For each message, ask "what makes this one valid, here, now?"

§5Common Mistakes

MistakeWhat HappensFix
Authenticating fields by plain concatenationBoundaries shift and the tag still verifiesUse length-prefixed or structured canonical encoding
Tokens that don't encode their purposeA token for one flow works in anotherInclude purpose, identities, and expiry in the authenticated data
Leaving version negotiation unauthenticatedAn attacker forces the weakest optionCover the negotiation in the authenticated transcript
Practice
  1. Show two different (field A, field B) pairs that concatenate to the same bytes, and propose a safe encoding.
  2. List, for a password-reset token, every value that should be inside the authenticated data.
Key takeaways
  • Protocols fail through replay, reflection, downgrade, and cross-context reuse even with strong primitives.
  • Authenticate purpose, identities, version, and freshness, using unambiguous encoding.
  • Prefer reviewed protocols and libraries over homemade compositions.
