Security Requirements & Abuse Cases

Security requirements and abuse cases move the work to design time, where a missing safeguard costs a sentence to fix, not a rewrite.

§1Negative Requirements

Ordinary requirements say what the system should do. Security requirements often say what it must not allow, and they need to be specific enough to test.

VagueTestable
"Passwords must be secure""Passwords are stored with Argon2id; a database dump must not reveal any password"
"Only authorized users see invoices""A user cannot read, list, or infer the existence of another tenant's invoices through any endpoint"
"Reset must be safe""A reset token is single-use, expires in 30 minutes, and responses are identical for unknown emails"

§2Abuse Cases

A user story says "As a user, I want to...". An abuse story flips the viewpoint: "As an attacker, I want to...", and asks what the design does about it.

Feature: apply a discount code at checkout
Abuse: As an attacker, I want to apply the same code on many accounts
       or in parallel requests to get repeated discounts.
Requirement: a single-use code is redeemed atomically; concurrent redemptions fail.
Test: fire 20 parallel redemptions; exactly one succeeds.

§3Design Flaws Versus Bugs

A bug is an implementation mistake, such as a missing check in one handler. A design flaw is a problem in the approach, such as designing password reset around a guessable question. Scanners and code review find bugs far better than flaws, and flaws are costly to repair once built. Early review of designs, with the threat model and abuse cases in hand, is the main defense.

  • Tie each requirement to a threat from your model, so nothing is added without a reason.
  • Add each requirement's test to the acceptance criteria, so "done" includes "secure."
  • Review the design when it changes, not just once.
Why do this early Fixing a flawed design after launch means migrating data, changing APIs, and re-testing everything. Fixing it in a design review means editing a paragraph.

§4Common Mistakes

MistakeWhat HappensFix
Writing vague security requirementsThey can't be tested, so nobody knows if they're metState testable negative requirements
Only listing happy-path storiesAbuse is discovered by attackers after launchWrite an abuse story for each feature that handles money, data, or access
Reviewing security only at the endDesign flaws are expensive to fix by thenReview the design and the threat model before building
Practice
  1. Write three abuse stories and matching testable requirements for a file-sharing feature.
  2. Rewrite "the API must be secure" as five testable requirements.
Key takeaways
  • Security requirements say what must not happen, in a testable form.
  • Abuse stories surface attacker behavior at design time.
  • Design flaws are costlier than bugs, so review designs early and again after changes.
