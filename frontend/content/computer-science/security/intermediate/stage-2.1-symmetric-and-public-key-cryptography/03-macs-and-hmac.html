MACs & HMAC

A message authentication code lets someone who shares a key prove a message wasn't altered, and HMAC is the construction nearly everything relies on.

§1What a MAC Does

A MAC takes a secret key and a message and produces a short tag. Anyone holding the key can recompute the tag and compare. Without the key, an attacker can't produce a valid tag for a changed message. The guarantee is integrity and authenticity: the message came from someone with the key and wasn't modified. It provides no secrecy.

import hmac, hashlib
tag = hmac.new(key, message, hashlib.sha256).digest()

# Receiver recomputes and compares in constant time
expected = hmac.new(key, message, hashlib.sha256).digest()
ok = hmac.compare_digest(expected, received_tag)

§2Why HMAC and Not Hash(key + message)

SHA-256 and the other SHA-2 hashes are vulnerable to length extension: given H(key || msg) and the length of the key, an attacker can compute H(key || msg || extra) without knowing the key. HMAC's nested construction avoids this, so use HMAC-SHA256 and not a homemade "hash the key and the message."

§3Using MACs Correctly

  • Compare tags in constant time (hmac.compare_digest), so response timing can't reveal how many leading bytes matched. The Architecture track explained why timing leaks.
  • Cover everything that matters: sign the exact bytes, plus any context such as a timestamp, a user ID, or the purpose, to prevent reuse in another place.
  • Add a timestamp or nonce and reject old ones to stop replay: a valid tagged message sent again later.
  • Use separate keys for separate purposes.

The webhook lesson in Networking used exactly this: the provider computes an HMAC over the raw body and timestamp with a shared secret, and you recompute it.

Limits of a shared key Because both sides hold the same key, either one can create valid tags. A MAC proves the message came from *one of the key holders*, not which one, and a receiver can't prove to a third party that the sender wrote it. Signatures (next lessons) change that.

§4Common Mistakes

MistakeWhat HappensFix
Computing SHA256(key + message) as a MACLength-extension attacks forge new messagesUse HMAC
Comparing tags with ==Timing differences leak the correct tag byte by byteUse a constant-time comparison
Not binding the tag to context or timeA valid message is replayed or reused elsewhereInclude purpose, identifiers, and timestamps in the authenticated data
Practice
  1. Implement signing and verification of a JSON payload with HMAC-SHA256, then change one character and confirm verification fails.
  2. Add a timestamp to the signed data and reject messages older than five minutes.
Key takeaways
  • A MAC gives integrity and authenticity between holders of a shared key.
  • Use HMAC and constant-time comparison, never a bare hash of key plus message.
  • Bind tags to context and time to prevent reuse and replay.
