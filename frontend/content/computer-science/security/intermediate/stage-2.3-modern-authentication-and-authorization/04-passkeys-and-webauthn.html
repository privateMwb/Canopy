Passkeys & WebAuthn

Passkeys replace the shared secret with a key pair bound to the site's origin, which makes them resistant to phishing in a way passwords and one-time codes cannot be.

§1How a Passkey Login Works

At registration, the user's device creates a key pair for that site. The private key stays in the authenticator (a phone, laptop, or hardware key), and the site stores only the public key. At login, the site sends a random challenge and the device signs it.

Register:  device makes key pair for example.com → server stores PUBLIC key
Login:     server ──challenge──▶ device
           device signs (challenge + origin) with PRIVATE key  ──▶ server
           server verifies with stored public key

The user unlocks the key locally with a biometric or PIN. That unlock never leaves the device and isn't sent to the server. This is the signature scheme from Stage 2.1 used for login.

§2Why It Resists Phishing

The signature covers the origin the browser is actually on. A look-alike site at examp1e.com gets no valid credential because the key pair is scoped to the real origin, and the browser won't offer it. There's no secret for the user to type or a code to relay. Compare with TOTP, where an attacker's proxy can forward a freshly typed code in real time.

PasswordTOTPPasskey
Stolen from a breached serverHash can be crackedSeed can be stolenOnly a public key is stored

§3Tradeoffs and Recovery

  • Synced passkeys (stored in a platform's cloud keychain) survive a lost device, but trust that account's security. Device-bound keys are stronger against cloud compromise but harder to recover.
  • Recovery is the new weak point: if a lost-device flow falls back to email or SMS, attackers target that instead. Design recovery to be as strong as the credential it replaces.
  • Keep a fallback during adoption, and encourage registering more than one authenticator.

The standards are WebAuthn (the browser API) and FIDO2; use a maintained server library for verification rather than writing the checks yourself.

Why this matters Passkeys remove the shared secret that phishing, credential stuffing, and database breaches all depend on. The remaining attack surface is account recovery and device security.

Practice
  1. Register a passkey on a site that supports it and note which device holds the private key.
  2. Explain why a phishing site can't use a stolen passkey signature on the real site.
Key takeaways
  • Passkeys use a per-site key pair and a signed challenge, so the server stores no secret.
  • Origin binding makes them phishing-resistant, unlike passwords and TOTP.
  • Recovery and fallback flows are the new weak point and must be designed carefully.
