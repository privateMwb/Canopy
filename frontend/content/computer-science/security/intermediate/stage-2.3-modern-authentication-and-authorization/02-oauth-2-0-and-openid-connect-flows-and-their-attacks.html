OAuth 2.0 & OpenID Connect: Flows and Their Attacks

OAuth and OpenID Connect are the standard way to sign in with another service, and most real attacks are not on the cryptography but on skipped checks in the flow.

§1The Flow, in One Request

The Networking track introduced OAuth 2.0 and the authorization code flow with PKCE. Here is the request that starts it, with every security-relevant parameter.

GET /authorize
  ?response_type=code
  &client_id=abc123
  &redirect_uri=https://app.example/callback    # must exactly match a registered URI
  &scope=openid profile
  &state=<random per login>                      # ties the response to this browser
  &nonce=<random per login>                      # ties the ID token to this request
  &code_challenge=<BASE64URL(SHA256(verifier))>  # PKCE
  &code_challenge_method=S256
  • PKCE makes a stolen authorization code useless: only the client that knows the original code_verifier can redeem it.
  • state prevents login CSRF, where an attacker forces your browser to complete *their* login. The app must check the value on return.
  • Exact-match redirect URIs stop the server from sending the code to an attacker's page. Patterns, wildcards, or open redirects on the client's domain break this.

§2OpenID Connect: Authentication on Top

OAuth by itself is about *authorization* to access an API. OpenID Connect (OIDC) adds an ID token, a signed JWT that tells the client who logged in. The two tokens have different audiences and purposes.

ID tokenAccess token
ForThe client appThe resource server (API)
SaysWho authenticated, when, and howWhat the bearer may access
Client mustValidate iss, aud, exp, nonce, and signatureTreat as opaque and send to the API

Don't use an access token as proof of identity. A token issued to a different app for the same user could be replayed to yours, a confused-deputy problem.

§3Bugs That Keep Recurring

  • Skipping or not verifying state, enabling login CSRF.
  • Loose redirect URI matching, leaking codes and tokens to attackers.
  • The legacy implicit flow, which returns tokens in the URL; current guidance (the OAuth Security Best Current Practice and OAuth 2.1) is to use code flow with PKCE instead.
  • Accepting an ID token without checking aud and iss, or the nonce value.
  • Over-broad scopes requested "just in case," widening the damage of any leak.
  • Trusting an email claim without checking it's verified, which enables account takeover via account linking.
Use a vetted library Validating every parameter, signature, and claim correctly is hard to get right by hand. Use a maintained OIDC client library and then review its configuration, because misconfiguration is where the bugs live.

§4Common Mistakes

MistakeWhat HappensFix
Not verifying state on the callbackAn attacker logs the victim into the attacker's accountGenerate state per login and require it to match
Allowing wildcard or prefix redirect URIsAuthorization codes are delivered to attacker-controlled pagesRegister exact URIs and compare them exactly
Using an access token to identify the userTokens meant for other apps are accepted as loginsUse the validated ID token, with aud and nonce checked
Practice
  1. Trace an OAuth login in your browser's Network panel and identify state, the code, and where PKCE appears.
  2. List, for each parameter in the authorize request, the attack that would work if it were missing.
Key takeaways
  • PKCE, state, and exact redirect URIs each close a specific hole in the code flow.
  • OIDC's ID token proves who logged in; an access token is for calling APIs.
  • Most OAuth breaches are skipped validations, so use a vetted library and review the config.
