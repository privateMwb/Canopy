JWT Pitfalls: Algorithm & Key Confusion

JWTs are signed, not secret, and nearly every JWT vulnerability comes from letting the token tell the server how to verify it or from skipping a claim check.

§1Decoding Is Not Verifying

A JWT's header and payload are just Base64URL text that anyone can read or edit. The signature is the only thing that makes it trustworthy, and only if the server verifies it with a key and algorithm it chose. Code that decodes and uses claims before verification is processing attacker-written data.

§2Algorithm Attacks

  • alg: none: the header claims no signature is needed. A library that honors it accepts forged tokens. Never allow none.
  • Algorithm confusion (RS256 to HS256): the server expects an RSA signature and verifies with its public key. If the library lets the token choose HS256, an attacker signs with HMAC using the *public key as the secret*. The public key is public, so the forged token verifies.
# Vulnerable: the token chooses how it is verified
header = jwt.get_unverified_header(token)
claims = jwt.decode(token, key, algorithms=[header["alg"]])

# Safe: the server decides algorithm, key, and required claims
claims = jwt.decode(token, public_key, algorithms=["RS256"],
                    audience="api", issuer="https://auth.example.com")

Signatures make this easy to understand: a verification key must be used only for the algorithm it was created for.

§3Header and Claim Pitfalls

  • kid injection: the header names which key to use. If the server uses kid in a file path or SQL query without care, it is another injection point. Look keys up in a fixed set.
  • jku, x5u, and embedded jwk headers let a token point at a key location or carry its own key. Never trust keys the token supplies; use keys from your own configuration or a pinned issuer.
  • Unchecked claims: verify exp, nbf, iss, and aud. A valid signature on a token meant for a different service or already expired is still a bad token.
  • Sensitive data in the payload: it is readable by anyone.
The rule that fixes most of these The server fixes the algorithm, the key source, the issuer, and the audience in configuration. The token supplies only claims to be checked, never instructions on how to check them.

§4Common Mistakes

MistakeWhat HappensFix
Reading claims before verifying the signatureAttacker-supplied data drives decisionsVerify first, then use the claims
Allowing the token header to select the algorithmnone or HS256-with-public-key forgeries are acceptedPin the algorithm list in server configuration
Following jku or embedded keys from the tokenThe attacker supplies their own verification keyAccept keys only from trusted configuration
Practice
  1. Write a JWT validation function and test it with a token using alg: none and one with the wrong audience.
  2. Explain in three sentences how signing with the public key as an HMAC secret can verify.
Key takeaways
  • A JWT is only trustworthy after verification with a server-chosen algorithm and key.
  • Reject none, never let the header pick the algorithm, and don't trust token-supplied keys.
  • Always check exp, iss, and aud, and keep secrets out of the payload.
