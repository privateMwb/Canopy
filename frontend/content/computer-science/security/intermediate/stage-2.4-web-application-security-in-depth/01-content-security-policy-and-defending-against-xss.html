Content Security Policy & Defending Against XSS

Content Security Policy tells the browser which scripts it may run, so even when an XSS bug slips through, the injected code often fails to execute.

§1How CSP Works

CSP is a response header listing the sources the browser may load code and content from. Anything outside the list is blocked, including an injected inline script.

Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-R4nd0mPerResponse' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none'
  • default-src 'self' allows resources only from your own origin by default.
  • script-src with a nonce allows only <script nonce="..."> tags carrying the value the server generated for this response. An attacker can't guess it.
  • object-src 'none' and base-uri 'none' remove two classic bypass routes.

§2Strict CSP Over Allow-Lists of Hosts

Policies that list allowed script hosts tend to be bypassable, since any allowed host that serves a vulnerable or user-controlled script becomes a gadget. Current guidance favors a nonce- or hash-based strict CSP, with 'strict-dynamic' so scripts your trusted script loads are also allowed. Avoid 'unsafe-inline' and 'unsafe-eval', which cancel most of the protection.

Roll out with Content-Security-Policy-Report-Only first. It reports violations without blocking, so you can find legitimate scripts you forgot about.

§3Trusted Types

DOM-based XSS comes from risky sinks such as innerHTML. Trusted Types makes the browser refuse plain strings at those sinks, so only values produced by a policy you wrote are accepted.

Content-Security-Policy: require-trusted-types-for 'script'

It turns "find every dangerous assignment" into an enforced rule, and it's most practical in new or well-structured front ends.

A second wall, not the first CSP reduces the impact of XSS but doesn't remove the bug. Output encoding is still the primary defense (Stage 1.4); CSP is what limits the blast radius when that defense has a gap.

§4Common Mistakes

MistakeWhat HappensFix
Adding 'unsafe-inline' to make things workInjected inline scripts run againUse nonces or hashes for legitimate inline scripts
Reusing the same nonce across responsesAn attacker who learns it can use itGenerate a fresh random nonce for every response
Enabling CSP without testingThe site breaks for real usersDeploy in report-only mode first and fix violations
Practice
  1. Deploy a report-only CSP on a test page and review which violations it reports.
  2. Convert one inline script on a page to use a per-response nonce.
Key takeaways
  • CSP restricts which scripts run, limiting what injected code can do.
  • Prefer nonce- or hash-based strict policies over long host allow-lists.
  • CSP and Trusted Types back up output encoding; they don't replace it.
