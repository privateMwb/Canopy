File Uploads & Untrusted Content

Uploaded files are attacker-controlled bytes that your server stores and may later serve, so every step from acceptance to delivery needs its own control.

§1Accept Carefully

  • Enforce size limits early, before the whole file is read, and cap total uploads per user.
  • Allow-list extensions and types that you actually need.
  • Don't trust Content-Type or the filename. Both are chosen by the client. Check the file's real content, such as its magic bytes, with a trusted library.
  • Re-process images (decode and re-encode) to strip embedded payloads and unusual metadata.
  • Scan for malware where files are shared with other users.

Beware of archives and images that expand enormously when decompressed (decompression bombs), and of formats that can carry script, such as SVG.

§2Store Safely

  • Generate your own storage name, a random ID, and never use the client's filename in a path. That closes the path traversal bug from Stage 1.4.
  • Store outside the web root or in object storage, so the web server can't run an uploaded file as code.
  • Never execute uploaded content, and don't give the storage location execute permissions.

§3Serve Safely

Serving a user's file from your main origin lets any script it contains run with your site's authority, which is XSS. Reduce that risk:

Content-Type: application/octet-stream            # or the verified type
Content-Disposition: attachment; filename="report.pdf"
X-Content-Type-Options: nosniff
# Serve from a separate origin, e.g. usercontent.example-cdn.net

A separate, cookie-less origin for user content means a malicious file can't read your site's session or DOM. Use Content-Disposition: attachment for types that should download, not render.

Think about the whole path Acceptance, storage, and delivery each need protection. A perfect type check doesn't help if the file is later served inline from your main domain.

§4Common Mistakes

MistakeWhat HappensFix
Trusting the extension or Content-Type headerA script uploaded as image.png is acceptedValidate real content and re-encode images
Using the original filename in the storage pathPath traversal or overwritesUse a generated random name
Serving uploads inline from the main originUploaded HTML or SVG runs as your siteServe from a separate origin with nosniff and attachment where appropriate
Practice
  1. Upload a text file renamed to .png to a test app and see whether your check catches it by content.
  2. Design the storage and serving setup for user avatars, including origin, headers, and naming.
Key takeaways
  • Validate uploads by size, type, and content, never by client-supplied names or headers.
  • Store under random names outside the web root.
  • Serve user content from a separate origin with nosniff and safe disposition.
