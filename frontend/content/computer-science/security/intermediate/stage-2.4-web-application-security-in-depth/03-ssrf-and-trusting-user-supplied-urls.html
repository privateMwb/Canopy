SSRF & Trusting User-Supplied URLs

Server-side request forgery turns your server into a proxy for the attacker, letting them reach internal systems that the internet can't, and the simple fixes people try first usually fail.

§1The Bug

Any feature where the server fetches a URL the user supplies, such as link previews, image imports, webhooks, or PDF generators, can be abused. The attacker points it at addresses only the server can reach.

  • Cloud metadata endpoints, such as 169.254.169.254, can return the instance's credentials.
  • localhost admin interfaces and internal dashboards.
  • Internal services in private IP ranges, with no authentication because they were "internal."

The OWASP API lesson listed SSRF as one item. This lesson covers why the obvious blocklist fails.

§2How Naive Filters Are Bypassed

TrickWhy it beats a string check
Alternate IP encodings (decimal 2130706433, octal, hex, IPv6 forms)All resolve to 127.0.0.1 but don't match the text "127.0.0.1"
A domain that resolves to an internal IPThe name looks harmless; the address is internal
DNS rebindingThe name resolves to a safe IP at check time and an internal one at fetch time
RedirectsAn allowed URL answers with a redirect to an internal target
URL parser disagreements (http://allowed.com@evil.com, backslashes, #)Your validator and your HTTP client parse the URL differently
Other schemes (file://, gopher://)The client supports more than HTTP

§3Layered Defenses

  • Allow-list destinations whenever the set is known, and permit only http and https.
  • Resolve the hostname yourself, validate the resulting IP (not private, loopback, link-local, or reserved), and connect to that exact IP so rebinding can't swap it.
  • Don't follow redirects automatically, or re-validate every hop.
  • Limit timeouts and response size, and don't return raw responses to the user.
  • Network egress rules: run fetchers in a segment that can't reach internal services or metadata at all.
  • Harden metadata services, for example by requiring AWS IMDSv2 session tokens, which most simple SSRF requests can't produce.
import ipaddress, socket
from urllib.parse import urlparse

def resolves_to_public_ip(url):
    u = urlparse(url)
    if u.scheme not in ("http", "https") or not u.hostname:
        return False
    for *_, addr in socket.getaddrinfo(u.hostname, u.port or 443, type=socket.SOCK_STREAM):
        ip = ipaddress.ip_address(addr[0])
        if ip.is_private or ip.is_loopback or ip.is_link_local or ip.is_reserved:
            return False
    return True      # still connect to the validated IP, and don't follow redirects blindly
Where the real fix is Application checks are fragile on their own. Network-level egress restrictions and hardened metadata services mean that even a missed bug can't reach anything valuable.

§4Common Mistakes

MistakeWhat HappensFix
Blocklisting 127.0.0.1 and localhost as stringsOther encodings and hostnames bypass itResolve and validate the IP address
Checking the URL once and then fetching by nameDNS rebinding changes the answer between check and useConnect to the IP you validated
Following redirects automaticallyAn allowed host redirects to an internal addressDisable redirects or validate each hop
Practice
  1. In a local test app with a URL-fetch feature, try three IP encodings of localhost against a string-based blocklist and note which pass.
  2. Design the network rules that would stop an image-import service from reaching cloud metadata.
Key takeaways
  • SSRF lets attackers use your server's network position to reach internal resources.
  • String-based blocklists fail to encodings, DNS tricks, redirects, and parser differences.
  • Validate resolved IPs, avoid redirects, and enforce network egress limits.
