Key Management: Generation, Storage & Rotation

Strong algorithms don't help if the keys sit beside the data they protect, so key management, not the cipher, is usually where real systems succeed or fail.

§1The Key Lifecycle

  1. Generate with a CSPRNG, ideally inside a hardware or managed boundary so the key is never exposed.
  2. Store apart from the data it protects, in a KMS or HSM, not in the same database or repository.
  3. Use under access control and logging, so you know who used which key and when.
  4. Rotate on a schedule and after any suspected exposure.
  5. Retire and destroy keys that are no longer needed, once nothing depends on them.

§2Envelope Encryption

Instead of encrypting data directly under one master key, systems use two layers. A data encryption key (DEK) encrypts the data. A key encryption key (KEK), held in a KMS, encrypts ("wraps") the DEK. You store the wrapped DEK next to the ciphertext.

document ──encrypt with DEK──▶ ciphertext
DEK      ──wrap with KEK (in KMS)──▶ wrapped DEK
store:  ciphertext + wrapped DEK + key ID

# To read: ask the KMS to unwrap the DEK (access is checked and logged),
# then decrypt the data locally.
  • The KEK never leaves the KMS, so a stolen database contains only ciphertext and wrapped keys.
  • Each object can have its own DEK, which limits what any single leaked key exposes.
  • Every unwrap goes through the KMS, creating an audit trail and a place to revoke access.

§3Rotation Without Pain

Rotating the KEK means re-wrapping the DEKs, not re-encrypting all the data, which is why envelope encryption scales. Tag each ciphertext with a key ID or version so old and new keys can coexist during rotation, and keep an old key available only as long as data under it exists.

The SQL track's database-security lesson said to keep keys in a KMS or HSM, separate from the data. This is the mechanism behind that advice.

What it protects, and what it doesn't Envelope encryption protects against stolen storage and snapshots. It doesn't protect against an attacker who can call the KMS as your application. Access control on the unwrap permission is part of the defense.

§4Common Mistakes

MistakeWhat HappensFix
Storing the key beside the encrypted dataOne leak reveals bothKeep keys in a KMS or HSM with separate access control
Never rotating keysA long-exposed key has unlimited time to leakRotate on a schedule and after incidents, using key versions
Re-encrypting everything for each rotationSlow, risky, and often skippedUse envelope encryption and re-wrap DEKs
Practice
  1. Draw the data flow for reading one encrypted record under envelope encryption, labeling where each key lives.
  2. Decide what you'd store alongside each ciphertext to support rotation.
Key takeaways
  • Key management determines real security more than the choice of cipher.
  • Envelope encryption wraps per-object data keys with a KMS-held key.
  • Rotate by re-wrapping keys, and tag ciphertext with a key version.
