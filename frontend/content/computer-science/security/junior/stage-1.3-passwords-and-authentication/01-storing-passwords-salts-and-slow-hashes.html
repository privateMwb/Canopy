Storing Passwords: Salts & Slow Hashes

Passwords must be stored so that a stolen database doesn't hand attackers the passwords, which means a deliberately slow, salted hash and never a fast one.

§1Why a Fast Hash Is the Wrong Tool

SHA-256 is built to be fast, and that's exactly the problem. A modern GPU can try billions of SHA-256 guesses per second, so an attacker with a stolen table of SHA-256(password) values just hashes a list of common passwords and looks for matches. Most users pick guessable passwords, so most of the table falls quickly.

Precomputed tables of hash-to-password pairs (rainbow tables) make this even cheaper when everyone's hash is computed the same way.

§2Salting

A salt is a random value, unique per user, stored beside the hash and mixed into it. Two users with the same password get different hashes, and precomputed tables become useless, since the attacker must attack each account separately.

stored = salt + hash(salt + password)
# the salt is not secret; it only has to be unique and random

§3Slow, Memory-Hard Password Hashes

A password hashing function adds a tunable cost so each guess is expensive for the attacker but still affordable for one login. Use an established one, with its own built-in salt handling.

FunctionNotes
Argon2idMemory-hard and the usual first choice for new systems
scryptMemory-hard; a solid alternative
bcryptLong-standing and widely supported; truncates input at 72 bytes
PBKDF2Standards-friendly but not memory-hard; needs high iteration counts
from argon2 import PasswordHasher
ph = PasswordHasher()
stored = ph.hash(password)        # salt and parameters are inside the string
ph.verify(stored, attempt)        # raises on mismatch

Tune the cost so a login takes a noticeable fraction of a second on your hardware, and use current guidance, such as the OWASP Password Storage Cheat Sheet, for parameters. Store the parameters with each hash so you can raise them later.

Pepper, optionally A pepper is an extra secret kept outside the database, such as in a secrets manager, and mixed into the hash. It helps if only the database leaks, but it adds key management, so treat it as an extra layer and not a substitute for a slow hash.

§4Common Mistakes

MistakeWhat HappensFix
Hashing passwords with plain SHA-256 or MD5Billions of guesses per second on stolen dataUse Argon2id, scrypt, or bcrypt
One global salt, or no saltIdentical passwords share hashes and tables applyUse a unique random salt per password, which good libraries do automatically
Writing your own password hashing schemeSubtle flaws remain unnoticedUse a vetted library and its defaults
Practice
  1. Using a library, hash the same password twice and confirm the two stored strings differ.
  2. Time one hash on your machine and adjust the cost parameters until it takes roughly a quarter of a second.
Key takeaways
  • Password storage must be slow on purpose: use Argon2id, scrypt, or bcrypt.
  • A unique random salt per password defeats precomputed tables.
  • Use a vetted library and store the parameters so you can raise the cost later.
