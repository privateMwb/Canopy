Using Hashes: Integrity & Fingerprints

Hashes are the everyday tool for checking that data is the data you expected, as long as you remember what they can't tell you.

§1Verifying a Download

Publishers list a digest next to a file. You hash what you downloaded and compare, which catches corruption and accidental changes.

$ sha256sum tool-1.4.tar.gz
9f2c...e41a  tool-1.4.tar.gz
$ echo '9f2c...e41a  tool-1.4.tar.gz' | sha256sum -c
tool-1.4.tar.gz: OK

For this to defend against tampering, the digest must reach you by a different, trusted channel than the file. If an attacker can change the file on the same server, they can change the digest beside it.

§2Content Addressing

Systems like Git name objects by the hash of their contents. Identical content gets the same name, so duplicates collapse, and any change produces a new name, so history can't be quietly rewritten without every later hash changing.

$ echo 'hello' | git hash-object --stdin
ce013625030ba8dba906f756967f9e9ca394464a

Hash chains extend the idea: each record includes the hash of the one before it, so altering an old record breaks every record after it. Later stages use this for tamper-evident logs.

§3What a Bare Hash Does Not Prove

  • Who made it. Anyone can hash anything, so a digest proves nothing about origin.
  • That it's safe. A hash matches the file you meant to check, not whether the file is benign.
  • That it hasn't been replaced along with its hash. See the trusted-channel rule above.

To bind data to a producer, use a signature, which signs the digest with a private key (Stage 2.1).

Fingerprints A hash works like a fingerprint for data: it lets you check identity cheaply without comparing every byte. The security comes from where the trusted copy lives, not from the hash itself.

§4Common Mistakes

MistakeWhat HappensFix
Fetching file and checksum from the same untrusted placeAn attacker swaps bothObtain the digest over a separate trusted channel, or verify a signature
Treating a matching hash as proof of safetyA malicious file that matches its own hash passesCombine integrity checks with trust in the publisher
Comparing digests by eyeNear-matches go unnoticedUse sha256sum -c or a script to compare
Practice
  1. Download a release with a published SHA-256, verify it with sha256sum -c, and note where the digest came from.
  2. Build a three-record hash chain by hand, then change record 1 and see which hashes change.
Key takeaways
  • Hashes verify integrity cheaply, for downloads, deduplication, and content addressing.
  • A hash is only as trustworthy as the channel that delivered it.
  • Hashes don't prove origin or safety; signatures and trust decisions do.
