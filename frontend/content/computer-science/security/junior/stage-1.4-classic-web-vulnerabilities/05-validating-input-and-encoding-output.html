Validating Input & Encoding Output

Two habits close most injection holes: accept only what you expect, and encode everything for the exact context it's placed into.

§1Validate with Allow-Lists

Define what good looks like and reject everything else, rather than trying to list bad things. A deny-list is incomplete by nature.

import re
def valid_username(s):
    return bool(re.fullmatch(r"[a-z0-9_]{3,20}", s))   # whole value must match

# Also validate: type, length, range, and business rules (is this ID yours?)

Validation checks shape, not safety: a perfectly valid name like O'Brien is still dangerous inside a SQL string. That's why output handling matters.

§2Encode for the Context

The same text needs different handling depending on where it's placed. Use the encoder for that context, preferably from your framework.

ContextRight handling
HTML body textHTML-escape <, >, &, quotes
HTML attributeAttribute-escape and always quote the attribute
JavaScript stringAvoid; pass data as JSON in a data attribute, or use textContent
URL parameterPercent-encode the value
SQLParameterized queries, never string building
ShellAvoid the shell; pass an argument array

§3Let the Framework Do It

Modern template engines and UI frameworks escape output by default. Bugs come from opting out, with escape hatches such as innerHTML, dangerouslySetInnerHTML, v-html, or a template's |safe filter. Treat each one as a code-review flag, and sanitize with a well-maintained HTML sanitizer if you truly must allow rich text.

Encode late, for the destination Don't store "escaped" data and hope it's right everywhere. Store the raw value, and encode at the moment you output it, for the place it's going.

§4Common Mistakes

MistakeWhat HappensFix
Stripping "bad" characters instead of encodingValid input like O'Brien breaks, and tricks still get throughEncode for the context and keep the data intact
Escaping once and reusing the string everywhereThe right escape for HTML is wrong for a URL or JavaScriptEncode at output for each context
Disabling framework auto-escaping for convenienceA direct path to XSSKeep the default, and sanitize with a vetted library when you need rich text
Practice
  1. Write an allow-list validator for a postal code field and test it with five bad inputs.
  2. Find every use of innerHTML or an equivalent escape hatch in a small project and decide whether it can be replaced.
Key takeaways
  • Validate with allow-lists for shape, type, and length.
  • Encode output for each context, because HTML, URL, SQL, and shell all differ.
  • Rely on framework escaping, and review every opt-out.
