Cross-Site Request Forgery (CSRF)

CSRF tricks a logged-in user's browser into sending a request the user never intended, because browsers attach cookies automatically.

§1How CSRF Works

Cookies are sent with every request to their site, no matter which page triggered the request. If you're logged in to a bank and visit a malicious page, that page can make your browser submit a request to the bank, and your session cookie goes along.

<!-- On evil.example, hidden from the user -->
<form action="https://bank.example/transfer" method="POST">
  <input name="to" value="attacker">
  <input name="amount" value="1000">
</form>
<script>document.forms[0].submit()</script>

The attacker can't read the response, but doesn't need to: the damage is the state change.

§2Defenses

  • SameSite cookies: SameSite=Lax (the default in modern browsers) withholds the cookie on most cross-site POSTs. Strict is stronger but can hurt usability. Use it as your first layer.
  • Anti-CSRF tokens: a random, per-session or per-request value included in each state-changing form or header and verified by the server. An attacker's page can't read it.
  • Check Origin or Fetch-Metadata headers to reject cross-site requests.
  • Never change state on GET: GET requests can be triggered by an image tag.

§3CORS Is Not CSRF Protection

A common mix-up from the Networking track's CORS lesson: CORS controls whether a page may read a cross-origin response. A forged form post is a request the browser sends regardless, so CORS doesn't stop it. Use SameSite and tokens.

APIs that authenticate with a bearer token in a header (not a cookie) aren't vulnerable in the same way, because the browser doesn't attach that header automatically.

The one-line test If the browser adds your credentials automatically (cookies, or HTTP auth) and the server acts on the request, CSRF protection is needed. If the credential must be added by your own code, it generally isn't.

§4Common Mistakes

MistakeWhat HappensFix
Changing state with GET requestsAn image tag or link can trigger the actionUse POST, PUT, or DELETE for changes, plus CSRF protection
Relying on CORS to block forged requestsThe request is sent and acted on anywayAdd SameSite cookies and CSRF tokens
A static or guessable CSRF tokenThe attacker supplies it themselvesUse a random token tied to the user session and verify it server-side
Practice
  1. Inspect the Set-Cookie header on a login you control and confirm it has SameSite.
  2. Write the checks a server must perform to validate an anti-CSRF token on a form submission.
Key takeaways
  • CSRF abuses cookies being sent automatically with cross-site requests.
  • Use SameSite cookies and anti-CSRF tokens, and never change state on GET.
  • CORS doesn't prevent CSRF; it only governs reading responses.
