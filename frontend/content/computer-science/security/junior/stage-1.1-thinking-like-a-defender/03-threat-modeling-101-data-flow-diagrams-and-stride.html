Threat Modeling 101: Data-Flow Diagrams & STRIDE

Threat modeling means drawing your system, marking where trust changes, and asking what can go wrong at each point, before an attacker answers for you.

§1Step 1: Draw a Data-Flow Diagram

A data-flow diagram (DFD) shows four things: external actors (users, other systems), processes (your code), data stores (databases, files), and the data flows between them. Draw dashed lines for trust boundaries.

[User] ──login form──▶ (Web app) ──SQL──▶ [[Users DB]]
                           │
 - - - - - - - - - - - - - │ - - - -  trust boundary
                           ▼
                      (Email service)

§2Step 2: Ask What Can Go Wrong, with STRIDE

STRIDE is a checklist of six threat types, each the opposite of a security property.

LetterThreatViolatesExample
SSpoofingAuthenticationLogging in with a stolen session cookie
TTamperingIntegrityEditing a price in a request
RRepudiationAccountability"I never deleted that file," with no log to disprove it
IInformation disclosureConfidentialityAn error page that prints the database password
DDenial of serviceAvailabilityOne request that triggers a huge computation
EElevation of privilegeAuthorizationA normal user calling an admin endpoint

Walk each element and each flow in your diagram and ask which letters apply. A data store can be tampered with or disclosed; a data flow crossing a boundary can be spoofed, tampered with, or read.

§3Step 3: Decide What to Do

For each threat, choose a response: mitigate it (add a control), eliminate it (remove the feature), transfer it (insurance, a vendor), or accept it knowingly. Write the decision down, so the accepted risks are visible choices and not accidents.

Start small A threat model doesn't need special tools: a whiteboard, a boundary, six letters, and thirty minutes with the people who built the system will find more problems than most scanners.

§4Common Mistakes

MistakeWhat HappensFix
Modeling without a diagramDiscussion wanders and obvious flows are missedDraw the data flows first, then enumerate threats against them
Stopping at listing threatsNothing changes in the productAssign each threat a decision and an owner
Modeling once and never againThe model describes a system that no longer existsRevisit when a feature adds a new flow or boundary
Practice
  1. Draw a DFD for a login page backed by a database and an email service, with trust boundaries.
  2. Apply the six STRIDE letters to the flow between the browser and your server, writing one threat per letter.
Key takeaways
  • Draw the system, mark the trust boundaries, then ask what can go wrong.
  • STRIDE gives six prompts: spoofing, tampering, repudiation, disclosure, denial of service, and elevation.
  • Every threat needs a recorded decision: mitigate, eliminate, transfer, or accept.
