Assets, Attackers & Trust Boundaries

Security starts with three questions: what is worth protecting, who might go after it, and where does untrusted data cross into your system.

§1Assets: What Is Worth Protecting

An asset is anything whose loss or misuse would hurt: data, accounts, money, uptime, or reputation. You can't defend everything equally, so naming the assets comes first.

AssetExampleWhat going wrong looks like
User dataEmails, addresses, messagesLeak, and legal and trust damage
CredentialsPasswords, API keys, session tokensAccount takeover, and attackers acting as users
Money and goodsPayments, coupons, inventoryFraud and direct financial loss
AvailabilityThe site being upOutage, lost revenue, missed deadlines
Code and infrastructureSource, build servers, cloud accountsA foothold for attacking everything else

§2Attackers: Who, and With What

An attacker is defined by capability (what they can do), access (where they start), and motive (why they bother). Different attackers need different defenses.

  • Opportunists run automated scans for known bugs and weak passwords. They are the most common and the easiest to stop.
  • Malicious users have a legitimate account and abuse it: changing an ID in a URL, replaying a coupon, uploading a hostile file.
  • Insiders already hold privileges, such as an employee or contractor, and can misuse them.
  • Targeted attackers pick you specifically and are patient, well-resourced, and willing to chain several small flaws.

§3Trust Boundaries: Where Data Changes Hands

A trust boundary is a line where data moves between components with different levels of trust. Bugs cluster at these lines, because code on the inside often assumes data from the outside is well formed.

Browser  ──(boundary 1)──▶  Web server  ──(boundary 2)──▶  Database
                                  │
                                  └──(boundary 3)──▶  Third-party API

# Boundary 1: everything from the browser is attacker-controlled
# Boundary 2: the server must not pass raw input into queries
# Boundary 3: responses from outside are input too

Anything that arrives from the user's side of a boundary, including form fields, headers, cookies, and uploaded files, must be treated as hostile until checked.

The key insight Security is always relative to a specific asset and a specific attacker. "Is this secure?" has no answer until you say secure against whom, protecting what.

§4Common Mistakes

MistakeWhat HappensFix
Defending against an imaginary attackerEffort goes to exotic threats while a missing password rule goes unfixedList real attackers and start with the most likely
Trusting the browser's checksClient-side validation is bypassed with a single edited requestRe-check everything on the server, where the attacker can't edit the code
Treating internal traffic as trustedOne compromised service reaches everythingTreat each service boundary as a trust boundary
Practice
  1. List five assets for a note-taking app and rank them by how much a loss would hurt.
  2. Pick any web app you use, draw its main components, and mark every trust boundary.
  3. For one asset, describe an opportunist, a malicious user, and an insider, and what each could realistically do.
Key takeaways
  • Name the assets before choosing defenses.
  • Attackers differ in capability, access, and motive, and so do the defenses that stop them.
  • Bugs cluster at trust boundaries, where outside data enters inside code.
