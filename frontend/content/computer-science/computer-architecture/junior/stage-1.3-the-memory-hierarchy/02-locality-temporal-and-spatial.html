Locality: Temporal & Spatial

Caches only work because programs tend to reuse data they've just used and to touch data near it, and writing code that keeps those habits is the main lever you control.

§1Two Kinds of Locality

  • Temporal locality: a location that was just accessed is likely to be accessed again soon, such as a loop counter or a running total
  • Spatial locality: locations near a recently accessed one are likely to be accessed soon, such as consecutive array elements

Hardware exploits both. Temporal locality is why caches *keep* recently used data, and spatial locality is why caches fetch a whole line (typically 64 bytes) at once. Instructions have locality too: a loop re-executes the same few instructions, so the instruction cache hits almost always.

§2Row-Major vs. Column-Major Traversal

C stores a 2D array row by row: a[0][0], a[0][1], ..., a[0][N-1], a[1][0], .... Walking along a row touches consecutive addresses, while walking down a column jumps a whole row each step.

#define N 4096
static float a[N][N];

float sum_rows(void) {              // good spatial locality: stride 4 bytes
    float s = 0;
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            s += a[i][j];
    return s;
}

float sum_cols(void) {              // poor: stride N*4 = 16 KiB per access
    float s = 0;
    for (int j = 0; j < N; j++)
        for (int i = 0; i < N; i++)
            s += a[i][j];
    return s;
}

Both functions do identical arithmetic. On typical hardware, the column-order version is several times slower for a large array, because almost every access lands on a different cache line that has been evicted before the loop returns to it. Swapping the loops, called loop interchange, fixes it.

§3The Working Set

The working set is the data a program touches over some period. If it fits in a cache level, access is fast; if it spills, the next, slower level serves the overflow. Performance often degrades in steps as the working set outgrows L1, then L2, then L3, then DRAM.

# Rule of thumb for a traversal: cost per access depends on where the working set fits
working set < L1 (32 KiB)    -> about 1 ns per access
working set < L2 (1 MiB)     -> a few ns
working set < L3 (30 MiB)    -> about 10-20 ns
working set > L3             -> DRAM speed, 60-100 ns when accesses are not sequential

Sequential access stays fast even for a huge working set, because the hardware prefetches ahead. Random access over a large working set is the worst case.

The key insight The same loops in a different order can differ in speed by several times, without changing a single arithmetic operation. Access pattern is a first-class performance property.

§4Common Mistakes

MistakeWhat HappensFix
Iterating a C 2D array column by columnLarge strides cause a miss on almost every accessMake the innermost loop run along the contiguous dimension
Using linked structures when an array would doPointer chasing destroys spatial localityPrefer contiguous arrays for hot data
Testing performance only on small inputsSmall data fits in cache and hides the problemTest with working sets larger than the last-level cache
Practice
  1. Time sum_rows and sum_cols for N = 512, 2048, and 8192. At which size does the gap open up, and why?
  2. Name the temporal and spatial locality in a loop that sums an array into a single variable.
Key takeaways
  • Temporal locality reuses recent data; spatial locality uses nearby data.
  • Caches fetch whole lines to exploit spatial locality, and keep recent lines to exploit temporal locality.
  • Loop order and access stride can change speed several-fold with the same arithmetic.
