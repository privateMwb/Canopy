Floating Point & Its Surprises

Floating-point numbers store a sign, an exponent, and a fraction, which gives huge range at the price of rounding, and explains why 0.1 + 0.2 is not exactly 0.3.

§1The IEEE 754 Layout

A floating-point number is scientific notation in binary: ±1.fraction × 2^exponent. IEEE 754 defines the standard layouts.

FormatSignExponentFractionDecimal precision
binary32 (float)1 bit8 bits (bias 127)23 bitsAbout 7 digits
binary64 (double)1 bit11 bits (bias 1023)52 bitsAbout 15–16 digits
value = (-1)^sign * 1.fraction * 2^(exponent - bias)

1.0   = 0 01111111 00000000000000000000000  = 0x3F800000
0.5   = 0 01111110 00000000000000000000000  = 0x3F000000
-2.0  = 1 10000000 00000000000000000000000  = 0xC0000000

The leading 1 before the fraction is implied and not stored, which buys one extra bit of precision. The exponent is stored with a bias, so the all-zeros pattern doesn't mean a tiny number.

§2Rounding and Surprises

Most decimal fractions can't be written exactly in binary, just as 1/3 can't be written exactly in decimal. The value 0.1 becomes a repeating binary fraction that is rounded to the nearest representable number.

0.1 + 0.2               # 0.30000000000000004 in Python (a double)
0.1 + 0.2 == 0.3        # False

# Large numbers lose the small ones: a float has only 24 bits of precision
16777216.0 + 1.0        # as float32: 16777216.0, the +1 vanishes

# Order matters: floating-point addition is not associative
(1e16 + 1.0) + -1e16    # 0.0
1e16 + (1.0 + -1e16)    # 1.0 or 0.0 depending on rounding; results can differ

Never compare floating-point values with ==. Compare with a tolerance, such as abs(a - b) <= 1e-9 * max(abs(a), abs(b)).

§3Special Values and Safe Habits

  • Infinity: dividing a nonzero value by zero gives ±∞, and overflow produces ∞
  • NaN (not a number): results like 0/0 or ∞ − ∞. NaN compares unequal to everything, including itself, so x != x detects it
  • Subnormals: tiny numbers near zero with reduced precision, which some CPUs process much more slowly
  • Negative zero: −0.0 exists and compares equal to 0.0

For money, don't use binary floating point. Use integers (cents) or a decimal type. For sums of many values, sort or use compensated (Kahan) summation, since errors accumulate. These rules aren't quirks of one language; they follow from the hardware format that every modern CPU implements.

The key insight A double isn't a real number; it's the nearest of about 2^64 representable values. Think of each result as slightly rounded, and design comparisons and accumulations with that in mind.

§4Common Mistakes

MistakeWhat HappensFix
Comparing floats with ==Equality fails for values that should matchCompare within a relative or absolute tolerance
Using floating point for currencyCents drift and totals don't balanceUse integer cents or a decimal type
Summing a huge array in one pass of single precisionSmall values are lost, and results differ by orderUse double, pairwise or Kahan summation
Practice
  1. Print 0.1 + 0.2 and 0.1 + 0.2 == 0.3 in your language. Then print the double's exact value, for example with Decimal(0.1) in Python.
  2. Decode the 32-bit pattern 0x40490FDB as a float by hand, identifying sign, exponent, and fraction. (Hint: it is close to π.)
Key takeaways
  • Floats store sign, biased exponent, and fraction: 32 bits for float, 64 for double.
  • Most decimal fractions are rounded, so equality tests and long sums need care.
  • NaN is unequal to itself, and floating-point addition isn't associative.
