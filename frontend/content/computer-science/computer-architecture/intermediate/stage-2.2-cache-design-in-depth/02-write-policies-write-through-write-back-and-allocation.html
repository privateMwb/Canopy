Write Policies: Write-Through, Write-Back & Allocation

Reads are easy to cache, but a write forces a choice about when to update the next level, and that choice determines how much memory traffic a program creates.

§1Write-Through vs. Write-Back

When the CPU stores to an address that is in the cache, the cache must decide what to do about the copy below it.

PolicyBehaviorProsCons
Write-throughUpdate the cache and the next level on every storeSimple, memory always up to dateA lot of write traffic
Write-backUpdate only the cache and mark the line dirty; write it out when evictedFar less trafficMore complex; the cache holds the only up-to-date copy

With write-back, a line written 100 times causes one write to the next level, when it's evicted, rather than 100. The dirty bit records which lines need writing out. Most CPU data caches at L1 and below use write-back, while a write-through L1 is sometimes paired with a write-back L2.

§2What Happens on a Write Miss

If the target line isn't in the cache, there are two choices.

  • Write-allocate: fetch the line into the cache, then perform the write. Good if the data will be accessed again soon (the usual choice with write-back)
  • No-write-allocate: send the write straight to the next level and don't cache it. Good for data that is only written once, such as streaming output

Write-allocate has a hidden cost: a store to a line not in the cache first reads the whole line from memory, even if the program will overwrite every byte. A program that fills a huge buffer therefore generates both reads and writes.

§3Write Buffers and Streaming Stores

To keep the CPU from stalling on slow writes, caches use a write buffer, a small queue of pending stores that drain in the background.

// A large one-time fill: normal stores read each line, then write it back later.
for (size_t i = 0; i < N; i++) out[i] = compute(i);

// x86 non-temporal (streaming) stores skip the cache and avoid the read-for-ownership.
#include <immintrin.h>
_mm_stream_si32((int *)&out[i], value);    // write directly to memory, bypassing the caches
_mm_sfence();                              // make the streamed stores visible in order
  • Streaming stores help when you write a large block you won't read soon, since they skip the read half of the traffic and can cut it by up to half
  • They hurt if you do read the data soon, because it is not in the cache
  • Compilers and memcpy implementations choose them automatically for big copies
perf stat -e L1-dcache-stores,L1-dcache-store-misses,LLC-store-misses ./prog
The key insight Stores aren't free. Under write-back with write-allocate, a store miss costs a read of the line, and every dirty line eventually costs a write. Memory bandwidth for writes can be double what the program's writes alone suggest.

§4Common Mistakes

MistakeWhat HappensFix
Counting only reads in a bandwidth estimateWrite-allocate adds reads, and write-back adds writebacksCount both directions of traffic
Using normal stores for huge, write-once buffersExtra read traffic and cache pollutionConsider streaming stores for large write-only fills
Using streaming stores on data read immediately afterThe data bypassed the cache, so the reads missUse them only for write-only or far-future-read data
Practice
  1. A line is written 50 times, then evicted. How many writes reach the next level under write-through and write-back?
  2. Explain why filling a 1 GiB array with zeros can move about 2 GiB of data on a write-allocate cache.
Key takeaways
  • Write-through updates the next level on every store; write-back defers it using a dirty bit.
  • Write-allocate fetches the line on a write miss, adding read traffic.
  • Streaming stores skip the cache for large write-only data, but hurt if the data is read soon.
