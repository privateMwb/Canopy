Address Translation Hardware: TLBs & Page Walks

Every memory access starts with a virtual address, and the hardware that translates it, the TLB and the page walker, adds a hidden cost that large working sets expose.

§1The TLB

From the OS course: virtual addresses are translated to physical ones through page tables. Walking those tables on every access would multiply memory traffic, so the CPU caches recent translations in the translation lookaside buffer (TLB).

StructureTypical sizeCovers (4 KiB pages)
L1 data TLBAbout 64 entriesAbout 256 KiB
L2 (shared) TLBAbout 1,500–2,000 entriesAbout 6–8 MiB
Page-walk cachesSmall caches of upper page-table levelsSpeeds up walks

A TLB hit adds almost nothing. A miss triggers a page walk, performed by dedicated hardware on x86 and ARM, that follows up to four levels of page tables (five with larger address spaces). Each level is a memory reference, though the walker caches upper levels and the entries often sit in the L2 or L3 caches, so a typical walk costs tens of cycles. If the page-table entries themselves miss to DRAM, it can cost hundreds.

§2Translation and the L1 Cache

To keep L1 hits fast, caches must start looking up data in parallel with translation. A virtually indexed, physically tagged (VIPT) L1 uses address bits that don't change under translation, the page offset, for the index, so lookup and translation overlap. The constraint is that the index and offset bits must fit inside the page offset:

L1 size = ways * page size

x86:  8 ways * 4 KiB pages = 32 KiB      # why L1 caches stayed at 32-48 KiB for years
# A 128 KiB L1 with 16 KiB pages is 8 ways * 16 KiB. Larger pages allow larger fast L1 caches.

This is a good example of hardware parts constraining each other: the page size, cache associativity, and L1 capacity are tied together.

§3When the TLB Becomes the Bottleneck

  • Large, sparse working sets, such as random access over many gigabytes, touch more pages than the TLB covers, so many accesses miss it
  • Huge pages (2 MiB or 1 GiB) multiply reach: 1,536 entries × 2 MiB covers 3 GiB. The OS course covers how to enable them
  • Context switches can flush TLB entries unless tagged with address-space IDs (PCID on x86)
  • Virtualization makes walks costlier, since guest and host tables are both walked (nested paging)
perf stat -e dTLB-loads,dTLB-load-misses,iTLB-load-misses ./prog
# A high ratio of dTLB misses with a large working set suggests trying huge pages.
grep -i huge /proc/meminfo

A useful sanity check is TLB reach versus working set. If a program's hot data spans far more pages than the TLB can hold, expect translation overhead, even when the data would fit in the cache.

Connection to earlier lessons This is the hardware view of paging from the Operating Systems category. The OS builds the tables, and the TLB and page walker are the hardware that makes using them fast enough to leave on all the time.

§4Common Mistakes

MistakeWhat HappensFix
Ignoring TLB misses in large random-access programsCache hit rates look fine, yet performance is poorCheck dTLB-load-misses and consider huge pages
Assuming a cache hit also avoids translationEvery access, even an L1 hit, needs a translationRemember the TLB sits on the path of every memory access
Enabling huge pages without measuringMemory bloat and compaction stalls can offset gainsTest on the real workload, and keep it optional per-process
Practice
  1. Compute the TLB reach of a 1,024-entry TLB with 4 KiB pages and with 2 MiB pages.
  2. Use perf stat to compare TLB misses for sequential versus random access over 4 GiB, and explain the difference.
Key takeaways
  • The TLB caches translations; a miss triggers a hardware page walk of up to four or five levels.
  • VIPT L1 caches tie L1 size to ways times page size.
  • Huge pages, PCID, and reducing page spread all reduce translation cost.
