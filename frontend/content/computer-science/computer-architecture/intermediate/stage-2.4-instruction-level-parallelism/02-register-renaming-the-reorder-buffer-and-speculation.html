Register Renaming, the Reorder Buffer & Speculation

Several hardware tricks let an out-of-order core run ahead of the program while staying correct: renaming removes false dependencies, the reorder buffer keeps order, and speculation guesses past branches.

§1Register Renaming

Programs reuse register names, which creates false dependencies: two instructions that don't share a value still appear to conflict because both write the same register name.

1: mul x1, x2, x3
2: add x4, x1, x5     # true dependency on 1 (reads x1)
3: mov x1, x6         # writes x1 again: unrelated value, but reuses the name
4: sub x7, x1, x8     # reads the x1 written by 3, not by 1

Without renaming, instruction 3 must wait for instruction 2 to read x1. The CPU solves this by mapping each architectural register (the 32 or 16 the ISA names) onto a larger pool of physical registers, often well over a hundred. Every write is given a fresh physical register, so instruction 1 writes p10, instruction 3 writes p11, and the two chains no longer interfere.

§2The Reorder Buffer

Executing out of order requires a way to commit results in order. The reorder buffer (ROB) is a queue holding every in-flight instruction in program order, from allocation until retirement.

  1. An instruction is allocated a ROB slot and a renamed destination in program order
  2. It waits in a scheduler until its operands are ready, then executes on a free unit, possibly out of order
  3. Its result is recorded, marking the ROB entry as complete
  4. The oldest entries retire in order, making their results architecturally visible

Recent cores have ROBs of roughly 200 to 600 entries, which sets how far ahead the core can look. A long-latency load at the head of the ROB eventually fills it, and then the core stalls, which is why very long misses still hurt. In-order retirement also gives precise exceptions: when a fault occurs, every earlier instruction has completed and no later one has changed state.

§3Speculation

The core doesn't wait for branches to resolve. It follows the predicted path, executing instructions speculatively, with their results held in the ROB and store buffer rather than committed.

  • Correct prediction: the speculative instructions retire normally, and the branch cost nothing
  • Misprediction: all younger instructions are squashed, the rename map is restored to its state at the branch, and fetch restarts at the right address, which costs the 15 to 20 cycles seen earlier
  • Memory speculation: loads may run before earlier stores have computed their addresses, with a check that catches the cases where they should have waited
perf stat -e instructions,uops_issued.any,uops_retired.retire_slots ./prog
# (Intel event names; issued minus retired uops approximates work thrown away by speculation.)

Speculation is a large part of why modern cores are fast, and also, as a later stage covers, the source of a class of security vulnerabilities, since squashed instructions can still leave traces in the caches.

The key insight Out-of-order execution is a bookkeeping system: rename to remove false dependencies, schedule by readiness, and retire in order to preserve correct program semantics. Speculation is the same machinery used with a bet on a branch.

§4Common Mistakes

MistakeWhat HappensFix
Believing an out-of-order core changes program resultsRetirement is in order, so semantics are preservedKeep program-order reasoning for correctness, and use the model for performance
Assuming the window is unlimitedThe ROB size bounds how far ahead it can lookLong stalls fill the ROB; reduce miss latency or overlap misses
Forgetting that wrong-path work still uses resourcesMispredictions waste power and cache bandwidthKeep branches predictable on hot paths
Practice
  1. Rename the registers in a short instruction sequence with false dependencies, mapping each write to a fresh physical register.
  2. Explain how the reorder buffer lets a CPU report a page fault precisely, even though instructions executed out of order.
Key takeaways
  • Renaming maps architectural registers to a larger physical pool, removing false dependencies.
  • The reorder buffer holds in-flight instructions and retires them in order for precise state.
  • Speculation executes past unresolved branches and squashes the wrong path on a misprediction.
