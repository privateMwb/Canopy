Side Channels: Caches, Timing & Rowhammer

Whenever two programs share hardware, how long an operation takes can leak information about what the other one did, and flipping bits in DRAM shows that even memory isolation can be bypassed physically.

§1Timing Reveals Cache State

A side channel leaks information through a physical or timing effect rather than through the program's intended output. The most studied one is cache timing. An access that hits in the cache is much faster than one that misses, so an observer who can measure time precisely can tell whether a given line was recently touched.

  • Shared lines: when attacker and victim share memory, such as a shared library, the attacker can evict a line and later check whether the victim brought it back, which reveals that the victim accessed it (the *flush-and-reload* idea)
  • Shared sets: without shared memory, the attacker fills cache sets with its own data and later checks which of its lines the victim evicted (the *prime-and-probe* idea)

Cryptographic code was the first major target: if the table lookups in an encryption routine depend on key bytes, the pattern of cache accesses reveals the key. That's why modern CPUs provide dedicated instructions (AES-NI) and why crypto libraries are written to be constant-time.

§2Other Shared Resources

Hyper-threading (SMT) is a particular concern because the two threads of a core share almost everything, including L1 caches and execution units, so a co-resident hostile thread sees very fine-grained effects.

§3Rowhammer: A Physical Attack

DRAM rows are packed so closely that repeatedly activating one row can disturb charge in the neighboring rows, flipping bits there. This Rowhammer effect, reported in 2014, means a program that can only read and write its own memory may corrupt memory it doesn't own, and researchers have used it to escalate privileges.

  • Mitigations: error-correcting (ECC) memory catches some flips, higher refresh rates reduce the window, and target row refresh (TRR) in newer DRAM refreshes neighbors of heavily activated rows
  • Limits of mitigation: later research showed ways to bypass TRR implementations, so the defenses are partial
  • Software side: isolating untrusted workloads and limiting access to precise timers and cache-flush instructions reduce risk

Rowhammer is a reminder that memory protection built on page tables assumes the memory cells behave ideally, and that physical reality can break the assumption.

§4Defensive Habits

  • Constant-time code for secrets: no secret-dependent branches or memory indices
  • Reduce timer precision where untrusted code runs, as browsers did, because attacks need fine timing
  • Isolate by process and by core: keep mutually distrusting code from sharing a core, a cache, or an address space
  • Use hardware crypto instructions and vetted libraries rather than writing your own

Software can't observe most microarchitectural state, so these channels are invisible to ordinary debugging, and reasoning about the threat model is the main defense.

The key insight Isolation at the ISA level doesn't imply isolation at the timing level. Anything two programs share, a cache set, a predictor entry, a DRAM row, is a potential channel.

  1. Explain in a few sentences how a cache-timing observer can learn whether a victim accessed a specific cache line.

Key takeaways
  • Cache, predictor, TLB, port, and DRAM-row behavior can leak information through timing.
  • Rowhammer shows physical effects can corrupt memory despite software isolation.
  • Defend with constant-time code, timer limits, process and core isolation, and hardware crypto.
