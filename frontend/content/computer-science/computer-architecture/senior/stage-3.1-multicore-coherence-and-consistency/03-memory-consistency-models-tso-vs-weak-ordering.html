Memory Consistency Models: TSO vs. Weak Ordering

Coherence orders accesses to one location, but a consistency model says how accesses to different locations may appear reordered to other cores, and x86 and ARM make different promises.

§1Sequential Consistency and Why Hardware Breaks It

The most intuitive model is sequential consistency (SC): all memory operations appear to execute in some single order that respects each thread's program order. Real hardware doesn't provide it, because it would forbid important optimizations. The main culprit is the store buffer: a core places stores in a small queue and continues, so its own later loads can execute before the store becomes visible to others.

// Store-buffering litmus test. Initially x = 0, y = 0.
Thread 0:            Thread 1:
  x = 1;               y = 1;
  r1 = y;              r2 = x;

// SC forbids r1 == 0 and r2 == 0 at the same time.
// x86 allows it: each store sits in its core's store buffer while the later load runs.

It really does happen, and a test run millions of times on a multicore x86 machine will show the 'impossible' outcome.

§2Two Families of Models

ReorderingSCx86 (TSO)ARM, RISC-V (weak)
Load → LoadNot allowedNot allowedAllowed
Load → StoreNot allowedNot allowedAllowed
Store → StoreNot allowedNot allowedAllowed
Store → LoadNot allowedAllowedAllowed

x86-TSO (total store order) is strong: only a store followed by a load to a different address may reorder. ARM and RISC-V's RVWMO are weak: unless an instruction creates an ordering, almost any reordering is allowed, subject to data dependencies. Weaker models give hardware more freedom to optimize and more power efficiency, and place more burden on programmers and compilers.

// Message passing. Initially data = 0, flag = 0.
Thread 0:            Thread 1:
  data = 42;           while (flag == 0) ;
  flag = 1;            r = data;

// Forbidden outcome: flag seen as 1 but r == 0.
// x86: cannot happen (stores stay ordered, loads stay ordered).
// ARM/RISC-V without barriers: CAN happen, the stores or the loads may reorder.

§3Fences and Acquire/Release

To restore order where needed, programs use fences (barriers) or instructions with built-in ordering.

Release storeOrdinary storestlrStore after fence rw,w

The C11 and C++ memory orders from the OS course (memory_order_acquire, release, seq_cst) are mapped by the compiler onto exactly these instructions. That's why correct acquire/release code costs nothing on x86 for the acquire and release, and generates real barrier or ordered instructions on ARM.

# Observe weak-memory behavior directly with the herd7 / litmus7 tools, or write your own litmus test
# harness with two threads and a barrier, then run it millions of times on x86 and on ARM.

Code that works on x86 may break when ported to ARM purely because of ordering, as many lock-free bugs have shown.

The key insight A memory model is a contract between hardware, compiler, and programmer about what orderings are guaranteed. Anything the contract doesn't promise, the hardware is free to reorder, and it will, sooner or later.

§4Common Mistakes

MistakeWhat HappensFix
Testing concurrent code only on x86Weak-memory bugs stay hiddenTest on ARM too, and use the language's atomics with proper orderings
Using plain variables as flags between threadsNo ordering or visibility guaranteesUse atomics with acquire/release
Over-fencing everything with full barriersUnnecessary cost on weak machinesUse the weakest ordering that is correct, once you have proven it
Practice
  1. Write the store-buffering litmus test in C with two threads, run it many times on your machine, and count how often r1 = r2 = 0 occurs.
  2. Explain why message passing needs no explicit barrier on x86 but does on ARM.
Key takeaways
  • SC is intuitive, but store buffers and other optimizations mean real CPUs reorder some operations.
  • x86-TSO allows only store-then-load reordering, while ARM and RISC-V allow nearly all reordering without fences.
  • Acquire/release and fences map onto specific instructions, and weak machines expose ordering bugs.
