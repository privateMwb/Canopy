Top-Down Microarchitecture Analysis

Top-down analysis answers 'why is this program slow?' by classifying every pipeline slot as useful work or as one of a few kinds of loss, then drilling into the biggest loss.

§1Pipeline Slots and Four Categories

A core with issue width W has W slots in each cycle in which it could deliver a micro-op. The top-down method classifies every slot into one of four buckets.

CategoryMeaningTypical cause
RetiringThe slot produced a micro-op that completedUseful work (the ideal)
Bad speculationThe slot's work was thrown away, or time was lost recoveringBranch mispredictions, other pipeline flushes
Frontend boundThe front end couldn't deliver micro-ops, though the back end could take themInstruction-cache misses, decode limits, large code
Backend boundThe back end couldn't accept new micro-opsWaiting on data or execution units

The percentages sum to 100%. A program with 70% backend bound has most of its slots lost to waiting, and the other 30% together can't account for a large win, so the next step is clear.

§2Drilling Down

Each category splits into sub-categories, so you go deeper only where the numbers are large.

Backend bound
 ├─ Memory bound   (stalls waiting on loads and stores)
 │    ├─ L1 bound / L2 bound / L3 bound
 │    ├─ DRAM bound   (latency and bandwidth)
 │    └─ Store bound
 └─ Core bound     (execution-unit pressure, long dependency chains, division)
Frontend bound:  fetch latency (i-cache or ITLB misses)  vs.  fetch bandwidth (decode)
Bad speculation: branch mispredicts  vs.  machine clears (such as memory-ordering flushes)

On Intel CPUs and recent AMD and ARM cores, perf can compute these from hardware counters. Support depends on the CPU and perf version, and the counters are often unavailable inside virtual machines.

perf stat -M TopdownL1 ./prog            # level 1: retiring / bad spec / frontend / backend
perf stat --topdown -a -- sleep 5         # system-wide, on supporting Intel CPUs
toplev.py -l2 ./prog                      # pmu-tools: deeper levels and plain-language hints

Typical output reads like a diagnosis:

Retiring 22%   Bad speculation 3%   Frontend bound 5%   Backend bound 70%
  -> Memory bound 58%  (DRAM bound 41%, L3 bound 12%)   Core bound 12%
# Interpretation: the program is dominated by DRAM waits. Fix locality, layout, or prefetching.

§3A Disciplined Method

  1. Measure level 1 on a representative run
  2. Pick the largest non-retiring category and drill into only that
  3. Form a hypothesis that explains the numbers, for example 'the hash table lookups miss to DRAM'
  4. Change one thing that tests it, such as a more compact layout or batched lookups
  5. Re-measure both the counters and the wall-clock time, and repeat

Don't optimize a category that is small. A program with 4% bad speculation won't benefit from branch tuning, however clever it is. And judge by time first: a counter that improved while the wall-clock time did not is not progress.

High retiring isn't a guarantee of efficiency. It can mean the core is busy doing a lot of unnecessary work. In that case, the answer is fewer instructions: a better algorithm, vectorization, or removing redundant computation.

The key insight Top-down turns a mass of counters into a decision tree. It tells you which of front end, speculation, memory, or core is leaking cycles, so you work on the biggest leak first.

§4Common Mistakes

MistakeWhat HappensFix
Chasing a small categoryLittle to gain even if fixed completelyAlways start with the largest non-retiring bucket
Trusting counters over timeA counter can improve while the program gets no fasterConfirm every change with wall-clock measurements
Running the analysis on a toy inputBehavior differs from production dataUse realistic inputs and sizes
Practice
  1. Run perf stat -M TopdownL1 (or toplev) on two programs, one that streams a large array and one that does heavy computation on a small one, and compare the breakdowns.
  2. Given Retiring 35%, Bad speculation 25%, Frontend 10%, Backend 30%, which bucket do you investigate first and what would you look for?
Key takeaways
  • Top-down classifies slots into retiring, bad speculation, frontend bound, and backend bound.
  • Drill into the largest loss only, such as memory-bound split into L1, L2, L3, and DRAM.
  • Change one thing at a time, and confirm with wall-clock time.
