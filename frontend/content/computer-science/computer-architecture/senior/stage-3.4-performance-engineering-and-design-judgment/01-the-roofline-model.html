The Roofline Model

One simple chart tells you whether a program is limited by arithmetic or by memory bandwidth, and how much headroom remains before it hits the hardware's limit.

§1The Model

The roofline model bounds a kernel's attainable performance using two machine limits and one property of the kernel.

attainable GFLOP/s = min( peak compute ,  peak bandwidth * arithmetic intensity )

arithmetic intensity (AI) = FLOPs performed / bytes moved to and from DRAM

# Machine: 500 GFLOP/s peak compute, 50 GB/s DRAM bandwidth
# Ridge point = 500 / 50 = 10 FLOP/byte
#   AI < 10: memory-bound (on the sloped part of the roof)
#   AI > 10: compute-bound (on the flat part)

Plot AI on the x-axis (log scale) against performance on the y-axis. The roof rises with a slope equal to the bandwidth, then flattens at peak compute. A kernel's measured point sits somewhere below the roof, and the gap shows how far it is from the limit.

Notice how far below the 500 GFLOP/s peak most simple kernels are limited: a vector add can use under 1% of the machine's arithmetic capability, since it is waiting on memory. Reaching a high roof needs data reuse, which is what blocking and tiling provide.

§3Using the Model to Choose What to Do

  • Left of the ridge (memory-bound): reduce bytes moved. Fuse loops to avoid writing and re-reading intermediates, use smaller types (float instead of double), compress, tile for reuse, and improve locality. Vectorizing or adding FMA won't help, because the arithmetic units aren't the limit
  • Right of the ridge (compute-bound): use more arithmetic throughput: SIMD, FMA instructions, multiple cores, and better instruction mix
  • Far below the roof: something else is wrong, such as poor prefetching, dependency chains, branch misses, or too little parallelism, so look at counters
  • Add ceilings: scalar, SIMD, and FMA compute limits, and L1, L2, and L3 bandwidth limits, show which one a specific kernel is hitting

To place a kernel, you need its measured performance and its DRAM traffic. Count FLOPs from the algorithm or counters, and estimate traffic from last-level-cache misses times 64 bytes, or from memory-controller counters. Tools such as Intel Advisor, likwid-perfctr, and, for GPUs, NVIDIA Nsight Compute produce roofline plots.

# Rough DRAM traffic from counters (event names vary by CPU):
perf stat -e LLC-load-misses,LLC-store-misses ./prog
# bytes ~= (load misses + store misses) * 64
The key insight Before optimizing, find which ceiling you are under. Vectorizing a memory-bound kernel and reducing traffic in a compute-bound one are both wasted effort.

Practice
  1. For a machine with 1 TFLOP/s and 100 GB/s, compute the ridge point, and decide whether y[i] = a * x[i] + y[i] (double) is memory- or compute-bound.
  2. Estimate the arithmetic intensity of a 3-point stencil b[i] = a[i-1] + a[i] + a[i+1] with ideal cache reuse of neighbors.
Key takeaways
  • Attainable performance = min(peak compute, bandwidth × arithmetic intensity).
  • Low-intensity kernels like vector add and sparse matrix-vector are memory-bound; reuse raises intensity.
  • Use the roofline to decide whether to cut bytes or raise arithmetic throughput.
