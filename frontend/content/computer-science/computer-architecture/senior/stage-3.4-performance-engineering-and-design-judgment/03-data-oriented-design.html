Data-Oriented Design

Designing data structures around how the hardware reads memory, rather than around how objects are named, can speed up memory-bound code several-fold without changing the algorithm.

§1Array of Structs vs. Struct of Arrays

The natural object-oriented layout puts all of one object's fields together, an array of structs (AoS). When a hot loop uses only a few fields, every cache line also drags in fields it doesn't need.

struct Particle {                 // 64 bytes: exactly one cache line
    float x, y, z;                // position (12 B)
    float vx, vy, vz;             // velocity (12 B)
    float mass;  int id;          // 8 B
    char  name[32];               // 32 B, never touched by the update loop
};
struct Particle p[N];
for (i = 0; i < N; i++) { p[i].x += p[i].vx * dt; ... }     // uses 24 of every 64 bytes: 37.5%

The struct of arrays (SoA) alternative stores each field in its own contiguous array.

struct Particles {
    float *x, *y, *z, *vx, *vy, *vz;      // the hot fields, each contiguous
    float *mass; int *id; char (*name)[32];   // cold fields, stored separately
};
for (i = 0; i < N; i++) {
    P.x[i] += P.vx[i] * dt;               // every byte loaded is used; also SIMD-friendly
    P.y[i] += P.vy[i] * dt;
    P.z[i] += P.vz[i] * dt;
}

Now every loaded cache line is fully used, the hardware prefetcher sees clean sequential streams, and the compiler can vectorize each loop. When the loop is memory-bound, this commonly gives a speedup of several times, roughly the ratio of bytes the loop needs to bytes it used to drag in.

§2Choosing a Layout

LayoutGood forWeakness
AoSAccessing all fields of one object together; random access to whole objectsWastes bandwidth when a loop uses few fields
SoALoops over one or few fields across many objects; SIMDGathering one whole object touches several arrays
AoSoA (blocks of, say, 8 objects with fields grouped within a block)SIMD-width vectors with good locality for whole-object accessMore complex indexing

The right layout depends on the access pattern, which is why the guideline is 'design for the data's most frequent use', and why you should measure the loops that matter.

§3Other Data-Oriented Habits

  • Hot/cold splitting: keep rarely used fields out of the hot structure
  • Indices instead of pointers: a 32-bit index into an array is half the size of a 64-bit pointer and keeps related data contiguous
  • Process by type and in batches: handling all objects of one kind together avoids per-object branches and indirect calls, and keeps the predictor and instruction cache warm
  • Use the smallest adequate types: uint8_t flags or 16-bit values pack more per cache line
  • Allocate in arenas and pools: objects allocated together sit together, unlike scattered individual allocations
  • Avoid pointer chasing in hot paths: replace linked lists and trees of small nodes with arrays or flattened structures where you can

These ideas are the basis of entity-component systems in games and of columnar storage in analytic databases, which are the same principle applied at different scales: store together what is processed together.

The key insight Memory-bound code is limited by the bytes it moves. Layout is how you decide which bytes those are, and it is usually the cheapest large win available.

§4Common Mistakes

MistakeWhat HappensFix
Putting all fields in one struct by habitHot loops pay for fields they never readSplit hot and cold, or use SoA for hot loops
Switching to SoA everywhereWhole-object access becomes scatteredMatch the layout to each access pattern
Using 64-bit pointers between small objectsDoubles the footprint of linked structuresUse compact indices into arrays
Practice
  1. Write AoS and SoA versions of the particle update, and time them for N = 10 million. Use perf stat to compare cache misses.
  2. Redesign a struct with 12 fields, of which a hot loop uses 3, into a hot/cold split, and estimate the bytes per iteration before and after.
Key takeaways
  • AoS loads unused fields into cache; SoA keeps hot fields contiguous and SIMD-friendly.
  • Pick the layout from the access pattern, with AoSoA as a compromise.
  • Hot/cold splitting, indices, batching, small types, and arenas all shrink and organize memory traffic.
