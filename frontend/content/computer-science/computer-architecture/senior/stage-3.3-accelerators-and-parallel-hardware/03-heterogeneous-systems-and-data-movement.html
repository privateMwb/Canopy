Heterogeneous Systems & Data Movement

An accelerator may be 50 times faster at the computation, and still lose overall if getting the data to it takes longer than the work saves.

§1Separate Memories and the Bus Between Them

A discrete GPU has its own memory, and data must cross the PCIe link from the host. That link is far slower than the GPU's own memory.

LinkApproximate bandwidth (each direction)
PCIe 4.0 x16About 31 GB/s peak, around 25 GB/s in practice
PCIe 5.0 x16About 63 GB/s peak
GPU HBM memory1 to 3+ TB/s on datacenter GPUs
NVLink or similar GPU interconnectHundreds of GB/s

The gap, tens of GB/s over PCIe against terabytes per second inside the GPU, means data that crosses the link must be used heavily to be worth the trip.

§2The Break-Even Calculation

Total time on the GPU is the sum of copying in, computing, and copying out.

T_gpu = T_copy_in + T_kernel + T_copy_out

# Example: 1 GiB in, 1 GiB out, 25 GB/s link; the kernel takes 3 ms; the CPU version takes 40 ms
T_copy   = 1.07e9 / 25e9   = 43 ms each way
T_gpu    = 43 + 3 + 43     = 89 ms
T_cpu    = 40 ms
# The GPU is 2x SLOWER end to end, even though its kernel is 13x faster.

The lesson is that the transfer-to-compute ratio decides. A kernel that does a lot of work per byte transferred, or that runs many times on data already resident on the device, justifies the copies. A single pass over a large array does not.

§3Techniques to Reduce the Cost

  • Keep data on the device: run a whole pipeline of kernels on the GPU, and copy only the final result back
  • Overlap copy and compute: with pinned host memory and streams, transfer one chunk while computing on another
  • Batch work to amortize launch and transfer overhead
  • Unified memory and shared-memory SoCs: integrated designs (Apple silicon, some APUs and game consoles) give CPU and GPU one physical memory, avoiding copies altogether, at the cost of lower peak bandwidth than discrete HBM
  • Direct paths: RDMA and GPU-direct technologies let network cards and storage deliver data straight to GPU memory, bypassing the host
cudaMallocHost(&h_in, bytes);                        // pinned (page-locked) host memory
cudaMemcpyAsync(d_in, h_in, bytes, cudaMemcpyHostToDevice, stream);
kernel<<<grid, block, 0, stream>>>(d_in, d_out);
cudaMemcpyAsync(h_out, d_out, bytes, cudaMemcpyDeviceToHost, stream);
// With several streams, copy for chunk k+1 overlaps with the kernel for chunk k.

The same thinking applies to any heterogeneous system: smart NICs, storage processors, and multi-GPU nodes all have an interconnect that is slower than the devices it joins, and good designs keep data where it's being processed.

The key insight Accelerating a computation is only half the job. Count the bytes that must cross each link, and divide by its bandwidth, before promising a speedup.

§4Common Mistakes

MistakeWhat HappensFix
Benchmarking only the kernelTotal time includes copies and launch overheadTime the whole pipeline end to end
Copying data to the GPU for a single passTransfers cost more than the CPU computationOffload only if work per byte is high, or reuse data on the device
Using pageable host memory for async copiesTransfers can't overlap with computeAllocate pinned memory for streaming transfers
Practice
  1. Recompute the break-even example for a PCIe 5.0 link at 50 GB/s effective. Is the GPU now faster than the 40 ms CPU version?
  2. Describe how to restructure a pipeline of four GPU kernels so data crosses PCIe only twice.
Key takeaways
  • PCIe is 1 to 2 orders of magnitude slower than GPU memory, so copies can dominate.
  • Total time = copy in + compute + copy out; compare it with the CPU time.
  • Keep data resident, overlap transfers, batch work, or use unified memory to avoid copies.
