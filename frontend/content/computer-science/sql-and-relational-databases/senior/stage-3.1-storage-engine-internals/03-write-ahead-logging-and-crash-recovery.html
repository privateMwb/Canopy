Write-Ahead Logging & Crash Recovery

Write-ahead logging is how a database makes committed data survive a crash without forcing every change to its final place on disk first.

§1The Problem

A commit must be durable: once the database says "committed", a power cut must not lose it. The obvious way (write every modified page to its location on disk before replying) is slow, because those writes are scattered randomly, and dangerous, because a crash in the middle of writing a page can leave it half old and half new (a torn page).

§2The Write-Ahead Log (WAL)

The rule: log the change before applying it. Every modification is first appended to a sequential log file and flushed to durable storage. Only then is the commit acknowledged. The actual data pages in the buffer pool are written to disk later, lazily.

UPDATE accounts SET balance = 400 WHERE id = 1;
  1. append to WAL:  [LSN 9041] tx 205: page 812 slot 3: balance 500 → 400
  2. modify page 812 in the buffer pool  (now "dirty")
COMMIT;
  3. append [LSN 9042] tx 205 COMMIT to WAL, then fsync the log   ← durable now
  4. reply "committed" to the client
  ... later: background writer flushes dirty page 812 to the data file

Why it's fast: the log is sequential (cheap on any disk), and a commit needs only one fsync of the log tail, with many transactions able to share it (group commit). Why it's safe: if the machine dies, the log contains everything needed to redo the work.

§3Crash Recovery

On restart, the database replays the log from the last checkpoint, the point up to which all dirty pages were known to be flushed. A classic design is ARIES:

  1. Analysis: scan the log to find which transactions were active and which pages were dirty at the crash.
  2. Redo: reapply logged changes to bring pages to their exact pre-crash state ("repeat history").
  3. Undo: roll back transactions that had not committed, writing compensation records as it goes.

Each log record has a log sequence number (LSN), and each page remembers the LSN of its last change, so recovery knows whether a logged change is already on the page and can skip it.

§4Checkpoints, Fsync, and Reuse of the WAL

  • A checkpoint flushes dirty pages and records that everything before some LSN is safe on disk. WAL older than that can be recycled. Frequent checkpoints shorten recovery but cause I/O bursts; spacing them out smooths I/O but lengthens recovery.
  • fsync is the durability line. A write that returned from the OS may still sit in a cache. Settings that skip it (synchronous_commit = off, innodb_flush_log_at_trx_commit = 2) make commits faster but can lose the last moments of transactions in a crash. Never disable fsync itself on data you care about.
  • Torn pages are handled with full-page writes (PostgreSQL logs a full copy of a page the first time it changes after a checkpoint) or a doublewrite buffer (InnoDB).
  • The same log powers replication (ship the WAL to followers) and point-in-time recovery (replay archived WAL to a chosen moment), as Stages 3.2 and 3.3 explain.
The key insight The WAL turns many random writes into one sequential write and one fsync. Durability then means "the log record is on disk", and the data files are just a cache of what the log says.

§5Common Mistakes

MistakeWhat HappensFix
Disabling fsync for speedA crash can corrupt the whole databaseKeep fsync on; relax synchronous_commit only where small data loss is acceptable
Putting the WAL on the same slow disk as heavily contended dataCommit latency suffersGive the log fast, dedicated storage where possible
Assuming a successful write() means data is safeIt may still be in an OS cacheDurability needs fsync (or equivalent) and trustworthy hardware
Never testing recoverySurprises when a real crash happensPractice crash and restart in staging; monitor recovery times
Practice
  1. Build a tiny key-value store that appends SET key value lines to a log file, fsyncs before acknowledging, and rebuilds its in-memory map by replaying the log on startup. Kill it mid-run to test.
  2. Explain what a user could lose in a crash with synchronous_commit = off versus on, and describe a workload where that trade-off is acceptable.
Key takeaways
  • Write-ahead logging records changes sequentially and durably before data pages are written.
  • Recovery replays the log from the last checkpoint: analysis, redo, and undo.
  • fsync is the durability boundary; the same log supports replication and point-in-time recovery.
