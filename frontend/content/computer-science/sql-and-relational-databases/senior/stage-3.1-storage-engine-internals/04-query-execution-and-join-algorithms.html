Query Execution & Join Algorithms

Behind every SQL query is a tree of operators, and the join algorithm the planner picks (nested loop, hash, or merge) often decides whether a query takes milliseconds or minutes.

§1The Executor: A Tree of Operators

The planner turns SQL into a plan tree. Each node is an operator (scan, filter, join, sort, aggregate) that pulls rows from its children. Most engines use the iterator (Volcano) model: each operator offers a "give me the next row" call, so rows flow up the tree one at a time or in small batches.

        Aggregate (SUM)
             │
        Hash Join  (o.customer_id = c.id)
        ┌────┴─────┐
   Seq Scan       Index Scan
   orders o       customers c

Some operators stream (a filter handles each row as it arrives), others are blocking (a sort can't emit anything until it has seen all input). Memory limits (work_mem in PostgreSQL) determine whether a sort or hash stays in RAM or spills to disk.

§2Nested Loop Join

for each row r in outer:
    for each row s in inner where s.key = r.key:     # ideally via an index
        emit (r, s)

Cost is roughly outer_rows × cost_of_one_inner_lookup. With an index on the inner side, each lookup is cheap, so it's excellent when the outer side is small. Without an index, it's O(n × m): catastrophic for large inputs.

§3Hash Join

build:  put the (smaller) input into a hash table keyed by the join column
probe:  for each row of the other input, look up matching rows in the hash table

Cost is roughly linear: O(n + m). It needs no index, handles large unsorted inputs well, and only supports equality joins. If the hash table exceeds memory, it's split into batches that spill to disk (a Grace hash join), slower but still working. Choose-the-smaller-side-to-build is a key planner decision, and one reason row estimates matter.

§4Merge Join and Choosing

sort both inputs by the join key (or read them already sorted via an index)
walk through both in step, matching equal keys, like merging two sorted lists

Cost is the sort (O(n log n)) plus one linear pass; if both sides arrive already sorted (from indexes), it's very cheap, and it supports range-style conditions and produces sorted output for later operators.

AlgorithmBest whenNeeds
Nested loopSmall outer input, indexed innerIndex on the inner join column
Hash joinLarge, unsorted inputs; equality joinMemory for the hash table
Merge joinInputs already sorted (or sort is needed anyway)Sorted inputs
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders o JOIN customers c ON c.id = o.customer_id WHERE c.country = 'NZ';
-- see which join node was chosen, and check 'Batches' / 'Sort Method: external' for spills
The key insight Join performance is about how many times you touch the inner side. Nested loops multiply by the outer size unless an index saves you; hash and merge joins make one pass over each input, at the cost of memory or sorting.

§5Common Mistakes

MistakeWhat HappensFix
A nested loop over a large unindexed inner tableQuadratic work, queries that run for hoursIndex the join column, or ensure the planner can choose a hash join
Too little work_mem for sorts and hashesSpilling to disk makes joins and sorts many times slowerSize memory per operation carefully (it's per node, per query)
Setting work_mem huge globallyMany concurrent queries multiply it and exhaust RAMRaise it per session for specific heavy queries
Ignoring the join orderA bad row estimate produces a huge intermediate resultCheck estimates; update statistics; simplify the query
Practice
  1. Write nested-loop and hash join in 20 lines each over two Python lists of dicts, and time them as inputs grow from 1,000 to 100,000 rows.
  2. On a real database, force each join strategy in turn (SET enable_hashjoin = off; and similar) for the same query and compare plans and timings. Which won, and why?
Key takeaways
  • Queries run as trees of operators; some stream rows while others block and may spill to disk.
  • Nested loop suits small outer inputs with an inner index; hash join suits large equality joins; merge join suits sorted inputs.
  • Memory settings and accurate row estimates strongly influence which algorithm runs and how fast.
