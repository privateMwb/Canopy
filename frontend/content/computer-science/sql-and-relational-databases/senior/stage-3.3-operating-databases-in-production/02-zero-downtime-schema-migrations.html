Zero-Downtime Schema Migrations

Changing a schema while the application is running requires that old and new code both work against the database at every moment. The expand-and-contract pattern gets you there safely.

§1Why a Simple ALTER Can Take You Down

Some schema changes take locks that block reads and writes for as long as they run, and on a big table that can be minutes or hours. Even a change that is quick still needs a brief lock, and if a long-running query holds a conflicting lock, your ALTER waits in the queue and everything behind it waits too.

Long query holds a lock on orders
        │
        ▼ ALTER TABLE orders ... queues, waiting for an exclusive lock
        ▼ every new query on orders now queues behind the ALTER
→ an outage from a one-line schema change

Also, during a deploy, old and new application versions run simultaneously. A change that's incompatible with either one breaks requests mid-rollout.

§2Expand and Contract

Break a breaking change into compatible steps, each deployed separately. Renaming column fullname to name:

  1. Expand: add the new column name (nullable). Old code keeps working.
  2. Dual-write: deploy code that writes both columns, still reading the old one.
  3. Backfill: copy existing fullname values into name in small batches.
  4. Switch reads: deploy code that reads name (and still writes both for safety).
  5. Stop writing the old column.
  6. Contract: drop fullname, in a later release when no running code uses it.
step 1  ALTER TABLE users ADD COLUMN name TEXT;
step 3  -- backfill in batches (see below)
step 6  ALTER TABLE users DROP COLUMN fullname;          -- weeks later

It's slower than one ALTER ... RENAME, but every step is individually safe and reversible.

§3Safe Backfills and Lock Hygiene

-- Backfill in small batches so locks are short and replication keeps up
UPDATE users SET name = fullname
WHERE id IN (SELECT id FROM users WHERE name IS NULL ORDER BY id LIMIT 5000);
-- repeat until 0 rows affected, with a short pause between batches

-- Protect production from lock queueing: fail fast instead of waiting
SET lock_timeout = '3s';
SET statement_timeout = '15min';
ALTER TABLE users ADD COLUMN name TEXT;

Specific operations to handle with care (PostgreSQL):

OperationRiskSafer approach
CREATE INDEXBlocks writesCREATE INDEX CONCURRENTLY
Add NOT NULL column with a defaultOld versions rewrote the table (fast since PG 11)Check your version; otherwise add nullable, backfill, then constrain
Add a NOT NULL or CHECK constraintFull scan under a lockAdd NOT VALID, then VALIDATE CONSTRAINT separately
Add a foreign keyLocks and validates both tablesNOT VALID, then validate
Change a column's typeMay rewrite the whole tableAdd a new column, backfill, swap (expand/contract)
Drop a columnBreaks code that still uses itContract only after code stops using it

MySQL users have tools such as gh-ost and pt-online-schema-change, which copy the table in the background and swap it in.

§4A Migration Checklist

  • Is every step compatible with the previous application version (so rollouts and rollbacks both work)?
  • Have you tested it against a production-sized copy for duration and lock behavior?
  • Are lock_timeout and statement_timeout set so a stuck migration fails instead of queueing?
  • Is the backfill batched, idempotent, and resumable?
  • Do you know how to roll back, and what's irreversible (dropped data)?
  • Is it scheduled when a long-running job or heavy traffic won't collide with it?
The key insight Treat the application and the schema as two things deployed at different times, which must be compatible at every intermediate moment. Add first, migrate gradually, remove last.

§5Common Mistakes

MistakeWhat HappensFix
Renaming or dropping a column in one stepRunning old code instantly breaksUse expand and contract across several deploys
Creating an index without CONCURRENTLYWrites block for the whole buildUse CREATE INDEX CONCURRENTLY (outside a transaction block)
Running ALTER TABLE with no lock_timeoutThe statement queues behind a long query and blocks all trafficSet a short lock_timeout and retry
One giant UPDATE to backfillLong lock, replication lag, bloatBackfill in small batches with pauses
Practice
  1. Plan the expand-and-contract sequence for changing orders.total from INTEGER cents to NUMERIC(12,2). List each deploy, what code does at each, and the rollback at each step.
  2. On a table with a few million rows, compare CREATE INDEX and CREATE INDEX CONCURRENTLY while a second session continuously inserts. What happens to the inserts?
Key takeaways
  • Naive schema changes can lock tables, and lock queueing can turn a small change into an outage.
  • Expand and contract: add, dual-write, backfill, switch, then remove, with every step compatible with old and new code.
  • Use lock timeouts, concurrent index builds, batched backfills, and staged constraints.
