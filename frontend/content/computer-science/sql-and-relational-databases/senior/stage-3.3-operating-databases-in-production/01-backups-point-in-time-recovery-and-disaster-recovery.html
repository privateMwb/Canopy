Backups, Point-in-Time Recovery & Disaster Recovery

A backup is only real if you've restored from it. Recovery objectives (RPO and RTO) tell you how much data you can lose and how long you can be down, and your backup design follows from them.

§1Two Numbers That Drive Everything

  • RPO (Recovery Point Objective): how much recent data you can afford to lose, measured in time. An RPO of 5 minutes means that after a disaster you must be able to recover to within 5 minutes of the failure.
  • RTO (Recovery Time Objective): how long you can be down. An RTO of 1 hour means service must be restored within an hour.

Both come from the business, not from engineering preference, and each tighter number costs more. Nightly backups give an RPO of up to 24 hours; continuous WAL archiving gives seconds. A restore of a 5 TB database from cold storage may take many hours, so a one-hour RTO needs a different approach (a warm standby).

Most production systems combine a periodic physical base backup with continuous log archiving.

§3Point-in-Time Recovery (PITR)

PITR restores a base backup and then replays archived logs up to a chosen moment, such as the second before someone ran a destructive statement.

base backup (Sunday 02:00) + WAL archive (continuous)
        │
        ▼ restore base, then replay WAL up to a target
recovery_target_time = '2026-10-20 14:31:59+00'     # one second before the bad DELETE
# PostgreSQL (recovery configuration, simplified)
restore_command = 'cp /archive/%f %p'
recovery_target_time = '2026-10-20 14:31:59+00'
recovery_target_action = 'promote'

This is the tool for human error, the most common cause of data loss. Replicas can't help, because they replay the mistake too.

§4Make Backups Trustworthy: The 3-2-1 Rule and Testing

  • 3-2-1: keep 3 copies of the data, on 2 different kinds of storage, with 1 off-site (a different account or region, protected from the same credentials that run production, so a compromise or ransomware can't delete them).
  • Encrypt backups and protect the keys separately.
  • Monitor that backups ran, finished, and have a plausible size.
  • Restore regularly, automatically if you can: restore the latest backup into a scratch environment, run integrity checks and a few sanity queries, and record how long it took. That number is your real RTO.
restore drill:  fetch latest backup → restore → run validation queries → compare row counts → log duration

Write a runbook so the person restoring at 3 a.m. doesn't have to invent the procedure. Include who decides, how to choose the recovery target, how to cut over, and how to verify.

The key insight Untested backups are hopes. The only way to know your RTO is to measure a real restore, and the only way to know your backups are complete is to restore them and look.

§5Common Mistakes

MistakeWhat HappensFix
Relying on replicas as backupsDeletes and corruption replicate immediatelyKeep independent backups with PITR
Never running a restoreDiscover corrupt, incomplete, or unusable backups during the emergencySchedule automated restore tests and record the timing
Storing backups with the same credentials or account as productionAn attacker or mistake deletes bothKeep an off-site, access-separated, ideally immutable copy
Setting RPO/RTO by guessSpending too much or protecting too littleAgree on numbers with the business and design to meet them
Practice
  1. Take a base backup and enable WAL archiving on a practice PostgreSQL instance. Delete a table, then restore to the moment just before the deletion.
  2. Write a one-page restore runbook for a database you know. Time how long each step actually takes in a rehearsal.
Key takeaways
  • RPO is how much data you can lose; RTO is how long you can be down. Both come from the business.
  • Combine physical base backups with continuous log archiving for point-in-time recovery.
  • Follow 3-2-1, protect backups from production credentials, and restore regularly to verify them.
