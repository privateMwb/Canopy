Denormalization & When to Break the Rules

Denormalization deliberately stores redundant data to make reads cheaper, and it's worth doing only when you can name the query it speeds up and the cost you accept.

§1Why Break the Rules

A fully normalized design is correct, but a hot query may need five joins and an aggregation on every page view. Denormalizing trades write complexity and risk of inconsistency for faster, simpler reads. The key word is trade: you're not eliminating work, you're moving it from read time to write time.

§2Common Denormalization Patterns

-- 1. Precomputed counters
ALTER TABLE posts ADD COLUMN comment_count INTEGER NOT NULL DEFAULT 0;
-- must be updated whenever a comment is added or removed

-- 2. Copying a stable value to avoid a join
ALTER TABLE orders ADD COLUMN customer_name TEXT;     -- snapshot, e.g. for invoices

-- 3. Summary tables
CREATE TABLE daily_sales AS
SELECT date(placed_at) AS day, COUNT(*) AS orders, SUM(total) AS revenue
FROM orders GROUP BY day;

Some copies are legitimate snapshots (the address on an invoice must not change when the customer moves). Others are caches of derived data that must be kept in sync.

§3Keeping Copies Correct

Derived data needs an owner: something that guarantees it stays right. Options, from safest to riskiest:

  • A view or materialized view: the database computes it for you (CREATE MATERIALIZED VIEW ... in PostgreSQL, refreshed on a schedule).
  • A trigger that updates the copy when the source changes.
  • Application code that updates both in one transaction.
  • A periodic job that recomputes and repairs drift.
BEGIN;
INSERT INTO comments (post_id, body) VALUES (7, 'Nice post');
UPDATE posts SET comment_count = comment_count + 1 WHERE id = 7;
COMMIT;                          -- both or neither (Stage 1.4)

§4A Decision Rule

Before denormalizing, work through these in order:

  1. Is the query actually slow? Measure it first.
  2. Would an index fix it? (Usually, yes. See Stage 2.1.)
  3. Would a materialized view or cache do the job without touching your core tables?
  4. If you still need stored redundancy, document it, write the sync logic once, and add a check that detects drift.

Keep the normalized tables as the source of truth, and treat denormalized columns as replaceable.

The key insight Denormalize after you've normalized and measured, never instead of it. A redundant column is a promise to keep two things in sync forever, so make sure the speedup is worth that promise.

§5Common Mistakes

MistakeWhat HappensFix
Denormalizing before measuringAdded complexity for a problem that an index would have solvedProfile first; try indexes and query fixes
Updating the original but forgetting the copyCounters and copies drift out of syncUpdate both in one transaction, or use a trigger / view
Treating the copy as the source of truthCorrupted summaries can't be rebuiltKeep normalized tables authoritative; make summaries rebuildable
Confusing snapshots with cachesRefreshing a value that should have been frozen (or vice versa)Decide per column: historical record or live cache?
Practice
  1. Add comment_count to posts, then write the transaction for adding and for removing a comment. Write a query that finds posts whose stored count doesn't match the real count.
  2. Name two columns in a shop schema that should be frozen snapshots and two that should be live derived values.
Key takeaways
  • Denormalization moves cost from reads to writes and risks inconsistency.
  • Prefer indexes, views, and materialized views before storing redundant columns.
  • Keep normalized data as the source of truth and make copies verifiable and rebuildable.
