Schema Migrations: Changing a Schema Safely

A migration is a versioned, repeatable change to your schema, which lets a database evolve alongside your code without hand-editing production.

§1Why Migrations Exist

Your schema changes as the product does: a new column here, a renamed table there. If those changes are applied by hand, your laptop, the test server, and production quickly disagree. A migration is a small file describing one change, applied in order and recorded in the database so it runs exactly once.

migrations/
  001_create_customers.sql
  002_create_orders.sql
  003_add_phone_to_customers.sql
  004_add_index_orders_customer.sql

A table such as schema_migrations records which have been applied, so tools know what's left to run.

§2Anatomy of a Migration

-- 003_add_phone_to_customers.sql   (up)
ALTER TABLE customers ADD COLUMN phone TEXT;

-- 003_add_phone_to_customers.down.sql   (down, to reverse it)
ALTER TABLE customers DROP COLUMN phone;

Tools such as Flyway, Liquibase, Alembic (Python), Rails/Django migrations, Prisma Migrate, and Knex all follow this model. Pick the one that matches your stack; the habits matter more than the tool.

§3Habits That Keep Migrations Safe

  • Never edit a migration that has already been applied elsewhere. Add a new one instead.
  • Commit migrations with the code that needs them.
  • Make each migration small and single-purpose, so failures are easy to understand.
  • Run them against a copy of production data before the real thing when possible.
  • Adding a NOT NULL column needs a default (or a staged approach), because existing rows have no value for it.
-- Adding a required column to a table that already has rows
ALTER TABLE customers ADD COLUMN country TEXT NOT NULL DEFAULT 'US';

-- Safer for large tables: add nullable, backfill, then add the constraint
ALTER TABLE customers ADD COLUMN country TEXT;
UPDATE customers SET country = 'US' WHERE country IS NULL;
ALTER TABLE customers ALTER COLUMN country SET NOT NULL;      -- PostgreSQL syntax

§4What Can Go Wrong

Some changes are easy and some are dangerous on a live database. Renaming or dropping a column breaks any code still using the old name; changing a column's type can rewrite the whole table and block writes while it runs. The expand-and-contract pattern (add the new thing, move code over, then remove the old) handles these safely, and Stage 3.3 covers it in depth. For now, the rule is: don't ship a destructive change in the same release as the code that stops needing it.

The key insight The schema is part of your codebase. Treat every change like code: versioned, reviewed, tested against realistic data, and applied by the same automated process in every environment.

§5Common Mistakes

MistakeWhat HappensFix
Editing the production schema by handEnvironments drift and nobody knows what changedMake every change a committed migration
Editing an already-applied migration fileOther environments never see the edit; checksums failWrite a new migration that corrects the old one
Adding NOT NULL with no default to a populated tableThe migration fails on existing rowsAdd a default, or add nullable, backfill, then constrain
Dropping a column in the same deploy as the code changeOld servers still running the previous code breakDeploy the code first; drop the column in a later release
Practice
  1. Set up a migrations/ folder with three numbered SQL files and a tiny script (or a tool such as Flyway or Alembic) that applies them in order and records them in a schema_migrations table.
  2. Write the up and down migrations for adding a required country column to a table that already contains rows.
Key takeaways
  • Migrations are versioned, ordered, run-once schema changes recorded in the database.
  • Never edit applied migrations; add a new one.
  • Adding constraints to populated tables takes a staged approach to stay safe.
