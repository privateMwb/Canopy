One-to-Many, Many-to-Many & Junction Tables

A many-to-many relationship is modeled with a junction table whose rows link two other tables, and that junction table can carry its own data.

§1Why a Column Can't Do It

An order contains many products, and a product appears in many orders. A single foreign key on either table can only point at one row. The fix is a third table with a foreign key to each side: the junction table (also called a join, link, or bridge table).

orders ──< order_items >── products
 1    N                 N     1

§2The Junction Table

CREATE TABLE order_items (
  order_id   INTEGER NOT NULL REFERENCES orders(id)   ON DELETE CASCADE,
  product_id INTEGER NOT NULL REFERENCES products(id),
  qty        INTEGER NOT NULL CHECK (qty > 0),
  unit_price NUMERIC(10,2) NOT NULL,       -- price at time of sale
  PRIMARY KEY (order_id, product_id)       -- a product appears once per order
);

The composite primary key (order_id, product_id) stops the same product from being listed twice in one order. Notice the table holds data about the relationship (qty, unit_price), which is why junction tables are often entities in their own right.

Querying across it uses two joins:

SELECT o.id, p.name, oi.qty, oi.qty * oi.unit_price AS line_total
FROM orders o
JOIN order_items oi ON oi.order_id   = o.id
JOIN products    p  ON p.id          = oi.product_id
WHERE o.customer_id = 1;

§3Pure Link Tables

Sometimes the relationship has no extra data. A student can take many courses and a course has many students:

CREATE TABLE enrollments (
  student_id INTEGER REFERENCES students(id),
  course_id  INTEGER REFERENCES courses(id),
  PRIMARY KEY (student_id, course_id)
);

Even here it's common to add enrolled_on or grade later, so expect the link table to grow attributes over time. Add an index on the second key column too, since the primary key's index only helps lookups starting from student_id.

§4Other Relationship Patterns

  • One-to-one: put a unique foreign key on one side (user_profile.user_id UNIQUE), or merge the tables if they always coexist.
  • Self-reference: a foreign key to the same table (employees.manager_id → employees.id) models hierarchies.
  • Polymorphic links (one column pointing at many possible tables) can't be enforced by a foreign key; avoid them unless you must, or use separate link tables per target.
The key insight Every many-to-many relationship hides a third thing. Name it (an order line, an enrollment, a membership) and give it its own columns; it nearly always turns out to have some.

§5Common Mistakes

MistakeWhat HappensFix
Storing a list of ids in a single columnNo integrity, no joins, no efficient lookupsUse a junction table with two foreign keys
Forgetting the composite primary key or a unique constraintDuplicate links such as the same product twiceDeclare PRIMARY KEY (a_id, b_id)
Not indexing the second foreign keyLookups from that side scan the whole tableAdd an index on (b_id) or (b_id, a_id)
Reading the current price for an old order lineHistory is rewritten when prices changeStore unit_price on the junction row
Practice
  1. Design tables for students, courses, and enrollments (with a grade). Write a query listing each student's courses and grades, and one for how many students each course has.
  2. Model a social app where users follow users. Which table is the junction? It joins users to itself: write the CREATE TABLE.
Key takeaways
  • Many-to-many relationships need a junction table with a foreign key to each side.
  • A composite primary key prevents duplicate links; the junction often carries its own attributes.
  • Index both directions you'll query from.
