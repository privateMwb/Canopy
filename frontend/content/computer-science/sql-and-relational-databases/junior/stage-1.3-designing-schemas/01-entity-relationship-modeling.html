Entity-Relationship Modeling

Entity-relationship modeling turns a plain-English description of a business into entities, attributes, and relationships before you write a single CREATE TABLE.

§1Start with Nouns and Verbs

Take a written brief and read it for nouns and verbs. Nouns become candidate entities (things you store information about). Verbs become candidate relationships.

Suppose the brief says: "Customers place orders. Each order contains one or more products. Products belong to a category."

  • Entities: customer, order, product, category
  • Relationships: customer places order; order contains product; product belongs to category

Attributes come from the details: a customer has a name and email, a product has a name, SKU, and price. If a "noun" has no attributes of its own and is just a value of something else, it's probably an attribute, not an entity.

§2Cardinality: How Many on Each Side

For each relationship, ask two questions: how many B can one A have, and how many A can one B have?

RelationshipCardinalityExample
One-to-one1 : 1user ↔ user_profile
One-to-many1 : Ncustomer → orders
Many-to-manyN : Morders ↔ products

Cardinality also has an optionality side: must every order have a customer (mandatory), or can a product exist with no category yet (optional)? Mandatory relationships become NOT NULL foreign keys.

§3From Diagram to Tables

Sketch boxes and lines, then translate mechanically:

CUSTOMER ──< ORDER >──< ORDER_ITEM >── PRODUCT >── CATEGORY
  1    places  N        1   has   N     N   is a    1
  • Each entity becomes a table with a surrogate primary key.
  • Each one-to-many becomes a foreign key on the "many" side.
  • Each many-to-many becomes a third table (next lesson but one).
  • Each attribute becomes a typed column with sensible constraints.
CREATE TABLE categories (id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE);
CREATE TABLE products (
  id          INTEGER PRIMARY KEY,
  category_id INTEGER REFERENCES categories(id),   -- optional: nullable
  name        TEXT NOT NULL,
  price       NUMERIC(10,2) NOT NULL CHECK (price >= 0)
);

§4Questions That Improve a Model

  • What identifies one of these things uniquely, and will that ever change?
  • Is this value a fixed set (an enum or lookup table) or free text?
  • Does history matter? If a product's price changes, must old orders keep the price paid at the time? (Almost always yes: store it on the order item.)
  • Who else will read this data, and what questions will they ask of it?

Modeling is conversation first and SQL second. Ten minutes with the people who run the business saves weeks of migrations.

The key insight Model the real world's rules, not the screens of your first version. Screens change often; what a customer, an order, and a payment actually are changes rarely, so a model built on them survives redesigns.

§5Common Mistakes

MistakeWhat HappensFix
Modeling pages or forms instead of entitiesTables mirror the UI and break when the UI changesModel the business concepts; build the UI on top
Reading the current price from products for old ordersHistorical totals change when prices changeCopy the price paid onto the order item at purchase time
Treating every noun as its own tableDozens of tiny tables that are really just attributesMake it an entity only if it has its own attributes and identity
Ignoring optional vs. mandatory relationshipsOrphan or half-filled rows accumulateExpress mandatory links with NOT NULL foreign keys
Practice
  1. Take this brief: "A clinic has doctors and patients. Patients book appointments with a doctor at a time. Doctors have specialties." List entities, relationships, and cardinalities, then draw the diagram.
  2. For your diagram, mark which relationships are mandatory and which are optional, and decide what historical data (if any) must be frozen at booking time.
Key takeaways
  • Entities come from nouns, relationships from verbs, attributes from details.
  • Cardinality and optionality decide where foreign keys go and whether they're nullable.
  • Store facts that must stay historically accurate (like price paid) on the transaction itself.
