Normalization: 1NF Through 3NF

Normalization is a step-by-step process for removing redundancy so that every fact is stored in exactly one place, which prevents whole classes of update bugs.

§1The Problem: Update Anomalies

Consider one wide table that mixes everything:

order_idcustomer_namecustomer_emailproductcategoryprice
101Adaada@x.comNotebookstationery4.50
101Adaada@x.comPenstationery1.20
102Adaada@x.comNovelbooks9.00

Ada's email is stored three times. Change it in one row and the data now disagrees with itself (an update anomaly). Delete the only order for a product and you lose the product's existence (a deletion anomaly). You can't add a new product until someone orders it (an insertion anomaly).

§2First Normal Form (1NF): Atomic Values

Every column holds a single value, and there are no repeating groups.

-- Violates 1NF: a list crammed into one column
orders(id, customer, products = 'Notebook, Pen')

-- 1NF: one fact per row
order_items(order_id, product)
  (101, 'Notebook')
  (101, 'Pen')

If you find yourself splitting strings on commas to query a column, it needs to be its own table.

§3Second Normal Form (2NF): Depend on the Whole Key

When a table's key has several columns, every other column must depend on all of them, not just part. A table order_items(order_id, product_id, product_name, qty) has the key (order_id, product_id), but product_name depends only on product_id. Move it out:

products(product_id PK, product_name)
order_items(order_id, product_id, qty)     -- PK (order_id, product_id)

§4Third Normal Form (3NF): No Hidden Dependencies

Non-key columns must depend on the key, and nothing but the key. In orders(id, customer_id, customer_email), the email depends on customer_id, not on the order id. That's a transitive dependency; move customer_email to the customers table.

A memorable summary: every non-key column should depend on "the key, the whole key, and nothing but the key".

customers(id PK, name, email)
orders(id PK, customer_id FK, placed_at)
products(id PK, name, category_id FK, price)
order_items(order_id FK, product_id FK, qty, unit_price)   -- PK (order_id, product_id)

Each fact now lives in one place: change an email once, in one row.

The key insight Normalization isn't about following rules for their own sake. Each normal form removes one specific way for the data to contradict itself. If you can state where each fact lives, you've normalized enough.

§5Common Mistakes

MistakeWhat HappensFix
Storing comma-separated lists in a columnCan't filter, join, or constrain the items properlyCreate a child table with one row per item
Copying a customer's name onto each order "for convenience"The copies diverge after an updateStore the foreign key; join when you need the name
Normalizing to extreme without looking at queriesSimple reads need too many joinsAim for 3NF, then denormalize only where measured need exists
Confusing a surrogate key with a real dependencyOverlooking that price can depend on category, not the itemAsk for each column: what determines this value?
Practice
  1. Normalize the wide order_id, customer_name, customer_email, product, category, price table above into 3NF. List the tables, keys, and foreign keys you end up with.
  2. A table employees(id, name, dept_id, dept_name, dept_location) is in 2NF. Why is it not in 3NF, and how do you fix it?
Key takeaways
  • Redundant data causes update, insertion, and deletion anomalies.
  • 1NF: atomic values; 2NF: depend on the whole key; 3NF: depend on nothing but the key.
  • Normalize to 3NF by default; deviate deliberately.
