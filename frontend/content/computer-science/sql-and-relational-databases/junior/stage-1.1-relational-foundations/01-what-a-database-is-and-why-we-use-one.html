What a Database Is & Why We Use One

A database is a program that stores data durably, lets many users read and write it at once, and answers questions about it without you writing the search logic yourself.

§1The Problem with Files

Imagine storing a shop's orders in a CSV file. It works for a week. Then two employees save at the same moment and one change is lost. Then someone asks for "all orders over $100 from last March" and you write a loop that reads the entire file. Then the program crashes halfway through writing and the file is left corrupt.

A database management system (DBMS) exists to solve exactly these problems. It sits between your application and the data on disk and takes responsibility for the hard parts.

ProblemWhat the DBMS provides
Two users edit at onceConcurrency control: changes don't overwrite each other
Crash mid-writeDurability and atomicity: a change is fully saved or not at all
Finding data in millions of rowsIndexes and a query planner: fast lookups without hand-written loops
Bad data creeping inConstraints: the database rejects invalid rows
Many programs, one datasetA shared, well-defined interface: usually SQL

§2Where Relational Databases Fit

A relational database stores data in tables of rows and columns, and uses a language called SQL (Structured Query Language) to read and change it. PostgreSQL, MySQL, SQLite, SQL Server, and Oracle are all relational. They have dominated since the 1980s because the model is simple, well understood, and flexible enough for most applications.

You'll also hear about NoSQL databases (document stores, key-value stores, and others). Those come later in this track. For now, the useful default is this: when you're unsure what to use, start relational.

Application  ──SQL──►  DBMS  ──►  files on disk
(your code)           (Postgres,    (managed for you:
                       SQLite...)    pages, indexes, logs)

§3Try It in Two Minutes

SQLite is the easiest way to start: it's a full relational database stored in a single file, with nothing to install on most systems. In this track the examples use standard SQL, and where PostgreSQL behaves differently the lesson says so.

sqlite3 shop.db                      # opens (or creates) shop.db

sqlite> CREATE TABLE products (id INTEGER PRIMARY KEY, name TEXT, price REAL);
sqlite> INSERT INTO products (name, price) VALUES ('Notebook', 4.50);
sqlite> SELECT * FROM products;
1|Notebook|4.5
sqlite> .quit

The file shop.db now holds your data. Reopen it tomorrow and the row is still there. That's persistence, the most basic thing a database offers.

The key insight A database isn't just storage. The valuable part is the guarantees: it keeps data correct under concurrency and crashes, so every application doesn't have to rebuild those guarantees badly.

§4Common Mistakes

MistakeWhat HappensFix
Using a spreadsheet or JSON file as the system of recordConcurrent edits clobber each other and there's no protection against partial writesUse a real database as soon as more than one process or user writes data
Assuming a database is just "a faster file"Missing the guarantees (transactions, constraints) and then re-implementing them in app codeLearn what the DBMS enforces, then lean on it
Picking a database by popularity rather than the workloadA poor fit shows up later as slow queries or awkward modelingStart with relational; move away only for a specific, named reason
Practice
  1. Install SQLite (or run sqlite3 if it's already present) and create a database file with one table. Close the program, reopen the file, and confirm your row survived.
  2. List three bugs you could hit by storing orders in a shared CSV file, and match each to a DBMS feature from the table above.
Key takeaways
  • A DBMS handles concurrency, durability, fast lookup, and data validation so your application doesn't have to.
  • Relational databases store data in tables and are queried with SQL.
  • SQLite is a full relational database in a single file, ideal for learning.
