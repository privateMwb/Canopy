Data Types, NULL & Constraints

Column types, NULL, and constraints let the database reject bad data at the door instead of leaving every query to cope with it later.

§1Choosing Data Types

A column's type controls what it can hold, how much space it takes, and how it sorts and compares. Names vary a little between databases, but the families are consistent.

Kind of dataTypical typeNotes
Whole numbersINTEGER, BIGINTUse BIGINT for ids that could pass ~2 billion
MoneyNUMERIC(12,2) / DECIMALNever FLOAT: binary floating point can't represent 0.10 exactly
TextTEXT, VARCHAR(n)In PostgreSQL, TEXT is fine and usually preferred
True/falseBOOLEAN
Dates and timesDATE, TIMESTAMP (with time zone)Store instants in UTC; never as text
IdentifiersUUID or auto-increment integer

§2NULL: The Absence of a Value

NULL means "unknown or not applicable". It is not zero and not an empty string. Any comparison with NULL yields neither true nor false but unknown, which WHERE treats as not matching.

SELECT NULL = NULL;        -- NULL (unknown), not true
SELECT * FROM customers WHERE phone = NULL;     -- returns nothing, always
SELECT * FROM customers WHERE phone IS NULL;    -- correct
SELECT * FROM customers WHERE phone IS NOT NULL;

This is three-valued logic: true, false, unknown. It also means NOT IN against a list containing a NULL returns nothing, one of the most common sources of mysterious empty results.

§3Constraints: Rules the Database Enforces

CREATE TABLE products (
  id        INTEGER PRIMARY KEY,
  sku       TEXT    NOT NULL UNIQUE,                 -- required and no duplicates
  name      TEXT    NOT NULL,
  price     NUMERIC(10,2) NOT NULL CHECK (price >= 0),   -- arbitrary rule
  category  TEXT    NOT NULL DEFAULT 'general',
  in_stock  BOOLEAN NOT NULL DEFAULT TRUE
);
ConstraintGuarantees
NOT NULLThe column always has a value
UNIQUENo two rows share this value (or combination)
CHECKA condition holds for every row
DEFAULTA value is filled in when none is given
PRIMARY KEY / FOREIGN KEYIdentity and relationships, as in Lesson 2

§4Why Constraints Beat App-Level Checks

Your application will have bugs, and other programs, scripts, and humans will also write to this database. A constraint is enforced for every writer, including a late-night manual fix. Validating in the app is still good for friendly error messages, but treat the database as the last line of defense.

The key insight Make the invalid state impossible to store. Every NOT NULL, UNIQUE, and CHECK you add is a whole category of bug you never have to hunt down in production data.

§5Common Mistakes

MistakeWhat HappensFix
Storing money as FLOATRounding errors appear in totals (0.1 + 0.2 ≠ 0.3)Use NUMERIC/DECIMAL, or integer cents
Testing with = NULLNever matches, so the query silently returns nothingUse IS NULL / IS NOT NULL
Leaving columns nullable by defaultMissing values spread and every query must handle themAdd NOT NULL unless absence genuinely means something
Storing dates as textSorting and arithmetic break; formats get mixedUse DATE / TIMESTAMP types
Practice
  1. Create a products table with NOT NULL, UNIQUE, CHECK, and DEFAULT constraints. Write an insert that violates each one and read the error message.
  2. A table has 3 customers with a phone number and 2 with NULL. What do COUNT(*), COUNT(phone), and WHERE phone <> '555' return? Verify by running it.
Key takeaways
  • Choose types deliberately; use exact numeric types for money and real date types for dates.
  • NULL means unknown; compare with IS NULL, and remember three-valued logic.
  • Constraints enforce correctness for every writer, not just your application.
