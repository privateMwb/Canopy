Parameterized Queries & SQL Injection

Never build SQL by gluing user input into a string. Parameterized queries send the SQL and the values separately, which makes injection structurally impossible.

§1How SQL Injection Works

Suppose a login form builds a query by concatenation:

name = request.form["name"]
sql = "SELECT * FROM users WHERE name = '" + name + "'"

If the user types x' OR '1'='1, the string becomes:

SELECT * FROM users WHERE name = 'x' OR '1'='1'      -- matches every row

Worse inputs can end the statement and append others, such as '; DROP TABLE users; --. The root cause is that data is being interpreted as code. SQL injection has been among the most common and damaging web vulnerabilities for over two decades.

§2The Fix: Parameterized Queries

A parameterized (or prepared) query sends the statement with placeholders, and the values travel separately. The database parses the SQL first, so values can never change its structure.

# Python / sqlite3 uses ?; psycopg uses %s; Postgres natively uses $1, $2
cur.execute("SELECT * FROM users WHERE name = ?", (name,))

# Node (pg)
await client.query("SELECT * FROM users WHERE name = $1", [name]);

# Java (JDBC)
PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE name = ?");
ps.setString(1, name);

With this, x' OR '1'='1 is just a strange username that matches nobody.

§3What Placeholders Can't Do

Placeholders stand in for values, not for identifiers or keywords. You can't parameterize a table name, a column name, or ASC/DESC.

-- Does NOT work:  ORDER BY ?
-- Instead, map user input to a known-good list:
ALLOWED = {"name": "name", "price": "price", "newest": "created_at"}
column = ALLOWED.get(request.args.get("sort"), "name")      # default if unknown
sql = f"SELECT * FROM products ORDER BY {column}"           # safe: from a fixed set

For dynamic IN lists, generate the right number of placeholders (?, ?, ?) and pass the values as parameters. Many libraries offer helpers for this.

§4Defense in Depth

Parameterization is the primary defense, but layer others:

  • Give the application's database user only the permissions it needs (no DROP, no access to unrelated tables).
  • Validate input types and lengths at the edge.
  • Don't show raw database errors to users; log them instead.
  • Use an ORM or query builder that parameterizes by default (next lessons), but know that raw-SQL escape hatches in them can reintroduce the problem.
The key insight Escaping quotes by hand is the wrong fix; it fails in surprising edge cases. The reliable rule is structural: SQL text is written by you and is constant, and anything from outside travels only as a parameter.

§5Common Mistakes

MistakeWhat HappensFix
Building SQL with string concatenation or f-stringsUser input becomes executable SQLUse placeholders for every value
Trying to sanitize by stripping quote charactersBypassed by encodings and other tricksParameterize instead of escaping
Putting user-supplied column or table names into SQLInjection through identifiersWhitelist allowed names and map input to them
Running the app as a superuser accountA single injection can drop or read everythingUse a least-privilege database user
Practice
  1. Write a deliberately vulnerable lookup function using string concatenation and demonstrate injection with x' OR '1'='1. Then fix it with a parameterized query and repeat the attack.
  2. Implement a sort option for a product-list query using a whitelist, and verify that an unexpected value falls back to the default.
Key takeaways
  • SQL injection happens when user input is concatenated into SQL text.
  • Parameterized queries keep values separate from SQL structure and eliminate the issue.
  • Identifiers and keywords can't be parameters; whitelist them instead.
