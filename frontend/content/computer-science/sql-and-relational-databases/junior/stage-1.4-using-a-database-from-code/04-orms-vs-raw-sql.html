ORMs vs. Raw SQL

An ORM maps tables to objects so you can work in your application's language, and it's a good servant and a poor master: use it for the routine and drop to SQL for the rest.

§1What an ORM Does

An object-relational mapper (SQLAlchemy, Django ORM, Hibernate, ActiveRecord, Prisma, TypeORM, GORM) translates between rows and objects, builds SQL for you, and parameterizes values automatically.

# SQLAlchemy-style example
customer = session.get(Customer, 1)
customer.email = "new@example.com"       # tracked change
session.commit()                          # emits UPDATE customers SET email=... WHERE id=1

top = (session.query(Customer)
        .filter(Customer.country == "US")
        .order_by(Customer.name)
        .limit(10).all())

Benefits: less boilerplate, injection-safe by default, schema and migration integration, and portability between databases.

§2Where ORMs Leak

The hardest problem is hiding the database: you still pay its costs. The classic trap is the N+1 query:

orders = session.query(Order).limit(100).all()      # 1 query
for o in orders:
    print(o.customer.name)                           # +100 queries, one per order (lazy loading)

That's 101 round trips instead of one join. Fix it by asking the ORM to eager load the relationship (joinedload, select_related, include, with). Other leaks: loading whole objects when you need two columns, hidden queries triggered by attribute access, and awkward handling of complex reports.

§3Reading the SQL It Generates

You can't tune what you can't see. Turn on query logging in development and read what your ORM actually sends.

# SQLAlchemy:  create_engine(url, echo=True)
# Django:      connection.queries   or   django-debug-toolbar
# Rails:       the development log shows every SQL statement
# Prisma:      log: ['query']

Count the queries per request, and run slow ones through EXPLAIN (Stage 2.1).

§4A Practical Policy

  • Use the ORM for CRUD and simple relationships: it's faster to write and safer.
  • Use raw SQL (still parameterized) for reports, bulk operations, window functions, and anything the ORM expresses awkwardly. Every mainstream ORM offers an escape hatch.
  • Always know your schema. An ORM doesn't replace understanding keys, indexes, and constraints; it just types the SQL for you.
  • Keep migrations as the source of truth for the schema, whether generated by the ORM or hand-written.
The key insight An ORM changes how you write queries, not what the database has to do. Each attribute access that hides a query is still a query, so count them.

§5Common Mistakes

MistakeWhat HappensFix
Accessing related objects in a loop (N+1)Hundreds of tiny queries per pageEager-load relationships or use an explicit join
Treating the ORM as a reason not to learn SQLCan't diagnose slow queries or design indexesRead the generated SQL and learn the fundamentals
Loading entire objects just to count or aggregateWasted memory and bandwidthUse count(), sum(), or projections in the database
Building raw SQL with string formatting inside the ORM escape hatchReintroduces SQL injectionKeep using bound parameters in raw queries
Practice
  1. With your ORM of choice (or any ORM tutorial project), load 50 orders with their customer names, count the queries with logging turned on, then fix any N+1 pattern and recount.
  2. Write the same "top 5 customers by spend" report once with the ORM and once in raw SQL. Which is clearer? Which would you maintain?
Key takeaways
  • ORMs map tables to objects and parameterize values for you.
  • The N+1 query is the classic ORM performance bug; eager load or join.
  • Use the ORM for routine CRUD, raw parameterized SQL for the complex, and always read the SQL it emits.
