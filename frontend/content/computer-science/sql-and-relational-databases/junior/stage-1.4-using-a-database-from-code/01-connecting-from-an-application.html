Connecting from an Application

Your application talks to a database through a driver over a connection, and understanding that connection's lifecycle prevents leaks, timeouts, and mystery errors.

§1Drivers and Connection Strings

A driver is a library that speaks the database's wire protocol on your behalf (psycopg for PostgreSQL in Python, pg in Node, JDBC in Java, sqlite3 built into Python). You point it at a database with a connection string (URL) containing the host, port, database, and credentials.

postgresql://app_user:s3cret@db.internal:5432/shop
└───────────┘ └──────────────┘ └────────────┘ └──┘ └──┘
   driver       user:password      host:port    database

Never hard-code credentials. Read them from environment variables or a secrets manager, and give your application a user with only the privileges it needs.

§2Opening, Using, and Closing

import sqlite3                       # Python example; other languages are similar

conn = sqlite3.connect("shop.db")     # open a connection
try:
    cur = conn.execute("SELECT id, name FROM customers WHERE id = ?", (1,))
    row = cur.fetchone()             # one row (a tuple), or None
    print(row)
finally:
    conn.close()                     # always release it

Use your language's structured cleanup (with in Python, try-with-resources in Java, defer in Go) so connections are closed even when an exception is thrown. A leaked connection holds server resources until the process dies.

§3Connections Are Expensive

Opening a connection involves a network round trip, authentication, and in PostgreSQL a whole server process. Doing it for every request is slow, and databases cap the number of simultaneous connections (often 100 by default in PostgreSQL).

bad:   request → connect → query → disconnect      (every time)
good:  app start → open N connections into a POOL
       request → borrow connection → query → return it to the pool

A connection pool keeps a few connections open and lends them out. Most frameworks provide one. Pooling gets a full lesson in Stage 3.3; for now, create the pool once at startup, and borrow and return connections rather than opening new ones.

§4Reading Results and Handling Errors

Results arrive as rows; you decide how to fetch them: one, many, or streaming. Expect failures, and handle them by type rather than swallowing them.

  • Connection errors (database down, network blip): retry with backoff, or fail clearly.
  • Constraint violations (duplicate email): turn into a friendly message for the user.
  • Timeouts: set them; a query without a timeout can hold a connection indefinitely.
The key insight A connection is a scarce, stateful resource, closer to a file handle than a function call. Acquire it late, release it early, and always release it, even on errors.

§5Common Mistakes

MistakeWhat HappensFix
Hard-coding passwords in source codeSecrets leak through version controlUse environment variables or a secrets manager
Opening a new connection per requestSlow responses and exhausted connection limitsUse a connection pool created at startup
Not closing connections on error pathsLeaks accumulate until the database refuses new onesUse with / try-finally / defer consistently
No query or connect timeoutsOne stuck query can freeze a whole workerSet connect and statement timeouts
Practice
  1. Write a small script that connects to your database, prints the number of customers, and closes the connection even if the query fails (simulate failure by misspelling the table).
  2. Look up the maximum number of connections your database allows (SHOW max_connections; in PostgreSQL). Estimate how many your app would open with 50 concurrent requests and no pool.
Key takeaways
  • Drivers and connection strings connect your code to the database; keep credentials out of source.
  • Always close connections, using the language's structured cleanup.
  • Connections are costly and limited; reuse them with a pool.
