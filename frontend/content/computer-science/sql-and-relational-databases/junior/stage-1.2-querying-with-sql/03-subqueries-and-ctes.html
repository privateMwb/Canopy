Subqueries & CTEs

Subqueries let one query use the result of another, and common table expressions (CTEs) give those intermediate results names so long queries stay readable.

§1Subqueries in Three Places

A subquery is a SELECT inside another statement. Where it appears determines what it can return.

-- 1. Scalar subquery: returns one value, used like a number
SELECT name, price
FROM products
WHERE price > (SELECT AVG(price) FROM products);

-- 2. List subquery: returns one column, used with IN
SELECT name FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE total > 100);

-- 3. Derived table: returns rows, used in FROM
SELECT c.name, t.spent
FROM customers c
JOIN (SELECT customer_id, SUM(total) AS spent
      FROM orders GROUP BY customer_id) AS t
  ON t.customer_id = c.id;

§2Correlated Subqueries and EXISTS

A correlated subquery refers to the outer query's current row, so it conceptually runs once per outer row. EXISTS is the standard form: it asks only whether any row matches.

-- Customers who have placed at least one order over $100
SELECT c.name
FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.id AND o.total > 100
);

EXISTS and NOT EXISTS are usually the safest way to express "has / has no matching rows". Prefer NOT EXISTS over NOT IN, which misbehaves when the subquery can return NULL.

§3CTEs: Naming Your Steps

A common table expression uses WITH to define a named, temporary result you can reference like a table. It turns a nested query into a top-to-bottom sequence of steps.

WITH customer_spend AS (
  SELECT customer_id, SUM(total) AS spent
  FROM orders
  GROUP BY customer_id
),
averages AS (
  SELECT AVG(spent) AS avg_spent FROM customer_spend
)
SELECT c.name, s.spent
FROM customer_spend s
JOIN customers c ON c.id = s.customer_id
CROSS JOIN averages a
WHERE s.spent > a.avg_spent
ORDER BY s.spent DESC;

Each CTE can use the ones before it. The query reads like a recipe: compute spend, compute the average, then compare.

§4Choosing Between Joins, Subqueries, and CTEs

Many questions can be written several ways, and modern optimizers often produce the same plan for all of them. Choose by readability:

  • A join when you need columns from both tables.
  • EXISTS / IN when you only need to test for presence.
  • A CTE when a query has several logical steps or reuses a result.
  • A derived table for a quick one-off aggregation in a join.

Note that in some databases (older PostgreSQL versions especially) a CTE could act as an optimization barrier. Check your version's behavior if performance matters.

The key insight Write the query as steps you could explain aloud: first this set, then that summary, then compare. A CTE per step is easier to read, test, and debug than one deeply nested statement.

§5Common Mistakes

MistakeWhat HappensFix
Using NOT IN with a subquery that can return NULLThe whole condition becomes unknown and returns no rowsUse NOT EXISTS, or filter NULLs out of the subquery
Scalar subquery returning several rowsRuntime errorAggregate it, add LIMIT 1 deliberately, or use a join
Deeply nested subqueriesUnreadable and hard to debugRewrite as a chain of CTEs and test each step alone
Assuming a correlated subquery is always slowPremature rewriting that hurts clarityMeasure with EXPLAIN (Stage 2.1) before changing it
Practice
  1. Find products priced above the average price of their own category (a correlated subquery), then rewrite it with a CTE that precomputes category averages.
  2. Write a query for customers who have never ordered, once using LEFT JOIN ... IS NULL and once using NOT EXISTS. Confirm they return the same rows.
Key takeaways
  • Subqueries can return a value, a list, or a table, depending on where they sit.
  • EXISTS is the clean way to test for related rows; avoid NOT IN with possible NULLs.
  • CTEs name each step, making long queries readable and testable.
