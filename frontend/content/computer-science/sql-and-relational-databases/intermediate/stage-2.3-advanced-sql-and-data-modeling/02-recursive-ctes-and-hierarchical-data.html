Recursive CTEs & Hierarchical Data

Recursive CTEs let a query repeatedly feed its own output back in, which is how SQL walks trees and graphs such as org charts and category hierarchies.

§1Hierarchies in Tables

The simplest way to store a tree is an adjacency list: each row points at its parent.

CREATE TABLE categories (
  id        INTEGER PRIMARY KEY,
  name      TEXT NOT NULL,
  parent_id INTEGER REFERENCES categories(id)       -- NULL for the root
);

It's easy to write and update, but a plain query can only follow one level at a time. "All descendants of Electronics" requires repeating the join to an unknown depth, which is what recursion is for.

§2Anatomy of a Recursive CTE

A recursive CTE has an anchor query (the starting rows) combined with UNION ALL to a recursive query that refers to the CTE itself. The database runs the recursive part repeatedly on the rows produced in the previous round until no new rows appear.

WITH RECURSIVE subtree AS (
  SELECT id, name, parent_id, 0 AS depth                  -- anchor: the starting node
  FROM categories WHERE name = 'Electronics'
  UNION ALL
  SELECT c.id, c.name, c.parent_id, s.depth + 1           -- recursive: children of what we have
  FROM categories c
  JOIN subtree s ON c.parent_id = s.id
)
SELECT * FROM subtree ORDER BY depth, name;

Walking up works the same way: start at a node and repeatedly join to its parent to get the full breadcrumb path.

§3Paths, Cycles, and Limits

Carry extra columns to build a path, and use it to detect cycles in graphs that might loop.

WITH RECURSIVE walk AS (
  SELECT id, name, name::text AS path, ARRAY[id] AS seen          -- PostgreSQL syntax
  FROM categories WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.name, w.path || ' > ' || c.name, w.seen || c.id
  FROM categories c JOIN walk w ON c.parent_id = w.id
  WHERE NOT c.id = ANY(w.seen)                                   -- stop if already visited
)
SELECT path FROM walk;
-- 'Electronics', 'Electronics > Phones', 'Electronics > Phones > Accessories', ...

Always ensure termination: either the data is genuinely acyclic, or you track visited nodes, or you cap depth.

§4Other Ways to Model Trees

ModelStrengthWeakness
Adjacency list (parent_id)Simple; cheap inserts and movesNeeds recursion for subtree queries
Materialized path ('/1/4/9/')Fast subtree via LIKE '/1/4/%'Moving a subtree rewrites many rows
Nested sets (lft, rgt)Very fast subtree readsExpensive writes
Closure table (all ancestor-descendant pairs)Fast queries, easy movesExtra table, more storage
PostgreSQL ltreePath queries with indexesPostgreSQL-specific

With recursive CTEs available, an adjacency list is the best starting point for most applications. Reach for closure tables when read performance on deep trees matters.

The key insight A recursive CTE is a loop expressed as a query: start with some rows, repeatedly derive new rows from the latest ones, stop when nothing new appears. Guarantee that ending, or the query never finishes.

§5Common Mistakes

MistakeWhat HappensFix
No termination condition on cyclic dataThe query runs forever or until a limit is hitTrack visited ids or cap depth
Forgetting RECURSIVE (PostgreSQL, MySQL) or the anchor/recursive splitSyntax error or unexpected resultsUse WITH RECURSIVE with UNION ALL between anchor and step
Using UNION instead of UNION ALL in the recursive stepNeedless de-duplication cost, and sometimes different resultsUse UNION ALL unless you intentionally need dedupe
Choosing an exotic tree model up frontComplex writes for a tree that rarely needs fast readsStart with an adjacency list; migrate if measurements demand
Practice
  1. Create an employees(id, name, manager_id) table and write a recursive query listing everyone who reports (directly or indirectly) to a given manager, with their depth.
  2. Write a query that returns the full path from a category up to its root (e.g. Phones > Electronics) by walking the tree upward.
Key takeaways
  • Adjacency lists store trees simply but need recursion for subtree queries.
  • A recursive CTE has an anchor query plus a recursive step joined by UNION ALL.
  • Guard against cycles with visited-tracking or a depth limit.
