Views, Triggers & Stored Procedures

Views, triggers, and stored procedures keep logic inside the database, which guarantees consistency for every client but makes that logic harder to test, version, and see.

§1Views: Saved Queries

A view is a named query that behaves like a table. It stores no data; each time you query it, the database runs the underlying SELECT.

CREATE VIEW customer_spend AS
SELECT c.id, c.name, COUNT(o.id) AS orders, COALESCE(SUM(o.total), 0) AS spent
FROM customers c LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name;

SELECT * FROM customer_spend WHERE spent > 500;

Views simplify complex joins, give analysts a stable interface, and can restrict access (expose some columns or rows but not others).

A materialized view stores the result physically and must be refreshed, so you trade freshness for speed:

CREATE MATERIALIZED VIEW daily_sales AS SELECT ... ;
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales;     -- PostgreSQL; needs a unique index

§2Triggers: Reacting to Changes

A trigger runs a function automatically when a row is inserted, updated, or deleted.

CREATE FUNCTION touch_updated_at() RETURNS trigger AS $$
BEGIN
  NEW.updated_at := now();
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_products_touch
BEFORE UPDATE ON products
FOR EACH ROW EXECUTE FUNCTION touch_updated_at();

Good uses: maintaining updated_at, writing audit logs, enforcing rules that can't be expressed as constraints. The danger is invisible behavior: an UPDATE quietly does extra work, triggers can cascade into other triggers, and they slow bulk operations.

§3Stored Procedures and Functions

Functions and procedures run application logic inside the database, close to the data.

CREATE FUNCTION order_total(p_order_id INTEGER) RETURNS NUMERIC AS $$
  SELECT COALESCE(SUM(qty * unit_price), 0) FROM order_items WHERE order_id = p_order_id;
$$ LANGUAGE sql STABLE;

SELECT id, order_total(id) FROM orders WHERE customer_id = 1;

They cut network round trips and apply the same logic to every client, but the language (PL/pgSQL, T-SQL, PL/SQL) is a separate skill, tooling for testing and debugging is weaker, and the code is easy to forget about when it's not in your application repository.

§4Where Should Logic Live?

Put it in the database whenKeep it in the application when
Many different programs write to the dataOne service owns all writes
It's an integrity rule (a constraint, audit trail)It's business policy that changes often
It processes big sets of rows (set-based work)You need unit tests, debuggers, feature flags
Round-trip latency mattersYou must scale logic horizontally

Whichever you choose, keep the code in version control (as migrations) and document it. Constraints and simple triggers are low-risk; large procedural systems tend to become hard to maintain.

The key insight Logic in the database is enforced for every client, but it's hidden from your application code and your test suite. Use it for integrity and data-shaped work, and keep changing business policy where developers will find it.

§5Common Mistakes

MistakeWhat HappensFix
Triggers that call other triggers or do heavy workSlow writes and surprising cascadesKeep triggers small and single-purpose; document them
Relying on a view's definition changing nothing for performanceA complex view hides an expensive query behind a simple nameCheck plans through the view; consider a materialized view
Forgetting to refresh a materialized viewUsers see stale numbersSchedule refreshes and show a freshness timestamp
Procedures edited directly on the serverNo history, no review, environments differDefine all database code in version-controlled migrations
Practice
  1. Create a view for a three-table report and a materialized version of it. Compare query times, then change the underlying data and show when each reflects it.
  2. Add an audit_log table and a trigger that records old and new values whenever a product's price changes.
Key takeaways
  • Views name queries; materialized views store results and need refreshing.
  • Triggers and procedures enforce logic for every client but add hidden behavior and maintenance cost.
  • Keep database code in version control and use it where integrity or set-based speed justifies it.
