Reading EXPLAIN Plans

EXPLAIN shows the plan the database chose to run a query, and learning to read it is the single most useful performance skill.

§1Asking for the Plan

EXPLAIN prints the plan without running the query. EXPLAIN ANALYZE runs it and adds real timings and row counts, so wrap data-changing statements in a transaction you roll back.

EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 42 ORDER BY placed_at DESC LIMIT 10;

 Limit  (cost=0.43..8.9 rows=10) (actual time=0.03..0.05 rows=10 loops=1)
   ->  Index Scan Backward using idx_orders_cust_date on orders
         Index Cond: (customer_id = 42)
 Planning Time: 0.15 ms
 Execution Time: 0.08 ms

Read a plan from the innermost, most-indented node outward: each node feeds its result to its parent. (SQLite uses EXPLAIN QUERY PLAN; MySQL uses EXPLAIN and EXPLAIN ANALYZE too.)

§2Scan Types

NodeMeaningTypical use
Seq ScanRead every row of the tableSmall tables, or most rows needed
Index ScanWalk the index, then fetch rows from the tableSelective filters
Index Only ScanAnswer entirely from the indexCovering indexes
Bitmap Heap ScanCollect matching locations, then read them in orderModerately selective filters or combined indexes

A Seq Scan isn't automatically bad. If you need 60% of the table, reading it sequentially beats jumping around via an index. It's a problem when you needed a handful of rows and read millions.

§3Join Strategies

  • Nested Loop: for each row on one side, look up matches on the other. Great when one side is small and the other is indexed.
  • Hash Join: build a hash table of one side, probe it with the other. Good for large, unsorted inputs.
  • Merge Join: walk two sorted inputs together. Efficient when both are already sorted (e.g. via indexes).

You rarely choose; the planner does, based on row estimates. Your job is to notice when its choice is bad, and ask why.

§4What to Look For

  1. Estimated vs. actual rows. rows=10 estimated but rows=500000 actual means the planner was misinformed (see Lesson 4), so it likely chose a poor plan.
  2. Where the time goes. actual time is per node: find the node with the largest share.
  3. Scans over large tables where you expected an index.
  4. Sorts that spill to disk (Sort Method: external merge), which signal memory pressure or a missing index to provide order.
  5. loops=N with big N: a nested loop executing an expensive inner step many times.
-- Useful extra detail in PostgreSQL
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;     -- shows pages read from cache vs. disk
The key insight The plan tells you what the database actually did, not what you hoped it did. Always compare estimated rows to actual rows: large gaps are the clue to most bad plans.

§5Common Mistakes

MistakeWhat HappensFix
Guessing at slow queries instead of reading the planTime spent adding indexes that aren't usedRun EXPLAIN ANALYZE first and find the expensive node
Running EXPLAIN ANALYZE on a destructive statementIt really executes the INSERT/UPDATE/DELETEWrap in BEGIN … ROLLBACK
Testing on tiny development dataThe planner picks different plans at scaleTest with production-sized data or a copy
Treating every Seq Scan as a bugPointless indexes on small or mostly-read tablesJudge by rows needed vs. rows read
Practice
  1. On your million-row table, run EXPLAIN ANALYZE for a filter on an unindexed column, add an index, and run it again. Note the scan type, time, and rows read before and after.
  2. Find a query where estimated rows and actual rows differ by 10× or more. Run ANALYZE tablename; and see whether the estimate improves.
Key takeaways
  • EXPLAIN shows the chosen plan; EXPLAIN ANALYZE adds actual timings and row counts.
  • Know the scan and join node types, and read plans from the inside out.
  • Gaps between estimated and actual rows reveal planner misjudgments.
