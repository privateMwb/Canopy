How B-Tree Indexes Work

An index is a separate, sorted structure that lets the database find rows without reading the whole table, and the B-tree is the structure behind almost all of them.

§1The Cost of Not Having One

Without an index, SELECT * FROM orders WHERE customer_id = 42 forces a sequential scan: the database reads every row of the table and checks each one. On 1,000 rows that's instant. On 100 million it's seconds to minutes, and it gets slower in proportion to table size.

An index is like the index at the back of a book: instead of reading every page to find "TLS", you look it up in a sorted list that tells you which pages to turn to.

CREATE INDEX idx_orders_customer ON orders (customer_id);

§2How a B-Tree Is Organized

A B-tree keeps keys in sorted order in a shallow, wide tree of fixed-size pages (usually 4–16 KB). Each internal page holds many keys and pointers to child pages, so the tree is very flat.

                  [ 300 | 600 ]                 ← root page
                 /      |      \
        [100|200]   [400|500]   [700|800]        ← internal pages
        /  |   \     ...          ...
   leaf pages: sorted keys + pointers to table rows   (leaves are linked left→right)

A lookup walks from the root down to a leaf: a few page reads even for hundreds of millions of rows. With a fan-out of several hundred keys per page, a 3–4 level tree covers billions of rows. That is O(log n) lookup, versus O(n) for a scan.

Because the leaves are sorted and linked, a B-tree also serves range queries (BETWEEN, <, >), ORDER BY, and prefix searches (LIKE 'abc%') efficiently, not just exact matches.

§3What Indexes Cost

Indexes aren't free. Each one:

  • Takes disk space (often 20–50% of the table size or more, per index).
  • Slows every write: each INSERT, UPDATE, or DELETE touching indexed columns must also update every affected index.
  • Competes for memory: hot index pages want to stay cached.

So the question is never "should I index everything?" but "which queries are worth speeding up, at what write cost?" Read-heavy tables tolerate many indexes; write-heavy ones prefer few.

§4What Gets Indexed Automatically

Primary keys and UNIQUE constraints create an index automatically, because the database needs one to enforce uniqueness quickly. Foreign keys usually do not (in PostgreSQL and SQLite; MySQL's InnoDB does create one). Joins and ON DELETE checks on the referencing column are slow without an index, so index foreign-key columns by default.

-- PostgreSQL: see the indexes on a table
\d orders
-- SQLite
PRAGMA index_list('orders');
The key insight An index turns a search over n rows into a walk down a short tree. You pay for that with extra storage and slower writes, so index the columns your real queries filter, join, and sort on.

§5Common Mistakes

MistakeWhat HappensFix
Not indexing foreign-key columnsJoins and cascading deletes scan the child tableCreate an index on each foreign key you join or delete through
Indexing every column "just in case"Writes slow down and storage balloons for little read benefitIndex based on actual query patterns
Assuming an index is always usedThe planner may still pick a scan (e.g. when most rows match)Check with EXPLAIN (Lesson 3)
Forgetting that indexes add write costBulk loads and heavy-insert tables get slowDrop and rebuild indexes for big loads; keep write-heavy tables lean
Practice
  1. Generate a table with a million rows (for example with generate_series in PostgreSQL). Time a lookup on an unindexed column, create an index, and time it again.
  2. Estimate the height of a B-tree for 100 million keys if each page holds about 400 keys. How many page reads does a lookup need?
Key takeaways
  • Without an index, filtering a table means scanning every row.
  • B-trees keep keys sorted in a shallow tree, giving O(log n) lookups and efficient range scans.
  • Every index speeds some reads and slows every write; choose them deliberately.
