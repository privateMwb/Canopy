Composite, Covering & Partial Indexes

Composite indexes cover several columns in a specific order, covering indexes can answer a query without touching the table, and partial indexes include only the rows you care about.

§1Composite Indexes and Column Order

A composite index sorts by the first column, then by the second within equal first values, and so on, like a phone book sorted by last name, then first name.

CREATE INDEX idx_orders_cust_date ON orders (customer_id, placed_at);

This index serves queries that use a leftmost prefix of its columns:

Query filters onUses the index?
customer_id = 5Yes
customer_id = 5 AND placed_at > '2026-01-01'Yes, fully
customer_id = 5 ORDER BY placed_atYes, and the sort is free
placed_at > '2026-01-01' onlyNo (or poorly): the leading column isn't constrained

A phone book is useless for finding everyone named "Ada" if you don't know the last name. Put equality columns first, then the range or sort column.

§2Covering Indexes: Skipping the Table

Normally the index finds a row's location, then the database fetches the row from the table. If the index itself contains every column the query needs, the table visit is skipped entirely: an index-only scan.

-- Query: SELECT customer_id, placed_at, total FROM orders WHERE customer_id = 5;
CREATE INDEX idx_orders_cover
  ON orders (customer_id, placed_at) INCLUDE (total);     -- PostgreSQL 11+, SQL Server

INCLUDE stores extra columns in the index leaves without making them part of the sort key. The trade-off is a larger index, so cover only your hottest queries.

§3Partial and Expression Indexes

A partial index indexes only the rows matching a condition, which keeps it small and fast.

-- Only a few orders are 'pending'; index just those
CREATE INDEX idx_orders_pending ON orders (placed_at) WHERE status = 'pending';

-- Uniqueness for only the active rows (allows re-using an email after soft delete)
CREATE UNIQUE INDEX idx_users_email_active ON users (email) WHERE deleted_at IS NULL;

An expression index indexes a computed value, so queries on that same expression can use it.

CREATE INDEX idx_users_lower_email ON users (lower(email));
SELECT * FROM users WHERE lower(email) = 'ada@example.com';    -- now indexed

§4Unique, Hash, and Other Index Types

  • UNIQUE indexes enforce uniqueness and are used like any other.
  • B-tree is the default and handles equality and ranges.
  • Hash indexes (PostgreSQL) support only equality; rarely better than B-tree.
  • GIN / GiST (PostgreSQL) index arrays, JSON, full-text search, and geometric data.
  • Full-text and trigram indexes help search patterns like LIKE '%word%', which a B-tree can't.
The key insight Index column order is semantic, not cosmetic. A composite index on (a, b) is a sorted list of a, then b. It can answer questions that start with a, but not questions about b alone.

§5Common Mistakes

MistakeWhat HappensFix
Putting the range column before the equality columnThe index can't narrow as much as it couldOrder: equality columns first, then range/sort
Creating separate single-column indexes for a two-column filterThe planner uses one and filters the rest, or merges them slowlyCreate one composite index matching the query
Wrapping an indexed column in a function (lower(email)) without an expression indexThe plain index can't be usedIndex the expression, or store the normalized value
Over-covering with many INCLUDE columnsHuge indexes that cost more than they saveCover only the hottest, narrowest queries
Practice
  1. For the query WHERE customer_id = ? AND status = 'paid' ORDER BY placed_at DESC LIMIT 20, design the best composite index and justify the column order.
  2. Create a partial index for pending orders only. Compare its size to a full index on the same column with pg_relation_size (or the equivalent).
Key takeaways
  • Composite indexes work on a leftmost prefix; put equality columns first, then range or sort.
  • Covering indexes enable index-only scans by including needed columns.
  • Partial and expression indexes target exactly the rows and expressions your queries use.
