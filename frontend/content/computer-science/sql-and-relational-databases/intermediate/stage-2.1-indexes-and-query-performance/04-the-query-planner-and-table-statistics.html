The Query Planner & Table Statistics

The query planner estimates the cost of many possible plans using statistics about your data and picks the cheapest, so wrong statistics produce wrong plans.

§1A Cost-Based Optimizer

Your SQL says what you want, not how to get it. The planner enumerates strategies (which index, which join order, which join algorithm), estimates a cost for each, and runs the cheapest. The estimates depend on:

  • Table size: rows and pages.
  • Value distribution: how many distinct values, the most common ones, and histograms of the rest.
  • Selectivity: the fraction of rows a condition keeps. WHERE country = 'US' may keep 60% (scan), whereas WHERE id = 5 keeps one row (index).
  • Cost constants: how expensive a random page read is compared with a sequential one.

§2Statistics and ANALYZE

These statistics are gathered by ANALYZE (run automatically by autovacuum in PostgreSQL, but not instantly after every change).

ANALYZE orders;                                  -- refresh statistics for one table
SELECT n_distinct, most_common_vals
FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';

ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;   -- finer histogram for a skewed column

After a bulk load, a mass delete, or a big change in data distribution, statistics can be stale. The plan was good yesterday, and today it isn't, with no code change: classic stale-statistics behavior.

§3Why Estimates Go Wrong

  • Stale statistics: data changed since the last ANALYZE.
  • Correlated columns: the planner assumes columns are independent, so city = 'Paris' AND country = 'France' is estimated as far rarer than it is. PostgreSQL's CREATE STATISTICS can describe the dependency.
  • Skewed data: one value covers 90% of the rows. Plans that suit rare values are terrible for the common one.
  • Expressions and functions: the planner often can't estimate WHERE lower(name) LIKE ... without an expression index.
  • Parameterized queries: a plan cached for one parameter value may be wrong for another ("parameter sniffing").

§4Working with the Planner

In order of preference:

  1. Make sure statistics are fresh (ANALYZE).
  2. Give it better options: the right index, extended statistics, a rewritten query.
  3. Simplify the query so estimates are easier (break huge queries into CTEs or temporary tables).
  4. As a last resort, use hints or settings. PostgreSQL has none by design, but you can adjust enable_* flags temporarily when diagnosing, and MySQL and SQL Server offer index hints.
SET enable_seqscan = off;       -- diagnosis only: does an index plan run faster?

Don't leave such overrides in production code: they freeze a decision the planner should keep making as the data changes.

The key insight The optimizer is only as good as its statistics. When a query suddenly gets slow with no code change, suspect stale or misleading statistics before blaming the hardware.

§5Common Mistakes

MistakeWhat HappensFix
Never running ANALYZE after a bulk loadThe planner thinks the table is empty and picks nested loopsRun ANALYZE after large data changes
Forcing plans with hints in productionThe override becomes wrong as data growsFix statistics or indexes; keep hints for diagnosis
Ignoring correlated columnsRow estimates are off by orders of magnitudeCreate extended statistics for related columns
Blaming the database for a "random" slowdownReal cause (stale stats, plan flip) remainsCompare plans before and after; check estimated vs. actual rows
Practice
  1. Bulk-insert 500,000 rows into a fresh table, run EXPLAIN on a selective query before and after ANALYZE, and compare the plans.
  2. Create a table where one status value covers 95% of rows. Compare the plans for status = 'common' and status = 'rare', and explain why they differ.
Key takeaways
  • The planner chooses the cheapest plan by estimating costs from table statistics.
  • Stale, skewed, or correlated data leads to bad estimates and bad plans.
  • Refresh statistics and give the planner better options before reaching for hints.
