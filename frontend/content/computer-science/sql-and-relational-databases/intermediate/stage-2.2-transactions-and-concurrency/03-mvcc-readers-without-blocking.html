MVCC: Readers Without Blocking

Multi-version concurrency control (MVCC) keeps several versions of each row so readers see a consistent snapshot without blocking writers, and writers don't block readers.

§1The Idea: Versions Instead of Locks

With plain locking, a reader would have to wait for a writer to finish. MVCC avoids that: an UPDATE doesn't overwrite a row, it creates a new version and marks the old one as superseded. Each transaction sees the versions that were current when its snapshot was taken.

Row id=1 (balance)
  version A: balance=500   created by tx 100, ended by tx 205
  version B: balance=400   created by tx 205, still current

A transaction that started before 205 (and hasn't seen it commit) keeps reading version A.
One that starts after 205 commits reads version B.

The practical result: readers never block writers and writers never block readers. Only two writers touching the same row conflict.

§2How PostgreSQL Does It

Each row version carries hidden system columns: xmin (the transaction that created it) and xmax (the one that deleted or replaced it).

SELECT xmin, xmax, * FROM accounts WHERE id = 1;

A snapshot is essentially a list of which transaction ids were committed when you started. A version is visible if its creator is visible to you and its deleter isn't. Old versions stay in the table as dead tuples until cleaned up. MySQL's InnoDB works differently: it updates in place and keeps old versions in an undo log to reconstruct them.

§3The Price: Cleaning Up Old Versions

Dead row versions must eventually be removed or the table bloats.

  • PostgreSQL uses VACUUM (run automatically by autovacuum) to reclaim dead tuples and mark space reusable.
  • A long-running transaction pins its snapshot, so versions it might still need can't be removed. A forgotten open transaction (idle in transaction) can cause table bloat across the whole database.
  • Heavy update workloads generate many dead tuples; tuning autovacuum for hot tables is routine.
SELECT pid, now() - xact_start AS age, state, left(query, 50)
FROM pg_stat_activity
WHERE xact_start IS NOT NULL ORDER BY age DESC LIMIT 5;     -- find old transactions

§4What MVCC Doesn't Solve

Snapshots protect readers, but two transactions can still read the same data and write conflicting results. Snapshot isolation allows write skew (Lesson 1), and concurrent updates of the same row still need locking or conflict detection. In PostgreSQL's REPEATABLE READ, the second writer to update an already-changed row gets a serialization error and must retry.

The key insight MVCC swaps waiting for storage. Readers get a stable snapshot for free, but old row versions must be garbage-collected, and a transaction left open pins that garbage in place.

§5Common Mistakes

MistakeWhat HappensFix
Leaving transactions open (idle in transaction)Prevents cleanup; tables and indexes bloatAlways end transactions; set idle_in_transaction_session_timeout
Assuming reads can never conflict with anythingSnapshot reads can still lead to write skewUse SERIALIZABLE or explicit locks for cross-row invariants
Disabling autovacuum to "save resources"Runaway bloat and eventually transaction-id wraparound riskTune autovacuum rather than turning it off
Running huge reporting queries on the primary for hoursHolds back cleanup for the whole systemRun long reports on a replica or in batches
Practice
  1. In PostgreSQL, update a row three times and query xmin, xmax, ctid. Then run VACUUM and observe how the table changes.
  2. Open a transaction in one session and leave it idle. In another, update a table repeatedly and watch n_dead_tup in pg_stat_user_tables before and after closing the first session.
Key takeaways
  • MVCC keeps multiple row versions so readers and writers don't block each other.
  • Each transaction reads a consistent snapshot; old versions must be vacuumed.
  • Long-open transactions block cleanup and cause bloat.
