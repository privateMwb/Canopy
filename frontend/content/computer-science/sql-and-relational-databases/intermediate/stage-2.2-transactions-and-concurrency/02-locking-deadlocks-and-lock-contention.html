Locking, Deadlocks & Lock Contention

Locks are how databases keep concurrent writers from clobbering each other, and deadlocks are what happens when transactions wait for one another in a circle.

§1Lock Modes and Granularity

A lock reserves something (a row, a page, a table) for a transaction. The two basic modes:

  • Shared (read) locks: many transactions can hold one at once.
  • Exclusive (write) locks: only one holder; blocks everyone else.

Locks are held at different granularities. Row-level locks allow high concurrency; table-level locks (taken by many schema changes) block a lot.

-- Explicitly lock rows you're about to modify
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;     -- exclusive row lock until COMMIT
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

Writers normally take row locks automatically: UPDATE locks the rows it changes until the transaction ends. A second transaction updating the same row waits.

§2Deadlocks

A deadlock is a cycle of waiting: each transaction holds a lock the other needs.

T1: UPDATE accounts SET ... WHERE id = 1;     -- T1 locks row 1
T2: UPDATE accounts SET ... WHERE id = 2;     -- T2 locks row 2
T1: UPDATE accounts SET ... WHERE id = 2;     -- T1 waits for T2
T2: UPDATE accounts SET ... WHERE id = 1;     -- T2 waits for T1   ← deadlock

Neither can proceed. The database detects the cycle, picks a victim, aborts it with an error, and lets the other finish. The error (deadlock detected in PostgreSQL, error 1213 in MySQL) is normal operation, not a bug in the database. Your code must retry.

§3Preventing Deadlocks

  • Lock in a consistent order. If every transaction updates the lower account id first, a cycle can't form.
  • Keep transactions short so locks are held briefly.
  • Touch fewer rows and avoid scanning updates that lock lots of rows.
  • Retry on deadlock errors, with a small random delay.
-- Always order by id when locking multiple rows
SELECT * FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;

§4Seeing and Taming Contention

When queries are slow because they're waiting, not working, EXPLAIN won't show it. Look at the lock state instead.

-- PostgreSQL: who is blocked, and by whom?
SELECT pid, wait_event_type, wait_event, state, left(query, 60)
FROM pg_stat_activity WHERE wait_event_type = 'Lock';

SELECT pg_blocking_pids(12345);       -- who blocks pid 12345?
SET lock_timeout = '2s';              -- fail fast rather than queue forever

Hot rows (a global counter, a "last updated" row everyone writes) serialize all writers. Spread the contention: shard counters, use per-user rows, or queue the updates.

The key insight A deadlock is an ordering problem. If all code acquires locks in the same order, cycles are impossible. And since you can't prevent every one, treat deadlock errors as retryable.

§5Common Mistakes

MistakeWhat HappensFix
Locking rows in different orders in different code pathsDeadlocks under loadDefine one canonical lock order (for example by id)
Holding a transaction open while waiting on a user or APILocks pile up and everything else blocksDo slow work outside the transaction
Not handling deadlock errorsUsers see failures that a retry would have fixedCatch the error and retry the whole transaction
A single hot row everyone updatesAll writers serialize on that rowRedesign: partition the counter or aggregate asynchronously
Practice
  1. Create the two-account deadlock with two sessions, observe the error, then fix it by locking in id order.
  2. In one session open a transaction and UPDATE a row without committing. From a second session, find the blocked query using pg_stat_activity and pg_blocking_pids.
Key takeaways
  • Writers lock the rows they change; others wait until commit or rollback.
  • Deadlocks are cycles of waiting; the database aborts one victim, and your code should retry.
  • Consistent lock ordering and short transactions prevent most deadlocks.
