Isolation Levels & Anomalies

Isolation levels define how much one running transaction can see of another's work, and each level up the ladder prevents a specific kind of anomaly at a cost in concurrency.

§1Why Isolation Is a Dial

Perfect isolation would make every transaction behave as if it ran alone, one after another (serializable execution). That's the simplest to reason about but the most expensive, because transactions must wait for or abort each other. So SQL defines weaker levels that allow some interference in exchange for speed, and you choose per transaction.

§2The Anomalies

Each anomaly is a way concurrent transactions can surprise you.

AnomalyWhat happens
Dirty readYou read data another transaction has written but not yet committed (and may roll back)
Non-repeatable readYou read a row twice in one transaction and get different values because someone committed a change in between
Phantom readYou run the same range query twice and get different sets of rows, because someone inserted or deleted matching rows
Lost updateTwo transactions read a value, both compute a new one, and the second write overwrites the first
Write skewTwo transactions each check a condition on overlapping data, then update different rows, jointly breaking a rule neither broke alone
-- Lost update: two sessions each add 10 to the same counter
T1: SELECT stock FROM items WHERE id=1;    -- 50
T2: SELECT stock FROM items WHERE id=1;    -- 50
T1: UPDATE items SET stock = 40 WHERE id=1;   -- 50 - 10
T2: UPDATE items SET stock = 40 WHERE id=1;   -- 50 - 10  ← T1's change is lost

§3The Four Standard Levels

LevelDirty readNon-repeatablePhantom
READ UNCOMMITTEDpossiblepossiblepossible
READ COMMITTEDpreventedpossiblepossible
REPEATABLE READpreventedpreventedpossible*
SERIALIZABLEpreventedpreventedprevented

*The standard allows phantoms at REPEATABLE READ, but implementations vary: PostgreSQL's REPEATABLE READ uses snapshot isolation and prevents them, yet still allows write skew. MySQL's InnoDB uses gap locks to limit phantoms.

Defaults differ: PostgreSQL, Oracle, and SQL Server default to READ COMMITTED; MySQL InnoDB defaults to REPEATABLE READ. PostgreSQL doesn't truly implement READ UNCOMMITTED (it behaves as READ COMMITTED).

BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ... statements ...
COMMIT;        -- may fail with a serialization error: be ready to retry

§4Choosing a Level

  • READ COMMITTED is a sound default for most OLTP work, as long as you don't assume values stay put between statements.
  • REPEATABLE READ suits reports that need a consistent snapshot across several queries.
  • SERIALIZABLE is the right tool when correctness depends on invariants across rows (booking, balances). It simplifies your reasoning but requires retrying transactions that the database aborts to preserve serial order.

The safest way to code against stronger isolation is a retry loop around the whole transaction on serialization failures (SQLSTATE 40001) and deadlocks (40P01).

The key insight Higher isolation moves complexity from your reasoning to the database's bookkeeping. Your code must then handle the new failure mode: transactions that get aborted and need a retry.

§5Common Mistakes

MistakeWhat HappensFix
Read-modify-write in application code at READ COMMITTEDLost updates under concurrencyUse an atomic UPDATE ... SET x = x - 1, SELECT FOR UPDATE, or a higher level
Assuming REPEATABLE READ means the same in every databaseDifferent anomalies are possible depending on the engineRead your database's documentation for each level
Using SERIALIZABLE without retry logicRandom user-visible failuresRetry the whole transaction on serialization errors
Checking a condition and then acting in separate statementsWrite skew breaks invariants like "at least one doctor on call"Lock the rows involved or use SERIALIZABLE
Practice
  1. Using two psql or sqlite3 sessions, reproduce a non-repeatable read at READ COMMITTED, then show it disappears at REPEATABLE READ.
  2. Reproduce the lost-update example, then fix it with an atomic UPDATE items SET stock = stock - 10. Why does that work without extra locking?
Key takeaways
  • Anomalies: dirty reads, non-repeatable reads, phantoms, lost updates, and write skew.
  • Isolation levels trade protection against anomalies for concurrency; defaults vary by database.
  • Stronger isolation requires retrying aborted transactions.
