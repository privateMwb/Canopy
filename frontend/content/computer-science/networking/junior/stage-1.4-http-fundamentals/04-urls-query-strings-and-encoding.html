URLs, Query Strings & Encoding

A URL packs several pieces of information into one string, and most encoding bugs come from not knowing which piece you're in.

§1Anatomy of a URL

https://alice@example.com:8443/shop/items?color=red&size=m#reviews
└─┬─┘   └──┬──┘ └────┬────┘└─┬─┘└─────┬─────┘└──────┬──────┘└──┬──┘
scheme  userinfo    host    port    path          query      fragment
PartRole
SchemeThe protocol (http, https)
HostThe server's name, resolved by DNS
PortDefaults to 80 for HTTP and 443 for HTTPS
PathWhich resource on the server
QueryExtra parameters as key=value pairs separated by &
FragmentA position within the page, handled by the browser and never sent to the server

Because the fragment stays on the client, a server can't see it, and it can't be used for anything the server must know.

§2Percent-Encoding

URLs may only contain a limited set of characters. Anything else, including spaces, non-ASCII text, and characters with special meaning like & and #, must be percent-encoded as % plus two hex digits.

from urllib.parse import urlencode, quote, urlparse, parse_qs

quote("a b&c")                         # 'a%20b%26c'
urlencode({"q": "rock & roll", "page": 2})
# 'q=rock+%26+roll&page=2'   (in a query string, a space may be written as +)

u = urlparse("https://example.com/search?q=cats&page=2")
u.netloc, u.path                       # ('example.com', '/search')
parse_qs(u.query)                      # {'q': ['cats'], 'page': ['2']}

The reason to encode is that an unescaped & inside a value would be read as the start of the next parameter, silently changing the meaning of the request.

§3Encoding Pitfalls

  • Encoding twice: %2520 is an encoded %20, a sign that something encoded an already-encoded value
  • Building URLs by string concatenation: use a library, since values you don't control can contain &, =, /, or #
  • Space as + vs. %20: + means a space only in query strings and form data, not in paths
  • Path vs. query: use the path to identify *which* resource, and the query to filter, sort, or modify the view of it

Security matters here too. User-supplied URLs and encoded values are a common route for injection and path-traversal attacks (such as ..%2f), so servers should decode once, validate, and reject surprises.

The key insight Always build and parse URLs with a library. Hand-assembling strings is how an & in a user's search term ends up changing the request.

§4Common Mistakes

MistakeWhat HappensFix
Concatenating user input into a URLSpecial characters change the structure of the URLEncode each component with a URL library
Expecting the server to receive the #fragmentIt's never sent; logic depending on it fails server-sideUse the query or path for anything the server needs
Double-encoding valuesBad data such as %2520 shows up in logs and queriesEncode exactly once, at the point of building the URL
Practice
  1. Take the URL https://example.com/a b?name=Tom & Jerry and produce a correctly encoded version using a library.
  2. Parse a URL with urlparse and list each component. Which parts would a web server actually receive?
Key takeaways
  • A URL has scheme, host, port, path, query, and fragment, and the fragment never reaches the server.
  • Percent-encode characters outside the allowed set, and encode each component exactly once.
  • Use a URL library rather than string concatenation.
