The HTTP Request-Response Cycle

HTTP is a plain-text conversation: the client sends a request, the server sends one response, and neither remembers the exchange afterward.

§1What a Request Looks Like

An HTTP/1.1 message is readable text. A request has a request line (method, path, version), then headers, then a blank line, then an optional body.

GET /index.html HTTP/1.1
Host: example.com
User-Agent: curl/8.4.0
Accept: */*
(blank line ends the headers)

The Host header is required in HTTP/1.1. It lets one server and one IP address host many websites and pick the right one by name. Lines end with a carriage return and line feed (\r\n).

§2What a Response Looks Like

A response has a status line (version, code, reason), headers, a blank line, and the body.

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 1256
Cache-Control: max-age=3600
(blank line)
<!doctype html>
<html> ... 1256 bytes ... </html>

Content-Length tells the client where the body ends, which matters because TCP is a byte stream with no built-in message boundaries.

§3Stateless by Design

HTTP is stateless: each request stands alone, and the server isn't required to remember anything about previous ones. This makes servers simple to scale, since any server can handle any request. Features that need memory, such as logins and shopping carts, are layered on top using cookies and tokens, which the next lessons cover.

# Type a request by hand with netcat (plain HTTP only)
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80

# Or let curl show both directions
curl -v http://example.com/

HTTP/2 and HTTP/3 carry the same ideas, methods, headers, and status codes, in a compact binary format rather than text. The semantics you learn here apply to all versions.

The key insight HTTP is just structured text over a TCP stream. Once you've seen a raw request and response, every tool and library is a convenience wrapper around that exchange.

§4Common Mistakes

MistakeWhat HappensFix
Omitting the Host header in a hand-written requestServer rejects it with 400 Bad RequestAlways send Host in HTTP/1.1
Forgetting the blank line after headersThe server waits for more headers and the request hangsEnd headers with an empty line (\r\n\r\n)
Assuming the server remembers earlier requestsFeatures break when requests hit different serversCarry state explicitly in cookies or tokens
Practice
  1. Use nc or telnet to send a hand-typed GET request to a plain HTTP site and read the raw response.
  2. Run curl -v on a site and mark the request line, request headers, status line, and response headers.
Key takeaways
  • An HTTP message is a start line, headers, a blank line, and an optional body.
  • HTTP is stateless, so each request must carry what the server needs.
  • The same semantics apply across HTTP/1.1, HTTP/2, and HTTP/3.
