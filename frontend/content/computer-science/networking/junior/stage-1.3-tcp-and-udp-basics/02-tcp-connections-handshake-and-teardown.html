TCP Connections: Handshake & Teardown

TCP establishes shared state on both ends with a three-way handshake before any data moves, and closes it with a careful exchange of FIN messages.

§1The Three-Way Handshake

TCP is connection-oriented: both sides must agree on starting sequence numbers and settings before exchanging data.

Client                                   Server
  │ ── SYN, seq=x ─────────────────────►  │   "I want to connect; my numbers start at x"
  │ ◄── SYN+ACK, seq=y, ack=x+1 ───────── │   "OK; mine start at y; I expect x+1 next"
  │ ── ACK, ack=y+1 ───────────────────►  │   "Got it"
  │ ══════════ data can now flow ═══════  │

The starting numbers are initial sequence numbers (ISNs), chosen unpredictably so that attackers can't easily inject packets. The handshake costs one full round trip before the client may send data, which is why latency to a server matters so much for short connections. On a 100 ms RTT link, that's 100 ms before your request even leaves.

§2Closing a Connection

Closing is separate for each direction, because one side may be done sending while the other still has more to say.

Client                                   Server
  │ ── FIN ───────────────────────────►  │   "I'm done sending"
  │ ◄── ACK ──────────────────────────── │
  │ ◄── FIN ──────────────────────────── │   "I'm done too"
  │ ── ACK ───────────────────────────►  │
  │ (client waits in TIME_WAIT)           │

A RST (reset) ends a connection abruptly. It's sent when a packet arrives for a connection that doesn't exist, when a port has no listener, or when a program aborts. Receiving a reset surfaces as 'connection reset by peer'.

§3Why TIME_WAIT Exists

The side that closes first ends up in TIME_WAIT, typically for 60 seconds on Linux. This protects against two problems. First, the final ACK may be lost, and the peer's retransmitted FIN needs someone to answer it. Second, delayed packets from the old connection must expire so that they can't be mistaken for part of a new connection reusing the same 5-tuple.

ss -tan state time-wait | wc -l      # how many connections are lingering
ss -tan | awk '{print $1}' | sort | uniq -c   # count of each state

A server that handles many short connections can accumulate thousands of TIME_WAIT sockets. That's normal; it only becomes a problem when it exhausts ports, covered in Stage 2.1.

The key insight TCP connection state lives only in the two endpoints' memory. Nothing in the network knows a connection exists, which is why a crashed server leaves clients waiting and why firewalls and NATs must keep their own state.

§4Common Mistakes

MistakeWhat HappensFix
Treating the handshake as freeConnection setup dominates short requests on high-latency linksReuse connections with keep-alive instead of opening new ones
Confusing 'connection refused' with a timeoutWrong diagnosis: refused means a RST came back; a timeout means silenceRefused = reachable host, no listener; timeout = packets dropped or host down
Assuming close() always sends a clean FINIf unread data is pending, the OS may send RST insteadRead and drain the connection before closing when it matters
Practice
  1. Capture a connection with tcpdump -nn 'tcp port 80' while running curl http://example.com. Identify the SYN, SYN-ACK, ACK, and the FIN exchange.
  2. Why does the client end up in TIME_WAIT rather than the server? Which side closes first in a typical HTTP/1.0 request?
Key takeaways
  • TCP's three-way handshake costs one round trip and sets up sequence numbers on both sides.
  • Each direction closes separately with FIN and ACK; RST aborts the connection immediately.
  • TIME_WAIT protects against lost final ACKs and stray old packets.
