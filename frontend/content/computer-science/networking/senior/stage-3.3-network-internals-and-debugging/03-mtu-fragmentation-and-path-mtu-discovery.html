MTU, Fragmentation & Path MTU Discovery

A connection that works for small requests and hangs on large ones is often an MTU problem, hiding behind a filtered ICMP message.

§1The Problem

Each link has an MTU, the largest packet it can carry, and Ethernet's standard is 1500 bytes. A path may include a link with a smaller MTU, commonly because of VPNs, tunnels, or cloud overlays that add their own headers. A packet bigger than a link's MTU has to be fragmented or dropped.

SetupTypical MTU
Standard Ethernet1500
WireGuard default1420
PPPoE (some DSL)1492
Jumbo frames (data centers)9000

In IPv4, a router *could* fragment a packet, but fragmentation is slow, and a lost fragment loses the whole datagram. So modern TCP sets the Don't Fragment (DF) bit and relies on discovery instead.

§2Path MTU Discovery

PMTUD works like this: the sender sends packets with DF set. A router that can't forward a packet because it's too large drops it and sends back an ICMP message, 'fragmentation needed' (type 3, code 4), which includes the next-hop MTU. The sender lowers its segment size and resends.

Sender (MTU 1500) ──► Router A ──► Router B (link MTU 1400) ──► ...
  sends 1500-byte packet, DF set
                         Router B drops it
  ◄── ICMP 'fragmentation needed, MTU 1400' ──
  sender now uses 1400-byte packets

IPv6 routers never fragment; only the sender may, so PMTUD (via ICMPv6 'Packet Too Big') is mandatory there.

§3The Blackhole Failure

Many firewalls drop all ICMP as a misguided security measure. Then the 'too big' message never arrives, and the sender keeps resending packets that can never get through. The symptom is distinctive: the TCP handshake succeeds (tiny packets), small requests work, but anything large, a big response, a file upload, or a TLS handshake with a large certificate, hangs.

# Find the working size: ping with DF set; payload + 28 bytes of headers = packet size
ping -M do -s 1472 example.com        # 1472 + 28 = 1500: works on a clean path
ping -M do -s 1372 example.com        # try smaller until it succeeds
tracepath example.com                 # reports the discovered path MTU hop by hop
  • MSS clamping: have the router or firewall rewrite the MSS in SYN packets to fit the smaller MTU, so TCP never builds oversized segments, the most common practical fix
  • Allow ICMP 'fragmentation needed' / 'packet too big' through firewalls
  • Set the right interface MTU on tunnel endpoints
  • Packetization-layer PMTUD: Linux can probe sizes using TCP itself when ICMP is unreliable (net.ipv4.tcp_mtu_probing)

QUIC avoids the issue differently, by starting with conservative datagram sizes, about 1200 bytes, and probing upward.

The key insight Handshake works but data hangs is the classic MTU signature. If small things work and big things stall, test with DF-flagged pings before looking anywhere else.

§4Common Mistakes

MistakeWhat HappensFix
Blocking all ICMP at the firewallPMTUD breaks and large transfers hang silentlyPermit the ICMP types needed for path MTU discovery
Forgetting tunnel overhead when setting MTUPackets exceed the real path limit after encapsulationSubtract encapsulation headers from the interface MTU
Testing connectivity only with small requestsThe failure appears only with larger payloadsTest with a range of sizes, including near-MTU
Practice
  1. Use ping -M do with different -s values to find the largest unfragmented payload to a host. Convert it to an MTU.
  2. Explain why a TLS handshake might hang when the server's certificate chain is large, but an HTTP request to a plain port works.
Key takeaways
  • MTU mismatches arise from tunnels and overlays, and PMTUD relies on ICMP messages to adapt.
  • Filtering ICMP creates blackholes where handshakes succeed and large transfers hang.
  • Fix with MSS clamping, allowing needed ICMP, and setting correct tunnel MTUs.
