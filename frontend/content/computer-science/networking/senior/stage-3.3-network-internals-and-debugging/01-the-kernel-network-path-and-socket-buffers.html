The Kernel Network Path & Socket Buffers

A packet passes through a series of queues between the wire and your application, and each queue is a place where it can wait, be delayed, or be dropped.

§1Receive Path

When a packet arrives, the path to your program looks like this:

  1. The NIC receives the frame and places it in a receive ring buffer in memory using DMA
  2. The NIC raises an interrupt; the kernel then switches to polling (NAPI) to process packets in batches under load, avoiding an interrupt per packet
  3. A softirq runs the protocol stack: firewall rules (netfilter), IP, then TCP or UDP
  4. The data is appended to the destination socket's receive buffer
  5. Your application reads it with recv, typically woken by epoll

Modern NICs have multiple queues, and receive-side scaling spreads flows across CPU cores by hashing the 5-tuple, so one core doesn't have to handle everything. A single heavy flow still maps to one queue and one core.

§2Send Path

  1. The application calls send, copying data into the socket's send buffer
  2. TCP decides how much may go out, subject to the congestion and receive windows, and builds segments
  3. IP routes the packet; the queueing discipline (qdisc) schedules it for the device
  4. The driver places it on the NIC's transmit ring, and the NIC sends it

If the send buffer is full because the peer is slow or the window is closed, send blocks, or fails with EAGAIN in non-blocking mode. This is how backpressure reaches your application.

Knowing the path turns 'packets are getting lost' into a question of *where*, and each location has a different fix: more queues or CPU for the NIC, a faster accept loop for the listen queue, larger buffers or faster reading for the socket.

The key insight Loss isn't only something the network does to you. Much of it happens inside your own host, in queues that overflow because something downstream is slow. Find which counter is rising to find which stage is the bottleneck.

Practice
  1. Run a network-heavy workload and capture nstat -az before and after. Which drop or retransmission counters changed?
  2. Identify where in the kernel path a slow application that stops calling recv causes packets to be dropped or backed up.
Key takeaways
  • Packets traverse NIC rings, softirq processing, socket buffers, and qdiscs, and each queue can drop.
  • Full socket buffers and listen queues push backpressure to senders and clients.
  • Use ethtool -S, nstat, ss -tmi, and tc -s to locate where loss occurs.
