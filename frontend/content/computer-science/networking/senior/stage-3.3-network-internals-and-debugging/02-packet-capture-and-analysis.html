Packet Capture & Analysis

A capture is the ground truth of what crossed the wire, and a few filters and habits turn it from a wall of packets into an answer.

§1Capturing With tcpdump

tcpdump records packets on an interface using BPF filters applied in the kernel, so you capture only what you need. Save to a file and analyze it in Wireshark.

sudo tcpdump -i eth0 -nn 'host 203.0.113.9 and tcp port 443' -w trace.pcap
sudo tcpdump -i any -nn -c 20 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'    # only SYNs and RSTs
sudo tcpdump -i eth0 -nn -s 128 port 53                                    # DNS, headers only (-s limits bytes)
  • -nn disables name and port lookups, which would slow capture and add their own DNS traffic
  • Capture on the right machine: client-side, server-side, or both. Comparing them shows where packets vanish
  • Limit the capture with filters and a packet count or duration, and watch disk space on a busy link
  • Captures contain sensitive data, so protect and delete them

§2Reading a Capture in Wireshark

Wireshark's display filters find the interesting packets after the fact.

QuestionDisplay filter
Which packets were retransmitted?tcp.analysis.retransmission
Where did connections reset?tcp.flags.reset == 1
Any zero-window stalls?tcp.analysis.zero_window
Slow DNS answers?dns && dns.time > 0.5
TLS handshake starttls.handshake.type == 1
HTTP requestshttp.request

Follow TCP Stream reassembles a conversation, and Statistics, I/O Graphs shows throughput over time, where stalls and drops appear as dips. The TCP Stream Graphs (time-sequence) reveal whether the sender was limited by window, loss, or idle time.

§3What to Look For

  • Handshake timing: the gap between SYN and SYN-ACK is the RTT; a missing SYN-ACK means filtering or a dead host
  • Retransmissions and duplicate ACKs: loss, and where it began
  • Window sizes: a shrinking or zero receive window means the receiver's application is slow
  • RSTs: which side sent them, and after which packet
  • Long idle gaps: time between a request and the first response byte is server think time, not network time
  • Packet sizes: unexpectedly small packets can mean Nagle or MTU trouble

TLS hides the payload. To decrypt your own browser's traffic for debugging, set the SSLKEYLOGFILE environment variable so the browser writes session keys that Wireshark can use, and never do this on a shared machine or with someone else's traffic.

export SSLKEYLOGFILE=$HOME/tls-keys.log        # then start your browser from this shell
# Wireshark → Preferences → Protocols → TLS → (Pre)-Master-Secret log filename
The key insight Start with a question, not a capture. 'Why did this request take four seconds?' tells you to look for gaps, retransmissions, and resets, and the filter follows from the question.

§4Common Mistakes

MistakeWhat HappensFix
Capturing everything with no filterHuge files and a needle-in-a-haystack searchFilter by host and port, and limit by time or count
Analyzing only one side of the conversationCan't tell whether a packet was lost before or after reaching the other sideCapture at both ends when the question is 'where did it go?'
Leaving captures lying aroundThey may contain passwords, tokens, or personal dataTreat them as sensitive: restrict access and delete when done
Practice
  1. Capture a curl https://example.com request, then use Wireshark filters to find the handshake, the TLS ClientHello, and the first response byte, and measure each gap.
  2. Introduce loss with tc netem on a test machine, capture a download, and find the retransmissions.
Key takeaways
  • Use BPF filters with tcpdump to capture only what matters, and analyze offline in Wireshark.
  • Display filters for retransmissions, resets, zero windows, and slow DNS locate problems quickly.
  • Capture at the right vantage point, and handle captures as sensitive data.
