Diagnosing Network Incidents

A layered method turns a vague report like 'the service can't be reached' into a precise answer, by ruling out one layer at a time.

§1The Failure Signatures

Different failures look different at the client, and the symptom alone narrows the search.

SymptomWhat it usually means
Could not resolve hostDNS failed: bad name, resolver unreachable, or no record
Connection refused (fast)The host answered with a RST: it's up, but nothing is listening on that port
Connection timed out (slow)Packets dropped silently: firewall, routing problem, or host down
Connection reset by peerSomething sent a RST mid-conversation: app crash, proxy timeout, or a middlebox
TLS error / certificate warningExpired, mismatched, or untrusted certificate, or a TLS version or cipher mismatch
4xx / 5xx responseThe network worked; the application or a proxy answered with an error
Works for small requests, hangs on largeMTU or PMTUD blackhole

§2A Layered Method

Work from the name down to the application, and stop at the first layer that fails.

# 1. Name: does it resolve, and to what?
dig +short api.example.com
# 2. Path: is the host reachable, and where does it stop?
ping -c 3 203.0.113.9 ; mtr -rwc 20 203.0.113.9
# 3. Port: can I open a TCP connection?
nc -vz 203.0.113.9 443
# 4. TLS: does the handshake and certificate check out?
openssl s_client -connect api.example.com:443 -servername api.example.com </dev/null
# 5. Application: what does the server actually say, and how long does each phase take?
curl -sv -o /dev/null -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer}\n' https://api.example.com/health
# 6. Transport health: retransmissions, windows, queues on the host
ss -ti dst 203.0.113.9 ; nstat -az | grep -i -E 'retrans|drop|overflow'

Remember that ping may be blocked even when the service works, so a failed ping isn't proof of failure; the port test and curl are what matter.

§3A Worked Example

Report: 'Checkout is slow for users in one region.'

  1. DNS: dig from a probe in that region returns the expected addresses, so name resolution is fine
  2. Path: mtr shows loss starting at one transit hop, but later hops are clean, which suggests that hop only deprioritizes probes and isn't the cause
  3. Timing: curl -w shows tcp and tls are normal but ttfb is 3 seconds, so connections are fast and the delay is in the server's response
  4. Compare vantage points: the same request from another region has ttfb of 120 ms. The slow region is routed to a different backend pool
  5. Evidence: the regional pool's health dashboard and ss -ti on its load balancer show a saturated connection pool to the database
  6. Conclusion: not a network fault. The regional backend is starved of database connections, and the fix is capacity or pool sizing there

Write findings as a timeline with evidence for each step: what you ran, what you saw, what you ruled out. It keeps the investigation honest and becomes the post-incident record.

The key insight Match the symptom to a layer first, then test that layer with a tool that isolates it. 'Refused' and 'timed out' look similar to users but point to opposite causes.

§4Common Mistakes

MistakeWhat HappensFix
Treating 'refused' and 'timed out' as the sameLooking at firewalls when nothing is listening, or vice versaRefused = reachable but closed; timeout = packets dropped or unreachable
Trusting a single vantage pointA problem visible only from some networks is missedTest from the client's region, from the server, and from outside
Concluding from a high hop latency in tracerouteRouters deprioritize replies to probesOnly worry when latency or loss persists to the destination
Practice
  1. Given three symptoms, 'refused', 'timeout', and 'handshake fine, large downloads hang', name the layer and your first command for each.
  2. Break a local service three ways (stop it, firewall the port, change its certificate) and see how each failure appears in curl, nc, and openssl.
Key takeaways
  • The error message is the first clue: resolve failure, refused, timeout, reset, TLS error, and HTTP status each point to a layer.
  • Test in order: DNS, path, port, TLS, application, then host transport health.
  • Compare vantage points and record a timeline of evidence.
