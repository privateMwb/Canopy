GraphQL Tradeoffs

GraphQL lets the client ask for exactly the fields it needs in one request, which shifts complexity from the client to the server.

§1What It Offers

A GraphQL API usually exposes a single endpoint and a typed schema. The client sends a query describing the shape of the data it wants, and the server returns exactly that shape.

POST /graphql
{
  "query": "query { user(id: 7) { name orders(first: 2) { id total } } }"
}

{ "data": { "user": { "name": "Ada",
    "orders": [ {"id": 101, "total": 40}, {"id": 100, "total": 15} ] } } }

This addresses two REST pain points. Over-fetching returns more fields than the client needs, and under-fetching forces several round trips to assemble one screen. Mobile apps on slow networks benefit from getting a tailored response in one trip. The schema is introspectable, which powers explorers and generated types.

§2The Costs

ConcernWhy it's harder than REST
N+1 queriesA naive resolver for each order's customer fires one database query per order; needs batching (such as the DataLoader pattern)
HTTP cachingEverything is a POST to one URL, so CDNs and browsers can't cache by URL; needs persisted queries or application-level caching
Unbounded queriesA client can request deeply nested or enormous data; needs depth, complexity, and cost limits
AuthorizationPermissions must be enforced per field and per object, not per endpoint
MonitoringEvery request is POST /graphql with status 200, even on errors, so generic dashboards see nothing

GraphQL returns HTTP 200 even when part of a query fails, with an errors array in the body, so error rates must be derived from the response content, and not the status code.

§3When to Choose It

  • Good fit: many different clients (web, iOS, Android) with differing data needs; deeply connected data; a frontend team that iterates faster than the backend
  • Poor fit: simple CRUD with few clients; public APIs where caching and rate limiting by URL matter; file transfers; teams without capacity to build the safeguards above
# Persisted queries: clients send a hash, the server maps it to an approved query.
GET /graphql?id=sha256:ab12...&variables={"id":7}
# Restores GET semantics, enables CDN caching, and blocks arbitrary queries.

Neither style is universally better. REST makes the server's work predictable, and GraphQL makes the client's data needs flexible. Choose by who your clients are and who bears the complexity.

The key insight GraphQL doesn't remove complexity; it moves it from the client's many round trips to the server's resolver, caching, and security logic. Adopt it when that trade is worth it for your clients.

§4Common Mistakes

MistakeWhat HappensFix
Exposing GraphQL without query depth or cost limitsOne crafted query can take the service downEnforce depth and complexity limits, timeouts, and pagination
Resolving each child field with a separate database queryN+1 queries cripple performanceBatch and cache lookups with a DataLoader-style layer
Relying on HTTP status for error monitoringErrors hide behind 200 responsesTrack the errors array and per-operation metrics
Practice
  1. Take one REST screen that needs three endpoints and express it as a single GraphQL query. What does the server need to implement?
  2. Describe how an N+1 problem appears in resolvers for orders { customer { name } }, and how batching fixes it.
Key takeaways
  • GraphQL lets clients select exactly the fields they need in one request.
  • Its costs are N+1 queries, weak HTTP caching, unbounded query risk, and per-field authorization.
  • Choose it for varied clients and connected data, not as a default.
