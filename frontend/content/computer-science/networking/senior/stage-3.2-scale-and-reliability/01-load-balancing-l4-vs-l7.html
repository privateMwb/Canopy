Load Balancing: L4 vs. L7

A load balancer spreads traffic across servers, and whether it works at the connection level or the request level determines what it can see and what it can do.

§1Two Layers of Balancing

Layer 4 (transport)Layer 7 (application)
SeesIPs, ports, TCP/UDPFull HTTP: host, path, headers, cookies
Decision unitA connectionA request
TLSUsually passes throughTerminates it (needs the key)
RoutingBy address and port onlyBy hostname, path, header, method
CostVery low per connection; very high throughputMore CPU; richer features
ExtrasHealth checks, simple failoverRetries, caching, compression, auth, rate limiting

A Layer 4 balancer forwards packets or connections without reading the payload, so it is fast and protocol-agnostic. A Layer 7 balancer understands HTTP, which lets it send /api to one pool and /static to another, retry a failed request on another backend, and spread requests across many backends over the same client connection.

§2Distribution Algorithms

  • Round robin: rotate through backends; fine when requests cost about the same
  • Weighted: give bigger servers more traffic
  • Least connections / least outstanding requests: favor the least busy backend, which handles uneven request costs better
  • Consistent hashing: hash a key such as a user or cache key to a backend, so the same key lands on the same server and adding or removing a server moves only a small share of keys
  • Power of two choices: pick two random backends and use the less loaded one, which is simple and surprisingly effective at scale

Sticky sessions pin a client to one backend, usually via a cookie or an IP hash. They hide the problem of server-local state, but cause uneven load and lose the session when that server dies. Prefer storing state in a shared store.

§3Health Checks and Long-Lived Connections

A balancer must stop sending traffic to dead backends. Active health checks probe each backend periodically, such as GET /healthz, and passive checks watch real traffic for errors and timeouts. A good health endpoint verifies that the service can actually do its job, but doesn't fail the whole fleet because one shared dependency blipped.

upstream api {
    least_conn;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
}
server { location / { proxy_pass http://api; } }       # nginx: a simple L7 balancer

HTTP/2 and gRPC clients keep one connection open and multiplex many requests. A connection-level balancer assigns that single connection to one backend, leaving the others idle, so such traffic needs L7 balancing that spreads requests individually. Drain connections gracefully during deploys, finishing in-flight requests before removing a backend.

The key insight Use L4 for raw speed and protocol independence, and L7 when you need request-level routing, retries, or inspection. Many systems chain both, with an L4 layer in front of a fleet of L7 proxies.

§4Common Mistakes

MistakeWhat HappensFix
Using an L4 balancer for gRPCAll of a client's calls land on one backendUse an L7 or client-side balancer that distributes requests
Health checks that only test the portA hung app still passes and receives trafficCheck a real readiness endpoint that exercises key paths
Relying on sticky sessions to hide local stateUneven load and lost sessions on failureMove session state to a shared store
Practice
  1. Configure nginx or HAProxy as an L7 balancer for two backends, and watch the distribution under least_conn versus round robin.
  2. Explain why consistent hashing is better than hash % N when you add a server to a cache fleet.
Key takeaways
  • L4 balances connections quickly; L7 balances requests with full HTTP awareness.
  • Pick algorithms by workload: least-loaded for uneven requests, consistent hashing for cache affinity.
  • Health checks and graceful draining are what make failover actually work.
