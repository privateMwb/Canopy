Errors, Pagination & Filtering

Clients can only handle failures and large collections well if the API reports errors in a consistent shape and pages through data predictably.

§1A Consistent Error Format

Every error should use the right status code and the same body structure, so clients can handle errors generically. The standard for this is Problem Details (RFC 9457), with the media type application/problem+json.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "One or more fields are invalid.",
  "errors": [
    {"field": "email", "message": "must be a valid address"},
    {"field": "qty",   "message": "must be at least 1"}
  ],
  "request_id": "req_8f2a"
}

Use 400 for malformed requests, 422 for well-formed but invalid ones, 401 and 403 for authentication and authorization, 404 for missing resources, 409 for conflicts, and 429 for rate limits. Include a request_id that appears in your logs. Never leak stack traces or internal details.

§2Pagination: Offset vs. Cursor

Returning an entire large collection is slow and wasteful, so APIs split results into pages.

StyleRequestStrengthWeakness
Offset?limit=20&offset=40Simple; allows jumping to a pageSlow for deep offsets, and items shift if the data changes between requests, causing skips or duplicates
Cursor?limit=20&after=eyJpZCI6NDJ9Stable and fast at any depthNo jumping to page N; cursor must be treated as opaque
GET /orders?limit=2 HTTP/1.1

{
  "items": [ {"id": 101, ...}, {"id": 100, ...} ],
  "next_cursor": "eyJpZCI6MTAwfQ"       # opaque: encodes 'after id 100'
}
# Next page: GET /orders?limit=2&after=eyJpZCI6MTAwfQ

Cap limit at a maximum, and always apply a stable sort order, or pages become inconsistent. Cursors work because the database can seek directly to 'after this key' using an index instead of counting rows to skip.

§3Filtering and Sorting

GET /orders?status=shipped&customer_id=7&created_after=2026-01-01&sort=-created_at
  • Use query parameters for filters, and a sort parameter, where a leading - means descending
  • Allow only a defined set of filter and sort fields, since arbitrary ones can force slow queries or expose data
  • Validate every parameter and return 400 for unknown or invalid values, rather than silently ignoring them
  • Index the fields you allow clients to filter and sort on
The key insight Errors and pages are part of your API's contract just like success responses. Clients write code against their shape, so changing them later breaks users.

§4Common Mistakes

MistakeWhat HappensFix
Returning 200 with an error objectClients and monitoring treat failures as successesUse real status codes with a consistent body
Offset pagination over fast-changing dataMissed or repeated items between pagesUse cursor pagination with a stable ordering
Unbounded limit or arbitrary filter fieldsOne request can overload the databaseCap page size and whitelist filterable fields
Practice
  1. Define an error format and write five example errors for a signup endpoint: invalid email, duplicate email, rate-limited, unauthorized, server error.
  2. Implement cursor pagination over a table ordered by (created_at, id), and describe how the cursor encodes the position.
Key takeaways
  • Use correct status codes with a consistent body, ideally Problem Details.
  • Cursor pagination stays stable and fast; offset pagination is simpler but degrades and drifts.
  • Cap limits, whitelist filters, and validate parameters.
