CORS & Browser Constraints

Browsers block pages from reading responses from other origins unless the server opts in, and understanding that rule explains why a request that works in curl fails in a web app.

§1The Same-Origin Policy

An origin is the combination of scheme, host, and port: https://app.example.com and https://api.example.com are different origins, as are http:// and https:// or different ports. The same-origin policy stops JavaScript on one origin from reading responses from another. Otherwise, any website you visit could silently read your email from another tab where you're logged in.

CORS (Cross-Origin Resource Sharing) is the mechanism that lets a server relax this rule for chosen origins by sending headers.

# Page at https://app.example.com calls https://api.example.com
Origin: https://app.example.com                         # sent by the browser

Access-Control-Allow-Origin: https://app.example.com    # server says: that origin may read this

§2Preflight Requests

Simple requests, such as a plain GET or a form-style POST, are sent directly, and the browser checks the response headers afterward. For anything that could have side effects, such as a PUT or DELETE, a custom header, or a JSON Content-Type, the browser first sends an OPTIONS preflight to ask permission.

OPTIONS /orders HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type, authorization

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Max-Age: 600           # browser may cache this preflight for 10 minutes

If the preflight answer doesn't allow the request, the browser never sends the real one. Access-Control-Max-Age avoids repeating the extra round trip on every call.

§3Credentials and What CORS Is Not

  • To send cookies or authorization on cross-origin requests, the client must opt in (credentials: 'include') and the server must reply with Access-Control-Allow-Credentials: true and a specific origin, never *
  • Never reflect the incoming Origin header back blindly, because that grants every site access; check it against an allow-list
  • CORS is enforced by the browser only. curl, mobile apps, and other servers ignore it entirely, which is why a request can work from the command line and fail in a web page
  • CORS is not an access-control mechanism. It doesn't stop others from calling your API; authentication and authorization do that
  • It isn't CSRF protection either. A cross-origin request may still reach the server and act, even if the page can't read the response
curl -i -X OPTIONS https://api.example.com/orders \
  -H 'Origin: https://app.example.com' \
  -H 'Access-Control-Request-Method: PUT'
# Inspect the Access-Control-* headers returned.

When debugging, the browser console message names the missing header, and the Network panel shows the preflight as a separate OPTIONS request.

The key insight A CORS error means the browser blocked your page from *reading* a response because the server didn't opt in. The request usually did reach the server, which is why CORS can't be your security boundary.

§4Common Mistakes

MistakeWhat HappensFix
Setting Access-Control-Allow-Origin: * on credentialed APIsBrowsers refuse it, or you expose private dataReturn a specific allow-listed origin and Allow-Credentials: true
Reflecting the Origin header without validationAny malicious site can read authenticated responsesCompare against an explicit allow-list
Forgetting to handle OPTIONSPreflight fails with 404 or 405 and the real request never runsAnswer OPTIONS with the right Allow-* headers
Practice
  1. Make a page on one origin call an API on another, trigger a CORS failure, then fix it and watch the preflight in DevTools.
  2. Explain why a CORS misconfiguration is dangerous for an API that uses cookie authentication, but not for one that requires a bearer token in a header.
Key takeaways
  • An origin is scheme + host + port, and the same-origin policy blocks cross-origin reads.
  • CORS lets servers opt in with Access-Control-* headers, with preflight OPTIONS for non-simple requests.
  • CORS is enforced only by browsers and is not authentication or CSRF protection.
