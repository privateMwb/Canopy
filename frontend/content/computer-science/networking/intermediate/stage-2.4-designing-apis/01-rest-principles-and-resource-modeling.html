REST Principles & Resource Modeling

A well-modeled REST API uses nouns for resources and lets the HTTP methods carry the verbs, so clients, caches, and proxies understand it without documentation.

§1Resources and URLs

REST treats everything as a resource with a stable URL, and uses HTTP methods to act on it. URLs name things, and methods say what to do with them.

OperationRequestTypical status
List ordersGET /orders200
Get one orderGET /orders/42200, or 404
Create an orderPOST /orders201 with Location: /orders/42
Replace an orderPUT /orders/42200 or 204
Change part of an orderPATCH /orders/42200 or 204
Delete an orderDELETE /orders/42204
List a user's ordersGET /users/7/orders200

Collections are plural nouns, /orders, and items are addressed by ID, /orders/42. Verbs in the URL, such as /getOrder or /deleteUser, duplicate what the method already says.

§2Design Guidelines

  • Statelessness: each request carries everything needed, so any server instance can answer it and the API scales horizontally
  • Representations: a resource can be sent in several formats, usually JSON, selected with Accept and Content-Type
  • Shallow nesting: /users/7/orders is fine; deeper chains such as /a/1/b/2/c/3/d are hard to use, so give deep items their own top-level URL
  • Actions that don't fit CRUD: model them as resources, such as POST /orders/42/cancellation, or a clearly named sub-resource, rather than inventing a new method
  • Consistent naming: pick one style for fields and paths (such as snake_case) and use it everywhere

PUT replaces the entire resource, so omitted fields are cleared. PATCH changes only the fields supplied. Choose the one that matches what clients expect, and document the semantics.

§3An Example

POST /orders HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"customer_id": 7, "items": [{"sku": "A-100", "qty": 2}]}

HTTP/1.1 201 Created
Location: /orders/42
Content-Type: application/json

{"id": 42, "customer_id": 7, "status": "pending", "items": [...]}

True REST also includes hypermedia, with responses containing links to related actions. Most real-world 'REST' APIs skip that and stick to resources, methods, and status codes, and that's a reasonable place to start.

The key insight Use HTTP the way it was designed and you inherit its infrastructure for free. Caches can cache your GETs, proxies can retry your idempotent calls, and any developer can guess how your API behaves.

§4Common Mistakes

MistakeWhat HappensFix
Tunneling everything through POSTLoses caching, safe retries, and clear semanticsUse GET, PUT, PATCH, and DELETE where they apply
Verbs in URLs (/createUser)Inconsistent, harder to learn and evolveUse POST /users
Exposing database structure directly as the APIInternal changes become breaking changesModel resources around what clients need, not your tables
Practice
  1. Design the URLs and methods for a library API with books, members, and loans, including 'return a loan'.
  2. Take three verb-style endpoints you know, and rewrite each as a resource and method.
Key takeaways
  • Resources are nouns in URLs, and methods carry the verbs.
  • Statelessness and correct status codes let intermediaries do their jobs.
  • Keep nesting shallow and model non-CRUD actions as resources.
