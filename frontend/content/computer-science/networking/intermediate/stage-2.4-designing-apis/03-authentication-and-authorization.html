Authentication & Authorization

Authentication asks who you are, authorization asks what you may do, and most API breaches come from getting the second one wrong.

§1Two Different Questions

Authentication (authn) establishes identity: is this really Alice? Authorization (authz) decides permissions: may Alice read this order? A valid login says nothing about whether the request is allowed. Both checks must happen on every request.

§2OAuth 2.0 in Brief

OAuth lets an app act for a user without ever seeing their password. In the authorization code flow with PKCE, the standard for web and mobile apps:

  1. The app redirects the user to the authorization server, along with a hashed one-time secret (the PKCE challenge)
  2. The user logs in and consents to specific scopes
  3. The server redirects back with a short-lived code
  4. The app exchanges the code, plus the original PKCE secret, for an access token and optionally a refresh token
  5. The app calls the API with the access token

Access tokens are short-lived so that a leak has a limited window, and refresh tokens obtain new ones. Scopes limit what the token permits.

§3JWTs and What to Verify

A JWT is a compact, signed token with three Base64URL parts: header, payload (claims), and signature.

eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiI3IiwiZXhwIjoxNzUwMDAwMDAwLCJhdWQiOiJhcGkifQ.<signature>

# Decoded payload:
{"sub": "7", "exp": 1750000000, "aud": "api", "iss": "https://auth.example.com"}
  • Verify the signature with the expected algorithm and key; never trust a token whose header says alg: none or lets the token choose
  • Check exp, iss, and aud so expired tokens or ones meant for another service are rejected
  • The payload is readable by anyone, signed but not encrypted, so never put secrets in it
  • Revocation is hard: a valid JWT stays valid until it expires, which is why lifetimes should be short

Whatever the mechanism, authorize each object the request touches. Checking that the token is valid, but not that this user owns order 42, is the most common serious API flaw, returning to this in Stage 3.4.

Gotcha Send credentials only over HTTPS, keep them out of URLs, because URLs end up in logs and browser history, and store secrets hashed or encrypted. A token in a query string is a token in someone's log file.

§4Common Mistakes

MistakeWhat HappensFix
Authenticating but not authorizing each resourceAny logged-in user can read anyone's data by changing an IDCheck ownership or permissions on every object access
Accepting JWTs without validating signature, aud, and expForged or misdirected tokens are acceptedUse a vetted library and verify all required claims
Long-lived tokens with no revocation pathA leaked token works for monthsUse short-lived access tokens plus refresh tokens
Practice
  1. Decode a JWT with base64 or an online tool and list its claims. Which are checked for expiry and audience?
  2. Sketch the OAuth authorization code flow with PKCE for a mobile app, labeling which party holds which secret.
Key takeaways
  • Authentication is identity; authorization is permission, and both are required on every request.
  • OAuth 2.0 with PKCE gives apps tokens without exposing passwords; scopes and short lifetimes limit damage.
  • Verify a JWT's signature, issuer, audience, and expiry, and never store secrets in it.
