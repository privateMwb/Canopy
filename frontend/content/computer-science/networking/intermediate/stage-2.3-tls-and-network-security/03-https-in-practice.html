HTTPS in Practice

Having a certificate is only the start; redirects, HSTS, and sensible TLS settings decide whether a site is actually protected.

§1Redirects and HSTS

Users type example.com without a scheme, and browsers may try HTTP first. That first plain request can be intercepted and tampered with before any redirect to HTTPS. HSTS (HTTP Strict Transport Security) closes that gap: after one HTTPS visit, the browser remembers to use HTTPS only for that site.

# Redirect all HTTP to HTTPS
HTTP/1.1 301 Moved Permanently
Location: https://example.com/

# On HTTPS responses:
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

preload submits the domain to a list built into browsers, protecting even the very first visit. HSTS is a commitment: if you later break HTTPS on the domain or a subdomain, browsers refuse to fall back, so enable it carefully and start with a short max-age.

§2Mixed Content and Secure Cookies

A page loaded over HTTPS that pulls in a script or image over plain HTTP undermines it, since an attacker can alter the insecure resource. Browsers block active mixed content, such as scripts, and often upgrade or warn on passive content like images.

  • Use https:// or scheme-relative URLs for every subresource
  • Mark cookies Secure so they never travel over HTTP
  • Consider Content-Security-Policy: upgrade-insecure-requests while migrating

§3Server TLS Settings

  • Versions: enable TLS 1.3 and 1.2; disable 1.1 and older
  • Ciphers: use modern AEAD suites with ephemeral key exchange; follow a maintained profile, such as Mozilla's recommended configurations, rather than inventing your own
  • OCSP stapling: reduces latency and avoids leaking visitors' browsing to the CA
  • ALPN with HTTP/2 (and HTTP/3): enable them for performance
  • Session resumption: keep it on, and rotate ticket keys regularly to preserve forward secrecy
openssl s_client -connect example.com:443 -tls1_1 </dev/null     # should fail on a hardened server
curl -sI https://example.com/ | grep -i strict-transport
# Third-party scanners (SSL Labs, testssl.sh) grade a whole configuration at once.

TLS terminates wherever your certificate and key live, whether on a CDN, a load balancer, or the app itself. Traffic after that point may be plain text, so decide deliberately whether the internal leg also needs encryption, a topic that returns under zero trust in Stage 3.4.

The key insight HTTPS protects the connection only if it's actually used. HSTS, secure cookies, and no mixed content ensure that nothing silently falls back to plain HTTP.

§4Common Mistakes

MistakeWhat HappensFix
Redirecting to HTTPS but skipping HSTSThe first request is still exposed to interceptionSend Strict-Transport-Security on HTTPS responses
Setting a long HSTS max-age before testingA later HTTPS problem locks users outRamp up max-age gradually and test every subdomain
Loading scripts over HTTP on HTTPS pagesBrowsers block them, or an attacker can alter themServe every subresource over HTTPS
Practice
  1. Check a site's redirect and HSTS header with curl -I http://... and curl -I https://....
  2. Run a TLS scanner against a test server and fix the top two findings.
Key takeaways
  • Redirect HTTP to HTTPS and add HSTS so browsers stop attempting plain HTTP.
  • Avoid mixed content and mark cookies Secure.
  • Enable TLS 1.2 and 1.3 only, with modern ciphers from a maintained profile.
