Connection Management in Practice

Several TCP behaviors, TIME_WAIT, keepalives, Nagle's algorithm, and listen queues, rarely matter until a busy system hits one.

§1TIME_WAIT and Port Exhaustion

A client that opens and closes many short connections to one server leaves each in TIME_WAIT for 60 seconds. With about 28,000 ephemeral ports, a single client IP making more than roughly 450 new connections per second to the same destination can run out, failing with 'Cannot assign requested address'.

  • Best fix: reuse connections with keep-alive or connection pooling
  • More ports: widen net.ipv4.ip_local_port_range
  • More addresses: spread across several source or destination IPs
  • Avoid: disabling TIME_WAIT protections, which can corrupt connections with stray packets

§2Keepalives

An idle TCP connection sends nothing, so if the peer disappears silently, such as a crashed host or a NAT entry that expired, neither side notices. TCP keepalive sends probes on idle connections to detect this. On Linux it's off unless the application enables SO_KEEPALIVE, and the defaults wait 7,200 seconds before the first probe.

sysctl net.ipv4.tcp_keepalive_time       # 7200 s before the first probe
# Per-socket (Python):
s.setsockopt(socket.SOL_SOCKET, socket.SO_KEEPALIVE, 1)
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPIDLE, 60)

Idle-connection timeouts in NATs and load balancers are often a few minutes, far shorter than the default, so long-lived connections need keepalives or application-level heartbeats.

§3Nagle's Algorithm and Delayed ACKs

Nagle's algorithm reduces tiny packets: while unacknowledged data is outstanding, small writes are held and combined. Delayed ACKs have the receiver wait briefly, up to tens or hundreds of milliseconds, hoping to piggyback the ACK on outgoing data. Together they can stall a request-response protocol that writes in two small pieces: the second piece waits for an ACK, and the ACK waits for more data.

s.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)   # disable Nagle: send immediately

Latency-sensitive services usually set TCP_NODELAY. The better long-term fix is to write each message in a single call.

§4The Listen Backlog

A listening socket has two queues: connections still completing the handshake, and completed ones waiting for accept. If the application is too slow to accept, the second queue fills and new connections are dropped or delayed, appearing as client timeouts.

ss -ltn
# For LISTEN sockets: Recv-Q = connections waiting to be accepted, Send-Q = queue limit
nstat -az TcpExtListenOverflows TcpExtListenDrops
sysctl net.core.somaxconn

listen(backlog) is capped by somaxconn, commonly 4096 on recent kernels. SYN cookies let a server survive SYN floods by encoding state in the reply, without storing a half-open entry per request.

Gotcha Silent connection death is the common failure. A NAT or load balancer drops an idle flow, and the client's next write just hangs until a timeout. If a long-lived connection mysteriously stalls after quiet periods, suspect an idle timeout.

§5Common Mistakes

MistakeWhat HappensFix
Opening a new connection per requestTIME_WAIT buildup and port exhaustionPool and reuse connections
Relying on default keepalive for long-lived connectionsDead peers go undetected for hoursEnable keepalives with short intervals or send app-level heartbeats
Writing a message in many tiny send calls with Nagle onAdded latency from the Nagle and delayed ACK interactionSend each message in one write and set TCP_NODELAY for interactive traffic
Practice
  1. Make a client open and close 40,000 connections to one server. Watch TIME_WAIT counts, and report whether and when ports run out.
  2. Check ss -ltn on a server under load. Is Recv-Q on the listen socket ever non-zero? What would that mean?
Key takeaways
  • Reuse connections to avoid TIME_WAIT piles and ephemeral-port exhaustion.
  • Keepalives detect silently dead peers and keep idle flows alive through NATs.
  • Nagle plus delayed ACKs can add latency; TCP_NODELAY and single-write messages avoid it.
