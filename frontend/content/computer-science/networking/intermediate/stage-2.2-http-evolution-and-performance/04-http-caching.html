HTTP Caching

The fastest request is the one never sent, and a few headers decide whether a response can be reused, for how long, and by whom.

§1Freshness: Cache-Control

A response can tell caches how long it stays fresh, during which the cached copy is used with no network request at all.

DirectiveMeaning
max-age=3600Fresh for 3600 seconds
s-maxage=600Like max-age, but for shared caches such as CDNs
public / privateAny cache may store it / only the user's own browser may
no-cacheMay be stored, but must be revalidated before every use
no-storeNever store it (for sensitive data)
immutableWon't change while fresh; skip revalidation even on reload

no-cache doesn't mean 'don't cache'; it means 'check first'. no-store is the one that forbids storing.

§2Validation: ETag and 304

When a response goes stale, the cache doesn't have to download it again. It revalidates by asking whether it changed. The server provides a validator, an ETag (a fingerprint of the content) or a Last-Modified date, and the client sends it back.

GET /logo.png HTTP/1.1
If-None-Match: "a1b2c3"          # I have version a1b2c3; has it changed?

HTTP/1.1 304 Not Modified         # no body: reuse your copy
ETag: "a1b2c3"
Cache-Control: max-age=3600

A 304 costs one round trip but no body, which is far cheaper than re-sending a large file. Responses that differ by request header, such as Accept-Encoding or Accept-Language, must say so with Vary, so the cache stores each variant separately.

§3A Practical Strategy and CDNs

  • Fingerprinted static assets (app.3f9a1c.js): Cache-Control: public, max-age=31536000, immutable. A content change produces a new URL, so it never needs invalidation
  • HTML pages: short max-age or no-cache with an ETag, so users see updates promptly
  • Personalized or sensitive responses: private or no-store
  • APIs: cache read-heavy endpoints with modest max-age and validators

A CDN is a shared cache close to users. It obeys the same headers, with s-maxage giving CDN-specific control. Purging is slow and error-prone, so versioned URLs are the reliable way to ship changes.

curl -sI https://example.com/app.js | grep -i -E 'cache-control|etag|age|x-cache'
# 'Age' shows how many seconds the response has sat in a cache
Gotcha A response with no caching headers isn't uncacheable; caches may apply heuristics, such as a fraction of its age since Last-Modified. Always state your intent explicitly.

§4Common Mistakes

MistakeWhat HappensFix
Using no-cache to mean 'don't store'Sensitive data is stored and reused after revalidationUse no-store for data that must never be kept
Long max-age on non-fingerprinted filesUsers see stale code for days after a deployVersion file names, or keep max-age short
Forgetting Vary on content-negotiated responsesA cache serves the wrong language or encodingList every request header that changes the response
Practice
  1. Request the same static file twice with curl -sI and If-None-Match, and show the server returning 304.
  2. Design caching headers for a site with a hashed JS bundle, an HTML page, and a personalized dashboard API.
Key takeaways
  • Cache-Control sets freshness, and no-store is the only directive that forbids storing.
  • ETags and conditional requests let a stale copy be revalidated with a body-less 304.
  • Fingerprinted URLs with long max-age are the reliable way to cache and still ship changes.
