HTTP/2: Multiplexing & Header Compression

HTTP/2 sends many requests at once over a single connection by splitting them into interleaved binary frames, fixing HTTP-level head-of-line blocking.

§1Binary Framing and Streams

HTTP/2 keeps the same methods, headers, and status codes, but replaces text with a binary framing layer. Each request and response is a stream with an ID, broken into frames that can be interleaved on one TCP connection.

One TCP connection:
  [HEADERS s1][HEADERS s3][DATA s1][DATA s3][DATA s1][HEADERS s5][DATA s3] ...
   └ stream 1 ┘ └ stream 3 ┘                    └ stream 5 ┘

# A slow response on stream 1 no longer blocks stream 3 or 5.

A browser needs just one connection per origin, so there's one handshake, one slow start, and a well-warmed congestion window. This is why bundling and domain sharding stop being useful.

§2HPACK Header Compression

Headers are repetitive: the same User-Agent, cookies, and Accept values accompany every request, sometimes hundreds of bytes each. HPACK compresses them using a table of previously seen headers shared by both sides, so repeated headers shrink to a few bytes. It uses a fixed code table rather than general-purpose compression, which avoids attacks like CRIME that exploited compression of secrets.

curl -v --http2 https://example.com/ 2>&1 | grep -E 'ALPN|HTTP/2'
# * ALPN: server accepted h2
# > GET / HTTP/2

HTTP/2 over TLS is negotiated through ALPN, an extension in the TLS handshake where the client lists h2 and http/1.1 and the server picks one. No extra round trip is needed.

§3What HTTP/2 Doesn't Fix

Everything still rides on one TCP connection. If a single packet is lost, TCP stalls delivery of every stream behind it until the retransmission arrives, because TCP can't deliver later bytes before earlier ones. On a lossy network, a single connection can be worse than the six parallel ones HTTP/1.1 used.

  • Stream prioritization was in the spec but inconsistently implemented, and later redesigned
  • Server push, letting servers send resources before the client asks, proved hard to use well and has been largely abandoned
  • TCP head-of-line blocking remains, which is the problem HTTP/3 addresses
The key insight HTTP/2 removed HTTP-level head-of-line blocking but moved the problem down a layer. With one shared TCP stream, loss on any stream stalls all of them.

§4Common Mistakes

MistakeWhat HappensFix
Keeping HTTP/1.1 workarounds on HTTP/2Bundling and sharding reduce cache hits and add costsSimplify to fewer, well-cached resources over one connection
Assuming HTTP/2 helps on very lossy linksTCP blocking affects all streams at onceTest under realistic loss; consider HTTP/3
Relying on server pushBrowsers have removed or deprioritized itUse preload hints and caching instead
Practice
  1. Load a page with the DevTools Protocol column visible and note which requests use h2, http/1.1, and h3.
  2. Explain with a diagram how one lost packet affects three concurrent HTTP/2 streams on one TCP connection.
Key takeaways
  • HTTP/2 multiplexes interleaved streams over one connection using binary frames.
  • HPACK compresses repeated headers using a shared table.
  • TCP-level head-of-line blocking remains, since all streams share one ordered byte stream.
