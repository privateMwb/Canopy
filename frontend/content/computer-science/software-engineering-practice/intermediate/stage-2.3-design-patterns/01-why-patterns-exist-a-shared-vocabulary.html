Why Patterns Exist: A Shared Vocabulary

Design patterns are names for solutions that experienced developers kept rediscovering. Their main value is a shared vocabulary.

§1Where Patterns Came From

In 1994 four authors, nicknamed the Gang of Four, catalogued 23 recurring object-oriented designs in the book *Design Patterns*. They didn't invent these ideas; they named what good programmers were already doing. A pattern has a name, a problem it addresses, a solution shape, and trade-offs.

The three families are creational (how objects are made), structural (how they're composed), and behavioral (how they interact and share responsibility).

§2A Vocabulary, Not a Recipe Book

Patterns let you say a lot in a few words. "Wrap it in an adapter" or "make that a strategy" conveys a design in a sentence, to anyone who knows the terms. They also give you a checklist of known trade-offs before you choose.

"We need to support three payment providers."
 -> "Define a PaymentGateway interface, one adapter per provider,
     pick the adapter at startup."   # one sentence, a whole design

But patterns are not code to copy. Each language has different built-ins: a function passed as an argument already is the Strategy pattern, and a Python generator already is the Iterator pattern. The pattern is the idea, not the class diagram.

§3Using Patterns Well

  • Start from the problem, not the pattern. "I need to vary this behavior at runtime" leads to Strategy; "I want a pattern" leads nowhere good.
  • Know the trade-off. Every pattern adds indirection, so it must earn its keep.
  • Let patterns emerge. Often the cleanest path is to write simple code, then refactor toward a pattern when duplication or rigidity appears.

The following lessons tour the most useful patterns in each family, with the problem each one solves.

The key insight A pattern is a solution to a recurring problem, so if you don't have the problem, you don't want the pattern.

§4Common Mistakes

MistakeWhat HappensFix
Learning patterns as class diagrams to memorizeYou can name them but not recognize the problemLearn each one as a problem and its trade-off
Starting a design by choosing patternsOver-built code that solves problems you don't haveStart from the concrete need; reach for a pattern when a problem repeats
Copying the textbook structure in a language that needs lessNeedless boilerplate (e.g. a Strategy class where a function works)Use the language's native feature for the same idea
Practice
  1. Pick three patterns you have used without knowing their names and name them.
  2. Describe a design from your own project in a sentence using pattern vocabulary.
  3. Find a Strategy-like idea in your language implemented as just a function.
Key takeaways
  • Patterns are named solutions to recurring design problems.
  • Their biggest value is a shared vocabulary and known trade-offs.
  • Start from the problem; the pattern is a tool, not a goal.
