Reviewing Code: What to Look For and How to Say It

A review is a conversation about whether a change is correct, understandable, and worth having. Knowing what to look for, and how to phrase it, makes reviews fast and kind.

§1What to Look For, in Order

Review from the top down. Spend attention where it matters most, and don't let formatting debates eat the time needed for design.

  1. Design: does the change fit the system? Is it in the right place? Is this the right approach?
  2. Correctness: does it do what it claims, including edge cases, errors, and concurrency?
  3. Tests: do they cover the behavior and would they fail if it broke?
  4. Readability: can the next person understand it without asking the author?
  5. Details: naming, comments, consistency (ideally automated; see the next lesson)

Read the description and the tests first. Tests describe the intended behavior; if they're unclear, the code usually is too.

§2Saying It Well

How you phrase a comment decides whether it's heard. Ask questions, explain reasons, and be specific about what is blocking and what is optional.

Harsh:     "This is wrong. Why would you loop here?"
Helpful:   "This re-queries the database on each iteration, which will be
            slow for large carts. Could we fetch once before the loop?"

Prefix to signal weight:
  blocking:  returns None on error, but the caller assumes a list
  question:  is this loop ordered by date on purpose?
  nit:       could be `total` rather than `t` (non-blocking)
  • Comment on the code, not the person: "this function" rather than "you"
  • Praise good work; it tells the author what to repeat
  • Suggest, don't dictate, when several solutions are fine
  • Approve when it's good enough and improvements are optional

§3Working Efficiently

Review promptly, since waiting for review is one of the largest hidden costs in engineering. If a change is too big to review well, say so and ask for it to be split. And review what is missing, such as a missing test, an unhandled error, or a forgotten migration, as carefully as what is there.

  • Check out the branch and run it for anything risky
  • Scan the file list first for surprises (unrelated files, secrets)
  • Aim to review within a working day
The key insight The goal of review is a better codebase and a better team. A comment that teaches is worth ten that just correct.

§4Common Mistakes

MistakeWhat HappensFix
Spending the review on styleReal design and correctness issues slip throughAutomate style; review design, behavior, and tests first
Blunt or vague comments ('this is bad')Defensiveness and no clear fixSay what the issue is, why it matters, and what you suggest
Only reading what changedMissing tests, docs, or callers that were never touchedAsk what's missing and what the change affects
Practice
  1. Review a pull request using the five-step order and write three comments with different weights.
  2. Rewrite a harsh comment you've seen or sent into a helpful one.
  3. Check one pull request for something that is missing rather than wrong.
Key takeaways
  • Review design and correctness first; style last.
  • Be specific, explain why, and label what's blocking.
  • Review quickly and look at what is missing as well as what is there.
