Hunting Regressions: bisect, blame & the Pickaxe

When something that used to work breaks, version history lets you find the exact change that did it and the reason it was made.

§1Bisect: Binary Search Over Commits

If a bug appeared sometime in the last 200 commits, you don't need to read them all. git bisect does a binary search: you mark one commit bad and one good, Git checks out the middle, you test it and report, and it halves the range again. 200 commits take about 8 steps.

git bisect start
git bisect bad                  # current version is broken
git bisect good v1.3.0          # this older tag worked
# Git checks out a middle commit; build, test, then say:
git bisect good                 # or: git bisect bad
# ...repeat until Git prints "<hash> is the first bad commit"
git bisect reset                # return to where you started

Atomic commits make this pay off: the first bad commit is then a small change you can understand.

§2Automate It With bisect run

If you can write a script that exits 0 when the code is good and non-zero when bad, Git will do the whole search itself.

git bisect start HEAD v1.3.0
git bisect run pytest tests/test_checkout.py::test_total_with_tax
# Git finds the culprit commit unattended

A test that reproduces the bug is the ideal script, and it becomes a regression test afterward.

§3Blame and the Pickaxe

Once you've found the line, ask why it exists. git blame shows who last changed each line and in which commit; follow the commit message and linked ticket for the reason.

git blame -L 40,60 pricing.py         # only lines 40-60
git blame -w -C pricing.py            # ignore whitespace; follow moved code

git log -S"retry_limit" --oneline     # commits that added/removed that string
git log -L :apply_discount:pricing.py # full history of one function

-S (the pickaxe) finds when a string appeared or vanished, which is ideal for "when did we delete this check?" Blame points to the last change, which is sometimes just a reformat, so keep going back until you reach the meaningful one.

The key insight A reproducible failing test plus a clean history lets Git find the culprit for you. Writing the reproduction is the real work, and it pays twice.

§4Common Mistakes

MistakeWhat HappensFix
Reading commits one by one to find a bugHours spent on a search that takes minutesUse bisect with a script or a quick manual test
Bisecting through broken commitsA commit that doesn't build gives false 'bad' resultsUse git bisect skip for unbuildable commits
Stopping at the reformat in blameYou see a style change, not the original reasonUse -w -C or follow the line back through earlier commits
Practice
  1. Introduce a bug on purpose five commits back and find it with git bisect.
  2. Write a script and use git bisect run to find it unattended.
  3. Use git log -S to find when a specific string was added to your project.
Key takeaways
  • Bisect finds the commit that broke something in logarithmic steps.
  • A test script lets bisect run do it automatically.
  • Blame and pickaxe tell you why a line exists.
