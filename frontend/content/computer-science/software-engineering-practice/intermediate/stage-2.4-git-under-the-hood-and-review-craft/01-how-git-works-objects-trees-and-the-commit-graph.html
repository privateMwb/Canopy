How Git Works: Objects, Trees & the Commit Graph

Git feels like magic until you see that it stores just four kinds of object. Once you do, branches, merges, and the scary commands all get simpler.

§1Four Object Types

Inside .git/objects, Git is a content-addressed store: every object is saved under the hash of its contents. Four kinds exist.

ObjectWhat it holds
blobThe contents of one file (no name, no path)
treeA directory: a list of names pointing to blobs and other trees
commitA pointer to one tree, the parent commit(s), author, date, and message
tagA named, optionally signed pointer to a commit
git cat-file -p HEAD             # a commit: tree, parent, author, message
tree 9c1e...
parent 4b7a...
author Ana <ana@example.com> 1760000000 +0000

Fix rounding of tax on discounted items

git cat-file -p 9c1e             # its tree: files and sub-directories
100644 blob a1f3...    README.md
040000 tree 7d20...    src

§2The Commit Graph

Each commit names its parent, so commits form a directed acyclic graph. A normal commit has one parent; a merge commit has two. History is not a list but a graph that happens to look linear when nobody has branched.

A---B---C---F        main
     \     /
      D---E          feature      (F is a merge: parents C and E)

Because the hash covers the parent hash too, changing any old commit changes every commit after it. That is why history is tamper-evident, and why "editing" a commit actually creates new ones.

§3Branches Are Just Pointers

A branch is a tiny file containing one commit hash. Creating one copies 41 bytes, which is why branching in Git is instant. HEAD says which branch you're on, and a commit moves the branch pointer forward.

cat .git/refs/heads/main        # 4b7a91c...
cat .git/HEAD                   # ref: refs/heads/main

git branch experiment           # new pointer, same commit; nothing copied
git switch experiment           # HEAD now points at 'experiment'
git commit -m "Try idea"        # 'experiment' advances; 'main' stays put

Nearly every command is moving pointers around the graph. A reset moves a branch pointer; a rebase replays commits onto a new base; a fast-forward merge just slides the pointer. Seeing that makes the reflog make sense: it records where each pointer used to be.

The key insight Commits are immutable snapshots and branches are movable labels. Almost nothing you do in Git deletes data right away; you move labels, and the old commits stay reachable by hash and reflog for a while.

§4Common Mistakes

MistakeWhat HappensFix
Thinking of a branch as a copy of the codeFear of branching and fear of deleting branchesA branch is a pointer; creating and deleting one is cheap and safe
Believing a commit stores a diffConfusion about why history is rewritten rather than editedA commit stores a full snapshot; diffs are computed on demand
Assuming rewriting history changes old commitsSurprise when collaborators have the originalsRewriting creates new commits; the old ones still exist elsewhere
Practice
  1. Run git cat-file -p HEAD and follow the tree down to a blob in your own repo.
  2. Read .git/HEAD and .git/refs/heads/ and match them to git branch -v.
  3. Draw the commit graph of a recent merge and name its parents.
Key takeaways
  • Git stores blobs, trees, commits, and tags, addressed by hash.
  • Commits form a graph; branches are cheap movable pointers into it.
  • Most commands just move pointers or create new commits; the old ones stay.
