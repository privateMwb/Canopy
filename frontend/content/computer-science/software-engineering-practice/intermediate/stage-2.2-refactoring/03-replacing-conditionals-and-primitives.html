Replacing Conditionals & Primitives

Long chains of conditionals and bare primitive types are two of the most common design problems, and both have clean refactorings.

§1Repeated Conditionals on a Type

When the same if/elif on a type or status appears in several places, adding a new case means editing all of them, and missing one is a bug. Replace conditional with polymorphism puts the behavior with the type.

# before: three functions each switch on the same field
def price(p):    if p.kind == "digital": ... elif p.kind == "physical": ...
def ship(p):     if p.kind == "digital": ... elif p.kind == "physical": ...
def tax(p):      if p.kind == "digital": ... elif p.kind == "physical": ...

# after: each type knows its own behavior
class DigitalProduct:
    def ship(self): return None                   # nothing to ship
    def tax(self):  return self.price * 0.20
class PhysicalProduct:
    def ship(self): return Parcel(self)
    def tax(self):  return self.price * 0.10
# adding a new kind: write one class, edit nothing else

Don't do it for a single, stable conditional. A simple if is clearer than a hierarchy. The signal is the same switch repeated in several places.

§2Primitive Obsession

Primitive obsession is using bare strings and numbers for concepts that have rules. An email is not just a str, and money is not just a float. Wrapping them in small value types puts validation and behavior in one place and prevents mixing things up.

# before: any string, any number
def charge(email, amount): ...
charge(49.99, "ana@example.com")          # swapped; no error!

# after: types carry meaning and rules
@dataclass(frozen=True)
class Email:
    value: str
    def __post_init__(self):
        if "@" not in self.value: raise ValueError("invalid email")

@dataclass(frozen=True)
class Money:
    cents: int
    def __add__(self, other): return Money(self.cents + other.cents)

def charge(email: Email, amount: Money): ...

§3Guard Clauses and Data Clumps

Two quick relatives. Guard clauses replace nested conditionals with early returns. Data clumps are groups of values that always travel together (street, city, postcode) and want to become an object (Address). Each refactoring is small and safe, and each one removes a place where bugs hide.

def ship(order):
    if not order.paid:     return Err("unpaid")
    if not order.address:  return Err("no address")
    return send(order)
The key insight When you add a new case and have to hunt through the code editing conditionals, the design is asking for a type. When a value has rules, it deserves a type of its own.

§4Common Mistakes

MistakeWhat HappensFix
Polymorphism for a single simple ifClasses and indirection for no benefitWait until the same switch appears in several places
Using float for moneyRounding errors that corrupt totalsUse integers (cents) or a decimal type inside a Money value
Passing many related strings and numbersArgument mix-ups the compiler can't catchIntroduce small types and parameter objects
Practice
  1. Find a repeated if kind == ... chain and refactor it into classes.
  2. Wrap one validated string (email, phone, ID) in a value type.
  3. Replace a nested conditional with guard clauses.
Key takeaways
  • Repeated switches on a type suggest polymorphism.
  • Values with rules deserve their own small types.
  • Guard clauses and parameter objects flatten and tidy code cheaply.
