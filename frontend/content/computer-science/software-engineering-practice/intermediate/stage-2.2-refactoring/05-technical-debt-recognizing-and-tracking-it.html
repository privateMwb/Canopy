Technical Debt: Recognizing and Tracking It

Technical debt is a useful metaphor if you take all of it seriously: borrowing speed now, paying interest later, and deciding on purpose when to repay.

§1The Debt Metaphor

Ward Cunningham coined technical debt to describe a shortcut taken to ship sooner. Like a loan, it lets you move fast now and charges interest later: every change in that area takes longer and is riskier until the debt is repaid.

Debt is not automatically bad. Borrowing on purpose, to hit a real deadline with a plan to repay, can be a good decision, just as a business loan can be. The danger is debt nobody chose and nobody tracks.

§2Deliberate vs. Accidental

PrudentReckless
Deliberate"Ship now and refactor after the launch""We don't have time for design"
Accidental"Now we know how we should have built it""What's layering?"

The bottom-left, discovering a better design only after learning the domain, is unavoidable and healthy. The right-hand column is where teams get hurt: debt taken without thought, or from lack of skill.

§3Making It Visible

Debt you can't see never gets repaid. Keep a lightweight record: what the shortcut is, why it was taken, what it costs now, and what fixing it would involve. Link comments to tickets so they don't rot.

# TODO(PAY-218): retries are synchronous because the queue isn't ready.
# Cost: checkout latency +300ms on card failures.
# Fix: move to the job queue once Q3 infra lands.
  • Track it: a ticket label, a short debt register, or a markdown file in the repo
  • Measure interest: where do changes keep taking too long, or bugs keep appearing?
  • Repay as you go: budget a fixed share of each sprint rather than waiting for a cleanup week that never comes

Pay down the debt that charges the most interest first: the messy module everyone changes weekly, not the ugly one nobody touches.

The key insight Prioritize debt by interest, not by ugliness. Code that is ugly but stable costs nothing; code that is merely okay but changes daily costs a lot.

§4Common Mistakes

MistakeWhat HappensFix
Calling any messy code 'tech debt'The term loses meaning and nothing gets prioritizedDefine debt by its cost: what it slows down or risks
Never writing debt downThe team forgets what was deferred and whyKeep a short, linked, owned record
Saving it all for a big cleanupThe cleanup is always postponed and grows riskyPay a steady fraction continuously alongside feature work
Practice
  1. List five pieces of debt in your project and estimate the interest each charges.
  2. Write a debt entry for one shortcut: what, why, cost, and fix.
  3. Pick the highest-interest item and plan a small first step.
Key takeaways
  • Technical debt is a loan: speed now, interest later.
  • Deliberate, prudent debt is fine; unrecorded debt is dangerous.
  • Prioritize repayment by the interest it charges.
