The Test Pyramid & Where Tests Belong

A test suite needs a mix of fast, narrow tests and slower, broader ones, and the test pyramid is the classic guide to balancing them.

§1Three Kinds of Tests

LevelTestsSpeedWhen it fails
UnitOne function or class in isolationMillisecondsPoints straight at the culprit
IntegrationSeveral parts together, e.g. code plus a real databaseTens to hundreds of msNarrowed to an interaction
End-to-endThe whole system through its real interfaceSecondsCould be anywhere

§2The Pyramid Shape

The test pyramid says to have many unit tests at the base, fewer integration tests in the middle, and a handful of end-to-end tests at the top. The reasons are cost: lower-level tests are faster, more stable, and pinpoint failures, while higher-level tests cover real wiring but are slow and flaky.

        /\          few   E2E:  full user journeys, slowest
       /  \
      /----\        some  Integration: real DB, real HTTP boundary
     /      \
    /--------\      many  Unit: pure logic, milliseconds each

The opposite shape, the ice-cream cone, has few unit tests and a mass of slow end-to-end ones. It is the usual cause of suites that take an hour and fail at random.

§3Other Shapes and How to Choose

The pyramid is a heuristic, not a law. Some teams prefer a testing trophy, with a big middle layer of integration tests, because modern tools make them cheap and they catch real wiring bugs that mocks miss. A service that is mostly glue code between a database and an API may deserve more integration tests than one with rich business logic.

The principle behind every shape is the same: test each risk at the cheapest level that can catch it. Business rules in a pure function get a unit test. A SQL query gets a test against a real database. Whether login works end to end gets one smoke test.

The key insight Ask of every test what it protects against, and whether a cheaper test could protect against the same thing.

§4Common Mistakes

MistakeWhat HappensFix
Testing everything through the UISlow, flaky suite where any failure could be anywherePush logic tests down to units; keep few end-to-end journeys
Only unit tests, with everything mockedComponents pass alone but fail when wired togetherAdd integration tests at real boundaries like databases and APIs
Duplicating the same check at every levelMore maintenance for no extra confidenceCover each risk once, at the cheapest level that catches it
Practice
  1. List your project's tests by level and count them. What shape do you have?
  2. Pick one slow end-to-end test and move its logic checks into unit tests.
  3. Choose one risk (a SQL query, a payment flow) and decide which level should cover it.
Key takeaways
  • Unit, integration, and end-to-end tests trade speed against realism.
  • The pyramid puts many fast tests at the base and few slow ones on top.
  • Test each risk at the cheapest level that can catch it.
