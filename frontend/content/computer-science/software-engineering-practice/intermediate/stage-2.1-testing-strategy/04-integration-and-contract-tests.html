Integration & Contract Tests

Unit tests with fakes can all pass while the real system still fails. Integration and contract tests check the places where parts actually meet.

§1Integration Tests: Real Collaborators

An integration test runs your code against real components, such as a real database, a real message queue, or the real HTTP layer, to catch what fakes can't: a wrong SQL column name, a missing migration, a serialization mismatch.

def test_user_repository_saves_and_loads(db_connection):   # a real test database
    repo = SqlUsers(db_connection)
    repo.add(User(id=1, email="ana@example.com"))
    assert repo.find(1).email == "ana@example.com"

Run them against a throwaway database, often in a container, and reset the data between tests. They are slower than unit tests, so keep them focused on the boundary instead of repeating business rules.

§2Contract Tests Between Services

When two services talk to each other, each team can test its own side with fakes and still break the other. A contract test captures what the consumer expects from the provider (fields, types, status codes) and checks the provider honors it, without needing both running together.

# consumer's expectation, written as data
GET /users/42
-> 200  { "id": 42, "email": <string>, "created_at": <iso-date> }

# provider's CI replays the contract against the real API.
# Rename "email" to "mail" and this fails *before* release.

This is much cheaper than a full end-to-end environment and finds breaking API changes at the source.

§3Where to Draw the Line

  • Test your own boundaries thoroughly (your database queries, your HTTP handlers)
  • Don't test the third party. Trust that the database or library works; test that you use it correctly
  • Keep a few full-stack smoke tests to prove everything wires up, not to cover every branch

A good integration test is small, hermetic, and deterministic: it controls its own data and doesn't depend on a shared staging system that someone else may change.

The key insight Unit tests tell you the pieces work. Integration and contract tests tell you the pieces fit.

§4Common Mistakes

MistakeWhat HappensFix
Only testing against fakesReal SQL, serialization, or config bugs reach productionAdd integration tests at every real boundary
Tests that depend on a shared staging environmentRandom failures when another team changes dataUse isolated, disposable test databases or containers
Re-testing business logic through slow integration testsSuite becomes slow without adding confidenceCover logic with unit tests and the boundary with a few integration tests
Practice
  1. Write one integration test for a repository class against a real test database.
  2. Write down the contract one service expects from another, as example requests and responses.
  3. Find a bug your fakes would never catch, and write the test that would.
Key takeaways
  • Integration tests check the real wiring that fakes hide.
  • Contract tests keep consumers and providers in agreement without full end-to-end runs.
  • Test your side of the boundary, and trust the third party.
