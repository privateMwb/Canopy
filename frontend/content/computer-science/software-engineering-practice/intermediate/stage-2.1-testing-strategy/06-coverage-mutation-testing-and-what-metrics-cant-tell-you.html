Coverage, Mutation Testing & What Metrics Can't Tell You

Coverage numbers are easy to collect and easy to misread. Knowing what they do and don't measure keeps them useful.

§1What Coverage Measures

Line coverage reports which lines ran while the tests executed. Branch coverage adds whether each side of each if ran. Low coverage tells you something real: that code is never exercised by tests at all, which is a good place to look for gaps.

pytest --cov=shop --cov-report=term-missing

Name              Stmts   Miss  Cover   Missing
shop/pricing.py      42      6    86%   58-63    # lines no test touches

§2What It Can't Tell You

High coverage does not mean good tests. Coverage only records that code ran, not that anything was checked. This test gives 100% coverage and verifies nothing:

def test_discount():
    apply_discount(200, 25)       # runs every line, asserts nothing

Chasing a target such as 90% invites tests written to satisfy the tool. Once a measure becomes a goal, people optimize the measure instead of the quality it was meant to indicate.

§3Mutation Testing

Mutation testing asks a harder question: if the code were wrong, would the tests notice? A tool makes small deliberate changes to your code (mutants), such as turning > into >= or deleting a line, and re-runs the tests. If the tests still pass, the mutant survived, which means that behavior isn't really checked.

original:  if age >= 65: return SENIOR_PRICE
mutant:    if age >  65: return SENIOR_PRICE     # off-by-one introduced

tests still pass?  -> survived -> no test checks age 65 exactly
tests fail?        -> killed   -> the boundary is covered

Mutation scores are slow to compute, so run them on critical modules rather than whole projects. Used that way, they point precisely at weak assertions that coverage can't see.

The key insight Use coverage to find what is untested, never to prove what is well tested. Low numbers are informative; high numbers are not evidence of quality.

§4Common Mistakes

MistakeWhat HappensFix
Setting a hard coverage target for its own sakeTests with no assertions written to hit the numberUse coverage to find gaps; review tests for meaning
Treating 100% coverage as 'done'Missed boundary and logic bugs remainAdd boundary tests; try mutation testing on critical code
Ignoring uncovered critical pathsThe riskiest code, like error handling, is never runLook at what is missing from reports, and prioritize by risk
Practice
  1. Run a coverage report and pick the three riskiest uncovered areas to test first.
  2. Write a test that raises coverage without checking anything, then fix it so it fails if the code is broken.
  3. Run a mutation tool on one small module and look at the surviving mutants.
Key takeaways
  • Coverage shows what ran, not what was verified.
  • Targets distort behavior; use the number to find gaps.
  • Mutation testing checks whether tests would notice real bugs.
