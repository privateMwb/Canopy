Flaky Tests: Causes & Cures

A test that sometimes fails for no reason is worse than no test, because it teaches the team to ignore red builds.

§1Why Flakiness Is So Costly

A flaky test passes and fails on the same code. Once people see red builds that go away on a retry, they stop trusting failures, and a real bug eventually hides in the noise. Flakiness also wastes time as people re-run pipelines and investigate ghosts.

Treat a flaky test as a bug in the suite, to be fixed or removed, not tolerated.

§2The Usual Causes

CauseExampleCure
Shared stateTests share a database row or globalIsolate data per test; reset after each
Timingsleep(1) then assert; race with a background threadWait for a condition, not a duration; use a fake clock
Order dependencePasses alone, fails after another testRun in random order to expose it; remove the coupling
RandomnessUnseeded random data hits an edge caseSeed it and log the seed; or make inputs explicit
External systemsReal network, third-party API downFake it or run a local stand-in
EnvironmentTime zone, locale, file paths, CPU speedPin them in the test setup
# flaky: assumes the job finishes in 1 second
start_job(); time.sleep(1); assert job.done

# stable: wait for the condition, with a timeout
start_job(); wait_until(lambda: job.done, timeout=10); assert job.done

§3A Plan for Handling Them

First, reproduce: run the test in a loop (pytest --count=200) or in random order until it fails, and log everything. Then find the shared thing: state, time, order, randomness. Then fix the cause, not the symptom: adding a retry hides the flakiness without removing it.

If you can't fix it quickly, quarantine it: move it out of the blocking build into a separate job, file a ticket with an owner and a deadline, and keep it visible. A quarantine with no deadline is just a graveyard.

# random order exposes hidden dependencies
pytest -p random_order --random-order

# repeat to catch intermittent failures
pytest tests/test_jobs.py::test_retry --count=200
The key insight Fix the cause, not the symptom. A retry wrapper makes flaky tests quieter, never more correct.

§4Common Mistakes

MistakeWhat HappensFix
Adding automatic retries to flaky testsThe suite stays unreliable and hides real racesFind and fix the cause; quarantine meanwhile
Using sleep to wait for async workSlow when too long, flaky when too shortPoll for the condition with a timeout
Ignoring a test that fails 'sometimes'Trust in red builds erodesTrack flakes, assign owners, and set a deadline to fix or delete
Practice
  1. Run your suite in random order and list every test that fails.
  2. Replace one sleep in a test with a wait-for-condition helper.
  3. Set up a quarantine process: where flaky tests go, who owns them, and when they're deleted.
Key takeaways
  • A flaky test is a bug in the suite and erodes trust in every failure.
  • Common causes: shared state, timing, ordering, randomness, and external systems.
  • Reproduce, fix the cause, and quarantine with an owner and deadline.
