Designing for Testability: Dependency Injection & Seams

Code that makes its own database connections, reads the clock, and creates its own collaborators is hard to test. Passing those things in changes that.

§1Hidden Dependencies Block Tests

When a function reaches out for what it needs, such as datetime.now(), a global connection, or a hard-coded client, the test can't control it. Results change with the time of day, or the test needs a live service.

# untestable: depends on the real clock
def is_expired(token):
    return token.expires_at < datetime.now()

# testable: the dependency is passed in
def is_expired(token, now):
    return token.expires_at < now

assert is_expired(token_expiring_at(10), now=at(11)) is True

§2Dependency Injection

Dependency injection simply means passing collaborators in rather than creating them inside. No framework is required; a constructor argument is enough.

class ReminderService:
    def __init__(self, users, mailer, clock):
        self.users, self.mailer, self.clock = users, mailer, clock

    def send_due(self):
        for u in self.users.due_before(self.clock.now()):
            self.mailer.send(u.email, "Your invoice is due")

# production wiring, in one place at the edge
service = ReminderService(SqlUsers(db), SmtpMailer(), SystemClock())

# test wiring: fakes, no network, no waiting
service = ReminderService(InMemoryUsers(), FakeMailer(), FixedClock(at(9)))

§3Finding and Creating Seams

A seam is a place where you can change behavior without editing the code around it: an argument, a constructor parameter, an interface. Design seams at the boundaries of your system, where the code meets time, randomness, the file system, the network, and other services.

  • Time: pass a clock or a timestamp
  • Randomness: pass a random source or a seed
  • I/O: hide behind a small interface (read_file, send_email)
  • Configuration: pass values in; don't read environment variables deep inside logic

Wire everything together in one place, usually where the program starts. The rest of the code never calls new on a collaborator.

The key insight If a function is hard to test, the problem is usually its design, not the test. Moving a dependency out to a parameter often fixes both.

§4Common Mistakes

MistakeWhat HappensFix
Calling now(), random(), or global state inside logicTests depend on the time of day and on luckPass the clock or random source in
Creating collaborators inside constructorsNo way to substitute a fake without patchingAccept them as constructor arguments
A DI framework for a small programComplexity larger than the problemPlain constructor arguments are enough until the wiring gets large
Practice
  1. Make a function that calls datetime.now() take the time as an argument and test it at three moments.
  2. Refactor a class to take its database through the constructor and test it with a fake.
  3. List the seams your project has at its boundaries and find one that is missing.
Key takeaways
  • Pass dependencies in instead of reaching out for them.
  • Seams at time, randomness, and I/O boundaries make code testable.
  • Wire real implementations in one place, near the start of the program.
