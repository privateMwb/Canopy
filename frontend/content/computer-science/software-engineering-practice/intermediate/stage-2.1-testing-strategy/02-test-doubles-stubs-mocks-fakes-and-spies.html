Test Doubles: Stubs, Mocks, Fakes & Spies

Test doubles stand in for real collaborators, such as databases, clocks, and web services, so a test can run fast and deterministically. Each kind has a different job.

§1Four Kinds of Double

DoubleWhat it doesUse it to
StubReturns canned answersGive the code under test its inputs
FakeA simple working version (e.g. in-memory database)Replace a heavy dependency realistically
MockRecords calls and verifies themCheck that an interaction happened
SpyA real object that also records callsObserve without replacing
# stub: canned answer
class FixedClock:
    def now(self): return datetime(2026, 1, 1)

# fake: working but simple
class InMemoryUsers:
    def __init__(self): self._users = {}
    def add(self, u): self._users[u.id] = u
    def find(self, id): return self._users.get(id)

# mock: verify an interaction
mailer = Mock()
signup(user, mailer)
mailer.send.assert_called_once_with(user.email, "Welcome!")

§2The Danger of Over-Mocking

Mocks check how code works, not what it does. A test that asserts "method A called method B twice with these arguments" breaks whenever you refactor, even when behavior is unchanged. Heavy mocking produces tests that pass while the real system fails, because the mock agrees with your assumptions and nothing else.

# brittle: tied to implementation
repo.save.assert_called_once()
repo.flush.assert_called_once()
helper._normalize.assert_called_with(user)

# robust: check the outcome
signup(user, repo)
assert repo.find(user.id).email == "ana@example.com"

§3A Practical Rule

Prefer state-based checks (what ended up true) over interaction-based checks (what was called). Use fakes for things with real behavior, such as stores and queues; they make tests read naturally. Reserve mocks for outward effects you can't observe otherwise, like "an email was sent."

And don't mock what you don't own, such as a third-party library's internals. Wrap it in a small adapter of your own and fake that.

The key insight A test double should make a test simpler and more stable. If the test now mirrors the implementation line by line, you've mocked too much.

§4Common Mistakes

MistakeWhat HappensFix
Mocking everythingTests mirror the code and break on every refactorUse real objects or fakes; mock only outward effects
Verifying call counts and order by defaultTests lock in implementation detailsAssert on results and visible state instead
Mocking a third-party API directlyTests encode your guess of its behaviorWrap it in your own interface and fake that
Practice
  1. Rewrite one mock-heavy test as a state-based test with a fake.
  2. Write an in-memory fake for a repository and use it in three tests.
  3. Find a test that breaks when you rename a private method. Fix it.
Key takeaways
  • Stubs supply answers, fakes behave, mocks verify, spies observe.
  • Over-mocking couples tests to implementation.
  • Prefer fakes and state-based assertions; mock only outward effects.
