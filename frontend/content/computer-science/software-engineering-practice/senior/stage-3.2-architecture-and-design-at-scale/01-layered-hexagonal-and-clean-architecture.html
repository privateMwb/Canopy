Layered, Hexagonal & Clean Architecture

These three architectures share one idea: the business rules sit in the middle, and everything that changes for technical reasons sits around them, pointing inward.

§1The Problem: Logic Tangled With Frameworks

In many codebases, business rules end up inside web handlers and database queries. Then you can't test a pricing rule without an HTTP request and a database, changing the framework means rewriting the logic, and nobody can tell where the rules live.

# rule, framework, and database all in one function
@app.post("/orders")
def create_order():
    data = request.json
    if data["total"] > 1000 and not data["customer_vip"]:      # business rule
        return jsonify(error="approval needed"), 403
    db.execute("INSERT INTO orders ...", data)                  # persistence
    return jsonify(ok=True)                                     # HTTP

§2Ports and Adapters (Hexagonal)

Hexagonal architecture (ports and adapters) puts the core domain in the centre. The core defines ports, which are small interfaces describing what it needs from the outside (store orders, send mail), and what it offers. Adapters at the edge implement those ports for a particular technology: a SQL adapter, an HTTP adapter, a test fake.

            +--------------------------------+
 HTTP  ---> |   adapters                     | ---> SQL database
 CLI   ---> |      +------------------+      | ---> email service
 tests ---> |      |  domain / use    |      | ---> fakes in tests
            |      |  cases           |      |
            |      +------------------+      |
            +--------------------------------+
   dependencies always point INWARD toward the domain
class OrderRepository(Protocol):                 # port, owned by the domain
    def add(self, order): ...

def place_order(order, repo: OrderRepository):    # use case: pure of frameworks
    if order.total > 1000 and not order.customer_vip:
        raise ApprovalNeeded()
    repo.add(order)

class SqlOrderRepository:                         # adapter, at the edge
    def add(self, order): db.execute("INSERT ...", order.as_row())

§3The Dependency Rule and Its Costs

Clean architecture and layered designs express the same rule in rings or tiers: source-code dependencies may only point inward, toward policy. The inner layers never import the outer ones. A change of database or web framework then touches only an adapter.

  • Benefit: business rules are fast to test, outlive framework fashion, and are easy to find
  • Cost: more files, mapping between layers, and indirection
  • When it pays: long-lived systems with real business logic, several delivery channels, or a likelihood of changing infrastructure
  • When it doesn't: a small CRUD app or a script; a thin layer of well-named functions is enough

Adopt as much structure as the complexity of the domain justifies, and no more.

The key insight The question behind every one of these architectures is: which direction do the dependencies point? Policy should not depend on detail.

§4Common Mistakes

MistakeWhat HappensFix
Domain classes importing the web framework or ORMThe core can't be tested or reused without themDefine ports in the core; implement them at the edges
Many layers for a tiny appCeremony that costs more than it savesScale the structure to the domain's complexity
Leaking database rows or HTTP objects into the coreThe core becomes shaped by infrastructureMap at the boundary into domain objects
Practice
  1. Draw the current dependency directions of a service you work on. Which point outward?
  2. Move one business rule out of a request handler into a function with no framework imports.
  3. Define a port for storage and write an in-memory adapter for tests.
Key takeaways
  • Keep business rules in the center and technology at the edges.
  • Dependencies point inward; ports are owned by the core, adapters implement them.
  • Match the amount of structure to the real complexity.
