Stable Interfaces & Backward Compatibility

Once other people depend on an interface, changing it is expensive. Designing boundaries that can evolve is one of the most valuable senior skills.

§1Every Observable Behavior Becomes a Contract

Hyrum's law: with enough users of an interface, every observable behavior of it will be depended on by somebody, whether or not you promised it. Someone will rely on the order of your results, the exact text of an error, or a quirk in timing.

That means a public interface is bigger than its documentation. The defense is to expose as little as possible, because anything you never exposed can't be depended on.

§2Compatible and Breaking Changes

ChangeCompatible?Why
Add an optional field or parameterYesExisting callers don't send or need it
Add a new endpoint or functionYesNothing existing changes
Remove or rename a fieldNoCallers that use it break
Make an optional input requiredNoExisting calls become invalid
Change a field's type or meaningNoSilent misreads are worst of all
Tighten validation or error behaviorMaybeDepends who relied on the lenient behavior

Follow be conservative in what you send, liberal in what you accept. Ignoring unknown fields lets producers add things safely.

§3Evolving Without Breaking

  • Version deliberately: put the version in the path or a header, and keep old versions alive for a stated period
  • Deprecate in steps: announce, add warnings and metrics, find remaining users, then remove
  • Expand, then contract: add the new form, migrate callers, and only then delete the old one
  • Measure usage before removing anything; logs tell you who still depends on it
  • Write contract tests for consumers so a breaking change fails in CI, not in production
# expand/contract in three releases
v1: { "name": "Ana Ruiz" }
v2: { "name": "Ana Ruiz", "first_name": "Ana", "last_name": "Ruiz" }   # expand
v3: { "first_name": "Ana", "last_name": "Ruiz" }  # contract, after callers moved

The same ideas apply inside a codebase: module boundaries between teams are APIs too, and deserve the same care.

The key insight Making an interface smaller is safe and making it larger is permanent. Add only what you're prepared to support for years.

§4Common Mistakes

MistakeWhat HappensFix
Exposing internals 'just in case'Consumers depend on them and you can no longer change themKeep the interface minimal and add on request
Removing a field in the next releaseClients break with no warningDeprecate, measure usage, migrate callers, then remove
Assuming only documented behavior is relied onUndocumented quirks become de facto contractsTest compatibility with real consumers; keep unpromised behavior unpredictable where you can
Practice
  1. Classify five recent changes to one of your APIs as compatible or breaking.
  2. Write a deprecation plan with dates and metrics for one old field.
  3. Find one undocumented behavior your own team relies on.
Key takeaways
  • Everything observable can become a contract (Hyrum's law).
  • Additions are compatible; removals and meaning changes are breaking.
  • Evolve by expanding, migrating, and then contracting.
