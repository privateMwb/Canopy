Trunk-Based Development & Feature Flags

The more often a team integrates, the less painful integration gets. Trunk-based development takes that to its conclusion, with feature flags making it safe.

§1The Cost of Long-Lived Branches

A branch that lives for weeks drifts away from the main line. The longer it lives, the more conflicts it accumulates, the more it is tested in isolation, and the larger the final merge becomes. The pain grows faster than the time: merging two weeks of work is far more than twice as hard as merging one.

long-lived branch:    main  --A--B--C--D--E--F--G--H--  (everyone else moves on)
                           \                        /
                            x---------x------------x   (big merge, big risk)

trunk-based:          main  --A--B--C--D--E--F--G--H--
                            small branches, merged within a day or two

This is why "continuous integration" really means merging to the shared trunk at least daily, not just running a build server.

§2Trunk-Based Development

In trunk-based development, everyone commits to one main branch, either directly or through short-lived branches that last hours or a day or two. The trunk is always releasable. Teams that practice this tend to ship more often and with fewer surprises.

  • Branches live no longer than a couple of days
  • Small changes merge continuously, with tests running on every merge
  • A broken trunk is fixed or reverted within minutes
  • Large changes are broken into steps that can each merge safely

§3Feature Flags Make It Possible

How do you merge half-built work without exposing it? Hide it behind a flag. The code ships in the trunk but stays off until it's ready, so integration is decoupled from release.

if flags.enabled("new_search"):
    results = new_search(query)
else:
    results = old_search(query)       # production behaviour is unchanged

# day 1: merge flag + empty new_search     (flag off)
# day 3: merge ranking logic               (flag off)
# day 9: turn on for staff, then 5%, then everyone
# day 20: delete the flag and the old path
  • Release flags: hide unfinished work; short-lived
  • Ops flags: kill switches for risky features; long-lived
  • Experiment flags: A/B tests; removed after the result
  • Pay the cost: flags multiply code paths, so test both states and delete flags promptly

A related technique, branch by abstraction, covers large internal changes: introduce an interface, switch callers gradually, then replace the implementation behind it.

The key insight Integration pain is proportional to how long work stays apart. Merge small and often, and separate deploying code from turning features on.

§4Common Mistakes

MistakeWhat HappensFix
Feature branches that live for weeksPainful merges and late discovery of conflictsMerge in small steps, using flags for unfinished work
Flags that are never removedDead branches of code and untested combinationsGive each flag an owner and removal date
Merging with a red or slow buildA broken trunk blocks everyoneKeep checks fast and revert first, investigate after
Practice
  1. Take a week-long branch and write the plan to land it in five day-sized merges behind a flag.
  2. Measure the age of your open branches and set a limit.
  3. Add a release flag to an in-progress feature and test both states.
Key takeaways
  • Frequent small merges keep integration cheap.
  • Feature flags separate deploying code from releasing features.
  • Remove flags when they've done their job.
