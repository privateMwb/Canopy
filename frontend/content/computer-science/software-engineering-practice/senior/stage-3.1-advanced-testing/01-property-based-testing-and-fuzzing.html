Property-Based Testing & Fuzzing

Example-based tests check the cases you thought of. Property-based tests and fuzzers hunt for the ones you didn't.

§1Properties Instead of Examples

A property is a rule that should hold for every valid input. Instead of writing reverse([1,2,3]) == [3,2,1], you state the rule, and a tool generates hundreds of random inputs to try to break it.

from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_reversing_twice_gives_the_original(xs):
    assert list(reversed(list(reversed(xs)))) == xs

@given(st.lists(st.integers()))
def test_sorting_keeps_length_and_orders_items(xs):
    out = sorted(xs)
    assert len(out) == len(xs)
    assert all(a <= b for a, b in zip(out, out[1:]))

Properties are harder to think of than examples, but they force you to say what the code is really for.

§3Shrinking and Fuzzing

When a property fails, a good tool shrinks the failing input to the smallest one that still fails. Instead of a 400-element list, you get [0, -1], which is far easier to debug. Save the failing case as an ordinary regression test.

Fuzzing takes the idea to extremes: it feeds massive amounts of semi-random, mutated input to find crashes, hangs, and memory errors, especially in parsers and anything handling untrusted data. Coverage-guided fuzzers (libFuzzer, AFL, Atheris) watch which code paths each input reaches and evolve inputs to explore new ones.

# libFuzzer-style harness: the fuzzer calls this millions of times
extern "C" int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size) {
    parse_message(data, size);     // must never crash, hang, or leak
    return 0;
}

Run them with sanitizers (address, undefined behavior) so silent memory bugs become loud crashes.

The key insight Example tests check what you imagined; property tests check what you claimed. The gap between them is where surprising bugs live.

§4Common Mistakes

MistakeWhat HappensFix
Properties that just re-implement the codeThe test repeats any bug in the logicUse round trips, invariants, and simple oracles instead
Ignoring the shrunk failureYou debug the huge original inputRead the minimal case, then add it as a fixed example test
Fuzzing without sanitizers or time limitsMemory bugs go unnoticed and runs hangEnable address and UB sanitizers and set input and time limits
Practice
  1. Write a round-trip property for a serializer of your own and let it find a bug.
  2. Add an idempotence property to a normalization function.
  3. Run a fuzzer against a small parser for ten minutes with sanitizers on.
Key takeaways
  • Properties state rules for all inputs; tools search for counterexamples.
  • Shrinking reduces a failure to a minimal, debuggable case.
  • Fuzzing with sanitizers finds crashes in code that handles untrusted input.
