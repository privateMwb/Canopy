Choosing Cases: Boundaries & Equivalence Classes

You can't test every input, so the skill is choosing the handful that are most likely to expose a bug, which is why boundaries matter more than middles.

§1Equivalence Classes

Many inputs behave the same way. For a function that gives a discount to people aged 65 and over, ages 70 and 90 are equivalent: if one works, the other almost certainly does. Group inputs into equivalence classes and test one representative from each.

def ticket_price(age):
    if age < 0 or age > 120: raise ValueError("invalid age")
    if age < 13:  return 8      # child
    if age >= 65: return 10     # senior
    return 15                   # adult

# classes: invalid-low, child, adult, senior, invalid-high

§2Boundaries Are Where Bugs Live

Programmers make mistakes at edges: < where <= was meant, an off-by-one in a loop, an empty list nobody considered. So test at and around every boundary: the last value in a class and the first value in the next one.

import pytest

@pytest.mark.parametrize("age, price", [
    (0, 8), (12, 8),      # child range, both ends
    (13, 15), (64, 15),   # adult range, both ends
    (65, 10), (120, 10),  # senior range, both ends
])
def test_ticket_price_at_boundaries(age, price):
    assert ticket_price(age) == price

@pytest.mark.parametrize("age", [-1, 121])
def test_ticket_price_rejects_invalid_age(age):
    with pytest.raises(ValueError):
        ticket_price(age)

§3The Zero, One, Many Habit

For anything that handles collections, strings, or counts, always try zero, one, and many: an empty list, a single element, and several. Add the awkward cases that fit your domain: None, a string with spaces, duplicates, a very large number.

  • Numbers: 0, 1, -1, the smallest and largest allowed, and just outside the range
  • Collections: empty, one item, many items, duplicates
  • Strings: empty, one character, whitespace only, non-ASCII text
  • Time and dates: midnight, month ends, leap days, time zones
The key insight Test the edges of every range, not the middle. A test at age 40 tells you almost nothing; tests at 12, 13, 64, and 65 tell you a lot.

§4Common Mistakes

MistakeWhat HappensFix
Testing only typical valuesOff-by-one and empty-input bugs surviveAdd the first and last value of each class and just outside it
Testing every possible inputThe suite is huge, slow, and still incompleteOne representative per equivalence class, plus the boundaries
Forgetting invalid inputThe code crashes or silently returns nonsense on bad dataDecide the behavior for invalid input and test it explicitly
Practice
  1. List the equivalence classes and boundaries for a function grade(score) that maps 0-100 to A-F.
  2. Write a parametrized test for it, including scores of -1 and 101.
  3. Find a loop in your own code and write zero, one, and many tests for it.
Key takeaways
  • Group inputs into equivalence classes and test one from each.
  • Test on and around every boundary, where most bugs live.
  • Always consider zero, one, many, and invalid input.
