Anatomy of a Unit Test: Arrange, Act, Assert

Every good unit test has the same three parts in the same order, and learning to see them makes tests easy to read and easy to trust.

§1Arrange, Act, Assert

A unit test arranges the inputs and objects it needs, acts by calling the one thing being tested, and asserts that the result is what was expected. Separating the three with blank lines makes a test readable at a glance.

def test_cart_total_adds_item_prices():
    # arrange
    cart = Cart()
    cart.add(Item("pen", price=3))
    cart.add(Item("book", price=12))

    # act
    total = cart.total()

    # assert
    assert total == 15

§2One Reason to Fail

A test should fail for exactly one reason. When one test checks five unrelated things, a red result does not tell you which behavior broke. Prefer several small tests over one long one, and give each a name that states the behavior.

# vague: what broke if this fails?
def test_cart():
    ...

# specific: the name is the spec
def test_total_of_empty_cart_is_zero():
    assert Cart().total() == 0

def test_adding_same_item_twice_counts_it_twice():
    cart = Cart()
    cart.add(Item("pen", price=3)); cart.add(Item("pen", price=3))
    assert cart.total() == 6

§3Independent and Visible

Each test must build its own world and must not depend on another test having run first. If tests share a mutable object, they pass or fail depending on order, which is one of the most frustrating bugs to chase.

Keep everything the test needs visible in the test itself. If you must scroll to another file to understand why the expected value is 15, the test is hiding its own meaning.

# fragile: shared state across tests
cart = Cart()
def test_a(): cart.add(Item("pen", 3)); assert cart.total() == 3
def test_b(): assert cart.total() == 0     # fails if test_a ran first

# robust: every test makes its own cart
def test_b(): assert Cart().total() == 0
A useful habit Read the test name aloud as a sentence: "total of empty cart is zero." If it doesn't make sense as a claim about the code, the test is testing too much or the name is too vague.

§4Common Mistakes

MistakeWhat HappensFix
Many assertions about unrelated behavior in one testA failure doesn't say which behavior brokeOne behavior per test; split and name each clearly
Tests that share mutable stateResults depend on execution order and fail randomlyCreate fresh objects in each test, or use a fixture that resets
Computing the expected value with the same logic as the codeThe test repeats the bug and still passesWrite the expected value by hand as a literal
Practice
  1. Rewrite a long test of your own into three small ones with names that read as sentences.
  2. Find a test that depends on another test running first. Make it independent.
  3. Take any function and write its test using blank lines to mark arrange, act, and assert.
Key takeaways
  • Arrange the inputs, act once, assert the outcome.
  • One behavior per test, with a name that states it.
  • Tests must be independent and must show their own expected values.
