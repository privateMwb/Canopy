Pure Functions, Immutability & Side Effects

Code whose output depends only on its inputs, and that changes nothing else, is the easiest kind to test and understand, so it pays to build as much of your program as possible that way.

§1What a Pure Function Is

A pure function always returns the same output for the same input and has no side effects: it doesn't modify anything outside itself, read the clock, touch files, or print. Because it can't surprise you, you can understand it by reading it and test it with one line.

# impure: result depends on hidden state, and it changes state
total = 0
def add_to_total(x):
    global total
    total += x
    return total

# pure: depends only on arguments
def add(a, b):
    return a + b

§2Immutability

Data that never changes after it's created removes a whole class of bugs. If nobody can modify an object, nobody can modify it by mistake from far away, and sharing it between parts of a program or threads is safe.

from dataclasses import dataclass

@dataclass(frozen=True)
class Money:
    amount: int
    currency: str

price = Money(500, "USD")
# price.amount = 1   # error: cannot assign
discounted = Money(price.amount - 50, price.currency)   # make a new value

§3Push Side Effects to the Edges

Real programs must read files, call networks, and print. The trick is to keep those effects at the edges and put the decisions in a pure core. The core is then easy to test with plain values; the thin shell around it does the I/O.

# mixed: logic tangled with I/O, hard to test
def report():
    rows = db.query("SELECT amount FROM sales")
    total = sum(r[0] for r in rows)
    print(f"Total: {total}")

# separated
def total_sales(amounts):            # pure core: test with a list
    return sum(amounts)

def report():                        # thin shell: reads, calls, prints
    amounts = [r[0] for r in db.query("SELECT amount FROM sales")]
    print(f"Total: {total_sales(amounts)}")
The key insight Most of the code you need to get right can be pure. Keep the impure parts small and boring, so the logic worth testing never needs a database or a clock.

§4Common Mistakes

MistakeWhat HappensFix
Functions that quietly modify their argumentsCallers' data changes unexpectedly, causing distant bugsReturn a new value, or make the mutation obvious in the name
Hidden dependencies on time, randomness, or globalsResults differ per run and tests become flakyPass the time or random value in as an argument
Trying to make everything pureUnnatural code that can't do any real workKeep a pure core and accept side effects at the edges
Practice
  1. Pick a function with a side effect and split it into a pure calculation and a thin wrapper.
  2. Replace a function that reads datetime.now() with one that takes the time as an argument.
  3. Make one data class frozen and fix the code that tried to change it.
Key takeaways
  • Pure functions depend only on their inputs and change nothing else.
  • Immutable data cannot be changed by mistake from somewhere far away.
  • Keep side effects at the edges and logic in a pure core.
