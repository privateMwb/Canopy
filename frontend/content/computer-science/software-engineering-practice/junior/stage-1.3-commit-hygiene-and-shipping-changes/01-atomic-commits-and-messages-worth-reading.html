Atomic Commits & Messages Worth Reading

Version control history is documentation. Atomic commits and clear messages make it something you can actually use.

§1One Logical Change per Commit

An atomic commit contains one logical change: a bug fix, a rename, a new function with its test. It should leave the project in a working state. Small, focused commits are easy to review, easy to revert, and easy to find later.

# bad: one commit, five unrelated things
git commit -m "fixes and stuff"

# good: a series of focused commits
git commit -m "Rename Invoice.amt to Invoice.amount"
git commit -m "Fix rounding of tax on discounted items"
git commit -m "Add tests for zero-quantity line items"

Use git add -p to stage only some of the changes in a file, so unrelated edits don't ride along in the same commit.

§2Messages Worth Reading

A good message has a short summary line (about 50 characters, imperative mood) and, when needed, a blank line and a body explaining why the change was made. The diff already shows what changed; the message supplies the reason.

Fix double charge when payment retry succeeds

The retry handler created a second charge before checking the
status of the first. Check for an existing successful charge and
return it instead. Fixes #482.

Write the summary so it completes the sentence "If applied, this commit will...": *Fix double charge*, *Add retry limit*, *Remove unused config*.

§3Why It Pays Off

Months later, git log and git blame are how you learn why code is the way it is. A history of wip, fix, and stuff is useless; a history of clear commits is a project diary. Tools like git bisect and git revert only work well when each commit is one self-contained change.

git log --oneline          # a readable story, if commits are good
git blame payments.py      # why is this line here? the message tells you
git revert 3f2a1c9         # undo exactly one idea, if the commit was atomic
A useful habit Before committing, ask: could I describe this commit in one sentence without 'and'? If not, split it.

§4Common Mistakes

MistakeWhat HappensFix
Giant commits mixing unrelated changesImpossible to review or revert cleanlyStage related changes together with git add -p
Messages like 'fix' or 'wip'History says nothing about intentWrite a summary in imperative mood, and add the why when it isn't obvious
Committing broken or half-done states to shared branchesOthers pull a broken build; bisecting gets confusingKeep each commit building and passing, or tidy before sharing
Practice
  1. Look at your last ten commits and rewrite each message in imperative mood in a notes file.
  2. Make a change touching two unrelated things and commit them separately with git add -p.
  3. Pick an old line in your code and use git blame to find out why it exists.
Key takeaways
  • One logical change per commit.
  • A summary line in imperative mood, and a body that explains why.
  • Good history is documentation that pays off in blame, bisect, and revert.
