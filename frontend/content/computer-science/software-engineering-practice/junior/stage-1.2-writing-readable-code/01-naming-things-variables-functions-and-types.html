Naming Things: Variables, Functions & Types

Code is read far more often than it is written, and a good name is the cheapest way to make it readable.

§1Names Should Reveal Intent

A name should answer what something is, why it exists, and how it's used, without needing a comment. If a name needs one, the name is wrong. Compare the same logic with two sets of names.

# unclear
def f(l, d):
    r = []
    for x in l:
        if x[2] > d: r.append(x)
    return r

# clear
def overdue_invoices(invoices, today):
    return [inv for inv in invoices if inv.due_date < today]

§2Practical Rules

  • Use nouns for things and verbs for actions: invoice, send_invoice.
  • Booleans read as questions: is_paid, has_discount, not paid_flag.
  • Avoid vague words: data, info, manager, handle, process. Say what kind.
  • Be consistent: pick fetch or get or load for the same idea and stick to it.
  • Scale length to scope: i is fine in a three-line loop; a module-level name needs more.

Avoid abbreviations unless everyone already uses them (url, id). cust_acct_bal saves nine keystrokes and costs every reader a pause.

§3Renaming Is the Cheapest Refactoring

When you finally understand what a variable holds, rename it right away. Modern editors rename safely across a whole project in one step, and the improvement helps every future reader, including you in three months.

# you realize 'tmp' is really the retry delay in seconds
tmp = 30                      # before
retry_delay_seconds = 30      # after: no comment needed
The key insight If you struggle to name something, that is often a design signal. A function you can only call process_stuff probably does several things and should be split.

§4Common Mistakes

MistakeWhat HappensFix
Single-letter or cryptic names outside tiny scopesReaders must decode every lineUse full words that say what the value is
Names that lieA variable called users holding one user, or get_x that also modifies state, misleads for yearsRename as soon as meaning changes
Inconsistent vocabularyfetch_user, get_order, load_invoice suggest differences that don't existChoose one verb per concept across the codebase
Practice
  1. Rename every variable in a 20-line function of your own so the code needs no comments.
  2. Find three vague names (data, item, result) in a project and replace them with specific ones.
  3. Pick a boolean named flag or status and rename it as a question.
Key takeaways
  • A name should tell you what, why, and how without a comment.
  • Be consistent, avoid vague words, and make booleans read as questions.
  • Hard-to-name things are often badly designed; rename as soon as you understand.
