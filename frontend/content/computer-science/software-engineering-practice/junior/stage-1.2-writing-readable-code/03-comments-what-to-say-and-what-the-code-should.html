Comments: What to Say and What the Code Should

Comments are a tool for explaining what the code cannot say for itself. Use them for why, and let the code carry the what.

§1Explain Why, Not What

A comment that restates the code adds noise and a second thing to keep updated. A comment that explains a decision, a constraint, or a surprise saves the next reader real time.

# bad: says what the code already says
i = i + 1   # add one to i

# good: says why
# The payment API rejects amounts with more than 2 decimals, so round
# here rather than at the call site.
amount = round(amount, 2)

§2Comments That Go Bad

Comments are not checked by the compiler or tests, so they drift away from the code and become false. A wrong comment is worse than none, because readers trust it.

# Returns the user's age in years        <- still says "years"
def user_age(user):
    return (today() - user.birthdate).days   # ...but now returns days

§3Better Than a Comment

Before writing a comment, try making the code say it. Rename, extract a function, or introduce a named constant.

# before
if age >= 65:   # eligible for senior discount
    ...

# after: the code is the comment
SENIOR_AGE = 65
if age >= SENIOR_AGE:
    ...

Keep comments for what code can't express: why a workaround exists, a link to the bug it avoids, a warning about a non-obvious consequence, or the reasoning behind a surprising algorithm. Good docstrings describing a public function's contract are also valuable.

  • Do comment: intent, tradeoffs, workarounds, links to specs or tickets, warnings
  • Don't comment: what the next line obviously does, history (that's what Git is for), commented-out code
The key insight Delete commented-out code. Version control remembers it for you, and dead code in a file makes readers wonder whether it matters.

§4Common Mistakes

MistakeWhat HappensFix
Comments that repeat the codeNoise that has to be maintained and gets staleDelete them, or rename to make the code self-explanatory
Leaving commented-out codeClutter and confusion about whether it's neededDelete it; Git has the history
Not updating a comment when code changesThe comment now lies and readers trust itTreat comments as part of the change, and reread nearby ones when editing
Practice
  1. Go through one file and delete every comment that only restates the code.
  2. Replace two comments with better names or extracted functions.
  3. Add one 'why' comment to a place in your code that would surprise a new teammate.
Key takeaways
  • Comment the why, not the what.
  • Prefer clearer code to an explanatory comment.
  • Delete commented-out code and keep comments accurate.
