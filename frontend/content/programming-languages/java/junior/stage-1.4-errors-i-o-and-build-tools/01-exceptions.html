Exceptions

Exceptions separate the normal path of a program from its error handling, and the skill lies in knowing which to throw, which to catch, and which to let propagate.

§1The Hierarchy

Every exception is a Throwable. There are two main branches below it, and a third rule that follows from them.

KindExamplesRule
Checked (Exception but not RuntimeException)IOException, SQLExceptionThe compiler forces you to catch it or declare it with throws
Unchecked (RuntimeException)NullPointerException, IllegalArgumentException, IllegalStateExceptionUsually a bug or a violated precondition; no declaration required
Errors (Error)OutOfMemoryError, StackOverflowErrorThe JVM is in trouble; don't try to recover

The usual guidance: use a checked exception when a caller can reasonably recover (a missing file, a failed network call) and an unchecked exception for programming errors (a null argument, an impossible state). Many modern libraries lean toward unchecked exceptions because checked ones spread through every signature.

§2Throwing and Catching

static int parsePort(String s) {
    if (s == null) throw new IllegalArgumentException("port is required");
    try {
        int p = Integer.parseInt(s.trim());
        if (p < 1 || p > 65535) throw new IllegalArgumentException("out of range: " + p);
        return p;
    } catch (NumberFormatException e) {
        throw new IllegalArgumentException("not a number: " + s, e);   // keep the cause
    } finally {
        System.out.println("parse attempted");             // always runs
    }
}

A try can have multiple catch blocks; the first match wins, so list specific types before general ones. You can combine unrelated types with catch (IOException | SQLException e). The finally block runs whether or not an exception occurred, which is where cleanup used to go (the next lesson shows the better tool).

§3Custom Exceptions

Create your own when callers need to react differently to a particular failure. Extend Exception for checked, RuntimeException for unchecked, and always allow a message and a cause.

public class InsufficientFundsException extends Exception {
    private final long shortfallCents;
    public InsufficientFundsException(long shortfallCents) {
        super("short by " + shortfallCents + " cents");
        this.shortfallCents = shortfallCents;
    }
    public long shortfallCents() { return shortfallCents; }
}

void withdraw(long cents) throws InsufficientFundsException {
    if (cents > balance) throw new InsufficientFundsException(cents - balance);
    balance -= cents;
}

§4What to Catch

Catch an exception only if you can do something useful: retry, use a default, translate it into a better exception, or report it at a boundary such as the top of a request handler. Otherwise let it propagate. Two rules prevent most bad code: never swallow an exception with an empty catch, and never lose the cause when you rethrow, by passing it to the new exception's constructor.

try {
    save(order);
} catch (IOException e) {
    throw new UncheckedIOException("could not save order " + order.id(), e);   // cause preserved
}
The stack trace is the evidence When an exception is logged or printed, the full trace shows exactly where and why it happened. Catching an exception and throwing away its trace, or logging only e.getMessage(), throws away the best debugging information you have.

§5Common Mistakes

MistakeWhat HappensFix
An empty catch blockThe failure disappears and the program continues in a bad stateHandle it, rethrow it, or at least log it with the stack trace
catch (Exception e) everywhereHides bugs and catches things you can't handleCatch the most specific type you can handle
Rethrowing without the cause: throw new X("failed")The original stack trace is lostPass the cause: new X("failed", e)
Using exceptions for normal control flowSlow, and hard to readUse return values or checks (hasNext, isEmpty)
Putting a return inside finallyIt silently swallows any exception in flightKeep finally for cleanup only
Practice
  1. Write parseAge(String) that throws IllegalArgumentException for non-numeric or negative input, preserving the original cause.
  2. Define a checked ConfigMissingException and a method that throws it. Call it from main and decide which layer should catch it.
  3. Find a catch block in some code you've written and ask whether it handles, translates, or merely hides the error.
Key takeaways
  • Checked exceptions are for recoverable conditions, unchecked for programming errors, and Error is not for catching.
  • Catch only what you can handle, never swallow, and always preserve the cause.
  • Custom exceptions let callers react to specific failures with useful data.
