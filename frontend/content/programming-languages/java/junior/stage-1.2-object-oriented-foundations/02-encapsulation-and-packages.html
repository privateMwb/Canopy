Encapsulation & Packages

Encapsulation means hiding an object's internals behind a small public interface so it can protect its own invariants, and packages organize classes into namespaces.

§1Access Modifiers

Java has four access levels. Use the narrowest one that works.

ModifierVisible to
privateThe same class only
(no modifier), called "package-private"Classes in the same package
protectedThe same package, plus subclasses
publicEveryone

Make fields private by default and expose behavior, not raw data. That lets a class enforce rules that must always hold (its invariants).

public class BankAccount {
    private long balanceCents;                       // cannot be set to nonsense from outside

    public void withdraw(long cents) {
        if (cents <= 0) throw new IllegalArgumentException("amount must be positive");
        if (cents > balanceCents) throw new IllegalStateException("insufficient funds");
        balanceCents -= cents;
    }
    public long balanceCents() { return balanceCents; }   // read-only access
}

If balanceCents were public, any code anywhere could set it to a negative number and no check could stop it. Encapsulation also lets you change the internals later (store a BigDecimal, say) without breaking callers.

§2Getters, Setters, and Leaks

Don't add a getter and setter for every field automatically; that is just a public field with extra typing. Expose what callers need. Be careful with getters that return mutable objects, since they hand out the internals.

public class Team {
    private final java.util.List<String> members = new java.util.ArrayList<>();

    public java.util.List<String> badMembers() { return members; }            // caller can add or clear
    public java.util.List<String> members() { return java.util.List.copyOf(members); }  // safe snapshot
}

§3Packages

A package groups related classes and prevents name clashes. Packages are named in reverse-domain style and the folder structure must match.

// file: src/com/example/bank/BankAccount.java
package com.example.bank;

// file: src/com/example/app/Main.java
package com.example.app;
import com.example.bank.BankAccount;     // needed to use it from another package
javac -d out src/com/example/bank/*.java src/com/example/app/*.java
java -cp out com.example.app.Main        # fully qualified class name

import only saves typing; it does not load anything. A package-private class or member is invisible outside its package, which is a useful way to hide helper classes.

Keep the public surface small Every public method is a promise you may have to keep forever. Start private, and widen access only when another class genuinely needs it.

§4Common Mistakes

MistakeWhat HappensFix
Making every field publicAny code can break the object's invariantsMake fields private and validate in methods
Returning a mutable internal list from a getterCallers modify the object's internal stateReturn a copy or an unmodifiable view
Package name doesn't match the folder pathNoClassDefFoundError or "wrong name" errorsKeep package com.x.y; and com/x/y/ in sync
Running java Main for a class in a packageCould not find or load main classRun java -cp out com.example.app.Main
Reaching for protected out of habitSubclasses and package neighbors can both touch itPrefer private, and offer a method if needed
Practice
  1. Write a Temperature class that stores degrees Celsius privately, rejects values below absolute zero, and exposes celsius() and fahrenheit().
  2. Put two classes in different packages under src/, compile with -d out, and run the main class by its fully qualified name.
  3. Find a getter in your own code that returns a mutable object and rewrite it to return a copy.
Key takeaways
  • Make fields private and expose behavior so a class can protect its invariants.
  • Never return a mutable internal object directly; copy or use an unmodifiable view.
  • Packages are namespaces that must match the directory layout; import only saves typing.
