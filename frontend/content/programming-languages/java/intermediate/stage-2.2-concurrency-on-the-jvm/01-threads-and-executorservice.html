Threads & ExecutorService

A thread is an independent path of execution, but in real code you hand tasks to a pool through an ExecutorService rather than creating and managing threads yourself.

§1Creating a Thread

A Thread runs a Runnable. Calling start() begins concurrent execution; calling run() directly just runs the code on the current thread, which is a classic mistake. join() waits for a thread to finish.

Thread t = new Thread(() -> System.out.println("hello from " + Thread.currentThread().getName()));
t.start();               // new thread runs the lambda
t.join();                // wait until it finishes (throws InterruptedException)

Thread bad = new Thread(() -> System.out.println("oops"));
bad.run();               // NOT concurrent: runs on the calling thread

Starting a thread per task works for toy programs, but platform threads are expensive (each reserves stack memory and is backed by an operating system thread), and an unbounded number of them will exhaust the machine. Threads also give you no easy way to get a result back or capture an exception.

§2ExecutorService and Pools

An ExecutorService separates what to run (tasks) from how to run it (threads). You submit tasks, and a pool of reusable worker threads runs them.

try (ExecutorService pool = Executors.newFixedThreadPool(4)) {      // closes on exit (Java 19+)
    Future<Integer> f = pool.submit(() -> {
        Thread.sleep(500);
        return 42;
    });
    pool.execute(() -> System.out.println("fire and forget"));       // no result

    System.out.println(f.get());                                      // blocks until done
}

submit returns a Future representing the pending result. Future.get() blocks and rethrows any exception from the task wrapped in an ExecutionException; get(timeout, unit) bounds the wait. invokeAll runs a list of callables and waits for all of them; invokeAny returns the first to succeed.

List<Callable<String>> jobs = List.of(() -> "a", () -> "b", () -> "c");
List<Future<String>> results = pool.invokeAll(jobs);
for (Future<String> r : results) System.out.println(r.get());

The factory methods give different pool shapes: newFixedThreadPool(n) for a bounded pool, newCachedThreadPool() for short bursty tasks (unbounded: be careful), newSingleThreadExecutor() for strict ordering, and newScheduledThreadPool(n) for delayed and periodic work. Size a CPU-bound pool near the number of cores (Runtime.getRuntime().availableProcessors()); I/O-bound work can use more threads.

§3Shutdown and Interruption

A pool's threads keep the JVM alive, so you must shut the pool down. shutdown() stops accepting new tasks and lets queued ones finish; shutdownNow() interrupts running tasks. Java 19+ ExecutorService is AutoCloseable, so try-with-resources waits for completion.

pool.shutdown();
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
    pool.shutdownNow();                  // give up: interrupt workers
}

Cancellation in Java is cooperative: interrupt() sets a flag and wakes blocking calls with InterruptedException. Your task must check for it and stop. Never swallow the exception silently; either propagate it or restore the flag with Thread.currentThread().interrupt().

while (!Thread.currentThread().isInterrupted()) {
    try { doStep(); Thread.sleep(100); }
    catch (InterruptedException e) {
        Thread.currentThread().interrupt();    // restore the flag
        break;
    }
}
Tasks, not threads Think in terms of units of work to be done. Let the executor decide the threads. That makes concurrency level a configuration choice instead of something baked into the code.

§4Common Mistakes

MistakeWhat HappensFix
Calling run() instead of start()The code runs on the current thread, with no concurrencyCall start(), or submit to an executor
Never shutting down an executorThe JVM never exits because the worker threads are still aliveCall shutdown(), or use try-with-resources
newCachedThreadPool() for unbounded, slow tasksThousands of threads and out-of-memory errorsUse a bounded pool
Swallowing InterruptedExceptionTasks can't be cancelled and shutdown hangsRestore the interrupt flag or rethrow
Calling Future.get() immediately after each submitSerializes the work, defeating the poolSubmit everything first, then collect results
Practice
  1. Submit ten tasks that each sleep for one second to a pool of four threads and time the total. Predict first, then check.
  2. Write a task that loops until interrupted, run it in a pool, and cancel it with future.cancel(true).
  3. Make a task throw an exception and show how it appears when you call get().
Key takeaways
  • start() creates concurrency; run() doesn't, and raw threads are expensive and hard to manage.
  • An ExecutorService runs tasks on reusable threads, returns Futures, and must be shut down.
  • Cancellation is cooperative through interruption, so never swallow InterruptedException.
