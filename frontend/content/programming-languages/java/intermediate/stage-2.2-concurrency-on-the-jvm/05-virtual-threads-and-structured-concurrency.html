Virtual Threads & Structured Concurrency

Virtual threads are cheap enough to create one per task, letting you write simple blocking code that scales to huge numbers of concurrent operations, while structured concurrency treats related tasks as a single unit.

§1The Problem Virtual Threads Solve

A platform thread maps one-to-one to an operating system thread and costs roughly a megabyte of stack, so a server can afford thousands, not millions. The old scalable answer was asynchronous code (callbacks, CompletableFuture, reactive streams), which scales well but is harder to write, debug, and read, because stack traces and control flow are fragmented.

A virtual thread (final in Java 21) is a thread managed by the JVM rather than the OS. It costs a few hundred bytes to start and is mounted onto a small pool of carrier threads. When it blocks on I/O, the JVM unmounts it and the carrier runs something else, so blocking is almost free.

Thread.startVirtualThread(() -> System.out.println("hello"));

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<String>> futures = new ArrayList<>();
    for (String url : urls) {
        futures.add(executor.submit(() -> httpGet(url)));      // one virtual thread per task
    }
    for (var f : futures) System.out.println(f.get());
}                                                               // close() waits for all tasks

You write straightforward blocking code, one thread per request, and get the scalability of asynchronous code. The code looks the same as before; only the thread type changed.

§2When They Pay Off, and When They Don't

Virtual threads help when tasks spend most of their time waiting: HTTP calls, database queries, and other I/O. They do not make CPU-bound code faster; with a fixed number of cores, extra threads just compete for them. Some rules follow from how they work:

  • Don't pool them. They are cheap, so create one per task. A pool exists to limit expensive resources; use a Semaphore if you need to limit concurrency against a downstream service.
  • Keep ThreadLocal use light. Millions of threads each with a large thread-local is expensive; prefer passing data explicitly, or scoped values.
  • Avoid pinning. A virtual thread that blocks while inside a synchronized block could be pinned to its carrier on older JDKs, reducing scalability. Recent releases largely removed this limitation, but prefer ReentrantLock for long blocking sections in code that must run on Java 21.
Semaphore limit = new Semaphore(50);                // bound calls to a fragile dependency
executor.submit(() -> {
    limit.acquire();
    try { return callDependency(); } finally { limit.release(); }
});

§3Structured Concurrency

In plain concurrent code, a task started by a method can outlive it, and an error in one subtask doesn't cancel its siblings, leaving orphaned work. Structured concurrency applies the idea behind structured programming: subtasks live inside a scope, the scope doesn't end until they all finish, and failure or cancellation propagates through it. The StructuredTaskScope API expresses this, and cancelling the scope cancels its tasks.

// A preview API in recent releases: requires --enable-preview; check the current status for your JDK
try (var scope = StructuredTaskScope.open()) {
    var user  = scope.fork(() -> fetchUser(id));
    var order = scope.fork(() -> fetchOrders(id));
    scope.join();                                    // wait; if one fails, the other is cancelled
    return new Page(user.get(), order.get());
}                                                    // no subtask can escape this block

The details of this API have changed between preview releases, so treat the exact method names above as illustrative and consult the documentation for your JDK. The ideas are stable: a parent that waits for its children, fail-fast cancellation, and a thread dump that shows the task hierarchy. Scoped values (final in recent releases) are the companion feature, offering immutable per-task context that child tasks inherit more cheaply than ThreadLocal.

Blocking is cheap again With virtual threads the guidance flips: write simple, sequential, blocking code and run it in many threads, rather than contorting it into callbacks to save threads. Keep the asynchronous style for cases where it genuinely models the problem.

§4Common Mistakes

MistakeWhat HappensFix
Pooling virtual threads in a fixed-size executorThrows away their main advantageUse newVirtualThreadPerTaskExecutor()
Using virtual threads for CPU-bound number crunchingNo speedup beyond the core countUse a pool sized to the cores, or parallel streams
Limiting concurrency by limiting threadsHard to reason about, and wrong with virtual threadsUse a Semaphore or rate limiter
Heavy ThreadLocal caching per threadMemory explosion with huge thread countsPass values explicitly, or use scoped values
Assuming a failed subtask cancels the others in plain executorsOrphaned work continuesUse a structured scope with fail-fast behavior
Depending on a preview API in productionSignatures may change between releasesPin the JDK and check the API status
Practice
  1. Launch 10,000 virtual threads that each Thread.sleep(1000) and time it. Then try with a 200-thread fixed pool and compare.
  2. Write a task that makes ten simulated HTTP calls (sleeping 200 ms each) once with a fixed pool and once with a virtual-thread executor.
  3. Use a Semaphore to limit concurrent calls to a fake dependency to 20, with 1,000 virtual threads in flight.
Key takeaways
  • Virtual threads make blocking cheap, so one thread per task scales for I/O-bound work.
  • Don't pool them, don't expect CPU speedups, and limit concurrency with semaphores.
  • Structured concurrency keeps related subtasks inside a scope with shared cancellation, though the API may still be in preview.
