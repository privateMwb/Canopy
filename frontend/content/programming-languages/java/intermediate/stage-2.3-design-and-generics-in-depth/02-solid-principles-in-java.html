SOLID Principles in Java

SOLID is a set of five guidelines for keeping object-oriented code easy to change, and each one is a response to a specific kind of pain that becomes real as a codebase grows.

§1S: Single Responsibility

A class should have one reason to change. If invoicing logic, formatting, and email delivery live in one class, a change to any of them risks breaking the others and every test must set up all three.

// Tangled: three reasons to change
class InvoiceService {
    Invoice build(Order o) { /* pricing rules */ return null; }
    String toHtml(Invoice i) { /* presentation */ return ""; }
    void email(Invoice i) { /* SMTP */ }
}

// Separated
class InvoiceBuilder { Invoice build(Order o) { return null; } }
class InvoiceRenderer { String toHtml(Invoice i) { return ""; } }
class InvoiceMailer { void send(Invoice i) { } }

§2O: Open/Closed

Code should be open for extension, closed for modification: you add new behavior by adding new code, not by editing tested code. A growing if/switch over types is the usual smell.

interface Discount { long apply(long cents); }
record PercentOff(int pct) implements Discount { public long apply(long c) { return c - c * pct / 100; } }
record FlatOff(long off) implements Discount { public long apply(long c) { return Math.max(0, c - off); } }

long total(long cents, List<Discount> discounts) {
    for (Discount d : discounts) cents = d.apply(cents);       // new discounts need no change here
    return cents;
}

(With sealed types and a closed set of cases, a switch can be the better choice; see the earlier lesson. The principle applies where you expect new variants from outside.)

§3L: Liskov Substitution

A subtype must be usable anywhere its supertype is, without breaking the caller's expectations. The textbook violation is a Square that extends Rectangle and breaks setWidth/setHeight assumptions. In practice, watch for subclasses that throw UnsupportedOperationException, tighten preconditions, or weaken guarantees.

class ReadOnlyList<T> extends ArrayList<T> {
    @Override public boolean add(T t) { throw new UnsupportedOperationException(); }   // callers expecting a List break
}

If a subclass can't honor the contract, it probably shouldn't be a subclass; model the relationship differently, with a separate interface or by composition.

§4I: Interface Segregation

Don't force clients to depend on methods they don't use. A fat interface makes implementers write stubs and makes fakes in tests painful.

interface Worker { void work(); void eat(); }            // a Robot must implement eat()?
interface Workable { void work(); }                       // split into small, role-based interfaces
interface Feedable { void eat(); }

§5D: Dependency Inversion

High-level policy should depend on abstractions, not on concrete low-level details, and the concrete pieces are handed in from outside rather than created inside.

class ReportJob {
    private final ReportStore store;                      // abstraction
    ReportJob(ReportStore store) { this.store = store; }  // injected
    void run() { store.save("report"); }
}
interface ReportStore { void save(String data); }
class S3Store implements ReportStore { public void save(String d) { } }
class InMemoryStore implements ReportStore { public void save(String d) { } }   // for tests

This is what dependency injection frameworks automate, but you can do it by hand with constructor parameters.

§6Knowing When Not to Apply Them

SOLID can be overapplied. An interface with a single implementation that will never have another, a class split into ten tiny ones that must be read together, or an "extension point" nobody uses are all costs without benefits. Apply a principle when you feel the pain it addresses (hard-to-test code, ripple-effect changes, brittle subclasses), not in advance. The question is always: what kind of change do I expect, and does this design make it cheap?

Principles, not laws SOLID describes tradeoffs. Duplication is sometimes cheaper than the wrong abstraction. Use the principles to explain why a design hurts, and as a checklist when you review code.

§7Common Mistakes

MistakeWhat HappensFix
A giant Manager or Util classMany unrelated reasons to change; hard to testSplit by responsibility
Growing if (type == ...) chainsEach new case edits tested codeReplace with polymorphism, or a sealed type with exhaustive switch
A subclass throwing UnsupportedOperationExceptionViolates substitutability, so callers crashRework the hierarchy; prefer composition
One huge interface for all clientsStubs and unneeded dependenciesSplit into focused interfaces
Creating dependencies with new inside business logicImpossible to test or swapInject through constructors
An interface for every class "just in case"Indirection with no benefitIntroduce abstractions when a second use appears
Practice
  1. Take a class that reads a CSV, validates it, and writes to a database, and split it by responsibility. Which seams became easy to test?
  2. Replace a switch on a type string with a polymorphic design, then discuss whether a sealed-type switch would have been better.
  3. Find a place where a fake implementation would make a test simpler, and introduce an interface plus constructor injection.
Key takeaways
  • Each SOLID principle answers a concrete pain: tangled responsibilities, edited-in-place code, brittle subclasses, fat interfaces, and hard-wired dependencies.
  • Prefer small, focused types, composition over fragile inheritance, and constructor injection.
  • Apply the principles when the pain appears, and don't create abstraction speculatively.
