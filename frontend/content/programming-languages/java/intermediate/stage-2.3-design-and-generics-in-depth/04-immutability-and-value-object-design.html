Immutability & Value-Object Design

An immutable object can never change after construction, which makes it automatically safe to share between threads and far easier to reason about.

§1What Makes a Class Immutable

The recipe: make the class final (so subclasses can't add mutability), make all fields private final, provide no setters, and copy any mutable object that comes in or goes out. Records give you the first three for free.

public final class Booking {
    private final String guest;
    private final LocalDate checkIn;                  // already immutable
    private final List<String> requests;               // mutable type: must be copied

    public Booking(String guest, LocalDate checkIn, List<String> requests) {
        this.guest = Objects.requireNonNull(guest);
        this.checkIn = Objects.requireNonNull(checkIn);
        this.requests = List.copyOf(requests);           // defensive copy in
    }
    public String guest() { return guest; }
    public LocalDate checkIn() { return checkIn; }
    public List<String> requests() { return requests; }   // already immutable, safe to return

    public Booking withCheckIn(LocalDate d) { return new Booking(guest, d, requests); }   // "wither"
}

Instead of changing an object, you create a modified copy with a method like withCheckIn. Old references still see the old value, so nothing changes underneath them.

§2Why It Matters

Immutable objects are inherently thread-safe: with no mutation, there are no races, and no locks are needed. They are safe as keys in hash maps and elements in sets because their hash code can't change. They can be freely shared and cached without defensive copying at every use. And they make bugs easier to find, since an object's state is whatever the constructor set, with no history of changes to consider. String, Integer, LocalDate, and BigDecimal are all immutable, and the java.time classes replaced the mutable Date and Calendar for exactly this reason.

§3Defensive Copying Pitfalls

final on a field only freezes the reference, not the object it points to. A final List can still be modified, and an array field is always mutable.

final class Bad {
    private final Date created;                       // Date is mutable
    Bad(Date created) { this.created = created; }     // caller keeps a reference and can change it
    Date created() { return created; }                 // and so can anyone who receives it
}
final class Good {
    private final Instant created;                     // immutable type, no copy needed
    Good(Instant created) { this.created = created; }
    Instant created() { return created; }
}
int[] data = {1, 2, 3};
// private final int[] stored = data;                  // shares the caller's array
// private final int[] stored = data.clone();          // copy it, on the way in and out

Copy collections with List.copyOf and Map.copyOf, which also reject nulls. Remember that these copies are shallow: if the elements are themselves mutable, you must copy them too or make them immutable.

§4Value Objects

A value object represents a measurement or description rather than an entity with identity, such as Money, EmailAddress, Temperature, or DateRange. Two value objects with the same content are interchangeable, so equality is by value. Wrapping primitives in value types prevents mix-ups (passing a user ID where an order ID is expected) and gives validation one home.

public record EmailAddress(String value) {
    public EmailAddress {
        if (!value.contains("@")) throw new IllegalArgumentException("invalid email: " + value);
        value = value.toLowerCase();                    // normalize in the compact constructor
    }
}
public record UserId(long value) { }
public record OrderId(long value) { }
void cancel(OrderId id) { }                              // can't accidentally pass a UserId

§5Safe Publication

An immutable object whose fields are all final is safely visible to other threads even if you hand it over through a data race, because final fields get special guarantees from the Java Memory Model (covered in the senior track). Mutable objects need proper synchronization, or a safe handoff like a concurrent collection or a volatile field.

Immutability is the cheapest form of thread safety Before reaching for locks, ask whether the shared data can be made immutable. If it can, the whole category of concurrency bugs disappears for that data.

§6Common Mistakes

MistakeWhat HappensFix
Declaring a field final and assuming the object is immutableA final List or array can still be modifiedCopy mutable inputs and expose immutable views
Returning an internal array or mutable list from a getterCallers silently modify your stateReturn a copy or an immutable collection
Keeping a reference to a mutable constructor argumentThe caller can change your state laterDefensively copy in the constructor
Allowing subclasses of an "immutable" classA subclass can add mutable stateMake the class final, or use a record
Using raw long/String for different kinds of IDsEasy to pass the wrong oneWrap them in small value types
Using java.util.Date in new codeMutable and error-proneUse java.time types
Practice
  1. Convert a mutable Address class with setters into an immutable record with withStreet(...)-style methods.
  2. Write an immutable class holding a List<String>, then try to break it from outside through the constructor argument and the getter.
  3. Create Money(long cents, Currency currency) as a record whose add refuses to mix currencies.
Key takeaways
  • Immutable classes are final, with private final fields, no setters, and defensive copies of mutable data.
  • Immutable objects are automatically thread-safe and safe as map keys.
  • Value objects wrap primitives in meaningful types with validation and value-based equality.
