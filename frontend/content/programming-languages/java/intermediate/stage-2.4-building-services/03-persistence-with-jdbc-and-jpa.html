Persistence with JDBC & JPA

JDBC is the low-level API every Java database library sits on, JPA maps objects to tables for you, and the convenience of JPA comes with traps such as the N+1 query problem that you need to be able to recognize.

§1JDBC Underneath

JDBC lets you send SQL and read rows. Everything else, including JPA, is built on it. Always use a PreparedStatement with parameters, never string concatenation, which prevents SQL injection and lets the database reuse plans.

String sql = "SELECT id, title FROM book WHERE author = ? AND pages > ?";
try (Connection c = dataSource.getConnection();
     PreparedStatement ps = c.prepareStatement(sql)) {
    ps.setString(1, author);
    ps.setInt(2, 100);
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            System.out.println(rs.getLong("id") + " " + rs.getString("title"));
        }
    }
}

Connections are expensive, so applications borrow them from a connection pool (HikariCP is Spring Boot's default) and "closing" a pooled connection returns it to the pool. Always close connections, statements, and result sets, which try-with-resources does for you. Spring's JdbcClient and JdbcTemplate remove most of this boilerplate.

§2JPA Entities and Repositories

JPA (Jakarta Persistence, implemented by Hibernate) maps classes to tables. An entity is a class with an identity, and a repository gives you queries without writing SQL for the common cases.

@Entity
@Table(name = "book")
class Book {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String title;
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "author_id")
    private Author author;
    protected Book() { }                              // JPA requires a no-argument constructor
    Book(String title, Author author) { this.title = title; this.author = author; }
    // getters...
}

interface BookRepository extends JpaRepository<Book, Long> {
    List<Book> findByTitleContainingIgnoreCase(String fragment);       // query derived from the name
    @Query("select b from Book b where b.author.name = :name")
    List<Book> byAuthor(@Param("name") String name);
}

Entities are managed within a transaction: load an entity, change a field, and Hibernate detects the change and issues an UPDATE at commit, with no explicit save needed. Outside a transaction, entities are detached and lazy fields can no longer be loaded (LazyInitializationException).

§3Transactions

A transaction groups statements so they succeed or fail together. In Spring, put @Transactional on service methods that perform one logical unit of work, not on controllers or repositories.

@Service
class TransferService {
    @Transactional
    public void transfer(long from, long to, long cents) {
        Account a = accounts.findById(from).orElseThrow();
        Account b = accounts.findById(to).orElseThrow();
        a.withdraw(cents);
        b.deposit(cents);                              // both updates commit together, or both roll back
    }
}

By default, Spring rolls back on unchecked exceptions, not on checked ones. Keep transactions short: never call a slow remote service while holding one.

§4The N+1 Query Problem

This is the most common JPA performance bug. Loading a list of books issues one query; then touching each book's lazy author issues one more query per book.

List<Book> books = bookRepo.findAll();                // 1 query
for (Book b : books) {
    System.out.println(b.getAuthor().getName());      // N more queries, one per book
}

With 1,000 books that is 1,001 round trips to the database. Fixes: fetch the association in the query with a JOIN FETCH or an entity graph, or select a DTO projection with only the columns you need.

@Query("select b from Book b join fetch b.author")
List<Book> findAllWithAuthors();                       // 1 query

Turn on SQL logging in development (spring.jpa.show-sql=true or Hibernate's statistics) and look at the SQL your code generates. If a page makes dozens of near-identical queries, you have found an N+1. Also remember that FetchType.EAGER doesn't solve it; it just moves the cost somewhere less visible.

The ORM does not remove the database JPA writes the SQL but it is still your SQL: it runs in your transactions, against your indexes, with your query count. Check what it generates, especially for list screens.

§5Common Mistakes

MistakeWhat HappensFix
Building SQL with string concatenationSQL injectionUse PreparedStatement parameters or named parameters
Not closing connectionsThe pool is exhausted and the app hangsUse try-with-resources, or let Spring manage them
Iterating lazy associations in a loopN+1 queriesUse JOIN FETCH, an entity graph, or a projection
Accessing lazy fields after the transaction endsLazyInitializationExceptionFetch what you need inside the transaction, or return a DTO
Holding a transaction across a remote callLong locks and a starved poolKeep transactions short and local
Putting @Transactional on every method by habitHidden costs and unclear boundariesPut it on service methods defining a unit of work
Relying on ddl-auto=update in productionUncontrolled schema driftUse migrations (Flyway or Liquibase)
Practice
  1. Write a JDBC query by hand with a PreparedStatement, then pass a malicious-looking string (' OR '1'='1) and confirm it is treated as data.
  2. Create Author and Book entities, load 100 books, print their authors, and count the SQL statements. Then fix it with JOIN FETCH and count again.
  3. Write a @Transactional method that updates two rows and then throws, and verify that neither update persists.
Key takeaways
  • JDBC with PreparedStatement and a pooled DataSource is the foundation; JPA adds object mapping on top.
  • Put @Transactional on service methods, keep transactions short, and understand managed vs. detached entities.
  • Always inspect the generated SQL, and fix N+1 queries with fetch joins, entity graphs, or projections.
