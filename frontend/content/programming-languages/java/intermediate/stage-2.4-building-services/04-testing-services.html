Testing Services

A good service test suite has many fast unit tests, fewer slice tests that exercise one layer with the framework, and a small number of full integration tests against real infrastructure.

§1The Testing Pyramid

Unit tests exercise a class in isolation with plain Java and no Spring, running in milliseconds. Slice tests start only the part of the application a layer needs. Integration tests start the whole application against a real database. Write mostly the first kind, some of the second, and few of the third, because the higher layers are slower and give less precise failures.

§2Unit Tests with Mockito

Because you use constructor injection, you can build the class under test with new and pass test doubles. Mockito creates mocks that return canned answers and record calls.

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock OrderRepository repo;
    @Mock PaymentGateway payments;
    @InjectMocks OrderService service;

    @Test
    void placesOrderWhenPaymentSucceeds() {
        when(payments.charge(any(), eq(2500))).thenReturn(PaymentResult.ok("tx-1"));
        when(repo.save(any(Order.class))).thenAnswer(inv -> inv.getArgument(0));

        Order order = service.place(new NewOrder("ada", 2500));

        assertEquals("tx-1", order.paymentRef());
        verify(repo).save(order);
    }

    @Test
    void doesNotSaveWhenPaymentFails() {
        when(payments.charge(any(), anyLong())).thenReturn(PaymentResult.declined());
        assertThrows(PaymentDeclinedException.class, () -> service.place(new NewOrder("ada", 2500)));
        verifyNoInteractions(repo);
    }
}

Mock the boundaries (repositories, remote clients, clocks), not every collaborator. If a test mocks everything and verifies call order, it only restates the implementation and breaks on every refactor. Prefer asserting on outcomes (return values, state) over verifying interactions, and consider simple hand-written fakes for things like an in-memory repository.

§3Slice Tests

Spring Boot offers annotations that load only one layer.

@WebMvcTest(BookController.class)                 // web layer only: controllers, JSON, validation, advice
class BookControllerTest {
    @Autowired MockMvc mvc;
    @MockitoBean BookService service;              // replaces the bean in the context

    @Test
    void returns404ForMissingBook() throws Exception {
        when(service.get(7)).thenThrow(new BookNotFoundException(7));
        mvc.perform(get("/api/books/7"))
           .andExpect(status().isNotFound());
    }

    @Test
    void rejectsInvalidBody() throws Exception {
        mvc.perform(post("/api/books").contentType("application/json").content("{\"title\":\"\"}"))
           .andExpect(status().isBadRequest());
    }
}

@DataJpaTest                                       // JPA layer only: entities, repositories, queries
class BookRepositoryTest {
    @Autowired BookRepository repo;
    @Test void findsByTitleFragment() { /* save some rows, query, assert */ }
}

Web slice tests check routing, serialization, validation, and error mapping without a server. Data slice tests check that your queries really work.

§4Integration Tests with Testcontainers

An in-memory database such as H2 behaves differently from the production one (dialect, types, locking, JSON, constraints), so tests can pass while production fails. Testcontainers starts a real database in a Docker container for the test.

@SpringBootTest
@Testcontainers
class OrderFlowIT {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16");

    @Autowired OrderService service;

    @Test
    void persistsOrderEndToEnd() { /* run real code against real Postgres */ }
}

@ServiceConnection wires the container's URL and credentials into the application automatically in recent Spring Boot versions. These tests are slower and need Docker, so run them in CI, and keep each one meaningful, such as one per key user flow.

§5Keeping Tests Healthy

Tests should be independent, deterministic, and fast. Inject a Clock instead of calling Instant.now(), avoid Thread.sleep, and give each test its own data. Name tests for behavior. A flaky test that sometimes fails is worse than none, because it teaches the team to ignore red.

Test behavior at the right level Use a unit test for logic, a slice test for framework behavior (routing, JSON, queries), and an integration test for wiring and real infrastructure. Pushing everything to the highest level is slow; mocking everything at the lowest level proves little.

§6Common Mistakes

MistakeWhat HappensFix
Using @SpringBootTest for every testA slow suite that starts the full context repeatedlyUse unit tests and slice tests where they are enough
Mocking every collaborator and verifying call orderTests break on every refactor and prove littleMock only boundaries, and assert on outcomes
Testing against H2 when production runs PostgresDialect and behavior differences hide bugsUse Testcontainers with the real database
Tests sharing data or relying on orderFlaky, order-dependent failuresIsolate state per test
Calling Instant.now() or sleeping in testsNon-deterministic and slowInject a Clock, and poll with a timeout
Using the deprecated @MockBeanWarnings, and removal in newer versionsUse @MockitoBean
Practice
  1. Unit test a service with Mockito for a success path and a failure path, verifying no save happens on failure.
  2. Write a @WebMvcTest that checks a 404 for a missing resource and a 400 for invalid input.
  3. Write a repository test with Testcontainers that proves a custom query behaves correctly with real Postgres.
Key takeaways
  • Many fast unit tests, some slice tests (@WebMvcTest, @DataJpaTest), and a few integration tests with real infrastructure.
  • Mock boundaries, prefer asserting outcomes, and use Testcontainers instead of a different in-memory database.
  • Make tests deterministic by injecting clocks and isolating state, and treat flaky tests as bugs.
