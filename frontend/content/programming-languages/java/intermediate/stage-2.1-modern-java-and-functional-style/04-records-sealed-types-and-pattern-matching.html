Records, Sealed Types & Pattern Matching

Records model data, sealed types model a closed set of alternatives, and pattern matching in switch lets the compiler check that you handled every alternative.

§1Records as Data

A record is a transparent, immutable carrier of data, with a constructor, accessors, equals, hashCode, and toString generated for you. Records can have a compact constructor for validation, extra methods, and static factories, and they can implement interfaces.

record Point(double x, double y) {
    Point { if (Double.isNaN(x) || Double.isNaN(y)) throw new IllegalArgumentException(); }
    double dist(Point o) { return Math.hypot(x - o.x, y - o.y); }
    static Point origin() { return new Point(0, 0); }
}

§2Sealed Types

A sealed class or interface lists exactly which types may extend it. That turns an open-ended hierarchy into a closed set, the same idea as an algebraic data type in other languages. Permitted subtypes must be final, sealed, or non-sealed; records are implicitly final, which makes them a natural fit.

sealed interface Shape permits Circle, Rectangle, Triangle { }
record Circle(double radius) implements Shape { }
record Rectangle(double w, double h) implements Shape { }
record Triangle(double base, double height) implements Shape { }

If the permitted classes are in the same file, the permits clause can be omitted. Nobody outside can add a fourth shape without editing the sealed declaration, so the compiler always knows the full list.

§3Pattern Matching

instanceof patterns test and cast in one step, and switch can match on type, with the compiler checking exhaustiveness for sealed types, so no default is needed.

static double area(Shape s) {
    return switch (s) {
        case Circle c -> Math.PI * c.radius() * c.radius();
        case Rectangle r -> r.w() * r.h();
        case Triangle t -> 0.5 * t.base() * t.height();
    };                                   // no default: adding a new Shape makes this a compile error
}

if (obj instanceof String str && str.length() > 3) {         // pattern variable scoped to the && branch
    System.out.println(str.toUpperCase());
}

Record patterns deconstruct a record directly, even when nested, and when adds a guard.

sealed interface Expr permits Num, Add, Mul { }
record Num(int v) implements Expr { }
record Add(Expr l, Expr r) implements Expr { }
record Mul(Expr l, Expr r) implements Expr { }

static int eval(Expr e) {
    return switch (e) {
        case Num(int v) -> v;
        case Add(Expr l, Expr r) -> eval(l) + eval(r);
        case Mul(Expr l, Expr r) -> eval(l) * eval(r);
    };
}

static String classify(Object o) {
    return switch (o) {
        case null -> "null";
        case Integer i when i > 100 -> "big int";
        case Integer i -> "int";
        case String s -> "string of " + s.length();
        default -> "other";
    };
}

Order matters when patterns overlap: the compiler rejects a case that an earlier case already dominates.

§4The Payoff

Adding an operation (like eval) means writing one new switch, with no changes to the data types. Adding a new variant breaks every switch that lacks a case, and the compiler lists them for you. Compare that with a class hierarchy using virtual methods, where adding a variant is easy and adding an operation touches every class. Choose based on which kind of change you expect.

Make illegal states unrepresentable Instead of a class with an int type field and nullable fields for each case, use a sealed interface with one record per case. Each variant carries exactly the data it needs, and a missing case is a compile error rather than a runtime surprise.

§5Common Mistakes

MistakeWhat HappensFix
Adding a default branch to a switch over a sealed typeIt hides the compiler's exhaustiveness check for new variantsOmit default so new subtypes cause a compile error
Putting a general case before a specific onethis case label is dominated by a preceding case labelOrder specific patterns before general ones
Using a record for an entity with identity and changing stateImmutable semantics don't fitUse a normal class
Sealing a hierarchy that other modules must extendThey can't add subtypesLeave it open, or use non-sealed deliberately
Forgetting a null case in a pattern switchA NullPointerException at runtimeAdd case null or check beforehand
Practice
  1. Model a PaymentResult as a sealed interface with Success(String id), Declined(String reason), and Error(Exception cause), and write a method that turns each into a message.
  2. Extend the Expr example with a Neg variant and observe which methods stop compiling.
  3. Add a guard (when) to a pattern switch to treat negative numbers differently.
Key takeaways
  • Records carry immutable data, and sealed types fix the set of allowed subtypes.
  • Pattern matching in switch deconstructs values and is checked for exhaustiveness without a default.
  • Together they let you model alternatives so that a forgotten case is a compile error.
