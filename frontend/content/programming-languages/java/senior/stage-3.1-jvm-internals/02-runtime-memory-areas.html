Runtime Memory Areas

A running JVM uses several distinct kinds of memory, and the "heap" you size with -Xmx is only one of them, which is why a process can be killed for exceeding its memory limit while the heap looks fine.

§1The Map

Memory in a JVM process falls into regions with different owners and failure modes.

AreaHoldsSized byFailure
HeapAll objects and arrays-Xms, -XmxOutOfMemoryError: Java heap space
Thread stacksFrames for each thread: locals, call chain-Xss per threadStackOverflowError, or no more threads
MetaspaceClass metadata (native memory)-XX:MaxMetaspaceSize (unlimited by default)OutOfMemoryError: Metaspace
Code cacheJIT-compiled native code-XX:ReservedCodeCacheSizeThe JIT stops compiling and performance collapses
Direct / nativeByteBuffer.allocateDirect, native libraries, GC structures-XX:MaxDirectMemorySizeOutOfMemoryError: Direct buffer memory, or the OS kills the process

The heap is managed by the garbage collector. Everything else is either managed by the JVM in native memory or by native code, and it counts against the container or machine limit even though -Xmx doesn't mention it.

§2What Goes Where

Every object you create with new lives on the heap, and so does every array, even one stored in a local variable. The local variable holds the reference; a primitive local holds its value directly in the stack frame. Static fields live with the class metadata, and the objects they point to live on the heap. Each thread has its own stack, which holds one frame per active method call.

void process() {
    int count = 5;                       // primitive: in this frame on the thread stack
    String name = "x";                   // reference in the frame; the String object is on the heap
    List<Integer> list = new ArrayList<>();   // reference in the frame; the list and its array are on the heap
    recurse(0);
}
void recurse(int n) { recurse(n + 1); }  // each call adds a frame: eventually StackOverflowError

The escape analysis optimization can sometimes avoid heap allocation entirely: if the JIT proves an object never escapes a method, it may scalar-replace it into locals, so "all objects are on the heap" is a semantic rule rather than a physical guarantee. Each thread's stack is reserved memory (about 1 MB by default on 64-bit platforms), so thousands of platform threads are expensive in native memory.

§3Inside the Heap

Most collectors divide the heap into a young generation (new objects, where most die quickly) and an old generation (long-lived survivors), because of the generational hypothesis: most objects have short lives. That allows frequent, cheap collections of the young area without scanning everything. Objects that survive several young collections are promoted to the old generation. Large arrays may be allocated directly into old space (or in special "humongous" regions in G1). An object also has overhead: a header (around 12 to 16 bytes) plus alignment padding, and an Integer costs about 16 bytes versus 4 for an int, so a List<Integer> of a million items uses far more memory than the raw numbers suggest.

§4Seeing Where the Memory Went

You can't tune what you don't measure. Useful tools:

jcmd <pid> GC.heap_info                       # current heap usage by region
jcmd <pid> VM.native_memory summary           # needs -XX:NativeMemoryTracking=summary
jcmd <pid> GC.class_histogram | head -20      # which classes hold the most instances
jcmd <pid> Thread.print                       # all thread stacks
jmap -histo:live <pid>                        # similar histogram (forces a full GC)

With Native Memory Tracking on, a process using 2 GB resident memory with a 1 GB heap will show where the other gigabyte went: metaspace, thread stacks, code cache, GC bookkeeping, or direct buffers. This accounting is essential when running in a container, where the total footprint, not the heap, determines whether you get killed.

-Xmx is not the process size A JVM with -Xmx2g can easily use 3 GB or more of resident memory. Budget the heap plus metaspace, stacks, code cache, direct buffers, and GC overhead when you choose a memory limit.

§5Common Mistakes

MistakeWhat HappensFix
Setting the container limit equal to -XmxThe OS kills the process (OOMKilled) from non-heap memoryLeave headroom, or size the heap as a fraction of the limit
Treating StackOverflowError as a heap problemRaising -Xmx does nothingFix the recursion, or raise -Xss only if the depth is legitimate
Creating thousands of platform threadsNative memory exhausted by stacksUse a pool or virtual threads
Using List<Integer> for millions of numbersSeveral times the memory of a primitive arrayUse int[] or a specialized collection
Ignoring direct buffersOff-heap leaks that heap dumps never showTrack with NMT and MaxDirectMemorySize
Unbounded caches and static mapsSlow heap growth until OutOfMemoryErrorBound caches and give entries an eviction policy
Practice
  1. Write a program that recurses infinitely, catch the StackOverflowError, and report the depth reached. Change -Xss and compare.
  2. Run a program with -XX:NativeMemoryTracking=summary and use jcmd to list the memory categories, noting which is largest after the heap.
  3. Estimate by hand the heap used by a million Integers in an ArrayList, then measure it with a class histogram.
Key takeaways
  • JVM memory has several regions (heap, thread stacks, metaspace, code cache, direct and native memory), each with its own limit and failure mode.
  • Objects and arrays live on the heap, with locals and frames on thread stacks, and escape analysis can avoid some allocations.
  • Use jcmd and Native Memory Tracking to account for the whole process, since containers limit total memory, not just the heap.
