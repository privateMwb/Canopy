Class Loading & Bytecode

The JVM loads classes lazily, on demand, through a hierarchy of classloaders, and understanding that lifecycle and the bytecode it loads explains a whole family of baffling production errors.

§1The Lifecycle of a Class

A class is not loaded when your program starts; it is loaded the first time it is needed. The JVM then takes it through three phases.

  • Loading: a classloader finds the bytes (usually a .class file in a jar or directory) and creates a Class object.
  • Linking: verification checks the bytecode is structurally safe (the reason the JVM can run untrusted bytecode without crashing), preparation allocates static fields with default values, and resolution turns symbolic references into direct ones (often lazily).
  • Initialization: the static initializer (static { } and static field initializers) runs, exactly once, thread-safely, the first time the class is actively used.
class Config {
    static final Map<String, String> VALUES = load();       // runs once at initialization
    static { System.out.println("Config initialized"); }
}
// Merely declaring "Config c;" does not initialize it; calling Config.VALUES or new Config() does.

A failure in a static initializer throws ExceptionInInitializerError the first time, and then NoClassDefFoundError on every later use of that class, which confuses people because the real cause appears only once, early in the logs.

§2Classloader Hierarchy and Delegation

Classes are loaded by a classloader, and each loader is identified with a parent. The standard ones are the bootstrap loader (core java.base classes), the platform loader (other JDK modules), and the application (system) loader (your classpath). Loading follows parent delegation: a loader first asks its parent, and only tries itself if the parent can't find the class. This guarantees that java.lang.String is always the JDK's version and not something on your classpath.

System.out.println(String.class.getClassLoader());           // null: bootstrap
System.out.println(Main.class.getClassLoader());              // the application classloader
Thread.currentThread().getContextClassLoader();               // used by frameworks to find app classes

A class's identity is its name plus its defining classloader. Two loaders can each load a class named com.acme.Plugin and get two distinct, incompatible types. That is the root of the confusing error ClassCastException: com.acme.Plugin cannot be cast to com.acme.Plugin, which appears in application servers, plugin systems, and hot-reload tools that use separate loaders per component.

§3Reading Bytecode with javap

Source compiles to bytecode for a stack machine. javap shows you what was actually generated, which settles questions about what the compiler does.

javap -c -p com.example.Counter        # -c: disassemble, -p: include private members
javap -v com.example.Counter           # verbose: constant pool, flags, class file version
int add(int a, int b) { return a + b; }
// javap -c shows roughly:
//   iload_1        push a
//   iload_2        push b
//   iadd           pop two, push the sum
//   ireturn        return the top of the stack

Useful things you can discover: string concatenation compiles to an invokedynamic call (so its implementation can improve without recompiling your code), lambdas also use invokedynamic, and switch on strings compiles to a hash lookup. The class file header records a major version (for example 65 for Java 21), and a JVM refuses a class compiled for a newer version with UnsupportedClassVersionError.

§4Where It Bites in Production

The common failures all come back to the classpath and loaders. ClassNotFoundException (loading by name failed at runtime, such as Class.forName) differs from NoClassDefFoundError (the class was present at compile time but is missing or failed to initialize at runtime). NoSuchMethodError or AbstractMethodError mean you compiled against one version of a library and ran against another, a classpath conflict where two versions of the same dependency are present and one wins. Tools such as mvn dependency:tree, -verbose:class, and -Xlog:class+load show what was loaded and from where. Resource leaks arise when a loader (and therefore all its classes and statics) can't be garbage collected because something still references it, a classic cause of metaspace leaks after repeated redeploys.

Same name does not mean same class The JVM identifies a class by name and loader together. When you see two apparently identical types that won't cast to each other, suspect two classloaders and look at who loaded each.

§5Common Mistakes

MistakeWhat HappensFix
Treating NoClassDefFoundError like "jar missing"Misses that a static initializer failed earlierSearch the logs for the first ExceptionInInitializerError
Two versions of one library on the classpathNoSuchMethodError and random behaviorInspect the dependency tree and force a single version
Assuming a class loads at startupFailures appear late, in a rarely used pathTest those paths, or load critical classes eagerly
Heavy work in static initializersSlow startup and cascading failuresKeep initializers trivial and defer work
Hot-redeploying without releasing the old loaderMetaspace grows until OutOfMemoryError: MetaspaceRemove references (threads, caches, ThreadLocals) to old classes
Compiling with a newer JDK than you runUnsupportedClassVersionErrorCompile with --release set to the runtime version
Practice
  1. Compile a small class with javac, run javap -c -p on it, and annotate what each instruction does.
  2. Write a class whose static initializer throws, touch it twice, and compare the two exceptions you get.
  3. Run an application with -Xlog:class+load and find which jar a particular class was loaded from.
Key takeaways
  • Classes load lazily and pass through loading, linking (verify, prepare, resolve), and initialization.
  • Delegation makes core classes consistent; a class's identity is name plus loader.
  • javap shows the real bytecode, and most class-related production errors trace back to classpath conflicts or loader leaks.
