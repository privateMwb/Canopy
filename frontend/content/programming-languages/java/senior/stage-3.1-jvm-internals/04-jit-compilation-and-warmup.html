JIT Compilation & Warmup

The JVM starts by interpreting bytecode and gradually compiles the hot parts to optimized machine code while the program runs, which is why Java code gets faster after it starts and why the first minute looks different from the tenth.

§1Interpret, Then Compile

When a method first runs, the JVM interprets its bytecode, which starts instantly but is slow. The JVM counts invocations and loop iterations, and when a method gets hot it hands it to a JIT (just-in-time) compiler. HotSpot uses tiered compilation: the C1 compiler quickly produces moderately optimized code (with profiling), and the C2 compiler later produces highly optimized code for the hottest methods using the profile data collected along the way. The compiled code is stored in the code cache.

The advantage over compiling ahead of time is that the JIT sees actual behavior in this run: which branches are taken, which concrete classes appear at a call site, and which values occur. It can bet on that behavior and generate code tuned for it.

§2What the Optimizer Does

The most important optimizations:

  • Inlining: replace a method call with the method body. This removes call overhead and, more importantly, exposes more code for further optimization. Small methods and final/monomorphic calls inline best.
  • Devirtualization: if profiling shows a call site only ever sees one (or two) concrete types, the JIT replaces the virtual dispatch with a direct call guarded by a type check.
  • Escape analysis: if an object never leaves a method, allocate its fields in registers and skip the heap allocation entirely.
  • Loop optimizations: unrolling, hoisting invariants, removing bounds checks, and vectorizing simple loops.
  • Lock elision and coarsening: removing locks on objects proven to be thread-local.
// After inlining and escape analysis, this may allocate nothing at all:
double dist(double x, double y) {
    Point p = new Point(x, y);          // never escapes: fields may live in registers
    return Math.sqrt(p.x() * p.x() + p.y() * p.y());
}

This is why writing small, clear methods is not a performance sin in Java, and why micro-level "optimizations" such as manually inlining code are usually pointless.

§3Deoptimization

Those bets can be wrong. If compiled code assumed a call site only saw Circle and a Square then appears, the JVM deoptimizes: it throws away the compiled code, falls back to the interpreter, collects new profile data, and recompiles. This is correct but costs time, so a service whose behavior changes (a new request type arriving, a cold path suddenly becoming hot) can show latency spikes after steady running.

§4Warmup and Its Consequences

Because compilation takes time and CPU, a freshly started JVM is slow: it is interpreting, then running C1 code, before it reaches peak performance with C2. This has practical effects:

  • The first requests after a deploy are slower, and a fleet restarted all at once can fall over under load it handled easily when warm.
  • Short-lived processes (command-line tools, serverless functions) may never reach peak speed.
  • Benchmarks that don't account for warmup measure the interpreter. (The JMH lesson covers how to do this correctly.)

Mitigations: send warm-up traffic or ramp load gradually behind a load balancer; avoid restarting everything at the same time; use CPU headroom during startup; and for fast-start needs consider ahead-of-time options, such as class-data sharing and the AOT cache that recent JDK releases (24 and later) provide, CRaC-style checkpoint and restore on supporting runtimes, or GraalVM Native Image, which trades peak throughput and dynamic features for instant startup and small memory.

java -XX:+PrintCompilation -jar app.jar | head           # watch methods compile (and "made not entrant")
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining ...    # see inlining decisions
java -XX:TieredStopAtLevel=1 -jar tool.jar               # C1 only: faster startup for short-lived tools
Peak performance is earned A JVM that has run for a while is not the same program as one that just started. Measure steady-state and startup separately, and plan deployments around the difference.

Practice
  1. Time a method 10 times in a row in one JVM and graph how the time per call changes. Explain each phase.
  2. Run a small program with -XX:+PrintCompilation and find a method compiled at multiple tiers.
  3. Write a loop calling an interface method with one implementation, then introduce a second and a third, and measure the effect on throughput.
Key takeaways
  • HotSpot interprets first, then compiles hot code with C1 and C2 using runtime profiles.
  • Inlining, devirtualization, and escape analysis let simple, small-method code run fast; wrong assumptions cause deoptimization.
  • Warmup is real: plan for slow starts, gradual rollouts, and measure steady state separately.
