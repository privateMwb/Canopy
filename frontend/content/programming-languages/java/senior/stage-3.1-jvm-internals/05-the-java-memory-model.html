The Java Memory Model

The Java Memory Model defines when one thread's writes are guaranteed to be visible to another, and code that ignores it can appear correct for years and then break on a different CPU or JVM.

§1Why Threads Disagree

Modern hardware and compilers reorder operations and keep values in per-core caches and registers. A single thread never notices, because the result looks as if it ran in order (as-if-serial), but another thread observing the same variables can see writes in a different order or not at all.

class Flag {
    boolean ready = false;
    int value = 0;

    void writer() { value = 42; ready = true; }        // thread A
    void reader() {                                     // thread B
        while (!ready) { }                              // may spin forever: no guarantee ready is ever seen
        System.out.println(value);                      // may even print 0 if the writes are reordered
    }
}

Both outcomes are legal under the model, because nothing establishes an ordering between the threads.

§2Happens-Before

The JMM's central concept is the happens-before relation. If action A happens-before action B, then A's effects are guaranteed visible to B (and ordered before it). Without a happens-before edge between a write and a read of the same variable, you have a data race and the result is undefined in practice. The edges that Java guarantees:

  • Program order: within one thread, each action happens-before later actions in that thread.
  • Monitor lock: unlocking a monitor (leaving synchronized) happens-before every later lock of the same monitor.
  • volatile: a write to a volatile field happens-before every later read of that same field.
  • Thread start and join: Thread.start() happens-before everything in the started thread; everything in a thread happens-before another thread's successful join() on it.
  • Executors and concurrent collections: submitting a task happens-before it runs; putting an element into a concurrent queue or map happens-before another thread retrieves it; Future.get() sees the task's writes.
  • final fields: after a constructor finishes, other threads see the correct values of final fields, if the object didn't leak during construction.
  • Transitivity: if A happens-before B and B happens-before C, then A happens-before C.

That transitivity is what makes the fix to the broken example work: make ready volatile, and the write to value (before the volatile write) is visible to any thread that sees ready == true.

volatile boolean ready = false;
void writer() { value = 42; ready = true; }            // volatile write publishes the earlier write too
void reader() { while (!ready) { } System.out.println(value); }   // guaranteed to print 42

§3Safe Publication

Making an object reachable by another thread is publishing it, and it's only safe if there is a happens-before edge between the construction and the reading thread. Safe ways: store it in a volatile field or AtomicReference, hand it over through a concurrent collection or queue, guard both sides with the same lock, initialize it in a static initializer, or make all its fields final. Publishing through a plain field is unsafe: another thread may see the reference but stale or default field values.

class Holder {
    private static Helper helper;                       // BROKEN double-checked locking
    static Helper get() {
        if (helper == null) {
            synchronized (Holder.class) { if (helper == null) helper = new Helper(); }
        }
        return helper;                                   // a thread may see a half-constructed Helper
    }
}
// Fix: declare the field volatile, or use the initialization-on-demand holder idiom:
class Holder2 {
    private static class Lazy { static final Helper INSTANCE = new Helper(); }
    static Helper get() { return Lazy.INSTANCE; }       // class initialization is thread-safe
}

§4Why "It Works On My Machine" Isn't Evidence

Races are timing-dependent. x86 processors are relatively strict, so some racy code appears to work there and then fails on ARM, or only after the JIT compiles a hot loop and hoists a read out of it (making the while (!ready) loop truly infinite). Testing can't prove the absence of a race; only reasoning about happens-before can. Also, non-volatile long and double writes are not guaranteed atomic by the specification in theory (a "torn" write), though modern 64-bit JVMs do in practice. Compound actions such as count++ are never atomic, with or without volatile.

The practical rules are short. Prefer immutability and thread confinement. Use the java.util.concurrent building blocks, which come with documented happens-before guarantees. When you must share mutable state, guard every access with the same lock or use volatile or atomics with a clear reason. And if you find yourself reasoning about reorderings, step back and use a higher-level construct.

Synchronize both sides A lock or a volatile only helps if the reader participates too. Protecting the write but not the read, or using different locks for each, creates no happens-before edge at all.

§5Common Mistakes

Practice
  1. Write the broken ready/value example, run the reader in a loop long enough for the JIT to compile it, and try to observe a hang. Then fix it with volatile.
  2. Explain, using the happens-before rules, why ExecutorService.submit followed by Future.get() safely transfers a task's results.
  3. Replace a double-checked locking singleton with the holder idiom, and explain why it is safe without explicit synchronization.
Key takeaways
  • Without a happens-before edge between a write and a read, another thread may see stale, partial, or reordered state.
  • Locks, volatile, thread start/join, concurrent collections, executors, and final fields create happens-before edges.
  • Publish objects safely, prefer immutability, and don't treat "it works in testing" as proof of correctness.
