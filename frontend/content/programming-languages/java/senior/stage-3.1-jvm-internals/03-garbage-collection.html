Garbage Collection

A garbage collector reclaims memory from unreachable objects automatically, and the different collectors trade throughput, pause time, and memory footprint against one another, so the right one depends on what your service values.

§1Reachability

An object is garbage if it can no longer be reached from a GC root: a local variable on a live thread, a static field, a JNI reference, or a few others. The collector traces from the roots through references and treats everything it didn't visit as free. This means cycles are not a problem (unlike with reference counting) and that a memory leak in Java isn't "forgetting to free" but holding a reference you no longer need, such as an entry in a static map or a listener that was never removed.

§2The Generational Approach and Pauses

Since most objects die young, collectors split the heap and collect the young generation often and cheaply (a minor or young collection), and the old generation less often. During some phases the collector must stop all application threads, a stop-the-world pause, because the object graph can't safely change while it's being examined. Collector design is largely about how to shrink and bound these pauses by doing more work concurrently alongside the application, at the cost of extra CPU and memory.

§3The Collectors

CollectorFlagOptimizes forNotes
Serial-XX:+UseSerialGCTiny footprintSingle-threaded; small heaps and tiny containers
Parallel-XX:+UseParallelGCThroughputMulti-threaded stop-the-world; batch jobs
G1-XX:+UseG1GCBalance with a pause-time goalThe default on server-class machines since Java 9
ZGC-XX:+UseZGCVery low pauses at large heapsConcurrent; pauses stay very short regardless of heap size
Shenandoah-XX:+UseShenandoahGCLow pausesConcurrent compaction; available in many OpenJDK builds

G1 divides the heap into equal-sized regions, collects the young regions with short pauses, runs concurrent marking for the old generation, and then reclaims the most garbage-filled regions in mixed collections. You give it a soft target with -XX:MaxGCPauseMillis (default 200 ms). It is a good general default. ZGC does nearly all its work, including moving objects, concurrently, so pauses are typically a millisecond or less and don't grow with heap size; it is generational by default in recent releases, which lowers its CPU and memory overhead. The price of low-pause collectors is some throughput and extra memory headroom. Shenandoah has a similar goal and approach. Parallel has the highest raw throughput when pauses don't matter, such as an overnight batch.

Note that allocation rate matters as much as heap size: a service allocating gigabytes per second will collect constantly no matter which collector is chosen, so reducing garbage (avoiding needless boxing, string churn, and temporary objects) is often the best "tuning".

§4Reading GC Behavior

Turn on unified logging and read it, rather than guessing.

java -Xlog:gc*:file=gc.log:time,uptime,level,tags -Xmx4g -jar app.jar
[12.3s][info][gc] GC(41) Pause Young (Normal) (G1 Evacuation Pause) 2048M->412M(4096M) 14.2ms
[58.1s][info][gc] GC(97) Pause Full (G1 Compaction Pause) 3980M->3901M(4096M) 2841.7ms

Things to look for: the pause durations against your latency goals; the heap after collection staying flat over time (a rising floor suggests a leak or too small a heap); the frequency of collections; and any Full GC events, which in G1 indicate it couldn't keep up (an allocation failure, humongous allocations, or an undersized heap). Tools like GCViewer, GCeasy, or JFR's GC events help visualize this.

§5Choosing and Tuning

Start with the default (G1 in most cases) and set only the heap size. Move to ZGC or Shenandoah when pause times are a measured problem and you have the memory headroom, and to Parallel for throughput-oriented batch work. Change one flag at a time and measure against a realistic load, because most GC tuning flags are best left alone and the wrong ones make things worse.

A Java memory leak is a reference you forgot The GC can't free what is still reachable. If the post-collection heap keeps rising, find what is holding the references, rather than adding heap.

§6Common Mistakes

Practice
  1. Run the same allocation-heavy program under Serial, Parallel, G1, and ZGC with GC logging enabled, and compare pause times and total runtime.
  2. Create a deliberate leak (an ever-growing static List), and watch the post-GC heap floor rise in the log.
  3. Lower -Xmx until G1 reports Full GCs, and describe what the log says right before them.
Key takeaways
  • Objects are collected when unreachable from GC roots, so a Java leak means holding unneeded references.
  • G1 is the balanced default, ZGC and Shenandoah minimize pauses, Parallel maximizes throughput, and Serial minimizes footprint.
  • Read GC logs for pause time, the post-collection heap trend, and Full GCs, and tune only against measurements.
