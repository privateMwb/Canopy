Resilience: Timeouts, Retries & Circuit Breakers

In a system of services, something is always slow or broken, and resilience is the set of techniques that stops one failing dependency from taking everything else down with it.

§1Failure Is the Normal Case

A call to another service can fail quickly, fail slowly, or never return. Slow failures are the dangerous ones: while a caller waits, it holds a thread, a connection, and memory, so a single slow dependency can exhaust a caller's resources and spread the failure upstream (a cascading failure). The design question is never "what if the dependency fails?" but "what do we do when it does, and how do we limit the damage?"

§2Timeouts: The First Line of Defense

Every remote call needs a timeout. Many clients default to no timeout or an enormous one, which means a stuck call can hold a thread forever. Set both a connect timeout (short, such as a second) and a read/response timeout based on what the dependency normally needs, plus a margin.

HttpClient client = HttpClient.newBuilder()
    .connectTimeout(Duration.ofSeconds(1))
    .build();
HttpRequest req = HttpRequest.newBuilder(URI.create(url))
    .timeout(Duration.ofSeconds(2))                    // total time for this request
    .build();
// JDBC: setQueryTimeout; pool: connectionTimeout; futures: orTimeout(...)

Think in terms of a deadline budget: if the user-facing request must finish in 3 seconds, the sum of the timeouts and retries of everything beneath it must fit, or you will keep working on a result nobody is waiting for. Propagate the remaining deadline downstream where you can.

§3Retries, Carefully

Retrying fixes transient faults (a dropped connection, a brief overload), but a naive retry loop can turn a small problem into an outage. Rules:

  • Retry only idempotent operations, or ones protected by an idempotency key. Retrying a non-idempotent payment can charge twice.
  • Retry only errors that may be transient (timeouts, 503, connection reset), not errors that will fail again (400, 404, validation).
  • Use exponential backoff with jitter: wait longer after each failure, and add randomness so thousands of clients don't retry in lockstep.
  • Cap the attempts, usually two or three, and respect the deadline.
  • Beware of retry amplification: if three layers each retry three times, one failed call becomes 27 against the struggling service. Retry at one layer, usually the outermost that can.
long delay = 100;
for (int attempt = 1; ; attempt++) {
    try { return call(); }
    catch (TransientException e) {
        if (attempt == 3) throw e;
        Thread.sleep(delay + ThreadLocalRandom.current().nextLong(delay));   // jitter
        delay *= 2;                                                           // exponential backoff
    }
}

§4Circuit Breakers

A circuit breaker wraps calls to a dependency and tracks failures. When the failure rate crosses a threshold, it opens: calls fail immediately without touching the dependency, giving it room to recover and freeing your threads. After a wait it goes half-open, lets a few trial calls through, and closes again if they succeed.

CircuitBreaker breaker = CircuitBreaker.of("inventory", CircuitBreakerConfig.custom()
    .failureRateThreshold(50)                          // open at 50% failures
    .slidingWindowSize(20)
    .waitDurationInOpenState(Duration.ofSeconds(30))
    .build());
Supplier<Stock> guarded = CircuitBreaker.decorateSupplier(breaker, () -> inventory.stock(id));
// the above uses Resilience4j; Spring Cloud Circuit Breaker and others wrap similar ideas

Pair the breaker with a fallback: a cached value, a default, a degraded feature ("recommendations unavailable"), or a clear error. Decide for each dependency what degraded behavior is acceptable.

§5Bulkheads and Backpressure

A bulkhead isolates resources so one dependency can't consume them all: separate thread pools, connection pools, or semaphores per downstream, so a slow inventory service can't starve the calls to payments. Backpressure is the system's way to say "slow down": bounded queues, rejecting work with 429/503 when overloaded (load shedding), and limiting concurrency. An unbounded queue is not resilience; it only hides overload until memory runs out, while latency grows without limit. It is usually better to reject some requests quickly than to accept all of them and serve every one badly.

ExecutorService pool = new ThreadPoolExecutor(
    10, 10, 0, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(50),                      // bounded
    new ThreadPoolExecutor.AbortPolicy());             // reject when full: caller gets an exception, can shed load

§6Test the Failure Paths

Resilience code that has never run is a guess. Verify behavior by injecting latency and errors (a proxy such as Toxiproxy, a stub that sleeps, or chaos testing in staging) and watching the timeouts, breakers, and fallbacks actually engage.

Slow is worse than down A dependency that fails fast costs you one error. A dependency that hangs costs you a thread per request until you have none left. Timeouts convert slow failures into fast ones.

§7Common Mistakes

MistakeWhat HappensFix
No timeout on an HTTP or database callThreads pile up behind a hung dependencySet connect and read timeouts everywhere
Retrying non-idempotent operationsDuplicate side effects such as double chargesRetry only idempotent calls, or use idempotency keys
Retrying immediately without backoff or jitterA retry storm overwhelms the recovering serviceUse exponential backoff with jitter and a cap
Retries at every layerMultiplied load (3 x 3 x 3 requests)Retry at one layer
An unbounded queue or thread poolMemory exhaustion with unbounded latencyBound the queue and reject excess work
A circuit breaker with no fallbackUsers just get errors fasterDefine degraded behavior for each dependency
Never testing the failure pathsThe first real test is the incidentInject latency and errors regularly
Practice
  1. Write a client call with a 500 ms timeout against a stub that sleeps for 5 seconds, and confirm the caller recovers in about 500 ms.
  2. Implement retry with exponential backoff and jitter, then run 100 simulated clients against a flapping stub and compare with a no-backoff retry.
  3. Put a bounded executor in front of a slow dependency and show that overload produces fast rejections rather than ever-growing latency.
Key takeaways
  • Timeouts turn slow failures into fast ones, so every remote call needs them, within an overall deadline.
  • Retry only safe, transient failures with backoff, jitter, caps, and at one layer.
  • Circuit breakers, bulkheads, bounded queues, and fallbacks contain failures, and they must be tested by injecting faults.
