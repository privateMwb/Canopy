API Design & Evolution

Once other teams or customers depend on an API, it is a contract, and the hard part of API design is changing it without breaking the people who rely on it.

§1Designing for Consumers

Design an API around the consumer's tasks rather than your internal data model. Use consistent naming, resource-oriented URLs, predictable error shapes, and clear documentation, ideally an OpenAPI specification that is the source of truth and can generate docs, clients, and contract tests. Make the safe path easy and the dangerous one explicit: require idempotency keys for operations that must not repeat, bound page sizes, and validate inputs strictly.

Remember that anything you expose, someone will depend on, including accidental behavior: the order of fields, an undocumented value, a quirk of a response time. This is sometimes called Hyrum's Law. The smaller and more deliberate the surface, the fewer promises you have to keep.

§2What Counts as a Breaking Change

A change is breaking if a correct existing client can fail or behave differently after it. Judge it from the consumer's side.

Usually safe (compatible)Breaking
Adding a new optional request fieldRemoving or renaming a field or endpoint
Adding a new response fieldChanging a field's type or meaning
Adding a new endpointMaking an optional field required
Adding a new enum value to a response, if clients were told to tolerate unknown valuesTightening validation; changing error codes or status semantics
Loosening validationChanging ordering, pagination, or default behavior that clients rely on

Even "safe" additions break clients that parse strictly (a client that fails on unknown JSON fields, or a switch over an enum with no default). That is why you should document the tolerant reader rule up front: clients ignore fields they don't know. For Java services, avoid exposing internal entities, enums, or exception types directly; keep a separate API model so internal refactors don't leak out.

§3Compatible Evolution Techniques

Most changes can be made compatibly if you plan for it. Expand and contract (parallel change) is the key pattern: add the new thing alongside the old, migrate consumers, then remove the old.

// Renaming "fullName" to "name": expand, migrate, contract
record UserDto(
    String name,                         // new field, added first
    @Deprecated String fullName,         // old field still returned during the migration window
    String email) {
    UserDto(String name, String email) { this(name, name, email); }
}
  • Add, don't change: introduce a new field or endpoint instead of altering the meaning of an old one.
  • Deprecate with notice: mark old fields and endpoints deprecated in the spec, return Deprecation/Sunset headers, announce a date, and track who still uses them (log the client id) before removal.
  • Feature flags and defaults: new behavior is opt-in by a parameter or header until it can become the default.
  • Never reuse a field name or number for a different meaning. (This is especially important for protobuf and other binary formats, where field numbers are the contract.)

§4Versioning

When a breaking change is truly necessary, version the API so old and new coexist. Common approaches are a version in the path (/v2/orders), a header or media type, or a date-based version. Path versions are simple and visible, which is why they are popular. Versioning has a cost: every version you keep alive is code to maintain, test, and secure, so aim to avoid new versions by evolving compatibly, and when you do ship one, set and enforce a sunset policy.

§5Contracts and Testing

Make compatibility checkable instead of a matter of good intentions. Use contract tests (such as consumer-driven contracts with Pact or Spring Cloud Contract), where consumers state what they use and the provider's build fails if it breaks them. Run an OpenAPI diff tool in CI to flag breaking changes in the spec. Keep old consumers' tests running against new provider versions. And for event and message schemas, use a schema registry with compatibility rules (backward, forward, or full) so a producer can't publish a message that breaks existing subscribers.

§6Rolling Out Changes

Deploys are not instantaneous: during a rolling deployment both old and new versions run at once, so each version must tolerate the other's requests, responses, and database schema. This is why you ship database changes in compatible steps too (add column, deploy code that writes both, backfill, switch reads, then drop the old column).

Additive and tolerant Safe evolution depends on both sides: providers only add, and consumers ignore what they don't recognize. State the tolerant-reader rule in your API guidelines, because without it even harmless additions are risky.

§7Common Mistakes

Practice
  1. Take an endpoint and rename a field using expand and contract, writing down the steps and the order of deployments.
  2. Run an OpenAPI diff on two versions of a spec in which you made one breaking and one non-breaking change, and read what it reports.
  3. Write a short deprecation policy: how it is announced, how usage is tracked, and when the old version is removed.
Key takeaways
  • An API is a contract: judge changes from the consumer's side, and prefer additive, backward-compatible evolution.
  • Use expand-and-contract, deprecation with usage tracking, and versioning only when a real break is unavoidable.
  • Enforce compatibility with contract tests and schema checks, and remember that rolling deployments run two versions at once.
