Profiling with JFR & async-profiler

A profiler shows where a running JVM actually spends its CPU time, allocates memory, and waits on locks, replacing guesses about performance with evidence at a cost low enough to use in production.

§1Measure Before You Change

Developers are reliably bad at guessing where time goes. The profile of a slow service usually surprises people: the hot spot is a JSON serializer, a regex, a logging call, or lock contention nobody suspected. The discipline is always the same: reproduce the problem under realistic load, profile, change the biggest thing, and measure again. Profiling an idle process, or a laptop that doesn't resemble production, proves little.

§2Two Kinds of Profiler

Sampling profilers periodically capture each thread's stack (say, every 10 to 20 ms) and count which methods appear. They have low overhead and are safe to run in production, but they only see what the sample catches. Instrumenting profilers modify methods to record every entry and exit; they are precise but slow enough to distort the very thing they measure, so they're a development tool at best.

A subtle problem is safepoint bias: some older profilers can only sample threads at JVM safepoints, which skews results toward loop ends and method returns rather than the true hot spot. JFR and async-profiler avoid it by sampling in a different way.

§3Java Flight Recorder

JFR is built into the JDK, records events with typically around 1 to 2 percent overhead, and can be left on continuously. It captures CPU samples, allocation profiles, GC activity, lock contention, I/O, thread states, and JIT activity.

java -XX:StartFlightRecording=filename=rec.jfr,duration=120s,settings=profile -jar app.jar
jcmd <pid> JFR.start name=live settings=profile duration=60s filename=/tmp/live.jfr   # attach to a running JVM
jcmd <pid> JFR.dump name=live filename=/tmp/now.jfr
jfr print --events jdk.ExecutionSample rec.jfr | head                               # command-line summary
jfr summary rec.jfr

Open the .jfr file in JDK Mission Control (or IntelliJ's profiler) and look at: the method profiling view or flame graph for CPU hot spots, allocation events (which code allocates the most, and of what), lock instances for contention, GC pauses, and the thread view to see whether threads are running, blocked, or waiting. The default settings are lighter than profile.

§4async-profiler and Flame Graphs

async-profiler is an open-source sampling profiler that gets accurate stacks without safepoint bias, and includes native frames (kernel, JVM internals, JNI) that JFR can't show. Its output is typically a flame graph.

./asprof -d 30 -e cpu -f cpu.html <pid>          # 30 seconds of CPU samples
./asprof -d 30 -e alloc -f alloc.html <pid>      # allocation profile
./asprof -d 30 -e lock -f lock.html <pid>        # lock contention
./asprof -d 30 -e wall -f wall.html <pid>        # wall-clock: where threads WAIT, not just burn CPU

In a flame graph, the x-axis is the share of samples (width means time), and the y-axis is the stack depth, with the function at the bottom calling those above it. Look for wide plateaus: a wide box near the top is a function consuming time directly, and a wide box lower down is a caller responsible for lots of work beneath it. Colors are only categories.

§5Choosing the Right Mode

CPU profiles show where CPU cycles go, which helps only when the process is CPU-bound. If your service is slow but CPU is low, the threads are waiting: use a wall-clock profile or JFR's thread-state views to find blocking I/O, lock waits, or pool exhaustion. Allocation profiles find what is creating garbage and driving GC. Lock profiles show contention hot spots. Matching the mode to the symptom is most of the skill.

§6Reading Results Honestly

Profile for long enough to gather statistically meaningful samples. Compare before and after under the same load. Beware of inlining, which attributes time to the caller, and of profiling at too short an interval. Treat a surprising result as a hypothesis, then confirm it with a change and a measurement. Finally, fix what is large: a function using 2 percent of the time can't give you more than a 2 percent improvement however well you optimize it.

Profile the symptom you have High CPU calls for a CPU profile, high latency with low CPU calls for a wall-clock or lock profile, and high GC activity calls for an allocation profile. The wrong profile mode can look perfectly healthy.

§7Common Mistakes

MistakeWhat HappensFix
Optimizing by intuitionEffort goes to code that isn't the bottleneckProfile first and target the widest frames
Using a CPU profile for a service that is waitingThe profile looks idle and shows nothing usefulUse wall-clock profiling or JFR thread states
Profiling on a laptop with no loadResults don't resemble production behaviorProfile under realistic load, in production if safe
Using an instrumenting profiler on a live serviceHigh overhead distorts the resultsUse sampling profilers such as JFR or async-profiler
Profiling for a few secondsToo few samples, noisy conclusionsCapture at least tens of seconds under steady load
Changing several things at onceYou can't tell which change helpedChange one thing and re-measure
Practice
  1. Start a JFR recording on a running program that does CPU-heavy work, open it in Mission Control, and find the top three methods by CPU samples.
  2. Capture a CPU flame graph and a wall-clock flame graph of a service that spends most of its time waiting on a database, and compare them.
  3. Make one targeted change based on a profile, then re-profile to confirm the improvement.
Key takeaways
  • Always profile realistic load and fix the largest cost, since intuition about hot spots is unreliable.
  • JFR is built in and cheap enough for production; async-profiler adds accurate flame graphs and native frames.
  • Pick the mode (CPU, wall-clock, allocation, lock) that matches the symptom, then confirm every fix with a measurement.
