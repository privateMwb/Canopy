Memory Sizing & GC Tuning in Containers

In a container the JVM has to fit inside a hard memory limit, so the useful skill is to budget the whole process, not just the heap, and to change only the few settings that actually matter.

§1What the JVM Knows About Its Container

Modern JVMs are container-aware: they read the cgroup CPU and memory limits and size themselves from them, not from the host. This was not always true (very old Java 8 releases saw the host's memory), so check the JVM version if behavior looks wrong. By default the maximum heap is 25 percent of the available memory and the JVM picks a GC based on the number of CPUs and memory: with fewer than 2 CPUs or under about 1792 MB, it selects Serial instead of G1.

java -XX:+PrintFlagsFinal -version | grep -E 'MaxHeapSize|UseG1GC|UseSerialGC|ActiveProcessorCount'
java -Xlog:os+container=debug -version        # see what limits the JVM detected
jcmd <pid> VM.flags                           # the flags a running JVM actually uses

So a pod with a 1 CPU request and a 512 MB limit may silently run Serial GC with a 128 MB heap, which is a very different system than the one you tested on a laptop.

§2Sizing the Heap

Because the heap is only part of the footprint, the process total is roughly heap plus metaspace plus thread stacks plus code cache plus direct buffers plus GC and JVM overhead. Setting -Xmx equal to the container limit guarantees the kernel's OOM killer eventually terminates the process (reported as OOMKilled, exit code 137, with no Java stack trace, because the JVM never got to throw anything).

Rather than a fixed number, prefer percentages so the heap tracks the limit.

java -XX:MaxRAMPercentage=75 -XX:InitialRAMPercentage=50 -jar app.jar     # for larger containers
# for small containers (under 1 GB) 75% leaves too little for non-heap memory: try 50-60%

A reasonable starting point is 60 to 75 percent for the heap in the larger containers, with the remainder for everything else, then validate with Native Memory Tracking and observed resident set size under load. Also set -Xms equal to -Xmx (or use InitialRAMPercentage) for services where you don't want the heap to grow and shrink, and consider -XX:+AlwaysPreTouch where startup time is less important than avoiding page faults later.

§3CPU Limits and Threads

The JVM uses the CPU limit to decide availableProcessors(), which sizes the common ForkJoinPool, GC worker threads, and many library pools. A container with a CPU limit of 1 (or less) can make the JVM think it has a single processor, selecting Serial GC and starving parallel work. CPU limits also cause throttling: a JVM bursting during GC or JIT compilation may be paused by the cgroup scheduler, which appears as latency spikes unrelated to the application. If this is a problem, raise or remove the CPU limit while keeping a request, or set -XX:ActiveProcessorCount explicitly.

§4The Settings Worth Changing

Most services need very few flags. The ones that earn their place:

  • Heap size (-XX:MaxRAMPercentage or -Xmx), the one setting that matters most.
  • The collector, chosen deliberately: G1 for a balanced default, ZGC or Shenandoah for a strict latency target, Parallel for batch throughput.
  • -XX:MaxGCPauseMillis for G1 if you have a specific goal, understanding it is a target, not a promise.
  • Metaspace and direct memory caps, for catching leaks early with a clear error instead of an OOM kill.
  • -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps (mount a volume) and GC logging so that failures leave evidence.
  • -Xss only if you really need deeper recursion or many threads.

Resist long copied lists of exotic flags; each one is a hypothesis you haven't tested. Tune with a load test that mimics production, change one thing at a time, and compare pause times, throughput, and resident memory.

§5Verifying in Production

Watch resident memory against the container limit, GC pause time and frequency, heap after collection, and CPU throttling metrics. A flat heap-after-GC trend with high resident memory suggests native or off-heap use; a rising heap-after-GC trend suggests a leak or an undersized heap. Keep headroom (many teams aim to stay below about 80 percent of the limit under peak load) so a traffic spike doesn't cross it.

Exit code 137 means the kernel killed you An OOMKilled pod has no Java stack trace and no heap dump, because the JVM never ran out of heap. It ran out of container memory. Check total resident size, not just the heap graph.

Practice
  1. Run java -XX:+PrintFlagsFinal -version inside containers limited to different CPU and memory settings, and record which GC and max heap you get in each.
  2. Run a service in a 512 MB container with -Xmx512m under load and watch it get OOM-killed, then fix it with a percentage-based heap.
  3. Enable -XX:NativeMemoryTracking=summary and produce a table of where a 1 GB-resident process is using memory.
Key takeaways
  • The JVM sizes itself from container limits, which can silently pick Serial GC and a small heap for small pods.
  • Budget the whole process; set the heap to a percentage of the limit rather than all of it.
  • Change few flags, choose the collector deliberately, enable heap dumps and GC logs, and verify against resident memory in production.
