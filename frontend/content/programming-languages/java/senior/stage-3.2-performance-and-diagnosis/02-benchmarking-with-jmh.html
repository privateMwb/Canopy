Benchmarking with JMH

Hand-rolled timing loops give wrong answers on the JVM because of warmup, JIT optimization, and dead-code elimination, and JMH exists to handle these traps so a microbenchmark means something.

§1Why Naive Timing Lies

The obvious benchmark is a loop wrapped in System.nanoTime(). It misleads for several reasons covered in earlier lessons.

long start = System.nanoTime();
for (int i = 0; i < 1_000_000; i++) { compute(i); }
long elapsed = System.nanoTime() - start;                 // what did this actually measure?
  • Warmup: the first iterations run in the interpreter and C1 code, so you measure startup, not steady state.
  • Dead-code elimination: if the result of compute(i) is never used, the JIT may delete the call, and you time an empty loop.
  • Constant folding: if the inputs are constants, the JIT can compute the answer at compile time.
  • Loop optimizations and on-stack replacement: code in a long main loop is compiled differently than normal method calls.
  • Noise: GC, other processes, CPU frequency scaling, and a single run give no idea of variance.

You can end up "proving" that a clearly slower approach is faster, or reporting a 0.3 ns operation that isn't real.

§2JMH Basics

JMH (the Java Microbenchmark Harness, from the OpenJDK project) forks a fresh JVM, runs warmup iterations, then measurement iterations, and reports statistics. You write a benchmark class with annotations and run it through the JMH build setup (the Maven archetype or Gradle plugin).

@State(Scope.Benchmark)
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 5, time = 1)
@Fork(2)
public class ConcatBenchmark {
    @Param({"10", "1000"})
    int size;

    String[] parts;

    @Setup
    public void setup() {
        parts = new String[size];
        Arrays.fill(parts, "abc");
    }

    @Benchmark
    public String stringBuilder() {
        StringBuilder sb = new StringBuilder();
        for (String p : parts) sb.append(p);
        return sb.toString();                          // returning the value prevents dead-code elimination
    }

    @Benchmark
    public void plusOperator(Blackhole bh) {
        String s = "";
        for (String p : parts) s += p;
        bh.consume(s);                                 // a Blackhole consumes values without cost or elimination
    }
}

Run it with java -jar target/benchmarks.jar (or -prof gc to include allocation rates, -prof async to attach a profiler). The output reports a score with an error margin, for example 120.3 ± 4.1 ns/op, for every @Param combination.

§3Key Concepts

  • @State objects hold benchmark inputs; set up data in @Setup so setup cost isn't measured, and keep inputs non-constant (read from fields, not literals).
  • Return values or use a Blackhole so the JIT can't discard the work.
  • @Fork runs the benchmark in separate JVMs, because JIT decisions in one run can influence another, so forks reveal run-to-run variation.
  • Modes: Throughput (operations per second), AverageTime, SampleTime (a distribution, useful for percentiles), and SingleShotTime (cold start).
  • -prof gc shows allocation per operation, which often explains the difference between two implementations.

§4Interpreting Results

Look at the error margin: if two results overlap within their errors, you can't claim one is faster. Check that the benchmark measures what you think by viewing it with a profiler. And remember what a microbenchmark can't tell you: it measures an isolated piece in a warm, quiet JVM with hot caches, so a 20 percent gain in a microbenchmark can vanish when the code runs inside a real service where the bottleneck is a database or lock. Use JMH to choose between two implementations of something that is genuinely hot, and end-to-end load tests to determine whether it matters.

A benchmark is a model, not the system JMH can tell you which of two small pieces of code is faster in isolation. Whether that difference shows up in your service is a separate question that only a profile or load test of the real system can answer.

§5Common Mistakes

MistakeWhat HappensFix
Timing a loop with System.nanoTime()Measures warmup, not steady stateUse JMH with warmup and measurement iterations
Not using or returning the resultThe JIT eliminates the computation entirelyReturn the value, or pass it to a Blackhole
Hardcoding constant inputsConstant folding computes the result at compile timeRead inputs from @State fields
Running with a single fork and few iterationsNo idea of variance or JIT run-to-run effectsUse multiple forks and iterations
Comparing results that overlap within errorClaiming a difference that isn't realCompare the score plus error margins
Benchmarking on a busy laptopNoisy, irreproducible numbersUse a quiet, dedicated machine, and a consistent power state
Generalizing from a microbenchmark to the whole serviceThe real bottleneck is elsewhereConfirm with profiling and load tests
Practice
  1. Write a naive nanoTime loop for two ways of summing a list, then reproduce the comparison in JMH, and explain any disagreement.
  2. Add @Param for list sizes of 100, 10,000, and 1,000,000 and see whether the faster approach changes with size.
  3. Run with -prof gc and explain the difference in bytes allocated per operation between two implementations.
Key takeaways
  • Naive timing ignores warmup, dead-code elimination, constant folding, and noise, and so lies.
  • JMH handles forks, warmup, measurement, and statistics; use @State, return values or Blackhole, and read error margins.
  • Microbenchmarks compare small pieces in isolation, and only profiling and load tests show whether a change matters in the real system.
