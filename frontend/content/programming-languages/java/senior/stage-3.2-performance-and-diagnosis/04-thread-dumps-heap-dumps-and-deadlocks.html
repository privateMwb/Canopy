Thread Dumps, Heap Dumps & Deadlocks

When a JVM hangs, slows, or runs out of memory, a thread dump shows what every thread is doing right now and a heap dump shows what every object is holding, and learning to read both turns an outage into an investigation.

§1Thread Dumps

A thread dump is a snapshot of every thread's stack and state. Take several dumps a few seconds apart, because one snapshot can mislead; what matters is what stays the same.

jcmd <pid> Thread.print                  # preferred
jstack <pid>                             # same idea
kill -3 <pid>                            # prints to the process's stdout (Unix)
jcmd <pid> Thread.dump_to_file -format=json /tmp/threads.json     # includes virtual threads

Each entry shows the thread's name, state, and stack:

"http-nio-8080-exec-17" #58 prio=5 tid=0x00007f... nid=0x1a2b waiting for monitor entry
   java.lang.Thread.State: BLOCKED (on object monitor)
        at com.acme.Cache.get(Cache.java:42)
        - waiting to lock <0x000000076ab62208> (a com.acme.Cache)
        at com.acme.OrderService.price(OrderService.java:88)

The key states: RUNNABLE (running, or in native I/O: a thread reading a socket often shows as RUNNABLE), BLOCKED (waiting to enter a synchronized block: lock contention), WAITING and TIMED_WAITING (in wait, park, sleep, or waiting on a queue or future: often idle pool threads, but sometimes the symptom).

§2What to Look For

  • Many threads blocked on the same lock (waiting to lock <0x...>): find the thread that holds that address (locked <0x...>) and see what it's doing, usually slow I/O inside a synchronized section.
  • All pool threads waiting on the same thing: a database connection pool, an HTTP client, or a downstream call. Threads in Future.get or SocketInputStream.read for every worker means the dependency is slow.
  • Many threads at the same code line across dumps: a hot loop or a stuck call.
  • Thread count growing across dumps: a leak of threads or an unbounded pool.

Group stacks to see the pattern (tools such as fastThread or a quick grep/sort | uniq -c on top frames).

§3Deadlocks

A deadlock happens when threads hold locks the others need, in a cycle. The JVM detects deadlocks involving synchronized and java.util.concurrent locks and reports them at the end of the dump.

Found one Java-level deadlock:
=============================
"worker-1": waiting to lock monitor 0x...(a Account), which is held by "worker-2"
"worker-2": waiting to lock monitor 0x...(a Account), which is held by "worker-1"

The report names the threads, locks, and the exact lines. The fix is nearly always a lock ordering rule (acquire in a consistent order, for example by account id), narrowing the critical section, or using tryLock with a timeout. A related failure is thread-pool starvation deadlock, where tasks wait for other tasks queued behind them in the same pool. The JVM can't detect it as a deadlock, so it shows as many threads WAITING on futures with an empty-looking system.

§4Heap Dumps

A heap dump is a snapshot of every live object, which lets you answer "what is using the memory?" and "why can't it be collected?". Take one when the heap-after-GC keeps rising, or automatically on OutOfMemoryError.

jcmd <pid> GC.heap_dump /tmp/heap.hprof                    # live objects only (triggers a full GC)
java -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps ...   # at crash time
jcmd <pid> GC.class_histogram | head -20                   # quick look without a full dump

A dump may be as large as the heap and it pauses the JVM, so take care on a production instance and treat the file as sensitive: it can contain passwords, tokens, and customer data. Open it in Eclipse MAT or VisualVM.

§5Finding a Leak

In MAT, look first at the dominator tree and leak suspects report. Two ideas matter. An object's shallow size is its own memory; its retained size is everything that would be freed if it were collected, which is what identifies the real culprit. Then use path to GC roots (excluding weak references) on a suspicious object to see why it can't be collected: a static map, a listener list, a ThreadLocal, or a cache with no eviction. Compare two dumps taken some time apart to see which class counts grew.

class Registry {
    private static final Map<String, Session> ALL = new HashMap<>();     // the root retaining everything
    static void open(Session s) { ALL.put(s.id(), s); }                   // but nothing ever calls remove()
}

The fix is to remove the reference (bounded caches, remove on close, weak references where appropriate), then re-check that the heap-after-GC floor is flat.

One dump is a photo; several are a film A single thread dump may catch a normal moment. Take three or four, a few seconds apart, and look for the thread that is in the same place every time.

§6Common Mistakes

MistakeWhat HappensFix
Taking a single thread dumpCan't tell stuck from busyTake several dumps and compare them
Assuming RUNNABLE means using CPUThreads blocked in native socket reads show as RUNNABLECheck the top frame, and correlate with CPU use
Looking at shallow size in a heap dumpThe real leak holds small objects that retain a lotSort by retained size, or use the dominator tree
Not capturing a dump on OutOfMemoryErrorThe evidence is gone after the restartEnable HeapDumpOnOutOfMemoryError with a persistent path
Sharing heap dumps freelyThey contain secrets and personal dataTreat them as sensitive and restrict access
Fixing a deadlock by adding more threadsThreads simply deadlock as wellImpose a lock order or use timeouts
Practice
  1. Write a program with a deliberate two-lock deadlock, take a thread dump with jcmd, and read the deadlock report to find the lines involved.
  2. Write a program with a static map that grows forever, take two heap dumps a minute apart, and find the leaking class in MAT with its path to GC roots.
  3. Take a dump of a service with a slow dependency and identify the common stack frame across the blocked threads.
Key takeaways
  • Take several thread dumps and look at thread states, shared locks, and common stack frames, and the JVM reports lock-cycle deadlocks directly.
  • Heap dumps answer what holds memory; retained size and the path to GC roots reveal leaks.
  • Capture evidence automatically (heap dump on OOM), and treat dumps as sensitive data.
