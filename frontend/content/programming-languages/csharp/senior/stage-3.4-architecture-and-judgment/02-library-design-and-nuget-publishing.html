Library Design & NuGet Publishing

When other code depends on yours, every public member is a promise. Library design is mostly about promising less and changing it safely.

§1Designing the Public Surface

  • Expose the minimum. Everything is internal by default, and each public member is something you must support forever.
  • Seal classes unless you've designed them for inheritance, and prefer interfaces and composition over base classes in the API.
  • Accept the least specific type (IEnumerable<T>, ReadOnlySpan<char>) and return the most useful (IReadOnlyList<T>).
  • Make invalid states unrepresentable: validate arguments (ArgumentNullException.ThrowIfNull) and document exceptions.
  • Async methods take a CancellationToken and use ConfigureAwait(false) internally.
  • Follow the framework's conventions: Try... methods, ...Async suffix, and IDisposable/IAsyncDisposable.
public sealed class CurrencyConverter
{
    public CurrencyConverter(IRateProvider rates) { ArgumentNullException.ThrowIfNull(rates); _rates = rates; }
    private readonly IRateProvider _rates;

    public async ValueTask<decimal> ConvertAsync(decimal amount, string from, string to, CancellationToken ct = default) { /* ... */ return amount; }
}

§2Versioning and Compatibility

Use Semantic Versioning: MAJOR.MINOR.PATCH. Bug fixes bump patch, backward-compatible additions bump minor, and breaking changes bump major. The hard part is knowing what "breaking" means in .NET:

ChangeBreaking?
Adding a new public method or typeNo (usually)
Adding an optional parameterYes for binary compatibility: callers compiled against the old signature break. Add an overload instead
Changing a return type, renaming, or removing a public memberYes
Adding a member to a public interfaceYes for implementers (default interface methods can soften it)
Changing behavior callers depend onYes, even if the signature is identical
<ItemGroup>
  <PackageReference Include="Microsoft.CodeAnalysis.PublicApiAnalyzers" Version="3.3.4" PrivateAssets="all" />
  <PackageReference Include="Microsoft.DotNet.ApiCompat.Task" Version="10.0.100" PrivateAssets="all" />
</ItemGroup>
<PropertyGroup>
  <EnablePackageValidation>true</EnablePackageValidation>
  <PackageValidationBaselineVersion>1.2.0</PackageValidationBaselineVersion>   <!-- compare against the last release -->
</PropertyGroup>

Tooling catches accidental breaks: the PublicApiAnalyzers package tracks the public surface in a checked-in PublicAPI.Shipped.txt so every change to it is visible in review, and package validation compares your build against a baseline version and fails on breaking changes. Mark things [Obsolete] for at least a full major version before removing them, and document the replacement.

§3Packing and Publishing

<PropertyGroup>
  <PackageId>Acme.Currency</PackageId>
  <Version>1.3.0</Version>
  <Authors>Acme</Authors>
  <Description>Currency conversion with pluggable rate providers.</Description>
  <PackageLicenseExpression>MIT</PackageLicenseExpression>
  <PackageReadmeFile>README.md</PackageReadmeFile>
  <RepositoryUrl>https://github.com/acme/currency</RepositoryUrl>
  <TargetFrameworks>net8.0;net10.0</TargetFrameworks>   <!-- multi-target to reach more consumers -->
  <IncludeSymbols>true</IncludeSymbols>
  <SymbolPackageFormat>snupkg</SymbolPackageFormat>
  <PublishRepositoryUrl>true</PublishRepositoryUrl>
  <ContinuousIntegrationBuild Condition="'$(CI)' == 'true'">true</ContinuousIntegrationBuild>
</PropertyGroup>
<ItemGroup><None Include="README.md" Pack="true" PackagePath="\" /></ItemGroup>
dotnet pack -c Release
dotnet nuget push bin/Release/Acme.Currency.1.3.0.nupkg --source https://api.nuget.org/v3/index.json --api-key $NUGET_API_KEY

Include a README, a license, symbols with Source Link so consumers can debug into your code, and deterministic CI builds. Publish from CI with a scoped API key stored as a secret, and never from a laptop. Published versions are immutable: you can unlist a bad package but never replace it, so test the exact .nupkg in a sample project first, and use pre-release versions (1.3.0-beta.1) for early feedback.

The key insight A public API is a contract with strangers. Keep it small, track every change to it with tooling, and remember that a version you have published can never be taken back.

§4Common Mistakes

MistakeWhat HappensFix
Adding an optional parameter to an existing public methodPreviously compiled callers throw MissingMethodExceptionAdd a new overload and keep the old signature
Making types public "just in case"You must support them foreverStart internal; promote when there's a real need
Publishing without testing the packed .nupkgMissing files or dependencies discovered by usersInstall the exact package into a sample app in CI before pushing
Practice
  1. Turn a small utility class into a library project, shrink its public surface to the minimum, and add package metadata, a README, and a license.
  2. Add package validation with a baseline, then make a deliberately breaking change and watch the build fail.
Key takeaways
  • Expose the minimum, seal by default, and accept general types while returning useful ones.
  • Use SemVer and tooling (PublicApiAnalyzers, package validation) to catch breaking changes, including binary-breaking ones like new optional parameters.
  • Pack with metadata, symbols, and a README, publish from CI, and treat published versions as permanent.
