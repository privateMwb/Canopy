Upgrading .NET & Migrating from .NET Framework

Most real .NET work happens in codebases that already exist. Upgrading safely is a project-management and risk problem as much as a technical one.

§1Staying Current

Modern .NET (the cross-platform successor to .NET Framework, versions 5 and later) ships a new major version every November. Even-numbered versions are LTS (long-term support, roughly three years), and odd-numbered ones are STS (standard-term support, shorter, check the current policy). Check Microsoft's support lifecycle page before planning, because dates change. Falling behind has a real cost: unsupported runtimes get no security patches.

  • Upgrade routinely, in small steps, ideally to each LTS and a quick pass over each release's breaking-change list, rather than every five years in one jump.
  • Change TargetFramework, restore and build, fix errors, run the tests, then read the breaking changes and behavior changes docs for each version crossed.
  • Update NuGet packages that must match the framework version, and check that third-party libraries support the new target.
  • The dotnet-outdated tool, dotnet list package --outdated --vulnerable, and Dependabot or Renovate keep dependencies visible.
  • Deploy to a canary or staging environment and watch counters and error rates before a full rollout; runtime behavior changes (GC, thread pool, serialization defaults) don't appear as compile errors.

§2Migrating from .NET Framework

A legacy app may target .NET Framework 4.x (Windows-only, in-box with the OS). Moving to modern .NET brings cross-platform support, performance gains, side-by-side runtimes, and active development. The path depends on what the app uses:

ComponentMigration outlook
Class librariesUsually easy: retarget to netstandard2.0 or multi-target, then move to net10.0
Console apps and servicesStraightforward, then replace ServiceBase with the Worker Service / Generic Host
ASP.NET MVC / Web API (System.Web)Significant: port to ASP.NET Core, which has a different pipeline and no System.Web
WinForms and WPFSupported on modern .NET (Windows only), often a smooth port
WCF servers, Web Forms, Windows WorkflowNo direct equivalent: rewrite, or use community projects (CoreWCF) or keep them on Framework
Entity Framework 6Runs on modern .NET, then migrate to EF Core separately if there's a reason

Microsoft's .NET Upgrade Assistant and the API Portability Analyzer (try-convert is retired) report which APIs won't port and automate project-file conversion. Use them to size the work, not as a guarantee that conversion is complete.

§3Managing the Risk

  • Characterize before you change. Wrap untested legacy behavior in tests (golden-master or approval tests) so you can tell whether the port altered it.
  • Move bottom-up. Convert shared libraries to netstandard2.0 or multi-targeting first, because both old and new apps can consume them while the migration proceeds.
  • Migrate incrementally with the strangler pattern: put a proxy such as YARP in front and move endpoints one at a time to the new app while the old one continues to serve the rest. Tools such as the System.Web adapters let shared code run in both.
  • Pick a stopping point per component. Not everything has to move. A stable, rarely changed Framework component with a support plan may be better left alone than rewritten.
  • Run both in production side by side and compare behavior, using shadow traffic if possible, before cutting over, with a tested rollback.

Estimate in terms of unknowns removed: do a spike on the hardest component first, because that result decides whether the plan is realistic.

The key insight Upgrading is cheap when it is routine and expensive when it is postponed. The best migration strategy is making the next upgrade small.

§4Common Mistakes

MistakeWhat HappensFix
Waiting until a runtime is out of support to upgradeA forced big-bang migration under time pressureUpgrade to each LTS and treat it as regular maintenance
Rewriting everything because migration is hardYears of work, with feature parity as a moving targetMigrate incrementally with a strangler approach and keep shipping
Trusting a clean build as proof the port worksBehavior changes at run time (serialization, culture, GC, threading)Use characterization tests and a canary deployment
Practice
  1. Take a small library targeting .NET Framework (or imagine one) and list what is needed to multi-target netstandard2.0 and net10.0.
  2. Draft a migration plan for a System.Web application: the order of components, the first spike, the rollback plan, and the criteria for stopping.
Key takeaways
  • Upgrade regularly: LTS releases, small steps, and checks for breaking and behavior changes.
  • Migrating from .NET Framework depends on the component: libraries are easy, System.Web and WCF are hard.
  • Reduce risk with characterization tests, bottom-up conversion, the strangler pattern, and side-by-side canaries.
