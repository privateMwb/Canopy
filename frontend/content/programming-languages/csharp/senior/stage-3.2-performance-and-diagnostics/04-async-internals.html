Async Internals

Knowing what the compiler builds for an async method explains its costs, its surprising behaviors, and when ValueTask and ConfigureAwait actually matter.

§1The State Machine

The compiler rewrites every async method into a state machine struct implementing IAsyncStateMachine. Local variables and parameters become fields, and a state number records which await to resume after.

async Task<int> LoadAsync(HttpClient http)
{
    var a = await http.GetStringAsync("/a");     // state 0: start the request, register continuation
    var b = await http.GetStringAsync("/b");     // state 1: resume here, start the second request
    return a.Length + b.Length;                   // state 2: set the result on the Task
}

At each await, the machine checks whether the awaited task has already completed. If so, it continues synchronously without allocation of a continuation. If not, it boxes itself onto the heap (once), hooks a continuation onto the awaited task, and returns an incomplete Task to the caller. When the awaited task finishes, the continuation calls MoveNext and the method resumes. So the cost of async is mainly one state machine allocation, and a Task object, for methods that actually suspend.

§2ValueTask

private readonly Dictionary<int, User> _cache = new();

public ValueTask<User> GetUserAsync(int id)
{
    if (_cache.TryGetValue(id, out var user))
        return new ValueTask<User>(user);            // synchronous path: zero allocations
    return new ValueTask<User>(LoadFromDbAsync(id)); // asynchronous path: wraps a Task
}

ValueTask<T> is a struct that holds either a ready result or a Task. It avoids allocating a Task when the method often completes synchronously, such as a cache hit or a buffered read, which is why Stream.ReadAsync(Memory<byte>) returns one. It comes with strict rules:

  • Await it exactly once. Don't await it twice, don't .Result it before it's complete, and don't use it concurrently.
  • If you need to await it multiple times or combine it (Task.WhenAll), convert it with .AsTask().
  • Use it only on hot paths where profiling shows Task allocations matter. Default to Task, which is simpler and safer.

§3Synchronization Contexts and ConfigureAwait

A SynchronizationContext says where continuations run. WinForms and WPF have one that posts back to the UI thread, so code after await can touch controls. ASP.NET Core has none: continuations run on a thread pool thread, which is why the classic .Result deadlock doesn't occur there. Without a context, ConfigureAwait(false) changes nothing.

// Library code: don't care where we resume; don't depend on the caller's context
public async Task<byte[]> ReadAllAsync(Stream s, CancellationToken ct)
{
    using var ms = new MemoryStream();
    await s.CopyToAsync(ms, ct).ConfigureAwait(false);
    return ms.ToArray();
}

// App code on the UI thread: keep the default so the UI update is on the UI thread
button.Text = await FetchTitleAsync();

A related hazard is thread-pool starvation: if many requests block threads (with .Result or sync I/O), the pool injects new threads slowly (roughly one or two per second beyond the minimum), so latency climbs while CPU stays low. The counters from earlier, thread count rising and queue length growing with low CPU, are its signature. The fix is to stop blocking, not to raise the minimum thread count.

The key insight An await on an already-finished task is nearly free, and an await that suspends costs one state-machine allocation. Optimize async by avoiding needless suspension and blocking, not by removing async.

§4Common Mistakes

MistakeWhat HappensFix
Awaiting a ValueTask twice or storing it for laterUndefined behavior and corrupted resultsAwait once, or convert with AsTask() first
Using ValueTask everywhere by defaultMore complexity and misuse risk for no measurable gainUse Task unless profiling shows allocation on a hot, mostly-synchronous path
Blocking threads in request handlers (.Result, sync I/O)Thread-pool starvation: high latency with low CPUMake the whole path async and watch the thread-pool counters
Practice
  1. Decompile a small async method with SharpLab and find the state-machine fields and the MoveNext switch.
  2. Write a cache-backed method returning ValueTask<T> and benchmark it against the Task<T> version for a 95% hit rate.
Key takeaways
  • async methods compile to state machines; completed awaits continue synchronously and suspended ones allocate.
  • ValueTask avoids allocation on synchronous paths but must be awaited exactly once.
  • ASP.NET Core has no synchronization context, and blocking on async causes thread-pool starvation.
