Memory Leaks & Finalizers

Managed code can't leak memory the way C does, but it can hold references it no longer needs. Most .NET "leaks" are objects that remain reachable.

§1How Managed Code Leaks

The GC frees only unreachable objects. A leak is an object you're done with that something still references. The usual suspects:

  • Static collections that only grow, such as a static Dictionary used as a cache with no eviction.
  • Event handlers never unsubscribed: a long-lived publisher keeps every subscriber alive.
  • Captured variables in long-lived lambdas or timers.
  • Unreleased native resources: file handles, sockets, HttpClient misuse, and unmanaged memory.
  • Thread-local or AsyncLocal data that outlives its use, and unbounded queues and channels.
public class PriceFeed                      // long-lived singleton
{
    public event EventHandler<decimal>? Updated;
}

public class Dashboard                         // short-lived, created per user
{
    public Dashboard(PriceFeed feed) => feed.Updated += OnUpdate;   // feed now references this
    private void OnUpdate(object? s, decimal p) { }
    // never unsubscribed: every Dashboard ever created stays in memory
}

§2Finalizers and the Dispose Pattern

A finalizer (~MyType()) is a last-resort cleanup the GC runs on a separate thread some time after an object becomes unreachable. It is non-deterministic, may be delayed or skipped at shutdown, and keeps the object alive an extra GC cycle (finalizable objects are promoted and queued). So you should rarely write one. Prefer IDisposable for deterministic cleanup, and SafeHandle to wrap native handles.

public sealed class NativeBuffer : IDisposable
{
    private SafeHandle? _handle = new MyHandle();   // SafeHandle has its own finalizer
    private bool _disposed;

    public void Dispose()
    {
        if (_disposed) return;
        _handle?.Dispose();
        _handle = null;
        _disposed = true;
    }
}

// Only a class that directly owns an unmanaged resource needs the full pattern:
protected virtual void Dispose(bool disposing)
{
    if (disposing) { /* dispose managed fields */ }
    /* free unmanaged resources */
}
~Resource() => Dispose(false);   // safety net if Dispose was never called

For a sealed class that just owns IDisposable fields, a simple Dispose() that disposes them is enough, and for native handles use SafeHandle instead of writing your own finalizer. If a type implements IDisposable, the caller must dispose it, and analyzer rule CA2000 and CA1001 help find the gaps.

§3Finding a Leak

  1. Confirm with counters that GC Heap Size (especially Gen 2) grows over time even after collections.
  2. Take two dumps some minutes apart under steady load.
  3. Run dumpheap -stat on each and compare: which type's count and size grew?
  4. Pick an instance with dumpheap -mt <MT> and run gcroot <address> to see the chain of references from a root to the object. The first link out of a static, a timer, or an event field is the culprit.
  5. Fix the cause (unsubscribe, bound or evict the cache, dispose), then repeat the measurement to confirm the growth stopped.
// Fix: unsubscribe when done
public sealed class Dashboard : IDisposable
{
    private readonly PriceFeed _feed;
    public Dashboard(PriceFeed feed) { _feed = feed; _feed.Updated += OnUpdate; }
    public void Dispose() => _feed.Updated -= OnUpdate;
    private void OnUpdate(object? s, decimal p) { }
}
The key insight A managed leak is a reachability bug. The question is never "why wasn't this freed?" but "what still points at it?", and gcroot answers that directly.

§4Common Mistakes

MistakeWhat HappensFix
Writing a finalizer for a class that only holds managed objectsExtra GC cost with no benefitImplement IDisposable only; finalize native handles via SafeHandle
A static Dictionary cache with no size limitUnbounded growthUse MemoryCache with a size limit or an eviction policy
Calling GC.Collect() to hide a leakThe memory is still reachable, so nothing is freedFind what holds the references with gcroot
Practice
  1. Create a long-lived publisher and subscribe 100,000 short-lived objects without unsubscribing. Take a dump and use dumpheap -stat and gcroot to show the chain.
  2. Fix the leak with IDisposable and unsubscribe, then repeat to confirm the instance count stays flat.
Key takeaways
  • Managed leaks are objects still reachable from statics, events, timers, or caches.
  • Prefer IDisposable and SafeHandle over finalizers, which are slow and non-deterministic.
  • Diagnose with growth over time, compared dumps, dumpheap -stat, and gcroot.
