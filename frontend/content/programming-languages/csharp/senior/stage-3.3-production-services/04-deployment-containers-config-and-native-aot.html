Deployment: Containers, Config & Native AOT

A service isn't finished until it runs reliably somewhere else. Packaging, configuration, and the runtime mode all affect how it behaves in production.

§1Building a Container

# Dockerfile: multi-stage; the SDK image builds, the small runtime image runs
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY *.sln ./
COPY src/Shop.Api/*.csproj src/Shop.Api/
RUN dotnet restore                          # cached until a csproj changes
COPY . .
RUN dotnet publish src/Shop.Api -c Release -o /app --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
WORKDIR /app
COPY --from=build /app .
USER $APP_UID                               # run as non-root (the images define this user)
EXPOSE 8080
ENTRYPOINT ["dotnet", "Shop.Api.dll"]

Copy the .csproj files and restore before copying the rest of the source, so Docker's layer cache skips restore when only code changed. The runtime image has no SDK, so it's smaller and has less attack surface. The .NET SDK can also publish a container directly with dotnet publish -t:PublishContainer. Run as a non-root user, and pin image versions deliberately.

§2Configuration and Operations in Containers

  • Configuration through environment variables: ConnectionStrings__Shop, Email__Host. One image, many environments.
  • Secrets from the platform (Kubernetes secrets, a vault, managed identity), never baked into the image.
  • Health endpoints: separate liveness ("restart me if this fails") from readiness ("send me traffic only when this passes").
  • Graceful shutdown: on SIGTERM the host stops accepting requests and drains in-flight ones within ShutdownTimeout. Align it with your orchestrator's termination grace period.
  • Memory limits: the runtime reads container limits, but heap, thread, and native memory all count. Leave headroom and watch the working set.
builder.Services.AddHealthChecks().AddDbContextCheck<ShopDb>(tags: ["ready"]);

app.MapHealthChecks("/health/live", new() { Predicate = _ => false });   // process is up
app.MapHealthChecks("/health/ready", new() { Predicate = c => c.Tags.Contains("ready") });  // dependencies OK

builder.Services.Configure<HostOptions>(o => o.ShutdownTimeout = TimeSpan.FromSeconds(25));

§3JIT or Native AOT?

FactorJIT (default)Native AOT
Startup timeHundreds of ms or moreTens of ms
Memory footprintHigher (JIT, metadata)Lower
Peak throughputHighest (dynamic PGO)Usually a bit lower
Image / binary sizeLarger with runtimeSmall, self-contained
Reflection, dynamic loadingFully supportedRestricted; needs source generators and annotations
Library compatibilityEverythingOnly AOT-compatible libraries (check trim/AOT warnings)
PlatformBuild once, run anywhereBuild per target OS/architecture
<PropertyGroup>
  <PublishAot>true</PublishAot>
  <InvariantGlobalization>true</InvariantGlobalization>   <!-- smaller; skips ICU if you don't need cultures -->
</PropertyGroup>

// ASP.NET Core minimal APIs with AOT
var builder = WebApplication.CreateSlimBuilder(args);
builder.Services.ConfigureHttpJsonOptions(o => o.SerializerOptions.TypeInfoResolverChain.Insert(0, AppJsonContext.Default));

Choose Native AOT for scale-to-zero, serverless, CLI tools, and dense small containers, where startup and memory dominate. Choose the JIT for long-running services that need peak throughput and use reflection-heavy libraries. Decide with data: build both, run your real workload, and compare startup, memory, and p99 latency before committing.

The key insight Build once, configure per environment. The same image should run in test and production with only environment variables and mounted secrets changing.

§4Common Mistakes

MistakeWhat HappensFix
Baking secrets or environment settings into the imageLeaks credentials and prevents reuse across environmentsInject configuration at run time through the platform
One health check for everythingOrchestrators restart healthy-but-waiting pods or send traffic to unready onesSeparate liveness from readiness
Adopting Native AOT without testing the published binaryReflection and dynamic features fail at run timeFix AOT warnings, then run the full test suite against the AOT build
Practice
  1. Write a multi-stage Dockerfile for a small API, build it twice, and confirm that the second build reuses the restore layer after a code-only change.
  2. Publish the same app with the JIT and with Native AOT and compare binary size, startup time, and memory at idle.
Key takeaways
  • Multi-stage builds with a restore layer give small images and fast rebuilds.
  • Configure through environment variables and platform secrets, with separate liveness and readiness checks and graceful shutdown.
  • Native AOT favors startup and footprint, and the JIT favors peak throughput and dynamic features, so measure before choosing.
