Observability with OpenTelemetry

Observability is being able to ask new questions about a running system without deploying new code. OpenTelemetry is the standard way to produce the data.

§1The Three Signals

SignalWhat it isAnswers
TracesA tree of spans for one request across servicesWhere did this request spend its time? Which call failed?
MetricsNumbers aggregated over time (counters, histograms, gauges)Is latency rising? What's the error rate?
LogsDiscrete structured events with contextWhat exactly happened in this case?

They work together: a metric alerts you that p99 latency rose, a trace shows which downstream call is slow, and the logs for that trace ID show why. The link between them is the trace ID attached to every log line.

§2Instrumenting an ASP.NET Core Service

builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService("shop-api", serviceVersion: "1.4.0"))
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()            // incoming requests become spans
        .AddHttpClientInstrumentation()            // outgoing calls become child spans
        .AddEntityFrameworkCoreInstrumentation()   // SQL as spans
        .AddSource("Shop.Orders")                  // your own spans
        .AddOtlpExporter())                        // send via OTLP to a collector or backend
    .WithMetrics(m => m
        .AddAspNetCoreInstrumentation()
        .AddRuntimeInstrumentation()               // GC, thread pool, and more
        .AddMeter("Shop.Orders")
        .AddOtlpExporter());

builder.Logging.AddOpenTelemetry(o => { o.IncludeScopes = true; o.AddOtlpExporter(); });

Auto-instrumentation gives you request, HTTP client, and database spans for free, and context propagates across services through the W3C traceparent header, so one trace follows a request through every service that participates. Export over OTLP to a collector, which can then forward to Jaeger, Tempo, Prometheus, Azure Monitor, Datadog, or any other backend, so the instrumentation stays vendor-neutral.

§3Custom Spans and Metrics That Answer Questions

public class OrderService
{
    private static readonly ActivitySource Source = new("Shop.Orders");
    private static readonly Meter Meter = new("Shop.Orders");
    private static readonly Counter<long> Placed = Meter.CreateCounter<long>("orders.placed");
    private static readonly Histogram<double> Value = Meter.CreateHistogram<double>("orders.value", unit: "EUR");

    public async Task PlaceAsync(Order o)
    {
        using var activity = Source.StartActivity("PlaceOrder");           // a span
        activity?.SetTag("order.items", o.Items.Count);                     // searchable detail
        try
        {
            await SaveAsync(o);
            Placed.Add(1, new KeyValuePair<string, object?>("channel", o.Channel));
            Value.Record((double)o.Total);
        }
        catch (Exception ex)
        {
            activity?.SetStatus(ActivityStatusCode.Error, ex.Message);      // mark the span failed
            throw;
        }
    }
}
  • Add spans around business operations, not every method, and tags that make traces searchable (order id, tenant, outcome).
  • Keep metric labels low-cardinality (channel, status), never user ids or order ids, or the metrics store explodes. Put high-cardinality details in traces and logs.
  • Alert on symptoms users feel (error rate, latency percentiles), not on causes such as CPU, and use causes to investigate.
  • Decide on sampling (for example 10% of traces, but all errors) so volume and cost stay controlled.
The key insight Instrument for the questions you'll have during an incident: which requests failed, for whom, and where did the time go? Dashboards that only show CPU and memory can't answer them.

§4Common Mistakes

MistakeWhat HappensFix
High-cardinality metric labels (user id, order id)Metric storage and cost explodeUse low-cardinality labels; keep identifiers in traces and logs
Logs without trace IDsYou can't connect a log line to the request that produced itEnable the OpenTelemetry logging provider and include scopes
Instrumenting every methodNoisy, expensive traces nobody readsCreate spans around meaningful operations and external calls
Practice
  1. Add OpenTelemetry to a small service, export to the console or a local collector, and make two services' spans appear in one trace.
  2. Add a counter and histogram to one business operation and define the alert you'd want from them.
Key takeaways
  • Traces, metrics, and logs answer different questions, and the trace ID links them.
  • OpenTelemetry instruments ASP.NET Core, HTTP, and EF automatically, exports over OTLP, and stays vendor-neutral.
  • Keep labels low-cardinality, span meaningful operations, and alert on user-visible symptoms.
