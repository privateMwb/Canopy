Resilience: Polly & HttpClientFactory

Every network call can be slow or fail. Resilience means deciding in advance what your service does when it does, instead of finding out during an outage.

§1HttpClientFactory First

The classic mistake is new HttpClient() per request, which can exhaust sockets because closed connections linger in TIME_WAIT. The opposite mistake, one static HttpClient forever, never picks up DNS changes. IHttpClientFactory pools and recycles the underlying handlers, solving both.

builder.Services.AddHttpClient<PaymentsClient>(client =>
{
    client.BaseAddress = new Uri("https://payments.internal/");
    client.Timeout = TimeSpan.FromSeconds(10);      // overall cap per call
});

public class PaymentsClient
{
    private readonly HttpClient _http;
    public PaymentsClient(HttpClient http) => _http = http;   // injected, managed by the factory

    public async Task<Receipt?> ChargeAsync(Charge c, CancellationToken ct)
    {
        using var response = await _http.PostAsJsonAsync("charges", c, ct);
        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<Receipt>(ct);
    }
}

§2Retries, Timeouts, and Circuit Breakers

builder.Services.AddHttpClient<PaymentsClient>()
    .AddStandardResilienceHandler();            // Microsoft.Extensions.Http.Resilience (built on Polly v8)

// Or compose your own pipeline
builder.Services.AddHttpClient<InventoryClient>()
    .AddResilienceHandler("inventory", pipeline =>
    {
        pipeline.AddTimeout(TimeSpan.FromSeconds(2));                    // per attempt
        pipeline.AddRetry(new HttpRetryStrategyOptions
        {
            MaxRetryAttempts = 3,
            BackoffType = DelayBackoffType.Exponential,
            UseJitter = true,                                             // avoid synchronized retries
            Delay = TimeSpan.FromMilliseconds(200)
        });
        pipeline.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
        {
            FailureRatio = 0.5, MinimumThroughput = 20,
            SamplingDuration = TimeSpan.FromSeconds(30),
            BreakDuration = TimeSpan.FromSeconds(15)
        });
    });
StrategyProtects againstCareful about
TimeoutA dependency that hangs foreverSet per-attempt and overall timeouts below your caller's
Retry (exponential backoff + jitter)Brief, transient failuresOnly retry idempotent operations; retries multiply load
Circuit breakerA dependency that is down, so you stop hammering itIt opens on failure ratios; callers must handle the open-circuit error
Rate limiter / bulkheadOne slow dependency eating all your threads or connectionsChoose concurrency limits from measurements
FallbackTotal failure when a degraded answer is acceptableA stale cached value is better than an error only if the business agrees

§3Designing for Failure

  • Idempotency: a retried POST /charges must not charge twice. Send an idempotency key and have the server de-duplicate.
  • Retry storms: if every layer retries 3 times, three layers produce 27 calls. Retry at one layer, usually the one closest to the failing call.
  • Budget your timeouts: if the user waits 5 s, the sum of attempts, delays, and downstream calls must fit within it.
  • Test the failure paths: kill the dependency, add latency, return 503s, and confirm the service degrades as designed. Untested resilience is a guess.

Pass the CancellationToken through all calls so that when the client gives up, your work stops too.

The key insight Retries fix brief failures and make long outages worse. Pair them with timeouts, jitter, and a circuit breaker so your service backs off instead of piling on.

§4Common Mistakes

MistakeWhat HappensFix
Creating new HttpClient() per requestSocket exhaustion under loadUse IHttpClientFactory and typed clients
Retrying non-idempotent calls without a keyDuplicate charges or ordersAdd idempotency keys, or don't retry those operations
Retries without backoff or jitterSynchronized retry storms that overload a recovering dependencyUse exponential backoff with jitter and a circuit breaker
Practice
  1. Add a standard resilience handler to a typed client, point it at an endpoint that returns 503 half the time, and log each attempt.
  2. Write down the timeout budget for a request that makes two downstream calls with retries. Does it fit within the caller's limit?
Key takeaways
  • IHttpClientFactory manages connection lifetimes and avoids socket exhaustion and stale DNS.
  • Combine timeouts, backed-off retries with jitter, and circuit breakers, and retry only idempotent operations.
  • Test failure modes deliberately, and make retries happen at one layer.
