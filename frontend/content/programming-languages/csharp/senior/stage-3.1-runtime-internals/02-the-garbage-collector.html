The Garbage Collector

The garbage collector removes the need to free memory by hand, but it has costs. Understanding how it works tells you which allocation patterns hurt.

§1Generations

The managed heap is split into generations based on a simple observation: most objects die young.

  • Gen 0: newly allocated objects. Collected frequently and cheaply; survivors are promoted.
  • Gen 1: a buffer between short- and long-lived objects.
  • Gen 2: long-lived objects. Collected rarely, and a Gen 2 collection is expensive because it examines the whole heap.
  • Large Object Heap (LOH): objects of about 85,000 bytes or more (big arrays, large strings). Collected only with Gen 2, and not compacted by default, so it can fragment.
  • Pinned Object Heap (POH): for objects that must not move, such as buffers handed to native code.

Allocation itself is cheap: the runtime bumps a pointer. The cost arrives later, when a collection has to find live objects. Short-lived garbage that dies in Gen 0 is cheap, but objects that live just long enough to be promoted, then die in Gen 2, are the costly pattern.

§2What a Collection Does

The GC starts from roots (stack variables, statics, handles), marks every reachable object, reclaims the rest, and usually compacts survivors so free space stays contiguous. Compaction means objects can move, which is why references are updated and why pinning exists. By default threads are paused during part of this (a pause), and your tail latency feels that.

GC.CollectionCount(0);                    // how many Gen 0 collections so far
GC.CollectionCount(2);                    // Gen 2 count: watch this one
GC.GetTotalAllocatedBytes();              // allocation volume
var info = GC.GetGCMemoryInfo();           // pause durations, heap size, fragmentation
Console.WriteLine(GC.GetGeneration(obj));  // which generation an object is in

Don't call GC.Collect() to "help." It forces expensive work and usually makes things worse.

§3GC Modes and Reducing Pressure

SettingEffect
Workstation (default for desktop)Optimized for responsiveness, lower memory overhead
Server GC (<ServerGarbageCollector>true</ServerGarbageCollector>)One heap and GC thread per core; higher throughput, more memory; the usual choice for servers
Concurrent / background GC (default)Gen 2 marking happens on a background thread, reducing pauses
GCHeapHardLimit / container limitsThe GC respects container memory limits; set them deliberately

The best tuning is to allocate less:

  • Avoid allocating in hot paths: no LINQ, closures, or string concatenation in tight loops.
  • Reuse buffers with ArrayPool<T>.Shared instead of allocating large arrays repeatedly (this also protects the LOH).
  • Prefer structs and spans for short-lived data (next lessons).
  • Don't keep references longer than needed, because objects reachable from a static or a long-lived cache can't be collected.
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try { /* use buffer; it may be larger than requested */ }
finally { ArrayPool<byte>.Shared.Return(buffer); }
The key insight Allocation is cheap and collection is where the cost lies. The expensive pattern is mid-lived objects that get promoted to Gen 2, and large arrays that land on the LOH.

§4Common Mistakes

MistakeWhat HappensFix
Calling GC.Collect() manuallyForces full collections and hurts throughput and latencyRemove the call, and reduce allocations instead
Allocating large temporary arrays in a loopLOH churn, Gen 2 collections, and fragmentationRent buffers from ArrayPool or reuse them
Caching objects in a static collection with no evictionMemory grows until the process fails (a "leak")Bound the cache, use MemoryCache with limits, or expire entries
Practice
  1. Write a loop that allocates short-lived small objects and another that allocates 100 KB arrays. Print GC.CollectionCount for each generation before and after.
  2. Process a stream in 1 MB chunks, first allocating a new array per chunk and then using ArrayPool. Compare Gen 2 counts.
Key takeaways
  • Most objects die young, so the heap is generational, and Gen 2 and LOH collections are the expensive ones.
  • Server GC and concurrent GC trade memory and latency, so choose per workload.
  • Reducing allocations (pooling, spans, avoiding hidden allocations) beats tuning the collector.
