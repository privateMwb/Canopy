Span<T>, Memory<T> & ref structs

Span<T> is a view over a contiguous region of memory, so you can slice and parse without copying or allocating.

§1Slicing Without Allocating

string line = "2026-10-23,Ada,42";

// Allocating version: three new strings
var parts = line.Split(',');
int age = int.Parse(parts[2]);

// Span version: no allocation at all
ReadOnlySpan<char> span = line.AsSpan();
int c1 = span.IndexOf(',');
ReadOnlySpan<char> rest = span[(c1 + 1)..];
int c2 = rest.IndexOf(',');
int age2 = int.Parse(rest[(c2 + 1)..]);       // parse directly from a slice

Span<int> window = stackalloc int[16];        // memory on the stack, no heap allocation
byte[] data = new byte[100];
Span<byte> header = data.AsSpan(0, 4);        // a view of the first 4 bytes: no copy
header[0] = 0xFF;                             // writes through to data

A Span<T> is a pointer plus a length. Slicing creates a new view over the same memory, so it costs nothing. It works over arrays, strings (read-only), stack memory, and native memory, and the BCL has span overloads for parsing, searching, and I/O (int.Parse(ReadOnlySpan<char>), Stream.Read(Span<byte>)).

§2ref structs and Their Rules

Span<T> is a ref struct, a type that can only live on the stack. That restriction is what makes it safe, because a span might point at stack memory that vanishes when the method returns. The compiler enforces the rules:

  • It can't be a field of a normal class or struct, and can't be boxed.
  • It can't be used in async methods across an await, in iterators across a yield, or captured by a lambda.
  • A method can't return a span that points into a local stack buffer (escape analysis rejects it).
// Compile error: the span would outlive the memory it points to
Span<int> Bad() { Span<int> s = stackalloc int[4]; return s; }

§3Memory and When to Use Which

async Task ProcessAsync(Stream input)
{
    Memory<byte> buffer = new byte[4096];       // heap-friendly, can cross await
    int n = await input.ReadAsync(buffer);
    Parse(buffer.Span[..n]);                    // use .Span for synchronous work
}
TypeLives onUse it for
Span<T> / ReadOnlySpan<T>Stack onlySynchronous parsing, slicing, hot paths
Memory<T> / ReadOnlyMemory<T>Anywhere (a normal struct)Async code, storing buffers in fields
stackallocStackSmall, short-lived scratch buffers (keep them modest, a few KB)

Use Memory<T> where a span can't be held (fields, async), and call .Span inside the method to do the synchronous work. Don't stackalloc large or unbounded sizes: stack space is small, and overflow crashes the process.

The key insight A span is a window, not a copy. Slicing is free because nothing moves, and the ref-struct rules exist so that the window can never outlive the memory behind it.

§4Common Mistakes

Assuming a slice is a copyWrites through the span change the original dataCall ToArray() when you need an independent copy
Practice
  1. Parse a CSV line of the form name,age,score into a struct using spans only, and verify with an allocation counter (GC.GetAllocatedBytesForCurrentThread) that it allocates nothing.
  2. Write an async method that reads a stream in chunks into a Memory<byte> and processes each chunk with a span.
Key takeaways
  • Span<T> slices and parses memory with zero allocation and zero copy.
  • As a ref struct, it stays on the stack: no fields, no await crossings, no escaping locals.
  • Use Memory<T> where spans can't go, and keep stackalloc small and bounded.
