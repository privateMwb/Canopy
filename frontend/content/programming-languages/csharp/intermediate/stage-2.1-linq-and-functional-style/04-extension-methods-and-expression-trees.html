Extension Methods & Expression Trees

Extension methods add behavior to existing types without modifying them, and expression trees represent code as data so libraries can translate it.

§1Extension Methods

public static class StringExtensions
{
    public static bool IsBlank(this string? s) => string.IsNullOrWhiteSpace(s);

    public static string Truncate(this string s, int max) =>
        s.Length <= max ? s : s[..max] + "…";
}

if (name.IsBlank()) { }
var shortTitle = title.Truncate(20); // reads like an instance method

An extension method is a static method in a static class whose first parameter has this. The compiler lets you call it with instance syntax. It's resolved at compile time, can't access private members, and an actual instance method with the same name always wins. This is how every LINQ operator is defined, as extensions on IEnumerable<T>.

§2Writing Good Extensions

public static IEnumerable<T> WhereNotNull<T>(this IEnumerable<T?> source) where T : class =>
    source.Where(x => x is not null)!;

public static IEnumerable<TResult> SelectIndexed<T, TResult>(
    this IEnumerable<T> source, Func<T, int, TResult> selector) =>
    source.Select(selector);
  • Put them in a clearly named namespace; they only appear when the namespace is imported.
  • Keep them generic and focused, and prefer extending the narrowest useful interface.
  • Don't extend object or a broad type with something relevant to few uses, since it clutters IntelliSense everywhere.
  • If the behavior belongs to a type you own, make it a real member instead.

§3Expression Trees

Func<int, bool> func = x => x > 5;                 // compiled delegate: opaque
Expression<Func<int, bool>> expr = x => x > 5;       // data structure: inspectable

var body = (BinaryExpression)expr.Body;
Console.WriteLine(body.NodeType);   // GreaterThan
Console.WriteLine(body.Left);       // x
Console.WriteLine(body.Right);      // 5

var compiled = expr.Compile();      // turn it into a delegate when you want to run it
Console.WriteLine(compiled(10));    // True

When a lambda is assigned to Expression<T>, the compiler doesn't produce executable code but a tree of objects describing it. That's how EF Core turns Where(o => o.Total > 100) into SQL: it walks the tree. Only a subset of C# is allowed inside an expression tree (no statement bodies), and a provider can only translate what it understands, which is why calling your own method inside an EF query can fail.

The key insight Func<T> is code you can run; Expression<Func<T>> is code you can read. The second is what lets a query be translated to another language such as SQL.

§4Common Mistakes

MistakeWhat HappensFix
Extension method on a very general type, such as object, for a niche helperEvery variable shows irrelevant membersConstrain it to the specific type or interface
Calling a local C# method inside an EF query expressionThe query can't be translated, or it runs client-sideUse translatable operators or move the work after ToList()
Compiling expression trees repeatedly in a hot pathCompilation is expensiveCompile once and cache the delegate
Practice
  1. Write an extension IsBetween<T>(this T value, T low, T high) where T : IComparable<T> and test it with ints and dates.
  2. Print the node types and parts of the expression (int a, int b) => a * b + 1 by walking the tree.
Key takeaways
  • Extension methods are static helpers called with instance syntax; LINQ is built from them.
  • Keep extensions focused, and put them in a namespace people import deliberately.
  • Expression trees represent code as data so providers like EF Core can translate it.
