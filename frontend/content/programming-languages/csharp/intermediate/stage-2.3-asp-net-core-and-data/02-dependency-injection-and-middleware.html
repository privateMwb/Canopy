Dependency Injection & Middleware

ASP.NET Core builds on two ideas: a built-in container that supplies dependencies, and a pipeline of middleware that every request flows through.

§1Dependency Injection and Lifetimes

builder.Services.AddSingleton<IClock, SystemClock>();          // one for the whole app
builder.Services.AddScoped<IOrderService, OrderService>();        // one per HTTP request
builder.Services.AddTransient<IEmailBuilder, EmailBuilder>();     // new each time
builder.Services.AddDbContext<ShopDb>(o => o.UseSqlite("Data Source=shop.db"));   // scoped

public class OrderService : IOrderService
{
    private readonly ShopDb _db; private readonly IClock _clock;
    public OrderService(ShopDb db, IClock clock) { _db = db; _clock = clock; }   // injected
}

app.MapGet("/orders", (IOrderService svc) => svc.ListAsync());      // injected into a handler

You register an interface with an implementation, and the container creates objects and passes them to constructors. The lifetime controls how long an instance lives: singleton (app-wide, must be thread-safe), scoped (per request), and transient (every resolution). A longer-lived service must not depend on a shorter-lived one. A singleton that takes a scoped DbContext keeps it forever (the framework detects this in development and throws).

§2The Request Pipeline

var app = builder.Build();

app.UseExceptionHandler("/error");   // outermost: catches everything below
app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();                  // endpoint: handles the request
app.Run();

A request passes through middleware components in the order you add them, then back out in reverse. Each can act before and after the next one, or short-circuit and respond itself. Order matters: UseAuthentication must come before UseAuthorization, and an exception handler should be first so it can see everything after it.

§3Writing Middleware

app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();
    context.Response.OnStarting(() =>            // headers must be set before the body starts
    {
        context.Response.Headers["X-Elapsed-Ms"] = sw.ElapsedMilliseconds.ToString();
        return Task.CompletedTask;
    });
    await next(context);                         // run the rest of the pipeline
});

public class RequestIdMiddleware
{
    private readonly RequestDelegate _next;
    public RequestIdMiddleware(RequestDelegate next) => _next = next;

    public async Task InvokeAsync(HttpContext ctx, ILogger<RequestIdMiddleware> log)
    {
        var id = ctx.Request.Headers["X-Request-Id"].FirstOrDefault() ?? Guid.NewGuid().ToString("n");
        ctx.Response.Headers["X-Request-Id"] = id;
        using (log.BeginScope(new Dictionary<string, object> { ["RequestId"] = id }))
            await _next(ctx);
    }
}

app.UseMiddleware<RequestIdMiddleware>();

Middleware is the right place for cross-cutting concerns that apply to every request: logging, correlation IDs, error handling, and security headers. Per-request services can be taken as InvokeAsync parameters, so the middleware itself, which is created once, never holds scoped state. Headers can't be changed after the response body has started.

The key insight Dependencies are asked for in constructors, not created with new. That single habit is what makes code swappable, testable, and configurable.

§4Common Mistakes

MistakeWhat HappensFix
Injecting a scoped service into a singleton (a captive dependency)Stale data, or thread-safety bugs with DbContextMatch lifetimes, or create a scope with IServiceScopeFactory
Putting middleware in the wrong orderAuthorization runs before authentication, or errors escape the handlerFollow the documented order; exception handling first
Using the service locator (GetService) inside business classesHidden dependencies that tests can't seeTake dependencies through the constructor
Practice
  1. Register one service with each lifetime, inject all three into an endpoint, and return their instance IDs across several requests to see which change.
  2. Write middleware that logs method, path, status, and elapsed time for each request.
Key takeaways
  • Register services with the right lifetime (singleton, scoped, or transient) and receive them through constructors.
  • Middleware forms an ordered pipeline; order determines behavior.
  • Use middleware for cross-cutting concerns, and never let a long-lived service capture a short-lived one.
