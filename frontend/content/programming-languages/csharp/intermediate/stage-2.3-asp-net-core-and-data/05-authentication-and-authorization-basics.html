Authentication & Authorization Basics

Authentication answers who are you? and authorization answers what may you do?. ASP.NET Core separates the two, and mixing them up leads to security holes.

§1Authentication with JWT Bearer Tokens

In a typical API, a client logs in with an identity provider, receives a JSON Web Token (JWT), and sends it on each request: Authorization: Bearer <token>. The token is a signed set of claims (subject, roles, expiry). The server verifies the signature and expiry without a database lookup, and builds a ClaimsPrincipal from the claims.

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.Authority = builder.Configuration["Auth:Authority"];   // issuer that signs the tokens
        o.Audience  = builder.Configuration["Auth:Audience"];    // this API
        // validates signature, issuer, audience, and lifetime by default
    });
builder.Services.AddAuthorization();

app.UseAuthentication();    // who are you?
app.UseAuthorization();     // are you allowed?

Use an established identity provider (Entra ID, Auth0, Keycloak, or ASP.NET Core Identity with a token issuer) rather than writing login, password storage, and token signing yourself. A JWT is signed, not encrypted: anyone can read its contents, so don't put secrets in it.

§2Protecting Endpoints

app.MapGet("/public", () => "anyone");
app.MapGet("/me", (ClaimsPrincipal user) => user.Identity!.Name).RequireAuthorization();
app.MapDelete("/orders/{id}", (int id) => Results.NoContent())
   .RequireAuthorization("AdminOnly");

[Authorize]                        // controller-level: require a signed-in user
public class OrdersController : ControllerBase
{
    [AllowAnonymous] [HttpGet("ping")] public IActionResult Ping() => Ok();
    [Authorize(Roles = "Admin")] [HttpDelete("{id}")] public IActionResult Delete(int id) => NoContent();
}

An endpoint without RequireAuthorization or [Authorize] is public. For a safer default, set a fallback policy that requires authentication everywhere, and opt out explicitly with AllowAnonymous. A missing or invalid token returns 401 Unauthorized, and an authenticated user lacking permission gets 403 Forbidden.

§3Policies and Resource Checks

builder.Services.AddAuthorizationBuilder()
    .AddPolicy("AdminOnly", p => p.RequireRole("Admin"))
    .AddPolicy("CanRefund", p => p.RequireClaim("permission", "refund"))
    .SetFallbackPolicy(new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build());

// Resource-based check: is THIS user allowed to touch THIS order?
app.MapGet("/orders/{id:int}", async (int id, ClaimsPrincipal user, ShopDb db) =>
{
    var order = await db.Orders.FindAsync(id);
    if (order is null) return Results.NotFound();
    var userId = user.FindFirstValue(ClaimTypes.NameIdentifier);
    return order.OwnerId == userId ? Results.Ok(order) : Results.Forbid();
}).RequireAuthorization();

Policies name an authorization rule so endpoints say what they require, not how it's computed. But role and policy checks only cover "what kind of user," and the common vulnerability is a missing ownership check: user A requesting user B's order by changing the id. Always verify that the caller may access the specific resource.

The key insight Authentication proves identity; authorization decides access. Securing the route isn't enough, because you must also check that this user may access this record.

§4Common Mistakes

MistakeWhat HappensFix
Using [Authorize] on some endpoints and forgetting othersUnprotected dataSet a fallback policy requiring authentication and opt out explicitly
Skipping ownership checks (IDOR)Users read or modify each other's data by changing an idVerify the resource belongs to the caller on every access
Putting sensitive data in a JWT payloadThe token is only signed, so anyone can decode itKeep tokens small and non-sensitive; look up sensitive data server-side
Practice
  1. Add JWT bearer authentication with a test issuer, protect one endpoint, and call it with and without a token. Note the 401.
  2. Add an /orders/{id} endpoint that returns 403 when the order belongs to someone else, and write a test for it.
Key takeaways
  • Authentication establishes identity (JWT claims); authorization decides what that identity may do.
  • Require authentication by default with a fallback policy, and use named policies for rules.
  • Always add resource-level ownership checks, because 401 is not logged in, and 403 is not allowed.
