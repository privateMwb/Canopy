Threads, Locks & Concurrent Collections

When several threads touch the same data, unsynchronized access produces wrong answers that appear only occasionally. Choose the simplest tool that makes access safe.

§1The Race Condition

int counter = 0;
Parallel.For(0, 100_000, _ => counter++);   // counter++ is read, add, write: NOT atomic
Console.WriteLine(counter);                 // often less than 100000

Two threads can read the same value, both add one, and both write the same result, so one update is lost. The result changes from run to run, which makes these bugs hard to reproduce. Any data that is shared and mutable needs protection, or must stop being shared or mutable.

§2lock, Interlocked, and SemaphoreSlim

private readonly object _gate = new();   // or System.Threading.Lock in newer .NET
private int _count;

public void Increment()
{
    lock (_gate) { _count++; }               // one thread at a time
}

Interlocked.Increment(ref _count);           // atomic single operation, no lock needed

private readonly SemaphoreSlim _limit = new(3);   // at most 3 concurrent
await _limit.WaitAsync();
try { await CallApiAsync(); }
finally { _limit.Release(); }
  • lock gives mutual exclusion: keep the locked region short, and never call unknown code or await inside it.
  • Interlocked handles simple atomic updates of a single variable.
  • SemaphoreSlim limits concurrency to N and, unlike lock, has an async WaitAsync.
  • Lock on a private object, never on this, a string, or a Type, because outside code could lock on it too.

§3Concurrent Collections and Designing for Safety

var cache = new ConcurrentDictionary<string, int>();
cache.AddOrUpdate("hits", 1, (_, old) => old + 1);          // atomic add-or-update
int v = cache.GetOrAdd("key", k => ExpensiveCompute(k));      // factory may run more than once

var queue = new ConcurrentQueue<string>();
queue.Enqueue("job");
if (queue.TryDequeue(out var job)) Handle(job);

The collections in System.Collections.Concurrent are safe for concurrent use, but safe operations aren't safe sequences: if (!d.ContainsKey(k)) d[k] = v still races, so use the atomic methods like GetOrAdd. Better yet, design for safety:

  • Don't share: give each task its own data and combine results afterward.
  • Share immutable data: it needs no locks.
  • Confine mutation to one owner, such as a single consumer reading from a channel.
The key insight Locks fix a race by making threads wait, which costs throughput and risks deadlock. The best synchronization is the code you don't need because the data isn't shared or isn't mutable.

§4Common Mistakes

MistakeWhat HappensFix
Check-then-act on a concurrent dictionary (ContainsKey then add)Another thread slips in between, causing duplicates or exceptionsUse GetOrAdd, AddOrUpdate, or TryAdd
Locking on this or a public objectOutside code can lock it and deadlock youLock on a private, dedicated object
Acquiring two locks in different orders in different placesDeadlockAlways take locks in one consistent order, or avoid nesting
Practice
  1. Reproduce the lost-update race with Parallel.For and fix it three ways: lock, Interlocked, and per-thread local sums combined at the end.
  2. Use ConcurrentDictionary to count word frequencies across several threads, and check the total against a single-threaded run.
Key takeaways
  • Shared mutable data needs synchronization; counter++ is not atomic.
  • Use lock for short critical sections, Interlocked for single counters, and SemaphoreSlim to limit concurrency or lock around await.
  • Prefer not sharing or sharing immutable data, and use atomic methods on concurrent collections.
