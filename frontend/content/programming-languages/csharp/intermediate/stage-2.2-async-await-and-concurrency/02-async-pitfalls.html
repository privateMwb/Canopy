Async Pitfalls

Async code fails in a few characteristic ways, and recognizing them quickly saves hours of confusing hangs and lost exceptions.

§1Don't Block on Async Code

// Sync-over-async: blocks the calling thread until the task finishes
var data = LoadAsync().Result;
LoadAsync().Wait();
var data2 = LoadAsync().GetAwaiter().GetResult();

Blocking on a task can deadlock in an app that has a synchronization context (classic ASP.NET, WinForms, WPF). The caller thread blocks waiting for the task, but the task's continuation needs that same thread to finish, so neither can proceed. ASP.NET Core has no such context, so the same code won't deadlock there, but it still ties up a thread and, under load, starves the thread pool. The fix is to be async all the way up: await instead of .Result, and make the caller async too.

§2ConfigureAwait and async void

// In library code: don't resume on the captured context
var bytes = await stream.ReadAsync(buffer).ConfigureAwait(false);

By default, await captures the current synchronization context and resumes on it. In library code, ConfigureAwait(false) opts out, which avoids the deadlock above and a little overhead. In application code that needs the UI thread afterward (WPF, WinForms, MAUI), keep the default. ASP.NET Core application code doesn't need it.

async void Button_Click(object? s, EventArgs e)   // OK: event handler
{
    await SaveAsync();
}

async void DoWork()   // BAD: caller can't await it or catch its exceptions
{
    await Task.Delay(100);
    throw new InvalidOperationException();   // crashes the process
}

async void can't be awaited, and an exception thrown in it is raised on the context directly, so it can take down the process. Use it only for event handlers. Everything else returns Task.

§3More Ways to Go Wrong

  • Fire and forget: calling an async method without awaiting hides its exceptions. If you truly want background work, run it deliberately with error handling, or use a hosted background service.
  • lock and await: you can't await inside a lock block. Use SemaphoreSlim.WaitAsync() instead.
  • Unnecessary async: if a method just returns another task, return task; avoids a state machine. But keep async/await if there's a using or try around the call, or the resource is disposed too early.
  • Shared mutable state: tasks that run concurrently can interleave at every await, so protect shared data.
private readonly SemaphoreSlim _gate = new(1, 1);

async Task UpdateAsync()
{
    await _gate.WaitAsync();
    try { await SaveAsync(); }
    finally { _gate.Release(); }
}
The key insight Go async all the way. The moment you block on a task with .Result or .Wait() you give up async's benefits and invite deadlocks and thread starvation.

§4Common Mistakes

MistakeWhat HappensFix
.Result or .Wait() on a TaskDeadlocks with a sync context; blocked threads elsewhereMake the whole chain async and await
async void for non-event-handler methodsUnobservable exceptions that crash the processReturn Task instead
return await inside using omitted (returning the task directly)The resource is disposed before the work completesKeep await when a using or try scope surrounds the call
Practice
  1. Reproduce a deadlock in a small WinForms or console app with a custom single-threaded context, or explain on paper why .Result hangs there.
  2. Convert a method using async void and .Wait() calls into one that returns Task end to end.
Key takeaways
  • Never block on async code with .Result or .Wait(), because it can deadlock or starve the thread pool.
  • async void is only for event handlers; use Task everywhere else.
  • ConfigureAwait(false) belongs in library code, and SemaphoreSlim replaces lock around awaits.
