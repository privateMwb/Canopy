Nullable Reference Types

With nullable reference types enabled, the type itself says whether null is allowed, and the compiler warns when you break that promise.

§1The Problem and the Annotation

A NullReferenceException happens when you use a reference that is null. With <Nullable>enable</Nullable> in the project, reference types are treated as non-nullable by default, and you add ? to say null is a legitimate value.

string name = "Ada";      // must never be null
string? nickname = null;  // may be null

name = null;              // warning CS8600: converting null to non-nullable
int len = nickname.Length; // warning CS8602: possible null dereference

This is a compile-time analysis, not a runtime guarantee. It produces warnings and doesn't change how your code runs. That's why a clean build with no nullable warnings is the real goal.

§2Handling Null Properly

// 1. Check
if (nickname is not null) Console.WriteLine(nickname.Length);

// 2. Null-conditional and null-coalescing
int? len = nickname?.Length;            // null if nickname is null
string display = nickname ?? "(none)";   // fallback value
nickname ??= "guest";                    // assign only if null

// 3. Reject early
ArgumentNullException.ThrowIfNull(input);

After a null check, the compiler's flow analysis knows the variable is non-null in that branch, so there's no warning. Library methods can carry this knowledge with attributes, for example string.IsNullOrEmpty and int.TryParse's [NotNullWhen(true)].

§3Fields, Properties, and the Bang Operator

Non-nullable fields and properties must be assigned by the end of the constructor, or the compiler warns. The required modifier makes callers set a member during initialization:

class User
{
    public required string Name { get; init; }  // callers must provide it
    public string? Nickname { get; init; }      // optional
}

var u = new User { Name = "Ada" };

The null-forgiving operator ! silences a warning without adding a check: value!.Length. It means "I know better than the compiler," so every use is a promise you must be able to defend. Use it sparingly, and never to make warnings disappear in bulk.

The key insight Nullability is part of the contract of every method and property. Prefer making the type non-nullable and rejecting bad input at the boundary, instead of checking for null everywhere inside.

§4Common Mistakes

MistakeWhat HappensFix
Sprinkling ! to clear warningsThe warning is gone but the NullReferenceException remainsFix the cause: check, default, or change the type to T?
Disabling nullable warnings project-wideNull bugs return silentlyKeep <Nullable>enable</Nullable> and consider TreatWarningsAsErrors
Assuming string? is a different runtime typeConfusion about reflection and genericsRemember it's an annotation: at run time it's still string
Practice
  1. Turn on nullable warnings in a small project, write a method that takes a string? and returns its trimmed length, and make it warning-free using ?. and ??.
  2. Create a class with one required and one optional property. Try to instantiate it without the required one and read the error.
Key takeaways
  • With nullable enabled, plain reference types are non-null and T? means null is allowed.
  • The analysis gives warnings at compile time; handle them with checks, ?., ??, or by tightening the type.
  • The ! operator silences the compiler without protecting you, so use it rarely and deliberately.
