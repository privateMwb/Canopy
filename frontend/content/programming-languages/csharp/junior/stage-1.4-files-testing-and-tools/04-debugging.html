Debugging

Debugging is a method, not guesswork: reproduce the problem, form a hypothesis, and use the debugger to test it.

§1Breakpoints and Stepping

Click in the margin (or press F9) to set a breakpoint, then start with the debugger (F5). Execution pauses on that line before it runs, and you can inspect every variable in scope.

ActionShortcut (VS / VS Code)Use it to
Step OverF10Run this line, skip into called methods
Step IntoF11Enter the method being called
Step OutShift+F11Finish this method and return to the caller
ContinueF5Run to the next breakpoint

Step over by default, and step into only when you suspect that exact call.

§2Watches, Conditions, and Logpoints

  • Locals, Autos, and Watch: hover a variable or add an expression such as orders.Count(o => o.Total > 100) to the Watch window to evaluate it at the paused point.
  • Conditional breakpoint: right-click a breakpoint and add a condition such as customerId == 42, so it only stops on the bad case instead of 10,000 times.
  • Hit count: stop on the 500th pass of a loop.
  • Logpoint: print a message when the line is reached without pausing and without editing code.
  • Call Stack: shows how you got here, and you can click any frame to see its variables.
// Temporary diagnostics that disappear in release builds
Debug.Assert(total >= 0, "Total should never be negative");
Debug.WriteLine($"Processing order {order.Id}");

§3Reading Exceptions

An unhandled exception prints a stack trace: the chain of calls, newest first. Read it like this:

  • Read the exception type and message first; they usually name the problem.
  • Find the first frame that points into your code, with a file and line number. Frames from the framework below it are how it got there.
  • Check InnerException: wrapped exceptions hold the original cause.
  • Turn on break when exception is thrown in the IDE's exception settings to stop at the exact line, with all variables still alive.

Debug with a hypothesis: "I think discount is null here." Set the breakpoint, check, and either confirm or cross it off. Changing code at random is the opposite of debugging.

The key insight The cheapest bug to fix is the one you can reproduce on demand. Write a failing test that captures the bug before you start stepping through, then it also protects you from regressions.

§4Common Mistakes

MistakeWhat HappensFix
Stepping through every line from the startHours spent in code that worksPlace a breakpoint near the symptom and work backward using the call stack
Debugging a Release build and finding variables "optimized out"Misleading values and skipped linesDebug with the Debug configuration
Fixing the symptom, such as adding a null check, without finding why it was nullThe real bug moves somewhere elseTrace back to where the bad value originated
Practice
  1. Write a loop that processes 1,000 items with one bad value. Use a conditional breakpoint to stop only on that item and inspect it.
  2. Throw an exception wrapped in another (set innerException), let it go unhandled, and practice reading the trace to find your code's line.
Key takeaways
  • Breakpoints, stepping, and the call stack let you inspect the program's real state.
  • Conditional breakpoints, hit counts, and logpoints save you from stopping thousands of times.
  • Read exception type, message, first frame in your code, and the inner exception, and test hypotheses.
