Unit Testing with xUnit

Automated tests let you change code with confidence, and xUnit makes writing and running them a one-command habit.

§1Your First Tests

dotnet new xunit -o tests/Bookshop.Tests
dotnet add tests/Bookshop.Tests reference src/Bookshop.Core
dotnet sln add tests/Bookshop.Tests
dotnet test
public class PriceCalculatorTests
{
    [Fact]
    public void ApplyDiscount_TenPercent_ReducesPrice()
    {
        // Arrange
        var calc = new PriceCalculator();
        // Act
        var result = calc.ApplyDiscount(200m, 10m);
        // Assert
        Assert.Equal(180m, result);
    }

    [Fact]
    public void ApplyDiscount_NegativePrice_Throws()
    {
        var calc = new PriceCalculator();
        Assert.Throws<ArgumentOutOfRangeException>(() => calc.ApplyDiscount(-1m, 10m));
    }
}

A [Fact] is one test. Follow Arrange, Act, Assert, and name tests after the behavior: Method_Scenario_Expected. Each test should check one thing and be independent of the others.

§2Theories for Parameterized Cases

[Theory]
[InlineData(100, 0, 100)]
[InlineData(100, 25, 75)]
[InlineData(100, 100, 0)]
public void ApplyDiscount_ReturnsExpected(decimal price, decimal pct, decimal expected)
{
    Assert.Equal(expected, new PriceCalculator().ApplyDiscount(price, pct));
}

A [Theory] runs the same test body once per [InlineData] row, and each row is reported separately. Use [MemberData] for larger or computed data sets. Add a case only when it exercises a genuinely different path, such as a boundary or an error.

§3Assertions and Organization

Assert.Equal(expected, actual);
Assert.True(list.Contains(5));
Assert.Contains("error", message);
Assert.Empty(results);
Assert.Null(user.Nickname);
Assert.Equal(1.5, value, precision: 3);   // floating-point tolerance
  • xUnit creates a new instance of the test class for each test, so instance fields don't leak state between tests. Use the constructor for setup and IDisposable for cleanup.
  • Mirror your source layout: PriceCalculator is tested by PriceCalculatorTests.
  • Tests must be deterministic: no reliance on the clock, random numbers, network, or test order. Pass those in as parameters or interfaces.
The key insight A good test fails for exactly one reason and tells you what broke from its name alone. If you have to read the test body to understand the failure, rename it or split it.

§4Common Mistakes

MistakeWhat HappensFix
Tests that depend on each other or on execution orderRandom failures and hard-to-debug runsMake each test arrange its own state
Asserting several unrelated things in one testThe first failure hides the rest, and the name is vagueSplit into separate focused tests or a theory
Copy-pasting near-identical testsA change means editing many placesUse [Theory] with inline data
Practice
  1. Write a Fact and a Theory for a Slugify(string) method, including an empty string and punctuation.
  2. Break the code on purpose and confirm the right test fails, with a name that explains why.
Key takeaways
  • [Fact] is one test and [Theory] with [InlineData] is many cases for one body.
  • Arrange, Act, Assert, with behavior-based names, keeps tests readable.
  • Tests should be independent and deterministic; xUnit gives each test a fresh class instance.
