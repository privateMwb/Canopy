Web Performance Basics

Performance is measured by what users experience — how fast content appears, how soon the page responds, and how stable it looks — and you should measure before you optimize.

§1Core Web Vitals

Google's Core Web Vitals are three user-centered metrics. Check them against real-user data (field data) where possible, because lab tests on your fast laptop mislead.

  • LCP (Largest Contentful Paint): when the main content appears. Good: ≤ 2.5 s.
  • INP (Interaction to Next Paint): how quickly the page responds to input. Good: ≤ 200 ms.
  • CLS (Cumulative Layout Shift): how much the layout jumps around. Good: ≤ 0.1.
new PerformanceObserver((list) => {
  const last = list.getEntries().at(-1);
  console.log("LCP:", Math.round(last.startTime), "ms", last.element);
}).observe({ type: "largest-contentful-paint", buffered: true });

§2Loading Strategy

The fastest byte is the one you don't send. Ship less JavaScript, load it later, and tell the browser what matters most. Give images dimensions so the layout doesn't shift, and lazy-load what's below the fold.

<script type="module" src="/app.js"></script>           <!-- modules defer by default -->
<link rel="preload" href="/hero.avif" as="image">       <!-- fetch the LCP image early -->

<img src="/hero.avif" width="1200" height="600" alt="..." fetchpriority="high">
<img src="/gallery-1.avif" width="400" height="300" alt="..." loading="lazy" decoding="async">

const Chart = await import("./chart.js");               // load heavy code on demand

Serve modern image formats (AVIF/WebP), compress text with gzip or brotli, and set long cache headers on hashed asset filenames.

Measure first Open Lighthouse or the Performance panel *before* changing anything. Guessing leads to optimizing things that were never slow. Fix the biggest measured problem, then measure again.

§3Common Mistakes

MistakeWhat HappensFix
Images without width and heightLayout shifts as they load (bad CLS)Set dimensions or an aspect-ratio
Shipping one large JS bundle for every routeSlow load and long parse timeSplit by route and lazy-load heavy features
Optimizing without measuringEffort spent in the wrong placeProfile first; fix the largest bottleneck
Practice
  1. Run Lighthouse on a page, record LCP, INP/TBT, and CLS, then fix the single largest issue and re-run.
  2. Add loading="lazy", dimensions, and fetchpriority="high" to the right images on a page and show the before/after in the Network panel.
Key takeaways
  • Track LCP, INP, and CLS — preferably with real-user data.
  • Send less, load later: code splitting, lazy images, compression, and caching.
  • Measure, change one thing, and measure again.
