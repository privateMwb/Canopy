Blocking the Main Thread

The browser's main thread runs your JavaScript, handles input, and paints — so any task over about 50 ms makes the page feel broken.

§1Long Tasks

The browser aims to paint every ~16 ms (60 fps). While your script is running, it can't paint or respond. A long task is any task over 50 ms; long tasks cause janky scrolling and delayed taps (poor Interaction to Next Paint).

button.addEventListener("click", () => {
  // 400 ms of synchronous work: the button doesn't even show a pressed state
  const result = heavyCompute(bigArray);
  output.textContent = result;
});

// Find long tasks in the wild
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) console.warn("long task", Math.round(e.duration), "ms");
}).observe({ entryTypes: ["longtask"] });

§2Chunking Work

Break big jobs into small slices and yield between them so the browser can handle input and paint. await new Promise(r => setTimeout(r)) yields to the task queue; scheduler.yield() (where supported) does it with better priority.

const yieldToMain = () =>
  globalThis.scheduler?.yield?.() ?? new Promise((r) => setTimeout(r));

async function processAll(items) {
  let last = performance.now();
  for (const item of items) {
    process(item);
    if (performance.now() - last > 12) {   // stay under a frame
      await yieldToMain();
      last = performance.now();
    }
  }
}

§3requestAnimationFrame

requestAnimationFrame(cb) runs the callback right before the next paint — the correct place for visual updates. Use it instead of setInterval for animation, and avoid forcing layout by mixing DOM reads and writes.

function animate(t) {
  box.style.transform = `translateX(${(t / 10) % 300}px)`;   // transform: cheap
  requestAnimationFrame(animate);
}
requestAnimationFrame(animate);

// Layout thrashing: each read forces a layout flush after the previous write
for (const el of els) { el.style.width = el.offsetWidth + 10 + "px"; }      // slow
const widths = els.map((el) => el.offsetWidth);                              // batch reads
els.forEach((el, i) => { el.style.width = widths[i] + 10 + "px"; });         // then writes

When the work is pure computation with no DOM access, the best fix isn't chunking at all — move it to a Web Worker (next lesson).

The 50 ms budget Aim for tasks under 50 ms and handlers that return within a frame. Measure first: the Performance panel marks long tasks in red so you can see which function is responsible.

§4Common Mistakes

MistakeWhat HappensFix
Running a big loop inside a click handlerUI freezes until it finishesChunk with yields, or use a Web Worker
Animating with setInterval and left/topJanky, causes layout every tickUse requestAnimationFrame with transform
Interleaving DOM reads and writes in a loopLayout thrashing — repeated forced reflowsBatch all reads, then all writes
Practice
  1. Create a button that runs a 500 ms loop and record it in the Performance panel; then rewrite it with chunking and compare.
  2. Animate a box across the screen using requestAnimationFrame and transform, then confirm it stays smooth in the Performance panel.
Key takeaways
  • Anything over ~50 ms on the main thread hurts responsiveness.
  • Yield between chunks (scheduler.yield or a timer) so input and paint can run.
  • Use requestAnimationFrame for visuals and batch DOM reads before writes.
