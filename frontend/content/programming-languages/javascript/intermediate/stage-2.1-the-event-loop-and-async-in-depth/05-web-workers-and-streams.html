Web Workers & Streams

Workers run JavaScript on another thread so heavy computation doesn't block the UI, and streams let you process data as it arrives instead of waiting for all of it.

§1Web Workers

A worker is a separate thread with its own event loop. It cannot touch the DOM. You communicate with postMessage, and data is copied (structured clone) unless you transfer it.

// main.js
const worker = new Worker(new URL("./hash-worker.js", import.meta.url), { type: "module" });
worker.postMessage({ file: bigText });
worker.onmessage = (e) => console.log("hash:", e.data);
worker.onerror = (e) => console.error(e.message);

// hash-worker.js
self.onmessage = (e) => {
  const result = expensiveHash(e.data.file);   // runs off the main thread
  self.postMessage(result);
};

§2Transferring Data

Copying a 50 MB buffer on every message is slow. Transferable objects such as ArrayBuffer move to the other thread with zero copy — the sender loses access to it.

const buffer = new ArrayBuffer(50 * 1024 * 1024);
worker.postMessage({ buffer }, [buffer]);      // transfer, don't copy
console.log(buffer.byteLength);                // 0 — it's gone from this thread

// Workers cost memory and startup time: use a few long-lived ones,
// not a new worker per tiny job. Terminate with worker.terminate().

§3Streams

A ReadableStream hands you data in chunks, so memory stays small and processing can begin immediately. fetch response bodies are streams, and you can pipe them through transforms.

const res = await fetch("/big-log.txt");

const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();
let lines = 0;
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  lines += value.split("\n").length - 1;     // process one chunk at a time
}

// Or compose with pipeThrough / pipeTo
await res.body
  .pipeThrough(new DecompressionStream("gzip"))
  .pipeTo(new WritableStream({ write(chunk) { sink(chunk); } }));

Streams support backpressure: a slow consumer signals the producer to pause, so a fast source can't flood memory. Senior-level lessons return to this.

When to use which Workers are for CPU-bound work (parsing, hashing, image processing). Streams are for large or incremental data. Network-bound work doesn't need a worker — await already doesn't block.

§4Common Mistakes

MistakeWhat HappensFix
Trying to use document or window in a workerReferenceErrorDo only computation in the worker; post results back
Posting huge objects repeatedlyStructured-clone copying dominates the costTransfer ArrayBuffers or send less data
Creating a new worker for every small taskStartup overhead exceeds the savingsReuse a small pool of workers
Practice
  1. Move a CPU-heavy function (like computing primes up to 5 million) into a worker and show the UI staying responsive with a running counter.
  2. Fetch a large text file and count its lines using a stream reader, without ever holding the whole file as one string.
Key takeaways
  • Workers run on separate threads, can't touch the DOM, and communicate by postMessage.
  • Transfer large buffers instead of copying them; reuse a few workers.
  • Streams process data chunk by chunk with backpressure, keeping memory low.
