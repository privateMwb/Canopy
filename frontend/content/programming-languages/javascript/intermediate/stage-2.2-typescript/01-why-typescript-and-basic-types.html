Why TypeScript & Basic Types

TypeScript adds a static type checker on top of JavaScript: it finds a whole class of bugs before you run the code, then erases itself at compile time.

§1What Types Catch (and Don't)

TypeScript analyzes your code without running it and reports mismatches: calling a function with the wrong argument, reading a property that doesn't exist, forgetting a null case. It does not check data that arrives at runtime — an API response is whatever the server sends, whatever you annotated.

function area(r: number): number {
  return Math.PI * r * r;
}
area("3");          // Error: Argument of type 'string' is not assignable to 'number'

const user = { name: "Ana" };
user.nmae;          // Error: Property 'nmae' does not exist — typo caught

const data = JSON.parse(text) as { id: number };   // a promise, not a check!

§2Basic Types and Inference

You rarely need to write types everywhere. TypeScript infers them from values. Annotate function parameters and public boundaries; let inference handle local variables.

const n = 5;                       // inferred: number
let name = "Ana";                  // inferred: string
const flags: boolean[] = [true, false];
const pair: [string, number] = ["a", 1];            // tuple
const point: { x: number; y: number } = { x: 1, y: 2 };
const id: number | undefined = undefined;

function greet(name: string, excited = false): string {
  return excited ? name.toUpperCase() : name;
}

type User = { id: number; name: string; email?: string };   // ? = optional
interface Admin extends User { permissions: string[] }

Prefer unknown to any for values you can't describe yet. any switches the checker off for that value (and everything it touches); unknown forces you to check before use.

§3TypeScript Compiles Away

Types exist only at compile time. The compiler removes them and emits plain JavaScript; nothing about types remains in the running program. That also means you can't use a type in a runtime expression, or check instanceof against an interface.

// input.ts                              // output.js
function id(x: number): number {          function id(x) {
  return x;                                 return x;
}                                         }

// Run it: tsc (compile), or run .ts directly with tsx / Node's type stripping
// $ npx tsc --noEmit          # type-check only — a common CI step

const v: unknown = fetchValue();
if (typeof v === "string") v.toUpperCase();   // narrowing makes it safe
Where the value is TypeScript is most valuable at boundaries — function signatures, module exports, and data shapes. Annotate those carefully and the compiler checks everything flowing through them.

§4Common Mistakes

MistakeWhat HappensFix
Using any to silence an errorDisables checking and spreads through the codeUse unknown and narrow, or write the real type
Casting API data with as and treating it as validatedWrong data passes the compiler and fails at runtimeValidate at runtime (e.g., with a schema library) then trust the type
Annotating every local variableNoisy; adds nothing over inferenceAnnotate parameters and return types at boundaries
Practice
  1. Type a small price(item, qty) function and confirm the compiler rejects a string argument; then fix a typo'd property on an object.
  2. Replace each any in a short snippet with unknown and add the narrowing needed to compile.
Key takeaways
  • TypeScript finds bugs statically and compiles to plain JavaScript — types vanish at runtime.
  • Rely on inference locally; annotate function boundaries.
  • Prefer unknown to any, and never mistake a type assertion for validation.
