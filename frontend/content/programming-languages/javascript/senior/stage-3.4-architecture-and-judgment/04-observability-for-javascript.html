Observability for JavaScript

You can't reproduce every user's browser — so production needs error tracking, readable stack traces, and traces that connect a click to a server query.

§1Capturing Errors Where They Happen

Errors in users' browsers vanish unless you collect them. Listen globally for uncaught errors and unhandled rejections, and send them to an error tracker (Sentry, Datadog, Rollbar, or your own endpoint) with context: release version, route, user id (if permitted), and the recent breadcrumbs of what the user did.

window.addEventListener("error", (e) => report({ type: "error", message: e.message, stack: e.error?.stack, source: e.filename }));
window.addEventListener("unhandledrejection", (e) => report({ type: "rejection", reason: String(e.reason), stack: e.reason?.stack }));

function report(payload) {
  const body = JSON.stringify({ ...payload, release: __RELEASE__, url: location.pathname, ua: navigator.userAgent });
  navigator.sendBeacon("/api/errors", body);       // survives page unload, doesn't block
}

// Node: never let these go unseen
process.on("uncaughtException", (err) => { logger.fatal({ err }, "uncaught"); process.exit(1); });
process.on("unhandledRejection", (err) => { logger.fatal({ err }, "unhandled rejection"); process.exit(1); });

// A failing fetch that nobody awaited is the classic invisible failure — report it in your fetch wrapper

§2Source Maps

Production code is minified, so a raw stack trace points to a.js:1:48213. Source maps translate it back to your original file, line, and name. Generate them at build time, upload them privately to your error tracker keyed by release, and don't serve them publicly unless you intend your source to be readable.

// vite.config.js
export default { build: { sourcemap: "hidden" } };    // emits maps but no //# sourceMappingURL comment

# In CI, after the build and before deploy:
#   sentry-cli sourcemaps upload --release=$GIT_SHA ./dist
#   then delete the .map files from the deployable output

# Tag every deploy with a release id so errors map to the exact code that ran
# define: { __RELEASE__: JSON.stringify(process.env.GIT_SHA) }

Scrub personal data before it leaves the browser: URLs with tokens, form fields, and request bodies often contain secrets.

§3Tracing and Diagnosing What You Can't Reproduce

A trace follows one request across services as a tree of timed spans. Propagate a trace id from the browser to the API to the database (W3C traceparent header) and a slow click becomes a readable chain. OpenTelemetry is the vendor-neutral standard. Combine it with structured logs and real-user monitoring for Web Vitals.

import { trace } from "@opentelemetry/api";
const tracer = trace.getTracer("checkout");

async function placeOrder(order) {
  return tracer.startActiveSpan("placeOrder", async (span) => {
    try {
      span.setAttribute("order.items", order.items.length);
      await chargeCard(order);                       // child spans created automatically by instrumentation
      return await saveOrder(order);
    } catch (err) {
      span.recordException(err);
      span.setStatus({ code: 2, message: String(err) });
      throw err;
    } finally {
      span.end();
    }
  });
}

logger.info({ traceId, userId, route, durationMs }, "order placed");   // structured: searchable fields, not prose

When a bug "can't be reproduced", the evidence is in the breadcrumbs, the release id, the device and browser, the trace, and the exact stack trace — collect all of them before you need them.

Instrument before the incident The data you need to debug an outage must already be flowing when it starts. Add error reporting, release tags, source maps, and trace ids on a calm day.

§4Common Mistakes

MistakeWhat HappensFix
Shipping minified code without uploaded source mapsStack traces are unreadableUpload maps per release; keep them off the public site
No release id on errorsYou can't tell which deploy introduced a bugTag every report with the git SHA
Sending raw URLs and form data to a third-party trackerLeaks tokens and personal dataScrub sensitive fields before sending
Practice
  1. Add global error and unhandled-rejection reporting to a small app with sendBeacon, trigger a deliberate error, and confirm you receive a readable (source-mapped) stack trace.
  2. Instrument one request path with spans for the HTTP handler and a database call, and read the resulting trace to find the slowest step.
Key takeaways
  • Capture uncaught errors and unhandled rejections with context and a release id.
  • Source maps make minified traces readable — upload them privately per release.
  • Distributed traces, structured logs, and real-user metrics let you diagnose failures you can't reproduce.
