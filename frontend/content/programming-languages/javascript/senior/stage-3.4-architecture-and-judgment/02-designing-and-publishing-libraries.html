Designing & Publishing Libraries

A library is an API other people depend on: design the surface carefully, ship both module formats correctly, and treat every public change as a promise.

§1Dual ESM/CommonJS Packages

Consumers use both module systems, so many libraries ship ESM and CommonJS builds. The exports map tells each environment which file to use, and types tells TypeScript. Test the built package the way users will install it — not just your source.

{
  "name": "@acme/slug",
  "version": "2.1.0",
  "type": "module",
  "sideEffects": false,                       // allows tree shaking
  "files": ["dist"],                          // publish only what's needed
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",           // 'types' first
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./package.json": "./package.json"
  },
  "engines": { "node": ">=18" }
}

# Build with tsup / unbuild / Rollup, emitting .js, .cjs and .d.ts
# Check your package before releasing:
#   npm pack --dry-run          (what files go in the tarball?)
#   npx publint                 (lint exports and format problems)
#   npx @arethetypeswrong/cli --pack .   (are types correct for every consumer?)

§2API Design and Stability

Small, predictable surfaces age best. Everything exported is a promise: removing or changing it breaks someone. Prefer an options object over long positional parameter lists (you can add fields without breaking callers), accept AbortSignal for async work, throw typed errors, avoid global state, and have no side effects on import.

// Hard to extend: adding a parameter later gets awkward
function fetchUser(id, retries, timeout, cache) {}

// Extensible: add options without breaking anyone
function fetchUser(id, { retries = 2, timeoutMs = 3000, signal } = {}) {}

export class SlugError extends Error {          // stable, catchable error type
  name = "SlugError";
  constructor(message, options) { super(message, options); }
}

// Don't export internals "just in case" — exports are forever
export { slugify };                              // public
// internal/normalize.js is not in the exports map

§3Versioning, Deprecation, and Release

Follow semantic versioning honestly: breaking changes require a major version. Deprecate before removing — keep the old API working, warn once with guidance, and set a removal version. Automate releases with changesets or similar so each version has a changelog, and publish from CI with provenance.

// Deprecation: warn once, point to the replacement, keep behavior
let warned = false;
export function oldName(...args) {
  if (!warned) { warned = true; console.warn("oldName() is deprecated; use newName(). Removal in v3."); }
  return newName(...args);
}

# npx changeset            # record a change: patch / minor / major + a summary
# npx changeset version    # bump versions and write the changelog
# npm publish --provenance --access public     # from CI, with trusted publishing

# What counts as breaking? Removing/renaming exports, narrowing accepted input,
# changing return shapes or error types, raising the minimum Node version, changing defaults

Document with runnable examples and keep a clear README. Types are documentation too — a well-typed public API reduces support questions more than prose does.

Exports are forever The cheapest API to maintain is the one you didn't publish. Start with the smallest surface that solves the problem; adding is a minor release, removing is a major one.

§4Common Mistakes

MistakeWhat HappensFix
Shipping only main and no exports mapConsumers can import private files; module format mismatchesDefine exports with import, require, and types
Positional parameter lists and boolean flagsCan't extend without breaking; calls are unreadableTake an options object
Removing or changing behavior in a minor releaseBreaks downstream apps that trusted semverDeprecate first; break only in a major version
Practice
  1. Build a small library into ESM, CJS, and .d.ts, then verify it with npm pack, publint, and a test project that consumes it from both module systems.
  2. Take a function with four positional parameters, redesign it with an options object, and write the deprecation path for the old signature.
Key takeaways
  • Ship ESM and CJS through an exports map with correct types, and test the built package.
  • Keep the public surface small; use options objects, typed errors, and no import-time side effects.
  • Follow semver strictly: deprecate first, break only in majors, and automate releases.
