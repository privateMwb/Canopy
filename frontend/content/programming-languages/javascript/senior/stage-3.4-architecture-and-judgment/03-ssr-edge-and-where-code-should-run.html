SSR, Edge & Where Code Should Run

The same JavaScript can run in the browser, on a server, or at the edge — and each placement trades latency, cost, capability, and complexity.

§1Rendering Strategies

Where HTML is produced determines what users see first and what you pay to serve it:

  • CSR (client-side rendering): the server sends an empty shell and JavaScript builds the page. Cheap to host, but slow first paint and weak for SEO without extra work.
  • SSG (static generation): pages are built ahead of time and served from a CDN. Fastest and cheapest, but content is only as fresh as the last build.
  • SSR (server-side rendering): HTML is generated per request. Fresh and personalized, but uses server compute and needs hydration on the client.
  • ISR / streaming: serve cached HTML and revalidate in the background, or stream pieces of the page as they become ready.
// Typical choice, per route:
// /blog/*          -> SSG or ISR       (content rarely changes, huge read traffic)
// /dashboard       -> CSR or SSR       (private, interactive, no SEO need)
// /product/:id     -> SSR/ISR          (SEO + fresh price/stock)
// /search          -> SSR + streaming  (dynamic, but show the shell immediately)

// Hydration: the server's HTML must match what the client renders first.
// Anything different (Date.now(), Math.random(), window.* checks) causes a mismatch.

§2The Edge

Edge runtimes run your code in many locations near users, which cuts network latency. The trade-off is a restricted environment: no filesystem, a subset of Node APIs, small memory and CPU budgets, and — critically — distance from your database. An edge function that makes three sequential calls to a single-region database can be *slower* than one server colocated with the data.

// An edge-friendly handler uses only web-standard APIs: Request, Response, fetch, URL
export default async function handler(request) {
  const url = new URL(request.url);
  const country = request.headers.get("x-vercel-ip-country") ?? "US";
  if (url.pathname === "/") {
    return Response.redirect(new URL(`/${country.toLowerCase()}`, url), 307);
  }
  return new Response("ok", { headers: { "cache-control": "public, s-maxage=60" } });
}
// Good at the edge: redirects, A/B routing, auth checks, header rewrites, caching, light personalization.
// Poor at the edge: chatty database access, heavy CPU, long-running jobs, large native dependencies.

§3Deciding Where Work Belongs

Place each piece of work by asking four questions: Where is the data? (put compute near it). Who is it for? (shared, cacheable results go to the CDN/edge; per-user results do not). What's the secret or trust boundary? (anything involving secrets or authorization is server-side, never the client). How interactive is it? (instant feedback belongs on the client).

// Decision sketch
// Validate a form field as you type        -> client (instant), and again on the server (trust)
// Render the product page for crawlers     -> server / static, cached at the CDN
// Check a session cookie and redirect      -> edge middleware (cheap, no DB round trip if a signed token)
// Charge a card, check inventory           -> server, near the primary database
// Resize images, heavy PDF generation      -> background worker / queue, not a request handler

Every boundary you add is a place for latency, failure, and complexity. The best architecture is usually the simplest one that meets measured needs.

Colocate compute with data Latency to the user matters, but latency to the database matters more for dynamic pages. Moving code to the edge while the database stays in one region often makes responses slower, not faster.

§4Common Mistakes

MistakeWhat HappensFix
Using SSR for fully static contentPays compute per request for no freshness benefitUse SSG or ISR and a CDN
Reading window/localStorage during server renderCrashes on the server or causes hydration mismatchesAccess browser APIs only in client-side effects
Chatty database calls from the edge to one regionMany long round trips; higher latency than a regional serverColocate with the data or batch queries into a single call
Practice
  1. For a product with a marketing site, a logged-in dashboard, and a checkout, choose a rendering strategy and runtime for each route and justify it in two sentences.
  2. Take a handler that makes three database queries and decide whether it belongs at the edge, with a measurement plan to check your answer.
Key takeaways
  • CSR, SSG, SSR, and streaming trade freshness, speed, cost, and complexity — choose per route.
  • The edge cuts user latency but restricts the runtime and adds distance to your data.
  • Place work by data location, audience, trust boundary, and interactivity.
