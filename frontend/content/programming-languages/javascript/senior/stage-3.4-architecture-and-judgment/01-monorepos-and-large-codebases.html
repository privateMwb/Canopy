Monorepos & Large Codebases

A monorepo keeps many packages in one repository so they can share code and change together — and it only stays pleasant if builds, boundaries, and ownership are managed deliberately.

§1Workspaces and Shared Packages

npm, pnpm, and Yarn workspaces link local packages together: the root package.json lists where packages live, and the package manager symlinks them so import "@acme/ui" resolves to your local source. Shared code gets its own package with a clear public API instead of being copy-pasted or imported through relative ../../ paths.

# repo layout
# apps/web        apps/api
# packages/ui     packages/config     packages/utils
# package.json    pnpm-workspace.yaml

// package.json (root)
{ "private": true, "workspaces": ["apps/*", "packages/*"] }

// apps/web/package.json
{ "dependencies": { "@acme/ui": "workspace:*" } }

// Keep each package's public surface small
// packages/utils/package.json
{ "name": "@acme/utils", "exports": { ".": "./src/index.ts" } }
// Anything not exported is private — other packages can't reach into src/internal/

§2Keeping Builds Fast

Rebuilding everything on every change makes a large repo unbearable. Task runners (Turborepo, Nx, Bazel) build a dependency graph between packages and give you three things: run tasks in the right order, run independent ones in parallel, and cache results so unchanged packages are skipped — locally and, with a remote cache, across CI and teammates.

// turbo.json
{
  "tasks": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] },   // build dependencies first
    "test":  { "dependsOn": ["build"] },
    "lint":  {}
  }
}

# turbo run build --filter=web...        # web and everything it depends on
# turbo run test --filter=...[origin/main]   # only packages changed since main (and dependents)
# Cache hit: the task's inputs hash is unchanged -> outputs are restored instantly

Correct cache keys depend on honest declarations: list every input a task reads and every output it writes. A wrong declaration gives you stale caches that are worse than slow builds.

§3Boundaries, Versions, and Ownership

Scale is a people problem as much as a build problem. Enforce architectural boundaries with lint rules or tooling (no importing app code from libraries; no cycles), keep a single version of shared dependencies where possible, and assign ownership (CODEOWNERS) so every package has a reviewer.

// eslint: forbid reaching into another package's internals
"no-restricted-imports": ["error", { "patterns": ["@acme/*/src/*", "../../*/src/*"] }]

# CODEOWNERS
# /packages/ui/       @acme/design-system
# /apps/api/          @acme/backend

# Tools to keep the graph healthy:
#   madge --circular src     (find dependency cycles)
#   syncpack                 (align dependency versions across packages)
#   changesets               (versioning and changelogs for published packages)

A monorepo is not automatically better. Many small teams with different release cadences, or strong security separation between projects, can be better served by separate repositories.

Trade-off A monorepo trades repository simplicity for tooling investment. It pays off with shared code, atomic cross-package changes, and consistent tooling; it costs you CI engineering, discipline about boundaries, and slower naive clones.

§4Common Mistakes

MistakeWhat HappensFix
Importing another package through a relative path (../../utils/src)Bypasses the public API; builds and publishing breakImport by package name and keep an exports map
Rebuilding and retesting everything on every changeCI becomes slow; developers stop waiting for itUse affected-only runs and task caching
Incorrect cache inputs/outputsStale builds or constant cache missesDeclare all inputs and outputs for each task
Practice
  1. Create a two-app, two-package workspace where both apps import a shared utils package, and make turbo run build cache correctly.
  2. Add a lint rule that forbids importing src/ internals across packages, and demonstrate it catching a violation.
Key takeaways
  • Workspaces link local packages; give shared code a package with a small, explicit public API.
  • Task graphs, parallelism, and caching keep builds fast as the repo grows.
  • Enforce boundaries, share one version of dependencies, and assign ownership — or the monorepo decays.
