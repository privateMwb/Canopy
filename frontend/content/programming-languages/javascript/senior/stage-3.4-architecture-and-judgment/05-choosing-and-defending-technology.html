Choosing & Defending Technology

Senior engineering is choosing tools for the situation, writing down why, and explaining the trade-offs clearly enough that a team can disagree productively.

§1Reasoning About Choices

Technology decisions are trade-offs under uncertainty, not contests with a winner. Start from the problem and constraints — team skills, timeline, scale, hiring, operations budget, risk tolerance — and evaluate options against them. Distinguish reversible decisions (a UI library you can swap) from hard-to-reverse ones (your primary datastore, your language); spend your deliberation on the second kind.

// JavaScript vs TypeScript
// - TS: catches whole classes of bugs, makes refactoring safe, documents shapes. Costs: build step,
//   learning curve, type gymnastics. Strong default for anything with >1 developer or a long life.
// - Plain JS (+JSDoc): fine for small scripts, prototypes, tiny libraries; zero toolchain.

// Runtime: Node (ecosystem, maturity) vs Bun / Deno (speed, built-in tooling, security model)
// - Decide on: dependency compatibility, hosting support, team familiarity, stability needs.

// Frameworks: pick for the team and the product, not the hype cycle.
// - Content site -> static/SSG framework.  App with auth + data -> full-stack framework.
// - Interactive dashboards -> component framework + data layer.  Don't add what you don't need.

§2Writing It Down: Architecture Decision Records

An ADR is a short document capturing one decision: the context, the options considered, what was chosen, and the consequences. Future engineers (including you) will ask "why did we do this?" — the ADR answers it, and it also shows when the original reasons no longer hold.

# ADR-014: Use TypeScript and a Node + Postgres stack for the orders service

Status: Accepted (2026-03-02)        Deciders: backend team

## Context
Small team (4), all strong in JavaScript, 6-month deadline, moderate scale (<500 rps),
need transactional integrity for orders and payments.

## Options considered
1. TypeScript on Node + Postgres.  2. Go + Postgres.  3. Python + Django + Postgres.

## Decision
Option 1.

## Consequences
+ One language across frontend and backend; shared types; fast onboarding.
+ Mature libraries for payments and queues.
- CPU-heavy work (PDF generation) must go to worker threads or a queue.
- We accept Node's single-threaded model; revisit if sustained load exceeds ~2,000 rps.

## Risks and how we'll know
Event-loop delay p99 > 100 ms for a week -> reopen this decision.

§3Communicating Trade-offs

Make your reasoning legible. State the decision in one sentence, then the strongest alternative and why you're not choosing it, then the risks you are knowingly accepting and the signals that would change your mind. Separate facts (benchmarks, constraints) from judgment (preferences), disagree with ideas rather than people, and commit once the decision is made.

// A useful structure for a design discussion:
// 1. The problem and constraints, in two sentences.
// 2. The recommendation, in one sentence.
// 3. The strongest alternative — presented fairly — and why it loses here.
// 4. What we give up (be specific) and how we'd mitigate it.
// 5. The trigger that would make us revisit: a metric, a date, a scale.

// Avoid: "X is better." Prefer: "X is better *for us* because the team knows it and our load fits it."
// Avoid: relitigating decided questions without new information.
// Practice: prototype the riskiest assumption before committing to a large build.

The point of an ADR is not to be right forever. It is to make today's reasoning visible, so tomorrow's team can change course for the right reasons.

Boring is a feature Prefer well-understood technology where you don't need novelty. Spend your "innovation budget" only on the parts of the system where being different creates real advantage.

§4Common Mistakes

MistakeWhat HappensFix
Choosing technology by popularity or noveltyMismatch with team skills and the real problemStart from constraints; evaluate options against them
Undocumented decisionsNo one knows why; the same debate repeatsWrite a short ADR for each significant decision
Presenting a choice as obviously correctHides the trade-offs; erodes trustState what you're giving up and what would change your mind
Practice
  1. Pick a project you know and write a one-page ADR choosing a language, runtime, and rendering strategy, including the alternatives and the risks you accept.
  2. Take a decision your team made recently and write the strongest case for the option that lost; identify what new information would justify revisiting it.
Key takeaways
  • Decide from constraints and reversibility; spend deliberation on hard-to-reverse choices.
  • Record decisions as ADRs with context, alternatives, consequences, and revisit triggers.
  • Communicate trade-offs honestly: what you gain, what you give up, and what would change your mind.
