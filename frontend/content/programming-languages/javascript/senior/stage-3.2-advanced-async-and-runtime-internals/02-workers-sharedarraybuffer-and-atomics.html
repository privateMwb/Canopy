Workers, SharedArrayBuffer & Atomics

Workers give JavaScript real parallelism, and SharedArrayBuffer plus Atomics let threads share memory — at the price of every classic concurrency bug.

§1Message Passing vs. Shared Memory

By default workers share nothing: each has its own heap, and messages are copied (or transferred). That model rules out data races and is the right default. SharedArrayBuffer (SAB) is a block of memory that several threads can read and write simultaneously — useful when copying costs too much or threads must coordinate in real time.

// main.js
const sab = new SharedArrayBuffer(4 * 1024);       // 1024 shared Int32 slots
const view = new Int32Array(sab);
const workers = [1, 2, 3, 4].map(() => new Worker("./count.js"));
workers.forEach((w) => w.postMessage(sab));        // shared, not copied

// count.js
self.onmessage = ({ data: sab }) => {
  const view = new Int32Array(sab);
  for (let i = 0; i < 100000; i++) view[0]++;      // DATA RACE: lost updates!
};

In browsers, SAB requires cross-origin isolation (Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp) because of Spectre-class attacks.

§2Atomics

view[0]++ is three steps — read, add, write — and two threads can interleave them. Atomics operations are indivisible and also provide the memory-ordering guarantees you need. Use them for counters, flags, locks, and signaling. Atomics.wait/notify let a thread sleep until another wakes it (wait is not allowed on the main thread in browsers).

Atomics.add(view, 0, 1);                      // atomic increment — no lost updates
Atomics.load(view, 0);                        // read with ordering guarantees
Atomics.store(view, 1, 42);
Atomics.compareExchange(view, 2, 0, 1);       // CAS: set to 1 only if currently 0 -> returns old value

// A tiny mutex: 0 = unlocked, 1 = locked
function lock(a, i) {
  while (Atomics.compareExchange(a, i, 0, 1) !== 0) Atomics.wait(a, i, 1);
}
function unlock(a, i) {
  Atomics.store(a, i, 0);
  Atomics.notify(a, i, 1);                    // wake one waiter
}

§3What It Costs

Shared memory brings back data races, deadlocks, and ordering bugs that single-threaded JavaScript spared you — and they are hard to reproduce. SAB holds only typed arrays of numbers, so complex objects must be serialized into bytes by hand. Before reaching for it, ask whether a worker pool with message passing is enough.

// Usually enough: a pool of workers, each given a slice of input (copied or transferred)
const results = await Promise.all(chunks.map((chunk) => pool.run(chunk)));

// Reach for SAB when: very large shared data (image/audio/wasm memory),
// tight coordination (lock-free queues, progress counters), or per-message copy cost dominates.

Measure first. A message-passing design that's correct and 20% slower is usually better than a shared-memory design that's occasionally wrong.

The default stays Share nothing, send messages. Use shared memory only for a measured bottleneck, keep the shared surface tiny (a few counters or a ring buffer), and put every access behind Atomics.

Practice
  1. Reproduce the lost-update bug with four workers incrementing a shared counter with ++, then fix it with Atomics.add and verify the total.
  2. Implement the mutex above and protect a two-field shared record; explain what could go wrong without it.
Key takeaways
  • Workers share nothing by default; SharedArrayBuffer shares raw bytes between threads.
  • Plain reads and writes race — use Atomics for counters, locks, and signaling.
  • Shared memory costs correctness and complexity; prefer message passing unless measurements demand otherwise.
