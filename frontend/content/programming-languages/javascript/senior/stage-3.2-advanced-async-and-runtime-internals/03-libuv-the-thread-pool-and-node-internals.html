libuv, the Thread Pool & Node Internals

Node runs your JavaScript on one thread, but libuv and the operating system do the waiting — and knowing what runs where explains both Node's scalability and the ways to stall it.

§1The Architecture

Node combines V8 (runs your JS), libuv (the event loop and async I/O), and C++ bindings. Your code runs on a single main thread. When you start an operation, Node hands it to the OS or to libuv and returns immediately; when it finishes, a callback is queued back onto the main thread.

  • Network I/O (TCP, HTTP, DNS sockets) uses OS-level non-blocking mechanisms (epoll, kqueue, IOCP) — no thread per connection.
  • File system, dns.lookup, some crypto, and zlib run on libuv's thread pool (4 threads by default, UV_THREADPOOL_SIZE up to 1024).
  • Your JavaScript — including JSON parsing, regexes, and loops — always runs on the main thread.

§2The Event Loop Phases

Each iteration of the loop passes through phases, in order. Between every callback, Node drains process.nextTick callbacks first and then promise microtasks.

// timers          -> setTimeout / setInterval callbacks that are due
// pending         -> some deferred system callbacks
// poll            -> wait for and run I/O callbacks
// check           -> setImmediate callbacks
// close           -> close events (socket.on("close"))
// (between each callback: process.nextTick queue, then promise microtasks)

setTimeout(() => console.log("timeout"), 0);
setImmediate(() => console.log("immediate"));
process.nextTick(() => console.log("nextTick"));
Promise.resolve().then(() => console.log("promise"));
// nextTick, promise, then timeout/immediate (their order is not guaranteed from the main module)

// Inside an I/O callback, setImmediate always fires before a 0ms timer

§3What Blocks, and Thread Pool Saturation

Anything synchronous and slow on the main thread blocks every connection. The thread pool can also saturate: with 4 threads, 4 slow fs or pbkdf2 calls make the fifth wait, even though the main thread is idle.

// Blocks the whole server for the duration:
app.get("/report", (req, res) => { res.json(heavyCpuLoop()); });
JSON.parse(hugeString);                      // synchronous: blocks while it parses
/(a+)+$/.test(attackerString);               // catastrophic regex backtracking (ReDoS)
fs.readFileSync("big");                      // blocks

// Detect it: how late is the loop?
import { monitorEventLoopDelay } from "node:perf_hooks";
const h = monitorEventLoopDelay({ resolution: 10 }); h.enable();
setInterval(() => console.log("p99 delay ms:", h.percentile(99) / 1e6), 5000);

// Fixes: worker_threads for CPU work, streaming parsers, bounded input sizes,
// a larger UV_THREADPOOL_SIZE if the pool (not the main thread) is the bottleneck

Tell the two bottlenecks apart: *main thread busy* (event-loop delay is high, CPU at 100% on one core) versus *pool saturated* (event loop is idle but file/crypto operations queue up).

Diagnose before fixing Event-loop delay answers "is the main thread blocked?" A CPU profile answers "by what?" Adding workers or threads without that answer often just adds complexity.

§4Common Mistakes

MistakeWhat HappensFix
Doing CPU-heavy work in a request handlerAll other requests stall behind itOffload to worker_threads or a job queue
Assuming Node handles everything concurrentlySlow fs/crypto calls queue on a 4-thread poolRaise UV_THREADPOOL_SIZE or reduce pool-bound work
Using regexes with nested quantifiers on user inputReDoS: one request can freeze the processUse safe patterns, limit input length, or a linear-time engine
Practice
  1. Write a server whose route runs a 2-second CPU loop and measure the latency of a second route while it runs; then move the loop into a worker thread.
  2. Run 8 simultaneous crypto.pbkdf2 calls and observe how total time changes as you set UV_THREADPOOL_SIZE to 4, then 8.
Key takeaways
  • Your JS runs on one main thread; libuv and the OS handle waiting, with a small thread pool for some work.
  • Know the loop's phases and that nextTick and microtasks run between callbacks.
  • Distinguish a blocked main thread from a saturated pool before choosing a fix.
