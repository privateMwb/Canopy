Bundle Size & Loading Performance

Every kilobyte of JavaScript costs download time and parse/execute time — so measure what users actually download and load the rest only when it's needed.

§1Measure What Ships

Start by seeing the bundle. Treemap tools (rollup-plugin-visualizer, source-map-explorer, webpack-bundle-analyzer) show what each dependency contributes. Look at *gzipped/brotli* transfer size for the network, and at total JavaScript for parse and execution cost on slow devices.

# npx vite-bundle-visualizer
# npx source-map-explorer dist/assets/*.js
# npx esbuild src/main.js --bundle --minify --metafile=meta.json   # then upload meta.json to esbuild.github.io/analyze

# Spot the usual suspects: moment (use date-fns/Temporal), full lodash, icon libraries imported wholesale,
# polyfills you don't need for your browser targets, duplicate copies of one package at different versions

# CI guard: fail the build when the budget is exceeded
# bundlesize / size-limit: "limit": "170 KB"  (compressed JS for the initial route)

§2Code Splitting and Lazy Loading

Split the bundle so the first page loads only what it needs. Dynamic import() is a split point: the bundler puts that module in its own chunk, fetched on demand. Split by route first, then by heavy features (charts, editors, maps) behind interactions.

// Route-level split (React shown; the idea is framework-independent)
const Settings = lazy(() => import("./pages/Settings.jsx"));

// Feature-level split: load a 200 KB chart library only when needed
button.addEventListener("click", async () => {
  const { renderChart } = await import("./chart.js");
  renderChart(data);
});

// Hint the browser to fetch likely-needed code ahead of time
// <link rel="modulepreload" href="/assets/settings.js">
// <link rel="prefetch" href="/assets/reports.js">      (low priority, for the next navigation)

// Tree shake: named imports from ESM builds
import { format } from "date-fns";

§3Loading Strategy and Caching

Cache aggressively what doesn't change. Content-hashed filenames (app.3f9a1c.js) can be cached for a year because a change creates a new URL, while the HTML that references them is revalidated each time. Compress with brotli. Serve third-party scripts async or defer and question each one — they're often the largest cost you didn't write.

# Response headers
# /assets/app.3f9a1c.js  ->  Cache-Control: public, max-age=31536000, immutable
# /index.html            ->  Cache-Control: no-cache          (always revalidate)
# Content-Encoding: br

<script async src="https://analytics.example/a.js"></script>   <!-- never render-blocking -->
<link rel="preconnect" href="https://api.example.com" crossorigin>   <!-- early connection setup -->

Measure on real conditions: throttle to "Fast 4G" and a 4x CPU slowdown, and track real-user LCP/INP over time so regressions are caught when they ship.

Budget it A performance budget (for example, 170 KB of compressed JavaScript on the first route) turns "keep it small" from a wish into a check that fails the build.

§4Common Mistakes

MistakeWhat HappensFix
Importing an entire utility or icon library for a few functionsLarge unused code in the bundleUse specific/ESM imports; check the analyzer
Caching index.html for a long timeUsers keep loading old asset URLs and see broken or stale pagesRevalidate HTML; cache only hashed assets long-term
Adding third-party scripts without measuringHidden long tasks and blocked renderingLoad async/defer, audit regularly, remove what you don't need
Practice
  1. Analyze one of your bundles with a treemap, identify the three largest dependencies, and replace or lazy-load one of them.
  2. Add size-limit or an equivalent to CI with a budget for your initial JavaScript and verify it fails when you exceed it.
Key takeaways
  • Analyze what ships; track compressed transfer size and total JS execution cost.
  • Split by route and by heavy feature using dynamic import().
  • Cache hashed assets long-term, revalidate HTML, and enforce a size budget in CI.
