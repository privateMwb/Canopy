Errors & Debugging

Errors are objects you can throw, catch, and inspect — and the DevTools debugger lets you stop time and look at what your program is really doing.

§1try, catch, finally, throw

throw interrupts normal flow. catch handles it; finally always runs, whether or not anything was thrown — the right place for cleanup. You can throw anything, but throw Error objects: only they carry a stack trace.

function parse(text) {
  try {
    return JSON.parse(text);
  } catch (err) {
    if (err instanceof SyntaxError) return null;   // expected problem
    throw err;                                      // unexpected: don't swallow it
  } finally {
    console.log("done");                            // runs either way
  }
}

throw new Error("Something broke");
throw new RangeError("Index out of bounds");

§2Error Types and Custom Errors

Built-in types — TypeError, RangeError, SyntaxError, ReferenceError — tell you the category. Create your own by extending Error, and pass cause to keep the original failure attached.

class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}

try {
  throw new ValidationError("Email is required", "email");
} catch (e) {
  if (e instanceof ValidationError) console.log(e.field);   // "email"
}

try { risky(); }
catch (e) { throw new Error("Could not load profile", { cause: e }); }

§3Stack Traces and the Debugger

A stack trace lists the call chain at the moment of the error: read from the top (where it happened) down. Use console.log for a quick look, and breakpoints when you need to inspect state.

function total(items) {
  debugger;                       // pauses here when DevTools is open
  return items.reduce((s, i) => s + i.price, 0);
}

console.error("failed", err);     // logs with stack trace
console.table(rows);              // great for arrays of objects
console.time("load"); /* work */ console.timeEnd("load");

In the Sources panel, click a line number to set a breakpoint. Then use *Step over* (next line), *Step into* (enter the call), and watch the Scope and Call Stack panes. Conditional breakpoints (right-click the line) pause only when an expression is true.

Catch what you can handle Only catch an error if you can do something useful with it. Catching everything and logging "error" hides bugs; rethrow what you don't understand.

§4Common Mistakes

MistakeWhat HappensFix
An empty catch {} blockFailures disappear silentlyHandle it, log it, or rethrow
Throwing strings: throw "bad"No stack trace; can't use instanceofThrow new Error("bad")
Debugging only with console.logSlow; you see only what you thought to printSet a breakpoint and inspect scope
Practice
  1. Write safeParse(json) that returns { ok: true, value } or { ok: false, error } without ever throwing.
  2. Plant a bug in a small function, then find it using a breakpoint and the Scope pane without adding any console.log.
Key takeaways
  • Throw Error objects; use try/catch/finally, and rethrow what you can't handle.
  • Custom error classes and cause keep failures meaningful and traceable.
  • Breakpoints and stepping in DevTools beat guesswork with console.log.
