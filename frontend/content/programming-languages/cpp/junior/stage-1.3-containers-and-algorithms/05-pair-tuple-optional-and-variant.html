pair, tuple, optional & variant

These vocabulary types let a function return several values, "maybe a value," or "one of several types" while the type system keeps you honest.

§1pair and tuple

std::pair holds two values and std::tuple holds any number. With structured bindings, unpacking is clean.

#include <tuple>
std::pair<std::string, int> p{"Ada", 36};
std::cout << p.first << ' ' << p.second << '\n';

std::tuple<int, double, std::string> t{1, 2.5, "x"};
std::cout << std::get<0>(t) << '\n';

auto [id, score, label] = t;               // structured binding

std::pair<int, int> divmod(int a, int b) { return {a / b, a % b}; }
auto [q, r] = divmod(17, 5);

For anything beyond a throwaway, a small named struct is clearer than a tuple, because .quotient explains itself better than get<0>.

§2std::optional

std::optional<T> either holds a T or holds nothing. It replaces "magic" return values like -1, nullptr, or an empty string for "not found."

#include <optional>
std::optional<int> findIndex(const std::vector<int>& v, int target) {
    for (std::size_t i = 0; i < v.size(); ++i)
        if (v[i] == target) return static_cast<int>(i);
    return std::nullopt;
}
if (auto idx = findIndex(v, 5)) std::cout << "at " << *idx << '\n';
std::cout << findIndex(v, 9).value_or(-1) << '\n';

*opt is unchecked, so test has_value() first, or use .value(), which throws std::bad_optional_access. The value is stored inside the optional itself, with no heap allocation.

§3std::variant

std::variant<A, B, C> holds exactly one of the listed types at a time, tracking which. It is a type-safe union.

#include <variant>
std::variant<int, std::string> v{42};
v = "hello";                                       // now holds a string
if (auto* s = std::get_if<std::string>(&v)) std::cout << *s << '\n';

struct Printer {
    void operator()(int x) const { std::cout << "int " << x << '\n'; }
    void operator()(const std::string& s) const { std::cout << "str " << s << '\n'; }
};
std::visit(Printer{}, v);                          // calls the overload for the held type

std::visit forces you to handle every alternative, so adding a new type to the variant produces compile errors at each place that needs updating.

The key insight optional and variant move "might be missing" and "might be several things" out of comments and conventions and into the type, where the compiler checks them.

§4Common Mistakes

MistakeWhat HappensFix
Dereferencing an optional without checkingUndefined behavior when it's emptyCheck with if (opt) or use value_or
Using std::get<T> on the wrong alternativeThrows std::bad_variant_accessUse std::visit or std::get_if
Returning a tuple with five unnamed fieldsCallers can't tell what each meansDefine a small struct
Practice
  1. Write std::optional<double> parseNumber(std::string_view) that returns nullopt on bad input.
  2. Represent a JSON-like value as std::variant<int, double, std::string, bool> and print it with std::visit.
Key takeaways
  • pair and tuple group values; use a named struct when the meaning isn't obvious.
  • optional<T> is the honest way to say "no result," instead of sentinels or null pointers.
  • variant holds one of several types, and visit makes you handle every case.
