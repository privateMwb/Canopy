RAII

RAII means a resource is acquired in a constructor and released in the destructor, so cleanup happens on every exit path without extra code.

§1The Problem

Anything that must be released — memory, files, locks, sockets — is easy to leak when a function has several exit paths.

void process(const char* path) {
    FILE* f = std::fopen(path, "r");
    if (!f) return;
    if (!validate(f)) return;        // LEAK: forgot fclose
    work(f);                         // may throw: LEAK
    std::fclose(f);
}

Remembering a cleanup call on every path does not scale.

§2Resource Acquisition Is Initialization

C++ guarantees that when an object goes out of scope, its destructor runs, on normal return, early return, and during exception unwinding. RAII exploits that: wrap the resource in a class that acquires it in the constructor and releases it in the destructor.

class File {
    std::FILE* f_;
public:
    explicit File(const char* path) : f_{std::fopen(path, "r")} {
        if (!f_) throw std::runtime_error{"cannot open file"};
    }
    ~File() { std::fclose(f_); }
    File(const File&) = delete;              // exactly one owner
    File& operator=(const File&) = delete;
    std::FILE* get() const { return f_; }
};

void process(const char* path) {
    File f{path};
    if (!validate(f.get())) return;          // destructor closes the file
    work(f.get());                           // destructor closes it even on throw
}

The resource's lifetime is now the object's lifetime, and the compiler writes the cleanup calls for you.

§3RAII Is Everywhere

Most of the standard library is RAII: std::vector and std::string free their memory, std::ofstream closes its file, std::lock_guard unlocks a mutex, and std::unique_ptr deletes its object.

{
    std::lock_guard<std::mutex> lock{m};   // locks here
    counter++;
}                                          // unlocks here, even if an exception was thrown

Destructors run in the reverse order of construction, so a resource acquired later is released earlier, matching dependencies naturally.

The key insight RAII turns "remember to clean up" into "can't forget to clean up." This is why C++ has no finally and rarely needs one.

§4Common Mistakes

MistakeWhat HappensFix
Allowing a resource wrapper to be copiedTwo owners both release the same handle: double closeDelete copying or implement it correctly (see the Rule of 0/3/5 lesson)
Throwing an exception from a destructorCan terminate the program during unwindingDestructors should not throw
Holding a raw handle in a plain structNo automatic releaseWrap every handle in a class with a destructor
Practice
  1. Write a Timer class that records the time in its constructor and prints the elapsed time in its destructor, then drop one into a function.
  2. Print a message in a class's constructor and destructor, create several objects in nested scopes, and predict the output order.
Key takeaways
  • RAII ties a resource's lifetime to an object's scope so it is released on every exit path.
  • Destructors run in reverse order of construction, including during exception unwinding.
  • Prefer standard RAII types (containers, smart pointers, lock guards) over writing manual cleanup.
