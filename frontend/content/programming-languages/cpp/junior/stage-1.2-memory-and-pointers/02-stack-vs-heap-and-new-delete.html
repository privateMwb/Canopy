Stack vs. Heap & new/delete

Local variables live on the stack and vanish automatically, while heap objects live until you free them, which is where leaks and double frees come from.

§1Automatic Storage (the Stack)

Local variables are created when execution reaches them and destroyed when their scope ends, in reverse order. Allocation is nearly free and cleanup is automatic.

void f() {
    int a{1};
    std::string s{"hi"};
}   // s destroyed, then a; no cleanup code needed

The stack is small (often 1–8 MB), so huge local arrays or deep recursion can overflow it.

§2Dynamic Storage (the Heap)

new allocates an object on the heap and returns a pointer; delete destroys it and releases the memory. The object stays alive until you delete it, regardless of scope.

int* p = new int{42};
std::cout << *p << '\n';
delete p;                    // must happen exactly once
p = nullptr;

int* arr = new int[100]{};   // array form
delete[] arr;                // arrays need delete[], not delete

Use the heap when an object must outlive the function that created it, when its size is only known at runtime, or when it is too large for the stack.

§3What Goes Wrong

Manual management has four classic failures:

int* a = new int{1};
a = new int{2};              // LEAK: first int is unreachable, never freed

int* b = new int{3};
delete b;
delete b;                    // DOUBLE FREE: undefined behavior

int* c = new int{4};
delete c;
*c = 5;                      // USE AFTER FREE: dangling pointer

int* d = new int[4];
delete d;                    // WRONG FORM: should be delete[]

Even correct code leaks if an exception or early return skips the delete. This is why modern C++ treats a bare new in application code as a warning sign.

§4The Modern Alternative

Let a library type own the allocation. A std::vector or std::string manages heap memory for you, and std::make_unique does the same for a single object (covered fully in the smart pointers lesson).

auto p = std::make_unique<int>(42);     // freed automatically at scope end
std::vector<int> v(100);                // 100 ints on the heap, freed automatically
The key insight Heap memory is not the problem; unowned heap memory is. Every allocation needs exactly one owner responsible for freeing it, ideally an object whose destructor does it.

§5Common Mistakes

MistakeWhat HappensFix
Using delete on memory from new[]Undefined behaviorMatch new with delete and new[] with delete[]
Early return or exception between new and deleteThe allocation leaksUse RAII types so cleanup is automatic
Using a pointer after deleteReads or writes freed memorySet to nullptr, better, avoid raw owners entirely
Practice
  1. Write a function that allocates with new int[n], then rewrite it with std::vector<int> and compare the code for cleanup.
  2. Deliberately leak an int and run the program under -fsanitize=address to read the leak report.
Key takeaways
  • Stack objects are cleaned up automatically; heap objects must have an owner that frees them exactly once.
  • Match new/delete and new[]/delete[], but better, avoid them in application code.
  • Prefer containers and smart pointers over a bare new.
