Allocators & Memory Resources

The general-purpose heap is flexible but slow and unpredictable on hot paths, and C++ lets you replace it with arenas and pools without rewriting your containers.

§1What malloc Costs

Each new or malloc may take a lock, search free lists, and touch cold memory, and the time varies. A program doing millions of small allocations can spend more time in the allocator than in its own logic, and fragmentation makes worst cases unpredictable. The usual fixes are to allocate less (reserve, reuse buffers, emplace), or to allocate differently with an arena (bump allocator) or pool.

§2Arena (Bump) Allocation

An arena grabs one big block, then hands out pieces by moving a pointer forward. Allocation is a few instructions and freeing is all at once by resetting the pointer. This is ideal for data with a common lifetime, such as everything built while handling one request.

class Arena {
    std::byte* base_; std::size_t cap_, used_{0};
public:
    Arena(std::byte* buf, std::size_t cap) : base_{buf}, cap_{cap} {}
    void* alloc(std::size_t n, std::size_t align) {
        std::size_t p = (used_ + align - 1) & ~(align - 1);     // align up
        if (p + n > cap_) throw std::bad_alloc{};
        used_ = p + n;
        return base_ + p;
    }
    void reset() { used_ = 0; }
};

§3std::pmr: Allocators Without Template Pain

Traditional allocators change a container's *type* (vector<int, MyAlloc>). C++17's polymorphic memory resources keep the type the same and choose the resource at run time.

#include <memory_resource>
std::array<std::byte, 64 * 1024> buffer;
std::pmr::monotonic_buffer_resource arena{buffer.data(), buffer.size()};

std::pmr::vector<std::pmr::string> names{&arena};   // allocates from the arena
names.emplace_back("alpha");
names.emplace_back("beta");
// arena frees everything when it goes out of scope; no per-element deallocation

Nested pmr containers pass their resource down to their elements automatically (via polymorphic_allocator). monotonic_buffer_resource falls back to an upstream resource (the default heap) if the buffer runs out, and std::pmr::unsynchronized_pool_resource provides size-class pools for repeated alloc/free patterns.

§4Custom Allocator Interface

When you do need a typed allocator, the minimal interface is small.

template <typename T>
struct CountingAlloc {
    using value_type = T;
    CountingAlloc() = default;
    template <typename U> CountingAlloc(const CountingAlloc<U>&) {}
    T* allocate(std::size_t n) { ++allocs; return static_cast<T*>(::operator new(n * sizeof(T))); }
    void deallocate(T* p, std::size_t) noexcept { ::operator delete(p); }
    static inline int allocs{0};
};
template <typename T, typename U> bool operator==(const CountingAlloc<T>&, const CountingAlloc<U>&) { return true; }
std::vector<int, CountingAlloc<int>> v;

A counting allocator like this is also a handy way to measure how many allocations code performs.

The key insight Allocation strategy follows lifetime. Same-lifetime objects belong in an arena freed in one step, and many same-size objects belong in a pool. The general heap is for everything else.

§5Common Mistakes

MistakeWhat HappensFix
Returning pmr containers that point into a local arenaDangling pointers after the arena diesKeep the resource alive longer than every container using it
Using monotonic_buffer_resource for long-running churnMemory never returns until the resource is destroyedUse it for bounded, batch-shaped work
Optimizing allocation without counting it firstMight not be the bottleneckCount or profile allocations before and after
Practice
  1. Parse 1 million small strings into a std::vector<std::string> using default allocation and then std::pmr with a monotonic buffer, and compare times.
  2. Write a counting allocator and report how many allocations a std::vector makes as it grows to 1000 elements, with and without reserve.
Key takeaways
  • Heap allocation is slow and unpredictable on hot paths; arenas and pools make it fast and deterministic.
  • std::pmr switches allocation strategy at run time without changing container types.
  • Tie allocator choice to object lifetime, and measure allocations before optimizing.
