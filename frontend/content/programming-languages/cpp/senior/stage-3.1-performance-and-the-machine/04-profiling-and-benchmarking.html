Profiling & Benchmarking

Optimization starts with measurement: a profiler tells you where time goes, and a benchmark tells you whether a change helped.

§1Profile Before You Optimize

Programmers are bad at guessing bottlenecks. A sampling profiler interrupts the program many times per second and records the call stack, so the functions that show up most often are where time is spent. Build with optimization and symbols: -O2 -g (or RelWithDebInfo), and -fno-omit-frame-pointer for good stacks.

perf record -g ./app          # sample with call graphs
perf report                   # interactive: where is the time?
perf stat ./app               # counters: cycles, instructions, cache-misses, branch-misses

perf stat is revealing: instructions per cycle (IPC) well below 1 usually means the CPU is waiting on memory, and a high cache-miss rate points at layout.

§2Flame Graphs

A flame graph shows stacks as stacked boxes: width is the share of samples, and the top edge is where time is actually being spent. Wide boxes are the places to look.

perf record -F 99 -g ./app
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg

Look for wide plateaus near the top, such as memcpy, malloc, a hash function, or one unexpected function. Tools like valgrind --tool=callgrind, Instruments (macOS), and Visual Studio Profiler give similar views.

§3Microbenchmarks with Google Benchmark

When you want to compare two implementations of a small piece of code, use a benchmark framework. It runs the code enough times for stable statistics.

#include <benchmark/benchmark.h>
static void BM_VectorSum(benchmark::State& state) {
    std::vector<int> v(state.range(0), 1);
    for (auto _ : state) {
        long long s = std::accumulate(v.begin(), v.end(), 0LL);
        benchmark::DoNotOptimize(s);            // keep the result alive
    }
    state.SetItemsProcessed(state.iterations() * state.range(0));
}
BENCHMARK(BM_VectorSum)->Range(1 << 10, 1 << 20);
BENCHMARK_MAIN();

§4Not Fooling Yourself

  • Use a Release build, and run on a quiet machine (no other load, stable CPU frequency).
  • Warm up, repeat, and look at variance, not one run.
  • Prevent the optimizer from deleting the work (DoNotOptimize, ClobberMemory).
  • Benchmark realistic data sizes and patterns: a table that fits in cache says nothing about one that doesn't.
  • Change one thing at a time, and keep the baseline.
  • Remember Amdahl's law: speeding up 5% of the runtime gains at most 5%.
The key insight A benchmark answers "is A faster than B on this input?" and a profiler answers "where should I even look?" Use the profiler to choose what to change and the benchmark to prove the change helped.

§5Common Mistakes

MistakeWhat HappensFix
Profiling a Debug buildHotspots differ from the optimized programProfile -O2 -g
Trusting one timingNoise and frequency scaling dominate small differencesRepeat and compare distributions
Optimizing the code that's easy to read rather than the code that's hotAlmost no effect on total runtimeFollow the flame graph
Practice
  1. Profile a program of your own with perf record -g and identify its widest function. Fix it and re-measure.
  2. Write two Google Benchmark cases comparing std::map and std::unordered_map lookups at three sizes.
Key takeaways
  • Profile first with a sampling profiler on an optimized build with symbols.
  • Flame graphs show where time goes, and benchmarks show whether a change helped.
  • Control the environment, defeat dead-code elimination, and measure realistic inputs.
