Object Lifetime & Provenance

C++ cares about when an object's lifetime begins and ends, and a pointer is only usable while it refers to a living object of the right type.

§1When Lifetime Starts and Ends

An object's lifetime begins when its storage is obtained and its initialization (constructor) completes, and it ends when its destructor starts (or its storage is released, for trivial types). Outside that window you may only do a few things, such as take its address. Reading or calling members is UB.

std::string* p = new std::string{"hi"};
delete p;
p->size();                     // UB: object no longer exists; p is dangling

int* p2{nullptr};
{
    int x{5};
    p2 = &x;
}
*p2;                           // UB: x's lifetime ended with the scope

Even comparing or copying an invalid pointer value has implementation-defined results in the standard.

§2Pointer Provenance

A pointer isn't just an address. It carries provenance: the object (or allocation) it was derived from. Arithmetic must stay within that array, plus one past the end. A pointer that happens to hold the same address as another object isn't allowed to access it.

int a[4];
int b[4];
int* p = a + 4;                // one past a: valid to hold, not to dereference
int* q = b;
// *(p) reads at b's address maybe, but p's provenance is `a`: UB

Optimizers use provenance for alias analysis, so code that fabricates pointers from integers or compares addresses across allocations can be miscompiled. If you must round-trip through integers, use std::uintptr_t and know that compilers differ on provenance rules, so keep it out of portable code.

§3Placement new, Reuse, and std::launder

Storage can host a new object via placement new. After you destroy an object and construct a new one in the same storage, old pointers and references to it may not refer to the new object, particularly if the type has const or reference members. std::launder returns a pointer the compiler must treat as pointing at the new object.

alignas(Widget) std::byte buf[sizeof(Widget)];
Widget* w = new (buf) Widget{};            // object created in buf
w->~Widget();                              // lifetime ends
Widget* w2 = new (buf) Widget{};           // a different object, same storage
Widget* ok = std::launder(reinterpret_cast<Widget*>(buf));   // when reusing via a different pointer

Container implementations use this machinery. Application code rarely needs it, and it is a sign to use std::optional or std::variant instead.

§4Implicit Lifetime, Temporaries, and Extension

Binding a temporary to a const& or && extends its lifetime to that of the reference, but only for a direct binding, not through a function call.

const std::string& r = std::string{"temp"};     // OK: lifetime extended
const std::string& bad = identity(std::string{"temp"});   // dangles after the statement

Range-for has a trap: for (auto x : makeObject().getVector()) destroys the temporary makeObject() before the loop, in code before C++23's fix.

The key insight Every pointer or reference carries an implicit claim: "the thing I refer to still exists and is of this type." Review code by asking, for each borrow, what ends the lifetime of its referent and whether the borrow can outlive it.

§5Common Mistakes

Keeping a reference to an element of a container that reallocatesReference refers to freed storageUse indices or re-fetch
Reusing storage via placement new and using the old pointerCompiler may assume it still refers to the old objectstd::launder, or avoid by using proper types
Practice
  1. Write three functions that each return a dangling reference in a different way, and run them under ASan with detect_stack_use_after_return=1.
  2. Explain why const auto& x = f().member; is safe if f() returns by value but unsafe if f() returns a reference to a short-lived object.
Key takeaways
  • An object may only be used between the end of its construction and the start of its destruction.
  • Pointers carry provenance, so arithmetic must stay inside the original allocation.
  • Reusing storage needs placement new and std::launder care, and is mostly a library-writer's concern.
