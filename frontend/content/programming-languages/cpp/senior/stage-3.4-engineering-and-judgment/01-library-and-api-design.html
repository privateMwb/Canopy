Library & API Design

A good API makes correct use easy and misuse hard, states ownership and error behavior in its signatures, and can evolve without breaking its users.

§1Express Ownership and Intent in the Signature

The function signature is the contract. A reader should know who owns what, who may modify it, and whether it can fail without reading the body.

void render(const Scene& s);                    // reads only, doesn't keep it
void setName(std::string name);                 // takes a copy or moves from the caller
std::unique_ptr<Widget> create();               // caller owns the result
void adopt(std::unique_ptr<Widget> w);          // takes ownership
Widget* find(std::string_view id) const;        // non-owning, may be null: document the lifetime
[[nodiscard]] std::expected<Config, Error> load(const path& p);   // can't be silently ignored

Prefer value and const& parameters, return values over out-parameters, and [[nodiscard]] on functions whose result must be used. Use explicit constructors, enum class, and strong types (struct UserId { int v; };) so arguments can't be silently swapped.

§2Make Misuse Hard

Design the type so invalid states can't be represented, and errors show up at compile time.

// Easy to misuse: which is width, which is height, which is the unit?
void resize(int, int, bool);
// Hard to misuse:
struct Size { Pixels width; Pixels height; };
enum class Aspect { Keep, Ignore };
void resize(Size, Aspect);

Builder or options structs with designated initializers (C++20) beat long parameter lists: connect({.host = "db", .port = 5432, .timeout = 2s}).

§3Error Reporting Policy

Pick one error strategy for the library and document it: exceptions, std::expected, or error codes. Exceptions that cross a library boundary need the same compiler and settings on both sides. Keep failure modes in the signature when callers are expected to handle them. State preconditions and whether violating them is checked or undefined.

§4Header Design and Compile-Time Cost

Headers are part of the API and part of every user's build time.

  • Include only what you need; forward-declare types used by reference or pointer.
  • Keep headers self-contained: each compiles on its own (a test that includes each header first catches this).
  • Hide implementation behind the pimpl idiom when you want freedom to change it without recompiling users.
  • Put public headers in a namespaced directory (include/mylib/foo.h) and keep internals in detail or private directories.

§5Evolving Without Breaking

Once published, assume someone depends on every public name and behavior.

  • Add, don't change: new overloads and optional parameters over altering existing ones.
  • Deprecate with [[deprecated("use bar() instead")]] for at least one release before removal.
  • Follow semantic versioning, where ABI-breaking changes require a major version and a documented rebuild.
  • Test the API from the user's side: examples and tests that only use the public headers.
The key insight Write the usage code before the implementation. If the example calling your API looks awkward or needs comments to explain, the interface is wrong, and it is much cheaper to change now.

§6Common Mistakes

MistakeWhat HappensFix
Returning raw owning pointers or accepting ones that mean "I take ownership"Ownership unclear, leaksUse unique_ptr for transfer and references or string_view/span for borrows
Several adjacent parameters of the same typeArguments swapped silentlyStrong types or an options struct
Putting implementation details in public headersUsers depend on them; every change forces rebuildsPimpl or a detail namespace, and keep headers minimal
Practice
  1. Redesign a function with signature bool send(char*, int, int, bool) into a safer one, and write the call site first.
  2. Write a test that includes every public header on its own and compile it with -Wall -Wextra.
Key takeaways
  • Ownership, mutability, and failure should be visible in each signature.
  • Make invalid states unrepresentable, and prefer strong types and options structs to long parameter lists.
  • Treat published headers as frozen, deprecating before removing, and write the user's code first.
