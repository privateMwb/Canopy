Debugging Crashes

A crash is data: a core dump or a stack trace tells you where a program died, and a methodical approach gets you from that to the root cause, even when you can't reproduce it.

§1Prepare to Be Debuggable

Build with symbols even in release (-g with -O2, or RelWithDebInfo), keep the matching binaries and debug info for every shipped version, and avoid stripping them from the build artifacts you keep. Without symbols a stack trace is raw addresses.

g++ -O2 -g -fno-omit-frame-pointer app.cpp -o app
ulimit -c unlimited                      # allow core dumps in this shell
cat /proc/sys/kernel/core_pattern        # where cores go (may be systemd-coredump: coredumpctl)

§2Reading a Core Dump with gdb or lldb

A core file is a snapshot of the process memory at the crash. Load it alongside the exact binary that produced it.

gdb ./app core
(gdb) bt                    # backtrace of the crashing thread
(gdb) thread apply all bt   # all threads: look for deadlocks and the odd one out
(gdb) frame 3               # select a frame
(gdb) info locals
(gdb) print *this
(gdb) print vec.size()      # inspect objects (pretty printers help with STL types)
(gdb) x/16xb ptr            # raw memory

lldb equivalents: lldb ./app -c core, bt, bt all, frame select 3, frame variable, p *this. Read the stack from the top: the crash site is often a symptom, and the cause is a few frames up or in memory corrupted much earlier.

§3Interpreting Common Crashes

  • SIGSEGV near address 0 (e.g. 0x8): null pointer dereference; find which pointer was null in the frame.
  • SIGSEGV with a wild or recently freed address: use-after-free or corruption. Reproduce under ASan.
  • SIGABRT inside malloc/free: heap corruption detected; the damage happened earlier.
  • terminate called after throwing: an uncaught exception or a noexcept violation; the stack shows the throw site.
  • Stack overflow: thousands of near-identical frames; look for unbounded recursion.
  • Hang: attach (gdb -p PID) and run thread apply all bt to see where threads wait.

§4When You Can't Reproduce It

1. Collect crash reports in production (Breakpad/Crashpad, systemd-coredump, a crash service) with the build ID, so each report maps to its symbols. 2. Group by stack signature to find the frequent ones. 3. Form a hypothesis from the stack and the memory state; then try to reproduce with sanitizers, a stress test, fuzzing, or changed timing. 4. For flaky concurrency bugs, use TSan. For heap bugs, ASan or Valgrind. For "what happened before the crash," record and replay with rr (rr record ./app, rr replay) and step backwards. 5. Add logging or assertions near the suspect area, and ship them. asserts with messages and a signal handler that prints a stack trace (or std::stacktrace in C++23) help turn silent corruption into an early, informative crash.

The key insight The crash site is where the damage was noticed, not where it was done. Use sanitizers and reverse debugging to move from "where did it die" to "who corrupted this."

§5Common Mistakes

MistakeWhat HappensFix
Debugging a core with a different binary than the one that crashedWrong symbols and nonsense stacksKeep the exact build and its debug info, matched by build ID
Stopping at the top frameFixes the symptom (a null check) and leaves the causeTrace why the value was null or the pointer invalid
Debugging optimized code and trusting print of variablesValues may be optimized out or staleBuild -Og/-O1 -g for investigation, or use rr
Practice
  1. Write a program that dereferences a dangling pointer, make it dump core, and find the faulty line with gdb.
  2. Reproduce the same bug under ASan and compare what it tells you with the core dump.
Key takeaways
  • Ship builds with symbols retained, and enable core dumps or crash reporting.
  • Read stacks from the top, but look for the earlier cause of corrupted state.
  • Use sanitizers, TSan, and rr to turn an unreproducible crash into a reproducible one.
