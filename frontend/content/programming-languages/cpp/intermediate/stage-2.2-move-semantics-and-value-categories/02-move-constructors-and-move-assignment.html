Move Constructors & Move Assignment

A move constructor takes over another object's resource in constant time and leaves the source safe to destroy, so returning and storing big objects stops being expensive.

§1Why Moves Exist

Copying a std::vector of a million elements copies a million elements. If the source is a temporary that is about to be destroyed, it's wasteful. A move transfers ownership of the buffer: a pointer copy and a reset.

class Buffer {
    int* data_{nullptr};
    std::size_t n_{0};
public:
    explicit Buffer(std::size_t n) : data_{new int[n]{}}, n_{n} {}
    ~Buffer() { delete[] data_; }

    Buffer(const Buffer& o) : data_{new int[o.n_]}, n_{o.n_} {      // copy: deep
        std::copy(o.data_, o.data_ + n_, data_);
    }
    Buffer(Buffer&& o) noexcept                                      // move: steal
        : data_{std::exchange(o.data_, nullptr)}, n_{std::exchange(o.n_, 0)} {}
};

std::exchange(x, v) returns the old value of x and assigns v, a tidy way to steal and null out in one step.

§2Move Assignment

The move assignment operator must free what the target already owns, take the source's resource, and leave the source valid.

Buffer& operator=(Buffer&& o) noexcept {
    if (this != &o) {
        delete[] data_;                          // release our old resource
        data_ = std::exchange(o.data_, nullptr);
        n_    = std::exchange(o.n_, 0);
    }
    return *this;
}

The self-assignment check matters: a = std::move(a) must not leave a empty.

§3The Moved-From State

After a move, the source must still be valid: its destructor must work, and assignment must work. It need not hold any particular value. Setting the pointer to nullptr and size to zero achieves that, since delete[] nullptr is safe.

Buffer a{100};
Buffer b = std::move(a);      // b owns the memory; a is empty but destructible
a = Buffer{5};                // assignment to a moved-from object is fine

§4When You Get Moves for Free

If a class follows the Rule of Zero and holds only members that are themselves movable, the compiler-generated move operations are correct. The compiler only generates moves when you declare none of the copy operations or destructor, so declaring any of those turns off the automatic moves.

The key insight Move operations should be cheap and noexcept. Moving usually just copies pointers and nulls the source, which can't fail, and declaring it noexcept lets containers use it (see the next lessons).

§5Common Mistakes

MistakeWhat HappensFix
Forgetting to null out the source's pointerBoth objects free the same memory: double freeUse std::exchange or set the source to nullptr
Writing a destructor and expecting automatic movesMove operations aren't generated; copies are used insteadDeclare them = default or write them
Forgetting noexcept on move operationsstd::vector falls back to copying on growthMark moves noexcept
Practice
  1. Add move operations to your Buffer and add a counter to show copies vs. moves when pushing 10 Buffers into a vector.
  2. Delete the move constructor's null-out step, run under ASan, and read the double-free report.
Key takeaways
  • A move steals a resource and leaves the source valid but empty.
  • Declare move operations noexcept, and handle self-assignment in move assignment.
  • Rule of Zero classes get correct moves for free; declaring a destructor or copy op disables them.
