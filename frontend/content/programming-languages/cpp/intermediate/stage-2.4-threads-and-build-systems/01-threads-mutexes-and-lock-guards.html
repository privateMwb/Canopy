Threads, Mutexes & Lock Guards

A thread runs code concurrently, and any data touched by more than one thread, with at least one writer, needs a mutex or it's a data race and undefined behavior.

§1Starting and Joining Threads

std::thread begins running its callable immediately. You must join() (wait) or detach() it before the thread object is destroyed, or the program calls std::terminate.

#include <thread>
void work(int id) { std::cout << "worker " << id << '\n'; }
int main() {
    std::thread t1{work, 1};
    std::thread t2{[] { work(2); }};
    t1.join();
    t2.join();
}

Arguments are copied into the thread. To pass by reference you must say so with std::ref(x), and make sure x outlives the thread. Link with -pthread on Linux (CMake handles this with Threads::Threads).

§2Data Races

A data race happens when two threads access the same memory at once and at least one writes. It is undefined behavior, not merely a wrong number.

int counter{0};
auto inc = [&] { for (int i = 0; i < 100000; ++i) ++counter; };
std::thread a{inc}, b{inc};
a.join(); b.join();
std::cout << counter << '\n';        // not 200000: lost updates, and UB

++counter is a read, an add, and a write, so two threads can read the same value and both write back one more.

§3Mutexes and lock_guard

A std::mutex lets one thread at a time into a critical section. Never call lock() and unlock() by hand; use an RAII guard so the mutex is released on every path, including exceptions.

std::mutex m;
int counter{0};
auto inc = [&] {
    for (int i = 0; i < 100000; ++i) {
        std::lock_guard<std::mutex> lock{m};        // locks here, unlocks at scope end
        ++counter;
    }
};

Use std::scoped_lock lock{m1, m2}; to lock several mutexes at once with a deadlock-avoidance algorithm. Use std::unique_lock when you need to unlock early, or to pair with a condition variable. Keep the critical section small: hold the lock for the shared-state access, not for slow work like I/O.

§4Protecting Data by Design

Tie the data to its mutex in one class so callers can't touch it without locking.

class SafeCounter {
    mutable std::mutex m_;
    int n_{0};
public:
    void increment() { std::lock_guard lock{m_}; ++n_; }
    int get() const { std::lock_guard lock{m_}; return n_; }
};

Don't return references to protected data from inside the class, or the lock stops protecting it. Locking two mutexes in different orders in different threads causes deadlock, so always lock multiple mutexes together with scoped_lock.

The key insight A mutex protects data only if every access to that data takes the same mutex. Bugs here are intermittent, and the program may pass tests for months, so run ThreadSanitizer (covered in this stage's last lesson).

§5Common Mistakes

MistakeWhat HappensFix
Destroying a joinable std::threadstd::terminate is calledjoin() it, or use std::jthread
Calling lock()/unlock() manuallyAn exception or early return leaves the mutex lockedUse lock_guard/scoped_lock
Capturing a local by reference in a detached threadThe local dies while the thread still runsCapture by value, or join before leaving scope
Practice
  1. Reproduce the lost-update counter, then fix it with a mutex, and time both versions with 4 threads.
  2. Write a thread-safe queue class with push and try_pop guarded by one mutex.
Key takeaways
  • Unsynchronized shared writes are data races, which are undefined behavior.
  • Guard shared state with a mutex through lock_guard or scoped_lock, never manual lock/unlock.
  • Join every thread, and keep critical sections short.
