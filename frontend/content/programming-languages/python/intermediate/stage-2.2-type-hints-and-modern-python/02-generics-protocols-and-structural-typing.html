Generics, Protocols & Structural Typing

Generics let one function or class work over many types without losing track of them, and Protocols describe what an object can do instead of what it inherits from.

§1Generic Functions with TypeVar

If a function returns the same kind of thing it receives, a plain annotation can't say so. A type variable can.

from typing import TypeVar, Sequence

T = TypeVar("T")

def first(items: Sequence[T]) -> T:
    return items[0]

n = first([1, 2, 3])        # checker infers int
s = first("abc")            # checker infers str

Python 3.12 added a shorter syntax with no import: def first[T](items: Sequence[T]) -> T:.

§2Generic Classes

from typing import Generic, TypeVar

T = TypeVar("T")

class Box(Generic[T]):
    def __init__(self, item: T) -> None:
        self.item = item

    def get(self) -> T:
        return self.item

b = Box(42)
reveal_type(b.get())         # checker shows: int  (reveal_type is for checkers)

With 3.12+ syntax, this is class Box[T]: with no Generic import. Constrain a variable with TypeVar("N", int, float) or a bound such as bound=Comparable.

§3Protocols: Structural Typing

Normal (nominal) typing asks "does this class inherit from X?" A Protocol asks "does it have the right methods?", which matches duck typing. Nothing needs to inherit from the protocol.

from typing import Protocol

class SupportsClose(Protocol):
    def close(self) -> None: ...

def shutdown(resource: SupportsClose) -> None:
    resource.close()

class Connection:
    def close(self) -> None:
        print("closed")

shutdown(Connection())        # OK: Connection has close(), no inheritance needed
shutdown(open("f.txt"))       # OK: file objects have close()
shutdown(42)                  # checker error: int has no close()

Mark a protocol @runtime_checkable if you want isinstance checks, which verify only that the methods exist, not their signatures.

§4Callables and Abstract Bases

from collections.abc import Callable, Iterable, Mapping

def apply_all(funcs: Iterable[Callable[[int], int]], x: int) -> list[int]:
    return [f(x) for f in funcs]

Accept the most general type you need (Iterable, Mapping) for parameters, and return concrete types (list, dict) so callers know what they get. For an inheritance-based contract with enforcement, abc.ABC and @abstractmethod remain available.

The key insight A Protocol lets the *caller* of an API stay independent of it. Your library can define "anything with read() and close()" and users never have to subclass or import your classes.

§5Common Mistakes

MistakeWhat HappensFix
Annotating a parameter as list[int] when you only iterate itRejects tuples, sets, and generatorsUse Iterable[int] or Sequence[int]
Forgetting that a Protocol method body is ...Unnecessary code in the protocolLeave bodies as ...; they define shape only
Using isinstance with a non-runtime protocolTypeErrorAdd @runtime_checkable or avoid the runtime check
Practice
  1. Write a generic Stack[T] class with push, pop, and peek, and confirm with reveal_type that Stack[int]().pop() is int.
  2. Define a Drawable protocol with draw() and write a function that accepts any list of drawable objects.
Key takeaways
  • TypeVar ties input and output types together; generic classes carry a type parameter.
  • A Protocol matches by structure (methods and attributes), not by inheritance.
  • Accept general abstract types such as Iterable and return concrete ones such as list.
