Reading Errors & Debugging

A traceback is a map to your bug, and print and pdb are the two tools for confirming what really happened.

§1Read a Traceback Bottom-Up

A traceback lists the call stack, oldest call first. The last line names the exception type and message; the lines above show where it happened. Start at the bottom, then read upward to the first frame in your own code.

Traceback (most recent call last):
  File "stats.py", line 9, in <module>
    print(average([]))
  File "stats.py", line 5, in average
    return sum(nums) / len(nums)
ZeroDivisionError: division by zero

The cause is in average (line 5), but the *reason* is the caller passing an empty list. Common exception types: SyntaxError, NameError (undefined name), TypeError (wrong type), ValueError (right type, bad value), KeyError, IndexError, AttributeError.

§2Print Debugging

Printing is fast and legitimate. Print the values you assumed, with labels, using repr so whitespace and types are visible. The = specifier in f-strings (Python 3.8+) prints the expression and its value.

def average(nums):
    print(f"{nums=} {len(nums)=}")    # nums=[] len(nums)=0
    return sum(nums) / len(nums)

Remove debug prints before committing, or switch to the logging module (covered in Stage 2.4).

§3Stepping with pdb

breakpoint() pauses execution and opens the debugger at that line.

def average(nums):
    breakpoint()
    return sum(nums) / len(nums)
CommandWhat it does
nrun the next line
sstep into a call
ccontinue to the next breakpoint
p exprprint an expression
llist source around the current line
qquit

You can also run python3 -m pdb script.py to debug from the first line, or after a crash use python3 -m pdb -c continue script.py to land at the failure point.

The key insight Don't guess. Form a hypothesis ("nums is empty here"), then use a print or breakpoint to confirm or kill it. Debugging is controlled experiments, not staring.

§4Common Mistakes

MistakeWhat HappensFix
Reading a traceback from the topYou fixate on irrelevant entry-point framesRead the last line first, then the nearest frame in your own code
Catching the exception just to silence itThe bug survives, hiddenFix the cause; catch only errors you can handle
Leaving breakpoint() in committed codeThe program hangs waiting for input in productionRemove it, or set PYTHONBREAKPOINT=0
Practice
  1. Create a script that raises KeyError three calls deep, and write down which frame holds the real mistake.
  2. Put a breakpoint() inside a loop, step through two iterations with n, and inspect a variable with p.
Key takeaways
  • Read tracebacks from the bottom: exception type and message first, then your nearest frame.
  • Print with labels (f"{x=}") to test one hypothesis at a time.
  • breakpoint() and pdb let you pause, inspect, and step through live state.
