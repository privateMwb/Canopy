Dependency Management & Supply Chain

Every dependency is code you run with your own privileges, so pin what you ship, audit what you pull in, and choose dependencies deliberately.

§1Declaring vs. Locking

  • Declared dependencies (in pyproject.toml) state what your code is compatible with, usually as ranges: requests>=2.31,<3.
  • A lockfile records the exact resolved versions of everything, including indirect dependencies, so every install is identical.

Libraries publish ranges (so they combine with other packages); applications and services commit lockfiles (so builds are reproducible).

uv lock                                # resolve and write uv.lock
uv sync --frozen                       # install exactly what's locked
python -m pip install pip-tools
pip-compile pyproject.toml -o requirements.txt --generate-hashes
python -m pip install --require-hashes -r requirements.txt

Tools such as uv, pip-tools, Poetry, and PDM each produce lockfiles. A newer standard lockfile format, pylock.toml (PEP 751), is emerging for interoperability, so check what your tools support.

§2Hash Pinning

With hashes in the lockfile, pip refuses any artifact whose digest doesn't match. If an attacker replaces a package file or a mirror serves something different, the install fails instead of running it.

requests==2.32.3 \
    --hash=sha256:<digest of the exact file you reviewed>

Hashes protect against tampering after the fact; they don't tell you whether the version you pinned was safe to begin with.

§3Auditing and Updating

python -m pip install pip-audit
pip-audit -r requirements.txt           # checks against known vulnerability databases
pip list --outdated

Automate updates with a bot (Dependabot or Renovate) that opens pull requests, and let CI test each one. Update regularly in small steps rather than rarely in big leaps. Scan for known vulnerabilities in CI, and subscribe to security advisories for your key dependencies.

§4Supply-Chain Threats

  • Typosquatting: a malicious package named like a popular one (reqeusts). Copy install commands from official docs.
  • Dependency confusion: a public package with the same name as your private one wins resolution. Configure indexes so private names resolve only from your index.
  • Compromised maintainers or releases: a legitimate package ships malicious code. Pinning, review of diffs for sensitive updates, and not auto-installing the newest release within minutes of publication all reduce exposure.
  • Build-time code execution: installing an sdist can run arbitrary code. Prefer wheels where possible.
  • PyPI supports Trusted Publishing and attestations, which help consumers verify where a release came from.

§5Choosing What to Depend On

Before adding a dependency, ask:

  • Does the standard library or ten lines of our own code do it?
  • Is it maintained, widely used, and released recently, with a responsive security process?
  • How big is its transitive tree, and what licenses come with it?
  • Could we wrap it behind our own small interface, so swapping it later is cheap?

Each dependency is a long-term relationship, so treat adding one as a design decision, not a convenience.

The key insight Convenience and risk both scale with the number of dependencies. The question isn't "is there a package for this?" but "is this package worth trusting with our production systems for years?"

§6Common Mistakes

MistakeWhat HappensFix
Deploying from loose ranges with no lockfileDifferent builds get different versions, and "it worked yesterday" bugsCommit a lockfile and install from it
Pinning exact versions in a published libraryUsers hit unsolvable conflictsUse compatible ranges for libraries
Never updating pinned dependenciesKnown vulnerabilities pile upAutomate update PRs and audit in CI
Practice
  1. Generate a hash-pinned requirements file for a small project and install it with --require-hashes in a clean venv.
  2. Run pip-audit on a project, and for the first finding, trace which direct dependency pulls it in.
Key takeaways
  • Libraries declare ranges; applications commit lockfiles, ideally with hashes.
  • Audit and update continuously, with automation and CI checking each change.
  • Evaluate each dependency for maintenance, size, and trust, and isolate it behind your own interface when it matters.
