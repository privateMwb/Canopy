Upgrading Python & Migrating Large Codebases

Upgrading a runtime or adopting new practices across a big repository is mostly a risk-management exercise: small steps, strong tests, and automation.

§1Why Upgrade

Each Python release is supported for about five years: roughly two years of bug-fix releases, then security fixes only until end of life. After end of life, vulnerabilities go unpatched. Newer versions are also typically faster and add language and library improvements. Plan upgrades as routine maintenance, ideally yearly, rather than as a rare emergency.

§2A Safe Upgrade Process

  • Read the changelog and deprecation notes: the "What's New" pages list removed modules and changed behavior. Features that emit DeprecationWarning today are the ones that will break later.
  • Surface warnings now: run the test suite with -W error::DeprecationWarning on the *current* version, and fix what it finds.
  • Check dependencies: confirm each has releases supporting the target version, including compiled wheels. Packages with C extensions are the usual blockers.
  • Add the new version to the CI matrix alongside the old one, and make it required once green.
  • Upgrade one minor version at a time (3.10 to 3.11 to 3.12), not several at once, so failures point to a single change.
  • Roll out gradually: canary instances, a fraction of traffic, then everything, with a quick rollback.
strategy:
  matrix:
    python-version: ["3.11", "3.12", "3.13"]     # old, current, next

Typical breakage categories: removed standard-library modules, stricter parsing, changed default behaviors (such as the multiprocessing start method), dependency incompatibilities, and subtle numeric or ordering differences.

§3Automating Large Changes

When a change touches thousands of files, hand-editing doesn't scale and doesn't stay consistent.

ruff check --select UP --fix .          # pyupgrade rules: modernize syntax automatically
ruff check --select UP --target-version py311 --diff .
python -m pip install libcst            # write custom codemods that preserve formatting

Use codemods (LibCST, ruff, pyupgrade, bowler-style tools) for mechanical rewrites. Land them as separate, reviewable, behavior-neutral pull requests, apart from functional changes, so reviewers can check the transformation rather than every line.

§4Adopting Types Gradually

  • Start with a baseline: run the checker, and record existing errors so new code is held to the standard while old errors are burned down over time.
  • Enforce strictness per module (as covered in Stage 2.2) and add modules as they're cleaned.
  • Type the boundaries first: public functions, data models, and widely imported utilities.
  • Track progress with a simple metric, such as the share of annotated functions or modules passing strict mode.

§5Managing Risk Across a Big Repo

  • Tests are your safety net. If coverage is thin, write characterization tests (record current behavior) before changing things.
  • Feature flags and dual-running let you compare old and new paths in production before switching.
  • Small, frequent, reversible steps beat one heroic migration. Each should be shippable on its own.
  • Communicate: document the plan, owners, and deadlines, and say what developers must do differently.
  • Decide an explicit end state and a cutoff date for the old way; otherwise the migration never finishes.
The key insight A migration is a project with a plan, metrics, and an end date, not a heroic weekend. Automate the mechanical parts, keep each step reversible, and let CI prove each step.

§6Common Mistakes

MistakeWhat HappensFix
Skipping minor versions in one jumpA pile of failures with unclear causesUpgrade one minor version at a time and keep CI green at each

Mixing mechanical rewrites with behavior changes in a single PRReviewers can't verify eitherSeparate codemod PRs from functional ones
Practice
  1. Run your project's tests with -W error::DeprecationWarning on its current Python version and list what breaks.
  2. Use ruff check --select UP --diff on a repo to preview modernizing changes, and categorize which are safe to apply automatically.
Key takeaways
  • Upgrade on a schedule, one minor version at a time, with CI covering old and new versions.
  • Use codemods for mechanical changes, kept in separate reviewable pull requests.
  • Migrate in small reversible steps with tests, flags, and a defined end state.
