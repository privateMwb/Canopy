When Python Is the Wrong Tool

Python is an excellent default, but an honest engineer can name the cases where its limits in speed, deployment, or correctness outweigh its strengths.

§1What Python Is Best At

Python wins on productivity: readable code, a vast ecosystem (data, ML, web, automation, scientific computing), quick iteration, and a large hiring pool. For a huge share of systems, whose time goes to waiting on databases and networks, developer time is the scarce resource and Python's speed is not the bottleneck. It's also the glue of the data and AI world: much of the core numerical work happens in compiled libraries that Python orchestrates.

§2Where the Limits Bite

Performance

  • Pure-Python CPU-bound code is typically tens of times slower than compiled languages like Go, Rust, or C++.
  • Standard CPython threads don't run Python code in parallel, though processes, native libraries, and the free-threaded builds help.
  • Per-object memory overhead is high, which matters with hundreds of millions of small objects.
  • Tail latency and startup time can matter for tiny serverless functions or CLIs started thousands of times.

Deployment

  • Shipping a single static binary is awkward, and bundlers produce large artifacts with caveats.
  • You must manage the interpreter version and dependencies (containers and lockfiles solve this, at a cost).
  • Native dependencies add platform-specific build problems.
  • Distributing proprietary code to untrusted machines offers weak protection, since source and bytecode are easily recovered.

Correctness and maintainability

  • Dynamic typing defers errors to runtime. Hints and checkers recover much of the safety, but only where you invest in them.
  • Large codebases with many contributors need discipline: types, tests, and linting aren't optional.
  • No compile-time guarantees against data races or null dereferences.
  • Hard real-time requirements, memory-constrained embedded devices, and kernel or driver code are poor fits.

§3Weighing It Honestly

A structured way to decide:

QuestionPoints toward PythonPoints away
Where does the time go?waiting on I/O, databases, other servicestight CPU loops with no library to do the work
What's the team's expertise?strong Python and ecosystem familiaritya team fluent in another stack, with no reason to switch

What does the ecosystem offer?mature libraries for the domain (ML, data, web)the best libraries live in another language

§4Hybrid Answers

The choice isn't binary. Common, defensible architectures: Python for orchestration and business logic with Rust, C++, or NumPy for the hot kernels; Python for the control plane and Go for the data plane; Python for prototyping and a rewrite of the one component that proves performance-critical. Measure first, because teams often rewrite whole services for a bottleneck that sits in one function or one query. Also weigh the cost of a rewrite: new bugs, lost institutional knowledge, and the opportunity cost of features not shipped. A Python service that's "fast enough" and understood beats a faster one nobody can maintain.

The key insight A good language-choice argument names a concrete requirement, a measured result, and a cost for each option. "Python is slow" and "Python is productive" are both incomplete without numbers and context.

Practice
  1. Pick a system you know and write a table of its real constraints (latency target, deployment target, team skills), then say where Python fits and where it doesn't.
  2. Find one piece of a Python system that could be replaced by a compiled component, estimate the benefit from a profile, and list the costs of doing so.
Key takeaways
  • Python optimizes for developer productivity and ecosystem breadth; its limits are CPU-bound speed, distribution, and compile-time guarantees.
  • Decide from measured constraints (where time goes, who deploys it, who maintains it), not from reputation.
  • Hybrid designs, with native components behind a Python layer, often beat full rewrites.
