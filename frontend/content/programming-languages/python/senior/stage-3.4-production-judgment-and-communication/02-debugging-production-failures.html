Debugging Production Failures

You can't attach a debugger to production, so the evidence has to already be there: structured logs, tracebacks with context, metrics, and a method for reading them.

§1Structured Logging

Plain-text lines are hard to search at scale. Emit one JSON object per line with consistent fields, and include a correlation ID tying together everything from one request.

import contextvars, json, logging, uuid

request_id = contextvars.ContextVar("request_id", default="-")

class JsonFormatter(logging.Formatter):
    def format(self, record):
        payload = {
            "ts": self.formatTime(record),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
            "request_id": request_id.get(),
        }
        if record.exc_info:
            payload["exc"] = self.formatException(record.exc_info)
        return json.dumps(payload)

handler = logging.StreamHandler()
handler.setFormatter(JsonFormatter())
logging.getLogger().addHandler(handler)
logging.getLogger().setLevel(logging.INFO)

def middleware(request):
    request_id.set(request.headers.get("X-Request-ID", uuid.uuid4().hex))

contextvars carry the ID through both threads and async tasks correctly, where a global variable would mix requests together. Libraries such as structlog offer this pattern ready-made. Never log secrets, tokens, or personal data.

§2Tracebacks in the Wild

Log exceptions with log.exception(...) so the traceback is captured, and don't log and re-raise at every layer, which duplicates entries. Handle or log at one boundary, such as the request handler.

try:
    charge(order)
except PaymentError as err:
    log.error("charge failed", extra={"order_id": order.id})
    raise OrderFailed(order.id) from err        # keeps the original cause visible

Read chained tracebacks from the bottom, but follow "The above exception was the direct cause of..." upward to find the root. Error trackers such as Sentry group occurrences and capture local variable context, release version, and request details, which reproduce what a debugger would show.

§3Reading Evidence Systematically

When an incident arrives, work like an investigator:

  • Define the symptom precisely: which endpoint, what error or latency, when it began, and who is affected.
  • Correlate with changes: deploys, config changes, traffic shifts, dependency incidents. "What changed?" resolves many cases.
  • Look at the metrics first: error rate, latency percentiles, saturation of CPU, memory, connections, and queues; then drill into logs from an affected request ID.
  • Form a hypothesis that predicts something you can check, then check it.
  • Mitigate before you fully diagnose: roll back, shed load, or disable a feature, and then find the root cause calmly.

§4Tools for Live Systems

  • py-spy dump shows what every thread is doing now.
  • faulthandler prints tracebacks on a crash, signal, or timeout: faulthandler.enable(), and faulthandler.register(signal.SIGUSR1) for an on-demand dump.
  • Log memory and open file descriptors trends, and use tracemalloc snapshots for suspected leaks.
  • Feature flags and sampling let you turn on verbose logging for one user or percentage of traffic without a deploy.
  • Keep reproducible evidence: save the failing request payload (scrubbed), and write the regression test before fixing.
The key insight The best production debugging happens before the incident: logs with request IDs, metrics for the four golden signals (latency, traffic, errors, saturation), and a deploy history. Without them, you're guessing.

§5Common Mistakes

MistakeWhat HappensFix
Logging free-form strings with no correlation IDYou can't follow one request across servicesUse structured logs and a request ID in a ContextVar
Logging and re-raising at every layerDuplicate entries obscure the real sequenceLog once, at the boundary that handles the error
Fixing without a regression testThe bug returns laterCapture the failing case as a test first
Practice
  1. Add a JSON formatter and request-ID ContextVar to a small app, and confirm the ID appears on every log line of one request, including inside async tasks.
  2. Enable faulthandler with a SIGUSR1 handler in a test script, trigger it during a sleep, and read the resulting stack dump.
Key takeaways
  • Emit structured logs with a correlation ID carried by contextvars.
  • Log exceptions once at the right boundary and preserve causes with raise ... from.
  • Investigate by symptom, change history, and metrics; mitigate first, then root-cause and add a regression test.
