Python Services in Production

A Python web service's throughput depends on its server interface, its worker model, and what each request waits for, so size and shape it deliberately.

§1WSGI vs. ASGI

  • WSGI is the older, synchronous interface: one request occupies one worker (a process or thread) until it completes. Flask and Django run on it, served by Gunicorn or uWSGI.
  • ASGI supports async code, WebSockets, and long-lived connections. FastAPI, Starlette, and Django's async mode run on it, served by Uvicorn, Hypercorn, or Granian.
# ASGI app
from fastapi import FastAPI

app = FastAPI()

@app.get("/users/{uid}")
async def get_user(uid: int):
    return await fetch_user(uid)       # awaits don't block other requests
uvicorn app:app --host 0.0.0.0 --port 8000 --workers 4
gunicorn app:app -k uvicorn.workers.UvicornWorker -w 4

Neither is universally better. Async frameworks excel at many concurrent, I/O-bound requests, but one blocking call stalls everything on that worker. Synchronous frameworks are simpler to reason about, with the cost of more workers for the same concurrency.

§2Worker Models and Capacity

In standard CPython, one process uses roughly one core for Python code, so you scale with multiple worker processes, usually near the core count, behind a load balancer or process manager.

  • Sync workers (processes): concurrency equals the number of workers. Slow downstream calls tie up a worker, so budget for the *p99* latency of calls, not the average.
  • Threaded workers: more concurrency per process for I/O-bound work, with the usual thread-safety care.
  • Async workers: thousands of concurrent waits per process, if nothing blocks.

Memory multiplies by worker count. Many servers fork workers after loading the app (preloading) so memory pages are shared copy-on-write, though Python's reference counting touches pages and erodes that sharing over time. Restarting workers periodically (--max-requests in Gunicorn) is a pragmatic guard against slow leaks.

§3What Actually Limits Throughput

Measure rather than assume. Typical limits, in rough order of how often they bite:

  • The database: slow queries, missing indexes, connection pool exhaustion. This is the most common bottleneck.
  • Downstream services: no timeouts, no limits on retries, and retry storms.
  • Serialization and validation: building huge JSON responses; Pydantic models for large payloads.
  • Python CPU time per request: template rendering, data processing in the request path.
  • Blocking in async code, and a thread pool that is too small.

Use Little's Law to size: concurrency in flight = request rate × latency. At 200 requests per second with 100 ms latency, you need about 20 requests in flight, so 20 sync workers, or fewer async workers each holding many.

§4Deployment Shape

  • Run in a container with a pinned Python and a locked dependency set.
  • Put a reverse proxy (nginx, a load balancer) in front for TLS, buffering slow clients, and static files.
  • Provide health and readiness endpoints, and handle SIGTERM for graceful shutdown: stop accepting, finish in-flight requests, then exit.
  • Set resource limits and watch memory, CPU, event-loop lag, and queue depth.
  • Move slow or retryable work (emails, reports) to a background worker with a queue (Celery, RQ, Dramatiq, or a cloud queue) so requests return fast.
  • Configure everything through the environment, and keep logs on stdout in a structured format.
The key insight Production performance is mostly about waiting: on the database, on other services, on slow clients. Pick the concurrency model that matches what your requests wait for, and measure with real traffic shapes.

§5Common Mistakes

MistakeWhat HappensFix
Running Flask's development server in productionNot built for load or securityUse Gunicorn or Uvicorn behind a proxy
Using blocking database or HTTP clients inside async def handlersOne slow call freezes the workerUse async clients, or run the handler as a regular def so the framework offloads it to a thread
Sizing workers by guessworkOver-provisioned memory or timeouts under loadEstimate with request rate × latency, then load-test
Practice
  1. Load-test a small FastAPI or Flask app with different worker counts and note where throughput stops improving.
  2. Add SIGTERM handling or a graceful shutdown configuration and verify that an in-flight request completes during a deploy.
Key takeaways
  • WSGI is synchronous per worker; ASGI supports async and long-lived connections; choose by workload.
  • Scale CPython services with multiple worker processes, and size using request rate times latency.
  • The database and downstream calls usually limit throughput before Python does.
