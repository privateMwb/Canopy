The GIL, Free-Threading & the JIT

Recent CPython releases add an optional free-threaded build and an experimental JIT, and it's worth knowing exactly what each changes for your code and what it doesn't.

§1Why the GIL Exists

The GIL protects CPython's internals, especially reference counts, with one lock instead of fine-grained ones. That kept single-threaded code fast and C extensions simple, at the price of limiting pure-Python threads to one core at a time. Earlier lessons covered the effects: threads help I/O, processes help CPU work.

§2The Free-Threaded Build

PEP 703 made the GIL optional. A free-threaded build of CPython (installed separately, usually named python3.13t or python3.14t) runs Python threads truly in parallel on multiple cores. It was experimental in 3.13 and became officially supported in 3.14 (PEP 779), but it is still not the default build.

import sys, sysconfig

print(sysconfig.get_config_var("Py_GIL_DISABLED"))   # 1 in a free-threaded build
print(sys._is_gil_enabled())                          # False when it's really off (3.13+)
# CPU-bound work in threads can now scale across cores on a free-threaded build
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(8) as pool:
    results = list(pool.map(cpu_heavy, chunks))

To make this work without the GIL, the runtime uses techniques such as biased and atomic reference counting and per-object locks.

§3What It Does Not Change

  • Your races are real. The GIL was hiding some timing bugs. Code like counter += 1 on shared state needs a lock, with or without the GIL. Built-in containers stay internally consistent, but multi-step logic is still yours to protect.
  • Single-thread speed can be lower. The free-threaded build has some overhead on single-threaded code, which has shrunk with each release but hasn't vanished.
  • Extension modules must opt in. A C extension that doesn't declare free-threading support causes the interpreter to re-enable the GIL when imported (you can override with PYTHON_GIL=0 or -X gil=0, at your own risk). Check your dependencies before assuming parallel speedups.
  • I/O-bound code was already fine with threads or asyncio.

§4The Experimental JIT

CPython 3.13 introduced an experimental copy-and-patch JIT (PEP 744). It translates hot sequences of specialized bytecode into machine code using pre-built templates. It's off by default and must be enabled at build time and run time (for example, PYTHON_JIT=1). Early gains are modest and workload-dependent, and the design aims for gradual improvement over several releases rather than a dramatic jump.

PYTHON_JIT=1 python3 bench.py        # only if your build includes the JIT

The JIT is separate from free-threading; the two features have their own limitations on combining, so check the current documentation for your version.

§5What to Do With This

  • Don't rewrite working code for either feature. Measure on your real workload.
  • Do write thread-safe code now: use locks, queues, and immutable data, so your code is correct under free-threading when you adopt it.
  • Treat the status of these features as a moving target and read the release notes for your target Python version.
  • For CPU-bound parallelism today, multiprocessing and native libraries remain the proven route.
The key insight Removing the GIL changes performance, not correctness rules. Thread-safe code was always required; free-threading just stops hiding the bugs.

§6Common Mistakes

MistakeWhat HappensFix
Assuming the default Python is GIL-freeNo parallel speedupInstall and verify the free-threaded build, and check sys._is_gil_enabled()
Importing a dependency that silently turns the GIL back onBenchmarks show no gainCheck import warnings and extension support, and test with PYTHON_GIL=0 carefully
Expecting the JIT to speed up every programLittle or no change on many workloadsBenchmark your workload before and after
Practice
  1. Run a CPU-bound threaded benchmark on a regular build and, if available, a free-threaded build, and record both timings and sys._is_gil_enabled().
  2. Review a piece of threaded code you've written and list every shared mutable value that would need a lock without the GIL.
Key takeaways
  • The free-threaded build runs threads in parallel; it's supported from 3.14 but is a separate, non-default build.
  • Race conditions and extension compatibility remain your responsibility.
  • The JIT is experimental and off by default; measure before relying on it.
