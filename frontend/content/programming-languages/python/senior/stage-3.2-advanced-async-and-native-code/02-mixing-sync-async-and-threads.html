Mixing Sync, Async & Threads

Real systems combine blocking libraries, async code, and threads, and the main hazard is stalling the event loop with a call that doesn't yield.

§1Detecting Event-Loop Stalls

Any synchronous call inside a coroutine, whether time.sleep, a requests.get, a big JSON parse, or a CPU loop, blocks every other task until it returns. Symptoms: latency spikes that affect unrelated requests. asyncio's debug mode reports slow callbacks.

asyncio.run(main(), debug=True)           # or env PYTHONASYNCIODEBUG=1
# logs: "Executing <Task ...> took 0.512 seconds"
import time

async def heartbeat():
    while True:
        t = time.perf_counter()
        await asyncio.sleep(0.1)
        lag = time.perf_counter() - t - 0.1
        if lag > 0.05:
            log.warning("event loop lag: %.0f ms", lag * 1000)

A lag monitor like this in a service tells you when something is blocking the loop.

§2Calling Blocking Code from async

Offload it to a thread, or a process for CPU-heavy work.

import asyncio, hashlib

def blocking_read(path):
    with open(path, "rb") as f:
        return f.read()

async def handler(path):
    data = await asyncio.to_thread(blocking_read, path)    # runs in the default thread pool
    return len(data)

from concurrent.futures import ProcessPoolExecutor
pool = ProcessPoolExecutor()

async def checksum_many(blobs):
    loop = asyncio.get_running_loop()
    return await asyncio.gather(*[
        loop.run_in_executor(pool, hashlib.sha256, b) for b in blobs
    ])

Threads suit blocking I/O and C code that releases the GIL. For pure-Python CPU work on a standard build, use processes. The default thread pool is limited in size, so a flood of long to_thread calls queues up.

§3Calling async from Sync

A sync function can't await. At the outermost layer, start a loop with asyncio.run(coro()). You can't call asyncio.run from inside a running loop, so from a worker thread, hand the coroutine to the loop instead.

def from_thread(loop, coro):
    future = asyncio.run_coroutine_threadsafe(coro, loop)
    return future.result(timeout=5)       # blocks THIS thread, not the loop

# loop = asyncio.get_running_loop() was captured in the async side earlier

To notify the loop from another thread, use loop.call_soon_threadsafe(...). Most asyncio objects, such as Queue and Event, are not thread-safe.

§4Bridging Old and New Code

  • Keep the boundary narrow: one adapter layer converts between sync and async, instead of sprinkling to_thread everywhere.
  • Prefer a natively async library for hot paths, and a thread wrapper for rarely used legacy calls.
  • Never hold a threading lock across an await; another task on the same thread could try to acquire it and deadlock the loop. Use asyncio.Lock for coroutine mutual exclusion.
  • Avoid libraries that hide their own asyncio.run() or global loops.
The key insight There is exactly one event loop thread, and its only job is to switch between ready tasks quickly. Anything slow, blocking, or CPU-heavy belongs elsewhere.

§5Common Mistakes

MistakeWhat HappensFix
Calling a blocking function directly in async defThe whole service freezes for the call's durationUse await asyncio.to_thread(...) or an async library
Calling asyncio.run() inside a running loopRuntimeError: asyncio.run() cannot be called from a running event loopawait the coroutine, or use run_coroutine_threadsafe from other threads
Using threading.Lock around an awaitDeadlocks or unfair stallsUse asyncio.Lock
Practice
  1. Add a lag-monitor coroutine to a small server, then insert a time.sleep(1) and watch the warnings; fix it with to_thread.
  2. Write a sync function that submits a coroutine to a loop running in another thread and waits for the result.
Key takeaways
  • Blocking calls in coroutines stall every task; detect with debug mode or a lag monitor.
  • Offload blocking work with to_thread or an executor; use run_coroutine_threadsafe to go from threads into the loop.
  • Keep the sync/async boundary narrow and don't hold thread locks across await.
