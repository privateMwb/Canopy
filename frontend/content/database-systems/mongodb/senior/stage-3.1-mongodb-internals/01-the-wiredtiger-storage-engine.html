The WiredTiger Storage Engine

WiredTiger is MongoDB's default storage engine, and its B-tree structure, document-level concurrency, and compression explain much of how MongoDB performs.

§1What a Storage Engine Does

The storage engine decides how documents and indexes are laid out on disk, how they are cached in memory, and how concurrent operations are coordinated. MongoDB has used WiredTiger as its default engine since version 3.2.

db.serverStatus().storageEngine          // { name: "wiredTiger", ... }
db.orders.stats().wiredTiger             // per-collection engine details

Each collection and each index is stored as its own file in the dbPath directory, and a record id links an index entry to its document.

§2B-Trees, Pages, and Records

WiredTiger stores collections and indexes as B-trees made of pages. Documents are kept as key-value records, where the key is a record id and the value is the BSON document. An index is another tree whose keys are the indexed values and whose values lead back to the record id.

A page is read from disk into the cache, modified in memory, and written back later. Updates do not overwrite pages in place: they are recorded in memory first, and reconciliation writes a new page version when the page is evicted or at a checkpoint. A write therefore costs far less than rewriting a whole disk block.

§3Document-Level Concurrency

WiredTiger uses multiversion concurrency control (MVCC). Each operation reads from a consistent snapshot and writers create new versions of a document, instead of locking the collection. Two clients can update different documents in the same collection at once, and a write conflict arises only when two operations change the same document.

// both succeed in parallel: different documents
db.accounts.updateOne({ _id: "A" }, { $inc: { n: 1 } })
db.accounts.updateOne({ _id: "B" }, { $inc: { n: 1 } })

When two operations hit the same document, one gets a write conflict and the server retries it transparently.

§4Compression

Data is compressed when written to disk.

WhereDefaultNotes
CollectionssnappyFast, moderate savings
Collections, optionalzstd or zlibBetter ratio, more CPU
IndexesPrefix compressionRepeated key prefixes are stored once
db.createCollection("logs", { storageEngine: { wiredTiger: { configString: "block_compressor=zstd" } } })

Compression reduces disk use and I/O, and the cost is CPU. Pages are stored uncompressed in the cache.

The key insight WiredTiger gives you document-level concurrency and compression automatically, but it also means that a hot single document, such as a global counter, becomes a point of contention no matter how big the machine is.

§5Common Mistakes

MistakeWhat HappensFix
One document updated by every requestWrite conflicts and retries serialize the workloadSpread the writes, for example with several counters
Assuming collection-level locksWrong picture of concurrencyThink in terms of document-level conflicts
Choosing heavy compression without measuring CPUHigher CPU for small savingsTest snappy against zstd on real data
Practice
  1. Run two scripts that increment one document and two that increment different documents, and compare throughput.
  2. Compare the storage size of the same collection with snappy and zstd.
Key takeaways
  • WiredTiger stores collections and indexes as B-trees of pages, one file each.
  • MVCC gives document-level concurrency, so only writes to the same document conflict.
  • Data is compressed on disk, with a trade-off between ratio and CPU.
