The Oplog & Replication Mechanics

Replication works by copying a log of operations, the oplog, to each secondary, and the size of that log decides how long a member can be away and still catch up.

§1The Oplog

Every replica set member that can become primary keeps the oplog: a capped collection, local.oplog.rs, recording every write that changes data. The primary writes each operation to it, and secondaries read from it and apply the same operations.

use local
db.oplog.rs.find().sort({ $natural: -1 }).limit(1)
// { ts: Timestamp(1730000000, 1), op: "i", ns: "shop.orders", o: { _id: 1, item: "A" } }

Each entry has a timestamp (ts), an operation type (op: insert, update, delete), a namespace (ns), and the operation (o). Oplog entries are idempotent: applying one twice gives the same result, so a retry is safe. For example, $inc is recorded as the resulting $set.

§2How Secondaries Replicate

  1. A secondary picks a sync source and asks for oplog entries after the last timestamp it has.
  2. It applies batches of entries to its own data and appends them to its own oplog.
  3. It reports its progress, so the primary knows which writes a majority has.

The gap between the primary's newest entry and a secondary's is replication lag. A write is majority committed when a majority of members have applied it.

§3The Oplog Window

The oplog is a fixed-size capped collection, so old entries are overwritten. The oplog window is the time span between the oldest and newest entries.

rs.printReplicationInfo()
// configured oplog size: 10240MB
// log length start to end: 172800secs (48hrs)

If a secondary is down longer than the window, the entry it needs is gone, and it cannot catch up. It must be rebuilt with an initial sync, copying all the data again. The same limit applies to a change stream consumer's resume token. Heavy write bursts and bulk operations shorten the window, so size the oplog for your busiest period plus the longest outage you want to survive.

The key insight The oplog window is your recovery budget. When a member falls behind by more than the window, the cheap fix is gone and the expensive one begins.

§4Common Mistakes

MistakeWhat HappensFix
An oplog too small for bulk jobsThe window shrinks to minutes during a migrationSize it for peak write rate and plan around bulk operations
Ignoring replication lagSecondary reads stale, majority writes slowMonitor lag and alert on it
Taking a secondary down for longer than the windowThe member needs a full initial syncKeep maintenance shorter than the window, or enlarge the oplog first
Practice
  1. Read the newest and oldest oplog entries on a test replica set and compute the window.
  2. Perform a bulk update and observe how many oplog entries it creates.
Key takeaways
  • The oplog is a capped log of idempotent operations that secondaries replay.
  • Lag is the distance between the primary and a secondary, and majority commit depends on it.
  • The oplog window sets how long a member can be offline and still catch up.
