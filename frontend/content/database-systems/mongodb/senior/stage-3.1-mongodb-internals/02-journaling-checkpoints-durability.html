Journaling, Checkpoints & Durability

MongoDB survives a crash by combining periodic checkpoints with a write-ahead journal, and knowing what each covers tells you what can be lost.

§1Two Mechanisms

WiredTiger keeps data durable with two cooperating pieces.

  • A checkpoint is a consistent snapshot of all data files written to disk, taken about every 60 seconds.
  • The journal is a write-ahead log recording every change between checkpoints.
 time ─────────────────────────────────────────────▶
   checkpoint 1        writes recorded in journal        checkpoint 2
        │                 ▲ ▲ ▲ ▲ ▲                            │
        └─ data files consistent              data files consistent again

Between checkpoints, the data files on disk are the old consistent version, and the journal holds what happened since.

§2What Happens on Crash and Restart

After an unclean shutdown, MongoDB starts from the latest checkpoint and replays the journal to re-apply every change recorded after it. This restores the data to the last journaled write.

Journal records are flushed to disk about every 100 ms by default, or immediately when a write asks for it with j: true. This leaves a window in which a write has been acknowledged but is still only in memory.

db.orders.insertOne({ item: "A" }, { writeConcern: { w: 1, j: true } })     // wait for the journal flush

With w: "majority", durability also comes from replication: the write exists on other machines even if one loses its last 100 ms of journal.

§3Practical Consequences

  • Journaling is always on for replica set members, and you should not disable it.
  • A single standalone server with w: 1 and no j can lose up to about 100 ms of acknowledged writes on a power failure.
  • The journal lives on disk and gets frequent small writes, so fast, reliable storage helps.
  • Take care that the disk and any controller honor flush requests, since a cache that lies about flushing defeats the journal.
The key insight Checkpoints keep recovery fast and files consistent, the journal covers the time since the last checkpoint, and replication with majority write concern covers the loss of a whole machine.

§4Common Mistakes

MistakeWhat HappensFix
Disabling or ignoring the journal for speedCorruption and data loss after a crashLeave it on
Assuming an acknowledged w: 1 write is on diskA crash can lose the last fraction of a secondUse j: true or w: "majority"
Putting data on storage with an unsafe write cacheFlush guarantees are brokenUse storage that honors flushes
Practice
  1. Describe in order what the server does when it restarts after a crash in the middle of a checkpoint interval.
  2. State what is lost, if anything, for each of w: 1, w: 1, j: true, and w: "majority" if the primary loses power immediately after acknowledging.
Key takeaways
  • Checkpoints give a consistent on-disk state roughly every 60 seconds, and the journal records changes in between.
  • Recovery loads the last checkpoint and replays the journal.
  • Durability against machine loss comes from replication with w: "majority".
