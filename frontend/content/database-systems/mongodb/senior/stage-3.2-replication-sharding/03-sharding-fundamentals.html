Sharding Fundamentals

Sharding splits a collection across several replica sets so that data and load can grow beyond one machine, at the cost of a more complex deployment.

§1The Components

A sharded cluster has three kinds of parts.

  • Shards: each is a replica set that holds a portion of the data.
  • mongos: a router that applications connect to. It knows where data lives and sends operations to the right shards.
  • Config servers: a replica set storing the cluster's metadata, which tells the routers where each range of data lives.
 app ──▶ mongos ──▶ shard A (replica set)
          │   └───▶ shard B (replica set)
          └── asks config servers where the data is

§2How Data Is Divided

You pick a shard key, a field or fields in each document, and MongoDB divides the key's value range into chunks, assigning them to shards.

sh.enableSharding("shop")
sh.shardCollection("shop.orders", { customerId: 1 })                  // range-based
sh.shardCollection("shop.events", { deviceId: "hashed" })             // hashed
sh.status()
  • Range sharding keeps nearby key values together, which makes range queries efficient but can concentrate load.
  • Hashed sharding spreads values evenly, which balances load but turns range queries into scatter-gather.

§3Routing: Targeted and Scatter-Gather

db.orders.find({ customerId: 42 })            // targeted: includes the shard key, goes to one shard
db.orders.find({ status: "open" })            // scatter-gather: every shard is asked and mongos merges the results

A query that includes the shard key (or a prefix of it) is targeted to the shards that hold the data. Otherwise, it is broadcast, which is expensive as the cluster grows.

§4When to Shard

Shard when a single replica set cannot handle your data size, working set, or write throughput after you have tuned queries and indexes and scaled up the hardware. Sharding adds routers, config servers, balancing, and harder operations, so it is not the first answer to slowness.

The key insight Sharding does not make every query faster. It lets total capacity grow, and it rewards queries that include the shard key.

§5Common Mistakes

MistakeWhat HappensFix
Sharding early "for scale"Added complexity with no needTune and scale vertically first
Queries that omit the shard keyEvery shard is hit on every requestInclude the key, or design for it
Connecting applications directly to shardsBypasses routing and breaks resultsAlways connect through mongos
Practice
  1. Draw a cluster with three shards and explain which component answers db.orders.find({ customerId: 42 }).
  2. Compare range and hashed sharding for the same collection, naming one query each does well.
Key takeaways
  • A sharded cluster is shards (replica sets), mongos routers, and config servers.
  • The shard key divides data into chunks, and queries with the key are targeted.
  • Shard only after simpler scaling is exhausted.
