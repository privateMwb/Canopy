Failover, Rollback & Trade-offs

When a primary fails, writes it had not yet replicated can be rolled back, and your write concern decides whether that can happen to data you thought was safe.

§1What Failover Looks Like

After the primary fails, the election takes a few seconds, usually under 12. During that time the set has no primary and writes fail. Drivers with retryable writes wait for the new primary and retry once. Reads with a secondary read preference continue.

// the driver discovers the new primary by itself; the application sees only a pause
await orders.insertOne({ item: "A" });     // retried automatically after the election

Application code should expect brief errors during failover and handle them.

§2How a Rollback Happens

Suppose the primary accepts a write with w: 1, but fails before any secondary copies it. A secondary is elected and accepts new writes. When the old primary rejoins, it has an operation the new history does not contain, and must roll back that operation to match.

old primary:   A  B  C  X      (X was never replicated)
new primary:   A  B  C  D  E
                       └─ old primary rolls back X, then replays D E

The rolled-back documents are saved to files in a rollback directory for manual recovery, but the application was told the write succeeded, and it is no longer in the database.

§3Preventing Data Loss

  • Write with w: "majority". A write acknowledged by a majority is on at least one member of any future majority, so a new primary will have it, and it is never rolled back.
  • Read with majority read concern when acting on data you cannot afford to see disappear.
  • Use retryable writes with idempotent operations, so a failover during a write does not produce a duplicate.
SettingFailover behaviour
w: 1Fast, but can lose acknowledged writes
w: "majority"Slower by one replication step, and acknowledged writes survive
The key insight Rollbacks are not a bug. They are the price of acknowledging a write before it is replicated, and majority write concern removes that price for data you care about.

§4Common Mistakes

MistakeWhat HappensFix
Treating w: 1 as durableAcknowledged writes vanish after a failoverUse w: "majority" for important data
No application retry or error handlingRequests fail during the electionUse retryable writes and sensible timeouts
Never testing a failoverThe first real one is a surpriseStep down the primary in a test, and watch the application
Practice
  1. Run rs.stepDown() on a test primary while a client inserts in a loop, and count errors and retries.
  2. Explain exactly which writes can be rolled back under w: 1 and why none can under w: "majority".
Key takeaways
  • Failover takes seconds, during which writes pause and drivers retry.
  • Unreplicated writes can be rolled back after a failover.
  • w: "majority" makes acknowledged writes survive failover.
