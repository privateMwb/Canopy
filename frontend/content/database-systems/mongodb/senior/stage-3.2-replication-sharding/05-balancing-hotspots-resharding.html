Balancing, Hotspots & Resharding

The balancer moves chunks to keep shards even, but it cannot fix a bad key, so you need to know how to spot hotspots and what your options are for changing a key later.

§1The Balancer

A background process, the balancer, watches how many chunks each shard holds. When one has noticeably more than another, it migrates chunks from the fuller shard to the emptier one. A migration copies the chunk's documents, catches up with writes made in the meantime, then updates the metadata so routers send traffic to the new shard.

sh.status()                                  // chunk distribution per shard
sh.getBalancerState()
sh.setBalancerState(false)                   // pause the balancer (for example around a backup)
sh.balancerCollectionStatus("shop.orders")

Migrations use network, disk, and CPU, so you can restrict the balancer to a balancing window off-peak. Adding a shard triggers a long period of rebalancing as data moves to it.

§2Hotspots

The balancer evens out the number of chunks (more precisely, the data size), not the traffic. If one chunk receives most of the writes, as with a monotonically increasing key, moving chunks does not help, because the hot range keeps being the newest one.

Signs of a hotspot:

  • One shard has far higher CPU, disk, or operation counts than the others.
  • Chunk counts look even, but load does not.
  • A jumbo chunk is flagged, a chunk too large to split or move because many documents share one key value.

The fixes are in the key: hashed or compound keys, a higher-cardinality field, and pre-splitting for new empty collections.

§3Resharding

When a key turns out to be wrong, MongoDB offers two ways out.

  • reshardCollection (5.0 and later) copies the collection into a new layout online, then switches over.
  • Refine the shard key (4.4 and later) adds a suffix field to the existing key, for better cardinality, without moving data.
sh.reshardCollection("shop.orders", { customerId: "hashed" })
db.adminCommand({ refineCollectionShardKey: "shop.orders", key: { customerId: 1, orderId: 1 } })

Resharding needs spare disk and I/O capacity for the copy, and it should be tested and scheduled, not done in an emergency.

The key insight Balancing fixes uneven storage, and the key fixes uneven traffic. If load is uneven while chunks are even, the problem is the key.

§4Common Mistakes

MistakeWhat HappensFix
Expecting the balancer to fix a write hotspotChunks move but the hot range stays hotChange the key
Running migrations at peak loadLatency spikesSet a balancing window
Leaving jumbo chunksUneven shards that cannot be fixed by movingRefine the key to add cardinality
Practice
  1. Describe what the balancer sees and does when you add a fourth shard to a three-shard cluster.
  2. Explain why a monotonic key with perfectly even chunk counts still produces a hotspot, and how you would fix it.
Key takeaways
  • The balancer migrates chunks to even out shard storage, off-peak if you configure it.
  • Hotspots come from the key, and the balancer cannot cure them.
  • You can refine or reshard a key later, but these are expensive and need planning.
