Backups & Restores

A backup strategy combines a method (dumps, snapshots, or continuous backup), a schedule, and regular restore tests, because an untested backup is only a hope.

§1Backup Methods

MethodHow it worksGood forLimits
mongodumpReads documents through the server into BSON filesSmall to medium data, single databases, moving dataSlow on large data, and heavy on the cache
Filesystem snapshotSnapshots the storage volume (LVM, EBS, and similar)Large deployments, fast backups and restoresNeeds journaling on the same volume, and care on sharded clusters
Atlas Cloud BackupManaged snapshots with optional continuous backupAtlas usersCost, and retention settings to configure
Ops Manager / Cloud ManagerManaged backup for self-hosted clustersLarger self-managed estatesExtra product to run
# snapshot-style backup on a secondary, with minimal disruption
mongosh --eval 'db.fsyncLock()'      # flush and block writes on this secondary (short pause)
# ... take the volume snapshot ...
mongosh --eval 'db.fsyncUnlock()'

Back up from a secondary or a hidden member, so the primary is not disturbed.

§2Point-in-Time Recovery

A snapshot restores to the moment it was taken. To restore to a specific time, such as one minute before someone dropped a collection, you need the snapshot plus the oplog from that point, replayed up to the chosen time.

mongorestore --oplogReplay --oplogLimit "1730000000:1" ./dump-with-oplog      # replay up to a timestamp

Atlas continuous backup and Ops Manager provide this as a managed feature. In a self-managed setup you must keep the oplog (or archive it) as long as your recovery window requires.

§3Proving Restores Work

Set a recovery point objective (RPO), how much data you can lose, and a recovery time objective (RTO), how long a restore may take. Then measure both by actually restoring.

  1. Restore the latest backup into an isolated test cluster on a schedule.
  2. Check collection counts, spot-check documents, and run the application's smoke tests.
  3. Time the restore, and compare to your RTO.
  4. Keep copies in another region or account, so one incident cannot destroy both data and backups.
The key insight Replication is not a backup. A bad delete or a corrupting bug is replicated to every member within moments, and only a separate, point-in-time copy lets you go back.

§4Common Mistakes

MistakeWhat HappensFix
Counting replica set members as backupsA dropped collection is gone everywhereTake independent backups
Never restoring a backupIt turns out incomplete or unusable during an incidentSchedule restore tests
Backups stored beside the dataOne failure or breach loses bothStore copies in a separate account or region, with immutability if you can
Practice
  1. Back up a test database, delete a collection, and restore it to a point just before the deletion.
  2. Write your RPO and RTO for a service, and decide which backup method meets them.
Key takeaways
  • Choose between dumps, snapshots, and managed backup based on data size and recovery goals.
  • Point-in-time recovery needs a snapshot plus the oplog.
  • A backup counts only after a timed, verified restore.
