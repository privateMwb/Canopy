Sorting, Pagination & Cursors

sort, limit, and skip shape a result, but large offsets get slow, so production paging uses a range on an indexed field instead.

§1Sort and Limit

find returns a cursor: a handle that streams results in batches. You chain modifiers onto it.

db.products.find({ stock: { $gt: 0 } })
  .sort({ price: -1, name: 1 })      // 1 ascending, -1 descending
  .limit(10)

Sorting without an index means MongoDB must collect and sort results in memory, and it gives up with an error past a memory limit (100 MB by default for a blocking sort). An index that matches the sort lets results come out already ordered.

Sort ties are not stable between queries, so add a unique field such as _id as the last sort key to get a deterministic order.

§2Offset Paging with skip

const page = 3, size = 20
db.products.find().sort({ _id: 1 }).skip((page - 1) * size).limit(size)

This is simple, but skip(n) still walks past n entries, so page 5,000 is far slower than page 1. Concurrent inserts also shift rows between pages, so a reader can see duplicates or gaps.

§3Range-Based Paging

Instead of "skip 40,000," say "give me what comes after the last item I saw." This uses the index to jump straight to the spot, so every page costs the same.

// first page
db.posts.find().sort({ createdAt: -1, _id: -1 }).limit(20)

// next page: pass the last item's values
db.posts.find({
  $or: [
    { createdAt: { $lt: last.createdAt } },
    { createdAt: last.createdAt, _id: { $lt: last._id } }
  ]
}).sort({ createdAt: -1, _id: -1 }).limit(20)

With a unique tiebreaker such as _id, no row is repeated or lost.

§4Cursors in Code

Cursors fetch in batches and close after a period of inactivity (10 minutes by default). Iterate instead of calling toArray() on a huge result.

const cursor = db.events.find({ type: "click" })
while (cursor.hasNext()) { process(cursor.next()) }    // streams one batch at a time
The key insight Page with a range on an indexed, unique-ordered field. Use skip only when the offset is small and the dataset is bounded.

§5Common Mistakes

MistakeWhat HappensFix
Sorting on an unindexed field in a large collectionSlow in-memory sort, or an error at the memory limitCreate an index that matches the sort
Deep skip for paginationEach page is slower than the lastUse range-based paging
Sorting on a non-unique field onlyItems repeat or vanish between pagesAdd _id as the final sort key
Practice
  1. Build offset paging and range paging over 100,000 inserted documents and time page 1 against page 4,000 for each.
  2. Explain why sort({ createdAt: -1 }) alone is unsafe for paging, and fix it.
Key takeaways
  • sort and limit shape results, and an index that matches the sort avoids an in-memory sort.
  • skip gets slower as the offset grows and is unstable under concurrent writes.
  • Range-based paging with a unique tiebreaker stays fast and consistent.
