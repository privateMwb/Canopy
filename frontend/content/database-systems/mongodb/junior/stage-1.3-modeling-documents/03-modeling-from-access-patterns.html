Modeling from Access Patterns

Start from the queries your application must answer, then shape documents so each important query is cheap, instead of starting from a diagram of entities.

§1Queries First

In a relational design you normalize first and write queries later. In MongoDB you do the reverse: list the operations, estimate how often each runs, and design documents around the hot ones.

OperationFrequencyNeeds
Show product pagevery highproduct, price, a few reviews
List a user's ordershighorder totals and dates, newest first
Place an ordermediumwrite order, decrement stock
Monthly sales reportlowaggregate across all orders

A write that is rare may be allowed to be more expensive in exchange for a read that happens a million times a day.

§2From Operations to Shape

Take the product page. It needs the product plus a few reviews, so embed the most recent ones and keep the full set in a separate collection.

{ _id: "NB-1", name: "Notebook", price: 4.5,
  recentReviews: [ { user: "Ada", stars: 5, text: "Great", at: ISODate("2026-03-01") } ],
  reviewCount: 214, avgStars: 4.6 }

db.reviews.find({ productId: "NB-1" }).sort({ at: -1 })    // all reviews, paged, for the "see all" page

One read serves the page. The cost is that a new review updates two places, which is acceptable because reviews are written far less often than the page is read.

§3Check the Design Against the List

For each operation, write the query and the index that supports it. If a query needs several round trips or no good index, revisit the shape.

db.orders.createIndex({ userId: 1, placedAt: -1 })
db.orders.find({ userId: 42 }, { total: 1, placedAt: 1 }).sort({ placedAt: -1 }).limit(20)
The key insight A model is good relative to a workload. When the workload changes, the model may need to change too, which is why MongoDB makes evolving documents easy.

§4Common Mistakes

MistakeWhat HappensFix
Modeling entities first and guessing at queriesCommon reads need many lookupsWrite the operations list before the schema
Optimizing a rare operationA hot path pays for itWeigh each operation by frequency
Never rechecking after requirements changeThe model slowly stops fittingReview the model when the access patterns change
Practice
  1. Write the operations list for a blog (home page, post page, author page, comment posting) and rank by frequency.
  2. For the highest-frequency operation, write the document shape and the exact query and index that serve it.
Key takeaways
  • Design starts from the application's queries and their frequencies.
  • Spend complexity on the hot reads, and accept costlier writes where they are rare.
  • Validate a design by writing each query and its index, and revise when the workload changes.
