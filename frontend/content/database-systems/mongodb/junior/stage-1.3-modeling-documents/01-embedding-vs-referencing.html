Embedding vs. Referencing

The central modeling decision in MongoDB is whether related data lives inside one document or in its own collection, and the access pattern should decide.

§1Two Ways to Relate Data

Embedding nests related data inside the parent document. Referencing stores an identifier and keeps the related data in a separate collection, as a foreign key would.

// Embedded: the address lives inside the user
{ _id: 1, name: "Ada", address: { street: "1 Main St", city: "London" } }

// Referenced: orders point at the user by _id
{ _id: 1, name: "Ada" }
{ _id: 900, userId: 1, total: 42.5 }

Embedding gives you one read and one atomic write for everything in the document. Referencing keeps data in one place and lets it grow and change independently, but reading it together takes a second query or a $lookup.

§2When to Embed and When to Reference

Embed whenReference when
The data is read together almost every timeThe related data is read on its own or by other parents
The child belongs to exactly one parentMany parents share the same child
The set is small and boundedThe set can grow without limit
You need to update parent and child atomicallyThe child changes often and independently

A one-to-few relationship, such as a user and their two addresses, is a natural embed. A one-to-squillions relationship, such as a server and its log lines, must be referenced.

§3Duplication Is a Choice

Embedding often means copying data. An order that embeds the product name and price is storing a snapshot of the sale, and that is correct, because the receipt should not change when the catalog does.

{ _id: 900, userId: 1,
  items: [ { productId: 12, name: "Notebook", priceAtSale: 4.5, qty: 2 } ] }

For each copied field, decide whether it is a frozen snapshot, or live data that must be updated everywhere it appears, or kept only by reference.

The key insight There is no single right shape. The same entities can be modeled several ways, and the best way is the one that makes your most frequent and most important queries cheapest.

§4Common Mistakes

MistakeWhat HappensFix
Embedding everything by defaultLarge documents, and rewrites for small changesEmbed only what is read together and bounded
Referencing everything like a relational schemaMany queries and $lookups per requestEmbed data that is always shown together
Copying live data with no update planStale duplicatesDecide per field: snapshot, update everywhere, or reference
Practice
  1. Model a user with addresses, and decide for each field whether it should be embedded or referenced.
  2. Write down one screen of an app and list exactly which data it needs, then choose the document shape that serves it in one read.
Key takeaways
  • Embed data that is read together, bounded, and owned by one parent.
  • Reference data that is shared, large, unbounded, or changed independently.
  • Copied data is either a deliberate snapshot or a synchronization problem you must plan for.
