Document Growth & Size Limits

A document can be at most 16 MB, but unbounded arrays cause real problems long before that limit, so every embedded list needs a bound.

§1The 16 MB Limit and Nesting

MongoDB caps a single BSON document at 16 MB, and nesting is limited to 100 levels. 16 MB sounds huge, but a document that stores every comment, log line, or event for a growing entity will eventually reach it, and the write that crosses the limit fails.

db.posts.updateOne({ _id: 1 }, { $push: { comments: newComment } })
// works for years, then: "BSONObj size ... is invalid"

Check a document's size in the shell:

Object.bsonsize(db.posts.findOne({ _id: 1 }))      // bytes

§2Why Unbounded Arrays Hurt Early

  • Every read of the document loads all of the array, even if you wanted the title.
  • The document uses more of the cache, which pushes other data out.
  • Updates to a large document write more data, and a multikey index on the array grows with it.
  • Replication copies larger changes to every secondary.

Performance usually degrades noticeably when documents reach hundreds of kilobytes, which is long before the hard limit.

§3Keeping Growth Under Control

  • Reference the unbounded side: comments in their own collection with a postId.
  • Cap the array with $push and $slice, keeping only the most recent items embedded.
  • Bucket old data into separate documents (a first look comes in the next lesson).
  • Archive data you no longer read into another collection.
db.posts.updateOne({ _id: 1 }, { $push: { recentComments: { $each: [c], $slice: -20 } }, $inc: { commentCount: 1 } })
The key insight For each array, ask "how large can this get in the worst realistic case?" If the answer is "unbounded," it should not be embedded.

§4Common Mistakes

MistakeWhat HappensFix
Appending forever to an embedded arraySlow reads, then write failures at 16 MBMove children to a collection, or cap and bucket
Never measuring document sizeGrowth goes unnoticedUse Object.bsonsize and watch average document size
Storing large binary files inlineDocuments hit the limit fastStore files in object storage or GridFS, with a reference
Practice
  1. Insert comments into one document in a loop until it fails, and note the size at each step with Object.bsonsize.
  2. Redesign that model so comments are bounded, keeping the latest ten embedded.
Key takeaways
  • A document may hold at most 16 MB, and performance suffers long before that.
  • Any array that can grow without bound belongs in its own collection or in buckets.
  • Measure document sizes, and cap lists with $slice when only recent items matter.
