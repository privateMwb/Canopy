Anti-Patterns to Avoid

Most schema problems come from a few repeated mistakes, and knowing them lets you spot trouble in a design before it reaches production.

§1Unbounded Arrays

An array that grows with usage, such as every comment, event, or follower, eventually makes documents huge, slow to read and update, and at risk of hitting 16 MB.

db.users.updateOne({ _id: 1 }, { $push: { loginHistory: new Date() } })     // grows forever

Fix it by moving the items to their own collection, bucketing, or keeping a capped recent list.

§2Massive Documents and Unneeded Indexes

Putting everything about an entity into one document means every read pays for data it ignores. The related problem is too many indexes: each one slows writes and consumes cache.

Object.bsonsize(doc)          // measure it
db.coll.aggregate([{ $indexStats: {} }])     // find unused indexes

Split cold data from hot data, and drop indexes that no query uses.

§3Over-Normalizing and Over-Denormalizing

Modeling documents like relational tables forces $lookup or several queries for every screen. In the other direction, copying the same field into many places creates update work and inconsistency. The middle path is to embed what is read together and reference the rest.

§4Other Common Traps

Anti-patternProblem
Collection per tenant or per user (thousands of collections)Overhead for files, indexes, and metadata
Dynamic field names as data ({ "2026-03-01": 5, "2026-03-02": 7 })Hard to index and query; use an array of { date, value }
Case-insensitive search with $regex and iCannot use an index well; use a collation, text, or search index
skip for deep paginationCost grows with the offset
Storing large files in documentsHits size limits; use object storage or GridFS
The key insight Most anti-patterns are fine at small scale and fail later. Review a design by asking what happens when each array, collection, and index is a thousand times larger.

§5Common Mistakes

MistakeWhat HappensFix
Using values as field namesQueries and indexes become awkwardUse arrays of key and value subdocuments
Never reviewing a model after launchProblems appear as data growsCheck document sizes, index use, and slow queries on a schedule
Copying a relational schema directlyJoin-heavy queriesRedesign from the access patterns
Practice
  1. Review a model with { prices: { "2026-01": 10, "2026-02": 12 } } and redesign it so prices can be queried by date.
  2. Examine a collection for unbounded arrays by finding the largest documents with Object.bsonsize.
Key takeaways
  • Unbounded arrays, huge documents, and excess indexes are the most common design failures.
  • Balance normalization and duplication by embedding what is read together.
  • Review models for what happens at a thousand times the data.
