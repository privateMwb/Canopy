Write Concern & Durability

Write concern controls how many servers must confirm a write before the driver reports success, and it decides whether an acknowledged write can still be lost.

§1What "Acknowledged" Means

When you call insertOne, the server answers when its write concern is satisfied. A weaker setting returns sooner but promises less.

db.orders.insertOne({ item: "A" }, { writeConcern: { w: 1 } })              // primary has applied it
db.orders.insertOne({ item: "A" }, { writeConcern: { w: "majority" } })     // a majority of voting members have it
db.orders.insertOne({ item: "A" }, { writeConcern: { w: "majority", j: true, wtimeout: 5000 } })
OptionMeaning
w: 0Do not wait for any acknowledgement (fire and forget)
w: 1The primary has applied the write
w: "majority"A majority of data-bearing voting members have applied it
j: trueThe write has reached the on-disk journal
wtimeoutHow long to wait before reporting a write concern error

§2Why majority Matters

With w: 1, a primary can acknowledge a write and then fail before any secondary copies it. A new primary is elected without that write, and when the old primary returns, the write is rolled back and lost to the application, even though it was acknowledged.

// connection string default for new MongoDB versions: w=majority
mongodb+srv://.../shop?w=majority&retryWrites=true

A write acknowledged by a majority survives the loss of the primary, because any new primary must come from a majority that includes at least one member with the write. Recent MongoDB versions default to w: "majority" for most deployments, but check your driver and server version.

§3The Cost

Waiting for replication adds latency, roughly one network round trip to the slowest member of the majority. j: true adds the wait for a disk flush. You choose per operation:

  • Critical data such as payments and orders: w: "majority" (and journaled).
  • High-volume, replaceable data such as metrics or logs: w: 1, accepting a small risk.
The key insight Durability is a dial, not a switch. Write concern is how you decide, per operation, how much loss risk you accept in return for speed.

§4Common Mistakes

MistakeWhat HappensFix
Using w: 1 for important dataAn acknowledged write can disappear after a failoverUse w: "majority"
Using w: 0 and assuming successErrors, including duplicates, are never reportedWait for acknowledgement unless loss is truly fine
No wtimeout on a majority writeA lagging cluster can make calls hangSet a timeout and handle the error
Practice
  1. Run the same insert with w: 1 and w: "majority" against a replica set, and compare the latency.
  2. Choose a write concern for each of: a payment, a page view counter, a user profile edit. Justify each choice.
Key takeaways
  • w sets how many members must confirm a write, and j adds the journal.
  • Only w: "majority" guarantees an acknowledged write survives a primary failure.
  • Choose write concern per operation by weighing loss risk against latency.
