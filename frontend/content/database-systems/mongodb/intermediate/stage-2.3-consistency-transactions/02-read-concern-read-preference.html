Read Concern & Read Preference

Read preference decides which replica set member serves a read, and read concern decides how up to date and how durable the data you see must be.

§1Read Preference

By default all reads go to the primary, which always has the latest data. You can allow other members.

ModeReads from
primaryThe primary only (default)
primaryPreferredPrimary, or a secondary if the primary is down
secondarySecondaries only
secondaryPreferredA secondary, or the primary if none available
nearestThe lowest-latency member
db.reports.find({ month: "2026-03" }).readPref("secondaryPreferred")

Secondaries replicate asynchronously, so they can lag behind. Reading from them offloads the primary and lowers latency for distant users, but you may read stale data, and the same user could see data go backward when two reads reach different secondaries.

§2Read Concern

Read concern sets the consistency level of the data returned.

LevelGuarantee
localThe member's latest data, which might later be rolled back
availableLike local, mainly relevant for sharded clusters
majorityOnly data acknowledged by a majority, so it will not be rolled back
linearizableReflects all majority-acknowledged writes before the read began (primary only, slower)
snapshotA consistent snapshot, used in transactions
db.accounts.find({ _id: 1 }).readConcern("majority")

§3Putting It Together

To read your own writes reliably, write with w: "majority" and read from the primary with majority, or use a causally consistent session, which guarantees reads reflect earlier writes in the same session even from secondaries.

const session = client.startSession({ causalConsistency: true });
await coll.insertOne({ x: 1 }, { session, writeConcern: { w: "majority" } });
await coll.findOne({ x: 1 }, { session, readPreference: "secondary", readConcern: { level: "majority" } });
The key insight Reading from secondaries is a decision to accept staleness. Make it only for data where a few seconds of delay is harmless, such as reports.

§4Common Mistakes

MistakeWhat HappensFix
Reading from secondaries right after a writeThe new data is not there yetRead from the primary, or use causal consistency
Assuming local reads are finalA rollback can remove data you already acted onUse majority for decisions that matter
Using linearizable everywhereHigh latency and loadReserve it for the few operations that need it
Practice
  1. Write a document, then read it immediately from a secondary and explain what might happen.
  2. Pick a read preference and read concern for a live account balance and for a nightly report.
Key takeaways
  • Read preference chooses the member, and secondary reads can be stale.
  • Read concern majority returns only data that cannot be rolled back.
  • Pair w: "majority" with majority reads, or use causal consistency, to read your own writes.
