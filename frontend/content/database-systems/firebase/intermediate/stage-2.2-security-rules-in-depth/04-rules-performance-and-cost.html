Rules Performance & Cost

Rules that read other documents are powerful but have limits, add latency, and are billed, so they deserve attention.

§1Billing and Limits

Each get(), exists(), or getAfter() call in a rule is billed as a document read, with the usual caching within a single request. There are also hard limits on how many such calls one rule evaluation can make: 10 for a single-document request, and 20 for a batch or transaction, with the exact numbers documented by Firebase. Exceeding the limit denies the request.

// two reads per request evaluated by this rule
allow write: if get(/databases/$(database)/documents/users/$(request.auth.uid)).data.active == true
             && exists(/databases/$(database)/documents/teams/$(teamId)/members/$(request.auth.uid));

§2Reducing the Cost

  • Prefer custom claims for roles checked on every request; they cost no reads
  • Cache-friendly designs: reuse the same get() path within one rule so it is counted once
  • Avoid rules that scale with data, since rules cannot loop over collections
  • Put checks in the cheapest order, using && so an early false stops evaluation

For a list query, rules are checked once against the query's constraints, not once per returned document. So a get() in a list rule is billed per query, but it can only depend on the query and the caller, never on each result's own fields. Rules that need per-result data must constrain the query so every possible result passes.

§3getAfter and Multi-Document Writes

getAfter() reads a document as it will be after the current batch or transaction, so rules can check consistency across documents written together.

// a like may only be created together with the counter increment
allow create: if getAfter(/databases/$(database)/documents/posts/$(postId)).data.likeCount
              == get(/databases/$(database)/documents/posts/$(postId)).data.likeCount + 1;
Every get() is a billed read A rule that reads one document is cheap, but it runs on every request, so thousands of small requests add up. Claims cost nothing to check, which makes them the best home for roles checked constantly.

§4Common Mistakes

MistakeWhat HappensFix
Using get() for a role on every operationDoubles reads and adds latencyMove frequently checked roles into custom claims
Putting a get() in a rule that runs on every requestEach request pays for an extra read plus latencyDenormalize the needed data onto the document or into a claim
Exceeding the call limit in one ruleRequests are denied unexpectedlyReduce the number of lookups or restructure the data
Practice
  1. Count how many get() and exists() calls your busiest rule makes and reduce it by one.
  2. Replace a role lookup with a custom claim and compare the number of reads in the emulator UI.
Key takeaways
  • Rule lookups with get(), exists(), and getAfter() are billed reads with hard limits.
  • Claims are free to check; documents are flexible but cost reads.
  • Use getAfter() to enforce consistency across documents written together.
