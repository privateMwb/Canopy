The Rules Language

Security rules are a small, typed expression language. Learning its building blocks lets you write rules you can read and reuse.

§1The Objects You Have

Every rule evaluates with a few built-in objects:

  • request.auth: the caller (uid and token claims), or null if signed out
  • request.resource.data: the document as it will be after a write
  • resource.data: the document as it is now, or null if it does not exist
  • request.time: the server time of the request
  • request.method: the operation, such as create or update
  • path variables like {userId} captured by match

resource == null is how you test that a document does not exist yet.

§2Functions and Granular Operations

Define functions at the top of the match block to name your conditions.

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    function signedIn() { return request.auth != null; }
    function isOwner(uid) { return signedIn() && request.auth.uid == uid; }

    match /notes/{noteId} {
      allow get, list: if isOwner(resource.data.ownerId);
      allow create:    if isOwner(request.resource.data.ownerId);
      allow update:    if isOwner(resource.data.ownerId)
                       && request.resource.data.ownerId == resource.data.ownerId;
      allow delete:    if isOwner(resource.data.ownerId);
    }
  }
}

read splits into get (one document) and list (queries); write splits into create, update, and delete. Granting the finest operations makes intent clear.

§3Wildcards and Evaluation

  • {name} matches one path segment; {path=**} matches any depth (needed for collection group queries)
  • If any matching allow is true, the operation is allowed; rules are a union, not a sequence
  • A rule that errors (for example, reading a field that does not exist) counts as false
  • Rules do not apply to the Admin SDK, which bypasses them entirely
Allows add up Because overlapping allow statements are combined with OR, one overly broad rule anywhere can override a careful one elsewhere. Review the whole file for overlaps, not just the rule you changed.

§4Common Mistakes

MistakeWhat HappensFix
A broad wildcard match /{document=**} left inIt grants access to every collectionRemove it; match explicit collections
Reading resource.data.field where the field is missingThe rule errors and denies, which can look like a bugGuard with 'field' in resource.data or validate on write
Using write when you mean only createUsers can also update and deleteGrant create, update, and delete separately
Practice
  1. Refactor a rules file to use signedIn() and isOwner() helper functions with separate create, update, and delete rules.
  2. Find a spot in your rules where two allow statements overlap and check whether the result is intended.
Key takeaways
  • Rules use request, resource, and path variables to decide per operation.
  • Functions make rules readable; granular operations make intent explicit.
  • Matching allow statements are OR'd, so overlaps can open holes.
