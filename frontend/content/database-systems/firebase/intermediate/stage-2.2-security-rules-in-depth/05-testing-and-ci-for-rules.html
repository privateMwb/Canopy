Testing & CI for Rules

Rules are code that guards your data, so they should have tests that run automatically before every deploy.

§1A Reusable Test Setup

Structure tests so each case is a small, named statement of policy.

import { initializeTestEnvironment, assertSucceeds, assertFails } from "@firebase/rules-unit-testing";
import { readFileSync } from "fs";
import { doc, getDoc, setDoc, updateDoc } from "firebase/firestore";

let env;
beforeAll(async () => {
  env = await initializeTestEnvironment({
    projectId: "demo-rules",
    firestore: { rules: readFileSync("firestore.rules", "utf8") },
  });
});
afterAll(() => env.cleanup());
beforeEach(() => env.clearFirestore());

const as = (uid) => env.authenticatedContext(uid, { role: "member" }).firestore();

test("owner can edit title but not ownerId", async () => {
  await env.withSecurityRulesDisabled(async (ctx) => {
    await setDoc(doc(ctx.firestore(), "notes/n1"), { ownerId: "alice", title: "a" });
  });
  await assertSucceeds(updateDoc(doc(as("alice"), "notes/n1"), { title: "b" }));
  await assertFails(updateDoc(doc(as("alice"), "notes/n1"), { ownerId: "bob" }));
});

The second argument to authenticatedContext sets custom claims, so you can test admin and role behavior.

§2Run Tests in CI

firebase emulators:exec --only firestore "npm test"

In GitHub Actions or any CI system, run that command on every pull request, and block merging if it fails. Deploy rules from CI only after tests pass.

- run: npm ci
- run: npx firebase-tools emulators:exec --only firestore "npm test"
- run: npx firebase-tools deploy --only firestore:rules --project prod   # on main only

§3What to Cover

For every collection, test a signed-out user, a normal user, the owner, a different user, and an admin, against each of get, list, create, update, and delete. Add a test for each bug you ever fix so it cannot come back. Rules coverage reports from the emulator show which allow statements your tests never exercised.

A rule without a test is a guess Rules are easy to read as correct and still be wrong. Tests turn "I think this is secure" into something that fails loudly when a later edit breaks it.

§4Common Mistakes

MistakeWhat HappensFix
Testing as a single userCross-user holes are never exercisedTest owner, other user, signed-out, and admin
Seeding data through rulesSetup fails for the wrong reasonsUse withSecurityRulesDisabled to seed
Deploying rules without running testsA broken rule reaches productionGate deploys on passing tests in CI
Practice
  1. Write a test matrix for one collection covering four kinds of user and five operations.
  2. Add a CI job that runs the rules tests on every pull request.
Key takeaways
  • Test rules with the emulator and rules-unit-testing, including custom claims.
  • Run tests in CI and deploy only when they pass.
  • Cover every user type and operation, and add a test for every fixed bug.
