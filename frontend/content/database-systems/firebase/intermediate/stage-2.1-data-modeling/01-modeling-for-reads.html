Modeling for Reads

In Firestore you design documents around the screens that read them, which usually means copying data instead of joining it.

§1Why Duplication Is Normal

Firestore has no joins. Showing a feed of posts with each author's name would take one read per post if the name lived only on the user document. Instead, store what the screen needs on the post itself.

// posts/p1
{
  text: "Hello",
  authorId: "alice",
  authorName: "Alice",          // copied from users/alice
  authorPhoto: "https://...",   // copied too
  createdAt: serverTimestamp()
}

One query returns everything the feed needs. The cost is that a change to Alice's name must reach every copy.

§2Choosing What to Copy

Copy fields that are small, read often, and change rarely, such as a display name or a title. Do not copy large or fast-changing data. Ask for each screen: "what is the one query that fills this?" and let that answer shape the document.

  • Read-heavy, write-light data suits duplication well
  • Frequently changing values (like a live score) are better read from one place
  • Keep the authoritative copy in one document and treat the others as caches of it

§3Keeping Copies Consistent

When the source changes, update the copies with a batched write or, better, a Cloud Function that fans out the change.

import { writeBatch, getDocs, query, collection, where, doc } from "firebase/firestore";

const posts = await getDocs(query(collection(db, "posts"), where("authorId", "==", uid)));
const batch = writeBatch(db);
posts.forEach((d) => batch.update(d.ref, { authorName: newName }));
batch.update(doc(db, "users", uid), { name: newName });
await batch.commit();

If a stale name for a short time is acceptable, the fan-out can run asynchronously. If it must be exact, update inside one transaction or batch.

Write once, read many Duplication moves cost from reads, which happen constantly, to writes, which happen rarely. That is usually the right trade for apps with far more readers than editors.

§4Common Mistakes

MistakeWhat HappensFix
Normalizing like a SQL databaseEvery screen needs many reads and is slow and costlyShape documents for each screen's query
Copying data without a plan to update itStale names and counts appear in placesDecide who updates copies and how, such as a function or batch
Duplicating large or fast-changing dataFan-out writes explode in costCopy only small, stable fields
Practice
  1. Design the post document for a feed that shows author name and avatar, and list what must be updated when a user renames themselves.
  2. Write a function that updates a user's name on all their posts using batches.
Key takeaways
  • Model data around the queries your screens need, not around normal forms.
  • Duplicate small, stable fields to avoid extra reads.
  • Always plan how copies stay consistent.
