Eventing & Analytics Integration

Firestore is good at serving an app and poor at analytics, so real products stream their data elsewhere.

§1Streaming to BigQuery

The Stream Firestore to BigQuery extension mirrors document changes into BigQuery tables. You can then run SQL across everything, join it with other data, and build dashboards, without loading your operational database.

firebase ext:install firebase/firestore-bigquery-export

It creates a changelog table and a view of the latest state. Analytics events can also be exported to BigQuery from the Analytics settings. Expect storage and query costs in BigQuery, and keep personal data in mind.

§2Pub/Sub for Fan-Out

Pub/Sub decouples systems: your function publishes a message, and any number of subscribers react.

import { PubSub } from "@google-cloud/pubsub";
import { onMessagePublished } from "firebase-functions/v2/pubsub";

export const onOrderCreated = onDocumentCreated("orders/{id}", async (e) => {
  await new PubSub().topic("orders").publishMessage({ json: { id: e.params.id, total: e.data.data().total } });
});

export const fulfil = onMessagePublished("orders", async (event) => {
  const order = event.data.message.json;
  // ship it, notify finance, update search...
});

This gives you retries and independent consumers. The same at-least-once delivery rules apply, so make subscribers idempotent.

§3Keeping Operational and Analytical Apart

Do analytics, reports, and heavy aggregations in BigQuery and not with Firestore queries. For reporting that must reach users inside the app, write precomputed results back into small Firestore documents from a scheduled query or function. This keeps the operational database fast and the bill predictable.

Firestore serves the app, not the analyst Ask "is this a product feature or a business question?" Product features read from Firestore; business questions read from a warehouse.

§4Common Mistakes

MistakeWhat HappensFix
Running reports with large Firestore queriesExpensive and slow, and they compete with usersExport to BigQuery and query there
Subscribers that are not idempotentDuplicates cause double processingHandle repeats using message IDs
Exporting personal data without a planPrivacy and deletion obligations are missedTrack and delete exported data on user removal
Practice
  1. Install the BigQuery export for one collection and write an SQL query counting documents per day.
  2. Publish an order event to Pub/Sub and handle it with a second function.
Key takeaways
  • Stream data to BigQuery for analytics and reporting.
  • Pub/Sub decouples producers and consumers, with at-least-once delivery.
  • Keep operational and analytical workloads separate.
