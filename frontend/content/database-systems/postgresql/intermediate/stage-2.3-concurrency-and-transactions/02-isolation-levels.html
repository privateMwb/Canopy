Isolation Levels

Isolation levels set how much concurrent transactions can see of each other, trading strictness against retries.

§1The Anomalies

Concurrency bugs have names. Each isolation level allows some and forbids others.

AnomalyWhat happens
Dirty readReading another transaction's uncommitted change
Non-repeatable readReading the same row twice in one transaction and getting different values
Phantom readThe same query returns a different set of rows the second time
Lost updateTwo transactions read a value, both write based on it, and one overwrites the other
Write skewTwo transactions each check a condition over several rows, then write different rows, together breaking a rule

Postgres implements three distinct levels: Read Committed, Repeatable Read, and Serializable. (Requesting Read Uncommitted gives you Read Committed, so dirty reads never happen.)

§2The Three Levels

  • Read Committed (the default): each *statement* sees a fresh snapshot of data committed before it began. Two statements in one transaction can see different data (non-repeatable reads and phantoms are possible). If an UPDATE finds the row changed by a concurrent committed transaction, it re-checks the row's current version and proceeds.
  • Repeatable Read: one snapshot for the whole transaction. In Postgres this prevents non-repeatable reads *and* phantoms. If you try to update a row that another transaction changed after your snapshot, you get an error and must retry.
  • Serializable: transactions behave as if they ran one at a time. Postgres uses serializable snapshot isolation, which detects dangerous read/write patterns and aborts one transaction, which prevents write skew too.
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT ...;
UPDATE ...;      -- may fail with SQLSTATE 40001 (serialization_failure)
COMMIT;

You can set the level per transaction, or by default through default_transaction_isolation.

§3Choosing and Retrying

Read Committed is right for most work, especially when each statement is atomic. Add explicit protection where a read-then-write pattern matters: an atomic UPDATE ... WHERE balance >= 100, a unique constraint, SELECT ... FOR UPDATE, or a stricter level.

A classic write skew: a hospital rule says at least one doctor must be on call. Two doctors each check that the other is on call and then each go off call. Under Read Committed or Repeatable Read both succeed and nobody is on call. Under Serializable, one is aborted.

BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM on_call WHERE shift = 'night';
UPDATE on_call SET available = false WHERE doctor = 'ann';
COMMIT;      -- may raise 40001: retry the whole transaction

The cost of the stricter levels is that your application must catch serialization failures (SQLSTATE 40001) and retry the entire transaction. Retries must be safe, so keep side effects such as emails outside the transaction.

The key insight Higher isolation does not make code correct for free; it turns silent anomalies into explicit errors you must retry. Build the retry loop once, in a shared helper.

§4Common Mistakes

MistakeWhat HappensFix
Assuming Read Committed prevents lost updates in read-then-write codeTwo sessions read the same balance and one overwrites the otherUse an atomic UPDATE, FOR UPDATE, or a higher isolation level
Using Serializable without a retry loopUsers see random 40001 errorsRetry the whole transaction on SQLSTATE 40001 (and 40P01)
Running long transactions at Repeatable Read or SerializableMore conflicts and more state kept by the serverKeep them short and narrowly scoped
Practice
  1. Reproduce a non-repeatable read at Read Committed using two psql sessions, then show Repeatable Read prevents it.
  2. Reproduce the doctors-on-call write skew at Repeatable Read, then repeat it at Serializable and observe the error.
  3. Write a retry helper in your language that reruns a transaction on SQLSTATE 40001.
Key takeaways
  • Postgres offers Read Committed (default), Repeatable Read, and Serializable; dirty reads never occur.
  • Repeatable Read gives a transaction-wide snapshot; Serializable also prevents write skew.
  • Stricter levels require catching serialization failures and retrying the whole transaction.
