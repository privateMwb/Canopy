Long Transactions & Bloat

One transaction left open holds back cleanup for the whole database, so dead rows pile up and everything slowly gets worse.

§1What Vacuum Can and Cannot Remove

VACUUM can only remove a dead row version if no transaction could still need to see it. The oldest snapshot still in use sets a horizon (the xmin horizon); anything that became dead after that point must be kept. One transaction that starts and then sits idle (state idle in transaction) or runs for hours pins that horizon, so vacuum can clean nothing newer, on *every* table in the database.

SELECT pid, state, now() - xact_start AS xact_age, backend_xmin, left(query, 60) AS last_query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start
LIMIT 5;

Other things that hold the horizon back: long-running queries, prepared transactions that were never finished, replication slots that fall behind, and standbys with hot_standby_feedback enabled running long queries.

§2Bloat and Its Symptoms

When dead tuples cannot be removed, tables and indexes bloat: they occupy far more disk than the live data needs. Scans read more pages, indexes get larger and slower, caches hold useless data, and updates have fewer free spaces to reuse.

SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;

-- Exact (but expensive) measurement, from the pgstattuple extension:
SELECT * FROM pgstattuple('orders');

A table with a large dead_pct and an old last_autovacuum deserves a look at what is holding the horizon, not just a vacuum. Reclaiming already-bloated space needs VACUUM FULL (which rewrites the table under an exclusive lock) or an online tool like pg_repack.

§3Defending Against It

Prevention is cheap compared with cleanup.

-- Kill sessions that sit idle inside a transaction
ALTER ROLE shop_app SET idle_in_transaction_session_timeout = '30s';

-- Bound any statement or whole transaction (transaction_timeout exists in PostgreSQL 17+)
ALTER ROLE shop_app SET statement_timeout = '60s';
ALTER ROLE shop_app SET transaction_timeout = '5min';

Habits that help: begin a transaction only when you are ready to run statements and commit promptly; never wait for user input or a remote call inside one; run big reports against a replica; batch large updates into small transactions (for example, 10,000 rows at a time) so vacuum can follow along; and alert on the age of the oldest transaction and on replication slot lag.

The key insight Vacuum works at the speed of your slowest open transaction. Watch the age of the oldest transaction like you watch disk space.

§4Common Mistakes

MistakeWhat HappensFix
Letting application code hold a transaction open while waiting on I/OIdle-in-transaction sessions pin the horizon and block cleanupSet idle_in_transaction_session_timeout and shrink transaction scope
Fixing bloat only by running VACUUM repeatedlySpace is not reclaimed because something still holds old versionsFind and end the long transaction or lagging slot first
Updating millions of rows in a single statementOne huge transaction, long locks, and a flood of dead tuples at onceProcess in batches and commit between them
Practice
  1. Open a transaction in one session, update and delete rows in another, run VACUUM VERBOSE, and note the dead rows that could not be removed.
  2. Write a monitoring query that reports the oldest open transaction and its age.
  3. Set idle_in_transaction_session_timeout for a role and confirm an idle transaction is terminated.
Key takeaways
  • Vacuum can only remove row versions that no open transaction might still need, so one old transaction blocks cleanup everywhere.
  • Bloat shows up as dead tuples, growing tables and indexes, and slower scans; fix the cause, not just the symptom.
  • Use timeouts, short transactions, batched writes, and alerts on oldest-transaction age and slot lag.
