MVCC Explained

MVCC keeps several versions of a row so each transaction reads a consistent snapshot, which is why readers never block writers in Postgres.

§1Row Versions

Postgres never overwrites a row in place. An UPDATE writes a new version of the row and marks the old one as expired; a DELETE just marks the current version as expired. Each version records which transaction created it (xmin) and which one removed it (xmax). You can see these hidden system columns:

CREATE TABLE acct (id int PRIMARY KEY, balance int);
INSERT INTO acct VALUES (1, 100);

SELECT xmin, xmax, ctid, * FROM acct;      -- ctid is the row version's physical location
UPDATE acct SET balance = 90 WHERE id = 1;
SELECT xmin, xmax, ctid, * FROM acct;      -- new xmin, new ctid: a new version

The old versions are dead tuples once no transaction can still need them. They stay in the table until VACUUM reclaims the space (Lessons 2.3.5 and 2.4.4).

§2Snapshots

When a transaction (or, under Read Committed, each statement) starts, it takes a snapshot: a record of which transactions had committed at that moment. A row version is visible to you only if it was created by a transaction your snapshot considers committed, and not removed by one it considers committed. Your own changes are always visible to you.

-- Session A                           -- Session B
BEGIN;
SELECT balance FROM acct WHERE id=1;   -- 90
                                       BEGIN;
                                       UPDATE acct SET balance = 50 WHERE id=1;
SELECT balance FROM acct WHERE id=1;   -- still 90: B has not committed
                                       COMMIT;

This is the heart of MVCC (multi-version concurrency control): readers do not block writers and writers do not block readers. A long report can run while updates continue, each seeing a consistent view.

§3The Costs and What Still Blocks

MVCC is not free. Every update leaves a dead tuple, so tables need regular vacuuming, and tables with heavy updates grow beyond their live data size (bloat). Indexes also hold entries for old versions until vacuum cleans them.

Writers still block *each other*: two transactions updating the same row must take turns, because the second must wait to see whether the first commits.

-- Session A                                -- Session B
BEGIN;
UPDATE acct SET balance = 80 WHERE id=1;
                                            UPDATE acct SET balance = 70 WHERE id=1;  -- waits
COMMIT;                                     -- now B proceeds

So: reads never wait on writes, but row conflicts between writers serialize, and the cost of MVCC is paid by vacuum. Update only the columns and rows you must, since every update creates a version.

The key insight An UPDATE is really an insert of a new row version plus an expiry of the old one. That single fact explains snapshots, bloat, vacuum, and why readers and writers do not block each other.

§4Common Mistakes

MistakeWhat HappensFix
Assuming an UPDATE changes data in placeSurprise at table bloat and the need for vacuumRemember each update leaves a dead version until vacuum removes it
Expecting two writers to the same row to run in parallelThe second one waits for the first to commit or roll backKeep write transactions short, and avoid hot rows where possible
Updating all columns or rows when only one changesNeedless new versions and write amplificationUpdate only what changed, with a precise WHERE
Practice
  1. Run the xmin/ctid example, update the row twice, and watch the values change.
  2. Open two sessions and show that a reader sees the old value until the writer commits.
  3. Show a second writer blocking on the same row until the first session commits.
Key takeaways
  • Updates create new row versions; old versions are dead tuples until VACUUM reclaims them.
  • Each transaction or statement sees a snapshot, so readers and writers do not block each other.
  • Writers to the same row still serialize, and the price of MVCC is vacuum work and possible bloat.
