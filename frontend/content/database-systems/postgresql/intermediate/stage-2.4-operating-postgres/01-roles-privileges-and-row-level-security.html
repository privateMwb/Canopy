Roles, Privileges & Row-Level Security

GRANT and REVOKE control what each role can do, default privileges cover future objects, and row-level security filters which rows each user can see.

§1GRANT, REVOKE, and Default Privileges

Privileges are granted per object type: SELECT, INSERT, UPDATE, DELETE on tables; USAGE on schemas and sequences; EXECUTE on functions; CONNECT on databases. Grant to group roles, then add login roles to the groups.

CREATE ROLE reporting NOLOGIN;
GRANT CONNECT ON DATABASE shop TO reporting;
GRANT USAGE ON SCHEMA public TO reporting;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO reporting;      -- existing tables only

-- Tables created later by shop_owner get the same grant automatically
ALTER DEFAULT PRIVILEGES FOR ROLE shop_owner IN SCHEMA public
    GRANT SELECT ON TABLES TO reporting;

REVOKE ALL ON SCHEMA public FROM PUBLIC;       -- remove what everyone gets by default
CREATE ROLE analyst LOGIN; GRANT reporting TO analyst;

PUBLIC is a pseudo-role meaning everyone, and some objects grant it privileges by default (for example, CONNECT on new databases and EXECUTE on new functions). Review and revoke those in locked-down systems. Postgres also ships predefined roles such as pg_read_all_data, pg_write_all_data, and pg_monitor for common needs. Use \dp and \ddp in psql to inspect privileges.

§2Row-Level Security

GRANT works at the table level. Row-level security (RLS) adds rules that decide which *rows* a role can see or change, enforced by the database for every query. It is a strong fit for multi-tenant data.

ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON invoices
    USING      (tenant_id = current_setting('app.tenant_id')::bigint)   -- which rows are visible
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);  -- which rows can be written

-- Per request, the application sets who the caller is:
BEGIN;
SET LOCAL app.tenant_id = '17';
SELECT * FROM invoices;          -- only tenant 17's rows
COMMIT;

USING filters reads and the old row of updates and deletes; WITH CHECK validates new rows. With RLS enabled and no policy, nobody except the owner sees any rows (default deny). You can write policies per command (FOR SELECT, FOR UPDATE) and per role (TO app_user).

§3Pitfalls of RLS

  • Owners and superusers bypass RLS unless you run ALTER TABLE ... FORCE ROW LEVEL SECURITY (owners) and roles with BYPASSRLS are always exempt. Run the application as a non-owner, non-superuser role.
  • Pooling: use SET LOCAL inside a transaction, not session-level SET, so tenant context cannot leak between clients that share a server connection.
  • Performance: policy expressions are added to every query, so index the columns they use (such as tenant_id) and keep expressions simple and non-volatile.
  • Leaks through views and functions: views run with the view owner's privileges by default; set security_invoker = true (PostgreSQL 15+) so the caller's privileges and policies apply.

RLS is defense in depth, not a replacement for correct application logic. Test it: connect as the app role, set the context, and try to read and write across tenants.

The key insight Grant the least that works to group roles, and make the database the last line of defense: RLS means a forgotten WHERE tenant_id = ... in application code returns nothing instead of leaking data.

§4Common Mistakes

MistakeWhat HappensFix
Granting SELECT on existing tables and forgetting ALTER DEFAULT PRIVILEGESNew tables are inaccessible, or someone grants too broadly to fix itSet default privileges for the role that creates objects
Running the application as the table owner with RLS enabledThe owner bypasses the policies, so nothing is enforcedUse a separate non-owner role, or FORCE ROW LEVEL SECURITY
Using session-level SET app.tenant_id behind a poolerThe next client on that connection inherits the previous tenantUse SET LOCAL in a transaction
Practice
  1. Create a read-only role, grant it the minimum on a schema, and verify what it can and cannot do with \dp.
  2. Enable RLS on a multi-tenant table, write a policy, and test two tenant contexts from a non-owner role.
  3. Show that the table owner bypasses RLS, then use FORCE ROW LEVEL SECURITY and retest.
Key takeaways
  • Grant to group roles, set default privileges for future objects, and revoke unneeded PUBLIC privileges.
  • RLS policies (USING and WITH CHECK) enforce per-row access; no policy means no rows for non-owners.
  • Owners and superusers bypass RLS, and pooled connections need SET LOCAL for per-request context.
