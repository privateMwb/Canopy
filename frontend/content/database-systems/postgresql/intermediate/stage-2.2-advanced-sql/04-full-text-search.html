Full-Text Search

Postgres can search documents by meaning-bearing words rather than raw characters, with stemming, ranking, and an index, using tsvector and tsquery.

§1tsvector and tsquery

Full-text search turns a document into a tsvector: a sorted list of normalized words (lexemes) with positions, after removing stop words and reducing words to stems. A search is a tsquery. The @@ operator matches them.

SELECT to_tsvector('english', 'The quick brown foxes jumped over the lazy dogs');
-- 'brown':3 'dog':9 'fox':4 'jump':5 'lazi':8 'quick':2

SELECT to_tsvector('english', 'foxes jumped') @@ to_tsquery('english', 'fox & jump');   -- true

SELECT websearch_to_tsquery('english', '"brown fox" -cat OR dog');

to_tsquery uses operators &, |, !, and <-> (followed by). plainto_tsquery and websearch_to_tsquery accept natural user input, and websearch_to_tsquery understands quotes, OR, and - like a web search box, which makes it the best default for user-entered text. The text-search configuration ('english') decides stemming and stop words, so use the one matching your language.

§2Indexing, Ranking, and Highlighting

Computing to_tsvector for every row on every search is slow. Store it in a generated column and index it with GIN.

ALTER TABLE articles
    ADD COLUMN search tsvector GENERATED ALWAYS AS (
        setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
        setweight(to_tsvector('english', coalesce(body, '')),  'B')
    ) STORED;

CREATE INDEX articles_search_idx ON articles USING gin (search);

SELECT id, title,
       ts_rank(search, q) AS rank,
       ts_headline('english', body, q) AS snippet
FROM articles, websearch_to_tsquery('english', 'postgres replication') AS q
WHERE search @@ q
ORDER BY rank DESC
LIMIT 20;

setweight (A, B, C, D) lets title matches outrank body matches. ts_rank scores matches, and ts_headline returns a snippet with matched terms highlighted. Ranking runs only on the rows that match, so keep the match selective.

§3When Built-In Search Is Enough

Built-in full-text search is a strong fit for search over your own application data: documentation, product catalogs, articles, support tickets. It avoids a second system, stays transactionally consistent with the data, and needs no synchronization pipeline.

It is not a drop-in for everything. It does not tolerate typos, and ranking is simpler than dedicated engines (no learned relevance, limited faceting). For fuzzy matching and substring search, the pg_trgm extension adds trigram similarity and makes LIKE '%term%' indexable. Consider a dedicated search engine when you need typo tolerance at scale, advanced relevance tuning, faceted navigation, or very large multi-language corpora. Many applications never reach that point.

The key insight Store the tsvector in a generated column with a GIN index, accept user input through websearch_to_tsquery, and rank only the matches. That small recipe covers most application search.

§4Common Mistakes

MistakeWhat HappensFix
Calling to_tsvector(...) in WHERE without an indexEvery search recomputes the vector for every rowUse a stored tsvector column with a GIN index
Using the wrong language configurationPoor stemming and wrong stop wordsPass the correct configuration, or store the language per row
Building queries by concatenating user text into to_tsquerySyntax errors on stray punctuationUse websearch_to_tsquery or plainto_tsquery
Practice
  1. Add a weighted, generated tsvector column and GIN index to an articles table and search it with websearch_to_tsquery.
  2. Return ranked results with ts_rank and a highlighted snippet with ts_headline.
  3. Enable pg_trgm and compare a LIKE '%term%' query with and without a trigram GIN index.
Key takeaways
  • tsvector holds normalized words; tsquery is the search; @@ matches them.
  • Generated tsvector column plus GIN index, websearch_to_tsquery for input, ts_rank and ts_headline for presentation.
  • Built-in search suits most application data; reach for pg_trgm for fuzzy matching and a dedicated engine only when you outgrow it.
