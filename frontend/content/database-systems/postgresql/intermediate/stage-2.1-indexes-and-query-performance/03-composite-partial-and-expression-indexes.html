Composite, Partial & Expression Indexes

Column order in a composite index matters, a partial index covers only the rows you query, and an expression index covers a computed value.

§1Composite Indexes and Column Order

A multi-column index is sorted by the first column, then by the second within equal first values, and so on, like a phone book sorted by surname then first name.

CREATE INDEX orders_cust_date_idx ON orders (customer_id, placed_at);

-- Uses the index fully
SELECT * FROM orders WHERE customer_id = 42 AND placed_at >= '2026-01-01';
SELECT * FROM orders WHERE customer_id = 42 ORDER BY placed_at DESC LIMIT 10;

-- Weak: no condition on the leading column
SELECT * FROM orders WHERE placed_at >= '2026-01-01';

The general rule: put columns tested with equality first and the column with a range or sort last. The index serves queries that constrain a *prefix* of its columns. On PostgreSQL 18, B-tree skip scan can sometimes use an index even when the leading column is unconstrained, but only when that column has few distinct values; do not rely on it for high-cardinality columns. One composite index often replaces several single-column ones, and a separate index on (customer_id) is redundant if (customer_id, placed_at) exists.

§2Partial Indexes

A partial index has a WHERE clause and indexes only matching rows. It is smaller, faster to maintain, and perfect when queries target a small, well-defined slice.

-- Only unshipped orders are queried by status; most rows are shipped
CREATE INDEX orders_open_idx ON orders (placed_at) WHERE status = 'new';

-- Uniqueness for a subset: one active subscription per user
CREATE UNIQUE INDEX one_active_sub ON subscriptions (user_id) WHERE active;

The planner uses a partial index only when it can prove the query's WHERE implies the index's predicate. A query for status = 'new' qualifies; a query that does not mention the status does not.

§3Expression Indexes

An expression index stores the result of a function or computation, so queries on that expression can use it. The query must use the identical expression.

CREATE INDEX books_lower_title_idx ON books (lower(title));
SELECT * FROM books WHERE lower(title) = 'dune';          -- uses the index

CREATE INDEX orders_day_idx ON orders (date_trunc('day', placed_at));
CREATE UNIQUE INDEX users_email_ci ON users (lower(email)); -- case-insensitive uniqueness

The expression must be IMMUTABLE (same input always gives the same output). Functions that depend on the session time zone, like casting timestamptz to date, are not immutable; specify the zone explicitly, for example (placed_at AT TIME ZONE 'UTC')::date. After creating an expression index, run ANALYZE so the planner has statistics on the expression.

The key insight Design indexes from your queries, not from your columns. Equality columns first, range or sort column last, and add a WHERE or an expression when the query targets a slice or a computed value.

§4Common Mistakes

MistakeWhat HappensFix
Putting the range column first in a composite indexThe index cannot narrow by the equality column that followsOrder columns equality first, then range or sort
A partial index whose predicate does not match the queryThe planner ignores itRepeat the same condition in the query's WHERE
Writing lower(email) in queries but indexing plain emailA sequential scan on every loginCreate an expression index on lower(email)
Practice
  1. Create (customer_id, placed_at) and show with EXPLAIN which of three queries use it.
  2. Build a partial index for open orders and compare its size with a full index (\di+).
  3. Add a case-insensitive unique index on lower(email) and confirm duplicates differing only by case are rejected.
Key takeaways
  • A composite index serves queries that constrain a prefix of its columns; equality columns go first.
  • Partial indexes shrink the index to the rows you query, and the query must imply the predicate.
  • Expression indexes need the exact same expression in the query, and the expression must be immutable.
