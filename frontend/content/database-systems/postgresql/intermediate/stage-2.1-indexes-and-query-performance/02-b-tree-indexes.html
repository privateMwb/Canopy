B-tree Indexes

A B-tree index keeps keys in sorted order so Postgres can find a value, a range, or an ordering without reading the whole table.

§1What a B-tree Does

CREATE INDEX builds a B-tree by default: a balanced tree of sorted keys, each pointing to the row's location in the table. Finding one key takes a handful of page reads even in a table of hundreds of millions of rows, because each level of the tree fans out wide.

CREATE INDEX orders_customer_id_idx ON orders (customer_id);

SELECT * FROM orders WHERE customer_id = 42;          -- equality
SELECT * FROM orders WHERE placed_at >= '2026-01-01'; -- range (with an index on placed_at)
SELECT * FROM orders ORDER BY placed_at DESC LIMIT 20; -- ordering, no sort needed

A B-tree serves =, <, <=, >, >=, BETWEEN, IN, anchored LIKE 'abc%' (with the right operator class or the C collation), IS NULL, and ORDER BY on the indexed column. Primary key and UNIQUE constraints create B-tree indexes for you.

§2What an Index Cannot Do

An index helps only when the query's condition matches how the index is sorted.

SELECT * FROM books WHERE lower(title) = 'dune';     -- no use: index is on title, not lower(title)
SELECT * FROM orders WHERE total + 0 > 100;          -- expression hides the column
SELECT * FROM books WHERE title LIKE '%dune%';       -- leading wildcard: no sorted prefix
SELECT * FROM orders WHERE customer_id::text = '42'; -- cast on the column defeats the index

Also, if a query reads a large fraction of the table, the planner correctly prefers a sequential scan, because jumping around by index for millions of rows costs more than reading pages in order. Each index also has a cost: it takes disk space and every INSERT, UPDATE, and DELETE must maintain it. Index what you query, not every column.

§3Building and Checking Indexes

On a live table, CREATE INDEX blocks writes for its duration. Use CONCURRENTLY to build without blocking writes; it takes longer and cannot run inside a transaction block. If it fails it leaves an INVALID index that you must drop.

CREATE INDEX CONCURRENTLY orders_placed_at_idx ON orders (placed_at);
DROP INDEX CONCURRENTLY orders_placed_at_idx;

-- Is an index ever used? Unused indexes only cost you writes.
SELECT relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
ORDER BY idx_scan;

Verify an index helps by comparing EXPLAIN ANALYZE before and after. If the planner ignores your index, the cause is usually a mismatch (an expression or cast), a query that returns too many rows, or stale statistics, not a planner bug.

The key insight An index is a second copy of some columns, sorted for fast lookup. It speeds reads that match its order and slows every write, so each index must earn its keep.

§4Common Mistakes

MistakeWhat HappensFix
Applying a function to an indexed column in WHEREThe planner cannot use the plain indexIndex the expression, or rewrite the condition so the column stands alone
Indexing every column "just in case"Writes slow down and disk use balloonsIndex columns that real queries filter, join, or sort on; check idx_scan
Creating a big index without CONCURRENTLY on a live tableWrites are blocked while it buildsUse CREATE INDEX CONCURRENTLY and check for INVALID leftovers
Practice
  1. Create a table with a million rows, time a lookup by an unindexed column, add an index, and compare EXPLAIN ANALYZE output.
  2. Show that WHERE lower(title) = 'dune' does not use an index on title.
  3. Query pg_stat_user_indexes and identify any index with zero scans.
Key takeaways
  • B-tree indexes serve equality, ranges, and ordering on the indexed columns.
  • Functions, casts, and leading wildcards on the column prevent index use.
  • Every index costs write performance and space; build with CONCURRENTLY on live tables and drop the unused.
