Normalization in Practice

Normalization removes redundancy so each fact is stored once, and knowing the normal forms tells you when copying data is a deliberate choice.

§1Why Redundancy Hurts

Suppose every order row repeats the customer's name and city. Changing a customer's city now means updating many rows, and missing one leaves the database contradicting itself. These update, insert, and delete anomalies are what normalization prevents.

-- Unnormalized: customer facts repeated on every order
orders(order_id, customer_name, customer_city, product, price)

-- Normalized: each fact lives in exactly one place
customers(id, name, city)
orders(id, customer_id)
products(id, name, price)
order_items(order_id, product_id, quantity)

§2The Normal Forms in Plain Terms

  • First normal form (1NF): each column holds one atomic value, with no repeating groups or comma-separated lists, and each row is identifiable by a key.
  • Second normal form (2NF): every non-key column depends on the *whole* key. This matters for composite keys: in order_items(order_id, product_id, product_name), product_name depends only on product_id, so move it out.
  • Third normal form (3NF): non-key columns depend on the key and nothing but the key. If zip determines city, store city in a zip_codes table rather than on every address.

A handy phrase: every non-key attribute depends on the key, the whole key, and nothing but the key. Stopping at 3NF is the right target for most transactional systems. Higher forms (BCNF, 4NF) rarely change a practical design.

§3Breaking the Rules on Purpose

Normalization is a tool, not a law. Controlled denormalization is justified when you have evidence:

  • Snapshots of history: an order line should store the unit price at purchase time, not look up today's price. This is not redundancy; it is a different fact.
  • Derived values for speed: a cached order_total or a counter column, kept correct by a trigger or by the application inside the same transaction.
  • Read-heavy reporting: a summary table or materialized view refreshed on a schedule.
  • Semi-structured attributes: a jsonb column for properties that really do vary per row.
CREATE TABLE order_items (
    order_id   bigint NOT NULL REFERENCES orders (id),
    product_id bigint NOT NULL REFERENCES products (id),
    quantity   int    NOT NULL CHECK (quantity > 0),
    unit_price numeric(10,2) NOT NULL,        -- price at time of sale
    PRIMARY KEY (order_id, product_id)
);

Every denormalized column is a promise to keep two copies in sync. Write down who keeps that promise.

The key insight Normalize first, then denormalize only for a measured reason and with a clear owner for keeping copies consistent. Historical snapshots are not violations; they are different facts.

§4Common Mistakes

MistakeWhat HappensFix
Storing a list in a column to "save a table"Cannot query, index, or constrain individual valuesUse a child table or, for truly flexible data, jsonb
Copying customer details onto every order and treating them as currentUpdates diverge and reports disagreeReference the customer; snapshot only what must be historical (address at ship time)
Denormalizing before measuring anythingExtra write complexity with no proven benefitFix the query or add an index first; denormalize with evidence
Practice
  1. Take a flat spreadsheet of orders (customer, address, product, price, quantity) and normalize it to 3NF, listing each table's key.
  2. Identify two columns in a schema you know that are snapshots, and two that are accidental copies.
  3. Add a cached order_total and describe how you would keep it correct within a transaction.
Key takeaways
  • Normalization stores each fact once, preventing update, insert, and delete anomalies.
  • 3NF: each non-key attribute depends on the key, the whole key, and nothing but the key.
  • Denormalize deliberately, for history, measured performance, or flexible attributes, and name who keeps copies in sync.
