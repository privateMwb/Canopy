Views, Sequences & Identity Columns

Views save reusable queries, and sequences and identity columns generate keys, with gaps that are expected and harmless.

§1Views and Materialized Views

A view is a stored query that behaves like a table. It stores no data; each time you select from it, Postgres runs the underlying query.

CREATE VIEW active_customers AS
SELECT c.id, c.email, count(o.id) AS orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.email;

SELECT * FROM active_customers WHERE orders > 5;

Views hide complexity, give applications a stable shape, and let you grant access to a subset of columns. A materialized view stores the result physically and must be refreshed, trading freshness for speed.

CREATE MATERIALIZED VIEW daily_sales AS
SELECT date_trunc('day', placed_at) AS day, count(*) AS orders
FROM orders GROUP BY 1;

REFRESH MATERIALIZED VIEW daily_sales;                          -- locks readers while it runs
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales;             -- needs a unique index

§2Sequences and Identity Columns

A sequence is a counter object that hands out increasing numbers. An identity column attaches one to a column using the SQL standard syntax, and is the modern replacement for serial.

CREATE TABLE books (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title text NOT NULL
);

INSERT INTO books (title) VALUES ('Dune') RETURNING id;
INSERT INTO books (id, title) VALUES (5, 'x');
-- ERROR: cannot insert a non-DEFAULT value into column "id"

GENERATED ALWAYS rejects manual values unless you add OVERRIDING SYSTEM VALUE; GENERATED BY DEFAULT allows them. Prefer ALWAYS so application code cannot collide with the counter. After a bulk load with explicit IDs, move the sequence forward with SELECT setval(pg_get_serial_sequence('books','id'), (SELECT max(id) FROM books));.

§3Why There Are Gaps

Sequences are not transactional. A value, once handed out, is never given back, even if the transaction rolls back or the insert fails. Postgres also hands out values to concurrent sessions in any order, and a crash can skip cached values. The result is gaps, and sometimes ordering that differs from commit order.

BEGIN;
INSERT INTO books (title) VALUES ('a');   -- gets id 10
ROLLBACK;
INSERT INTO books (title) VALUES ('b');   -- gets id 11; 10 is a gap

Keys exist to be unique, not gapless. If a legal requirement demands gapless numbering (invoice numbers in some jurisdictions), generate them in a separate, locked process rather than from a sequence, and accept the contention that costs.

The key insight Treat generated IDs as opaque unique labels. Never rely on them being consecutive, never reuse them, and never infer row counts or creation order from them.

§4Common Mistakes

MistakeWhat HappensFix
Expecting ID sequences to have no gapsCode that depends on consecutive numbers breaks after the first rollbackTreat IDs as opaque; use a separate counter for legally gapless numbers
Selecting from a slow view on every requestThe full underlying query runs each timeIndex the base tables, or use a materialized view with a refresh schedule
Bulk loading explicit IDs and forgetting the sequenceLater inserts collide with existing keysRun setval to move the sequence past the maximum
Practice
  1. Create a view over a join and grant a role access to the view but not the base tables.
  2. Insert rows, roll one back, and observe the gap in the identity sequence.
  3. Create a materialized view and compare REFRESH with REFRESH ... CONCURRENTLY.
Key takeaways
  • A view is a saved query; a materialized view stores results and needs refreshing.
  • Use identity columns (GENERATED ALWAYS AS IDENTITY) instead of serial for new tables.
  • Sequences are non-transactional, so gaps are normal; never depend on consecutive IDs.
