Modeling Entities & Relationships

Good schemas start on paper: identify the things you store, how they relate, and how many of each can be linked to the other.

§1Entities and Attributes

An entity is a kind of thing the system must remember: a customer, an order, a book. Each entity becomes a table, each instance a row, and each fact about it a column (an attribute). Start by writing nouns from the requirements, then ask for each one: what identifies it, and what do we know about it?

A good first pass names the key explicitly. Prefer a surrogate key (id bigint GENERATED ALWAYS AS IDENTITY) for most tables, and add a UNIQUE constraint on any natural identifier such as an email address or ISBN, so both are enforced.

§2One-to-Many

The most common relationship: one customer has many orders, but each order belongs to one customer. Store the relationship as a foreign key on the "many" side.

CREATE TABLE customers (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL UNIQUE
);
CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL REFERENCES customers (id),
    placed_at   timestamptz NOT NULL DEFAULT now()
);

NOT NULL on the foreign key means an order cannot exist without a customer; leave it nullable only when the link is optional. A one-to-one relationship is a one-to-many with a UNIQUE foreign key, and is rare: it usually means two tables should be one, or that you are splitting off rarely used or sensitive columns.

§3Many-to-Many and Join Tables

Books have many authors and authors have many books. A relational table cannot hold a list of foreign keys, so you add a join table (also called a junction or link table) with one row per pairing.

CREATE TABLE book_authors (
    book_id   bigint NOT NULL REFERENCES books (id),
    author_id bigint NOT NULL REFERENCES authors (id),
    position  int NOT NULL DEFAULT 1,           -- attribute of the relationship
    PRIMARY KEY (book_id, author_id)
);
CREATE INDEX ON book_authors (author_id);       -- the reverse lookup

The composite primary key prevents duplicate pairings. The join table is also the right place for facts about the relationship itself, like author order, or the quantity and unit price on an order line. Draw boxes and crow's-foot lines for tables and relationships before writing SQL; mistakes are far cheaper to fix on a whiteboard.

The key insight Foreign keys live on the "many" side, and a many-to-many relationship always needs its own table. If you catch yourself storing a comma-separated list in a column, you need a join table.

§4Common Mistakes

MistakeWhat HappensFix
Storing multiple values in one column ('1,4,9')Cannot join, index, or constrain the valuesUse a join table with one row per value
Putting the foreign key on the wrong sideA relationship that should be many-to-one becomes unrepresentableThe table that can have many gets the column pointing to the "one"
Forgetting an index for the reverse direction of a join tableLookups from authors to books scan the whole tableIndex the second key column too
Practice
  1. Sketch a library system with members, books, copies, and loans, and label every relationship's cardinality.
  2. Create customers, orders, and order_items (a join table with quantity and unit price) in SQL.
  3. Explain which side holds the foreign key in a one-to-many, and why a one-to-one is a design smell.
Key takeaways
  • Entities become tables and attributes become columns; give each table a primary key.
  • One-to-many puts the foreign key on the "many" side.
  • Many-to-many needs a join table, which is also where relationship attributes belong.
