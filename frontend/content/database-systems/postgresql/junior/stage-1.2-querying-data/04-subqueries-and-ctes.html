Subqueries & CTEs

Subqueries nest one query inside another, and common table expressions (CTEs) name each step so complex SQL reads top to bottom.

§1Subqueries

A subquery is a SELECT inside another statement. A scalar subquery returns one value; a list subquery feeds IN; an EXISTS subquery asks whether any row exists.

SELECT title, price
FROM books
WHERE price > (SELECT avg(price) FROM books);             -- scalar

SELECT name FROM authors
WHERE id IN (SELECT author_id FROM books WHERE in_stock); -- list

SELECT name FROM authors a
WHERE NOT EXISTS (SELECT 1 FROM books b WHERE b.author_id = a.id);

The last query is correlated: it refers to the outer row (a.id), so conceptually it runs once per outer row. The planner usually rewrites these into joins, so write whichever form reads best. Prefer NOT EXISTS over NOT IN because NOT IN returns nothing at all if the subquery produces any NULL.

§2Common Table Expressions

WITH defines named temporary result sets that later parts of the query can use.

WITH recent AS (
    SELECT id, author_id, price
    FROM books
    WHERE published >= current_date - interval '1 year'
),
per_author AS (
    SELECT author_id, count(*) AS n, sum(price) AS total
    FROM recent
    GROUP BY author_id
)
SELECT a.name, p.n, p.total
FROM per_author p
JOIN authors a ON a.id = p.author_id
ORDER BY p.total DESC;

Each step is small enough to test on its own: select from recent, then from per_author. Since Postgres 12, a non-recursive CTE that is referenced once is inlined into the query, so it carries no performance penalty by default. Write WITH x AS MATERIALIZED (...) to force it to be computed once, or NOT MATERIALIZED to force inlining.

§3Data-Modifying CTEs and When to Use Each

CTEs can contain INSERT, UPDATE, or DELETE ... RETURNING, which lets one statement move rows atomically.

WITH moved AS (
    DELETE FROM books WHERE in_stock = false RETURNING *
)
INSERT INTO books_archive SELECT * FROM moved;

Use a plain subquery for a single small lookup, EXISTS for presence checks, and a CTE when you have multiple steps or want to refer to a result twice. Recursive CTEs, which walk hierarchies, are covered in Stage 2.2.

The key insight A CTE is a readability tool first. Name each step after what it produces, and your query becomes a short pipeline instead of a deeply nested block.

§4Common Mistakes

MistakeWhat HappensFix
NOT IN with a subquery that can return NULLThe whole condition becomes unknown and zero rows come backUse NOT EXISTS
Assuming a correlated subquery is always slowNeedless rewrites that hurt readabilityCheck EXPLAIN; the planner often turns it into a join
Chaining five levels of nested subqueriesHard to read and impossible to test piecewiseBreak the logic into named CTEs
Practice
  1. Find books priced above the average price of their own author's books (a correlated subquery).
  2. Rewrite a three-level nested query as a sequence of CTEs.
  3. Use a data-modifying CTE to archive and delete out-of-stock books in one statement, inside a transaction you can roll back.
Key takeaways
  • Scalar, list, and EXISTS subqueries each answer a different shape of question.
  • NOT EXISTS is safer than NOT IN when NULLs are possible.
  • CTEs name each step; on modern Postgres they are inlined by default, so readability costs nothing.
