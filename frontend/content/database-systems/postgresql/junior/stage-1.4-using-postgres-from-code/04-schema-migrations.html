Schema Migrations

Migrations are versioned scripts that change the schema in order, so every environment reaches the same structure by the same path.

§1Why Versioned Migrations

Editing the database by hand makes environments drift: production differs from staging, and nobody knows which ALTER ran where. A migration is a numbered script stored in version control. A tool records which ones have been applied (in a table, often schema_migrations) and runs only the new ones, in order.

migrations/
  0001_create_customers.sql
  0002_create_orders.sql
  0003_add_orders_status.sql

Common tools: Flyway, Liquibase, Alembic (Python), golang-migrate, Sqitch, Atlas, and the migration systems built into Rails, Django, and Prisma. They differ in syntax, but all rely on the same idea: schema as ordered, reviewed code.

§2Writing a Good Migration

Each migration should do one logical change, be safe to run once, and be committed with the application code that needs it. Never edit a migration that has already been applied elsewhere; add a new one that corrects it.

-- 0003_add_orders_status.sql
BEGIN;
ALTER TABLE orders
    ADD COLUMN status text NOT NULL DEFAULT 'new'
    CHECK (status IN ('new', 'paid', 'shipped', 'cancelled'));
CREATE INDEX orders_status_idx ON orders (status);
COMMIT;

Because Postgres DDL is transactional, a failed migration rolls back cleanly instead of leaving a half-changed schema. A few statements cannot run inside a transaction block, such as CREATE INDEX CONCURRENTLY; tools offer a per-migration switch for that. Many tools also support a "down" script, but a tested forward fix is usually safer than a rollback script nobody has run.

§3Safety Habits

  • Test migrations on a copy of realistic data, not just an empty database.
  • Apply them in a deploy step, from CI, with the owner role, before the new application version needs them.
  • Mind locks. ALTER TABLE can take a strong lock; on a large, busy table a naive change can block every query. Stage 3.4 covers zero-downtime patterns.
  • Separate schema from data. Large backfills belong in batched jobs, not inside the migration transaction.
-- Check what a migration will lock before running it in production
SET lock_timeout = '3s';     -- fail fast instead of queuing behind a long query
ALTER TABLE orders ADD COLUMN note text;
The key insight The schema is code. If a change is not in a numbered, reviewed, committed migration, it did not happen in a way anyone else can reproduce.

§4Common Mistakes

MistakeWhat HappensFix
Editing an already-applied migrationEnvironments diverge and checksums failLeave it alone and add a new corrective migration
Making manual changes in production "just this once"Staging and production drift apartWrite the migration and apply it through the tool
Running a long backfill inside the migration transactionLocks held for the duration, blocking trafficRun backfills in small batches as a separate job
Practice
  1. Set up a migration tool of your choice and create three migrations for a bookstore schema.
  2. Add a NOT NULL column with a default in a migration and verify it on a table with a million rows, noting how long it took.
  3. Add lock_timeout to a migration and show what happens when another session holds a conflicting lock.
Key takeaways
  • Migrations are ordered, committed scripts, and a table records what has been applied.
  • Never edit applied migrations; fix forward with a new one.
  • Use transactional DDL, lock_timeout, and realistic test data to make changes safe.
