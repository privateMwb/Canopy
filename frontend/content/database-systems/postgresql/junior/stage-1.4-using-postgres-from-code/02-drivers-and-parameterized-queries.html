Drivers & Parameterized Queries

Passing values as parameters, never by building SQL strings, is what stops SQL injection and lets Postgres reuse query plans.

§1What a Driver Does

A driver speaks the Postgres wire protocol for your language: psycopg for Python, pgx for Go, node-postgres (pg) for Node, the official JDBC driver for Java, and so on. It opens connections, sends statements, and converts results into native types. Many applications put an ORM or query builder on top, but those also rely on a driver underneath.

# Python, psycopg 3
import psycopg

with psycopg.connect("postgresql://app@localhost/shop") as conn:
    rows = conn.execute("SELECT id, title FROM books WHERE price < %s", (15,)).fetchall()

§2SQL Injection and Parameters

Building SQL by concatenating user input lets that input become part of the statement.

# DANGEROUS: string formatting
title = request.args["title"]                  # user types:  x'; DROP TABLE books; --
conn.execute(f"SELECT * FROM books WHERE title = '{title}'")

# SAFE: the value travels separately from the SQL text
conn.execute("SELECT * FROM books WHERE title = %s", (title,))

With a parameterized query, the SQL text and the values are kept apart, so a value can never change the structure of the statement. Placeholder styles differ by driver (%s in psycopg, $1 in pg and pgx, ? in JDBC), but the principle is identical. The driver may use the extended protocol (the server receives the values separately) or escape values correctly itself; either way, use placeholders and never hand-built strings.

§3What Cannot Be a Parameter

Parameters stand in for values, not for identifiers or keywords. Table names, column names, and ORDER BY directions cannot be parameters.

# Wrong: this tries to pass a column name as a value
conn.execute("SELECT * FROM books ORDER BY %s", (sort_col,))   # sorts by a constant

# Right: choose from an allowlist, or quote identifiers with the driver's helper
allowed = {"price", "title", "published"}
col = sort_col if sort_col in allowed else "title"
conn.execute(f"SELECT * FROM books ORDER BY {col}")            # safe: value is from the allowlist

Also: use RETURNING to fetch generated IDs in one round trip, send many rows with one multi-row INSERT or the driver's batch or COPY support, and always close cursors and connections (a with block does this). Let the driver handle types: pass a real date object, not a formatted string.

The key insight SQL injection is a failure to separate code from data. Parameters enforce that separation in the protocol itself, which no amount of hand-written escaping reliably matches.

§4Common Mistakes

MistakeWhat HappensFix
Building queries with f-strings or + concatenationUser input can change the statement; classic SQL injectionUse placeholders for every value
Trying to parameterize a table or column nameThe value is treated as a literal and the query does not do what you expectValidate against an allowlist, or use the driver's identifier-quoting helper
Opening a new connection for every requestHigh latency and exhausted server connectionsReuse connections through a pool (next lesson)
Practice
  1. Write a function that fetches a book by title with a parameterized query, then try passing x' OR '1'='1 and confirm it returns nothing.
  2. Implement a safe sortable listing endpoint that accepts a column name from the user using an allowlist.
  3. Insert 1,000 rows with one batched call instead of 1,000 separate calls and compare the time.
Key takeaways
  • Always pass values as parameters; never format user input into SQL text.
  • Placeholders cover values only; identifiers need an allowlist or proper quoting.
  • Use RETURNING and batched writes to cut round trips.
