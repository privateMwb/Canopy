Connection Pooling Basics

Each Postgres connection is a whole operating system process, so you cap how many there are and reuse them through a pool.

§1Why Connections Are Expensive

Postgres starts one backend process per client connection. Each one needs memory (typically several megabytes at idle, more under load), competes for CPU, and adds work to the server's bookkeeping. Opening a connection also costs a TCP handshake, TLS negotiation, authentication, and process startup, often tens of milliseconds.

The server's max_connections (100 by default) is a hard limit. Setting it to thousands does not make the database faster; more simultaneous active queries than CPU cores just means they queue and contend. A healthy system has a small number of active connections doing real work.

SHOW max_connections;
SELECT count(*), state FROM pg_stat_activity GROUP BY state;

§2Application Pools and PgBouncer

A connection pool keeps a set of open connections and lends one to each request, so you pay the setup cost once. Most drivers and frameworks include an in-process pool: size it by what the database can run, not by the number of web requests.

When you have many application instances, or serverless functions that cannot hold connections, put an external pooler such as PgBouncer in front of Postgres. Clients connect to PgBouncer cheaply and it multiplexes them onto a small set of real server connections.

# pgbouncer.ini (excerpt)
[databases]
shop = host=127.0.0.1 port=5432 dbname=shop

[pgbouncer]
listen_port = 6432
pool_mode = transaction
default_pool_size = 20
max_client_conn = 1000

§3Pool Modes and Their Catch

PgBouncer can assign a server connection for different lengths of time.

ModeServer connection held forNotes
sessionThe whole client connectionSafest; least sharing
transactionOne transactionBest sharing; most common
statementOne statementCannot use multi-statement transactions

In transaction mode, anything tied to a session is unreliable because the next transaction may run on a different server connection: SET without LOCAL, session-level advisory locks, LISTEN/NOTIFY, and temporary tables. Prepared-statement support depends on the PgBouncer version and settings, so check your version's documentation. A rough sizing guide: the number of active server connections should sit near a small multiple of CPU cores, and the pool queues the rest.

The key insight More connections do not mean more throughput. Size pools to what the CPU and disks can run concurrently, and let extra requests wait in the pool rather than inside Postgres.

§4Common Mistakes

MistakeWhat HappensFix
Raising max_connections to fix "too many connections" errorsMemory pressure and context switching slow everythingAdd a pooler and cap pool sizes
Using session state with transaction poolingSettings and locks leak between clients or vanish unexpectedlyUse SET LOCAL, or session pool mode for those clients
Each of many app instances opening its own large poolTotal connections exceed the server limit during scale-outBudget pool_size × instances against max_connections, or use PgBouncer
Practice
  1. Query pg_stat_activity while running a small load test and see how many connections are active versus idle.
  2. Compute the connection budget for 10 app instances with a pool size of 20 against max_connections = 100.
  3. Run PgBouncer in transaction mode locally and connect through port 6432.
Key takeaways
  • Each connection is a server process; the count that actually helps is small.
  • Pool in the application, and add PgBouncer when many instances or serverless clients connect.
  • Transaction pooling breaks session-scoped state; know which features you rely on.
