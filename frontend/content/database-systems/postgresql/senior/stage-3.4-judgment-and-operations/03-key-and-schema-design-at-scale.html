Key & Schema Design at Scale

Some design choices are cheap to make and expensive to reverse: key types, tenant models, and partition keys deserve extra thought on day one.

§1bigint, UUID, and Public Identifiers

bigint identity keys are compact (8 bytes), ordered by insertion, and friendly to indexes and caches, because new rows append to the right edge of the B-tree. Their downsides: sequential values are guessable, and generating them in a sharded or offline setting needs coordination.

UUIDs (16 bytes) can be generated anywhere without coordination and are not guessable. Random UUIDv4 keys scatter inserts across the whole index, hurting cache locality, causing page splits, and inflating WAL. UUIDv7 values are time-ordered and avoid most of that; PostgreSQL 18 provides uuidv7() natively, and earlier versions can generate them in the application.

CREATE TABLE orders (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- internal
    public_id  uuid NOT NULL DEFAULT gen_random_uuid() UNIQUE,    -- exposed in URLs and APIs
    ...
);

A common compromise: a bigint primary key for joins and storage, plus a separate unguessable public identifier for outside use. Whatever you choose, use one consistent type everywhere; mixing types makes foreign keys and joins awkward, and changing a primary key's type later means rewriting every table that references it.

§2Multi-Tenancy Models

When one application serves many customers (tenants), you choose how to separate their data.

ModelStrengthsCosts
Shared tables with a tenant_id columnSimplest to operate; scales to many small tenantsIsolation relies on queries and RLS; noisy neighbors; hard to move one tenant
Schema per tenantClear separation; per-tenant restore easierThousands of schemas strain the catalog; migrations run N times
Database per tenantStrong isolation; easy to move or delete a tenantConnection and operational overhead; cross-tenant reporting is hard
-- Shared-tables model: tenant_id leads every key and index; RLS as a safety net
CREATE TABLE invoices (
    tenant_id bigint NOT NULL,
    id        bigint GENERATED ALWAYS AS IDENTITY,
    total     numeric(12,2) NOT NULL,
    PRIMARY KEY (tenant_id, id)
);
ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;

Most products start with shared tables plus RLS and move a few very large or regulated tenants into their own databases. Put tenant_id into the schema from the first day; adding it later to every table is a large migration.

§3Decisions That Are Painful to Reverse

Treat these as one-way doors and decide them deliberately:

  • Primary key type and strategy (above), since it spreads into every foreign key.
  • Tenant model and tenant key, which touches every table, index, and query.
  • Partition key, because repartitioning means rewriting the data.
  • timestamptz versus timestamp, and storing UTC instants rather than local times.
  • Money as numeric or integer minor units, plus a currency column.
  • Enums versus lookup tables: an enum is compact but removing or reordering values is awkward; a lookup table or CHECK is easier to change.
  • Soft deletes (deleted_at): they complicate every query, unique constraint, and foreign key; consider archiving tables or partial unique indexes instead.
  • Naming conventions (singular or plural, snake_case), which you will live with forever.

Write down the reasoning (a short design note per decision), because future maintainers need the "why", not only the schema. Review the one-way doors with a skeptical colleague before the first migration ships.

The key insight Reversibility is a design criterion. Spend design effort where changing your mind later would mean rewriting data, and stay flexible everywhere else.

§4Common Mistakes

MistakeWhat HappensFix
Using random UUIDv4 as the primary key of a huge, write-heavy tableIndex fragmentation, cache misses, and extra WALUse bigint or time-ordered UUIDv7, with a separate public ID if needed
Exposing sequential IDs in URLsEnumeration and information leaks about volumeUse an unguessable public identifier
Adding multi-tenancy after the schema existsA migration of every table, key, index, and queryDecide the tenant model at the start, and include tenant_id from day one
Practice
  1. Insert a million rows with bigint, UUIDv4, and UUIDv7 keys into three tables and compare index size and insert time.
  2. Choose a tenant model for a hypothetical product with 50,000 small customers and five large ones, and defend your choice.
  3. List five decisions in a schema you know that would be hard to reverse, and note who decided each and why.
Key takeaways
  • Pick one key strategy deliberately: bigint for storage, time-ordered UUIDs for distributed generation, a separate public ID for exposure.
  • Tenant models trade operational simplicity against isolation; decide early and carry tenant_id into every key.
  • Identify the one-way doors up front, and record the reasoning behind each.
