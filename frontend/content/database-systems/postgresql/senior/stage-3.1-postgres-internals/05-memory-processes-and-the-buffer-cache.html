Memory, Processes & the Buffer Cache

Each connection is a process, shared memory holds the buffer cache, and the operating system's page cache sits underneath it, so Postgres effectively caches twice.

§1The Process Model

Postgres is process-per-connection. A supervisor process (the postmaster) listens for connections and forks a backend process for each one. Several background processes run alongside: the checkpointer, background writer, WAL writer, autovacuum launcher and workers, WAL senders and receivers for replication, and the stats machinery.

SELECT pid, backend_type, state FROM pg_stat_activity ORDER BY backend_type;

Processes share state through shared memory: the buffer cache, lock tables, and WAL buffers. This design is simple and robust (a crashed backend does not take down the others' memory), and it explains why connections cost memory and why poolers matter. Parallel queries add temporary parallel workers that cooperate on one query (max_parallel_workers_per_gather).

§2Shared Buffers and the OS Cache

Reads go through shared buffers: a fixed-size array of 8 kB buffers in shared memory. A page is looked up there first (a hit); if absent, it is read from the kernel (a read), which may come from the operating system's page cache or from disk, and placed in a buffer, evicting another using a clock-sweep algorithm. Dirty buffers are written out by the background writer and at checkpoints.

EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
-- Buffers: shared hit=1200 read=350     <- "read" may still be an OS cache hit

SELECT sum(heap_blks_hit) / nullif(sum(heap_blks_hit + heap_blks_read), 0) AS hit_ratio
FROM pg_statio_user_tables;

CREATE EXTENSION pg_buffercache;
SELECT c.relname, count(*) AS buffers
FROM pg_buffercache b JOIN pg_class c ON b.relfilenode = pg_relation_filenode(c.oid)
GROUP BY 1 ORDER BY 2 DESC LIMIT 5;

Because the kernel also caches file data, the same page may exist twice. That is why shared_buffers is commonly set to around a quarter of RAM and the rest is left to the OS, and why effective_cache_size tells the planner about *both* layers.

§3Per-Query Memory and Asynchronous I/O

Beyond shared buffers, each backend allocates private memory: work_mem for sorts and hashes (possibly several per query), maintenance_work_mem for vacuum and index builds, and temp_buffers for temporary tables. Total memory use is therefore roughly shared_buffers + connections × (private memory) plus the OS cache, which is why careless work_mem settings cause out-of-memory kills.

PostgreSQL 18 introduced an asynchronous I/O subsystem (io_method), which lets the server issue multiple reads ahead of need, improving sequential scans, bitmap scans, and vacuum on suitable storage. It changes how reads are issued, not the buffer-cache model described here.

On Linux, memory overcommit and the OOM killer can end a backend, and in bad cases force a crash-recovery restart; set vm.overcommit_memory = 2 carefully or size memory with headroom. Large shared_buffers benefit from huge pages (huge_pages = try).

The key insight Postgres relies on the operating system as a second cache and on a process per connection. Sizing memory means budgeting shared buffers, the OS cache, and every connection's private allocations together.

§4Common Mistakes

MistakeWhat HappensFix
Giving shared_buffers nearly all of RAMStarves the OS cache and per-connection memory; double caching wastes the restStart near 25% and measure
Reading a read in BUFFERS as a physical disk readIt may be satisfied by the OS page cacheCompare actual times; use track_io_timing for I/O wait time
Ignoring per-connection memory when raising max_connectionsOut-of-memory conditions under loadUse a pooler and compute worst-case memory
Practice
  1. List all backend types in pg_stat_activity and describe what each does.
  2. Install pg_buffercache and find which tables occupy the most shared buffers after running a workload.
  3. Run a query twice and compare shared hit and read counts and times; then restart Postgres (but not the OS) and repeat.
Key takeaways
  • Postgres forks one process per connection and shares memory through shared buffers, lock tables, and WAL buffers.
  • Reads pass through shared buffers and the OS page cache; effective_cache_size accounts for both.
  • Budget memory as shared buffers plus per-connection private memory plus OS cache headroom.
