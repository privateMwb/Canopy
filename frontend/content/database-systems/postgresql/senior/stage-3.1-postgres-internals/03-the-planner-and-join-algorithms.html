The Planner & Join Algorithms

Postgres uses three join algorithms, and the planner picks among them by estimating the cost of each from row counts and available indexes.

§1Nested Loop, Hash, and Merge Joins

  • Nested Loop: for each row from the outer input, look for matches in the inner input. Cheap when the outer side is small and the inner side has an index on the join column, because each lookup is fast. Terrible when both sides are large and unindexed (work grows with outer times inner rows).
  • Hash Join: build an in-memory hash table from one input (the smaller), then scan the other and probe the table. Excellent for large, unsorted inputs and equality joins; needs memory (work_mem), and spills to disk in batches if the hash does not fit.
  • Merge Join: sort both inputs on the join key (or read them already sorted from an index) and walk them together. Good for large inputs that are already ordered, and supports non-equality range conditions partly.
EXPLAIN (ANALYZE)
SELECT * FROM orders o JOIN customers c ON c.id = o.customer_id WHERE c.country = 'NZ';

 Hash Join  (rows=4200 ...)
   Hash Cond: (o.customer_id = c.id)
   ->  Seq Scan on orders o
   ->  Hash
         ->  Index Scan using customers_country_idx on customers c

§2How the Planner Chooses

The planner enumerates join orders and methods (exhaustively for small queries; with a genetic search, geqo, beyond geqo_threshold tables), costs each plan from row estimates and the cost parameters, and keeps the cheapest. The cost of a node is built from page reads (seq_page_cost, random_page_cost) and CPU work per tuple, operator, and index entry.

SELECT name, setting FROM pg_settings WHERE name LIKE '%\_cost';

SET enable_nestloop = off;      -- diagnostic only: forbid a method to see the next-best plan
EXPLAIN ANALYZE SELECT ...;
RESET enable_nestloop;

The enable_* settings do not fix anything in production but are valuable experiments: if forbidding a method makes the query fast, the planner mis-estimated, and the real fix is better statistics, a better index, or a query rewrite. The join order is the other big lever: joining the most selective tables first keeps intermediate results small.

§3Reading Join Problems

Typical join pathologies and where to look:

Symptom in EXPLAIN ANALYZELikely cause
Nested Loop with loops=500000 over a slow inner scanUnderestimated outer rows; missing index on the inner join column
Hash with Batches: 16 and Disk: usagework_mem too small for the hash
Sort feeding a Merge Join with external mergeSorting large inputs that an index could supply pre-sorted
Estimated 1 row, actual 100,000Stale or missing statistics, or correlated columns (Lesson 2.1.5)

Raising join_collapse_limit or from_collapse_limit lets the planner reorder more tables at the price of more planning time. Plan caching matters too: a prepared statement may use a generic plan that ignores the actual parameter values, and for skewed data that can be worse than a custom plan. plan_cache_mode controls this.

The key insight The three join algorithms are different answers to the same question. When the planner picks the wrong one, the cause is almost always a bad row estimate rather than a bad algorithm.

§4Common Mistakes

MistakeWhat HappensFix
Leaving enable_nestloop = off (or similar) in productionThe planner is forced into poor plans for other queriesUse enable_* only as a diagnostic, then fix the estimates or indexes
Missing an index on the inner side of a nested-loop joinEach outer row triggers a sequential scanIndex the join column on the larger or inner table
Hashing a huge input with a tiny work_memMulti-batch hash spills to disk and slows the queryRaise work_mem for that role or transaction
Practice
  1. Create two tables of a million rows and a hundred rows, join them, and use enable_* settings to see all three join methods in EXPLAIN ANALYZE.
  2. Find a query where estimated and actual rows differ greatly and show how ANALYZE or extended statistics changes the join method.
  3. Reduce work_mem until a hash join reports multiple batches and read the disk usage line.
Key takeaways
  • Nested loop suits small outer sets with indexed lookups; hash suits large equality joins; merge suits sorted inputs.
  • The planner costs alternatives from estimated rows, so bad join choices usually trace back to bad estimates.
  • Use enable_* settings as experiments only, and fix root causes: statistics, indexes, and memory.
