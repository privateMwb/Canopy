Read Replicas & Consistency

Read replicas scale reads but lag behind the primary, so each read has to be routed according to how fresh it needs to be.

§1Why Lag Breaks Applications

A replica applies WAL a little after the primary commits it, usually milliseconds, but seconds or minutes under heavy writes, long queries, or network trouble. That causes visible bugs:

  • Read-your-writes violation: a user saves a profile, the page reloads from a replica, and the old data appears.
  • Non-monotonic reads: a user sees newer data from one replica, then older data from another.
  • Reports disagree because two replicas are at different points.
-- On a replica: how far behind is it?
SELECT now() - pg_last_xact_replay_timestamp() AS time_lag,
       pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();

Measure lag in both time and bytes, and alert on it. Note that pg_last_xact_replay_timestamp() keeps growing when the primary is idle, so interpret it together with byte lag from the primary's pg_stat_replication.

§2Routing Strategies

Decide per *query* whether stale data is acceptable.

  • Always primary for anything after a write: after a user's write, send that user's reads to the primary for a short window (a few seconds), or until the replica reports it has replayed past a remembered LSN.
  • Sticky replica per session: keeping one user on one replica gives monotonic reads (they never go backward in time).
  • Replica for tolerant reads: dashboards, search pages, exports, background jobs.
  • Synchronous remote_apply for the rare write that must be visible on a standby when it commits (it slows that commit).
-- on the primary, after the write, capture the position:
SELECT pg_current_wal_lsn();            -- e.g. 0/3A5B2C8
-- later, route to a replica only if it has replayed beyond that point:
SELECT pg_last_wal_replay_lsn() >= '0/3A5B2C8'::pg_lsn;

Frameworks and proxies (PgBouncer setups, Pgpool-II, application-level routers) can implement read/write splitting, but they cannot know which reads are safe; the application's intent must drive it.

§3Replica Conflicts and Capacity

A replica must replay WAL, and replaying certain changes (for example, vacuum removing row versions) conflicts with a long-running query that still needs those versions. Postgres resolves this by either delaying replay (up to max_standby_streaming_delay) or cancelling the query with "canceling statement due to conflict with recovery".

hot_standby_feedback = on tells the primary which rows the replica still needs, preventing cancellations at the cost of holding back vacuum on the primary, so a long replica query can bloat the primary (Lesson 2.3.5). Dedicate separate replicas to long analytics queries and keep replicas for latency-sensitive reads short-lived.

Reads scale; writes do not. Replicas help only when reads are the bottleneck. For write scaling you need partitioning, application-level sharding, or a different architecture, and you should first confirm that indexes, queries, and hardware are not the real limit.

The key insight A replica is a view of the past. Ask of every read: how stale can this be before the user or the business notices? Route by that answer, not by habit.

§4Common Mistakes

MistakeWhat HappensFix
Sending a user's read to a random replica right after their writeThey do not see their own changeRead from the primary briefly after writes, or wait for the replica's LSN to catch up
Expecting replicas to scale writesThe primary remains the single writer and bottleneckAdd partitioning or sharding for write scale; use replicas only for reads
Enabling hot_standby_feedback and running hours-long queries on the replicaVacuum on the primary is held back and bloat growsUse a dedicated analytics replica, or accept cancellations on that replica
Practice
  1. Create a replica with artificial lag (for example recovery_min_apply_delay = '10s'), then demonstrate a read-your-writes failure.
  2. Implement an LSN-based check that routes a read to a replica only if it has replayed past the user's last write.
  3. Run a long query on a replica while the primary vacuums a busy table and observe the conflict handling.
Key takeaways
  • Replica lag produces read-your-writes and monotonic-read anomalies unless routing accounts for it.
  • Route reads by tolerance for staleness: primary after writes, sticky sessions, replicas for tolerant reads.
  • Replication conflicts cancel or delay queries on replicas, and replicas scale reads only, never writes.
