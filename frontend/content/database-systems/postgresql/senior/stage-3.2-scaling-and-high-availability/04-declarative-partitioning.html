Declarative Partitioning

Declarative partitioning splits one large table into smaller physical tables by a key, so queries read only the relevant pieces and old data can be dropped instantly.

§1Range, List, and Hash Partitions

A partitioned table is a logical table with no storage of its own; its rows live in partitions, each defined by bounds on the partition key.

CREATE TABLE events (
    id         bigint GENERATED ALWAYS AS IDENTITY,
    created_at timestamptz NOT NULL,
    kind       text NOT NULL,
    payload    jsonb,
    PRIMARY KEY (id, created_at)             -- must include the partition key
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_10 PARTITION OF events
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');     -- upper bound is exclusive
CREATE TABLE events_default PARTITION OF events DEFAULT;  -- catches everything else

Range suits time series. List (FOR VALUES IN ('EU','US')) suits discrete categories such as region or tenant group. Hash (FOR VALUES WITH (MODULUS 8, REMAINDER 0)) spreads rows evenly when there is no natural range. Unique and primary key constraints on a partitioned table must include the partition key, since each partition enforces uniqueness only within itself.

§2Pruning and Maintenance Benefits

The planner uses the query's conditions on the partition key to prune: partitions that cannot match are not scanned at all.

EXPLAIN SELECT count(*) FROM events WHERE created_at >= '2026-10-15' AND created_at < '2026-10-20';
-- only events_2026_10 appears in the plan

DROP TABLE events_2025_01;                                  -- instant, no giant DELETE
ALTER TABLE events DETACH PARTITION events_2025_02 CONCURRENTLY;   -- keep it, move to archive

Dropping or detaching an old partition is a metadata operation, far cheaper than DELETEing millions of rows, which also avoids bloat and vacuum load. Each partition is vacuumed, analyzed, and indexed on its own, so maintenance runs on smaller, manageable units. Indexes created on the parent are created on every partition. Loading data into a new table and then ATTACH PARTITION avoids long locks on the live table.

§3Costs and Operational Care

Partitioning is not a free speedup. Queries that do not filter on the partition key scan every partition, which is slower than one big table. Planning time grows with the number of partitions, so hundreds are fine but many thousands hurt. Every partition needs to exist before rows arrive (or land in the default partition), so creation must be automated.

-- Create next month's partition ahead of time (cron job or pg_partman)
CREATE TABLE IF NOT EXISTS events_2026_11 PARTITION OF events
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

Use pg_partman or your own scheduled job to create future partitions and retire old ones. Partition when a table is big enough that maintenance or retention is the problem (a common rule of thumb is when the table no longer fits comfortably in memory, or you need to drop old data quickly), and when queries naturally filter by the key. Otherwise a good index on one table is simpler and often faster.

The key insight Partition for data lifecycle and pruning, not just for size. The payoffs are cheap retention and scans limited to recent data; the price is that every query must be able to use the partition key.

§4Common Mistakes

MistakeWhat HappensFix
Partitioning a table whose queries never filter on the keyEvery query scans all partitions and gets slowerChoose a key that matches the dominant access pattern, or do not partition
Forgetting to create future partitionsInserts land in the default partition or failAutomate partition creation well ahead of time
Creating thousands of tiny partitionsPlanning overhead and catalog bloatUse coarser ranges (monthly rather than hourly) where possible
Practice
  1. Create a range-partitioned events table by month, insert data across three months, and confirm pruning with EXPLAIN.
  2. Detach and drop an old partition and compare it with DELETE on the equivalent rows.
  3. Write a script or SQL function that creates next month's partition if it does not exist.
Key takeaways
  • A partitioned table routes rows to partitions by range, list, or hash on the partition key.
  • Pruning limits scans to relevant partitions, and dropping a partition replaces massive deletes.
  • Partitioning needs a partition key in unique constraints, filters on that key, and automated partition management.
