Logical Replication & CDC

Logical replication sends row-level changes for chosen tables, which allows selective copies, cross-version moves, and a stream of changes for other systems.

§1Publications and Subscriptions

Where physical replication copies the whole cluster byte by byte, logical replication decodes the WAL into row changes (insert, update, delete) and applies them on a subscriber. You choose what to send with a publication and receive it with a subscription. The subscriber is an independent, writable database: it can have different indexes, extra tables, and even a different major version.

-- publisher (wal_level = logical)
CREATE PUBLICATION shop_pub FOR TABLE customers, orders;

-- subscriber (tables with matching names and columns must already exist)
CREATE SUBSCRIPTION shop_sub
    CONNECTION 'host=primary dbname=shop user=replicator'
    PUBLICATION shop_pub;

The subscription first copies the existing rows, then streams changes. Since PostgreSQL 15 you can limit a publication by column list and row filter (FOR TABLE orders WHERE (region = 'EU')).

§2What It Does Not Do

Logical replication has limits to plan around:

  • Tables need a replica identity, normally the primary key, so updates and deletes can find the row.
  • Schema changes (DDL) are not replicated. Apply them yourself on both sides, subscriber first for additive changes.
  • Sequences' values are not kept in step by ordinary table replication; set them on the target before cutover.
  • Conflicts are your problem. If the subscriber is written to and a row clashes, apply stops with an error until you fix it.
  • Large objects and some other objects are not replicated.
SELECT * FROM pg_stat_subscription;               -- subscriber progress
SELECT slot_name, active, restart_lsn FROM pg_replication_slots;   -- publisher

As with physical slots, a subscriber that falls behind or disappears makes the publisher retain WAL; monitor and drop abandoned slots.

§3Zero-Downtime Moves and CDC

Because source and target can differ, logical replication is the standard tool for zero-downtime major-version upgrades and migrations: set up the new cluster, subscribe, let it catch up, briefly stop writes, confirm lag is zero, fix sequences, and switch the application over. PostgreSQL 17 added pg_createsubscriber to convert a physical standby into a logical subscriber, speeding up this setup.

The same decoding machinery supports change data capture (CDC): tools such as Debezium read the change stream through a replication slot and publish events to Kafka or similar, so search indexes, caches, and analytics stores can follow your database without dual writes.

SELECT * FROM pg_create_logical_replication_slot('cdc_slot', 'test_decoding');   -- demo plugin
SELECT * FROM pg_logical_slot_peek_changes('cdc_slot', NULL, NULL);               -- look without consuming
SELECT pg_drop_replication_slot('cdc_slot');                                      -- always clean up

CDC consumers must keep up and acknowledge progress; a stalled consumer pins WAL exactly like a stuck standby. Design events to be idempotent and ordered per key.

The key insight Physical replication copies the database; logical replication copies the data changes. That difference is what makes selective replication, upgrades, and CDC possible, and also why DDL and sequences need manual care.

§4Common Mistakes

MistakeWhat HappensFix
Expecting ALTER TABLE to replicateApply stops with errors on the subscriber when columns differApply schema changes on both sides in a safe order
Forgetting to move sequence values before cutoverInserts on the new primary collide with existing keysSet each sequence past the current maximum before switching
Leaving an unused logical slot on the publisherWAL accumulates indefinitelyDrop abandoned slots and alert on retained WAL
Practice
  1. Publish two tables from one database and subscribe from another, then verify an INSERT and an UPDATE both arrive.
  2. Add a row filter to a publication and confirm only matching rows replicate.
  3. Outline a zero-downtime major-version upgrade using logical replication, naming each step including sequences and cutover.
Key takeaways
  • Publications choose tables, rows, and columns to send; subscriptions apply them to an independent, writable database.
  • DDL, sequence values, and conflict handling are left to you.
  • Logical replication enables low-downtime upgrades and CDC pipelines, but both need monitoring of slots and lag.
