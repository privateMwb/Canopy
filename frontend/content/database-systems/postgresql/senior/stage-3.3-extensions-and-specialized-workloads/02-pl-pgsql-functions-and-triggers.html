PL/pgSQL, Functions & Triggers

Functions and triggers move logic into the database, which is powerful for invariants and dangerous when overused for business rules.

§1Functions and PL/pgSQL

Postgres can run code in several languages: plain SQL, PL/pgSQL (a procedural extension of SQL, built in), and others such as PL/Python and PL/Perl. PL/pgSQL adds variables, conditionals, loops, and exception handling around SQL statements, and runs next to the data without network round trips.

CREATE FUNCTION order_total(p_order_id bigint) RETURNS numeric
LANGUAGE plpgsql STABLE AS $$
DECLARE
    v_total numeric;
BEGIN
    SELECT coalesce(sum(quantity * unit_price), 0) INTO v_total
    FROM order_items WHERE order_id = p_order_id;
    RETURN v_total;
END;
$$;

SELECT order_total(42);

Declare volatility honestly: IMMUTABLE (same input, same output, usable in indexes), STABLE (consistent within one statement), or VOLATILE (default; may change anything). The planner relies on it. Since PostgreSQL 11, CREATE PROCEDURE and CALL support transaction control (COMMIT inside a procedure), which functions cannot do.

§2Triggers

A trigger runs a function automatically before or after a row or statement changes. In the function, NEW and OLD are the row after and before the change.

CREATE FUNCTION touch_updated_at() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    NEW.updated_at := now();
    RETURN NEW;                       -- a BEFORE trigger must return the row to proceed
END;
$$;

CREATE TRIGGER orders_touch
BEFORE UPDATE ON orders
FOR EACH ROW EXECUTE FUNCTION touch_updated_at();

CREATE FUNCTION audit_change() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO audit_log (tbl, op, row_data, at)
    VALUES (TG_TABLE_NAME, TG_OP, to_jsonb(coalesce(NEW, OLD)), now());
    RETURN NULL;                      -- ignored for AFTER row triggers
END;
$$;

BEFORE triggers can modify or reject a row; AFTER triggers see the final row and suit audit logs and notifications. FOR EACH STATEMENT fires once per statement. Triggers run inside the transaction, so a failure rolls back the whole change.

§3What Belongs in the Database

Server-side code has real benefits: it applies no matter which application writes, avoids round trips for data-heavy logic, and keeps integrity close to the data. It also has costs: it is harder to test, version, review, debug, and observe; it ties logic to one database; and triggers are invisible to people reading application code, so surprising side effects accumulate.

A sound division:

  • Database: invariants and integrity (constraints first, triggers when constraints cannot express it), audit trails, updated_at stamps, denormalized counters that must stay correct, and set-based data transformations.
  • Application: business workflows, calls to external services, anything that changes frequently or needs good tests and deployment control.

Two safety points: a SECURITY DEFINER function runs with its owner's privileges, so always set a safe search_path inside it (SET search_path = pg_catalog, public), and never build SQL by concatenating inputs inside a function; use format() with %I and %L, or EXECUTE ... USING.

The key insight Constraints first, triggers second, application code for the rest. Every line of logic you move into the database is logic every developer must know to look for there.

§4Common Mistakes

MistakeWhat HappensFix
Marking a function IMMUTABLE when it reads tables or the clockWrong results from cached or index-evaluated valuesUse STABLE or VOLATILE honestly
Building dynamic SQL by string concatenation in a functionSQL injection inside the databaseUse format('%I'), %L, and EXECUTE ... USING
Hiding business workflows in chains of triggersUnpredictable side effects and impossible debuggingKeep triggers to integrity and audit; put workflows in application code
Practice
  1. Write a trigger that keeps updated_at current and verify it with an UPDATE.
  2. Create an audit trigger that records old and new rows into audit_log as jsonb.
  3. Rewrite a trigger-based business rule as a constraint or application code and note what you gained or lost.
Key takeaways
  • PL/pgSQL runs procedural code next to the data; declare volatility correctly and use procedures for transaction control.
  • Triggers fire automatically on changes: BEFORE can alter or block rows, AFTER suits auditing.
  • Keep invariants and audit in the database; keep workflows and integrations in the application.
