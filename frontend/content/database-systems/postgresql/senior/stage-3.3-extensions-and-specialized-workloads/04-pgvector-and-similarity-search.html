pgvector & Similarity Search

pgvector stores embeddings and finds the nearest ones, trading a little accuracy for a lot of speed through approximate indexes.

§1Embeddings and the vector Type

An embedding is a list of numbers, produced by a machine-learning model, that represents the meaning of text, an image, or other content. Items with similar meaning have embeddings that are close together. Similarity search finds the stored embeddings nearest to a query embedding. The pgvector extension adds a vector type, distance operators, and approximate nearest-neighbor indexes to Postgres.

CREATE EXTENSION vector;

CREATE TABLE documents (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    body      text NOT NULL,
    embedding vector(1536) NOT NULL          -- dimension must match your model
);

-- operators:  <->  Euclidean (L2)    <=>  cosine distance    <#>  negative inner product
SELECT id, body, embedding <=> $1 AS distance      -- $1 is the query's embedding
FROM documents
ORDER BY embedding <=> $1
LIMIT 5;

Your application (or a service it calls) creates embeddings with a model, and the dimension count is fixed by that model. Use the distance operator that matches how the model was trained; cosine distance is the common default for text.

§2Approximate Indexes: HNSW and IVFFlat

Without an index the query compares the query vector to every row (exact search, perfect recall, slow at scale). Two approximate index types speed this up.

-- HNSW: graph-based; better recall/speed trade-off, slower build, more memory
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);
SET hnsw.ef_search = 100;           -- query-time breadth: higher = better recall, slower

-- IVFFlat: clusters vectors into lists; fast to build, needs data present first
CREATE INDEX ON documents USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
SET ivfflat.probes = 10;            -- how many clusters to search

The recall versus speed trade-off is the central concept. An approximate index may miss some true nearest neighbors; raising ef_search or probes improves recall and costs latency. Measure recall on a sample by comparing indexed results with exact results, and tune to your needs. Build indexes after loading the bulk of the data, and match the operator class (vector_cosine_ops) to the operator you query with, or the index is not used.

§3Filtering, Limits, and When pgvector Is Enough

Combining vector search with ordinary filters (WHERE tenant_id = 7) interacts with approximate indexes: the index returns candidates first and the filter applies afterward, which can leave fewer results than requested. Recent pgvector versions offer iterative scans to mitigate this, and partitioning or partial indexes per tenant are other tools; check the documentation for your installed version.

Other practical points: high-dimension vectors are large (1536 floats is about 6 kB per row, causing TOAST and big indexes); halfvec halves storage at some precision cost; index build memory (maintenance_work_mem) matters; and the index lives in Postgres's normal WAL, backup, and replication, a real advantage.

For many applications, up to millions of vectors, pgvector is enough, and it keeps embeddings transactionally consistent with the source rows and avoids a second system. Consider a dedicated vector database when you need billions of vectors, very high query rates with strict latency, or specialized features. Justify the extra system with measurements.

The key insight Similarity search is an accuracy dial. Exact search is perfect and slow; approximate indexes are fast and may miss neighbors. Measure recall on your own data and set the knobs deliberately.

§4Common Mistakes

MistakeWhat HappensFix
Querying with <-> but indexing with cosine operators (or vice versa)The index is ignored and the query scans every rowMatch the operator class to the query operator
Creating an IVFFlat index on an empty or tiny tablePoor cluster centers and bad recallLoad data first, then build the index
Adding a metadata filter and assuming a full result setApproximate index returns fewer rows after filteringTest filtered queries; use iterative scans, partial indexes, or partitions
Practice
  1. Create a documents table, insert a few thousand random vectors, and compare exact search with an HNSW index using EXPLAIN ANALYZE.
  2. Measure recall: for 100 queries, compare approximate results with exact results and compute the overlap while varying hnsw.ef_search.
  3. Estimate the storage for 5 million 1536-dimension vectors and decide whether halfvec is worth considering.
Key takeaways
  • pgvector adds the vector type and distance operators for embeddings; pick the operator that matches your model.
  • HNSW and IVFFlat indexes trade recall for speed; tune ef_search or probes and measure recall.
  • pgvector keeps embeddings beside relational data and suits most workloads; a dedicated system needs justifying with numbers.
