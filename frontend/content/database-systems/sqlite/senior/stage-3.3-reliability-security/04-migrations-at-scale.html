Migrations at Scale

Changing the schema of thousands of installed databases means every upgrade path must be safe, tested, and recoverable.

§1The Fleet Problem

A server migrates one database. A shipped product migrates a database on every user's device at an unpredictable time, from any previous version, possibly interrupted by a crash or a low battery. There is no DBA to fix a bad one.

§2Principles

  • Linear, versioned migrations with user_version, each in a transaction.
  • Never modify shipped migrations. Add new ones.
  • Make them re-runnable and idempotent where possible with IF NOT EXISTS.
  • Test from every released version, using saved database files, not just a fresh schema.
  • Back up before migrating a user database, and keep the backup until the app proves healthy.
def migrate(con, path):
    v = con.execute("PRAGMA user_version").fetchone()[0]
    if v < LATEST:
        shutil.copy(path, f"{path}.pre-v{LATEST}.bak")       # safety copy
        for i, sql in enumerate(MIGRATIONS[v:], start=v + 1):
            with con:
                con.executescript(sql)
                con.execute(f"PRAGMA user_version = {i}")

§3Handling Heavy Changes

Large rewrites can take minutes and temporarily double disk space. Do them off the UI thread, show progress, and check free space first. For server fleets with per-tenant files, migrate lazily on first access or in batches, and track status in a control database.

§4Expand and Contract

Add new columns or tables first (expand), deploy code that writes both, backfill, then switch reads and finally remove the old ones (contract). This lets old and new app versions coexist during a rollout.

§5Rolling Back

Down-migrations are rarely realistic. Instead, make new versions tolerant of old data, and keep the safety copy for emergency restore. If an older app version opens a newer schema, decide whether it should refuse to run (check user_version against the supported maximum).

The key insight Assume every migration will run on a database you have never seen, interrupted at the worst moment. Design so that is safe.

§6Common Mistakes

MistakeWhat HappensFix
Testing migrations only on an empty databaseReal data hits constraints that tests never seeTest with saved files from each release
Rewriting a huge table on the UI threadThe app freezes or is killedRun in the background with progress and enough disk space
Letting an old app version open a newer schemaSilent corruption of assumptionsRefuse to open when user_version is too new
Practice
  1. Build a test corpus of database files from three past versions and migrate each to the latest.
  2. Add a free-disk-space check and a safety backup before a heavy migration.
Key takeaways
  • Use linear, transactional, never-edited migrations tracked by user_version.
  • Test from every shipped version and keep a pre-migration backup.
  • Use expand and contract so old and new code can coexist.
