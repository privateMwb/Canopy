The Pager & Page Cache

The pager sits between the B-trees and the file, caching pages in memory and deciding when they are written.

§1The Layers

SQLite is built in layers. The SQL compiler produces bytecode, the B-tree module runs it, and the pager provides the B-tree with pages: it reads them from disk, keeps them in a cache, tracks which are modified, and handles transactions and locking.

§2Page Cache

The cache holds recently used pages, sized by cache_size. Reading a cached page is a memory access, and a cache miss reads from the file (possibly the OS cache). Each connection has its own cache, so many connections multiply memory use.

PRAGMA cache_size = -65536;       -- about 64 MiB per connection
PRAGMA cache_spill;               -- allow writing dirty pages before commit when the cache fills

Modified pages are dirty. They stay in the cache until commit. If the cache fills during a big transaction, dirty pages may be spilled to disk, which needs the write lock to be upgraded early.

§3Memory-Mapped I/O

With mmap_size set, SQLite can read pages directly through the operating system's page cache, skipping a copy. This helps read-heavy workloads, with caveats: errors in the mapped file can crash the process, and it is not for every platform.

PRAGMA mmap_size = 268435456;

§4Reading a Page

On a miss, the pager asks the VFS (virtual file system layer) to read page N at offset (N-1) × page_size. The VFS abstraction is what lets SQLite run on different operating systems, in memory, or over custom storage.

§5Freelist and Vacuum

Pages freed by deletes go on the freelist and are reused for new data before the file grows. VACUUM rewrites the whole file compactly. Auto-vacuum can truncate free pages at commit, at the cost of pointer-map pages and some fragmentation.

PRAGMA auto_vacuum = INCREMENTAL;
PRAGMA incremental_vacuum(100);
The key insight The page cache is per connection. Many connections with large caches can use a surprising amount of memory.

§6Common Mistakes

MistakeWhat HappensFix
Setting a very large cache_size on many connectionsMemory use multipliesSize the cache per connection against total RAM
Assuming free space is returned to the OSThe file does not shrink on deleteUse VACUUM or auto-vacuum if you need that
Using mmap_size on unreliable storageA storage error can crash the processTest it, and avoid it on removable or network media
Practice
  1. Run a query with a cold and a warm cache and compare timings and page reads.
  2. Create a database, delete most rows, check freelist_count, then run VACUUM and compare file sizes.
Key takeaways
  • The pager provides cached pages and manages dirty pages and transactions.
  • Each connection has its own cache, and mmap can skip a copy for reads.
  • Freed pages go on a freelist, and the file shrinks only on vacuum.
