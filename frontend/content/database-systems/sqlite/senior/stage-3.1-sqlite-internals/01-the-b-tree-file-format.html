The B-Tree File Format

A SQLite database is an array of fixed-size pages organized as B-trees, one per table and one per index.

§1The File Header

The first 100 bytes hold the header: the magic string SQLite format 3\0, the page size, file change counter, size in pages, the freelist location, text encoding, user_version, and more.

xxd -l 100 app.db
sqlite3 app.db "PRAGMA page_size; PRAGMA encoding; PRAGMA schema_version;"

Bytes 16–17 are the page size, a big-endian number (4096 appears as 10 00). Page 1 also contains the start of the sqlite_schema table.

§2Pages

Every page is the same size, a power of two from 512 to 65536. Pages are numbered from 1. A page is one of:

  • Table B-tree interior page (flag 0x05) and leaf page (0x0D).
  • Index B-tree interior page (0x02) and leaf page (0x0A).
  • Freelist pages for unused space.
  • Overflow pages that hold the remainder of values too large for one page.
  • A lock-byte page and, in auto-vacuum databases, pointer-map pages.

§3Table and Index B-trees

A rowid table is a B+tree keyed by rowid, with the row data in the leaves. An index is a B-tree keyed by the indexed columns, with the rowid appended. A WITHOUT ROWID table is stored as an index keyed by its primary key.

SELECT name, rootpage FROM sqlite_schema;     -- the root page number of each B-tree
SELECT * FROM dbstat WHERE name = 'orders';   -- pages used by a table

§4Cells and Records

Each row is a record: a header of serial-type codes followed by the column values, with integers stored in the smallest of several sizes. Rows are stored as variable-length cells inside a page, with a pointer array at the top growing down and cell content growing up from the bottom.

§5Why This Matters

A lookup by rowid reads a handful of pages from the root to a leaf. A big row can span overflow pages and cost extra reads. Wide rows mean fewer rows per page and more I/O per scan.

The key insight Everything in SQLite is pages in B-trees. Performance questions often reduce to how many pages a query must touch.

§6Common Mistakes

MistakeWhat HappensFix
Storing large blobs inline in frequently scanned tablesScans read overflow pages and cache poorlyKeep big blobs in a separate table or file
Choosing a huge page size without testingUnneeded I/O per small readBenchmark 4096 against larger sizes
Assuming an index is free to scanEach index entry also stores the rowid and takes spaceCheck sizes with dbstat
Practice
  1. Hex-dump a small database, find the page size and text encoding, and match them with the pragmas.
  2. Use dbstat to list pages per table and index, and identify the largest.
Key takeaways
  • A database is a sequence of fixed-size pages beginning with a 100-byte header.
  • Tables and indexes are B-trees whose root pages are listed in sqlite_schema.
  • Rows are variable-length records, with overflow pages for large values.
