Read/Write Patterns & the Single Writer

With one writer at a time, throughput depends on making each write transaction tiny and moving everything else off the write path.

§1The Constraint

Every write goes through a single lock. If a write transaction takes 1 ms, you can do about a thousand per second in sequence. If it takes 100 ms because it waits on a network call or a slow query, you can do ten.

write capacity ≈ 1 / (average write-transaction duration)

§2Design Patterns

  • Do preparation outside the transaction. Fetch, validate, and compute first.
  • Batch small writes from many requests into one transaction using a queue and a single writer thread.
  • Use BEGIN IMMEDIATE for writes, and a busy timeout for the queue.
  • Separate reads from writes. In WAL mode, run read connections in parallel and one writer connection.
write_queue = queue.Queue()
def writer():
    con = open_db()
    while True:
        batch = [write_queue.get()]
        while not write_queue.empty() and len(batch) < 500:
            batch.append(write_queue.get_nowait())
        with con:
            for sql, args in batch: con.execute(sql, args)

Group commit like this turns thousands of tiny commits into a few.

§3Reduce What Writes Touch

Fewer indexes, narrower rows, and counters kept in memory and flushed periodically all shorten write transactions. Move append-only logs and metrics to a separate database file so they do not compete for the main write lock.

§4Read Scaling

Readers scale with CPU cores on one machine, since each uses its own connection and snapshot. Cache expensive aggregates and use read-only connections with PRAGMA query_only = ON.

§5Where It Ends

When one machine's write rate or read capacity is exhausted, you either shard (next lesson), replicate for reads, or move to a server database.

The key insight A single writer is a design constraint, not a defect. Shape the work to fit it and you can reach very high throughput on one machine.

§6Common Mistakes

MistakeWhat HappensFix
Calling external services inside a write transactionEveryone waits on the slowest callFinish external work first, then write
One commit per tiny write from many threadsThe lock is taken thousands of timesQueue and batch writes
Mixing heavy logging with core data in one fileLogs lock out business writesPut logs in a separate database
Practice
  1. Benchmark single-row commits against a queued writer with batches of 100 and 1,000.
  2. Move a write-heavy log table to its own database file and measure the effect on the main one.
Key takeaways
  • Write throughput is about one divided by write-transaction time.
  • Queue and batch writes, and prepare data outside the transaction.
  • Split heavy writers into separate files when they contend.
