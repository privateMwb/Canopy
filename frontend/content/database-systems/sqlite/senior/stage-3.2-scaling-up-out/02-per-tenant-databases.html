Per-Tenant Databases

Giving each tenant its own database file replaces many cross-tenant problems with simple file management.

§1The Pattern

Instead of one big database with a tenant_id column, create tenant-123.db per customer, opened by name when a request arrives.

def db_for(tenant_id: int):
    path = DATA_DIR / f"tenant-{tenant_id}.db"
    con = sqlite3.connect(path)
    configure(con); migrate(con)
    return con

§2What It Simplifies

  • Isolation: one tenant's data never mixes with another's, so a missing WHERE tenant_id = ? cannot leak data.
  • Write concurrency: each file has its own writer lock, so tenants do not contend.
  • Backups, restores, and deletion: copy, restore, or remove a single file, which helps with data requests and legal deletion.
  • Moving tenants: move a file to another server to balance load.
  • Per-tenant performance: small files fit in cache and have small indexes.

§3What It Complicates

  • Migrations must run across thousands of files, and you need to track which ones are done.
  • Cross-tenant queries and reporting require opening many databases, or exporting to an analytics store.
  • Connections and file handles: limit open connections with a cache that closes idle ones.
  • Identity and routing: a central database or directory maps tenants to files and servers.
  • Operations: monitoring, backups, and integrity checks run per file.

§4Sizing

Thousands of small databases are routine. The file count is limited by the file system and your tooling, not by SQLite.

ATTACH DATABASE 'tenant-124.db' AS other;       -- cross-database query within one connection

ATTACH lets one connection query several files, with limits on how many may be attached.

The key insight Per-tenant files trade query convenience across tenants for isolation, parallelism, and simple operations. It is a good trade for tenant-centric products.

§5Common Mistakes

MistakeWhat HappensFix
Opening a new connection for every requestFile handle and setup overheadCache open databases and close idle ones
No central registry of tenants and schema versionsMigrations and routing get lostKeep a control database with each tenant's file and version
Planning cross-tenant analytics laterReports require touching every fileStream events to a warehouse from the start
Practice
  1. Sketch a router that opens the right file for a tenant and enforces a cap on open connections.
  2. Write a migration job that upgrades 1,000 tenant files and reports which ones failed.
Key takeaways
  • One file per tenant gives isolation, parallel writers, and easy per-tenant operations.
  • Migrations, reporting, and connection management become fleet problems.
  • Keep a control database that tracks tenants, files, and versions.
