Durability & the synchronous Setting

The synchronous setting decides when SQLite waits for the disk to confirm a write, and therefore what survives a power loss.

§1What a Sync Does

A commit is durable only if the data has really reached stable storage, not just the operating system's cache. A sync (fsync) asks the disk to confirm that. It is slow, so SQLite lets you choose how often to do it.

PRAGMA synchronous;         -- 0 OFF, 1 NORMAL, 2 FULL, 3 EXTRA

§2Settings in Rollback Mode

  • FULL (default): sync at critical moments of each commit. Safe through power loss.
  • NORMAL: fewer syncs, with a small chance of corruption on some very unusual hardware.
  • OFF: no syncs. Fast, but power loss or an OS crash can corrupt the file.

§3Settings in WAL Mode

  • FULL: syncs the WAL at every commit. Committed transactions survive power loss.
  • NORMAL: syncs only at checkpoints. The database cannot be corrupted, but the last few committed transactions can be lost on power loss or an operating system crash. An application crash alone loses nothing, because the data is already in the OS cache.
  • OFF: like rollback mode, unsafe on power loss.

§4Choosing

PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;    -- fast, consistent, may lose last commits on power loss
-- or, if every commit must survive power loss:
PRAGMA synchronous = FULL;

Pick FULL for financial records and anything the user was told is saved. Pick NORMAL for caches, logs, and data that can be rebuilt or re-synced.

§5Hardware Reality

Some disks and virtual machines acknowledge writes before they are truly stored. No setting can make SQLite safer than the storage below it, so test on the same kind of hardware you deploy.

The key insight "Committed" and "durable" are different. The synchronous setting is the dial between them, and you should choose it consciously.

§6Common Mistakes

MistakeWhat HappensFix
Using OFF for convenience in productionA power loss may corrupt the fileUse NORMAL or FULL
Believing NORMAL in WAL corrupts dataIt loses recent commits at worst, not integrityUse FULL when each commit must survive
Trusting disks that lie about syncingDurability claims fail in a real power cutTest on production-class storage
Practice
  1. Write a test that commits rows, kills the process abruptly, and checks what survived under NORMAL and FULL.
  2. Decide the synchronous setting for three data types in an application and justify each.
Key takeaways
  • Durability depends on fsync, and synchronous controls how often it happens.
  • In WAL mode, NORMAL keeps integrity but can lose the last commits on power loss.
  • Choose per data type, and remember that hardware can undermine the setting.
