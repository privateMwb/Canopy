Multi-Process Access & Pitfalls

Several processes can open one SQLite file, but several writers, and especially a network file system, bring problems that no setting fully removes.

§1Multiple Processes on One Machine

This is supported. Locking is done through the operating system's file locks, and WAL uses shared memory between processes on the same host. The same rules as with threads apply: one writer at a time, busy timeouts, and short transactions.

§2Network File Systems

NFS, SMB, and many cloud-synced folders have unreliable or missing file locking, so two machines writing the same SQLite file can corrupt it. WAL mode explicitly does not work across machines.

Safe:      app server ↔ local disk ↔ one database file
Unsafe:    server A ↔ NFS share ↔ server B  (both writing)

If clients on different machines need the database, put a server in front of it, or choose a client-server database.

§3Other Pitfalls

  • File-sync tools (Dropbox, iCloud, OneDrive) copying a live database can snapshot it mid-write. Sync backups, not the live file.
  • Forking after opening a connection shares the connection state, which SQLite does not support. Open connections after the fork.
  • Containers and shared volumes: two containers writing one file through a shared volume need to be on the same host and file system with proper locking.
  • Multiple versions of SQLite in one process (e.g. a system library and a bundled one) can cause confusing bugs.

§4Ways to Share Safely

A small service that owns the file and exposes an API, or replication tools that copy the data to other machines (covered later), or moving to a server database when concurrency outgrows one machine.

The key insight One machine, local disk, any number of processes is fine. More machines than that means a different architecture.

§5Common Mistakes

MistakeWhat HappensFix
Putting the database on NFS for several serversLocking failures and corruptionUse one owning service or a server database
Syncing the live file with a cloud-sync folderTorn copiesSync backups made with .backup
Sharing a connection across a forkUndefined behaviorOpen a new connection in the child
Practice
  1. Run four processes that read and write one database on a local disk and record busy errors and throughput.
  2. Write a short rule for your team about where SQLite files may and may not live.
Key takeaways
  • Multiple processes on one machine and local disk are supported.
  • Network file systems and cloud-sync tools risk corruption.
  • For multi-machine access, add a service in front or use a server database.
