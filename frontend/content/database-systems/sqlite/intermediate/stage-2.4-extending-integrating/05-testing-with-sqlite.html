Testing with SQLite

Tests that use SQLite in memory are fast, but only trustworthy when the production engine behaves the same way.

§1Fast, Isolated Tests

An in-memory database is created and destroyed in microseconds, so each test can have a fresh one.

import sqlite3, pytest

@pytest.fixture
def db():
    con = sqlite3.connect(":memory:")
    con.execute("PRAGMA foreign_keys = ON")
    migrate(con)
    yield con
    con.close()

def test_unique_email(db):
    db.execute("INSERT INTO account (email) VALUES ('a@x.com')")
    with pytest.raises(sqlite3.IntegrityError):
        db.execute("INSERT INTO account (email) VALUES ('a@x.com')")

Use the same migration code as production, not a separate test schema.

§2When SQLite Is the Production Database

Test against the real thing, including WAL mode, STRICT tables, and pragmas. Also test the file-based path, because :memory: does not exercise WAL, locking, or sidecar files. A temporary file in a temp directory is easy to use.

§3When It Is Not

If production runs PostgreSQL or MySQL, testing on SQLite can hide differences: type enforcement, ALTER TABLE support, date handling, case sensitivity, concurrency, and SQL dialect. A test that passes on SQLite may fail in production. Use the production engine in tests, for example with a container.

§4What to Test

Migrations from every previous version, constraints and triggers, upgrade of real sample data, concurrent access with several connections, and backup and restore.

def test_upgrade_from_v1(tmp_path):
    path = tmp_path / "old.db"
    build_v1_database(path)                # fixture file shipped with the tests
    con = sqlite3.connect(path); migrate(con)
    assert con.execute("PRAGMA user_version").fetchone()[0] == LATEST
The key insight A fast test on the wrong database proves little. Match the engine to production wherever behavior matters.

§5Common Mistakes

MistakeWhat HappensFix
Testing only with :memory:WAL, locking, and file behavior go untestedAdd file-based tests
Using SQLite in tests for a PostgreSQL appDifferent types and SQL behavior hide bugsUse the production engine
Separate schema code for testsTests pass on a schema production does not haveRun the real migrations
Practice
  1. Write a fixture that runs your real migrations on a fresh in-memory database and test two constraints.
  2. Add a test that upgrades a saved version-1 database file to the latest schema.
Key takeaways
  • In-memory SQLite gives fast, isolated tests.
  • Also test the file-based path and real migrations.
  • Do not use SQLite in tests when production uses a different engine.
