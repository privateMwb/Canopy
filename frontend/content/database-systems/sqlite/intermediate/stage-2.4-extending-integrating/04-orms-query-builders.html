ORMs & Query Builders

ORMs and query builders save time with schema mapping and migrations, but SQLite's behavior can make some of their defaults surprising.

§1What They Help With

Mapping rows to objects, generating migrations, composing queries safely, and keeping code portable. For ordinary create, read, update, and delete work they are productive.

§2Where They Fight SQLite

  • Type system: an ORM may declare VARCHAR(255) or DECIMAL columns and assume enforcement. SQLite ignores length and stores flexible types.
  • ALTER TABLE: some migrations assume the database can alter or drop constraints, while SQLite often requires a rebuild. Good ORMs rebuild the table for you, and bad ones fail.
  • Foreign keys: the pragma must be enabled per connection, which ORMs may not do by default.
  • Concurrency: connection pools that open many write connections cause SQLITE_BUSY.
  • Transactions: default isolation can start DEFERRED transactions that fail on upgrade.
engine = create_engine("sqlite:///app.db")
@event.listens_for(engine, "connect")
def pragmas(dbapi_con, rec):
    cur = dbapi_con.cursor()
    cur.execute("PRAGMA foreign_keys = ON")
    cur.execute("PRAGMA journal_mode = WAL")
    cur.execute("PRAGMA busy_timeout = 5000")
    cur.close()

§3Practical Advice

Log the SQL the ORM generates and read the plans for the slow ones. Use a small connection pool, or a single writer connection plus read connections. Drop to raw SQL for reports, bulk operations, and FTS queries.

The key insight Let the ORM handle the routine work, and keep the escape hatch to raw SQL for what SQLite does best.

§4Common Mistakes

MistakeWhat HappensFix
Not setting pragmas on every pooled connectionForeign keys silently off on some connectionsUse a connect hook
Many write connections in a poolSQLITE_BUSY under loadLimit writers, set a busy timeout, and use BEGIN IMMEDIATE for writes
Trusting the ORM's migration on SQLiteFailed or data-losing table rebuildsReview the generated SQL and test migrations on real data
Practice
  1. Add a connect hook to your ORM that applies your standard pragmas and verify with a query.
  2. Log the SQL for one slow endpoint and check its plan.
Key takeaways
  • ORMs speed up routine work but assume server-database behavior.
  • Typing, ALTER TABLE, foreign keys, pooling, and transaction defaults need attention.
  • Set pragmas per connection and drop to raw SQL when needed.
