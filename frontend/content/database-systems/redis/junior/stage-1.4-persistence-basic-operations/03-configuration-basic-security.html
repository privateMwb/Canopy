Configuration & Basic Security

Redis ships with minimal protection, so you must bind it to private interfaces, require authentication, and limit what each user can do.

§1The Danger

Redis was designed for trusted networks. An instance open to the internet without a password has been used to steal data, wipe it, and in some cases gain code execution on the host. Never expose port 6379 publicly.

§2Network Controls

bind 127.0.0.1 ::1        # listen only on loopback
protected-mode yes        # refuse outside connections when no password is set
port 6379

Put Redis on a private network, behind a firewall or security group that allows only your application servers.

§3Passwords and ACL Users

Since Redis 6 you can create named users with limited permissions.

ACL SETUSER app on >s3cretPassw0rd ~cache:* +get +set +del +expire
ACL SETUSER reader on >another ~* +@read
ACL LIST
AUTH app s3cretPassw0rd

The user app can only touch keys that start with cache: and only run four commands. A leaked application credential then does far less damage.

§4Dangerous Commands

FLUSHALL, CONFIG, DEBUG, and KEYS can wipe data or change the server. Restrict them with ACLs rather than leaving them open to everyone.

The key insight Authentication is the last layer. The first is not being reachable at all.

§5Common Mistakes

MistakeWhat HappensFix
Binding to 0.0.0.0 with no passwordAnyone who finds the port has full controlBind privately and require a password or ACL user
One shared admin password in every applicationA leak gives total accessCreate per-service ACL users with key patterns and command limits
Putting passwords in code or version controlCredentials leak with the repositoryLoad them from a secret store or environment
Practice
  1. Create an ACL user that can only GET and SET keys beginning with cache: and test that other commands are denied.
  2. Check which interfaces your local Redis listens on with ss -ltn or netstat.
Key takeaways
  • Never expose Redis to the internet, and bind to private interfaces.
  • Use ACL users with narrow key and command permissions.
  • Restrict dangerous commands and keep credentials out of code.
