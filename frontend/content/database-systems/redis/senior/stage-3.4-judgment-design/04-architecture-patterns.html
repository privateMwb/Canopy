Architecture Patterns

Where Redis sits in a system matters, because a pattern that looks harmless can couple services together in ways that only show up during an outage.

§1Common Placements

  • Cache in front of a database: the most common and safest, since the app works without it.
  • Session and token store: shared across stateless web servers.
  • Queue or event stream between services.
  • Shared state for real-time features: presence, counters, rate limits.
  • Coordination: locks, leader election hints, feature flags.

§2Patterns That Create Hidden Coupling

  • Shared Redis across services: one team's big key or flush affects everyone. Use separate instances or ACL-isolated prefixes with limits.
  • Using Redis as the integration layer: services communicate by reading each other's keys, so the key format becomes an undocumented API.
  • Cache that has become required: the database cannot handle traffic without it, so a cache outage becomes a full outage.
  • Synchronous dependence on Redis in the request path with no timeout or fallback.

§3Making It Safer

Give each service its own instance or namespace and quotas, document key formats as contracts, load-test with the cache cold, and add timeouts, circuit breakers, and fallbacks.

request → try cache (50 ms timeout) → on failure → database (with load shedding)
The key insight The test for a cache is whether you can turn it off. If you cannot, plan and provision it like a primary system.

§4Common Mistakes

MistakeWhat HappensFix
One shared Redis for everythingNoisy neighbors and a shared blast radiusIsolate by service or tier
Undocumented keys read by several servicesChanges break other teams silentlyTreat key schemas as versioned contracts
Never testing with a cold cacheThe database fails under real load after a restartLoad-test cold and warm
Practice
  1. Draw your architecture and mark every place a Redis outage would halt a user-facing request.
  2. Run a test with Redis down and describe the behavior and the fix.
Key takeaways
  • Caches are the safest placement, while shared state and integration are riskier.
  • Shared instances and undocumented keys create hidden coupling.
  • Test with a cold or missing cache, and use timeouts and fallbacks.
