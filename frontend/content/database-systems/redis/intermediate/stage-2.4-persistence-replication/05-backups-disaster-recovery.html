Backups & Disaster Recovery

A backup you have never restored is only a hope, so copy data safely and practice recovery before you need it.

§1Taking Backups

RDB files are the easiest backup. A completed dump.rdb is a consistent point-in-time snapshot and is safe to copy.

redis-cli BGSAVE
redis-cli LASTSAVE                       # wait until it changes
cp /var/lib/redis/dump.rdb /backups/dump-$(date +%F-%H%M).rdb

Copy to another machine or object storage, encrypted. For AOF, copy the whole appendonlydir while no rewrite is changing it, or take a snapshot from a replica.

§2Restoring

Stop Redis, put the file in the data directory, check the file name matches dbfilename, and start. If AOF is enabled, Redis loads the AOF and ignores the RDB, so restore the AOF too or restart with appendonly no first, then enable it again.

redis-check-rdb dump.rdb
redis-check-aof --fix appendonlydir/appendonly.aof.manifest    # file names differ by version

§3Planning Recovery

Define how much data you can lose (RPO) and how long recovery may take (RTO). Backups taken hourly give an RPO of an hour. Restore time grows with dataset size, so test with real volumes.

The key insight Replicas handle machine failure, backups handle mistakes and corruption. You need both.

§4Common Mistakes

MistakeWhat HappensFix
Never testing a restoreThe backup turns out to be unusableRestore to a scratch server on a schedule
Backups on the same disk as the dataOne failure destroys bothStore off-host and off-site
Restoring RDB with AOF enabled and wondering why data is oldRedis loaded the AOFFollow the restore steps for AOF-enabled servers
Practice
  1. Back up a running instance, restore it on a second server, and compare DBSIZE and a few keys.
  2. Write down your RPO and RTO for a cache and for a session store.
Key takeaways
  • A finished RDB file is a consistent backup and safe to copy.
  • When AOF is on, Redis restores from the AOF, so manage both.
  • Backups protect against mistakes, and only a tested restore counts.
