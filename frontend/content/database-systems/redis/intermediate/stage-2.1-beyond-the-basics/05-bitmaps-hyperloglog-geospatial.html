Bitmaps, HyperLogLog & Geospatial

Bitmaps, HyperLogLog, and geospatial indexes pack specific kinds of data into very little memory.

§1Bitmaps

A bitmap is a string treated as an array of bits, one per id, so a million flags takes about 125 KB.

SETBIT active:2025-05-14 1001 1          # user 1001 was active
GETBIT active:2025-05-14 1001
BITCOUNT active:2025-05-14               # how many active users
BITOP AND active:both active:2025-05-13 active:2025-05-14

BITOP answers questions like "who was active both days?" in a single command.

§2HyperLogLog Revisited

PFADD and PFCOUNT estimate unique counts in a fixed 12 KB with about 0.8% error, and PFMERGE combines days into weeks.

§3Geospatial

GEOADD shops 13.4050 52.5200 "berlin-1" 13.3777 52.5163 "berlin-2"
GEOSEARCH shops FROMLONLAT 13.40 52.52 BYRADIUS 5 km ASC WITHDIST
GEODIST shops "berlin-1" "berlin-2" km

Geo data is stored in a sorted set, so you can also use ZREM to remove a member.

§4Choosing Among Them

  • Dense, small integer ids and yes/no flags: bitmap.
  • "About how many unique": HyperLogLog.
  • "What is near this point": geo.

Bitmaps waste space when ids are huge and sparse, because the string must reach the highest bit set.

Gotcha Setting bit 4,000,000,000 allocates hundreds of megabytes at once. Bitmaps suit ids that are small and dense.

§5Common Mistakes

MistakeWhat HappensFix
Using a bitmap with large, sparse idsA huge string is allocatedUse a set or map ids to dense numbers
Reading HyperLogLog membersIt stores noneKeep a set if you need them
Mixing up longitude and latitude orderPoints land in the wrong placeAlways pass longitude first, then latitude
Practice
  1. Track daily active users with a bitmap and compute users active on three consecutive days.
  2. Store ten locations and find those within 2 km of a point.
Key takeaways
  • Bitmaps store one flag per id in about one bit each.
  • HyperLogLog estimates unique counts in constant memory.
  • Geo commands index points in a sorted set and search by radius or box.
