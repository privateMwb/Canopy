Transactions: MULTI, EXEC & WATCH

MULTI and EXEC run commands as a block, and WATCH adds optimistic locking so a transaction fails instead of overwriting someone else's change.

§1MULTI and EXEC

MULTI
DECRBY stock:7 1
INCR sold:7
EXEC                  # run both, in order, with nothing interleaved

Commands are queued and then run together. No other client's command runs in the middle. But there is no rollback: if one command fails at run time, the others still execute.

§2Optimistic Locking With WATCH

WATCH marks keys; if any of them changes before EXEC, the transaction is aborted and returns nil.

WATCH stock:7
GET stock:7              # read, decide in your code
MULTI
DECRBY stock:7 1
EXEC                     # nil means someone changed stock:7: retry
for (let i = 0; i < 5; i++) {
  await redis.watch("stock:7");
  const n = Number(await redis.get("stock:7"));
  if (n < 1) { await redis.unwatch(); return "sold out"; }
  const res = await redis.multi().decrBy("stock:7", 1).exec();
  if (res) return "reserved";      // null means retry
}

§3When to Use Which

Use a single atomic command (DECR) when possible. Use WATCH when your decision depends on a read. Use Lua (next lesson) when the retry rate gets high or the logic is complex.

The key insight Redis transactions guarantee isolation, not rollback. Validate before EXEC, because errors found while running do not undo earlier commands.

§4Common Mistakes

MistakeWhat HappensFix
Expecting EXEC to roll back after a failed commandEarlier commands stay appliedCheck inputs first, or use Lua
WATCH without handling a nil resultSilent lost updatesRetry in a loop with a limit
Reading inside MULTI expecting a valueReads are queued and return only at EXECRead before MULTI under WATCH
Practice
  1. Implement a stock reservation with WATCH and run it from two clients at the same time.
  2. Count how many retries you need when 20 clients compete for the same key.
Key takeaways
  • MULTI/EXEC run queued commands together without interleaving.
  • There is no rollback if a command fails at execution.
  • WATCH gives optimistic locking that you handle with a retry loop.
