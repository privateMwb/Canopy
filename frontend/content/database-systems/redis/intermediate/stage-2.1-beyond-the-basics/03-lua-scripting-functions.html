Lua Scripting & Functions

A Lua script runs on the server as one atomic unit, which makes read-decide-write logic safe without retries.

§1Running a Script

EVAL "return redis.call('GET', KEYS[1])" 1 mykey
EVAL "
  local n = tonumber(redis.call('GET', KEYS[1]) or '0')
  if n < tonumber(ARGV[1]) then return 0 end
  redis.call('DECRBY', KEYS[1], ARGV[1])
  return 1
" 1 stock:7 2

Keys go in KEYS and other values in ARGV. The whole script runs without any other command interleaving, so check-then-change is atomic.

§2Caching Scripts and Functions

SCRIPT LOAD returns a SHA that you call with EVALSHA, saving bandwidth. Redis 7 adds Functions, which are named libraries stored on the server and replicated with the data.

SCRIPT LOAD "return redis.call('INCR', KEYS[1])"
EVALSHA <sha> 1 counter
FCALL reserve_stock 1 stock:7 2     # a function, Redis 7+

§3The Cost of Atomicity

While a script runs, nothing else does. A slow script blocks every client. Keep scripts short, avoid loops over large collections, and declare every key you touch in KEYS so that cluster routing works.

Gotcha Scripts should be deterministic and only touch keys passed in KEYS. Reading keys not declared breaks Redis Cluster.

§4Common Mistakes

MistakeWhat HappensFix
Long loops inside a scriptThe server stalls for everyoneKeep scripts to a few commands
Hard-coding key names inside the scriptFails in Cluster and hides dependenciesPass keys in KEYS
Sending the full script on every callWasted bandwidthUse EVALSHA or Functions
Practice
  1. Rewrite the WATCH reservation as a Lua script and test it with 50 concurrent clients.
  2. Add a script that increments a counter and sets a TTL only when the key is new.
Key takeaways
  • Lua scripts run atomically on the server.
  • Pass keys in KEYS, values in ARGV, and cache scripts by SHA or as Functions.
  • Keep scripts short, because they block the server while running.
