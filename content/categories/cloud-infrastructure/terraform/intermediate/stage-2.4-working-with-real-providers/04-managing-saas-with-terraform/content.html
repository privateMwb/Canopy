Managing SaaS With Terraform

Terraform manages much more than cloud servers. Repositories, DNS, and monitoring can live in code too, with the same review and history.

§1Why Manage SaaS

Anything with a good API and settings that matter is a candidate. Repository permissions, branch protection, DNS records, alerts, and dashboards all benefit from review, history, and the ability to recreate them. When someone asks "who changed that alert?", the answer is in git.

§2GitHub

terraform {
  required_providers {
    github = { source = "integrations/github", version = "~> 6.0" }
  }
}

resource "github_repository" "api" {
  name        = "api"
  visibility  = "private"
  description = "Public API service"
}

resource "github_branch_protection" "main" {
  repository_id = github_repository.api.node_id
  pattern       = "main"
  required_pull_request_reviews {
    required_approving_review_count = 1
  }
}

§3Cloudflare and Monitoring

resource "cloudflare_dns_record" "api" {
  zone_id = var.zone_id
  name    = "api"
  type    = "A"
  content = aws_eip.api.public_ip
  ttl     = 300
}

resource "datadog_monitor" "latency" {
  name    = "API latency high"
  type    = "metric alert"
  query   = "avg(last_5m):avg:api.latency{env:prod} > 0.5"
  message = "Latency is high. @slack-oncall"
}

Provider versions change resource names and argument names, so check the documentation for the version you pin. The Cloudflare provider, for example, renamed its DNS record resource in a major release.

§4Practical Concerns

  • Credentials: these providers use API tokens. Scope them narrowly and pass them through environment variables.
  • Rate limits: large plans can hit API limits. Lower parallelism if needed (-parallelism=5).
  • Import first: for existing SaaS configuration, import before applying, or you will create duplicates.
Connect systems through references The real value is wiring across providers: a DNS record pointing at a cloud IP, a monitor created for a service Terraform just deployed. One graph, several providers, a single reviewed change.

§5Common Mistakes

MistakeWhat HappensFix
Applying against an existing SaaS setup without importingDuplicate records or conflicting settingsImport first, then converge the code
Over-broad API tokensA leak affects the whole organizationScope tokens to the resources Terraform manages
Using old resource names from blog posts"Unsupported resource" errorsCheck the docs for your provider version
Practice
  1. Create a private repository and a branch protection rule with the GitHub provider.
  2. Add a DNS record that points at an output from another resource in the same configuration.
Key takeaways
  • Terraform can manage repositories, DNS, monitoring, and many more SaaS tools.
  • Import existing settings before applying, and scope API tokens narrowly.
  • Cross-provider references link systems into one reviewed change.
