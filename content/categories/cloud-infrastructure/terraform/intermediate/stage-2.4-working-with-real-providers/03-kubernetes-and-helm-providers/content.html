Kubernetes & Helm Providers

Terraform can manage Kubernetes objects and Helm charts, but a cluster and the things running on it make an awkward pair.

§1The Providers

The kubernetes provider manages Kubernetes objects as resources, and the helm provider installs charts as releases. Both need to authenticate to the cluster.

data "aws_eks_cluster_auth" "this" {
  name = module.eks.cluster_name
}

provider "kubernetes" {
  host                   = module.eks.cluster_endpoint
  cluster_ca_certificate = base64decode(module.eks.cluster_certificate_authority_data)
  token                  = data.aws_eks_cluster_auth.this.token
}

resource "kubernetes_namespace" "app" {
  metadata { name = "app" }
}

A Helm release looks like this:

resource "helm_release" "cert_manager" {
  name             = "cert-manager"
  repository       = "https://charts.jetstack.io"
  chart            = "cert-manager"
  version          = "v1.16.2"        # pin the version you have tested
  namespace        = "cert-manager"
  create_namespace = true
  values           = [file("${path.module}/cert-manager-values.yaml")]
}

Pin the chart version, and keep chart settings in a values file so the Terraform stays small. The syntax for inline set arguments differs between major versions of the helm provider, so check the documentation for yours.

§2Where It Gets Awkward

  • The chicken-and-egg problem. Provider configuration cannot depend on a resource that does not exist yet. If the cluster is created in the same configuration that configures the provider, the first plan can fail. Split the cluster and its in-cluster resources into separate stacks.
  • Plan-time access. Some resources, such as kubernetes_manifest, need to reach the cluster during planning.
  • Two sources of truth. Applications are often managed by a GitOps tool such as Argo CD or Flux. Having both Terraform and GitOps own the same objects causes endless drift.

A common split: Terraform builds the cluster and installs the bootstrap pieces (the GitOps controller, core add-ons); GitOps manages applications from there.

Use each tool for what it does well Terraform is strong at infrastructure with a lifecycle (clusters, networks, IAM). Kubernetes-native tooling is better at the fast-changing, many-object world of applications. Choose a boundary and keep it clear.

§3Common Mistakes

MistakeWhat HappensFix
Creating the cluster and its workloads in one stackFirst plan fails because the provider has no cluster to talk toUse separate stacks, or apply in two steps
Letting Terraform and Argo CD manage the same objectsConstant drift and fights over ownershipAssign each object to exactly one tool
Not pinning chart versionsUpgrades arrive unannouncedSet version and review chart changes
Practice
  1. Install a Helm chart to a local cluster (kind or minikube) with a pinned version and a values file.
  2. Decide, for five objects in a cluster you know, whether Terraform or GitOps should own each, and why.
Key takeaways
  • Terraform can manage Kubernetes objects and Helm releases through providers.
  • Do not create a cluster and configure its provider in the same stack.
  • Give each object a single owner, and avoid overlapping with GitOps tools.
