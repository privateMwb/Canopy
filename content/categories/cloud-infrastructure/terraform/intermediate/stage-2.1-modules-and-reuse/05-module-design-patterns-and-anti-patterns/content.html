Module Design Patterns & Anti-Patterns

A good module is easy to use and hard to misuse. Most poor ones share a handful of recognizable mistakes.

§1What Good Modules Do

  • One clear purpose. "A VPC with subnets" is a module; "everything for the app" is a stack.
  • Safe defaults. Encryption on, public access off. Callers opt into risk.
  • Few, typed variables. A module with forty inputs is a resource wrapper in disguise.
  • Useful outputs and good docs. A README with an example call, and descriptions on every variable.
  • Stable addresses. Renaming internal resources without a moved block forces recreation for every caller.
moved {
  from = aws_s3_bucket.bucket
  to   = aws_s3_bucket.this
}

§2Anti-Patterns

  • Thin wrappers. A module that only forwards every argument to one resource adds indirection and no value.
  • Provider configuration inside modules. Modules should inherit providers from the caller. A provider block in a child module makes it hard to remove or reuse.
  • God modules. One module that builds a network, servers, and databases cannot be reused in parts or tested alone.
  • Hidden global assumptions. Reading data sources for names or tags that the caller does not know about.
  • Deep nesting. Modules calling modules calling modules make plans and addresses hard to follow. Prefer flat composition in the root.

§3Test the Interface

Call your module from a scratch configuration as a stranger would, with only the README. If you need to read the source to make it work, the interface needs improving.

Make the safe path the default The best modules make the secure, cheap, or reversible choice the default and require a deliberate argument for the opposite. A module's defaults decide how every caller behaves when they stop reading.

§4Common Mistakes

MistakeWhat HappensFix
Renaming a resource inside a published moduleEvery caller's plan wants to destroy and recreate itAdd a moved block and release a new version
Putting a provider block in a moduleCannot reuse with count/for_each or other regionsDeclare only required_providers, and pass providers from the caller
Making everything a variableCallers must understand every detailHide choices that do not vary, and expose the ones that do
Practice
  1. Review a module of your own and mark its variables as essential, optional, or unnecessary.
  2. Rename a resource inside a module and add the matching moved block, then confirm the plan shows no changes.
Key takeaways
  • Good modules have a single purpose, safe defaults, and a small interface.
  • Use moved blocks to refactor without forcing recreation.
  • Avoid thin wrappers, provider blocks in modules, and deep nesting.
