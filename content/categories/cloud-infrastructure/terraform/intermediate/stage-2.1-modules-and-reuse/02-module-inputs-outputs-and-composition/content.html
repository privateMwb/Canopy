Module Inputs, Outputs & Composition

A module's interface is its variables and outputs. Good interfaces are small, typed, and composable with other modules.

§1Designing the Interface

Variables are the module's arguments, so give them types, descriptions, and defaults only where a default is genuinely safe. Outputs are its return values: expose IDs and attributes that callers will plausibly need, and nothing more.

variable "name"        { type = string }
variable "cidr_block"  { type = string }
variable "az_count" {
  type    = number
  default = 2
}

output "vpc_id"         { value = aws_vpc.this.id }
output "public_subnets" { value = [for s in aws_subnet.public : s.id] }

When a module needs structured input, an object type with optional attributes keeps the interface tidy.

variable "database" {
  type = object({
    engine         = string
    instance_class = optional(string, "db.t4g.micro")
    multi_az       = optional(bool, false)
  })
}

§2Composition

Compose modules by wiring one module's outputs into another's inputs, from the root.

module "network" {
  source = "./modules/network"
  name   = "app"
}

module "web" {
  source     = "./modules/web"
  vpc_id     = module.network.vpc_id
  subnet_ids = module.network.public_subnets
}

The root stays a thin layer that connects well-defined pieces. Modules should not reach into each other; the root passes values between them, which keeps dependencies visible and each module testable alone.

§3Scale Modules With count and for_each

Modules accept count and for_each too, producing one instance of the whole module per key.

module "bucket" {
  for_each = toset(["logs", "assets", "backups"])
  source   = "./modules/bucket"
  name     = "acme-${each.key}"
}
Outputs are a contract Once other code depends on an output, renaming or removing it is a breaking change. Treat outputs like a public API: add freely, change carefully, and version the module when you must break them.

§4Common Mistakes

MistakeWhat HappensFix
Exposing every resource attribute as an outputA huge surface callers come to depend onOutput only what consumers need
Hard-coding values inside the moduleCallers cannot adapt itTurn the varying values into variables
Passing a whole object when one field is neededTight coupling between modulesPass the single value, such as an ID
Practice
  1. Build a network module and a web module, and wire them from the root with outputs and inputs.
  2. Use for_each on a module call to create three buckets, then remove one and read the plan.
Key takeaways
  • A module's variables and outputs are its interface; keep both small and typed.
  • Compose modules in the root by connecting outputs to inputs.
  • for_each on a module creates a full copy per key.
