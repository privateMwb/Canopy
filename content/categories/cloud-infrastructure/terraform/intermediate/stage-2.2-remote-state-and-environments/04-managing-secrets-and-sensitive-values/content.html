Managing Secrets & Sensitive Values

Terraform needs secrets to create things, and then tends to remember them. Know where values travel so you can keep them out of the places that leak.

§1Where Secrets Appear

  • Your code and tfvars files: avoid; these end up in git.
  • State: every attribute a provider returns is stored, including generated passwords.
  • Plan files and logs: values appear unless marked sensitive, and sometimes even then in debug logs.
  • Outputs: printed in CI logs unless marked sensitive.

sensitive = true on a variable or output hides it from display only. It does not encrypt anything in state.

§2Better Patterns

Let the platform generate and store the secret, so Terraform never handles it.

resource "aws_db_instance" "main" {
  # ...
  manage_master_user_password = true    # stored in AWS Secrets Manager
}

When a secret must be read, fetch it from a secrets manager at plan time and pass it to a resource that needs it.

data "aws_secretsmanager_secret_version" "api" {
  secret_id = "prod/api-key"
}

Reading it as a data source still places the value in state. Newer Terraform releases add ephemeral resources and write-only arguments, which let values be used during a run without being saved in state. Check whether your provider and the resource you are configuring support them (write-only arguments commonly end in _wo).

§3Guarding the Rest

  • Pass runtime secrets through environment variables (TF_VAR_...) or your CI system's secret store.
  • Encrypt state and restrict who can read it, since reading state is reading secrets.
  • Treat saved plan files as sensitive artifacts and expire them.
Assume state is readable by anyone with backend access The question to ask about every secret is "does this value land in state?" If it does, the access policy on state is your secret policy.

§4Common Mistakes

MistakeWhat HappensFix
Relying on sensitive for protectionSecrets remain in state and logsAvoid handling the secret, or use ephemeral values where supported
Committing .tfvars with passwordsCredentials in git historyUse environment variables or a secrets manager
Reading secrets with a data source and assuming safetyThe value is stored in stateCheck whether an ephemeral or write-only option exists
Practice
  1. Apply a resource with a generated password, then find that value in terraform state show or the state file.
  2. Replace a hard-coded password with manage_master_user_password or another provider-managed option.
Key takeaways
  • Secrets reach state, plans, logs, and outputs; sensitive only hides display.
  • Prefer letting the platform generate secrets so Terraform never holds them.
  • Newer ephemeral and write-only features keep values out of state where supported.
