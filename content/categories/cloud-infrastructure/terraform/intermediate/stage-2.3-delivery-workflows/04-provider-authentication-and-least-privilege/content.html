Provider Authentication & Least Privilege

Terraform runs with the permissions you give it. Short-lived credentials and narrow roles limit what a mistake or a leak can do.

§1Stop Storing Keys

Long-lived access keys in a CI secret are a standing risk. Use OpenID Connect (OIDC) federation: your CI provider proves its identity to the cloud, which returns temporary credentials scoped to a role.

# GitHub Actions step
- uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123456789012:role/terraform-plan
    aws-region: us-east-1

The role's trust policy decides which repositories, branches, or environments may assume it, so a fork or an unrelated branch cannot.

§2Different Roles for Different Jobs

Planning needs read access. Applying needs write access. Give them different identities.

provider "aws" {
  region = "us-east-1"
  assume_role {
    role_arn = var.deploy_role_arn
  }
}

A plan job on a pull request can use a read-only role, so an untrusted change cannot modify anything just by being proposed. Only the apply job, which runs after approval on the main branch, assumes the write role.

§3Least Privilege in Practice

  • Start from the resources Terraform manages and grant only those actions.
  • Scope by account, region, and resource name pattern where you can.
  • Keep permissions for IAM itself separate and tightly controlled, since "can create roles" is nearly "can do anything".
  • Use separate roles per environment, so a dev pipeline cannot reach production.
Terraform is an administrator in disguise Because it creates and modifies infrastructure, the identity it uses is among the most powerful in your account. Protect who can change the code that runs under it, using branch protection and required reviews, as seriously as the credential itself.

§4Common Mistakes

MistakeWhat HappensFix
One admin role for every pipelineA compromise anywhere reaches everythingUse per-environment, per-job roles
An overly broad trust policyAny repository or branch can assume the roleRestrict by repository, branch, or environment claim
Giving the plan job write accessPull requests from untrusted code can change infrastructureUse a read-only role for plans
Practice
  1. Set up OIDC from your CI to a sandbox account and remove the stored access keys.
  2. Write a read-only role for plans and a separate role for applies, and confirm the plan role cannot create a bucket.
Key takeaways
  • Use OIDC and temporary credentials instead of stored keys.
  • Separate read-only planning from write-capable applying.
  • Scope roles tightly, and protect the code path that runs as Terraform.
