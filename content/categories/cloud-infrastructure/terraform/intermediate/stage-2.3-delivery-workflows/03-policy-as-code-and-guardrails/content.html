Policy as Code & Guardrails

Policy as code turns "please do not do that" into an automatic check on every plan.

§1What Policies Check

A policy evaluates a plan or configuration against rules and passes or fails it. Typical rules include:

  • Storage must be encrypted
  • No security group may allow 0.0.0.0/0 on SSH
  • Every resource must carry Owner and CostCenter tags
  • Only approved regions and instance sizes
  • Production databases must have deletion protection

Policies replace reviewers memorizing the rules, and they apply equally to every change, including ones reviewed in a hurry.

§2Where Checks Run

Run policies on the plan, after Terraform has computed real values, using its JSON form.

terraform plan -out=tfplan
terraform show -json tfplan > plan.json
conftest test plan.json --policy policy/      # OPA/Rego rules
checkov -f plan.json                          # scans the plan with built-in policies

A small Rego rule shows the idea.

package terraform

deny contains msg if {
  some r in input.resource_changes
  r.type == "aws_s3_bucket"
  not r.change.after.tags.Owner
  msg := sprintf("%s is missing an Owner tag", [r.address])
}

HCP Terraform and Terraform Enterprise can enforce policies written in Sentinel or OPA as part of every run, with enforcement levels such as advisory (warn) and mandatory (block).

§3Terraform's Own Guardrails

Inside the configuration, validation blocks check inputs, and precondition and postcondition blocks in a resource's lifecycle check assumptions. A check block runs assertions at the end of a plan or apply and reports problems without blocking.

Start advisory, then enforce A new policy that blocks everything on day one gets bypassed or removed. Roll rules out as warnings first, fix existing violations, then switch them to blocking, and provide a documented exception process.

§4Common Mistakes

MistakeWhat HappensFix
Writing policies against raw sourceMisses values only known in the planEvaluate the JSON plan
Blocking on day onePipelines stall and teams look for bypassesBegin in warning mode and tighten gradually
No exception pathLegitimate needs get blockedCreate a reviewed, time-limited way to waive a rule
Practice
  1. Write a policy that fails any plan creating an untagged resource, and run it against a saved plan.
  2. Add a validation block and a check block to a configuration and compare when each fires.
Key takeaways
  • Policy as code checks every plan consistently and automatically.
  • Evaluate the JSON plan so real values are visible.
  • Roll rules out as warnings first, with a clear exception process.
