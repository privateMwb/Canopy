Repository & Stack Layout

Where code lives and how it splits into states is the most consequential design choice you will make. It is also the hardest to change later.

§1Two Separate Questions

Repository layout decides who can read and change code, and how it is versioned. State layout decides what is planned and applied together. They are related but independent: one repository can hold many states, and teams can share a state across repositories (though rarely should).

§2State Boundaries

Split states along lines that matter operationally:

  • Rate of change. Networks change rarely; application stacks change daily. Do not make a daily change wait on a plan that refreshes a thousand stable resources.
  • Ownership. If one team owns networking and another owns services, give them separate states and permissions.
  • Blast radius. A single bad apply should not be able to reach everything.
  • Environment and account. Production and development should never share a state.

§3A Common Layout

infrastructure/
  modules/                      # reusable building blocks (versioned)
    network/
    service/
  live/
    dev/
      network/                  # one state
      data/                     # one state
      app/                      # one state
    prod/
      network/
      data/
      app/

Each leaf directory is a root module with its own backend key. It calls shared modules from modules/ with a pinned version, so production can lag behind development on purpose.

§4Monorepo or Many Repositories

A monorepo makes refactors, search, and consistent tooling easy. Separate repositories give teams independent access control and release cycles. Whichever you choose, keep reusable modules versioned (tags or a registry) so consumers upgrade deliberately.

Plan for the boundary you will want in two years Splitting a state later is possible but laborious (it needs state mv or import and removed). Merging is equally painful. Draw boundaries around ownership and change rate now, and avoid both a single monolith and one state per resource.

§5Common Mistakes

MistakeWhat HappensFix
One state for everythingSlow plans, huge blast radius, and constant lock contentionSplit by ownership, rate of change, and environment
A state per resourceThousands of tiny stacks and endless cross-referencesGroup resources that change and fail together
Sharing a state across environmentsOne mistake reaches productionSeparate states, accounts, and credentials
Practice
  1. Take a single large configuration and propose how to split it into states, listing the criterion for each boundary.
  2. Sketch the directory layout for dev and prod that shares modules but pins different versions.
Key takeaways
  • Repository layout and state layout are separate decisions.
  • Split states by rate of change, ownership, blast radius, and environment.
  • Pin shared module versions per stack so environments can progress independently.
