Terragrunt & Orchestration Tools

With dozens of stacks, copy-pasted backend and provider boilerplate drifts apart. Orchestration tools keep many stacks consistent and ordered.

§1The Problem

Every stack needs a backend block, provider block, and version pins. Backend blocks cannot use variables, so teams copy them and edit one value. Over time the copies diverge, a new account gets set up differently, and cross-stack ordering lives in someone's head.

§2Terragrunt

Terragrunt is a thin wrapper around Terraform and OpenTofu. A root terragrunt.hcl defines shared configuration, and each stack includes it.

# live/terragrunt.hcl (root)
remote_state {
  backend = "s3"
  generate = { path = "backend.tf", if_exists = "overwrite" }
  config = {
    bucket       = "acme-terraform-state"
    key          = "${path_relative_to_include()}/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }
}
# live/prod/app/terragrunt.hcl
include "root" {
  path = find_in_parent_folders()
}

terraform {
  source = "../../../modules/app"
}

dependency "network" {
  config_path = "../network"
}

inputs = {
  vpc_id = dependency.network.outputs.vpc_id
}

Terragrunt generates the backend, computes a unique state key per directory, passes inputs, and understands dependencies, so it can apply many stacks in the right order from one command (its run-all family of commands; newer releases consolidate these under run --all).

§3Other Approaches

  • Plain CI orchestration: pipelines with explicit stages and a script that renders backend config.
  • Terraform's own features: HCP Terraform's workspaces, run triggers, and Stacks. Stacks is aimed at deploying a configuration across many environments and regions as one unit.
  • Terraspace, Spacelift stacks, and similar: other layers that solve the same problem.

§4Costs

Another tool means another thing to learn, upgrade, and debug, and another layer between you and Terraform's own error messages. It pays off when you have many stacks sharing structure; it is overkill for three.

Reduce boilerplate, not understanding If your team can no longer read what will actually run, the wrapper has gone too far. Keep generated output inspectable, and make sure people still understand the plain Terraform underneath.

§5Common Mistakes

MistakeWhat HappensFix
Adopting an orchestrator for a handful of stacksExtra tooling with little benefitWait until duplication and ordering problems are real
Burying logic in the wrapperHard to debug, and new people cannot follow itKeep wrapper config thin and put logic in modules
Letting generated files drift from the sourceConfusing diffs and surprisesTreat generated files as build output and regenerate them
Practice
  1. Write a root terragrunt.hcl that generates an S3 backend with a unique key per directory.
  2. List the repetitive parts of your current stacks, and decide which a wrapper would remove and which it would hide.
Key takeaways
  • Orchestration tools remove backend boilerplate and encode ordering across stacks.
  • Terragrunt, Stacks, and similar tools solve the same problem with different tradeoffs.
  • Adopt one when repetition hurts, and keep wrappers thin and transparent.
