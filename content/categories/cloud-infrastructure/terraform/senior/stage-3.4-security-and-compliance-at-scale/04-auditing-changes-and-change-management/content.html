Auditing Changes & Change Management

When something goes wrong, or an auditor asks, you need to prove who changed what, when, and why. Good change management makes that a query, not an investigation.

§1The Evidence Chain

Each infrastructure change should leave a connected trail:

  1. A pull request shows the author, the reviewers, the discussion, and the reasons.
  2. The plan shows exactly what was proposed, attached to that pull request.
  3. The pipeline run shows who or what applied it, when, and the result.
  4. The cloud's audit log (such as AWS CloudTrail) shows the actual API calls and the identity that made them.
  5. State version history shows what Terraform recorded at each point.

If every change flows through the pipeline, one identity makes all the writes, so CloudTrail alone will not say which human was responsible. Link the layers by tagging resources or sessions with the commit or run.

provider "aws" {
  default_tags {
    tags = {
      ManagedBy = "terraform"
      Commit    = var.git_sha
      RunId     = var.ci_run_id
    }
  }
}

Role session names or tags set by the pipeline can carry the same identifiers into audit logs.

§2Making It Enforceable

  • Branch protection: required reviews, required status checks, no direct pushes, and signed commits where you need them.
  • CODEOWNERS for sensitive paths such as IAM, networking, and production.
  • Remove standing human write access to production. Use a documented, logged break-glass role for emergencies, with an alert whenever it is used.
  • Immutable logs: send audit logs to a separate, write-once location that the pipeline cannot alter.

§3Change Management That Scales

Match process to risk. Routine changes, such as adding a tag or a bucket, go through normal review and automation. High-risk changes, such as IAM, network edges, and data deletion, need extra reviewers, a maintenance window, a rollback plan, and a clear record. Detect changes made outside the process through drift detection and cloud-side alerting, then investigate each one.

Audit by making the right path the only path If humans can change production directly, your audit trail has holes. The strongest control is a pipeline that is the only identity with write access, protected code review, and alerts on anything that bypasses both.

§4Common Mistakes

MistakeWhat HappensFix
Letting engineers keep standing admin accessChanges bypass review and leave no clear trailUse pipeline-only writes and a logged break-glass role
Audit logs stored where the pipeline can edit themEvidence can be alteredShip logs to a separate, write-protected location
Treating all changes the sameEither too slow for routine work or too lax for risky changesTier the process by risk
Practice
  1. Trace one real infrastructure change from pull request to cloud audit log, and note where the link between them is weak.
  2. Define which paths in your repository require additional reviewers, and write the CODEOWNERS entries.
Key takeaways
  • Link pull request, plan, pipeline run, cloud audit log, and state history into one chain.
  • Enforce with branch protection, code owners, pipeline-only writes, and immutable logs.
  • Scale process to risk, and detect changes that bypass it.
