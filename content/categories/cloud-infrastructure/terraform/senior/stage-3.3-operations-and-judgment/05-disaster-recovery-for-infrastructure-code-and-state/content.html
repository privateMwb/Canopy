Disaster Recovery for Infrastructure Code & State

Backups of data are common; backups of the ability to rebuild are not. Plan for losing state, a pipeline, or an entire account.

§1What Can Be Lost

  • State, through corruption, deletion, or a bad write.
  • The state bucket or backend, taking every state with it.
  • The pipeline or its credentials.
  • A whole account or region.
  • The repository itself, or access to third-party modules and providers.

Each has a different recovery path, and most recoveries depend on preparation done before the incident.

§2Protect and Recover State

  • Enable versioning on the state store, and replicate it to a second region or account.
  • Restrict deletion and require extra approval for the bucket.
  • To recover: restore an earlier version, then run terraform plan -refresh-only to see how reality differs.
  • If state is completely lost but the infrastructure exists, rebuild it with import blocks. Keeping a resource inventory from the cloud makes that practical.
terraform plan -generate-config-out=recovered.tf   # draft config for imported resources

§3Rebuilding an Environment

Code recreates infrastructure, not data. An account-level recovery needs, in order:

  1. A clean account (or region) with the baseline applied
  2. The bootstrap: state backend, pipeline roles, and credentials
  3. Foundation stacks (identity, network), then data, then applications
  4. Data restored separately from backups, snapshots, or replicas
  5. Secrets and external dependencies restored or reissued
  6. DNS and traffic cut over last, after verification

§4Make It Real

  • Keep code in more than one place, and mirror providers and modules you depend on, so a registry outage does not block recovery.
  • Write the runbook, with commands, and keep it where you can read it during an outage.
  • Test it. Rebuild a non-production environment from scratch on a schedule, and time it. An untested plan is a guess.
The bootstrap is the hardest part Everything depends on a state backend and pipeline that were not created by that same pipeline. Document how to recreate those from zero, and practice it, because that circular dependency is where real recoveries stall.

§5Common Mistakes

MistakeWhat HappensFix
No versioning or replication on the state bucketOne mistake or outage loses every stateEnable versioning and cross-region replication
Assuming code alone is a recovery planData, secrets, and DNS are missingInclude data restoration and secrets in the runbook
Never rehearsing a rebuildThe first attempt happens during a crisisPractice rebuilds in a non-production account on a schedule
Practice
  1. Delete the state of a small stack in a sandbox and rebuild it using import blocks, timing how long it takes.
  2. Write a numbered runbook to rebuild one environment in a fresh account, and mark each step with its prerequisites.
Key takeaways
  • Protect state with versioning and replication, and know how to rebuild it from imports.
  • A recovery order runs from bootstrap to foundations, data, applications, and traffic.
  • Rehearse rebuilds; an untested runbook is a hypothesis.
