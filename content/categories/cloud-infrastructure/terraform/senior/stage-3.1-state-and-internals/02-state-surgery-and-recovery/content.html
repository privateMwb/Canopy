State Surgery & Recovery

Sometimes state itself is wrong. Moving, removing, and repairing it safely is a core operations skill, and every step starts with a backup.

§1Back Up First

terraform state pull > state-backup-$(date +%F).json

With a versioned remote backend you also have prior copies, but a local backup taken immediately before surgery is cheap and certain.

§2The Commands

terraform state list
terraform state show aws_instance.web
terraform state mv aws_instance.web module.app.aws_instance.web   # re-address without recreating
terraform state rm aws_instance.legacy                            # forget it; the real resource stays
terraform state replace-provider registry.terraform.io/-/aws hashicorp/aws

Prefer the declarative equivalents when they exist. moved and removed blocks and import blocks are reviewable, repeatable across environments, and work in pipelines, while state commands are one-off changes to a single state.

§3Recovery Scenarios

  • A bad apply wrote wrong state. Restore the previous version from your versioned bucket, and then run a plan to see what reality looks like against it.
  • A resource exists but state lost it. Re-attach it with import.
  • State references something deleted by hand. Run terraform state rm, or let a refresh-only apply record its absence.
  • A stuck lock. Confirm no run is active, then terraform force-unlock LOCK_ID.
  • Pushing state back. terraform state push overwrites remote state with a file. It checks the file's serial and lineage to stop you replacing newer state with older, and the check exists for good reason, so overriding it is a last resort.
terraform plan -refresh-only      # does reality match this restored state?
Surgery is for state, not for code mistakes If the real resources are right and only the addressing is wrong, a state mv fixes it. If the real resources are wrong, fix them with code and apply. Never edit state to hide a difference you do not understand.

§4Common Mistakes

MistakeWhat HappensFix
Running state rm without a backupNo way back if you picked the wrong addressAlways state pull first
Hand-editing the state JSONCorrupted serial or lineage and unpredictable behaviorUse the state subcommands, or import/moved
Force-unlocking during a live runTwo writers corrupt stateVerify the other run is dead before unlocking
Practice
  1. In a scratch project, state mv a resource into a module and confirm the next plan shows no changes.
  2. Delete a resource by hand in the console, run plan, then reconcile it two ways: recreate it, and state rm it.
Key takeaways
  • Back up state before any surgery.
  • Use moved, removed, and import blocks where possible; use state commands for one-off fixes.
  • Restore from a versioned backend, then plan to see how reality differs.
