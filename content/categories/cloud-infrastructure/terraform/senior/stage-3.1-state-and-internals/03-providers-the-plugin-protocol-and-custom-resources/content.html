Providers, the Plugin Protocol & Custom Resources

Providers are separate programs that Terraform talks to over a protocol. Understanding that boundary tells you when a custom provider is worth building.

§1How Core and Providers Talk

Each provider is a standalone executable. Terraform core launches it and communicates over gRPC (using the go-plugin library). Core sends requests such as "validate this configuration", "plan this resource change", "apply it", and "read this object". The provider translates them into API calls for its platform and returns results.

That separation is why one Terraform binary supports thousands of providers, why provider versions upgrade independently, and why a provider bug can show up as a "provider produced inconsistent result" error.

terraform providers                       # providers required by this configuration
terraform providers schema -json | jq     # the full schema a provider exposes

The schema lists every resource, argument, type, and whether a change forces replacement, which is the source of what you see in plans.

§2Building One

Providers are written in Go, most often with the Terraform Plugin Framework (the SDKv2 library is the older option). Each resource implements create, read, update, and delete functions that call your API.

Before you write one, ask:

  • Does one already exist? Check the registry first, including community ones.
  • Is there an OpenAPI spec? Generators can scaffold much of a provider from it.
  • Is it a simple HTTP API? A generic REST or http data source, or an external data source calling a script, can cover small cases without a provider.
  • Is it internal and long-lived? A custom provider makes sense when many teams will manage a real internal system as code.

§3Cost of Owning a Provider

A provider is a product. It needs schema design that stays backward compatible, tests (acceptance tests against a real API), documentation, releases, and signing. Changing an argument's name or type breaks every user's configuration.

Write one when the lifecycle is the point If the thing you manage has create, update, and delete with state worth tracking, a provider fits. If you only need to run a one-off call, a script or an existing provider's resource is far cheaper than owning a plugin.

§4Common Mistakes

MistakeWhat HappensFix
Writing a provider for a one-off taskMaintenance forever for little valueUse an existing provider, an external data source, or a script
Making breaking schema changes freelyEvery consumer's plan breaksVersion carefully and deprecate before removing
Skipping acceptance testsProvider bugs reach users' infrastructureTest against a real or realistic API
Practice
  1. Dump a provider's schema with terraform providers schema -json and find an argument that forces replacement.
  2. Sketch the resources a provider for an internal service would need, and list their create, read, update, and delete calls.
Key takeaways
  • Providers are separate gRPC plugins that translate Terraform requests into API calls.
  • The schema defines arguments, types, and replacement behavior.
  • Building a provider is a long-term commitment; prefer existing options first.
