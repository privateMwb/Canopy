Branch Naming, Cleanup & Tags

Consistent branch names, regular cleanup, and tags keep a repository understandable as it grows.

§1Naming Branches

Use short, lowercase, hyphenated names with a prefix that says the purpose.

feature/user-login
fix/null-pointer-on-save
docs/update-readme
chore/upgrade-deps

If your team uses a tracker, include the ticket id, such as fix/PAY-231-rounding. Avoid names like test or my-branch that explain nothing.

§2Cleaning Up

Merged branches clutter the list. Delete them once their work is in.

git branch --merged main            # safe to delete
git branch -d feature/user-login    # delete a merged branch
git branch -D experiment            # force-delete an unmerged branch

-D throws away unmerged commits from the branch list, though the reflog may still hold them for a while.

§3Tags

A tag is a permanent label on a commit, typically used for releases.

git tag v1.0.0                       # lightweight tag
git tag -a v1.0.1 -m "Fix login bug" # annotated tag with message and author
git tag                              # list tags
git show v1.0.1
git checkout v1.0.0                  # look at the project as it was, detached HEAD

Prefer annotated tags for releases, and use semantic versions such as v2.3.1.

The key insight Branches move and tags stay put. Use branches for ongoing work and tags to mark points you will want to find again.

§4Common Mistakes

MistakeWhat HappensFix
Naming branches test2 and final-finalNobody knows what they holdUse prefix and purpose
Keeping dozens of old merged branchesThe list becomes noiseDelete after merging
Using -D casuallyUnmerged work can be lostCheck with git branch --no-merged first
Practice
  1. Adopt a naming convention, create three branches with it, merge them, and delete them.
  2. Tag a release, make more commits, then check out the tag and return to main.
Key takeaways
  • Use descriptive prefix-and-purpose branch names.
  • Delete merged branches, and be careful with -D.
  • Tags mark releases, and annotated tags are preferred.
