Writing Commit Messages That Help

A good commit message tells a future reader why a change was made, and small, focused commits make history something you can actually search and trust.

§1Anatomy of a Good Message

A commit message has a short subject line, a blank line, and an optional body. The subject summarizes the change in about 50 characters, written as a command ("Add", "Fix", "Remove"), with no trailing period. The body explains why, because the diff already shows what.

Fix crash when the cart is empty

Checkout read the first item without checking the list length,
which raised an IndexError for new users. Return early with a
friendly message instead.

Fixes #214

Run git commit with no -m to open your editor for a multi-line message. -m is fine for a one-line change.

§2Bad vs. Good Subjects

WeakBetter
fixed stuffFix login redirect loop on expired sessions
updatesUpdate tax rates for 2026
WIPAdd draft of password reset form
Changed the file and also did thingsTwo commits, one per change

§3Small, Focused Commits

Each commit should do one logical thing and leave the project working. Small commits are easy to review, easy to undo, and easy to find later. If you cannot summarize a commit without the word "and", split it. Stage part of a file with patch mode to do this:

git add -p app.py        # choose hunks one at a time: y / n / s (split) / q
git commit -m "Validate email format on signup"
git add -p app.py
git commit -m "Refactor error messages into one module"
Write for the person debugging at 2 a.m. That person is often you, six months later. Commands like git log, git blame, and git bisect only help if the messages explain the intent behind each change.

§4Common Mistakes

MistakeWhat HappensFix
Vague subjects like "fix" or "updates"History cannot be searched or understoodName what changed and where, in the imperative mood
One huge commit at the end of the dayImpossible to review or partially undoCommit after each logical step
Describing what instead of whyThe body repeats the diffExplain the reason and any trade-off
Practice
  1. Rewrite these three messages: "stuff", "fixed bug", "final version" for changes you invent, each with a subject and a one-sentence body.
  2. Make two unrelated edits in one file and use git add -p to commit them separately with clear messages.
Key takeaways
  • Write a short imperative subject and use the body to explain why.
  • One logical change per commit, leaving the project in a working state.
  • Use git add -p to split mixed changes into separate commits.
