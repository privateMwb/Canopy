Why Version Control & How Git Thinks

Git records your project as a series of snapshots, and everything it does follows from three places your files can live: the working tree, the staging area, and the repository.

§1The Problem Version Control Solves

Without version control you end up with report_final.docx, report_final_v2.docx, and report_final_REAL.docx. You cannot tell what changed between them, who changed it, or how to get back to a version from last Tuesday. A version control system keeps a complete, labelled history of a project so you can see every change, undo any of them, and let several people work at once without overwriting each other.

Git is a distributed version control system. Every clone of a repository contains the full history, so you can commit, browse history, and branch with no network connection. A hosting site such as GitHub is just another copy that people agree to treat as the shared one.

§2Snapshots, Not Differences

Many older tools stored each version as a list of line-by-line differences. Git thinks differently: each commit is a snapshot of the whole project at one moment. If a file did not change, Git simply points at the copy it already stored, so snapshots stay cheap. Each commit also records who made it, when, a message, and a link to its parent commit. Following the parent links gives you the history.

A---B---C   <- three commits, each a full snapshot
^       ^
first   latest (each one points back at its parent)

§3The Three Areas

Almost every beginner command moves changes between three places:

AreaWhat it isMoved by
Working treeThe actual files in your folder, where you editYour editor
Staging area (index)A draft of your next commit: the changes you have chosen to includegit add
RepositoryThe permanent history of commits, stored in the hidden .git foldergit commit
edit files          # working tree changes
git add notes.txt   # copy that change into the staging area
git commit          # turn the staged draft into a permanent snapshot

The staging area exists so you can commit part of your work. If you fixed a bug and also started a half-finished feature, you can stage only the bug fix and commit it on its own.

The key insight A commit is a snapshot you built on purpose. Editing a file does not save anything in history, and neither does staging it. Only git commit writes to the repository, which is why you can experiment freely in the working tree.

§4Common Mistakes

MistakeWhat HappensFix
Assuming a saved file is a saved versionThe edit exists only in the working tree and can be lostCommit when a piece of work is complete and working
Thinking Git needs a server to workConfusion when commands behave offline, or when GitHub is mistaken for Git itselfRemember Git is local first; a host is just a shared copy
Expecting git add to save historyChanges are staged but not committed, so there is no snapshot yetRun git commit after staging to record it
Practice
  1. Draw the three areas on paper and trace a one-line edit to a file from the working tree to the repository, naming the command for each move.
  2. Explain in two sentences why Git can show you a project exactly as it was last month without storing a separate copy of every file each time.
Key takeaways
  • Git stores snapshots of the whole project, linked in a chain by parent references.
  • Changes move from the working tree to the staging area to the repository.
  • Git is distributed: every clone holds the full history and works offline.
