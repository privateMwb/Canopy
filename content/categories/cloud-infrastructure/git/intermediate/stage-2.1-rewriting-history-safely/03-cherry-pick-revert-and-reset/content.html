Cherry-Pick, Revert & Reset

Cherry-pick copies a commit, revert undoes one by adding another, and reset moves a branch pointer; each leaves a different trace, so choose by whether history is shared.

§1Cherry-Pick: Copy a Commit

git cherry-pick applies the changes from one commit onto your current branch as a new commit. It is handy for pulling a bug fix onto a release branch.

git switch release/1.4
git cherry-pick a1b2c3d            # copy that commit here
git cherry-pick a1b2c3d..f6e5d4c  # a range (excludes the first)
git cherry-pick -x a1b2c3d        # also record the original ID in the message

§2Revert: Undo by Adding

git revert creates a new commit that reverses an earlier one. History is preserved, so this is the safe way to undo something that has been shared.

git revert a1b2c3d              # new commit undoing a1b2c3d
git revert HEAD~2..HEAD         # undo the last two commits
git revert -m 1 <merge-commit>  # undo a merge: choose which parent is the mainline

§3Reset: Move the Pointer

git reset moves the current branch to another commit. How it treats your staging area and files depends on the mode.

ModeBranch movesStaging areaWorking tree
--softYesKeptKept
--mixed (default)YesReset to matchKept
--hardYesReset to matchReset: edits are lost
git reset --soft HEAD~1      # un-commit but keep everything staged
git reset HEAD~1             # un-commit and unstage; files keep your edits
git reset --hard HEAD~1      # discard the commit AND your uncommitted edits

§4Which One to Use

GoalShared commitsPrivate commits
Undo a changerevertreset, or revert
Copy a change elsewherecherry-pickcherry-pick
Redo a commitDo not rewritereset --soft, then recommit
Reset rewrites; revert records Reset makes history look as if a commit never happened, which is why it is dangerous on shared branches. Revert admits the commit happened and adds a correction, which is why it is safe.

§5Common Mistakes

MistakeWhat HappensFix
Using reset --hard on a pushed branchYour branch diverges from the remote and uncommitted work is lostUse revert for shared history
Cherry-picking many commits instead of mergingDuplicate commits with different IDs, and confusing history laterUse cherry-pick sparingly, for individual fixes
Reverting a merge without -mGit refuses because it does not know the mainlineRun git revert -m 1 <merge>
Practice
  1. Make three commits; undo the middle one with git revert and read the resulting history.
  2. Try reset --soft, --mixed, and --hard on a throwaway repository and note what git status shows after each.
Key takeaways
  • Cherry-pick copies, revert undoes by adding a commit, reset moves the branch.
  • reset --hard discards uncommitted edits; revert is safe for shared history.
  • Pick the tool by whether the commits have been shared.
