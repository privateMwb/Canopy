Recovering From a Bad Merge or Rebase

Whether the merge is still local or already pushed, there is a safe path back; which one depends on whether other people have the commits.

§1A Bad Merge That Is Still Local

If you have not pushed, you can discard the merge as if it never happened. ORIG_HEAD is set by Git before dangerous operations and points at where the branch was.

git merge --abort                # during an unfinished, conflicted merge
git reset --hard ORIG_HEAD       # after a completed merge: back to before it
git reflog                       # if ORIG_HEAD was overwritten, find the commit here
git reset --hard HEAD@{1}

§2A Bad Rebase

git rebase --abort               # mid-rebase: restore everything
git reflog                       # after finishing: find the line before 'rebase (start)'
# abc1234 HEAD@{9}: commit: Add search tests   <- the state before the rebase
git reset --hard abc1234         # or: git reset --hard ORIG_HEAD

§3A Bad Merge That Was Already Pushed

Never reset a shared branch. Add a commit that undoes the merge:

git revert -m 1 <merge-commit>     # undo the merge, keeping the first parent (main) as mainline
git push

There is one catch. Reverting a merge tells Git that those changes are intentionally gone. If you later merge the same branch again, Git skips the already-merged commits, and the changes do not come back. To bring the feature back, first revert the revert:

git revert <the-revert-commit>     # restores the feature's changes
# or merge the branch again after rebuilding it as new commits

§4Cleaning Up After Recovery

  1. Tell the team what happened and what the branch looks like now.
  2. Find out why it went wrong (wrong target, a bad conflict resolution, an overzealous -X theirs) and add a test or protection to prevent a repeat.
  3. If a conflict resolution dropped code, use git diff <good-commit> HEAD to see exactly what is missing and restore it in a new commit.
Shared history moves forward only On a pushed branch, undo with revert and a new commit, and let everyone pull normally. Resetting and force-pushing a shared branch makes everyone else's clone wrong.

§5Common Mistakes

MistakeWhat HappensFix
Resetting and force-pushing a shared branchTeammates' clones diverge and work is lostUse git revert -m 1 and push normally
Re-merging a reverted branch and getting nothingGit considers those commits already mergedRevert the revert first, or rebuild the branch with new commits
Running reset --hard with uncommitted edits presentEdits are lost permanentlyStash or commit first
Practice
  1. Create a merge, then undo it three ways: reset --hard ORIG_HEAD (local), revert -m 1 (pushed), and recover it via the reflog.
  2. Revert a merge, merge the same branch again, notice what is missing, and fix it by reverting the revert.
Key takeaways
  • Local mistakes: --abort, reset --hard ORIG_HEAD, or the reflog.
  • Pushed mistakes: git revert -m 1 <merge> and a normal push.
  • Reverting a merge means re-merging later needs a revert of the revert.
