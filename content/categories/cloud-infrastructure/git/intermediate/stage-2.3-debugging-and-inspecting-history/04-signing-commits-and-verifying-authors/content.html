Signing Commits & Verifying Authors

The author on a commit is only a label anyone can type, so signing commits with a cryptographic key is how you prove who really made a change.

§1Why Signing Exists

user.name and user.email are not authenticated. Anyone can create a commit that claims to be from anyone. A signature is created with your private key and verified with your public key, so it shows the commit came from the key holder and was not altered afterward.

§2Setting Up Signing

Git can sign with GPG, with SSH keys (simplest if you already use SSH), or with S/MIME. SSH signing:

git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true      # sign every commit
git config --global tag.gpgsign true
git commit -S -m "Add payment retries"        # sign one commit explicitly

Then register the public key on your hosting account as a signing key, so the site can show a "Verified" badge.

§3Verifying

git log --show-signature -3          # who signed these, and is it valid?
git verify-commit a1b2c3d
git tag -s v1.0.0 -m "Release 1.0.0"       # signed tag
git verify-tag v1.0.0

# for SSH signatures, tell Git which keys to trust
echo "ada@example.com $(cat ~/.ssh/id_ed25519.pub)" >> ~/.ssh/allowed_signers
git config --global gpg.ssh.allowedSignersFile ~/.ssh/allowed_signers

Branch protection can require signed commits, making an unverified commit impossible to merge.

§4What a Signature Does and Does Not Prove

  • It proves the key holder made or approved the commit, and the content was not modified since
  • It does not prove the code is safe: a signed commit can still contain a bug or a malicious change
  • Rebasing creates new commits, so the original signatures are lost and must be re-signed
  • A stolen private key still signs as you, so protect keys and revoke on loss
Verified means authentic, not correct A signature answers "who?", not "is it good?". It is one layer of supply-chain defense alongside review, CI, and least-privilege access.

§5Common Mistakes

MistakeWhat HappensFix
Trusting the author fieldSpoofed commits look legitimateRely on signatures for identity and require them on protected branches
Signing with a key not registered on the hostCommits show as unverifiedUpload the public key as a signing key
Rebasing signed commits and forgetting to re-signSignatures vanish from the rewritten commitsUse git rebase --exec 'git commit --amend --no-edit -S' or -S on rebase
Practice
  1. Set up SSH commit signing, make one signed commit, and confirm it with git log --show-signature.
  2. Create a signed tag for a release and verify it using git verify-tag.
Key takeaways
  • The author field is unauthenticated; signatures prove who made a commit.
  • SSH signing is a simple route: set gpg.format ssh and a signing key.
  • Signed means authentic, not safe, and rebasing drops the old signatures.
