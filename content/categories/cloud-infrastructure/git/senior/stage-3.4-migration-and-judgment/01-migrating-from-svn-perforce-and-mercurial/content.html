Migrating From SVN, Perforce & Mercurial

A successful migration preserves history, maps people correctly, and earns the team's trust, and the cutover plan matters as much as the conversion tool.

§1Understand the Source Model First

Different systems store history differently, so a conversion is a translation, not a copy.

SourceKey differences from GitCommon tool
Subversion (SVN)Centralized; global revision numbers; folders as branches and tags; path-based permissionsgit svn, svn2git, SubGit
Perforce (Helix Core)Centralized; changelists; stream or depot paths; huge binary assets; file lockinggit p4, git-fusion, P4 migration tools
MercurialDistributed, close to Git; named branches and bookmarks; different phases and rewriting modelhg-fast-export, git-remote-hg

§2Convert, Map Authors, Verify

# authors.txt maps old usernames to Git identities
jdoe = John Doe <john.doe@example.com>
asmith = Alice Smith <alice.smith@example.com>

git svn clone https://svn.example.com/repo --stdlayout --authors-file=authors.txt converted
cd converted
git for-each-ref refs/remotes/origin/tags      # SVN tags arrive as branches: convert them
git tag v1.0 refs/remotes/origin/tags/v1.0     # create real Git tags from those refs
  • Map every author to a name and email, or commits will carry meaningless identities
  • Decide how to treat branches and tags: convert tags to real tags and keep only branches still in use
  • Verify: compare file trees at several revisions (diff -r the checked-out source against a Git checkout of the matching commit), and compare commit counts and the latest state
  • Handle large binaries with LFS or exclude them, since Perforce depots often hold gigabytes of assets that Git cannot store comfortably
  • Consider not migrating all history: a clean start in Git, with the old system archived read-only, is sometimes the right call

§3Cutover Without Losing Trust

  1. Run the conversion repeatedly in rehearsal until it is scripted and repeatable.
  2. Freeze the old system on a stated date and time, read-only, and announce it early.
  3. Do a final incremental conversion, verify it, and push to the new host with branch protection and CI already configured.
  4. Migrate surrounding systems: build jobs, hooks, issue links, deployment scripts, and documentation.
  5. Keep the old system readable for a defined period as a safety net, and keep a rollback plan.
  6. Train and support the team during the first weeks, with short guides for the five commands they will use most.
People are the hard part of a migration The conversion is a technical task, but adoption is a human one. A team that has not been trained, or that sees its history garbled, will resent the move no matter how clean the tool output is.

§4Common Mistakes

MistakeWhat HappensFix
Skipping the authors fileHistory attributed to usernames like jdoe@svn-serverMap all authors before the real conversion
Migrating once on cutover nightSurprises with no time to fix themRehearse the full conversion several times
Forgetting build and deploy integrationCI and release scripts still point at the old systemInventory and migrate every consumer of the old repository
Practice
  1. Write a migration plan for a ten-year-old SVN repository: tool, author mapping, verification steps, and what you would do about large binaries.
  2. Draft the announcement for the freeze date, including what changes for developers on day one.
Key takeaways
  • Treat conversion as translation: map authors, branches, tags, and large files deliberately.
  • Rehearse, verify against the source, and keep the old system as a safety net.
  • Train people and migrate the surrounding build and deploy tooling.
