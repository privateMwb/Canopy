Rewriting History at Scale

git filter-repo can split, merge, and clean entire repositories, but it rewrites every affected commit, so it needs planning, a backup, and a coordinated cutover.

§1Why Rewrite

Typical reasons: remove a leaked secret or a huge binary that bloats every clone, extract a folder into its own repository, merge repositories into one, fix author identities, or reorganize a directory layout. Because commits are immutable, rewriting creates a new history with new hashes for everything downstream of the first change.

Use git filter-repo (a separate tool) rather than the old git filter-branch, which is slow and easy to misuse.

§2Common Operations

git clone --no-local original rewrite-work && cd rewrite-work    # always work on a fresh clone

git filter-repo --path services/billing/ --path-rename services/billing/:   # extract a folder as its own repo
git filter-repo --path-glob '*.mp4' --invert-paths             # remove all video files from history
git filter-repo --strip-blobs-bigger-than 10M                  # drop very large blobs
git filter-repo --mailmap mailmap.txt                          # fix author names and emails
git filter-repo --replace-text replacements.txt                # scrub secrets from file content
git filter-repo --analyze                                      # report what is taking up space

To merge repositories, rewrite each one into a subdirectory first, then merge them as unrelated histories so paths do not collide:

git filter-repo --to-subdirectory-filter app-a      # run inside a clone of app-a
# in the combined repo:
git remote add app-a ../app-a
git fetch app-a
git merge app-a/main --allow-unrelated-histories

§3Doing It Safely at Scale

  1. Back up the original repository and keep it untouched until the end.
  2. Rewrite in a fresh clone, and compare results with --analyze and sample checkouts before publishing.
  3. Announce a freeze: all open branches and PRs are based on old commits and will have to be recreated.
  4. Force-push the rewritten history to the host, including all branches and tags.
  5. Have everyone re-clone (or follow a documented rebase-onto procedure for unpushed work). An old clone that is pushed back reintroduces the old history.
  6. Clean up hidden references on the host: pull request refs, forks, and caches may keep old objects until the host purges them.
git push --force --all origin
git push --force --tags origin
# for unpushed work on an old clone:
git rebase --onto new-main old-base my-branch
Rewriting history is a coordination problem The command takes seconds. The cost is that every collaborator's clone, open branch, and pull request is now based on commits that no longer exist. Plan the communication and the cutover as carefully as the filter.

§4Common Mistakes

MistakeWhat HappensFix
Running filter-repo on your only copyNo way back if the filter is wrongBack up, and work in a fresh clone
Letting someone push an old clone afterwardThe removed content reappears in historyHave everyone re-clone, and block pushes of old history
Assuming the host forgets old objects immediatelySecrets remain retrievable by hash or through forksAsk the host to purge, and rotate any leaked credential anyway
Practice
  1. Use filter-repo --analyze on a repository with some large files, remove the biggest, and compare clone sizes before and after.
  2. Extract one folder of a monorepo into its own repository with --path, and verify the history of one file survived.
Key takeaways
  • git filter-repo rewrites history to split, merge, clean, and remap a repository.
  • Always work on a backed-up fresh clone and compare before publishing.
  • A rewrite requires everyone to re-clone, and the host to purge old references.
