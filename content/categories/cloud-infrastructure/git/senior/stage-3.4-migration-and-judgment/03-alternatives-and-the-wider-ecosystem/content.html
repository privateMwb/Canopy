Alternatives & the Wider Ecosystem

Jujutsu, Mercurial, Fossil, and Sapling take different approaches to version control, and each shows a design choice Git made, or could have made differently.

§1Why Look Beyond Git

Git dominates, but its interface is widely criticized, and several tools redesign the user experience, the data model, or the scale story. Knowing them sharpens your understanding of Git itself, and some can be used on top of a Git repository without changing how your team works.

§2A Tour

ToolIdeaWhat it teaches
Jujutsu (jj)Works on Git repositories; the working copy is itself a commit that is amended automatically; no staging area; conflicts are stored in commits; every operation is recorded and undoable (jj undo)How much of Git's friction comes from the index and from fear of rewriting
Mercurial (hg)Distributed like Git, with a simpler interface and strong extension system; history is harder to rewrite by default (phases)A different balance between safety and flexibility
SaplingMeta's source control, compatible with Git hosting; smartlog view, stacked commits as the norm, built for very large monoreposHow stacked, small-commit workflows and scale feel when they are first-class
FossilOne executable bundling version control, wiki, tickets, and a web UI, stored in one SQLite file; used by SQLite itselfThe value of integrated project management in a single portable file
Perforce / Plastic SCMCentralized with locking and strong binary/asset handlingWhy game studios and others with huge binaries still use them
jj git clone https://example.com/repo.git     # use a normal Git remote
jj new main -m "experiment"                      # start a change; no add or commit needed
jj log                                            # change graph
jj undo                                           # undo the last operation, whatever it was
jj git push                                       # push to the Git remote

§3What These Tools Reveal About Git

  • The staging area is a design choice, and you can have a good workflow without it
  • Commit identity can be a stable change ID rather than only a hash, which makes rewriting and stacking easier to follow
  • Conflicts can be first-class data, recorded in commits and resolved later
  • Safety (operation logs, undo) can be built into the tool rather than left to the reflog
  • Git's hosting ecosystem (pull requests, CI, tooling) is a stronger reason to stay than its interface

Evaluate a switch by asking what problem it solves for your team, whether it interoperates with your host and CI, and how much retraining it costs.

Interoperability lowers the risk Tools that speak Git, such as Jujutsu and Sapling, let one person try a different workflow while everyone else keeps using ordinary Git. That makes experimentation cheap and reversible.

§4Common Mistakes

MistakeWhat HappensFix
Switching a whole team for interface preference aloneRetraining and tooling cost without a measurable gainPilot individually, via a Git-compatible tool
Assuming alternatives are unfinished or obscureMissing real innovations in workflow and scaleTry them on a throwaway repository
Judging Git only by its commandsOverlooking that its strength is its ecosystem and data modelSeparate the interface from the storage and hosting layers
Practice
  1. Install Jujutsu (or Sapling) and use it on a clone of a small Git repository; list three things that felt different and the Git concept each one maps to.
  2. Write a short argument for and against moving a team to a non-Git tool, naming the specific problem it would solve.
Key takeaways
  • Jujutsu, Sapling, Mercurial, and Fossil rethink the interface, data model, or scale of version control.
  • Several work on top of Git repositories, so you can try them without switching the team.
  • They show that the staging area, commit identity, and conflict handling are design choices.
