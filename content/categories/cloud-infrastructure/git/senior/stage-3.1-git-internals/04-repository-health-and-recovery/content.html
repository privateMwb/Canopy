Repository Health & Recovery

Git can check its own database for corruption, find unreachable objects, and rebuild around damage, and knowing these commands makes a broken repository a solvable problem.

§1Checking for Damage

git fsck --full                    # verify object connectivity and integrity
# error: object file .git/objects/ab/cd... is empty
# missing blob 3f2a...
# dangling commit 9c8b...      <- unreachable, but not corruption
git fsck --lost-found              # write dangling objects to .git/lost-found/
git count-objects -vH              # size and shape of the object store

Dangling objects (unreachable but intact) are normal leftovers from rebases and resets. Missing or corrupt objects are real problems.

§2Recovering Unreachable Work

git fsck --unreachable --no-reflogs | grep commit      # find orphaned commits
git show 9c8b7a6                                            # inspect one
git branch recovered 9c8b7a6                                # keep it by naming it

This is the deeper version of the reflog rescue: it finds commits nothing refers to, even when no reflog entry remains, until garbage collection prunes them.

§3Garbage Collection and Pruning

git gc                          # pack objects; prune very old unreachable ones
git gc --auto                    # only if the repo needs it (runs automatically)
git prune --dry-run              # show what unreachable objects would be deleted
git reflog expire --expire=30.days --all
git repack -ad

Unreachable objects are removed only after a grace period (two weeks by default), so recent mistakes remain recoverable.

§4Repairing a Damaged Repository

  1. Back up first: copy the whole folder before attempting any repair.
  2. If the corruption is in objects and a remote has a good copy, fetch to repair: git fetch origin after removing the empty or corrupt object files.
  3. If refs are broken, rebuild them: git update-ref refs/heads/main <good-sha>, or restore .git/HEAD.
  4. If only a clone is damaged and everything is pushed, the simplest fix is a fresh clone, then copying uncommitted work across manually.
  5. Run git fsck --full again to confirm a clean result.
find .git/objects -type f -empty -delete     # remove empty (corrupt) loose objects
git fetch origin                               # pull good copies back from the remote
git fsck --full
A remote is also a backup Most corruption is repairable by fetching from another clone, because every clone holds the full history. This is one more reason to push often.

§5Common Mistakes

MistakeWhat HappensFix
Running gc --prune=now while investigatingDangling objects you might need vanishUse fsck first; avoid aggressive pruning
Repairing without a backup copyA failed repair makes things worseCopy the repository folder first
Treating dangling objects as corruptionNeedless panicDangling is normal; only missing or corrupt objects matter
Practice
  1. Create commits, reset them away, and find one with git fsck --unreachable, then restore it with a branch.
  2. In a scratch clone, delete one loose object file, run git fsck, and repair it with git fetch.
Key takeaways
  • git fsck verifies the object store; dangling objects are normal.
  • Unreachable commits can be found with fsck and rescued by giving them a branch.
  • Back up before repairing, and use a remote to restore missing objects.
