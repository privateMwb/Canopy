Repository Health & Recovery

Git repositories are durable but not indestructible, so know how to check, repair, and shrink one.

§1Checking Health

git fsck --full                      # verify objects and connectivity
git fsck --lost-found                # find dangling objects
git count-objects -vH
git maintenance start                # schedule background gc and commit-graph updates

fsck reports corrupt or missing objects and dangling commits not reachable from any ref.

§2Common Repairs

  • Corrupt object: fetch it again from a remote, or copy the object file from another clone.
  • Broken ref: inspect with git show-ref, fix with git update-ref.
  • Empty object file after a crash: delete the empty file, then fetch.
  • Last resort: clone fresh and copy over your unpushed work, using git format-patch or git bundle.
git bundle create repo.bundle --all     # a single-file backup of the repository
git format-patch origin/main            # turn local commits into patch files

§3Garbage Collection

git gc --prune=now                      # remove unreachable objects immediately
git reflog expire --expire=now --all    # also expire the reflog (destructive)

Normal git gc keeps unreachable objects for a grace period, so recent mistakes stay recoverable.

§4Removing Large or Sensitive Content

Deleting a file does not shrink history. Use git filter-repo, which rewrites every commit.

git filter-repo --path secrets/ --invert-paths
git filter-repo --strip-blobs-bigger-than 10M

Rewriting changes every later hash: everyone must re-clone, open PRs must be recreated, and forks and caches may still hold the old data.

The key insight A clone elsewhere is your best backup. Most corruption is fixed by fetching the missing objects again.

§5Common Mistakes

MistakeWhat HappensFix
Running gc --prune=now in a panicYou delete the commits you wanted to recoverRecover first, clean later
Using filter-branch instead of filter-repoSlow and easy to get wrongUse git filter-repo
Expecting history rewrite to un-leak a secretCopies and forks still have itRotate the secret
Practice
  1. Create a deliberate corruption in a test clone and repair it by fetching.
  2. Remove a large file from a test repository's history and compare sizes.
Key takeaways
  • fsck finds corruption, and fetching from another clone usually repairs it.
  • gc reclaims space, and reflog expiry and --prune=now are destructive.
  • filter-repo rewrites history and forces everyone to re-clone.
