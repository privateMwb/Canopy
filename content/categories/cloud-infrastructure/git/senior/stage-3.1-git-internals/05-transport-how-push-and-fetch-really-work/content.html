Transport: How Push and Fetch Really Work

A push or fetch is a short negotiation about which objects each side already has, followed by a single packfile carrying only what is missing.

§1Refspecs: Mapping Names

A refspec says which refs to transfer and where to put them: <source>:<destination>, with a leading + meaning "update even if not a fast-forward". Your config contains the defaults.

git config --get-all remote.origin.fetch
# +refs/heads/*:refs/remotes/origin/*      # remote branches -> origin/* tracking refs
git push origin main:release                # push local main to remote branch release
git push origin :old-branch                 # empty source: delete the remote branch
git push origin v1.0.0                      # push one tag
git fetch origin '+refs/pull/*/head:refs/remotes/origin/pr/*'   # fetch PR heads

§2The Smart Protocol

Over SSH or HTTPS, Git runs a small program on each end (upload-pack for fetch, receive-pack for push) and they talk in a smart protocol:

  1. The server advertises its refs and the hashes they point to.
  2. The client says which hashes it wants and which it already has.
  3. The server computes the minimal set of objects the client lacks and builds a thin packfile of just those.
  4. The client stores the pack and updates its remote-tracking refs. For a push, the roles are reversed, and the server applies the ref updates only if they are fast-forwards or forced.
GIT_TRACE=1 git fetch origin                       # show the commands being run
GIT_TRACE_PACKET=1 git fetch origin 2>&1 | head -40   # the protocol conversation
GIT_CURL_VERBOSE=1 git fetch origin                   # HTTP-level detail
git ls-remote origin                                  # what the remote advertises

§3Why Pushes Get Rejected

A push is refused when the server's branch contains commits your local branch does not, because updating it would orphan them: a non-fast-forward update. --force-with-lease forces the update only if the remote ref still points where you last saw it, protecting against overwriting someone else's new push.

CommandBehavior
git push --forceOverwrites the remote ref unconditionally
git push --force-with-leaseOverwrites only if the remote ref is what you last fetched
git push --force-if-includesAdditionally checks that you integrated the remote's changes locally
Transfers are incremental by design Because objects are named by hash, Git can ask "do you have this?" and send only what is missing. That is why pushing a one-line change to a huge repository is fast.

§4Common Mistakes

MistakeWhat HappensFix
Using --force on a shared branchOthers' commits are overwritten without warningUse --force-with-lease, and avoid forcing shared branches at all
Misreading git push origin a:bPushing to an unintended remote branch nameRead it as <local>:<remote>, and check with git ls-remote
Assuming tags are pushed automaticallyReleases missing from the remotePush tags explicitly, or use --follow-tags for annotated ones
Practice
  1. Run GIT_TRACE_PACKET=1 git fetch against a repository and identify the advertisement, the wants and haves, and the returned pack.
  2. Use refspecs to push a local branch to a differently named remote branch, then delete that remote branch with an empty source.
Key takeaways
  • Refspecs map source refs to destination refs; + allows non-fast-forward updates.
  • Fetch and push negotiate what each side has, then send one packfile with only the missing objects.
  • --force-with-lease is the safe form of forcing, but it is still not for shared branches.
