Large Repositories & Performance

When a repository grows, commands slow down for specific, diagnosable reasons, and Git has features that fix most of them.

§1Find the Slow Part First

Slowness usually comes from one of three places: too many files (status, add), too much history (log, blame, clone), or too much data (clone, fetch, gc). Measure before tuning.

GIT_TRACE2_PERF=1 git status 2>&1 | head -30     # where time goes
git count-objects -vH                           # object store size
git rev-list --count HEAD                       # number of commits
git ls-files | wc -l                            # number of tracked files
time git status

§2Speed Up Working-Tree Commands

git config core.fsmonitor true            # a filesystem watcher tells Git what changed
git config core.untrackedCache true         # cache untracked-file scans
git update-index --index-version 4          # smaller index
git sparse-checkout set --cone dir1 dir2    # fewer files to scan at all

§3Speed Up History Commands

A commit-graph file caches commit relationships, making log --graph, merge-base, and reachability checks much faster. Multi-pack indexes and bitmaps speed up fetch and clone on servers.

git commit-graph write --reachable --changed-paths   # faster log and blame on paths
git config fetch.writeCommitGraph true
git maintenance start                       # schedule prefetch, commit-graph, loose-objects, and pack tasks
git maintenance run --task=gc

§4Reduce What You Transfer and Store

ProblemRemedy
Huge clone for CI--depth 1, --filter=tree:0, or cache the clone
Developers download every old blob--filter=blob:none partial clone
Big binaries inflating historyGit LFS going forward; git filter-repo to clean the past
Many refs (thousands of branches/tags)Prune stale branches; fetch.prune; archive old tags
Slow server fetchesServer-side bitmaps, multi-pack index, geometric repacking
git for-each-ref --format='%(refname)' | wc -l       # how many refs?
git fetch --prune --prune-tags                         # drop refs deleted on the remote
git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | sort -k3 -n -r | head   # biggest objects
Fix the cause you measured Turning on every performance option at once makes it hard to know what helped. Trace one slow command, change one thing, and re-measure.

§5Common Mistakes

MistakeWhat HappensFix
Tuning without measuringTime spent on settings that change nothingUse GIT_TRACE2_PERF and time first
Running aggressive gc constantlyWasted CPU, and short windows for recoveryUse git maintenance and let Git schedule work
Committing large generated filesPermanent growth of every cloneKeep them out, or use LFS before the first commit
Practice
  1. Take a large public repository, record git status and git log times, then enable fsmonitor and the commit-graph and measure again.
  2. Use the object-size pipeline above to find the five largest blobs in a repository and decide what to do about each.
Key takeaways
  • Diagnose first: many files, much history, or much data.
  • fsmonitor, untracked cache, and sparse checkout speed up the working tree; commit-graph speeds up history.
  • Partial clones, LFS, and ref pruning reduce transfer and storage.
