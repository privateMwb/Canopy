CI/CD Integration & Merge Queues

Status checks stop broken code from merging, and a merge queue keeps the main branch green even when many pull requests land at once.

§1Required Status Checks

CI runs your build, tests, and linters on every pull request and reports a status back to the hosting site. Branch protection can then require specific checks to pass before merging. Name the required checks explicitly; a renamed job that silently stops being required is a common gap.

# .github/workflows/ci.yml (excerpt)
on:
  pull_request:
  push:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make test

§2The Stale-Green Problem

Two pull requests can each pass CI against an older main, yet break each other once both merge. PR A renames a function; PR B adds a new call to the old name. Both are green alone; main is red after the second merge.

The partial fix is "require branches to be up to date before merging", but that forces everyone to rebase and re-run CI each time someone else merges, which does not scale.

§3Merge Queues

A merge queue (GitHub merge queue, GitLab merge trains, Bors, Mergify, Aviator) fixes this. When a PR is approved, it joins a queue. The queue builds a temporary branch of main plus the queued PRs in order, runs CI on that exact combination, and merges only if it passes.

main ── A ── B ── C        queue order
         │
         ▼
  temp: main + A          ✓ merge A
  temp: main + A + B      ✓ merge B
  temp: main + A + B + C  ✗ C is ejected; later PRs rebuild without it

Because CI tests what will actually land, main stays green without developers repeatedly rebasing. Queues can batch several PRs into one CI run for throughput, and bisect the batch when it fails.

§4Practical Settings

  • Make CI fast and reliable; flaky tests make queues stall and people distrust them
  • Trigger CI for the merge_group event as well as pull_request, since queues run their own checks
  • Quarantine flaky tests instead of retrying blindly
  • Keep an emergency path (a bypass by a small group, logged) for outages
  • Measure queue time; if it exceeds your tolerance, add batching or parallelism
Test what will merge, not what was written A pull request's green check says it works against the old main. A merge queue's check says it works against the main it is about to join. That difference is the whole value of the queue.

§5Common Mistakes

MistakeWhat HappensFix
Requiring checks by a job name that later changesMerging proceeds with no required checkReview required checks whenever workflows are renamed
Allowing flaky tests in the queueRandom ejections and long waitsFix or quarantine flaky tests
Forgetting the merge_group triggerQueue entries wait forever for checks that never runAdd the event to your CI configuration

  1. Describe a concrete example of two PRs that each pass CI alone but break main together, and explain how a queue catches it.
  2. List the branch protection rules and CI changes needed to turn on a merge queue for a repository.
Key takeaways
  • Required status checks block broken code; name them carefully.
  • Green PRs can still break main together; queues test the real merge result.
  • Fast, reliable CI is the foundation of any queue.
