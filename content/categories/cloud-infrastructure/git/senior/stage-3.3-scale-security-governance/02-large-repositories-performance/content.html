Large Repositories & Performance

Large repositories make everyday Git commands slow, and a few settings and clone strategies bring them back.

§1Where Time Goes

Operations such as status scan the working tree, log walks history, and clone transfers every object. The cost grows with files, commits, and history size.

§2Clone Strategies

git clone --depth=1 URL                          # shallow: only the latest commit (good for CI)
git clone --filter=blob:none URL                 # partial: fetch file contents on demand
git clone --filter=tree:0 URL                    # treeless: even leaner
git fetch --unshallow                            # restore full history when needed

Shallow clones hurt tools that need history (blame, bisect, version computation), so use them where history does not matter.

§3Speeding Up Commands

git config core.fsmonitor true                   # watch for changes instead of scanning
git config core.untrackedCache true
git config feature.manyFiles true
git commit-graph write --reachable               # speeds up log and merge-base queries
git maintenance start                            # background maintenance
git config fetch.writeCommitGraph true

§4Finding the Bottleneck

GIT_TRACE=1 GIT_TRACE_PERFORMANCE=1 git status
git count-objects -vH
du -sh .git
git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | sort -k3 -n -r | head

That last command lists the largest objects in history, which usually points to accidentally committed binaries.

§5Beyond Settings

If a repository is still too big, consider LFS for assets, splitting out generated or vendored directories, archiving old history into a separate repository, or tools that provide virtual file systems.

The key insight Measure first. Most slowness comes from a few large blobs, too many files, or a missing cache, and each has a specific fix.

§6Common Mistakes

MistakeWhat HappensFix
Shallow clones for developers who need historyBlame and log are incompleteUse partial clones instead
Tuning settings without measuringNo improvement, extra complexityUse trace output to find the slow step
Letting binaries accumulate in historyEvery clone pays for themUse LFS, and clean history if needed
Practice
  1. Measure git status time before and after enabling fsmonitor on a big repository.
  2. List the ten largest objects in a repository and decide what to do with each.
Key takeaways
  • Shallow, partial, and treeless clones trade history or data for speed.
  • fsmonitor, commit-graph, and maintenance speed up daily commands.
  • Trace and measure before you change anything.
