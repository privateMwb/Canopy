Feature Flags & Release Branches

Feature flags separate deploying code from releasing it, while release branches give you a stable place to harden a version, ship hotfixes, and backport fixes.

§1Deploy Is Not Release

A feature flag is a runtime switch, so incomplete or risky code can be merged into trunk and shipped to production while still turned off. Releasing becomes flipping the flag, which can target a percentage of users, one team, or a region, and be reverted instantly without a deploy.

if (flags.isEnabled("new-checkout", user)) {
  return newCheckout(cart);      // merged and deployed, but dark until enabled
}
return oldCheckout(cart);

Flags have a cost: more code paths to test, and stale flags become clutter and risk. Give each flag an owner and a removal date, and delete it once the rollout finishes.

§2Release Branches

When you must stabilize a version while new work continues, cut a release branch from trunk at a chosen point. Only fixes go onto it.

git switch -c release/2.4 main        # cut the release branch
git tag -a v2.4.0 -m "Release 2.4.0"      # tag the shipped commit
# new development continues on main

§3Hotfixes and Backports

Fix the bug on trunk first, then copy the fix to each supported release branch. Fixing trunk first ensures the problem cannot reappear in the next version.

git switch main
# ...fix, review, merge; note the fix commit's hash, e.g. 5d6e7f8...
git switch release/2.4
git cherry-pick -x 5d6e7f8                 # -x records the source commit in the message
git tag -a v2.4.1 -m "Hotfix: crash on empty cart"
git push origin release/2.4 v2.4.1

Fixing the release branch only and forgetting trunk is the classic way a bug returns in the next release. Some teams enforce "trunk first" with a CI check or a tool that opens the backport pull requests automatically.

§4Choosing Between Them

SituationReach for
Ship half-built work safelyA feature flag
Gradual rollout or instant kill switchA feature flag
Support v2.4 while building v3A release branch
Urgent fix for a released versionA hotfix plus a cherry-picked backport
Fix forward, then backport Merge the fix into trunk first, then cherry-pick it into each release branch with -x. Every release branch then gets the fix, and trunk can never lose it.

§5Common Mistakes

MistakeWhat HappensFix
Leaving flags in the code for yearsCombinatorial test paths and dead codeTrack flags with owners and expiry; remove after rollout
Fixing only the release branchThe bug returns in the next versionFix trunk first, then backport
Cherry-picking without -xNobody can tell where a backport came fromUse cherry-pick -x to record the source commit
Practice
  1. Create a release/1.0 branch, fix a bug on main, and backport it to the release with cherry-pick -x, then tag v1.0.1.
  2. Design a flag rollout plan for a risky change: who sees it first, what you monitor, and the rule for removing the flag.
Key takeaways
  • Feature flags separate deployment from release and allow instant rollback.
  • Release branches stabilize a version while trunk moves on.
  • Fix trunk first, then backport with cherry-pick -x.
