Versioning, Changelogs & Release Automation

Semantic versions, tags, and automation turn releases from a ceremony into a routine.

§1Semantic Versioning

MAJOR.MINOR.PATCH: increment MAJOR for breaking changes, MINOR for compatible features, PATCH for compatible fixes.

1.4.2 → 1.4.3   bug fix
1.4.2 → 1.5.0   new feature, backward compatible
1.4.2 → 2.0.0   breaking change

For applications, calendar versioning (such as 2026.03) can be more honest than semantic versions.

§2Tags as Releases

git tag -s v1.5.0 -m "Release 1.5.0"
git push origin v1.5.0
git describe --tags                  # version relative to the last tag, e.g. v1.5.0-12-g3f9a2c1
git log v1.4.2..v1.5.0 --oneline     # what is in the release

§3Changelogs

A changelog says what changed for users. With Conventional Commits you can generate one from history, but a human edit usually improves it.

## 1.5.0 — 2026-03-02
### Added
- Passkey login
### Fixed
- Rounding error in invoice totals (#231)

§4Automating Releases

Tools such as semantic-release, release-please, and changesets read commit messages or change files, choose the next version, update the changelog, tag, and publish.

on: { push: { branches: [main] } }
jobs:
  release:
    steps:
      - uses: googleapis/release-please-action@v4

Automation is only as good as the commit discipline feeding it, and publishing steps need protected credentials.

The key insight A release should be a repeatable procedure that starts from a tag. If it needs a hero, automate it.

§5Common Mistakes

MistakeWhat HappensFix
Reusing or moving a published tagConsumers get different code under one versionNever retag. Publish a new version
Breaking changes in a minor releaseDownstream builds failReserve breaking changes for major versions
Automating releases from messy commit messagesWrong versions and empty changelogsEnforce commit conventions in CI
Practice
  1. Create a tag, generate a changelog between two tags, and publish release notes.
  2. Set up release automation on a test repository with conventional commits.
Key takeaways
  • Semantic versions communicate compatibility, and tags mark exact releases.
  • Changelogs are for users, and tools can draft them from history.
  • Automate the release path, and never rewrite published tags.
