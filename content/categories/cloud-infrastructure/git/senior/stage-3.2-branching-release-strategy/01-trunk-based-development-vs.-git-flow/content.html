Trunk-Based Development vs. Git Flow

Branching models trade integration speed against release control, and the right one depends on how you ship.

§1Git Flow

Long-lived main and develop branches, with feature, release, and hotfix branches. It suits software with scheduled, versioned releases and multiple supported versions, such as desktop software or libraries.

Costs: long-lived branches drift, merges get large and risky, and releases need ceremony.

§2GitHub Flow

main is always deployable. Work happens on short-lived branches that go through a pull request and merge to main, then deploy. It is simple and fits continuously deployed web services.

§3Trunk-Based Development

Everyone integrates into main (the trunk) at least daily, either by committing directly or through very short-lived branches measured in hours. Incomplete work is hidden behind feature flags so the trunk is always releasable.

Git Flow:     main ──────────●───────────●───
              develop ─●──●──●──●──●──●──●──   (long-lived, merges are big)
Trunk-based:  main ─●─●─●─●─●─●─●─●─●─●─●─    (tiny, frequent integrations)

§4What the Evidence Suggests

Research on delivery performance (DORA) links frequent integration to better outcomes, and trunk-based development requires strong automated tests, fast CI, and flags.

§5Choosing

  • Continuous deployment web app, strong CI: trunk-based or GitHub Flow.
  • Versioned releases with long support windows: release branches off the trunk, backporting fixes.
  • A team without reliable tests: fix testing first. No branching model rescues a weak safety net.
git switch -c release/2.4 main        # cut a release branch only when you need to support it
The key insight The branching model is a decision about how long code stays unintegrated. Shorter is almost always better, if your tests can keep up.

§6Common Mistakes

MistakeWhat HappensFix
Adopting Git Flow for a continuously deployed serviceLong-lived branches and slow mergesUse short-lived branches and deploy from main
Going trunk-based without tests or flagsBroken main and unfinished features exposedInvest in CI and flags first
Letting feature branches live for weeksPainful, risky mergesBreak work into small increments
Practice
  1. Describe how a team of eight shipping a mobile app and a team of eight running a web service should each branch, and why.
  2. Measure how long branches live in a repository you know.
Key takeaways
  • Branching models trade integration speed against release control.
  • Short-lived branches and frequent integration usually win when CI is strong.
  • Release branches are for versions you must support, not for every project.
