Reading Errors: Common Failures & Fixes

Most Docker problems are one of a small set of failures, and a repeatable routine of logs, state, and exit code finds the cause quickly.

§1A Diagnosis Routine

Work from the outside in, and read the actual message before changing anything:

docker ps -a                                   # is it running? did it exit?
docker logs --tail 100 NAME                    # what did it say?
docker inspect NAME --format '{{.State.ExitCode}} {{.State.OOMKilled}}'
docker compose config                          # what did Compose really resolve?
docker run --rm -it --entrypoint sh IMAGE      # get a shell in the image itself

Exit codes help: 0 is a clean exit, 1 is a general application error, 125/126/127 mean Docker or the command could not run or was not found, 137 means killed by SIGKILL (often out of memory), and 143 means terminated by SIGTERM.

§3Narrowing the Cause

Ask three questions in order: Did the container start? Did the process stay running? Is the network path open? For the last one, test from inside the network rather than from your host:

docker exec web wget -qO- http://localhost:3000/health   # does the app itself answer?
docker run --rm --network appnet curlimages/curl -sS http://web:3000/health

If the first works and the second fails, the problem is networking or binding, not the app.

Change one thing at a time The fastest debugging is a small experiment: reproduce the failure with the shortest command, change one variable, and observe. Rebuilding everything after each guess hides the cause.

§4Common Mistakes

MistakeWhat HappensFix
Rerunning the same command hoping it worksNo new informationRead the logs and exit code first
Debugging a Compose file by eyeMissed indentation or variable defaultsRun docker compose config to see the resolved file
Reading only the last line of an errorRoot cause is often a few lines aboveRead from the first error, not the last one
Practice
  1. Intentionally start a container that exits (for example docker run alpine false) and find the exit code with docker inspect.
  2. Publish a service bound to 127.0.0.1 inside the container, observe the failure from the host, then fix the binding.
Key takeaways
  • Diagnose with ps -a, logs, inspect, and an exit code before changing anything.
  • Most failures fall into a short list: daemon, ports, exit paths, architecture, permissions, names, memory, and binding.
  • Test connectivity from inside the network to separate app problems from network problems.
