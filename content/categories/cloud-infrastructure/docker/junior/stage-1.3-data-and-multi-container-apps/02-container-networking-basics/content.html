Container Networking Basics

Containers on the same user-defined network can reach each other by name, while the outside world only reaches the ports you publish.

§1The Default Bridge and Why to Avoid It

Docker creates a default bridge network, and containers join it unless told otherwise. On it, containers can reach each other by IP address but not by name. IPs change on every restart, so this is awkward to rely on. Create your own network instead.

§2User-Defined Networks and Container DNS

On a network you create, Docker provides a built-in DNS server, so each container is reachable by its container name (and service name in Compose):

docker network create appnet
docker run -d --name db --network appnet -e POSTGRES_PASSWORD=devpass postgres:16
docker run --rm --network appnet postgres:16 \
  psql -h db -U postgres -c "select 1"      # "db" resolves to the container
docker network ls
docker network inspect appnet

Inside the network, containers connect to each other's container port directly (db:5432). No publishing is needed for container-to-container traffic.

§3Published Ports and the Outside World

Publishing is only for traffic coming from outside the network, such as your browser or another machine.

docker run -d --name web --network appnet -p 8080:80 nginx

Here web can call db:5432 over the network, your browser reaches web at localhost:8080, and nothing outside can reach db at all, which is exactly what you want. Two containers can both listen on port 80 internally; only the host ports must be unique.

"localhost" means the container itself Inside a container, localhost is that container. An app that connects to localhost:5432 expecting a database next door will fail. Use the other container's name (db) instead, and when you need to reach a service on your host machine, use host.docker.internal on Docker Desktop.

§4Common Mistakes

MistakeWhat HappensFix
Using localhost to reach another container"connection refused"Use the container or service name on a shared network
Relying on the default bridge for name lookupName resolution failsCreate a user-defined network
Publishing the database port when only the app needs itThe database is exposed to your networkDo not publish it; let the app connect over the Docker network
Practice
  1. Put a database and a client container on a custom network and connect by name; then repeat on the default bridge and observe the difference.
  2. Run two containers that both listen on port 80, publishing them on host ports 8081 and 8082.
Key takeaways
  • Use user-defined networks for automatic DNS by container name.
  • Publish ports only for traffic from outside the network.
  • Inside a container, localhost is the container itself, not your machine or its neighbors.
