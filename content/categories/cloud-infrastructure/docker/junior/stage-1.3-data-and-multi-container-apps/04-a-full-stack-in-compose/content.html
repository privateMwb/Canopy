A Full Stack in Compose

A realistic Compose stack adds a cache, uses health checks so services start in a usable order, and mounts source code for a fast development loop.

§1Health Checks and Real Readiness

A healthcheck is a command Docker runs inside a container on an interval; the container is healthy once it succeeds. Combined with depends_on conditions, the app waits for what it actually needs:

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: devpass
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d app"]
      interval: 5s
      timeout: 3s
      retries: 10
  cache:
    image: redis:7
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10
  web:
    build: .
    ports: ["8080:3000"]
    environment:
      DATABASE_URL: postgres://postgres:devpass@db:5432/app
      REDIS_URL: redis://cache:6379
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
volumes:
  pgdata:

docker compose ps now shows each service's health. Even so, production code should retry its connections, because dependencies can restart at any time.

§2A Development Workflow

For local work, mount your source into the container so edits appear without rebuilding, and run a reloading dev server:

  web:
    build: .
    command: npm run dev
    volumes:
      - ./src:/app/src
    ports: ["8080:3000"]

Keep installed dependencies inside the image (do not bind-mount over node_modules), or use an anonymous volume for it so the host copy does not overwrite it. Later stages cover compose watch, which handles this more cleanly.

§3Inspecting the Whole Stack

docker compose up -d --build
docker compose ps                    # states and health
docker compose logs -f --tail=50     # all services interleaved
docker compose exec cache redis-cli
docker compose top                   # processes per container
Name the port you reach, not the one you publish Between services, always use the container port (cache:6379). The ports: entries only matter to your host. Do not publish the database or cache unless you need to connect from a tool on your own machine.

§4Common Mistakes

MistakeWhat HappensFix
No healthcheck on the databaseApp crashes at startup because Postgres is not readyAdd healthcheck and condition: service_healthy
Healthcheck command missing from the imageContainer stays unhealthy foreverUse a command the image actually ships, such as pg_isready
Bind-mounting the project over installed dependenciesThe host's empty or foreign node_modules replaces the container'sMount only the source folder, not the whole project
Practice
  1. Extend a web and database Compose file with Redis, add health checks to both, and watch docker compose ps as the stack starts.
  2. Stop the database with docker compose stop db, observe what your app does, then restart it and see whether the app recovers.
Key takeaways
  • Health checks plus condition: service_healthy make startup order reflect real readiness.
  • For development, bind-mount source code but keep dependencies in the image.
  • Services talk on container ports; publish only what your host needs.
