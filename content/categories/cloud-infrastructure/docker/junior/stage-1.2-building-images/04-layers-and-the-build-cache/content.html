Layers & the Build Cache

Docker caches each layer and reuses it until an instruction or the files it depends on change, so putting rarely changing steps first makes rebuilds fast.

§1How the Cache Decides

For each instruction, the builder asks: has this exact instruction, on top of this exact parent layer, with the same inputs, been built before? If so it reuses the result (you will see CACHED in the output). For COPY, the inputs are the contents of the copied files. Once one layer is rebuilt, every layer after it is rebuilt too, because their parent changed.

§2Order From Stable to Volatile

Compare two Dockerfiles for the same Python app:

# Slow: any source edit reinstalls every dependency
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "app.py"]
# Fast: dependencies reinstall only when requirements.txt changes
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]

In the second version, editing app.py invalidates only the final COPY; the slow dependency layer stays cached. The pattern is always the same: copy the dependency manifest, install, then copy the source.

§3Cache Pitfalls and Layer Hygiene

  • Combine commands that belong together, and clean up in the same RUN, so the deleted files never enter a layer: RUN apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/*.
  • Never put apt-get update on its own line; a cached stale package index will make a later install fail.
  • RUN commands are cached by their text, not their effect, so RUN git clone ... never re-runs on its own. Force a fresh build with docker build --no-cache.
docker build -t app .
docker build -t app .           # all CACHED
touch app.py && docker build -t app .   # only the last COPY onward reruns
Cache is a speed feature, not a correctness guarantee A cached RUN apt-get install or RUN curl | sh can quietly keep an old result for months. When a build behaves strangely, try --no-cache before debugging further.

§4Common Mistakes

MistakeWhat HappensFix

Deleting files in a later RUNImage stays the same size; the earlier layer still holds themDelete in the same RUN that created them

Practice
  1. Time a rebuild of your app after changing one source file, before and after reordering the Dockerfile.
  2. Build with --no-cache and compare the total time to a fully cached build.
Key takeaways
  • A changed layer invalidates every layer after it.
  • Order instructions from least to most frequently changing: base, dependency manifest, install, source.
  • Clean up inside the same RUN that created the mess, and use --no-cache when you suspect staleness.
