Logging & Debugging Containers

Containers should write logs to stdout and stderr, and Docker's logging drivers and debugging tools take it from there.

§1Logs Go to stdout

Docker captures what the main process writes to stdout and stderr. Do not write log files inside the container; log to the console and let the platform collect it:

docker logs api                       # everything so far
docker logs -f --since 10m --tail 200 api
docker logs -t api                    # with timestamps
docker compose logs -f api db

Many official images achieve this by symlinking their log files to /dev/stdout. Structured JSON logs make later searching far easier than free text.

§2Logging Drivers and Rotation

The default json-file driver stores logs on the host and, without rotation, grows forever:

docker run -d --log-opt max-size=10m --log-opt max-file=3 myapi
{
  "log-driver": "local",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}

The second block goes in /etc/docker/daemon.json to set a default for the whole host. Other drivers ship logs to journald, syslog, Fluentd, or cloud services. Note that with some non-default drivers docker logs may not work, so check how your driver behaves.

§3Debugging a Misbehaving or Minimal Container

docker inspect api                    # config, mounts, state, health log
docker events --since 10m             # what Docker did recently
docker exec -it api sh                # if the image has a shell
docker cp api:/app/error.log ./       # pull a file out
docker run --rm -it --entrypoint sh myapi   # override entrypoint to explore the image

For images with no shell, attach a debug sidecar that shares the target's namespaces:

docker run --rm -it --pid=container:api --net=container:api \
  --cap-add=SYS_PTRACE nicolaka/netshoot

You can then run ss, curl, tcpdump, and ps against the target container's network and processes without changing its image. Docker also offers docker debug in some editions for the same purpose.

A container that exits immediately has no shell to enter When a container crashes at start, exec is impossible. Read docker logs, then run the image with --entrypoint sh to explore its filesystem and test the command by hand.

§4Common Mistakes

MistakeWhat HappensFix
Writing logs to files inside the containerdocker logs is empty and the writable layer growsLog to stdout and stderr
No log rotationHost disk fills with JSON logsSet max-size and max-file, or use the local driver
Debugging with exec on a distroless image"executable file not found"Use a debug sidecar sharing the target's namespaces
Practice
  1. Run a container that logs a line every second and configure rotation so it keeps only three small files.
  2. Debug a running container using a netshoot sidecar to test connectivity to its dependencies.
Key takeaways
  • Log to stdout and stderr, and rotate logs on the host.
  • inspect, events, cp, and --entrypoint sh cover most investigations.
  • Debug minimal images with a sidecar that shares namespaces rather than changing the image.
