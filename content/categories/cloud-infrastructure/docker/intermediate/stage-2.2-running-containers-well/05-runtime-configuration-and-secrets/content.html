Runtime Configuration & Secrets

Configuration arrives from outside the image at run time, and credentials deserve a delivery method better than plain environment variables.

§1Twelve-Factor Configuration

An image should be identical in every environment, with behavior set by configuration supplied when it runs: environment variables, mounted files, or command arguments. Never build separate images for staging and production just to change a URL.

docker run -d -e LOG_LEVEL=info --env-file ./app.env myapi
docker run -d -v ./config/app.yaml:/etc/app/app.yaml:ro myapi

Environment variables suit simple settings. Mounted config files suit structured configuration, and are easy to swap per environment.

§2Why Environment Variables Are a Weak Place for Secrets

Environment values are exposed to docker inspect, appear in /proc/<pid>/environ, are inherited by child processes, and often get printed by crash dumps and debug endpoints. They are acceptable for development. For real credentials, use files.

§3Secrets as Files

Compose secrets mount a value as a file at /run/secrets/<name> in memory-backed storage:

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
secrets:
  db_password:
    file: ./secrets/db_password.txt

Many official images support the *_FILE convention for exactly this purpose. For your own code, read the secret from the file path at startup. In production, the source of the secret should be a manager (a cloud secret service, Vault, or your orchestrator) that injects the file, rather than a text file in a repository. Outside Compose and Swarm, mount a read-only file from a protected directory on the host, or have the application fetch the secret from a secrets service at startup using a short-lived credential.

Rotation is the real test A good secrets setup lets you change a credential without rebuilding images or editing code. If rotating a password requires a new image, the design has the secret in the wrong place.

§4Common Mistakes

MistakeWhat HappensFix
Credentials in the image (ENV, COPY .env)Anyone with the image can read themSupply them at run time, as files
Committing secrets/ filesCredentials permanently in Git historyIgnore the directory; use a secret manager
Logging the environment at startupSecrets end up in the log pipelineNever print raw config; redact sensitive keys
Practice
  1. Run Postgres with POSTGRES_PASSWORD_FILE and a Compose secret instead of an environment variable, and confirm docker inspect no longer shows the password.
  2. Change the password source without rebuilding any image.
Key takeaways
  • Build one image and configure it at run time.
  • Prefer mounted files over environment variables for credentials.
  • Design so a secret can rotate without a rebuild.
