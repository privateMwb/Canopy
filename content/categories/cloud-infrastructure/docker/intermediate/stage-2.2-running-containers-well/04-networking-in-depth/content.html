Networking in Depth

Beyond the default bridge, Docker offers user-defined networks with DNS and aliases, host networking, and none, each suited to different problems.

§1Network Drivers

DriverBehaviorUse when
bridge (user-defined)Private network per project with DNSAlmost always
hostContainer shares the host's network stackYou need raw performance or many ports (Linux only)
noneNo network except loopbackMaximum isolation for offline jobs
overlaySpans hosts (Swarm)Multi-host setups
macvlanGives a container its own LAN addressLegacy apps needing a real IP

With --network host, -p has no effect, because the container is already using the host's ports directly.

§2Isolation, Aliases, and Multiple Networks

A container can join several networks, which lets you build a layered topology where only the front end sees the outside:

docker network create frontend
docker network create backend --internal      # no route to the outside world
docker run -d --name db --network backend postgres:16
docker run -d --name api --network backend myapi
docker network connect frontend api            # api sits on both
docker run -d --name proxy --network frontend -p 80:80 nginx

In this layout the proxy reaches api, api reaches db, and the proxy cannot reach db at all. --internal blocks outbound internet access too, so use it for data stores that should never call out. In Compose, list each service's networks: and Compose creates them.

docker run -d --network appnet --network-alias search myservice

An alias is an additional DNS name for a container on that network, and several containers may share an alias for simple round-robin DNS.

§3DNS and Reaching the Host

Docker's embedded DNS answers names for containers on user-defined networks and forwards everything else to the host's resolvers. Inspect and test it:

docker exec api getent hosts db
docker network inspect backend --format '{{json .Containers}}'
docker run --add-host=host.docker.internal:host-gateway myapi   # reach the host (Linux)

host.docker.internal works out of the box on Docker Desktop; on Linux add the host-gateway mapping as shown.

Publishing is a firewall decision Every -p is a hole from the outside world to a container. For production, publish only the front door, and bind internal tools to 127.0.0.1. Remember that published ports bypass some host firewall rules on Linux, so verify what is actually reachable.

§4Common Mistakes

MistakeWhat HappensFix
Using --network host for conveniencePort clashes and no isolationPrefer bridge networks and publish only what you need
Same alias on unrelated servicesRequests land on the wrong containerUse unique names unless you want load spreading
Publishing a database to 0.0.0.0Database exposed to the networkDo not publish it, or bind to 127.0.0.1
Practice
  1. Build a three-tier layout where only the proxy is published and the database is on an --internal network, and prove the proxy cannot reach it.
  2. Resolve a container name with getent hosts from inside another container.
Key takeaways
  • User-defined bridge networks give DNS and isolation; host and none are special cases.
  • Multiple networks and --internal let you build least-privilege topologies.
  • Treat every published port as exposure and keep the list short.
