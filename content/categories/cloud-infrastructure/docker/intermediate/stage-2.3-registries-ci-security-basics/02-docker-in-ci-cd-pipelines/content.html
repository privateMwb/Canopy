Docker in CI/CD Pipelines

A good container pipeline builds, tests, scans, and publishes the same image quickly and repeatably.

§1The Pipeline

name: image
on: { push: { branches: [main] }, pull_request: {} }
permissions: { contents: read, packages: write }
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        if: github.event_name != 'pull_request'
        with: { registry: ghcr.io, username: "${{ github.actor }}", password: "${{ secrets.GITHUB_TOKEN }}" }
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: ${{ github.event_name != 'pull_request' }}
          tags: ghcr.io/${{ github.repository }}:sha-${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

Pull requests build and test but do not push, and merges to main push.

§2Caching in CI

CI runners start clean, so the local layer cache is empty. Use a remote cache: the CI provider's cache, or a registry cache (type=registry,ref=...). Order the Dockerfile for the cache and use cache mounts.

§3Testing the Image

Run tests inside the built image or against a running container.

docker run --rm app:test npm test
docker compose -f compose.test.yaml up --abort-on-container-exit --exit-code-from tests

Test what you ship. Unit tests may run in a test build stage, and a smoke test should start the final image and call its health endpoint.

§4Security in CI

Use short-lived credentials such as OIDC federation instead of long-lived registry passwords, and give the workflow the minimum permissions. Do not give pull requests from forks access to secrets.

The key insight CI should build the image once, test that exact image, and publish it only on trusted branches.

§5Common Mistakes

MistakeWhat HappensFix
No cache in CIEvery build takes ten minutesUse a remote build cache
Testing source but shipping a different imageBugs in packaging are never caughtSmoke test the final image
Long-lived registry passwords in CI secretsA leak gives permanent accessUse OIDC or short-lived tokens
Practice
  1. Create a pipeline that builds on pull requests without pushing and pushes only on main.
  2. Add a smoke test that starts the image and fails the build if the health check does not pass.
Key takeaways
  • CI builds, tests, and publishes the same image, pushing only from trusted branches.
  • Remote caches make clean runners fast.
  • Prefer short-lived credentials and minimal permissions.
