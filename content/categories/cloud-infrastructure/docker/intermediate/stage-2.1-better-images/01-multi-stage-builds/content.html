Multi-Stage Builds

A multi-stage Dockerfile uses several FROM stages so you can build with a full toolchain and ship only the finished artifact.

§1The Idea

Building software needs compilers, headers, and package managers. Running it usually needs none of them. A multi-stage build keeps them in a builder stage and copies just the output into a clean final stage; only the last stage becomes your image, and earlier stages are discarded.

FROM node:22 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html

The final image contains nginx and static files, not Node, node_modules, or your source. It is often a tenth of the single-stage size.

§2Named Stages and Targets

AS name labels a stage, COPY --from=name pulls files out of it, and --target lets you build up to a specific stage:

FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app .

FROM build AS test
RUN go test ./...

FROM gcr.io/distroless/static-debian12 AS final
COPY --from=build /out/app /app
USER nonroot
ENTRYPOINT ["/app"]
docker build --target test -t app:test .      # run the tests stage
docker build -t app:1.0 .                     # default: last stage

With BuildKit (the default builder), stages that the target does not depend on are skipped entirely, and independent stages build in parallel.

§3What to Copy Between Stages

Copy only what is needed at run time: a compiled binary, a dist folder, or a virtualenv or installed node_modules tree. You can also copy from an external image with COPY --from=nginx:1.27 /etc/nginx/nginx.conf /tmp/. Make sure runtime libraries match: a binary linked against glibc will not run on a musl-based Alpine final stage, which is why static Go binaries pair so well with minimal bases.

A stage is a throwaway, not a hiding place Secrets used in an earlier stage do not appear in the final image, but they do stay in the build cache and in any image you tag from that stage. Do not rely on stages as a secret-handling mechanism; use build secrets, covered shortly.

§4Common Mistakes

MistakeWhat HappensFix
Copying the whole builder filesystemFinal image is as large as beforeCopy only the artifact paths
Final stage missing runtime libraries"not found" or crashes at startChoose a base compatible with how the binary was built
Running tests only on the final imageBuild tools are not thereAdd a test stage and build it with --target
Practice
  1. Convert a single-stage Dockerfile for a compiled or bundled app into two stages and compare image sizes.
  2. Add a test stage and run it with docker build --target test.
Key takeaways
  • Build with the full toolchain, ship only the artifact in a minimal final stage.
  • AS, COPY --from, and --target give you named, selectable stages.
  • BuildKit skips unneeded stages and runs independent ones in parallel.
