Non-Root Users & Least Privilege

By default a container's process is root, and removing that default, along with unneeded capabilities and write access, sharply limits what a compromise can do.

§1Run as a Non-Root User

Root inside a container is not the same as root on the host, but it is still too powerful: it can write anywhere in the container and is one bug away from a worse situation. Create and switch to an unprivileged user:

FROM node:22-slim
WORKDIR /app
COPY --chown=node:node package*.json ./
RUN npm ci --omit=dev
COPY --chown=node:node . .
USER node
CMD ["node", "server.js"]
RUN groupadd -r app && useradd -r -g app -u 10001 app
USER 10001:10001          # a numeric ID is clearer to orchestrators and policies

Many official images already ship a non-root user (node, nonroot in distroless). Non-root users cannot bind ports below 1024 by default, so listen on 8080 and publish it however you like. Check mounted volume ownership, because a non-root process cannot write to a directory owned by root.

§2Read-Only Root Filesystem and tmpfs

Most services do not need to write to their own filesystem. Make it read-only and grant narrow writable spots:

docker run -d --read-only --tmpfs /tmp --tmpfs /run \
  -v appdata:/var/lib/app myapi
services:
  api:
    read_only: true
    tmpfs: [ /tmp ]

Attackers who gain code execution cannot drop tools onto a read-only filesystem, and the app is forced to be explicit about where it writes.

§3Drop Capabilities and Block Escalation

Linux capabilities split root's powers into pieces; Docker grants a default subset. Drop them all and add back only what you need:

docker run -d --cap-drop ALL --cap-add NET_BIND_SERVICE \
  --security-opt no-new-privileges:true myapi
services:
  api:
    cap_drop: [ ALL ]
    security_opt: [ "no-new-privileges:true" ]

no-new-privileges stops a process from gaining more privileges through setuid binaries. Avoid --privileged, which disables most protections, and never mount the Docker socket into an application container.

Make the secure setup the default setup Put USER, read-only mode, and dropped capabilities in your base templates and Compose files so teams inherit them. Security that requires every developer to remember extra flags will not survive.

§4Common Mistakes

MistakeWhat HappensFix
Leaving the process as rootA compromised app has maximum power inside the containerAdd USER with a numeric ID
Using --privileged to "make it work"Nearly all isolation is removedFind and add the specific capability or device needed
Non-root user with root-owned volumepermission denied writing dataSet ownership with chown in the image or an init step
Practice
  1. Convert an existing Dockerfile to run as a non-root user and fix any permission errors it exposes.
  2. Run it with --read-only --cap-drop ALL, then add back only what the app proves it needs.
Key takeaways
  • Run as a non-root numeric user, with a read-only filesystem and tmpfs for scratch space.
  • Drop all capabilities and add back the minimum; enable no-new-privileges.
  • Never use --privileged or the Docker socket as shortcuts.
