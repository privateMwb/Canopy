Union Filesystems & Image Layers

An image is a stack of read-only filesystem layers plus a manifest, and a union filesystem presents them as one tree with a writable layer on top.

§1The OCI Image Format

Images follow the OCI image specification, which defines three JSON-and-tarball parts:

  • Layers: compressed tar archives, each a set of filesystem changes, identified by a content digest.
  • Config: JSON describing the default command, environment, user, and the ordered list of layer digests.
  • Manifest: JSON pointing to the config and layers by digest. An index (manifest list) points to several manifests, one per platform.
docker save myapp:1.0 -o myapp.tar && mkdir x && tar -xf myapp.tar -C x
ls x/blobs/sha256 && cat x/index.json
skopeo inspect --raw docker://docker.io/library/alpine:3.20

Everything is addressed by hash, so identical layers are stored once and shared between images, and a registry can skip uploading layers it already holds.

§2Union Mounts and Copy-on-Write

At run time the engine stacks the layers using a union filesystem. On Linux the usual driver is overlayfs (the overlay2 storage driver): read-only lowerdir layers, one writable upperdir, and a merged view.

mount | grep overlay
docker inspect t --format '{{json .GraphDriver.Data}}'
# LowerDir=...:..., UpperDir=..., WorkDir=..., MergedDir=...

Reading a file finds it in the top-most layer that has it. Copy-on-write: modifying a file from a lower layer first copies the whole file up to the writable layer. Deleting one creates a whiteout marker in the upper layer that hides the lower file without removing it. New files appear only in UpperDir, and docker diff lists exactly that layer.

§3Why Layers Behave the Way They Do

This explains rules you learned as habits:

  • Deleting a file in a later layer does not shrink the image, because the earlier layer still contains it.
  • Changing a big file by one byte copies the entire file into a new layer.
  • Putting rarely changing content first maximizes shared layers and cache hits.
  • Ordering by change frequency also minimizes bytes pulled on update, since only changed layers transfer.
docker history --no-trunc myapp:1.0
docker image inspect myapp:1.0 --format '{{json .RootFS.Layers}}'

Newer Docker versions can use the containerd image store, which stores images in OCI form and enables multi-platform images in the local store; the on-disk layout differs but the model above is the same.

Secrets in any layer are permanent Since layers are immutable content-addressed tarballs, a secret copied in one layer and "deleted" in the next is still extractable from the first. Removing it requires rebuilding without it, and rotating the secret.

§4Common Mistakes

MistakeWhat HappensFix
Editing large files in many layersEach change duplicates the full fileMake one change in one layer, or avoid large mutable files in images
Assuming rm shrinks an imageThe lower layer retains the dataClean up in the same RUN, or use multi-stage builds
Relying on tags rather than digests for layersTags can move, digests cannotUse digests to identify exact content
Practice
  1. Export an image with docker save, unpack it, and identify the config, manifest, and layer blobs.
  2. Run a container, change one existing file and delete another, and match both changes to docker diff and the overlay UpperDir contents.
Key takeaways
  • An image is layers, a config, and a manifest, all addressed by digest in the OCI format.
  • Overlayfs presents read-only layers plus one writable layer, with copy-on-write and whiteouts.
  • Layer behavior explains why cleanup, ordering, and secrets rules exist.
