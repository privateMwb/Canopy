The Runtime Stack: containerd, runc & OCI

The Docker CLI hands work to a daemon, which delegates to containerd, which delegates to runc, and runc finally creates the namespaces and cgroups for your process.

§1The Layers of the Stack

docker CLI -> dockerd -> containerd -> containerd-shim -> runc -> your process
ComponentJob
docker CLIParses commands, talks to the daemon's API
dockerdImages, builds, networks, volumes, and the user-facing API
containerdImage pull and storage, container lifecycle, snapshots
containerd-shimStays alive as the container's parent so containerd or dockerd can restart without killing it
runcA short-lived OCI runtime that sets up namespaces, cgroups, and execs your command

The same containerd sits under Kubernetes (via the CRI), which is why images and container behavior carry over. Alternatives to runc, such as crun, gVisor's runsc, and Kata, can plug in at the bottom of the same stack.

§2The OCI Runtime Specification

runc consumes an OCI bundle: a root filesystem directory plus a config.json describing the process, mounts, namespaces, capabilities, cgroup limits, and seccomp profile. You can generate and run one by hand:

mkdir -p bundle/rootfs && cd bundle
docker export $(docker create alpine) | tar -C rootfs -xf -
runc spec                          # writes a default config.json
sudo runc run demo                 # starts a container from the bundle

Editing config.json changes the container: set "terminal": false, change args, add a namespace, or lower a limit. Docker produces exactly this kind of file for each container.

§3Following a docker run

  1. The CLI sends a create request to dockerd over its API socket (/var/run/docker.sock).
  2. dockerd resolves the image, asks containerd to prepare a snapshot (the overlay mount), and sets up networking.
  3. containerd starts a shim, and the shim invokes runc create then runc start with a generated bundle.
  4. runc creates the namespaces and cgroup, configures mounts and capabilities, applies seccomp, and executes your entrypoint, then exits.
  5. The shim remains as the parent, relaying stdio and the exit code.
ps -ef --forest | grep -E 'dockerd|containerd|runc|sleep'
docker info --format '{{.DefaultRuntime}} {{json .Runtimes}}'
sudo ctr -n moby containers ls       # containerd's view of Docker's containers
The socket is root Whoever can write to /var/run/docker.sock can ask the daemon to start a container with the host's root filesystem mounted. Treat socket access as root access, and never hand it to untrusted code.

§4Common Mistakes

MistakeWhat HappensFix
Blaming "Docker" for a Kubernetes container problemThe runtime may be containerd and runc, not dockerdIdentify the actual runtime with crictl info or node configuration
Expecting a runc process to stay aroundrunc exits after starting the containerLook for the shim and your application process
Giving containers the Docker socketContainer can control the hostUse socket proxies with limited APIs or avoid the pattern
Practice
  1. Trace a running container from the CLI process through dockerd, containerd, the shim, and your process using ps --forest.
  2. Export a root filesystem, generate a bundle with runc spec, and run it, then edit config.json to change the command.
Key takeaways
  • The stack is CLI, dockerd, containerd, a shim, and runc, with runc doing the kernel work and then exiting.
  • OCI specs define both images and the runtime bundle, so components are replaceable.
  • The Docker socket is a root-equivalent interface.
