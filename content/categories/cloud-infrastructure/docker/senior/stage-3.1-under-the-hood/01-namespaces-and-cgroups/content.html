Namespaces & cgroups

Namespaces control what a process can see and cgroups control what it can use, and together they are what a container is.

§1Namespaces: What a Process Can See

A namespace wraps a global kernel resource so processes inside get their own private view of it. Linux has several kinds:

NamespaceIsolatesEffect inside a container
pidProcess IDsThe main process is PID 1; host processes are invisible
netNetwork stackOwn interfaces, routing table, and ports
mntMount pointsOwn root filesystem view
utsHostname and domainOwn hostname
ipcSystem V IPC, POSIX queuesSeparate shared memory
userUser and group IDsContainer root can map to an unprivileged host user
cgroupThe cgroup tree viewSees its own cgroup as the root
timeSelected system clocksOptional offset of boot and monotonic clocks
lsns                                    # list namespaces on the host
ls -l /proc/<pid>/ns                    # a process's namespace handles
sudo nsenter --target <pid> --net ip addr   # run a command inside a container's netns
unshare --pid --fork --mount-proc bash  # make your own PID namespace

§2cgroups: What a Process Can Use

Control groups account for and limit CPU, memory, I/O, and process counts for a group of processes. Modern systems use cgroup v2, one unified hierarchy mounted at /sys/fs/cgroup. Docker's flags map directly to files:

docker run -d --name t --memory 256m --cpus 0.5 --pids-limit 100 alpine sleep 3600
cat /sys/fs/cgroup/system.slice/docker-<container-id>.scope/memory.max
cat /sys/fs/cgroup/system.slice/docker-<container-id>.scope/cpu.max
cat /sys/fs/cgroup/system.slice/docker-<container-id>.scope/pids.max

Writing a number to memory.max is all that "setting a memory limit" means. When usage hits it, the kernel reclaims memory and then invokes the OOM killer inside that cgroup, which is how exit code 137 is produced. memory.events and cpu.stat (with its nr_throttled counter) are where to look when diagnosing limits. The exact path depends on the cgroup driver (systemd or cgroupfs).

§3Seeing It From Both Sides

The same process is visible with two different identities:

docker run -d --name t alpine sleep 3600
docker exec t ps                          # PID 1 is "sleep 3600"
docker inspect t --format '{{.State.Pid}}'    # e.g. 48213
ps -p 48213 -o pid,cmd                    # the same process, host PID
cat /proc/48213/cgroup

There is no container object in the kernel; the runtime assembles a normal process with a set of namespaces and a cgroup, and /proc shows both.

Limits are not visible to everything Many tools read /proc/meminfo or CPU counts, which show the host's totals, not the cgroup's. Programs that size pools from those values (older JVMs, some native libraries) can overcommit inside a limited container. Check that your runtime reads the cgroup files.

§4Common Mistakes

MistakeWhat HappensFix
Treating a container as a VM-like boundaryKernel bugs and misconfigurations can cross itLayer additional controls such as seccomp, user namespaces, and non-root
Reading memory from free inside a containerHost totals, not your limitRead memory.max and memory.current
Assuming cgroup v1 pathsFile names and layout differ in v2Check stat -fc %T /sys/fs/cgroup and use v2 paths
Practice
  1. Start a container with a memory and PID limit, locate its cgroup directory on the host, and read the limit files.
  2. Use unshare to start a shell in a new PID and mount namespace, and confirm it sees itself as PID 1.
Key takeaways
  • Namespaces provide the view; cgroups provide the limits and accounting.
  • A container is an ordinary process with a namespace set and a cgroup, visible in /proc.
  • Limit enforcement and diagnosis happen through cgroup files, not the Docker daemon.
