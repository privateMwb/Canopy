Observability & Performance of Containers

Containers hide resource problems behind limits, so observability must look at the cgroup, not just the application.

§1What to Measure

  • CPU usage and throttling: a container may use little CPU on average and still be throttled in bursts.
  • Memory: working set against the limit, and OOM kill counts.
  • Restarts and exit codes.
  • Network and disk I/O.
  • Application metrics (latency, errors, saturation) alongside resource metrics.
docker stats --no-stream
cat /sys/fs/cgroup/<group>/cpu.stat             # nr_throttled, throttled_usec
cat /sys/fs/cgroup/<group>/memory.events        # oom, oom_kill

§2CPU Throttling

With a CPU limit of 1 CPU, the container can run for 100 ms of CPU time per 100 ms period. A multi-threaded app can burn its quota in 25 ms and then stall for 75 ms, causing latency spikes even at low average CPU. Watch nr_throttled and consider raising or removing CPU limits while keeping requests.

§3Memory and OOM

Memory limits count page cache and kernel memory too. Runtimes that cache aggressively or have a heap larger than the limit get killed. Tune the runtime to the limit.

docker run -m 512m -e JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75" myjava

§4Tools

  • cAdvisor exposes per-container metrics, scraped by Prometheus.
  • Node exporter reports host metrics.
  • Tracing and profiling (OpenTelemetry, continuous profilers) find where time goes.
  • Centralized logs keyed by container, image, and version.

§5Noisy Neighbors

Containers on one host share the CPU caches, memory bandwidth, disk, and network. One heavy workload can slow others even within limits. Isolate critical services, use requests and limits wisely, and watch host-level saturation.

The key insight Low average CPU with high latency often means throttling. Look at the throttling counters before blaming the code.

§6Common Mistakes

MistakeWhat HappensFix
Watching only average CPUThrottling hides behind low averagesTrack nr_throttled
Setting runtime heap equal to the memory limitThe OOM killer strikesLeave headroom, such as 70 to 75 percent
Observing the host but not each containerYou cannot attribute resource useCollect per-container metrics
Practice
  1. Run a multi-threaded CPU test under a CPU limit and show throttling in cpu.stat while average CPU looks low.
  2. Build a Prometheus and cAdvisor dashboard with memory working set, throttling, and restarts.
Key takeaways
  • Measure container-level CPU throttling, memory, restarts, and I/O.
  • Throttling and OOM kills explain many "mysterious" latency and crash problems.
  • Plan for noisy neighbors on shared hosts.
