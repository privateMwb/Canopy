Single Host, Compose, or an Orchestrator?

One well-run host with Compose carries a surprising amount of production, and the real question is which specific needs push you toward an orchestrator.

§1What One Host Does Well

A single modern server can run dozens of services, handle substantial traffic, and be rebuilt from a repository. Compose gives you declarative config, restart policies, health checks, and rolling by hand with up -d. You gain simplicity: one machine to understand, debug, back up, and pay for. Many products never need more.

§2The Needs That Push You Beyond It

NeedSingle host + ComposeOrchestrator (for example Kubernetes or Nomad)
Survive host failureManual rebuild or standbyAutomatic rescheduling onto other nodes
Zero-downtime deploysPossible with a proxy and careBuilt-in rolling updates and readiness gates
Scale beyond one machineNoYes, across a cluster
AutoscalingNoYes (pods, nodes)
Many teams, many servicesGets tangledNamespaces, quotas, RBAC
Secrets, config, service discoveryManual or DIYBuilt-in APIs
Operational costLowHigh: control plane, upgrades, networking, expertise

Decide based on specific requirements such as an availability target, traffic spikes, or the number of teams, not on fashion. An orchestrator replaces some problems with others: more moving parts, more YAML, and an on-call burden.

§3The Middle Ground

Options exist between Compose and full Kubernetes: Docker Swarm (simple, in maintenance mode but still functional), Nomad, managed container services such as AWS ECS/Fargate, Google Cloud Run, or Azure Container Apps, and a PaaS layered on a host. Managed services shift cluster operations to the provider, often the best compromise for small teams.

# Evaluate honestly: write the requirement, then the cheapest option that meets it
Requirement: 99.9% monthly availability (~43 min downtime)
Option A:    1 host + Compose + restore from backup (~2h recovery)   -> does not meet
Option B:    2 hosts + load balancer + Compose on each               -> meets, modest complexity
Option C:    managed container service                               -> meets, lowest ops burden
Availability needs drive the choice Convert "we need high availability" into a number and a recovery time. Once you know the downtime you can actually afford, the cheapest architecture that meets it usually becomes obvious.

§4Common Mistakes

MistakeWhat HappensFix
Adopting Kubernetes for one small serviceOperational overhead dwarfs the benefitStart with Compose or a managed container service
Staying on one host after availability needs riseHost failure becomes an outageIntroduce redundancy deliberately when requirements say so
Choosing by résumé or hypeUnnecessary complexityWrite requirements first and compare options against them
Practice
  1. For a service you run, write its availability requirement as a number and decide which of the three architectures meets it at the lowest complexity.
  2. List three operational tasks an orchestrator would automate for you, and three it would add.
Key takeaways
  • A single host with Compose is a legitimate production platform for many workloads.
  • Move to an orchestrator when specific needs (failure survival, scale, multi-team) require it.
  • Managed services often beat self-run clusters for small teams.
