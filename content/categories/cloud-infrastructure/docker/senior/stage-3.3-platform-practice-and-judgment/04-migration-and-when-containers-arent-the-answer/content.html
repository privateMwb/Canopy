Migration & When Containers Aren't the Answer

Containerizing a legacy application is a staged process, and some workloads are better left on virtual machines or bare metal.

§1Migrating a Legacy Workload

Move in small, reversible steps:

  1. Inventory the app: runtime and OS dependencies, configuration files, ports, hard-coded paths, scheduled jobs, local state, and licenses.
  2. Make it configurable: read settings from environment or mounted files, log to stdout, and handle SIGTERM.
  3. Containerize as-is first (the "lift and shift"), accepting an imperfect Dockerfile to get it running.
  4. Externalize state: move uploads, sessions, and local databases to volumes or managed services.
  5. Run beside the old system, compare behavior, then shift traffic gradually (for example 5%, 25%, 100%) with an easy rollback.
  6. Improve afterwards: slim images, add health checks, tests, and pipelines.
# a pragmatic first Dockerfile for a legacy app
FROM eclipse-temurin:8-jre
WORKDIR /opt/app
COPY app.war ./
COPY conf/ /opt/app/conf/
VOLUME /opt/app/data
EXPOSE 8080
CMD ["java", "-jar", "app.war"]

Plan for stateful pieces separately: databases are often better as managed services or dedicated hosts than as containers you operate yourself.

§2Poor Fits and Hard Cases

  • Stateful systems with heavy I/O (large databases) can run in containers on volumes, but the benefit is small and the operational care is the same as without containers.
  • GUI or desktop applications and software needing special hardware or kernel modules are awkward, and GPUs need runtime support.
  • Different kernel required (Windows apps on a Linux host, a custom kernel) means a VM or Windows containers.
  • Strict multi-tenant isolation of hostile code calls for VMs or sandboxed runtimes.
  • Tiny, stable, rarely changed systems gain little; the migration cost can exceed the return.
  • Latency-critical, tuned-to-the-metal systems may need CPU pinning, huge pages, and direct hardware access that containers can provide but at the cost of their portability.

§3Deciding With Evidence

Ask what concrete problem containers would solve: environment drift, slow onboarding, deploy repeatability, density, or CI. If you cannot name one that matters, and the system is stable, leaving it alone is a valid, defensible choice. Pilot with the most painful service, measure the outcome, then decide how far to go.

A container is a packaging choice, not a goal The goal is reliable delivery and operation of software. If a VM or a managed service achieves that with less effort, choose it and revisit when circumstances change.

§4Common Mistakes

MistakeWhat HappensFix
Rewriting while migratingTwo risky changes at onceLift and shift first, then refactor
Containerizing the database by reflexSame operational burden, new failure modesUse managed databases or dedicated hosts unless you have a reason
Big-bang cutoverNo easy rollbackShift traffic gradually with a rollback plan
Practice
  1. Take a legacy application you know and write its migration plan as the six steps above, listing the first three risks.
  2. Name one workload at your organization that should not be containerized yet, with reasons.
Key takeaways
  • Migrate in small steps: configure, containerize as-is, externalize state, shift traffic, then improve.
  • Containers are a poor fit for some stateful, hardware-bound, kernel-specific, or hostile-multitenant workloads.
  • Choose containers for a named benefit, not as an end in themselves.
