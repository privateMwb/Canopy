The Container Security Model & Isolation Limits

Containers share the host kernel, so their security is a stack of kernel restrictions layered on one boundary, and understanding each layer shows where it can fail.

§1The Layers of Defense

A container process is constrained by several overlapping mechanisms:

LayerRestrictsDefault in Docker
NamespacesWhat the process can seeOn
cgroupsWhat it can consumeOptional limits
CapabilitiesWhich root powers it hasReduced default set
seccompWhich system calls it may makeDefault profile blocks dozens of syscalls
AppArmor / SELinuxFiles and operations by policyDefault profile where available
Non-root userPrivileges inside the containerOff: root unless configured
Read-only filesystemWrites to the container FSOff

No single layer is a wall. Together they raise the cost of an attack, but all of them depend on the one kernel the container shares with the host.

§2seccomp and Capabilities in Practice

seccomp filters system calls with a profile. Docker's default blocks dangerous ones (such as mount, reboot, and kernel module loading), and you can tighten or replace it:

docker run --security-opt seccomp=./profile.json myapi
docker run --security-opt seccomp=unconfined myapi     # removes the filter. Avoid.
docker run --cap-drop ALL --cap-add NET_BIND_SERVICE myapi
capsh --print                                          # inspect capabilities

Generate a minimal profile by tracing which syscalls your app uses in tests, then enforce that list. Treat seccomp=unconfined, --privileged, --pid=host, --net=host, mounting /, and mounting the Docker socket as escape-enabling settings that need explicit justification.

§3What an Escape Looks Like

Container escapes come from a few categories:

  • Misconfiguration: a privileged container, a mounted Docker socket, or a writable host path lets the process simply act on the host.
  • Runtime or kernel vulnerabilities: flaws in the kernel or in runc (past examples include a runc file-descriptor leak, CVE-2019-5736, and the overlayfs and cgroup release-agent issues) let code in a container affect the host.
  • Shared resources: side channels and noisy neighbors, which leak information or availability rather than control.

Most real incidents are misconfiguration, which is controllable. Kernel and runtime bugs are mitigated by patching quickly, running as non-root, using user namespaces, and sandboxed runtimes for untrusted code.

docker run --rm --privileged alpine sh -c 'ls /dev | head'   # sees host devices
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock docker:cli ps

The second command shows why a mounted socket is a full takeover: the container can launch any other container with any mount.

Decide who the adversary is Containers are good isolation for your own code from your other code, with defense in depth. They are not sufficient alone for hostile tenants running arbitrary code; that requires VM-level or sandboxed isolation, covered later in this stage.

§4Common Mistakes

MistakeWhat HappensFix
Treating the default profile as sufficient for untrusted codeKernel attack surface remains largeUse sandboxed runtimes or VMs for hostile workloads
Using --privileged for convenienceAll protections disabledGrant the specific capability or device only
Delaying kernel and runtime updatesKnown escapes remain exploitablePatch hosts and the container runtime on a schedule
Practice
  1. List the capabilities of a default container and of one started with --cap-drop ALL, and explain each missing one.
  2. Demonstrate what a mounted Docker socket allows from inside a throwaway test container, then describe how you would detect it with a policy check.
Key takeaways
  • Container security is namespaces, cgroups, capabilities, seccomp, and MAC policy over a shared kernel.
  • Most escapes are misconfigurations you can forbid with policy.
  • Match the isolation mechanism to the threat; containers are not VM-strength boundaries.
