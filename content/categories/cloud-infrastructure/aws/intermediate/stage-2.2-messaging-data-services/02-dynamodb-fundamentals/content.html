DynamoDB Fundamentals

DynamoDB is a managed key-value and document database that scales almost without limit, but only if you design the table around your queries first.

§1Tables, Items, and Keys

A table holds items (like rows) with flexible attributes. Every item has a partition key, optionally a sort key, and the combination must be unique. The partition key's hash decides where data lives, so reads and writes by key are fast at any size.

aws dynamodb create-table --table-name Orders \
  --attribute-definitions AttributeName=CustomerId,AttributeType=S \
                          AttributeName=OrderId,AttributeType=S \
  --key-schema AttributeName=CustomerId,KeyType=HASH \
               AttributeName=OrderId,KeyType=RANGE \
  --billing-mode PAY_PER_REQUEST

§2Design From Access Patterns

Unlike a relational database, you cannot freely join or filter on any column. You list your queries first, then shape keys to serve them.

Access patternKey design
Get an order by idPK = CustomerId, SK = OrderId
List a customer's orders, newest firstSame table, SK sorted by date-prefixed id
Find orders by status across customersGlobal secondary index on Status

Query reads items within one partition key efficiently; Scan reads the whole table and should be avoided in production paths.

§3Capacity, Indexes, and Consistency

  • On-demand billing suits unpredictable traffic; provisioned with auto scaling suits steady load.
  • Global secondary indexes offer alternative keys, are eventually consistent, and consume their own capacity.
  • Reads are eventually consistent by default; strongly consistent reads cost twice as much and are available on the base table.
  • Choose partition keys with high cardinality to avoid hot partitions.
  • Use TTL to expire items automatically.
Queries first, schema second In DynamoDB the table design is the query design. Adding a new access pattern later often means a new index or a data migration, so collect patterns before creating keys.

§4Common Mistakes

MistakeWhat HappensFix
Using Scan for routine readsSlow and costly as the table growsQuery by key or index
Low-cardinality partition key (e.g. status)Hot partition and throttlingPick a key with evenly distributed values
Modeling like a relational schemaNeeds joins DynamoDB doesn't haveList access patterns and design keys around them
Practice
  1. Write the five queries an order system needs, then design keys and one index to serve them.
  2. Create the table in on-demand mode and load data with a script.
Key takeaways
  • DynamoDB is fast by key; design starts from the access patterns.
  • Query uses keys efficiently; Scan reads everything.
  • Partition key choice drives performance and cost.
