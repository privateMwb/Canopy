Multi-AZ Design

Multi-AZ design means no single data center failure takes the application down, which requires every tier to span zones.

§1Every Tier, Every Layer

LayerMulti-AZ approach
Load balancerSubnets in at least two AZs (the ALB does this itself)
ComputeASG spanning subnets in multiple AZs
DatabaseRDS Multi-AZ, or Aurora with replicas in other AZs
Shared filesEFS stores across AZs; EBS does not
NAT / egressOne NAT gateway per AZ to avoid a cross-AZ dependency
CacheReplication groups with replicas in other AZs

§2Capacity and Failure Behavior

If one of two AZs fails, the remaining one must absorb the load. Size so that losing an AZ does not exhaust capacity: with 2 AZs, each should be able to carry the full load, or keep headroom and a scaling plan; with 3 AZs, each needs to carry about half.

  • Test by taking instances out of one AZ and watching health and latency.
  • Cross-AZ traffic costs money and adds latency; keep chatty calls within an AZ where you can, but never at the cost of a single point of failure.
  • AWS Fault Injection Service can simulate AZ-level failure.

§3Finding Single Points of Failure

For each component ask:
- What happens if the AZ holding it disappears?
- Is it stateful? Where is the state?
- Is anything pinned to one AZ (one NAT, one EBS volume, one subnet)?
- Do I know how long recovery takes?
Multi-AZ is not multi-region Spreading across AZs defends against a data center failure, not against a regional outage, a bad deploy, or data corruption. Those need other controls.

§4Common Mistakes

MistakeWhat HappensFix
One NAT gateway for all AZsAZ failure cuts off outbound access everywhereUse a NAT gateway per AZ
App spans AZs but the database does notDatabase AZ loss means full outageEnable Multi-AZ on the database
Never testing failoverAssumptions fail during a real eventRun a drill and measure the result
Practice
  1. Review one architecture and list every single-AZ dependency.
  2. Fail over an RDS Multi-AZ instance and measure how long the app was affected.
Key takeaways
  • Each layer needs its own multi-AZ answer: compute, data, files, and egress.
  • Plan capacity so surviving AZs can absorb the load.
  • Multi-AZ protects against data center loss, not every failure.
