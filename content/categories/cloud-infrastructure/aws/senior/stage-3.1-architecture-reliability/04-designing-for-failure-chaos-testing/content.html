Designing for Failure & Chaos Testing

Resilient systems assume components will fail, and they are proven resilient by causing failures deliberately.

§1Static Stability and Graceful Degradation

A statically stable design keeps working when a dependency fails without needing to take new actions. Example: pre-provision enough capacity across AZs so losing one needs no scaling event, because the control plane may be the thing that is impaired.

  • Prefer the data plane (serving requests) over the control plane (creating or changing resources) in recovery paths.
  • Degrade gracefully: serve cached or partial results if recommendations are down, rather than an error page.
  • Use timeouts, retries with exponential backoff and jitter, and circuit breakers so one failing dependency doesn't exhaust everything.
delay = random(0, min(cap, base * 2 ** attempt))   # exponential backoff with full jitter

§2Bulkheads and Limits

Isolate failure domains: separate queues, thread pools, accounts, or cells so a problem in one area stays contained. Cell-based architecture serves a slice of customers per cell, so a bad deploy or noisy tenant hits a fraction of users. Retries without limits cause retry storms that turn a small fault into an outage.

§3Chaos Testing

AWS Fault Injection Service runs controlled experiments such as stopping instances, injecting API errors, or disrupting network to an AZ.

Hypothesis: if one AZ's instances are stopped, p99 latency stays under 500 ms
Action:     FIS stops all instances tagged app=web in eu-west-1a
Stop condition: CloudWatch alarm on 5xx rate > 2%
Outcome:    record, fix gaps, repeat

Define a steady-state metric, form a hypothesis, set automatic stop conditions, start small in non-production, then widen the blast radius.

Experiments need a stop button Every chaos experiment needs an alarm that halts it automatically, a small blast radius, and a team that knows it is running. The goal is learning, not outages.

§4Common Mistakes

MistakeWhat HappensFix
Retrying immediately and unboundedlyRetry storm amplifies the outageUse backoff with jitter and retry budgets
Recovery that depends on launching new resourcesControl plane problems block recoveryPre-provision capacity; stay statically stable
Chaos tests in production without stop conditionsSelf-inflicted outageAdd alarms, small scope, and approvals
Practice
  1. Define a steady-state metric and run a small FIS experiment in a test environment.
  2. Add backoff with jitter and a circuit breaker to one outbound call.
Key takeaways
  • Statically stable designs keep working without needing recovery actions.
  • Backoff with jitter, circuit breakers, and bulkheads contain failures.
  • Chaos experiments need hypotheses, small scope, and automatic stop conditions.
