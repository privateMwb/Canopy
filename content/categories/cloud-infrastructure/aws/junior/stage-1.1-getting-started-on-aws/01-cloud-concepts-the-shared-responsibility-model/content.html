Cloud Concepts & the Shared Responsibility Model

The cloud means renting compute, storage, and services on demand instead of buying hardware, and the shared responsibility model says exactly which parts of security you still own.

§1What the Cloud Changes

Traditional IT means buying servers up front, waiting weeks for delivery, and sizing for peak load. In the cloud you rent capacity by the second or hour, provision it with an API call, and give it back when you are done. Capital expense becomes operating expense, and capacity planning becomes a continuous adjustment instead of a one-time bet.

The standard service models describe how much AWS runs for you:

ModelYou manageAWS example
IaaSOS, runtime, app, dataEC2, EBS, VPC
PaaSApp and dataElastic Beanstalk, RDS
SaaS / fully managedConfiguration and dataWorkMail, S3 (storage as a service)

§2The Shared Responsibility Model

AWS is responsible for security of the cloud: data centers, hardware, the network fabric, and the virtualization layer. You are responsible for security in the cloud: your data, identities, permissions, network rules, and the guest operating system on anything you launch.

ServiceAWS securesYou secure
EC2Hardware, hypervisor, facilitiesGuest OS patches, firewall rules, IAM, data
RDSHardware, OS and database patching (managed)Who can connect, parameters, data, backups you rely on
S3Durability and the storage platformBucket policies, public access settings, encryption choices
LambdaServers, OS, runtime patchingYour code, its permissions, its data

The more managed the service, the more AWS takes on, but data and access are always yours.

§3Why It Matters in Practice

Nearly every public cloud breach involves the customer side of the line: a bucket made public, a leaked access key, a database open to the internet. AWS can keep the building and the hypervisor safe, but it cannot know that a bucket was meant to be private.

# Customer-side questions to ask about any resource
Who can reach it over the network?
Who can call its API (which IAM principals)?
Is the data encrypted, and who holds the keys?
Is there a log of who touched it?
The key insight Ask "is this the part AWS runs or the part I configure?" for every service you adopt. If you configure it, you are the one who can misconfigure it.

§4Common Mistakes

MistakeWhat HappensFix
Assuming AWS backs up and protects your data automaticallyDeleted or corrupted data is goneEnable versioning, snapshots, and backups yourself
Thinking managed means no security workOpen database ports or public bucketsStill configure access, network, and encryption
Leaving the guest OS unpatched on EC2Known vulnerabilities stay exploitablePatch or use managed services and automation
Practice
  1. Take three services (EC2, RDS, Lambda) and list who patches the OS for each.
  2. For S3, write down two things AWS does and two things you must configure.
Key takeaways
  • Cloud trades up-front hardware cost for on-demand, pay-as-you-go capacity.
  • AWS secures the cloud itself; you secure what you put and configure in it.
  • Data and access are your responsibility in every service, however managed.
