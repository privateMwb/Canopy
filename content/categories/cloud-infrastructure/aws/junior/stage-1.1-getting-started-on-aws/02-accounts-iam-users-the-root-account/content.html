Accounts, IAM Users & the Root Account

The root user owns the account and can do anything, so the first job is to lock it away and create an identity you use for daily work instead.

§1Root vs. Everyday Identities

When you create an AWS account you sign in with an email and password. That is the root user: it cannot be restricted by IAM policies and can close the account or change the support plan. Treat it as a break-glass identity, not a login.

  • Enable MFA on root immediately (an authenticator app or a hardware key).
  • Do not create access keys for the root user.
  • Use a shared mailbox or distribution list as the root email so it survives staff changes.
  • Use root only for the few tasks that require it, such as changing the account's email or closing the account.

§2IAM Users, Groups, and Policies

IAM (Identity and Access Management) is where you define who can do what. A user is a person or program, a group is a set of users, and a policy is a JSON document granting or denying actions.

aws iam create-group --group-name admins
aws iam attach-group-policy --group-name admins \
  --policy-arn arn:aws:iam::aws:policy/AdministratorAccess
aws iam create-user --user-name alice
aws iam add-user-to-group --group-name admins --user-name alice

Attach permissions to groups, not individual users, so access follows role in the team rather than one-off decisions.

§3Least Privilege and MFA

Start with no permissions and add what is needed. Even your admin user should have MFA. For people, newer setups use IAM Identity Center instead of long-lived IAM users, covered later; for learning on a single account, an MFA-protected IAM user is fine.

aws iam create-virtual-mfa-device --virtual-mfa-device-name alice-mfa \
  --outfile qr.png --bootstrap-method QRCodePNG
Root is not a daily driver The root user's power is the point and the danger. A leaked root password with no MFA means total account loss, including the ability to delete your backups.

§4Common Mistakes

MistakeWhat HappensFix
Using root for daily workEvery action runs with unrestricted powerCreate an admin IAM user or SSO identity and use that
No MFA on root or adminsA stolen password is a full compromiseRequire MFA for every human identity
Creating access keys for rootKeys can leak into code or laptopsDelete any root keys; never create them
Practice
  1. Create a new test account (or use a sandbox), enable MFA on root, and verify you can sign in as an admin IAM user.
  2. Write a policy that allows only s3:ListBucket on one bucket and attach it to a test user.
Key takeaways
  • Root has unrestricted power: protect it with MFA and stop using it day to day.
  • Grant permissions through groups and policies, starting from least privilege.
  • Every human identity should have MFA.
