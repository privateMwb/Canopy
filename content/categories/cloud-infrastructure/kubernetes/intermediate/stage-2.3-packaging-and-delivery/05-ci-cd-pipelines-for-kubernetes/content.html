CI/CD Pipelines for Kubernetes

A CI/CD pipeline for Kubernetes turns a commit into a tested image and a controlled deployment, with promotion between environments that is automatic where it is safe and gated where it is not.

§1The Pipeline Stages

commit -> build & test -> build image -> scan -> push -> update manifests -> deploy dev
                                                                         -> promote staging -> promote prod

CI (continuous integration) covers everything up to a tested, scanned, uniquely tagged image. CD (continuous delivery) covers getting that image running, and decides who or what approves each step.

§2Building the Image

# GitHub Actions (abbreviated)
- name: Build and push
  uses: docker/build-push-action@v5
  with:
    push: true
    tags: ghcr.io/myorg/web:${{ github.sha }}

Tag with the commit SHA so every image is traceable to source and never overwritten. Add steps for unit tests, image vulnerability scanning (Trivy, Grype), and, in stricter setups, an SBOM and a signature.

§3Two Ways to Deploy

Push: the pipeline runs helm upgrade or kubectl apply against the cluster.

  • Simple, but the CI system needs cluster credentials, and the pipeline becomes a high-value target.

Pull (GitOps): the pipeline commits the new image tag to the config repository, and Argo CD or Flux applies it.

  • No cluster credentials in CI, a Git history of every deployment, and drift detection.
# the last CI step in a GitOps flow
yq -i '.images[0].newTag = "'"$GITHUB_SHA"'"' overlays/dev/kustomization.yaml
git commit -am "deploy web $GITHUB_SHA to dev" && git push

§4Promotion and Safety Checks

Promote the same image through environments rather than rebuilding it. Between environments add checks:

  • Smoke tests or integration tests run against the new deployment.
  • kubectl rollout status --timeout=... fails the pipeline when a rollout does not become healthy.
  • Manual approval gates for production, or automated gates based on metrics.
  • An easy rollback: revert the commit, or helm rollback.

If CI must reach a cloud cluster directly, prefer short-lived credentials through OIDC federation with the cloud provider over long-lived kubeconfig secrets.

Build once, promote many If production runs a rebuilt image rather than the exact image that passed staging, you have not tested what you shipped.

§5Common Mistakes

MistakeWhat HappensFix
Rebuilding the image for each environmentProduction runs untested bitsBuild once and promote the same digest or tag
Long-lived cluster admin credentials in CIA leaked secret hands over the clusterUse OIDC, scoped roles, or a pull-based GitOps agent
Pipeline marks success when the rollout failsBroken versions look "deployed"Wait on rollout status and fail loudly
Practice
  1. Sketch a pipeline for one app showing where tests, scanning, image push, and promotion occur.
  2. List the credentials each stage needs, and design them to be as narrow and short-lived as possible.
Key takeaways
  • CI produces a tested, traceable image; CD moves it through environments.
  • Pull-based GitOps keeps cluster credentials out of CI.
  • Promote one immutable artifact, and verify each rollout before continuing.
