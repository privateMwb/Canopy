GitOps with Argo CD or Flux

GitOps makes a Git repository the source of truth for the cluster and uses an in-cluster agent to continuously make reality match it.

§1The Idea

In the push model, a CI job runs kubectl apply with cluster credentials. In GitOps, an agent inside the cluster pulls from Git and applies changes itself. Four principles: the desired state is declarative, versioned in Git, pulled automatically, and continuously reconciled.

Benefits:

  • Auditability: every change is a commit with an author and a review.
  • Rollback: revert the commit.
  • Drift correction: manual edits to the cluster are detected and can be reverted.
  • Security: CI no longer needs admin credentials to the cluster.

§2Argo CD and Flux

Two CNCF projects dominate:

ToolStyle
Argo CDWeb UI and an Application resource per app; strong visualization of sync state
FluxA set of controllers configured with Kubernetes objects (GitRepository, Kustomization, HelmRelease); no built-in UI

An Argo CD application:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: shop-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/shop-config
    targetRevision: main
    path: overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: shop
  syncPolicy:
    automated:
      prune: true
      selfHeal: true

prune deletes resources removed from Git, and selfHeal reverts manual changes in the cluster. Flux expresses the same with a GitRepository source and a Kustomization that applies a path from it.

§3A Typical Repository Layout

app-source-repo      # code and Dockerfile; CI builds and pushes an image
config-repo          # manifests per environment (Helm values or Kustomize overlays)

Separating code from configuration is common. CI builds the image, then updates the image tag in the config repository (by pull request or an image-automation tool), and the GitOps agent deploys it.

§4Secrets in GitOps

Plain Secrets cannot sit in Git. Common answers are Sealed Secrets or SOPS (encrypted values in Git), or the External Secrets Operator (Git holds only a reference to a secret in a vault).

Git becomes the control plane Whoever can merge to the config repository can change production. Protect it with branch protection, required reviews, and restricted write access.

§5Common Mistakes

MistakeWhat HappensFix
Making manual kubectl changes with selfHeal onThey are reverted within secondsChange Git, not the cluster
Putting plaintext Secrets in the config repoCredentials live in history foreverUse sealed, SOPS-encrypted, or external secrets
One repo and branch for every environment with no review gateA bad merge reaches production at onceUse per-environment paths or branches and protect production
Practice
  1. Install Argo CD or Flux on a local cluster, point it at a repository containing one Deployment, and change replicas via a commit.
  2. Make a manual change to the live object and watch the agent revert it.
Key takeaways
  • GitOps stores desired state in Git and pulls it into the cluster with a reconciling agent.
  • Argo CD and Flux provide sync, pruning, and drift correction.
  • Secrets and repository permissions need explicit design.
