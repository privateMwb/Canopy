Network Policies

By default every pod can talk to every other pod; network policies let you restrict that to the connections an app actually needs.

§1The Default Is Open

A fresh cluster has a flat network: any pod can reach any pod, in any namespace. If one pod is compromised, the attacker can probe everything. A NetworkPolicy selects pods and specifies which traffic is allowed to or from them.

Enforcement depends on the network plugin. NetworkPolicy objects are accepted by every cluster, but they only take effect if the CNI supports them (Calico, Cilium, and others do; some basic setups do not). Test that a policy actually blocks traffic.

§2How Policies Behave

  • A pod with no policy selecting it accepts all traffic.
  • Once any policy selects a pod for ingress, only traffic explicitly allowed by some policy is permitted. Policies are additive: they only allow, never deny, and multiple policies are combined as a union.
  • Ingress and egress are controlled separately via policyTypes.

§3Default Deny, Then Allow

Start by denying everything in a namespace, then add allowances:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: shop
spec:
  podSelector: {}           # all pods in the namespace
  policyTypes: ["Ingress"]
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-from-api
  namespace: shop
spec:
  podSelector:
    matchLabels: { app: db }
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: api }
        - namespaceSelector:
            matchLabels: { team: payments }
      ports:
        - protocol: TCP
          port: 5432

Under from, items in the list are ORed. Putting podSelector and namespaceSelector in the same list item makes them ANDed, which is a frequent source of mistakes.

§4Controlling Egress

Egress rules limit outbound traffic, such as allowing only DNS and one external API:

egress:
  - to:
      - namespaceSelector: {}
        podSelector:
          matchLabels: { k8s-app: kube-dns }
    ports:
      - { protocol: UDP, port: 53 }
      - { protocol: TCP, port: 53 }

When you deny egress by default, remember DNS, or every name lookup breaks.

Test with a real connection After applying a policy, run kubectl exec into an allowed pod and a disallowed pod and attempt the connection. A policy you have not tested is a guess.

§5Common Mistakes

MistakeWhat HappensFix
Assuming policies are enforcedThe CNI ignores them and traffic stays openVerify support and test blocking
Egress deny that forgets DNSEvery service name fails to resolveExplicitly allow DNS to kube-dns
Confusing OR and AND in fromAccess is wider or narrower than intendedRead indentation carefully and test each case
Practice
  1. Apply default deny to a namespace, confirm a connection fails, then add one allow rule and confirm it works.
  2. Write an egress policy that allows only DNS and HTTPS to a specific namespace.
Key takeaways
  • Pod networking is open by default; NetworkPolicy narrows it.
  • Policies are additive allow-lists, enforced only by a supporting CNI.
  • Start with default deny, add precise allows, and always test.
