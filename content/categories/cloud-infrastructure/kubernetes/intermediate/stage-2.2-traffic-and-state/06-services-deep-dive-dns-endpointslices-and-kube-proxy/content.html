Services Deep Dive: DNS, EndpointSlices & kube-proxy

A Service name resolves through DNS to a virtual IP, and kube-proxy rules plus EndpointSlices turn that IP into a real pod, and knowing each step makes network bugs tractable.

§1Step 1: DNS

When a pod looks up web, its resolver (configured by the kubelet) asks CoreDNS. A pod's /etc/resolv.conf contains search domains and ndots:5:

search shop.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5

Names with fewer than five dots are tried against each search domain first. That is why web works, but also why external names like api.example.com generate several failed lookups before succeeding. Adding a trailing dot (api.example.com.) or lowering ndots reduces extra DNS load.

CoreDNS returns the Service's ClusterIP for a normal Service, or the pod IPs for a headless one.

§2Step 2: The Virtual IP

A ClusterIP is not assigned to any network interface. No process listens on it. It is a virtual IP that only has meaning because of packet rewriting rules on every node.

§3Step 3: EndpointSlices

Kubernetes tracks which pods back a Service in EndpointSlice objects, each holding up to 100 endpoints by default, with each pod's IP, readiness, and node. The older Endpoints object is being phased out in favor of slices because slices scale better.

kubectl get endpointslices -l kubernetes.io/service-name=web
kubectl get endpoints web

Only Ready pods appear as ready endpoints, which is how readiness probes keep traffic away from unhealthy pods.

§4Step 4: kube-proxy

kube-proxy runs on every node, watches Services and EndpointSlices, and programs the node's kernel so traffic to a ClusterIP is rewritten (DNAT) to one chosen pod IP:

ModeHow it works
iptables (long-standing default)A chain of rules chooses a backend randomly; cost grows with the number of services
ipvsUses the kernel load balancer with hash tables and more algorithms
nftablesA newer kernel packet filter backend that is intended to scale better than iptables

Some network plugins, notably Cilium, can replace kube-proxy entirely using eBPF. A later Senior lesson inspects these rules directly.

§5Tracing a Failure

kubectl run dbg --rm -it --image=busybox -- sh
nslookup web                         # DNS step
wget -qO- http://web                 # whole path
kubectl get endpointslices           # are there ready endpoints?
SymptomLikely layer
nslookup failsDNS: CoreDNS down, bad name, or egress policy blocking port 53
Name resolves, connection hangsRules or policies: kube-proxy issue, or NetworkPolicy
Resolves but connection refusedPods ready but app not listening on targetPort
Resolves, no endpointsSelector mismatch or no ready pods
Check from the inside Always test from a pod in the cluster. Behavior from your laptop passes through a different path and can hide or invent problems.

§6Common Mistakes

MistakeWhat HappensFix
Debugging only from outside the clusterYou test a different path than your pods useUse a temporary debug pod in the same namespace
Ignoring ndotsExternal lookups multiply and DNS gets slowUse fully qualified names or tune dnsConfig
Assuming a ClusterIP is pingableIt is virtual and often does not answer ICMPTest with the real protocol and port
Practice
  1. From a debug pod, run nslookup web.shop.svc.cluster.local and read /etc/resolv.conf.
  2. Scale a Deployment to zero and watch its EndpointSlice become empty.
Key takeaways
  • Service resolution runs DNS, then a virtual IP, then node rules selecting a ready endpoint.
  • EndpointSlices list ready pod addresses; kube-proxy turns them into forwarding rules.
  • Locating the failing step (DNS, endpoints, rules, app) makes network debugging systematic.
