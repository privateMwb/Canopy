Sidecars, Init Containers & Ambassadors

A pod can hold several containers that cooperate, and a few well-known patterns describe how to split responsibilities among them.

§1Why Multi-Container Pods

Containers in one pod share a network namespace (so localhost works between them), can share volumes, and have the same lifecycle on the same node. That is the right fit for helpers that exist only to serve one app container. Keep the one main concern per container rule, and add a second container only when the helper must live and die with the app.

§2Sidecar

A sidecar runs alongside the main container for its whole life, extending it without changing its code. Examples: a log shipper tailing files from a shared volume, a service mesh proxy that handles TLS and retries, a config reloader, or a Cloud SQL proxy.

spec:
  containers:
    - name: app
      image: myorg/app:1.0
      volumeMounts: [{ name: logs, mountPath: /var/log/app }]
    - name: log-shipper
      image: fluent/fluent-bit:3.0
      volumeMounts: [{ name: logs, mountPath: /var/log/app, readOnly: true }]
  volumes:
    - name: logs
      emptyDir: {}

Historically, sidecars had two problems: they started in no guaranteed order, and a Job pod never finished while its sidecar kept running. Modern Kubernetes versions fix this with native sidecars: an init container with restartPolicy: Always starts before the app, runs for the pod's lifetime, and is stopped after the app exits.

initContainers:
  - name: proxy
    image: myorg/proxy:2.1
    restartPolicy: Always        # makes it a native sidecar

§3Init Containers

These run to completion before the app starts, in order. Use them for tasks that must finish first: waiting for a dependency, running a schema migration, fetching configuration, or setting file permissions on a volume.

§4Ambassador

An ambassador is a proxy container that represents a remote service to the app. The app talks to localhost:6379, and the ambassador handles sharding, connection pooling, authentication, or choosing between environments. This keeps connection logic out of the app.

§5Adapter

An adapter translates the app's output into a standard form, for example converting custom metrics into the Prometheus format, or normalizing log formats.

PatternDirectionExample
SidecarExtends the appLog shipper, mesh proxy
InitPrepares before the appMigration, wait-for-dependency
AmbassadorApp to outside worldConnection-pooling proxy
AdapterOutside world to app's outputMetrics format converter

§6Costs to Remember

Every extra container adds CPU and memory to every replica, and a failure in one container can affect the pod's readiness. Pod resource requests are the sum across containers.

Couple tightly or not at all If the helper could run as its own Deployment and be shared, it probably should. Use a sidecar when it must share the network, files, or lifecycle with one specific app instance.

§7Common Mistakes

MistakeWhat HappensFix
Putting unrelated services in one podThey cannot scale or deploy independentlyUse separate Deployments connected by Services
Sidecar blocking a Job from completingThe Job never finishesUse native sidecars, or have the main container signal the helper to stop
Ignoring the sidecar's resource costTotal requests balloon across replicasSet requests for each container and measure
Practice
  1. Build a pod with an app that writes logs to a shared emptyDir and a second container that reads them.
  2. Write an init container that waits for a Service name to resolve before the app starts.
Key takeaways
  • Containers in a pod share network and volumes and live and die together.
  • Sidecar, init, ambassador, and adapter patterns divide responsibilities cleanly.
  • Native sidecars solve startup order and Job completion problems on current versions.
