Requests, Limits & QoS Classes

Requests and limits decide where a pod fits, how much it can burst, and which pods are sacrificed first when a node runs short.

§1Two Numbers, Two Jobs

  • Requests are used by the scheduler for placement and define a pod's guaranteed share.
  • Limits are enforced by the kernel through cgroups at runtime.

The two resources behave differently when a limit is hit:

ResourceOver the limitCompressible?
CPUThe container is throttled: it gets less time, but keeps runningYes
MemoryThe kernel OOM-kills the container (exit code 137, reason OOMKilled)No

Memory cannot be taken back once given, which is why exceeding a memory limit is fatal while CPU is merely slowed.

§2QoS Classes

Kubernetes labels each pod with a Quality of Service class, derived from its requests and limits, and uses it to pick victims during node pressure.

ClassConditionEviction order
GuaranteedEvery container has CPU and memory requests equal to limitsEvicted last
BurstableAt least one request or limit set, but not GuaranteedMiddle
BestEffortNo requests or limits at allEvicted first
kubectl get pod web -o jsonpath='{.status.qosClass}'

When a node runs low on memory, the kubelet evicts pods, starting with ones using more than they requested, and BestEffort pods go before Burstable. Beyond kubelet eviction, the Linux OOM killer can also act if memory runs out suddenly.

§3Choosing Values

A practical starting point:

  • Memory: set the limit slightly above the observed peak, and the request near typical usage. For critical services, requests equal to limits make behavior predictable.
  • CPU: set a request based on average usage. Many teams omit CPU limits because throttling can hurt latency even when the node has idle CPU, while keeping requests so scheduling stays fair. This is a debated practice, so measure before adopting it.

Namespace-wide guardrails come from a LimitRange (defaults and bounds per container) and a ResourceQuota (a total cap for the namespace).

kubectl describe node worker-1      # see Allocated resources: requests vs. capacity
kubectl top pod --containers
Requests are a promise to the scheduler A node full of requests is "full" even if its real CPU is idle. Over-requesting wastes money; under-requesting causes noisy neighbors and evictions.

§4Common Mistakes

MistakeWhat HappensFix
Memory limit set to typical, not peakSpikes cause OOMKilled restartsBase the limit on peak plus headroom
Requests far above real usageNodes look full while mostly idle, so you pay for wasteRight-size from metrics
Relying on BestEffort for important podsThey are the first to be evictedSet requests, or use Guaranteed for critical workloads
Practice
  1. Create one pod of each QoS class and verify with jsonpath on .status.qosClass.
  2. Run a container that allocates memory past its limit and find OOMKilled in its status.
Key takeaways
  • Requests drive scheduling; limits are enforced, with CPU throttled and memory killed.
  • QoS classes (Guaranteed, Burstable, BestEffort) determine eviction order.
  • Base values on measurement, and use LimitRange and ResourceQuota for guardrails.
