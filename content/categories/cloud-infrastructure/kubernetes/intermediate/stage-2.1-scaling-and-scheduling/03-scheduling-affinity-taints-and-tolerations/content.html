Scheduling: Affinity, Taints & Tolerations

Scheduling rules let you steer pods toward the right nodes, keep them apart, and reserve nodes for special workloads.

§1How the Scheduler Chooses

For each unscheduled pod the scheduler first filters out nodes that cannot host it (not enough resources, wrong labels, taints), then scores the rest and picks the best. The tools below add constraints to the filtering and scoring steps.

§2nodeSelector and Node Affinity

The simplest rule matches node labels:

spec:
  nodeSelector:
    disktype: ssd

Node affinity is the expressive version. required... is a hard rule; preferred... is a soft hint with a weight.

affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: topology.kubernetes.io/zone
              operator: In
              values: ["us-east-1a", "us-east-1b"]
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 50
        preference:
          matchExpressions:
            - { key: node.kubernetes.io/instance-type, operator: In, values: ["m6i.xlarge"] }

§3Pod Affinity and Anti-Affinity

These place pods relative to other pods. Anti-affinity spreads replicas across failure domains:

affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels: { app: web }
        topologyKey: kubernetes.io/hostname      # at most one web pod per node

Strict anti-affinity can leave pods Pending when there are fewer nodes than replicas. For even spreading, topology spread constraints are usually the better tool:

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels: { app: web }

§4Taints and Tolerations

Affinity attracts pods to nodes. Taints do the opposite: a node repels every pod that does not tolerate the taint.

kubectl taint nodes gpu-1 hardware=gpu:NoSchedule
tolerations:
  - key: hardware
    operator: Equal
    value: gpu
    effect: NoSchedule
EffectMeaning
NoScheduleNew pods without a toleration are not placed here
PreferNoScheduleThe scheduler tries to avoid the node
NoExecuteAlso evicts running pods that do not tolerate it
A toleration permits, it does not attract A pod that tolerates a GPU taint may still land on an ordinary node. To dedicate nodes, combine a taint (keep others out) with node affinity or a selector (pull yours in).

§5Common Mistakes

MistakeWhat HappensFix
Required anti-affinity with too few nodesExtra replicas stay PendingUse topology spread constraints or a preferred rule
Tolerations without node selectionThe pod can still run anywherePair tolerations with node affinity for dedicated nodes
Misspelled label keysNo node matches and the pod is PendingCheck kubectl get nodes --show-labels and the Events
Practice
  1. Label a node, then use nodeSelector to pin a pod to it, and read the scheduling event.
  2. Taint a node with NoSchedule and observe that a plain pod avoids it while a tolerating pod can land there.
Key takeaways
  • The scheduler filters then scores; affinity, taints, and spread constraints shape both steps.
  • Topology spread constraints distribute replicas across zones and nodes.
  • Dedicating nodes takes a taint plus affinity or a selector.
