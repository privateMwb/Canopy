Horizontal Pod Autoscaling

The Horizontal Pod Autoscaler changes a Deployment's replica count to match load, so capacity follows demand without anyone editing a number.

§1What the HPA Does

The HorizontalPodAutoscaler (HPA) is a controller that runs a loop every 15 seconds by default: read a metric, compare it to a target, and adjust replicas on a Deployment (or StatefulSet). It scales out (more pods) rather than up (bigger pods).

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

kubectl autoscale deployment web --cpu-percent=70 --min=3 --max=20 creates a simple one from the command line.

§2The Arithmetic

The core formula is:

desiredReplicas = ceil( currentReplicas * currentMetric / targetMetric )
# 4 pods at 90% CPU, target 70%  ->  ceil(4 * 90/70) = 6 pods

Utilization is measured relative to the pod's CPU request, not the node. A pod with no CPU request gives the HPA nothing to divide by, so the autoscaler cannot work. This is the most common reason an HPA shows <unknown>.

§3Requirements

  • A metrics source. CPU and memory come from metrics-server, an add-on that must be installed (many managed clusters include it).
  • Resource requests on the containers being scaled.
  • Custom or external metrics (queue length, requests per second) need an adapter such as Prometheus Adapter or KEDA, which exposes them through the metrics APIs.
kubectl get hpa
kubectl describe hpa web          # shows current vs target and recent scaling events
kubectl top pods                  # confirms metrics-server works

§4Stability Controls

Scaling up should be quick and scaling down cautious, or replicas flap. The behavior field tunes this:

behavior:
  scaleDown:
    stabilizationWindowSeconds: 300    # use the highest recommendation of the last 5 minutes
    policies:
      - type: Percent
        value: 50
        periodSeconds: 60
  scaleUp:
    policies:
      - type: Pods
        value: 4
        periodSeconds: 60

New pods also take time to start and become ready, so an HPA lags a sudden spike. Keep a sensible minReplicas for known baseline load.

Do not fight the HPA If an HPA manages a Deployment, remove replicas from the manifest you apply, or each apply resets the count and the HPA keeps undoing it.

§5Common Mistakes

MistakeWhat HappensFix
No CPU request on the podsUtilization cannot be computed and the HPA reports unknownSet requests before enabling autoscaling
Scaling on CPU for an I/O-bound appCPU stays low while latency climbsScale on a metric that tracks load, such as requests per second or queue depth
minReplicas: 1 for a critical serviceOne pod is a single point of failure and slow to reactUse at least two or three replicas in production
Practice
  1. Install metrics-server on a local cluster, create an HPA with a 50% CPU target, and generate load with a busy-loop pod.
  2. Compute by hand the replica count for 5 pods at 140% utilization with a target of 70%.
Key takeaways
  • The HPA adds or removes replicas based on metrics compared with a target.
  • It needs metrics-server and resource requests to work on CPU or memory.
  • Stabilization and scaling policies prevent flapping.
