Disruption Budgets & Safe Node Maintenance

Disruption budgets keep enough replicas alive while nodes are drained for upgrades, so planned maintenance does not cause outages.

§1Two Kinds of Disruption

  • Involuntary: hardware failure, kernel panic, cloud host loss. You cannot ask permission.
  • Voluntary: you or the platform choose it, such as draining a node for an upgrade, a cluster autoscaler removing a node, or a rollout.

A PodDisruptionBudget (PDB) only constrains voluntary disruptions that go through the eviction API. It will not stop a node crashing.

§2Writing a PDB

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web
spec:
  minAvailable: 2          # or use maxUnavailable: 1
  selector:
    matchLabels:
      app: web

With three replicas and minAvailable: 2, an eviction is allowed only while at least two pods remain Ready afterwards. Use either minAvailable or maxUnavailable, and prefer maxUnavailable (it scales with replica count).

kubectl get pdb
# NAME   MIN AVAILABLE   ALLOWED DISRUPTIONS
# web    2               1

§3Draining a Node

kubectl cordon worker-2        # mark unschedulable; running pods stay
kubectl drain worker-2 --ignore-daemonsets --delete-emptydir-data
# ... do maintenance ...
kubectl uncordon worker-2

drain cordons the node and evicts pods one by one, respecting PDBs. If an eviction would violate a budget, the drain waits and retries until it is safe, for example once a replacement pod elsewhere becomes Ready.

§4Pitfalls That Block Drains

  • minAvailable equal to the replica count (or maxUnavailable: 0) allows zero disruptions, so drains hang forever.
  • A single-replica Deployment with a PDB of minAvailable: 1 can never be evicted.
  • Pods that are already unhealthy count against the budget; unhealthyPodEvictionPolicy: AlwaysAllow lets broken pods be evicted.

Budgets protect only if there are enough replicas, and replicas must be spread across nodes (see the previous lesson). Three replicas on one node mean a drain still takes the service down.

Budgets and spread work together A PDB limits how many pods can go at once; spread constraints make sure those pods are not all on the node being drained.

§5Common Mistakes

MistakeWhat HappensFix
PDB that allows zero disruptionsNode drains and cluster upgrades hangLeave room for at least one pod to be evicted
Replicas packed on one nodeDraining that node removes them allAdd anti-affinity or topology spread
Expecting a PDB to protect against crashesIt only governs voluntary evictionsUse replicas, probes, and zone spreading for resilience
Practice
  1. Create a three-replica Deployment with maxUnavailable: 1, then drain a node and watch evictions proceed one at a time.
  2. Set a PDB that allows zero disruptions and observe the drain stall.
Key takeaways
  • PDBs limit voluntary evictions; they do not stop failures.
  • cordon and drain empty a node safely while honoring budgets.
  • Budgets, replicas, and spreading must be designed together.
