RBAC & ServiceAccounts

RBAC decides who may do what to which objects, and ServiceAccounts give workloads their own identity so they never borrow a human's.

§1The Four Objects

ObjectScopePurpose
RoleOne namespaceA set of permissions
ClusterRoleCluster-widePermissions on cluster-scoped resources, or reusable across namespaces
RoleBindingOne namespaceGrants a Role or ClusterRole to subjects within that namespace
ClusterRoleBindingCluster-wideGrants a ClusterRole across the whole cluster

Permissions are purely additive; there are no deny rules. A request is allowed if any binding grants it.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: shop
  name: pod-reader
rules:
  - apiGroups: [""]               # "" is the core group
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: shop
  name: read-pods
subjects:
  - kind: Group
    name: shop-developers
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

roleRef is immutable; to change it, delete and recreate the binding.

§2Subjects and Identity

Kubernetes has no user objects. Users and groups come from the authentication layer: client certificates, OIDC tokens from your identity provider, or cloud IAM integration. A ServiceAccount is the one identity Kubernetes does manage, used by pods.

kubectl create serviceaccount reporter -n shop
kubectl auth can-i list pods -n shop --as=system:serviceaccount:shop:reporter
kubectl auth can-i --list -n shop --as=jane@example.com

kubectl auth can-i and --as impersonation are the quickest way to test and debug permissions.

§3Workload Identity

Pods authenticate to the API server using a bound ServiceAccount token: short-lived, audience-scoped, and injected as a projected volume that the kubelet refreshes. Since version 1.24, long-lived token Secrets are no longer created automatically.

spec:
  serviceAccountName: reporter
  automountServiceAccountToken: false    # for pods that never call the Kubernetes API

To access cloud resources, avoid static keys: IRSA / EKS Pod Identity (AWS), Workload Identity (GKE), and Azure Workload Identity exchange a pod's ServiceAccount token for cloud credentials scoped to that identity.

§4Dangerous Permissions

These are effectively privilege escalation or broad access:

  • * verbs or resources, and cluster-admin bindings.
  • get, list, or watch on secrets, since list reveals contents.
  • create on pods (a pod can mount secrets or run privileged, subject to admission).
  • The escalate, bind, and impersonate verbs.
  • nodes/proxy and writes to roles/rolebindings.

Membership in the system:masters group bypasses RBAC entirely, so certificates issued with it are as powerful as root on the cluster.

Least privilege in practice Grant roles to groups from your identity provider, not to individuals; bind in namespaces where possible; review bindings regularly. Tools such as kubectl get clusterrolebindings -o wide, rbac-tool, and audit logs help find overbroad grants.

§5Common Mistakes

MistakeWhat HappensFix
Binding cluster-admin to workloadsA compromised pod controls the clusterCreate narrow Roles for exactly the verbs needed
Using the default ServiceAccount for everythingUnrelated workloads share permissionsOne ServiceAccount per workload, with token automount off by default
Granting secrets read broadlyAnyone with it reads every credential in scopeLimit to specific resource names, or avoid and use a secrets manager
Practice
  1. Create a ServiceAccount that can only read pods in one namespace, and verify with auth can-i.
  2. Audit your cluster for ClusterRoleBindings to cluster-admin and justify or remove each.
Key takeaways
  • RBAC is additive: Roles define permissions, bindings grant them to users, groups, or ServiceAccounts.
  • Pods use short-lived bound tokens, and cloud workload identity avoids static keys.
  • Secrets access, pod creation, and escalation verbs are the permissions to guard.
