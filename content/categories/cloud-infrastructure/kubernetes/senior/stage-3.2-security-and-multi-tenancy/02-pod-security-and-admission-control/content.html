Pod Security & Admission Control

Pod Security Standards define what a safe pod looks like, and admission control is where the cluster enforces rules before objects are stored.

§1Pod Security Standards

Three cumulative profiles describe pod hardening:

ProfileIntentExamples of what it blocks
privilegedUnrestrictedNothing
baselinePrevents known privilege escalationsPrivileged containers, host namespaces, hostPath volumes, dangerous capabilities
restrictedCurrent hardening best practiceRunning as root, privilege escalation, missing seccomp profile, non-dropped capabilities

Pod Security Admission, built into the API server since version 1.25 (replacing PodSecurityPolicy), enforces them per namespace through labels:

kubectl label namespace shop \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted

enforce rejects violating pods, warn shows a message to the user, and audit records the violation. A common rollout is warn and audit first, fix findings, then enforce.

§2A Restricted-Compliant Pod

securityContext:
  runAsNonRoot: true
  seccompProfile:
    type: RuntimeDefault
containers:
  - name: app
    image: myorg/app:1.0
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]

Most violations come from images that run as root and from missing drop: ALL.

§3Admission Control

After authentication and authorization, a request goes through admission controllers: built-in plugins, then mutating webhooks (which can change the object, such as injecting a sidecar), then schema validation, then validating webhooks (which can only accept or reject).

Ways to add your own policy:

ApproachNotes
ValidatingAdmissionPolicyBuilt in and stable since 1.30; rules written in CEL, with no webhook to run
KyvernoPolicy engine whose policies are Kubernetes YAML; can validate, mutate, and generate resources
OPA GatekeeperPolicies in Rego, with constraint templates
Custom webhookMaximum flexibility, but you must run it reliably
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: require-team-label
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ["apps"]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["deployments"]
  validations:
    - expression: "has(object.metadata.labels) && 'team' in object.metadata.labels"
      message: "Deployments must have a 'team' label"

A policy also needs a ValidatingAdmissionPolicyBinding to take effect.

§4Webhook Risks

A webhook sits in the request path of every matching API call. Set a short timeout, choose failurePolicy deliberately (Fail is safer but can block the cluster when the webhook is down, Ignore keeps working but skips the check), and exclude the webhook's own namespace and kube-system so it cannot lock itself out.

Policy as guardrails, not gates Start in audit mode, publish exceptions with owners and expiry dates, and give developers clear error messages. Rules nobody can satisfy get bypassed.

§5Common Mistakes

MistakeWhat HappensFix
Enforcing restricted immediatelyMany existing workloads fail to startRoll out with warn and audit first
Webhook with failurePolicy: Fail and no HAWebhook outage blocks all matching changesRun multiple replicas, exclude system namespaces, set timeouts
Relying only on admission checksRunning pods created earlier are not re-evaluatedScan existing workloads and use audit reports
Practice
  1. Label a test namespace with enforce=restricted, try to run nginx as root, and fix the manifest until it is accepted.
  2. Write a ValidatingAdmissionPolicy that rejects containers without resource requests.
Key takeaways
  • Pod Security Standards (privileged, baseline, restricted) are enforced per namespace through Pod Security Admission.
  • Admission runs mutating then validating checks before storage, with CEL policies, Kyverno, or Gatekeeper.
  • Webhooks are availability risks, so design their failure modes.
