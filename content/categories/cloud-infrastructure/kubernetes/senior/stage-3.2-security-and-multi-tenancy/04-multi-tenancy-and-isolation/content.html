Multi-Tenancy & Isolation

Multi-tenancy means several teams or customers share a cluster, and the real work is knowing exactly what namespaces do and do not isolate.

§1Soft and Hard Tenancy

  • Soft multi-tenancy: tenants are different teams in one company who trust each other not to be malicious. The goal is to prevent accidents and noisy neighbors.
  • Hard multi-tenancy: tenants are mutually untrusting, such as customers running their own code. Namespaces alone are not enough; you need stronger isolation or separate clusters.

§2What a Namespace Gives You

A namespace is a scope for names, RBAC, quotas, and policy. By itself it does not isolate:

DimensionNamespace aloneAdd
API accessNot isolated by defaultRBAC Roles bound per namespace
NetworkAny pod can reach any podNetworkPolicy default deny
Compute fairnessOne tenant can consume everythingResourceQuota, LimitRange, PriorityClass
Node kernelPods share the node kernelPod security, sandboxed runtimes, dedicated nodes
Cluster-scoped objectsCRDs, ClusterRoles, StorageClasses, and webhooks are sharedRestrict who can create them

§3Controls to Apply Per Tenant

apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a
  namespace: team-a
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 64Gi
    limits.memory: 96Gi
    persistentvolumeclaims: "20"
    services.loadbalancers: "2"
    count/pods: "200"
---
apiVersion: v1
kind: LimitRange
metadata:
  name: defaults
  namespace: team-a
spec:
  limits:
    - type: Container
      default: { memory: 512Mi }
      defaultRequest: { cpu: 100m, memory: 256Mi }

Combine with: RBAC limited to the tenant's namespaces, default-deny NetworkPolicies, Pod Security restricted, policy that forces resource requests and approved registries, and per-tenant ServiceAccounts and secrets.

§4Stronger Isolation

  • Dedicated node pools with taints and tolerations, so tenants do not share kernels.
  • Sandboxed runtimes (gVisor, Kata Containers) selected through a RuntimeClass, which add a boundary between container and host kernel.
  • Virtual clusters (vcluster) give each tenant their own control plane inside a host cluster, isolating cluster-scoped objects such as CRDs.
  • Separate clusters per tenant or per environment, the strongest and simplest to reason about, at the cost of operating more clusters.
  • Hierarchical namespaces and tenant operators (Capsule, HNC) automate applying all of the above consistently.

§5Shared Components Are Shared Risks

Control plane load, DNS, ingress controllers, logging pipelines, and cluster-scoped CRD versions are shared. One tenant's runaway list calls or excessive CRD instances can degrade the API server for everyone; API Priority and Fairness and per-tenant quotas on object counts help.

Decide the trust model first The question is not "how do I configure namespaces" but "what happens if one tenant is hostile or careless." The answer picks the isolation level and the cost.

§6Common Mistakes

MistakeWhat HappensFix
Treating namespaces as a security boundaryCross-tenant traffic and node escapes remain possibleAdd network policy, pod security, and node or runtime isolation
No quotasOne tenant exhausts shared capacitySet ResourceQuota and LimitRange from day one
Mixing hostile tenants in one clusterA single kernel or API flaw exposes allUse separate clusters or strong sandboxing
Practice
  1. Write the quota, network policy, RBAC, and pod security settings you would apply when onboarding a new team.
  2. List three things in a cluster that namespaces cannot isolate.
Key takeaways
  • Namespaces scope names and policy but do not isolate the network, kernel, or cluster-scoped objects on their own.
  • Quotas, RBAC, network policy, and pod security together make soft multi-tenancy workable.
  • Hard multi-tenancy needs sandboxing, dedicated nodes, virtual clusters, or separate clusters.
