Secrets Management & Supply Chain

Secrets and the software supply chain are two sides of trust: protecting the credentials workloads use, and knowing that the images they run came from you and are what you think they are.

§1Secrets: Beyond Base64

Kubernetes Secrets are a start, not a vault. Improve them in layers:

  1. Encrypt at rest in etcd with an EncryptionConfiguration that uses a KMS provider, so backups and disk access do not expose values.
  2. Restrict access with RBAC, and keep Secrets out of logs and environment variables where possible (env vars appear in process listings and crash dumps; mounted files are easier to scope).
  3. Use an external store (HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault) as the source of truth.

Ways to bring external secrets into a cluster:

ToolHow it works
External Secrets OperatorAn ExternalSecret object references a remote secret; a controller creates and refreshes a Kubernetes Secret
Secrets Store CSI DriverMounts secrets from the store as files in the pod, optionally syncing to a Secret
Sealed SecretsEncrypt a Secret with a cluster key so the ciphertext can live in Git
SOPSEncrypt values in files with KMS or age keys, decrypted by your GitOps tool
Vault Agent / injectorA sidecar fetches and renews secrets, supporting dynamic, short-lived credentials

Prefer dynamic, short-lived credentials and workload identity over static passwords, so a leak expires on its own.

§2Supply Chain Risks

Between source code and a running pod are many places to tamper: dependencies, the build system, the registry, and the deployment pipeline. Defenses form a chain:

  • Minimal, pinned base images and dependency pinning, with regular rebuilds.
  • Vulnerability scanning in CI and in the registry (Trivy, Grype), and continuous scanning of running images.
  • SBOMs (software bills of materials) in SPDX or CycloneDX format, so you can answer "are we running the vulnerable library?" quickly.
  • Provenance and signing: build systems emit attestations (the SLSA framework describes levels), and images are signed with Sigstore cosign.
  • Deploy by digest, not by mutable tag.
  • Verify at admission: a policy engine refuses images that are unsigned, from unapproved registries, or lacking required attestations.
cosign sign ghcr.io/myorg/web@sha256:9b2f...
cosign verify --certificate-identity-regexp 'https://github.com/myorg/.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/myorg/web@sha256:9b2f...

Keyless signing ties a signature to the CI workflow's identity, so there are no long-lived signing keys to guard. A Kyverno verifyImages rule or a similar admission policy can then require valid signatures before any pod starts.

§3Controlling the Pipeline

Protect the build and deploy path itself: least-privilege CI credentials, protected branches, reviewed changes to pipeline definitions, isolated build runners, and a private registry or pull-through cache so builds do not depend on arbitrary public sources.

Trust is verified, not assumed "It came from our registry" is not proof. A signed image with provenance, checked automatically at admission, is.

§4Common Mistakes

MistakeWhat HappensFix
Long-lived static credentials in SecretsA leak is valid for monthsUse dynamic credentials and workload identity
Scanning once at buildNew vulnerabilities appear in images already runningRescan continuously and keep SBOMs
Signing images but never verifyingThe signature protects nothingEnforce verification in admission policy
Practice
  1. Pick one workload and list every secret it uses, where each is stored, and how it would be rotated.
  2. Sign an image with cosign and write a policy that rejects an unsigned one.
Key takeaways
  • Encrypt Secrets at rest, restrict access, and prefer an external store with short-lived credentials.
  • Supply chain security combines scanning, SBOMs, signing, provenance, and digest pinning.
  • Verification must be enforced at admission, or signing is decoration.
