etcd, Backup & Disaster Recovery

etcd holds every object in the cluster, so a tested backup and a rehearsed restore are the foundation of disaster recovery.

§1What Lives in etcd

All API objects: Deployments, Secrets, ConfigMaps, RBAC, CRDs, leases. It does not hold your application data (that lives in volumes and databases) or running container state. If you restore etcd, you restore the *declaration* of the cluster; the controllers then reconcile reality toward it, which means pods are recreated and volumes reattached.

Without encryption at rest, Secrets are readable from an etcd backup, so backups contain sensitive data and must be encrypted and access-controlled.

§2Taking a Snapshot

ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /backup/etcd-$(date +%F-%H%M).db

etcdutl snapshot status /backup/etcd-2026-01-15-0200.db -w table

Take snapshots on a schedule (hourly is typical), copy them off the cluster and off the failure domain, and keep several generations. Managed services (EKS, GKE, AKS) back up the control plane for you but do not back up your application data, and do not give you etcd access.

§3Restoring

Restoring a snapshot creates a new data directory and, in a multi-member cluster, a new cluster identity:

etcdutl snapshot restore /backup/etcd.db \
  --data-dir /var/lib/etcd-restored \
  --name cp-1 \
  --initial-cluster cp-1=https://10.0.0.11:2380,cp-2=https://10.0.0.12:2380,cp-3=https://10.0.0.13:2380 \
  --initial-advertise-peer-urls https://10.0.0.11:2380

The outline of a restore: stop the API servers, restore the snapshot on each member with the new data directory, point etcd at it, start etcd, then start the API servers and check. The exact flags vary by installer, so follow your distribution's runbook and rehearse it.

§4Beyond etcd: What Else to Back Up

ItemHow
etcd stateSnapshots, as above
Cluster PKI (certificates and keys)Copy the pki directory securely; needed to rebuild control planes
ManifestsKeep them in Git, so GitOps can recreate workloads
Persistent volume dataVolume snapshots, application-level backups, or tools like Velero
SecretsA vault or sealed secrets, not only the cluster

A GitOps setup shortens disaster recovery: rebuild a cluster from scratch, point it at the repository, and workloads return. etcd backups then matter most for state that is not in Git, such as Secrets created manually, CRD instances produced at runtime, and PVC bindings.

§5Maintenance

  • Compact and defragment periodically; etcd has a storage quota (2 GiB by default, with 8 GiB a common recommended ceiling). When exceeded, it raises an alarm and refuses writes.
  • Monitor etcd_server_has_leader, leader changes, etcd_disk_wal_fsync_duration_seconds, and database size.
A backup you never restored is a hope Schedule a drill: restore a snapshot into a scratch cluster and verify that expected objects exist. Do it before you need it.

§6Common Mistakes

MistakeWhat HappensFix
Backups stored on the same disk or clusterA single failure destroys bothCopy off-cluster and off-site
Never testing a restoreYou learn the procedure during the outageRun restore drills on a schedule
Forgetting backups contain SecretsA leaked snapshot leaks credentialsEncrypt backups and restrict access
Practice
  1. Take an etcd snapshot on a kubeadm or kind cluster, delete a Deployment, and restore the snapshot into a fresh data directory.
  2. List what you would still need besides etcd to rebuild a production cluster from nothing.
Key takeaways
  • etcd holds all API state, not your application data.
  • Take scheduled snapshots, store them elsewhere, and encrypt them.
  • A restore is only trusted once you have rehearsed it.
