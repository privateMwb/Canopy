The Control Plane in Depth

Every Kubernetes behavior is the API server, etcd, the scheduler, and a set of controllers running one idea: compare desired state with observed state, and act on the difference.

§1The API Server as the Hub

The API server is a stateless REST front end to etcd. Every request passes through a fixed pipeline:

request -> authentication -> authorization (RBAC) -> mutating admission
        -> schema validation -> validating admission -> write to etcd -> response

It is the only component that talks to etcd. Scaling it is easy because it holds no authoritative state: run several behind a load balancer. Each object carries a resourceVersion, which comes from etcd's revision, and writes use optimistic concurrency: an update with a stale resourceVersion fails with a conflict, and the client rereads and retries.

§2etcd

etcd is a distributed key-value store using the Raft consensus protocol. A write succeeds when a quorum (majority) of members persist it. That has consequences for design:

  • Run an odd number of members, typically 3 or 5. Three tolerates one failure; five tolerates two. More members make writes slower, not safer.
  • Disk fsync latency is the most important performance factor, so etcd belongs on fast, dedicated SSDs.
  • Losing quorum makes the cluster read-only or unavailable for changes, though already-running pods keep running.

§3Watches: How Components Learn About Change

Components do not poll. They open a watch on the API server, which streams events when objects change, sourced from etcd's watch feature. Clients wrap this in informers: a local cache kept in sync by a list followed by a watch, with event handlers that enqueue work. Controllers read from that cache instead of hammering the API.

§4The Reconciliation Loop

Every controller has the same shape:

func reconcile(key):
    desired  = get(key)                 # from the informer cache
    actual   = observe the world
    if desired == actual: return
    make one step toward desired        # create / update / delete
    # requeue; the loop is level-triggered, not edge-triggered

Controllers are level-triggered: they act on the *current* difference, not on remembered events, so a missed event is healed by the next reconcile. The built-in kube-controller-manager runs dozens: ReplicaSet, Deployment, Node, Job, EndpointSlice, ServiceAccount, and so on.

§5Where the Scheduler Fits

The scheduler is a controller too, with one job: watch for pods without a nodeName, pick a node, and write a binding. It never starts a container. The kubelet watches for pods bound to its node and does the rest.

The key insight A Deployment does not create pods. The Deployment controller creates a ReplicaSet, the ReplicaSet controller creates pod objects, the scheduler assigns them, and the kubelet runs them. Each layer only edits objects in the API; coordination happens through the data, not through calls.

§6Common Mistakes

MistakeWhat HappensFix
Even number of etcd membersFault tolerance is no better than one fewer memberUse 3 or 5
etcd on slow shared disksLeader elections and API latency spikesUse dedicated low-latency SSDs and watch fsync metrics
Treating events as the source of truthMissed events cause permanent driftDesign controllers as level-triggered reconcilers
Practice
  1. Run kubectl get pods -w while creating a Deployment, and map each event to the controller that caused it.
  2. Explain why losing etcd quorum stops changes but does not immediately stop running pods.
Key takeaways
  • Requests pass through authentication, authorization, admission, validation, then etcd.
  • etcd uses Raft and quorum; the API server is stateless and horizontally scalable.
  • Controllers are level-triggered reconcile loops fed by informer caches.
