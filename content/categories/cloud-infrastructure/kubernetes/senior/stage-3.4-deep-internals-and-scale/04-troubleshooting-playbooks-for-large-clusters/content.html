Troubleshooting Playbooks for Large Clusters

Large-cluster problems need a method that narrows scope before it narrows cause, because "something is slow" can mean a hundred different things.

§1Principles

  1. Define the symptom precisely: what is slow or failing, for whom, since when, and compared to what.
  2. Establish scope: one pod, one node, one zone, one namespace, one cluster-wide component?
  3. Check recent changes first: deployments, upgrades, config changes, certificate rotations, autoscaling events.
  4. Follow the path of a request layer by layer and test each hop.
  5. Change one thing at a time, and record what you tried.
  6. Preserve evidence before you restart things that destroy it.

§3Tools for the Toolbox

  • Metrics and dashboards for the control plane, nodes, CNI, and DNS, with history, so you can compare to "normal."
  • Events and audit logs to reconstruct what happened and who or what triggered it.
  • Node-level: journalctl -u kubelet, crictl ps and crictl logs (talking to the runtime directly), dmesg for OOM kills and disk errors, ss, tcpdump, conntrack.
  • Ephemeral debug containers and node debugging: kubectl debug node/<name> -it --image=busybox gives a shell with the node's filesystem mounted.
  • Distributed traces to find which hop consumed the time.
  • Canary checks from inside the cluster, so you separate cluster problems from client problems.
kubectl debug node/worker-7 -it --image=nicolaka/netshoot
journalctl -u kubelet --since "30 min ago" | grep -i -E 'error|pleg|evict'

§4Bisecting

When the cause is unclear, bisect: split the possibilities in half with one test. Is it all nodes or a subset? Compare a bad node to a good one, side by side, on kernel version, CNI version, instance type, and zone. Does it reproduce outside the cluster? Disabling components or draining a suspect node is a test, not a fix.

§5Playbooks and Learning

Capture the diagnosis paths that worked as playbooks: symptom, likely causes in order, commands, and decision points. Pair them with dashboards and alerts, and update them after every incident. Rehearse with failure injection in a non-production cluster.

Narrow scope before guessing cause Knowing that only one zone is affected removes ninety percent of hypotheses before you open a single log.

§6Common Mistakes

MistakeWhat HappensFix
Restarting components before capturing stateEvidence disappears and the problem recursCollect logs, metrics, and events first
Changing several things at onceYou cannot tell what helpedMake one change, observe, then proceed
Comparing against memory of "normal"You miss slow driftKeep dashboards with history and baselines
Practice
  1. Write a playbook for "new pods take more than two minutes to start" with the first six checks in order.
  2. Choose two nodes, one healthy and one not, and list five attributes you would compare.
Key takeaways
  • Define the symptom, then narrow scope, then check what changed, then follow the request path.
  • Use node-level tools, metrics, events, and traces together, and bisect when unsure.
  • Turn each diagnosis into a playbook and rehearse it.
