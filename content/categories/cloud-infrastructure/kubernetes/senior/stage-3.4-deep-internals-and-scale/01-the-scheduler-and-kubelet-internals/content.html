The Scheduler & Kubelet Internals

The scheduler decides where a pod goes through a filter-and-score pipeline, and the kubelet turns that decision into running, healthy containers on the node.

§1The Scheduling Cycle

The scheduler keeps a queue of unscheduled pods in three parts: an active queue (ready to try), a backoff queue (recently failed, waiting), and an unschedulable pool (waiting for a cluster change that might help, such as a new node or freed resources). For each pod it runs a scheduling cycle, then a binding cycle.

The cycle is built from plugins at defined extension points:

PhaseExtension pointsPurpose
FilteringPreFilter, Filter, PostFilterRemove nodes that cannot run the pod; PostFilter runs preemption if none fit
ScoringPreScore, Score, NormalizeScoreRank feasible nodes (spreading, affinity, image locality, resource fit)
ReservationReserve, PermitHold resources in the scheduler's cache; optionally delay or gate binding
BindingPreBind, Bind, PostBindWrite the node assignment to the API server

Built-in filters include NodeResourcesFit, NodeAffinity, TaintToleration, VolumeBinding, and PodTopologySpread. In large clusters scoring all nodes is wasteful, so percentageOfNodesToScore limits how many feasible nodes are scored.

§2Preemption

When no node fits, the scheduler may preempt: evict lower-priority pods (per PriorityClass) so a higher-priority pod fits. It chooses victims to minimize disruption while honoring PDBs where it can, and the pod is nominated to a node while the victims terminate. This is the mechanism behind overprovisioning "placeholder" pods.

§3Configuring and Extending

Scheduling behavior is configured through a KubeSchedulerConfiguration, which sets plugin weights and enables or disables plugins, and scheduling profiles let one scheduler serve different pod classes via spec.schedulerName. You can run entirely separate schedulers or write plugins for special needs such as gang scheduling (all-or-nothing placement for batch and ML), as projects like Volcano and Kueue do.

§4The Kubelet

The kubelet is the node agent. Its core is a sync loop that compares the pods assigned to its node with what is actually running through the runtime, and acts on differences.

API server --watch--> kubelet --CRI--> containerd / CRI-O --> container processes
                         |--CNI--> network plugin sets up pod networking
                         |--CSI--> storage plugin mounts volumes

Responsibilities:

  • Pod lifecycle: pull images, create the sandbox (the pause container holding the namespaces), run init containers, start app containers, restart per policy.
  • Probes: executes startup, liveness, and readiness checks and reports results.
  • Health reporting: updates node status and renews a Lease object in kube-node-lease, which is how the control plane notices a dead node cheaply.
  • Resource management: enforces limits through cgroups, manages CPU and memory managers and device plugins, and performs eviction under pressure.
  • PLEG (Pod Lifecycle Event Generator): detects container state changes in the runtime. Slow PLEG is a classic cause of NotReady nodes.
  • Static pods: manifests in a node directory that the kubelet runs directly, which is how kubeadm starts control plane components.

§5Node Pressure and Eviction

The kubelet monitors memory, disk, inodes, and PIDs. Past a soft threshold (with a grace period) or a hard threshold, it marks the node under pressure, stops new pods landing there, and evicts pods ranked by QoS class and usage over requests. This differs from the kernel OOM killer, which acts when memory is already gone.

Two cooperating loops The scheduler decides *where* in the cluster using a global view; the kubelet decides *how* on one machine using local reality. Most placement mysteries are scheduler events, and most startup mysteries are kubelet events.

§6Common Mistakes

MistakeWhat HappensFix
Debugging a startup failure in scheduler logsThe scheduler's job ended at bindingCheck kubelet logs and pod Events for image, volume, and runtime errors
Ignoring node pressure conditionsEvictions look randomCheck kubectl describe node conditions and kubelet eviction settings
Relying on soft preemption without PDBsCritical pods can be displacedUse priority classes carefully and set PDBs
Practice
  1. Read the scheduler's decision for one pod from kubectl describe pod Events and name the plugin responsible.
  2. Find the kubelet's configuration on a node and note its eviction thresholds.
Key takeaways
  • The scheduler runs queue, filter, score, reserve, and bind via plugins, with preemption for priority.
  • The kubelet runs a sync loop over pod lifecycle, probes, resources, and node health through CRI, CNI, and CSI.
  • Placement problems are scheduler problems; startup and runtime problems are kubelet problems.
