Networking Internals: iptables, IPVS & eBPF

A Service address is a promise implemented by packet-rewriting rules on every node, and reading those rules shows exactly how traffic is routed.

§1The Service Data Path

A ClusterIP has no interface and no listener. When a pod sends a packet to it, rules on the node (installed by kube-proxy or an eBPF datapath) rewrite the destination to a real pod IP: DNAT (destination network address translation). The kernel's conntrack table remembers the translation so replies and later packets of the same connection follow the same path.

§2iptables Mode

In iptables mode, kube-proxy writes chains into the nat table:

iptables-save -t nat | grep -E 'KUBE-SERVICES|KUBE-SVC|KUBE-SEP' | head
# KUBE-SERVICES  : match destination ClusterIP:port, jump to the service chain
# KUBE-SVC-XXXX  : one chain per Service; picks an endpoint with probability rules
# KUBE-SEP-YYYY  : one chain per endpoint; DNAT to podIP:port

For a Service with three endpoints, the KUBE-SVC chain uses statistic rules: 1/3 chance of the first endpoint, then 1/2 of the remainder, then the last. The selection is random and per connection, not per request, so a long-lived connection sticks to one pod.

The cost: rule matching in iptables is linear, and large rulesets (tens of thousands of services and endpoints) make both packet processing and rule updates slow, since kube-proxy rewrites rules and the kernel locks tables while loading them.

§3IPVS Mode

IPVS uses the kernel's L4 load balancer with hash-table lookups, so lookups stay fast as services grow, and it offers more algorithms (round robin, least connections, source hash). It still relies on iptables or ipsets for some functions, and has been losing favor, with the community moving toward other backends.

§4nftables Mode

The nftables backend of kube-proxy uses the newer netfilter framework, with maps and sets that give constant-time service lookups and faster incremental updates than iptables. It is the direction the in-tree kube-proxy is moving, and needs recent kernels and kube-proxy versions.

§5eBPF and kube-proxy Replacement

Cilium (and other eBPF CNIs) can replace kube-proxy: a small program attached at the socket or network interface layer maps service IPs to backends using eBPF hash maps, often translating the address at connect time, before a packet exists. That avoids per-packet DNAT and conntrack for in-cluster traffic and gives lower latency and richer flow visibility.

§6Inspecting a Live Path

kubectl get svc web -o wide                      # ClusterIP and port
kubectl get endpointslices -l kubernetes.io/service-name=web
conntrack -L | grep 10.96.12.34                  # active translations for this ClusterIP
iptables-save -t nat | grep 10.96.12.34          # the rules matching it (iptables mode)
cilium service list                              # eBPF mode equivalent

Symptoms and where they point: new connections failing intermittently suggests stale endpoints or an unhealthy backend still in rotation; connection resets after a pod is replaced often implicate conntrack entries for pods that no longer exist; slow service updates on large clusters point to rule-programming cost.

Externally, externalTrafficPolicy: Local preserves the client source IP and avoids an extra hop, but only nodes with local endpoints pass health checks, which can cause imbalance. Cluster spreads traffic but may SNAT the source address.

Rules explain behavior Random-per-connection balancing, source IP changes, and stale connection problems all read directly from the NAT rules and conntrack state. When the abstraction misbehaves, look one layer down.

§7Common Mistakes

MistakeWhat HappensFix
Expecting request-level load balancing from a ServiceOne long-lived HTTP/2 or gRPC connection pins to one podUse client-side balancing, a mesh, or an L7 proxy
Assuming iptables mode scales indefinitelyLarge clusters see slow updates and latencyMove to nftables or eBPF at scale
Ignoring conntrack limitsNew connections are dropped when the table fillsMonitor conntrack usage and raise limits where justified
Practice
  1. On a node, find the KUBE-SVC chain for one Service and count its endpoint rules.
  2. Explain why a gRPC client sees uneven load across pods behind a ClusterIP.
Key takeaways
  • Service routing is DNAT performed by node rules plus conntrack, chosen per connection.
  • iptables scales linearly; nftables and eBPF use maps for constant-time lookup.
  • Inspecting rules and conntrack state explains many network oddities.
