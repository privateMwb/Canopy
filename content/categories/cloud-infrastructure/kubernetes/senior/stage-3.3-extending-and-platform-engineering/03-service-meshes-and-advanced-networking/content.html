Service Meshes & Advanced Networking

The network plugin and any service mesh decide how pods connect and what visibility, security, and cost that connection carries.

§1CNI Plugins

Kubernetes defines the Container Network Interface (CNI) and leaves the implementation to a plugin. Every pod needs an IP, and every pod must reach every other pod without NAT. Common choices:

PluginApproach
CiliumeBPF-based datapath; networking, policy, observability, and optional kube-proxy replacement
CalicoBGP or overlay networking with mature network policy; can use iptables or eBPF
FlannelSimple overlay network; little beyond connectivity and no NetworkPolicy
Cloud-native CNIs (AWS VPC CNI, Azure CNI, GKE)Pods get addresses from the cloud network directly

Questions to settle: overlay or routed networking, IP address capacity (pod CIDR size limits cluster growth, and VPC-native CNIs can exhaust subnet IPs), network policy support, and observability.

§2Why eBPF Matters

eBPF lets small verified programs run inside the Linux kernel. Cilium and others use it to forward packets, enforce policy, and collect flow data without long iptables chains, which improves performance at scale and gives per-connection visibility (Hubble) and identity-based policy decisions. It requires reasonably modern kernels.

§3What a Service Mesh Adds

A service mesh manages service-to-service traffic:

  • Mutual TLS between workloads, with automatic certificate rotation and identity.
  • Traffic control: retries, timeouts, circuit breaking, weighted routing, fault injection.
  • Observability: uniform request metrics, tracing hooks, and access logs.
  • Authorization policy between services.

Architectures differ:

ModelHow it worksTrade-off
Sidecar proxy (Istio classic, Linkerd)A proxy container in every podRich per-pod features, but extra CPU and memory, and startup complexity
Ambient / node-level (Istio ambient, Cilium service mesh)Shared per-node proxies, with optional per-namespace L7 proxiesLower overhead, a newer model

Popular meshes are Istio, Linkerd, and Cilium Service Mesh. Check each project's current release and licensing status when evaluating, since distribution models have changed over time.

§4What It Costs

  • Resources: sidecars add CPU and memory per pod, and latency per hop.
  • Operations: another control plane to upgrade, debug, and secure, with its own failure modes.
  • Complexity: when traffic misbehaves there is now a proxy layer to examine.
  • Skills: the team must learn the mesh's configuration model.

§5Deciding

A mesh pays off when you need uniform mTLS and policy for many services, rich traffic management, or consistent observability across teams and languages. For a handful of services, simpler alternatives often suffice: TLS from your ingress, libraries for retries, network policies, and Gateway API for traffic splitting.

Start with the problem "We need mTLS everywhere" or "we need canaries with automatic analysis" are problems a mesh solves. "Everyone uses one" is not.

§6Common Mistakes

MistakeWhat HappensFix
Adopting a mesh with no concrete needOperational cost with little benefitWrite the specific requirements first
Pod CIDR too smallThe cluster cannot add nodes or pods laterPlan address ranges for growth before installation
Assuming every CNI enforces NetworkPolicyPolicies exist but do nothingVerify support and test enforcement
Practice
  1. Identify which CNI your cluster uses and what its pod IP capacity limit is.
  2. Write three requirements that would justify a service mesh and three that a simpler tool could meet.
Key takeaways
  • The CNI plugin determines pod addressing, policy support, and performance; eBPF datapaths avoid iptables scaling limits.
  • A mesh adds mTLS, traffic control, and observability at a real cost in resources and operations.
  • Choose a mesh only when specific requirements justify it.
