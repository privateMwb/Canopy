Why Kubernetes Exists

Kubernetes is a system that keeps your containers running in the shape you described, across many machines, without you babysitting each one.

§1The Problem: Containers at Scale

Running one container with docker run is easy. Running two hundred across twenty machines is not. Someone has to decide which machine each container goes on, restart the ones that crash, replace the ones on a machine that dies, route traffic to whichever copies are healthy, and roll out new versions without downtime. Doing this by hand, or with shell scripts, collapses quickly.

Container orchestration is the automation of those jobs. Kubernetes (often written K8s) is the dominant orchestrator. It started at Google, drew on their internal system Borg, and is now maintained by the Cloud Native Computing Foundation.

§2Desired State, Not Commands

The central idea is declarative desired state. You do not tell Kubernetes "start three copies of this container." You tell it "there should be three copies of this container," and Kubernetes works to make that true and keep it true.

# You declare:           replicas: 3
# Kubernetes observes:   2 running (one node died)
# Kubernetes acts:       starts 1 more, somewhere healthy
# Kubernetes observes:   3 running, done, keeps watching

This loop of observe, compare, act is called reconciliation, and every part of Kubernetes is built from it. It is why a cluster heals itself: nobody has to notice the failure, the loop notices the gap between what you asked for and what exists.

§3What Kubernetes Gives You

  • Scheduling: placing containers on machines that have room.
  • Self-healing: restarting failed containers and replacing lost ones.
  • Scaling: changing the number of copies by editing one number, or automatically.
  • Service discovery and load balancing: stable names and addresses in front of changing containers.
  • Rollouts and rollbacks: gradual version changes with an undo.
  • Configuration and secrets: injecting settings without rebuilding images.
The key insight Kubernetes is not a way to run a container. Docker already does that. Kubernetes is a control system that continuously drives a fleet toward a state you wrote down.

§4What It Does Not Do

Kubernetes does not build your images, write your application, make a badly designed app scalable, or remove the need to understand networking and storage. It also adds real complexity. Later lessons, especially the Senior-level question "Is Kubernetes the Right Tool?", come back to when that complexity pays for itself.

§5Common Mistakes

MistakeWhat HappensFix
Treating Kubernetes as "Docker but bigger"Commands are issued imperatively and drift goes unnoticedDescribe the end state in files and let the cluster converge on it
Assuming it makes any app scalableA stateful or single-threaded app still bottlenecks, just with more copiesDesign the app to run as interchangeable replicas first
Adopting it for one small serviceYou carry cluster operations cost with no benefitWeigh simpler options first; see the Senior judgment lesson
Practice
  1. List three things you would have to script yourself to keep ten containers running across three servers.
  2. In your own words, explain why "there should be three replicas" is different from "start three replicas."
Key takeaways
  • Kubernetes automates placing, healing, scaling, and updating containers across many machines.
  • You declare desired state; controllers reconcile reality toward it in a continuous loop.
  • It solves operational problems at scale and has its own cost, so it is a tool, not a default.
