Cluster Architecture

A cluster is a set of machines split into a control plane that makes decisions and worker nodes that run your containers.

§1Two Kinds of Machine

Every cluster has two halves. The control plane is the brain: it stores the desired state, decides where things should run, and reacts when reality drifts. The worker nodes are the muscle: they are the machines (physical or virtual) that actually run your containers.

          CONTROL PLANE                       WORKER NODES
  +-------------------------------+      +--------------------+
  | kube-apiserver   (front door) |      | kubelet            |
  | etcd             (the memory) | <--> | container runtime  |
  | kube-scheduler   (placement)  |      | kube-proxy         |
  | controller-manager (loops)    |      | [pod] [pod] [pod]  |
  +-------------------------------+      +--------------------+

§2Control Plane Components

  • kube-apiserver: the only component everything talks to. kubectl, the scheduler, the kubelets, and controllers all read and write state through its REST API. It validates and authenticates every request.
  • etcd: a consistent key-value store holding all cluster state. If etcd is lost with no backup, the cluster forgets everything it was supposed to run.
  • kube-scheduler: watches for pods with no node assigned and picks a suitable node for each.
  • kube-controller-manager: runs the reconciliation loops (for Deployments, nodes, jobs, and more) in one process.

§3Node Components

  • kubelet: the agent on each node. It watches the API server for pods assigned to its node, tells the container runtime to start them, and reports status back.
  • Container runtime: the software that actually runs containers, such as containerd or CRI-O, reached through the Container Runtime Interface (CRI). Docker Engine is no longer used directly since Kubernetes 1.24 removed dockershim, though images built with Docker run fine.
  • kube-proxy: programs the node's network rules so Service addresses reach the right pods.

§4Following One Request

When you create a pod, no component calls another directly. The flow goes through the API server and etcd:

  1. kubectl sends the pod definition to the API server, which stores it in etcd.
  2. The scheduler sees a pod with no node, picks one, and writes that choice back.
  3. The kubelet on that node sees a pod assigned to it and starts the containers.
  4. The kubelet reports status, which is again stored through the API server.
The key insight Components never command each other. They watch the API server for changes relevant to them and act. That is why you can restart a control plane component and the cluster recovers.

§5Common Mistakes

MistakeWhat HappensFix
Thinking kubectl talks to nodesDebugging the wrong layer when kubectl works but pods failRemember kubectl only talks to the API server; the kubelet does the node work
Ignoring etcdLosing it means losing every object in the clusterBack it up, or use a managed service that does
Running workloads on control plane nodesHeavy pods starve the components keeping the cluster aliveKeep control plane nodes tainted for system components only
Practice
  1. Draw the path a new pod takes from kubectl apply to a running container, naming each component it touches.
  2. Which single component would you protect and back up first, and why?
Key takeaways
  • The control plane stores state and decides; nodes run containers.
  • Everything flows through the API server, which is backed by etcd.
  • Components coordinate by watching shared state, not by calling each other.
