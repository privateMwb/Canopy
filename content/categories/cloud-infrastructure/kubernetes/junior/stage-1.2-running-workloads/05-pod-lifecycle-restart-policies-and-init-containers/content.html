Pod Lifecycle, Restart Policies & Init Containers

A pod passes through defined phases from scheduling to termination, and restart policies and init containers let you control what happens along the way.

§1The Pod Lifecycle

PhaseMeaning
PendingAccepted, but not yet running: waiting to be scheduled, or images are being pulled
RunningBound to a node, with at least one container running or starting
SucceededAll containers exited with code 0 and will not restart
FailedAll containers ended and at least one failed
UnknownThe node cannot be reached, so state is not known

Phase is a coarse summary. The detail is in container states (Waiting, Running, Terminated) and in the Events section of kubectl describe pod, where reasons like FailedScheduling or Pulling appear.

§2Restart Policies

spec.restartPolicy tells the kubelet what to do when a container exits:

  • Always (default): restart no matter how it exited. Right for servers.
  • OnFailure: restart only on a non-zero exit. Used for jobs.
  • Never: do not restart.

Restarts back off exponentially (10s, 20s, 40s, up to five minutes). A container that keeps crashing shows the status CrashLoopBackOff, which means "it keeps restarting and I am waiting longer each time," not a separate failure type.

§3Init Containers

Init containers run to completion, one at a time and in order, before any app container starts. Use them for setup the app must not start without.

spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command: ['sh', '-c', 'until nc -z db 5432; do sleep 2; done']
  containers:
    - name: app
      image: myapp:1.0

If an init container fails, the pod restarts it according to the restart policy and the app containers never start.

§4Termination

When a pod is deleted:

  1. It is marked Terminating and removed from Service endpoints.
  2. The kubelet sends SIGTERM to each container's main process.
  3. After the grace period (terminationGracePeriodSeconds, default 30), it sends SIGKILL.
Handle SIGTERM Your app gets thirty seconds to finish in-flight work and exit cleanly. If it ignores SIGTERM, every deploy forces a hard kill. A later lesson covers graceful shutdown in depth.

§5Common Mistakes

MistakeWhat HappensFix
Reading Running as "healthy"The process started but may not be servingAdd readiness and liveness probes
Treating CrashLoopBackOff as a causeYou look at Kubernetes instead of your appRun kubectl logs --previous to see why the last run exited
Init container that never finishesThe pod stays in Init:0/1 foreverGive init tasks a clear exit condition and check their logs with -c <name>
Practice
  1. Start a pod whose command exits with code 1 and watch the status change; then read kubectl logs --previous.
  2. Add an init container that sleeps ten seconds and observe the pod's Init status.
Key takeaways
  • Phases summarize state; Events and container states explain it.
  • restartPolicy and exponential backoff produce CrashLoopBackOff for repeatedly failing containers.
  • Init containers run first and in order; termination sends SIGTERM, then SIGKILL after the grace period.
