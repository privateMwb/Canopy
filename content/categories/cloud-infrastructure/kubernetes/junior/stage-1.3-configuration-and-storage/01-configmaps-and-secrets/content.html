ConfigMaps & Secrets

ConfigMaps and Secrets hold configuration outside your image, so the same image runs in every environment with different settings.

§1Why Separate Configuration

An image should be identical in dev, staging, and production. What changes between them, such as database hostnames, feature flags, and credentials, belongs in objects you attach at runtime. Kubernetes has two for this: ConfigMap for ordinary settings and Secret for sensitive values.

§2ConfigMaps

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
  FEATURE_X: "true"
  app.properties: |
    cache.ttl=300
    cache.size=1000

Keys can hold single values or whole files. Create one quickly from the command line with kubectl create configmap app-config --from-literal=LOG_LEVEL=info or --from-file=app.properties.

§3Using Them in a Pod

There are two ways to consume a ConfigMap:

containers:
  - name: app
    image: myapp:1.0
    envFrom:
      - configMapRef:
          name: app-config          # every key becomes an environment variable
    env:
      - name: DB_PASSWORD
        valueFrom:
          secretKeyRef:
            name: db-credentials
            key: password           # a single key from a Secret
    volumeMounts:
      - name: config
        mountPath: /etc/app         # keys appear as files in this directory
volumes:
  - name: config
    configMap:
      name: app-config

Environment variables are simple but are read once when the container starts. Mounted files are refreshed in the running pod after a short delay when the ConfigMap changes, though the app must reread them. Values from subPath mounts are never updated.

§4Secrets

A Secret has the same shape as a ConfigMap, with values stored base64-encoded.

kubectl create secret generic db-credentials \
  --from-literal=username=app --from-literal=password='s3cret'
kubectl get secret db-credentials -o jsonpath='{.data.password}' | base64 -d
Base64 is not encryption Anyone who can read the Secret object can decode it in one command. By default Secrets are stored unencrypted in etcd. Restrict who can read them with RBAC, enable encryption at rest, and consider an external secret store. Never commit Secret YAML with real values to Git.

§5Limits and Behavior

Each object is capped at 1 MiB. Changing a ConfigMap does not restart pods that use it as environment variables; you must roll the Deployment (kubectl rollout restart deployment/web). Marking a ConfigMap or Secret immutable: true prevents edits and reduces load on the API server.

§6Common Mistakes

MistakeWhat HappensFix
Committing Secret manifests with real valuesCredentials leak into Git historyCreate Secrets out of band or use an external secrets tool
Expecting env vars to update livePods keep old values until restartedRun kubectl rollout restart, or mount as files and reload in the app
Treating base64 as protectionAnyone with read access sees the valueLock down access and encrypt at rest
Practice
  1. Create a ConfigMap and inject it into a pod both as environment variables and as a mounted file; verify with exec.
  2. Decode a Secret value with base64 -d to see why it is not secure on its own.
Key takeaways
  • ConfigMaps and Secrets keep configuration out of images.
  • They can be injected as environment variables or as mounted files, and behave differently on change.
  • Secrets are encoded, not encrypted; protect them with access control and encryption at rest.
