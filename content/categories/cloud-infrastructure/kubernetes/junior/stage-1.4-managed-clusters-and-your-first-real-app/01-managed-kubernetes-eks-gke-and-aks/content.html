Managed Kubernetes: EKS, GKE & AKS

A managed Kubernetes service runs the control plane for you, which removes the hardest operational work but not your responsibility for what runs on it.

§1What Managed Means

Running your own control plane means patching it, backing up etcd, and keeping it highly available. Managed services take that over. The three major ones:

ServiceProviderNotes
EKSAWSControl plane managed; you choose managed node groups, self-managed nodes, or Fargate for serverless pods
GKEGoogle CloudStandard mode (you manage node pools) or Autopilot (Google manages nodes, billing is per pod)
AKSAzureControl plane free in the basic tier; node pools run on virtual machine scale sets

§2The Shared Responsibility Line

The provider runsYou still own
API server, etcd, scheduler, controller managerYour workloads, manifests, and images
Control plane availability and patchingChoosing when to upgrade the cluster and node versions
Integration with cloud load balancers and disksNode sizing, scaling, and cost
Optional managed node upgradesAccess control, network policy, and pod security
Nothing here; the service does not watch your appsMonitoring, application data backups, and incident response

Managed does not mean hands-off. Clusters still need version upgrades on a regular schedule, because old Kubernetes versions leave support and some providers force an upgrade after a deadline.

§3Connecting to One

Each provider's CLI writes a context into your kubeconfig:

aws eks update-kubeconfig --name my-cluster --region us-east-1
gcloud container clusters get-credentials my-cluster --region us-central1
az aks get-credentials --resource-group my-rg --name my-cluster
kubectl get nodes

Credentials are tied to your cloud identity, so access is governed by the cloud's IAM as well as Kubernetes RBAC.

§4Cloud Integration

A LoadBalancer Service provisions a cloud load balancer. A PVC provisions a cloud disk through a CSI driver. Both create billable resources outside the cluster, and deleting the cluster does not always remove them.

Cost trap Load balancers, disks, and idle nodes keep billing after you stop using a cluster. Always delete Services of type LoadBalancer and PVCs first, then the cluster, then check the cloud console for leftovers.

§5Common Mistakes

MistakeWhat HappensFix
Assuming the provider secures workloadsPublic pods, open roles, and weak images are your riskApply RBAC, network policy, and pod security yourself
Ignoring upgrade deadlinesA forced upgrade lands at a bad timeTrack support dates and upgrade on your schedule
Deleting only the clusterLoad balancers and disks keep costing moneyRemove cloud-backed objects first and audit afterward
Practice
  1. List which of the control plane components in Lesson 1.1.2 your chosen provider hides from you.
  2. Find the Kubernetes version support window for your provider and note the next deadline.
Key takeaways
  • Managed services run the control plane; you own workloads, nodes, access, and cost.
  • Each provider connects through its CLI into your kubeconfig.
  • Cloud-backed Services and volumes cost money until they are explicitly deleted.
