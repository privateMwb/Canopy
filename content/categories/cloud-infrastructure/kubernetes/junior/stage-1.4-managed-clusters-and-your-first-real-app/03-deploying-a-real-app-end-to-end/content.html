Deploying a Real App End to End

This lesson ties the Junior stage together by deploying a web app with a database, configuration, storage, and a public address.

§1The Architecture

We will deploy a simple two-tier app:

Internet -> LoadBalancer Service -> web Deployment (3 pods)
                                         |
                                         v  (ClusterIP Service "db")
                                   Postgres Deployment (1 pod) -> PVC

Everything goes in its own namespace so it can be deleted in one command.

§2Step 1: Namespace and Secret

kubectl create namespace shop
kubectl -n shop create secret generic db-credentials \
  --from-literal=POSTGRES_PASSWORD='change-me'

§3Step 2: Database With Storage

apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: pgdata, namespace: shop }
spec:
  accessModes: ["ReadWriteOnce"]
  resources: { requests: { storage: 5Gi } }
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: db, namespace: shop }
spec:
  replicas: 1
  strategy: { type: Recreate }       # a ReadWriteOnce disk cannot be mounted twice
  selector: { matchLabels: { app: db } }
  template:
    metadata: { labels: { app: db } }
    spec:
      containers:
        - name: postgres
          image: postgres:16
          envFrom: [{ secretRef: { name: db-credentials } }]
          volumeMounts: [{ name: data, mountPath: /var/lib/postgresql/data }]
          readinessProbe:
            exec: { command: ["pg_isready", "-U", "postgres"] }
      volumes:
        - name: data
          persistentVolumeClaim: { claimName: pgdata }
---
apiVersion: v1
kind: Service
metadata: { name: db, namespace: shop }
spec:
  selector: { app: db }
  ports: [{ port: 5432 }]

The Recreate strategy matters: a rolling update would try to start a second database pod on the same single-attach disk.

§4Step 3: The Web App

apiVersion: apps/v1
kind: Deployment
metadata: { name: web, namespace: shop }
spec:
  replicas: 3
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
        - name: web
          image: myorg/shop-web:1.0.0
          env:
            - { name: DB_HOST, value: db }          # the Service name
          envFrom: [{ secretRef: { name: db-credentials } }]
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits: { memory: 256Mi }
          readinessProbe:
            httpGet: { path: /ready, port: 8080 }
---
apiVersion: v1
kind: Service
metadata: { name: web, namespace: shop }
spec:
  type: LoadBalancer
  selector: { app: web }
  ports: [{ port: 80, targetPort: 8080 }]

§5Step 4: Verify

kubectl -n shop get all
kubectl -n shop get svc web -w            # wait for an EXTERNAL-IP
curl http://<external-ip>/
kubectl -n shop logs deploy/web

Note how the app reaches the database: by the Service name db, resolved by cluster DNS. No IP addresses appear anywhere.

A database in a Deployment is for learning Real databases want stable identity and careful storage handling. A later stage introduces StatefulSets, and many teams use a managed database outside the cluster instead.

§6Common Mistakes

MistakeWhat HappensFix
Rolling-updating a single-attach disk workloadThe new pod cannot mount the disk and hangsUse Recreate, or a StatefulSet
Hard-coding pod IPs for the databaseThe address changes on every restartAlways connect through the Service name
Forgetting the namespace on commandsResources look missingUse -n shop, or set the context's default namespace
Practice
  1. Deploy the stack above (substituting any web image that talks to Postgres) and reach it from a browser.
  2. Delete the database pod and confirm the data persists after it is recreated.
Key takeaways
  • Namespaces, Secrets, PVCs, Deployments, and Services combine into a complete app.
  • Components find each other through Service DNS names, not IPs.
  • Matching strategy to storage (Recreate for single-attach disks) prevents stuck rollouts.
