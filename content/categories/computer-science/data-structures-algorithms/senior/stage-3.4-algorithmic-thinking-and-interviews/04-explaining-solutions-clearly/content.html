Explaining Solutions Clearly

Communicating a solution's logic and complexity to someone who didn't watch you build it.

§1Why Explaining Is a Separate Skill From Solving

Understanding your own solution and clearly explaining it to someone else are genuinely different skills — plenty of correct solutions get poorly explained, leaving a reviewer (or future teammate reading the code) more confused than informed.

§2A Reliable Structure for Explaining a Solution

  1. Restate the problem, briefly — confirms shared understanding before diving in.
  2. State the approach at a high level before any code or implementation detail — "this uses a sliding window to avoid recomputing the sum each time."
  3. Walk through the logic, connecting each piece back to the high-level approach already stated.
  4. State the complexity, and briefly justify why — not just "it's O(n)," but what makes it O(n).

§3A Concrete Comparison

Weak vs. strong explanation Weak: "So I have this pointer here, and this other pointer, and I move them until they meet, and then I return." Strong: "This uses two pointers starting at opposite ends, since the array is sorted — moving the left pointer up increases the sum, moving the right pointer down decreases it, so I can narrow in on the target in one pass instead of checking every pair." The second version explains why, not just what.

§4Explaining Complexity Convincingly

"It's O(n log n)" is a claim; "it's O(n log n) because we sort once (O(n log n)) and then do a single O(n) pass" is a justification. The second version lets the listener verify the claim themselves, rather than just trusting it.

§5Why This Matters Beyond Interviews

This same structure — restate, high-level approach, walkthrough, complexity justification — is exactly what a good pull request description or design doc does. The skill built here transfers directly to explaining real production code to teammates, which is a far more common need than interview performance itself.

§6Common Mistakes

MistakeWhat HappensFix
Diving into implementation details before stating the high-level approachListener struggles to follow without the big-picture context firstAlways state the approach at a high level before walking through specifics
Stating complexity without justificationAn unverifiable claim the listener has to just trustBriefly explain what makes the complexity what it is
Practice
  1. Take a solution from any earlier stage and write a four-part explanation following the structure above.
  2. Explain, in one or two sentences, why "it's O(n)" alone is a weaker explanation than justifying why.
Key takeaways
  • Explaining a solution well is a distinct skill from solving it — plenty of correct solutions get poorly communicated.
  • A reliable structure: restate the problem, state the approach, walk through the logic, justify the complexity.
  • This same structure transfers directly to writing clear pull request descriptions and design docs.
