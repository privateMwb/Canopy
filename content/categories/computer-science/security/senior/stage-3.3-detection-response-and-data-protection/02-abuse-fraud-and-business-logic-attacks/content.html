Abuse, Fraud & Business-Logic Attacks

Some of the most costly attacks use features exactly as designed, so no scanner flags them, and defending against them means thinking like someone trying to profit from the rules.

§1Race Conditions

When a check and an update aren't atomic, parallel requests can all pass the check before any update lands. This enables double-spending, redeeming a one-time code many times, or exceeding a limit.

# Vulnerable: check, then act (two requests can both pass the check)
if coupon.unused:
    apply_discount()
    coupon.unused = False

# Safer: make the claim atomic in the database
UPDATE coupons SET used = true WHERE id = :id AND used = false;
-- proceed only if exactly one row was updated

Use transactions, unique constraints, row locks, or atomic compare-and-set operations, and test with parallel requests.

§2Abusing Legitimate Flows

The OWASP API lesson listed unrestricted access to sensitive business flows. Typical examples:

  • Coupon, referral, and free-trial abuse through many fake accounts.
  • Scalping and inventory hoarding with bots.
  • Bulk scraping through a legitimate search endpoint.
  • Skipping workflow steps by calling a later endpoint directly, such as shipping before payment.
  • Negative or fractional quantities, or currency rounding, that produce credits.

Defenses are mostly design: enforce workflow state on the server, validate business rules (quantities, limits, price) server-side, set per-account and per-device quotas, and require stronger verification for high-value actions.

§3Automated Account Takeover and Bots

The credential-stuffing defenses from Stage 1.3 scale up here. Combine signals, since any single one is evaded:

  • Rate limits across account, IP, device, and behavior.
  • Risk scoring that challenges unusual logins with step-up verification.
  • Bot detection and proof-of-work or challenge pages for abuse-prone endpoints.
  • Monitoring for business-level anomalies, such as unusual redemption rates, that infrastructure metrics won't show.
Why scanners miss these A scanner knows how to find missing escaping, not that a coupon should work once. Business-logic security needs people who understand the rules, plus abuse cases and tests written from the attacker's point of view.

§4Common Mistakes

MistakeWhat HappensFix
Checking a limit, then updating separatelyParallel requests all pass the checkMake the check-and-update a single atomic operation
Trusting the client to follow the workflowSteps are skipped by calling later endpoints directlyTrack and enforce state transitions on the server
Only monitoring system metricsBusiness abuse looks like normal trafficAdd alerts on business-level anomalies
Practice
  1. Write a test that sends 20 simultaneous redemption requests for a single-use code and asserts exactly one succeeds.
  2. Pick a multi-step checkout and list every step an attacker might skip or repeat.
Key takeaways
  • Race conditions break check-then-act logic, so make claims atomic.
  • Enforce workflow state and business rules on the server, not in the client.
  • Monitor business-level anomalies, since attacks may look like ordinary traffic.
