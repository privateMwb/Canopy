Logging, Detection & Audit Trails

You can't respond to what you can't see, so logging and detection decide whether an intrusion lasts hours or months, and the logs have to be trustworthy to be useful.

§1What to Log

Log the events a defender will need to reconstruct an incident, each with who, what, where, when, and the outcome.

  • Authentication: logins, failures, MFA challenges, password resets, session creation and revocation.
  • Authorization: denied access, especially repeated denials by one user.
  • Sensitive actions: privilege changes, data exports, configuration and key changes, admin operations.
  • Input anomalies: validation failures, blocked requests, malformed tokens.

Use structured logs (JSON) with a request or correlation ID so one action can be followed across services.

§2What Never to Log

Passwords, session tokens, API keys, full card numbers, and other secrets don't belong in logs, because logs are widely readable and long-lived. Redact or hash sensitive fields before writing them, and be careful with request bodies and URLs. Also sanitize log input: an attacker who can insert newlines into a logged value can forge fake log lines (log injection).

§3Tamper-Evident Logs

An attacker's first move is often to erase their tracks. Ship logs off the host immediately to a separate, append-only system the compromised machine can't alter. You can also chain entries by hash, as in Stage 1.2: each entry includes the hash of the previous one, so removing or changing an old entry breaks every hash after it.

entry_n = { event, time, prev_hash: H(entry_{n-1}) }
# editing or deleting entry_k changes H(entry_k), so entry_{k+1} no longer matches

§4From Logs to Detection

Detection turns events into alerts: impossible travel, a burst of failed logins then a success, a service account used from a new place, a large export by a user who never exports. The DevOps track's alerting lesson applies directly: alert on conditions that need a human, tune out noise, and attach a runbook. Test detections by simulating the behavior, because an alert that has never fired is unproven.

Logs are evidence In an incident, logs answer what happened and how far it went. Retention, integrity, and access control for logs matter as much as the application's own security.

§5Common Mistakes

MistakeWhat HappensFix
Logging secrets and tokensA log leak becomes a credential leakRedact sensitive fields before writing
Keeping logs only on the host they describeAn attacker deletes the evidenceForward to a separate, append-only store
Collecting everything but alerting on nothingNobody notices the intrusionDefine a few high-signal detections and test them
Practice
  1. List ten events your application should log for a login system, with the fields each must include.
  2. Write a detection rule for "many failed logins followed by a success from the same IP" and describe how you'd test it.
Key takeaways
  • Log security-relevant events with who, what, where, when, and the outcome, and never secrets.
  • Store logs off-host and make them tamper-evident.
  • Turn logs into tested, low-noise detections tied to a response.
