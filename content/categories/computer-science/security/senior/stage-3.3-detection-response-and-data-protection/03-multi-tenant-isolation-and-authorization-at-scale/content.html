Multi-Tenant Isolation & Authorization at Scale

In a multi-tenant system, one missing check lets one customer see another's data, so isolation has to be designed in layers, not left to each developer remembering.

§1Where Tenant Boundaries Live

The SQL track showed row-level security as a database-level safety net. Isolation can sit at several layers, and stronger layers cost more.

Isolation modelHow it worksTradeoff
Shared tables, tenant columnEvery query filters by tenant_idCheapest; one missed filter leaks data
Shared tables plus row-level securityThe database enforces the filterSafety net; performance and role care needed
Schema or database per tenantSeparate namespacesStronger isolation; more operational overhead
Separate deployment per tenantFully separate stacksStrongest; highest cost

Pick the level by data sensitivity and contractual needs, and carry the tenant identity through every request, derived from the authenticated session, never from a user-supplied parameter.

§2The Confused Deputy

A confused deputy is a service with legitimate power that is tricked into using it on an attacker's behalf. Example: a reporting service can read every tenant's data, and a user passes a report ID belonging to someone else. The service uses *its* authority instead of the *caller's*.

  • Propagate the caller's identity to downstream services, and authorize against it, instead of checking only that the calling service is allowed.
  • Use scoped, short-lived tokens that carry the user and tenant, not a broad service credential.
  • Never accept a tenant or user ID from the request body as an authority; derive it from the verified token.

§3Authorization at Scale

When many services must agree on who may do what, per-service if statements drift apart. A shared policy engine (for example OPA or Cedar, mentioned in Stage 2.3) lets you define rules once, test them, version them, and audit decisions. Keep a decision log of what was allowed and denied, and test isolation explicitly: automated tests that act as tenant A and try every endpoint against tenant B's objects.

Defense in depth for isolation Combine layers: the application derives tenant from the session, the data layer filters by default, and the database enforces row-level rules. A bug in one layer shouldn't expose another customer's data.

§4Common Mistakes

MistakeWhat HappensFix
Taking tenant_id from the requestA user claims someone else's tenantDerive tenant from the authenticated identity
Services authorizing the calling service, not the userA confused deputy exposes cross-tenant dataPass user identity and authorize against it
No cross-tenant testsIsolation bugs ship unnoticedAutomate tenant-A-versus-tenant-B access tests for every endpoint
Practice
  1. Write a test harness that creates two tenants and checks that every endpoint rejects cross-tenant access.
  2. Describe how a reporting service could become a confused deputy in a system you know, and how to fix it.
Key takeaways
  • Choose an isolation level by sensitivity, and layer application, data, and database controls.
  • Derive tenant and user identity from verified credentials and propagate it downstream.
  • Centralize authorization policy and test cross-tenant access automatically.
