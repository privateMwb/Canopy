Padding Oracles & Other Decryption Oracles

A decryption oracle is any behavior of a system that reveals whether decrypted data was valid, and attackers can use that tiny signal, repeated many times, to decrypt data without the key.

§1The Padding Oracle

CBC mode needs the plaintext padded to a whole number of blocks. After decrypting, the receiver checks the padding. If the server answers differently for bad padding than for good padding but bad content (a different error message, status code, or response time), it has become an oracle.

server receives ciphertext
  decrypt → check padding
     bad padding        → error A
     good padding       → continue, then maybe error B    # A vs B leaks a bit of information

Because CBC XORs each decrypted block with the previous ciphertext block, an attacker who can alter the previous block can steer the decrypted bytes and observe whether the padding became valid. Repeating this lets them recover plaintext one byte at a time, typically a few hundred requests per byte, with no knowledge of the key. This was described by Vaudenay in 2002, and variants such as POODLE and Lucky Thirteen hit real TLS deployments.

§2The General Lesson

The cryptography wasn't broken. The *error behavior* was. The same pattern appears elsewhere: Bleichenbacher's attack on RSA PKCS#1 v1.5 encryption uses whether a decrypted message was well formed, and several JSON Web Encryption and XML encryption implementations leaked the same way. Any system where an attacker can submit modified ciphertext and learn something from the response is a candidate.

§3Fixes

  • Use authenticated encryption (AEAD). The tag is verified before anything is decrypted or parsed, so modified ciphertext is rejected with one uniform failure and no padding step is exposed.
  • If stuck with CBC, encrypt-then-MAC and verify the MAC (in constant time) before touching padding.
  • Return a single generic error for every decryption or validation failure, with the same timing and size.
  • Rate-limit and alert on floods of malformed ciphertexts, which look like oracle probing.
The rule Never process data before authenticating it, and never let the way you fail reveal why you failed. Order of checks is a security property.

§4Common Mistakes

MistakeWhat HappensFix
Decrypting first, then validatingError behavior leaks information about the plaintextVerify the authentication tag before decrypting or parsing
Different error messages for padding, MAC, and parse failuresEach difference is an oracleReturn one generic failure
Relying on CBC with padding in new designsPadding oracle exposure remains a riskUse AES-GCM or ChaCha20-Poly1305
Practice
  1. Review an encryption helper in your codebase and list every distinct error path after a modified ciphertext is submitted.
  2. Explain in four sentences why verifying the MAC first removes the padding oracle.
Key takeaways
  • An oracle is any observable difference that reveals whether decryption or parsing succeeded.
  • Verify authenticity before decrypting, and fail with one uniform error.
  • Prefer AEAD so malformed ciphertext is rejected before it is processed.
