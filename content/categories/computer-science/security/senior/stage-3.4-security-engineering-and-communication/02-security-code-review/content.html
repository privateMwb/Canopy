Security Code Review

Security code review is a way of reading: follow untrusted data from where it enters to where it is used, and check every trust decision on the way.

§1Sources, Sinks, and Taint

A source is where untrusted data enters (request parameters, headers, files, queues, third-party responses). A sink is where data does something dangerous (a SQL call, a shell command, an HTML output, a file path, a deserializer, an outbound request). The review question is: can data from a source reach a sink without proper handling?

source:  request.args["url"]
   │
   ├─ validated? (scheme, host, resolved IP)
   ▼
sink:    http_client.get(url)        ← SSRF if the answer is no

§2A Review Checklist

  • Authentication: is it required on every route, and where is it enforced?
  • Authorization: is there a function-level *and* object-level check, and is the identity from the verified session?
  • Input handling: what are the sources, and is each handled for its sink's context?
  • Cryptography: are primitives from a vetted library, with random nonces and constant-time comparison? Any custom schemes?
  • Secrets: any in code, logs, or error messages?
  • Error handling: do failures fail closed, and do messages avoid leaking details?
  • Concurrency: are check-then-act sequences atomic?

§3Patterns to Search For

Search for dangerous sinks and risky shortcuts, then trace backwards. Common flags: string-built SQL, os.system, eval, pickle.loads, innerHTML, disabled certificate verification, verify=False, md5, random used for tokens, a new endpoint without the standard auth decorator, and TODO: add auth. Read what is missing too: the endpoint with no check is invisible in a diff that only shows added lines.

§4Reviewing Well

  • Review design and diff together: ask what the change is meant to do, then whether it does only that.
  • Write findings as specific, fixable comments with a short explanation of the impact, not a bare "insecure."
  • Prioritize the riskiest changes: auth, crypto, parsers, payments, anything crossing a trust boundary.
  • Use tools for breadth and humans for judgment.
Read for absences The most serious bugs are often a check that isn't there. Compare each endpoint to its siblings: if all the others verify ownership and this one doesn't, that's the finding.

§5Common Mistakes

MistakeWhat HappensFix
Reviewing only the added linesMissing checks and changed context stay invisibleRead the surrounding code and compare to similar endpoints
Looking only for known bad functionsLogic and authorization flaws passTrace data flow and check each trust decision
Vague review commentsDevelopers don't know what to fix or why it mattersState the impact and a concrete fix
Practice
  1. Pick one endpoint in a project and list its sources, sinks, and the checks between them.
  2. Review a recent pull request touching authentication using the checklist, and write two specific comments.
Key takeaways
  • Trace untrusted data from sources to sinks, checking every trust decision.
  • Use a checklist covering authn, authz, input, crypto, secrets, errors, and concurrency.
  • Look for what's missing, and write specific, fixable findings.
