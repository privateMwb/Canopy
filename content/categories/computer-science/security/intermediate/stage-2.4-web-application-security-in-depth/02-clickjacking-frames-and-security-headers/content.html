Clickjacking, Frames & Security Headers

A handful of response headers switch off whole classes of browser-side attacks, but only if you know what each one actually stops.

§1Clickjacking

In clickjacking, an attacker loads your page in an invisible frame over a decoy and tricks the user into clicking a real button on your site, such as "delete account." The fix is to say who may frame you.

Content-Security-Policy: frame-ancestors 'none'     # or 'self', or a specific origin
X-Frame-Options: DENY                               # older equivalent, still widely sent

§2The Everyday Headers

§3Cookie Hardening

Beyond Secure, HttpOnly, and SameSite, the __Host- cookie prefix tells the browser to accept the cookie only if it is Secure, has Path=/, and has no Domain attribute. That prevents a sibling subdomain from overwriting it.

Set-Cookie: __Host-sid=<random>; Secure; HttpOnly; SameSite=Lax; Path=/

§4Don't Over-Trust Headers

Security headers are defense in depth: they harden the browser's behavior but don't fix vulnerable code. Test with a header scanner, such as an online security-headers checker or your browser's DevTools, but don't treat a perfect score as proof the app is secure.

Pick the right one frame-ancestors is about who may *embed you*. CSP frame-src is about what *you* embed. They're different and are easy to confuse.

§5Common Mistakes

MistakeWhat HappensFix
Leaving pages frameable that perform actionsClickjacking tricks users into clickingSend frame-ancestors 'none' or 'self'
Serving uploads without nosniffThe browser may run user content as scriptAdd X-Content-Type-Options: nosniff and a correct Content-Type
Treating headers as a replacement for secure codeApplication bugs remain exploitableUse headers as an additional layer
Practice
  1. Check the response headers of a site you build with curl -I and list which of the above are missing.
  2. Try embedding your own page in an <iframe> on a test page before and after adding frame-ancestors 'none'.
Key takeaways
  • frame-ancestors stops clickjacking, and nosniff stops type confusion.
  • Referrer, permissions, and cross-origin headers reduce leaks and unused-feature risk.
  • Headers harden the browser but don't fix vulnerable application code.
