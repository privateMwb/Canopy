Authenticated Encryption: AES-GCM & ChaCha20-Poly1305

Authenticated encryption protects both secrecy and integrity in one step, and its one great weakness is that a repeated nonce under the same key can destroy it.

§1What AEAD Gives You

AEAD (Authenticated Encryption with Associated Data) encrypts a message and attaches an authentication tag. On decryption, any change to the ciphertext, the nonce, or the associated data makes verification fail and no plaintext is released. The TLS lesson named AES-GCM and ChaCha20-Poly1305 as the bulk ciphers; this is how they behave.

from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os
key  = AESGCM.generate_key(bit_length=256)
aead = AESGCM(key)
nonce = os.urandom(12)                                  # 96-bit nonce, unique per message
ct = aead.encrypt(nonce, b"balance=100", b"user:7")     # last argument is associated data
pt = aead.decrypt(nonce, ct, b"user:7")                 # raises InvalidTag if anything changed

Associated data is authenticated but not encrypted. Use it to bind a ciphertext to its context, such as a user ID or record ID, so an attacker can't copy a valid ciphertext into a different record.

§2The Nonce Rule

With AES-GCM and ChaCha20-Poly1305, the nonce must never repeat under the same key. In GCM, reuse reveals the XOR of the two plaintexts and lets an attacker recover the authentication key and forge messages. In practice:

  • Random 96-bit nonces are acceptable only up to a limit, since collisions become likely after about 2^32 messages under one key. Rotate keys before that.
  • Counters avoid collisions but require reliable state, which is risky across restarts and multiple servers.
  • Misuse-resistant or extended-nonce designs, such as XChaCha20-Poly1305 (192-bit nonces) or AES-GCM-SIV, make random nonces safe or forgive reuse.

§3Use a High-Level Library

Libraries such as libsodium (its secretbox API) and Google's Tink choose algorithms, handle nonces, and give you one encrypt and one decrypt. They remove most of the decisions that cause real-world failures. Verification failure should be handled as a hard error, never as an invitation to try again with a different mode.

Verify before use Decrypt-then-check is a classic mistake. An AEAD API verifies the tag first and returns nothing on failure. If you assemble the parts yourself, you get to recreate the attacks that the combined API prevents (Stage 3.2).

§4Common Mistakes

MistakeWhat HappensFix
Reusing a nonce with the same keyPlaintext leaks and the authentication key can be recoveredUse unique nonces, rotate keys, or choose an extended-nonce construction
Leaving context out of associated dataValid ciphertext can be moved between records or usersBind ciphertexts to their context with associated data
Ignoring decryption failure or falling backTampered data is processed or attackers learn from error differencesTreat failure as fatal and return a generic error
Practice
  1. Encrypt a record with AES-GCM, flip one byte of the ciphertext, and confirm decryption raises an error.
  2. Design a nonce scheme for a service with ten servers writing under one key, and say how you'd rule out collisions.
Key takeaways
  • AEAD provides confidentiality and integrity together and releases no plaintext on failure.
  • Never repeat a nonce under the same key; rotate keys or use extended-nonce schemes.
  • Use associated data to bind ciphertext to context, and prefer high-level libraries.
