Cross-Site Scripting (XSS)

Cross-site scripting happens when a site puts attacker-controlled text into a page in a way the browser runs as script, giving the attacker the user's session and powers.

§1How XSS Works

A browser trusts every script in a page equally, and scripts in a page run with that site's authority. If an attacker can get their script into your page, it can read the DOM, act as the user, and send data anywhere.

<!-- Server builds this with unescaped input -->
<p>Results for: <b>USER_INPUT</b></p>

<!-- If USER_INPUT is: <script>send(document.cookie)</script> -->
<!-- the browser executes it as part of your site -->

§2Three Kinds

TypeWhere the payload livesExample
ReflectedIn the request; bounced back in the responseA search page that echoes the query, delivered via a crafted link
StoredIn the database, shown to other usersA comment or profile name containing script
DOM-basedHandled entirely in client-side JavaScriptCode that writes location.hash into the page with innerHTML

Stored XSS is the most damaging, since it hits every visitor without them clicking anything special.

§3What an Attacker Can Do

  • Perform actions as the user, such as changing an email or sending messages, with no password needed.
  • Read anything on the page, including personal data and anti-CSRF tokens.
  • Steal a session cookie, unless it's marked HttpOnly. Even then the script can still *use* the session by making requests from the user's browser.
  • Rewrite the page to phish credentials.

The core defense is to encode output for its context, covered next, with HttpOnly cookies and Content-Security-Policy (Stage 2.4) as additional layers.

The key insight HttpOnly stops script from reading the session cookie, but XSS can still act as the user from inside their browser. It limits one kind of theft; it doesn't make XSS harmless.

§4Common Mistakes

MistakeWhat HappensFix
Inserting user text into HTML with innerHTMLScript and event handlers in the text runUse textContent, or a framework's escaping by default
Thinking only <script> tags are dangerousEvent attributes and URLs like javascript: also executeEncode for the exact output context
Trusting your own database outputStored data from other users fires laterEncode at output every time
Practice
  1. In a local practice app, find a field that reflects input and show that special characters are escaped on output.
  2. List three places in a page where untrusted text could end up: HTML body, an attribute, and a JavaScript string, and note that each needs different escaping.
Key takeaways
  • XSS runs attacker script with your site's authority in the victim's browser.
  • Reflected, stored, and DOM-based XSS differ in where the payload travels.
  • HttpOnly helps, but only output encoding fixes the cause.
