Reproducibility

Seeds, environments, and versioning — making sure a result today can be recreated tomorrow.

§1Why Results Silently Stop Reproducing

A model trained today can give different results tomorrow for reasons that have nothing to do with the code changing: random initialization, library version differences, or even which GPU it ran on. Reproducibility is about controlling the sources of that silent drift.

§2Setting Random Seeds

import random, numpy as np, torch

random.seed(42)
np.random.seed(42)
torch.manual_seed(42)

Many steps in ML involve randomness — data shuffling, weight initialization, dropout. Setting a fixed seed makes that randomness deterministic, so the same code with the same seed produces the same result every time.

§3Pinning Environments

# requirements.txt, with exact versions, not loose ranges
numpy==1.26.4
scikit-learn==1.4.2
torch==2.2.1

Library updates sometimes change default behaviors or numerical results subtly. Pinning exact versions (not just "numpy>=1.20") means your environment can be recreated exactly, months later.

§4Versioning Data, Not Just Code

Code gets versioned in git almost automatically. Data often doesn't — but if the training dataset changes (even by a few rows) without being tracked, "reproducing" the old result becomes impossible even with identical code. Tools like DVC extend version control to datasets and model artifacts, not just code.

§5Common Mistakes

MistakeWhat HappensFix
Setting a seed for NumPy but not PyTorch (or vice versa)Partial determinism — results still vary run to runSeed every library that introduces randomness in your pipeline
Using loose version ranges in requirementsA future install can silently pull a different library versionPin exact versions for anything affecting results
Practice
  1. Write the seed-setting code needed at the start of a PyTorch training script.
  2. In one or two sentences, explain why "the code hasn't changed" doesn't guarantee reproducibility on its own.
Key takeaways
  • Random seeds make otherwise-random steps deterministic and repeatable.
  • Pinning exact library versions prevents silent behavior changes from updates.
  • Data needs versioning too — code alone isn't enough to reproduce a result.
