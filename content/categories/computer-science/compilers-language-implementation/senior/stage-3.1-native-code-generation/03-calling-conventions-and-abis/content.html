Calling Conventions & ABIs

A calling convention is the agreement that lets separately compiled code call each other: where arguments go, where results come back, and who preserves which registers.

§1Why an agreement is needed

When your compiled function calls another, both must agree on where the arguments are. If caller and callee were compiled separately, perhaps by different compilers, they can't negotiate. The ABI (application binary interface) fixes the rules, and a calling convention is its part about calls.

call add(3, 4)
    caller: put 3 and 4 where the callee expects them, then call
    callee: reads its arguments from those places, puts the result where the caller expects it

For example, the System V x86-64 convention uses rdi, rsi, rdx, rcx, r8, r9 for the first six integer arguments and rax for the return value. Other platforms use other registers, but the idea is the same.

§2Caller-saved and callee-saved registers

A call can overwrite registers, so someone must preserve live values across it. The convention splits the registers:

  • Caller-saved (volatile): the callee may freely change them. If the caller needs a value in one across a call, it saves it first.
  • Callee-saved (non-volatile): the callee must restore them before returning. If it wants to use one, it saves the old value in its prologue.
my_function:
    push rbx                  # prologue: save a callee-saved register we will use
    mov  rbx, rdi             # keep our argument across the call below
    call helper               # helper may clobber caller-saved registers
    add  rax, rbx             # rbx is still ours
    pop  rbx                  # epilogue: restore it
    ret

The register allocator uses this: values live across calls go in callee-saved registers if possible, so the caller needn't save and restore them around every call.

§3Stack frames

Each call has a stack frame that holds saved registers, spilled values, local arrays, and sometimes arguments past the first few.

high addresses
 ┌─────────────────────┐
 │ caller's arguments   │  (extra arguments, if any)
 ├─────────────────────┤
 │ return address       │  pushed by CALL
 ├─────────────────────┤
 │ saved frame pointer  │
 ├─────────────────────┤
 │ saved registers      │
 │ spilled values       │
 │ locals               │
 └─────────────────────┘ ◄ stack pointer
low addresses

The prologue builds the frame by adjusting the stack pointer and saving registers. The epilogue undoes it before ret. Conventions also require stack alignment at call boundaries (16 bytes on System V x86-64) because some instructions fault on misaligned data.

This is the same idea as the VM's call frames in Stage 2.3, but now it is specified down to the register.

The key insight A calling convention is a contract between compilers. Nothing in the hardware requires it, but without it separately compiled code could never work together.

§4Common Mistakes

MistakeWhat HappensFix
Using a callee-saved register without saving itThe caller's value is destroyed after the call, with strange failures laterSave it in the prologue and restore it in the epilogue
Misaligning the stack at a callA vector instruction in the callee faults, but only sometimesKeep the stack aligned as the ABI demands
Assuming arguments always fit in registersFunctions with many arguments read garbageFollow the ABI's rules for stack-passed arguments
Practice
  1. Write the prologue and epilogue for a function that uses two callee-saved registers and 16 bytes of locals, keeping the stack aligned.
  2. Decide, for a value live across a call, whether it should go in a caller-saved or callee-saved register, and what code the choice adds.
Key takeaways
  • A calling convention fixes where arguments and results go and who preserves which registers.
  • Callee-saved registers survive calls; caller-saved ones don't.
  • The prologue and epilogue build and tear down a stack frame, keeping the stack aligned.
