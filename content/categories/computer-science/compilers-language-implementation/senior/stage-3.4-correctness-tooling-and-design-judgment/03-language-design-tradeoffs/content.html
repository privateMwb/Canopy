Language Design Tradeoffs

Adding a feature to a language costs more than implementing it: it has to be taught, combined with everything else, and supported for as long as the language exists.

§1Features have costs on three axes

When someone proposes a new feature, 'would it be useful?' is only the first question. Weigh each feature across several costs.

  • Implementation cost: how many stages does it touch (parser, checker, IR, VM, optimizer, tooling), and how much new testing does it need?
  • Learning cost: how much more must a programmer know, and how surprising is its behaviour?
  • Interaction cost: how does it combine with every existing feature, and with features not yet imagined?

The third is the one people underestimate. Features multiply: a language with n features has roughly n² pairs that might interact badly.

§2Interactions and irreversibility

Consider adding exceptions to Twig. Each existing feature raises a question.

exceptions × closures:     which handler does a throw inside a closure see?
exceptions × generators:   what if a generator throws after yielding?
exceptions × optimizer:    can any call be reordered? (see Stage 3.3)
exceptions × GC:           how does unwinding keep roots correct?

Most questions have answers, but each answer constrains future design. Once programmers depend on a behaviour, changing it breaks their code. A feature is easy to add and nearly impossible to remove, so a good question is 'what would I regret?'

risky additions:    features that block other things you may want later
safer additions:    features that are orthogonal, small, and removable

Many successful languages remain small by saying no often, and by making existing features compose well, so one general feature replaces several special cases.

§3A way to evaluate proposals

A repeatable checklist keeps decisions consistent.

1. What problem does this solve, with a real example that is painful today?
2. What can people do now, and how bad is the workaround?
3. What are the semantics, precisely, including edge cases and errors?
4. How does it interact with the 5 most related existing features?
5. What does it cost in each stage of the implementation, and in tooling?
6. Could a smaller, more general change solve the same problem?
7. What are we closing off by choosing this design?
8. How would we know in a year if it was a mistake?

Notice that implementation difficulty is only item 5. Features that are easy to build can still be poor ideas, and difficult ones can be worth it. The point is to make the tradeoffs explicit and arguable instead of leaving them to taste.

The key insight Language design is mostly the art of not adding things. Each feature is a permanent commitment that interacts with every other, so the best proposal is often the smallest one that solves the real problem.

§4Common Mistakes

MistakeWhat HappensFix
Judging a feature only by its usefulnessThe language accretes special cases that interact badlyWeigh implementation, learning, and interaction costs together
Designing from one exampleThe feature fits that example and nothing elseGather several real cases and look for the general form
Treating a feature as easily reversibleUsers depend on it and removal breaks their programsDecide as if the feature would be permanent
Practice
  1. Pick two existing Twig features and write out four interactions with a proposed feature (say, operator overloading), noting which are problems.
  2. Take a feature you'd like in Twig, apply the eight-question checklist, and decide whether to add it.
Key takeaways
  • Features cost implementation, learning, and interaction, and the interaction cost grows fastest.
  • Features are easy to add and almost impossible to remove, so decide as if permanent.
  • A checklist makes tradeoffs explicit and the decision defensible.
