Testing Compilers: Differential Testing & Fuzzing

A compiler has an unbounded space of valid inputs, so the best bug-finders generate programs automatically and compare what different implementations do with them.

§1Why hand-written tests aren't enough

Golden tests (Stage 1.4) check what you thought of. Compiler bugs live in what you didn't: unusual combinations of features, odd corner cases, interactions between passes. The space of programs is far too large to enumerate by hand.

Fuzzing generates inputs automatically and watches for failures. For compilers there are two levels.

  • Crash fuzzing: feed random or mutated text and look for crashes and hangs in the front end. Easy to set up, and effective at finding parser bugs.
  • Semantic fuzzing: generate *valid* programs and check that the compiler handles them correctly. Much harder, but finds miscompilation bugs, the worst kind.

§2Differential testing

Checking correctness needs an oracle: some way to know the right answer. For a random program you don't have one, but you can compare implementations.

def differential_test(program):
    results = {}
    results["tree-walker"] = run_interpreter(program)
    results["vm"]          = run_vm(compile(program, opt=0))
    results["vm-opt"]      = run_vm(compile(program, opt=2))
    results["native"]      = run_native(compile_native(program))
    assert len(set(results.values())) == 1, results

If the tree-walker, unoptimized VM, optimized VM, and native build disagree, at least one is wrong, and you didn't need to know the right answer to find that out. The tree-walker you built in Stage 1.3 becomes your reference.

Generating good programs is the hard part. A generator that picks random tokens produces gibberish. A grammar-based generator produces syntactically valid programs, and one that tracks types and scopes produces well-typed, deterministic programs, with no undefined behaviour, so differences can't be blamed on the program.

def gen_expr(depth, env):
    if depth == 0: return random_literal() or random_var(env)
    return Binary(gen_expr(depth - 1, env), random_op(), gen_expr(depth - 1, env))

§3Reducing a failing case

A random program that exposes a bug is usually huge and mostly irrelevant. Before you can debug it, shrink it. Test-case reduction repeatedly tries to delete or simplify parts of the program and keeps each change that still triggers the same failure.

def reduce(program, still_fails):
    changed = true
    while changed:
        changed = false
        for candidate in simplifications(program):   # delete a statement, replace an expr by a literal, ...
            if is_valid(candidate) and still_fails(candidate):
                program = candidate; changed = true; break
    return program

A 500-line failing program often reduces to five lines, and a five-line program tells you what is wrong. Together with a per-pass bisect (Stage 2.4), this gives a systematic path from 'the fuzzer found something' to 'this pass mishandles this construct.'

Every reduced failure should become a permanent regression test.

The key insight You don't need to know the right answer to find a compiler bug, only two implementations that should agree. Randomized programs plus differential comparison turn your own earlier work into a bug detector.

§4Common Mistakes

MistakeWhat HappensFix
Generating programs with undefined or nondeterministic behaviourImplementations disagree for legitimate reasons and the results are noiseGenerate only programs with fully defined semantics
Not reducing failing casesYou debug a 500-line program for hoursAutomate reduction and keep the result as a regression test
Running the fuzzer without recording the random seedA failure can't be reproducedLog the seed with every failure
Practice
  1. Write a generator for random well-typed Twig integer expressions with variables in scope, and use it to check the tree-walker against the VM on 10,000 programs.
  2. Design the simplification steps a reducer for Twig should try, in the order you'd try them.
Key takeaways
  • Fuzzing finds bugs your tests didn't think of; semantic fuzzing needs valid programs.
  • Differential testing compares implementations when you have no oracle.
  • Automated reduction turns a huge failing program into a small, debuggable regression test.
