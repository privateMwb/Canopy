Language Servers & Incremental Compilation

Editors need a compiler that can answer questions about half-written code, instantly, which changes how parsing, analysis, and caching are designed.

§1What a language server does

When you type in an editor with completion, go-to-definition, and live errors, a language server is answering queries: 'what is at this position?', 'where is this defined?', 'what can go here?'. The Language Server Protocol standardizes the conversation, so one server serves many editors.

This is a different workload from a batch compiler.

  • Code is almost always incomplete or wrong while it is being typed.
  • Answers must come in milliseconds, after every keystroke.
  • Only a tiny part of the program changed since the last query.

§2Error-tolerant parsing

A batch compiler can stop at the first syntax error. A language server cannot, since a half-typed line would disable all features for the whole file. The parser must produce a useful tree even from broken input.

fn area(w, h) {
  let a = w *            // the user is still typing
  return a;
}

Panic-mode recovery (Stage 1.2) is a start. Better is to insert error nodes and keep the surrounding structure.

Let(a, Binary(w, *, ErrorExpr("expected expression")))
Return(Variable(a))

The tree remains well-formed, so the resolver and type checker can still tell the editor that a is defined here and w is a parameter, and completion keeps working. Designing the grammar so recovery points are clear, with statement and block delimiters, makes this much easier.

§3Incremental and query-based compilation

Re-running the whole compiler after every keystroke wastes nearly all its work. Incremental compilation recomputes only what could have changed.

The popular architecture treats the compiler as a set of queries, memoized functions of their inputs.

parse(file)          → tree
resolve(file)        → bindings        depends on parse(file)
type_of(function)    → type            depends on resolve(file), type_of(callees)
errors(file)         → diagnostics     depends on all of the above

The system records which queries each result depended on. When a file changes, it invalidates results that depended on it, and recomputes lazily when asked.

def query(key):
    if key in cache and all_dependencies_unchanged(cache[key]): return cache[key].value
    value = compute(key)                  # computing may call other queries, recording them
    cache[key] = (value, dependencies_read_during_compute)
    return value

A subtle optimization is early cutoff: if a function's body changes but its type doesn't, queries that depend only on its type needn't rerun. Good design of what each query returns (for example, signatures separate from bodies) makes incremental recompilation fast.

The key insight A compiler for humans in an editor has to be fast in a different way: not fast at compiling everything, but fast at answering a small question about a mostly unchanged program.

§4Common Mistakes

MistakeWhat HappensFix
Failing the parse on the first errorEvery editor feature stops working while the user is mid-editProduce a tree with error nodes and keep going
Caching by file onlyAny edit invalidates everything in the fileUse fine-grained queries, such as per function, with dependency tracking
Forgetting early cutoffA body-only edit re-checks every callerSeparate signatures from bodies, and stop invalidation when a result is unchanged
Practice
  1. Design the queries for a Twig language server that answers 'what is the type under the cursor?', and list the dependencies of each.
  2. Show how the parser should handle a missing closing brace so that functions after it still get analyzed.
Key takeaways
  • Editors need trees from broken code, so parsers must tolerate errors with error nodes.
  • Query-based compilation caches fine-grained results and tracks what each depends on.
  • Early cutoff stops recomputation when a recomputed result didn't change.
