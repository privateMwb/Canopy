Scanning: Characters to Tokens

A scanner groups raw characters into tokens, the smallest pieces the parser cares about, and throws away everything else.

§1What a token is

The parser should not have to think about spaces, comments, or whether <= is one symbol or two. The lexer (or scanner) handles that, turning text into a flat list of tokens. A token has a type (what kind of thing it is) and often a lexeme (the exact text).

source:  let total = 10 + x;

tokens:  LET            "let"
         IDENT          "total"
         EQUAL          "="
         NUMBER         "10"       value = 10
         PLUS           "+"
         IDENT          "x"
         SEMICOLON      ";"
         EOF

Whitespace and comments produce no tokens. The final EOF token lets the parser ask 'what is next?' without checking for the end of the list.

§2A hand-written scanner

A scanner is a loop with a cursor into the source. It looks at one character, decides what token starts there, and consumes the rest of that token.

# pseudocode
def scan_token():
    c = advance()
    match c:
        '(' : add(LEFT_PAREN)
        '+' : add(PLUS)
        '=' : add(EQUAL_EQUAL if match('=') else EQUAL)
        '<' : add(LESS_EQUAL  if match('=') else LESS)
        ' ', '\t', '\n': pass                  # skip
        '/' : if match('/'): skip_to_end_of_line()
              else: add(SLASH)
        else:
            if is_digit(c): number()
            elif is_alpha(c): identifier()
            else: error("unexpected character")

match('=') consumes the next character only if it equals =. That one-character lookahead is how < and <= are told apart.

§3Numbers, identifiers, and keywords

Numbers and names are runs of characters. Keep reading while the next character still belongs to the token.

def number():
    while is_digit(peek()): advance()
    add(NUMBER, int(text_so_far()))

def identifier():
    while is_alnum(peek()) or peek() == '_': advance()
    word = text_so_far()
    add(KEYWORDS.get(word, IDENT))      # 'while' is a keyword, 'whale' is not

Keywords are not a separate case in the scanner. Scan an identifier first, then look it up in a table. This also follows maximal munch: always take the longest possible token, so iffy is one identifier, never if followed by fy.

The key insight A lexer decides token boundaries using only a character or two of lookahead. Doing that once, up front, keeps every later stage from caring about spelling.

§4Common Mistakes

MistakeWhat HappensFix
Treating keywords as a special scanner caseCode grows a branch per keyword and misses iffy-style namesScan an identifier, then look it up in a keyword table
Stopping at the first non-digit without checking what follows12abc scans as number then identifier with no complaintDecide whether adjacent tokens need a separator, or report it
Forgetting the EOF tokenThe parser reads past the end of the list and crashesAlways append EOF and let the parser stop on it
Practice
  1. Hand-scan if (a <= 10) { print a; } into a token list, showing each type and lexeme.
  2. Extend the scanner sketch to recognise != and ! (Twig has not, so decide whether a lone ! is an error).
Key takeaways
  • A lexer turns characters into tokens, dropping whitespace and comments.
  • One or two characters of lookahead are enough to separate < from <= and numbers from names.
  • Scan identifiers first and use a table for keywords, always taking the longest match.
