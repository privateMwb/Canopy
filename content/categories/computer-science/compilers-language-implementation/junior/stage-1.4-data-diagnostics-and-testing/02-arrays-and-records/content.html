Arrays & Records

Adding arrays and records touches every stage: new syntax, new AST nodes, new runtime values, and new ways for programs to fail.

§1The syntax

Adding a feature means walking the pipeline from front to back. For arrays and records, start with what programs look like.

let nums = [10, 20, 30];
print nums[1];                       // 20
nums[1] = 99;

let p = rec { x: 3, y: 4 };
print p.x + p.y;                     // 7
p.x = 10;

Extend the grammar first, because it makes you decide the awkward cases before writing any code.

primary  = NUMBER | STRING | IDENT | "(" expr ")" | array | record ;
array    = "[" [ expr { "," expr } ] "]" ;
record   = "rec" "{" [ field { "," field } ] "}" ;
field    = IDENT ":" expr ;
postfix  = primary { "[" expr "]" | "." IDENT | "(" [ args ] ")" } ;

Indexing, field access, and calls are all postfix operations, so a[0].name(1) chains left to right.

§2Parser and AST

New constructs get new node types, and assignment now needs to accept more than a bare name on its left.

Expr += ArrayLit(elements)
      | RecordLit(fields)
      | Index(target, index)
      | Field(target, name)

Stmt += AssignIndex(target, index, value)
      | AssignField(target, name, value)

The parser parses the left side as an ordinary expression. If an = follows, it checks that the expression is something assignable (a name, an index, or a field) and builds the matching assignment node. If it is not, report 'invalid assignment target' there.

§3Evaluating them

At run time these are one more case each, and each has failure modes.

        Index(t, i):
            arr = eval(t); idx = eval(i)
            if not is_array(arr): runtime_error("can only index arrays")
            if not is_int(idx):   runtime_error("index must be an integer")
            if idx < 0 or idx >= len(arr): runtime_error("index out of range")
            return arr.items[idx]

        Field(t, name):
            r = eval(t)
            if not is_record(r): runtime_error("only records have fields")
            if name not in r.fields: runtime_error("no field '" + name + "'")
            return r.fields[name]

Notice how many new errors one feature adds. Each is a place where a test should confirm both the message and the position it points at.

The key insight A feature is done only when every stage handles it: grammar, parser, AST, evaluator, and error cases. Walk the pipeline in order and nothing gets forgotten.

§4Common Mistakes

MistakeWhat HappensFix
Allowing only a variable name on the left of =a[0] = 1 and p.x = 2 fail to parseParse the left as an expression, then check that it is assignable
Not bounds-checking indexingThe host crashes, or negative indexes read garbageCheck type and range, and raise a Twig runtime error with a span
Letting arrays be copied on assignment by accidentlet b = a; b[0] = 1; leaves a unchanged when the spec says arrays are referencesDecide the semantics (Twig: references) and make Value hold a reference
Practice
  1. Write the parser code for the postfix rule so that f(1)[2].x parses as field access on an index of a call.
  2. Decide and test what print [1, 2, 3]; should output, and implement a to_string for arrays and records.
Key takeaways
  • New features need work in every stage, starting with the grammar.
  • Index, field, and call are postfix operations that chain left to right.
  • Each new construct brings new runtime errors that deserve tests.
