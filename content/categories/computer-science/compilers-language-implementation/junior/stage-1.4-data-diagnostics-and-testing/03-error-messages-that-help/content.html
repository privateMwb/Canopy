Error Messages That Help

Good error messages are a feature: they show where the problem is, say what went wrong in the programmer's terms, and suggest what to look at next.

§1Anatomy of a diagnostic

A helpful error has four parts: a kind, a message, a location, and the source line with a marker.

error: cannot add string and number
  --> shop.twig:9:20
   |
 9 | print "total: " + count;
   |       ----------   ^^^^^ this is a number
   |       |
   |       this is a string

The position comes from the span stored on AST nodes and tokens (Stage 1.1). The marker is drawn by using col and the span length. Highlighting both operands, not just the operator, tells the reader why it failed.

§2Three kinds of error

Not all errors happen at the same time, and it helps to name them.

  • Syntax errors come from the lexer and parser; the program has no valid tree.
  • Static errors are found by analysis before running (undefined names now; type errors in Stage 2.1).
  • Runtime errors happen during execution and depend on actual values.
let x = ;               // syntax error: expected expression
print y;                // runtime error today, static error after Stage 2.1
print 1 / 0;            // runtime error: division by zero

A good implementation reports all errors of the earlier kinds before running anything, and a runtime error includes a stack trace of the Twig calls that led to it.

§3A diagnostics module

Don't print errors from random places. Build one place that formats them, and give every stage the same Diagnostic type.

struct Diagnostic { severity, message, span, notes: [string] }

def report(d, source):
    line_text = source.line(d.span.start_line)
    print(d.severity + ": " + d.message)
    print("  --> " + d.span.file + ":" + d.span.line + ":" + d.span.col)
    print(" " + d.span.line + " | " + line_text)
    print("   | " + " " * (d.span.col - 1) + "^" * d.span.length)

Stages return Diagnostic values rather than printing. That makes errors testable (compare the list) and lets a future editor tool show them in its own way.

The key insight An error message is the part of the compiler the programmer reads most. Time spent making it precise pays back on every mistake anyone ever makes in your language.

§4Common Mistakes

MistakeWhat HappensFix
Printing errors where they are foundFormats drift apart and tests have to capture outputReturn Diagnostic values and format them in one place
Reporting only a line numberThe reader must hunt for the problem within the lineShow the line and mark the exact span
Messages in implementation terms ('unexpected token type 14')The programmer can't act on themSay what was expected and what was found in the language's own words
Practice
  1. Write the error you would want for calling a function with the wrong number of arguments, including both the call site and the function's declaration.
  2. Implement report for spans that cover more than one line, and decide how to render them.
Key takeaways
  • A diagnostic has a kind, a message, a span, and a marked source line.
  • Syntax, static, and runtime errors happen at different times and deserve different handling.
  • Stages return diagnostics as data, and one module formats them.
