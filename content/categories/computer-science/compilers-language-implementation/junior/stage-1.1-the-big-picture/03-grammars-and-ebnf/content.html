Grammars & EBNF

A grammar states exactly which strings are programs, using a few rules in a notation precise enough to turn into a parser.

§1Rules that generate programs

A grammar is a set of rules saying how bigger pieces of a language are built from smaller ones. We write them in EBNF (extended Backus–Naur form). A rule has a name on the left, a definition on the right, and ends with ;.

program    = { statement } ;
statement  = printStmt | letStmt ;
printStmt  = "print" expr ";" ;
letStmt    = "let" IDENT "=" expr ";" ;

Quoted text is a literal token. | means 'or'. { x } means zero or more repetitions of x, [ x ] means optional, and ( ... ) groups. Names in lowercase are nonterminals (defined by another rule); quoted strings and names like IDENT are terminals (single tokens).

§2Expressions and ambiguity

Expressions are where grammars get interesting. A naive rule looks right but is ambiguous: one string has more than one tree.

expr = expr "-" expr | NUMBER ;     # ambiguous!

1 - 2 - 3   can parse as   (1 - 2) - 3   = -4
                     or    1 - (2 - 3)   = 2

An ambiguous grammar cannot define a language, because two implementations could pick different trees and compute different answers. The fix is to build precedence and associativity into the layers of the grammar.

expr   = term   { ( "+" | "-" ) term } ;
term   = factor { ( "*" | "/" ) factor } ;
factor = NUMBER | "(" expr ")" ;

term sits below expr, so * binds tighter than +. The repetition { ... } groups to the left, giving 1 - 2 - 3 only one reading: (1 - 2) - 3.

§3From grammar to parser

EBNF is not just documentation. Each rule becomes a function in a hand-written parser (Stage 1.2), so the grammar is both the specification and the blueprint. The order of layers is the precedence table.

# precedence from loosest to tightest, in Twig
or  <  and  <  == !=  <  < <= > >=  <  + -  <  * / %  <  unary - not  <  call [] .
The key insight Precedence is not a separate feature to bolt on. It falls out of how the rules are layered: the deeper a rule sits, the tighter its operators bind.

§4Common Mistakes

MistakeWhat HappensFix
Writing expr = expr op exprThe grammar is ambiguous, so the language has no single meaningLayer rules by precedence and loop with { } for left associativity
Putting + and * in the same ruleThey get the same precedence and 1 + 2 * 3 can become 9Give * its own, deeper rule
Mixing up terminals and nonterminalsThe parser tries to match a rule name as if it were textQuote literal tokens; leave rule names bare
Practice
  1. Write EBNF for Twig's if statement with an optional else, using block = "{" { statement } "}" ;.
  2. Show with two trees why a - b - c is ambiguous under expr = expr "-" expr | NUMBER, then rewrite the rule to remove the ambiguity.
Key takeaways
  • EBNF rules define which strings are programs; |, { }, and [ ] cover choice, repetition, and optional parts.
  • An ambiguous grammar gives one string several trees and must be fixed.
  • Layering rules encodes precedence, and each rule becomes a function in a hand-written parser.
