Closures & Captured Variables

A closure is a function bundled with the environment it was created in, so it keeps access to variables long after the code that made them has finished.

§1The counter example

fn make_counter() {
  let n = 0;
  return fn() {
    n = n + 1;
    return n;
  };
}

let a = make_counter();
let b = make_counter();
print a();   // 1
print a();   // 2
print b();   // 1

When make_counter returns, its call is over, yet a can still read and change n. Each call to make_counter created a separate n, which is why b starts from 1.

§2Why it already works

The previous lesson built a function value with a closure field, and a call parents its environment on that field. That is the whole mechanism.

        FnExpr(params, body):                  # anonymous function
            return Function(null, params, body, closure = env)

env here is make_counter's call environment, the one holding n. Because the function object references it, the environment stays alive after the call returns, and the host's memory management keeps it around for as long as a does.

global env: { make_counter, a, b }
                       a ──► Function(closure ─► env1 { n: 2 })
                       b ──► Function(closure ─► env2 { n: 1 })

§3What gets captured

A closure captures variables, not their values at that moment. Two closures that share an environment share the variable.

fn pair() {
  let x = 0;
  let inc = fn() { x = x + 1; };
  let get = fn() { return x; };
  return rec { inc: inc, get: get };
}

let p = pair();
p.inc();
print p.get();     // 1  (both closures see the same x)

This is simple in a tree-walker, where whole environments are heap objects. In a VM that keeps locals on a stack, the same behaviour needs extra machinery (upvalues), which is the topic of Stage 2.3.

The key insight Closures need no special feature in a tree-walking interpreter. They fall out of storing the defining environment in the function value.

§4Common Mistakes

MistakeWhat HappensFix
Capturing the caller's environment instead of the defining oneFunctions see the wrong variables, and closures stop workingCapture env when the function expression is evaluated, not when it is called
Copying variable values into the closureMutations through one closure aren't seen by anotherCapture the environment (the variables), not a snapshot of values
Creating all loop-body closures in one shared environmentEvery closure sees the final value of the loop variableCreate a fresh environment per iteration if each should have its own variable
Practice
  1. Write a Twig make_adder(n) that returns a function adding n to its argument, and predict what make_adder(3)(4) prints.
  2. Explain what happens in the pair example if you change get to fn() { let x = 5; return x; }.
Key takeaways
  • A closure is a function plus the environment it was defined in.
  • It captures variables, so closures sharing an environment share the variable.
  • In a tree-walking interpreter, storing the defining environment is the whole implementation.
