Evaluating Expressions

A tree-walking interpreter evaluates a program by recursing over its AST and doing what each node says.

§1One function, one case per node

The simplest interpreter is a function eval(node) that returns the value of an expression. Each kind of node gets one case, and the case recurses into its children first.

# pseudocode
def eval(e):
    match e:
        Literal(v):        return v
        Unary(op, x):
            v = eval(x)
            if op == MINUS: return -check_int(v, op)
            if op == NOT:   return not truthy(v)
        Binary(l, op, r):
            a = eval(l)
            b = eval(r)
            return apply(op, a, b)

The tree already encodes precedence, so there is no precedence logic here at all. 1 + 2 * 3 is Binary(1, +, Binary(2, *, 3)), and evaluating the children first gives 7 for free.

§2Runtime values and type checks

Twig is dynamically typed, so each value carries its own type and operators check it when they run.

def apply(op, a, b):
    match op:
        PLUS:
            if is_int(a) and is_int(b): return a + b
            if is_str(a) and is_str(b): return a + b
            runtime_error("'+' needs two numbers or two strings", op)
        STAR:
            return check_int(a) * check_int(b)
        EQUAL_EQUAL: return values_equal(a, b)
        LESS:        return check_int(a) < check_int(b)
        SLASH:
            if check_int(b) == 0: runtime_error("division by zero", op)
            return check_int(a) // check_int(b)

A runtime error carries the node's source span so the message can point at the exact operator that failed.

§3Short-circuit operators

and and or cannot use the pattern above, because they must not evaluate the right side when the left side decides the answer.

        Logical(l, op, r):
            a = eval(l)
            if op == OR  and truthy(a): return a
            if op == AND and not truthy(a): return a
            return eval(r)                   # only now look at the right side

Twig returns the deciding operand itself, not true or false, so nil or 5 is 5. This is one of the semantic rules from Stage 1.1, and it shows why the rules have to be written down: evaluating both sides would be simpler and wrong.

The key insight An interpreter is the language's semantics written as code. Each case in eval is one sentence of the specification.

§4Common Mistakes

MistakeWhat HappensFix
Evaluating both sides of and / orSide effects and errors on the right happen even when they should be skippedEvaluate the left, decide, and evaluate the right only if needed
Using the host language's + on any valuesConfusing results like adding a string to an int silentlyCheck operand types and report a runtime error with a span
Not checking for division by zeroThe host crashes instead of reporting a Twig errorCheck the divisor and raise a runtime error
Practice
  1. Write eval cases for == and != on mixed types, deciding what 1 == "1" and nil == false should give.
  2. Trace eval by hand on -(2 + 3) * 4, writing each recursive call and its result.
Key takeaways
  • eval has one case per node kind and recurses into children first.
  • Dynamic typing means operators check operand types at run time and report errors with spans.
  • and and or must short-circuit, so they get their own case.
