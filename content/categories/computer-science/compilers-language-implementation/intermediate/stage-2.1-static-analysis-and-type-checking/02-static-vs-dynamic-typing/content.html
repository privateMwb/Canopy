Static vs. Dynamic Typing

A static type system proves, before the program runs, that certain mistakes cannot happen, in exchange for rejecting some programs that would actually have worked.

§1What a type is, and what checking buys

A type is a claim about the set of values an expression can produce. int means 'always an integer'. A static type checker verifies those claims for the whole program without running it.

fn double(n: int): int { return n * 2; }

print double(4);          // fine
print double("four");     // static error: expected int, found str

The dynamic interpreter would only report the second error if that line ran, and only after doing earlier work. The static checker rejects the program up front.

§2The tradeoff

Types are not free. Static checking is conservative: it must reject any program it cannot prove safe, including some that would run fine.

fn pick(flag) {
  if (flag) { return 1; } else { return "one"; }     // fine dynamically
}

A checker that wants a single return type must reject this, or have a feature (like union types) to describe it. In short:

  • Static typing: earlier errors, better tools and optimization, documentation in the code; more rules to satisfy, and some valid programs rejected.
  • Dynamic typing: more flexible and quicker to start; errors found late, and less information for the compiler.

Neither is better in general. Twig started dynamic and gains optional annotations now, so you can feel both.

§3Types in Twig

The type language we'll check:

type = "int" | "bool" | "str" | "nil"
     | "[" type "]"                          # array of type
     | "fn" "(" [ type { "," type } ] ")" ":" type     # function type

Annotations are optional and written after a name:

let n: int = 3;
let names: [str] = ["a", "b"];
fn add(a: int, b: int): int { return a + b; }
let f: fn(int): int = fn(x: int): int { return x * x; };

Where annotations are missing, the next lessons add inference to fill them in. The checker's job is the same either way: assign every expression a type and check that the types fit together.

The key insight A type checker is a proof system. Soundness means the proof is trustworthy: if the checker accepts a program, the checked kinds of error cannot occur. That guarantee, not the syntax, is what you are buying.

§4Common Mistakes

MistakeWhat HappensFix
Believing static types catch all bugsLogic errors, off-by-one errors, and division by zero still happenBe precise about which errors the type system rules out
Rejecting valid programs without telling the user whyPeople fight the checker without understanding the ruleExplain the conflict and point at both places involved
Mixing up 'dynamically typed' and 'untyped'Values still have runtime types and operators still check themThink of it as checks happening at run time instead of before
Practice
  1. Write a Twig function that is valid dynamically but would be rejected by a checker requiring one return type, and say how you could change the program or the language to accept it.
  2. List five runtime errors from Stage 1.3 and say which a type checker could rule out and which it could not.
Key takeaways
  • A static checker proves claims about types before the program runs.
  • It is conservative: it rejects programs it cannot prove safe, including some valid ones.
  • Soundness is the guarantee that accepted programs avoid the checked errors.
