Type Inference & Unification

Type inference lets the checker work out types you didn't write, by giving unknowns a name and solving for them.

§1Type variables

Requiring an annotation on everything is tedious, and the compiler often has enough information to work them out.

let n = 3;                    // obviously int
let xs = [1, 2, 3];           // obviously [int]
let add = fn(a, b) { return a + b; };    // a and b: ?

For the last line the checker invents type variables: a: α, b: β, and the result γ. Then it collects constraints from how they are used. a + b forces α = int and β = int (or both str), and so on.

§2Unification

Unification is the algorithm that solves 'make these two types equal' by finding values for the type variables.

def unify(t1, t2):
    t1 = resolve(t1); t2 = resolve(t2)           # follow variables already solved
    if t1 == t2: return
    if is_var(t1): bind(t1, t2); return          # α := t2  (after occurs check)
    if is_var(t2): bind(t2, t1); return
    if both_arrays(t1, t2): unify(t1.elem, t2.elem); return
    if both_functions(t1, t2):
        if len(t1.params) != len(t2.params): fail()
        for (a, b) in zip(t1.params, t2.params): unify(a, b)
        unify(t1.result, t2.result); return
    fail("cannot make " + show(t1) + " equal to " + show(t2))

def bind(var, t):
    if occurs(var, t): fail("infinite type")     # α = [α] has no solution
    var.ref = t

The occurs check rejects α = [α], which would describe an infinitely nested type.

§3Hindley–Milner in one idea

The system behind this is called Hindley–Milner. Its central trick is generalization: after checking a let-bound function, any type variables that remain unsolved become universally quantified, so the function can be used at several types.

let id = fn(x) { return x; };       // id : for all T. fn(T): T
print id(3);                        // T = int
print id("hi");                     // T = str

Without generalization, id(3) would fix T = int forever and id("hi") would be an error. With it, each use gets fresh variables. This gives parametric polymorphism without any annotations.

Local inference like let x = 5; is cheap and covers most of the benefit. Full HM-style inference is elegant, but can produce confusing errors far from the real mistake, and many languages stop partway for exactly that reason.

The key insight Inference is constraint solving. Every use of a value adds an equation between types, and unification solves all of them together, instead of you writing the answers down.

§4Common Mistakes

MistakeWhat HappensFix
Skipping the occurs checkSelf-referential types loop the solver foreverCheck whether the variable occurs in the type before binding
Not resolving variables before comparingTwo types that are already equal are reported as differentFollow bindings (resolve) at the start of unify
Reporting the error where unification failedThe message points at a line far from the real mistakeRecord the span of the expression that created each constraint and use it in messages
Practice
  1. Infer by hand the type of fn(f, x) { return f(f(x)); }, writing each type variable and the constraint that solves it.
  2. Write the unification result, or the failure, for unify([α], [int]) and unify(fn(α): β, fn(int): α).
Key takeaways
  • Type variables stand for unknown types, and unification solves equations between types.
  • The occurs check prevents infinite types.
  • Generalization after let is what lets one function be used at several types.
