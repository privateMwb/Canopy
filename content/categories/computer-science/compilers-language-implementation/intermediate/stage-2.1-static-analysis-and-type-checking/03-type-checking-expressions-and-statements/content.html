Type Checking Expressions & Statements

Type checking is a recursive walk over the AST that assigns each expression a type and checks that the types fit the rules.

§1Typing rules

Type systems are written as rules that say 'if the parts have these types, the whole has that type.'

 n is an integer literal              Γ ⊢ a : int    Γ ⊢ b : int
 ───────────────────────              ───────────────────────────
     Γ ⊢ n : int                            Γ ⊢ a + b : int

 Γ ⊢ cond : bool    Γ ⊢ a : T    Γ ⊢ b : T
 ──────────────────────────────────────────
         Γ ⊢ (if cond then a else b) : T

Read Γ ⊢ e : T as 'in the environment Γ, expression e has type T.' Γ (gamma) is the type environment, a map from names to types, built from the scopes the resolver already knows about.

§2From rules to a checker

Each rule becomes one case in a function that returns the type of an expression, reporting an error when a premise fails.

# pseudocode
def check(e, env):
    match e:
        Literal(v):         return type_of_value(v)
        Variable(name):     return env.lookup(name)
        Binary(l, PLUS, r):
            lt = check(l, env); rt = check(r, env)
            if lt == INT and rt == INT: return INT
            if lt == STR and rt == STR: return STR
            error("cannot add " + show(lt) + " and " + show(rt), e.span)
        Call(f, args):
            ft = check(f, env)
            expect_function(ft, f.span)
            if len(args) != len(ft.params): error("wrong number of arguments", e.span)
            for (a, pt) in zip(args, ft.params):
                at = check(a, env)
                if at != pt: error("expected " + show(pt) + ", found " + show(at), a.span)
            return ft.result

This has the same shape as the interpreter's eval, but it computes types instead of values. One pass of this checker visits the entire program, including branches that would never run.

§3Statements, returns, and errors

Statements don't have types, but they have rules. A return must match the enclosing function's declared result, and a condition must be bool.

        If(c, a, b):
            if check(c, env) != BOOL: error("condition must be bool", c.span)
            check_stmt(a); check_stmt(b)
        Return(x):
            t = check(x, env) if x else NIL
            if t != current_function.result:
                error("returns " + show(t) + " but declared " + show(current_function.result), x.span)

Once a subexpression has a type error, the checker should return a special ERROR type that matches everything. That prevents one mistake from creating a flood of follow-up errors.

The key insight A type checker is an interpreter that runs on types instead of values. The same recursion, one case per node, and the same scope handling apply.

§4Common Mistakes

MistakeWhat HappensFix
Comparing types with only == on namesFunction types and array types compare wrongly or not at allCompare types structurally, recursing into components
Returning nil or crashing after the first type errorFollow-up errors flood the outputReturn an ERROR type that unifies with anything
Forgetting to check branches that never runErrors hide in unreachable code until it's usedCheck every branch; the checker doesn't depend on values

Key takeaways
  • Typing rules say what type a whole expression has given the types of its parts.
  • Each rule becomes one case in a recursive check function that mirrors eval.
  • An ERROR type stops one mistake from causing many follow-up messages.
