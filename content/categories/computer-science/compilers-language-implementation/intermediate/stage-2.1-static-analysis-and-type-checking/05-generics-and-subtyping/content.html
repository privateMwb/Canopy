Generics & Subtyping

Generics and subtyping are two different ways to let one piece of code work on many types, and both bring subtle ways to break soundness.

§1Parametric polymorphism

Generics let a function work for any type while keeping the types connected.

fn first<T>(xs: [T]): T { return xs[0]; }

let a: int = first([1, 2, 3]);       // T = int
let b: str = first(["x", "y"]);      // T = str

The key promise is parametricity: first can't inspect a T because it doesn't know what it is, so it can only move values around. The checker treats T as an opaque type inside the body, and picks a concrete type at each call by unification.

check_call(first, [ [int] ]):
    instantiate T with fresh variable α        # fn([α]): α
    unify([α], [int])  →  α = int
    result type: int

§2Subtyping

Subtyping says that a value of type S can be used where type T is expected, written S <: T. If Twig records had structural subtyping, a record with more fields could be used where fewer are needed.

fn show_x(p: rec { x: int }): int { return p.x; }
let q = rec { x: 1, y: 2 };
show_x(q);         // ok if rec{x:int, y:int} <: rec{x:int}

Subtyping comes with variance rules, which say how it extends to compound types:

  • Function results are covariant: if S <: T, then fn(): S <: fn(): T.
  • Function parameters are contravariant: fn(T) <: fn(S). A function that accepts any T can stand in for one that only needs to accept S.
  • Mutable containers are usually invariant, because you can both read and write them.

§3Where soundness breaks

The classic hole is treating mutable arrays as covariant.

# pretend [int] <: [num]  where int <: num
let ints: [int] = [1, 2, 3];
let nums: [num] = ints;          # allowed if arrays were covariant
nums[0] = 3.14;                  # writes a non-int into an array typed [int]
let x: int = ints[0];            # type says int, value is 3.14: unsound

Languages that allow this either add run-time checks on every write or accept the hole. Designing a type system is largely about picking which conveniences to allow, then checking that none of them lets a well-typed program go wrong.

The key insight Every convenience in a type system is a promise. Parametricity, variance, and mutability all interact, and each new feature has to be checked against the others for soundness.

§4Common Mistakes

MistakeWhat HappensFix
Treating generic type parameters as anyThe body can do things that are wrong for some instantiationsTreat T as an opaque type within the body
Making mutable containers covariantA write can break the invariant a read relies onMake mutable containers invariant, or add run-time checks
Mixing up covariance and contravariance for parametersPassing a function that needs more fields is accepted wronglyParameters flip direction: a function accepting more can replace one accepting less
Practice
  1. Write the type of a generic map<A, B>(xs: [A], f: fn(A): B): [B] and show the unification steps for map([1, 2], fn(x: int): str { ... }).
  2. Explain, using the array example, why you can read from a covariant container safely but not write to it.
Key takeaways
  • Generics keep types connected without knowing them, using opaque type parameters inside the body.
  • Subtyping needs variance rules: results covariant, parameters contravariant, mutable data invariant.
  • Soundness holes usually come from interactions between features, not one feature alone.
