Inlining & Loop Optimizations

Inlining removes call overhead and exposes the callee's body to other optimizations, while loop optimizations move or simplify work that repeats.

§1Inlining

Inlining replaces a call with a copy of the called function's body, with arguments substituted for parameters.

fn square(x) { return x * x; }
let y = square(a + 1);

# after inlining:
t = a + 1
y = t * t

The saved call overhead (frame setup, jump, return) is usually small. The real benefit is that the body is now visible in context, so folding, propagation, and dead code elimination can work across what used to be a boundary.

If square(3) is inlined, it folds to 9. That was impossible while it sat inside a call.

§2Inlining tradeoffs

Inlining everything would explode code size. A compiler needs heuristics.

  • Inline small functions (a few instructions).
  • Inline functions called from one site (the original can be removed).
  • Don't inline recursive calls without a limit.
  • Weigh hot call sites (inside loops) more than cold ones.
def should_inline(callee, site):
    if callee.is_recursive: return false
    if callee.size <= SMALL: return true
    if callee.call_count == 1: return true
    return site.loop_depth > 0 and callee.size <= MEDIUM

Bigger code can also hurt by overflowing the instruction cache, so more inlining isn't always faster. Measure.

§3Loop optimizations

Programs spend most of their time in loops, so small savings inside them multiply.

Loop-invariant code motion moves a computation that gives the same result on every iteration out of the loop.

while (i < n) {              t = limit * 2
  s = s + limit * 2;   ──►   while (i < n) {
  i = i + 1;                   s = s + t;
}                              i = i + 1;
                             }

An instruction is invariant if its operands are constants or defined outside the loop. It also has to be safe to run once even if the loop runs zero times, so anything that might raise an error needs extra care.

Strength reduction replaces expensive operations with cheaper equivalent ones, such as i * 8 with a running sum that adds 8 each iteration, or x * 2 with a shift.

# before: multiply each time        # after: add each time
for (i = 0; i < n; i++) a[i*8]      p = 0; for (...) { use p; p = p + 8; }
The key insight Many optimizations don't help much alone but open the door to others. Inlining is the clearest example: its main value is letting the other passes see more code.

§4Common Mistakes

MistakeWhat HappensFix
Inlining recursive functions without a limitThe compiler loops, or code size explodesSkip recursive calls or cap the depth
Hoisting a division out of a loop that may run zero timesA division by zero error appears that the original program never triggeredOnly hoist instructions that can't fail, or guard them
Inlining by name instead of by resolved bindingA shadowing variable or later reassignment changes which function is calledInline only when the callee is known and can't change
Practice
  1. Inline fn add1(x) { return x + 1; } into let y = add1(add1(2)); and then fold the result step by step.
  2. Write the check for whether an instruction in a loop is invariant, and explain why a[i] is not invariant even when a and i are.
Key takeaways
  • Inlining substitutes a call's body, mostly to expose it to other passes.
  • Heuristics balance code size against benefit: small, single-site, and hot calls.
  • Loop-invariant code motion and strength reduction speed up work repeated on every iteration.
