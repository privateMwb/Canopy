Control-Flow Graphs & Basic Blocks

A control-flow graph splits a function into basic blocks and draws an edge for every way control can move, giving analyses a structure to work on.

§1Basic blocks

A basic block is a straight-line run of instructions with one entry (the first instruction) and one exit (the last). Control never enters in the middle or leaves from the middle.

 block entry:
     s = 0
     i = 0
     jump top
 block top:
     t1 = i < n
     branch t1, body, end
 block body:
     s = s + i
     i = i + 1
     jump top
 block end:
     ret s

A block always ends in a terminator: jump, branch, or ret. Everything between the first and last instruction is plain computation with no control flow.

§2Building the graph

The control-flow graph (CFG) has a node per block and an edge from block A to block B whenever A can transfer control to B.

        entry
          │
          ▼
   ┌───► top ──────┐
   │      │        │
   │      ▼        ▼
   └──── body     end

Finding the blocks in a flat instruction list uses leaders. The first instruction, every jump target, and every instruction after a jump are leaders, and each block runs from one leader to just before the next.

def build_cfg(code):
    leaders = {0}
    for i, ins in enumerate(code):
        if is_jump(ins):
            leaders.add(target_of(ins))
            if i + 1 < len(code): leaders.add(i + 1)
    blocks = split_at(code, sorted(leaders))
    for b in blocks:
        for t in successors(b.terminator): add_edge(b, block_of(t))

If your lowering already creates blocks directly, you skip this step and build edges as you emit.

§3What the graph tells you

Graph properties answer questions that are hard on a flat list.

  • Reachability: blocks with no path from entry are dead code.
  • Predecessors/successors: which blocks flow into this one, and which can follow.
  • Loops: a back edge, one pointing to a block that already appears earlier in a path, marks a loop.
  • Dominators: block A dominates B if every path from entry to B passes through A. This idea underlies SSA and many optimizations.
def reachable(entry):
    seen = {entry}; work = [entry]
    while work:
        b = work.pop()
        for s in b.successors:
            if s not in seen: seen.add(s); work.append(s)
    return seen
The key insight A flat instruction list hides the program's shape. The CFG makes the shape explicit, so questions like 'which code is dead?' and 'where are the loops?' become simple graph questions.

§4Common Mistakes

MistakeWhat HappensFix
Letting a block end without a terminatorControl falls through to whatever block comes next in memory, and the CFG has a missing edgeRequire every block to end in jump, branch, or ret, and check it in the verifier
Forgetting the instruction after a branch is a leaderTwo blocks merge into one and a jump lands in the middle of a blockMark target and fall-through instructions as leaders
Keeping unreachable blocksLater passes analyze code that can never run, wasting time or raising false errorsRemove blocks not reachable from entry
Practice
  1. Draw the CFG for a function with while containing an if/else, labelling every block and edge.
  2. Write a function that finds all blocks that can reach ret, and explain why a block that cannot reach ret might be a bug in the source program.
Key takeaways
  • A basic block is straight-line code ending in a terminator.
  • The CFG has blocks as nodes and possible control transfers as edges.
  • Reachability, loops, and dominators all come from graph structure.
