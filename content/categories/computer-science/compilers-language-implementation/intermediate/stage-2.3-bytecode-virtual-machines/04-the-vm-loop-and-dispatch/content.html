The VM Loop & Dispatch

The VM loop fetches an instruction, decodes it, and does what it says, over and over; its speed depends on how cheaply it can do that.

§1The core loop

At the heart of every bytecode VM is a loop around a big dispatch.

def run(code, constants):
    stack = []
    ip = 0
    while true:
        op = code[ip]; ip += 1
        match op:
            PUSH_CONST:
                stack.push(constants[code[ip]]); ip += 1
            ADD:
                b = stack.pop(); a = stack.pop()
                stack.push(add(a, b))
            LT:
                b = stack.pop(); a = stack.pop()
                stack.push(Bool(check_int(a) < check_int(b)))
            JUMP:
                ip += read_u16(code, ip) + 2
            JUMP_IF_FALSE:
                off = read_u16(code, ip); ip += 2
                if not truthy(stack.pop()): ip += off
            PRINT:
                print(to_string(stack.pop()))
            RETURN:
                return

This is the VM version of eval. The tree walk is gone; the program counter ip and the stack replace recursion.

§2Where the time goes

Every instruction pays a dispatch cost: load the opcode, jump to its handler. For cheap instructions like ADD, dispatch can cost more than the work.

  • Branch prediction: one big match compiles to a single indirect jump that the CPU predicts poorly, since the next opcode varies.
  • Memory traffic: the stack lives in memory, so pushes and pops are loads and stores.
  • Type checks: every ADD checks that both operands are integers.

Optimizations aim at these. We cover the main ones in Stage 3.2, but the principle is simple: reduce the number of dispatches (fewer, bigger instructions or register machines) and make each dispatch cheaper.

§3Testing the VM

Because the tree-walking interpreter already exists, you have an oracle. Run every test program through both and require identical output.

for program in all_test_programs:
    expected = run_tree_walker(program)
    actual   = run_vm(compile(program))
    assert expected == actual, program

This is differential testing. It doesn't tell you either is right, but any disagreement is a bug in one of them, and the golden files from Stage 1.4 tell you which. Add runtime assertions in debug builds too: the stack should be empty at the end of each statement, and never underflow.

The key insight A VM's speed comes mostly from how it handles the *common* path: dispatching small instructions. Correctness, though, comes from having a second implementation to compare against.

Practice
  1. Add CALL and RETURN handling to the loop sketch for a function with no arguments (arguments come in the next lesson).
  2. Run the fib(25) program through both the tree-walker and the VM and compare times; write down what accounts for the difference.
Key takeaways
  • The VM loop is a fetch, decode, execute cycle driven by an instruction pointer and a value stack.
  • Dispatch overhead, memory traffic, and type checks dominate the cost.
  • Differential testing against the tree-walker catches compiler and VM bugs.
