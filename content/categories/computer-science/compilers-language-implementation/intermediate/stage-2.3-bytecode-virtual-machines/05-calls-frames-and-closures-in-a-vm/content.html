Calls, Frames & Closures in a VM

Function calls in a VM use frames on a shared stack, and closures need upvalues so captured variables can outlive the frame that created them.

§1Call frames

A function call needs somewhere to keep the function's locals and a place to return to. A call frame holds that, and frames live on a shared stack.

struct Frame { function, ip, base }   # base: where this call's slots start on the stack

   stack:  [ ... | arg0 arg1 local2 temp temp | ... ]
                    ▲ base

Arguments are pushed by the caller, so they already sit at the start of the callee's frame, and become its first local slots without any copying.

        CALL n:
            callee = stack[len(stack) - n - 1]
            frames.push(Frame(callee, ip = 0, base = len(stack) - n))
        RETURN:
            result = stack.pop()
            frame = frames.pop()
            stack.truncate(frame.base - 1)       # drop locals and callee
            stack.push(result)

LOAD_LOCAL s becomes stack[frame.base + s]. There's no environment chain at all, which is much faster than the tree-walker's map lookups.

§2The closure problem

Stack slots disappear when a frame is popped. That's a problem for closures.

fn make_counter() {
  let n = 0;
  return fn() { n = n + 1; return n; };
}

When make_counter returns, n's slot is gone, but the inner function still needs it. The tree-walker avoided this by keeping whole environments alive on the heap. A VM that keeps locals on a stack needs another way.

§3Upvalues

An upvalue is a reference to a captured variable. While the variable's frame is still on the stack, the upvalue points at the stack slot (open). When the frame is about to be popped, the VM closes the upvalue by copying the value into the upvalue itself, which lives on the heap.

struct Upvalue { location: ref Value, closed: Value }

def capture(slot):
    existing = open_upvalues.find(slot)
    if existing: return existing          # share one upvalue per variable
    u = Upvalue(location = &stack[slot])
    open_upvalues.add(u)
    return u

def close_upvalues(from_slot):
    for u in open_upvalues where u.location >= &stack[from_slot]:
        u.closed = *u.location
        u.location = &u.closed           # now points into the heap object
        open_upvalues.remove(u)

Call close_upvalues when a block ends or a function returns. Sharing one upvalue per variable makes two closures capturing the same variable see each other's writes, matching the 'capture variables, not values' rule from Stage 1.3. Compile-time resolution tells each closure which locals it captures.

The key insight Stack frames are fast because they are short-lived. Closures need a variable to live longer than its frame, and upvalues are the bridge: stack-backed while the frame lives, heap-backed afterward.

§4Common Mistakes

MistakeWhat HappensFix
Copying captured values into the closure at creationTwo closures sharing a variable stop seeing each other's updatesCapture variables by reference using upvalues
Closing upvalues only on function returnA block-scoped variable captured in a loop is closed too late, so all closures share one variableClose upvalues when a block exits too
Creating a new upvalue each time a variable is capturedClosures that should share state don'tLook up open upvalues first and reuse
Practice
  1. Trace make_counter and two calls of the returned function through the frames, stack, and upvalues, showing when the upvalue is closed.
  2. Explain why a loop for (let i = 0; ...) creating closures inside needs the upvalue to close at the end of each iteration for each closure to see its own i.
Key takeaways
  • Frames on a shared stack give locals as base + slot, with arguments already in place.
  • Closures need captured variables to outlive their frame.
  • Open upvalues point at stack slots; closing them moves the value to the heap.
