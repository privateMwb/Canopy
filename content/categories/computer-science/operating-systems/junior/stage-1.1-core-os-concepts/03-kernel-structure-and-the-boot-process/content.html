Kernel Structure & the Boot Process

Kernels differ in how much code runs in privileged mode, and every one of them starts life as a few bytes of firmware code.

§1Monolithic vs. Microkernel

A monolithic kernel (Linux, BSD) runs the scheduler, memory manager, file systems, drivers, and network stack all in one privileged address space. Calling between them is a plain function call, which is fast. The cost is that a bug in any driver can crash or compromise the whole kernel.

A microkernel (QNX, seL4, MINIX) keeps only the bare minimum in kernel mode: address spaces, scheduling, and message passing. File systems and drivers run as ordinary user processes. A faulty driver then crashes one process, not the machine, but every request needs extra messages and context switches.

DesignSpeedFault isolationExamples
MonolithicFast internal callsWeak: one bug can take down the kernelLinux, FreeBSD
MicrokernelMessage-passing overheadStrong: drivers are separate processesQNX, seL4, MINIX
HybridMixedMixedWindows NT, macOS (XNU)

Linux softens the monolithic design with loadable kernel modules, which let drivers be added at runtime, but modules still run with full kernel privileges.

§2From Power-On to Your First Process

The CPU starts executing firmware (UEFI on modern machines). Firmware initializes hardware, finds a bootloader on disk, and loads it. The bootloader loads the kernel image into memory and jumps to it.

  1. Firmware runs a hardware self-check and picks a boot device
  2. Bootloader (such as GRUB) loads the kernel and an initial RAM disk
  3. Kernel sets up memory management, interrupts, and drivers
  4. First user process starts as PID 1 (init or systemd)
  5. PID 1 launches everything else
# On Linux, see PID 1 and its children
ps -p 1 -o pid,comm
pstree -p | head

Every other process in the system descends from PID 1. If PID 1 dies, the kernel panics, because nothing is left to reap orphaned children.

The key insight The monolithic vs. microkernel choice is a tradeoff between speed and fault isolation. Real systems mix both ideas, which is why 'which is better' has no single answer.

§3Common Mistakes

MistakeWhat HappensFix
Saying Linux is not a microkernel because it has modulesMisunderstanding what modules areModules load at runtime but still run in kernel mode, so Linux remains monolithic
Believing the OS starts first when the power turns onMissing the firmware and bootloader stagesRemember that firmware runs first and hands off to the bootloader, then the kernel
Thinking PID 1 is just another processNot understanding why killing it causes a panicPID 1 is the root of the process tree and adopts orphans
Practice
  1. Run lsmod on a Linux machine. Pick three modules and look up what each one does.
  2. Run pstree -p and trace the ancestry of your current shell back to PID 1.
Key takeaways
  • Monolithic kernels trade fault isolation for speed; microkernels do the opposite.
  • Boot goes firmware, then bootloader, then kernel, then PID 1.
  • Every process descends from PID 1, and the system can't run without it.
