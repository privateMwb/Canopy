What an Operating System Does

An OS does two jobs at once: it shares one machine fairly among many programs, and it hides hardware behind clean abstractions.

§1The OS as a Resource Manager

A computer has a small number of expensive resources: CPU time, memory, storage, and devices. Dozens of programs want them at the same time. The operating system decides who gets what, for how long, and stops anyone from taking more than their share.

ResourceWhat the OS hands outAbstraction programs see
CPUSlices of time on each coreA process that seems to run continuously
MemoryPieces of physical RAMA private address space
StorageBlocks on a diskFiles and directories
DevicesExclusive or shared accessDevice files and system calls

The right-hand column is the important one. Programs never touch the disk controller or physical RAM directly; they use the abstraction, and the OS does the messy translation underneath.

§2The OS as an Abstraction Layer

Without an OS, every program would need its own disk driver, its own memory layout, and its own way of sharing the CPU. Abstractions let you write fopen once and have it work on an SSD, a network drive, or a USB stick.

# Same program, any storage hardware
cat notes.txt

# What the program asked for: "give me the bytes of this file"
# What the OS did: find the inode, locate disk blocks, check permissions,
# talk to the driver, copy bytes into the program's memory

Three words recur through the whole OS field: virtualization (each program sees its own CPU and memory), concurrency (many things in progress at once), and persistence (data that survives power loss). This course follows the first two most closely.

§3What Lives Where

The kernel is the always-running core of the OS. It runs with full hardware privileges, owns all memory, and responds to requests from programs and from hardware. Everything else, including your shell, your editor, and system daemons, is an ordinary user program that happens to ship with the system.

  • Kernel: scheduler, memory manager, drivers, file systems, network stack
  • System libraries: such as libc, which wraps kernel requests in friendly functions
  • User programs: shells, browsers, your own code
The key insight The OS is not a program you run; it is the program that runs your programs. Every later lesson, from scheduling to paging, is one resource being shared and one abstraction being maintained.

§4Common Mistakes

MistakeWhat HappensFix
Treating the OS as just a GUI and appsYou can't explain why programs crash independently or why one can't read another's memoryThink of the OS as the kernel plus the services it provides, with or without a graphical shell
Calling libc functions system callsConfusing a library wrapper with the actual privileged crossing into the kernelprintf is a library function; the write it eventually triggers is the system call
Assuming programs see real hardwareSurprise when two processes use the same address and don't collideRemember that addresses, CPUs, and files are all abstractions the OS presents
Practice
  1. For each resource in the table, name one thing that would go wrong if programs accessed it directly with no OS in between.
  2. Pick three programs you ran today. Which parts of each were doing OS-provided work (files, memory, networking)?
Key takeaways
  • The OS manages shared resources and presents abstractions over them.
  • The kernel is the privileged core; everything else is a user program, even if it ships with the OS.
  • Virtualization, concurrency, and persistence are the three themes behind almost every OS feature.
