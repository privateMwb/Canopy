Memory Bugs

Memory errors share a pattern: the program touches memory it no longer owns, and the symptom shows up far from the cause.

§1The Common Four

BugWhat it isTypical symptom
Memory leakAllocated but never freedMemory use grows over time
Use-after-freeUsing a pointer after freeRandom corruption or crash
Double freeFreeing the same block twiceAllocator abort or heap corruption
Buffer overflowWriting past the end of a blockCorrupted neighbors, crashes, exploits
int *p = malloc(4 * sizeof *p);
p[4] = 1;          // overflow: valid indices are 0..3
free(p);
p[0] = 2;          // use-after-free
free(p);           // double free

None of these necessarily crash right away. The corrupted memory may be used much later, which is what makes them hard to debug.

§2Finding Them With Tools

Reading code isn't enough. Run memory checkers during development and in your test suite.

# AddressSanitizer: fast, catches overflow, use-after-free, double free, leaks
gcc -fsanitize=address -g prog.c -o prog && ./prog

# Valgrind: slower, no recompile needed
valgrind --leak-check=full ./prog

The reports show the exact line that made the bad access and the line that allocated or freed the block, which is usually enough to find the root cause.

§3Habits That Prevent Them

  • Set pointers to NULL after free, so a second free is harmless
  • Pair every malloc with one free in the same module
  • Pass buffer sizes alongside pointers and check bounds
  • Prefer snprintf, strncpy-style bounded calls, and calloc for arrays

Memory-safe languages eliminate most of these bugs by checking bounds and managing lifetimes for you, at some cost in control or speed.

Gotcha A leak is not a crash. A program can leak slowly for weeks until the OS kills it, so watch memory over time and not just at the end of a short test.

§4Common Mistakes

MistakeWhat HappensFix
Off-by-one writes past an array's endSilently corrupts adjacent heap dataCheck i < n, and run AddressSanitizer in tests
Keeping a pointer after the owner frees the blockUse-after-free appears later and elsewhereNull the pointer, or restructure so ownership is clear
Only testing with tiny inputsOverflows appear only with long inputsInclude large and boundary-sized inputs in tests
Practice
  1. Write a deliberately buggy program with each of the four bugs and run AddressSanitizer on it. Compare the reports.
  2. Find a leak using Valgrind and explain the difference between 'definitely lost' and 'still reachable'.
Key takeaways
  • Leaks, use-after-free, double free, and overflows are all violations of memory ownership.
  • Run AddressSanitizer or Valgrind routinely; don't rely on reading code.
  • Symptoms often appear far from the cause, so use tools that report the original mistake.
