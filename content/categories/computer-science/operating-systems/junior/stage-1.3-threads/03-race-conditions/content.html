Race Conditions

A race condition happens when the result depends on the unlucky timing of threads touching the same data, and even counter++ is vulnerable.

§1Why counter++ Isn't Atomic

It looks like one operation, but the CPU does three: load the value into a register, add one, store it back. Two threads can interleave those steps and lose an update.

StepThread AThread Bcounter
1load (reads 5)5
2load (reads 5)5
3add (6)add (6)5
4store 6store 66

Two increments happened, but the counter went up only once. This is a lost update.

§2Seeing the Race

Races are non-deterministic, so they hide in small tests. Run enough iterations and the wrong answer shows up reliably.

#include <pthread.h>
#include <stdio.h>

long counter = 0;

void *inc(void *arg) {
    for (int i = 0; i < 1000000; i++)
        counter++;                    // unprotected shared write
    return NULL;
}

int main(void) {
    pthread_t a, b;
    pthread_create(&a, NULL, inc, NULL);
    pthread_create(&b, NULL, inc, NULL);
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    printf("%ld (expected 2000000)\n", counter);
}

The output is usually less than 2,000,000, and different on every run. If you compile with optimizations it may behave differently again, which is part of the danger.

§3Critical Sections and Data Races

A critical section is code that touches shared data and must not be run by two threads at once. A data race is two threads accessing the same memory at the same time with at least one writing and no synchronization. In C and C++, a data race is undefined behavior, not just a wrong number.

# Tools that find races you can't see by eye
gcc -fsanitize=thread -g race.c -o race && ./race
valgrind --tool=helgrind ./race
The key insight Races depend on timing, so passing tests proves nothing. Detect them with tools like ThreadSanitizer, and prevent them by design.

§4Common Mistakes

MistakeWhat HappensFix
Declaring a variable volatile to fix a racevolatile doesn't make operations atomic or ordered between threadsUse a mutex or atomic operations
Concluding code is safe because tests passThe race simply didn't trigger this timeRun a race detector and reason about shared data
Protecting writes but not readsA reader can see a half-updated valueEvery access to shared mutable data needs the same protection
Practice
  1. Run the racy counter ten times and record the results. How much do they vary?
  2. Build the counter with ThreadSanitizer enabled and read its report. Which two lines does it flag?
Key takeaways
  • counter++ is load, add, store, and threads can interleave those steps.
  • A data race on shared memory is undefined behavior in C and C++.
  • Race detectors find what tests miss; fix races by design, not by luck.
