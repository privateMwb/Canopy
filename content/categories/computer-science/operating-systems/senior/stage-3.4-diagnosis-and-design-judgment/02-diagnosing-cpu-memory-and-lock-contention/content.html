Diagnosing CPU, Memory & Lock Contention

A systematic method, check each resource for use, saturation, and errors, beats guessing and keeps you from fixing the wrong bottleneck.

§1The USE Method

For every resource, check three things: Utilization (how busy is it?), Saturation (is work queued waiting for it?), and Errors. A resource at 100% utilization with a growing queue is a bottleneck; one with high utilization and no queue may be fine.

pidstat -w -u -r 1         # per-process CPU, context switches, memory
iostat -x 1                # disk utilization, queue size, latency

§2Reading the Signals

  • High us: your code is computing. Profile it with perf.
  • High sy: lots of kernel time: system calls, page faults, or lock contention. Check strace -c and context switches.
  • High wa: CPUs idle while waiting on disk. Look at I/O, not CPU.
  • High st: steal time: the hypervisor is giving your CPU to someone else.
  • Load average high, CPU idle: threads are blocked, often in uninterruptible I/O (state D).

Load average on Linux counts runnable tasks plus those in uninterruptible sleep, so a number above the core count doesn't by itself mean the CPU is the problem.

§3A Worked Example: Slow Service, Low CPU

A service has slow responses while CPU shows 30% busy. Work through it:

  1. vmstat: r is low, b is low, cs (context switches) is very high. The CPU isn't saturated, but threads are constantly switching.
  2. pidstat -w: huge voluntary context switches, so threads are blocking and waking, not being preempted.
  3. strace -f -c: futex dominates syscall time. That's lock contention.
  4. perf off-CPU or a thread dump shows most threads waiting on one lock around a shared cache.
  5. Fix: shard the lock, shorten the critical section, or reduce sharing. Re-measure.

The conclusion came from following the evidence in order, with each step ruling out an alternative.

Gotcha Averages hide the problem. A 30% average CPU can coexist with one core pegged at 100% running a serial section, or with cgroup throttling. Look per core, per thread, and at percentiles.

§4Common Mistakes

MistakeWhat HappensFix
Fixing the first anomaly you seeThe real bottleneck remainsCheck every resource with USE before deciding
Equating high load average with a CPU problemIt also counts tasks blocked on I/OCompare r and b in vmstat, and check CPU states
Looking at system-wide averages onlyA single hot thread or core goes unnoticedLook per core and per thread (mpstat -P ALL, top -H)
Practice
  1. Generate load with stress-ng for CPU, memory, and I/O separately, and write down which vmstat columns change for each.
  2. Build a program with heavy lock contention. Show how it looks in vmstat, pidstat -w, and strace -c.
Key takeaways
  • USE: check utilization, saturation, and errors for every resource.
  • The split of user, system, I/O wait, and steal time points to where to look next.
  • Follow evidence step by step; averages and load numbers alone mislead.
