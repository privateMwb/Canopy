Processes vs. Threads vs. Async: Design Tradeoffs

Choosing a concurrency model is a design decision about isolation, memory, and complexity, and the best answer comes from the workload and failure model.

§1The Three Models

ModelStrengthWeakness
Multiple processesStrong isolation; a crash affects one worker; no shared-memory racesHigher memory per worker; needs IPC; more costly to create
Multiple threadsShared memory is fast and convenient; cheaper creationOne bug can corrupt or crash everything; locks and races
Async / event loopHandles very many idle connections cheaply; little lockingBlocking calls stall everything; harder control flow; uses one core per loop

These combine. The right question isn't which one wins, but what each layer of the system needs.

§2Real Systems Make Different Choices

  • PostgreSQL: a process per connection, chosen for isolation and crash containment, with the cost handled by connection pooling
  • nginx: a few worker processes, each running an event loop, giving isolation across workers and efficiency within them
  • Chrome: a process per site and per renderer, so a compromised page can't read another site's memory
  • Go runtime: goroutines multiplexed over a pool of kernel threads, with the scheduler turning blocking calls into cheap waits
  • Node.js: a single-threaded event loop plus a small thread pool for file and CPU-heavy operations

Each choice reflects what the designers valued: isolation, per-connection cost, or simplicity of the programming model.

§3A Decision Framework

  1. Is the work CPU-bound or I/O-bound? CPU-bound needs parallelism across cores (threads or processes); I/O-bound with many connections favors async
  2. How many concurrent connections? Thousands of mostly idle ones favor event loops; dozens of busy ones are fine with threads
  3. What is the failure model? If one task's bug must not take down others, use processes or sandboxing
  4. What does shared state look like? Heavily shared mutable state favors threads with care; mostly independent tasks favor processes
  5. What can the team operate and debug? A simpler model you can reason about beats a faster one you can't

In a design review, state your assumptions about workload and failure, name the alternative you rejected, and say what measurement would change your mind. For example: 'We use a process pool because the parsing library isn't thread-safe and a crash must not affect other jobs; if profiling shows memory per worker dominates, we'll revisit threads.'

The key insight Every concurrency model is a bet about the workload. Strong answers name the bet, the measurement that would prove it wrong, and the cost of switching later.

§4Common Mistakes

MistakeWhat HappensFix
Choosing a model by fashionMismatch with the real workloadCharacterize CPU vs. I/O, connection count, and failure needs first
Mixing blocking calls into an event loopLatency spikes across all connectionsOffload blocking work to a thread pool, or use async-native libraries
Sharing mutable state between threads by defaultRaces and lock contentionPrefer message passing, immutable data, or per-thread state
Practice
  1. For an image-resizing service, a chat server with 50,000 idle connections, and a database, choose a model for each and justify it in two sentences.
  2. Take a design you know. Write down the assumptions behind its concurrency model and one measurement that would prove an assumption wrong.
Key takeaways
  • Processes favor isolation, threads favor shared-memory speed, and async favors many cheap waits.
  • Real systems combine models, as with nginx's processes running event loops.
  • Justify a choice by naming the workload assumptions, the rejected alternative, and what would change your mind.
