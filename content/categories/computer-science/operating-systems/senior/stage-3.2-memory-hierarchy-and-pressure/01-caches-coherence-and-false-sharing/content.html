Caches, Coherence & False Sharing

Cores move memory in 64-byte cache lines, so two unrelated variables that share a line can slow each other down as if they were one.

§1Cache Lines and Coherence

CPUs don't fetch single bytes; they move cache lines, 64 bytes on most modern x86 and ARM systems. Each core has its own L1 and L2 caches, so the same line can sit in several cores' caches at once. A coherence protocol such as MESI keeps them consistent. A core must gain exclusive ownership of a line before writing it, which invalidates the copies in other cores' caches.

StateMeaning
ModifiedThis core has the only copy, and it has changed
ExclusiveThis core has the only copy, unchanged
SharedSeveral cores hold identical copies, read-only
InvalidThe copy is stale and unusable

Reading a line another core has modified means waiting for that line to travel between cores, costing tens to hundreds of cycles.

§2False Sharing

If two threads write to different variables that live on the same cache line, the line ping-pongs between their cores on every write, even though the threads never touch each other's data. This is false sharing.

struct counters {
    long a;     // written only by thread 1
    long b;     // written only by thread 2 -- same 64-byte line as a!
};

// Fix: give each hot variable its own cache line
struct counters {
    _Alignas(64) long a;
    _Alignas(64) long b;
};

In benchmarks, padding alone can make a multi-threaded counter several times faster with no change to the logic. The cost is memory: 64 bytes per padded variable.

§3Finding It

# perf can report cache lines contended between cores
perf c2c record ./program
perf c2c report

# Symptoms: threads scale badly, high time in memory accesses, no lock contention

Related patterns: many threads incrementing one shared atomic counter (true sharing), and a hot lock's cache line bouncing between waiters. The fixes are to shard the counter per thread and combine at the end, or to reduce how often threads write shared data.

The key insight Performance depends on who writes which cache lines, not just which variables. Data written by different threads should be on different lines; data that's read-only can safely share.

§4Common Mistakes

MistakeWhat HappensFix
Packing per-thread counters into one arrayNeighboring counters share a line and false sharePad each element to the cache line size, or use per-thread structures
Padding everything 'just in case'Wastes memory and hurts cache capacityPad only data that is written often by different threads
Blaming locks for a scaling problemThe real cause is cache-line contentionProfile with perf c2c before changing the locking
Practice
  1. Write two threads incrementing adjacent long values, then pad them to separate lines. Measure the speedup.
  2. Design a per-thread counter scheme that scales to 64 threads and describe how reading the total works.
Key takeaways
  • Caches move 64-byte lines, and writing a line requires exclusive ownership.
  • False sharing slows threads that write different variables on the same line.
  • Pad hot per-thread data to separate lines, and detect problems with perf c2c.
