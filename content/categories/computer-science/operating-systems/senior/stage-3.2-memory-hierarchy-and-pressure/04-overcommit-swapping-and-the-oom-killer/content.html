Overcommit, Swapping & the OOM Killer

Linux lets processes ask for more memory than exists and sorts it out later, and when it can't, something has to die.

§1Overcommit

Because of demand paging, a process that allocates 10 GiB may only use 1 GiB. Linux therefore allows total allocations to exceed RAM plus swap, a policy called overcommit. It's controlled by vm.overcommit_memory.

SettingBehavior
0 (default)Heuristic: refuse obviously excessive single requests
1Always allow; malloc practically never fails
2Strict accounting: refuse when the commit limit is reached

The consequence is that malloc returning non-NULL doesn't guarantee the memory exists. The failure comes later, at first touch, when the kernel can't find a free frame.

§2Reclaim and Swap

When free memory runs low, the kernel reclaims pages in stages. It drops clean page cache first, which is cheap since the data can be re-read from disk. Then it writes dirty pages to their files, and finally swaps out anonymous pages, which have no file to go back to, to swap space.

free -h                          # look at available, not free
grep -E 'MemAvailable|SwapFree|Dirty' /proc/meminfo
cat /proc/pressure/memory         # PSI: share of time tasks stall on memory
cat /proc/sys/vm/swappiness

Page cache counts as 'used' memory but is reclaimable, which is why MemAvailable is the number to watch. If processes hit direct reclaim, stalling to free memory themselves, latency spikes. Heavy swapping that thrashes makes the whole machine crawl.

§3The OOM Killer

When reclaim fails, the kernel invokes the OOM killer, which picks a process to kill to free memory. Its oom_score is based mostly on how much memory the process uses, adjusted by oom_score_adj, from -1000 (never kill) to +1000.

cat /proc/1234/oom_score                  # higher means more likely to be chosen
echo -500 > /proc/1234/oom_score_adj      # make it less likely (needs privilege)
dmesg | grep -i -E 'out of memory|oom-kill'   # find who was killed and why

The killed process receives SIGKILL, so it gets no chance to clean up, and the log shows only a process that vanished. Inside containers, the same thing happens at the cgroup limit, covered in Stage 3.3.

Gotcha A service that 'randomly restarts' with no error in its own logs is often an OOM kill. Check dmesg or the system journal for the kernel's report, which lists each process's memory use at the time.

§4Common Mistakes

MistakeWhat HappensFix
Reading free instead of available memoryPanic at a full cache that's actually reclaimableUse MemAvailable and memory pressure (PSI)
Assuming malloc success means memory is guaranteedFailure appears at first touch as an OOM killReserve and touch critical memory up front, or limit via cgroups
Disabling swap to avoid slownessLess room for reclaim and earlier OOM killsKeep modest swap, and tune swappiness; fix the memory demand
Practice
  1. Write a program that allocates and touches memory in a loop inside a VM, and watch MemAvailable, PSI, and dmesg until the OOM killer acts.
  2. Set oom_score_adj on two processes and predict which one the kernel will kill first.
Key takeaways
  • Overcommit means malloc can succeed for memory the system can't actually supply.
  • Under pressure, the kernel drops cache, writes dirty pages, swaps anonymous pages, and finally invokes the OOM killer.
  • Watch MemAvailable and memory pressure, and check kernel logs for OOM kills.
