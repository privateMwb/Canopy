Thread Pools, Work Stealing & Async I/O

Creating a thread per task or per connection stops scaling, so real systems bound their threads and use event-driven I/O to handle many connections.

§1Thread Pools

A thread pool starts a fixed number of worker threads that pull tasks from a shared queue. It avoids per-task creation cost and caps resource use, since you control how many threads exist. The queue is a producer–consumer buffer from Stage 2.2.

WorkloadPool size guideline
CPU-boundAbout the number of cores; more only adds switching
I/O-boundLarger, since threads spend most of their time blocked
MixedSeparate pools, so slow I/O can't starve compute

An unbounded queue hides overload: tasks pile up and latency grows without limit. Prefer a bounded queue with a clear policy when it's full, such as rejecting new work or making callers wait.

§2Work Stealing

A single shared queue becomes a contention point. In work stealing, each worker has its own double-ended queue (deque). A worker pushes and pops tasks at one end, with no contention. An idle worker steals from the opposite end of a busy worker's deque. This keeps cores busy and keeps related tasks local for cache reuse.

worker i:   own_deque.push_bottom(task)    // spawned subtask stays local
            task = own_deque.pop_bottom()  // LIFO: fresh data, warm cache
            if none: victim = random worker
                     task = victim.deque.steal_top()   // FIFO: older, larger tasks

Stealing the oldest task usually grabs the largest piece of work, so thieves rarely need to steal again. Fork-join frameworks and runtimes like Go's scheduler and Rust's Rayon use this design.

§3Event-Driven I/O: epoll and io_uring

With one thread per connection, 10,000 connections means 10,000 stacks and context switches. An event loop instead uses a small number of threads and asks the kernel which sockets are ready.

int ep = epoll_create1(0);
epoll_ctl(ep, EPOLL_CTL_ADD, sock, &ev);       // register interest in a socket

for (;;) {
    int n = epoll_wait(ep, events, MAX, -1);   // sleep until something is ready
    for (int i = 0; i < n; i++)
        handle(events[i]);                     // must never block for long
}

epoll tells you a socket is *ready*, and you then issue the read. io_uring goes further: you queue many operations in a shared submission ring, the kernel completes them, and results appear in a completion ring, with fewer system calls and support for files as well as sockets.

The tradeoff is programming complexity. Code is split into callbacks or state machines, and a single blocking call or long computation stalls every connection on that loop.

The key insight Threads are the right tool for parallel computation, and event loops are the right tool for waiting on many things. Most high-scale servers combine the two: an event loop per core plus a pool for blocking or CPU-heavy work.

§4Common Mistakes

MistakeWhat HappensFix
Running blocking calls in an event-loop threadEvery connection on that loop stallsMove blocking or heavy work to a worker pool
Using an unbounded task queueMemory grows and latency explodes under overloadBound the queue and define a rejection policy
Sizing every pool as 'number of cores'I/O-bound work leaves cores idleSize by workload type and measure utilization
Practice
  1. Build a thread pool with a bounded queue. What does submit do when the queue is full, and why did you choose that?
  2. Write an epoll-based echo server and compare its memory use with a thread-per-connection version at 5,000 connections.
Key takeaways
  • Thread pools bound resource use; size them by whether work is CPU-bound or I/O-bound.
  • Work stealing keeps cores busy while minimizing contention and preserving locality.
  • Event loops via epoll or io_uring handle many connections cheaply but must never block.
