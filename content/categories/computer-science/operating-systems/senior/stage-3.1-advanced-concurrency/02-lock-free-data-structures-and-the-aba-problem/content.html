Lock-Free Data Structures & the ABA Problem

Lock-free structures use CAS retries instead of locks, which avoids blocking but trades it for subtle failure modes like ABA and unsafe memory reclamation.

§1A Lock-Free Stack

The Treiber stack keeps a pointer to the top node. To push, point the new node at the current top and CAS the top to the new node. If another thread changed the top in the meantime, the CAS fails and you retry.

struct node { int val; struct node *next; };
_Atomic(struct node *) top;

void push(struct node *n) {
    struct node *old = atomic_load(&top);
    do { n->next = old; }
    while (!atomic_compare_exchange_weak(&top, &old, n));
}

struct node *pop(void) {
    struct node *old = atomic_load(&top);
    while (old && !atomic_compare_exchange_weak(&top, &old, old->next))
        ;
    return old;
}

No thread ever holds a lock, so a stalled thread can't block the others.

§2The ABA Problem

CAS checks only that the value matches, not that nothing happened in between. Suppose Thread 1 reads top = A with A->next = B, then gets paused. Meanwhile Thread 2 pops A, pops B, and pushes A back, now with A->next = C. Thread 1 resumes, sees top is still A, and its CAS succeeds, setting top to B, a node that has already been removed. The stack is corrupted.

  • Tagged pointers: pair the pointer with a version counter so A with version 1 differs from A with version 2 (needs a double-width CAS)
  • Hazard pointers: each thread announces which nodes it's reading, and nodes are freed only when no one has announced them
  • Epoch-based reclamation: defer freeing until all threads have passed a safe epoch
  • Garbage collection: languages with a GC avoid reuse of a node while any reference exists

Even without ABA, pop reads old->next from a node another thread may have already freed. Safe memory reclamation is the hardest part of lock-free design.

§3Progress Guarantees and When to Use This

GuaranteeMeaning
BlockingA stalled thread holding a lock can block everyone
Lock-freeSome thread always makes progress, though an individual thread may retry indefinitely
Wait-freeEvery thread finishes in a bounded number of steps

Lock-free is not automatically faster. Under high contention, many threads retry CAS on the same cache line and waste work. Use it when you need freedom from priority inversion or lock convoys, such as in signal handlers or real-time code, or when profiling proves a lock is the bottleneck. Otherwise use a well-tested library rather than writing your own.

The key insight Lock-free code removes the lock but not the coordination. It moves the difficulty into memory ordering, ABA, and reclamation, which are harder to get right than a mutex.

§4Common Mistakes

MistakeWhat HappensFix
Freeing a popped node immediatelyAnother thread may still be reading it, causing use-after-freeUse hazard pointers, epochs, or a GC
Ignoring ABA when comparing pointersA reused address makes CAS succeed incorrectlyAdd a version tag or use safe reclamation
Assuming lock-free means wait-free or fasterContended retry loops waste cyclesBenchmark against a mutex under realistic contention
Practice
  1. Write a trace of ABA on the Treiber stack with three nodes, showing the state after each step.
  2. Implement the stack with a tagged head (pointer plus counter) using a 128-bit CAS or an index-based design.
Key takeaways
  • Lock-free structures use CAS retry loops instead of locks, so no stalled thread blocks the others.
  • ABA and unsafe reclamation are the core hazards; solve them with tags, hazard pointers, or epochs.
  • Use lock-free code when profiling justifies it, preferably from a vetted library.
