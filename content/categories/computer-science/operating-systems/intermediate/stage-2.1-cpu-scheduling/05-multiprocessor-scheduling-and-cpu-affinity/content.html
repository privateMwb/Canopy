Multiprocessor Scheduling & CPU Affinity

With many cores, the scheduler must keep all of them busy while also keeping each thread near the cache that already holds its data.

§1Per-Core Run Queues

One shared run queue is simple, but every core must lock it, and it becomes a bottleneck. Modern kernels give each core its own queue, so a core usually schedules from its own work without contention.

# See which CPU each thread last ran on (psr column)
ps -eLo pid,tid,psr,comm | head
# Count CPUs
nproc

The cost is imbalance: one core's queue may be long while another sits idle.

§2Load Balancing and Cache Affinity

To fix imbalance, the scheduler migrates tasks between cores, either idle cores pulling work or busy cores pushing it. But a migrated task loses its cache affinity: the data it had warmed in the old core's L1 and L2 caches is not there, and the first accesses are slow.

GoalPushes towardCost if overdone
Even loadMigrating tasksCold caches
Cache warmthKeeping tasks putIdle cores while others are busy

Schedulers prefer to migrate between cores that share cache, such as hyperthreads or cores in one cluster, before crossing to a separate socket.

§3Pinning with Affinity

You can restrict a task to specific CPUs. This can improve cache behavior and predictability, or isolate noisy work.

taskset -c 2,3 ./server          # run only on CPUs 2 and 3
taskset -cp 4242                 # show a running process's allowed CPUs

// In C: sched_setaffinity(0, sizeof set, &set);

Pinning is a blunt tool. A pinned task can't escape a busy core, so use it only when measurements show a benefit.

Connection to later lessons On machines with multiple memory nodes, where a thread runs also determines how far its memory is. Stage 3.2 covers NUMA and why pinning threads next to their data matters.

§4Common Mistakes

MistakeWhat HappensFix
Pinning threads by defaultPinned work waits while other cores sit idleMeasure first; pin only when it helps
Assuming more cores always finish fasterLock contention and migration overhead can dominateCheck the scaling of the workload, not just the core count
Ignoring cache sharing when placing tasksCross-socket migration is much more expensivePrefer placement that keeps related threads on cores sharing a cache
Practice
  1. Run a CPU-bound program with and without taskset -c 0. Check the psr column over time to see whether it migrates.
  2. Describe a workload where pinning threads to cores helps, and one where it hurts.
Key takeaways
  • Per-core run queues avoid contention but require load balancing.
  • Migrating a task discards its warm cache, so balance and affinity pull in opposite directions.
  • CPU pinning helps only when measured; it removes the scheduler's flexibility.
