Classic Synchronization Problems

Producer–consumer, readers–writers, and dining philosophers each isolate a pattern you'll meet again in real systems.

§1Producer–Consumer (Bounded Buffer)

Producers add items to a fixed-size buffer; consumers remove them. Producers must wait when the buffer is full, and consumers must wait when it's empty. With semaphores:

sem_t empty;  // counts free slots, starts at N
sem_t full;   // counts filled slots, starts at 0
sem_t mutex;  // protects the buffer itself, starts at 1

void produce(int item) {
    sem_wait(&empty);      // wait for a free slot (acquire this before the mutex!)
    sem_wait(&mutex);
    buffer_put(item);
    sem_post(&mutex);
    sem_post(&full);       // announce a new item
}

If you swap the order and take mutex before empty, a producer holding the mutex can block on a full buffer while consumers can't get the mutex to drain it. That is a deadlock.

§2Readers–Writers

Many threads may read shared data simultaneously, but a writer needs exclusive access. A read-write lock expresses this directly.

pthread_rwlock_t rw = PTHREAD_RWLOCK_INITIALIZER;

pthread_rwlock_rdlock(&rw);   // many readers at once
read_data();
pthread_rwlock_unlock(&rw);

pthread_rwlock_wrlock(&rw);   // one writer, no readers
write_data();
pthread_rwlock_unlock(&rw);

The policy question is who goes first. If readers always win, a steady stream of readers starves writers. If writers always win, readers can starve. Real implementations choose a policy and document it.

§3Dining Philosophers

Five philosophers sit around a table with one fork between each pair. A philosopher needs both adjacent forks to eat. If every philosopher picks up the left fork at once, each waits forever for the right: deadlock.

  • Resource ordering: number the forks and always pick up the lower-numbered one first
  • Limit concurrency: allow at most four philosophers to try to eat at once
  • Asymmetry: make one philosopher pick up the right fork first

The lesson transfers directly: any time threads each hold one resource while wanting another, you have the ingredients for deadlock.

The key insight These problems keep reappearing in disguise. A thread pool queue is producer–consumer, a cache is readers–writers, and two locks acquired in different orders are dining philosophers.

§4Common Mistakes

MistakeWhat HappensFix
Acquiring the mutex before the counting semaphore in producer–consumerDeadlock when the buffer fills or emptiesWait on empty or full first, then take the mutex
Using a read-write lock for short critical sectionsLock overhead exceeds the benefitUse a plain mutex unless reads are long and heavily dominate
Ignoring writer starvationWriters never run under constant read loadChoose a fair policy or one that blocks new readers when a writer waits
Practice
  1. Implement the bounded buffer with condition variables instead of semaphores, with two producers and two consumers.
  2. Implement dining philosophers with five threads using resource ordering and run it for ten minutes without a hang.
Key takeaways
  • Producer–consumer needs one counter for empty slots, one for full slots, and a lock for the buffer.
  • Readers–writers is a policy choice that decides who may starve.
  • Deadlock in dining philosophers is cured by breaking the circular wait.
