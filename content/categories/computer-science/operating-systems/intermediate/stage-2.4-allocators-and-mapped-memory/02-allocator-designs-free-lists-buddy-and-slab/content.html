Allocator Designs: Free Lists, Buddy & Slab

Allocators differ mainly in how they track free space, and each design trades speed, fragmentation, and simplicity differently.

§1Free Lists with Splitting and Coalescing

The simplest allocator keeps a linked list of free blocks. To allocate, it finds a block big enough using a placement policy such as first fit, and splits off the remainder if the block is much larger than requested. To free, it returns the block to the list and coalesces it with any adjacent free neighbors, otherwise memory fragments into unusable crumbs.

struct block {
    size_t size;
    int    free;
    struct block *next;
};

// Split: if block->size is at least request + header + minimum payload,
//   carve a new free block from the tail and shrink this one.
// Coalesce: on free(), if the next block (by address) is free,
//   merge: block->size += sizeof(struct block) + next->size.

Finding the previous neighbor is awkward with a single list. Boundary tags, a copy of the size at the end of each block, let you check the preceding block in constant time.

§2Size Classes and the Buddy System

Searching a long list is slow. Segregated free lists keep one list per size class (16, 32, 48, ... bytes), so allocation is nearly constant time, at the cost of some internal fragmentation from rounding up.

The buddy allocator rounds requests up to powers of two. A free block of size 2^k splits into two buddies of 2^(k-1), and a freed block merges with its buddy when both are free. The buddy's address is found by flipping one bit, so merging is cheap.

// Buddy of a block at address a with size 2^k (offsets from the region base):
buddy = a ^ (1UL << k);

The Linux kernel uses a buddy allocator to hand out physical page frames. Its drawback is internal fragmentation: a 65 KiB request consumes a 128 KiB block.

§3Slab Allocation

Kernels allocate the same small objects constantly, such as process descriptors and inodes. A slab allocator keeps a cache per object type, each made of pages pre-divided into equal-sized slots. Allocation pops a slot; freeing pushes it back. There's no search, no splitting, and no fragmentation within the cache, and objects can stay initialized for reuse.

# See the kernel's slab caches on Linux (needs root on some systems)
sudo cat /proc/slabinfo | head
slabtop -o | head

The key insight The best allocator depends on the allocation pattern. Same-size objects want slabs, mixed sizes want size classes, and page-sized chunks suit buddies. General-purpose malloc combines several of these ideas.

§4Common Mistakes

MistakeWhat HappensFix
Not coalescing on freeThe heap fragments and big requests start failingMerge adjacent free blocks every time
Searching a single list for every allocationAllocation time grows with heap sizeUse size classes or segregated lists
Using the buddy system for small objectsA power-of-two rounding wastes up to half of each blockUse slabs or size classes for small objects
Practice
  1. A buddy allocator has a 1 MiB region. Show the splits for requests of 100 KiB, 200 KiB, and 60 KiB, and compute the wasted space.
  2. Why do boundary tags let you coalesce with the previous block in constant time?
Key takeaways
  • Free-list allocators must split and coalesce to avoid fragmentation.
  • Size-class, buddy, and slab designs trade internal fragmentation for speed.
  • Kernels use buddy allocation for pages and slabs for fixed-size objects.
