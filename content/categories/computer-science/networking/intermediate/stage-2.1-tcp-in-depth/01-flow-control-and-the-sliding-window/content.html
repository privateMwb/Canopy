Flow Control & the Sliding Window

A receiver advertises how much data it can buffer, and the sender must stay within that window, so throughput is capped at window size divided by round-trip time.

§1The Receive Window

A receiver has finite buffer space. If a fast sender pushed data faster than the application could read it, the buffer would overflow. TCP's flow control prevents this: every ACK carries a receive window (rwnd), the number of bytes the receiver is currently willing to accept. The sender may have at most that much unacknowledged data in flight.

Sender                                         Receiver (rwnd = 4000)
  send 1000 bytes ─────────────────────►
  send 1000 bytes ─────────────────────►
  send 1000 bytes ─────────────────────►
  send 1000 bytes ─────────────────────►     4000 unacked: window is full, sender waits
                  ◄── ack, rwnd = 2000       app read some data, window reopens partly
  send 2000 bytes ─────────────────────►

As the window slides forward with each ACK, new data is allowed out. That's why it's called a sliding window. If the application stops reading, the window shrinks to zero and the sender pauses, probing periodically until space opens.

§2Window Size Caps Throughput

Data in flight can never exceed the window, and an ACK takes a round trip to return. So the most a connection can send per RTT is one window, giving:

max throughput = window / RTT

# 64 KB window, 100 ms RTT:
#   65,536 bytes / 0.1 s = 655,360 B/s = about 5.2 Mbps
# This holds even on a 1 Gbps link: the window, not the link, is the limit.

The original TCP header's window field is 16 bits, capping it at 64 KB. The window scaling option negotiated in the handshake multiplies it, allowing windows up to about 1 GiB, which is essential on long, fast paths. Without scaling, high-bandwidth, high-latency links sit mostly idle.

§3Inspecting and Tuning

ss -tmi dst 203.0.113.9
# Shows rcv_space, rcv_wnd, window scale, and buffer usage (skmem).

sysctl net.ipv4.tcp_rmem            # min, default, max receive buffer
sysctl net.ipv4.tcp_window_scaling  # should be 1

Linux auto-tunes receive buffers up to a maximum. If the maximum is smaller than the bandwidth-delay product of your path, throughput is capped. Raise it only after measuring; oversized buffers waste memory and can add latency.

The key insight Flow control protects the receiver. A slow transfer with an idle link often means the window is too small, either from a limit or because the receiving application isn't reading fast enough.

§4Common Mistakes

MistakeWhat HappensFix
Blaming the network when a receiver is slowZero or small windows throttle the senderCheck the advertised window in a capture; fix the application's read loop
Disabling window scalingThroughput stays capped near 64 KB per RTTKeep window scaling enabled, which is the default
Raising buffer limits blindlyMemory use grows with many connectionsSize buffers to the bandwidth-delay product of real paths
Practice
  1. Compute the maximum throughput for a 256 KB window on a 40 ms RTT path. What window is needed to fill a 1 Gbps link at that RTT?
  2. Write a receiver that sleeps without reading, and watch the sender stall with ss -ti and a capture showing a zero window.
Key takeaways
  • The receive window tells the sender how much unacknowledged data it may have in flight.
  • Throughput is at most window divided by RTT.
  • Window scaling lifts the 64 KB limit and is needed for fast, long paths.
