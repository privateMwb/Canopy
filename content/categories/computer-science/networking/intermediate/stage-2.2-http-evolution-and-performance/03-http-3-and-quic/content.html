HTTP/3 & QUIC

HTTP/3 runs over QUIC, a transport built on UDP that gives each stream independent delivery and folds encryption into the handshake.

§1Why Move Off TCP

TCP lives in the operating system kernel, and middleboxes across the internet make assumptions about it, so changing TCP is slow and risky. QUIC (RFC 9000) re-implements reliable, congestion-controlled delivery on top of UDP in user space, which can evolve as quickly as the application. HTTP/3 is HTTP's mapping onto QUIC.

PropertyHTTP/2 over TCP + TLSHTTP/3 over QUIC
TransportTCP (kernel)UDP-based QUIC (user space)
HandshakeTCP then TLS: 2 round trips (TLS 1.3)Combined transport and TLS 1.3: 1 round trip
Lost packet blocksAll streamsOnly the affected stream
Connection identityIP and port 4-tupleConnection ID, surviving address changes

§2What QUIC Improves

  • Faster setup: transport and encryption negotiate together, so the first request can go after one round trip, and 0-RTT resumption lets returning clients send data in the first flight (with replay risk, so only for safe requests)
  • Independent streams: loss on one stream doesn't stall the others, fixing TCP head-of-line blocking
  • Connection migration: a connection survives a switch from Wi-Fi to cellular because it's identified by a connection ID rather than IP addresses
  • Always encrypted: QUIC encrypts nearly everything, including most transport headers, which discourages middlebox interference

These gains matter most on mobile and lossy networks. On a clean, fast network, HTTP/3 and HTTP/2 often perform similarly.

§3Deployment Realities

Browsers don't know a server supports HTTP/3 up front. The server advertises it with an Alt-Svc header, or via DNS HTTPS records, and the browser tries QUIC on UDP port 443. Some networks block or throttle UDP, so clients fall back to TCP and HTTP/2 when QUIC fails.

curl -sI https://example.com/ | grep -i alt-svc
# alt-svc: h3=":443"; ma=86400      <- HTTP/3 available on UDP 443
curl --http3 -I https://example.com/    # works if your curl is built with HTTP/3

Because QUIC runs in user space and is CPU-heavier than kernel TCP at scale, operators watch the cost. Firewalls that only allow TCP 443 need a rule for UDP 443 for it to work.

Connection to later lessons The TLS 1.3 handshake that QUIC embeds is covered in Stage 2.3, and this is why QUIC achieves a one-round-trip setup: it doesn't run a TCP handshake first.

§4Common Mistakes

MistakeWhat HappensFix
Blocking UDP 443 and assuming HTTP/3 'doesn't work'Clients silently fall back to TCP and lose the benefitsAllow UDP 443 where HTTP/3 is wanted
Sending non-idempotent requests with 0-RTTAn attacker can replay early dataRestrict 0-RTT to safe, idempotent requests
Assuming HTTP/3 always beats HTTP/2Gains depend on loss and mobilityMeasure real-user performance
Practice
  1. Check whether a major site advertises Alt-Svc: h3. Use browser DevTools to see which protocol it actually used.
  2. Explain, for a user walking from Wi-Fi to cellular, what happens to a TCP connection versus a QUIC connection.
Key takeaways
  • HTTP/3 runs over QUIC on UDP, combining transport and TLS 1.3 setup.
  • Independent streams mean loss on one stream no longer stalls the others.
  • Connection IDs allow migration, and clients fall back to TCP if UDP is blocked.
