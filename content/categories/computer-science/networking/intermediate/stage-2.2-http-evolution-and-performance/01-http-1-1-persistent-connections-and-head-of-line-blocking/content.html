HTTP/1.1: Persistent Connections & Head-of-Line Blocking

HTTP/1.1 made connections reusable, but it can only have one request in flight per connection, which shaped a decade of web performance tricks.

§1Persistent Connections

HTTP/1.0 opened a new TCP connection for every request, paying the handshake, and slow start, each time. HTTP/1.1 made connections persistent by default: after a response, the connection stays open for the next request. A page with 50 resources no longer needs 50 handshakes.

GET /a.css HTTP/1.1
Host: example.com
Connection: keep-alive        # the default in 1.1; 'Connection: close' opts out

# Same TCP connection, next request:
GET /b.js HTTP/1.1
Host: example.com

Persistent connections require knowing where each response ends. That's what Content-Length and chunked transfer encoding are for: the server streams the body in length-prefixed chunks when it can't know the total size ahead of time.

§2Head-of-Line Blocking

On one connection, responses must come back in the order requests were sent. If the first response is slow, everything behind it waits, even if it's ready. This is head-of-line (HOL) blocking at the HTTP level.

Pipelining, sending several requests without waiting, was meant to help. But responses still had to return in order, so one slow response blocked the rest, and buggy proxies mishandled it. Browsers abandoned it.

Connection 1:  request A ──── slow response A ────────────►
               request B (waits)        response B (ready, but blocked)
               request C (waits)        response C (ready, but blocked)

§3The Workarounds

  • Multiple connections: browsers open up to about six per origin, which parallelizes but multiplies handshakes and competes for bandwidth
  • Domain sharding: spreading assets across several hostnames to get more connections, which adds DNS lookups and defeats reuse
  • Bundling: combining many scripts or stylesheets into one file to reduce requests, at the cost of cache efficiency
  • Image sprites and inlining: merging small assets to save round trips

These tricks existed to compensate for HTTP/1.1's limits, and many hurt under HTTP/2, which removes the underlying problem.

curl -v --http1.1 https://example.com/ 2>&1 | grep -i -E 'connection|keep-alive'
The key insight HTTP/1.1's limit is one outstanding request per connection. Most performance advice from that era, bundling, sharding, sprites, is a workaround for that single constraint.

§4Common Mistakes

MistakeWhat HappensFix
Sharding domains under HTTP/2Extra DNS and TLS costs with no benefitServe assets from one origin when HTTP/2 is available
Closing connections after every responseRepeated handshakes and slow startLeave keep-alive on and tune idle timeouts
Omitting Content-Length and chunkingThe client can't tell where the response endsSend Content-Length, or Transfer-Encoding: chunked
Practice
  1. Use curl -v with two URLs on the same host. Does it reuse the connection? Find the 'Re-using existing connection' line.
  2. Explain how six parallel connections reduce head-of-line blocking, and what they cost.
Key takeaways
  • HTTP/1.1 keeps connections open, saving handshakes and slow-start repeats.
  • One request at a time per connection causes head-of-line blocking; pipelining failed.
  • Multiple connections, sharding, and bundling were workarounds, and many are counterproductive on newer versions.
