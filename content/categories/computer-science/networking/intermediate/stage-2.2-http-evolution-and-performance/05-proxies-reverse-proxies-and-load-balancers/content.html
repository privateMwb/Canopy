Proxies, Reverse Proxies & Load Balancers

Between a client and a server often sit several intermediaries, each able to see, change, or break the traffic passing through.

§1Forward and Reverse Proxies

A forward proxy acts on behalf of clients. The client is configured to send requests through it, and the proxy fetches from the internet, for filtering, caching, or anonymity. A reverse proxy acts on behalf of servers. Clients think they're talking to the site; the proxy receives requests and forwards them to backend servers.

client ──► forward proxy ──► internet ──► site          (client-side; client chooses it)
client ──► internet ──► reverse proxy ──► app servers   (server-side; invisible to client)

Reverse proxies such as nginx, HAProxy, and Envoy do much of the work in modern deployments: TLS termination, response caching, compression, routing by path or host, rate limiting, and distributing load across servers. A load balancer is a reverse proxy whose main job is spreading traffic.

§2What Intermediaries Change

Each hop adds behavior you must account for.

  • Client IP: the backend sees the proxy's address, so proxies add X-Forwarded-For or the standard Forwarded header with the original client IP. Trust these only from your own proxies, since a client can forge them
  • Original scheme: after TLS termination, the app sees plain HTTP, so X-Forwarded-Proto tells it the client used HTTPS
  • Hop-by-hop headers such as Connection apply only to one hop and are removed by proxies
  • Connections: the proxy usually maintains separate, reused connections to the backend from those with clients
GET /api/items HTTP/1.1
Host: api.example.com
X-Forwarded-For: 203.0.113.9, 10.0.1.4     # original client, then earlier proxies
X-Forwarded-Proto: https

§3When Proxies Cause Errors

SymptomLikely cause
502 Bad GatewayThe backend closed the connection, crashed, or sent invalid output
503 Service UnavailableNo healthy backends, or the proxy is shedding load
504 Gateway TimeoutThe backend didn't answer within the proxy's timeout
Random 502s on idle connectionsThe proxy reuses a connection the backend already closed (idle timeout mismatch)

Timeouts must be coordinated across every hop. Make each outer timeout longer than the inner one, and the backend's keep-alive timeout longer than the proxy's, so the proxy never reuses a connection the backend just dropped.

curl -v https://example.com/ 2>&1 | grep -i -E '^< (server|via|x-)'
# 'Via', 'Server', and X- headers often reveal which proxies handled the request
Gotcha A TLS-terminating proxy sees every request in plain text. That's what lets it route and cache by content, and it's also why the proxy becomes a high-value security target.

§4Common Mistakes

MistakeWhat HappensFix
Trusting X-Forwarded-For from the open internetClients spoof IPs to bypass rate limits or access rulesAccept it only from known proxy addresses, and use the rightmost trusted entry
Mismatched keep-alive timeoutsIntermittent 502 errors on reused connectionsSet the backend's idle timeout longer than the proxy's
Forgetting the app sees HTTP after TLS terminationRedirect loops or insecure URLs in responsesHonor X-Forwarded-Proto when generating links and redirects
Practice
  1. Draw the path of a request through a CDN, a load balancer, and an app server, and mark where TLS terminates and which header carries the real client IP.
  2. A service returns intermittent 502s only after quiet periods. Propose two causes and how to check each.
Key takeaways
  • Forward proxies serve clients; reverse proxies and load balancers serve servers.
  • Proxies hide client IP and scheme, so use forwarded headers, but trust them only from your own infrastructure.
  • Align timeouts across hops: outer longer than inner, and backend keep-alive longer than the proxy's.
