The TLS Handshake

TLS lets two strangers agree on a secret key over an open network and verify who they're talking to, and TLS 1.3 does it in a single round trip.

§1What TLS Provides

PropertyMeaningHow
ConfidentialityEavesdroppers can't read the dataSymmetric encryption
IntegrityTampering is detectedAuthenticated encryption (AEAD)
AuthenticationYou're talking to the real serverCertificates and signatures

TLS sits between TCP and the application, so HTTP, email, and many other protocols can use it unchanged. HTTPS is simply HTTP carried inside TLS.

§2The TLS 1.3 Handshake

The two sides must agree on keys without ever sending the keys themselves. They use an ephemeral Diffie–Hellman exchange: each side generates a temporary key pair, shares the public half, and both compute the same shared secret.

Client                                           Server
  │ ClientHello                                    │
  │   key share, supported ciphers, SNI, ALPN ───► │
  │                                                │  (compute shared secret)
  │ ◄─ ServerHello + key share                     │
  │ ◄─ {Certificate, signature, Finished}          │  (already encrypted)
  │ {Finished} ──────────────────────────────────► │
  │ ═══════ encrypted application data ═══════════ │

After this one round trip, the client can send its HTTP request. TLS 1.2 needed two round trips, because key exchange was negotiated step by step. SNI (Server Name Indication) tells the server which hostname the client wants, so one IP can serve many certificates. ALPN selects the application protocol, such as h2.

§3Forward Secrecy and Symmetric Encryption

Because the key pairs are ephemeral, discarded after each connection, an attacker who records traffic today and steals the server's long-term private key next year still can't decrypt it. This property is forward secrecy. The certificate's key is used only to *sign* the handshake and prove identity, not to encrypt data.

The bulk data uses fast symmetric ciphers in AEAD modes, such as AES-GCM or ChaCha20-Poly1305, with keys derived from the shared secret.

openssl s_client -connect example.com:443 -tls1_3 -servername example.com </dev/null
# Shows: Protocol TLSv1.3, Cipher TLS_AES_256_GCM_SHA384, and the certificate chain

curl -v https://example.com/ 2>&1 | grep -E 'TLS|ALPN|subject|issuer'

Session resumption lets a returning client skip parts of the handshake, and 0-RTT can send data in the first flight, with the replay caveat from the HTTP/3 lesson.

The key insight The handshake solves a chicken-and-egg problem: how to share a secret over a channel anyone can watch. Public-key math creates the shared key, and the certificate proves the other end is who it claims to be.

§4Common Mistakes

MistakeWhat HappensFix

Allowing old protocol versionsDowngrade and known-weak cipher attacksDisable SSL and TLS 1.0 and 1.1; allow TLS 1.2 and 1.3

Practice
  1. Run openssl s_client with -tls1_2 and -tls1_3 and compare the negotiated cipher and handshake output.
  2. Explain in two sentences why recording encrypted traffic now and stealing the server's key later doesn't expose it under TLS 1.3.
Key takeaways
  • TLS gives confidentiality, integrity, and authentication on top of TCP.
  • TLS 1.3 completes in one round trip using an ephemeral key exchange, giving forward secrecy.
  • The certificate proves identity by signing the handshake; bulk data uses fast symmetric AEAD ciphers.
