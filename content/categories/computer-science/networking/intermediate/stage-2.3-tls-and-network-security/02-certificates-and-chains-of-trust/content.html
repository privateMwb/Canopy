Certificates & Chains of Trust

A certificate binds a name to a public key, and clients trust it by following a chain of signatures back to a root they already have.

§1What a Certificate Contains

An X.509 certificate is a signed statement that a particular public key belongs to a particular name.

  • Subject and Subject Alternative Names (SAN): the hostnames it's valid for, such as example.com and www.example.com
  • Public key: the server's key for the handshake signature
  • Issuer: who signed it, a certificate authority (CA)
  • Validity period: not-before and not-after dates
  • Signature: the issuer's signature over everything above
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

§2The Chain of Trust

How does your browser know to trust a certificate from a server it has never met? A CA signs the server's leaf certificate. That CA's own certificate, an intermediate, is signed by a root CA. Your operating system and browser ship with a trust store of root certificates they trust directly.

Root CA (in your trust store)
   └─ signs ─► Intermediate CA
                  └─ signs ─► Leaf certificate: example.com

# The server sends the leaf and intermediate(s); the client already has the root.

Roots stay offline and sign only intermediates, which do the day-to-day issuing. If an intermediate is compromised, it can be revoked without replacing the root.

§3What a Client Checks

  1. Every signature in the chain verifies, up to a trusted root
  2. Every certificate is within its validity dates
  3. The requested hostname matches a SAN entry (the old Common Name is ignored)
  4. The certificate hasn't been revoked (checked via OCSP or CRLs, often with OCSP stapling, where the server supplies a fresh signed status)
  5. Modern browsers also require the certificate to appear in public Certificate Transparency logs

Failure of any check produces the browser warning pages. Common causes in practice are an expired certificate, a name mismatch, a missing intermediate (the server forgot to send it, so some clients fail while others cache it), and a self-signed certificate that no trust store contains.

§4Automation

Certificates now last at most a few months, and automation is the norm. The ACME protocol, used by Let's Encrypt and others, lets a server prove control of a domain, then receive and renew certificates without human involvement. Expiry outages are among the most common self-inflicted failures, so monitor expiry dates and automate renewal.

openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null | grep -E 's:|i:'
# Each pair of s:/i: lines is one certificate in the chain: subject and issuer
Gotcha A missing intermediate certificate often works in your own browser, which cached it earlier, and fails for other clients, such as curl, mobile apps, or API consumers. Test with openssl s_client, which shows exactly what the server sends.

§5Common Mistakes

MistakeWhat HappensFix
Letting certificates expireSudden, total outages for HTTPS clientsAutomate renewal and alert well before expiry
Serving only the leaf certificateSome clients can't build the chainConfigure the full chain: leaf plus intermediates
Disabling certificate verification to 'fix' errorsRemoves all protection against impostorsFix the certificate or trust store; never turn off verification in production
Practice
  1. Print the subject, issuer, SAN list, and expiry of a site's certificate, and then list the chain with -showcerts.
  2. Create a self-signed certificate with openssl, and explain exactly why a browser rejects it.
Key takeaways
  • A certificate binds a name to a public key and is signed by a CA.
  • Clients validate the chain up to a trusted root, plus dates, hostname, and revocation status.
  • Most real failures are expiry, missing intermediates, or name mismatch, so automate and monitor.
