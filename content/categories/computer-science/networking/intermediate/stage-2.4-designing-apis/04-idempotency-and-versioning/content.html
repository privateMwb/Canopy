Idempotency & Versioning

Networks fail halfway, so clients retry, and APIs must make retries safe and changes non-breaking.

§1Why Retries Need Idempotency

If a request times out, the client doesn't know whether the server never received it or processed it and the reply was lost. Retrying is the only option, but retrying a POST /payments might charge twice. GET, PUT, and DELETE are idempotent by definition, but POST isn't.

The standard fix is an idempotency key: the client generates a unique value for each logical operation and sends it with the request. The server records the result against that key, and a repeat returns the stored result without running the operation again.

POST /payments HTTP/1.1
Idempotency-Key: 7c3e9a52-4b6f-4d3a-9a77-0e4b1b8a2d10
Content-Type: application/json

{"amount": 5000, "currency": "USD"}

# First call: processes the payment, stores (key → response).
# Retry with the same key: returns the identical stored response, no second charge.
# Same key with a different body: reject with 422 or 409.

Store keys for a bounded time, such as 24 hours, and make the check and the write atomic, for example with a unique database constraint, so that two simultaneous retries can't both pass.

§2Changing an API Without Breaking Clients

Once clients depend on an API, you can't freely change it. Distinguish the kinds of change:

ChangeBreaking?
Adding a new endpoint or optional fieldNo
Adding a new optional request parameterNo
Removing or renaming a field or endpointYes
Changing a field's type or meaningYes
Making an optional parameter requiredYes
Adding a new value to an enum clients switch onPossibly

Clients should follow the tolerant reader principle, ignoring unknown fields, so additive changes stay safe.

§3Versioning Strategies

  • URL versioning (/v1/orders): visible, simple, and easy to route and cache; the most common
  • Header or media-type versioning: keeps URLs stable but is less discoverable
  • No versions, only additive evolution: ideal when feasible, but needs discipline

Whichever you choose, announce deprecations early, use the Deprecation and Sunset headers to signal retirement dates, monitor which clients still use old versions, and give a generous migration window. Maintaining many versions is costly, so prefer additive changes and cut a new major version only for real breaks.

The key insight Retries are inevitable, so design every state-changing operation to be safe to repeat. Then you can say 'just retry' and mean it.

§4Common Mistakes

MistakeWhat HappensFix
Retrying POST requests with no idempotency keyDuplicate orders or chargesRequire an Idempotency-Key for creation and payment endpoints
Renaming a field in placeExisting clients break with no warningAdd the new field, deprecate the old, and remove after a sunset
Releasing a new major version for every changeMany versions to maintainPrefer additive changes; reserve new versions for true breaks
Practice
  1. Implement an idempotency-key check for POST /payments that stays correct under two simultaneous identical requests.
  2. Classify each of these as breaking or non-breaking: renaming name to full_name, adding nickname, changing id from integer to string.
Key takeaways
  • Idempotency keys make retried POSTs safe by returning the stored result.
  • Additive changes are safe; removing, renaming, or retyping fields is breaking.
  • Version deliberately, deprecate with notice, and expect clients to ignore unknown fields.
