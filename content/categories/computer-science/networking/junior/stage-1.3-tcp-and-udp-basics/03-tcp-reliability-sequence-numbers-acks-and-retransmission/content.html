TCP Reliability: Sequence Numbers, ACKs & Retransmission

TCP builds a reliable, ordered byte stream on top of IP's unreliable packets by numbering bytes, acknowledging them, and resending whatever goes missing.

§1A Stream of Numbered Bytes

TCP numbers every byte, not every segment. Each segment carries the sequence number of its first byte, and the receiver replies with an acknowledgment number: the next byte it expects. ACKs are cumulative, saying 'I have everything up to this point.'

Sender                                    Receiver
  seq=1000, 500 bytes  ─────────────────►
                                          ack=1500   ("got through byte 1499")
  seq=1500, 500 bytes  ─────────────────►  ✗ lost
  seq=2000, 500 bytes  ─────────────────►
                       ◄─ ack=1500         ("still waiting for 1500")
                       ◄─ ack=1500         (duplicate ACK)

The receiver holds segment 2000 aside but can't deliver it to the application until the missing bytes arrive. The application always sees bytes in order, with no gaps.

§2Detecting and Repairing Loss

TCP uses two signals to decide that a segment is lost:

  • Timeout: no ACK arrives within the retransmission timeout (RTO), so the sender retransmits
  • Duplicate ACKs: three duplicate ACKs for the same number imply that later data is arriving while one segment is missing, triggering a fast retransmit without waiting for the timer

Modern TCP also uses selective acknowledgments (SACK), where the receiver reports exactly which ranges it holds, so the sender resends only the actual gaps rather than everything after the hole.

ss -ti dst 203.0.113.9
# Shows per-connection details such as rtt, retrans, and congestion window.
nstat -az TcpRetransSegs            # host-wide retransmission counter

§3What TCP Does and Doesn't Guarantee

GuaranteeProvided by
Data arrivesRetransmission on loss
Data arrives in orderSequence numbers and receiver reordering
Data isn't corruptedA checksum on each segment, plus link-level checks
No duplicates deliveredSequence numbers

TCP gives you a byte stream, not messages. If you send 100 bytes then 200 bytes, the receiver might read 300 bytes at once, or 50 then 250. Applications must define their own message boundaries, with lengths or delimiters, which HTTP does with Content-Length and chunking.

Reliability comes at a cost. A lost segment stalls delivery of everything behind it, called head-of-line blocking, a problem that motivates HTTP/3 in Stage 2.2.

The key insight TCP's 'reliability' means the bytes you send arrive intact and in order or the connection fails. It doesn't mean fast, and it doesn't mean your messages stay separate.

§4Common Mistakes

MistakeWhat HappensFix
Assuming one send equals one recvMessages merge or split unexpectedlyFrame your messages with a length prefix or delimiter
Thinking an ACK means the application processed the dataIt only means the receiving OS buffered the bytesUse an application-level acknowledgment when you need confirmation of processing
Ignoring high retransmission countsLoss hides behind 'it works but slowly'Check ss -ti and nstat when throughput is poor
Practice
  1. Sender transmits segments seq=1, 101, 201, 301 (100 bytes each) and the segment at 101 is lost. List the ACK numbers the receiver sends back.
  2. Use ss -ti on a busy connection and find its RTT and retransmission count.
Key takeaways
  • TCP numbers bytes, and cumulative ACKs report the next byte expected.
  • Loss is repaired by timeouts or fast retransmit after three duplicate ACKs, with SACK narrowing what's resent.
  • TCP delivers an ordered byte stream, not messages, and a lost segment blocks the ones behind it.
