Inspecting HTTP with curl & DevTools

When something goes wrong between a client and a server, seeing the actual request, response, and timing beats guessing, and two tools show you everything.

§1curl: HTTP From the Command Line

curl -v https://example.com/            # verbose: show request and response headers
curl -i https://example.com/            # include response headers in the output
curl -I https://example.com/            # HEAD request: headers only
curl -L http://example.com/             # follow redirects
curl -X POST https://httpbin.org/post \
     -H 'Content-Type: application/json' \
     -d '{"name":"Ada"}'                 # send a JSON body
curl --data-urlencode 'q=a b&c' https://example.com/search
curl -o page.html https://example.com/  # save the body to a file

curl talks plain HTTP without a browser's caching, cookies, or JavaScript, so it shows what the server really sends and removes browser behavior as a variable.

§2Timing a Request

curl can break a request into phases, which tells you where time goes.

curl -s -o /dev/null -w '
dns:       %{time_namelookup}
connect:   %{time_connect}
tls:       %{time_appconnect}
first byte:%{time_starttransfer}
total:     %{time_total}
' https://example.com/
PhaseWhat it measures
time_namelookupDNS resolution
time_connectTCP handshake complete (cumulative)
time_appconnectTLS handshake complete
time_starttransferFirst byte of the response (includes server think time)
time_totalWhole transfer

The numbers are cumulative, so subtract adjacent ones to get each phase's own cost. A big gap before time_starttransfer points at a slow server; a big time_namelookup points at DNS.

§3Browser DevTools

The Network panel in a browser's developer tools (usually F12) lists every request a page makes. Click one to see its headers, cookies, response body, and a timing breakdown. The waterfall column shows requests starting and finishing over time, revealing which resources block others.

  • Right-click, Copy as cURL: reproduces the exact request in your terminal, with all headers and cookies, which is the quickest way to hand a bug to someone else
  • Disable cache: forces fresh loads when measuring
  • Preserve log: keeps requests across page navigations and redirects
  • Throttling: simulates slow networks to see how the page behaves

Compare the browser's view with curl's. If curl works and the browser fails, suspect cookies, CORS, caching, or JavaScript. If both fail, suspect the server or network.

Gotcha Never paste a 'Copy as cURL' command containing cookies or tokens into a public bug report or chat. It includes your real credentials.

§4Common Mistakes

MistakeWhat HappensFix
Debugging from the browser aloneCaching and extensions muddy the pictureReproduce with curl to isolate the server's behavior
Reading time_connect as the handshake's own durationThe values are cumulative from the startSubtract the previous phase to get each phase's cost
Sharing 'Copy as cURL' output publiclyLeaks session cookies and tokensRedact credentials before sharing
Practice
  1. Use curl -w timing variables on a site and work out how long DNS, TCP, TLS, and server time each took.
  2. Open the Network panel on a news site, sort by size, and find the three largest requests. What are they?
Key takeaways
  • curl -v, -I, and -L reveal what the server really sends and how redirects behave.
  • curl -w timing variables break a request into DNS, TCP, TLS, and server time.
  • The DevTools Network panel and 'Copy as cURL' connect what the browser does to what you can reproduce.
