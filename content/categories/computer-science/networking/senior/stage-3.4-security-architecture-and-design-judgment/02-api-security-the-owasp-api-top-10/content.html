API Security: The OWASP API Top 10

The most damaging API vulnerabilities are rarely exotic cryptography flaws; they are missing authorization checks and exposed functionality that the OWASP API Security Top 10 catalogs.

§1The List

OWASP maintains a ranked list of the most common serious API risks. This is the 2023 edition; check for newer versions.

#RiskIn one line
API1Broken Object Level Authorization (BOLA)Changing an ID in the request exposes someone else's object
API2Broken AuthenticationWeak or flawed login, token, or credential handling
API3Broken Object Property Level AuthorizationReading or writing fields the caller shouldn't (mass assignment, excessive data exposure)
API4Unrestricted Resource ConsumptionNo limits on size, rate, or cost of requests
API5Broken Function Level AuthorizationRegular users can call admin endpoints
API6Unrestricted Access to Sensitive Business FlowsAbuse of legitimate flows, such as bulk buying or scraping
API7Server-Side Request Forgery (SSRF)The API fetches a URL the attacker chooses, reaching internal systems
API8Security MisconfigurationDebug mode, open CORS, verbose errors, missing hardening
API9Improper Inventory ManagementForgotten old versions and undocumented endpoints stay exposed
API10Unsafe Consumption of APIsBlindly trusting data from third-party APIs

§2BOLA in Depth

The top item is the simplest and the most common. The API authenticates the user but never checks that the requested object belongs to them.

GET /api/orders/1041          # my order: works
GET /api/orders/1042          # someone else's order: also works (BOLA)

# Vulnerable
order = db.get_order(order_id)
return order

# Fixed: authorize the specific object
order = db.get_order(order_id)
if order.owner_id != current_user.id:
    return 404                # 404 avoids confirming the object exists
return order

Sequential numeric IDs make guessing trivial, though unguessable IDs (UUIDs) are only a speed bump, not a fix. The real defense is an authorization check on every object access, enforced centrally, such as in a data-access layer or policy engine, rather than remembered endpoint by endpoint.

§3Defenses That Generalize

  • Authorize every object and every function: deny by default, and test with two users to confirm that A cannot touch B's data
  • Allow-list input and output fields: never bind request bodies directly to database models (mass assignment), and return only the fields the caller needs
  • Limit resources: page size caps, request body limits, rate limits, and timeouts
  • Block SSRF: allow-list outbound destinations, and reject requests to private and link-local ranges, including cloud metadata addresses
  • Keep an inventory: know every API, version, and environment, and retire old ones
  • Harden configuration: disable debug output, return generic errors with a request ID, and restrict CORS to known origins
  • Validate third-party data as carefully as user input

Automated scanners catch some misconfiguration, but BOLA and business-logic flaws need targeted tests and code review, because the scanner doesn't know who should own what.

The key insight Authentication answers who you are; most API breaches happen because nothing asked whether you're allowed to touch *this* object. Test every endpoint with a second user's credentials.

§4Common Mistakes

MistakeWhat HappensFix
Relying on hard-to-guess IDs for protectionLeaked or enumerated IDs still expose dataEnforce ownership checks regardless of ID format
Binding request JSON straight onto a modelClients set fields like role or is_adminAccept only an explicit allow-list of writable fields
Leaving old API versions runningUnpatched endpoints stay attackableTrack versions and decommission the old ones
Practice
  1. Write a test with two users that confirms user A gets a 404 or 403 when requesting user B's order on every endpoint that takes an ID.
  2. Review an endpoint that updates a user profile from JSON, and list which fields should never be writable by the user.
Key takeaways
  • BOLA, broken authentication, and function-level authorization are the most common serious API flaws.
  • Check authorization on every object and function, and allow-list input and output fields.
  • Limit resources, block SSRF, inventory your APIs, and test with multiple user identities.
