Rate Limiting & Backpressure

Every service has finite capacity, and rate limits plus backpressure keep one noisy client or one traffic spike from taking everyone down.

§1Why Limit

Limits protect the service from overload, abuse, and runaway clients, and they make cost and fairness predictable. Without them, one buggy retry loop can consume capacity meant for all users. The standard response is 429 Too Many Requests with a Retry-After header telling the client when to try again.

HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 30

Decide what you limit by: API key, user, IP address, or endpoint. IP limits are weak against shared NATs and easy to evade, and keys or user IDs are fairer when available.

§2Algorithms

AlgorithmHow it worksTradeoff
Fixed windowCount requests per clock window (such as per minute)Simple, but allows a 2× burst across a window boundary
Sliding windowCount over the last N seconds, continuouslySmoother, costs more to track
Token bucketTokens refill at a steady rate up to a cap; each request spends oneAllows controlled bursts; the most common choice
Leaky bucketRequests enter a queue drained at a fixed rateSmooths output; adds queuing delay
import time
class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate, self.capacity = rate, capacity        # tokens/second, max burst
        self.tokens, self.last = capacity, time.monotonic()

    def allow(self):
        now = time.monotonic()
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

With several servers, counters must be shared, commonly in a fast store such as Redis, or limits must be approximated per node. Perfect global accuracy costs latency, so many systems accept small errors.

§3Backpressure and Load Shedding

Rate limits control individual clients. Backpressure is the broader idea of pushing load signals back toward the source so the system doesn't accept more than it can finish.

  • Bounded queues: when full, reject new work immediately instead of letting latency grow without limit
  • Load shedding: under overload, drop low-priority work and keep serving the important traffic, with a fast 503 rather than a slow failure
  • Concurrency limits: cap in-flight requests per instance, since beyond a point, extra concurrency only adds latency
  • Client cooperation: honor Retry-After, back off exponentially with jitter, and cap retries

A service that accepts everything and slows down for all users fails worse than one that rejects excess quickly and keeps serving the rest. Failing fast is a feature.

The key insight Rejecting early is cheaper than failing late. A fast 429 or 503 costs microseconds, while an accepted request that times out wastes the full cost of processing and the client's wait.

§4Common Mistakes

MistakeWhat HappensFix
Limiting only by IP addressShared NATs are blocked together and attackers rotate IPsLimit by authenticated key or user, with IP as a fallback
Unbounded request queuesLatency balloons and memory fills during overloadBound the queue and reject when full
Clients retrying immediately on 429Retry storms worsen the overloadHonor Retry-After and use exponential backoff with jitter
Practice
  1. Implement a token bucket allowing 10 requests per second with bursts up to 20, and test it with a burst of 50 requests.
  2. Explain how a fixed-window limiter allows twice the intended rate around a window boundary.
Key takeaways
  • Return 429 with Retry-After, and limit by key or user where possible.
  • Token bucket allows bursts at a steady average; fixed windows allow boundary spikes.
  • Bound queues and shed load early so overload degrades gracefully instead of cascading.
