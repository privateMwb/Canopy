gRPC & Protocol Buffers

gRPC trades REST's human-readable flexibility for a strict binary contract, generated clients, and built-in streaming, which pays off for service-to-service calls.

§1Schema First

In gRPC, the API is defined in a Protocol Buffers (.proto) file, a language-neutral schema. A compiler generates typed client and server code in many languages, so calling a remote service looks like calling a local function.

syntax = "proto3";

service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);
  rpc WatchOrders (WatchRequest) returns (stream Order);   // server streaming
}

message GetOrderRequest { int64 id = 1; }
message Order {
  int64  id     = 1;
  string status = 2;
  repeated Item items = 3;
}

Each field has a number (= 1, = 2) that identifies it on the wire, rather than a name. Messages are encoded in a compact binary format that is smaller and faster to parse than JSON. Transport is HTTP/2, so many calls share one connection.

§2Four Call Types and Deadlines

TypeShapeExample
UnaryOne request, one responseGetOrder
Server streamingOne request, a stream of responsesWatching updates
Client streamingA stream of requests, one responseUploading chunks
Bidirectional streamingBoth sides stream independentlyChat, live telemetry

Every call can carry a deadline, an absolute time by which the answer must arrive. The deadline propagates through nested calls, so downstream services stop work the caller has already given up on. Errors use a defined set of status codes, such as NOT_FOUND, DEADLINE_EXCEEDED, and UNAVAILABLE, rather than HTTP codes.

§3Costs and Evolution Rules

  • Browsers can't speak gRPC directly, so web clients need a proxy translation layer (gRPC-Web) or a separate REST/JSON gateway
  • Harder to inspect: binary payloads need tools such as grpcurl rather than curl
  • Load balancing needs care: a client holds one long-lived HTTP/2 connection, so a plain connection-level (L4) balancer sends all its calls to one backend. Use an L7 or client-side balancer that distributes individual calls
  • Never reuse or renumber a field number. Removed fields should be marked reserved. Adding new fields is safe, because old readers skip unknown numbers
grpcurl -plaintext localhost:50051 list
grpcurl -plaintext -d '{"id": 42}' localhost:50051 OrderService/GetOrder

gRPC fits internal service-to-service traffic, polyglot environments, and streaming. REST/JSON fits public APIs, browser clients, and any case where easy exploration and caching matter more than raw efficiency.

The key insight gRPC moves the contract from documentation into code. The schema is the source of truth, which prevents a whole class of mismatches between caller and callee, at the cost of tooling and browser friction.

§4Common Mistakes

MistakeWhat HappensFix
Reusing a retired field numberOld clients decode new data as the wrong field, silentlyMark removed numbers reserved and never reuse them
Putting a gRPC service behind an L4 load balancerOne connection pins all calls to one backendUse an L7 balancer or client-side load balancing
Calling without a deadlineA stuck call can hang forever and exhaust resourcesAlways set a deadline and propagate it
Practice
  1. Write a .proto for a small service with one unary and one server-streaming call, and generate code in a language you use.
  2. Explain why adding a new field is a compatible change but changing a field's type usually isn't.
Key takeaways
  • gRPC uses .proto schemas, generated code, binary encoding, and HTTP/2.
  • It supports unary and three streaming modes, with deadlines that propagate across calls.
  • It suits internal services; browsers, debugging, and L4 load balancing need extra handling.
