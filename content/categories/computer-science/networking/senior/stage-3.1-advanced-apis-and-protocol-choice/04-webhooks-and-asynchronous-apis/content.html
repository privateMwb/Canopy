Webhooks & Asynchronous APIs

A webhook reverses the direction of an API call: the provider sends events to you, so you must verify them, handle duplicates, and survive your own downtime.

§1How Webhooks Work

Instead of polling a provider to ask 'did anything happen?', you register a URL, and the provider sends an HTTP POST to it whenever an event occurs.

POST /webhooks/payments HTTP/1.1
Host: yourapp.example.com
Content-Type: application/json
X-Signature: t=1750000000,v1=5257a869e7ecebeda32affa62cdca3fa51cad7e77a0e56ff536d0ce8e108d8bd

{"id": "evt_123", "type": "payment.succeeded", "data": {"payment_id": "pay_9"}}

Your endpoint is a public URL that anyone can call, so the first duty is to prove the request really came from the provider.

§2Receiving Them Safely

  1. Verify the signature. The provider signs the raw body, plus a timestamp, with a shared secret using HMAC. Recompute it and compare in constant time. Reject old timestamps to block replays
  2. Respond quickly with 2xx. Acknowledge after durably recording the event, then do heavy work asynchronously. Providers time out and retry slow endpoints
  3. Be idempotent. Providers retry on failure and may deliver the same event more than once, so record each event ID and ignore repeats
  4. Don't assume order. payment.updated can arrive before payment.created; handle events based on their data and fetch current state when it matters
import hmac, hashlib
expected = hmac.new(SECRET, f"{timestamp}.".encode() + raw_body, hashlib.sha256).hexdigest()
if not hmac.compare_digest(expected, received_sig):     # constant-time comparison
    return 401
if event_id_seen(event["id"]):                          # idempotency
    return 200
enqueue(event); mark_seen(event["id"]); return 200

§3Designing the Sending Side

If you provide webhooks, the same concerns apply in reverse.

  • Retries with exponential backoff over hours or days, then a dead-letter queue and a way to replay events
  • Sign every payload and include a timestamp and unique event ID
  • Timeouts: give receivers a short window, such as 5 to 10 seconds, and treat anything else as failure
  • Protect yourself (SSRF): customers supply URLs, so block requests to internal addresses such as 169.254.169.254 or 10.0.0.0/8
  • Visibility: show delivery logs and let users resend events
  • Disable endpoints that fail persistently, and notify the owner

For flows that take a long time, a common asynchronous pattern is to answer 202 Accepted with a Location header pointing to a status resource, which the client polls, or by registering a webhook for completion.

The key insight A webhook receiver must assume events are duplicated, delayed, out of order, and possibly forged. Signature verification, idempotent handling, and fast acknowledgment answer all four.

§4Common Mistakes

MistakeWhat HappensFix
Skipping signature verificationAnyone can forge events to your endpointVerify the HMAC over the raw body with a constant-time comparison
Doing slow work before respondingThe provider times out and retries, causing duplicatesPersist the event, return 2xx, and process in the background
Assuming exactly-once, in-order deliveryDouble processing or wrong stateDeduplicate on event ID and tolerate reordering
Practice
  1. Implement a webhook endpoint that verifies an HMAC signature and ignores duplicate event IDs, then test it with a replayed request.
  2. List the ways a webhook delivery can go wrong and how your receiver handles each.
Key takeaways
  • Webhooks push events to your URL, so verify signatures, acknowledge fast, and process asynchronously.
  • Expect retries and duplicates: handle each event ID idempotently, and don't assume ordering.
  • Senders need retries with backoff, dead-letter handling, replay, and SSRF protection.
