WebSockets, SSE & Real-Time Updates

HTTP is request-driven, so pushing data to clients needs another pattern, and the choice among polling, server-sent events, and WebSockets depends on direction and scale.

§1Four Ways to Get Updates

TechniqueHow it worksDirectionNotes
PollingClient asks every N secondsClient → serverSimple, but wasteful and delayed
Long pollingRequest held open until data exists, then repeatedServer → clientWorks anywhere; many round trips
Server-Sent Events (SSE)One long HTTP response streaming text/event-streamServer → client onlyAuto-reconnect, plain HTTP
WebSocketUpgraded connection with framed messages both waysBothFull duplex, custom protocol

§2SSE and WebSocket Basics

SSE keeps one HTTP response open and streams lines of text events. Browsers reconnect automatically and can resume using the Last-Event-ID header, and it works through most proxies and with HTTP/2 multiplexing.

GET /events HTTP/1.1
Accept: text/event-stream

HTTP/1.1 200 OK
Content-Type: text/event-stream

id: 42
event: price
data: {"symbol":"ACME","value":101.5}
(blank line ends one event)

A WebSocket starts as an HTTP request asking to upgrade, then the same TCP connection switches to a message-framed protocol where either side can send at any time.

GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
# From here on: binary/text frames, with ping/pong for liveness.

§3Operating Real-Time Connections

Long-lived connections behave differently from request-response, and most problems surface in operation.

  • State: each connection is held by one server, so scaling needs a shared pub/sub layer to fan messages out to whichever node holds the recipient
  • Idle timeouts: proxies and load balancers close quiet connections, so send heartbeats or pings regularly
  • Reconnection storms: after an outage, every client reconnects at once; use exponential backoff with jitter
  • Authentication: validate during the handshake, and again as tokens expire, since browsers can't set custom headers on WebSocket handshakes from JavaScript
  • Backpressure: a slow client must not make the server buffer unlimited messages, so bound queues and drop or disconnect laggards
  • Load balancing: long-lived connections make connection counts uneven; drain gracefully during deploys

A practical rule: use SSE when the server only needs to push (dashboards, notifications, progress), WebSockets when the client also sends frequent messages (chat, collaboration, games), and plain polling when updates are infrequent and simplicity wins.

Gotcha Real-time connections hold server resources for their whole lifetime, so a deploy or crash disconnects everyone at once. Plan for graceful draining and jittered reconnects before you need them.

§4Common Mistakes

MistakeWhat HappensFix
Using WebSockets when SSE is enoughMore complexity for one-way pushesChoose SSE for server-to-client updates
No heartbeats on idle connectionsIntermediaries silently drop them and clients don't noticeSend periodic pings and detect missed ones
Immediate reconnects after a failureThundering herd overloads the recovering serverReconnect with exponential backoff and random jitter
Practice
  1. Implement an SSE endpoint that sends a counter every second, and consume it with curl -N.
  2. Design how a chat service with 10 server nodes delivers a message to a recipient connected to a different node.
Key takeaways
  • Polling, long polling, SSE, and WebSockets trade simplicity against direction and efficiency.
  • SSE is one-way over plain HTTP with automatic reconnection; WebSockets are full-duplex after an upgrade.
  • Operate them with heartbeats, backpressure, jittered reconnects, and a pub/sub layer for scaling.
