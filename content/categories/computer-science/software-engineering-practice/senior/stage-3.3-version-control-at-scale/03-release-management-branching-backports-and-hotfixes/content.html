Release Management: Branching, Backports & Hotfixes

Shipping a library or a service to many users means answering: how do fixes reach old versions, and how do you ship them without chaos?

§1Release Branches

In trunk-based teams, releases are cut by tagging the trunk. When you need to support a released version while the trunk moves on (a library with long-term users, an on-premises product), you create a release branch at the release point and keep fixes there.

main      --A--B--C--D--E--F--G--H--      (new development)
                 \
release/1.4       C1--X1--X2                (1.4.1, 1.4.2: fixes only)
                      ^   ^
                  tag v1.4.1 v1.4.2

§2Backports and Hotfixes

A backport applies a fix made on the trunk to older supported releases. The usual flow: fix on main first (so it can't regress in the next release), then cherry-pick to each supported release branch.

git switch main
# ...fix the bug, merge it...  commit abc1234

git switch release/1.4
git cherry-pick -x abc1234         # -x records the original hash in the message
git tag v1.4.2 && git push origin release/1.4 v1.4.2

A hotfix is an urgent fix to production, done with the same discipline: smallest possible change, reviewed, tested, tagged, and then merged back so that the main line has it too.

  • Fix forward on main first whenever you can
  • Keep the hotfix tiny; urgent isn't the time for cleanup
  • Always port the fix to every branch that needs it, or it reappears later

§3Support Policy and Cadence

Every supported version costs effort, so decide explicitly what you will support. Publish the policy so users can plan.

Support policy (example):
  - Current release:     all fixes and features
  - Previous minor:      security and critical bug fixes for 12 months
  - Older than that:     unsupported; upgrade path documented

Cadence: a minor release every 6 weeks; patches as needed.
  • Frequent, small releases are safer than rare large ones; they're easier to test and to roll back
  • Release checklist: version bump, changelog, tag, artifacts, announcement, ideally automated
  • Rollback plan: know before each release how you'd undo it
  • Keep branches few: every extra supported branch multiplies backport work
The key insight Release strategy is mostly a decision about how many versions you promise to keep alive. Fewer, shorter-lived branches cost far less.

§4Common Mistakes

MistakeWhat HappensFix
Fixing only on the release branchThe bug returns in the next releaseFix on main, then backport, or merge the release branch back
Supporting every old version foreverBackport work grows without boundSet and publish a support window
Large, infrequent releasesEach is risky and hard to roll backShip smaller changes more often
Practice
  1. Write a support policy for a library you maintain or use.
  2. Practice a backport: cherry-pick a fix onto a release branch and tag it.
  3. Write a release checklist and mark the steps that could be automated.
Key takeaways
  • Use release branches only for versions you support.
  • Fix on main first, then backport with cherry-pick.
  • Publish a support policy and release often.
