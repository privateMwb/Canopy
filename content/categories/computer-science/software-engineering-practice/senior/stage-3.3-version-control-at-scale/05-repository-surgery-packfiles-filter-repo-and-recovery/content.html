Repository Surgery: Packfiles, filter-repo & Recovery

Sometimes history has to be rewritten: a leaked secret, a huge binary, a corrupted repository. Knowing the tools, and the cost, keeps you calm when it happens.

§1Packfiles and Why Repos Grow

Git stores objects as individual files, then periodically bundles them into compressed packfiles, storing similar objects as deltas. A repository grows when large or frequently changing binary files are committed, because every version stays in history, even after the file is deleted.

git count-objects -vH                 # size of the repository
git rev-list --objects --all |
  git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' |
  sort -k3 -n -r | head                # largest objects in history

git gc --aggressive                    # repack (does NOT drop reachable history)

Deleting a file in a new commit doesn't shrink anything: the old blob is still reachable from history. To really remove it, history itself must be rewritten.

§2Removing Secrets and Big Files

The tool for this is git filter-repo (the modern replacement for filter-branch and BFG).

# remove a file from every commit
git filter-repo --invert-paths --path config/secrets.yml

# remove files over a size
git filter-repo --strip-blobs-bigger-than 10M

# replace text everywhere in history
git filter-repo --replace-text expressions.txt
  • First, treat the secret as compromised and rotate it. Rewriting history doesn't un-leak a key that was pushed
  • Work on a fresh clone and keep a backup
  • Every commit hash after the change is new, so all collaborators must re-clone or reset to the rewritten history
  • Also purge forks, caches, and CI artifacts; remove it from the hosting provider's cached views, which may need a support request

Prevention is far cheaper: .gitignore, secret scanning in pre-commit hooks and CI, and Git LFS or external storage for large binaries.

§3Recovery and What Rewriting Costs

When things go wrong, the reflog is your safety net. It records every position of HEAD and each branch for around 90 days, so lost commits are usually recoverable.

git reflog                            # where HEAD has been
git branch rescue 7c3d9e1             # make a branch at the lost commit
git fsck --lost-found                 # find unreachable (dangling) commits
git bundle create backup.bundle --all # portable full backup before surgery

Rewriting shared history has real costs: broken open pull requests, invalidated signatures and tags, stale clones that reintroduce the removed data, and coordination across the team. Do it rarely, announce it, schedule it, and write down the steps. Do it only when the reason (a secret, legal removal, repository health) outweighs the disruption.

The key insight Deleting a file doesn't delete its history. And rewriting history removes data from your repository, but it can't take back what others already copied.

§4Common Mistakes

MistakeWhat HappensFix
Deleting a leaked secret in a new commitIt's still in history and visible to anyone with the repoRotate the secret first, then purge history if needed
Running filter-repo on your only copyA mistake can destroy work with no way backOperate on a fresh clone, and keep a bundle backup
Rewriting shared history without warningTeammates' clones diverge and old data returnsAnnounce, coordinate, and have everyone re-clone
Practice
  1. Find the five largest objects in a repository's history.
  2. On a throwaway clone, use git filter-repo to remove a file from all history.
  3. Recover a deleted branch using the reflog.
Key takeaways
  • Large and sensitive files stay in history after deletion.
  • Rotate leaked secrets first; filter-repo cleans history second.
  • The reflog and a bundle backup make surgery recoverable; coordinate before rewriting shared history.
