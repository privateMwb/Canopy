Conventional Commits, Changelogs & Automated Releases

If commit messages follow a format, tools can work out version numbers, write changelogs, and publish releases, taking human error out of the process.

§1Conventional Commits

The Conventional Commits convention gives each commit message a structured prefix describing the kind of change.

<type>(<scope>): <summary>

feat(cart): add coupon codes
fix(payments): avoid double charge on retry
docs: explain retry settings
refactor(auth): extract token parsing
feat(api)!: remove v1 endpoints          # '!' marks a breaking change

BREAKING CHANGE: /v1/orders is gone; use /v2/orders.
TypeMeaningVersion bump
fixA bug fixPATCH
featA new featureMINOR
feat! / BREAKING CHANGEIncompatible changeMAJOR
docs, refactor, test, choreNo user-visible changeNone

§2Automatic Versions and Changelogs

Because the types map onto semantic versioning, a tool can read the commits since the last tag and compute the next version for you, with no one arguing about whether this is a minor or a patch.

commits since v1.4.2:
  fix(payments): avoid double charge on retry
  feat(cart): add coupon codes
  docs: explain retry settings

-> next version: 1.5.0          (a feat was added, no breaking change)

## 1.5.0 (2026-10-21)
### Features
* cart: add coupon codes
### Bug Fixes
* payments: avoid double charge on retry

Tools such as semantic-release, release-please, and git-cliff generate the changelog from the same data, so the notes users read are always in step with what shipped.

§3Automating the Release

A release pipeline can run on every merge to main: decide whether a release is warranted, bump the version, update the changelog, tag, build artifacts, and publish.

  • Enforce the format with a commit-message linter in CI (commitlint)
  • Squash-merge with a well-written PR title if you'd rather not police every commit
  • Keep humans in the loop for major versions or high-risk packages: a release pull request that you review and merge
  • Beware of garbage in, garbage out: if messages are careless, versions and notes will be wrong

The payoff isn't only speed. A release becomes a boring, repeatable procedure, and that is what makes frequent releases safe.

The key insight Structure in commit messages is data. Once it's data, the repetitive parts of a release can be computed instead of done by hand.

§4Common Mistakes

MistakeWhat HappensFix
Mislabeling a breaking change as fixUsers upgrade expecting safety and breakUse ! or a BREAKING CHANGE footer, and review the computed version
Free-form messages with automated releasesWrong version numbers and empty changelogsLint the format in CI
A changelog that is just a commit dumpUsers can't find what matters to themGenerate by type and edit the highlights by hand
Practice
  1. Rewrite your last ten commit messages in conventional format.
  2. Compute the next version from a list of commits by hand, using the rules.
  3. Add a commit-message linter to CI.
Key takeaways
  • Conventional Commits encode the kind of change in the message.
  • Tools turn commits into version bumps and changelogs.
  • Automating releases makes them frequent and boring.
