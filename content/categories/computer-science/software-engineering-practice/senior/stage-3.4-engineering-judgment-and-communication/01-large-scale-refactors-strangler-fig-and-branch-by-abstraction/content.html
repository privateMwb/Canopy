Large-Scale Refactors: Strangler Fig & Branch by Abstraction

The hardest refactors replace something that has to keep running. Two techniques, the strangler fig and branch by abstraction, make that possible.

§1Why Big-Bang Rewrites Fail

The tempting plan is to build the new system on the side and switch over at the end. It rarely works: the old system keeps changing so the target moves, the new one has no real users or data until the end so problems surface late, and the team is stuck maintaining two systems. The switch-over becomes a high-risk event, often delayed again and again.

The safer idea is to replace the system piece by piece, while it runs, so that every step is small, reversible, and delivers value.

§2The Strangler Fig

Named after a vine that grows around a tree and gradually replaces it, the strangler fig pattern puts a routing layer in front of the old system and moves one capability at a time to the new one. Old and new coexist until nothing is left of the old.

             +--> new service   (invoices, since March)
requests --> router --+--> new service   (customers, since June)
             +--> legacy monolith (everything else; shrinking)

step: pick a slice -> build it new -> route a % of traffic -> compare
      -> route 100% -> delete the old slice
  • Choose seams along natural boundaries: a feature, an endpoint, a data set
  • Run in parallel: send traffic to both and compare results (shadow mode) before trusting the new path
  • Migrate data deliberately: decide which side owns each table and for how long; sync both ways if needed
  • Be able to roll back each slice independently
  • Delete the old code at the end of each slice, or you keep both forever

§3Branch by Abstraction

For changes inside one codebase, such as swapping a library or an internal component, use branch by abstraction: introduce an interface in front of the old code, migrate callers to it, build the new implementation behind the same interface, switch over, then remove the old one. Every step ships on the trunk, and the system works at all times.

1. introduce interface Mailer; wrap old SmtpClient behind it
2. change every caller to use Mailer                    (no behavior change)
3. build ApiMailer implementing Mailer                  (flag off)
4. switch via flag: 1% -> 100%, comparing deliveries
5. delete SmtpClient and the flag

Each of those steps can be merged and released independently. That's the whole point: a large change is made of many small safe ones.

The key insight The way to make a risky change safe is to make it in small, reversible steps while the system keeps serving users, not to make it safer by planning it more.

§4Common Mistakes

MistakeWhat HappensFix
Rewriting everything beside the live systemA moving target, late feedback, and a risky cutoverReplace one slice at a time behind a router or interface
Never deleting the old pathTwo systems to maintain foreverSchedule removal as the last step of each slice
Switching all traffic at onceHard to find the cause of problems and to undoShift gradually, compare outputs, and keep a rollback
Practice
  1. Pick one capability of a legacy system and sketch the first strangler step.
  2. Plan a library swap as five branch-by-abstraction steps, each shippable.
  3. Decide how you'd compare old and new outputs for the first slice.
Key takeaways
  • Replace systems incrementally while they keep running.
  • The strangler fig reroutes traffic slice by slice; branch by abstraction swaps internals behind an interface.
  • Every step must be small, reversible, and followed by deleting what it replaced.
