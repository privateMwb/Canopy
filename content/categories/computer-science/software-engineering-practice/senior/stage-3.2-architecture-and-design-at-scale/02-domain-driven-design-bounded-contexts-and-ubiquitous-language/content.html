Domain-Driven Design: Bounded Contexts & Ubiquitous Language

Domain-driven design starts from a simple observation: most software failures are failures of understanding the business. Its tools help code say what the business says.

§1Ubiquitous Language

Developers and domain experts often use different words for the same thing, and the translation hides misunderstanding. DDD asks for a ubiquitous language: one set of terms used by everyone, in conversation, in documents, and in the code itself.

# technical vocabulary: the business can't read it
record.status = 3
record.flag_b = True

# business vocabulary: a domain expert can read this
claim.approve(by=adjuster)
claim.mark_as_fraud_suspected()

When the experts say "policy" and the code says contract, bugs hide in the gap. Rename the code, or settle the word with the experts.

§2Bounded Contexts

A single model of the whole company never works, because words change meaning across departments. "Customer" in sales means a prospect with a pipeline; in billing it means a payer with an address and tax ID; in support it means someone with open tickets. Trying to build one Customer class for all three produces a bloated compromise.

A bounded context is a boundary inside which one model and one language are consistent. Each context gets its own model, and contexts talk through explicit translation at the edges.

+-----------+      +-----------+      +-----------+
|  Sales    |      |  Billing  |      |  Support  |
| Customer: |      | Customer: |      | Customer: |
| lead,     |  ->  | payer,    |  ->  | tickets,  |
| pipeline  |      | tax id    |      | history   |
+-----------+      +-----------+      +-----------+
     each context owns its model; mapping happens at the boundaries

§3Aggregates: Units of Consistency

An aggregate is a cluster of objects treated as one unit for changes, with a single root that guards its rules. Outside code talks only to the root, and the whole aggregate is saved or loaded together. This defines what must be consistent immediately and what can be consistent later.

class Order:                                  # aggregate root
    def __init__(self): self._lines = []
    def add_line(self, product, qty):
        if qty <= 0: raise ValueError("quantity must be positive")
        if len(self._lines) >= 100: raise ValueError("too many lines")
        self._lines.append(OrderLine(product, qty))   # invariants enforced here

# outside code never edits OrderLine directly; it asks Order

Keep aggregates small. A giant aggregate causes contention and slow saves; refer to other aggregates by ID, not by holding them.

DDD is heavy machinery, worth it for complex domains with rich rules and several teams, and overkill for simple data entry.

The key insight Draw boundaries where the meaning of words changes. Inside a boundary, keep one clear model and speak the business's language.

§4Common Mistakes

MistakeWhat HappensFix
One shared model for the whole organizationA bloated class that means different things to everyoneSplit into bounded contexts with explicit translation
Technical names that experts don't recognizeMisunderstandings sit in the code unnoticedUse the domain's words in classes, methods, and tests
Huge aggregatesSlow saves and conflicting updatesKeep them small and reference others by ID
Practice
  1. List five domain terms from your project and check whether the code uses the same words.
  2. Find a word that means two things in different parts of the system and sketch two contexts.
  3. Identify an aggregate root in your code and the rules it should enforce.
Key takeaways
  • A ubiquitous language ties code and business together.
  • Bounded contexts keep each model small and coherent.
  • Aggregates define the boundary of immediate consistency.
