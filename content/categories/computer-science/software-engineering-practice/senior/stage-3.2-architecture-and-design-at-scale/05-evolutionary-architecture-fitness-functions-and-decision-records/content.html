Evolutionary Architecture: Fitness Functions & Decision Records

Architecture drifts unless something holds it in place. Fitness functions defend its intent automatically, and decision records explain why it looks the way it does.

§1Why Architecture Erodes

A clean design on a diagram degrades one shortcut at a time. Each pull request that reaches across a boundary seems reasonable alone. Reviews catch some of it, but reviewers forget the rules, and new people never learned them. Without active defense, the architecture on the wiki and the one in the code diverge.

Evolutionary architecture accepts that systems change and designs so that they can, with automatic checks that guard what matters.

§2Fitness Functions: Rules You Can Run

A fitness function is an automated check that an architectural property still holds. It runs in CI like any test and fails the build when someone breaks a rule.

# layering rule as a test: domain must not import infrastructure
def test_domain_does_not_depend_on_infrastructure():
    for module in modules_under("shop/domain"):
        imports = imported_modules(module)
        assert not any(i.startswith(("shop.infrastructure", "flask", "sqlalchemy"))
                       for i in imports), f"{module} breaks the dependency rule"
  • Structure: no cycles; layer and package dependency rules (tools: ArchUnit, import-linter, dependency-cruiser)
  • Performance: the checkout endpoint's p95 stays under 300 ms in a load test
  • Size and complexity: no module above an agreed size or complexity score
  • Security: no use of banned functions; all endpoints require authentication

Start with the one or two rules that would hurt most to lose.

§3Architecture Decision Records

Six months on, nobody remembers why the team picked a message queue over direct calls, so someone reverses it, or defends it blindly. An ADR is a short, dated note stored in the repo that records a significant decision and its reasoning.

# ADR 0007: Use an outbox table for publishing events
Status:   Accepted (2026-03-02)
Context:  Orders must publish an event, and the DB write and the publish
          must not diverge. Dual writes lost events twice in Q4.
Decision: Write events to an outbox table in the same transaction;
          a relay publishes them.
Consequences:
  + No lost events; simple to reason about.
  - Extra table and relay process; events are slightly delayed.
Alternatives considered: two-phase commit (too heavy), CDC (later).

ADRs record context and trade-offs, not just the outcome. When circumstances change, write a new ADR that supersedes the old one instead of editing history.

The key insight Write the rules down as tests so they hold themselves, and write the reasons down as ADRs so people can tell when it is time to change them.

§4Common Mistakes

MistakeWhat HappensFix
Architecture only on a diagramThe code drifts from the design with nobody noticingEncode key rules as automated fitness functions in CI
ADRs that state only the decisionLater readers can't judge whether it still appliesCapture context, alternatives, and consequences
Too many rules, too earlyNoisy build and constant exceptionsGuard only what is costly to lose and review them periodically
Practice
  1. Write one fitness function that enforces a layering rule in your project.
  2. Write an ADR for the last significant technical decision your team made.
  3. List the three architectural rules whose loss would hurt most.
Key takeaways
  • Fitness functions are automated architectural tests.
  • ADRs preserve context and trade-offs for future decisions.
  • Guard what matters most, and let rules and records evolve.
