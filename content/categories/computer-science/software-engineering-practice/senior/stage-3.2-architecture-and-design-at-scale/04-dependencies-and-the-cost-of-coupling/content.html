Dependencies & the Cost of Coupling

Every library and every internal package you depend on is a long-term commitment. Choosing and containing dependencies is part of design.

§1Dependencies Are Liabilities

A dependency gives you code you don't have to write, and charges you for it: security vulnerabilities you inherit, breaking upgrades, abandoned projects, license obligations, larger builds, and the work of understanding it when it fails. The cost isn't paid on the day you add it, but over years.

Before adding one, ask: how much do I use? Could I write that part in an afternoon? Who maintains it, and how healthy is the project? How hard would it be to replace?

§2Direction and Shape of Dependencies

Inside your own code, the same questions apply to packages. Healthy structure has acyclic dependencies that point toward stable, general code. Unhealthy structure has cycles, and hubs that everything depends on and that change constantly.

healthy:                         unhealthy:
  app -> orders -> pricing          app <-> orders <-> pricing
          |                                 ^           |
          v                                 +--- util --+  (cycle)
       storage
  • Stable dependencies principle: depend in the direction of stability; volatile modules depend on stable ones, not the reverse
  • Break cycles by extracting the shared part into a new module both can use, or by inverting one dependency with an interface
  • Depend on what you use: a huge utility module pulled in for one function drags everything along

§3Containing and Maintaining Them

  • Wrap third-party libraries behind your own small interface (adapter), so replacing one touches one file
  • Pin versions and use lockfiles so builds are repeatable
  • Update regularly in small steps; a three-year-old dependency is a painful jump, while a monthly bump is routine
  • Watch for vulnerabilities with automated scanning, and know your transitive dependencies
  • Track and remove unused dependencies
# your code depends on this, not on the vendor's types
class Geocoder(Protocol):
    def locate(self, address: str) -> LatLng: ...

class AcmeGeocoder:                    # the only file that imports acme_sdk
    def locate(self, address): return to_latlng(acme_sdk.lookup(address))

Dependency choices are architectural decisions. Record the important ones, with the reason, as you would any other.

The key insight The price of a dependency is paid over its whole lifetime, not on the day you install it. Keep them few, wrapped, current, and pointing in a sensible direction.

§4Common Mistakes

MistakeWhat HappensFix
Adding a library for ten lines of codeA permanent dependency for a trivial gainWeigh usage against maintenance and risk first
Calling a vendor SDK from everywhereSwitching vendors means editing the whole codebaseWrap it behind one adapter
Never updating dependenciesUpgrades pile up into a risky multi-year jumpUpdate in small, regular steps with tests
Practice
  1. List your direct dependencies and mark which ones you could replace in a day.
  2. Wrap one third-party library behind an interface of your own.
  3. Find one cycle between your packages and break it.
Key takeaways
  • Every dependency has a lifetime cost.
  • Keep internal dependencies acyclic and pointing toward stability.
  • Wrap, pin, and update third-party code regularly.
