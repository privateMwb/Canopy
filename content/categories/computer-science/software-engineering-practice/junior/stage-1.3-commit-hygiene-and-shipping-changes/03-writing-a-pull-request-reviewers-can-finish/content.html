Writing a Pull Request Reviewers Can Finish

A pull request is a message to a busy person. Small, well-described changes get reviewed faster and more carefully.

§1Keep the Diff Small

Review quality drops sharply as a change grows. Reviewers skim a 1,000-line diff, but read a 100-line one. Aim for a change that can be understood in 15 minutes: one purpose, a few files.

If a feature is big, split it: a preparatory refactor first, then the new behavior in a second pull request. Mixing a refactor with a feature hides the real change in noise.

PR 1: Rename and move payment helpers (no behavior change)
PR 2: Add retry logic to payments
PR 3: Expose retry count in the admin page

§2Write the Description for a Stranger

The description should let someone with no context understand the change. Say what the problem was, what you changed, and how to check it.

Title: Retry failed payments up to 3 times

Why:    Card processor returns transient errors; ~2% of orders failed
        and needed manual re-entry.
What:   Retry with backoff on 5xx responses only. Declines are not retried.
Test:   New unit tests for backoff; manually tested against sandbox.
Notes:  Retry limit is in config (PAYMENT_MAX_RETRIES), default 3.

Pointing at anything that needs a closer look, such as a tricky decision or something you're unsure of, helps reviewers spend attention where it matters.

§3Review Your Own Change First

Before asking anyone, read your own diff as if someone else wrote it. You will catch leftover debug prints, stray formatting changes, commented-out code, and missing tests. Make sure tests pass and the branch is up to date.

  • No debug output or unrelated formatting changes
  • Tests added or updated, and passing
  • The description matches what the diff actually does
  • You can explain every line in it
The key insight The author does the work to make a change easy to review. Time spent on a clear small pull request is repaid in faster, better feedback.

§4Common Mistakes

MistakeWhat HappensFix
One huge pull requestReviewers skim, miss bugs, and the PR sits for daysSplit into small steps with a single purpose each
An empty descriptionReviewers must reverse-engineer the intentState the why, the what, and how it was tested
Not reviewing your own diffReviewers find debug prints and typos you could have caughtRead the diff as a stranger before requesting review
Practice
  1. Take a large branch of yours and decide how to split it into three pull requests.
  2. Write a description for a recent change using why, what, and test.
  3. Read your next diff before submitting and note what you would have flagged.
Key takeaways
  • Small, single-purpose changes get better reviews.
  • Write the description for someone with no context.
  • Self-review before you ask others to spend time.
