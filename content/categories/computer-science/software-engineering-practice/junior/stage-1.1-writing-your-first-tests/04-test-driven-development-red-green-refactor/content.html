Test-Driven Development: Red, Green, Refactor

TDD turns the usual order around: you write a failing test first, and the test tells you exactly what to build next.

§1The Red, Green, Refactor Loop

Test-driven development is a short loop. Red: write a small test for behavior that doesn't exist yet, and watch it fail. Green: write the simplest code that makes it pass. Refactor: clean up the code and the test while everything stays green. Then repeat with the next small behavior.

# RED: write the test first; it fails because is_palindrome doesn't exist
def test_single_letter_is_a_palindrome():
    assert is_palindrome("a") is True

# GREEN: the simplest thing that passes
def is_palindrome(s):
    return True

# next RED: forces the real logic
def test_two_different_letters_are_not_a_palindrome():
    assert is_palindrome("ab") is False

# GREEN again
def is_palindrome(s):
    return s == s[::-1]

§2Why Watch It Fail?

Seeing the test fail first proves the test can fail. A test that has never been red might be checking nothing at all. Running it red also confirms it fails for the reason you expect, not because of a typo.

Writing tests first also shapes the design. If a function is hard to call from a test, it will be hard to call from everywhere else, and you find out before you've built much on top of it.

§3When TDD Helps and When It Doesn't

TDD works best where the behavior is clear and the logic is intricate: parsers, calculations, business rules, bug fixes. For bugs it is especially good: write a test that reproduces the bug, see it fail, fix it, and the bug is guarded forever.

It works less well when you are still exploring what to build, such as a throwaway prototype or a visual layout. It's fine to explore first, then write tests as you settle on the design. TDD is a tool, not a rule of conduct.

# Bug-fix TDD: the cheapest, highest-value use
def test_username_with_trailing_space_is_trimmed():   # fails today
    assert normalize_username("  ana ") == "ana"
A good rhythm Each loop should take a few minutes. If you've been red for half an hour, the step was too big. Throw it away and take a smaller one.

§4Common Mistakes

MistakeWhat HappensFix
Writing many tests before any codeA wall of red with no clear next stepOne failing test at a time, then make it pass
Skipping the refactor stepThe code passes but fills up with duplication and hacksSpend the green moment cleaning up before the next test
Making the test pass by special-casing the exact inputCode that only works for the exampleAdd a second example that forces the general rule
Practice
  1. Use TDD to build fizzbuzz(n) in five loops. Commit after each green.
  2. Take a bug you know of, write a failing test for it first, then fix it.
  3. Try writing a prototype with no tests, then add tests afterward. Compare how each felt.
Key takeaways
  • Red, green, refactor, in small steps.
  • Watching a test fail proves it can fail for the right reason.
  • TDD shines for clear logic and bug fixes; explore first when the design is unclear.
