Why We Test: Confidence, Regression & Fast Feedback

A test is a small program that runs your code and checks the answer, so you don't have to check it by hand every time you change something.

§1What Tests Are Really For

Tests do three jobs. They give you confidence that code does what you think it does. They catch regressions, where a change in one place quietly breaks something that used to work. And they give fast feedback: a failing test points at the problem seconds after you made it, not weeks later in production.

def apply_discount(price, percent):
    return price - price * percent / 100

def test_apply_discount_takes_percent_off():
    assert apply_discount(200, 25) == 150

# run with:  pytest -q

That is the whole idea. The test is a worked example with the answer written down, and the computer re-checks it every time you ask.

§2The Cost of Finding a Bug Late

A bug costs more the later it is found. On the line you just typed, it costs seconds. In code review, it costs a round trip. In QA, a ticket and a context switch. In production, it can cost customer trust, a hotfix, and an incident review.

minute 0    test fails on your machine      -> fix the line you just wrote
day 2       reviewer spots it               -> re-open the branch, re-test
week 3      QA finds it                     -> find which of 40 commits did it
month 2     a customer finds it             -> hotfix, support tickets, apology

Tests are a way of moving discovery to the left, toward the cheap end. The goal is not a number of tests, it is shortening the distance between making a mistake and learning about it.

§3What Tests Cannot Do

A passing test shows that one case works. It cannot show that every case works. Tests prove the presence of bugs, never their absence, so a green suite means "no known problems," not "no problems."

That is why you add a test whenever you find a bug. The new test fails first, you fix the code, and from then on that exact bug cannot come back unnoticed.

def test_discount_of_zero_percent_changes_nothing():   # added after a bug report
    assert apply_discount(200, 0) == 200
The key insight Tests are what make change safe. Code with good tests can be improved, renamed, and restructured without fear; code without them gets frozen because nobody dares to touch it.

§4Common Mistakes

MistakeWhat HappensFix
Testing only the happy pathBugs live at the edges, so the suite passes while real inputs failAdd cases for empty, zero, negative, and invalid input
Running tests only before a releaseA failure appears weeks after the change that caused itRun tests on every save or commit, and in CI on every push
Treating green as proof of correctnessGaps go unnoticed and overconfidence growsRead green as 'no known failures' and add a test for every bug you find
Practice
  1. Write apply_discount and a test for it, then run it. Change - to + in the function and watch the test fail.
  2. Think of a bug you shipped or found late. At which earlier point could a test have caught it?
  3. Add a test for a 100% discount and for a negative price. Decide what each should do.
Key takeaways
  • Tests give confidence, catch regressions, and shorten the time between a mistake and learning about it.
  • A passing suite means no known failures, not no failures.
  • Every bug you fix should leave behind a test that would have caught it.
