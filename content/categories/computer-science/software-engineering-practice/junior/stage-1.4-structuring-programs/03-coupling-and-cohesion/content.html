Coupling & Cohesion

Almost every piece of design advice comes down to two ideas: things that belong together should be together, and things that don't should barely know each other.

§1Cohesion: Belongs Together

Cohesion measures how closely the parts of one module relate to each other. A highly cohesive class has one clear purpose and everything in it serves that purpose. A low-cohesion class is a grab bag.

# low cohesion: unrelated jobs in one place
class Utils:
    def format_date(self, d): ...
    def send_email(self, msg): ...
    def calculate_tax(self, x): ...

# high cohesion: each class has a single purpose
class DateFormatter: ...
class Mailer: ...
class TaxCalculator: ...

§2Coupling: How Much They Know

Coupling measures how much one module depends on another. Tight coupling means a change in one forces changes in the other. Loose coupling means modules talk through small, stable interfaces and can change independently.

# tightly coupled: reaches into another object's internals
total = order.customer.account.discount_policy.rate * order.subtotal

# loosely coupled: asks, doesn't dig
total = order.total_after_discount()

The second version also follows a useful guideline: talk to your direct collaborators and don't reach through them. If Order changes how it stores discounts, only Order has to change.

§3Seeing It in a Dependency Diagram

Draw boxes for modules and arrows for "depends on." Good designs have few arrows, pointing one way, and clusters of related things. Warning signs are arrows going both directions (a cycle), one box with arrows to everything, or one box everything points at and nobody dares to change.

good:                      bad:
  UI -> Orders -> Storage      UI <-> Orders <-> Storage
                                  ^               |
                                  +---- Reports --+   (cycle)

High cohesion and low coupling go together: when each module has one purpose, it needs little from the others.

The key insight When a small change forces edits in many places, coupling is too high. When you can't say what a module is for, cohesion is too low.

§4Common Mistakes

MistakeWhat HappensFix
A 'Utils' or 'Helpers' dumping groundUnrelated code lives together; nobody knows where to lookGroup by purpose and give each module a clear name
Reaching through objects with long chainsA change in a distant class breaks code hereAsk the nearest object to do it, and add a method if needed
Circular dependencies between modulesThey can't be understood, tested, or changed aloneBreak the cycle by moving shared code or inverting a dependency
Practice
  1. Draw the dependency arrows between five modules in your project. Find one cycle or hub.
  2. Rewrite one long call chain as a single method on the nearest object.
  3. Split a low-cohesion class into two focused ones.
Key takeaways
  • Cohesion: things in a module belong together.
  • Coupling: how much modules depend on each other; keep it low.
  • Few one-directional arrows between focused modules is the target.
