The SOLID Principles as Rules of Thumb

SOLID is a set of five guidelines for classes and modules. They're rules of thumb, useful when you understand the problem each one prevents.

§1The Five Principles

PrincipleIn plain wordsWarning sign it prevents
Single ResponsibilityA class has one reason to changeA class that edits whenever billing, email, or storage changes
Open/ClosedAdd behavior by adding code, not editing working codeA growing if/elif chain edited for every new case
Liskov SubstitutionA subclass must work anywhere its parent doesSubclasses that throw or ignore parent behavior
Interface SegregationSmall interfaces, not one fat oneClasses forced to implement methods they don't use
Dependency InversionDepend on abstractions, not concrete classesHigh-level logic hard-wired to a specific database

§2Single Responsibility and Open/Closed in Code

A class with one reason to change is easier to understand and test. And when new cases arrive, you want to add code instead of rewriting a conditional.

# violates open/closed: every new shape edits this function
def area(shape):
    if shape.kind == "circle":    return 3.14159 * shape.r ** 2
    if shape.kind == "square":    return shape.side ** 2
    # add a triangle -> edit here again

# open for extension: add a class, change nothing else
class Circle:
    def area(self): return 3.14159 * self.r ** 2
class Square:
    def area(self): return self.side ** 2
def area(shape): return shape.area()

§3Dependency Inversion in Code

High-level logic shouldn't know which database or mail service it uses. It depends on an abstraction and the concrete choice is handed in from outside.

# hard-wired: can't test without a real database
class SignupService:
    def __init__(self): self.db = PostgresDatabase()

# inverted: depends on a small interface, passed in
class SignupService:
    def __init__(self, users):           # users: anything with .add(user)
        self.users = users

SignupService(PostgresUsers())           # production
SignupService(InMemoryUsers())           # tests

Treat SOLID as questions to ask when code feels hard to change, not boxes to tick. Applying all five everywhere, in small programs, creates the over-engineering it was meant to prevent.

The key insight Each principle names a specific kind of pain. Reach for one when you feel that pain, not before.

§4Common Mistakes

MistakeWhat HappensFix
Splitting every class into tiny pieces up frontA maze of classes for a simple problemSplit when a second reason to change actually appears
Interfaces with a single implementation, everywhereCeremony with no benefitIntroduce an abstraction at real seams like I/O and external services
Subclasses that break the parent's promisesCallers get surprises at runtimeCheck substitution; if it fails, use composition
Practice
  1. Find a class with more than one reason to change and split it.
  2. Replace an if/elif chain on a type field with classes that each know their own behavior.
  3. Make one class receive its database or mailer through its constructor.
Key takeaways
  • SOLID is five rules of thumb, each aimed at a particular pain.
  • Add code instead of editing code where cases keep growing.
  • Depend on small abstractions at the edges of your program, and pass them in.
