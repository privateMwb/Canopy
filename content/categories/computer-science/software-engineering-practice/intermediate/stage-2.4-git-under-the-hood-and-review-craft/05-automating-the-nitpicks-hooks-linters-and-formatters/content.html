Automating the Nitpicks: Hooks, Linters & Formatters

Machines are better than people at checking formatting and common mistakes. Let hooks, linters, and formatters do the nitpicking so reviews can focus on design.

§1Formatters End Style Debates

An auto-formatter rewrites code into one standard style. Tabs versus spaces, brace placement, and line length stop being review topics, because nobody chooses; the tool does. Pick a formatter with few options (Black, Prettier, gofmt, clang-format), configure it once, and accept its output.

black .                    # Python
prettier --write .         # JS/TS/CSS
clang-format -i src/*.cpp  # C/C++

Formatting-only changes should go in their own commit, so git blame stays useful (add that commit to .git-blame-ignore-revs).

§2Linters Catch Mistakes

A linter analyzes code without running it and flags likely bugs and bad habits: unused variables, unreachable code, missing awaits, risky patterns. Static type checkers go further and catch whole classes of errors before any test runs.

ruff check .         # Python lint
eslint .             # JavaScript
mypy src/            # Python types
clang-tidy src/*.cpp # C++ checks

Start with a modest rule set and fix what it flags. Too many noisy rules teach people to ignore the tool.

§3Hooks and CI Working Together

A Git hook runs a script at a point in the workflow, such as before each commit. The pre-commit framework manages hooks from one config file so everyone runs the same checks.

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/psf/black
    rev: 24.8.0
    hooks: [{id: black}]
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.0
    hooks: [{id: ruff}]

pre-commit install      # runs these on every `git commit`

Hooks live on each developer's machine and can be skipped (--no-verify), so they're a convenience, not enforcement. Run the same checks in CI so nothing broken can merge. Hooks give fast feedback; CI is the guarantee.

The key insight Every nitpick a tool can catch is one a human reviewer doesn't have to write, so reviews get shorter and more interesting.

§4Common Mistakes

MistakeWhat HappensFix
Debating style in pull requestsTime wasted and tempers raised on tasteAdopt a formatter and stop discussing it
Relying on local hooks aloneA skipped or missing hook lets bad code inRun the same checks in CI as the real gate
Turning on every lint ruleNoise, so people ignore or silence themStart small; add rules the team agrees prevent real bugs
Practice
  1. Add a formatter and linter to a project and run them across the code in one commit.
  2. Set up pre-commit with two hooks and see it block a bad commit.
  3. Add the same checks to a CI job and make it required for merging.
Key takeaways
  • Formatters remove style debates; linters catch likely bugs.
  • Hooks give fast local feedback and CI gives the guarantee.
  • Automate what machines do well so humans review design.
