Characterization Tests & Legacy Code

Legacy code, as Michael Feathers put it, is code without tests. The way in is to pin down what it does now, then change it safely.

§1Characterization Tests

You can't write a normal test when you don't know what the right answer is. A characterization test records what the code actually does today, right or wrong, so you can tell if a change alters it. You run the code, observe the result, and write that as the expected value.

def test_legacy_invoice_total_characterization():
    # we don't know if 112.5 is "right"; we know it is what happens today
    assert legacy_total(items=SAMPLE_ITEMS, region="EU") == 112.5

# trick: write a test with a wrong expected value, run it, and copy the real
# value from the failure message into the assertion

Cover a range of inputs, including the weird ones. If a test records an obvious bug, note it, but keep the behavior pinned until you've decided to change it deliberately.

§2Finding Seams

Legacy code is often tangled with databases, files, and global state, which makes it hard to put under test. Look for a seam: a place where you can alter behavior without editing the code there. Often the smallest first step is to extract the hard-to-test dependency behind a parameter.

# before: reads a global config and hits the real database
def monthly_report():
    rate = CONFIG["tax_rate"]
    rows = db.query("SELECT ...")
    ...

# first safe step: pass them in, keeping the old call working
def monthly_report(rate=None, rows=None):
    rate = CONFIG["tax_rate"] if rate is None else rate
    rows = db.query("SELECT ...") if rows is None else rows
    ...

Make the minimal change needed to get a test around it. Don't clean while you do it. Cleanliness comes after the net is in place.

§3The Sprout and Wrap Techniques

When you can't get existing code under test, don't edit it in place. Sprout: write new behavior as a new, fully tested function and call it from one line in the old code. Wrap: put a new function around the old one to add behavior before or after.

# sprout: new logic is new, tested code; one line added to the legacy function
def process_order(order):
    ...                                  # 300 untouched legacy lines
    order.discount = loyalty_discount(order)   # new, tested function
    ...

Over time, the new tested islands grow and the untested ocean shrinks.

The key insight You don't need to understand legacy code before testing it; you need to record what it does. Understanding follows once the net is in place.

§4Common Mistakes

MistakeWhat HappensFix
Refactoring legacy code first and testing laterBehavior changes with nothing to catch itPin behavior with characterization tests before touching structure
Trying to rewrite instead of wrappingMonths of work and new bugsSprout and wrap: add tested code around the old
Fixing bugs you find while characterizingBehavior shifts before you've decided to change itNote them, keep the behavior pinned, and fix them deliberately in a separate change
Practice
  1. Pick an untested function. Write three characterization tests from observed output.
  2. Find a hidden dependency in a legacy function and extract it into a parameter.
  3. Add a small feature to legacy code by sprouting a new tested function.
Key takeaways
  • Characterization tests record current behavior, right or wrong.
  • Find seams to get hard-to-test code under test with minimal edits.
  • Sprout and wrap to grow tested code around untested code.
