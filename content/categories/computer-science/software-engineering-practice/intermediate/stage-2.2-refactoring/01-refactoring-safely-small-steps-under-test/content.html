Refactoring Safely: Small Steps Under Test

Refactoring means changing the structure of code without changing what it does. The discipline is in doing it in steps small enough that you always know it still works.

§1What Counts as Refactoring

Refactoring is improving the design of existing code while keeping its behavior exactly the same. Fixing a bug or adding a feature changes behavior, so it isn't refactoring. Mixing them is what makes refactors dangerous: when something breaks you can't tell which kind of change did it.

A useful discipline is two hats. Wear the feature hat or the refactor hat, never both at once, and commit separately.

§2Small Steps Under Test

Safe refactoring needs a safety net, which is a test suite that passes before you begin. Make one tiny change, run the tests, and commit if they're green. If they go red, undo the last step, which is small enough to understand.

# the loop
run tests            # green before you start
make one small change
run tests            # still green?  commit : revert
repeat

git commit -m "Extract subtotal() from checkout"   # one move, one commit

Many small steps beat one big leap. A fifty-step refactor in which each step is green can be paused, reviewed, or stopped halfway at any point, and nothing is ever left broken.

§3When Not to Refactor

  • No tests and no time to add any: write characterization tests first (see lesson 4)
  • Code you won't touch again: working, stable code that nobody changes doesn't need polish
  • Right before a deadline: unrelated cleanup adds risk to a release

A good moment is the boy-scout rule: leave the code a little cleaner than you found it, in the area you are already changing. Small, continuous refactoring beats a postponed 'cleanup sprint' that never happens.

The key insight Behavior stays fixed and structure changes. If a test result changes during a refactor, you have either found a bug or made one.

§4Common Mistakes

MistakeWhat HappensFix
Refactoring with no testsBehavior changes silently and you only find out in productionAdd characterization tests first, then restructure
Mixing refactoring with feature work in one commitReviews are confusing and reverts take features with themRefactor in separate commits or a preparatory pull request
Large rewrites in one goA long red period with no safe point to return toTake steps small enough to keep the tests green at every commit
Practice
  1. Take a function of yours, and refactor it in five commits where the tests pass after each.
  2. Do a refactor-only pull request with no feature changes and see how reviewers react.
  3. Next time a refactor goes red, revert and make the step half the size.
Key takeaways
  • Refactoring changes structure and leaves behavior alone.
  • Work in tiny steps with tests passing after each one.
  • Keep refactoring and feature changes in separate commits.
