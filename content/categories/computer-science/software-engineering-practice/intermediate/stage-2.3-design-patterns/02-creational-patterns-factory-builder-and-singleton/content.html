Creational Patterns: Factory, Builder & Singleton

Creational patterns control how objects get made, so the code that uses an object doesn't need to know exactly how it was built.

§1Factory: Hide the Choice of Class

A factory is a function or method that decides which concrete class to create. Callers ask for what they need and get an object that behaves right, without naming the class.

def make_notifier(channel):
    if channel == "email": return EmailNotifier()
    if channel == "sms":   return SmsNotifier()
    raise ValueError(f"unknown channel: {channel}")

notifier = make_notifier(user.preferred_channel)
notifier.send("Your order shipped")     # caller never names the class

In many languages a plain function is all the factory you need. The benefit is one place to change when a new type is added.

§2Builder: Construct Step by Step

A builder assembles a complex object through named steps, which avoids constructors with a dozen arguments of confusing order.

# unreadable
req = Request("https://api.x.com", "POST", None, {"a": 1}, 30, True, False)

# readable
req = (RequestBuilder("https://api.x.com")
       .method("POST")
       .json({"a": 1})
       .timeout(30)
       .follow_redirects()
       .build())

Where the language has named and default arguments, those often do the job more simply. Reach for a builder when construction has many optional parts or needs validation at the end.

§3Singleton: Handle With Care

A singleton ensures exactly one instance exists and provides a global way to reach it. It looks convenient, and that is the problem: it is hidden global state. Code that calls Config.instance() anywhere has a secret dependency, can't be tested with a different value, and may break when tests share state.

# hidden dependency: how would you test with different settings?
def total(price):
    return price * (1 + Config.instance().tax_rate)

# explicit: create one object at startup and pass it where needed
def total(price, config):
    return price * (1 + config.tax_rate)

The legitimate need, "only one of these exists in the program," is better met by creating one instance at startup and passing it in. Treat singletons as a smell unless you have a strong reason.

The key insight Creational patterns move the decision of what to build out of the code that uses it, and that separation is what makes substitution possible.

§4Common Mistakes

MistakeWhat HappensFix
A giant factory with a branch for every classAnother if chain, now in a different placeRegister types in a map, or let new classes register themselves
A builder for a three-field objectMore code than the problem needsUse constructor arguments with names and defaults
Using a singleton as a convenient globalHidden coupling and tests that interfere with each otherCreate the object once at startup and pass it in
Practice
  1. Write a factory that returns the right exporter (CSV, JSON, XML) for a file extension.
  2. Replace a constructor with eight arguments by a builder or named arguments.
  3. Find a singleton in your code and pass it as a parameter instead.
Key takeaways
  • Factories hide which class is created.
  • Builders make complex construction readable.
  • Singletons are global state in disguise; prefer passing one instance in.
