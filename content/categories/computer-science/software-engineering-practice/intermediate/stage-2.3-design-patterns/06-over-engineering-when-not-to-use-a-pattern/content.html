Over-Engineering: When Not to Use a Pattern

The biggest risk with patterns isn't misusing one, but using one where a few plain lines would have done.

§1Pattern Fever and Speculative Generality

Newcomers who learn patterns tend to see opportunities everywhere. The result is an AbstractFactoryProviderStrategy wrapped around a function that adds two numbers. This is speculative generality: flexibility built for requirements that may never arrive.

# over-engineered
class DiscountStrategyFactory:
    def create(self, kind): return TenPercentDiscountStrategy()
class TenPercentDiscountStrategy(DiscountStrategy):
    def apply(self, price): return price * 0.9

# enough
def apply_discount(price): return price * 0.9

Every pattern adds classes, indirection, and names to learn. That cost is justified only by a problem you actually have.

§2Signs You've Gone Too Far

  • An interface with exactly one implementation and no plan for a second
  • Classes whose names end in Manager, Handler, Helper, or Factory that mostly delegate
  • You can't explain the design without a diagram
  • Tracing one request means opening ten files
  • New teammates ask why a simple thing takes so many steps

§3Simpler Alternatives

Many patterns exist to work around limits in languages like early Java. Check whether yours already provides the idea natively.

PatternOften replaced by
Strategy, CommandPassing a function or lambda
IteratorGenerators, for loops
SingletonA module-level object, or one instance passed in
Template MethodHigher-order functions
BuilderNamed and default arguments

The rule of three applies here as well: wait until the third similar case before you introduce an abstraction. Then refactor toward the pattern with tests in place. A pattern you refactor into is almost always better fitted than one you plan in advance.

The key insight The best design is the simplest one that handles today's real requirements and doesn't block tomorrow's. Add structure when change demands it, not before.

§4Common Mistakes

MistakeWhat HappensFix
Interfaces and factories for things with one implementationIndirection with no benefitStart concrete; extract an interface when a second case appears
Naming classes after patterns (UserFactoryManager)Names describe the form, not the purposeName by what it does in the domain
Designing for requirements that may never comeComplexity paid now for flexibility never usedBuild for what you need; refactor when real change arrives
Practice
  1. Find an interface with only one implementation in a codebase and consider removing it.
  2. Simplify one pattern-heavy piece of code into a function and compare readability.
  3. List three patterns your language makes unnecessary.
Key takeaways
  • Patterns carry a complexity cost that only a real problem justifies.
  • Speculative generality builds flexibility nobody asked for.
  • Prefer native language features, and refactor toward patterns when pressure appears.
