Transactions & ACID Basics

A transaction groups several statements into one all-or-nothing unit, and ACID names the four guarantees that make that dependable.

§1Why You Need Transactions

Transferring $100 between two accounts takes two updates. If the server crashes between them, money has vanished.

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- crash here?  the $100 is gone, never credited to account 2
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

A transaction makes both updates succeed together or not at all.

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;            -- make it permanent
-- or ROLLBACK;    -- undo everything since BEGIN

§2ACID, One Letter at a Time

LetterPropertyMeaning
AAtomicityAll the statements take effect, or none of them do
CConsistencyA transaction moves the database from one valid state to another; constraints always hold
IIsolationConcurrent transactions don't see each other's half-finished work (details in Stage 2.2)
DDurabilityOnce committed, the change survives a crash or power loss

Durability is achieved by writing changes to a write-ahead log on disk before reporting success, and Stage 3.1 explains how that works.

§3Using Transactions from Code

conn = psycopg.connect(DSN)
try:
    with conn.transaction():                     # BEGIN ... COMMIT, or ROLLBACK on exception
        conn.execute("UPDATE accounts SET balance = balance - %s WHERE id = %s", (100, 1))
        conn.execute("UPDATE accounts SET balance = balance + %s WHERE id = %s", (100, 2))
except Exception as e:
    log.error("transfer failed: %s", e)            # nothing was applied

Most drivers start a transaction implicitly and require an explicit commit(); others auto-commit each statement. Learn which mode your driver uses, since a forgotten commit() silently loses your writes.

§4Keep Transactions Short

A transaction holds locks and resources until it finishes. Do the thinking (HTTP calls, user waits, heavy computation) outside the transaction, then open it, apply the writes, and commit quickly.

bad:   BEGIN → read → call payment API (2 s) → write → COMMIT     (locks held for 2 s)
good:  call payment API → BEGIN → write → COMMIT                  (locks held for ms)

Long-running transactions block other writers, bloat storage, and are a common cause of production slowdowns.

The key insight Put statements in the same transaction when they must succeed or fail together: they protect an invariant (like "money isn't created or destroyed"). Don't wrap unrelated work in one, since that only makes locks last longer.

§5Common Mistakes

MistakeWhat HappensFix
Multi-step changes without a transactionA failure in the middle leaves inconsistent dataWrap statements that must succeed together in BEGIN/COMMIT
Forgetting commit() in a driver with implicit transactionsWrites vanish when the connection closesUse the driver's transaction context manager
Calling external services inside a transactionLocks are held across slow, unreliable network callsDo slow work before or after, not during
Swallowing an error and committing anywayPartial results become permanentRoll back on any exception
Practice
  1. Implement the money transfer with two accounts. Force a failure between the two updates (raise an exception) and show that the balances are unchanged after rollback.
  2. Add a CHECK constraint balance >= 0, then try to transfer more than the source holds. Which statement fails, and what happens to the other?
Key takeaways
  • A transaction makes a group of statements atomic: commit applies all, rollback applies none.
  • ACID: atomicity, consistency, isolation, durability.
  • Keep transactions short and free of slow external calls.
