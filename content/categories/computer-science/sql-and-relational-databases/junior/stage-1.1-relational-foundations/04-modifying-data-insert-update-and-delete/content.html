Modifying Data: INSERT, UPDATE & DELETE

INSERT, UPDATE, and DELETE change data, and each is dangerous in proportion to how loosely its WHERE clause is written.

§1INSERT: Adding Rows

Always name the columns you're inserting into, so the statement keeps working if the table later gains a column.

INSERT INTO customers (name, email)
VALUES ('Ada Lovelace', 'ada@example.com');

INSERT INTO customers (name, email) VALUES      -- several rows at once
  ('Alan Turing', 'alan@example.com'),
  ('Grace Hopper', 'grace@example.com');

Columns you omit get their default value, or NULL if none is defined. An auto-incrementing primary key is filled in for you.

§2UPDATE: Changing Rows

UPDATE changes every row that matches its WHERE. If there's no WHERE, that means every row in the table.

UPDATE products
SET price = price * 1.10, updated_at = CURRENT_TIMESTAMP
WHERE category = 'books';

Expressions can refer to the row's current values, so price * 1.10 is computed per row.

§3DELETE: Removing Rows

DELETE FROM orders WHERE placed_at < '2020-01-01';

Again, omit WHERE and the table is emptied. Foreign keys matter here: you can't delete a customer who still has orders unless you've told the database what to do about them.

customer_id INTEGER REFERENCES customers(id) ON DELETE CASCADE   -- delete orders too
customer_id INTEGER REFERENCES customers(id) ON DELETE RESTRICT  -- refuse (the safe default)
customer_id INTEGER REFERENCES customers(id) ON DELETE SET NULL  -- keep orders, clear the link

§4Safe Habits

Before running a destructive statement, preview what it will touch by running the same WHERE as a SELECT. Then wrap it in a transaction so you can undo it (covered fully in Stage 1.4).

SELECT count(*) FROM orders WHERE placed_at < '2020-01-01';   -- how many rows?

BEGIN;
DELETE FROM orders WHERE placed_at < '2020-01-01';
-- check the result, then:  COMMIT;   (or ROLLBACK; to undo)

Many teams also prefer soft deletes: an is_deleted or deleted_at column, so "deleting" is an UPDATE and the data can be recovered.

The key insight A missing WHERE clause is valid SQL, and the database will do exactly what you said. The habit that saves careers: write the WHERE first, run it as a SELECT, and only then change it into an UPDATE or DELETE.

§5Common Mistakes

MistakeWhat HappensFix
UPDATE or DELETE without WHEREEvery row is changed or removedPreview with SELECT, use a transaction, and enable your client's safe-update mode
INSERT without a column listBreaks, or silently misassigns values, when the table changesAlways list the target columns
Deleting a parent row with live childrenForeign key error, or unintended cascading deletesChoose RESTRICT, CASCADE, or SET NULL deliberately
Practice
  1. Insert three products, raise the price of one by 10%, and delete one. Before each change, run the matching SELECT to confirm which rows it will affect.
  2. Set up orders.customer_id with ON DELETE RESTRICT, then try deleting a customer who has orders. Change to CASCADE and repeat. What differs?
Key takeaways
  • INSERT adds rows, UPDATE changes matching rows, DELETE removes matching rows.
  • Omitting WHERE affects the whole table; preview with SELECT first.
  • Foreign keys decide what happens to child rows when a parent is deleted.
