The Relational Model: Tables, Keys & Relationships

Relational databases organize data into tables, identify each row with a primary key, and connect tables by storing one table's key inside another.

§1Tables, Rows, and Columns

A table holds one kind of thing: customers, products, orders. Each row is one instance (one customer) and each column is one attribute with a fixed type (name, email, signup date).

Unlike a spreadsheet, every row in a table has the same columns, and each column has one declared type. That rigidity is a feature: it's what lets the database check and optimize your data.

§2Primary Keys: Identifying a Row

A primary key is a column (or set of columns) whose value is unique and non-null for every row. It's how you refer to exactly one row, forever, even if the person changes their name or email.

CREATE TABLE customers (
  id    INTEGER PRIMARY KEY,   -- unique, never NULL
  name  TEXT NOT NULL,
  email TEXT NOT NULL
);

Prefer a meaningless surrogate key (an auto-incrementing integer or a UUID) over real-world data like an email. Emails change; a customer's id shouldn't.

§3Foreign Keys: Connecting Tables

Instead of copying a customer's name into every order, an order stores the customer's id. That column is a foreign key: a value that must match a primary key in another table.

CREATE TABLE orders (
  id          INTEGER PRIMARY KEY,
  customer_id INTEGER NOT NULL REFERENCES customers(id),
  placed_at   TEXT NOT NULL,
  total       REAL NOT NULL
);

The database now refuses an order for customer_id = 42 if no such customer exists. This is referential integrity: relationships can't point at nothing.

§4Why Split Data Across Tables?

Storing the customer's name once, and referring to it by id, means a name change is a one-row update instead of a hunt through thousands of orders. It also removes the chance that two orders disagree about who a customer is. Designing these splits well is the subject of Stage 1.3.

customers (1) ───────< orders (many)
   id  ◄─────────────  customer_id

This is a one-to-many relationship: one customer, many orders.

The key insight A foreign key is just a column that holds another table's primary key, plus a promise from the database that the target really exists. Every relationship in a relational database is built from this one idea.

§5Common Mistakes

MistakeWhat HappensFix
Using an email or name as the primary keyWhen it changes, every referencing row must change too, or links breakUse a surrogate id; keep the email as a separate unique column
Storing a related row's data instead of its idCopies drift apart and updates miss some of themStore the foreign key and look the data up when needed
Skipping foreign key declarations "because the app checks"Bugs and manual edits create orphan rows the database would have blockedDeclare the FOREIGN KEY; enforce integrity where it can't be bypassed
Practice
  1. Create customers and orders tables as above. Try inserting an order with a customer id that doesn't exist. What error do you get? (In SQLite, first run PRAGMA foreign_keys = ON;.)
  2. Sketch tables for a library: books, members, and loans. Which columns are primary keys and which are foreign keys?
Key takeaways
  • Tables hold one kind of thing; rows are instances; columns are typed attributes.
  • A primary key uniquely identifies a row; prefer meaningless surrogate keys.
  • A foreign key links a row to another table's primary key and the database enforces that link.
