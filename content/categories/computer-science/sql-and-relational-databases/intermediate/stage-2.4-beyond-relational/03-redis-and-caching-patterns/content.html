Redis & Caching Patterns

Redis is an in-memory data store used chiefly as a cache, and good caching comes down to choosing a pattern, setting expiry, and being honest about invalidation.

§1What Redis Is

Redis is an in-memory key-value store with rich data structures: strings, hashes, lists, sets, sorted sets, and more. Everything lives in RAM, so operations take microseconds. It can persist to disk (snapshots or an append-only log) but is mostly used for data you can afford to lose or rebuild.

SET  session:abc123 '{"user_id": 42}' EX 3600      # string, expires in 1 hour
GET  session:abc123
INCR page:home:views                                 # atomic counter
HSET user:42 name "Ada" plan "pro"                   # hash: fields of an object
ZADD leaderboard 1500 "ada" 1320 "alan"              # sorted set
ZREVRANGE leaderboard 0 9 WITHSCORES                 # top 10
EXPIRE key 60                                        # set a time-to-live

§2Cache-Aside (Lazy Loading)

The most common caching pattern: the application checks the cache first, and on a miss reads from the database and fills the cache.

def get_product(pid):
    key = f"product:{pid}"
    cached = redis.get(key)
    if cached:                                 # cache hit
        return json.loads(cached)
    row = db.query("SELECT * FROM products WHERE id = %s", (pid,))   # cache miss
    redis.set(key, json.dumps(row), ex=300)    # store with a 5-minute TTL
    return row

The cache holds only data that has actually been requested, and a Redis outage degrades performance rather than correctness, because the database is still the source of truth.

§3Other Patterns and Uses

  • Write-through: write to the cache and database together, so reads are always warm, but every write pays double.
  • Write-behind: write to the cache and flush to the database later; fast but risks data loss.
  • Rate limiting: INCR a per-user key with a short expiry.
  • Sessions, leaderboards, queues, pub/sub, distributed locks: all common Redis jobs, each with caveats of its own.

§4Invalidation: The Hard Part

"There are only two hard things in computer science: cache invalidation and naming things." When the database changes, cached copies become wrong. Your options:

  1. TTL (time-to-live): let entries expire. Simple; data can be stale up to the TTL.
  2. Delete on write: after updating the database, delete the cache key so the next read refills it.
  3. Versioned keys: include a version in the key (product:7:v12); bumping the version orphans old entries.
db.execute("UPDATE products SET price = %s WHERE id = %s", (new_price, pid))
redis.delete(f"product:{pid}")      # delete AFTER the DB commit, not before

Watch for a cache stampede: a popular key expires and hundreds of requests hit the database at once. Mitigate with jittered TTLs, request coalescing (only one request refills), or refreshing early.

The key insight A cache is a copy, and copies go stale. Decide up front how stale is acceptable for each piece of data, and choose expiry and invalidation to match. A cache you can't explain the freshness of is a bug waiting to happen.

§5Common Mistakes

MistakeWhat HappensFix
Caching with no expiryEntries live forever and drift from the databaseAlways set a TTL, even a long one
Treating Redis as the only copy of important dataA restart or eviction loses itKeep the database as the system of record
Deleting the cache key before the database commitA concurrent read refills the cache with old dataInvalidate after the commit
Identical TTLs on many keysThey all expire together and stampede the databaseAdd random jitter to TTLs
Practice
  1. Add a cache-aside layer to one slow query in a small app, with a 60-second TTL. Measure database hits with and without it under a simple load test.
  2. Implement a per-user rate limiter of 10 requests per minute using INCR and EXPIRE. What happens at the boundary between two windows?
Key takeaways
  • Redis is an in-memory store with rich data structures, most often used for caching.
  • Cache-aside: check the cache, on a miss read the database and fill the cache.
  • Plan expiry and invalidation deliberately; guard against stampedes.
