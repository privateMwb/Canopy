Document Databases & Data Modeling

In a document database you model data around how your application reads it: embed what is read together, reference what is shared or grows without bound.

§1Documents and Collections

A document database stores self-describing, JSON-like documents grouped into collections. Each document has an _id and can hold nested objects and arrays, so one document can contain what would take several relational tables.

// MongoDB shell
db.orders.insertOne({
  _id: 101,
  customer: { id: 1, name: "Ada" },
  placedAt: ISODate("2026-03-01T10:00:00Z"),
  items: [
    { sku: "NB-1", name: "Notebook", qty: 2, unitPrice: 4.50 },
    { sku: "PN-3", name: "Pen",      qty: 1, unitPrice: 1.20 }
  ],
  total: 10.20
})

db.orders.find({ "customer.id": 1, total: { $gt: 5 } }).sort({ placedAt: -1 })

Reading an order is a single lookup with no joins: the whole thing arrives together.

§2Embed or Reference?

The central design decision: put related data inside the document (embedding) or store an id and look it up (referencing).

Embed whenReference when
Data is read together almost alwaysData is shared by many documents (a product used in many orders)
The child belongs to one parentThe related set grows without bound (all comments on a viral post)
The child is bounded in sizeThe child is updated independently and often
You want atomic update of the whole thingYou need to query the child on its own

Note the order above: the order items are embedded (they belong to the order and never change), but the product is referenced by sku for the live catalog, with the name and price copied into the item as a snapshot of the sale, much like a relational unit_price.

§3Design Around Access Patterns

List your application's queries first, then shape documents so each is answered from one document (or one indexed lookup).

  • A blog: embed the author's display name and the last few comments in the post; keep the full comment set in its own collection.
  • An activity feed: precompute each user's feed as documents (denormalization on purpose).

Duplication is normal here, and it moves the cost to writes: if a customer changes their name, you decide whether to update every embedded copy or accept stale snapshots.

db.orders.createIndex({ "customer.id": 1, placedAt: -1 })     // indexes work as in SQL

§4Schema Flexibility, Carefully

Documents in a collection may differ in shape, which makes evolving fields easy: new documents simply include the new field. But your code must then cope with old documents that lack it. Practices that help:

  • Include a schemaVersion field and migrate lazily or in batches.
  • Use the database's schema validation (for example MongoDB's $jsonSchema) to enforce required fields and types.
  • Remember that MongoDB documents have a size limit (16 MB), which unbounded embedded arrays can eventually hit.
The key insight In a relational database you normalize and join at read time. In a document store you pre-join at write time by embedding. Decide by asking: what data does this one screen or API call need, and can I fetch it in one read?

§5Common Mistakes

MistakeWhat HappensFix
Embedding an unbounded list (all comments, all events)Documents grow without limit and every update rewrites a huge documentReference or bucket unbounded children into a separate collection
Modeling documents like normalized tables and joining in codeMany round trips; lost the benefit of the modelEmbed what is read together
Duplicating data with no plan to keep it in syncStale or conflicting copiesDecide per field: snapshot (frozen) or live (update everywhere or reference)
Skipping validation because it's "schemaless"Inconsistent documents that break readersAdd schema validation and a schemaVersion
Practice
  1. Model a blog (posts, authors, comments) in documents. Decide what to embed and what to reference, and write down the queries your design must answer in one read.
  2. Take your relational shop schema and convert the order, order items, and customer into a document design. Which fields are snapshots, and which are references?
Key takeaways
  • Document databases store nested JSON-like documents, which removes many joins.
  • Embed data read together and bounded in size; reference shared or unbounded data.
  • Design from the queries backwards, and plan for how duplicated data stays correct.
