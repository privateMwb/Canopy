Optimistic vs. Pessimistic Concurrency

Pessimistic concurrency locks data before changing it, while optimistic concurrency proceeds freely and checks for conflicts at the end. Which is better depends on how often conflicts really happen.

§1Pessimistic: Lock First

Assume conflicts are likely, so reserve the rows before touching them.

BEGIN;
SELECT stock FROM items WHERE id = 1 FOR UPDATE;      -- other writers wait here
-- application checks stock, decides ...
UPDATE items SET stock = stock - 1 WHERE id = 1;
COMMIT;

Variants help with queues and contention: FOR UPDATE NOWAIT fails immediately if the row is locked, and FOR UPDATE SKIP LOCKED skips locked rows, which makes it ideal for worker queues.

SELECT id FROM jobs WHERE status = 'queued'
ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;           -- each worker gets a different job

§2Optimistic: Check at the End

Assume conflicts are rare. Read without locking, remember the row's version, and make the update conditional on that version being unchanged.

-- items has a version column
SELECT id, stock, version FROM items WHERE id = 1;     -- version = 7

UPDATE items
SET stock = 49, version = version + 1
WHERE id = 1 AND version = 7;          -- succeeds only if nobody changed it

-- rows affected = 0  →  someone else got there first: re-read and retry (or tell the user)

A timestamp column or a hash of the row can serve as the version. ORMs often support this directly ("optimistic locking" or "row versioning" in Hibernate, Rails, Django packages).

§3Atomic Updates Beat Both

Many read-modify-write patterns need neither if you push the logic into a single statement.

-- No race, no explicit lock: the database does read+write atomically
UPDATE items SET stock = stock - 1 WHERE id = 1 AND stock > 0;
-- rows affected = 1 → success; 0 → out of stock

INSERT INTO page_views (page, hits) VALUES ('/home', 1)
ON CONFLICT (page) DO UPDATE SET hits = page_views.hits + 1;     -- upsert (PostgreSQL)

Prefer a single conditional statement whenever the rule fits in a WHERE clause.

§4Choosing

SituationPrefer
Conflicts frequent, or retries expensivePessimistic (FOR UPDATE)
Conflicts rare, long think time (user editing a form)Optimistic (version column)
Simple counter or stock decrementAtomic UPDATE ... SET x = x - 1 WHERE ...
Job queue with many workersFOR UPDATE SKIP LOCKED

Never hold a pessimistic lock across a user's think time. For the web "two people edit the same record" case, optimistic versioning is the right tool.

The key insight Pessimistic locking pays a small cost up front on every operation to avoid conflicts; optimistic pays nothing until a conflict occurs, then retries. If conflicts are rare, optimistic wins; if they're common, pessimistic does.

§5Common Mistakes

MistakeWhat HappensFix
Read, compute in the app, then write unconditionallyLost updates when two requests interleaveUse an atomic update, FOR UPDATE, or a version check
Holding FOR UPDATE across user interactionRows stay locked while a person decidesUse optimistic versioning for human-speed edits
Ignoring the rows-affected countA failed version check goes unnoticed and the update is silently lostCheck that exactly one row changed; retry or report a conflict
Retrying optimistic failures without a limitLivelock under heavy contentionCap retries with backoff, or switch to pessimistic locking
Practice
  1. Add a version column to a table and implement an optimistic update. Simulate two clients editing the same row and show that the second gets a conflict.
  2. Build a tiny job queue table and run three worker scripts that claim jobs with FOR UPDATE SKIP LOCKED. Verify no job is processed twice.
Key takeaways
  • Pessimistic concurrency locks first; optimistic detects conflicts with a version check at write time.
  • Single-statement atomic updates avoid many races entirely.
  • Choose based on conflict frequency and how long the work between read and write takes.
