JSON & Semi-Structured Data in SQL

Modern relational databases can store and query JSON documents, which is a powerful tool for flexible attributes and a trap when it replaces proper columns.

§1JSON Columns

PostgreSQL (JSONB), MySQL (JSON), SQLite, and SQL Server can store JSON in a column and query inside it.

CREATE TABLE events (
  id         BIGSERIAL PRIMARY KEY,
  user_id    INTEGER NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  payload    JSONB NOT NULL
);

INSERT INTO events (user_id, payload)
VALUES (1, '{"type": "purchase", "amount": 42.5, "items": ["pen", "notebook"]}');

In PostgreSQL prefer JSONB over JSON: it's stored in a parsed binary form that's faster to query and indexable. (JSON keeps the original text and re-parses it each time.)

§2Querying Inside JSON

SELECT payload->>'type'                  AS type,       -- ->> returns text
       (payload->>'amount')::numeric     AS amount      -- cast to a real type
FROM events
WHERE payload->>'type' = 'purchase'
  AND payload @> '{"items": ["pen"]}';                  -- @> : "contains" (JSONB)

SELECT payload->'items'->>0 AS first_item FROM events;  -- -> returns JSON; index into arrays

-> returns JSON, ->> returns text, and #>> follows a path. MySQL's equivalents are JSON_EXTRACT and the -> / ->> operators; SQLite has json_extract.

§3Indexing JSON

-- Index one frequently-queried field
CREATE INDEX idx_events_type ON events ((payload->>'type'));

-- GIN index: supports containment (@>), key-existence (?) over the whole document
CREATE INDEX idx_events_payload ON events USING GIN (payload);

Without an index, every query on a JSON field scans and parses the documents. Another useful feature: generated columns can promote a JSON field to a real column that is indexed and typed automatically.

§4When JSON Is the Right Choice, and When It Isn't

Good uses:

  • Genuinely variable attributes (product specs that differ per category).
  • Storing a third-party payload exactly as received (webhooks, API responses).
  • Sparse, optional metadata and user preferences.

Poor uses:

  • Core fields you filter, join, and constrain on every day (should be real columns).
  • Relationships between entities (no foreign keys inside JSON).
  • Data that needs NOT NULL, uniqueness, or type enforcement.

A pragmatic pattern: real columns for what you know and query, JSON for the long tail. Promote a JSON field to a column the moment it becomes important.

The key insight JSON columns give you schema flexibility, but you give up the database's enforcement: types, constraints, and foreign keys don't reach inside the document. Use it where flexibility is worth that price.

§5Common Mistakes

MistakeWhat HappensFix
Putting everything in one JSONB columnA schemaless table with no constraints and slow filtersModel known fields as columns; keep JSON for variable attributes
Using JSON instead of JSONB in PostgreSQLSlower queries and no good indexingUse JSONB
Filtering on a JSON field without an indexFull scan parsing every documentAdd an expression or GIN index, or a generated column
Relying on application code to validate JSON shapeBad documents slip in via other writersAdd CHECK constraints or validate against a JSON schema at write time
Practice
  1. Create an events table with a JSONB payload, insert a few shapes of event, and write queries for events of one type and events whose items contain 'pen'. Add an index and compare plans.
  2. Take a product table with a JSON attributes column and decide which three attributes deserve to become real columns. Justify each.
Key takeaways
  • JSON columns store flexible documents and can be queried and indexed.
  • In PostgreSQL use JSONB; index the fields you query.
  • Use real columns for core, constrained data; JSON for the variable long tail.
