Partitioning & Sharding

Partitioning splits a large dataset into smaller pieces, and sharding spreads those pieces across machines. It's the way to scale writes and storage beyond a single server, at a high cost in complexity.

§1Partitioning vs. Sharding

  • Partitioning splits a big table into smaller physical pieces, typically within one database server, for manageability and pruning (queries touch only the relevant partition).
  • Sharding splits data across multiple servers, each holding a subset (a shard) and each handling only its share of the load.
-- PostgreSQL declarative partitioning: one table, many time-based pieces
CREATE TABLE events (id BIGINT, created_at TIMESTAMPTZ NOT NULL, payload JSONB)
PARTITION BY RANGE (created_at);
CREATE TABLE events_2026_10 PARTITION OF events
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

Time-based partitions are especially useful because old data can be dropped instantly (DROP TABLE events_2024_01) instead of running a huge DELETE.

§2Choosing a Shard Key

Each row is assigned to a shard by its shard key. The choice is the most consequential decision in a sharded system.

A good shard key has high cardinality (many distinct values), spreads writes evenly, and matches your most common queries so each touches one shard. For a multi-tenant app, tenant_id often fits; for a social network, user_id.

§3What Sharding Breaks

  • Cross-shard queries: a join or aggregate across shards must be assembled by a coordinator (scatter-gather), which is slower and more complex.
  • Cross-shard transactions: atomicity across machines needs distributed protocols (Lesson 4).
  • Global uniqueness and foreign keys: can't be enforced by a single shard's database.
  • Hotspots: one celebrity user or giant tenant overloads its shard; choose keys and splitting strategies with skew in mind.
  • Rebalancing: adding shards means moving data, and live migration is delicate.
  • Operations: schema changes, backups, and monitoring multiply by the number of shards.

§4Ways to Shard, and When Not To

Options, roughly from least to most effort:

  1. Don't shard yet. Scale up the machine, add read replicas, add indexes and caching, archive old data, partition on one server. This takes most systems far.
  2. Application-level sharding: your code routes each request to the right database. Flexible but laborious.
  3. A sharding middleware or extension (Vitess for MySQL, Citus for PostgreSQL).
  4. A natively distributed database (CockroachDB, YugabyteDB, Spanner, Cassandra, DynamoDB) that shards and rebalances automatically.
shard = hash(tenant_id) % 16          # application routing (simple, hard to change later)
-- Better: hash into many logical shards (say 1024), then map logical → physical servers,
-- so you can move logical shards between servers without re-hashing every key.
The key insight Sharding scales writes and storage, but it removes the single-node conveniences: joins, transactions, and global constraints. Postpone it until measurements demand it, and when you do it, choose the shard key from your query patterns.

§5Common Mistakes

MistakeWhat HappensFix
Sharding too earlyYears of added complexity for a problem a bigger server or replicas would have solvedExhaust vertical scaling, replicas, and caching first
Choosing a shard key that creates hotspots (timestamp, low-cardinality status)One shard takes all the trafficPick a high-cardinality key with even distribution
Hash-mod-N with a fixed N and direct serversAdding a server reshuffles almost every keyUse many logical shards or consistent hashing
Designing queries that need every shardLatency is set by the slowest shard; load multipliesAlign the shard key with the dominant queries; denormalize if needed
Practice
  1. Create a time-partitioned events table, insert data across three months, and use EXPLAIN to show a query touching only one partition. Then drop the oldest partition.
  2. For an e-commerce system, argue for a shard key (customer_id, order_id, or region) and list which common queries become single-shard and which become scatter-gather.
Key takeaways
  • Partitioning splits a table within a server; sharding spreads data across servers.
  • The shard key determines load balance, query efficiency, and future flexibility.
  • Sharding breaks joins, cross-shard transactions, and global constraints; delay it as long as you sensibly can.
