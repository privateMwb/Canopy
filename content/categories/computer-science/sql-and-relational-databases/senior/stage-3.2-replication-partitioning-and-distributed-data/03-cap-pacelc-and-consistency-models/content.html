CAP, PACELC & Consistency Models

CAP and PACELC describe what a distributed database must give up under failure and even in normal operation, and consistency models name the different promises a system can make about what readers see.

§1CAP: What Happens When the Network Splits

A network partition is a failure where machines can't talk to each other. The CAP theorem says that when a partition happens, a distributed data store must choose between:

  • Consistency (C): every read sees the most recent write (specifically linearizability), or an error.
  • Availability (A): every request to a working node gets a non-error response, even if it may be stale.

Partitions will happen, so the real choice is CP (refuse some requests to stay correct) or AP (keep answering and reconcile later). A single-node database isn't "CA" in any useful sense; it simply isn't distributed.

Partition splits replicas into {A, B} and {C}
  CP system:  the minority side {C} stops serving (or errors); majority continues, data stays consistent
  AP system:  both sides keep accepting writes; later they must merge conflicting versions

§2PACELC: The Everyday Trade-Off

CAP only describes behavior during a partition, but systems spend nearly all their time without one. PACELC adds: if there's a Partition, choose A or C; Else (normal operation), choose Latency or Consistency.

Why? Strong consistency requires coordination between replicas, which costs round trips. Answering from the nearest replica is fast but may be stale.

Many databases let you choose per query, such as Cassandra's quorum settings and DynamoDB's strongly consistent reads.

§3The Consistency Spectrum

"Consistent" is overloaded; precise names help.

  • Linearizability (strong consistency): the system behaves as if there's one copy and every operation takes effect instantly at some point between its start and end. Once a write completes, all later reads see it.
  • Sequential consistency: all clients see operations in the same order, but not necessarily real-time order.
  • Causal consistency: if one operation could have influenced another (you read a post, then reply), everyone sees them in that order; unrelated operations may be seen in different orders.
  • Read-your-writes / monotonic reads: session guarantees that make a weakly consistent system feel sane to one user.
  • Eventual consistency: if writes stop, all replicas eventually converge. It promises nothing about what you read right now.

Stronger models are easier to program against and more expensive to provide.

§4Quorums and Conflict Resolution

Leaderless systems (Dynamo-style) write to N replicas, require W acknowledgments for a write, and ask R replicas for a read. If R + W > N, read and write sets overlap, so a read sees at least one up-to-date copy.

N = 3, W = 2, R = 2   →  R + W = 4 > 3   (strong-ish: every read overlaps the last write)
N = 3, W = 1, R = 1   →  fast, but reads can miss the latest write

When replicas accept concurrent writes, conflicts must be resolved: last-write-wins (simple, but silently discards data and depends on clocks), vector clocks that detect concurrency and keep both versions for the app to merge, or CRDTs (data types such as counters and sets that merge automatically). Choose consciously; last-write-wins is the default in many systems and loses updates.

The key insight "Eventually consistent" is a promise about the far future, not about what the next read returns. If an operation's correctness depends on seeing the latest data (a balance check, a seat booking), you need a stronger guarantee for that operation, whatever the rest of the system uses.

Practice
  1. For each of these, name the minimum consistency you'd accept and why: an account balance check, a social-media like count, a seat reservation, a user's profile edit shown on their next page load.
  2. With N = 5 replicas, list valid (W, R) choices that give overlapping quorums, and describe the availability each tolerates when two replicas are down.
Key takeaways
  • During a partition a system must choose consistency or availability; otherwise it trades latency against consistency (PACELC).
  • Consistency is a spectrum: linearizable, causal, session guarantees, and eventual.
  • Quorums (R + W > N) and explicit conflict resolution make weaker consistency workable.
