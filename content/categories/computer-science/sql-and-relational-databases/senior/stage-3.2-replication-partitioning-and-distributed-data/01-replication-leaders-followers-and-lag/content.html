Replication: Leaders, Followers & Lag

Replication keeps copies of the data on several machines for availability and read capacity, and every replication scheme is a negotiation between speed, safety, and how stale a copy may be.

§1Why Replicate

One server is a single point of failure and a ceiling on read throughput. Replication addresses three needs:

  • Availability: if the primary dies, another copy takes over.
  • Read scaling: spread read queries across replicas.
  • Locality and isolation: keep a copy near distant users, or run heavy analytics on a replica without touching production.

Replication is not a backup: a mistaken DELETE replicates instantly to every copy (Stage 3.3).

§2Leader-Follower Replication

The most common design: one leader (primary) accepts all writes and ships its change stream to followers (replicas), which apply them in the same order.

clients (writes) ──► LEADER ──── WAL / binlog stream ────┬──► FOLLOWER 1
                                                         └──► FOLLOWER 2
clients (reads)  ────────────────────────────────────────►   (either follower, or the leader)

PostgreSQL ships WAL records (physical streaming replication) or decoded row changes (logical replication, which can replicate selected tables or across versions). MySQL ships the binlog. The followers are usually read-only.

§3Synchronous vs. Asynchronous

ModeCommit completes when...Effect
AsynchronousThe leader has written it locallyFastest; if the leader dies, the latest commits may not have reached any follower (data loss)
SynchronousAt least one follower confirms it tooNo acknowledged commit is lost; but a slow or dead follower stalls writes
Semi-synchronous / quorumA configured number of followers confirmA balance; tolerates some follower failures
-- PostgreSQL: wait for one named standby to confirm each commit
synchronous_standby_names = 'FIRST 1 (replica_a, replica_b)'

Most deployments run asynchronously with fast failover accepting a small possible loss, or use quorum-synchronous replication where losing committed data is unacceptable.

§4Replication Lag and Its Surprises

With asynchronous replication, followers are slightly behind: milliseconds normally, minutes during a heavy write burst or network trouble. Reading from a follower can therefore show stale data, and users notice in specific ways:

  • Read-your-writes violation: a user posts a comment, the page reloads from a lagging replica, and the comment is missing. Fix: route a user's reads to the leader for a short time after they write, or track the LSN they last wrote and wait for a replica to reach it.
  • Monotonic-read violation: refreshing the page shows newer, then older data as requests hit different replicas. Fix: pin a user's session to one replica.
-- PostgreSQL: how far behind is each replica?
SELECT client_addr, state, replay_lag, pg_wal_lsn_diff(sent_lsn, replay_lsn) AS bytes_behind
FROM pg_stat_replication;

§5Failover

When the leader fails, a follower must be promoted. Doing it well is hard:

  1. Detect failure reliably, without false alarms (a slow leader isn't necessarily dead).
  2. Choose the most up-to-date follower.
  3. Reconfigure clients and other followers to use the new leader.
  4. Prevent split brain: ensure the old leader, if it comes back, can't accept writes alongside the new one (called fencing).

With asynchronous replication, writes the old leader accepted but never shipped are lost or conflict. Use proven tooling (Patroni, Orchestrator, managed cloud failover) rather than scripting this yourself, and rehearse it regularly.

The key insight Asynchronous replication gives you speed and availability but allows data loss and stale reads; synchronous replication gives you durability but makes writes depend on more machines. Know which you chose, and design the application around it.

§6Common Mistakes

MistakeWhat HappensFix
Treating replicas as backupsA bad DELETE or DROP is replicated within secondsKeep separate backups with point-in-time recovery
Reading your own writes from an async replicaUsers see their changes vanishRoute recent writers to the leader or wait for the replica to catch up
Automatic failover without fencingSplit brain: two leaders accept conflicting writesUse fencing/STONITH and a proper consensus-based tool
Never testing failoverIt fails the first time it's really neededRun regular failover drills and measure recovery time
Practice
  1. Set up a PostgreSQL primary and one streaming replica (Docker works). Write to the primary, confirm it appears on the replica, then pause the replica and watch lag build.
  2. Design the read-routing rule for a social app so that a user always sees their own new post immediately but other users' feeds can lag by a few seconds.
Key takeaways
  • Leader-follower replication ships the leader's change stream to followers for availability and read scaling.
  • Async replication risks lost commits and stale reads; sync replication trades write latency for durability.
  • Failover needs reliable detection, the right candidate, and fencing to avoid split brain.
