Diagnosing a Slow or Failing Production Database

Diagnosing a struggling production database is a method, not a hunch: establish what changed, find where time is going, and work from the symptoms inward to the cause.

§1Start with Symptoms and Scope

Before touching anything, answer: what exactly is wrong, since when, and how widely?

  • Is it all queries or specific ones? All users or some?
  • Latency, errors, or both? Did it start suddenly (a deploy, a config change, a traffic spike, a plan flip) or gradually (growth, bloat)?
  • What changed? Check deploys, migrations, feature flags, batch jobs, certificate or credential rotations, and cloud events.

A timeline of changes lined up against the metric graphs solves a surprising share of incidents.

§2A Layered Checklist

Work from the outside in, ruling out one layer at a time.

  1. Is the database reachable and healthy? Connections accepted? Errors? Failover happened? Disk full? Replicas lagging?
  2. Is it saturated? CPU, memory pressure (swapping), disk I/O wait, network. Saturation means everything is slow.
  3. Connections: are we at the limit, or is the pool exhausted with requests waiting?
  4. Locks and waiting: queries blocked, an idle in transaction session holding locks, a deadlock storm.
  5. The queries: which statements dominate total time? Did a plan change? Is a new query pattern in the mix?
  6. Data and storage: table/index bloat, missing or stale statistics, a huge table that crossed a threshold.
  7. The application: N+1 patterns, retry storms, a changed access pattern, a runaway job.
-- 1. What is running right now, and for how long?
SELECT pid, state, wait_event_type, wait_event, now() - query_start AS runtime, left(query, 70)
FROM pg_stat_activity WHERE state <> 'idle' ORDER BY runtime DESC LIMIT 15;

-- 2. Who is blocked, and by whom?
SELECT pid, pg_blocking_pids(pid) AS blocked_by, left(query, 60)
FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- 3. Which queries cost the most in total?   (pg_stat_statements)

§4Acting Safely and Learning from It

  • Stabilize first, diagnose second: if a runaway query is hurting everyone, cancel it (pg_cancel_backend) and take the time to understand it afterwards. Prefer cancelling the query over killing the connection.
  • Change one thing at a time, and note what you changed and when.
  • Capture evidence (plans, stats, activity snapshots) before the system returns to normal, since transient problems vanish.
  • Communicate: a clear status update to stakeholders is part of the job.
  • Write a blameless postmortem: timeline, root cause, why it wasn't caught, and concrete fixes (alerts, tests, guardrails). The goal is that the same failure becomes impossible or loud next time.
The key insight The fastest diagnosis is a disciplined one: scope the problem, check each layer from the outside in, and let evidence (waits, plans, and timelines of change) lead you, not the first theory that sounds right.

§5Common Mistakes

MistakeWhat HappensFix
Restarting the database as the first stepClears evidence, empties the cache, and often doesn't fix the causeCapture state first; restart only with a reason
Changing several things at onceCan't tell what helped or hurtMake one change, observe, then proceed
Jumping to indexes for every slowdownWasted effort when the problem is locks, connections, or a plan flipCheck waits and saturation before tuning queries
No postmortem or follow-upThe same incident returnsRecord root cause and add monitoring or guardrails
Practice
  1. Using a test database, create each of these problems: a long open transaction blocking an update, a missing index causing a slow query, and exhausted connections. For each, write down the exact signs you'd see in the diagnostic queries above.
  2. Write a one-page runbook titled "The database is slow" with the first five checks in order, the query for each, and what a bad result looks like.
Key takeaways
  • Scope the problem, then work outside-in: health, saturation, connections, locks, queries, data, application.
  • Learn the signatures of common failures: plan flips, contention, connection exhaustion, bloat, and cold caches.
  • Stabilize first, change one thing at a time, preserve evidence, and learn through blameless postmortems.
