OLTP vs. OLAP & Columnar Warehouses

Transactional databases and analytical databases answer different kinds of questions, and storing data by column instead of by row is the main reason analytics systems can scan billions of rows quickly.

§1Two Workloads, Two Designs

OLTP (online transaction processing)OLAP (online analytical processing)
Typical query"Fetch order 123"; "update this user's address""Revenue by region by month for 3 years"
Rows touchedA fewMillions to billions
Columns touchedMost of the rowA few columns of a wide table
ConcurrencyThousands of small transactionsFew, large, long-running queries
FreshnessCurrent dataOften minutes to hours old
Storage layoutRow-orientedColumn-oriented
ExamplesPostgreSQL, MySQLBigQuery, Snowflake, Redshift, ClickHouse, DuckDB

Running heavy analytics on your production OLTP database slows the application and still isn't optimal for the analytics, which is why the workloads are usually separated.

§2Row vs. Column Storage

Row store: each row's values are stored together
  [id=1, Ada, NZ, 45.00] [id=2, Alan, UK, 12.50] [id=3, Grace, US, 99.99] ...
  great for: read or write one whole row

Column store: each column's values are stored together
  id:      [1, 2, 3, ...]
  name:    [Ada, Alan, Grace, ...]
  country: [NZ, UK, US, ...]
  total:   [45.00, 12.50, 99.99, ...]
  great for: SUM(total) GROUP BY country  →  read only two columns, skip the rest

Column stores win for analytics because:

  • Less I/O: a query over 3 of 50 columns reads about 6% of the data.
  • Compression: values in one column are similar, so encodings like dictionary, run-length, and delta compress 5–10× or more.
  • Vectorized execution: process thousands of values per CPU instruction batch, using SIMD.
  • Skipping: per-block min/max metadata lets the engine skip whole blocks that can't match a filter.

Their weakness is single-row writes and point lookups, which have to touch every column file.

§3From OLTP to the Warehouse: ETL and ELT

Data moves from operational systems to the warehouse through a pipeline.

  • ETL: Extract from sources, Transform (clean, reshape) in a separate engine, Load the result.
  • ELT: Extract and Load raw data first, then Transform inside the warehouse with SQL (tools like dbt). Cheap storage and powerful warehouses made this the modern default.

Typical layers: raw (as received) → staging (cleaned, typed) → marts (business-ready tables). Analytical tables are often modeled as a star schema: a central fact table of events (orders, clicks) with foreign keys to dimension tables (customer, product, date), which means deliberately denormalized and optimized for aggregation.

            dim_date
               │
dim_customer ─ fact_orders ─ dim_product       ← star schema

§4Lakes, Lakehouses, and Choosing

  • A data lake stores raw files (Parquet, ORC, JSON) in cheap object storage, flexible and cheap, but with weak guarantees.
  • A lakehouse adds table formats (Apache Iceberg, Delta Lake, Hudi) giving the lake transactions, schema evolution, and time travel, queried by engines such as Spark, Trino, or Snowflake.
  • HTAP systems aim to serve both workloads in one engine; useful in some cases but a compromise in each.

For modest data sizes, you may not need any of this: a read replica or a PostgreSQL extension can handle early analytics, and DuckDB can query Parquet files locally at impressive speed. Introduce a warehouse when analytics load, data volume, or the need to combine many sources justifies it.

The key insight Row stores are built to find and change one record fast; column stores are built to scan a few columns across enormous numbers of rows. Use the right engine for each workload, and move data between them deliberately.

§5Common Mistakes

MistakeWhat HappensFix
Running heavy reports on the production primaryApplication latency spikes during large queriesUse a replica, or better, a separate analytical store
Expecting a columnar warehouse to handle high-rate single-row updatesPoor performance and costBatch loads and append-oriented writes; keep OLTP in an OLTP database
Building a warehouse before there's an analytics needCost and maintenance with no payoffStart with replicas or DuckDB; grow into a warehouse
Analytical tables with no modeling (dumping raw tables)Slow, confusing queries and inconsistent metricsBuild clean fact and dimension tables with agreed definitions
Practice
  1. Export an orders table to Parquet and run the same aggregate query in DuckDB and in PostgreSQL. Compare time and the files' sizes. Explain the differences in terms of row vs. column storage.
  2. Design a star schema for an online store: name the fact table, its grain (what one row means), and at least four dimensions.
Key takeaways
  • OLTP and OLAP have opposite needs, so they usually run on different systems.
  • Column stores read only the needed columns, compress well, and scan in vectorized batches.
  • Data flows to analytics through ETL/ELT into modeled fact and dimension tables.
