Change Data Capture, Event Sourcing & the Outbox Pattern

Keeping several systems in sync is easy to get subtly wrong. Change data capture, the transactional outbox, and event sourcing let you do it reliably by treating the database's own changes as the source of events.

§1The Dual-Write Problem

An order service saves an order to its database and also publishes an OrderPlaced event to a message broker for other systems.

db.commit()           # succeeds
broker.publish(evt)   # ← crash or network error here: the event is never sent

Reverse the order and you may publish an event for an order that then fails to save. Two systems can't be updated atomically by ordinary code (there's no shared transaction), so they drift apart. This is the dual-write problem, and the fix is to write to one place atomically and derive the rest from it.

§2Change Data Capture (CDC)

CDC reads the database's own change log (the WAL or binlog) and turns every insert, update, and delete into an event stream, without changing application code or adding load on tables.

PostgreSQL WAL ──► Debezium (logical decoding) ──► Kafka topics ──► search index, cache, warehouse, other services

Uses: feeding a warehouse or search index, invalidating caches, replicating to other databases, and building event-driven integrations. Points to know: events arrive at least once (consumers must tolerate duplicates), ordering is guaranteed per row/key, not globally, and schema changes need coordination with consumers. Initial loads need a snapshot before streaming begins.

§3The Transactional Outbox Pattern

When you need to publish domain events (not raw row changes) reliably, write the event into an outbox table in the same transaction as the business change. A separate relay then publishes outbox rows to the broker.

BEGIN;
INSERT INTO orders (id, customer_id, total) VALUES (101, 1, 45.00);
INSERT INTO outbox (id, aggregate_id, type, payload)
VALUES (gen_random_uuid(), 101, 'OrderPlaced', '{"order_id":101,"total":45.00}');
COMMIT;                  -- both rows commit together, or neither does

-- relay process (or CDC on the outbox table) then:  read unsent rows → publish → mark sent

Because the event and the state change are one atomic commit, you never publish an event for something that didn't happen or lose one that did. Delivery to the broker is still at least once, so make consumers idempotent (deduplicate on the event id).

§4Event Sourcing

Event sourcing goes further: instead of storing current state and overwriting it, store the sequence of events (immutable facts) as the source of truth, and derive current state by replaying them.

events for account 7:
  1  AccountOpened   {owner: "Ada"}
  2  Deposited       {amount: 100}
  3  Withdrew        {amount: 30}
  state = fold(events)  →  balance 70

Benefits: a complete audit trail, the ability to rebuild state or new views from history, and easy "what did we know at time T" answers. Costs: replay needs snapshots for long histories; evolving event schemas over years is hard; queries need separate read models (CQRS), which are eventually consistent; and the learning curve is steep. Use it where history is the product (ledgers, bookings, compliance-heavy domains), not by default.

The key insight You can't atomically update a database and a message broker with two separate calls. Make one write authoritative (the database commit), and derive everything else from it, through the log, an outbox, or the events themselves.

§5Common Mistakes

MistakeWhat HappensFix
Committing to the database and then publishing in application codeLost or phantom events after crashesUse an outbox or CDC so the event is part of the commit
Assuming exactly-once deliveryDuplicates cause double-processingMake consumers idempotent; deduplicate by event id
Treating CDC row changes as stable public eventsInternal schema changes break every consumerPublish deliberate domain events (outbox) as the public contract
Adopting event sourcing for ordinary CRUDHeavy complexity with little benefitReserve it for domains where the history itself matters
Practice
  1. Implement the outbox pattern for an order service: write the order and outbox row in one transaction, then write a relay that publishes unsent rows and marks them sent. Kill it mid-way to confirm no event is lost.
  2. A consumer receives the same OrderPlaced event twice. Describe two ways to make its handling idempotent.
Key takeaways
  • Updating a database and a broker separately risks inconsistency (the dual-write problem).
  • CDC streams the database's change log; the outbox makes domain events part of the same transaction.
  • Expect at-least-once delivery and make consumers idempotent; use event sourcing only where history is core.
