Connection Pooling, Capacity & Monitoring

Connections are a scarce resource, so a pool in front of the database, a handful of well-chosen metrics, and capacity planning keep you ahead of problems instead of reacting to them.

§1Why Pools Matter at Scale

Each PostgreSQL connection is a separate OS process using memory (several MB, more when active), and performance degrades once there are many more active connections than CPU cores. With 50 app servers × 20 connections each, you have 1,000 connections, which is far more than the database can run efficiently, even if most are idle.

app servers (many connections) ──► PgBouncer / ProxySQL / RDS Proxy ──► database (few connections)

A pooler multiplexes many client connections onto a small number of server connections. Pooling modes:

ModeServer connection held forNotes
SessionThe whole client sessionSafest; little multiplexing
TransactionOne transaction at a timeBest multiplexing; session features (prepared statements, SET, advisory locks, temp tables) need care
StatementOne statementRare; breaks multi-statement transactions

Application-side pools (HikariCP, SQLAlchemy's pool) still matter; the external pooler caps the total across all app instances.

§2Sizing a Pool

Counter-intuitively, more connections usually means slower. A database can only do as much parallel work as it has CPU cores and I/O capacity; extra connections just queue and contend. A common starting formula:

pool size ≈ (core_count × 2) + effective_spindle_count        # a starting point, then measure

Often a pool of 10–30 connections serves a database on a modest server better than 500. If requests wait for a connection, first look at why queries are slow before raising the pool size: slow queries hold connections longer, which creates the shortage.

§3Metrics That Matter

Watch saturation and errors before averages.

  • Latency percentiles (p50, p95, p99) for queries, not just the mean, since the tail is what users feel.
  • Throughput: queries or transactions per second.
  • Connections: active vs. idle vs. waiting; pool wait time.
  • Cache hit ratio and I/O wait: are you reading from disk?
  • Replication lag, in time and bytes.
  • Locks and long transactions: blocked queries, idle in transaction sessions, oldest transaction age.
  • Disk: free space, growth rate, WAL volume, table and index bloat.
  • Slow query log and top queries by total time (pg_stat_statements).
-- The single most useful PostgreSQL view for tuning: which queries cost the most in total
SELECT left(query, 60) AS query, calls, round(total_exec_time) AS total_ms,
       round(mean_exec_time::numeric, 2) AS mean_ms
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

§4Capacity Planning and Alerting

Plan from trends: disk growth per week, connection peaks, CPU headroom at the daily peak, and how each grew with traffic. Know your breaking points by load testing with production-like data.

Alert on conditions that need a human, and have a clear action behind each:

  • Disk will be full in under N days (not "disk is 80%").
  • Replication lag over a threshold for several minutes.
  • Connection count near the limit; pool wait times rising.
  • Backup failed or is missing.
  • Long-running transactions beyond a limit.
  • Error rate or p99 latency above the service-level objective.

An alert nobody acts on trains people to ignore alerts. Tune or delete it.

The key insight A database running at high utilization has no room for a traffic spike or a slow query. Watch saturation and tail latency, keep connections few and busy rather than many and idle, and plan capacity from trends.

§5Common Mistakes

MistakeWhat HappensFix
Raising connection limits to fix "too many connections"More contention and memory use; slower overallAdd a pooler and size pools to the database's capacity
Using transaction pooling with session-level features unawareBroken prepared statements, session settings, and advisory locksCheck pooler compatibility; use session mode or adjust the code
Alerting on averagesTail latency problems hide behind a healthy meanAlert on p95/p99 and error rates
No capacity trend dataSurprise outages from a full disk or exhausted connectionsChart growth over time and project when limits are reached
Practice
  1. Install pg_stat_statements and identify the top three queries by total execution time on a database under test load. Decide whether each needs an index, a rewrite, or caching.
  2. Run a load test against a database with a pool size of 10, 50, and 200 connections. Plot throughput and p99 latency. Where does adding connections stop helping?
Key takeaways
  • Use a pooler to multiplex many clients onto few database connections, and size pools to the hardware, not the number of clients.
  • Track tail latency, saturation, replication lag, locks, disk, and top queries by total time.
  • Plan capacity from trends and alert on actionable conditions.
