Database Security: Roles, Row-Level Security & Encryption

Database security is layered: limit who can connect and what each role can do, isolate tenants with row-level security, encrypt data in transit and at rest, and keep an audit trail.

§1Authentication and Least Privilege

Give each application, service, and person their own role, with only the permissions needed. The application should never connect as a superuser or as the table owner.

CREATE ROLE app_rw LOGIN PASSWORD '...';                  -- load from a secrets manager in practice
GRANT CONNECT ON DATABASE shop TO app_rw;
GRANT USAGE ON SCHEMA public TO app_rw;
GRANT SELECT, INSERT, UPDATE ON orders, customers TO app_rw;   -- no DELETE, no DDL

CREATE ROLE analyst_ro LOGIN;
GRANT SELECT ON orders_summary TO analyst_ro;               -- a view that hides sensitive columns

Other basics: separate roles for migrations (which need DDL rights) and runtime; rotate credentials; prefer certificate or cloud-IAM authentication to static passwords; and restrict the network so the database isn't reachable from the public internet (private subnets, firewall rules, pg_hba.conf).

§2Row-Level Security

In multi-tenant systems, a bug in one WHERE clause can leak one customer's data to another. Row-level security (RLS) moves the rule into the database, so every query is filtered automatically.

ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON invoices
  USING (tenant_id = current_setting('app.tenant_id')::int);

-- per request, the application sets the tenant for its session/transaction:
SET LOCAL app.tenant_id = '42';
SELECT * FROM invoices;       -- sees only tenant 42's rows, even with no WHERE clause

RLS is a safety net, not a substitute for correct code: make sure table owners and superusers (who bypass policies by default) aren't used by the app, and remember policies add a small performance cost, so index tenant_id.

§3Encryption

  • In transit: require TLS between application and database (sslmode=verify-full in PostgreSQL clients), so credentials and data can't be read or altered on the network.
  • At rest: disk or volume encryption (the cloud default for managed databases) protects against stolen disks and snapshots. It does not protect against a compromised application or database login, since the database decrypts for any authorized connection.
  • Column-level / application-level encryption for especially sensitive fields (national IDs, health data): the database stores only ciphertext. The trade-off is that you can't search or index it normally.
  • Key management: keep keys in a KMS/HSM, separate from the data, rotated and access-logged.
  • Secrets: no credentials in code or images. Use a secrets manager.

Also consider masking in non-production copies, so developers don't work with real personal data.

§4Auditing and Detection

Know who did what, and be able to prove it.

  • Log connections, disconnections, failed logins, and DDL; use pgAudit (or the equivalent) for statement-level auditing of sensitive tables.
  • Ship logs to a separate, append-only system that a compromised database host can't alter.
  • Alert on anomalies: logins from new locations, spikes in rows read, privilege changes, access to sensitive tables outside business logic.
  • Keep an inventory of what personal data you store and where; compliance rules (GDPR, HIPAA, PCI DSS) often require retention limits, deletion on request, and access records.
  • Patch and upgrade the database regularly; old versions accumulate known vulnerabilities.
The key insight Assume some layer will fail: an application bug, a leaked credential, a misconfigured firewall. Least-privilege roles, row-level isolation, encryption, and auditing each limit what a single failure can expose.

§5Common Mistakes

MistakeWhat HappensFix
The application connects as a superuser or table ownerOne SQL injection or leaked credential means total controlUse a restricted runtime role; keep DDL rights in a separate migration role
Exposing the database port to the internetConstant scanning and brute-force attacksKeep it on a private network behind firewalls or a VPN
Treating disk encryption as full protectionDoesn't stop an authorized-but-abused connectionCombine with least privilege, auditing, and column-level encryption for secrets
Copying production data into dev or test unmaskedPersonal data in weakly protected environmentsMask or synthesize non-production data
Practice
  1. Create read-only and read-write roles for an application, then verify with a test connection that the read-only role cannot modify data and the app role cannot drop tables.
  2. Enable row-level security on a table with a tenant_id, set the tenant per transaction, and write a test proving tenant 1 can never read tenant 2's rows, even with SELECT * FROM invoices.
Key takeaways
  • Apply least privilege with separate roles for runtime, migrations, and analysts; keep the database off the public internet.
  • Row-level security enforces tenant isolation inside the database as a safety net.
  • Encrypt in transit and at rest, manage keys separately, and audit access.
