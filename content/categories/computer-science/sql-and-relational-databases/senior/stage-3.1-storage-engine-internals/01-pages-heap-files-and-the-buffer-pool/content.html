Pages, Heap Files & the Buffer Pool

Databases don't read individual rows from disk; they read fixed-size pages, and a buffer pool in memory decides which pages stay close at hand. Most performance behavior follows from that.

§1Everything Is a Page

Disks and SSDs transfer data in blocks, so a database organizes storage into fixed-size pages (8 KB in PostgreSQL, 16 KB in MySQL InnoDB, 4 KB in SQLite by default). A table is a collection of pages; each page holds many rows. Reading one row means reading its whole page.

Page (8 KB)
┌────────────────────────────────────────────┐
│ header │ item pointers →                   │
│        │ (offset, length) per row          │
│                free space                  │
│                  ← row data grows from end │
│ row 3 │ row 2 │ row 1                      │
└────────────────────────────────────────────┘

The slotted page layout lets rows vary in size: pointers at the front point to row data packed from the back. A row's address is its (page number, slot). PostgreSQL exposes it as ctid, which is what indexes store.

§2Heap Files and Row Layout

A table without an inherent order is a heap file: rows go wherever there's room. Indexes then map keys to row locations. InnoDB instead stores the table as its primary-key B-tree (a clustered index), so rows are physically ordered by primary key and secondary indexes store the primary key rather than a physical address.

DesignProsCons
Heap + separate indexes (PostgreSQL)Simple inserts; any index is equalExtra hop from index to heap; updates create new row versions
Clustered primary key (InnoDB, SQL Server)Range scans on the key read adjacent pages; no hop for key lookupsRandom primary keys (UUIDs) scatter inserts; secondary lookups need two index walks

Very large values (long text, blobs) are moved out of the page into TOAST (PostgreSQL) or overflow pages so rows stay small.

§3The Buffer Pool

Reading from disk takes microseconds to milliseconds; from RAM, nanoseconds. The buffer pool (PostgreSQL calls it shared_buffers) is a region of memory caching recently used pages.

query needs page 812
  → in buffer pool?  yes → use it (a "hit")
                     no  → pick a victim page, evict it (write it first if dirty),
                           read page 812 from disk (a "miss")

Pages modified in memory are dirty; a background writer or checkpoint flushes them to disk later. Eviction uses an LRU-like policy (PostgreSQL uses clock-sweep) with protection so one big table scan doesn't flush the entire cache.

-- PostgreSQL: cache hit ratio per database
SELECT datname, blks_hit::float / NULLIF(blks_hit + blks_read, 0) AS hit_ratio
FROM pg_stat_database;

§4Why This Explains Performance

  • Hot data in RAM is fast; cold data costs I/O. A query is "slow after restart" because the cache is empty.
  • Random I/O is expensive; sequential is cheap, so the planner prefers scans when many pages are needed.
  • Row width matters: narrow rows mean more rows per page, so fewer page reads.
  • Index-only scans win by skipping heap pages.
  • The OS cache also helps: PostgreSQL relies on it as a second layer (double buffering), while some databases bypass it with direct I/O.

Sizing rule of thumb: you want the working set (the data and indexes actively used) to fit in memory.

The key insight The unit of cost in a database is the page, not the row. To speed something up, reduce the number of pages it must touch, or make sure those pages are already in the buffer pool.

§5Common Mistakes

MistakeWhat HappensFix
Evaluating performance on a warm cache onlyProduction cold starts and cache misses look much worseTest both warm and cold; check hit ratios
Wide rows with rarely used large columnsFew rows per page; scans read lots of unneeded bytesMove big, rarely read columns to a separate table or rely on TOAST
Random UUID primary keys in a clustered-index engineInserts scatter across the tree, causing page splits and cache churnUse time-ordered ids (UUIDv7, ULID) or sequential keys
Setting the buffer pool to nearly all RAMThe OS and other processes starve; swapping beginsLeave headroom; follow engine-specific sizing guidance
Practice
  1. In PostgreSQL, run SELECT ctid, * FROM customers LIMIT 5; and SELECT pg_relation_size('customers') / 8192 AS pages;. Compute average rows per page.
  2. Install the pg_buffercache extension (or use InnoDB status) and see which tables occupy the buffer pool after running a big query.
Key takeaways
  • Data is stored and transferred in fixed-size pages, not individual rows.
  • The buffer pool caches pages in memory; hits are fast, misses cost disk I/O, and writes are deferred.
  • Performance work often means touching fewer pages or keeping the working set in memory.
