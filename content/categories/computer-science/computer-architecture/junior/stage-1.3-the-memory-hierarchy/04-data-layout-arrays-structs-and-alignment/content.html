Data Layout: Arrays, Structs & Alignment

How you arrange data in memory determines how many cache lines you touch, and structure padding and layout choices decide whether those lines carry useful bytes.

§1Alignment and Padding

CPUs access values most efficiently when each is aligned: a 4-byte int at an address divisible by 4, an 8-byte double at an address divisible by 8. The compiler inserts padding between struct members to maintain this, so the size of a struct can exceed the sum of its fields.

struct A { char a; int b; char c; };      // a:0  pad:1-3  b:4-7  c:8  pad:9-11  -> sizeof = 12
struct B { int b; char a; char c; };      // b:0-3  a:4  c:5  pad:6-7          -> sizeof = 8

#include <stddef.h>
printf("%zu %zu\n", sizeof(struct A), sizeof(struct B));          // 12 8
printf("%zu\n", offsetof(struct A, b));                           // 4

Ordering members from largest to smallest alignment usually removes the padding. For an array of a million such structs, that is the difference between 12 MB and 8 MB, which also means 50% more cache lines to fetch.

§2Arrays vs. Linked Structures

An array stores elements contiguously, so a scan uses every byte of every cache line fetched, and the hardware prefetcher can run ahead. A linked list scatters nodes across memory and each step depends on the previous load, so every hop is a likely miss, with nothing for the prefetcher to predict.

StructureAccess patternCache behavior
Array of intsSequentialOne miss per 16 elements; prefetch-friendly
Linked listPointer chasingAbout one miss per node; cannot overlap misses
Hash table with chainingRandom bucket then chainOne or more misses per lookup

This is why a vector of values often beats a linked list even for operations that, by big-O analysis, favor the list, such as inserting in the middle: the array's constant factor is so much lower.

§3Fitting Hot Data on Fewer Lines

If you only touch some fields of a large struct in a hot loop, you still pull the whole struct's lines into the cache. Splitting hot fields into a separate, smaller structure can multiply how many items fit per line.

// Each element is 64+ bytes, but the loop uses only score: one cache line per element
struct Player { char name[48]; float score; int id; double extra[4]; };

// Hot/cold split: the loop scans a compact array of 4-byte scores: 16 per cache line
float scores[N];
struct PlayerCold { char name[48]; int id; double extra[4]; } cold[N];

Keep data that is used together close together, and data that is used separately apart. Senior-level lessons return to this as data-oriented design.

The key insight Layout is a performance decision made at design time. Choosing contiguous storage and compact structs costs nothing in code complexity, and often beats any later micro-optimization.

§4Common Mistakes

MistakeWhat HappensFix
Ordering struct members arbitrarilyPadding bloats memory and cache footprintGroup members by size, largest first
Defaulting to linked lists for sequencesPointer chasing makes every step a likely cache missUse arrays or vectors unless you need stable pointers
Scanning large structs for one fieldCache lines are mostly wastedSplit hot and cold fields
Practice
  1. Predict sizeof for a struct of char, double, char, int in that order, then print it and the offsets to check. Reorder it to minimize size.
  2. Compare summing 10 million ints in a std::vector versus a linked list on your machine. What's the ratio?
Key takeaways
  • Compilers pad structs to keep members aligned; ordering members by size reduces waste.
  • Contiguous arrays are prefetch-friendly, while pointer-based structures cause serial misses.
  • Separating hot from cold fields makes each cache line carry more useful data.
