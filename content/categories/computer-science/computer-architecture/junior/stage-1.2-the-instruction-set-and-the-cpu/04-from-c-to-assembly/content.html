From C to Assembly

Seeing what a compiler produces from your C turns performance from folklore into something you can check, and the difference between optimization levels is often dramatic.

§1Looking at Compiler Output

You can ask the compiler for assembly instead of a finished program, or use an interactive viewer such as Compiler Explorer (godbolt.org) to see it side by side with your source.

gcc -S -O1 -masm=intel sum.c -o sum.s    # write assembly instead of an executable
objdump -d -M intel ./a.out | less        # disassemble a built binary

int sum(const int *a, int n) {
    int s = 0;
    for (int i = 0; i < n; i++) s += a[i];
    return s;
}

Typical x86-64 output at -O1 (exact instructions vary by compiler version, and the shape is what matters):

sum:
    test  esi, esi          # is n <= 0 ?
    jle   .Lzero
    mov   rax, rdi          # rax = pointer to a[0]  (first argument is in rdi)
    movsx rsi, esi
    lea   rdx, [rdi+rsi*4]  # rdx = end pointer = a + n
    mov   ecx, 0            # s = 0
.Lloop:
    add   ecx, DWORD PTR [rax]   # s += *p   (load and add in one instruction)
    add   rax, 4                 # p++
    cmp   rax, rdx
    jne   .Lloop
    mov   eax, ecx          # return value goes in eax
    ret
.Lzero:
    mov   eax, 0
    ret

§2What Optimization Changes

Compare -O0 and -O2 on the same function and you'll see:

  • -O0: every variable lives in memory on the stack, and each statement loads and stores it again. Easy to debug, but slow
  • -O1 and above: values stay in registers, the index becomes a moving pointer, and redundant work disappears
  • -O2 and -O3: the loop may be unrolled or vectorized with SIMD instructions, and the compiler may remove code whose result is unused
  • Inlining: small functions are copied into their callers, so the call and return overhead vanishes

Compilers are very good at this, so reading output is mostly for checking that an expected optimization happened, such as whether a hot loop was vectorized, and for understanding performance surprises.

§3The Calling Convention Seen From Outside

On x86-64 Linux (the System V ABI), the first six integer arguments go in rdi, rsi, rdx, rcx, r8, r9 and the return value in rax. On RISC-V they're a0 to a7, with the result in a0. When assembly looks puzzling, find which registers carry the arguments, then follow how each is used.

# Ask GCC what it did with a loop
gcc -O3 -fopt-info-vec-optimized sum.c       # reports which loops were vectorized
gcc -O2 -fopt-info-vec-missed sum.c          # reports why a loop could not be

The same C produces different machine code on different ISAs, because the compiler targets the instruction set. This is why binaries built for x86-64 don't run on ARM without recompiling or emulation.

The key insight Assembly is the ground truth of what runs. When a benchmark surprises you, reading the generated code is often the fastest way to find out why.

§4Common Mistakes

MistakeWhat HappensFix
Benchmarking an -O0 buildResults reflect memory traffic the optimizer would removeMeasure with the optimization level you ship
Writing a microbenchmark whose result is never usedThe compiler deletes the work, and you time an empty loopUse the result, or mark a sink as volatile
Assuming the compiler will vectorize any loopAliasing, dependencies, or branches can block itCheck -fopt-info output, and restructure the loop if needed
Practice
  1. Compile a small function at -O0, -O1, and -O2, and compare the instruction counts and where variables live.
  2. Find a simple loop in your own code on Compiler Explorer and note which instruction does the load and which does the add.
Key takeaways
  • gcc -S and Compiler Explorer show the machine code a compiler generates.
  • Optimization moves values into registers, simplifies addressing, inlines, unrolls, and vectorizes.
  • Calling conventions tell you which registers hold arguments and results.
