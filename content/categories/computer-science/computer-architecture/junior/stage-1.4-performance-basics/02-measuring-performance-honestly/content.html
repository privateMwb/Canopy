Measuring Performance Honestly

Timing code is easy to do badly, and a good measurement accounts for warm-up, noise, and a compiler that may have quietly deleted the work you meant to time.

§1What to Measure

MeasureMeaningWhen to use
Wall-clock (real) timeElapsed time on the clockWhat users experience
CPU (user + sys) timeTime spent running on a CPUCost of computation, ignoring waiting
ThroughputWork per unit timeServers, batch jobs
Latency percentiles (p50, p99)Distribution of response timeInteractive and request-driven systems
time ./prog                  # real, user, sys
perf stat -r 10 ./prog       # run 10 times, report mean and variation
hyperfine './prog' --warmup 3    # a benchmarking tool that handles warm-up and statistics

Wall time larger than CPU time means the program was waiting for I/O, locks, or other processes. CPU time larger than wall time means it ran on several cores at once.

§2Common Measurement Traps

  • Cold start: the first run pays for loading files, filling caches, and page faults. Warm up, then measure
  • Noise: other processes, frequency scaling, and thermal throttling. Run many times, and report the median and spread rather than one number
  • Dead-code elimination: if a benchmark's result is never used, the compiler removes the computation, and you time an empty loop
  • Timer resolution: very short operations need to be repeated thousands of times inside the timed region
  • Unrepresentative input: tiny data fits in cache; real data may not
#include <time.h>
double now(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);          // monotonic: never jumps backward
    return t.tv_sec + t.tv_nsec * 1e-9;
}

volatile double sink;                            // writing a result here prevents deletion
double t0 = now();
for (int r = 0; r < 100; r++) sink = work(data, n);
double t1 = now();
printf("%.3f ms per call\n", (t1 - t0) / 100 * 1e3);

§3Controlling the Environment

CPU frequency changes with load and temperature, which makes timings drift. For repeatable results on a test machine, you can fix the governor and pin the process to a core. Always compare changes on the same machine, in the same state.

sudo cpupower frequency-set -g performance      # avoid slow ramp-up and idle clocks
taskset -c 2 ./prog                             # run on one core, reducing migration noise

Report what you measured: the machine, the compiler flags, the input size, and the statistic. A result that others can't reproduce isn't really a result. And always verify that the fast version produces the same answer, because wrong code can be arbitrarily fast.

Gotcha A benchmark that runs 'too fast to be true' usually is. Check whether the compiler optimized the work away, and look at the generated code if the numbers seem impossible.

§4Common Mistakes

MistakeWhat HappensFix
Timing a single runNoise and warm-up dominate the resultRepeat, discard warm-up, and report median and spread
Not using the result of benchmarked codeThe compiler deletes the computationConsume the result with a volatile sink or by printing it
Comparing results from different machine statesFrequency and background load skew the comparisonTest both versions in alternation, on the same system
Practice
  1. Write a microbenchmark for summing an array. Make it report the median of 20 runs, and show that removing the use of the result changes the time.
  2. Run perf stat -r 10 on a program and read the variation figure. Is the measurement stable?
Key takeaways
  • Wall time, CPU time, throughput, and tail latency answer different questions.
  • Warm up, repeat, report median and spread, and guard against dead-code elimination.
  • Control the environment, document it, and check correctness alongside speed.
