Prefetching & Cache-Friendly Code

Hardware tries to fetch your data before you ask, and the loop transformations you choose either help it, or defeat it.

§1Hardware Prefetching

CPUs watch the stream of cache misses and detect patterns. When it sees a sequential or constant-stride pattern, the hardware prefetcher begins fetching lines ahead of the program's requests, so that data arrives before it's needed. This is why scanning an array is fast even for data far larger than the cache.

PatternPrefetcherResult
Sequential array scanEffectiveMisses are mostly hidden
Constant stride (every 8th element)Often effectiveGood, within page limits
Pointer chasing (linked list)Cannot predictEach hop exposes full latency
Random access (hash table)Cannot predictLatency-bound

Prefetchers usually stop at page boundaries, because the next virtual page may map somewhere unrelated, so very large strides get little help.

§2Software Prefetching and Overlap

When access is irregular but predictable by the program, you can request lines early yourself.

for (int i = 0; i < n; i++) {
    __builtin_prefetch(&table[index[i + 8]]);   // start fetching 8 iterations ahead
    sum += table[index[i]];                      // this line was requested earlier
}

The distance matters: too short and the data hasn't arrived, too long and it may be evicted before use. Software prefetch is a measured, last-mile tool, and often the better fix is to restructure the data or process in batches so that several independent misses overlap.

§3Blocking (Tiling) a Loop

A naive matrix multiply walks through memory in a pattern that reuses data only after the cache has overwritten it. Tiling splits the work into small blocks that fit in the cache, so every loaded element is used many times before being evicted.

// Naive: B[k][j] strides down a column of B, with poor locality
for (i = 0; i < N; i++)
  for (j = 0; j < N; j++)
    for (k = 0; k < N; k++)
      C[i][j] += A[i][k] * B[k][j];

// Tiled: work on BS x BS blocks that fit in L1/L2
for (ii = 0; ii < N; ii += BS)
 for (jj = 0; jj < N; jj += BS)
  for (kk = 0; kk < N; kk += BS)
   for (i = ii; i < ii+BS; i++)
    for (j = jj; j < jj+BS; j++)
     for (k = kk; k < kk+BS; k++)
      C[i][j] += A[i][k] * B[k][j];

// Pick BS so three blocks fit: 3 * BS * BS * 8 bytes <= L1 size.  BS = 32 -> 24 KiB.

The arithmetic is unchanged, but memory traffic drops dramatically, and on large matrices tiled code is commonly several times faster. Optimized libraries (BLAS) do this, with extra register-level blocking and SIMD, which is why you should use them rather than writing your own.

The key insight Make your access pattern predictable and reuse data while it's still in cache. Structure loops so that the hardware can prefetch, and so that each loaded line does as much work as possible.

§4Common Mistakes

MistakeWhat HappensFix
Relying on prefetching for pointer-heavy structuresThe prefetcher can't predict dependent loadsUse contiguous layouts, or batch lookups to overlap misses
Choosing tile sizes by guessTiles that are too big thrash, too small waste overheadSize tiles from the cache capacity and measure
Hand-writing matrix multiply in productionLibraries are far better tunedUse BLAS or a similar optimized library
Practice
  1. Implement naive and tiled matrix multiply for N = 1024, try BS = 8, 16, 32, 64, and plot the time against block size.
  2. Describe how you would restructure a loop doing sum += table[index[i]] so that several table lookups are in flight at once.
Key takeaways
  • Hardware prefetchers detect sequential and strided access, but not pointer chasing or random access.
  • Software prefetch helps irregular but predictable patterns, with a well-chosen distance.
  • Tiling reuses data within the cache, and optimized libraries already do it.
