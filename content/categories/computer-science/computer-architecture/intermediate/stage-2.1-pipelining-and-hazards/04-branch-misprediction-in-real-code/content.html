Branch Misprediction in Real Code

A famous experiment shows the same loop running several times faster on sorted data than on random data, with no change to the work done, only to how predictable the branches are.

§1The Experiment

Sum the elements of an array that are at least 128, where the array holds random bytes.

#include <stdint.h>
#include <stdlib.h>
#define N 32768

long run(const uint8_t *data) {
    long sum = 0;
    for (int rep = 0; rep < 100000; rep++)
        for (int i = 0; i < N; i++)
            if (data[i] >= 128)          // the branch we care about
                sum += data[i];
    return sum;
}

With random data, the condition is true about half the time, in no pattern the predictor can learn, so it mispredicts close to 50% of the branches. After sorting the array, the first half is all 'not taken' and the second half is all 'taken', and the predictor is nearly perfect. The arithmetic is identical, but the sorted version can be several times faster.

§2Measuring It

gcc -O1 sort_test.c -o t              # lower optimization to keep the branch (see note below)
perf stat -e branches,branch-misses ./t random
perf stat -e branches,branch-misses ./t sorted

# Typical shape of the result:
#   random: branch-misses around 25-50% of the data-dependent branches, slow
#   sorted: branch-misses under 1%, much faster

At higher optimization levels, a compiler may turn the branch into a conditional move or vectorize the loop, which removes the branch and with it the effect. That's an instructive result in itself: a fast outcome can come from the compiler making the code branchless.

§3Making Code Branch-Friendly

  • Make the pattern predictable: sorting, or grouping items by type, so that consecutive iterations take the same path
  • Use branchless arithmetic for tiny decisions, so the CPU never has to guess
  • Move rare cases out of the hot path: error handling and unlikely cases should not interleave with common work
  • Trust the compiler, then verify: it often chooses conditional moves for simple cases, so look at the assembly
// Branchless: the mask is all 1s if the condition holds, otherwise 0
int mask = -(data[i] >= 128);         // -1 (0xFFFFFFFF) or 0
sum += data[i] & mask;

// GCC/Clang hint for a genuinely rare path (use sparingly, measure first)
if (__builtin_expect(error, 0)) handle_error();

Branchless isn't always better. When a branch is highly predictable, a branch is cheaper, because the branchless form does extra work on every iteration. The benefit appears when the outcome is unpredictable.

The key insight Branch cost depends on predictability, not on the branch itself. The same if is free in one program and expensive in another, so measure with branch-misses rather than assuming.

§4Common Mistakes

MistakeWhat HappensFix
Optimizing branches without measuring the misprediction rateEffort goes into branches that were already well predictedCheck perf stat branch-misses first
Writing branchless code everywhereExtra work on every iteration slows predictable casesUse it only where outcomes are unpredictable
Benchmarking at an optimization level that removes the branchThe experiment seems to show no effectInspect the assembly to see if a cmov or vector code replaced it
Practice
  1. Run the experiment at -O1 with random and sorted data, and report the branch-miss rates and times.
  2. Rewrite the loop in a branchless form and compare its time on random data against the branchy version.
Key takeaways
  • The same loop can be several times faster when branch outcomes are predictable, such as after sorting.
  • Measure with perf stat -e branches,branch-misses and check generated code for conditional moves.
  • Branchless code helps only for unpredictable branches; predictable ones are cheap.
