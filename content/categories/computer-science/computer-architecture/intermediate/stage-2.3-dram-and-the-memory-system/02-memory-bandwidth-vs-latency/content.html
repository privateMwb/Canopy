Memory Bandwidth vs. Latency

Latency is how long one access takes, and bandwidth is how many bytes per second the system can move, and which one limits your program decides what to optimize.

§1Two Different Limits

Latency is the time from request to data, about 80 ns for a DRAM access. Bandwidth is the sustained rate, such as GB/s. They aren't two views of one number: a system can have high bandwidth and high latency, like a wide, long pipe.

# Peak bandwidth of DDR4-3200: 3200 million transfers/s * 8 bytes per transfer
= 25.6 GB/s per channel      # dual-channel: 51.2 GB/s
# DDR5-4800: 4800e6 * 8 B = 38.4 GB/s per channel

Real, achieved bandwidth is typically 70 to 90% of peak on a streaming workload, because of refresh, bank conflicts, and read-write turnaround.

§2Concurrency Links the Two

How many bytes must be in flight to keep the memory busy? Little's law says concurrency = bandwidth × latency.

in flight = 25.6 GB/s * 80 ns = 2,048 bytes = 32 cache lines

# A single core can only track so many outstanding misses (line fill buffers, about 10 to 16):
one core:  ~10 lines * 64 B / 80 ns  = ~8 GB/s       # far below 25.6 GB/s

# A dependent chain (pointer chasing) has exactly 1 miss in flight:
64 B / 80 ns = 0.8 GB/s

This is memory-level parallelism (MLP). Streaming code issues many independent loads, so many misses overlap and bandwidth is high. Pointer chasing serializes the misses, so it runs at latency speed, regardless of how fast the memory bus is. A single core often cannot saturate DRAM by itself, and several cores together can.

§3Telling Which One You're Hitting

SymptomLikely limitRemedy
Streaming code with many threads, bandwidth near peakBandwidthReduce traffic: compress, fuse loops, tile, shrink data types

Bandwidth grows when adding threadsConcurrency (MLP)Add threads or independent streams
// STREAM triad: a classic bandwidth test. 24 bytes of traffic per element (2 reads + 1 write),
// about 32 with write-allocate reads.
for (size_t i = 0; i < n; i++)
    a[i] = b[i] + s * c[i];

# Standard tools
./stream                          # STREAM benchmark: sustainable bandwidth
mlc --latency_matrix              # Intel Memory Latency Checker (Intel-specific)
lat_mem_rd                        # lmbench: latency at each working-set size

If your program moves 40 GB of data in 2 seconds, that's 20 GB/s. Compare it to the machine's measured peak: if it is close, the program is bandwidth-bound and only reducing the bytes moved will help.

The key insight A program is latency-bound when each access waits on the last, and bandwidth-bound when many independent accesses fill the pipe. The two need opposite fixes: more overlap, or fewer bytes.

§4Common Mistakes

MistakeWhat HappensFix
Optimizing for latency when the code is bandwidth-boundAdded prefetching and overlap do nothing, since the bus is already fullMeasure bytes moved per second against the machine's peak
Quoting peak bandwidth as achievableReal programs get a fraction of itUse STREAM to find the sustainable figure
Expecting one thread to saturate memoryA core tracks limited outstanding missesUse several threads or streams for bandwidth-heavy work
Practice
  1. Compute the number of cache lines in flight needed to sustain 40 GB/s at 90 ns latency.
  2. Write a pointer-chasing loop and a sequential-sum loop over the same 1 GiB of data. Compare effective GB/s.
Key takeaways
  • Latency is time per access, and bandwidth is bytes per second; programs can be limited by either.
  • Bandwidth = concurrency ÷ latency (Little's law), so memory-level parallelism matters.
  • Pointer chasing is latency-bound, and streaming is bandwidth-bound.
