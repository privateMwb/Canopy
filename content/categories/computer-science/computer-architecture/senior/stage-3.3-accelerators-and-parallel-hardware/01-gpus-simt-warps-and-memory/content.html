GPUs: SIMT, Warps & Memory

A GPU trades the CPU's fast single-thread speed for thousands of simple threads running together, and it performs well only when those threads move in step and touch memory in orderly patterns.

§1A Different Design Goal

A CPU core is built to finish one thread as fast as possible, with big caches, branch predictors, and out-of-order machinery. A GPU is built for throughput: it devotes its silicon to many simple execution lanes and hides latency by switching among thousands of threads rather than by speculating.

CPUGPU
GoalLow latency for each threadHigh total throughput
CoresTens of complex coresThousands of simple lanes, grouped into streaming multiprocessors
Latency hidingCaches, out-of-order, speculationMany resident threads; switch to another when one waits
MemoryBig caches, modest bandwidth (tens of GB/s)Small caches, very high bandwidth (hundreds of GB/s to several TB/s)
Best atBranchy, serial, irregular codeData-parallel, regular computation

§2The SIMT Execution Model

GPU programs are written as a kernel, a function run by a huge number of threads, each handling one piece of data. Threads are grouped into blocks, and the hardware runs them in warps of 32 threads (NVIDIA; AMD uses 32 or 64) that execute the same instruction in lockstep. This is SIMT (single instruction, multiple threads).

__global__ void add(const float *a, const float *b, float *c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // this thread's element
    if (i < n) c[i] = a[i] + b[i];
}
// Launch enough blocks of 256 threads to cover n elements:
add<<<(n + 255) / 256, 256>>>(a, b, c, n);

Each warp is scheduled on an SM, and while one warp waits for memory, the SM instantly switches to another that is ready, at no cost. Keeping many warps resident, called high occupancy, is how a GPU hides its memory latency.

§3What Makes GPU Code Slow

  • Divergence: if threads in a warp take different sides of a branch, the warp executes both paths one after the other, with the inactive lanes masked off. Heavy per-thread branching can cut throughput several-fold
  • Uncoalesced memory access: when the 32 threads of a warp read adjacent addresses, the hardware combines them into a few wide transactions (coalescing). When they read scattered addresses, it needs many transactions and wastes bandwidth
  • Too little parallelism: a small problem can't fill thousands of lanes, and occupancy stays low
  • Data movement: moving data between CPU and GPU can cost more than the computation, as the next lessons show
  • Low arithmetic intensity: kernels that do little work per byte are limited by memory bandwidth, not by the lanes
// Coalesced: consecutive threads read consecutive elements, so one wide transaction per warp
float x = in[blockIdx.x * blockDim.x + threadIdx.x];

// Uncoalesced: a stride between threads scatters the warp's reads across many lines
float y = in[(blockIdx.x * blockDim.x + threadIdx.x) * 32];

GPUs also have a fast on-chip shared memory, programmer-managed and visible to a block, used for tiling, the same locality idea as in the cache lessons, only explicit.

The key insight A GPU is fast when the work is wide, regular, and arithmetic-heavy, and slow when it is narrow, branchy, or scattered. Most GPU tuning is making memory access orderly and keeping all lanes doing the same thing.

§4Common Mistakes

MistakeWhat HappensFix
Putting heavy branching in a kernelWarp divergence serializes both pathsRestructure so threads in a warp take the same path, or sort the data
Letting adjacent threads read strided memoryUncoalesced access wastes bandwidthArrange data so adjacent threads touch adjacent addresses
Launching too few threadsLanes sit idle and latency isn't hiddenGive the GPU many thousands of independent work items
Practice
  1. Write a CUDA (or HIP, or a pseudocode) kernel for c = a + b, and calculate how many blocks of 256 threads cover 1,000,000 elements.
  2. Explain why a branch that depends on threadIdx.x % 2 is worse for performance than one that depends on blockIdx.x.
Key takeaways
  • GPUs maximize throughput with many simple lanes, hiding latency by switching among thousands of threads.
  • Threads run in warps of 32 in lockstep, so divergence serializes branches.
  • Coalesced access, high occupancy, and enough parallel work are the keys to GPU speed.
