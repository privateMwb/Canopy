Speculative Execution & Spectre-Class Flaws

Speculation is invisible to programs by design, but it leaves traces in the cache, and that gap between architectural and microarchitectural state is the root of a whole class of vulnerabilities.

§1Two Kinds of State

Architectural state is what the ISA defines: registers, memory, and the program counter. A correct CPU guarantees that squashed, speculative instructions leave it unchanged. Microarchitectural state is everything else the hardware keeps for speed: cache contents, branch predictor tables, TLB entries. The ISA says nothing about it, and speculation can change it.

When a branch is mispredicted, the registers and memory writes of the wrong-path instructions are discarded. But if those instructions loaded data into the cache, the line stays there. Whether a particular line is in the cache can be inferred by timing an access to it, as the next lesson explains. That is the opening.

§2The Spectre Family, Conceptually

Spectre-class attacks, disclosed publicly in January 2018, trick the CPU into speculatively executing code that wouldn't run in a correct program execution, and then detect the side effects.

  • Bounds-check bypass (Spectre v1): a program checks that an index is within bounds before using it. By repeatedly feeding in-bounds values, an attacker trains the branch predictor to expect the check to pass. Then, with an out-of-bounds index, the CPU speculates past the check, reads memory it should not, and uses the value in a way that leaves a data-dependent footprint in the cache. After the misprediction is detected, the architectural effects are undone, but the cache footprint remains
  • Branch-target injection (Spectre v2): the attacker poisons the indirect branch predictor so that a victim's indirect jump speculatively goes to an attacker-chosen location
  • Meltdown: on affected CPUs, a user program's load from kernel memory could proceed speculatively, with data forwarded to later instructions, before the permission check raised its fault, and the fault was handled too late to prevent the cache footprint

These descriptions are deliberately high level. What matters for an engineer is the pattern: a secret is read under speculation, and then converted into cache state by a dependent access.

§3Why It Is Hard to Fix

  • Speculation isn't a bug in one chip; it's the core mechanism that makes modern CPUs fast. Removing it would cost enormous performance
  • Many separate variants exist, which exploit different predictors and buffers: later disclosures include MDS, L1TF, and others
  • The hardware, operating systems, compilers, and browsers all had to ship mitigations, and the fix surface was large
  • Some flaws are fixed in newer silicon, while others needed microcode and software workarounds that cost performance
# See which known issues your CPU is affected by and what the kernel does about each
grep . /sys/devices/system/cpu/vulnerabilities/*
lscpu | grep -i vulnerab

The lasting lesson is that the interface between hardware and software is not just the ISA. Timing and resource-sharing effects are an additional channel that correct-by-ISA designs did not consider.

The key insight Speculation breaks the abstraction that squashed instructions have no effect. The architectural result is rolled back, but the cache isn't, and timing can reveal what the cache holds.

§4Common Mistakes

MistakeWhat HappensFix
Thinking this is a software bug in one programThe root cause is in hardware behaviorMitigate at several layers, hardware, OS, compiler, and application
Believing a rolled-back instruction left no traceMicroarchitectural state persistsTreat caches and predictors as observable state
Assuming it only affects shared hostsAny boundary where untrusted code runs, such as browsers and sandboxes, mattersApply mitigations where untrusted code shares a core or process
Practice
  1. In your own words, explain the difference between architectural and microarchitectural state, and why squashing leaves one but not the other.
  2. Run the vulnerabilities listing on your machine. Which issues does the kernel report as mitigated, and by what?
Key takeaways
  • Architectural state is rolled back on a misprediction, but microarchitectural state such as the cache is not.
  • Spectre-class flaws read secrets under speculation and encode them into cache state.
  • The flaws are a class stemming from speculation itself, so fixes are layered and have costs.
