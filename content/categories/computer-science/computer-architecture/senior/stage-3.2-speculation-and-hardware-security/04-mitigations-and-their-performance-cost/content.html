Mitigations & Their Performance Cost

Every defense against speculation attacks gives something up, and the right set depends on whether you run untrusted code, share hardware with strangers, or only your own programs.

§1The Toolbox

MitigationTargetsWhat it doesTypical cost
Kernel page-table isolation (KPTI)MeltdownUnmaps most kernel memory from user page tablesSyscall- and interrupt-heavy work slows, from negligible to tens of percent
RetpolineBranch-target injectionReplaces indirect branches with a form that traps speculationSmall to moderate on indirect-call-heavy code
IBRS / eIBRS, STIBP, IBPBBranch-target injectionRestrict sharing of predictor state across privilege levels, threads, and contextsVaries; lower on newer hardware
Speculation barriers (lfence) and index maskingBounds-check bypassStop or neutralize speculation at sensitive pointsPer site; small when targeted
Buffer clearing on transitionsMDS-class flawsFlush internal buffers when crossing privilege boundariesPer transition; adds up for syscall-heavy loads
Disabling SMTCross-thread leakageRemoves the co-resident siblingOften 10–30% throughput on SMT-friendly loads
Site isolation, timer coarsening (browsers)Attacks from web contentA process per site; reduced timer precisionMemory overhead; reduced timing features

Newer CPUs fix some issues in silicon, for example, later Intel parts are not vulnerable to Meltdown and gain hardware-assisted branch-prediction controls (eIBRS), so the software costs shrink on newer hardware.

§2Where the Cost Shows Up

  • Costs are highest for frequent privilege transitions: system calls, interrupts, VM exits, and context switches, which is why I/O-heavy and virtualized workloads notice them most
  • Compute-bound code that rarely enters the kernel sees little effect
  • Mitigations have been tuned and partly moved into hardware since 2018, so figures from the first patches overstate today's costs on current CPUs
  • Benchmark with and without a mitigation on your own workload, because generic percentages mislead
cat /proc/cmdline                                         # kernel boot options, including any mitigation settings
grep . /sys/devices/system/cpu/vulnerabilities/*          # per-issue status and the mitigation in use
# The kernel parameter mitigations=off disables them: only acceptable on an isolated,
# single-tenant machine running fully trusted code.

§3Choosing by Threat Model

SettingPosture
Multi-tenant cloud, hosts running other customers' codeFull mitigations; consider disabling SMT or core-scheduling for isolation
Browser or sandbox running untrusted web or plugin codeSite isolation, timer limits, current browser and OS patches
Dedicated machine, only your own trusted codeDefaults are fine; relax carefully only with measured benefit and an accepted risk
Handling secrets (keys, tokens) in shared environmentsConstant-time code, hardware crypto, and isolation by process or machine

Treat these as engineering decisions, not defaults to flip blindly: state the threat model, measure the cost, record the decision, and revisit it when hardware or software changes. A mitigation turned off to win 5% can become an incident, and one left on across a fleet can cost real money.

The key insight Security and performance are being traded here. The right answer depends on who can run code on your hardware, so decide from the threat model, measure on your workload, and write the decision down.

§4Common Mistakes

MistakeWhat HappensFix
Disabling mitigations globally to 'recover performance'Exposes shared or sandboxed environmentsScope any relaxation to isolated, trusted machines
Quoting 2018 slowdown numbers for current hardwareCosts have fallen on newer CPUs and kernelsBenchmark on your actual hardware
Ignoring cost on syscall-heavy servicesHidden overhead on I/O pathsProfile kernel time before and after changes
Practice
  1. List the mitigations your machine reports as active and describe in one sentence what each protects against.
  2. Write a threat-model paragraph for a service that runs only your company's code on dedicated hardware, and decide which mitigations you would keep.
Key takeaways
  • Mitigations include KPTI, retpoline, predictor controls, barriers, buffer clearing, and SMT changes.
  • Costs concentrate on privilege transitions and are lower on newer CPUs.
  • Choose mitigations from the threat model and measured cost, and record the decision.
