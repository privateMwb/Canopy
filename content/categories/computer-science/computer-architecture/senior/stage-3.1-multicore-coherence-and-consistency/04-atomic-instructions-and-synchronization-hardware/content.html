Atomic Instructions & Synchronization Hardware

Locks, counters, and lock-free structures all bottom out in a few special instructions that perform a read-modify-write on memory as one indivisible step.

§1Atomic Read-Modify-Write

An ordinary x++ is a load, an add, and a store, and another core can intervene between them. Hardware provides atomic instructions that do the whole sequence as a single step, with respect to every other core.

# AArch64 without LSE: a load-linked / store-conditional retry loop
.Lretry:
    ldxr  w1, [x0]
    add   w1, w1, 1
    stxr  w2, w1, [x0]       # w2 = 0 on success, 1 if the reservation was lost
    cbnz  w2, .Lretry

On x86, atomic read-modify-write instructions also act as full memory barriers, which makes them simple to reason about but costly compared with plain stores.

§2How the Hardware Does It

The core must have the line in the Modified state and keep it from being stolen for the duration of the operation. On a read-modify-write, the cache locks the line briefly: it acquires exclusive ownership, performs the read, the modify, and the write, and only then answers other cores' requests for it.

  • Uncontended atomics are cheap, around 15 to 25 cycles on many x86 cores, because the line is already local
  • Contended atomics cost a cache-to-cache transfer each, tens to hundreds of cycles, as in the ping-pong example
  • LL/SC (load-linked/store-conditional, used by ARM and RISC-V) sets a reservation on a line, and the store succeeds only if nothing else wrote it in the meantime. It can fail spuriously, for instance if the line is evicted, so it is always used in a retry loop
  • Compare-and-swap is the building block for lock-free algorithms, and has the ABA problem discussed in the OS category

Atomics that need a whole-line lock are why a misaligned atomic crossing a cache-line boundary is expensive on x86: it needs a system-wide bus lock, and some platforms now flag or trap it.

§3Building Locks on Top

A simple spinlock repeatedly attempts an atomic exchange until it gets the old value 0.

void lock(atomic_int *l) {
    while (atomic_exchange_explicit(l, 1, memory_order_acquire)) {   // try to set 1
        while (atomic_load_explicit(l, memory_order_relaxed))        // spin on a cheap read
            __builtin_ia32_pause();                                   // x86 'pause' hint
    }
}
void unlock(atomic_int *l) { atomic_store_explicit(l, 0, memory_order_release); }

Spinning on a plain load rather than the exchange keeps the line in the Shared state while waiting, so waiting cores don't keep stealing it. The pause instruction tells the core it's in a spin loop, which saves power and avoids a costly pipeline flush when the lock is released. Under heavy contention, more scalable lock designs queue waiters, so each spins on its own cache line, such as ticket locks and MCS locks.

Connection to earlier lessons These instructions are what the OS course's mutexes, futexes, and lock-free stacks rest on. Their cost is the coherence cost of this stage: an atomic is as fast as the cache line is close.

Practice
  1. Compile atomic_fetch_add for x86-64 and for AArch64 on Compiler Explorer, with and without LSE (-march=armv8.1-a), and compare the instructions.
  2. Measure the cost of an uncontended atomic_fetch_add versus a plain ++, and then with 4 threads contending.
Key takeaways
  • Atomic read-modify-write instructions, like lock xadd, ldadd, and amoadd, perform one indivisible update.
  • They work by holding the cache line exclusively; contention turns them into cache-line transfers.
  • LL/SC and CAS are retry-based building blocks; spin locks should spin on reads, with a pause hint.
