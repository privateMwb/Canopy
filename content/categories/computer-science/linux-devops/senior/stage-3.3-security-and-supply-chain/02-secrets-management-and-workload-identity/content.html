Secrets Management & Workload Identity

Long-lived passwords in files are a standing liability, so modern systems hand out short-lived credentials tied to the identity of the workload asking for them.

§1Why Static Secrets Fail

A long-lived key copied into CI settings, config files, or images can leak through logs, backups, and old repositories, and it works for anyone who has it until someone remembers to rotate it. Treat each such secret as a risk to shrink: fewer of them, shorter lived, narrower scope, and stored in a purpose-built system.

# find and rotate what you already have
git log -p | grep -E "AKIA[0-9A-Z]{16}"        # AWS key pattern, as an example
gitleaks detect --source .                       # scan the repo and its history
# a leaked secret in history is compromised: ROTATE it, do not just delete it

§2Secrets Managers and Dynamic Credentials

A secrets manager such as Vault or a cloud's native service provides encrypted storage, access control, audit logs, and rotation. Better still, it can mint dynamic credentials: a database login created on request that expires in an hour and is revoked automatically.

# the application asks for a credential when it starts
vault read database/creds/shop-readonly
# Key             Value
# lease_duration  1h
# username        v-shop-ro-8s2k
# password        <generated>

§3Workload Identity and OIDC

Instead of storing a cloud key in CI, let the pipeline prove who it is. The CI provider issues a signed OIDC token for each run, stating the repository and branch. The cloud trusts the provider and exchanges the token for temporary credentials, scoped by a trust policy. No long-lived secret exists to steal.

permissions:
  id-token: write        # allow this job to request an OIDC token
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/shop-deploy
      aws-region: eu-west-1
# the role's trust policy only accepts tokens whose subject is
#   repo:acme/shop:ref:refs/heads/main

The trust policy is the security boundary. A subject condition that is too loose, such as any branch of any repository in your organization, lets unrelated code assume a powerful role.

The key insight The strongest secret is the one that does not exist. OIDC and workload identity replace "something you have" with "something you are": a verifiable identity, a short lifetime, and no file to leak.

§4Common Mistakes

MistakeWhat HappensFix
Committing a secret and deleting it in the next commitIt stays in Git history and may already be copiedRotate it immediately, then scrub history if needed
One powerful credential shared by every pipelineA single leak reaches every systemIssue per-workload, narrowly scoped identities
Trust policies that accept any repository or branchUnrelated code can assume your deploy roleConstrain the token subject to the exact repo and branch
Practice
  1. Replace a stored cloud key in a pipeline with OIDC, and write the trust policy restricted to one repo and the main branch.
  2. Run a secret scanner over a repository's full history and rotate anything it finds.
Key takeaways
  • Static long-lived secrets are a liability, so reduce, scope, and rotate them.
  • Secrets managers provide audited access and dynamic, expiring credentials.
  • OIDC workload identity removes stored cloud keys, and the trust policy is what must be precise.
