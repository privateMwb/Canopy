Why Orchestrators: Desired State & Reconciliation

Kubernetes is built on one idea: you declare the state you want, and controllers continuously work to make reality match it.

§1Desired State and Control Loops

You do not tell Kubernetes "start three copies". You submit an object saying "I want three replicas", stored in the cluster's database (etcd) through the API server. Controllers run endless loops: observe actual state, compare with desired state, and act to close the gap. If a node dies, the controller sees two replicas where three are wanted and starts another.

kubectl apply -f deployment.yaml          # submit the desired state
kubectl get pods -w                       # watch controllers converge
kubectl delete pod shop-7d9f-abcde        # a controller notices and replaces it
kubectl get events --sort-by=.lastTimestamp

§2The Architecture

The control plane holds the API server, etcd, the scheduler (which assigns pods to nodes), and the controller manager. Each node runs the kubelet (which makes the node match its assignments), a container runtime, and a network proxy. Everything talks to the API server and never directly to each other.

# a pod's journey
#   kubectl apply -> API server stores the object
#   scheduler picks a node (watching for unassigned pods)
#   kubelet on that node sees its assignment
#   kubelet asks the container runtime to start the containers
#   kubelet reports status back to the API server
kubectl get nodes -o wide
kubectl describe node worker-1 | less

§3Why This Beats Scripts

A deploy script runs once and exits. A control loop never stops, so it also handles what happens afterwards: crashes, node failures, and scale changes. That is also why declarative config suits Git: the files in the repository are the desired state, and a tool can keep the cluster synchronized to them.

kubectl diff -f deployment.yaml           # what would change?
kubectl apply -f deployment.yaml
kubectl get deploy shop -o yaml | less    # spec = desired, status = observed
The key insight Compose starts containers on one machine and stops caring. Kubernetes keeps caring: it is a system that continuously repairs itself toward your declared intent. Debugging it is mostly asking "what do the controllers believe, and why can't they converge?"

§4Common Mistakes

MistakeWhat HappensFix
Running imperative commands to change live objectsThe cluster drifts from the files in GitEdit the YAML and kubectl apply it
Expecting immediate resultsControllers converge over timeWatch with -w, and read events and status
Treating the cluster as a pile of serversYou fight the scheduler instead of using itDeclare what you want and let controllers place it
Practice
  1. Create a Deployment with three replicas, delete one pod, and watch it return.
  2. Compare the spec and status sections of a Deployment and explain which one you control.
Key takeaways
  • You declare desired state, and controllers reconcile reality toward it continuously.
  • The control plane (API server, etcd, scheduler, controllers) decides, and kubelets execute on nodes.
  • Declarative files in Git are what make the cluster reproducible.
