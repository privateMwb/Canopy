Requests, Limits & Scheduling

Kubernetes turns the cgroups you met in the OS track into requests and limits, and the numbers you choose decide where pods land and how they fail.

§1Requests and Limits

A request is what the scheduler reserves for the container when choosing a node. A limit is the cgroup ceiling enforced at run time. CPU is measured in cores (500m is half a core) and memory in bytes.

resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    memory: 512Mi          # a hard ceiling
    # cpu limit omitted on purpose; see below

§2How Each Limit Fails

CPU is compressible: exceed the CPU limit and the cgroup is throttled, so the process slows down but survives. Memory is not: exceed the memory limit and the kernel OOM killer ends the container, which shows as OOMKilled and exit code 137, then Kubernetes restarts it, often leading to CrashLoopBackOff.

kubectl describe pod shop-7d9f-abcde      # look for: Last State: OOMKilled
kubectl top pod                           # live usage (needs metrics-server)
kubectl get pod shop-7d9f-abcde -o jsonpath='{.status.containerStatuses[0].lastState}'
# inside the node, the same limits are plain cgroup files:
#   /sys/fs/cgroup/<pod-path>/memory.max
#   /sys/fs/cgroup/<pod-path>/cpu.max

Many teams set a memory limit equal to the request and leave CPU limits off or generous, to avoid unexplained latency from throttling. Choose from measurements rather than guesses.

§3Scheduling, QoS, and Eviction

The scheduler places a pod only on a node with enough unreserved capacity for its requests. Requests also define the pod's QoS class: Guaranteed (requests equal limits for all resources), Burstable, or BestEffort (none set). Under node pressure, BestEffort pods are evicted first.

kubectl describe node worker-1            # see "Allocated resources"
kubectl get pod shop-7d9f-abcde -o jsonpath='{.status.qosClass}'
# Pending pod? the event usually says why:
#   0/5 nodes are available: Insufficient memory
kubectl get events --field-selector reason=FailedScheduling
Requests drive placement, limits drive failure Set requests too low and nodes get overpacked and unstable. Set them too high and you pay for capacity nobody uses. Right-size from observed usage, and revisit as the workload changes.

§4Common Mistakes

MistakeWhat HappensFix
Setting no requestsThe scheduler overpacks nodes, and the pods are first to be evictedSet requests from measured usage
Memory limit below real peak usageOOMKilled and restart loopsMeasure peak memory and leave headroom
Tight CPU limits on latency-sensitive servicesThrottling causes mysterious slow requestsSet CPU requests, and use limits sparingly after measuring
Practice
  1. Deploy a pod that allocates memory until it exceeds its limit, then find OOMKilled and exit code 137 in kubectl describe.
  2. Find the cgroup files for a running container on a node and match them to its resource settings.
Key takeaways
  • Requests reserve capacity for scheduling, and limits are cgroup ceilings enforced at run time.
  • CPU over the limit is throttled, but memory over the limit is killed (OOMKilled, exit 137).
  • Requests decide QoS class and eviction order, so size them from real measurements.
