Remotes, Pull Requests & Code Review

Remotes let you share branches, and pull requests wrap a branch in a review and automated checks before it merges, which is the trigger for almost every CI pipeline.

§1Remotes

A remote is another copy of the repository, usually on GitHub or GitLab, conventionally named origin. fetch downloads new commits without touching your work, pull is fetch plus merge (or rebase), and push uploads your commits.

git clone git@github.com:acme/shop.git
git remote -v                    # where do origin pushes go?
git fetch origin                 # update remote-tracking branches
git pull --rebase                # fetch and replay my work on top
git push -u origin fix-login     # first push; sets upstream tracking
git push                         # later pushes

origin/main is your local record of where main was on the server at your last fetch. It does not update by itself.

§2The Pull Request Flow

The standard team loop: branch from the latest main, commit in small steps, push, open a pull request (PR), get review and passing checks, then merge. Reviewers read a diff, ask questions, and approve or request changes.

git switch main && git pull
git switch -c add-rate-limiting
# ...edit, test, commit...
git push -u origin add-rate-limiting
# open the PR in the web UI (or: gh pr create --fill)
# respond to review with more commits, then merge

Keep PRs small. A 50-line change gets a careful review, while a 2,000-line change gets a rubber stamp.

§3Protecting the Main Branch

Teams enforce the process with branch protection: require PRs, require approvals, and require status checks (tests, linting) to pass before merging. This is where Git meets CI/CD. The checks are pipelines triggered by the push.

# typical protection rules on main
#   - require a pull request with 1 approval
#   - require status checks: lint, test, build
#   - block force-pushes and deletion
git push --force-with-lease      # safer force-push for your own branch
Review is part of the system A good PR description says what changed, why, and how it was tested. Reviewers are checking your reasoning as much as your code, and CI checks the part a human should not have to.

§4Common Mistakes

MistakeWhat HappensFix
Force-pushing with --forceOverwrites commits someone else pushedUse --force-with-lease, and never on shared branches
Opening one giant PRReviews are shallow and bugs slip throughSplit work into small, reviewable changes
Committing secrets, then deleting them laterThey remain in history and are already exposedRotate the secret immediately; prevention beats cleanup
Practice
  1. Clone a repo, create a branch, push it, and open a pull request against main.
  2. Review someone's PR (or your own from yesterday), and leave one comment about a risk rather than style.
Key takeaways
  • fetch downloads, pull updates your branch, and push shares your commits.
  • Pull requests combine review and automated checks before changes reach main.
  • Protect main with required reviews and status checks, and keep PRs small.
