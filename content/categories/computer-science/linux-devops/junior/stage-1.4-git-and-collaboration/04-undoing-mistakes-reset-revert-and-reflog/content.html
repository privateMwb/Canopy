Undoing Mistakes: reset, revert & reflog

Git rarely loses committed work, so knowing which undo to use, and how to find lost commits with the reflog, turns most disasters into minor events.

§1Undoing Local Changes

Choose the undo by where the change is: not yet staged, staged, or already committed. Each tool is safe or dangerous depending on whether the history is shared.

git restore app.py               # discard working-tree edits (DESTRUCTIVE)
git restore --staged app.py      # unstage, keep the edits
git commit --amend               # fix the last commit (local only)
git reset --soft HEAD~1          # undo the commit, keep changes staged
git reset --hard HEAD~1          # undo the commit and DISCARD changes

reset moves the branch label backward, which rewrites history, so use it only on commits you have not pushed. --hard also throws away uncommitted work, with no undo.

§2Undoing Shared History with revert

When a bad commit is already on a shared branch, do not rewrite history. git revert creates a new commit that applies the opposite change, which is safe for everyone who has pulled.

git revert a1b2c3d               # new commit that undoes a1b2c3d
git revert -m 1 9f8e7d6          # undo a merge commit (keep parent 1)
git push                         # an ordinary push; no force needed

§3Recovering with the reflog

The reflog records every position HEAD has been at on your machine, including commits no branch points to anymore. After a bad reset or a deleted branch, the commits are usually still there for around 30 to 90 days.

git reflog                       # history of where HEAD has been
# a1b2c3d HEAD@{0}: reset: moving to HEAD~3
# 7e8f9a0 HEAD@{1}: commit: Add retry logic
git switch -c rescued 7e8f9a0    # make a branch at the lost commit
git reset --hard HEAD@{1}        # or jump back to that point
git stash                        # park uncommitted work safely
git stash pop
Commit often, push when ready Anything committed can almost always be recovered. Uncommitted changes cannot. Frequent small commits are a safety net, and you can tidy them later with an interactive rebase.

§4Common Mistakes

MistakeWhat HappensFix
Using reset --hard casuallyUncommitted work is gone permanentlyCommit or stash first, then reset
Resetting a branch others have pulledTheir history diverges and pushes get rejectedUse git revert on shared branches
Panicking after a "lost" commitRushed commands make recovery harderStop, run git reflog, and create a branch at the commit
Practice
  1. Make three commits, run git reset --hard HEAD~2, then recover them with the reflog.
  2. Revert a commit on a shared branch and explain why a reset would have been the wrong choice.
Key takeaways
  • Pick the undo by location: restore for files, reset for local commits, revert for shared ones.
  • git reflog finds commits that no branch references, so committed work is rarely lost.
  • Uncommitted changes are the real risk, so commit or stash before dangerous commands.
