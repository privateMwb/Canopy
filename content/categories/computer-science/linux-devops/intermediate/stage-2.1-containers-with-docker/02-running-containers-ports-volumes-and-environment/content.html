Running Containers: Ports, Volumes & Environment

A container is isolated by default, so you must explicitly publish ports, mount storage, and pass configuration into it.

§1Running and Publishing Ports

docker run creates and starts a container. A container's ports are private until you publish them with -p host:container. Use -d to run in the background and --rm to delete the container when it exits.

docker run -d --name web -p 8080:80 nginx:1.27   # host 8080 -> container 80
curl -i http://localhost:8080
docker logs -f web                               # stdout/stderr of the main process
docker exec -it web sh                           # shell inside the running container
docker run --rm alpine:3.20 echo "one-off task"  # run and clean up

A container stays alive only as long as its main process (PID 1) does. If that process exits, the container stops.

§2Volumes and Bind Mounts

Data that must survive the container belongs outside its writable layer. A named volume is managed by Docker, and a bind mount maps a host directory into the container, which is handy for development.

docker volume create pgdata
docker run -d --name db \
  -v pgdata:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=devonly \
  postgres:16
docker run --rm -v "$PWD":/app -w /app node:20 npm test   # bind mount the code
docker volume ls

Remove the database container and start a new one with the same pgdata volume, and the data is still there. That separation of compute (disposable) from state (persistent) is the core habit of container work.

§3Environment and Resource Limits

Configuration enters through environment variables (-e, --env-file). Limits map directly onto cgroups, so a container can be capped on memory and CPU.

docker run -d --env-file .env myapp:1.4
docker run -d --memory=256m --cpus=0.5 myapp:1.4
docker stats --no-stream                       # live CPU and memory use
docker inspect web -f '{{.HostConfig.Memory}}'
docker update --restart unless-stopped web
A memory limit is a hard wall Exceeding --memory triggers the kernel OOM killer on that cgroup, and the container is killed with exit code 137 (128 + SIGKILL). The same thing happens later under Kubernetes limits.

§4Common Mistakes

MistakeWhat HappensFix
Forgetting -pThe app runs but nothing outside can reach itPublish with -p host:container
Writing important data inside the containerIt disappears with docker rmMount a volume at the data path
Putting passwords on the command lineThey appear in docker inspect and shell historyUse --env-file, secrets, or a secrets manager
Practice
  1. Run Postgres with a named volume, create a table, remove the container, start a new one on the same volume, and confirm the table is still there.
  2. Run a container with a 64 MB memory limit and trigger an OOM kill, then find exit code 137.
Key takeaways
  • Publish ports with -p, persist data with volumes, and configure through environment variables.
  • A container lives as long as its main process; logs are that process's stdout and stderr.
  • Memory and CPU limits are cgroup limits, and exceeding memory means an OOM kill.
