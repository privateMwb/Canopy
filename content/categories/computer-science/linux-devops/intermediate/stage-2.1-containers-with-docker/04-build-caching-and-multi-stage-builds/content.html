Build Caching & Multi-Stage Builds

Docker caches layers and rebuilds only what changed, so the order of your Dockerfile decides your build speed, and multi-stage builds keep tools out of the final image.

§1How the Build Cache Works

Docker reuses a layer when the instruction and everything before it are unchanged. The first changed step invalidates every layer after it. So put things that change rarely (dependency installation) before things that change constantly (your source code).

# SLOW: any code change reinstalls all dependencies
COPY . .
RUN npm ci

# FAST: dependencies only reinstall when package files change
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
docker build -t shop:dev .       # the second build prints CACHED for unchanged steps
docker build --no-cache -t shop:dev .   # force a clean rebuild

§2Multi-Stage Builds

Compilers, build tools, and dev dependencies are needed to build but not to run. A multi-stage build uses one stage to build and copies only the results into a minimal final stage.

FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/server ./cmd/server

FROM gcr.io/distroless/static-debian12
COPY --from=build /out/server /server
USER nonroot
ENTRYPOINT ["/server"]

The final image contains only the binary and a tiny base, often a few megabytes instead of hundreds. Smaller images pull faster, start faster, and expose far less attack surface.

§3Keeping Layers Small

Files deleted in a later layer still exist in the earlier one, so cleanup must happen in the same RUN. Combine related commands, and use slim or distroless bases where they fit.

# bad: the apt cache stays in the first layer forever
RUN apt-get update && apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# good: one layer, cleaned in the same step
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
The key insight Think of a Dockerfile as a pipeline sorted by how often each step changes. Stable steps go first so the cache keeps them, and volatile steps go last. This is the same reasoning you will apply to CI caching.

§4Common Mistakes

MistakeWhat HappensFix
Copying all source before installing dependenciesEvery code edit re-downloads every dependencyCopy only the manifest files first, install, then copy the rest
Deleting files in a separate RUNThe data is still stored in an earlier layerInstall and clean up in the same instruction
Shipping the build toolchain in productionLarge image with more known vulnerabilitiesUse a multi-stage build with a minimal runtime stage
Practice
  1. Rebuild an image after changing only one source file, and verify the dependency layer prints CACHED.
  2. Convert a single-stage Dockerfile to multi-stage and compare the image sizes with docker images.
Key takeaways
  • A changed layer invalidates all later layers, so order steps from least to most frequently changed.
  • Multi-stage builds separate building from running, which shrinks images and attack surface.
  • Clean up in the same layer that created the mess.
