Images, Layers & the Container Runtime

A container is an ordinary Linux process wrapped in namespaces and cgroups, started from an image, which is a stack of read-only filesystem layers.

§1A Container Is a Process

From the OS track: namespaces limit what a process can see (its own PID tree, network, mounts, hostname) and cgroups limit what it can use (CPU, memory). A container runtime sets those up, then starts your program inside them. There is no guest operating system: containers share the host kernel.

docker run -d --name demo nginx:1.27
docker top demo                          # the process as the container sees it
ps aux | grep "nginx: master"            # the same process, on the host
docker inspect -f '{{.State.Pid}}' demo  # its host PID
sudo ls -l /proc/$(docker inspect -f '{{.State.Pid}}' demo)/ns   # its namespaces

This shared kernel is why containers start in milliseconds and use little memory, and also why a container is not as strongly isolated as a virtual machine.

§2Images and Layers

An image is a packaged filesystem plus metadata (default command, environment, exposed ports). It is built from layers: each build step adds a read-only layer, identified by a content hash. A running container adds a thin writable layer on top using a union filesystem such as overlayfs.

docker pull python:3.12-slim
docker images                            # local images and sizes
docker history python:3.12-slim          # one row per layer
docker inspect python:3.12-slim | head -40
docker diff demo                         # files changed in the writable layer

Layers are shared. Fifty images built on the same base store that base once, and pulling a new version downloads only the layers you do not already have.

§3Image vs. Container

An image is a template, and a container is a running (or stopped) instance of it. You can start many containers from one image. When a container is removed, its writable layer, and any data written there, is deleted with it.

docker ps                                # running containers
docker ps -a                             # including stopped ones
docker stop demo && docker rm demo       # stop, then delete the container
docker rmi nginx:1.27                    # delete the image
docker system df                         # disk used by images and containers
The key insight There is nothing magic inside a container. If you can explain clone() with namespace flags and a cgroup directory, you can explain Docker. This is why debugging a container often means using ordinary Linux tools on the host.

§4Common Mistakes

MistakeWhat HappensFix
Thinking a container is a lightweight VMExpecting a separate kernel, or VM-level isolationRemember: same kernel, isolated via namespaces and cgroups
Storing data in the container's writable layerData is lost when the container is removedUse volumes for anything that must persist
Treating images like running machinesHand-edited containers cannot be reproducedRebuild the image from a Dockerfile instead
Practice
  1. Start a container and find its PID on the host, then list its namespace links under /proc/<pid>/ns.
  2. Run docker history on an image you use and identify which layer is the largest.
Key takeaways
  • A container is a normal process isolated by namespaces and limited by cgroups.
  • Images are stacked, shared, read-only layers; containers add a disposable writable layer.
  • Containers share the host kernel, which makes them fast and lighter than VMs but less isolated.
