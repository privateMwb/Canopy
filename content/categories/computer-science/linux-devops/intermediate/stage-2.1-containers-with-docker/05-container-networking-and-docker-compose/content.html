Container Networking & Docker Compose

Containers talk to each other over virtual networks and find each other by name, and Docker Compose describes a whole multi-container application in one file.

§1Container Networking

Each container gets its own network namespace. Docker connects them through a virtual bridge network. On a user-defined network, containers resolve one another by name through built-in DNS, so you never hard-code IP addresses.

docker network create appnet
docker run -d --name db --network appnet -e POSTGRES_PASSWORD=devonly postgres:16
docker run --rm --network appnet postgres:16 \
  psql -h db -U postgres -c "select 1"     # "db" resolves to the container
docker network inspect appnet

Inside a container, localhost means that container itself, not the host and not another container. This is the most common cause of "connection refused" between services.

§2Docker Compose

Compose defines services, networks, and volumes in a YAML file and manages them together. Compose creates a network for the project automatically, so each service name is a hostname.

# compose.yaml
services:
  web:
    build: .
    ports: ["8000:8000"]
    environment:
      DATABASE_URL: postgres://app:devonly@db:5432/app
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: devonly
      POSTGRES_DB: app
    volumes: ["pgdata:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      retries: 5
volumes:
  pgdata:
docker compose up -d --build     # build and start everything
docker compose ps
docker compose logs -f web
docker compose down              # stop and remove containers (volumes stay)
docker compose down -v           # ...and delete volumes too

§3Ordering and Health

depends_on by itself only controls start order, not readiness. A database container can be "started" long before it accepts connections. A healthcheck plus condition: service_healthy makes dependents wait until the service is actually ready.

docker compose exec db psql -U app -c "\dt"
docker compose run --rm web python manage.py migrate
docker compose config            # print the fully resolved file
Compose is for one host Compose is excellent for local development, test environments, and small single-server deployments. It does not spread services across machines or heal failed nodes, which is the gap orchestrators fill later in this track.

§4Common Mistakes

MistakeWhat HappensFix
Using localhost to reach another serviceConnection refused, because localhost is the container itselfUse the service name, such as db
Assuming depends_on waits for readinessThe app starts before the database can accept connectionsAdd a healthcheck and condition: service_healthy
Running compose down -v casuallyDeletes the volumes and all stored dataUse plain down, and add -v only when you mean it
Practice
  1. Write a Compose file for a web app and a database, and make the web service wait for a healthy database.
  2. Run docker compose down and up again and confirm data in the volume survives.
Key takeaways
  • User-defined networks give containers DNS names, so services reach each other by name.
  • localhost inside a container refers to that container alone.
  • Compose describes a multi-container app in one file, and healthchecks provide real readiness.
