Anatomy of a Pipeline

A pipeline is an automated sequence of steps that runs on every change, and CI and CD each make a different promise about what that change is ready for.

§1CI, Continuous Delivery, and Continuous Deployment

Continuous integration (CI) means every change is merged into the shared branch often and verified automatically by building and testing it. Continuous delivery means every change that passes is *always releasable*, with the release itself one button away. Continuous deployment goes further and releases every passing change to production automatically.

# the usual shape of a pipeline
#   push / pull request
#     -> lint         (seconds)
#     -> unit tests   (a minute or two)
#     -> build        (create the artifact: image, binary, package)
#     -> integration tests
#     -> publish      (registry, artifact store)
#     -> deploy       (staging, then production)

§2The Vocabulary

Every CI system uses the same ideas under different names. A trigger (push, pull request, schedule, manual) starts a pipeline or workflow. It contains stages or jobs, which run on runners (machines or containers) and are made of steps. Jobs can run in parallel or depend on one another, and they produce artifacts that later jobs consume.

# fast feedback first: cheap checks fail early, expensive ones wait
lint ──┐
       ├──> build ──> integration ──> publish ──> deploy
test ──┘

§3What Makes a Good Pipeline

Speed and trust matter most. If a pipeline takes an hour, people stop waiting for it, and if it fails randomly, they stop believing it. Aim for results within about ten minutes, run cheap checks first, and make every failure reproducible. The pipeline definition lives in the repository with the code, so changes to it are reviewed like any other.

# the pipeline should run the same commands you can run locally
make lint
make test
make build
# CI just calls these, so "works on my machine" and "works in CI" converge
Build once, promote the artifact Build the artifact a single time, then promote that exact artifact through test, staging, and production. Rebuilding for each environment means production runs something no test has ever seen.

§4Common Mistakes

MistakeWhat HappensFix
Putting all logic in the CI YAMLCannot be run or debugged locallyKeep logic in scripts or a Makefile, and have CI call them
Slow, flaky pipelinesDevelopers ignore or bypass the resultsParallelize, cache, and fix or quarantine flaky tests
Rebuilding per environmentThe thing tested is not the thing deployedBuild one artifact and promote it
Practice
  1. Draw the pipeline for a project you know: triggers, stages, and what each stage produces.
  2. Time each step of an existing build and identify the slowest one that could run in parallel.
Key takeaways
  • CI verifies every change, continuous delivery keeps it releasable, and continuous deployment ships it automatically.
  • Pipelines are triggers, jobs, steps, runners, and artifacts, regardless of the tool.
  • Keep pipelines fast and trustworthy, and build the artifact once.
