Configuration Management & Idempotency with Ansible

Configuration management describes what a machine should look like, and a good tool can be run repeatedly without causing harm, which is called idempotency.

§1Playbooks and Inventory

Ansible connects over SSH, so there is no agent to install. An inventory lists the hosts, and a playbook lists the tasks to run on them. Each task calls a module, such as apt, copy, template, or service.

# inventory.ini
[web]
web-01 ansible_host=203.0.113.10
web-02 ansible_host=203.0.113.11

# site.yml
- hosts: web
  become: true
  tasks:
    - name: Install nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true
    - name: Deploy site config
      ansible.builtin.template:
        src: shop.conf.j2
        dest: /etc/nginx/conf.d/shop.conf
        mode: "0644"
      notify: Reload nginx
    - name: Ensure nginx is running
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
  handlers:
    - name: Reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded

§2Idempotency

A task states a desired state (state: present), not an action. If the machine already matches, Ansible changes nothing and reports ok. If not, it fixes it and reports changed. Running a playbook twice should change nothing the second time. Handlers run only when something actually changed, so nginx reloads only when its config did.

ansible-playbook -i inventory.ini site.yml --check --diff   # dry run with diffs
ansible-playbook -i inventory.ini site.yml                  # apply
ansible-playbook -i inventory.ini site.yml                  # second run: changed=0

§3Avoid Shell Commands Where a Module Exists

command and shell modules are not idempotent by default, because Ansible cannot know whether they need to run. Prefer a real module. If you must use a command, tell Ansible when it is needed with creates, removes, or changed_when.

- name: Initialize the database once
  ansible.builtin.command: /opt/shop/bin/init-db
  args:
    creates: /var/lib/shop/.initialized    # skip if this file exists
- name: Check version (never counts as a change)
  ansible.builtin.command: nginx -v
  changed_when: false
Terraform and Ansible fit together Terraform creates the infrastructure (the VM, network, and disks), and Ansible configures what runs inside the machine. With containers, much of the second job moves into the image, but you still configure hosts.

§4Common Mistakes

MistakeWhat HappensFix
Using shell for everythingNot idempotent, so every run changes thingsUse modules, or add creates and changed_when
Never doing a dry runA playbook change surprises a production hostRun --check --diff first
Treating hosts as pets edited by handServers drift and cannot be rebuiltMake all changes via the playbook, and rebuild if in doubt
Practice
  1. Write a playbook that installs a package, deploys a templated config, and enables a service.
  2. Run it twice and confirm the second run reports changed=0.
Key takeaways
  • Ansible tasks declare a desired state, so playbooks can be run repeatedly.
  • Handlers run only when a change happened, such as reloading after a config update.
  • Prefer modules over raw commands, and always dry-run with --check --diff.
