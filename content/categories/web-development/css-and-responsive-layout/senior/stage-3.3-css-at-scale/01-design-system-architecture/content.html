Design System Architecture

A design system is layered: tokens at the bottom, primitives and components above them, patterns on top, with governance that keeps the layers honest.

§1The Layers

LayerContentsWho changes it
TokensColor, type, space, radius, motion, z-index valuesDesign system core team; rarely
Foundations / primitivesReset, typography, layout primitives (stack, cluster, grid, container)Core team
ComponentsButton, input, card, dialog, tabs, with variants and statesCore team and contributors
Patterns / templatesPage-level compositions built from componentsProduct teams
Product codeFeature-specific stylesProduct teams, constrained by the lower layers

Each layer depends only on the ones below it. A component uses tokens and primitives, and never reaches into product code.

§2Tokens, Primitives, and Component APIs

Layout primitives, tiny single-purpose layout components, replace one-off spacing rules and make pages composable.

/* layout primitive: vertical rhythm */
.stack { display: flex; flex-direction: column; gap: var(--stack-space, var(--space-m)); }

/* component with a small public styling API */
.button {
  --button-bg: var(--color-accent);
  --button-ink: var(--color-on-accent);
  background: var(--button-bg);
  color: var(--button-ink);
  padding: var(--space-xs) var(--space-m);
  border-radius: var(--radius-m);
}
.button[data-variant="secondary"] { --button-bg: transparent; --button-ink: var(--color-accent); }

The documented API of a component is its markup, its variants, and its exposed custom properties. Anything else is private and can change without a major version.

§3Governance

  • Contribution model: how teams propose, review, and add components, with a clear definition of done (accessibility, docs, tests, tokens).
  • Versioning and deprecation: semantic versions, changelogs, codemods, and a published deprecation window.
  • Documentation: usage guidance, do and don't, accessibility notes, and live examples for every component.
  • Quality gates: automated accessibility, visual regression, and lint checks in CI.
  • Adoption metrics: percent of UI using system components, and number of overrides and one-offs.

A design system succeeds when teams *choose* it because it is faster than building from scratch. If it is hard to adopt or slow to change, they will route around it.

A system is a product It has users (developers and designers), a roadmap, support, and metrics. Treat it like one, or it decays into an outdated pile of components.

§4Common Mistakes

MistakeWhat HappensFix
Building components before tokens and primitivesInconsistent values hard-coded everywhereEstablish tokens and layout primitives first
Allowing product code to override component internalsUpgrades break unpredictablyExpose a small API of custom properties and variants
No ownership or contribution modelThe system stagnates or fragmentsName owners, define how to contribute, and publish a roadmap
Practice
  1. Draw the layers of your team's current CSS and list where each rule actually lives.
  2. Define a button's public API: its variants, states, and custom properties, and write down what is private.
Key takeaways
  • Layer the system: tokens, primitives, components, patterns, product.
  • Expose a small, documented styling API per component.
  • Governance, documentation, and metrics keep the system used and healthy.
