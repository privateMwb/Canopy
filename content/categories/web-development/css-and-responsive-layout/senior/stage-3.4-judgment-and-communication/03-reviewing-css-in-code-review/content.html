Reviewing CSS in Code Review

Good CSS review looks for maintainability and user impact, not personal taste, and leaves style nitpicks to tools.

§1What to Look For

AreaQuestions to ask
Specificity and cascadeAny IDs, !important, or deep selectors? Does it fit the layer or architecture?
ReuseIs there an existing token, utility, or component that already does this?
ResponsivenessDoes it work at narrow widths and in a container, or is it viewport-specific?
AccessibilityFocus visible? Contrast? Targets? Reduced motion? Zoom and reflow?
RobustnessDoes it survive long text, missing images, RTL, and large fonts?
PerformanceAnimating layout properties? Large shadows or filters? Huge selectors?
ScopeCould this leak into other components? Is it deletable with the component?

Start from the behavior in the browser: check out the branch, resize the window, use the keyboard, and look at the screenshot diffs before reading the diff text.

§2What to Leave Alone

  • Formatting and naming style that a linter and formatter can enforce, so automate them (Prettier, Stylelint).
  • Property order debates; pick one tool setting and stop.
  • Personal preferences with no user or maintenance impact.
  • Rewrites out of scope: file a follow-up rather than blocking the change.

If a comment would be the same on every pull request, it belongs in a lint rule, not in a human review.

§3Writing Useful Comments

Be specific, explain the *why*, and offer a path forward. Distinguish blocking issues from suggestions.

blocking:   This hard-codes #15803d. We have --color-accent for this; using the token
            keeps dark mode working. Could you switch to var(--color-accent)?

suggestion: .card .title .link is 3 levels deep, so it will be hard to override. A
            single class (.card__link) would keep specificity flat. Non-blocking.

question:   Does this need to be viewport-based? If the card is used in the sidebar,
            a container query would adapt it to the slot. Worth a quick check?

praise:     Nice use of :focus-visible here; much cleaner than the old outline hack.

A short checklist in the pull request template keeps reviews consistent: responsiveness, accessibility, tokens, specificity, and screenshots attached.

Automate the boring parts Every minute a human spends on semicolons and spacing is a minute not spent on user impact. Lint and format automatically, and review for design and behavior.

§4Common Mistakes

MistakeWhat HappensFix
Reviewing only the diff and never running the codeVisual and responsive bugs slip throughCheck the preview, resize, and tab through it
Blocking on preferencesSlows the team and breeds resentmentReserve blocking for real issues; mark the rest as suggestions
Vague comments ("this is messy")The author can't act on itSay what's wrong, why, and what to do instead
Practice
  1. Review a real CSS pull request using the checklist, and label each comment as blocking, suggestion, or question.
  2. Convert three recurring review comments into Stylelint rules.
Key takeaways
  • Review for specificity, reuse, responsiveness, accessibility, robustness, and performance.
  • Automate style and formatting, and keep humans on impact.
  • Write specific, kind comments that distinguish blockers from suggestions.
