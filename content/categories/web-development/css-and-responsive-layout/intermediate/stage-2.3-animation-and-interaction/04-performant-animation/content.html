Performant Animation

Smooth animation depends on which properties you animate: transforms and opacity can run on the compositor, while layout and paint properties stall the main thread.

§1The Rendering Pipeline

Each frame can include style, layout, paint, and composite steps. The earlier the step a change forces, the more work follows it.

Property typeTriggersExamplesCost
LayoutLayout, paint, compositewidth, height, top, margin, font-sizeHigh
PaintPaint, compositecolor, background, box-shadow, border-radiusMedium
Composite onlyCompositetransform, opacity, (some) filterLow

To hit 60fps you have about 16ms per frame, and for a 120Hz display about 8ms. Compositor-only animations can run on the GPU even while JavaScript is busy.

§2Use transform and opacity

Replace layout-affecting animations with their transform equivalents.

/* slow: triggers layout every frame */
.slide { transition: left .3s; }
.slide.open { left: 0; }

/* fast: compositor only */
.slide { transform: translateX(-100%); transition: transform .3s; }
.slide.open { transform: translateX(0); }

/* shadows: animate the opacity of a pseudo-element instead of box-shadow */
.card::after { content: ""; box-shadow: 0 12px 24px rgb(0 0 0 / .2); opacity: 0; transition: opacity .2s; }
.card:hover::after { opacity: 1; }

§3will-change and Measuring

will-change hints that a property is about to change so the browser can prepare a layer. It consumes memory, so use it only on elements that genuinely animate, and remove it afterwards.

.menu-toggle:hover .menu { will-change: transform, opacity; }   /* just before it's needed */
  • Open DevTools Performance, record the interaction, and look for long frames and purple Layout or green Paint bars.
  • Enable Paint flashing and Layers in the Rendering panel to see what repaints.
  • Test on a mid-range phone, not only on a fast laptop.
  • Avoid reading layout values (like offsetHeight) between writes in a script; that forces synchronous layout.
Measure before optimizing If an animation looks smooth on your target devices and the trace is clean, it's fine. Don't sprinkle will-change everywhere hoping for a speedup; overuse makes things slower.

§4Common Mistakes

MistakeWhat HappensFix
Animating top, left, width, or heightLayout on every frame causes jankUse transform and opacity
Putting will-change on many elements permanentlyWastes memory and can slow renderingApply it briefly, to few elements
Animating box-shadow on large listsRepaints for every item each frameFade a pre-rendered pseudo-element
Practice
  1. Convert a left-based slide animation to transform, and compare Performance traces before and after.
  2. Turn on Paint flashing and find an animation that repaints more than it should.
Key takeaways
  • Animate transform and opacity to stay on the compositor.
  • Layout and paint properties are expensive in animation.
  • Use will-change sparingly and verify with the Performance panel.
