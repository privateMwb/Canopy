Built-in Validation

Browsers validate required, pattern, and range constraints for you; the Constraint Validation API lets you customize messages without rewriting the logic.

§1Declarative Constraints

Add attributes, and the browser blocks submission, focuses the first invalid field, and shows a message.

<form>
  <label for="user">Username</label>
  <input id="user" name="user" required
         minlength="3" maxlength="16"
         pattern="[a-z0-9_]+"
         title="Lowercase letters, numbers, and underscores only">

  <label for="age">Age</label>
  <input id="age" type="number" name="age" min="13" max="120">

  <button>Create account</button>
</form>

pattern is a regular expression matched against the whole value. The title text is often shown alongside the browser's error message.

§2Styling Valid and Invalid States

CSS pseudo-classes let you react to validity. :user-invalid applies only after a user has interacted, which avoids red fields on page load.

input:user-invalid { border-color: #b91c1c; }
input:user-valid   { border-color: #15803d; }
/* older option: input:invalid, but it fires immediately */

§3The Constraint Validation API

Each control exposes validity, checkValidity(), and setCustomValidity(). Use the last to supply your own message or to add rules that attributes can't express.

const pw = document.querySelector("#pw");
const again = document.querySelector("#confirm");

again.addEventListener("input", () => {
  again.setCustomValidity(
    again.value === pw.value ? "" : "Passwords must match"
  );
});

Pass an empty string to setCustomValidity to clear the error; otherwise the field stays invalid forever. Add novalidate to a form only if you take over validation completely.

Client-side validation is a convenience Anyone can bypass it. Always validate again on the server, which is the only check you can trust.

§4Common Mistakes

MistakeWhat HappensFix
Trusting browser validation for securityRequests can be sent without the form at allRe-validate every input on the server
Forgetting to reset setCustomValidity("")The field remains invalid after the fixClear it whenever the condition passes
Writing a pattern without a titleThe user sees a vague generic errorExplain the expected format in title or nearby text
Styling :invalid on page loadFields look wrong before anyone has typedUse :user-invalid or add classes after interaction
Practice
  1. Add required, length, and pattern constraints to a sign-up form and watch the built-in messages.
  2. Use setCustomValidity to require that a confirmation field matches a password.
Key takeaways
  • required, pattern, min, max, and minlength give validation with no script.
  • Use setCustomValidity to customize messages, and clear it when valid.
  • Always repeat validation on the server.
