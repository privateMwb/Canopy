Feature Support & Fallbacks

New HTML and CSS arrive faster than every browser ships them; checking support and degrading gracefully lets you use new features safely.

§1Checking Support

Before adopting a feature, check its browser support. MDN's compatibility tables and caniuse.com show support by browser and version. The Baseline label marks features that work across all major current browsers, which is a helpful rule of thumb.

  • Look up the feature on MDN and read the compatibility table.
  • Compare with your own analytics: which browsers do your users run?
  • Decide: use freely, use with a fallback, or wait.

§2Graceful Degradation in HTML

Many HTML features are designed to be ignored safely. Unknown elements render as inline content, unknown input types fall back to text, and unknown attributes are harmless.

<!-- unsupported type="date" becomes a text field -->
<input type="date" name="when" placeholder="YYYY-MM-DD" pattern="\d{4}-\d{2}-\d{2}">

<!-- picture falls back to img -->
<picture>
  <source type="image/avif" srcset="a.avif">
  <img src="a.jpg" alt="...">
</picture>

<!-- content between the tags is the fallback -->
<video src="a.mp4" controls><a href="a.mp4">Download</a></video>

§3@supports and Feature Queries

In CSS, @supports applies rules only where a feature exists. In JavaScript, test for the API before calling it.

.layout { display: block; }

@supports (display: grid) {
  .layout { display: grid; grid-template-columns: 1fr 2fr; }
}

if ("showPopover" in HTMLElement.prototype) {
  // use native popover
} else {
  // fall back to a simple visible panel
}

Fall back to something that works, not just something that looks acceptable. A page that is usable but plainer is a successful fallback.

Baseline is your friend A feature marked Baseline is available in the current stable versions of all major browsers. Features that aren't there yet usually deserve a fallback, or progressive enhancement.

§4Common Mistakes

MistakeWhat HappensFix
Choosing a feature because it works in your own browserSome users see it brokenCheck MDN and caniuse before adopting
Using user-agent sniffingBrittle and wrong over timeDetect the feature itself
Fallbacks that merely look OK but don't functionUsers can't complete tasksTest the fallback path in an older or constrained browser
Practice
  1. Pick a newer HTML or CSS feature, check its support, and write a fallback for browsers without it.
  2. Use @supports to enhance a layout, and confirm the baseline layout is usable on its own.
Key takeaways
  • Check support on MDN and caniuse; Baseline signals broad availability.
  • Prefer features that degrade safely, and detect features rather than browsers.
  • A fallback must work, not just look acceptable.
