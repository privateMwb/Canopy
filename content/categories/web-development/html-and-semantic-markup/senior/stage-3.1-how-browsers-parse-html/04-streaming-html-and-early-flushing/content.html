Streaming HTML & Early Flushing

Browsers parse HTML while it downloads, so sending the head and above-the-fold content early gets resources fetching and pixels painting sooner.

§1Parse While Downloading

HTTP responses arrive in chunks, and the parser consumes each chunk as it lands. A page can therefore start rendering before the response is complete. This works best if the server sends a response using chunked transfer encoding (HTTP/1.1) or HTTP/2 and HTTP/3 data frames, instead of building the entire page first.

HTTP/1.1 200 OK
Transfer-Encoding: chunked

<chunk 1>  <!DOCTYPE html><html><head> ... <link rel="stylesheet" ...>  </head>
<chunk 2>  <body><header>...</header><main> ... first screen ...
<chunk 3>  ... slow database content ...
<chunk N>  </main><footer>...</footer></body></html>

§2Flush the Head Early

If the server flushes the <head> before it runs slow work, such as a database query, the browser can discover stylesheets, fonts, and scripts, and start downloading them during the server's think time.

// pseudo-code for a server-rendered page
res.write(head());          // doctype, meta, CSS, preloads
res.flush();                // send now

const data = await slowQuery();
res.write(renderBody(data));
res.end();

Frameworks expose this as streaming SSR or out-of-order streaming. React's renderToPipeableStream, for example, sends the shell first and fills in slower parts later.

§3Pitfalls

  • Status codes — once you've flushed, the status and headers are sent. You can no longer switch to a 404 or redirect, so decide those first.
  • Buffering proxies and compression — an intermediary may hold chunks until it has enough bytes to compress or forward.
  • Errors mid-stream — you can't un-send HTML; plan for a graceful fallback or inline error state.
  • Layout stability — streamed content that arrives late must not shift what is already visible.

Put what matters first. Anything the user needs in the first screen, plus all critical <link> and <script> tags, should appear early in the stream.

Time to first byte isn't the goal Flushing early moves *useful* bytes forward. A streamed response that delivers the head in 50 ms and the body in 800 ms beats one that delivers everything at 700 ms.

§4Common Mistakes

MistakeWhat HappensFix
Waiting for all data before sending any HTMLBrowser sits idle during the server's workFlush the head, stream the shell

Not testing through the CDN or proxyBuffering undoes your streamingVerify chunk timing on the production path
Practice
  1. Write a small Node server that sends the head, waits one second, then sends the body, and watch the waterfall in DevTools.
  2. Check whether your CDN buffers streamed responses by measuring the time to first byte of each chunk.
Key takeaways
  • Browsers parse incrementally, so streaming gets resources downloading earlier.
  • Flush the head and critical resources before slow work.
  • Headers are committed on first flush, so settle status and redirects first.
