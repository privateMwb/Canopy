The Parsing Algorithm

HTML parsing is a precisely specified state machine in two stages, tokenization and tree construction, which is why invalid markup renders the same way in every browser.

§1Two Stages: Tokenizer and Tree Builder

The HTML spec defines parsing as an algorithm, not a grammar. Bytes are decoded into characters, the tokenizer turns characters into tokens (start tag, end tag, character, comment, doctype, end-of-file), and the tree constructor consumes tokens to build the DOM.

bytes → [decode] → characters → [tokenizer] → tokens → [tree builder] → DOM

<p class="a">Hi</p>
 tokens:  StartTag(p, class=a)  Char(H) Char(i)  EndTag(p)
 tree:    p[class=a] → "Hi"

The tokenizer is a state machine with states such as *data*, *tag open*, *attribute name*, and *RCDATA*. The tree builder has its own state called the insertion mode (initial, before html, in head, in body, in table, and so on) that decides how each token is handled.

§2Why Invalid HTML Still Works

Every possible token sequence has a defined result, so there are no "syntax errors" that halt parsing. Mistakes are *parse errors* that the spec says how to recover from.

<p>One
<p>Two          <!-- a new <p> implicitly closes the previous one -->

<b><i>text</b></i>   <!-- misnested: the adoption agency algorithm repairs it -->

<table><tr><td>cell</table>   <!-- missing end tags are implied -->

Tag omission is partly legal, too: </li>, </p>, </td>, and several others may be left out in valid HTML, because the parser will infer them. That is a rule of the grammar, not a mistake.

§3The Parser Can Pause and Re-enter

Parsing is incremental: the browser can build the DOM while bytes are still arriving. A synchronous <script> pauses the tree builder until it runs. Scripts may even write into the input stream with document.write(), which re-enters the tokenizer, and this is one reason it is discouraged.

  • Preload scanner — a lightweight, secondary scan that looks ahead for resources to fetch while the main parser is blocked.
  • Speculative parsing — lets browsers continue past blocking scripts and discard work if the script changes things.
  • Fragment parsing — the same algorithm used by innerHTML, with a context element to choose the initial insertion mode.
The spec is executable Browsers share one algorithm, so two engines given the same invalid input should build the same DOM. When a page parses "wrongly", the spec almost always explains exactly why.

§4Common Mistakes

MistakeWhat HappensFix
Assuming browsers reject malformed HTMLYou ship errors that silently get repaired and behave unexpectedlyValidate; treat repaired markup as a bug
Using regex to parse HTMLMisses the real parser's recovery rulesUse a spec-compliant parser such as DOMParser or an HTML5 parser library
Relying on implied tags without realizing itThe DOM differs from the source (for example, an inserted tbody)Inspect the DOM, not just the source
Practice
  1. Paste <table><tr><td>x</table> into DevTools by loading it in a page, and look at the DOM. Which elements did the parser add?
  2. Feed <b><i>text</b></i> to DOMParser and print body.innerHTML.
Key takeaways
  • Parsing = decode → tokenize → tree construction, with explicit state machines.
  • Every input has a defined result, so errors are repaired rather than rejected.
  • The preload scanner and speculative parsing keep downloads moving while the parser is blocked.
