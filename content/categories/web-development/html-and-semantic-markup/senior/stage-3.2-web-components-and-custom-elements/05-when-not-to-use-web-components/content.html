When Not to Use Web Components

Web components are a good fit in some places and the wrong tool in others; knowing the trade-offs against framework components keeps you from picking by fashion.

§1Where They Shine

  • Design-system primitives shared across teams using different frameworks.
  • Embeddable widgets dropped into pages you don't control.
  • Long-lived, framework-independent UI, such as a video player or rich editor.
  • Progressive enhancement of server-rendered markup with a few custom tags.

They are standardized, need no build step, and work with any framework or none.

§2Where They Struggle

ConcernWeb componentsFramework components
State and reactivityManual; bring your own (or Lit)Built in, ergonomic
Data flowAttributes are strings; objects need propertiesProps of any type
SSR and hydrationDeclarative Shadow DOM, still maturingFirst-class in major frameworks
Styling and themingShadow boundary requires deliberate hooksStraightforward, global or scoped
Forms and a11yExtra work (ElementInternals, ARIA refs)Native elements are used directly
EcosystemSmallerLarge: routers, data layers, devtools

For a data-heavy application with lots of shared state, a framework or a library on top of web components, such as Lit, is usually more productive than raw custom elements.

§3A Decision Checklist

  • Will multiple frameworks, or none, consume this? → web component.
  • Is it a page-level app with complex state and routing? → framework.
  • Does it need to render fully on the server for SEO and speed? → check SSR support first.
  • Can a native element do it? → use that, and skip both.
  • How big is the team and what does it already know? → favor consistency.

They're not mutually exclusive: most frameworks can render custom elements, and many design systems ship web components and wrap them for each framework.

Platform first The order of preference is usually: a native element, then a thin enhancement of it, then a custom element, then a full framework component. Each step adds cost and responsibility.

§4Common Mistakes

MistakeWhat HappensFix
Rebuilding native controls as custom elementsLose built-in accessibility and form behaviorUse <button>, <dialog>, and <details>
Choosing web components to avoid learning a frameworkYou reimplement reactivity badlyUse Lit or a framework for stateful UI
Passing complex data through attributesEverything gets stringifiedSet properties from JavaScript
Practice
  1. Write a one-page recommendation on whether a given component (say, a date picker) should be native, a web component, or a framework component.
  2. Take a component you know in a framework and list what would be hard to port to a custom element.
Key takeaways
  • Web components shine for cross-framework, embeddable, long-lived UI.
  • Frameworks win on state, SSR, and ecosystem for large applications.
  • Prefer native elements first, and choose by constraints, not trend.
