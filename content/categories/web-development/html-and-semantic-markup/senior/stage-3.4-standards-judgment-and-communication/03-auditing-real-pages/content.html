Auditing Real Pages

A good audit combines automated tools, manual testing, and evidence, so findings are reproducible and tied to real user impact.

§1Three Layers of Evidence

LayerFindsTools
AutomatedMissing alt, contrast failures, invalid ARIA, duplicate IDs, bad structureaxe DevTools, Lighthouse, Pa11y, the W3C validator
ManualKeyboard traps, focus order, meaningful alt text, reading order, errors that are unclearKeyboard only, zoom to 200–400%, forced colors, reduced motion
Assistive techHow it actually sounds and operatesNVDA, JAWS, VoiceOver, TalkBack, voice control

Automated tools catch only some problems, often the easier ones, so a page can score 100 and still be unusable. Treat the score as a floor.

§2A Practical Walkthrough

  1. Scope: choose key templates and user journeys (home, search, product, checkout), not every URL.
  2. Automated pass: run axe and Lighthouse and collect results with page and selector.
  3. Keyboard pass: Tab through. Can you reach and operate everything? Is focus always visible and in a logical order? Is there a skip link?
  4. Structure pass: check headings, landmarks, labels, and the accessibility tree in DevTools.
  5. Screen reader pass: complete the main task with NVDA or VoiceOver.
  6. Visual pass: 400% zoom, small viewport, high contrast, dark mode, reduced motion.
  7. Record: capture each issue with steps, evidence, and the criterion affected.

§3Writing Findings That Get Fixed

Each finding should be understandable and actionable by someone who wasn't there.

Title:     Search button has no accessible name
Page:      /search
Impact:    High — screen reader users hear only "button"; blocks core task
Evidence:  <button><svg>...</svg></button>   (screenshot + accessibility tree)
Criterion: WCAG 4.1.2 Name, Role, Value
Fix:       Add aria-label="Search" or visible text; hide the SVG with aria-hidden
Test:      Tab to button; screen reader announces "Search, button"

Rank by user impact (does it block a task, and for how many people), not by how easy it is to detect. Distinguish blockers from annoyances.

Impact over count Twenty minor contrast notes matter less than one checkout that keyboard users can't complete. Lead the report with what stops people.

§4Common Mistakes

MistakeWhat HappensFix
Reporting only the Lighthouse scoreMisses what tools can't detectCombine automated, manual, and assistive tech testing
Auditing every page instead of key journeysHuge report, little actionSample templates and critical flows
Findings with no steps to reproduce or fixThey sit unresolvedInclude evidence, criterion, and a concrete fix
Practice
  1. Audit one real page with axe, the keyboard, and a screen reader, and write up its three highest-impact findings in the format above.
  2. Compare your manual findings to the automated report and note which issues only manual testing found.
Key takeaways
  • Combine automated, manual, and assistive technology testing.
  • Audit key journeys and templates, and record reproducible evidence.
  • Prioritize findings by user impact, with a clear fix and test for each.
