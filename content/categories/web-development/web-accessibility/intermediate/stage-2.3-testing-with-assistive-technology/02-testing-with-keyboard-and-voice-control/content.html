Testing with Keyboard & Voice Control

Keyboard and voice testing need no special software and catch a huge share of real barriers. Both are repeatable if you turn them into short, written checks.

§1A Repeatable Keyboard Check

Keyboard testing is the fastest accessibility test there is. Put the mouse aside and run the same checklist on every page or component, so results are comparable over time.

  1. Reach. Press Tab from the top. Can you reach every interactive element, and nothing that is not interactive?
  2. See. Is a strong focus indicator visible at every stop, including at 200% zoom?
  3. Order. Does focus move in an order that matches the visual layout?
  4. Operate. Can you activate everything with Enter, Space, and arrow keys, as appropriate?
  5. Escape. Do dialogs, menus, and popups close with Escape, and does focus return where it started?
  6. No traps. Can you always move forward and back out, using only the keyboard?
  7. Shortcuts. If the page has single-key shortcuts, can they be turned off or remapped (WCAG 2.1.4)?

Write the result for each step as pass, fail, or not applicable, with a note. That small record is the difference between "I tried it" and a test.

§2Voice Control Testing

Voice control lets people operate a device by speaking. Built-in options include Voice Control on macOS and iOS, Voice Access on Windows 11 and Android, and commercial tools such as Dragon. Users speak what they see, so visible text must match accessible names.

CommandWhat it tests
"Click Save"Visible label contains the accessible name (WCAG 2.5.3)
"Show numbers"Every actionable item gets a number, so missing items are obvious
"Show names"Which names the tool has found for controls
"Scroll down", "Go back"Basic page operation
"Click" on an icon buttonWhether an icon button has any usable name
A failure you will meet often
<button aria-label="Submit form">Send</button>
Visible: "Send"  Accessible name: "Submit form"
A voice user says "Click Send" and nothing happens.

The fix: the accessible name starts with, or contains, the visible text

§3Putting It in a Test Plan

Turn these into a short script you can run on any feature. The same steps every time make regressions obvious.

Feature: Checkout address form
Browser: Firefox, Chrome   Input: keyboard, voice control

[ ] Tab reaches every field and button, in visual order
[ ] Focus indicator is visible on every control
[ ] Enter submits the form from any text field
[ ] Errors appear after submit and can be reached by keyboard
[ ] Escape closes the address suggestions list
[ ] Voice: "Click Postal code" focuses the field
[ ] Voice: "Click Place order" activates the button

Add devices to the matrix over time, such as a phone with a Bluetooth keyboard, but start with the cheapest ones. The keyboard and voice runs rarely take more than five minutes per component.

The key insight Keyboard testing is a necessary condition for almost everything else: switch devices, screen readers, and voice tools all depend on controls that can be reached and operated without a mouse.

§4Common Mistakes

MistakeWhat HappensFix
Testing with the keyboard once, informallyRegressions slip back in without anyone noticingUse a written checklist and record results
Visible labels that differ from accessible namesVoice users cannot activate the control by what they seeMake the accessible name contain the visible text
Ignoring Escape and focus returnOverlays trap or strand keyboard usersTest closing every dialog, menu, and popup
Practice
  1. Run the seven keyboard checks above on one component, and record pass, fail, or note for each.
  2. Turn on your operating system's voice control and try to operate three controls by saying their visible names. List any that fail and why.
Key takeaways
  • Use a written keyboard checklist covering reach, visibility, order, operation, Escape, traps, and shortcuts.
  • Voice control testing verifies that accessible names contain the visible labels.
  • Record results in a repeatable test plan so regressions are easy to spot.
