Automated Testing

Automation will never judge whether your page is usable, but it can reliably catch whole categories of mistakes, on every commit, for free. The trick is knowing where to put it.

§1Where Automated Checks Fit

Tools such as axe-core run a library of rules against the rendered page. They find missing labels, bad ARIA, low contrast, duplicate IDs, and similar problems consistently. They cannot judge alt text quality or focus order, so they complement manual testing, not replace it.

StageToolWhat it catches
While codingeslint-plugin-jsx-a11y, editor lintersInvalid markup patterns in source
In componentsStorybook a11y addon, jest-axeProblems in isolated components
In the browseraxe DevTools, Lighthouse, WAVEIssues on a running page
In CIaxe with Playwright or Cypress, pa11yRegressions on every pull request

§2Adding axe to End-to-End Tests

The most useful integration is a check inside the same end-to-end tests you already run. Because the page is in a real browser, it can also test states such as an open dialog or an error message.

import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('home page has no detectable WCAG A/AA violations', async ({ page }) => {
  await page.goto('/');
  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'])
    .analyze();
  expect(results.violations).toEqual([]);
});

test('checkout dialog is accessible when open', async ({ page }) => {
  await page.goto('/cart');
  await page.getByRole('button', { name: 'Checkout' }).click();
  const results = await new AxeBuilder({ page })
    .include('[role="dialog"]')
    .analyze();
  expect(results.violations).toEqual([]);
});

Testing states matters. A page can pass in its default state and fail when a menu is open, an error is shown, or a modal is up.

§3Making It Stick in CI

A few practices keep automated testing useful rather than noisy:

  • Fail the build on new violations. If the tool is advisory only, issues pile up.
  • Start with a baseline. For a legacy product with hundreds of issues, record the current set and block only new ones, then reduce the baseline over time.
  • Document exceptions. Every disabled rule needs a reason and an owner.
  • Cover the key journeys. Home, search, sign-in, checkout, and any complex component.
  • Keep tool versions pinned, and review upgrades, since new rules can fail old pages.
Lighthouse CI budget: fail if the accessibility score drops below 0.95
{
  "ci": {
    "assert": {
      "assertions": {
        "categories:accessibility": ["error", { "minScore": 0.95 }]
      }
    }
  }
}

Do not turn a score into a goal on its own. A tool can reach 100 on a page with a broken keyboard flow. Treat the score as a regression alarm.

The key insight Automation is a safety net that guards against regressions. It is good at the things that are easy to break and easy to detect, and it frees your manual time for the things only people can judge.

§4Common Mistakes

MistakeWhat HappensFix
Relying on automation aloneMost usability problems pass every automated ruleCombine automated checks with keyboard, screen reader, and user testing
Testing only the default state of a pageDialogs, errors, and menus ship with violationsRun checks on important states and interactions
Running a scan and ignoring the resultsViolations accumulate and the tool is switched offFail the build on new issues, and burn down a baseline
Practice
  1. Add axe to one existing end-to-end test. Run it, and fix or document each violation it reports.
  2. Choose three states in an app (such as a menu, a modal, an error message) and write an automated check for each.
Key takeaways
  • Automated tools find a defined set of problems quickly and consistently, but cannot judge usability.
  • Run axe in CI against key pages and states, and fail builds on new violations.
  • Use a baseline for legacy code, and treat the score as an alarm, not a goal.
