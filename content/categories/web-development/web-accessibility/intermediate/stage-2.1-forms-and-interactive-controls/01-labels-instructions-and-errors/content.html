Labels, Instructions & Errors

A form is a conversation. Labels say what is being asked, instructions explain how to answer, and errors explain what went wrong. Each has to be available to everyone, in text, and programmatically tied to its field.

§1Every Field Needs a Label

A label is the accessible name of a form control. Screen readers announce it when focus lands on the field, and voice control users say it to jump there. Clicking a properly linked label also focuses the field, which enlarges the target for everyone. WCAG covers this under 1.3.1, 3.3.2, and 4.1.2.

<!-- Explicit association: for matches id -->
<label for="email">Email address</label>
<input id="email" name="email" type="email">

<!-- Implicit association: wrap the control -->
<label>
  Email address
  <input name="email" type="email">
</label>

<!-- Bad: placeholder is not a label -->
<input type="email" placeholder="Email address">

Placeholder text disappears as soon as the user types, usually has weak contrast, and is not reliably exposed as a name. Use it, if at all, for a short example, never in place of a label.

§2Grouping and Instructions

Some questions need a shared prompt for several controls, such as a set of radio buttons. Group them with fieldset and name the group with legend, so each radio is announced with its question.

<fieldset>
  <legend>Preferred contact method</legend>
  <label><input type="radio" name="contact" value="email"> Email</label>
  <label><input type="radio" name="contact" value="phone"> Phone</label>
</fieldset>

<label for="pw">Password</label>
<input id="pw" type="password" aria-describedby="pw-hint" required>
<p id="pw-hint">At least 12 characters. Spaces are allowed.</p>

aria-describedby links extra help text to a field, so it is read after the label. Put format rules and requirements before the user types, not only in an error afterward.

§3Marking Required Fields

Tell users which fields are required, in text, and do not rely on color alone. A common convention is a visible note that states the rule once, plus a marker on each field.

<p>Fields marked <span aria-hidden="true">*</span> (required) must be completed.</p>

<label for="name">Full name <span aria-hidden="true">*</span></label>
<input id="name" required>

The required attribute exposes the requirement to assistive technology. Hiding the asterisk from screen readers avoids a redundant "star" announcement, since "required" is already spoken.

The key insight A visible label, programmatically connected, is the single most important form accessibility feature. If a field announces as "edit text" with no name, nothing else you do will make up for it.

§4Common Mistakes

MistakeWhat HappensFix
Using placeholder as the only labelThe name vanishes while typing and may not be announcedAdd a real label and keep placeholders optional
A label not linked to its inputThe screen reader announces an unnamed field, and clicking the label does nothingUse for and id, or wrap the control in the label
Radio groups with no fieldset and legendEach option is announced without its questionGroup related controls and name the group
Practice
  1. Open a signup form and inspect every field. Which have a real label? Which depend on placeholders or position only?
  2. Build a small form with a text field, a radio group, and a required field with a hint. Check that a screen reader announces the label, hint, and required state.
Key takeaways
  • Every control needs a visible, programmatically associated label. Placeholders are not labels.
  • Use fieldset and legend for groups, and aria-describedby for hints and format rules.
  • State requirements in text before the user types, and expose them with required.
