Documents & PDFs

Many organizations publish their most important content, such as forms, reports, and contracts, as downloadable files. WCAG applies to those just as it does to web pages, and a PDF is not accessible unless someone made it so.

§1Why Documents Fail

An accessible document has the same needs as an accessible page: structure, text alternatives, a logical reading order, and operable forms. A PDF made by "printing to PDF", or scanned from paper, usually has none of them. It is a picture of text, with no headings, no reading order, and nothing for a screen reader to read.

FeatureWhat it needs
TagsA tagged structure with headings, paragraphs, lists, tables, and links
Reading orderA logical order that matches the visual order
Text alternativesAlt text for meaningful images and charts
TablesHeader cells that are marked as headers
Language and titleA document language, and a title that is shown in the title bar
FormsLabeled, keyboard-operable fields with a sensible tab order

The relevant file-format standard is PDF/UA (ISO 14289), and WCAG techniques exist for PDF.

§2Build Accessibility In at the Source

The best way to produce an accessible PDF is to start from an accessible source document and export it properly. Fixing a bad PDF afterward is slow and fragile.

  • Use real heading styles (Heading 1, 2, 3), not bold text of a larger size.
  • Use real lists and table header rows. Avoid blank paragraphs and tabs for spacing.
  • Add alt text to images and charts, and mark decorative ones.
  • Write meaningful link text, not "click here" or bare URLs.
  • Set the document language and title.
  • Export with tags. In Word and similar tools, keep "Document structure tags for accessibility" enabled when saving as PDF.

For scanned documents, run OCR first to turn the image into real text, then add tags and check the result.

§3Checking and Choosing a Format

Check documents with more than one method, as you would a web page.

A quick command-line check that a PDF has tags and a title
pdfinfo report.pdf
  Title:     Annual Report 2025
  Tagged:    yes
  1. Run an automated checker, such as the Accessibility Checker in Adobe Acrobat, or the free PDF Accessibility Checker (PAC).
  2. Open the file in a screen reader, and navigate by headings. Listen to the order.
  3. Check tab order and labels on any form fields.

Finally, ask whether the content should be a PDF at all. For most reading content, an HTML page is easier to make accessible, adapts to the reader's device and settings, and is simpler to maintain. Keep PDFs for cases that truly need a fixed layout, and say what you are linking to.

<a href="/reports/annual-2025.pdf">Annual report 2025 (PDF, 2.4 MB)</a>
<p>Also available as <a href="/reports/annual-2025">a web page</a>.</p>
The key insight Accessibility belongs at the source. Start from a well-structured document, export with tags, and check the result. Retrofitting a finished PDF costs far more and works less well.

§4Common Mistakes

MistakeWhat HappensFix
"Printing" a document to PDFProduces an untagged file with no headings or reading orderExport with tags from the source application
Publishing scanned images of textScreen readers see nothing to readRun OCR, then tag and check the document, or provide an HTML version
Linking to a PDF with no warning or alternativeUsers are surprised, and PDF-hostile setups are blockedState the format and size, and offer HTML where practical
Practice
  1. Create a short Word document with headings, a list, and an image with alt text. Export it to PDF with tags, then check it with Acrobat's checker or PAC.
  2. Take a PDF from a public website and open it in a screen reader. Write down three things that make it hard to use.
Key takeaways
  • PDFs need tags, reading order, alt text, table headers, a language, and a title to be accessible.
  • Start with an accessible source and export with tags. Scanned documents need OCR.
  • Prefer HTML for reading content, and label PDF links with the format and size.
