Your First Accessibility Audit

An audit is a structured look for barriers. You will start with an automated checker, learn exactly what it can and cannot find, and then add a few quick manual checks that catch the rest.

§1Start With an Automated Checker

Automated tools scan the page's code and rules and report likely failures. They are fast, free, and consistent. Good starting points are axe DevTools, Lighthouse (built into Chrome DevTools), and WAVE.

Lighthouse from the command line, accessibility category only
npx lighthouse https://example.com --only-categories=accessibility --view

axe command-line scan
npx @axe-core/cli https://example.com

Each result lists the element, the rule that failed, and a suggested fix. Typical findings include missing alt text, form fields with no label, low contrast, empty links or buttons, and missing document language.

§2What Automation Cannot See

Tools can only test what a computer can judge. They can tell whether an alt attribute exists, but not whether the text is meaningful. Depending on how issues are counted, automated checks typically find only a portion of real problems, often cited as somewhere between a third and a half.

Tools are good atTools cannot judge
Missing alt, labels, or page languageWhether alt text is accurate and useful
Most color contrast failuresWhether the focus order makes sense
Invalid ARIA attributesWhether a custom widget is actually operable
Duplicate IDs and empty buttonsWhether instructions and errors are understandable

This is why a score of 100 does not mean a page is accessible. It means the tool found nothing it knows how to find.

§3Five Quick Manual Checks

Add a few minutes of manual testing to every audit. These catch the most common issues tools miss:

  1. Keyboard only. Put the mouse aside. Use Tab, Shift+Tab, Enter, Space, and Escape to complete the main task. Can you reach everything, and can you always see where focus is?
  2. Zoom to 200%. Zoom the browser. Does content stay readable without losing information or scrolling in two directions?
  3. Headings and landmarks. List the headings (a browser extension or a screen reader can do this). Do they outline the page sensibly?
  4. Images and links. Do images carry meaningful text alternatives? Do link and button names make sense out of context?
  5. Screen reader skim. Listen to the first screen of the page with NVDA or VoiceOver. Does it make sense without looking?
Record each finding so others can act on it
Issue:    Search button has no accessible name
Where:    Header, magnifier icon
WCAG:     4.1.2 Name, Role, Value (Level A)
Impact:   Screen reader says "button" with no purpose
Fix:      Add aria-label="Search" or visible text
The key insight Treat automated results as a list of things to fix, not as a verdict. The most important findings usually come from the manual steps, because they reveal how the page actually feels to use.

§4Common Mistakes

MistakeWhat HappensFix
Reporting only the tool scoreBarriers that tools cannot detect stay hidden behind a high numberAlways add manual keyboard, zoom, and screen reader checks
Running a scan once and moving onNew code reintroduces old problemsRe-test after changes and automate checks over time
Reporting issues without contextDevelopers cannot reproduce or prioritize themRecord the element, the criterion, the impact, and a suggested fix
Practice
  1. Run Lighthouse or axe on any public page. Pick the three most serious findings and write each as an issue with location, criterion, impact, and fix.
  2. Do the five manual checks on the same page, and list at least one problem the automated tool did not report.
Key takeaways
  • Automated checkers are fast and consistent but find only a portion of real accessibility problems.
  • Manual checks (keyboard, zoom, headings, names, and a screen reader skim) find what tools cannot.
  • Write findings with location, criterion, impact, and fix so they can actually be fixed.
