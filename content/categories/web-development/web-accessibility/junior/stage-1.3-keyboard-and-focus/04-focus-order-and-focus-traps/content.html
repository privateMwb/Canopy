Focus Order & Focus Traps

Focus should move through a page in an order that makes sense, and users should always be able to leave wherever they land. Two criteria cover this: a logical order, and no traps.

§1A Logical Focus Order

WCAG Success Criterion 2.4.3 (Level A) says focus order must preserve meaning and operability. In practice, focus should follow the visual reading order: usually top to bottom, left to right in left-to-right languages, and group by group within a form.

The focus order comes from the DOM, so most problems trace back to source order or to CSS that repositions elements visually. Also, focus must never trigger an unexpected change of context. Success Criterion 3.2.1 (Level A) forbids things like a form submitting or a page navigating just because a field received focus.

<!-- Bad: a positive tabindex jumps the queue -->
<input tabindex="3" ...>
<input tabindex="1" ...>
<input tabindex="2" ...>

<!-- Good: DOM order matches the visual order, no tabindex needed -->
<input id="first"  ...>
<input id="second" ...>
<input id="third"  ...>

§2Keyboard Traps

A keyboard trap is a place where focus goes in and cannot get out using the keyboard. Success Criterion 2.1.2 (Level A) forbids them. Traps are most often caused by embedded widgets, third-party scripts, and badly built custom dialogs.

A related and legitimate pattern is a modal dialog, which intentionally holds focus inside while it is open, as long as the user can leave it with a standard key. Escape must close it, and focus must return to the element that opened it.

<button id="open">Open settings</button>

<dialog id="settings">
  <h2>Settings</h2>
  ...
  <button id="close">Close</button>
</dialog>

<script>
  const dlg = document.getElementById('settings');
  document.getElementById('open').addEventListener('click', () => dlg.showModal());
  document.getElementById('close').addEventListener('click', () => dlg.close());
  // showModal() makes the rest of the page inert, traps Tab inside,
  // closes on Escape, and returns focus to the opener.
</script>

§3Managing Focus Deliberately

Sometimes you need to move focus yourself, for example after opening a dialog, deleting an item, or showing an error summary. Follow a simple rule: move focus when the context changes, and put it somewhere the user can make sense of.

// After an inline validation error summary appears
const summary = document.getElementById('error-summary');
summary.setAttribute('tabindex', '-1');
summary.focus();

// After a user deletes a list item, send focus somewhere logical
nextItem ? nextItem.focus() : list.focus();

Do not move focus without a reason. Unexpected focus jumps are disorienting, and losing focus entirely (it falls back to the top of the page) forces a user to tab back to where they were.

The key insight Prefer the native dialog element with showModal() over hand-built focus trapping. It handles Tab containment, Escape, the inert background, and returning focus for you.

§4Common Mistakes

MistakeWhat HappensFix
Using positive tabindex to fix orderA fragile order that breaks as content changesReorder the DOM so source order matches the visual order
A modal that cannot be closed with EscapeKeyboard users are trapped insideSupport Escape, a visible close button, and return focus to the opener
Losing focus after removing an elementFocus drops to the top of the pageMove focus to a logical next target
Practice
  1. Tab through a form or card layout and compare the focus path to the visual order. List any place the two disagree and what causes it.
  2. Build a simple dialog with the dialog element. Verify that Escape closes it and that focus returns to the opening button.
Key takeaways
  • Focus order should follow a logical reading order (WCAG 2.4.3), and focus must not trigger a change of context (3.2.1).
  • Keyboard traps are forbidden (2.1.2). Intentional modal traps need Escape and restore focus when closed.
  • The native dialog element with showModal() handles most dialog focus behavior for you.
