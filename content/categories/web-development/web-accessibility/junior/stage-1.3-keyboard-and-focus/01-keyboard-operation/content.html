Keyboard Operation

Many people never touch a mouse: screen reader users, people with motor impairments, and plenty of power users. If something works only with a pointer, it does not work for them at all.

§1The Keys That Matter

Keyboard users move through a page with a small, standard set of keys. Your job is to make every interactive thing respond the way those keys are expected to behave.

KeyWhat it does
Tab / Shift+TabMove focus to the next or previous interactive element
EnterActivate links and buttons, submit forms
SpaceActivate buttons, toggle checkboxes, scroll the page
Arrow keysMove within a group, such as radio buttons, tabs, or menu items
EscapeClose dialogs, menus, and popups

WCAG Success Criterion 2.1.1 (Level A) requires that all functionality be operable through a keyboard. That includes hover menus, drag interactions, and custom controls, not just links and form fields.

§2What Is Focusable by Default

Native interactive elements are keyboard-ready without any extra work. They receive focus in Tab order and respond to the right keys.

  • Focusable by default: a href, button, input, select, textarea, and summary.
  • Not focusable: div, span, and a link with no href.

This is the best argument for native elements. A real button gives you focus, Enter, Space, and the right role in a single tag. Reproducing that on a div takes a lot of code and is easy to get wrong.

<!-- Native: works with Enter and Space automatically -->
<button type="button" onclick="save()">Save</button>

<!-- Bad: the mouse works, the keyboard does not -->
<div onclick="save()">Save</div>

§3Using tabindex Carefully

The tabindex attribute controls whether and how an element can take focus. Only three values are worth using.

ValueEffectUse it for
tabindex="0"Adds the element to the normal Tab orderCustom widgets that truly cannot be native elements
tabindex="-1"Focusable with script, but skipped by TabMoving focus to a heading, dialog, or error summary
tabindex="1" and other positive valuesForces a custom order, ahead of everything elseAvoid. It becomes unmaintainable and confusing
<!-- If you truly must build a custom control, add role, focus, AND keys -->
<div role="button" tabindex="0" id="custom">Save</div>

<script>
  const el = document.getElementById('custom');
  el.addEventListener('click', save);
  el.addEventListener('keydown', (e) => {
    if (e.key === 'Enter' || e.key === ' ') {
      e.preventDefault();
      save();
    }
  });
</script>

Look at how much code the custom version needs, and it still lacks the finer behavior of a real button. Reach for native elements first.

How to test Unplug your mouse mentally. Press Tab from the top of the page and try to complete the main task: reach every control, activate it, and leave again. Anything you cannot reach or operate is a barrier.

§4Common Mistakes

MistakeWhat HappensFix
Click handlers on div or span elementsNot focusable and no keyboard activationUse button or a href, or add role, tabindex="0", and key handlers
Functionality only on hoverKeyboard and touch users never trigger itAlso trigger it on focus and click, and keep content reachable
Positive tabindex valuesUnpredictable focus order that breaks when content changesUse tabindex="0" or -1, and fix the DOM order instead
Practice
  1. Pick one page and complete its main task using only Tab, Shift+Tab, Enter, Space, and Escape. Note every element you could not reach or operate.
  2. Search a codebase (or a site's source) for onclick on a div or span. Rewrite one as a proper button.
Key takeaways
  • All functionality must work with a keyboard (WCAG 2.1.1), using standard keys.
  • Native elements are focusable and keyboard-ready. Generic elements are neither.
  • Use tabindex="0" or -1 only when needed, and avoid positive values.
