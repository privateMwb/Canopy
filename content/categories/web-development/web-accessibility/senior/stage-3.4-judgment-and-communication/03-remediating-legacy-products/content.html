Remediating Legacy Products

You will rarely build accessibility into a clean slate. More often you inherit a product with years of debt, and the work is to improve it steadily without stopping everything else.

§1Start With a Map

A legacy remediation fails when it tries to fix everything at once. Begin by understanding what you have and what matters most.

  1. Inventory: list the main templates, key journeys, and shared components. Most issues cluster in a small number of these.
  2. Baseline audit: test the core journeys and templates against your target standard, using automated, keyboard, and screen reader checks.
  3. Prioritize: rank findings by user impact, reach, and journey criticality, as in the previous lesson.
  4. Plan in phases: group fixes into releases with owners and dates.

Fixing a shared component or template once repairs every page that uses it, so aim your first effort at shared code, not individual pages.

§2Stop Adding New Debt

Remediating while new inaccessible features ship is running up a down escalator. The most important rule is: new work must meet the standard. Add accessibility to the definition of done for anything new or changed, and let old areas improve as they are touched.

Use a ratchet in continuous integration. Record the current set of automated violations as a baseline, then fail the build only when violations increase. Over time, lower the baseline.

scripts/a11y-ratchet.js
const fs = require('fs');
const baseline = JSON.parse(fs.readFileSync('a11y-baseline.json', 'utf8'));   // { "label": 12, "color-contrast": 40 }
const current  = JSON.parse(fs.readFileSync('a11y-current.json', 'utf8'));    // from the latest axe run

let regressed = false;
for (const [rule, count] of Object.entries(current)) {
  const allowed = baseline[rule] || 0;
  if (count > allowed) {
    console.error(rule + ': ' + count + ' (baseline ' + allowed + ')');
    regressed = true;
  }
}
if (regressed) process.exit(1);
console.log('No new accessibility regressions.');

§3Quick Wins and Big Rocks

Sort the work by effort. Quick wins build momentum, and big rocks need planning.

Quick wins (days)Big rocks (weeks or months)
Add missing labels and alt textReplace a custom widget library with accessible components
Fix color tokens that fail contrastRebuild a complex custom grid or editor
Restore visible focus stylesRestructure navigation and page templates
Add a skip link and landmarksRework a multi-step form flow
Set lang and page titlesMake video and document libraries accessible

For big rocks, use a strangler approach. Build the new accessible component alongside the old one, switch over page by page, and retire the old one. This is safer than a rewrite, and delivers value along the way.

Throughout, be open about progress. Publish an accessibility statement that lists known issues and a roadmap. It sets honest expectations, shows good faith, and gives users a place to report problems you have not yet found.

The key insight Legacy remediation is a long game. The sequence that works is: map, stop the bleeding, fix shared code, fix the core journeys, and keep ratcheting. Perfection is not the first milestone. Steady improvement is.

§4Common Mistakes

MistakeWhat HappensFix
Fixing page by page across the whole siteEndless work, and shared components keep reintroducing bugsFix shared components and templates first
Remediating while new inaccessible code shipsDebt grows as fast as you pay it downRequire new work to meet the standard, and use a CI ratchet
Planning a big-bang rewriteRisky, slow, and delivers nothing for monthsUse the strangler pattern, replacing one piece at a time
Practice
  1. Pick a legacy page and list the shared components and templates behind it. Which three would give the biggest accessibility improvement if fixed?
  2. Draft a six-month remediation roadmap for a product: what happens in the first sprint, the first quarter, and the first six months?
Key takeaways
  • Map the product, audit core journeys, prioritize, and fix shared components and templates first.
  • Stop new debt with a definition of done and a CI ratchet that blocks regressions.
  • Mix quick wins with phased big-rock replacement, and communicate openly with a statement and a roadmap.
