Metrics & Continuous Monitoring

What you measure shapes what teams do. Good accessibility metrics show real progress and trigger action. Poor ones reward gaming, and give leaders false comfort.

§1What to Measure

No single number captures accessibility. A small set of metrics covering process, product, and people gives a more honest picture than any one score.

TypeExample metrics
Process (leading)Share of stories with accessibility criteria, share of PRs with an accessibility check, training completion, components with automated tests
Product (lagging)Open accessibility defects by severity, time to fix, pass rate on core journeys in the latest audit, automated violations per page
PeopleReports from users, response time, and task success with assistive technology users in testing

Leading metrics tell you whether the habits are in place. Lagging metrics tell you whether the product is improving. You need both.

§2Avoiding Goodhart's Law

When a measure becomes a target, it stops being a good measure. This is especially true for automated scores, which are easy to inflate without helping users.

  • Do not use a Lighthouse or axe score as the only goal. A page can score 100 and still fail a keyboard user.
  • Measure severity-weighted defects, so ten cosmetic issues do not outweigh one blocker.
  • Prefer outcomes such as the share of core journeys that complete with a screen reader, over counts of tests run.
  • Pair numbers with stories from user feedback and audits, so leaders see what the numbers mean.
  • Look at trends, not single points. A rising count may mean you are finding more, not doing worse.

§3Continuous Monitoring

Products change constantly, so monitor continuously. Scheduled automated scans are cheap, and catch regressions and new content problems between audits.

.pa11yci.json: scan key pages on a schedule or in CI
{
  "defaults": { "standard": "WCAG2AA", "timeout": 30000 },
  "urls": [
    "https://example.com/",
    "https://example.com/search",
    "https://example.com/checkout"
  ]
}

Run it
npx pa11y-ci
  1. Automated scans on core pages and templates, with trends over time.
  2. Regular manual audits of a rotating sample, since tools find only a portion of issues.
  3. Component-level monitoring in the design system.
  4. Feedback channel metrics: volume, topics, and time to resolve.
  5. A simple dashboard with a handful of numbers, reviewed on a fixed schedule.

For leaders, report on few things: trend in serious defects on core journeys, time to remediate, and adoption of the practices. Tie each to a decision, such as where to invest next.

The key insight A metric is only useful if someone will act on it. If a number goes up or down and nothing changes, remove it, and measure something that drives a decision.

§4Common Mistakes

MistakeWhat HappensFix
Making the automated score the goalTeams chase the number, and real barriers stayUse severity-weighted defects and journey-level outcomes
Tracking only lagging metricsYou learn about problems after they shipAdd process metrics such as checks in PRs and training
A dashboard nobody reviewsNumbers drift and no decisions followReview on a schedule, and link each metric to an action
Practice
  1. Choose five metrics for an accessibility program, split across process, product, and people. For each, name the decision it informs.
  2. Set up pa11y-ci or a similar tool on three key pages, and record the baseline violation count.
Key takeaways
  • Use a small mix of process, product, and people metrics instead of a single score.
  • Weight by severity, favor outcomes over activity, and watch for gaming.
  • Monitor continuously with scheduled scans plus sampled manual audits, and tie every metric to a decision.
