Design System Governance

A design system that was accessible at launch will not stay that way by itself. Governance is the set of rules, reviews, and tests that keep shared components accessible as they change, grow, and are adopted by new teams.

§1Accessibility as an Entry Requirement

Decide what a component must prove before it enters the system, and write that down as a gate. This avoids the common situation where an inaccessible component is shipped first and "fixed later".

GateWhat a new component must show
SemanticsNative elements where possible, and ARIA that follows the Authoring Practices Guide
Keyboard modelDocumented keys, tested with a keyboard
Screen reader behaviorName, role, state, and announcements verified with at least two screen reader and browser pairs
VisualContrast, focus indicator, target size, zoom, and forced colors checked
Automated testsaxe checks for each state and variant
DocumentationUsage rules, do and don't examples, and accessibility notes

§2Tokens, Versions, and Change

Governance also covers the values the system provides. Color tokens are a good example: you can enforce contrast at build time, so an inaccessible pairing never reaches a product.

scripts/check-contrast.js: fail the build if a token pair is below its threshold
const lum = (hex) => {
  const [r, g, b] = [1, 3, 5]
    .map((i) => parseInt(hex.slice(i, i + 2), 16) / 255)
    .map((c) => (c <= 0.03928 ? c / 12.92 : Math.pow((c + 0.055) / 1.055, 2.4)));
  return 0.2126 * r + 0.7152 * g + 0.0722 * b;
};
const ratio = (a, b) => {
  const [hi, lo] = [lum(a), lum(b)].sort((x, y) => y - x);
  return (hi + 0.05) / (lo + 0.05);
};

const tokens = { text: '#1C1F26', muted: '#595959', bg: '#FFFFFF', link: '#1D4ED8' };
const pairs = [['text', 'bg', 4.5], ['muted', 'bg', 4.5], ['link', 'bg', 4.5]];

let failed = false;
for (const [fg, bgName, min] of pairs) {
  const r = ratio(tokens[fg], tokens[bgName]);
  if (r < min) { console.error(fg + ' on ' + bgName + ' is ' + r.toFixed(2)); failed = true; }
}
process.exit(failed ? 1 : 0);
  • Versioning: decide how accessibility changes are released. A fix that changes visible markup or keyboard behavior can break product tests, so communicate it in the changelog and use semantic versioning honestly.
  • Deprecation: retire inaccessible components on a published timeline, and provide a migration path.
  • Regression testing: run accessibility tests across all components on every change, including visual checks in dark mode and forced colors.

§3Contributions, Exceptions, and Community

A system is used and changed by many teams, so set rules for how they take part.

  1. Contribution model: teams may propose components, and the system team reviews them against the accessibility gate.
  2. Exception process: when a team needs to deviate, require a written rationale, an owner, a mitigation, and an expiry date, so exceptions do not become permanent.
  3. Audits: audit the system with assistive technology on a regular schedule, and publish the results.
  4. Community of practice: a channel and regular session where teams share patterns and questions.

Finally, make adoption measurable. Know which products use which component versions, because an accessibility fix helps no one until teams upgrade.

The key insight Governance is what makes accessibility survive success. A system's popularity multiplies both good fixes and new bugs, so the review gates, tests, and upgrade paths matter as much as the components.

§4Common Mistakes

MistakeWhat HappensFix
Accepting components that are "accessible later"Inaccessible patterns spread to every adopterRequire accessibility evidence before a component ships
Allowing permanent exceptionsTemporary deviations become the new normalRequire owners and expiry dates, and review them regularly
Fixing the system but not tracking upgradesProducts keep running old, inaccessible versionsTrack versions in use, and support migration
Practice
  1. Write the accessibility gate for adding one new component to a system, with at least six checks.
  2. Run the contrast script above against your own tokens, and note any pair that fails.
Key takeaways
  • Set an accessibility gate for every new component: semantics, keyboard, screen reader behavior, visuals, tests, and documentation.
  • Enforce what you can automatically, such as token contrast at build time, and version and deprecate changes responsibly.
  • Manage exceptions with owners and expiry dates, audit regularly, and track adoption of fixes.
