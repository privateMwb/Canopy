Accessibility in Canvas, WebGL & Games

A canvas is a bitmap. To the browser it has no headings, buttons, or text, only pixels. Anything interactive drawn on one has to be made available through a second, parallel layer.

§1The Canvas Problem

When you draw text, shapes, or a whole interface onto a canvas or WebGL surface, the accessibility tree sees a single graphic. Screen readers, voice control, find-in-page, and translation all fail, and keyboard users cannot reach anything you drew.

The general solution is a parallel accessible layer: real DOM elements that mirror what is meaningful on the canvas, with correct roles, names, states, and keyboard behavior. The canvas becomes the visual presentation, and the DOM carries the meaning.

SituationApproach
Decorative or purely visual canvasHide it from assistive technology, or give it role="img" with a short label
Static chart or diagramrole="img" with a label, plus a text summary or data table nearby
Interactive canvas (editor, map, game UI)Overlay or mirror real, focusable DOM controls, and keep them in sync

§2Building the Parallel Layer

Content placed inside the canvas element is a fallback, and it can include focusable elements. Many projects instead position a visually hidden or overlaid set of real controls next to the canvas.

<div class="stage">
  <canvas id="board" width="480" height="480" aria-hidden="true"></canvas>

  <!-- Accessible layer: real buttons mirror the playable squares -->
  <div role="group" aria-label="Game board" class="a11y-layer">
    <button data-cell="0,0" aria-label="Row 1, column 1, empty"></button>
    <button data-cell="0,1" aria-label="Row 1, column 2, X"></button>
    ...
  </div>
  <p role="status" id="game-status"></p>
</div>

<script>
  function placeMark(r, c, mark) {
    drawMark(r, c, mark);                       // update the canvas visuals
    const btn = document.querySelector('[data-cell="' + r + ',' + c + '"]');
    btn.setAttribute('aria-label', 'Row ' + (r + 1) + ', column ' + (c + 1) + ', ' + mark);
    document.getElementById('game-status').textContent = mark + ' placed at row ' + (r + 1);
  }
</script>

Draw a clear focus indicator on the canvas as well, so that sighted keyboard users can see which item is active. Libraries that render to canvas or WebGL (game engines, mapping libraries, charting tools) often have partial support, so check their documentation and test early rather than at the end.

§3Games and Rich Interactive Experiences

Games add challenges beyond the DOM: real-time input, timing, and visual communication. The Game Accessibility Guidelines and platform standards offer practical guidance. Common principles:

  • Remappable controls, and alternatives to rapid or simultaneous inputs, including one-handed play.
  • Adjustable difficulty and timing, with options to pause, slow, or skip timed challenges.
  • Captions and subtitles, with speaker names and sound cues, and a resizable, high-contrast style.
  • Do not rely on color alone for team, danger, or status. Add shapes, labels, or audio.
  • Audio cues with visual equivalents, and the reverse.
  • Motion and flashing controls, including reduced motion and photosensitivity warnings.

Not every game can be made fully accessible to every player, but most can offer far more choice than they do. Treat options as a core feature rather than a late addition, and involve disabled players in playtesting.

The key insight If meaning lives only in pixels, assistive technology cannot reach it. Keep the semantics in the DOM, and treat the canvas as a rendering layer.

§4Common Mistakes

MistakeWhat HappensFix
Drawing an interactive UI on a canvas with no DOM equivalentKeyboard, screen reader, and voice users cannot operate or perceive itAdd a parallel DOM layer with real controls
Leaving a canvas unlabeledScreen readers say "canvas" or skip it, with no idea of its purposeLabel it, or hide it if decorative, and add a text summary
Treating game accessibility as optional polishExcludes players, and is costly to retrofitPlan remapping, timing, captions, and color alternatives from the start
Practice
  1. Take a canvas drawing or chart you have made and add a text summary and a labeled alternative. Test with a screen reader.
  2. List five accessibility options a game you play could add. Rank them by the number of players they would help.
Key takeaways
  • Canvas and WebGL content is invisible to assistive technology, so mirror what matters in real DOM elements.
  • Label static canvases, and build a parallel accessible layer for interactive ones, with a visible focus indicator.
  • For games, offer remapping, timing, captions, and non-color cues, and plan them from the start.
