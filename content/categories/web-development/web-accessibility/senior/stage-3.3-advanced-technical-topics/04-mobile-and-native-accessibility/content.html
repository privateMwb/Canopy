Mobile & Native Accessibility

Most of the principles carry over, but the APIs change. Native apps use the platform's own accessibility framework instead of HTML and ARIA, and the same WCAG ideas apply with different attributes.

§1The Same Ideas, Different Names

WCAG is written for web content, but its principles apply to apps, and standards such as EN 301 549 cover native software. In practice you ask the same questions: does every control have a name, a role, a state, and can it be operated by assistive technology? Only the vocabulary changes.

§2Platform Code in Practice

The pattern is the same everywhere: use the standard controls, label anything that has no visible text, and set sensible text and touch behavior.

iOS (Swift)
closeButton.accessibilityLabel = "Close"
closeButton.accessibilityTraits = .button
titleLabel.font = UIFont.preferredFont(forTextStyle: .headline)
titleLabel.adjustsFontForContentSizeCategory = true    // respects Dynamic Type

Android (XML)
<ImageButton
    android:id="@+id/close"
    android:contentDescription="Close"
    android:minWidth="48dp"
    android:minHeight="48dp" />
<TextView android:textSize="16sp" />    <!-- sp scales with the user's font size -->

React Native
<Pressable
  accessibilityRole="button"
  accessibilityLabel="Close"
  accessibilityState={{ disabled: false }}
  onPress={close}>
  <CloseIcon />
</Pressable>

§3Mobile-Specific Concerns

Mobile devices add situations that desktop pages rarely face.

  • Touch targets: about 44 points on iOS, and 48 dp on Android, as a floor for important controls.
  • Text scaling: support Dynamic Type on iOS and font scale on Android, and test at the largest sizes, where layouts often break.
  • Orientation: do not lock to portrait or landscape unless it is essential (WCAG 1.3.4, Level AA).
  • Gestures: every swipe, pinch, or long press needs a simple alternative, and screen reader users use different gestures, so custom ones can conflict.
  • Focus order and traversal: the reading order follows the view hierarchy, so check it with the screen reader on.
  • Reduce motion and other settings: read the system preferences (for example UIAccessibility.isReduceMotionEnabled) and respect them.
  • Hybrid and WebView content: ensure web content inside a native shell is accessible, with correct focus behavior across the boundary.

Test on real devices with VoiceOver and TalkBack, and with large text, bold text, and reduced motion enabled. The simulators do not tell you how it feels.

The key insight A senior accessibility engineer is fluent in the underlying model, not one syntax. Name, role, state, and operability are the same on every platform. Learn those, and each new framework is only a new set of property names.

§4Common Mistakes

MistakeWhat HappensFix
Icon buttons with no label in a native appThe screen reader says "button" and nothing elseSet the platform label, such as accessibilityLabel or contentDescription
Fixed text sizes in points or pixelsThe app ignores the user's text size settingUse scalable units and text styles, and test at the largest size
Locking orientation without a needUsers with devices mounted in one orientation are shut outSupport both orientations unless it is essential
Practice
  1. Turn on VoiceOver or TalkBack and navigate an app you use. Write down three unlabeled or confusing controls.
  2. Set your phone's text size to the largest setting and open an app. List what breaks.
Key takeaways
  • Native platforms use the same concepts as ARIA (name, role, state), with different property names.
  • Use standard controls, label non-text controls, and support text scaling, touch target sizes, and both orientations.
  • Test on real devices with VoiceOver and TalkBack, large text, and reduced motion.
