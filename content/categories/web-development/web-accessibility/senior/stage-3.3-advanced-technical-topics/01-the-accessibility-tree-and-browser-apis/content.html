The Accessibility Tree & Browser APIs

Assistive technology never sees your DOM or your pixels. It sees a separate structure the browser builds from them. Knowing how that tree is made explains almost every strange screen reader behavior you will meet.

§1From DOM to Accessibility Tree

The browser builds the accessibility tree from the DOM and the computed CSS. Each node carries a role, an accessible name, a description, states, and properties, plus relationships such as what labels or controls what. It then exposes that tree to the operating system through a platform accessibility API, and the screen reader reads from there.

PlatformAccessibility API the browser talks to
WindowsUI Automation (UIA), plus IAccessible2 in some browsers
macOS and iOSNSAccessibility and UIAccessibility
LinuxAT-SPI
AndroidAccessibilityNodeInfo and the Android accessibility framework

This is why the same page can sound slightly different in different browser and screen reader pairs: each browser maps the tree to each platform API in its own way, and each screen reader interprets what it receives.

§2What Is In, and What Is Out

Not every DOM node becomes an accessibility node. The browser prunes the tree, and the rules explain a lot of "why can't the screen reader see this?" bugs.

Markup or styleEffect on the tree
display: none, visibility: hidden, hiddenRemoved from the tree for everyone
aria-hidden="true"Removed with all its descendants, but still visible and focusable on screen
inertRemoved and made non-interactive
role="presentation" or role="none"Drops the element's own role, but keeps its children
Generic wrappers (div, span) with no role or nameUsually ignored or flattened
Text from CSS contentOften included in the name, with varying support

The accessible name itself comes from the accessible name computation, a defined algorithm that checks sources in order: aria-labelledby, then aria-label, then native sources such as label or alt, then content, and finally title. Knowing the order tells you why an aria-label on a button silently overrides its visible text.

§3Inspecting and Testing the Tree

You can look at the tree directly instead of guessing. Chrome and Edge DevTools have an Accessibility pane, and Firefox has an Accessibility Inspector that shows the full tree, with name, role, and states for each node.

Testing tools also use the tree. Role-based queries in Testing Library and Playwright find elements the same way assistive technology does, so a test that cannot find a button by role and name has found a real bug. Playwright can also capture the tree as an ARIA snapshot and compare it over time.

Playwright: assert the accessibility structure of a region
await expect(page.getByRole('navigation', { name: 'Primary' })).toMatchAriaSnapshot(`
  - list:
    - listitem:
      - link "Home"
    - listitem:
      - link "Guides"
`);

A snapshot of part of a page might look like this
- banner:
  - link "Trailhead"
  - navigation "Primary"
- main:
  - heading "Trail Running Guide" [level=1]
  - button "Save"

Snapshot tests catch structural regressions such as a heading that turned into a div, which pixel-based tests never would.

The key insight When a screen reader behaves strangely, look at the accessibility tree before blaming the screen reader. The tree is the real interface, and DevTools shows it to you.

§4Common Mistakes

MistakeWhat HappensFix
Debugging screen reader output by reading the DOMThe DOM and the tree differ in names, roles, and pruningInspect the accessibility tree in browser DevTools
Hiding content with aria-hidden and expecting it to disappear visuallyStill visible and focusable, but missing from the treeUse hidden or inert for content that should be gone for everyone
Adding aria-label to a labeled buttonThe label silently overrides the visible text and breaks voice controlKeep the accessible name matched to the visible label
Practice
  1. Open the Accessibility pane in DevTools on a page you built. Find one element whose name, role, or state surprised you.
  2. Write a role-based test that finds a button by role and name, then break the markup (turn it into a div) and watch the test fail.
Key takeaways
  • Assistive technology reads the accessibility tree the browser builds from DOM and CSS, through platform APIs.
  • Hiding, aria-hidden, inert, and roles decide what is in the tree. The name computation follows a defined order.
  • Inspect the tree in DevTools, and use role-based and ARIA snapshot tests to catch structural regressions.
