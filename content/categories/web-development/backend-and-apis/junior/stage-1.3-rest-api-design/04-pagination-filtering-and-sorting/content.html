Pagination, Filtering & Sorting

Lists that don't return everything.

§1Lists Must Not Return Everything

GET /notes is fine with 20 rows and an outage with 2 million. Any endpoint that returns a collection needs a maximum page size from day one: it protects your database, your memory, and your clients. Add filtering and sorting so clients can find what they want without downloading everything.

§2Offset Pagination

The simplest scheme: ?limit=20&offset=40 (or page=3). It supports jumping to an arbitrary page, which suits admin tables.

const limit  = Math.min(Number(req.query.limit ?? 20), 100);   // clamp: client can't ask for 1,000,000
const offset = Math.max(Number(req.query.offset ?? 0), 0);

const { rows } = await pool.query(
  "SELECT * FROM notes WHERE user_id = $1 ORDER BY created_at DESC, id DESC LIMIT $2 OFFSET $3",
  [req.user.id, limit, offset]
);

Offset has two weaknesses. It gets slower with depth, because the database must still walk past all the skipped rows. And it is unstable when data changes between requests: if a new note is inserted while a client reads page 1, page 2 repeats an item the client already saw.

§3Cursor (Keyset) Pagination

Instead of "skip N rows," the client says "give me the rows after this one." The cursor encodes the sort position of the last item seen, and the query uses an index to jump straight to it. It stays fast at any depth and remains stable as data changes; the trade-off is that you can move only forward and backward, not jump to page 47.

-- First page
SELECT * FROM notes WHERE user_id = $1
ORDER BY created_at DESC, id DESC LIMIT 21;          -- fetch limit + 1 to know if there's more

-- Next page: cursor = (created_at, id) of the last row returned
SELECT * FROM notes
WHERE user_id = $1 AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC LIMIT 21;

Notice the sort includes id as a tiebreaker: without a unique, total ordering, rows with equal timestamps can be skipped or repeated. Encode the cursor as an opaque string (such as base64 JSON) so clients treat it as a token rather than build their own.

§4Filtering and Sorting Safely

  • Filtering: accept known fields as query parameters (?tag=sql&archived=false) and validate each one.
  • Sorting: accept ?sort=-created_at (a leading minus for descending) but map it through an allow-list. Never place a client-supplied column name into SQL directly.
  • Be mindful of indexes: every filter-and-sort combination you offer should be backed by an index, or it will not scale.
const SORTABLE = { created_at: "created_at", title: "title" };   // allow-list
const [, dir, field] = /^(-?)(\w+)$/.exec(req.query.sort ?? "-created_at") ?? [];
const column = SORTABLE[field] ?? "created_at";
const direction = dir === "-" ? "DESC" : "ASC";
const sql = `SELECT * FROM notes WHERE user_id = $1 ORDER BY ${column} ${direction}, id ${direction} LIMIT $2`;
Which should you choose? Use offset for small, bounded datasets where page numbers matter. Use cursors for feeds, large tables, and anything that changes frequently. Many public APIs (including most social feeds) use cursors for exactly these reasons.

§5Common Mistakes

MistakeWhat HappensFix
No maximum page sizeOne request can load the entire table and take the service downClamp limit to a sensible maximum, with a default
Sorting by a non-unique column with offset or cursor pagingDuplicated or missing rows across pagesAdd a unique tiebreaker such as id
Interpolating the sort field into SQLSQL injection through ?sort=Map it through a hard-coded allow-list
Practice
  1. Add offset pagination with a clamped limit to a list endpoint and return the total count in the response.
  2. Convert it to cursor pagination with (created_at, id). Insert rows between page requests and confirm nothing repeats.
  3. Add ?sort= with an allow-list of three fields and test that ?sort=password;DROP is harmless.
Key takeaways
  • Always cap page size; unbounded lists are an outage waiting to happen.
  • Offset is simple but slow and unstable at depth; cursors scale and stay consistent.
  • Validate filters and allow-list sort fields, and back each combination with an index.
