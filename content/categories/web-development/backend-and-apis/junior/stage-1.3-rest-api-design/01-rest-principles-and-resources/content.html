REST Principles & Resources

Nouns, verbs, and designing URLs.

§1Resources, Not Actions

REST (Representational State Transfer) is a style for designing APIs on top of HTTP. Its central idea is to model your system as resources, the nouns of your domain (users, notes, orders), each identified by a URL, and to use HTTP's standard methods as the verbs. Clients exchange representations of those resources, almost always JSON.

Instead of (RPC-style)Use (resource-style)
POST /createNotePOST /notes
GET /getNoteById?id=7GET /notes/7
POST /deleteNoteDELETE /notes/7
GET /getNotesForUser?user=3GET /users/3/notes

Notice that the URL names what, and the method says what to do with it. The same URL supports different operations depending on the method, which keeps the API small and predictable.

§2URL Design Conventions

  • Plural nouns for collections: /notes is the collection; /notes/7 is one member.
  • Nest to express ownership, sparingly: /users/3/notes reads well; going deeper than about two levels becomes awkward. Prefer /notes/7/comments over /users/3/notes/7/comments/9.
  • Lowercase, hyphenated, no verbs, no file extensions, no trailing noise: /order-items, not /OrderItems.php.
  • Filters go in the query string: /notes?tag=sql&archived=false, not in the path.

§3The Constraints That Matter in Practice

REST has formal constraints; the ones you feel daily are:

  • Client-server: the client and server evolve independently as long as the contract holds.
  • Stateless: each request carries everything needed to process it (including credentials). The server does not rely on remembering earlier requests, which is what lets you run many identical servers behind a load balancer.
  • Uniform interface: standard methods, status codes, and consistent resource naming across the whole API, so that learning one endpoint teaches you the rest.
  • Cacheable: responses can declare whether they may be reused, which is why GET must be safe.
GET    /notes            list notes
POST   /notes            create a note
GET    /notes/7          read one note
PUT    /notes/7          replace note 7
PATCH  /notes/7          change some fields of note 7
DELETE /notes/7          delete note 7
GET    /notes/7/comments list comments on note 7
POST   /notes/7/comments add a comment to note 7
When an action does not fit a noun Not everything is CRUD. For operations like "publish" or "send a password reset," either model the result as a resource (POST /notes/7/publication) or accept a pragmatic action endpoint (POST /notes/7/publish). Be consistent, and do not contort the model into absurdity just to avoid a verb.

§4Common Mistakes

MistakeWhat HappensFix
Verbs in URLs (/getUser, /deleteNote)Inconsistent, undiscoverable APIs with duplicated meaningUse nouns in the path and let the HTTP method be the verb
Mixing singular and plural (/note and /users)Clients must memorize exceptionsPick plural collection names everywhere
Storing session state on the server between requestsBreaks horizontal scaling and makes behavior hard to reason aboutSend identity (a token) with each request; keep the server stateless
Practice
  1. Design the URLs and methods for a recipe app: recipes, ingredients, and user favorites. Write out the list like the one above.
  2. Take these RPC endpoints and rewrite them as resources: /searchProducts, /addToCart, /cancelOrder.
  3. Explain why a stateless server is easier to scale than one that remembers each client.
Key takeaways
  • Model resources as plural nouns with URLs, and let HTTP methods supply the verbs.
  • Stay stateless: each request must carry what the server needs to handle it.
  • Be consistent; a predictable, uniform API is worth more than a clever one.
