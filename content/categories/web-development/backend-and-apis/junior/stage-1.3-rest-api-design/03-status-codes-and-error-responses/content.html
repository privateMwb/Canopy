Status Codes & Error Responses

Consistent, helpful error shapes.

§1Errors Are Part of Your API

Clients spend a surprising amount of code handling failure, so your errors deserve the same design care as your successes. A good error answers three questions: what went wrong, whose fault is it (status code), and what can I do about it (message and details). The key quality is consistency: every error from every endpoint should have the same shape, so a client can handle them in one place.

§2Choosing the Right Code

CodeWhen to use it
400 Bad RequestMalformed or invalid input (bad JSON, failed validation)
401 UnauthorizedNo valid credentials: the client is not authenticated
403 ForbiddenAuthenticated, but not allowed to do this
404 Not FoundResource does not exist (or you may not know it exists)
409 ConflictValid request that clashes with current state, such as a duplicate email
422 Unprocessable ContentWell-formed but semantically invalid (an alternative for validation errors)
429 Too Many RequestsRate limit exceeded; include Retry-After
500 Internal Server ErrorUnexpected bug on the server
503 Service UnavailableTemporarily overloaded or down for maintenance

The most confused pair is 401 and 403. Despite its name, 401 means "unauthenticated" (who are you?) and 403 means "unauthorized" in the everyday sense (I know who you are, and the answer is no).

§3A Consistent Error Shape

You can invent your own envelope, or adopt the standard Problem Details format (RFC 9457, served as application/problem+json), which many tools understand. Either way, include a machine-readable code, a human-readable message, and field-level details for validation errors.

{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Your request parameters didn't validate.",
  "status": 400,
  "detail": "2 fields are invalid.",
  "errors": [
    { "field": "email", "message": "Must be a valid email address" },
    { "field": "password", "message": "Must be at least 12 characters" }
  ]
}

Centralize this in one error-handling middleware so route code simply throws, and the shape is guaranteed:

class ApiError extends Error {
  constructor(status, title, extra = {}) { super(title); this.status = status; this.extra = extra; }
}

app.use((err, req, res, next) => {
  if (err instanceof ApiError) {
    return res.status(err.status).type("application/problem+json")
      .json({ status: err.status, title: err.message, ...err.extra });
  }
  req.log?.error(err);                               // full details go to the logs...
  res.status(500).type("application/problem+json")
    .json({ status: 500, title: "Internal server error" });   // ...but never to the client
});

// In a route:  throw new ApiError(409, "Email already registered");
Never leak internals Stack trace, SQL text, table names, and library versions in a 500 response are a gift to attackers. Log the details server-side with a request id, and return that id (not the stack) so support can find the log entry.

§4Common Mistakes

MistakeWhat HappensFix
Returning 500 for client mistakesAlerts fire for non-bugs, and clients retry when they should fix the requestUse the 4xx code that matches the problem
Using 401 and 403 interchangeablyClients cannot tell whether to log in again or give up401 = not authenticated, 403 = authenticated but not allowed
A different error shape per endpointEvery client needs special casesOne error middleware and one documented shape
Practice
  1. Build the error middleware above and make three routes throw a 400, a 409, and an unexpected error. Verify the shapes and that the 500 reveals nothing sensitive.
  2. Decide the right status for: wrong password, expired token, deleting someone else's note, signing up with a taken email, uploading a 50 MB file when the limit is 5 MB.
  3. Add a requestId to every error response and to your logs.
Key takeaways
  • Pick the status code that says whose fault it is and what the client should do next.
  • Use one consistent error shape (such as RFC 9457) produced by a single error handler.
  • Return helpful detail for client errors, and log (don't expose) detail for server errors.
