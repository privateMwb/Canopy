CRUD Endpoints

Create, read, update, and delete done correctly.

§1Create, Read, Update, Delete

CRUD is the backbone of most APIs, and the details of doing it correctly are where quality shows. Here is a complete resource, with a pg pool and validation, for notes that belong to a user.

const router = express.Router();

// CREATE: 201 plus a Location header pointing at the new resource
router.post("/notes", async (req, res) => {
  const input = CreateNote.parse(req.body);          // validation (schema from earlier lesson)
  const { rows } = await pool.query(
    "INSERT INTO notes (user_id, title, body) VALUES ($1, $2, $3) RETURNING *",
    [req.user.id, input.title, input.body ?? ""]
  );
  res.status(201).location(`/notes/${rows[0].id}`).json(rows[0]);
});

// READ (one): 404 if missing
router.get("/notes/:id", async (req, res) => {
  const { rows } = await pool.query(
    "SELECT * FROM notes WHERE id = $1 AND user_id = $2", [req.params.id, req.user.id]);
  if (rows.length === 0) return res.status(404).json({ error: "Note not found" });
  res.json(rows[0]);
});

§2PUT vs PATCH

PUT replaces the resource: the client sends the full representation and any omitted field is reset. It is idempotent. PATCH applies a partial change: only the fields sent are modified. Most real-world APIs use PATCH for updates because clients rarely want to resend everything, and it avoids accidentally wiping fields the client did not know about.

router.patch("/notes/:id", async (req, res) => {
  const input = UpdateNote.parse(req.body);          // all fields optional, at least one required
  const { rows } = await pool.query(
    `UPDATE notes
        SET title = COALESCE($1, title),
            body  = COALESCE($2, body)
      WHERE id = $3 AND user_id = $4
      RETURNING *`,
    [input.title ?? null, input.body ?? null, req.params.id, req.user.id]
  );
  if (rows.length === 0) return res.status(404).json({ error: "Note not found" });
  res.json(rows[0]);
});

// DELETE: 204 No Content on success (nothing to return)
router.delete("/notes/:id", async (req, res) => {
  const { rowCount } = await pool.query(
    "DELETE FROM notes WHERE id = $1 AND user_id = $2", [req.params.id, req.user.id]);
  if (rowCount === 0) return res.status(404).json({ error: "Note not found" });
  res.status(204).end();
});

§3Details That Separate Good from Sloppy

OperationSuccess statusNotes
Create201 CreatedReturn the new resource and a Location header
Read200 OK404 if it does not exist (or you may not see it)
Update200 OKReturn the updated resource so clients need no second call
Delete204 No ContentDecide whether repeat deletes return 404 or 204; document it
  • Scope every query by owner (AND user_id = $2), so users can never touch each other's rows by guessing ids.
  • Return the database-generated fields (id, timestamps) on create so clients stay in sync.
  • Never let clients set server-controlled fields such as id, user_id, or created_at.
404 doubles as access control Returning 404 for "exists but not yours" avoids confirming that other users' ids exist. The authorization lesson in stage 1.4 returns to this trade-off.

§4Common Mistakes

MistakeWhat HappensFix
Returning 200 for creation with no LocationClients cannot tell what was created or where it livesReturn 201, the resource, and a Location header
Using PUT for partial updatesOmitted fields get wipedUse PATCH for partial changes; reserve PUT for full replacement
Looking up by id only, not by ownerAny user can read or change any row (an IDOR vulnerability)Include the owner in the query, or check ownership explicitly
Practice
  1. Implement all five operations for a resource of your choice, then test each with curl and record the status codes.
  2. Make PATCH reject an empty body with a 400. What should happen if the client sends {"title": null}?
  3. Try to read, update, and delete another user's note and confirm all three return 404.
Key takeaways
  • Use the right status per operation: 201 with Location, 200 with the resource, 204 for deletes.
  • PUT replaces, PATCH modifies; most update endpoints should be PATCH.
  • Always scope queries by owner and never accept server-controlled fields from clients.
