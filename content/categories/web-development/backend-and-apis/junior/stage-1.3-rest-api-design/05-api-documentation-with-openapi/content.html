API Documentation with OpenAPI

A contract that doubles as docs and tests.

§1A Contract You Can Read and Run

An API nobody can understand is an API nobody can use. OpenAPI (formerly Swagger) is the standard, language-neutral format for describing an HTTP API in YAML or JSON: every path, method, parameter, request body, and response. Because it is machine-readable, one file produces interactive docs, client SDKs, mock servers, and automated request/response validation.

openapi: 3.1.0
info:
  title: Notes API
  version: 1.0.0
paths:
  /notes:
    get:
      summary: List notes
      parameters:
        - name: limit
          in: query
          schema: { type: integer, minimum: 1, maximum: 100, default: 20 }
      responses:
        "200":
          description: A page of notes
          content:
            application/json:
              schema:
                type: array
                items: { $ref: "#/components/schemas/Note" }
    post:
      summary: Create a note
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: "#/components/schemas/NewNote" }
      responses:
        "201": { description: Created }
        "400": { $ref: "#/components/responses/ValidationError" }
components:
  schemas:
    NewNote:
      type: object
      required: [title]
      properties:
        title: { type: string, minLength: 1, maxLength: 200 }
        body:  { type: string }
    Note:
      allOf:
        - $ref: "#/components/schemas/NewNote"
        - type: object
          required: [id]
          properties:
            id: { type: integer }

Reusable pieces live under components and are referenced with $ref, so a Note is defined once and used by every endpoint that returns one.

§2Two Ways to Work

ApproachHow it worksGood for
Contract-first (design-first)Write the spec, review it with consumers, then implement against itPublic APIs and APIs consumed by other teams; agree before building
Code-firstGenerate the spec from annotations or schemas in your code (for example Zod-to-OpenAPI or framework plugins)Small teams that want docs to stay in sync with minimal effort

§3What the Spec Unlocks

  • Interactive docs with Swagger UI, Redoc, or Scalar: readers can try requests in the browser.
  • Generated clients in many languages, so consumers do not hand-write HTTP calls.
  • Request and response validation in your server or in tests, which turns the spec into an enforced contract.
  • Linting and breaking-change detection in CI, comparing the new spec with the previous version.
Docs that lie are worse than no docs A spec that drifts from the real behavior misleads everyone. Keep them honest by generating one from the other, or by testing the live API against the spec in CI so that any mismatch fails the build. The stage checkpoint asks you to do exactly this.

§4Common Mistakes

MistakeWhat HappensFix
Writing the spec once and never updating itDocs and behavior drift apart; consumers lose trustGenerate it from code or validate the API against it in CI
Describing only the happy pathClients guess at error shapes and edge casesDocument every status code, including the error schema
Copy-pasting schemas into every endpointInconsistent definitions and noisy diffsDefine once in components and $ref it
Practice
  1. Write an OpenAPI file for two endpoints of your own API, including an error response, and open it in Swagger UI or Scalar.
  2. Use a generator to produce a typed client from your spec and call your API with it.
  3. Add a test that sends a request and validates the response body against the schema in the spec.
Key takeaways
  • OpenAPI is a machine-readable contract that doubles as docs, client generator, and test oracle.
  • Define shared schemas once under components and reference them with $ref.
  • Keep the spec honest through generation or contract tests, or it will rot.
