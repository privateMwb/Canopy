Migrations

Evolving a schema safely over time.

§1Schemas Change, and Databases Hold Real Data

Your first schema will not be your last. Features add columns, requirements rename things, and mistakes need fixing, all while a database full of real data stays in place. Editing the schema by hand in a console works on your laptop and becomes a disaster across a team and several environments: nobody can say what state production is in. Migrations solve this by recording every schema change as a small, ordered, versioned file that is committed to git and applied by a tool.

-- migrations/0003_add_notes_archived.sql
ALTER TABLE notes ADD COLUMN archived BOOLEAN NOT NULL DEFAULT false;
CREATE INDEX idx_notes_user_archived ON notes (user_id, archived);

§2How a Migration Tool Works

  • Files are applied in order (by number or timestamp).
  • The database keeps a history table listing which migrations have run, so each runs exactly once.
  • Every environment (local, CI, staging, production) runs the same files and converges on the same schema.
  • Tools range from SQL-file runners (node-pg-migrate, Flyway, Atlas) to ORM-integrated ones (prisma migrate, drizzle-kit) that generate the SQL from changes to your schema definition.
# Typical workflow with an ORM-integrated tool
# 1. Edit the schema definition (add a column)
# 2. Generate a migration file and apply it locally
npx prisma migrate dev --name add-notes-archived
# 3. Commit the migration file with the code that uses it
# 4. In CI/production, apply pending migrations only
npx prisma migrate deploy

§3Rules That Keep You Safe

  • Never edit a migration that has already been applied anywhere shared. Add a new migration instead; otherwise environments drift apart.
  • Review the generated SQL. A rename can be generated as drop-and-create, which destroys data.
  • Prefer additive changes. Adding a nullable column or a new table is low-risk; dropping or renaming columns needs care because running code may still use them.
  • Test on realistic data. A migration that takes a millisecond on ten rows may lock a ten-million-row table for minutes.
Down migrations are less valuable than they look Many teams write "down" scripts, but reversing a migration after data has been written often cannot restore what was lost. A safer rollback strategy is to make changes backward compatible and fix forward. The senior level returns to this with the expand-and-contract pattern.

§4Common Mistakes

MistakeWhat HappensFix
Editing a migration that already ranEnvironments diverge and the history table no longer matches realityNever rewrite history; add a new migration
Changing the schema manually in productionNobody knows the true state, and the next deploy may failAll changes go through migration files in version control
Not reviewing generated SQLA rename becomes drop and recreate, and the data is goneRead every migration before applying it, especially renames
Practice
  1. Set up a migration tool in your project and create migrations that (1) create users, (2) create notes, and (3) add a pinned column to notes.
  2. Drop your local database, re-run all migrations from scratch, and confirm you get an identical schema.
  3. Write a migration that renames a column safely in two steps (add new column and copy data, then drop the old one in a later migration). Why two steps?
Key takeaways
  • Migrations are ordered, versioned schema changes stored in git and applied by a tool, once per environment.
  • Never edit an applied migration, never hand-edit production, and always review generated SQL.
  • Favor additive, backward-compatible changes so running code keeps working during a deploy.
