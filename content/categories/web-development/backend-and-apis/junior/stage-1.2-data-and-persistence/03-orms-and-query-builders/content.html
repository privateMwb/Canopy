ORMs & Query Builders

Prisma and Drizzle: benefits and costs.

§1Three Levels of Abstraction

Writing raw SQL strings is precise but repetitive and untyped. Tools exist at three levels. A driver (like pg) gives you raw SQL. A query builder lets you compose SQL with code while staying close to it. An ORM (object-relational mapper) maps tables to objects and generates SQL for you. In the Node ecosystem, Prisma and Drizzle are two popular choices, with Drizzle sitting closer to SQL and Prisma offering a higher-level client.

// Prisma: describe models in schema.prisma, then use the generated client
const notes = await prisma.note.findMany({
  where: { userId, title: { contains: "sql", mode: "insensitive" } },
  orderBy: { createdAt: "desc" },
  take: 10,
});

// Drizzle: SQL-shaped, fully typed
import { eq, and, desc, ilike } from "drizzle-orm";
const notes = await db
  .select()
  .from(notesTable)
  .where(and(eq(notesTable.userId, userId), ilike(notesTable.title, "%sql%")))
  .orderBy(desc(notesTable.createdAt))
  .limit(10);

§2What You Gain

  • Type safety: typos in column names become compile errors, and results come back with known types.
  • Less boilerplate: inserts, updates, and relation loading take a few lines.
  • Safe by default: values are parameterized automatically.
  • Migration support: the schema definition doubles as the source for generating migrations.

§3What It Costs

Abstractions leak. The most common surprise is the N+1 query problem: you load a list of notes, then loop over them and load each note's author separately, producing one query for the list plus one per row. It works fine on ten rows and crawls on ten thousand.

// N+1: 1 query for notes, then 1 query PER note
const notes = await prisma.note.findMany();
for (const n of notes) {
  n.author = await prisma.user.findUnique({ where: { id: n.userId } });
}

// Fixed: ask for the relation up front (a join or one batched query)
const notes = await prisma.note.findMany({ include: { user: true } });

Other costs: generated SQL can be inefficient for complex queries, a learning curve for the tool's own vocabulary, and a build or generation step. Every serious ORM provides an escape hatch for raw SQL, and you should use it when a query is complex or performance-critical.

Learn SQL first, then pick a tool An ORM saves typing, not understanding. Turn on query logging in development and read the SQL it produces; if you cannot predict what it generates, you will not be able to diagnose a slow endpoint later.

§4Common Mistakes

MistakeWhat HappensFix
Looping and querying inside the loopN+1 queries: latency grows with row countLoad relations up front with include / joins, and log queries to spot repeats
Fighting the ORM for complex reportsUnreadable code and slow generated SQLDrop to raw SQL (or a view) for that query
Never reading the generated SQLMissing indexes and wasteful queries stay hiddenEnable query logging in development and inspect it
Practice
  1. Define a users and notes model in Prisma or Drizzle and write a query returning each user's notes in one round trip.
  2. Reproduce an N+1 on purpose with a loop, count the queries in the log, and fix it.
  3. Write one query with the ORM's raw-SQL escape hatch and compare it with the builder version.
Key takeaways
  • Drivers, query builders, and ORMs trade control for convenience; none removes the need to understand SQL.
  • ORMs give type safety and safe defaults, but can hide N+1 queries and inefficient SQL.
  • Log the generated SQL and keep a raw-SQL escape hatch for complex or hot queries.
