Schema Design Basics

Keys, relations, and normalization.

§1Design Tables Around Facts

A schema is a set of promises about your data. Good design starts by listing the things your app cares about (users, notes, tags) and the facts about each, then giving every fact exactly one home. When the same fact is stored in two places, the copies eventually disagree.

§2Keys and Relationships

Every table gets a primary key. Relationships are expressed with foreign keys, and there are three shapes:

  • One-to-many: a user has many notes. The foreign key lives on the "many" side (notes.user_id).
  • Many-to-many: a note has many tags and a tag appears on many notes. This needs a junction table holding pairs of ids.
  • One-to-one: rare; usually the data belongs in the same table unless it is optional, large, or sensitive.
CREATE TABLE tags (
  id   SERIAL PRIMARY KEY,
  name TEXT NOT NULL UNIQUE
);

CREATE TABLE note_tags (
  note_id INTEGER NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  tag_id  INTEGER NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
  PRIMARY KEY (note_id, tag_id)                      -- a note can't have the same tag twice
);

ON DELETE CASCADE means deleting a note also removes its tag links. Choose deliberately: cascade for dependent rows, restrict (the default behavior) when a delete should be blocked while related rows exist.

§3Normalization in Plain English

Normalization is the practice of removing redundancy. The practical rules of thumb: keep one value per column (no comma-separated lists of tags in a single cell), make every column depend on the whole key of its table, and do not store facts about one thing inside the row of another. Storing the author's name on every note, for instance, means renaming the author requires updating thousands of rows and risks missing some.

Normalization is a default, not a religion. Deliberate denormalization (a stored counter, a cached total) is a legitimate performance optimization, but make it a conscious choice with a plan for keeping it correct.

§4Let the Database Enforce Rules

CREATE TABLE orders (
  id          SERIAL PRIMARY KEY,
  user_id     INTEGER NOT NULL REFERENCES users(id),
  status      TEXT NOT NULL CHECK (status IN ('pending', 'paid', 'shipped')),
  total_cents INTEGER NOT NULL CHECK (total_cents >= 0),   -- money as integer cents, not float
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
Constraints are your last line of defense Application validation can be bypassed by a bug, a script, or a second service. NOT NULL, UNIQUE, CHECK, and foreign keys make impossible states impossible, no matter who writes to the table.

§5Common Mistakes

MistakeWhat HappensFix
Storing lists in one column (tags = "a,b,c")Cannot query, index, or constrain individual valuesUse a junction table for many-to-many
Using floating point for moneyRounding errors such as 0.1 + 0.2 produce wrong totalsStore integer minor units (cents) or NUMERIC
Skipping constraints and relying on app codeBad rows creep in from scripts and bugsAdd NOT NULL, UNIQUE, CHECK, and foreign keys
Practice
  1. Design tables for a library: books, authors, and members who borrow books. Identify each relationship and mark the keys.
  2. Take a table with a tags comma-separated column and redesign it into proper tables.
  3. Add a constraint that prevents a member from borrowing the same copy twice at the same time (think about what to make unique).
Key takeaways
  • Give each fact one home; store relationships with foreign keys and junction tables for many-to-many.
  • Normalize by default, and denormalize only deliberately for measured performance reasons.
  • Use constraints and sensible types (timestamptz, integer cents) so the database guards the data.
