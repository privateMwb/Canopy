Passwords & Hashing

bcrypt and argon2, salts, and why not to roll your own.

§1Never Store a Password

If your database leaks (and you should plan as though it eventually might), plaintext passwords hand attackers every user's account, plus every other site where those users reused the same password. The defense is to store only a hash: a one-way transformation you can compute from the password, but cannot reverse into it. At login you hash what the user typed and compare it with the stored hash.

Hashing is not encryption. Encryption is designed to be reversed with a key; a password hash is designed to be impossible to reverse, so there is no key to steal.

§2Why Ordinary Hashes Are Not Enough

General-purpose hashes such as SHA-256 are built to be fast, which is exactly wrong here: an attacker with a stolen table can try billions of guesses per second on a graphics card. Password hashing algorithms are deliberately slow and memory-hungry, with a tunable cost, and they mix in a unique random salt per password so identical passwords produce different hashes and precomputed "rainbow tables" are useless.

import argon2 from "argon2";                         // npm install argon2

// Registration: the library generates a random salt and embeds it, with the
// cost settings, inside the returned string.
const hash = await argon2.hash(password);            // "$argon2id$v=19$m=65536,t=3,p=4$...$..."
await pool.query("INSERT INTO users (email, password_hash) VALUES ($1, $2)", [email, hash]);

// Login: verify against the stored string
const { rows } = await pool.query("SELECT id, password_hash FROM users WHERE email = $1", [email]);
const user = rows[0];
const ok = user && await argon2.verify(user.password_hash, password);
if (!ok) return res.status(401).json({ error: "Invalid email or password" });

§3Login Details That Matter

  • Use one generic error for "no such user" and "wrong password". Distinguishing them lets attackers discover which emails have accounts.
  • Equalize timing. If a missing user returns instantly while a real user takes 100 ms to hash-check, the difference leaks the same information. Verify against a dummy hash when the user does not exist.
  • Rehash when settings improve. After a successful login, if argon2.needsRehash(hash) is true, store a fresh hash with the new parameters.
  • Favor length over complexity rules. Current guidance (NIST SP 800-63B) recommends allowing long passphrases and screening against known-breached passwords, rather than forcing symbols and periodic changes.
Do not roll your own Writing your own hashing scheme, or inventing "clever" salting and peppering, is how breaches happen. Use a maintained library with its defaults, keep it updated, and spend your effort on rate limiting login attempts and on offering multi-factor authentication.

§4Common Mistakes

MistakeWhat HappensFix
Storing plaintext or using unsalted SHA-256/MD5A leak instantly exposes all accountsUse argon2id or bcrypt through a maintained library
Different error messages for unknown email vs wrong passwordAttackers enumerate valid accountsReturn the same message and similar timing for both
Logging request bodies on login or registrationPlaintext passwords end up in log filesRedact password fields in all logs and error reports
Practice
  1. Implement register and login endpoints using argon2 or bcrypt, and inspect the stored value in the database. Register two users with the same password and compare their hashes.
  2. Time the login for an existing user versus a nonexistent one. Add a dummy-hash comparison to equalize them.
  3. Write a short explanation, for a teammate, of why SHA-256 is a bad choice for passwords even though it is a secure hash.
Key takeaways
  • Store only a slow, salted, one-way hash; use argon2id or bcrypt from a maintained library.
  • Return identical errors (and similar timing) for unknown user and wrong password.
  • Never log passwords, and prefer long passphrases and breach screening over complexity rules.
