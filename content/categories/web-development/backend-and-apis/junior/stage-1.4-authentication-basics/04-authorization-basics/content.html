Authorization Basics

Who can do what, enforced on the server.

§1Authentication Is Not Authorization

Authentication answers "who are you?" Authorization answers "what are you allowed to do?" A logged-in user is not automatically allowed to do everything; a huge share of real-world security bugs are authorization bugs in which any authenticated user can reach data that belongs to someone else.

The rule that matters most: enforce authorization on the server, on every request. Hiding a button in the UI is not security; anyone can send the request directly with curl.

§2Ownership Checks

The most common rule is "a user may only access their own resources." The bug that violates it is called IDOR (insecure direct object reference): the endpoint trusts an id from the URL without checking that the caller owns it.

// VULNERABLE: any logged-in user can read any note by changing the id
router.get("/notes/:id", requireLogin, async (req, res) => {
  const { rows } = await pool.query("SELECT * FROM notes WHERE id = $1", [req.params.id]);
  res.json(rows[0]);
});

// SAFE: ownership is part of the query itself
router.get("/notes/:id", requireLogin, async (req, res) => {
  const { rows } = await pool.query(
    "SELECT * FROM notes WHERE id = $1 AND user_id = $2", [req.params.id, req.user.id]);
  if (!rows[0]) return res.status(404).json({ error: "Note not found" });
  res.json(rows[0]);
});

Folding the owner into the WHERE clause is the cleanest approach: a row you do not own simply does not exist as far as you are concerned, and there is no separate check to forget. Returning 404 rather than 403 also avoids confirming that other users' ids exist.

§3Roles and Permissions

Some actions depend on what kind of user you are rather than which rows you own. Role-based access control (RBAC) assigns each user a role (member, editor, admin) and each route requires certain roles.

function requireLogin(req, res, next) {
  if (!req.user) return res.status(401).json({ error: "Authentication required" });
  next();
}

function requireRole(...roles) {
  return (req, res, next) => {
    if (!req.user) return res.status(401).json({ error: "Authentication required" });
    if (!roles.includes(req.user.role)) return res.status(403).json({ error: "Forbidden" });
    next();
  };
}

router.get("/admin/users", requireRole("admin"), listUsers);
router.delete("/notes/:id", requireLogin, deleteOwnNote);

§4Principles to Build In

  • Deny by default. New routes should require authentication unless explicitly marked public, not the other way around.
  • Least privilege. Give each user and each service the minimum access it needs.
  • Never trust client-supplied identity. Take the user id from the verified session or token, never from the request body ({"userId": 5}).
  • Check at the resource, not just the route. A role check on /admin does not protect /notes/:id.
Test the negative cases Authorization code is easy to write wrongly and easy to assume is right. For every endpoint, write a test that a different user, and an anonymous caller, are refused. These tests catch more security bugs than almost anything else.

§5Common Mistakes

MistakeWhat HappensFix
Looking up by id with no owner check (IDOR)Users read or modify each other's dataInclude the owner in the query or verify ownership explicitly
Hiding UI but not protecting the endpointAnyone can call the API directlyEnforce every rule on the server
Trusting userId or role from the request bodyUsers impersonate others or grant themselves adminDerive identity from the verified session or token only
Practice
  1. Take your notes API and write two integration tests: user B cannot read, update, or delete user A's note, and an unauthenticated request gets 401.
  2. Add a role column and a requireRole("admin") route, then confirm a member gets 403.
  3. Review your API for any place that accepts a user id from the body or URL as proof of identity.
Key takeaways
  • Authentication proves identity; authorization decides access, and must be enforced on the server for every request.
  • Put ownership in the query (WHERE ... AND user_id = ...) to prevent IDOR by construction.
  • Deny by default, apply least privilege, and test that the wrong users are refused.
