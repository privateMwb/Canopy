Routing & Middleware

Express-style routing and the middleware chain.

§1Routing Without the Boilerplate

A router maps a method plus a path pattern to a handler function. Express is the best-known Node framework for this, and its conventions (and those of Fastify, Hono, Koa, and many other frameworks in other languages) share the same ideas. Install it with npm install express.

import express from "express";

const app = express();
const books = [{ id: 1, title: "Dune" }, { id: 2, title: "Neuromancer" }];

app.get("/books", (req, res) => {
  res.json(books);                                   // sets status 200 + JSON header
});

app.get("/books/:id", (req, res) => {
  const book = books.find(b => b.id === Number(req.params.id));
  if (!book) return res.status(404).json({ error: "Book not found" });
  res.json(book);
});

app.listen(3000);

Path segments starting with a colon (:id) become entries on req.params. Note that params always arrive as strings, hence the Number() call.

§2Middleware: A Pipeline for Requests

Middleware is a function that sits between the incoming request and your final handler. It receives req, res, and next; it can read or modify the request, end the response itself, or call next() to pass control onward. Logging, authentication, body parsing, and CORS are all middleware.

function requestLogger(req, res, next) {
  const start = Date.now();
  res.on("finish", () => {
    console.log(`${req.method} ${req.originalUrl} ${res.statusCode} ${Date.now() - start}ms`);
  });
  next();                                            // without this, the request stalls
}

function requireApiKey(req, res, next) {
  if (req.get("x-api-key") !== process.env.API_KEY) {
    return res.status(401).json({ error: "Missing or invalid API key" });
  }
  next();
}

app.use(requestLogger);                              // runs for every request
app.use("/admin", requireApiKey);                    // runs only for /admin/*

§3Order Is Everything

Middleware runs in the order it is registered. A logger registered after your routes never sees them; a 404 handler registered before your routes swallows everything. A typical, healthy order is: logging, body parsing, routes, then a catch-all 404, then an error handler.

app.use((req, res) => {                              // 404: reached only if no route matched
  res.status(404).json({ error: "Not found" });
});

app.use((err, req, res, next) => {                   // four arguments = error handler
  console.error(err);
  res.status(500).json({ error: "Internal server error" });
});

Error-handling middleware is recognized by its four parameters. Express 5 forwards rejected promises from async handlers to it automatically; in Express 4 you must catch and call next(err) yourself.

Why this design wins Cross-cutting concerns (logging, auth, parsing) live in one place and apply to many routes, instead of being copy-pasted into each handler. The handler can then focus on the business logic.

§4Common Mistakes

MistakeWhat HappensFix
Forgetting to call next() in middlewareRequests hang because nothing responds and nothing continuesEither respond or call next() on every path through the function
Registering the 404 handler before the routesEvery route returns 404Put catch-alls last, error handlers after that
Calling next() and then also sending a response"Headers already sent" errorsUse return next() or return res... so only one thing happens
Practice
  1. Write a middleware that adds an X-Request-Id response header with a random id, and register it globally.
  2. Protect only DELETE routes with a simple auth middleware, leaving GET routes public.
  3. Throw an error inside a route on purpose and confirm your error handler returns clean JSON rather than a stack trace.
Key takeaways
  • Routers map method and path to handlers; req.params values are strings.
  • Middleware is a chain of functions that either responds or calls next().
  • Registration order defines behavior: logging first, routes in the middle, 404 and error handlers last.
