Cost & Performance Engineering

Finding waste and speeding up hot paths.

§1Performance Is Money

In production, speed and cost are linked: a slower endpoint needs more servers to serve the same traffic; a chatty service pays for network egress; verbose logging bills you per gigabyte. Cost and performance engineering is the practice of finding waste and speeding up the paths that matter, with measurement guiding every step. Without measurement it degrades into guessing, and guessing usually optimizes the wrong thing.

§2Measure First: Where Does Time and Money Go?

  • Unit economics: compute cost per request, per tenant, or per order. Without a unit cost you cannot tell whether growth is healthy. Tag cloud resources by service, team, and environment so the bill can be attributed.
  • Find the heavy hitters: the Pareto principle usually holds, with a few endpoints, queries, or tenants responsible for most of the load or cost. Sort by total time consumed (calls × duration), not just by slowest single call.
  • Profile real workloads: use production-like traffic and profilers rather than intuition.
# Node.js: find where CPU time goes
node --cpu-prof server.js            # writes a .cpuprofile you can open in Chrome DevTools
npx clinic flame -- node server.js   # flamegraph while you apply load

# Is the event loop being blocked? (a single slow synchronous call stalls EVERY request)
import { monitorEventLoopDelay } from "node:perf_hooks";
const h = monitorEventLoopDelay(); h.enable();
setInterval(() => console.log("p99 loop delay ms:", h.percentile(99) / 1e6), 5000);

-- PostgreSQL: which queries consume the most total time?
SELECT query, calls, round(total_exec_time) AS total_ms, round(mean_exec_time) AS mean_ms
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

§3Common Wins, Roughly in Order of Payoff

AreaTypical wasteTypical fix
DatabaseMissing indexes, N+1 queries, SELECT *, unbounded queriesIndex and rewrite hot queries; batch; paginate; read replicas
Repeated workRecomputing the same results for every requestCaching, memoization, precomputed or materialized views
PayloadsLarge JSON, uncompressed responses, over-fetchingCompression (gzip or brotli), field selection, pagination, HTTP caching with ETags
NetworkNew connection per call, chatty service calls, cross-region trafficConnection reuse and keep-alive, batching, co-locating services, a CDN for static and cacheable content
CPUSynchronous heavy work on the event loop, inefficient algorithmsMove work to workers or queues; fix the algorithm; profile
InfrastructureOversized instances, idle capacity, always-on non-prod environmentsRight-size from actual utilization; autoscale; schedule dev and staging off at night; spot or preemptible capacity for tolerant workloads; commitment discounts for steady baselines
Observability and storageDebug logs in production, infinite retention, high-cardinality metricsSampling, log levels, retention tiers, lifecycle rules for storage, bounded labels

§4Hot Paths and Tail Latency

Optimize what users hit most and feel most. Under fan-out, tail latency dominates: if a page waits on ten parallel calls, the page is as slow as its slowest, so each service's p99 matters far more than its average. Techniques include timeouts and fallbacks, hedged requests (sending a second request if the first is slow, only for idempotent reads), and removing synchronous dependencies from the critical path.

§5Optimize With Discipline

  • Set a target and a budget ("p95 under 250 ms at 500 requests per second"), so you know when you are done.
  • Change one thing, re-measure, and keep a record of the effect size. Many "optimizations" do nothing, or make things worse.
  • Weigh engineering cost. A week of work to save $50 a month is a poor trade; a one-line index that saves $5,000 is not. Compare against engineer-time and risk.
  • Beware premature optimization: clarity first, and optimize what the data shows to matter. But do not use the phrase to avoid obvious fixes like indexing a foreign key.
  • Protect your gains: add performance tests and cost alerts (budget thresholds, anomaly detection), so that regressions are caught.
Cheaper is often just faster The same changes (fewer queries, less data transferred, less repeated work) reduce latency and cost together. When a cost review and a performance review find the same culprit, the fix tends to be uncontroversial and durable.

§6Common Mistakes

MistakeWhat HappensFix
Optimizing by intuitionEffort goes into code that does not matterProfile and rank by total time or cost first
Looking only at average latency or only at average utilizationTail problems and wasted headroom hide behind averagesUse percentiles, and compare utilization against real peaks
No cost attribution or alertsSurprise bills and no idea which service or tenant caused themTag resources, track unit costs, and set budget alerts
Practice
  1. Use pg_stat_statements to list your top ten queries by total time and fix the worst one. Record before and after.
  2. Profile an endpoint under load with a flamegraph and name the single largest contributor.
  3. Compute the cost per 1,000 requests for your service from last month's bill and traffic, and propose two changes that would lower it.
Key takeaways
  • Tie cost and performance together with unit economics: cost per request, tenant, or order.
  • Profile and rank by total time or spend, then fix the biggest contributor, usually the database or repeated work.
  • Set targets, change one thing at a time, weigh engineering cost, and add guardrails against regression.
