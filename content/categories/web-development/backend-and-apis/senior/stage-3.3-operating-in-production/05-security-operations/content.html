Security Operations

Dependency scanning, secrets rotation, and incident readiness.

§1Security Is an Ongoing Practice

Earlier lessons covered building secure code. Security operations is what keeps it secure afterwards: new vulnerabilities are published daily, dependencies age, credentials leak, and people make mistakes. The aim is not perfection; it is to shrink the window in which weaknesses can be exploited, and to be ready when something gets through.

§2Dependency and Supply-Chain Hygiene

Most of the code you run is not yours. A typical Node service pulls in hundreds or thousands of transitive packages, and each is a potential entry point.

  • Scan continuously. Use npm audit, Dependabot or Renovate, and software composition analysis tools, in CI and on a schedule, because a package that was safe at release can have a vulnerability disclosed tomorrow.
  • Triage by exposure, not just severity. A critical CVE in a function you never call, or in a dev-only tool, is less urgent than a medium issue in your request-parsing path. Reachability analysis helps; so does knowing what is internet-facing.
  • Patch on a cadence. Set expectations: for example critical fixes within days, high within two weeks, the rest in regular maintenance. Small, frequent updates are easier and safer than yearly leaps.
  • Commit lockfiles and install with npm ci so builds are reproducible, and review dependency updates rather than auto-merging blindly.
  • Guard against malicious packages: beware typosquatting and newly published versions, consider a minimum release age before adopting updates, disable or audit install scripts where practical, and require two-factor authentication and provenance for any packages you publish.
  • Generate an SBOM (software bill of materials) for each release, so when a new vulnerability lands you can answer "are we affected?" in minutes.
# CI security gates (illustrative)
- run: npm ci
- run: npm audit --omit=dev --audit-level=high      # fail the build on serious production-dependency issues
- run: npx gitleaks detect --no-banner                # block committed secrets
- run: docker build -t api:${{ github.sha }} .
- run: trivy image --severity HIGH,CRITICAL --exit-code 1 api:${{ github.sha }}   # scan the container image

§3Least Privilege and Credentials

  • Narrow identities. Each service gets its own database user and cloud role with only the permissions it needs; the API's database user cannot drop tables, and the read-only reporting job cannot write.
  • Short-lived, automatically rotated credentials (workload identity, OIDC for CI) over long-lived keys; rotate on a schedule and immediately upon suspected exposure.
  • Protect people's access: single sign-on and multi-factor authentication for every engineer account (cloud console, source control, package registries), and prompt offboarding.
  • Segment the network so databases and internal services are not reachable from the internet, and a compromised service cannot freely reach the rest.

§4Detection: Know When Something Is Wrong

Prevention fails eventually, so detection matters. Alert on security-relevant signals using the audit logs and metrics from earlier lessons:

  • Spikes in failed logins, password resets, or token errors (credential stuffing).
  • A single account or IP touching many resources, unusual data export volumes, or access at odd hours.
  • New admin users, permission changes, API keys created, or changes to security settings.
  • Unexpected outbound connections or sudden egress spikes, and unusual processes or dependencies in containers.
  • Cloud audit trail events such as new access keys, disabled logging, or public storage buckets.

§5Incident Readiness for Security Events

A security incident follows the general incident process, with additional demands: contain (revoke credentials, isolate hosts, block the attacker) while preserving evidence (logs, snapshots) for investigation; eradicate the cause (patch, remove persistence, rotate everything the attacker could have seen); recover with verified-clean systems; and notify affected users, customers, and regulators as required. Breach-notification deadlines can be short (some regimes require notice within 72 hours), so know your obligations beforehand.

  • Maintain a security incident plan with named roles, contact lists (legal, communications, key vendors), and a decision tree for severity.
  • Keep offline, tested backups. Ransomware and destructive attackers target backups first. A backup you have never restored is a hope, so rehearse restores regularly.
  • Run tabletop exercises ("a customer reports seeing another tenant's data; what do we do?"), and commission periodic penetration tests to find what scanners cannot.
  • Offer a vulnerability disclosure policy and a security.txt so researchers know how to reach you.
Reduce the blast radius Assume some credential, dependency, or account will eventually be compromised. The question is how much damage it can do: narrow permissions, segmented networks, short-lived keys, and tenant isolation turn a catastrophic breach into a contained one.

§6Common Mistakes

MistakeWhat HappensFix
Scanning dependencies once at launchNew vulnerabilities in old packages go unnoticed for yearsScan in CI and on a schedule; patch to an agreed SLA
Shared, long-lived admin credentialsOne leak equals total compromise, and nobody knows who did whatPer-service and per-person identities, MFA, and short-lived credentials
Backups that have never been restoredDiscovering they are corrupt or incomplete during the disasterTest restores regularly and keep a copy that attackers cannot delete
Practice
  1. Add dependency, secret, and container scanning to your CI pipeline, and triage the findings into "fix now", "schedule", and "accept with reason".
  2. List the credentials your service uses, and for each write who can read it, how it is rotated, and what an attacker could do with it.
  3. Run a one-hour tabletop: "a leaked API key was used to download customer data." Write the containment, evidence, notification, and recovery steps.
Key takeaways
  • Keep software secure over time: continuous scanning, risk-based triage, and a regular patch cadence for dependencies and images.
  • Apply least privilege, short-lived credentials, MFA, and network segmentation to limit the blast radius.
  • Detect anomalies, rehearse security incidents and restores, and know your notification obligations in advance.
