Zero-Downtime Deploys & Migrations

Expand and contract, feature flags, and rollbacks.

§1Two Versions Always Overlap

A deployment is not an instant switch. During a rolling update, old and new application versions run at the same time, against the same database, and mobile apps and API clients in the wild lag behind for months. Zero downtime means every change must be compatible with the version before and the version after. The core technique is expand and contract (also called parallel change): break any incompatible change into a series of individually compatible steps.

§2Expand and Contract: Renaming a Column

Suppose users.fullname must become users.display_name. A single ALTER TABLE ... RENAME would instantly break every running old instance. Do it in phases, deploying between each:

  1. Expand: add the new column (nullable), a purely additive and safe change.
  2. Write both: deploy code that writes to both columns (and reads from the old).
  3. Backfill: copy existing data into the new column, in small batches.
  4. Switch reads: deploy code that reads from the new column. Both still receive writes, so rollback remains safe.
  5. Stop writing the old column, once you are sure no old code is running.
  6. Contract: drop the old column in a later release.
-- Phase 1: expand
ALTER TABLE users ADD COLUMN display_name TEXT;

-- Phase 3: backfill in small batches, so no long lock and no giant transaction
UPDATE users SET display_name = fullname
WHERE id IN (SELECT id FROM users WHERE display_name IS NULL ORDER BY id LIMIT 5000);
-- ...repeat (from a script with a short pause between batches) until 0 rows are updated

-- Phase 6: contract (a later release, after everything has moved on)
ALTER TABLE users DROP COLUMN fullname;

§3Operations That Lock Tables

Some schema changes take locks that block reads or writes on a busy table, which looks like an outage. Know the dangerous ones and use the safe alternatives:

RiskySafer approach
CREATE INDEXCREATE INDEX CONCURRENTLY (slower, but does not block writes)
Adding a NOT NULL column with a volatile default (older PostgreSQL rewrote the table)Add nullable, backfill in batches, then add the constraint
Adding a constraint (foreign key, CHECK) that must scan the whole tableADD CONSTRAINT ... NOT VALID then VALIDATE CONSTRAINT separately, which takes a weaker lock
Changing a column's type (often rewrites the table)Add a new column, dual-write, backfill, and swap
Long-running migration blocking behind a long query, and everything queuing behind itSet lock_timeout so the migration fails fast instead of stalling the application
BEGIN;
SET LOCAL lock_timeout = '3s';                       -- give up quickly rather than queue behind other sessions
SET LOCAL statement_timeout = '30s';
ALTER TABLE orders ADD CONSTRAINT orders_total_nonneg CHECK (total_cents >= 0) NOT VALID;
COMMIT;

ALTER TABLE orders VALIDATE CONSTRAINT orders_total_nonneg;   -- scans the table, but doesn't block writes

§4Compatible Code Changes

  • New code must tolerate old data and old code must tolerate new data, including unknown columns and extra JSON fields.
  • Deploy the schema before the code that needs it, and remove schema only after no code uses it.
  • Make API changes additive (the versioning lesson), and keep old fields until clients are gone.
  • Prefer migrations as a separate step from application rollout, so each can be observed and rolled back independently.

§5Feature Flags and Rollbacks

Feature flags separate deploying code from releasing behavior. Ship the new path dark, enable it for staff, then 1%, 10%, 100% of users, watching your SLOs, and switch it off instantly if it misbehaves, without a deploy. Clean up flags once rollout completes; stale flags become tangled, untested code paths.

if (flags.isEnabled("new-pricing-engine", { userId: req.user.id, tenantId: req.tenantId })) {
  return newPricing.quote(cart);                     // gradually rolled out; instantly reversible
}
return legacyPricing.quote(cart);

Plan for rollback before every release. Application rollback is easy if the schema stayed compatible; rolling back a migration that dropped or rewrote data is usually impossible, which is why destructive steps are last and separated by time. Combine progressive delivery (canary, gradual flag rollout) with automatic rollback on SLO regressions.

The contract step is the dangerous one Adding things is safe; removing things is where outages and data loss live. Delay destructive changes until you have evidence (metrics, logs, query statistics) that nothing uses the old column, field, or endpoint, and keep a backup you have actually restored.

§6Common Mistakes

MistakeWhat HappensFix
A single migration that renames or drops a column used by running codeInstant errors from old instances during the rolloutUse expand and contract across several deployments
Building indexes or adding constraints without CONCURRENTLY or NOT VALIDTable locks that block production trafficUse the non-blocking forms, with lock_timeout
Backfilling millions of rows in one transactionLong locks, replication lag, and bloatBatch it with pauses, and monitor load
Practice
  1. Plan, in numbered deployments, how to split a name column into first_name and last_name with zero downtime.
  2. Add a CHECK constraint to a large local table first the naive way, then with NOT VALID + VALIDATE, and compare the locks held using pg_locks.
  3. Put a risky code path behind a feature flag with a percentage rollout, and write down the metrics that would trigger switching it off.
Key takeaways
  • Old and new versions overlap during deploys, so every change must be compatible with both; use expand and contract.
  • Avoid blocking schema operations: concurrent indexes, NOT VALID constraints, batched backfills, and lock timeouts.
  • Use feature flags and progressive rollout, and treat destructive steps as the last, separate release.
