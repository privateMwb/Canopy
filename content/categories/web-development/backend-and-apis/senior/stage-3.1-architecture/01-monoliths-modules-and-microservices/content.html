Monoliths, Modules & Microservices

Choosing boundaries, and the cost of splitting.

§1Boundaries Are the Real Decision

"Monolith or microservices?" is usually the wrong first question. The question is where to draw boundaries, meaning which parts of the system can change, scale, fail, and be understood independently. A boundary can be enforced by folder conventions, by module APIs inside one process, or by a network between separately deployed services. Each step buys independence and charges you in complexity.

StyleShapeStrengthsCosts
MonolithOne deployable; code organized by technical layerSimple to build, test, deploy, and debug; transactions are freeBoundaries erode; everything scales and deploys together
Modular monolithOne deployable; strictly separated modules with explicit public APIsMost of the clarity of services with none of the networkRequires discipline (and tooling) to enforce boundaries
MicroservicesMany independently deployed services, each owning its dataIndependent deploys and scaling; team autonomy; fault isolationDistributed-systems problems, operational overhead, harder debugging and testing

§2What Splitting Actually Costs

A function call becomes a network call, and a network call can be slow, fail, time out, or succeed while the reply is lost. Splitting a monolith trades in-process certainty for all of the following:

  • No shared transaction. An operation spanning two services can no longer be one ACID transaction; you need sagas, compensation, and idempotency.
  • Partial failure. Service A can be healthy while B is down, so every call needs timeouts, retries, and a plan for degradation.
  • Operational load. Each service needs its own pipeline, monitoring, alerting, on-call knowledge, and security posture.
  • Harder debugging and testing. One request now spans many logs and processes; reproducing a bug may require the whole constellation.
  • Data consistency and queries. A join across services becomes API calls or replicated data.

§3Reasons That Justify a Split

  • Team independence: many teams are blocked by each other's release cadence, and a clear domain boundary exists between them.
  • Different scaling or resource profiles: an image-processing workload needs GPUs and bursts, while the API does not.
  • Different reliability or compliance needs: payment handling that must be isolated and audited separately.
  • Different technology needs that cannot reasonably co-exist in one runtime.

Notice what is not on the list: "it's modern," "it will scale better someday," or "the code is messy." Messy code split across a network is still messy, plus distributed. The common failure is the distributed monolith: services that must be deployed together, share a database, or call each other synchronously in long chains, giving you every cost of both styles and the benefits of neither.

§4Modules Inside One Process

src/
  billing/
    index.js          <- the ONLY file other modules may import (the public API)
    internal/         <- everything else is private to the module
      invoices.js
      pricing.js
  notes/
    index.js
    internal/
  users/
    index.js

// Enforce it, don't just hope: lint rule (e.g. eslint-plugin-boundaries / dependency-cruiser)
// "no module may import from another module's internal/ folder"
// Modules talk through their public API or through events, never through each other's tables.

If modules cannot touch each other's tables, each already owns its data, and extracting one into a service later becomes a matter of replacing function calls with network calls at a boundary you have already proven.

§5Evolving Safely

  • Start modular, split on evidence. Extract when a specific pain (scaling, team contention, isolation) justifies the cost, and not before.
  • Strangler fig migration: put a routing layer in front, move one capability at a time behind it into a new service, and retire the old code gradually.
  • Own your data. A service that shares a database with another has not really been separated; integrate through APIs and events.
Conway's Law is a design tool Systems tend to mirror the communication structure of the organization that builds them. Choose boundaries that match how teams actually own work; a service owned by three teams has no owner. Align the architecture and the org chart deliberately, or the org chart will decide for you.

§6Common Mistakes

MistakeWhat HappensFix
Splitting into services for fashion or "scale" that does not existLarge operational cost with no measurable benefitDefine the specific problem a split solves, and prove it with data
Services sharing one databaseHidden coupling: schema changes break other teams and deploys must coordinateEach service owns its data and exposes it through an API or events
Chains of synchronous calls between servicesLatency adds up and one failure cascadesReduce hops, use async messaging, and add timeouts and fallbacks
Practice
  1. Take an existing codebase (or a sample) and sketch its modules. For each, write the public API it would expose and the tables it would own.
  2. Identify one capability you believe should become a separate service, and write the three strongest reasons for and against, with evidence.
  3. Add a lint rule or dependency-boundary check that fails CI if one module imports another's internals.
Key takeaways
  • Boundaries matter more than deployment units; a well-structured modular monolith is a strong default.
  • Splitting into services trades in-process simplicity for network failure, eventual consistency, and operational load.
  • Split on evidence (team autonomy, scaling, isolation), keep data ownership clean, and avoid the distributed monolith.
