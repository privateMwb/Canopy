Domain Modeling & Clean Boundaries

Keeping business logic independent.

§1Business Rules Should Outlive Frameworks

Frameworks, databases, and delivery mechanisms change; the business rules ("an order cannot ship before it is paid", "a refund cannot exceed the charge") are the valuable, durable part. When those rules are scattered across route handlers and SQL queries, they are hard to find, test, and change. Domain modeling means giving those rules a clear home that does not depend on HTTP or the database.

§2Building Blocks of a Domain Model

ConceptMeaningExample
EntityHas an identity that persists as its attributes changeAn Order with id 918
Value objectDefined by its values, immutable, compared by valueMoney(5000, "USD"), an email address, a date range
AggregateA cluster of objects treated as one unit for consistency, accessed through a single rootOrder plus its OrderLines; rules like "total matches lines" are enforced inside
Domain serviceBusiness logic that does not belong to one entityPricing a basket across discounts
Bounded contextA boundary inside which a model and its language are consistent"Customer" means an account holder in Billing but a ticket requester in Support

The bounded context is the strategic idea: one universal model of the whole business is impossible, because the same word means different things to different parts of it. Draw explicit boundaries, let each context have its own model, and translate at the edges. These contexts are good candidates for your module (and, eventually, service) boundaries.

// A rich domain object: the rules live WITH the data, and invalid states are unrepresentable
export class Order {
  #lines = [];
  constructor(id, customerId) { this.id = id; this.customerId = customerId; this.status = "draft"; }

  addLine(sku, qty, unitPrice) {
    if (this.status !== "draft") throw new DomainError("Cannot modify a submitted order");
    if (!Number.isInteger(qty) || qty < 1) throw new DomainError("Quantity must be a positive integer");
    this.#lines.push({ sku, qty, unitPrice });
  }

  submit() {
    if (this.#lines.length === 0) throw new DomainError("Cannot submit an empty order");
    this.status = "submitted";
  }

  get total() { return this.#lines.reduce((sum, l) => sum + l.qty * l.unitPrice, 0); }
}

§3Ports and Adapters (Hexagonal Architecture)

Arrange code in layers where dependencies point inward. The domain knows nothing of Express or Postgres. It declares what it needs as an interface (a port), and the outer layers supply implementations (adapters). This is dependency inversion: high-level policy does not depend on low-level detail.

// application/submit-order.js: a use case. It depends on a PORT, not on pg or Express.
export async function submitOrder({ orderRepo, payments, clock }, { orderId, userId }) {
  const order = await orderRepo.get(orderId);
  if (!order || order.customerId !== userId) throw new NotFoundError();
  order.submit();                                    // domain rule
  await payments.authorize(order.id, order.total);   // port: any payment provider fits
  await orderRepo.save(order);
  return order;
}

// adapters/pg-order-repo.js: an ADAPTER implementing the port with Postgres
// adapters/stripe-payments.js: another adapter; tests use an in-memory fake instead

// http/routes.js: the delivery layer is thin: parse, call the use case, map errors to status codes
router.post("/orders/:id/submit", async (req, res) => {
  const order = await submitOrder(deps, { orderId: req.params.id, userId: req.user.id });
  res.json(toDto(order));
});
  • Testing becomes fast and easy: use cases run against in-memory fakes with no database or HTTP.
  • Replacing infrastructure is local: swapping a payment provider or database touches an adapter, not the business rules.
  • Controllers stay thin: they translate between the outside world and use cases.

§4Aggregates and Transactions

Design aggregates around consistency boundaries: what must be true together at the moment of commit. A single transaction should modify a single aggregate; consistency between aggregates is achieved eventually, via events. If you find a transaction needing five aggregates, the boundaries are probably wrong. This also tells you where service boundaries could one day safely fall.

Do not over-engineer simple CRUD These patterns pay off when business rules are rich and long-lived. A basic admin screen that stores and lists records does not need aggregates and ports; forcing them adds ceremony without benefit. Apply the structure where complexity actually lives, and keep the rest plain.

§5Common Mistakes

MistakeWhat HappensFix
Anemic models: entities that are bags of fields with all logic in services and handlersRules duplicated across endpoints and easy to bypassPut invariants inside the domain objects that own the data
Domain code importing the ORM, HTTP types, or frameworkBusiness logic cannot be tested or reused without infrastructureDepend on ports (interfaces); implement them in adapters
One giant model shared across the whole companyMeanings collide and every change ripples everywhereDefine bounded contexts and translate between them
Practice
  1. Identify two bounded contexts in a product you know, and list how a shared word (such as "customer" or "product") differs between them.
  2. Refactor one handler so its business rules move into a domain object and a use case that takes its dependencies as parameters, then test it with an in-memory fake.
  3. Choose an aggregate root for an e-commerce order and list the invariants it protects in a single transaction.
Key takeaways
  • Keep business rules in a domain model that does not depend on HTTP, SQL, or frameworks.
  • Ports and adapters point dependencies inward, making core logic fast to test and infrastructure swappable.
  • Use bounded contexts and aggregates to find consistent boundaries, and apply the heavier patterns only where complexity warrants.
