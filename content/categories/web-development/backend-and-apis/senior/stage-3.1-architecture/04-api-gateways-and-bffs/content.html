API Gateways & BFFs

Shaping APIs for different clients.

§1One Front Door for Many Services

When a system grows into several services, clients should not need to know the internal map: which service owns users, which owns orders, where each lives. An API gateway is a single entry point that receives external requests and routes them to the right backend, handling the concerns that every request shares.

  • Routing by path, host, or header to the right service, hiding internal topology and allowing services to move.
  • Authentication (verify tokens once at the edge) and coarse authorization.
  • Rate limiting, quotas, and abuse protection in one place.
  • TLS termination, request size limits, and CORS handled centrally.
  • Observability: consistent request ids, access logs, and metrics for all traffic.
  • Protocol translation and, sometimes, response caching.

Common choices include managed gateways (Amazon API Gateway, Google Cloud API Gateway, Azure API Management), and self-hosted ones (Kong, Envoy-based gateways, Traefik, NGINX).

# Illustrative gateway routing config (Kong-style, simplified)
routes:
  - path: /api/users     -> users-service:8080     plugins: [jwt-auth, rate-limit(100/min)]
  - path: /api/orders    -> orders-service:8080    plugins: [jwt-auth, rate-limit(60/min)]
  - path: /api/public    -> catalog-service:8080   plugins: [rate-limit(300/min)]
Keep the gateway thin The temptation is to put business logic in the gateway because it sees everything. Resist. A gateway full of domain rules becomes a bottleneck owned by no one, deployed by everyone, and a single point of failure for the entire company. It should handle cross-cutting concerns only.

§2The Backend for Frontend (BFF) Pattern

A mobile app, a web app, and a partner integration need different data shapes, payload sizes, and call patterns. A single general-purpose API ends up serving none of them well: mobile makes ten round trips on a slow network, web over-fetches, and every client team fights over one API. A BFF is a small backend owned by one client team that exists to serve that client: it aggregates calls to underlying services and shapes the response to exactly what the screen needs.

// Mobile BFF: one round trip for the home screen, with graceful degradation
app.get("/mobile/home", requireLogin, async (req, res) => {
  const signal = AbortSignal.timeout(800);            // total budget for downstream calls
  const [profile, orders, recs] = await Promise.allSettled([
    users.get(req.user.id, { signal }),
    orders.recent(req.user.id, { limit: 3, signal }),
    recommendations.forUser(req.user.id, { signal }),
  ]);

  res.json({
    user:   profile.status === "fulfilled" ? slim(profile.value) : null,            // required: if null, client shows login error
    orders: orders.status  === "fulfilled" ? orders.value.map(toCard) : [],         // optional: degrade to empty
    recommendations: recs.status === "fulfilled" ? recs.value.slice(0, 5) : [],     // optional: failure must not break the page
    degraded: [profile, orders, recs].some(r => r.status === "rejected"),
  });
});
  • Aggregation: fewer client round trips, with parallel downstream calls.
  • Shaping: smaller, client-specific payloads (and pagination or image sizes tuned for the device).
  • Isolation of change: the client team can evolve its BFF without negotiating with every service team.
  • Graceful degradation: decide which fields are required and which can be missing when a dependency fails.

§3Alternatives and Costs

  • GraphQL (and federation) can play the aggregation role generically: clients ask for what they need and a gateway composes subgraphs from many services.
  • Every extra hop adds latency and a failure point. Keep the gateway and BFFs stateless, horizontally scaled, and well monitored.
  • Beware duplication: several BFFs may re-implement similar aggregation. Share libraries, not business logic, and push shared rules down into the services.

§4Common Mistakes

MistakeWhat HappensFix
Putting business logic in the gatewayA central bottleneck with unclear ownershipKeep it to cross-cutting concerns; logic belongs in services
One generic API for web, mobile, and partnersClients over-fetch, make many calls, and block each otherGive each distinct client a BFF (or use a flexible query layer)
No timeouts or fallbacks when aggregatingOne slow service makes every screen slow or brokenSet a deadline per call, parallelize, and degrade optional data

Key takeaways
  • A gateway centralizes cross-cutting edge concerns (routing, auth, limits, TLS, observability) and should stay thin.
  • A BFF is a client-owned backend that aggregates and shapes data for one kind of client.
  • Always use timeouts, parallel calls, and graceful degradation when aggregating across services.
