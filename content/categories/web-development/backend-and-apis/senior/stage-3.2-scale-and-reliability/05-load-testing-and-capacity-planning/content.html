Load Testing & Capacity Planning

Finding limits before users do.

§1Find the Limits Before Users Do

You do not know how your system behaves under load until you load it. Load testing applies realistic traffic to a test environment to learn how latency and errors change as demand rises. Capacity planning turns those findings into decisions: how much infrastructure you need, how much headroom to keep, and what breaks first.

Test typeGoalShape
LoadDoes it meet targets at expected peak?Ramp to normal peak and hold
StressWhere does it break, and how?Keep increasing until failure
SpikeCan it survive a sudden surge?Jump rapidly to a high level, then drop
Soak (endurance)Do leaks or slow degradation appear over hours?Moderate steady load for a long time

§2Designing a Realistic Test

  • Model real traffic: use your production logs to get the mix of endpoints, read-to-write ratio, payload sizes, and user behavior. Hammering one endpoint tells you little.
  • Use realistic data: production-sized tables with realistic distributions. A database with 1,000 rows has different query plans than one with 100 million. Caches distort results if every request hits the same key.
  • Match the environment: same instance types, configuration, network topology, and dependencies (or realistic stubs with realistic latency). Results from a laptop do not transfer.
  • Generate load from separate machines, and make sure the load generator is not itself the bottleneck.
  • Define success up front: for example, p95 under 300 ms and under 0.1% errors at 500 requests per second.
// k6 script (run with: k6 run load.js)
import http from "k6/http";
import { check, sleep } from "k6";

export const options = {
  scenarios: {
    steady: {
      executor: "ramping-arrival-rate",              // OPEN model: a fixed arrival rate, like real users
      startRate: 50, timeUnit: "1s", preAllocatedVUs: 200, maxVUs: 1000,
      stages: [
        { target: 200, duration: "2m" },             // ramp up
        { target: 200, duration: "10m" },            // hold at target
        { target: 0,   duration: "1m" },
      ],
    },
  },
  thresholds: {
    http_req_duration: ["p(95)<300", "p(99)<800"],   // the test FAILS if these are breached
    http_req_failed: ["rate<0.001"],
  },
};

export default function () {
  const res = http.get(`${__ENV.BASE_URL}/api/notes?limit=20`, { headers: { Authorization: `Bearer ${__ENV.TOKEN}` } });
  check(res, { "status 200": r => r.status === 200 });
  sleep(Math.random() * 2);                          // think time
}

§3Open vs Closed Workload Models

In a closed model, a fixed set of virtual users each wait for a response before sending the next request. When the server slows, the load automatically drops, hiding the problem (a flaw called coordinated omission). Real users arrive independently regardless of how slow you are, which is an open model: requests arrive at a set rate. Prefer arrival-rate scenarios for web APIs, so that when latency rises, queues and errors build up as they would in production.

§4Reading the Results

  • Look at percentiles, not averages. The p95 and p99 reveal the slow tail that real users experience and that averages hide.
  • Find the knee. Latency stays flat as load increases, then rises sharply at saturation. The load just before the knee is your practical capacity, not the load at which it falls over.
  • Identify the first bottleneck by examining each resource, using the USE method (Utilization, Saturation, Errors) for CPU, memory, disk, network, connection pools, and database locks, while correlating with your tracing and metrics.

Little's Law helps you reason about concurrency: concurrency = arrival rate × average latency. At 500 requests per second with 200 ms average latency, about 100 requests are in flight. If latency doubles under stress, so does concurrency, and a fixed connection pool of 100 saturates, which is a common source of sudden cliffs.

§5From Test Results to Capacity Plans

  • Measure per-instance capacity (for example, 150 requests per second at acceptable latency) and divide forecast peak by it.
  • Keep headroom, often 30 to 50 percent above expected peak, for spikes, deploys, and the loss of an instance or availability zone (plan for N+1 or N+2).
  • Plan for the bottleneck you found, which is often the database, not the stateless tier.
  • Re-test regularly: after significant changes, before known peaks (sales events, launches), and as part of CI for performance-critical paths.
Fix one bottleneck at a time Removing the first bottleneck simply reveals the next. Change one thing, re-run the same test, and record the result. Keep a log of runs (date, version, configuration, results) so you can see capacity trends and catch regressions.

§6Common Mistakes

MistakeWhat HappensFix
Testing one endpoint with a closed-loop generatorUnrealistic results that hide the failures real traffic causesUse a traffic mix based on production and an arrival-rate (open) model
Testing against a small or empty databaseQuery plans and cache behavior differ from productionUse production-scale, realistically distributed data
Reporting average latencySlow requests, the ones users notice, are hiddenReport p95 and p99 and set thresholds on them
Practice
  1. Write a k6 (or similar) test for your API with a realistic mix of three endpoints and an arrival-rate profile, with pass/fail thresholds.
  2. Ramp the load until latency passes your target, identify the knee, and use metrics to name the first saturated resource.
  3. Compute the capacity needed for a forecast peak of 2,000 requests per second given a measured 180 requests per second per instance and 40 percent headroom with N+1.
Key takeaways
  • Load, stress, spike, and soak tests, run with realistic traffic and data, reveal limits before users do.
  • Use open-model arrival rates, read percentiles, find the knee, and identify the first bottleneck systematically.
  • Turn measurements into capacity plans with headroom and redundancy, and repeat the tests as the system changes.
