Resilience Patterns

Timeouts, circuit breakers, bulkheads, and backpressure.

§1Failure Is the Normal Case

In a system with many dependencies, something is always slow or down. The danger is not the initial failure but how it spreads: a slow downstream service ties up your threads or connections, your service stops responding, its callers pile up behind it, and a small problem becomes a cascading outage. Resilience patterns contain failures where they start.

§2Timeouts: The Foundation

A call with no timeout can wait forever, holding a connection, memory, and a user's patience. Every network call needs an explicit timeout, set from a latency budget: if the whole request must finish in 2 seconds, each dependency gets a slice, and the downstream timeouts must be shorter than the upstream ones.

const res = await fetch(`${PRICING_URL}/quote`, {
  method: "POST",
  body: JSON.stringify(cart),
  signal: AbortSignal.timeout(300),                  // fail fast: 300 ms budget for this hop
});

§3Retries, With Discipline

Retries rescue transient errors but can also multiply load on a struggling service: if every layer retries three times across three layers, one user request can become 27 calls. Retry only idempotent operations, with exponential backoff and jitter, a small attempt limit, and ideally a retry budget (retries limited to, say, 10% of traffic) so retries cannot overwhelm a service that is already failing.

§4Circuit Breaker

Like an electrical breaker, it stops calling a dependency that is clearly failing, failing fast instead of waiting on timeouts, and gives the dependency room to recover. It has three states:

  • Closed: calls flow normally; failures are counted.
  • Open: after too many failures, calls are rejected immediately (or served a fallback) for a cool-down period.
  • Half-open: after the cool-down, a few trial calls are allowed; success closes the breaker, failure reopens it.
import CircuitBreaker from "opossum";

const breaker = new CircuitBreaker(callRecommendations, {
  timeout: 400,                                      // each call: 400 ms max
  errorThresholdPercentage: 50,                      // open when >=50% of recent calls fail
  rollingCountTimeout: 10_000,                       // ...measured over a 10 s window
  resetTimeout: 15_000,                              // try again (half-open) after 15 s
});

breaker.fallback(() => ({ items: [], degraded: true }));   // degrade instead of failing the whole page

const recs = await breaker.fire(userId);

§5Bulkheads: Isolate Resources

Ships have watertight compartments so one leak does not sink the vessel. Apply the same idea by giving each dependency (or each customer tier) its own pool of resources, such as separate connection pools, worker queues, or concurrency limits, so one slow dependency can exhaust only its own share.

import pLimit from "p-limit";

const limits = {
  payments:        pLimit(20),                       // at most 20 concurrent calls to the payment provider
  recommendations: pLimit(5),                        // a flaky nice-to-have gets a tiny allowance
};

const recs = await limits.recommendations(() => breaker.fire(userId));

§6Backpressure and Load Shedding

When demand exceeds capacity, queues grow, latency explodes, and eventually everything times out, so no one is served. It is better to reject some work quickly and serve the rest well than to accept everything and fail everyone. Bound your queues and concurrency, and when full, return 503 Service Unavailable with Retry-After. Prioritize: shed analytics and batch traffic before checkout. Backpressure also means propagating the signal upstream, so producers slow down rather than flooding a consumer that cannot keep up.

let inFlight = 0;
const MAX_IN_FLIGHT = 200;

app.use((req, res, next) => {
  if (inFlight >= MAX_IN_FLIGHT && !req.isPriority) {
    return res.status(503).set("Retry-After", "2").json({ error: "Server busy, retry shortly" });
  }
  inFlight++;
  res.on("close", () => inFlight--);
  next();
});

§7Fallbacks and Graceful Degradation

Decide in advance what the product does when each dependency fails: show cached data, hide the optional widget, queue the action for later, or return a simpler result. Distinguish critical dependencies (cannot check out without payments) from optional ones (recommendations), and make sure optional ones can never take down the critical path.

Test failure on purpose Resilience code that has never run is a hope, not a feature. Inject latency and errors in staging (or carefully in production with chaos experiments) and verify that breakers open, fallbacks appear, and shedding kicks in. Pull the network cable on a dependency and watch what your dashboards and users see.

§8Common Mistakes

MistakeWhat HappensFix
No timeouts, or timeouts longer than the caller's ownRequests hang and failures cascade upstreamSet explicit timeouts from a latency budget, shorter downstream than upstream
Retrying at every layer without limitsRetry storms amplify an outageRetry at one layer, with backoff, jitter, limits, and budgets
Unbounded queues and concurrencyMemory grows, latency spikes, then the process diesBound them and shed load with 503 plus Retry-After
Practice
  1. Wrap a call to a flaky stub service with a timeout, a circuit breaker, and a fallback, then use a load generator to confirm the breaker opens during failures and closes after recovery.
  2. Add a concurrency cap to an expensive endpoint and show it returns 503 under overload rather than slowing everything.
  3. List the dependencies of one request in your system, mark each as critical or optional, and define a fallback for each optional one.
Key takeaways
  • Contain failures: timeouts everywhere, disciplined retries, circuit breakers, and bulkheads keep one problem from cascading.
  • Under overload, shed load and apply backpressure rather than accepting work you cannot finish.
  • Define fallbacks for optional dependencies and rehearse failures in testing.
