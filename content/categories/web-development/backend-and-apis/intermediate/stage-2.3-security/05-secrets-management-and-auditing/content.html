Secrets Management & Auditing

Rotating keys and knowing who did what.

§1From .env Files to Managed Secrets

Environment variables are fine for local work, but in production they have weaknesses: they sit in plain text in deployment configs, appear in process listings and crash dumps, and are hard to rotate or audit. A secrets manager (AWS Secrets Manager, Google Secret Manager, Azure Key Vault, HashiCorp Vault, Doppler, 1Password, and others) stores secrets encrypted, controls who can read each one, logs every access, and supports rotation.

  • Fetch at startup (or on demand with short caching) using the platform's identity, so the app authenticates by who it is, not by yet another stored password.
  • Prefer short-lived credentials over long-lived keys: workload identity and OIDC federation let a service or CI job obtain temporary credentials, leaving nothing permanent to steal.
  • Scope narrowly: each service gets access only to the secrets it needs, in the environment it runs in. Production secrets should not be readable from development laptops.

§2Rotation Without Downtime

Keys must be replaceable: people leave, systems leak, and compliance often requires it. Rotation fails when changing a secret means every consumer breaks at once. The fix is to support overlap, accepting both the old and new secret for a period.

// Verifying with multiple active signing keys (JWT example)
const keys = [
  { kid: "2026-03", secret: process.env.JWT_SECRET_NEW },       // used to SIGN new tokens
  { kid: "2025-09", secret: process.env.JWT_SECRET_OLD },       // still accepted for VERIFY
];

const signKey = keys[0];
const verifyKey = header => keys.find(k => k.kid === header.kid)?.secret;   // look up by key id

// Rotation steps:
// 1. Add the new key as a verifier, deploy.
// 2. Start signing with the new key, deploy.
// 3. After old tokens have expired, remove the old key.
  • Rotate on a schedule and immediately after any suspected exposure.
  • Automate it; manual rotation that nobody remembers is rotation that does not happen.
  • Give API keys that you issue to customers a way to create a second key before revoking the first.

§3Audit Logs: Who Did What, and When

Audit logging records security-relevant actions so you can investigate incidents, prove compliance, and deter abuse. It is different from debug logging: it is structured, retained longer, and protected from tampering.

CREATE TABLE audit_log (
  id          BIGSERIAL PRIMARY KEY,
  occurred_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  actor_id    BIGINT,                  -- who (user, service account); NULL for anonymous
  actor_ip    INET,
  action      TEXT NOT NULL,           -- 'user.login.failed', 'note.delete', 'role.grant'
  target_type TEXT,
  target_id   TEXT,
  request_id  TEXT,                    -- ties the entry to application logs and traces
  metadata    JSONB NOT NULL DEFAULT '{}'
);
-- Grant the app INSERT only; no UPDATE or DELETE on this table
  • What to record: logins and failures, password and email changes, permission and role changes, access to sensitive data, deletions, admin actions, and API key creation or revocation.
  • Never record secrets or sensitive content: not passwords, tokens, or full card numbers. Log identifiers and what changed, not the secret values themselves.
  • Make it append-only and ship it off the application host (a log service or write-once storage) so an attacker who compromises the app cannot erase their tracks.
  • Use a consistent actor and request id so one request can be traced across services.
Assume every secret will eventually leak Design so that leaks are survivable: short-lived credentials, narrow scopes, easy rotation, and audit logs that tell you what a leaked key was used for. Detection and recovery matter as much as prevention.

§4Common Mistakes

MistakeWhat HappensFix
Long-lived keys shared by many servicesOne leak compromises everything and rotation is painfulPer-service credentials, short lifetimes, and automated rotation
Logging full request bodies or tokens in audit entriesThe log becomes a second, less protected secret storeLog identifiers and metadata only; redact sensitive fields
Audit logs writable by the app that they describeAn intruder can delete the evidenceAppend-only permissions and off-host shipping
Practice
  1. Move one real secret from a .env file into a secrets manager (or a local equivalent such as Vault in dev mode) and read it at startup.
  2. Implement the two-key JWT verification above and walk through a rotation with tokens issued by both keys.
  3. Create an audit_log table and write entries for login success, login failure, and role changes. Then query it to answer: who deleted note 12, and from which IP?
Key takeaways
  • Use a secrets manager with narrow access, short-lived credentials, and audited reads instead of plain environment files in production.
  • Design for rotation with overlapping old and new keys, and automate it.
  • Keep append-only, structured audit logs of sensitive actions, without ever recording secrets.
