Unit & Integration Testing

Testing logic and endpoints against a test database.

§1What to Test, and at Which Level

Automated tests let you change code without fear. Backend tests fall into layers that trade speed for realism:

LevelScopeSpeedCatches
UnitOne function or module, with no I/O (pricing rules, validators, formatters)MillisecondsLogic errors
IntegrationYour app with a real database (and other real dependencies) through its HTTP interfaceTens to hundreds of msWiring, SQL, middleware, serialization, auth
End-to-endThe deployed system through its real entry pointsSecondsEnvironment and deployment problems

For API backends, the highest-value tests are usually integration tests: they exercise routing, validation, authorization, SQL, and JSON shape in one go. Keep many fast unit tests for pure logic, a solid set of integration tests for each endpoint, and only a few end-to-end checks.

§2Make the App Testable

Separate building the app from starting the server, so tests can drive it without opening a port.

// app.js: builds and exports the app; does NOT call listen()
export function buildApp({ pool }) {
  const app = express();
  app.use(express.json());
  app.use("/notes", notesRouter(pool));
  app.use(errorHandler);
  return app;
}

// server.js: the only place that listens
buildApp({ pool }).listen(config.PORT);
// notes.test.js  (Vitest or node:test; supertest drives the app in-process)
import request from "supertest";
import { describe, it, beforeAll, beforeEach, afterAll, expect } from "vitest";

let app, pool;
beforeAll(async () => {
  pool = new Pool({ connectionString: process.env.TEST_DATABASE_URL });   // a real, disposable Postgres
  await runMigrations(pool);
  app = buildApp({ pool });
});
beforeEach(() => pool.query("TRUNCATE notes, users RESTART IDENTITY CASCADE"));   // clean slate per test
afterAll(() => pool.end());

describe("POST /notes", () => {
  it("creates a note for the logged-in user", async () => {
    const { token } = await createUserAndLogin(app);
    const res = await request(app).post("/notes").set("Authorization", `Bearer ${token}`)
      .send({ title: "Hello", body: "World" });

    expect(res.status).toBe(201);
    expect(res.body).toMatchObject({ title: "Hello", body: "World" });
    expect(res.headers.location).toMatch(/^\/notes\/\d+$/);
  });

  it("rejects an empty title with 400", async () => {
    const { token } = await createUserAndLogin(app);
    const res = await request(app).post("/notes").set("Authorization", `Bearer ${token}`).send({ title: "" });
    expect(res.status).toBe(400);
  });

  it("refuses anonymous callers with 401", async () => {
    expect((await request(app).post("/notes").send({ title: "x" })).status).toBe(401);
  });

  it("does not let user B read user A's note", async () => {
    const a = await createUserAndLogin(app, "a@example.com");
    const b = await createUserAndLogin(app, "b@example.com");
    const note = await createNote(app, a.token, { title: "private" });
    const res = await request(app).get(`/notes/${note.id}`).set("Authorization", `Bearer ${b.token}`);
    expect(res.status).toBe(404);
  });
});

§3Habits of Good Backend Tests

  • Use a real database, not mocks. Mocking the database tests your mock; real Postgres (via Docker or Testcontainers) catches the SQL, constraint, and transaction bugs that actually occur.
  • Isolate tests. Reset state between tests (truncate, or wrap each test in a rolled-back transaction) so ordering never matters.
  • Test behavior through the public interface: request in, status and body out, rather than internal functions that change with each refactor.
  • Cover the unhappy paths: validation failures, missing auth, other users' data, duplicates, and not-found, since that is where bugs and security holes live.
  • Fake only the boundaries you do not own: email, payment providers, and the clock get test doubles; your own database does not.
  • Keep them deterministic: inject time and randomness, avoid sleeps, and never depend on the network.
A bug found becomes a test written When you fix a bug, first write a failing test that reproduces it, then make it pass. The test is the permanent record that this failure will never silently return.

§4Common Mistakes

MistakeWhat HappensFix
Mocking the database in integration testsTests pass while real SQL, constraints, or migrations failRun against a real, disposable database
Tests that depend on each other's data or orderRandom failures and impossible-to-debug suitesReset state before each test and build data in the test
Only testing the happy pathAuth bypasses and validation gaps ship to productionWrite tests for 400, 401, 403, 404, and conflict cases
Practice
  1. Refactor your API so the app is built by a function, then write integration tests for create, read, and not-found on one resource.
  2. Add tests proving user B cannot read, change, or delete user A's data, then temporarily break the ownership check and confirm the tests fail.
  3. Make the suite run in CI against a Postgres service container, and measure how long it takes.
Key takeaways
  • Favor integration tests that drive the real app against a real, resettable database.
  • Separate app construction from listening so tests run in-process and fast.
  • Test the unhappy paths (validation, auth, other users' data) as carefully as the happy one.
