Contract Testing

Keeping clients and servers in agreement.

§1The Problem: Two Teams, One Interface

The provider (your API) and its consumers (a web app, a mobile app, another service) are developed separately. A provider team renames a field, all its own tests pass, and the consumer breaks in production. Catching that with full end-to-end tests means spinning up every service together: slow, flaky, and often impossible to run before a merge.

A contract test checks that the two sides agree on the interface, without running them together. Each side is tested in isolation against a shared, explicit description of the interaction.

§2Consumer-Driven Contracts

In the consumer-driven approach (popularized by the Pact framework), the consumer writes down exactly what it relies on: this request, and these parts of the response. That recording is the contract. The provider then replays every consumer's contract against its real implementation as part of its own build.

// Consumer test: describes what the web app expects, runs against a Pact mock server
await provider
  .given("note 7 exists")                            // provider state
  .uponReceiving("a request for note 7")
  .withRequest({ method: "GET", path: "/notes/7", headers: { Accept: "application/json" } })
  .willRespondWith({
    status: 200,
    body: { id: like(7), title: like("SQL basics") },   // like(): match on type, not exact value
  });

await provider.executeTest(async mock => {
  const note = await new NotesClient(mock.url).get(7);
  expect(note.title).toBeDefined();
});
// Running this test produces a pact file (the contract), which is published to a broker
// Provider verification: replays each consumer's pact against the real API
await new Verifier({
  providerBaseUrl: "http://localhost:3000",
  pactBroker: process.env.PACT_BROKER_URL,
  provider: "notes-api",
  stateHandlers: {
    "note 7 exists": async () => { await seedNote({ id: 7, title: "SQL basics" }); },
  },
}).verifyProvider();
  • Only what the consumer uses is in the contract, so the provider is free to change everything else. This is what makes safe evolution possible.
  • Provider states ("note 7 exists") tell the provider how to set up data for each interaction.
  • A broker stores contracts and verification results, and a can-i-deploy check blocks a release that would break a consumer in the target environment.

§3Spec-Based Alternatives

If you already maintain an OpenAPI description, you can get much of the value more simply: validate real responses against the spec in your integration tests, generate the consumer's client from the same spec, and run a breaking-change detector (such as oasdiff) in CI to compare the new spec to the last released one. This is a provider-driven contract: the provider publishes it and consumers conform.

ApproachStrengthCost
Consumer-driven (Pact)Knows exactly who relies on what; supports many consumers; catches subtle breaksSetup, broker, and cultural buy-in from consumer teams
OpenAPI + diff in CICheap; reuses your spec as docs, validation, and client generationCannot tell which consumers use which fields; relies on the spec staying accurate
Contracts are a conversation The tooling matters less than the habit it enforces: a change to an interface is visible, checked automatically, and discussed with the people it affects before it reaches production.

§4Common Mistakes

MistakeWhat HappensFix
Relying on end-to-end tests to catch interface driftSlow, flaky, and run too lateVerify the contract independently on each side, in CI
Contracts that assert exact values everywhereBrittle tests that fail on harmless changesMatch on types and structure, and only for fields the consumer uses
Letting the spec and the implementation divergeThe spec lies and the tests prove nothingValidate real responses against the spec in tests
Practice
  1. Take an endpoint with an OpenAPI spec and write an integration test that validates its real response against the response schema.
  2. Run a diff tool between two versions of your spec and see which changes it flags as breaking.
  3. Write a consumer contract for one endpoint, then rename a response field in the provider and watch the verification fail.
Key takeaways
  • Contract tests verify that consumer and provider agree on the interface without running them together.
  • Consumer-driven contracts record exactly what consumers rely on; spec-based checks are a lighter alternative.
  • Run contract verification in CI so incompatible changes are caught before release.
