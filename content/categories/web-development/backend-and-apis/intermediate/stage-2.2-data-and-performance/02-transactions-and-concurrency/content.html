Transactions & Concurrency

ACID, isolation levels, and race conditions.

§1All or Nothing

Moving money between two accounts takes two updates. If the server crashes between them, money vanishes. A transaction groups statements so they succeed or fail together. Relational databases promise ACID behavior for them:

  • Atomicity: all of the changes happen, or none of them do.
  • Consistency: constraints hold before and after; a transaction cannot leave the data violating them.
  • Isolation: concurrent transactions do not see each other's half-finished work (to a degree you configure).
  • Durability: once committed, the data survives crashes.
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
UPDATE accounts SET balance = balance + 50 WHERE id = 2;
COMMIT;      -- or ROLLBACK to undo both

§2The Race Condition in Your Read-Modify-Write

Atomicity does not by itself stop two requests from interleaving. Consider a stock counter handled in application code:

// BUGGY: two requests can both read 1 and both think they succeeded
const { rows: [item] } = await db.query("SELECT stock FROM items WHERE id = $1", [id]);
if (item.stock > 0) {
  await db.query("UPDATE items SET stock = $1 WHERE id = $2", [item.stock - 1, id]);   // lost update
}

Both requests read stock = 1, both pass the check, and both write 0: two buyers got the last item. Three reliable fixes, from simplest to heaviest:

-- 1. Make it ONE atomic statement; let the database do the check
UPDATE items SET stock = stock - 1 WHERE id = $1 AND stock > 0 RETURNING stock;
-- 0 rows returned means sold out

-- 2. Pessimistic locking: lock the row until the transaction ends
BEGIN;
SELECT stock FROM items WHERE id = $1 FOR UPDATE;    -- other transactions wait here
UPDATE items SET stock = stock - 1 WHERE id = $1;
COMMIT;

-- 3. Optimistic locking: detect conflicts with a version column
UPDATE items SET stock = stock - 1, version = version + 1
WHERE id = $1 AND version = $2;                      -- 0 rows updated: someone else changed it, retry

§3Isolation Levels

Stronger isolation prevents more anomalies but costs concurrency. PostgreSQL's default is Read Committed: each statement sees only data committed before it began, so two reads in one transaction can return different results if someone commits in between.

LevelPreventsNotes
Read CommittedDirty readsPostgreSQL default; non-repeatable reads and lost updates are still possible
Repeatable ReadAlso non-repeatable readsA consistent snapshot for the whole transaction; may abort with a serialization failure
SerializableAll anomalies, behaving as if transactions ran one at a timeMay abort transactions; your code must retry them

If you use the higher levels, be ready to catch the serialization-failure error (SQLSTATE 40001) and retry the whole transaction.

§4Deadlocks and Keeping Transactions Short

A deadlock occurs when transaction A holds a lock B needs while B holds one A needs. The database detects this and aborts one of them. Reduce the chance by touching rows in a consistent order (always lower id first) and by keeping transactions short: never call an external API, wait on a user, or do slow work while holding locks.

Prefer the simplest tool that is correct A single atomic UPDATE ... WHERE statement beats application-level read-then-write in almost every case. Reach for explicit locks or higher isolation only when a rule really spans multiple rows or statements.

§5Common Mistakes

MistakeWhat HappensFix
Read, check, then write in application codeLost updates and double-spending under concurrencyUse one atomic statement, row locks, or version checks
Holding a transaction open across an HTTP callLocks pile up and the system stallsDo external calls before or after the transaction
Not retrying serialization failures or deadlocksRandom user-facing errors under loadCatch 40001 / 40P01 and retry the whole transaction
Practice
  1. Reproduce the lost-update bug by firing 20 parallel purchase requests at a stock of 5. Count how many succeed, then fix it with an atomic UPDATE and re-test.
  2. Open two psql sessions and demonstrate a non-repeatable read under Read Committed, then show it disappears under Repeatable Read.
  3. Create a deliberate deadlock between two transactions and read the error.
Key takeaways
  • Transactions give atomic, isolated, durable units of work, but concurrency bugs still hide in read-modify-write code.
  • Prefer a single atomic statement; otherwise use row locks or an optimistic version column.
  • Keep transactions short and retry on serialization failures and deadlocks.
