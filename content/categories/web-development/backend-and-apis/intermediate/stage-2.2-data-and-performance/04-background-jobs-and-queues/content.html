Background Jobs & Queues

Moving slow work out of the request.

§1Don't Make the User Wait

Sending a welcome email, resizing an image, generating a PDF, or calling a slow third-party API can take seconds, and if you do it inside the request, the user waits, a timeout can kill the work midway, and a traffic spike ties up your servers. A background job moves the slow work out of the request: the API records what needs to be done in a queue and answers immediately, and separate worker processes pick jobs up and run them.

// API process: enqueue and return right away
import { Queue } from "bullmq";
const emailQueue = new Queue("email", { connection: { url: process.env.REDIS_URL } });

app.post("/signup", async (req, res) => {
  const user = await createUser(req.body);
  await emailQueue.add("welcome", { userId: user.id }, {
    attempts: 5,                                      // retry up to 5 times
    backoff: { type: "exponential", delay: 2000 },    // 2s, 4s, 8s, ...
    removeOnComplete: 1000,                           // keep the last 1000 for inspection
  });
  res.status(201).json({ id: user.id });
});

// Worker process (separate from the API, can scale independently)
import { Worker } from "bullmq";
new Worker("email", async job => {
  const user = await getUser(job.data.userId);
  await mailer.send({ to: user.email, template: "welcome" });
}, { connection: { url: process.env.REDIS_URL }, concurrency: 5 });

§2What a Queue Gives You

  • Faster responses: the request does a few milliseconds of work instead of seconds.
  • Retries with backoff for flaky dependencies, handled by the queue rather than hand-written loops.
  • Load smoothing: a burst of 10,000 signups becomes a backlog that workers drain steadily instead of a crash.
  • Independent scaling: add workers when the backlog grows, without touching the API.
  • Scheduling: delayed and recurring jobs (nightly reports, reminders) share the same machinery.

§3Design Jobs for Failure

Most queues give at-least-once delivery: a job might run more than once (a worker crashes after sending the email but before acknowledging it). This is the same retry problem from the idempotency lesson, so make jobs idempotent:

  • Pass ids, not payloads, and load fresh data in the worker, so a retry sees current state rather than stale copies.
  • Record completion in your database (or use a unique job id) so the second run does nothing: check "already sent" before sending.
  • Use retries only for transient failures. A job failing because of bad data will fail forever; after the attempt limit it should land in a dead-letter queue (a failed-jobs set) that alerts a human.

§4Telling the Client What Happened

When the user needs the result of slow work, respond with 202 Accepted and a way to check progress, such as a job resource the client can poll or an event pushed over SSE.

POST /reports            -> 202 Accepted   Location: /reports/918
GET  /reports/918        -> 200 {"status": "running"}      ... later ...
GET  /reports/918        -> 200 {"status": "done", "downloadUrl": "https://..."}
Enqueue only after the data is committed If you enqueue inside a database transaction and the transaction rolls back, a worker may chase a row that never existed; if you enqueue first and the commit fails, same story. Enqueue after the commit, or use the transactional outbox pattern (write the job to a table in the same transaction and relay it) when you cannot afford to lose or phantom a job.

§5Common Mistakes

MistakeWhat HappensFix
Doing slow work inside the requestTimeouts, tied-up servers, and partial work on failureEnqueue and respond; process in workers
Non-idempotent jobs under at-least-once deliveryDuplicate emails, double chargesRecord completion and make repeats a no-op
Retrying forever with no dead-letter handlingPoison jobs loop endlessly and hide real failuresCap attempts, move failures to a dead-letter queue, and alert
Practice
  1. Add a queue and worker for sending a welcome email (log it instead of really sending). Kill the worker mid-job and confirm the job is retried.
  2. Make the job idempotent by recording sent emails in a table, then enqueue the same job twice and confirm one email.
  3. Design a 202 Accepted flow for a PDF export, including the status endpoint.
Key takeaways
  • Move slow or unreliable work to queue-fed workers and return quickly to the client.
  • Assume at-least-once delivery: pass ids, make jobs idempotent, and bound retries with a dead-letter queue.
  • Enqueue after commit (or use an outbox) and give clients a way to check on long-running work.
