File Storage & Third-Party Integrations

Object storage, email, and payments.

§1Files Don't Belong in Your Database or on Your Server

User uploads (avatars, documents, videos) seem simple until you run two servers: a file saved to server A's disk is invisible to server B, and a redeploy may wipe it. Storing large binary blobs in your relational database bloats backups and slows everything. The standard answer is object storage (Amazon S3, Google Cloud Storage, Cloudflare R2, and compatible services): cheap, durable, scalable storage reached over HTTP, with only a reference (the key) stored in your database.

§2Presigned URLs: Let the Client Upload Directly

Streaming big files through your API ties up your servers. Instead, your API authorizes the upload and hands the client a short-lived presigned URL that lets it upload straight to the bucket.

import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";
import crypto from "node:crypto";

const s3 = new S3Client({ region: process.env.AWS_REGION });

app.post("/uploads", requireLogin, async (req, res) => {
  const { contentType } = UploadRequest.parse(req.body);          // allow-list types, e.g. image/png
  const key = `avatars/${req.user.id}/${crypto.randomUUID()}`;    // never trust client file names
  const url = await getSignedUrl(
    s3,
    new PutObjectCommand({ Bucket: process.env.BUCKET, Key: key, ContentType: contentType }),
    { expiresIn: 300 }                                            // valid for 5 minutes
  );
  res.json({ uploadUrl: url, key });                              // client PUTs the file to uploadUrl
});
  • Keep buckets private by default and serve files through short-lived signed URLs or a CDN.
  • Validate content type and size limits, and consider scanning uploads for malware.
  • Store the key and metadata (owner, size, type) in your database, and confirm the upload completed before marking the record usable.

§3Third-Party Integrations

Email, payments, SMS, maps, and AI services mean your uptime now depends on someone else's. Treat every integration as an unreliable network call:

  • Set timeouts. A call with no timeout can hang a request, and eventually your whole server, when the provider has a bad day.
  • Retry transient failures with backoff, using idempotency keys for anything with side effects, such as charging a card.
  • Do slow or flaky calls in background jobs when the user does not need the answer immediately.
  • Wrap each provider behind your own interface (mailer.send(), payments.charge()), so swapping vendors and mocking them in tests is easy.
  • Keep secrets out of the client and apply the rate limits and quotas the provider documents.

§4Webhooks: Providers Calling You

Many providers (payments especially) notify you of events by sending an HTTP request to an endpoint you expose. Because anyone can POST to a public URL, you must verify the signature, and you must expect duplicates and out-of-order delivery.

// Signature verification needs the RAW body, so skip the JSON parser for this route
app.post("/webhooks/stripe", express.raw({ type: "application/json" }), async (req, res) => {
  let event;
  try {
    event = stripe.webhooks.constructEvent(req.body, req.get("stripe-signature"), process.env.STRIPE_WEBHOOK_SECRET);
  } catch {
    return res.status(400).send("Invalid signature");
  }

  // Idempotent: ignore events we've already processed
  const fresh = await pool.query(
    "INSERT INTO processed_events (id) VALUES ($1) ON CONFLICT DO NOTHING RETURNING id", [event.id]);
  if (fresh.rowCount === 0) return res.sendStatus(200);

  await queue.add("handle-stripe-event", { eventId: event.id });   // do the real work asynchronously
  res.sendStatus(200);                                              // acknowledge quickly
});
Acknowledge fast, process later Providers retry webhooks that do not return 2xx promptly. Verify, record the event id, enqueue the work, and respond. Doing the heavy lifting inline invites timeouts and duplicate deliveries.

§5Common Mistakes

MistakeWhat HappensFix
Saving uploads to local diskFiles vanish on redeploy and are missing on other instancesUse object storage and keep only the key in the database
No timeout on provider callsOne slow vendor hangs your whole APISet explicit timeouts and wrap calls in retries and circuit breakers
Trusting webhook payloads without verificationAnyone can forge a "payment succeeded" eventVerify the signature on the raw body and deduplicate by event id
Practice
  1. Build an upload flow: an endpoint that returns a presigned URL (use MinIO or LocalStack locally), then upload a file with curl and read it back.
  2. Wrap an email provider behind a mailer interface and write a fake implementation for tests.
  3. Write a webhook handler that verifies a signature, deduplicates by event id, and enqueues work. Replay the same event twice.
Key takeaways
  • Store files in object storage, upload via presigned URLs, and keep only references in the database.
  • Treat third-party calls as unreliable: timeouts, retries with idempotency, and background processing.
  • Verify webhook signatures, deduplicate events, and acknowledge quickly before processing.
