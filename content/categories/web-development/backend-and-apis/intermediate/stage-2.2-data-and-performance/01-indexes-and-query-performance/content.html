Indexes & Query Performance

Reading query plans and fixing slow queries.

§1Why Queries Get Slow

Without help, finding the notes for one user means reading every row in the table (a sequential scan). That is fine for a thousand rows and painful for fifty million. An index is a separate, sorted data structure (in PostgreSQL, usually a B-tree) that lets the database jump straight to matching rows, the way a book's index saves you from reading every page.

CREATE INDEX idx_notes_user_id ON notes (user_id);

-- Now this can use the index instead of scanning the whole table:
SELECT * FROM notes WHERE user_id = 42;

§2Read the Plan, Don't Guess

EXPLAIN ANALYZE runs the query and reports what the database actually did and how long each step took. It is the single most important performance tool you have. (Note that ANALYZE really executes the statement, so wrap data-changing queries in a transaction you roll back.)

EXPLAIN ANALYZE SELECT * FROM notes WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;

-- Before the index:
--   Seq Scan on notes  (cost=0.00..412000.00 rows=51 ...) (actual time=0.02..2310.55 rows=48 ...)
--   Filter: (user_id = 42)
--   Rows Removed by Filter: 9999952
--   Execution Time: 2311.2 ms
--
-- After a composite index (user_id, created_at DESC):
--   Index Scan using idx_notes_user_created on notes (actual time=0.03..0.09 rows=20 ...)
--   Execution Time: 0.12 ms
  • Seq Scan on a big table with a selective filter usually means a missing index.
  • Compare estimated and actual row counts. Large gaps mean stale statistics (run ANALYZE).
  • "Rows Removed by Filter" being huge is the signature of reading far more than you return.

§3Choosing and Shaping Indexes

  • Index the columns you filter, join, and sort on: foreign keys (user_id) are the classic missed case, since PostgreSQL does not create them automatically.
  • Composite indexes depend on column order. An index on (user_id, created_at) serves queries filtering on user_id, or on user_id and created_at, but not on created_at alone. Put equality columns first, then the range or sort column.
  • Partial indexes cover a subset: CREATE INDEX ON notes (user_id) WHERE archived = false is smaller and faster when most queries ignore archived rows.
  • Covering indexes add extra columns with INCLUDE so the query is answered from the index alone.

§4Indexes Are Not Free

Every index must be updated on each insert, update, and delete, takes disk space, and competes for memory. Adding an index for every column slows writes without helping reads. Index in response to real queries (check the slow-query log or pg_stat_statements), and drop the ones that are never used.

-- On a live production table, avoid blocking writes while building:
CREATE INDEX CONCURRENTLY idx_notes_user_created ON notes (user_id, created_at DESC);

§5Patterns That Defeat Indexes

Slow patternWhyFix
WHERE lower(email) = 'a@b.com'A function on the column hides it from a plain indexExpression index on lower(email), or store normalized values
WHERE name LIKE '%son'A leading wildcard cannot use a B-treeTrigram (pg_trgm) or full-text index

SELECT * on wide rowsFetches and transfers unneeded dataSelect only the needed columns
Measure before and after Performance work is empirical. Capture the plan and timing, change one thing, and measure again. Test with production-sized data: the plan for 100 rows says nothing about the plan for 50 million.

§6Common Mistakes

MistakeWhat HappensFix
No index on foreign key columnsJoins and lookups scan whole tablesIndex every foreign key you filter or join on
Indexing every column "just in case"Slower writes and bloated storageAdd indexes based on real slow queries; remove unused ones
Testing with tiny datasetsA query that looks fast locally collapses in productionTest with realistic volumes and read the plan
Practice
  1. Generate a million rows in a table, run EXPLAIN ANALYZE on a filtered query, add an index, and compare the plans and times.
  2. Create an index on (a, b) and test which of these can use it: WHERE a = 1, WHERE b = 2, WHERE a = 1 AND b = 2.
  3. Find your slowest query with pg_stat_statements (or your ORM's log) and explain its plan.
Key takeaways
  • Indexes turn full-table scans into targeted lookups; EXPLAIN ANALYZE shows which you are getting.
  • Composite index column order matters, and every index taxes writes, so add them deliberately.
  • Avoid patterns that defeat indexes, and always measure on realistic data.
