Realtime APIs

WebSockets and server-sent events.

§1When Request/Response Isn't Enough

Standard HTTP means the client must ask. For chat, live dashboards, notifications, collaborative editing, and progress bars, the server needs to push updates the moment something happens. There are four common techniques, in rough order of complexity.

TechniqueHow it worksBest for
PollingClient asks every N secondsLow-frequency updates; simplest; wasteful if nothing changed
Long pollingServer holds the request open until there is news, then client immediately re-asksFallback when nothing else is available
Server-Sent Events (SSE)One long-lived HTTP response; server streams events to the clientOne-way push: notifications, feeds, progress, LLM token streaming
WebSocketsUpgrades the connection to a persistent, full-duplex channelTwo-way, low-latency: chat, games, collaboration

§2Server-Sent Events

SSE is plain HTTP with Content-Type: text/event-stream. Browsers expose it through the built-in EventSource API, which reconnects automatically and can resume using the Last-Event-ID header. It is often the best first choice when data flows only from server to client.

app.get("/events", (req, res) => {
  res.set({
    "Content-Type": "text/event-stream",
    "Cache-Control": "no-cache",
    "Connection": "keep-alive",
  });
  res.flushHeaders();

  const send = (event, data) => res.write(`event: ${event}\ndata: ${JSON.stringify(data)}\n\n`);
  send("hello", { time: Date.now() });

  const heartbeat = setInterval(() => res.write(": ping\n\n"), 25_000);   // keeps proxies from timing out
  const unsubscribe = bus.subscribe(msg => send("update", msg));

  req.on("close", () => { clearInterval(heartbeat); unsubscribe(); });     // ALWAYS clean up
});

§3WebSockets

A WebSocket begins life as an HTTP request with an Upgrade: websocket header, after which the same TCP connection carries messages in both directions with very little overhead. Use it when clients also need to send frequent messages.

import { WebSocketServer } from "ws";

const wss = new WebSocketServer({ server: httpServer, path: "/ws" });

wss.on("connection", (socket, req) => {
  // Authenticate during the handshake (cookie or one-time ticket), not after
  socket.on("message", raw => {
    const msg = JSON.parse(raw);                      // validate it like any other input
    for (const client of wss.clients) {
      if (client.readyState === 1) client.send(JSON.stringify({ from: "someone", text: msg.text }));
    }
  });
});

§4Operating Realtime Connections

  • Connections are stateful and long-lived. Each one consumes memory and a file descriptor, so capacity is measured in concurrent connections, not requests per second.
  • Scaling out needs a shared bus. A message sent to server A must reach clients connected to server B, typically through Redis pub/sub, NATS, or Kafka.
  • Plan for disconnects. Mobile networks drop constantly: use heartbeats, automatic reconnection with backoff, and a way to catch up on missed events (sequence numbers or Last-Event-ID).
  • Authenticate and authorize. Browsers cannot set custom headers on a WebSocket handshake, so use cookies or a short-lived ticket, and validate every incoming message.
  • Proxies and load balancers often impose idle timeouts, so heartbeats matter.
Default to the simplest thing that works If updates are one-way, choose SSE over WebSockets: it works over ordinary HTTP, reconnects for free, and is far easier to operate. Reach for WebSockets when you truly need bidirectional, high-frequency messaging.

§5Common Mistakes

MistakeWhat HappensFix
Forgetting to clean up on disconnectLeaked timers and subscriptions slowly exhaust memoryHandle close and remove listeners and intervals
Storing connections only in one server's memoryMessages never reach users connected to other instancesFan out through a shared pub/sub layer
No heartbeat or reconnect logicIdle connections get silently dropped and clients show stale dataSend heartbeats and reconnect with backoff, then resync
Practice
  1. Build an SSE endpoint that streams a counter every second, and consume it with EventSource. Kill the server and watch the browser reconnect.
  2. Build a tiny WebSocket chat that broadcasts messages to all connected clients, then open it in three tabs.
  3. Explain what must change to run two instances of the chat server behind a load balancer.
Key takeaways
  • Pick the simplest realtime transport: polling, SSE for one-way push, or WebSockets for two-way messaging.
  • Long-lived connections are stateful: clean up on close, add heartbeats, and plan reconnection and catch-up.
  • Scaling across servers requires a shared pub/sub backbone, and every message still needs authentication and validation.
