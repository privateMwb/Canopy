WebSockets, SSE & Real-Time

Some data cannot wait for the user to refresh. Polling, Server-Sent Events, and WebSockets each solve real-time delivery differently, and choosing the simplest one that fits saves you a lot of operational pain.

§1Three Transports

All three move data from server to browser without a page reload, but they differ in direction, complexity, and how well they survive proxies and phones going to sleep.

TransportDirectionProtocolReconnectBest for
Polling (fetch on a timer)Client asksPlain HTTPBuilt in (it is just requests)Slow-changing data; simplest option
Server-Sent Events (EventSource)Server to client onlyHTTP streamAutomatic, with Last-Event-IDFeeds, notifications, progress, live dashboards
WebSocketBoth ways, low latencyOwn protocol after upgradeManual (you write it)Chat, collaboration, games, trading UIs

A useful rule: start with the simplest transport that meets the need. If data flows one way, SSE is nearly always simpler and sturdier than a WebSocket. Only reach for WebSockets when the client needs to send frequent, low-latency messages too.

§2Using SSE and WebSockets

// Server-Sent Events: one-way, auto-reconnecting, plain HTTP
const es = new EventSource("/api/events");
es.addEventListener("price", (e) => update(JSON.parse(e.data)));
es.onerror = () => console.warn("connection lost; the browser will retry");
// server sends:  event: price\ndata: {"sym":"ABC","px":12.3}\n\n   (Content-Type: text/event-stream)

// WebSocket: bidirectional
const ws = new WebSocket("wss://example.com/chat");     // always wss:// (TLS) in production
ws.addEventListener("open", () => ws.send(JSON.stringify({ type: "join", room: "general" })));
ws.addEventListener("message", (e) => handle(JSON.parse(e.data)));
ws.addEventListener("close", (e) => console.log("closed", e.code, e.reason));

EventSource reconnects on its own and resumes using the Last-Event-ID header, so a server that assigns event ids gives you missed-message recovery almost for free. A WebSocket does none of this. You must handle reconnection, backoff, and resynchronization yourself.

§3Making Real-Time Robust

The hard part of real-time is not the connection, it is the failure modes: networks drop silently, phones sleep, servers restart, and messages arrive late or twice. A robust client treats the connection as unreliable.

function connect(url, onMessage) {
  let attempt = 0, ws, heartbeat, closedByUs = false;

  function open() {
    ws = new WebSocket(url);
    ws.onopen = () => {
      attempt = 0;
      resync();                                           // fetch what we missed (e.g. since lastId)
      heartbeat = setInterval(() => ws.send('{"type":"ping"}'), 25000);
    };
    ws.onmessage = (e) => onMessage(JSON.parse(e.data));
    ws.onclose = () => {
      clearInterval(heartbeat);
      if (closedByUs) return;
      const delay = Math.min(30000, 500 * 2 ** attempt++) * (0.5 + Math.random() / 2);  // backoff + jitter
      setTimeout(open, delay);
    };
  }
  open();
  return { close() { closedByUs = true; ws.close(); } };
}

window.addEventListener("online", () => reconnectNow());
document.addEventListener("visibilitychange", () => { if (!document.hidden) checkConnection(); });
  • Reconnect with exponential backoff and jitter so a restarting server is not hit by every client at once.
  • Resynchronize after reconnecting: ask the server for what you missed, using a sequence number or timestamp. Do not assume the stream was gapless.
  • Make messages idempotent (include an id) so a duplicate is harmless.
  • Authenticate on connect (a short-lived token, since browsers cannot set arbitrary headers on WebSocket), and validate every incoming message as untrusted input.
  • Plan for scale: each open connection costs server memory, and load balancers need sticky routing or a pub/sub layer (Redis, NATS) between servers.
  • Show connection state to users ("Reconnecting...") and keep the UI usable offline where possible.
Prefer the boring option Polling is trivially reliable, SSE is simple and self-healing, and WebSockets are powerful but make you own every failure mode. Move up the ladder only when a requirement forces you.

§4Common Mistakes

MistakeWhat HappensFix
Choosing WebSockets for one-way updatesNeedless complexity and manual reconnectionUse SSE (or polling) for server-to-client feeds
Reconnecting immediately in a tight loopA server restart gets a stampede of clientsUse exponential backoff with jitter
Assuming no messages are lost while disconnectedThe UI silently shows stale or incomplete dataResync on reconnect using ids or timestamps
Trusting incoming messagesMalformed or malicious data can crash or exploit the clientValidate shape and sanitize before rendering
Practice
  1. Build a live counter with SSE, kill the server mid-stream, and watch EventSource reconnect on its own.
  2. Implement a WebSocket client with backoff, jitter, and a resync step, and test it by dropping the network in DevTools.
  3. Write a short decision note choosing a transport for three scenarios: a stock ticker, a chat, and a build-progress bar.
Key takeaways
  • Polling, SSE, and WebSockets trade simplicity for capability; choose the simplest that satisfies the need.
  • SSE reconnects automatically; WebSockets need your own backoff, heartbeat, and resync logic.
  • Design for unreliable connections: duplicates, gaps, and reconnection storms are normal.
