CSRF, Cookies & Auth in the Browser

Cookies are sent automatically, and that convenience is the root of cross-site request forgery. Choosing how the browser stores and sends credentials is one of the most consequential decisions in a web app.

§1CSRF and SameSite

Cross-site request forgery (CSRF) abuses automatic cookie sending. If you are logged in to bank.com, a malicious page can make your browser send a request to bank.com and the cookies go along, so the bank sees an authenticated request you never intended. SOP does not prevent this, because the attacker only needs to send, not read.

<!-- on evil.test: the browser attaches bank.com cookies to this request -->
<form action="https://bank.com/transfer" method="POST" id="f">
  <input name="to" value="attacker"><input name="amount" value="5000">
</form>
<script>document.getElementById("f").submit()</script>

The most effective modern defense is the SameSite cookie attribute, which tells the browser when to include a cookie on cross-site requests.

SameSiteSent on cross-site requests?Notes
StrictNeverStrongest; can break links arriving from other sites (first load is logged out)
LaxOnly top-level navigations using safe methods (GET)Browser default now; blocks cross-site POST forgery
None; SecureAlways (requires HTTPS)Needed for embedded/third-party use; offers no CSRF protection

Do not rely on SameSite alone for sensitive actions. Add an anti-CSRF token (a random value the server puts in the page and requires on each state-changing request, in a header or hidden field), or verify the Origin/Sec-Fetch-Site headers. Make sure GET requests never change state.

§2Cookies vs. Tokens in Storage

Where you keep a session credential decides which attacks you are exposed to. There is no perfect answer, but the trade-offs are clear:

ApproachXSS exposureCSRF exposure
Session cookie: HttpOnly; Secure; SameSite=LaxScript cannot read it (requests can still be made)Mitigated by SameSite + tokens
Token in localStorage, sent in an Authorization headerAny XSS can steal itNone (not sent automatically)
Token in memory only (JS variable)Reachable by XSS while the page livesNone; lost on reload (needs a refresh mechanism)
Set-Cookie: __Host-session=9f8a...; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=3600

// prefer the __Host- prefix: forces Secure, Path=/, and no Domain attribute
// the browser attaches it; script cannot read it
fetch("/api/me", { credentials: "include" });

// state-changing request with an anti-CSRF token
fetch("/api/transfer", {
  method: "POST",
  credentials: "include",
  headers: { "Content-Type": "application/json", "X-CSRF-Token": csrfToken },
  body: JSON.stringify({ to, amount }),
});

For most browser apps talking to their own backend, an HttpOnly session cookie plus SameSite and CSRF protection is the safer default than a long-lived token in localStorage. HttpOnly does not make XSS harmless (an attacker can still act as the user while the page is open), but it prevents the credential from being exfiltrated and reused elsewhere.

§3Sessions, Logout, and Sensitive Actions

Good session handling goes beyond where the credential is stored.

  • Rotate the session identifier at login to prevent session fixation, and expire it on the server at logout (clearing the cookie client-side is not enough).
  • Use short lifetimes for access, with a refresh mechanism, and an idle timeout for sensitive apps.
  • Require re-authentication (password or passkey) for dangerous actions such as changing email or paying.
  • Prefer passkeys / WebAuthn and standard flows (OAuth/OIDC with PKCE) over hand-rolled login; never put tokens in URLs, where they leak through history, logs, and Referer.
  • Defend against clickjacking with frame-ancestors 'none' (or X-Frame-Options: DENY) on pages with sensitive buttons.
  • Set Cache-Control: no-store on authenticated responses so a shared computer's Back button does not show the account.
Assume a request can be forged and a script can run Design for both: make state-changing requests prove they came from your own page (SameSite + token), and keep credentials where an injected script cannot copy them (HttpOnly).

§4Common Mistakes

MistakeWhat HappensFix
Changing state on GET requestsAny <img> or link can trigger the action; SameSite Lax allows top-level GETsUse POST/PUT/DELETE and require a CSRF token
Storing long-lived tokens in localStorageOne XSS bug lets an attacker steal the credentialUse an HttpOnly cookie or keep tokens short-lived in memory
Setting SameSite=None out of habitCookie is sent on all cross-site requests; CSRF returnsUse Lax or Strict unless cross-site use is required
"Logging out" by only deleting the cookieThe session stays valid if the cookie was copiedInvalidate the session on the server
Practice
  1. Build a vulnerable state-changing endpoint with a cookie session, attack it from a second origin, then stop the attack with SameSite and an anti-CSRF token.
  2. Compare, in a table, how an XSS bug and a CSRF bug would each affect an app using localStorage tokens versus HttpOnly cookies.
  3. Audit the cookies of a real site in DevTools and list which have HttpOnly, Secure, SameSite, and the __Host- prefix.
Key takeaways
  • CSRF exploits automatic cookie sending; SameSite plus anti-CSRF tokens (and safe GETs) defend against it.
  • HttpOnly cookies keep credentials out of reach of injected script; localStorage tokens expose them to XSS.
  • Rotate and invalidate sessions server-side, protect sensitive actions, and prefer standard auth flows.
