Profiling with DevTools

Profiling replaces guessing with evidence. Reading a flame chart and a heap snapshot is the skill that turns "the page feels slow" into a specific function and a specific fix.

§1Recording a Performance Profile

The Performance panel records everything the main thread does over time. For realistic results, profile a production-like build, in an incognito window (no extensions), with CPU throttling (4x or 6x slowdown) and network throttling enabled to approximate a mid-range phone.

  1. Open DevTools, choose Performance, enable CPU throttling and screenshots.
  2. Click Record, perform exactly one interaction (or reload with the reload button), then stop.
  3. Keep recordings short and focused on a single question, such as "why is this click slow?"

The recording shows tracks for frames, interactions, network, and the Main thread. Interactions that exceed the INP threshold are flagged, and the summary tab breaks time into scripting, rendering, painting, and idle.

§2Reading a Flame Chart

The Main track is a flame chart: time runs left to right, and the call stack grows downward. A bar's width is how long that function ran, including everything it called. The widest bars near the top of a task are where time goes.

What you seeWhat it means
Wide bar with a flat bottomSelf time is high: the function itself is slow
Wide bar with a deep stack under itIt is slow because of what it calls: follow the stack down
Many narrow repeated barsA function called far too often (a loop, an event storm)
Purple Recalculate Style / LayoutRendering work; check for forced reflow warnings
Yellow blocks from a third-party domainA third-party script is on the main thread

Use the Bottom-Up tab to sort functions by self time, which finds the single most expensive function across the whole recording, and the Call Tree tab to see who called it. Click any frame to jump to the exact source line, which works best with source maps enabled.

// add your own labels so the profile tells your story
performance.mark("search:start");
const results = runSearch(query);
performance.mark("search:end");
performance.measure("search", "search:start", "search:end");   // appears in the Timings track

console.time("render");   // also visible in the console
renderResults(results);
console.timeEnd("render");

§3A Method for Investigating

Profiling works best as a loop, not a one-off. Resist the temptation to fix the first thing you see.

  1. Define the problem with a number: "the filter click takes 600 ms on throttled CPU".
  2. Reproduce it reliably and record a profile of only that action.
  3. Find the biggest contributor (widest self time, or the longest task) and form a hypothesis.
  4. Change one thing, and record again under the same conditions.
  5. Compare the numbers. Keep the change only if the measurement improved, and then repeat or stop.
  • Lab data (DevTools) tells you why; field data (RUM, CrUX) tells you whether it matters to real users. You need both.
  • Profile on real devices when you can; desktop numbers can hide phone-sized problems.
  • Use the Memory panel and allocation sampling for memory issues, and the Network panel with throttling for loading issues.
  • Save profiles and record before-and-after numbers in the pull request: they are your evidence.
One change, one measurement If you change three things and the page gets faster, you do not know which one mattered, or whether one of them made things worse. Change one thing at a time and keep the numbers.

§4Common Mistakes

MistakeWhat HappensFix
Profiling a development build with extensions installedNumbers do not reflect what users seeProfile a production build in incognito with throttling
Optimizing the first function you noticeTime spent on something that is a tiny share of the totalSort by self time; fix the largest contributor
Recording a long, unfocused sessionImpossible to find the relevant momentRecord one interaction at a time
Relying on a fast laptop's numbersReal users on phones see much worseUse CPU throttling or test on a real device
Practice
  1. Record a slow interaction under 4x CPU throttling, and identify the function with the highest self time using Bottom-Up.
  2. Add performance.mark/measure around a function so it appears in the Timings track, then optimize it and show the before-and-after.
  3. Write a short before/after note (problem, hypothesis, change, measured result) for one real optimization.
Key takeaways
  • Profile production-like builds with throttling, focusing on a single interaction at a time.
  • In a flame chart, width is time; use Bottom-Up for self time and Call Tree for context.
  • Investigate with a loop: measure, hypothesize, change one thing, and measure again.
