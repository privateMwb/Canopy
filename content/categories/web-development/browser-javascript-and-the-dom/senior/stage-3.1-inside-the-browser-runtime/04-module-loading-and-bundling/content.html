Module Loading & Bundling

The browser can load modules natively, yet nearly every production site is bundled. Understanding what the browser does, and what a bundler changes, lets you decide how to ship code rather than just accepting defaults.

§1How the Browser Loads Modules

When it meets <script type="module" src="main.js">, the browser downloads the file, parses its import statements, then downloads those dependencies, and so on down the tree, before any module runs. This forms a dependency graph, and each level of imports can cost a network round trip: a waterfall.

<script type="module" src="/main.js"></script>
<!-- main.js imports a.js; a.js imports b.js; b.js imports c.js ...
     the browser cannot know about c.js until it has downloaded and parsed b.js -->

<!-- hints that flatten the waterfall -->
<link rel="modulepreload" href="/b.js">
<link rel="modulepreload" href="/c.js">

<!-- import maps let you use bare names without a bundler -->
<script type="importmap">
  { "imports": { "dayjs": "/vendor/dayjs.esm.js" } }
</script>

Modules are deferred by default, executed once, in dependency order, and in strict mode. Unbundled apps with hundreds of modules suffer from deep waterfalls and many requests, which is the main practical reason to bundle for production, though HTTP/2 and modulepreload narrow the gap.

§2What a Bundler Does

A bundler (Vite/Rollup, esbuild, webpack, Parcel) starts at your entry point, follows every import, and emits a few optimized files. It does several jobs at once, and it helps to separate them mentally:

JobWhat happensEffect
BundlingCombine many modules into few filesFewer requests, shallower waterfalls
Tree shakingDrop exports that nothing importsSmaller output (needs ES modules and side-effect-free code)
MinificationShorten names, remove whitespaceSmaller files
Code splittingEmit separate chunks for import() points and routesLoad only what the page needs
Hashingapp.3f9a1c.js filenames from contentSafe to cache forever
TransformsTypeScript, JSX, modern syntax to target browsersCompatibility
// code splitting: the chart code is its own chunk, fetched on demand
button.addEventListener("click", async () => {
  const { drawChart } = await import("./chart.js");
  drawChart(data);
});

// tree shaking works with named ES exports
import { debounce } from "lodash-es";        // only debounce ends up in the bundle
import _ from "lodash";                      // CommonJS: pulls in everything

§3Shipping Decisions

Bundling is a set of trade-offs, and good decisions come from measuring the result. A bundle analyzer shows exactly which dependencies take space, and often reveals that one library accounts for a third of your JavaScript.

  • Analyze: use rollup-plugin-visualizer or vite-bundle-visualizer and look for large or duplicated dependencies.
  • Split by route and by rarely used feature, so the first page loads only what it needs.
  • Long-term cache hashed files (Cache-Control: max-age=31536000, immutable), and never cache the HTML that references them.
  • Prefer small, ESM-friendly libraries over large CommonJS ones; check size before you add a dependency (e.g. bundlephobia).
  • Set a budget (for example, 170 KB of compressed JavaScript for the initial route) and fail the build when it is exceeded.
  • Differential loading is mostly unnecessary now: target modern browsers and let type="module" serve them directly.

Remember that bytes are only half the cost: JavaScript must also be parsed and executed, which is slow on mid-range phones. Shipping less code is the most reliable way to speed up both.

Measure the output, not the config You cannot reason about bundle size from package.json. Open the analyzer, look at what actually ships, and check what each dependency costs your users in transfer and execution.

§4Common Mistakes

MistakeWhat HappensFix
Importing a whole library for one functionLarge bundle with unused codeUse ES-module builds and named imports; check the analyzer
Putting everything in one bundleUsers download code for pages they never visitSplit by route and by feature with import()
Caching the HTML aggressivelyUsers get an old page pointing at deleted filesCache hashed assets forever; revalidate the HTML
Ignoring parse and execution costFast download, slow page on phonesReduce JavaScript, not just compress it
Practice
  1. Build a project with Vite, open a bundle visualizer, and identify the three largest dependencies.
  2. Turn a heavy feature into a dynamically imported chunk and confirm in the Network panel that it loads only on demand.
  3. Draw the module waterfall for a small unbundled app, then add modulepreload and compare timings.
Key takeaways
  • Native modules load as a dependency graph; deep import chains create network waterfalls.
  • Bundlers combine, tree-shake, minify, split, and hash; each job has a distinct effect.
  • Inspect the real output with an analyzer, split by route, cache hashed files forever, and set a budget.
