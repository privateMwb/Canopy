The Event Loop, Tasks & Microtasks

JavaScript in the browser runs on one thread. The event loop decides what runs next, and the difference between tasks and microtasks explains most surprising orderings you will ever see.

§1One Thread, One Call Stack

The main thread runs your JavaScript, handles input, computes styles and layout, and paints. Only one thing happens at a time. JavaScript functions run to completion on the call stack: nothing else, including a click handler or a repaint, can interrupt a function that is running.

Asynchronous work (timers, network, user events) is handled by the browser outside your code. When it finishes, the browser places a callback in a queue. The event loop takes the next callback from a queue and runs it, but only when the call stack is empty.

console.log("A");
setTimeout(() => console.log("B"), 0);
console.log("C");

// A, C, B
// the timeout callback waits in a queue until the stack is empty

§2Tasks and Microtasks

There are two kinds of queued work. A task (macrotask) comes from things like setTimeout, DOM events, and message events. A microtask comes from promise reactions (then, catch, finally, and the code after an await) and queueMicrotask.

SourceQueue
setTimeout, setIntervalTask
User input, click, message eventsTask
Promise.then, code after awaitMicrotask
queueMicrotask(fn), MutationObserverMicrotask
requestAnimationFrameBefore the next paint (its own step)

The rule: after each task, and whenever the call stack empties, the browser drains the entire microtask queue before it does anything else, including rendering and the next task.

console.log("1 sync");
setTimeout(() => console.log("4 task"), 0);
Promise.resolve().then(() => console.log("3 microtask"));
queueMicrotask(() => console.log("3b microtask"));
console.log("2 sync");

// 1 sync, 2 sync, 3 microtask, 3b microtask, 4 task

A popular question is why a promise callback runs before a setTimeout(…, 0) that was scheduled first. Because microtasks drain right after the current script, before the next task is picked.

§3Why It Matters: Starvation and Rendering

Rendering happens between tasks, not in the middle of them. A long-running task, or an endless chain of microtasks, blocks painting and input, and the page freezes.

// blocks the whole page: nothing repaints or responds for the duration
button.addEventListener("click", () => {
  status.textContent = "Working...";       // never painted
  for (let i = 0; i < 1e9; i++) {}         // main thread is busy
  status.textContent = "Done";
});

// microtasks can starve rendering too
function loop() { Promise.resolve().then(loop); }   // never yields to the browser

To let the browser paint, split work into smaller tasks and yield between them, for example with setTimeout(next, 0), scheduler.yield() where available, or by moving the work to a Web Worker (a later lesson).

async function processAll(items) {
  for (let i = 0; i < items.length; i++) {
    handle(items[i]);
    if (i % 100 === 0) {
      await new Promise((r) => setTimeout(r, 0));   // yield: browser can paint and respond
    }
  }
}
The ordering rule Run the current script, then all microtasks, then (possibly) render, then the next task. await and promises live in the microtask lane, timers and events in the task lane.

§4Common Mistakes

MistakeWhat HappensFix
Expecting setTimeout(fn, 0) to run right awayIt waits for the stack and all microtasks, plus a minimum delayTreat it as "later", not "now"
Long synchronous loops in event handlersThe page freezes; updates are not paintedChunk the work, yield, or use a worker
Unbounded promise chains that re-schedule themselvesMicrotask starvation: no renderingYield to a task with setTimeout or scheduler.yield()
Assuming await yields to renderingIt only yields to other microtasks and tasks, not necessarily a paintUse requestAnimationFrame or a task break to allow a paint
Practice
  1. Predict, then run, a snippet that mixes console.log, setTimeout, Promise.then, and queueMicrotask; explain each position in the output.
  2. Write a click handler with a heavy loop and show that the "Working..." text is never painted; then fix it with chunking.
  3. Draw the queues (stack, microtasks, tasks) for the snippet in section 2 at three moments in time.
Key takeaways
  • One thread runs your JS, input handling, and rendering; long tasks freeze the page.
  • After each task the browser drains all microtasks (promises, await) before rendering or running the next task.
  • Break up heavy work or move it off the main thread so the browser can stay responsive.
