Timers, requestAnimationFrame & Idle Callbacks

The browser gives you several ways to schedule code. Choosing the right one decides whether animation is smooth, background work stays out of the way, and timers behave in background tabs.

§1setTimeout and setInterval

setTimeout(fn, ms) runs fn once after at least ms milliseconds, and setInterval repeats. Both return an id for clearTimeout/clearInterval. The delay is a minimum, not a promise: if the main thread is busy, the callback waits.

const id = setTimeout(() => console.log("later"), 1000);
clearTimeout(id);

let ticks = 0;
const timer = setInterval(() => {
  if (++ticks === 5) clearInterval(timer);
}, 1000);

// timers in background tabs are throttled (often to once per second or less)

setInterval does not account for how long the callback takes, so overlapping or drifting runs are possible. A self-rescheduling setTimeout is safer for work that may take longer than the interval, and it lets you wait for async work to finish before scheduling the next run.

async function poll() {
  try { render(await getStatus()); }
  finally { setTimeout(poll, 5000); }     // next run only after this one is done
}
poll();

§2requestAnimationFrame

requestAnimationFrame(fn) runs fn just before the next repaint, usually 60 times per second, and pauses automatically in background tabs. It is the right tool for anything visual: it is synchronized with the screen, so there is no wasted work and no tearing.

let x = 0;
let last = performance.now();

function frame(now) {
  const dt = (now - last) / 1000;      // seconds since the last frame
  last = now;
  x += 200 * dt;                       // 200 px/second regardless of frame rate
  box.style.transform = `translateX(${x}px)`;
  if (x < 600) requestAnimationFrame(frame);
}
requestAnimationFrame(frame);

Use the timestamp to compute movement from elapsed time, not from frame count, so animation runs at the same speed on a 60 Hz and a 144 Hz display. It is also the right place to batch DOM writes: read layout first, then write, once per frame, to avoid forcing repeated layout.

§3requestIdleCallback and Scheduling Low-Priority Work

requestIdleCallback(fn, { timeout }) runs fn when the browser has nothing more important to do, and tells you how much idle time remains. It suits low-priority work such as sending analytics, prefetching, or pre-computing data.

function work(deadline) {
  while (queue.length && deadline.timeRemaining() > 1) {
    process(queue.shift());
  }
  if (queue.length) requestIdleCallback(work);   // continue later
}
requestIdleCallback(work, { timeout: 2000 });    // run within 2s even if busy

// fallback where unsupported (Safari)
const idle = window.requestIdleCallback ?? ((fn) => setTimeout(() => fn({ timeRemaining: () => 1 }), 1));

setTimeout"After a delay", debouncing, polling

Match the scheduler to the job Visual change belongs in requestAnimationFrame, urgent logic in microtasks or events, delayed work in setTimeout, and nice-to-have work in requestIdleCallback.

§4Common Mistakes

MistakeWhat HappensFix
Animating with setInterval(…, 16)Janky, drifts from the display, runs in hidden tabsUse requestAnimationFrame with elapsed time
Moving by a fixed amount per frameSpeed varies with the monitor's refresh rateMultiply by the time delta
Not clearing timers on teardownCallbacks run against removed elementsStore ids and call clear*
Using requestIdleCallback without a fallback or timeoutMay never run in a busy page or unsupported browserAdd timeout and a polyfill
Practice
  1. Animate a box across the screen with requestAnimationFrame using elapsed time, and verify speed stays constant when you throttle CPU in DevTools.
  2. Replace a setInterval poller with a self-scheduling setTimeout that waits for each request to finish.
  3. Defer a non-urgent task (such as sending analytics) to requestIdleCallback with a timeout fallback.
Key takeaways
  • Timer delays are minimums; background tabs throttle them.
  • Use requestAnimationFrame for visuals, with timestamp-based movement.
  • Push low-priority work to idle time so it never competes with input and rendering.
