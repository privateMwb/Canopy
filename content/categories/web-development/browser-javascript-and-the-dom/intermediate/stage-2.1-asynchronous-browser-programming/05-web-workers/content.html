Web Workers

A Web Worker runs JavaScript on a separate thread. Moving heavy computation there keeps the main thread free to respond to the user, at the price of explicit message passing.

§1Creating a Worker

A worker is a separate script with its own global scope, event loop, and thread. It has no access to the DOM and no window. The main thread and the worker communicate by sending messages.

// main.js
const worker = new Worker(new URL("./worker.js", import.meta.url), { type: "module" });

worker.postMessage({ numbers: bigArray });

worker.addEventListener("message", (e) => {
  console.log("sum:", e.data);
});
worker.addEventListener("error", (e) => console.error("worker failed", e.message));

// worker.js
self.addEventListener("message", (e) => {
  const sum = e.data.numbers.reduce((a, b) => a + b, 0);
  self.postMessage(sum);
});

Inside a worker, self is the global object. The worker can use fetch, timers, IndexedDB, and crypto, and it can import other modules. When you are finished, stop it with worker.terminate() from outside or self.close() from inside.

§2Message Passing and Transferables

Messages are copied using the structured clone algorithm: it handles objects, arrays, Map, Set, Date, and typed arrays, but not functions or DOM nodes. Copying a very large buffer is itself expensive, so you can transfer ownership instead: the buffer moves to the worker with no copy and becomes unusable on the sender's side.

const buffer = new ArrayBuffer(50 * 1024 * 1024);

worker.postMessage({ buffer }, [buffer]);     // transferred, not copied
console.log(buffer.byteLength);               // 0: it is detached here now

// request/response matching with ids
let nextId = 0;
const pending = new Map();
function call(payload) {
  return new Promise((resolve) => {
    const id = nextId++;
    pending.set(id, resolve);
    worker.postMessage({ id, payload });
  });
}
worker.addEventListener("message", ({ data }) => {
  pending.get(data.id)?.(data.result);
  pending.delete(data.id);
});

A request/response wrapper like call turns message passing into promises, which makes workers pleasant to use with async/await. Libraries such as Comlink automate exactly this.

§3When Workers Help, and When They Do Not

A worker is worth it for CPU-heavy work: parsing large files, image processing, search indexing, compression, or complex calculations. It does not help with work that is already asynchronous, such as waiting on the network, and it cannot touch the DOM, so the main thread still renders the result.

  • Starting a worker has a cost (a new thread and script), so keep one around and reuse it rather than spawning one per task.
  • Do not send huge objects back and forth on every keystroke; send small messages or transfer buffers.
  • For several tasks in parallel, create a small pool (often one fewer than navigator.hardwareConcurrency).
  • Shared workers and service workers are different kinds of worker with different purposes (the latter appear in the senior level).
// heavy filtering of 200k rows stays off the main thread
const filterWorker = new Worker(new URL("./filter.js", import.meta.url), { type: "module" });

input.addEventListener("input", () => {
  filterWorker.postMessage({ query: input.value });
});
filterWorker.addEventListener("message", (e) => renderRows(e.data.rows));
Measure first A worker adds complexity: separate files, message passing, and no DOM. Confirm in the Performance panel that a real long task exists before moving code into one.

§4Common Mistakes

MistakeWhat HappensFix
Trying to access document inside a workerReferenceError: workers have no DOMSend data back and update the DOM on the main thread
Posting large objects on every eventCopying costs as much as the work savedTransfer buffers, or send smaller messages
Creating a new worker for each taskStartup overhead dominatesReuse one worker or a small pool
Never terminating unused workersThreads and memory stay allocatedCall terminate() when done
Practice
  1. Move an expensive calculation (such as counting primes up to 5 million) into a worker and show that a CSS animation stays smooth.
  2. Wrap worker messaging in a call(payload) function that returns a promise, using message ids.
  3. Transfer a large ArrayBuffer to a worker and verify that its byteLength becomes 0 in the sender.
Key takeaways
  • Workers run in a separate thread with no DOM access; you communicate with postMessage.
  • Messages are cloned; use transferables for big binary data, and ids for request/response.
  • Use workers for CPU-bound work, reuse them, and verify with profiling that they help.
