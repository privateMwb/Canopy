Unit Testing with Vitest or Jest

Unit tests check small pieces of logic in isolation and run in milliseconds. A good set of them lets you change code with confidence, and pure functions make them nearly free to write.

§1A First Test

Vitest (built for Vite projects) and Jest share nearly the same API. A test file declares describe blocks (groups), test or it cases, and expect assertions. Install, name files *.test.js, and run.

npm install -D vitest
// package.json: "scripts": { "test": "vitest" }

// cart.js
export function cartTotal(items) {
  return items.reduce((s, i) => s + i.price * i.qty, 0);
}

// cart.test.js
import { describe, test, expect } from "vitest";
import { cartTotal } from "./cart.js";

describe("cartTotal", () => {
  test("sums price times quantity", () => {
    expect(cartTotal([{ price: 5, qty: 2 }, { price: 3, qty: 1 }])).toBe(13);
  });
  test("returns 0 for an empty cart", () => {
    expect(cartTotal([])).toBe(0);
  });
});

A good test has three parts: arrange the inputs, act by calling the code, and assert the result. Name tests by the behavior they check ("returns 0 for an empty cart") so that a failure explains itself.

§2Matchers, Async, and Mocks

toBe uses strict identity for primitives; use toEqual for deep comparison of objects and arrays. Async code is tested by returning or awaiting the promise.

expect(user).toEqual({ id: 1, name: "Ada" });
expect(list).toContain("dom");
expect(() => parse("{bad")).toThrow(SyntaxError);
expect(0.1 + 0.2).toBeCloseTo(0.3);

test("loads a user", async () => {
  const user = await getUser(1);
  expect(user.name).toBe("Ada");
});

import { vi } from "vitest";
test("calls the API once", async () => {
  const fetchMock = vi.fn().mockResolvedValue({ ok: true, json: async () => ({ id: 1 }) });
  vi.stubGlobal("fetch", fetchMock);
  await getUser(1);
  expect(fetchMock).toHaveBeenCalledTimes(1);
  expect(fetchMock).toHaveBeenCalledWith("/api/users/1");
});

A mock replaces a dependency (the network, a timer, the clock) with a controllable fake. Use vi.useFakeTimers() to test debounce and timeouts without waiting. Mock the edges of your system, and avoid mocking your own pure logic, or the test checks the mock instead of the code.

§3What to Test

  • Pure logic first: calculations, formatters, reducers, validators. They are the best return on effort.
  • Edge cases: empty inputs, zero, negatives, very large values, null and undefined, duplicates.
  • Behavior, not implementation: assert on outputs and effects a caller sees, so refactors do not break tests.
  • One reason to fail per test, and tests that do not depend on one another or on run order.
// parameterized tests cover many cases with one body
test.each([
  [0, "0 B"],
  [1023, "1023 B"],
  [1024, "1.0 KB"],
  [1048576, "1.0 MB"],
])("formatBytes(%i) is %s", (input, expected) => {
  expect(formatBytes(input)).toBe(expected);
});

Coverage reports (vitest --coverage) show which lines ran, but coverage measures execution, not correctness. A line can run without being checked. Use it to find untested areas, not as a goal in itself.

Testable code is separable code If a function needs a browser to be tested, it probably mixes concerns. Moving the logic into a pure function makes the test trivial, and improves the design at the same time.

§4Common Mistakes

MistakeWhat HappensFix
Using toBe on objects or arraysFails because the references differUse toEqual for structural comparison
Forgetting to await an async assertionTest passes before the assertion runsMake the test async and await
Mocking your own logicThe test verifies the mock, not the codeMock only external edges: network, time, storage
Tests that depend on each other's stateFail randomly or only in certain ordersReset state in beforeEach; keep tests independent
Practice
  1. Write tests for a formatBytes function using test.each, including 0, boundaries, and very large values.
  2. Test a function that calls fetch by stubbing it, and assert on both the result and the request made.
  3. Test a debounce helper using vi.useFakeTimers() and vi.advanceTimersByTime.
Key takeaways
  • Unit tests arrange, act, and assert on small pieces of logic; name them by behavior.
  • Use toEqual for structures, await async work, and mock only external dependencies.
  • Pure functions are the cheapest to test; coverage finds gaps but does not prove correctness.
