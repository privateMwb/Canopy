Error Monitoring & Logging

Once your app is in users' hands, you cannot open their console. Catching errors globally, reporting them with enough context, and reading minified stack traces through source maps is how you find out what is breaking.

§1Catching Errors Globally

Two global events catch what nothing else handled: error for uncaught exceptions and resource failures, and unhandledrejection for promises that rejected with no handler. Between them, they see almost every failure that escapes your own try/catch.

window.addEventListener("error", (e) => {
  report({
    type: "error",
    message: e.message,
    source: e.filename,
    line: e.lineno,
    col: e.colno,
    stack: e.error?.stack,
  });
});

window.addEventListener("unhandledrejection", (e) => {
  report({ type: "rejection", message: String(e.reason), stack: e.reason?.stack });
});

// handle errors where you can recover, and rethrow what you cannot
try { await save(); }
catch (err) { showToast("Could not save"); throw err; }   // rethrow so it is also reported

Cross-origin scripts report only "Script error." with no details unless they are served with CORS headers and loaded with crossorigin="anonymous". Frameworks usually provide an error-boundary mechanism too; use it to avoid a blank screen while still reporting.

§2Reporting and Context

Send reports with navigator.sendBeacon or fetch with keepalive: true, which survive page unloads. Raw messages are rarely enough; useful reports include the context needed to reproduce the problem.

function report(data) {
  const payload = JSON.stringify({
    ...data,
    url: location.href,
    ua: navigator.userAgent,
    release: "2026.10.3",
    time: new Date().toISOString(),
    userId: currentUser?.id ?? null,      // an id, never personal data
  });
  navigator.sendBeacon("/log", payload);
}

// rate-limit and de-duplicate so one bug does not flood the server
const seen = new Set();
function reportOnce(data) {
  const key = data.message + data.line;
  if (seen.has(key) || seen.size > 50) return;
  seen.add(key);
  report(data);
}

In practice most teams use a service (Sentry, Rollbar, and similar) that provides this and grouping, alerts, and breadcrumbs (the user actions leading up to the error). Whatever you use, scrub passwords, tokens, and personal data before sending, and respect user privacy rules.

§3Source Maps and Useful Logging

Production code is minified, so a stack trace points to app.min.js:1:48213. A source map maps that position back to your original file and line. Generate them in the build (build: { sourcemap: true } in Vite) and upload them to your monitoring service rather than serving them publicly if your source is private.

// vite.config.js
export default { build: { sourcemap: true } };

// structured logs are easier to search than free text
const log = {
  info: (msg, ctx) => console.info(JSON.stringify({ level: "info", msg, ...ctx })),
  warn: (msg, ctx) => console.warn(JSON.stringify({ level: "warn", msg, ...ctx })),
  error: (msg, ctx) => console.error(JSON.stringify({ level: "error", msg, ...ctx })),
};
log.error("checkout failed", { orderId, step: "payment" });
  • Log at meaningful levels and remove noisy debug logging from production builds.
  • Tag every report with a release version so you know which deploy introduced a bug.
  • Alert on new error types and rising rates, not on every single occurrence.
  • Track real-user failures too: failed requests (res.ok === false) are errors users feel even when no exception is thrown.
You can only fix what you can see Without reporting, bugs exist only in the minds of frustrated users. A small global handler, a release tag, and source maps turn "it is broken sometimes" into a specific line of code.

§4Common Mistakes

MistakeWhat HappensFix
No global error or unhandledrejection handlerProduction failures are invisibleRegister both and report to a log or service
Reporting with plain fetch during unloadRequest is cancelled and lostUse sendBeacon or keepalive: true
Including passwords or personal data in reportsA privacy and security problemScrub data; log ids, not content
Shipping no source maps (or exposing them carelessly)Unreadable traces, or leaked sourceGenerate them and upload privately to your monitoring tool
Practice
  1. Add error and unhandledrejection listeners that log a structured object, then trigger each on purpose.
  2. Enable source maps in your build and compare a minified stack trace with and without the map.
  3. Add a release version and a de-duplicating rate limit to your report function.
Key takeaways
  • window.onerror-style events and unhandledrejection catch what your own handlers missed.
  • Reports need context (URL, release, user id) sent with sendBeacon, with sensitive data removed.
  • Source maps turn minified traces into readable ones; tag every report with a release.
