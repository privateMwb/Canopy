Separating Concerns

A 500-line script that fetches, stores, and draws all at once is hard to change. Separating data, logic, and display into distinct pieces is the oldest idea in application design, and it works without any framework.

§1Why Separate?

Code that mixes DOM updates, business rules, and network calls in the same functions has a hidden cost: you cannot test the rules without a browser, you cannot change the markup without touching the logic, and every change risks something unrelated. Separation of concerns means each piece has one reason to change.

// tangled: fetching, rules, and DOM in one handler
button.addEventListener("click", async () => {
  const res = await fetch("/api/cart");
  const items = await res.json();
  let total = 0;
  for (const i of items) total += i.price * i.qty * (i.sale ? 0.9 : 1);
  document.querySelector("#total").innerHTML = "$" + total.toFixed(2);
  document.querySelector("#list").innerHTML = items.map((i) => `<li>${i.name}</li>`).join("");
});

This works, and it is already hard to answer simple questions: where is the discount rule? How do you test it? What if the list needs to show up in two places?

§2Model, View, Controller

A classic split has three roles. The model holds data and the rules about it, with no knowledge of the DOM. The view turns data into DOM and reports user actions. The controller connects them: it receives actions, asks the model to change, and tells the view to redraw.

// model.js: pure logic, testable in Node
export function cartTotal(items) {
  return items.reduce((sum, i) => sum + i.price * i.qty * (i.sale ? 0.9 : 1), 0);
}

// api.js: all network access in one place
export const getCart = () => fetch("/api/cart").then((r) => r.json());

// view.js: only DOM
export function renderCart(root, items, total) {
  root.querySelector("#total").textContent = `$${total.toFixed(2)}`;
  root.querySelector("#list").replaceChildren(
    ...items.map((i) => Object.assign(document.createElement("li"), { textContent: i.name }))
  );
}

// main.js: the controller
import { cartTotal } from "./model.js";
import { getCart } from "./api.js";
import { renderCart } from "./view.js";

button.addEventListener("click", async () => {
  const items = await getCart();
  renderCart(document, items, cartTotal(items));
});

The same behavior now lives in four small files. The discount rule is a pure function you can test with plain input and output, the view can change without touching the rules, and the network layer can be swapped for a mock.

§3Seams and Dependencies

The goal is not a particular pattern name, it is clean seams: places where one part can be replaced or tested without the others. Aim for dependencies that point one way: the controller knows the model, view, and API; the model knows nothing about the others.

LayerKnows aboutMust not know about
ModelData and rulesDOM, fetch, window
ViewDOM, the data shape it rendersHow data is fetched or stored
API / storageNetwork and persistenceRendering
ControllerAll of the aboveDetails of each, only their interfaces

A useful test: could you run the model's code in Node, with no browser? If yes, the separation is real. Resist the urge to over-engineer: for a 50-line script, one file is fine. Separate when the pain of mixing appears, and let the structure follow the growth.

Pure functions are the easiest seam Move rules into functions that take data and return data. They need no DOM, no mocks, and no setup, which makes them the cheapest code to test and the safest to change.

§4Common Mistakes

MistakeWhat HappensFix
Business rules inside event handlersCannot be tested or reusedExtract them into pure functions in a model module
Reading state back from the DOMThe DOM becomes the source of truth and driftsKeep state in data; render the DOM from it
fetch calls scattered across the UI codeChanging an endpoint touches many filesCentralize in an api.js module
Splitting into many tiny files up frontIndirection with no benefitSplit when a file has more than one reason to change
Practice
  1. Take a single-file script and split it into model.js, view.js, api.js, and main.js, keeping behavior identical.
  2. Write three assertions for a pure model function in plain Node (no browser).
  3. Replace api.js with a fake that returns canned data and confirm the rest of the app works unchanged.
Key takeaways
  • Separating data/rules, display, and wiring lets each change and be tested independently.
  • Keep dependencies one-directional; the model should run without a browser.
  • Pure functions are the simplest and most valuable seam; split code when mixing starts to hurt.
