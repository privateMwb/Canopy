Rendering Strategies

Every UI has to keep the DOM in sync with its data. There is a spectrum of ways to do it, from hand-written updates to templates to batching, and each has a place.

§1Direct DOM Updates

The simplest approach is to update exactly the node that changed. It is the fastest at runtime and uses no libraries, but you must track which node corresponds to which data, and the code grows as the UI does.

const counter = document.querySelector("#count");
let count = 0;
button.addEventListener("click", () => {
  count++;
  counter.textContent = count;      // touch only the one node
});

This is a great fit for small, local updates such as a counter, a toggled class, or a progress bar. It becomes error-prone for lists whose items are added, removed, and reordered, because you must hand-maintain the correspondence between data and nodes.

§2Templates and Re-rendering

A more declarative approach is to write a function from data to DOM and re-render when data changes. The simplest form rebuilds the container's contents every time. It is easy to reason about because the DOM is always a pure function of state.

function render(todos) {
  list.replaceChildren(
    ...todos.map((t) => {
      const li = document.createElement("li");
      li.dataset.id = t.id;
      li.classList.toggle("done", t.done);
      li.textContent = t.text;
      return li;
    })
  );
}

// tagged template with escaping, for HTML strings
const esc = (s) => String(s).replace(/[&<>"']/g, (c) => `&#${c.charCodeAt(0)};`);
const html = (strings, ...vals) =>
  strings.reduce((out, s, i) => out + s + (i < vals.length ? esc(vals[i]) : ""), "");

list.innerHTML = todos.map((t) => html`<li data-id="${t.id}">${t.text}</li>`).join("");

Rebuilding everything is wasteful when only one item changed, and it destroys state held in the DOM: input focus, cursor position, scroll position, and a playing video are all lost when their element is replaced. Libraries like lit-html or frameworks use diffing to update only what changed.

§3Batching and Avoiding Layout Thrash

Touching the DOM is cheap; layout is expensive. Reading a layout property (offsetHeight, getBoundingClientRect) right after a write forces the browser to recalculate layout immediately. Doing that in a loop is called layout thrashing.

// thrashing: write, read, write, read ...
for (const el of items) {
  el.style.width = box.offsetWidth / 2 + "px";   // read forces layout each time
}

// batched: all reads first, then all writes
const w = box.offsetWidth / 2;
for (const el of items) el.style.width = w + "px";

// schedule visual writes once per frame
let queued = false;
function scheduleRender() {
  if (queued) return;
  queued = true;
  requestAnimationFrame(() => { queued = false; render(store.getState()); });
}

§4Common Mistakes

MistakeWhat HappensFix

Building HTML strings from data without escapingXSSEscape values or use DOM APIs and templates

Practice
  1. Render a to-do list with replaceChildren, then show what happens to focus in an input inside an item when you re-render.
  2. Reproduce layout thrashing on 2,000 elements, then fix it by separating reads from writes, and compare timings.
  3. Coalesce multiple dispatch calls in one tick into a single render with requestAnimationFrame.
Key takeaways
  • Direct updates are fastest; re-rendering is simplest; diffing scales best.
  • Escape or avoid string HTML, and preserve focus and scroll when re-rendering.
  • Batch DOM reads and writes and coalesce renders to avoid layout thrashing.
