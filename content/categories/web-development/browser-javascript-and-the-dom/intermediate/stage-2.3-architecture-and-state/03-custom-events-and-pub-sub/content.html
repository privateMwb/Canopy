Custom Events & Pub/Sub

When parts of an app need to talk without knowing about each other, events do the job. The DOM already has an event system you can extend, and a small pub/sub hub covers everything else.

§1CustomEvent and the DOM

You can create and dispatch your own events on any element with CustomEvent. They go through the same capturing and bubbling phases as built-in events, so a component can announce what happened without knowing who is listening.

class Cart {
  constructor(root) { this.root = root; this.items = []; }
  add(item) {
    this.items.push(item);
    this.root.dispatchEvent(new CustomEvent("cart:add", {
      detail: { item, count: this.items.length },   // payload goes in detail
      bubbles: true,                                // let ancestors hear it
    }));
  }
}

const root = document.querySelector("#cart");
const cart = new Cart(root);

document.addEventListener("cart:add", (e) => {
  badge.textContent = e.detail.count;
});
cart.add({ id: 1, name: "Book" });

Name events with a prefix (cart:add) so they do not collide with built-in ones. Remember that event listeners run synchronously when you call dispatchEvent, in the order they were added, before dispatchEvent returns.

§2A Tiny Pub/Sub

Publish/subscribe decouples senders and receivers through a named channel: publishers announce topics, subscribers listen to topics, and neither knows the other exists. EventTarget gives you this for free, with no DOM needed.

class Bus extends EventTarget {
  emit(type, detail) { this.dispatchEvent(new CustomEvent(type, { detail })); }
  on(type, fn, opts) {
    this.addEventListener(type, fn, opts);
    return () => this.removeEventListener(type, fn);   // unsubscribe function
  }
}

export const bus = new Bus();

// anywhere
const off = bus.on("user:login", (e) => greet(e.detail.name));
bus.emit("user:login", { name: "Ada" });
off();                                                 // stop listening

Returning an unsubscribe function from on makes cleanup easy and hard to forget. You can also pass an AbortSignal in the options to unsubscribe a whole group of listeners at once.

§3When Events Help, and When They Hurt

Events shine at loose coupling: a form announces saved and any number of widgets react. They are poor for anything where you need a result, ordering guarantees, or to understand the flow at a glance: control flow hidden behind events is hard to trace, because the call site gives no hint of who will respond.

SituationPrefer
One component notifies many unrelated partsEvents or pub/sub
You need a return value or errorA direct function call
Parent and child that already know each otherCallbacks or method calls
App-wide shared dataA store with subscriptions
Strict ordering of stepsExplicit calls, not events
  • Document your events: names and detail shape are an API.
  • Always unsubscribe listeners on long-lived buses when a component goes away.
  • Avoid event chains (A emits, B emits, C emits): they become impossible to debug.
  • Do not use events to fake a global variable; use real state instead.
Events are an API The event name and the shape of detail are a contract that other code depends on. Treat them like function signatures: name them clearly, keep them stable, and write them down.

§4Common Mistakes

MistakeWhat HappensFix
Forgetting bubbles: true on a custom eventListeners on ancestors never fireSet bubbles: true when parents should hear it
Never unsubscribing from a shared busHandlers run for removed components; memory leaksKeep and call the unsubscribe function
Chains of events triggering each otherFlow is impossible to followUse a direct call or a clear state change
Putting results in global variables instead of detailHidden coupling between modulesPass data in event.detail
Practice
  1. Create a Cart that dispatches cart:add and a badge that updates by listening, with no direct reference between them.
  2. Build the Bus class and use it to connect three independent modules, returning unsubscribe functions.
  3. List three situations in your own app where a direct function call would be clearer than an event, and explain why.
Key takeaways
  • CustomEvent lets any element announce things; put the payload in detail and set bubbles if needed.
  • EventTarget is a ready-made pub/sub hub; return an unsubscribe function from on.
  • Events decouple, but hide control flow: use them for notification, not for required results.
