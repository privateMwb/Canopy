Notifications, Geolocation & Permissions

Some browser features touch the user's privacy: location, notifications, camera, and more. Asking at the right time, handling every outcome, and degrading gracefully is as much a part of the work as the API calls.

§1The Permission Model

Sensitive APIs require user consent, and usually a secure context (HTTPS). The browser shows a prompt, remembers the answer per origin, and lets the user change it later in site settings. Each permission has three states: granted, denied, and prompt (not yet asked).

const status = await navigator.permissions.query({ name: "geolocation" });
console.log(status.state);        // "granted" | "denied" | "prompt"

status.addEventListener("change", () => {
  console.log("now", status.state);   // the user changed it in settings
});

Not every browser supports permissions.query for every feature, so treat it as a helper, not as a guarantee. The reliable approach is always to call the API and handle the rejection.

§2Geolocation

navigator.geolocation.getCurrentPosition asks for the device's location. It is callback-based, and the error callback receives a code that tells you why it failed.

function getPosition(options) {
  return new Promise((resolve, reject) =>
    navigator.geolocation.getCurrentPosition(resolve, reject, options));
}

button.addEventListener("click", async () => {
  try {
    const pos = await getPosition({ enableHighAccuracy: false, timeout: 8000, maximumAge: 60000 });
    const { latitude, longitude, accuracy } = pos.coords;
    showNearby(latitude, longitude);
  } catch (err) {
    // 1 = permission denied, 2 = unavailable, 3 = timeout
    if (err.code === 1) showMessage("Location blocked. Enter your city instead.");
    else showMessage("Could not find you. Enter your city instead.");
  }
});

Use watchPosition for continuous tracking and clearWatch to stop it; tracking drains the battery. Prefer low accuracy and cached positions (maximumAge) unless you truly need precision, and always provide a manual fallback such as typing a city or postcode.

§3Notifications and Asking Well

The Notifications API shows system notifications. You request permission once, and you should do so in response to a user action, never on page load. Browsers increasingly auto-block sites that prompt without context, and a denial is hard to undo.

async function enableAlerts() {
  if (!("Notification" in window)) return showMessage("Not supported here.");
  if (Notification.permission === "denied") return showHowToUnblock();

  const result = await Notification.requestPermission();   // call from a click
  if (result === "granted") {
    new Notification("Alerts on", { body: "We will tell you when it's ready.", icon: "/icon.png" });
  }
}
enableBtn.addEventListener("click", enableAlerts);
  • Explain the benefit before triggering the browser prompt (a "soft ask" in your own UI).
  • Handle all three outcomes: granted, denied, and dismissed.
  • Never make a core feature depend on a permission that the user can refuse.
  • Notifications for pushes that arrive when the page is closed need a service worker (a senior-level lesson).
Earn the prompt A permission request is a trust moment. Ask only when the user has just done something that needs it, say why in plain language, and have a working fallback if they say no.

§4Common Mistakes

MistakeWhat HappensFix
Requesting permission on page loadUsers deny by reflex; browsers may block the originAsk after a relevant user action
Not handling deniedFeature silently breaks, user is stuckDetect it and offer an alternative or instructions
Using high-accuracy watchPosition by defaultBattery drain and slow responsesUse low accuracy and cache unless precision matters
Testing only over http://Geolocation and clipboard APIs are blockedUse HTTPS or localhost
Practice
  1. Build a "find nearby" button that gets location with a timeout, and shows a manual city input if denied or unavailable.
  2. Add a soft-ask dialog before Notification.requestPermission() and handle all three results.
  3. Use permissions.query to show the current state for geolocation, and update the UI when it changes.
Key takeaways
  • Sensitive APIs need HTTPS and user consent; permission states are granted, denied, and prompt.
  • Always handle rejection and offer a fallback so the feature is optional, not required.
  • Request permission in response to a user action, with context, never on load.
