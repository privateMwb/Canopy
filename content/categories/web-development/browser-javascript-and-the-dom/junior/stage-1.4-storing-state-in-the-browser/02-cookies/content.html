Cookies

Cookies are small pieces of data the browser sends back to the server on every matching request. That makes them the right tool for sessions, and the attributes you set decide how safe they are.

§1How Cookies Work

A server sets a cookie with a Set-Cookie response header. From then on, the browser attaches it to later requests to that site in a Cookie header. Unlike Web Storage, cookies travel with the request automatically, which is why they carry login sessions.

// server response
Set-Cookie: session=abc123; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=3600

// later requests to the same site
Cookie: session=abc123

Cookies are limited to about 4 KB each, and because they are sent with every request, large cookies slow down every page, image, and API call to your site.

§2Reading and Setting from Script

Script can use document.cookie, an unusual string-based API. Reading returns all non-HttpOnly cookies as one name=value; name2=value2 string, and assigning to it sets one cookie, it does not overwrite the whole string.

document.cookie = "theme=dark; Max-Age=31536000; Path=/; SameSite=Lax";

function getCookie(name) {
  const pair = document.cookie
    .split("; ")
    .find((c) => c.startsWith(name + "="));
  return pair ? decodeURIComponent(pair.split("=")[1]) : null;
}

document.cookie = "theme=; Max-Age=0; Path=/";    // delete by expiring it

To delete a cookie, set it again with Max-Age=0 and the same Path (and Domain) it was created with. Values should be encoded with encodeURIComponent if they may contain special characters.

§3The Attributes That Matter

AttributeWhat it does
Max-Age / ExpiresHow long it lives; without them it is a session cookie (until the browser closes)
Path, DomainWhich URLs and hosts receive it
SecureOnly sent over HTTPS
HttpOnlyHidden from JavaScript: protects against theft by XSS
SameSite=Strict/Lax/NoneControls sending on cross-site requests; limits CSRF

For a login session cookie, the usual choice is Secure; HttpOnly; SameSite=Lax and a sensible expiry. Because an HttpOnly cookie cannot be set or read from script, session cookies are normally set by the server.

Cookies vs. Web Storage Use a cookie when the server needs the value on each request (sessions, auth). Use localStorage when only the page's script needs it (preferences, drafts). Do not duplicate data in both.

§4Common Mistakes

MistakeWhat HappensFix
Setting a session cookie without HttpOnlyXSS can steal the sessionSet HttpOnly on the server
Omitting Secure on a site served over HTTPSCookie can leak over plain HTTPAdd Secure
Assuming document.cookie = ... replaces all cookiesConfusing behavior and lost dataEach assignment sets exactly one cookie
Storing lots of data in cookiesEvery request gets slowerKeep cookies tiny; store data on the server or in storage
Practice
  1. Set a theme cookie from script, reload, and read it back with a getCookie helper.
  2. In DevTools (Application tab), inspect a site's cookies and note which have HttpOnly, Secure, and SameSite set.
  3. Delete your cookie by setting Max-Age=0 and confirm in DevTools; then try deleting with the wrong Path and explain why it fails.
Key takeaways
  • Cookies are sent with every matching request, which is what makes them suitable for sessions.
  • HttpOnly, Secure, and SameSite are the attributes that decide a cookie's safety.
  • Use cookies for what the server must see; use Web Storage for script-only data.
