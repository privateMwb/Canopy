Modules & Organizing Code

Once a script grows past a few hundred lines, one file stops working. ES modules let you split code into files with explicit imports and exports, and give each file its own scope.

§1export and import

A module is a file that declares what it shares with export and pulls in others with import. Everything else in the file stays private, so names cannot collide across files.

// math.js
export const TAU = Math.PI * 2;
export function area(r) { return Math.PI * r * r; }
export default function circumference(r) { return TAU * r; }

// main.js
import circumference, { area, TAU } from "./math.js";
import * as math from "./math.js";           // everything under one name
import { area as circleArea } from "./math.js";   // rename on import

console.log(area(2), circumference(2));

Each file can have one default export and any number of named exports. Many teams prefer named exports because the name is the same everywhere it is used, which makes searching and refactoring easier.

§2Using Modules in the Browser

Load the entry file with type="module". The browser then follows each import and fetches the dependencies, running each module once even if many files import it.

<script type="module" src="/src/main.js"></script>

// inside a module
import { render } from "./view.js";    // paths need the extension and "./"
const mod = await import("./chart.js"); // dynamic import: load on demand
  • Import paths must be relative (./, ../), absolute (/), or a full URL. A bare name like "lodash" needs a bundler or an import map.
  • Modules run in strict mode and top-level this is undefined.
  • Modules are fetched with CORS, so open your page from a local server, not from file://.
  • Imports are live bindings: if the exporting module changes an exported let, importers see the new value.

Dynamic import() returns a promise, which lets you load heavy code (a chart library, an editor) only when the user needs it.

§3Organizing a Small App

Split by responsibility rather than by file type. A tidy layout keeps each module small and focused, and keeps dependencies flowing in one direction.

src/
  main.js          // wires everything together
  state.js         // data and the functions that change it
  api.js           // all fetch calls
  view.js          // functions that turn state into DOM
  utils/
    dom.js         // $, $$, createEl helpers
    format.js      // date and number formatting

Avoid circular imports (A imports B, which imports A); they often work but produce confusing initialization-order bugs. If two modules need each other, move the shared piece into a third module.

Modules are the unit of reuse A good module has a small public surface (a few exports), hides its details, and depends on as few other modules as possible. That makes it easy to test, replace, and understand.

Practice
  1. Split a single-file to-do app into state.js, api.js, view.js, and main.js with named exports.
  2. Use dynamic import() to load a rarely used feature only when a button is clicked.
  3. Create a deliberate circular import, observe the problem, and fix it by extracting a module.
Key takeaways
  • ES modules give each file its own scope with explicit export and import.
  • Load them with type="module" from a server; use import() to load code on demand.
  • Split by responsibility and keep dependencies one-directional.
