CORS Basics

CORS errors are among the most confusing things a front-end developer sees. They make sense once you know what the browser is protecting and who is responsible for the fix.

§1Origins and the Same-Origin Rule

An origin is the combination of scheme, host, and port: https://app.example.com:443. By default, script running on one origin can send requests to another origin but is not allowed to read the response unless the other server says so. This protects users: otherwise any website you visit could read your email by calling a mail server where you are logged in.

PageRequest toSame origin?
https://a.comhttps://a.com/apiYes
https://a.comhttp://a.com/apiNo (scheme)
https://a.comhttps://api.a.comNo (host)
https://a.comhttps://a.com:8443No (port)

§2How CORS Works

Cross-Origin Resource Sharing (CORS) is the mechanism a server uses to say "yes, that origin may read my responses." It does this with response headers. The browser enforces it; the server grants it.

// page at https://app.com fetches another origin
fetch("https://api.other.com/data");

// browser sends:
//   Origin: https://app.com
// server must answer with:
//   Access-Control-Allow-Origin: https://app.com
// otherwise the browser blocks your script from reading the response

Some requests trigger a preflight: before the real request, the browser sends an OPTIONS request asking whether the method and headers are allowed. This happens for methods other than GET/HEAD/POST, for custom headers, and for Content-Type: application/json. The server must respond with Access-Control-Allow-Methods and Access-Control-Allow-Headers.

HeaderSent byMeaning
OriginBrowserWhere the request came from
Access-Control-Allow-OriginServerWhich origin may read the response
Access-Control-Allow-MethodsServer (preflight)Allowed methods
Access-Control-Allow-HeadersServer (preflight)Allowed request headers
Access-Control-Allow-CredentialsServerCookies may be included

§3Fixing and Avoiding CORS Errors

The error message shows up in the console, but the request often did reach the server; only your script is blocked from seeing the result. The fix is on the server (or in how you route requests), not in your fetch call.

  • Configure the API to send the correct Access-Control-Allow-Origin for your front-end origin (an explicit origin, not *, if cookies are involved).
  • During development, proxy API calls through your dev server so the browser sees one origin (Vite's server.proxy does this).
  • Serve the front end and API from the same origin (or behind one domain) in production.
// credentials need a specific origin and an explicit opt-in on both sides
fetch("https://api.other.com/me", { credentials: "include" });
// server: Access-Control-Allow-Origin: https://app.com
//         Access-Control-Allow-Credentials: true

// `mode: "no-cors"` does NOT fix it: you just get an opaque, unreadable response
CORS protects users, not servers A blocked response does not mean the server was unreachable. It means the server did not opt in to sharing with your origin. You cannot work around it from front-end code, and you should not try to.

§4Common Mistakes

MistakeWhat HappensFix
Trying to "fix" CORS in the fetch callNothing changes, or you get an unreadable opaque responseChange the server's headers or use a proxy
Using Access-Control-Allow-Origin: * with credentialsBrowser rejects the responseReturn the exact origin and allow credentials
Not handling the OPTIONS preflightEvery non-simple request failsRespond to OPTIONS with allowed methods and headers
Using a public CORS proxy for private dataA third party sees your trafficRun your own proxy or fix the API
Practice
  1. Call a public API that allows CORS and one that does not; compare the console error and the Network panel entry.
  2. Identify which of three URL pairs are same-origin, and explain which part differs in each.
  3. Configure a Vite dev-server proxy so /api is forwarded to a backend on another port.
Key takeaways
  • An origin is scheme + host + port; scripts cannot read cross-origin responses by default.
  • CORS is the server opting in through Access-Control-* headers; preflight OPTIONS checks non-simple requests.
  • Fix CORS on the server or with a proxy, never in the client request.
