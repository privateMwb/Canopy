Rendering Performance

Most React apps are fast enough. When one is not, the cure is measurement first, then fixing the specific cause. Memoizing everything by habit is the most common way to add complexity and gain nothing.

§1Measure Before You Optimize

Performance work without a profile is guessing. Use the React DevTools Profiler: click record, perform the slow interaction, stop, and read the flame chart. Each bar is a component render, and its width is how long it took. With *Record why each component rendered* enabled, it tells you the cause (props changed, state changed, parent rendered, context changed).

  1. Reproduce the slow interaction (typing in a field, opening a panel) with CPU throttling (4x) to mimic a mid-range phone.
  2. Profile a production build (npm run build && npm run preview). The development build is much slower and misleading.
  3. Look for long renders (wide bars) and components that render but did not need to (the same output as last time).
  4. Form a hypothesis, change one thing, and profile again. Keep the change only if the numbers improved.

Also check the browser's Performance panel: sometimes the cost is not rendering at all, but a long task in your own code, layout thrashing, or a big commit to the DOM.

§2The Usual Causes and Fixes

CauseFix
State held too high, so a keystroke re-renders the whole pageMove state down into the component that uses it
A slow component re-rendered by a parent that does not matter to itPass it as children, or wrap in memo (see below)
Expensive calculation on every renderuseMemo (or compiler caching), or reduce the work
Huge lists rendered in fullVirtualize (render only visible rows)
Context value changing oftenSplit the context, or use a store with selectors
Rendering work for UI the user cannot seeLazy load, defer, or conditionally render

§3memo, useMemo, useCallback, and Virtualization

These are targeted tools, not defaults. memo(Component) skips re-rendering when props are shallowly equal to last time. It only helps if the props are actually stable, which is where useMemo and useCallback come in: they keep object, array, and function props from being a new value on every render.

const Row = memo(function Row({ item, onSelect }) {      // skip if props are equal
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});

function List({ items }) {
  const [selected, setSelected] = useState(null);
  const onSelect = useCallback((id) => setSelected(id), []);     // stable function identity
  const sorted = useMemo(() => [...items].sort(byName), [items]); // recompute only when items change

  return <ul>{sorted.map((i) => <Row key={i.id} item={i} onSelect={onSelect} />)}</ul>;
}

  • A render is not a problem by itself. React is built to re-render often; it matters only when it is slow or repeated pointlessly.
  • memo with an unstable prop (an inline object, array, or function) does nothing, because the comparison always fails.
  • Each memo/useMemo adds code and a comparison. Use them where the profiler shows a payoff.
  • For long lists, virtualization is usually worth more than any amount of memoization.
  • Avoid creating state or doing heavy work in render: use useDeferredValue/useTransition (later lessons) to keep input responsive.
Fix the structure before the cache Moving state down or passing slow parts as children removes work entirely and costs nothing. Reach for memoization only after the structural fix and the profiler say it is needed.

§4Common Mistakes

MistakeWhat HappensFix
Wrapping everything in memo/useMemo "just in case"More code and comparison cost with no measurable gainProfile first; optimize the proven hot spot
Profiling in development modeNumbers are inflated and misleadingProfile a production build with CPU throttling
Passing inline objects or functions to a memoed componentProps differ every render; memo never skipsStabilize with useMemo/useCallback, or restructure
Rendering thousands of rowsSlow every update and scrollVirtualize the list
Practice
  1. Take a page where typing in a field is laggy, profile it, and fix it by moving state down. Show before and after in the Profiler.
  2. Create an example where memo has no effect due to an inline object prop, then fix it so that it works.
  3. Virtualize a 10,000-row list and compare DOM node count and interaction time.
Key takeaways
  • Profile a production build with throttling before changing anything.
  • Structural fixes (move state down, pass children, virtualize) beat sprinkling memoization.
  • memo, useMemo, and useCallback are targeted tools that only work with stable props.
