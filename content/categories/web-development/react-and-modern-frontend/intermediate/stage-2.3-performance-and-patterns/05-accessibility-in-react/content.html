Accessibility in React

React does not make an interface accessible or inaccessible: your markup does. Semantic HTML, managed focus, keyboard support, and the right ARIA let everyone use what you build, and most of it is simpler than it sounds.

§1Semantics First

The most effective accessibility work is using the right HTML element. A <button> is focusable, activates with Enter and Space, and is announced as a button, all for free. A <div onClick> has none of that and takes a lot of code to approximate.

// bad: not focusable, no keyboard activation, no role
<div className="btn" onClick={save}>Save</div>

// good
<button type="button" onClick={save}>Save</button>

// landmarks and headings give screen reader users a map of the page
<header>...</header>
<nav aria-label="Main">...</nav>
<main>
  <h1>Orders</h1>
  <h2>Recent</h2>
</main>
  • Use <button> for actions and <a href> (or router <Link>) for navigation.
  • Keep a logical heading order (one <h1>, then h2, h3 without skipping).
  • Associate every input with a <label>; give icon-only buttons an accessible name (aria-label="Close").
  • Give images meaningful alt text, or alt="" if purely decorative.
  • Use fragments (<>...</>) so extra wrapper divs do not break semantic structures like lists, tables, and description lists.
  • Ensure sufficient color contrast, and never convey meaning by color alone.

§2Focus Management and Keyboard Support

In a single-page app the browser does not reset focus for you when content changes. After a route change, an opened modal, or a removed item, you decide where focus goes, or keyboard and screen reader users are left stranded.

// move focus to the page heading after navigation
function Page({ title }) {
  const ref = useRef(null);
  useEffect(() => { ref.current?.focus(); }, []);
  return <h1 ref={ref} tabIndex={-1}>{title}</h1>;        // -1: focusable by script, not by Tab
}

// native <dialog> handles focus trapping, Escape, and the backdrop
function Modal({ open, onClose, children }) {
  const ref = useRef(null);
  useEffect(() => {
    const d = ref.current;
    if (open && !d.open) d.showModal();
    if (!open && d.open) d.close();
  }, [open]);
  return <dialog ref={ref} onClose={onClose}>{children}</dialog>;
}

// custom widgets: arrow-key navigation (roving tabindex)
function onKeyDown(e) {
  if (e.key === "ArrowRight") focusNext();
  if (e.key === "ArrowLeft") focusPrev();
  if (e.key === "Home") focusFirst();
}
  • Everything a mouse can do must be possible with the keyboard, and the focus indicator must always be visible (style :focus-visible, never outline: none alone).
  • Never use tabIndex greater than 0; use 0 to include an element and -1 for programmatic focus.
  • When a modal closes, return focus to the element that opened it.
  • Provide a skip link ("Skip to content") as the first focusable element on content-heavy pages.

§3ARIA, Live Regions, and Testing

The first rule of ARIA is: do not use ARIA if a native element does the job. When you build a custom widget, ARIA supplies the roles and states that HTML cannot. Keep those states in sync with your React state.

// disclosure
<button aria-expanded={open} aria-controls="faq-1" onClick={() => setOpen(!open)}>Shipping</button>
<div id="faq-1" hidden={!open}>...</div>

// announce changes that happen without focus moving
<div role="status" aria-live="polite">{saved && "Changes saved"}</div>
<p role="alert">{error}</p>                     // assertive: for errors

// labels for controls with no visible text
<button aria-label="Close dialog"><XIcon aria-hidden="true" /></button>
  • Install eslint-plugin-jsx-a11y: it flags missing alt text, invalid ARIA, and clickable non-interactive elements as you type.
  • In tests, query by role and accessible name (getByRole("button", { name: /save/i })); if it is hard to find that way, it is hard for users too.
  • Use axe DevTools or Lighthouse to catch about a third of issues automatically, then test by hand with the keyboard and a screen reader (VoiceOver, NVDA).
  • Respect prefers-reduced-motion and make sure text can be zoomed to 200% without loss.
  • Consider headless libraries (Radix UI, React Aria) for complex widgets (menus, comboboxes, dialogs) rather than building them from scratch.
Semantic HTML is 80% of the work A page built from real buttons, links, headings, labels, and landmarks is accessible by default. ARIA and focus management handle the custom parts, and testing with your keyboard catches what tools miss.

§4Common Mistakes

MistakeWhat HappensFix
Clickable <div>s and <span>sNo keyboard access or role for assistive techUse <button> or <a>
Removing the focus outlineKeyboard users cannot see where they areStyle :focus-visible clearly
Moving content without managing focusFocus is lost or left on a removed elementMove focus to the new content; return it after modals
Adding ARIA without keeping it in sync with stateScreen reader announces the wrong stateBind aria-expanded, aria-selected, etc. to React state
Practice
  1. Unplug your mouse and complete a task in a project of yours using only the keyboard; write down every place you got stuck.
  2. Add eslint-plugin-jsx-a11y and fix every warning.
  3. Build an accessible disclosure and a modal using <dialog>, with focus returning to the trigger on close.
Key takeaways
  • Use semantic HTML first: real buttons, links, labels, headings, and landmarks.
  • Manage focus after navigation and dialogs, and support the keyboard everywhere.
  • Use ARIA only where HTML falls short, keep it in sync with state, and test with tools plus the keyboard.
