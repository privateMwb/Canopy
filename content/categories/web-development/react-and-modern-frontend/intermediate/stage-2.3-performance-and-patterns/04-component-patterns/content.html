Component Patterns

A handful of design patterns keep components flexible without piling on props. Composition is the foundation, and compound components and render props build on it for the hardest cases.

§1Composition over Configuration

The easiest way to make a component flexible is to let callers put things inside it. Instead of a prop for every variation, accept children or named slots (props that take JSX). The component controls the structure; the caller controls the content.

// configuration: grows without end
<Card title="A" subtitle="B" showIcon icon="star" footerText="C" footerLink="/c" hasBorder />

// composition: flexible, readable, nothing to remember
<Card>
  <Card.Header><Star /> A</Card.Header>
  <Card.Body>B</Card.Body>
  <Card.Footer><a href="/c">C</a></Card.Footer>
</Card>

// slots as props when there are a few fixed regions
<Layout sidebar={<Nav />} header={<Header />}>
  <Page />
</Layout>

A useful rule: if you are adding a boolean prop to toggle part of the output, or a prop that takes a string for something that could be JSX, consider composition instead.

§2Compound Components

Compound components are a set of components that work together and share hidden state, like <select> and <option>. The parent owns the state and exposes it through context, and the children read it. The caller gets a flexible, declarative API.

const TabsContext = createContext(null);

function Tabs({ defaultValue, children }) {
  const [value, setValue] = useState(defaultValue);
  return (
    <TabsContext value={{ value, setValue }}>
      <div className="tabs">{children}</div>
    </TabsContext>
  );
}

function Tab({ id, children }) {
  const { value, setValue } = useContext(TabsContext);
  return (
    <button role="tab" aria-selected={value === id} onClick={() => setValue(id)}>
      {children}
    </button>
  );
}

function Panel({ id, children }) {
  const { value } = useContext(TabsContext);
  return value === id ? <div role="tabpanel">{children}</div> : null;
}

Tabs.Tab = Tab;
Tabs.Panel = Panel;

<Tabs defaultValue="a">
  <Tabs.Tab id="a">Overview</Tabs.Tab>
  <Tabs.Tab id="b">Details</Tabs.Tab>
  <Tabs.Panel id="a">...</Tabs.Panel>
  <Tabs.Panel id="b">...</Tabs.Panel>
</Tabs>

This pattern powers most good UI libraries (Radix, Reach, Headless UI). Add the accessibility behavior (roles, arrow-key navigation, focus) inside the components so that every user of them gets it for free.

§3Render Props, Custom Hooks, and Controlled/Uncontrolled

A render prop is a prop whose value is a function that returns JSX, letting the caller decide how to render data the component owns. Custom hooks replace most uses, but render props remain useful when the shared logic is tied to a piece of UI, such as a virtualized list's rows.

function Mouse({ children }) {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  return <div onMouseMove={(e) => setPos({ x: e.clientX, y: e.clientY })}>{children(pos)}</div>;
}
<Mouse>{({ x, y }) => <p>{x}, {y}</p>}</Mouse>

// usually simpler as a hook
function useMouse() { /* ... */ return pos; }

// a component that supports both controlled and uncontrolled use
function Toggle({ on: controlled, defaultOn = false, onChange }) {
  const [internal, setInternal] = useState(defaultOn);
  const isControlled = controlled !== undefined;
  const on = isControlled ? controlled : internal;

  function toggle() {
    if (!isControlled) setInternal(!on);
    onChange?.(!on);
  }
  return <button aria-pressed={on} onClick={toggle}>{on ? "On" : "Off"}</button>;
}
PatternUse when
Composition (children, slots)Default choice for flexible layout components
Compound componentsSeveral parts share state (tabs, accordion, menu, dialog)
Custom hookShare stateful logic with no UI attached
Render propLogic tied to UI the caller must customize
Controlled/uncontrolledReusable inputs and widgets that parents may want to drive
  • Avoid higher-order components and deep prop spreading in new code unless a library requires them; hooks and composition are clearer.
  • Use ...rest props to forward attributes and className to the underlying element so wrappers do not block normal usage.
  • Do not build a mega-component with 20 props and nested option objects. Split it.
Give callers slots, not switches Every boolean prop that rearranges a component's insides is a sign it wants to be composed instead. Let the caller place content, and keep the component responsible for structure and behavior.

§4Common Mistakes

MistakeWhat HappensFix
Adding a new prop for every variationComponents with dozens of props and tangled logicUse children, slots, or compound components
Compound components without accessibility roles and keysLooks right but unusable with a keyboard or screen readerBuild ARIA roles and keyboard handling into the parts
Using render props where a hook is simplerNested callbacks and hard-to-read JSXExtract a custom hook
Not forwarding className and other propsCallers cannot style or extend the componentAccept and spread ...rest
Practice
  1. Refactor a component with five boolean props into a composed version using children and slots.
  2. Build Tabs, Tab, and Panel compound components with context, and add role attributes.
  3. Make an input component that works both controlled and uncontrolled.
Key takeaways
  • Prefer composition: accept children and slots instead of many configuration props.
  • Compound components share state through context to give flexible, declarative APIs.
  • Hooks replace most render props; support controlled and uncontrolled use in reusable widgets.
