useReducer

When a component has several pieces of state that change together, a pile of useState calls gets hard to follow. useReducer moves all the update logic into one function that lists every way the state can change.

§1From Many Setters to One Reducer

A reducer is a pure function (state, action) => newState. Instead of calling setters from handlers, components dispatch small objects called actions that describe what happened ("added a todo", "toggled item 3"). The reducer decides how the state changes in response.

import { useReducer } from "react";

function reducer(state, action) {
  switch (action.type) {
    case "added":
      return [...state, { id: crypto.randomUUID(), text: action.text, done: false }];
    case "toggled":
      return state.map((t) => (t.id === action.id ? { ...t, done: !t.done } : t));
    case "deleted":
      return state.filter((t) => t.id !== action.id);
    default:
      throw new Error(`Unknown action: ${action.type}`);
  }
}

function Todos() {
  const [todos, dispatch] = useReducer(reducer, []);

  return (
    <>
      <AddForm onAdd={(text) => dispatch({ type: "added", text })} />
      <ul>
        {todos.map((t) => (
          <li key={t.id}>
            <input type="checkbox" checked={t.done} onChange={() => dispatch({ type: "toggled", id: t.id })} />
            {t.text}
            <button onClick={() => dispatch({ type: "deleted", id: t.id })}>x</button>
          </li>
        ))}
      </ul>
    </>
  );
}

Event handlers now say what happened, and the reducer, in one place, says how state changes. Name actions after the event in the past tense (added, toggled) rather than the setter you would call. This makes the data flow readable at a glance.

§2Rules for Reducers

  • Pure: the same state and action always produce the same result. No fetching, timers, Math.random(), or Date.now() inside the reducer (generate ids in the handler and put them in the action).
  • Never mutate state. Return a new object or array, exactly as with useState.
  • Always return state: the default case should throw (to catch typos) or return the current state.
  • React may call your reducer twice in StrictMode to check purity; it must give the same answer both times.

Because the reducer is a plain function, you can test it without React at all, which is one of the biggest benefits.

import { expect, test } from "vitest";

test("toggling flips done for one item", () => {
  const before = [{ id: "a", text: "x", done: false }, { id: "b", text: "y", done: false }];
  const after = reducer(before, { type: "toggled", id: "a" });
  expect(after[0].done).toBe(true);
  expect(after[1].done).toBe(false);
  expect(before[0].done).toBe(false);          // original not mutated
});

§3State Machines and When to Choose It

Reducers shine when state has explicit modes. Modeling a request or a wizard as a small state machine prevents impossible combinations, such as being both loading and in error.

const initial = { status: "idle", data: null, error: null };

function fetchReducer(state, action) {
  switch (state.status) {
    case "idle":
      return action.type === "started" ? { status: "loading", data: null, error: null } : state;
    case "loading":
      if (action.type === "succeeded") return { status: "success", data: action.data, error: null };
      if (action.type === "failed") return { status: "error", data: null, error: action.error };
      return state;
    case "success":
    case "error":
      return action.type === "started" ? { status: "loading", data: null, error: null } : state;
    default:
      return state;
  }
}
Prefer useState whenPrefer useReducer when
One or two independent valuesSeveral values that change together
Updates are simple assignmentsUpdates follow rules or have many cases
Logic fits in a handlerThe same logic is triggered from many places
No need to test the logic aloneYou want to unit-test transitions without React

You do not have to choose forever: start with useState and move to useReducer when handlers start to sprawl. dispatch has a stable identity, so passing it down (or putting it in context) does not cause extra re-renders the way new callback functions can.

Say what happened, not what to set Actions describe events (toggled, submitted). The reducer owns the rules. That separation is what makes complex state predictable and testable.

§4Common Mistakes

MistakeWhat HappensFix
Mutating state inside the reducer (state.push(x))No re-render or doubled changes in StrictModeReturn new arrays and objects
Doing side effects (fetch, random ids) in a reducerImpure; runs twice in dev and behaves unpredictablyDo effects in handlers or effects; pass results in the action
Forgetting a default case or returning undefinedState becomes undefined and the UI crashesThrow on unknown actions or return state
Using a reducer for a single booleanMore code with no benefitUse useState for simple state
Practice
  1. Convert a to-do component with three useState calls to a single useReducer, with add, toggle, delete, and clear-completed actions.
  2. Write three unit tests for the reducer that do not render any component.
  3. Model a request as a state machine with idle, loading, success, and error states, and confirm that loading plus error is impossible.
Key takeaways
  • useReducer centralizes state transitions in a pure (state, action) function.
  • Actions describe events; reducers own the rules and are trivially testable.
  • Use it when state has many related updates or explicit modes; otherwise useState is enough.
