Forms at Scale

Controlled inputs are fine for small forms, but large forms re-render on every keystroke and need consistent validation. React Hook Form and a schema library solve both, and keep the form accessible.

§1React Hook Form

React Hook Form (RHF) registers inputs with the DOM and reads their values on submit or on demand, rather than storing each keystroke in React state. The result: far fewer re-renders and less code per field.

import { useForm } from "react-hook-form";

function Signup({ onSubmit }) {
  const {
    register,
    handleSubmit,
    formState: { errors, isSubmitting },
  } = useForm({ defaultValues: { email: "", age: "" } });

  return (
    <form onSubmit={handleSubmit(onSubmit)} noValidate>
      <label htmlFor="email">Email</label>
      <input
        id="email"
        type="email"
        aria-invalid={errors.email ? "true" : "false"}
        aria-describedby={errors.email ? "email-error" : undefined}
        {...register("email", { required: "Email is required" })}
      />
      {errors.email && <p id="email-error" role="alert">{errors.email.message}</p>}

      <button disabled={isSubmitting}>{isSubmitting ? "Saving..." : "Sign up"}</button>
    </form>
  );
}

register("email", rules) returns the props (name, onChange, onBlur, ref) to spread onto the input. handleSubmit runs validation first and only calls your function with valid data. For controlled third-party components (a date picker, a select library), use the Controller component or useController.

§2Schema Validation with Zod

Hand-writing rules per field gets repetitive. A schema library such as Zod declares the shape and constraints of the data once. You can reuse the same schema on the server, and derive the TypeScript type from it.

import { z } from "zod";
import { zodResolver } from "@hookform/resolvers/zod";

const schema = z
  .object({
    email: z.string().min(1, "Email is required").email("Enter a valid email"),
    age: z.coerce.number().int().min(18, "Must be 18 or older"),
    password: z.string().min(8, "At least 8 characters"),
    confirm: z.string(),
  })
  .refine((d) => d.password === d.confirm, {
    path: ["confirm"],
    message: "Passwords do not match",
  });

// type Signup = z.infer<typeof schema>;      // the TypeScript type comes free

const form = useForm({ resolver: zodResolver(schema), mode: "onTouched" });
  • mode controls when validation runs: onSubmit (default), onBlur, onTouched (after first blur, then on change), or onChange.
  • z.coerce.number() converts the string from the input to a number before validating.
  • Server errors can be placed on fields with setError("email", { message: "Already registered" }).
  • Always validate again on the server. Client validation is for usability.

§3Accessible, Usable Forms

A library does not make a form accessible. You still have to do the work, and it matters most in large forms.

  • Every input has a visible <label> connected with htmlFor/id (placeholders are not labels).
  • Connect errors to inputs with aria-describedby, and mark the field with aria-invalid. Announce errors with role="alert" or move focus to the first invalid field on a failed submit (RHF's shouldFocusError does this by default).
  • Do not rely on color alone to show errors; include text.
  • Use the right type and autocomplete attributes (email, tel, current-password, one-time-code) so browsers and password managers help.
  • Disable the submit button only while submitting, never to hide why the form is invalid. Prefer showing clear messages.
  • Long forms: group related fields with <fieldset> and <legend>, and preserve entered data if the submit fails.
// move focus to the first error and keep user data on failure
const onInvalid = (errs) => {
  const first = Object.keys(errs)[0];
  document.getElementById(first)?.focus();
};
<form onSubmit={handleSubmit(onSubmit, onInvalid)} noValidate>
Validate on the way in and on the way through Show friendly, specific errors in the browser, using a shared schema, and enforce the same rules on the server. Client checks are convenience; server checks are the actual guarantee.

§4Common Mistakes

MistakeWhat HappensFix
Storing every keystroke of a 40-field form in stateThe whole form re-renders on each keyUse uncontrolled registration (React Hook Form)
Using placeholder text instead of labelsFails accessibility; label disappears while typingAdd real <label> elements
Validating only on the clientAnyone can send bad data directly to the APIRe-validate on the server, ideally with the same schema
Showing errors only in redNot perceivable for some usersInclude error text and associate it with the input
Practice
  1. Build a signup form with React Hook Form and a Zod schema, including a password-confirmation refine.
  2. Make the form accessible: labels, aria-invalid, aria-describedby, and focus on the first error after a failed submit.
  3. Simulate a server-side "email already taken" error and show it on the field with setError.
Key takeaways
  • React Hook Form registers inputs instead of storing each keystroke, cutting re-renders and boilerplate.
  • Schema validation (Zod) declares rules once and can be shared with the server and with types.
  • Accessibility is your job: labels, error association, focus management, and the right input attributes.
