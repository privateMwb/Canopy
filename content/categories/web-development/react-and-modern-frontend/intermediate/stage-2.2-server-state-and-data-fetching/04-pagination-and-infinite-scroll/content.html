Pagination & Infinite Scroll

Loading every record is slow for the user and expensive for the server. Pagination and infinite scroll fetch data in pieces, and the right choice depends on how people use the list.

§1Page-Based Pagination

Classic pagination fetches one page at a time. Put the page in the query key so each page is cached separately, and keep it in the URL so that Back and shared links work. placeholderData: keepPreviousData keeps the previous page on screen while the next one loads, avoiding a flash of loading state.

import { useQuery, keepPreviousData } from "@tanstack/react-query";
import { useSearchParams } from "react-router";

function Products() {
  const [params, setParams] = useSearchParams();
  const page = Number(params.get("page") ?? 1);

  const { data, isPending, isPlaceholderData } = useQuery({
    queryKey: ["products", { page }],
    queryFn: () => fetch(`/api/products?page=${page}&limit=20`).then((r) => r.json()),
    placeholderData: keepPreviousData,
  });

  if (isPending) return <p>Loading...</p>;

  return (
    <>
      <ul style={{ opacity: isPlaceholderData ? 0.6 : 1 }}>
        {data.items.map((p) => <li key={p.id}>{p.name}</li>)}
      </ul>
      <button disabled={page === 1} onClick={() => setParams({ page: page - 1 })}>Previous</button>
      <span> Page {page} of {data.totalPages} </span>
      <button disabled={page >= data.totalPages} onClick={() => setParams({ page: page + 1 })}>Next</button>
    </>
  );
}

Page numbers suit content where users jump around or return to a position (tables, search results, admin lists). They are also easy to link to and to index for search engines.

§2Infinite Scroll

Infinite scroll appends the next chunk as the user nears the end. It suits feeds that are browsed linearly. TanStack Query's useInfiniteQuery manages a list of pages and a cursor that tells the server where to continue. Use an IntersectionObserver on a sentinel element to trigger loading, rather than scroll listeners.

import { useInfiniteQuery } from "@tanstack/react-query";
import { useEffect, useRef } from "react";

function Feed() {
  const { data, fetchNextPage, hasNextPage, isFetchingNextPage, status } = useInfiniteQuery({
    queryKey: ["feed"],
    queryFn: ({ pageParam }) =>
      fetch(`/api/feed?cursor=${pageParam ?? ""}&limit=20`).then((r) => r.json()),
    initialPageParam: null,
    getNextPageParam: (lastPage) => lastPage.nextCursor ?? undefined,   // undefined = no more pages
  });

  const sentinel = useRef(null);
  useEffect(() => {
    const el = sentinel.current;
    if (!el) return;
    const io = new IntersectionObserver(([e]) => {
      if (e.isIntersecting && hasNextPage && !isFetchingNextPage) fetchNextPage();
    }, { rootMargin: "400px" });
    io.observe(el);
    return () => io.disconnect();
  }, [hasNextPage, isFetchingNextPage, fetchNextPage]);

  if (status === "pending") return <p>Loading...</p>;
  const posts = data.pages.flatMap((p) => p.items);

  return (
    <>
      {posts.map((p) => <Post key={p.id} post={p} />)}
      <div ref={sentinel} />
      {isFetchingNextPage && <p>Loading more...</p>}
      {!hasNextPage && <p>You are all caught up.</p>}
    </>
  );
}

§3Choosing and Doing It Well

PagesInfinite scroll
Best forSearchable, comparable, or targeted contentCasual browsing of a feed
Reaching the footer / a positionEasyHard (content keeps moving)
Shareable positionYes (URL has the page)Difficult; needs extra work
Memory useConstantGrows; consider virtualization
AccessibilityStraightforwardNeeds care (focus, announcements, keyboard access to footer)
  • Prefer cursor-based pagination (nextCursor) over offsets for data that changes: offsets skip or repeat items when rows are inserted.
  • For very long lists, virtualize rendering (TanStack Virtual, react-window) so only visible rows are in the DOM.
  • Offer a "Load more" button as a middle path: it is accessible, controlled, and avoids surprise loading.
  • Handle the end of the list, empty results, and errors on the next page (with a retry), not just the happy path.
  • Keep filters and sort in the query key so that changing them starts a new list.
  • Use prefetchQuery for the next page to make Next feel instant.
Match the pattern to the task People who look for something want pages and a position they can return to. People who browse for fun are happy to scroll. Choose from how the list is used, not from what looks modern.

§4Common Mistakes

MistakeWhat HappensFix
Leaving page out of the query keyAll pages share one cache entryInclude page (and filters) in the key
Offset pagination on changing dataItems repeat or are skipped as rows are addedUse cursor-based pagination
Listening to scroll events for infinite loadingJanky and wastefulUse IntersectionObserver on a sentinel
Rendering thousands of rows in the DOMSlow scrolling and high memoryVirtualize the list
Practice
  1. Build page-based pagination with keepPreviousData, with the page stored in the URL.
  2. Build an infinite feed with useInfiniteQuery and an IntersectionObserver sentinel, including the end-of-list message.
  3. Add a virtualized version of a 10,000-row list and compare the number of DOM nodes before and after.
Key takeaways
  • Fetch large lists in pieces, with page or cursor included in the query key.
  • useInfiniteQuery plus an IntersectionObserver sentinel implements infinite scroll cleanly.
  • Choose pagination or infinite scroll by use case; use cursors and virtualization for scale.
