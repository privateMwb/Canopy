Suspense & Error Boundaries

Instead of checking isPending and isError in every component, Suspense and error boundaries let you declare, once, what shows while something loads and what shows when it fails.

§1Suspense: Declarative Loading

<Suspense fallback={...}> shows the fallback while any component inside it is waiting for something (lazy-loaded code, or data from a Suspense-enabled library). When ready, React swaps in the real content. The component that needs the data is written as if the data were already there.

import { Suspense } from "react";
import { useSuspenseQuery } from "@tanstack/react-query";

function Profile({ id }) {
  const { data: user } = useSuspenseQuery({            // data is always defined here
    queryKey: ["user", id],
    queryFn: () => getUser(id),
  });
  return <h2>{user.name}</h2>;
}

function Page() {
  return (
    <>
      <h1>Account</h1>
      <Suspense fallback={<ProfileSkeleton />}>
        <Profile id={42} />
      </Suspense>
      <Suspense fallback={<p>Loading orders...</p>}>
        <Orders />
      </Suspense>
    </>
  );
}

Place boundaries around meaningful regions. Several small boundaries let different parts of the page appear as they become ready, while one large boundary shows a single spinner until everything is done. Use skeletons that match the final layout to reduce layout shift.

Beware waterfalls: if a component inside a boundary starts a fetch only after its parent finishes loading, requests run one after another. Start independent fetches in parallel (prefetch, loaders, or useSuspenseQueries).

§2Error Boundaries

An error boundary catches errors thrown while rendering its children and shows a fallback instead of crashing the whole app to a blank page. It is the failure counterpart of Suspense. You write one as a class (the only place classes are still required), or use the react-error-boundary package.

import { ErrorBoundary } from "react-error-boundary";
import { QueryErrorResetBoundary } from "@tanstack/react-query";

function Fallback({ error, resetErrorBoundary }) {
  return (
    <div role="alert">
      <p>Something went wrong loading this section.</p>
      <pre>{error.message}</pre>
      <button onClick={resetErrorBoundary}>Try again</button>
    </div>
  );
}

function Section() {
  return (
    <QueryErrorResetBoundary>
      {({ reset }) => (
        <ErrorBoundary FallbackComponent={Fallback} onReset={reset} onError={(e) => logError(e)}>
          <Suspense fallback={<Skeleton />}>
            <Orders />
          </Suspense>
        </ErrorBoundary>
      )}
    </QueryErrorResetBoundary>
  );
}
  • Error boundaries catch errors in rendering, lifecycle, and constructors of descendants. They do not catch errors in event handlers, asynchronous code (timeouts, promises), or the boundary itself.
  • Handle errors in event handlers with try/catch and state; handle async failures with your data library.
  • Wrap the whole app in a top-level boundary as a last resort, and add local boundaries around risky or independent sections so one failure does not take down the page.
  • Log errors to a monitoring service in onError, and offer a retry that resets the boundary (and any caches that need resetting).

§3Putting Them Together

The standard layout nests the two: an error boundary outside, a Suspense boundary inside. Loading is handled by Suspense, failure by the boundary, and the component in the middle only handles the success case.

QuestionHandled by
What shows while data or code loads?<Suspense fallback>
What shows when rendering throws?<ErrorBoundary fallback>
What does the component handle?Only the success case
What about event-handler errors?try/catch + state
// lazy-loaded code uses the same mechanism
const Settings = lazy(() => import("./Settings"));

<ErrorBoundary FallbackComponent={Fallback}>
  <Suspense fallback={<Spinner />}>
    <Settings />
  </Suspense>
</ErrorBoundary>

// transitions keep the old UI visible instead of showing the fallback on updates
const [isPending, startTransition] = useTransition();
startTransition(() => setTab("orders"));

Frameworks build on this model: Next.js loading.js and error.js files and React Router's route errorElement are Suspense and error boundaries placed per route for you.

Loading and error as layout, not logic Move "what if it is not ready?" and "what if it fails?" out of every component and into a few boundaries around regions. The components inside become simpler, and the page degrades gracefully.

§4Common Mistakes

MistakeWhat HappensFix
Expecting an error boundary to catch errors in click handlers or promisesThe error escapes and nothing is shownUse try/catch plus state, or the data library's error handling
One Suspense boundary around the entire pageOne spinner blocks everythingUse several boundaries around independent regions
No error boundary at allA single thrown error blanks the whole appAdd a top-level boundary and local ones for risky sections
Nested components each starting a fetch after the parent resolvesRequest waterfalls and slow pagesStart independent requests in parallel, or prefetch
Practice
  1. Wrap two independent sections in separate Suspense boundaries with skeleton fallbacks and observe them appearing independently.
  2. Add an error boundary with a "Try again" button that resets a failed query.
  3. Throw an error inside an event handler and inside render, and confirm which one the boundary catches.
Key takeaways
  • Suspense declares the loading UI for a region; components inside assume their data exists.
  • Error boundaries catch render-time failures and show a fallback; they do not catch handler or async errors.
  • Nest Suspense inside an error boundary, place both around meaningful regions, and watch for waterfalls.
