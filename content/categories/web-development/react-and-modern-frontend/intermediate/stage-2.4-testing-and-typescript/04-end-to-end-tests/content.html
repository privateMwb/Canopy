End-to-End Tests

End-to-end tests drive a real browser through your running app, covering the places where components, routing, and the server meet. Keep them few and focused on the journeys that must never break.

§1What E2E Tests Are For

Component tests run in a simulated DOM and fake network. They cannot tell you whether routing works, whether the real build runs, or whether the front end and back end agree. End-to-end (E2E) tests open a real browser, load your app, and click through it, like a user. They are slow and costly, so they cover the critical paths only: sign up, log in, the core workflow, checkout.

LayerSpeedConfidence inHow many
Unit (functions, reducers)MillisecondsLogicMany
Component (RTL + MSW)Tens of msUI behavior and statesMany
End-to-end (Playwright)SecondsWhole system works togetherFew, critical

§2A Playwright Test

Playwright controls Chromium, Firefox, and WebKit. Its locators auto-wait for elements to be ready and its expect assertions retry, which removes most flakiness without manual sleeps. It starts your dev server for you.

npm init playwright@latest

// playwright.config.ts
export default defineConfig({
  testDir: "./e2e",
  use: { baseURL: "http://localhost:5173", trace: "on-first-retry" },
  webServer: { command: "npm run dev", url: "http://localhost:5173", reuseExistingServer: true },
  projects: [{ name: "chromium", use: { ...devices["Desktop Chrome"] } }],
});

// e2e/checkout.spec.ts
import { test, expect } from "@playwright/test";

test("a shopper can add an item and reach checkout", async ({ page }) => {
  await page.goto("/");

  await page.getByRole("link", { name: "Shop" }).click();
  await page.getByRole("button", { name: "Add to cart" }).first().click();
  await expect(page.getByTestId("cart-count")).toHaveText("1");

  await page.getByRole("link", { name: "Cart" }).click();
  await expect(page).toHaveURL(/\/cart/);
  await page.getByRole("button", { name: "Checkout" }).click();
  await expect(page.getByRole("heading", { name: "Payment" })).toBeVisible();
});

Use the same role- and label-based locators as in component tests. Run npx playwright test --ui to step through a test with DOM snapshots at every action, and npx playwright codegen to record clicks as test code. Each test gets a fresh browser context (clean storage), so tests do not affect one another.

§3Keeping E2E Reliable

  • Never use fixed sleeps (waitForTimeout). Wait for a visible condition; Playwright's assertions retry automatically.
  • Control your data: seed a test database, use a dedicated test account, or intercept network calls with page.route for third-party services. Do not depend on live external sites.
  • Log in once: save the authenticated state with a setup project and reuse it, instead of logging in through the UI in every test.
  • Test the failure path where it matters: force an API error with page.route and assert on the message.
  • Run in CI on every pull request, with traces and screenshots uploaded on failure so that failures are debuggable.
  • Treat flaky tests as bugs. A test people re-run until green is worse than none, because the suite stops being trusted.
  • Cover mobile viewports and at least one non-Chromium browser for the critical journeys.
test("shows an error when the API is down", async ({ page }) => {
  await page.route("**/api/orders", (route) => route.fulfill({ status: 500, body: "boom" }));
  await page.goto("/orders");
  await expect(page.getByRole("alert")).toContainText("Could not load orders");
});

// reuse login across tests (global setup saves storageState)
test.use({ storageState: "e2e/.auth/user.json" });
Few tests, high value Pick the five journeys whose breakage would hurt most, and automate those end to end. Put everything else in faster component and unit tests.

§4Common Mistakes

MistakeWhat HappensFix
Using waitForTimeout to wait for thingsSlow and still flakyRely on auto-waiting locators and retrying expect
Putting every scenario in E2EA slow suite nobody runsReserve it for critical journeys
Depending on live third-party services or shared dataRandom failures and test interferenceSeed data and intercept external calls
Logging in through the UI in every testSlow and brittleSave and reuse authenticated state
Practice
  1. Write an E2E test for one core journey in your app using only role- and label-based locators.
  2. Stub a failing API with page.route and assert that the error UI appears.
  3. Run the test with --ui and trace to find where a deliberately broken step fails.
Key takeaways
  • E2E tests verify the whole system in a real browser; keep them few and focused on critical paths.
  • Playwright's auto-waiting locators and retrying assertions remove the need for sleeps.
  • Control data, reuse login state, run in CI, and fix flaky tests immediately.
