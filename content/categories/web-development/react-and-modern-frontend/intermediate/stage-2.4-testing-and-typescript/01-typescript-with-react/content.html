TypeScript with React

TypeScript catches mistakes in props, state, and events before the code runs. Learning a small set of patterns for components and hooks gives you most of the benefit.

§1Typing Props

Describe props with a type or interface, and annotate the destructured parameter. You rarely need React.FC; a plain function with typed props is clearer. Use React.ReactNode for anything React can render (the type of children).

import type { ReactNode } from "react";

type ButtonProps = {
  label: string;
  variant?: "primary" | "secondary";        // a union: only these values allowed
  disabled?: boolean;
  onClick: (event: React.MouseEvent<HTMLButtonElement>) => void;
};

function Button({ label, variant = "primary", disabled, onClick }: ButtonProps) {
  return <button className={variant} disabled={disabled} onClick={onClick}>{label}</button>;
}

type CardProps = { title: string; children: ReactNode };

// extend native element props so callers can pass id, aria-*, className, etc.
type InputProps = React.ComponentProps<"input"> & { label: string };
function Field({ label, ...rest }: InputProps) {
  return <label>{label}<input {...rest} /></label>;
}

Use string-literal unions instead of plain string for fixed choices, and discriminated unions to model props where some combinations are invalid. TypeScript will then reject nonsensical usage at compile time.

type AlertProps =
  | { kind: "info"; message: string }
  | { kind: "error"; message: string; onRetry: () => void };   // retry only valid for errors

§2Typing State, Events, and Hooks

// state: inferred from the initial value, or give it explicitly when it starts empty
const [count, setCount] = useState(0);                          // number
const [user, setUser] = useState<User | null>(null);            // union with null
const [items, setItems] = useState<string[]>([]);               // empty array needs a type

// events: use the specific React event type
function onChange(e: React.ChangeEvent<HTMLInputElement>) { setName(e.target.value); }
function onSubmit(e: React.FormEvent<HTMLFormElement>) { e.preventDefault(); }

// refs: the element type, and null initially
const inputRef = useRef<HTMLInputElement>(null);
inputRef.current?.focus();

// reducers: type the state and a union of actions
type Action = { type: "added"; text: string } | { type: "toggled"; id: string };
function reducer(state: Todo[], action: Action): Todo[] {
  switch (action.type) {
    case "added": return [...state, { id: crypto.randomUUID(), text: action.text, done: false }];
    case "toggled": return state.map((t) => (t.id === action.id ? { ...t, done: !t.done } : t));
  }
}

// context with a safe default and a custom hook
const AuthContext = createContext<AuthValue | null>(null);
function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error("useAuth must be inside AuthProvider");
  return ctx;                                                   // now non-null for callers
}

A generic custom hook keeps its types flexible: function useFetch<T>(url: string): { data: T | null; error: Error | null } lets the caller say useFetch<User[]>("/api/users").

§3Working Well with TypeScript

  • Enable "strict": true in tsconfig.json. It is where most of the value is.
  • Let inference work: do not annotate what TypeScript already knows (const n = 5). Annotate function parameters, exported APIs, and empty initial state.
  • Avoid any. Use unknown for values you have not validated, then narrow them.
  • Data from outside is not typed at runtime. res.json() returns any; asserting as User[] is a promise, not a check. Validate with a schema (Zod) and infer the type: type User = z.infer<typeof UserSchema>.
  • Derive types from one source: typeof and keyof and z.infer prevent duplicated, drifting definitions.
  • Use import type for type-only imports, and keep types close to the code that uses them.
  • Read errors from the bottom up; the last line of a long TypeScript error is usually the actual mismatch.
import { z } from "zod";

const UserSchema = z.object({ id: z.number(), name: z.string(), email: z.string().email() });
type User = z.infer<typeof UserSchema>;

async function getUsers(): Promise<User[]> {
  const res = await fetch("/api/users");
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return z.array(UserSchema).parse(await res.json());          // checked at runtime, typed after
}
Types vanish at runtime TypeScript checks your code, not the data that arrives later. Type the inside of your app, and validate at the boundaries (API responses, storage, URL params).

§4Common Mistakes

MistakeWhat HappensFix
Casting API data with as User[]False confidence; wrong data crashes laterValidate with a schema and infer the type
Using any to silence errorsRemoves the safety you wantedUse unknown and narrow, or fix the type
useState([]) with no typeInferred as never[]; adding items errorsuseState<Item[]>([])
Typing every variable explicitlyNoise; types drift from realityLet inference handle locals
Practice
  1. Type a Button with a variant union and make an invalid variant a compile error.
  2. Write a discriminated-union Alert where onRetry is required only for kind: "error".
  3. Replace an as cast on API data with a Zod schema and an inferred type.
Key takeaways
  • Type props with unions and ReactNode; use specific event types, typed state, and typed refs.
  • Turn on strict, rely on inference, and avoid any.
  • Validate untrusted data at runtime and infer types from the schema.
