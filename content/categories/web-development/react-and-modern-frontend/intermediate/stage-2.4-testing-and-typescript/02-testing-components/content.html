Testing Components

Good component tests describe what a user sees and does, not how the component is built. React Testing Library makes that the easy path, so tests survive refactors and catch real breakage.

§1Test Behavior, Not Implementation

The guiding principle: *the more your tests resemble the way your software is used, the more confidence they give.* A user clicks a button named "Add" and sees a new item. They do not care that you used useReducer. Tests that check state variables or call internal functions break when you refactor, even though nothing visible changed.

// vitest.config / vite.config.ts
// test: { environment: "jsdom", setupFiles: "./src/test/setup.ts", globals: true }

// src/test/setup.ts
import "@testing-library/jest-dom/vitest";

// Counter.test.tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { test, expect } from "vitest";
import { Counter } from "./Counter";

test("increments when the button is clicked", async () => {
  const user = userEvent.setup();
  render(<Counter />);

  expect(screen.getByText("Count: 0")).toBeInTheDocument();
  await user.click(screen.getByRole("button", { name: /increment/i }));
  expect(screen.getByText("Count: 1")).toBeInTheDocument();
});

The pattern is always render, interact, assert. Notice that nothing refers to state, props of internal components, or class names.

§2Queries, Async, and User Events

Find elements the way users and assistive technology do. Prefer getByRole with an accessible name, then getByLabelText, then text. Use data-testid only as a last resort.

QueryBehavior when absentUse for
getBy*ThrowsSomething that must be there now
queryBy*Returns nullAsserting something is not there
findBy*Waits, then throwsSomething that appears asynchronously
test("shows an error if the email is invalid", async () => {
  const user = userEvent.setup();
  render(<SignupForm onSubmit={vi.fn()} />);

  await user.type(screen.getByLabelText(/email/i), "not-an-email");
  await user.click(screen.getByRole("button", { name: /sign up/i }));

  expect(await screen.findByRole("alert")).toHaveTextContent(/valid email/i);
});

test("calls onSubmit with the form data", async () => {
  const onSubmit = vi.fn();
  const user = userEvent.setup();
  render(<SignupForm onSubmit={onSubmit} />);

  await user.type(screen.getByLabelText(/email/i), "ada@example.com");
  await user.click(screen.getByRole("button", { name: /sign up/i }));

  expect(onSubmit).toHaveBeenCalledWith({ email: "ada@example.com" });
  expect(screen.queryByRole("alert")).not.toBeInTheDocument();
});

Always await user-event calls and use findBy* (or waitFor) for async changes. userEvent simulates a real sequence (focus, key presses, input events), unlike firing a bare click event.

§3Hooks, Providers, and What Not to Test

Components that need providers (router, query client, theme) should be rendered inside them. Wrap that setup in a helper so every test is short.

function renderWithProviders(ui: React.ReactElement, { route = "/" } = {}) {
  const queryClient = new QueryClient({ defaultOptions: { queries: { retry: false } } });   // no retries in tests
  return render(
    <QueryClientProvider client={queryClient}>
      <MemoryRouter initialEntries={[route]}>{ui}</MemoryRouter>
    </QueryClientProvider>
  );
}

// test a custom hook directly
import { renderHook, act } from "@testing-library/react";
test("useToggle flips", () => {
  const { result } = renderHook(() => useToggle());
  act(() => result.current[1]());
  expect(result.current[0]).toBe(true);
});
  • Do test: what users see and do, validation messages, loading and error states, conditional rendering, and accessibility roles.
  • Do not test: implementation details (state variable names, how many times a component rendered), third-party library internals, or CSS (jsdom has no layout).
  • Keep tests independent: a fresh render per test, no shared mutable state.
  • Snapshot tests are brittle for whole components: use them sparingly, and prefer explicit assertions.
  • If a query is hard to write, the component is probably hard to use. Fix the markup, not the test.
  • Cover the pure logic (reducers, formatters, validators) with plain unit tests: they are faster and sharper than component tests.
If the refactor breaks the test, the test was wrong A good component test fails when behavior breaks and stays green when you reorganize the code. Query by role and text, and assert on what the user would see.

§4Common Mistakes

MistakeWhat HappensFix
Asserting on internal state or class namesTests break on harmless refactorsAssert on visible output and roles
Forgetting to await user-event or use findByAssertions run too early; flaky testsawait interactions; use findBy*/waitFor for async UI
Using getBy to check absenceThrows before the assertionUse queryBy with not.toBeInTheDocument()
Reaching for data-testid firstTests unconnected to what users perceivePrefer getByRole and getByLabelText
Practice
  1. Write tests for a counter, a form with validation, and a component that shows a loading and then a success state.
  2. Create a renderWithProviders helper and use it in three tests.
  3. Refactor a component's internals (rename state, split into two components) and confirm your tests still pass unchanged.
Key takeaways
  • Test what users see and do: render, interact, assert, with queries by role and label.
  • Use await userEvent and findBy* for async behavior; queryBy* to assert absence.
  • Avoid testing implementation details, and push pure logic into easily tested functions.
