Styling Approaches

React does not choose how you style, and there are good reasons to pick different approaches. Knowing what each trades away helps you choose one for a project and stick with it.

§1Plain CSS and CSS Modules

You can import a regular .css file into a component, but its class names are global: two files that both define .title will collide. CSS Modules solve this. A file named Card.module.css has its class names rewritten to be unique, and you import them as an object.

/* Card.module.css */
.card { padding: 1rem; border: 1px solid #ddd; border-radius: 8px; }
.title { font-size: 1.25rem; }
.featured { border-color: gold; }

// Card.jsx
import styles from "./Card.module.css";

function Card({ title, featured, children }) {
  return (
    <section className={`${styles.card} ${featured ? styles.featured : ""}`}>
      <h3 className={styles.title}>{title}</h3>
      {children}
    </section>
  );
}

CSS Modules give you real CSS, scoped automatically, with no runtime cost and no new syntax to learn. They work out of the box in Vite. A tiny helper such as clsx makes combining conditional class names tidier: clsx(styles.card, featured && styles.featured).

§2Utility Classes and Component Libraries

Utility-first CSS (Tailwind CSS is the most popular) styles elements by composing small single-purpose classes directly in the markup. There is no naming and no separate file, and the build removes unused classes, so output stays small.

function Badge({ children, tone = "info" }) {
  const tones = {
    info: "bg-blue-100 text-blue-800",
    warn: "bg-amber-100 text-amber-800",
  };
  return (
    <span className={`inline-block rounded-full px-3 py-1 text-sm font-medium ${tones[tone]}`}>
      {children}
    </span>
  );
}

The markup gets busy, which is the usual complaint, and the answer is the same as everywhere else in React: extract a component (Badge) so the long class list lives in one place. Component libraries (Material UI, Chakra, Radix, shadcn/ui, and others) supply ready-made accessible components. They speed up building, but they also bring their own look, API, and bundle size, so weigh how much you will need to customize them.

§3Choosing and Other Options

ApproachStrengthCost
Plain CSS fileSimplest; no toolingGlobal names; collisions grow with the app
CSS ModulesScoped real CSS, zero runtimeDynamic styles need CSS variables or class switching
Tailwind / utilitiesFast iteration, consistent design tokensVerbose markup; a vocabulary to learn
Component libraryAccessible components out of the boxLook and bundle size come with it; harder to deviate
CSS-in-JS (runtime)Styles tied to props and componentsRuntime cost; poor fit with server components
// dynamic values: pass them through CSS custom properties
<div className={styles.bar} style={{ "--progress": `${percent}%` }} />

/* .bar { width: var(--progress); } */

// inline styles are fine for one-off dynamic values, but cannot do :hover or media queries
<div style={{ width: `${percent}%` }} />
  • Pick one primary approach per project; mixing four creates confusion.
  • Use CSS variables for colors, spacing, and fonts so themes (such as dark mode) are easy.
  • Style states with real CSS (:hover, :focus-visible, [aria-expanded="true"]) rather than JavaScript where you can.
  • Whatever you choose, keep focus outlines and sufficient color contrast: accessibility is not optional.
  • Runtime CSS-in-JS libraries (such as styled-components) are less common in new projects, partly because they do not mix well with server rendering.
Consistency beats cleverness The best styling approach is the one your team applies consistently. Choose, document the choice, and spend your attention on the design rather than on re-deciding.

§4Common Mistakes

MistakeWhat HappensFix
Relying on global class names in a large appStyles collide and break unrelated componentsUse CSS Modules or utilities
Building everything with inline style objectsNo hover, focus, or media queries; hard to maintainUse classes; inline only for dynamic one-offs
Pulling in a big UI library for two componentsLarge bundle and a look you then fightBuild the small pieces, or use a headless library
Removing focus outlines for looksKeyboard users cannot see where they areStyle :focus-visible instead of removing it
Practice
  1. Style one component with a CSS Module, including a conditional class built with clsx.
  2. Rebuild the same component with Tailwind utility classes and compare readability and file count.
  3. Add a dark theme by defining CSS variables on :root and overriding them under [data-theme="dark"].
Key takeaways
  • CSS Modules scope real CSS per component; utility CSS styles through small classes; libraries trade control for speed.
  • Use CSS variables for design tokens and pass dynamic values through custom properties.
  • Pick one approach, apply it consistently, and keep accessibility (focus, contrast) intact.
