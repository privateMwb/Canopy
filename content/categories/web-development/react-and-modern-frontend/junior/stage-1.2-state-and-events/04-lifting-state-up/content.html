Lifting State Up

When two components need the same data, the data cannot live in either of them. It moves up to their closest common parent, which passes it down and receives changes back through functions.

§1The Problem: Siblings Cannot Talk

Data flows only downward, from parents to children through props. Two sibling components have no direct way to share state. If a filter box and a product list both need the search text, keeping a separate copy in each leaves them disagreeing.

// broken idea: each component has its own copy of the query
function SearchBox() { const [query, setQuery] = useState(""); /* ... */ }
function ProductList() { /* needs the query, but cannot see SearchBox's state */ }

§2The Solution: Lift It Up

Find the closest common parent of the components that need the state and move the state there. Pass the value down as a prop, and pass a setter or callback down so children can request changes.

function ProductPage({ products }) {
  const [query, setQuery] = useState("");             // state lives in the parent

  const visible = products.filter((p) =>
    p.name.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <>
      <SearchBox query={query} onQueryChange={setQuery} />
      <ProductList items={visible} />
      <p>{visible.length} of {products.length} shown</p>
    </>
  );
}

function SearchBox({ query, onQueryChange }) {
  return <input value={query} onChange={(e) => onQueryChange(e.target.value)} />;
}

function ProductList({ items }) {
  return <ul>{items.map((p) => <li key={p.id}>{p.name}</li>)}</ul>;
}

SearchBox is now a controlled component: it owns no state, and is told what to display and how to report changes. That makes it simple, reusable, and easy to test. The parent is the single source of truth.

§3How Much to Lift

Keep state as low in the tree as possible, and lift it only as far as needed. State in a parent re-renders that parent and all its children when it changes, and it makes more components depend on one another.

QuestionAnswer
Does only one component use this state?Keep it local in that component
Do siblings need it?Lift to their common parent
Does a distant part of the tree need it?Lift higher, or use context (a later lesson)
Can it be calculated from other state?Do not store it; derive it during render
  • Name callback props onSomething and the receiving handlers handleSomething.
  • If you find yourself passing the same props through many layers (prop drilling), consider restructuring with children, or using context.
  • Lifted state should store the minimum data: store selectedId, not the whole selected object, so there is only one copy of the object.
Find the common parent Whenever two components need to agree, ask: what is their closest shared ancestor? Put the state there, pass it down, and pass a way to change it down too.

§4Common Mistakes

MistakeWhat HappensFix
Duplicating the same state in two componentsThey drift out of syncKeep one copy in the common parent
Lifting state higher than necessaryUnrelated components re-render and become coupledLift only to the closest common parent
Storing a copy of an object in state (selectedItem)The copy goes stale when the original changesStore the id and look up the item during render
Forgetting to pass the setter or callback downChild cannot change anythingPass an onChange-style prop
Practice
  1. Build a temperature converter with Celsius and Fahrenheit inputs that stay in sync, with state lifted into the parent.
  2. Create an accordion where only one panel can be open at a time by lifting an openId into the parent.
  3. Refactor a component holding its own search state so that a sibling can also read the query.
Key takeaways
  • Components that share data get it from their closest common parent through props.
  • Children request changes by calling callback props from the parent.
  • Keep state as low as possible and store the minimum; derive the rest.
