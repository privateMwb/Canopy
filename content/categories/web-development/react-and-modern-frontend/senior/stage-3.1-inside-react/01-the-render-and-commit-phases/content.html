The Render and Commit Phases

Between a setState call and pixels changing, React does a precise sequence of work. Knowing the phases, and which code runs in each, explains StrictMode, effect timing, and nearly every "why did that run now?" question.

§1Trigger, Render, Commit

Every update passes through the same pipeline. A trigger schedules work (the initial root.render, or a state setter, dispatch, or context change). React then renders: it calls your components to compute a new tree of elements and works out what changed. Finally it commits: it applies the minimal DOM changes and runs effects. The browser paints after the commit.

PhaseWhat happensCan touch the DOM?Interruptible?
RenderCall components and hooks; build the next fiber tree; diff against the current oneNo (pure calculation)Yes (in concurrent rendering)
CommitApply DOM mutations, attach refs, run layout effectsYesNo: synchronous and atomic
Passive effectsuseEffect callbacks run after paint (usually)Yes (DOM already updated)Scheduled separately

The render phase is pure calculation that React may pause, restart, or discard. That is why components and reducers must be pure, and why side effects in the render body are bugs: React may run your function more times than it commits, or never commit that render at all.

§2The Commit Phase in Detail

Commit has sub-steps that explain the different effect hooks. All DOM changes for an update are applied together, so the user never sees a half-updated screen.

  1. Before mutation: read from the DOM before it changes (class getSnapshotBeforeUpdate).
  2. Mutation: insert, update, and delete DOM nodes; run cleanups of layout effects; detach old refs.
  3. Layout: attach refs; run useLayoutEffect callbacks synchronously, before the browser paints.
  4. Paint: the browser draws the frame.
  5. Passive: React runs useEffect cleanups and callbacks (for urgent updates caused by discrete events such as clicks, React flushes them before the next render to preserve ordering).
function Tooltip({ anchorRef, children }) {
  const [pos, setPos] = useState({ top: 0, left: 0 });

  // measure after DOM update, before paint: no flicker from a wrong first position
  useLayoutEffect(() => {
    const r = anchorRef.current.getBoundingClientRect();
    setPos({ top: r.bottom, left: r.left });          // re-render happens synchronously, before paint
  }, [anchorRef]);

  // data fetching, subscriptions, logging: after paint, does not block it
  useEffect(() => {
    const id = analytics.track("tooltip-shown");
    return () => analytics.cancel(id);
  }, []);

  return <div style={{ position: "fixed", ...pos }}>{children}</div>;
}

Use useEffect by default. Reach for useLayoutEffect only when you must read layout and synchronously re-render to avoid a visible flash (tooltips, popovers, measurement). It blocks painting, so keep it short.

§3Consequences You Can Predict

  • StrictMode double-invocation: in development React renders components twice, and mounts effects twice (mount, unmount, mount). If doing that breaks your code, your render was impure or an effect lacks cleanup. Production runs once.
  • A render is not a commit: you may see console.log in the body run without the screen changing, especially with transitions or Suspense.
  • Batching: setters called in the same tick, including inside promises and timeouts, are batched into one render and one commit.
  • Same state, no work: if useState receives a value equal (Object.is) to the current one, React usually bails out, though it may still call the component once more before deciding.
  • Refs are not set during render: ref.current is populated in the commit, so read it in effects and handlers.
  • Rendering a component does not mean its DOM changes: React diffs the output and only mutates what differs.
function Profile({ user }) {
  console.log("render");              // may log more often than the DOM changes
  const ref = useRef(null);
  // ref.current === null here on first render

  useEffect(() => {
    console.log(ref.current.tagName); // set by now
  });
  return <h1 ref={ref}>{user.name}</h1>;
}
Render computes, commit changes Treat the render phase as a pure function that React may call freely and the commit phase as the only moment the world changes. Every rule of React follows from that split.

§4Common Mistakes

MistakeWhat HappensFix
Fetching or mutating in the component bodyRuns on discarded and repeated renders; double work in StrictModeMove side effects to handlers or useEffect
Using useLayoutEffect for ordinary effectsBlocks painting and hurts responsivenessUse useEffect unless you need pre-paint measurement
Reading ref.current during renderIt is null or stale before commitRead it in effects and event handlers
Treating each log of "render" as a visible updateMisreading performance and behaviorRemember render may run without commit; profile actual commits
Practice
  1. Add logs in the body, a layout effect, and a passive effect, and record the order for mount and for an update. Then explain it with the phases.
  2. Build a tooltip that flickers with useEffect positioning and fix it with useLayoutEffect.
  3. Turn StrictMode on and off and list every behavior that changes, with the reason for each.
Key takeaways
  • An update is trigger, render (pure, interruptible), then commit (DOM changes, synchronous).
  • Layout effects run before paint; passive effects run after; refs attach at commit.
  • Purity in render is what lets React pause, repeat, and discard work safely.
