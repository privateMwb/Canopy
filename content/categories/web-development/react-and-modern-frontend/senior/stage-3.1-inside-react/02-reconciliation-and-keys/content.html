Reconciliation & Keys

When state changes, React compares the new tree of elements with the previous one and applies the smallest set of changes. The rules for that comparison decide whether state is preserved or destroyed, which is why keys and component identity matter far beyond lists.

§1The Diffing Heuristics

A general tree diff is far too slow (cubic in the number of nodes), so React uses two heuristics that make it linear and work for almost all UIs:

  1. Elements of different types produce different trees. If the element type at a position changes (<div> to <span>, or <A> to <B>), React tears down the old subtree and builds a new one, destroying all state inside.
  2. Keys hint which children are stable across renders. Among siblings, React matches elements by key (then by position) to decide what to move, update, create, or delete.

When the type at a position is the same, React keeps the existing instance (and its state and DOM node) and only updates the changed props and attributes, then recurses into children.

// same type at the same position: state is PRESERVED
{isEditing ? <Form mode="edit" /> : <Form mode="view" />}

// different type at the same position: subtree is destroyed and recreated, state LOST
{isEditing ? <EditForm /> : <ViewForm />}

// a component's identity is its position in the tree plus its type (and key)

§2Keys Control Identity

A key is part of an element's identity. If the key changes, React treats it as a different element: it unmounts the old one and mounts a new one. If the key is the same, React updates in place and preserves state, even if the item moved.

// list: stable ids let React move rows instead of rewriting them
{items.map((item) => <Row key={item.id} item={item} />)}

// index keys: reordering reuses the wrong instances, so inputs and state stick to positions
{items.map((item, i) => <Row key={i} item={item} />)}

// the reset trick: change the key to deliberately reset a component's state
<Chat key={contactId} contactId={contactId} />      // switching contacts remounts Chat with fresh state

// a component defined inside another has a NEW type every render: remounted each time
function Parent() {
  function Child() { return <input />; }             // new function identity every render
  return <Child />;                                   // input loses focus and state on each keystroke
}

That last example is a classic bug. Because Child is created anew in each render of Parent, React sees a different type at that position every time, tears down the old subtree, and builds a new one. Always define components at module level.

§3Lists, Moves, and Practical Consequences

For a keyed list, React builds a map from key to existing child, then walks the new children: matched keys update, new keys mount, and missing keys unmount. Reordering is a move, not a rewrite, but React cannot detect a move for unkeyed items, and index keys make a reordered list look like content changes at fixed positions.

You do thisReact doesResult
Prepend an item, keys are idsMount one new row, keep the restEfficient, state intact
Prepend an item, keys are indexesUpdate every row's props, mount one at the endSlow, and row state misaligns
Swap <div> for <section> as a wrapperUnmount the whole subtreeAll child state lost
Change key on a componentUnmount and remount itFresh state (a useful reset)
Render {cond && <A />} vs {cond ? <A /> : null}Same: position stays reservedState preserved while rendered
  • Keys must be stable and unique among siblings, never random per render, or every item remounts.
  • Keep wrappers consistent across conditional branches if you want to preserve inner state.
  • Use key to reset a form or profile when its subject changes, instead of syncing with effects.
  • Reconciliation compares output, not code: re-rendering a component with the same output makes no DOM change.
  • Large lists cost reconciliation work on every update; virtualize them and avoid unnecessary parent re-renders.
Identity decides state State belongs to a component instance, and an instance is identified by its type, its position, and its key. Change any of the three and the state is gone; keep them and it survives.

§4Common Mistakes

MistakeWhat HappensFix
Defining a component inside another componentNew type each render: remounts, lost focus and stateDefine components at module scope
Using array index as key in reorderable listsState and DOM stick to positions, not itemsUse stable ids from the data
Swapping wrapper element types in a conditionalEntire subtree unmounts and state resetsKeep the wrapper stable, or accept the reset deliberately
Syncing state to a changing prop with an effectFlicker and stale intermediate rendersUse key={prop} to remount with fresh state
Practice
  1. Reproduce the nested-component bug (an input losing focus each keystroke) and fix it by moving the component out.
  2. Build a list of text inputs, reorder it with index keys and then id keys, and explain the difference.
  3. Replace an effect that resets a form on a prop change with a key, and verify the behavior is identical.
Key takeaways
  • React diffs in linear time using two rules: different type means different tree, and keys identify stable children.
  • A component's state lives with its identity: type, position, and key.
  • Use stable keys, define components at module level, and use key as an intentional reset.
