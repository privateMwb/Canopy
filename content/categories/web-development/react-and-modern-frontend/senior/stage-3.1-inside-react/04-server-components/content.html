Server Components

React Server Components split a component tree across two environments: some components run only on the server and never ship their code, others run in the browser. Understanding the boundary between them is the core skill of modern React frameworks.

§1Two Kinds of Components

In a framework that supports them (Next.js App Router, React Router framework mode, and others), components are Server Components by default. They run only on the server, during a request or at build time, and send their rendered output to the client. Their JavaScript is never included in the bundle. A component becomes a Client Component by adding the "use client" directive at the top of its file, and it then runs in the browser (and is also pre-rendered to HTML on the server for the first load).

Server ComponentClient Component ("use client")
RunsOnly on the serverBrowser (plus server pre-render for first HTML)
Code in bundleNoYes
Can use state, effects, event handlersNoYes
Can read the database / secrets / filesystemYes (directly)No
Can be async and await dataYesNo (use hooks or a data library)
Browser APIs (window, localStorage)NoYes
// app/products/page.jsx : a Server Component (no directive needed)
import { db } from "@/lib/db";
import AddToCart from "./AddToCart";

export default async function ProductsPage() {
  const products = await db.product.findMany();         // runs on the server, no API layer needed

  return (
    <ul>
      {products.map((p) => (
        <li key={p.id}>
          {p.name} ${p.price}
          <AddToCart productId={p.id} />                 {/* a Client Component */}
        </li>
      ))}
    </ul>
  );
}

// app/products/AddToCart.jsx
"use client";
import { useState } from "react";

export default function AddToCart({ productId }) {
  const [added, setAdded] = useState(false);
  return <button onClick={() => { addToCart(productId); setAdded(true); }}>{added ? "Added" : "Add"}</button>;
}

§2The Boundary and What Crosses It

"use client" marks a boundary: that file, and everything it imports, becomes part of the client bundle. Server Components can render Client Components, passing them props. Props that cross the boundary must be serializable (strings, numbers, booleans, plain objects and arrays, dates, promises, and Server Actions), because they are sent over the network. You cannot pass functions, class instances, or components-as-values that are not serializable.

// allowed: server renders a client component, passes serializable props
<Chart data={rows} title="Sales" />

// allowed: pass a Server Component as children, composition keeps it on the server
<ClientModal>
  <ServerRenderedContent />                           {/* still rendered on the server */}
</ClientModal>

// not allowed: a function prop from server to client (not serializable)
<Button onClick={() => doThing()} />                  // error, unless it is a Server Action

// a client component cannot import a server component (it would be pulled into the bundle),
// but it can receive one as children or a prop

Server Actions (functions marked "use server") let a client component call code that runs on the server, such as saving a form, without writing a separate API endpoint. They become POST endpoints behind the scenes, so treat every action as a public API: authenticate and validate the input inside it.

// actions.js
"use server";
export async function createPost(formData) {
  const session = await getSession();
  if (!session) throw new Error("Unauthorized");          // always authorize in the action
  const title = String(formData.get("title") ?? "").trim();
  if (!title) return { error: "Title is required" };      // always validate
  await db.post.create({ data: { title, authorId: session.userId } });
  revalidatePath("/posts");
}

// a Client Component can use it as a form action
<form action={createPost}><input name="title" /><button>Post</button></form>

§3Design Guidance and Pitfalls

  • Push "use client" down: keep it on small interactive leaves (a button, a dropdown) rather than whole pages, so most of the tree stays on the server and out of the bundle.
  • Fetch data where it is used, in Server Components, close to the UI that needs it; run independent fetches in parallel (Promise.all) to avoid waterfalls, and use Suspense to stream slow parts.
  • Keep secrets on the server. Anything imported by a Client Component can reach the browser: guard server-only modules with the server-only package so an accidental import fails the build.
  • Context and hooks do not work in Server Components; put providers in a small Client Component that takes children.
  • Mental model: Server Components are about where code runs and what ships, not about replacing client interactivity. Interactive UI still needs Client Components.
  • Not for every app: if you have a heavily interactive, offline-first, or fully client-rendered app, or you cannot run a server, plain client React remains a fine choice.
  • Frameworks implement the details (caching, routing, streaming); learn your framework's data and caching rules, because they differ and change.
The boundary is a bundle boundary Everything on the client side of "use client" ships to the browser. Draw that line as low and as small as you can, and keep data access, secrets, and heavy dependencies on the server side.

§4Common Mistakes

MistakeWhat HappensFix
Putting "use client" at the top of every fileWhole app ships to the browser; Server Components give no benefitApply it only to interactive leaf components
Passing a function or class instance from server to clientSerialization errorPass plain data; use Server Actions for server calls
Trusting Server Action inputsPublic endpoints with no auth or validationAuthenticate and validate inside every action
Importing a server-only module (with secrets) into a Client ComponentSecrets or server code can leak to the browserUse the server-only package and keep a clear boundary
Practice
  1. Take a page that fetches in useEffect and convert its data loading into an async Server Component, leaving only the interactive piece as a Client Component.
  2. Move a "use client" directive from a page down to the smallest interactive component and compare the client bundle size.
  3. Write a Server Action for a form with authentication and validation, and try to call it with invalid data.
Key takeaways
  • Server Components run only on the server and ship no JavaScript; Client Components add interactivity.
  • "use client" is a bundle boundary: props crossing it must be serializable, and children can stay on the server.
  • Push client boundaries down, keep secrets on the server, and treat Server Actions as public endpoints.
