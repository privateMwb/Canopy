Bundling, Tree Shaking & Delivery

Every kilobyte of JavaScript must be downloaded, parsed, and executed before it helps anyone. Analyzing what ships, and choosing how it is split and delivered, is one of the most reliable ways to speed up an app.

§1See What You Ship

You cannot shrink what you cannot see. A bundle analyzer draws a treemap of every module in your output, sized by bytes, and routinely reveals that one library accounts for a third of the total.

npm install -D rollup-plugin-visualizer
// vite.config.js
import { visualizer } from "rollup-plugin-visualizer";
export default { plugins: [react(), visualizer({ open: true, gzipSize: true, brotliSize: true })] };

npm run build        # opens a treemap; look for big, duplicated, or unexpected packages
  • Compare gzip/brotli sizes (what users download), but remember that parse and execute time depends on the uncompressed size, and matters most on phones.
  • Look for duplicates (two versions of the same library), moment-style locale bundles, whole icon sets, and server-only code in the client bundle.
  • Check a dependency's cost before adding it (bundlephobia, or size-limit), and prefer small, ES-module-friendly packages.
  • Set a budget (for example, 170 KB compressed JavaScript for the initial route) and fail CI when it is exceeded.

§2Tree Shaking and Splitting

Tree shaking removes exports nobody imports. It needs ES modules (static import/export) and code with no side effects at load time. A library published only as CommonJS, or one that does work on import, cannot be shaken.

// shakeable: named imports from an ES-module build
import { debounce } from "lodash-es";            // only debounce is included
import { format } from "date-fns";

// not shakeable: CommonJS or a default export of the whole library
import _ from "lodash";                           // pulls in everything
import * as Icons from "lucide-react";            // may defeat shaking in some setups

// tell the bundler a package has no side effects (in the library's package.json)
// { "sideEffects": false }

// avoid barrel files that re-export everything from a big module in app code
// import { Button } from "@/components";         // can pull in the entire folder in some toolchains

Code splitting turns dynamic import() calls into separate chunks loaded on demand: split by route first, then heavy features (editors, charts, PDF), and modals. Combine with React.lazy, framework route splitting, and preloading on hover or idle to hide the delay.

§3Delivery: Compression, Caching, and Hints

TechniqueWhat to do
CompressionServe Brotli (or gzip) for JS, CSS, HTML, and SVG; precompress at build time
Long-term cachingContent-hashed filenames (app.3f9a1c.js) with Cache-Control: max-age=31536000, immutable
HTML cachingShort or revalidated, so it always points at current hashed files
CDNServe static assets from the edge, close to users, over HTTP/2 or HTTP/3
Resource hintspreconnect to critical origins, preload critical assets, modulepreload for known chunks
Third-party scriptsLoad with async/defer, delay until consent or idle, or remove them
Modern targetsTarget modern browsers to avoid shipping heavy transpilation and polyfills
<link rel="preconnect" href="https://api.example.com" crossorigin>
<link rel="modulepreload" href="/assets/route-checkout.8a1f.js">
<script type="module" src="/assets/main.4c2e.js"></script>

// vite.config.js: manual control when needed
build: {
  target: "es2022",
  sourcemap: true,
  rollupOptions: { output: { manualChunks: { react: ["react", "react-dom"] } } },
}
  • Hashed filenames let returning visitors reuse unchanged chunks after a deploy, so keep vendor chunks stable by not changing them needlessly.
  • Handle chunk load failures after a new deploy (old tab requesting deleted files): catch the error and prompt a reload.
  • Measure the result with real-user metrics (LCP, INP) and the Network panel on throttled connections, not only with bundle size numbers.
  • Remember that less code beats better delivery: removing a dependency helps every user on every visit.
The fastest code is code you do not ship Analyze first, remove or replace the biggest offenders, split what is not needed immediately, and deliver what remains compressed, cached, and close to the user.

§4Common Mistakes

MistakeWhat HappensFix
Importing a whole library for one functionLarge bundle, unused codeUse ES-module builds and named imports; verify in the analyzer
Putting everything in one entry bundleEvery page downloads code for every other pageSplit by route and heavy feature
Caching HTML for a long timeUsers get a page pointing at deleted chunksCache hashed assets forever; revalidate HTML
Measuring only compressed bytesParse and execute cost on phones is ignoredAlso watch uncompressed size and long tasks
Practice
  1. Generate a bundle treemap for a real project and identify the three largest dependencies and a plan for each.
  2. Replace a whole-library import with a named import from the ES-module build and compare the output size.
  3. Add a CI budget check that fails when the initial route exceeds your limit.
Key takeaways
  • Analyze the bundle first; the biggest wins come from removing or splitting a few heavy dependencies.
  • Tree shaking needs ES modules and side-effect-free code; split by route and heavy feature.
  • Deliver with Brotli, hashed immutable assets, a CDN, and sensible hints, and handle chunk failures.
