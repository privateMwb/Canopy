Error Handling & Observability

Production is where assumptions fail. A front end that reports errors with context, traces them to a cause, and degrades gracefully turns outages into small, fixable incidents.

§1Layers of Error Handling

Different failures need different handlers. Design the layers deliberately so every error lands somewhere useful, and no error is both swallowed and invisible.

FailureWhere it is caughtWhat the user sees
Exception during renderError boundary around the regionA local fallback with retry; the rest of the page works
Error in an event handler or async codetry/catch plus state or a toastA specific, actionable message
Failed network requestThe data layer (query onError, retries)Retry button or cached data with a notice
Uncaught error or rejected promisewindow.onerror / unhandledrejectionLogged; ideally nothing worse than before
Failed chunk or asset loadError boundary around lazy routes"Reload to update" prompt
Everything else (last resort)Top-level boundaryA friendly error page with a way home
import { ErrorBoundary } from "react-error-boundary";

function logToService(error, info) {
  monitor.captureException(error, {
    extra: { componentStack: info.componentStack },
    tags: { area: "checkout" },
  });
}

<ErrorBoundary FallbackComponent={SectionError} onError={logToService} resetKeys={[orderId]}>
  <Suspense fallback={<Skeleton />}>
    <OrderSummary id={orderId} />
  </Suspense>
</ErrorBoundary>

// global safety nets
window.addEventListener("error", (e) => monitor.captureException(e.error ?? e.message));
window.addEventListener("unhandledrejection", (e) => monitor.captureException(e.reason));

Boundaries should be granular: a failing sidebar widget must not blank the checkout form. Use resetKeys so a boundary clears itself when the data it depends on changes.

§2Observability: Seeing What Users See

Observability means you can answer "what is happening for real users, and why?" from the data you collect, without redeploying to add logging. For front ends, that rests on three signals.

  • Errors: exceptions with stack traces (mapped through source maps to your original code), release version, browser, URL, and user/session id (an id, not personal data). Tools: Sentry, Datadog RUM, Rollbar, or your own endpoint.
  • Performance: Core Web Vitals (LCP, INP, CLS), route transitions, and key interaction timings from real users, sliced by route, device class, and connection.
  • Behavior and breadcrumbs: the trail of events (route changes, clicks, failed requests, state transitions) leading up to an error, which often reveals the cause on its own.
monitor.init({
  release: import.meta.env.VITE_APP_VERSION,           // tie every error to a deploy
  environment: import.meta.env.MODE,
  beforeSend(event) {
    return scrub(event);                                // strip emails, tokens, form values
  },
  sampleRate: 1.0,
  tracesSampleRate: 0.1,                                // sample performance data
});

monitor.setUser({ id: user.id });                        // never email or name
monitor.addBreadcrumb({ category: "cart", message: "coupon applied", level: "info" });

§3Tracing, Alerting, and Operating It

Front-end errors often originate in the back end, so connect the two. Send a trace/correlation id with each request (traceparent header, per the W3C Trace Context standard, or a request id), log it on errors, and use it to jump from a front-end error to the exact server logs.

async function api(path, init = {}) {
  const requestId = crypto.randomUUID();
  const res = await fetch(path, { ...init, headers: { ...init.headers, "x-request-id": requestId } });
  if (!res.ok) {
    monitor.captureMessage("API error", { extra: { path, status: res.status, requestId } });
    throw new ApiError(res.status, requestId);          // the UI can show "Reference: ab12..." to support
  }
  return res.json();
}
  • Alert on what matters: new error types, error-rate spikes after a release, and Web Vitals regressions, rather than every single event. Alert fatigue means real incidents get ignored.
  • Group and de-duplicate errors (fingerprinting) so a single bug is one issue with a count, not ten thousand events.
  • Tag every event with the release and upload source maps privately in CI; roll back quickly when a release raises the error rate. Combine with feature flags for safer rollouts.
  • Protect privacy: scrub personal data, respect consent and regional rules, and limit session-replay capture of sensitive fields.
  • Show users a path forward: a retry, a reference id they can give to support, and honest wording. Never show raw stack traces or internal messages.
  • Practice incidents: write runbooks, and review errors regularly as part of normal work, not only when something breaks.
  • Keep synthetic checks (scripted browser tests of critical journeys on a schedule) to catch outages before users report them.
An error you cannot see is an error you cannot fix Catch failures at the right layer, show users a way forward, and send enough context (release, route, trace id, breadcrumbs) that someone can diagnose it without asking the user to reproduce it.

§4Common Mistakes

MistakeWhat HappensFix
A single top-level error boundary onlyOne failing widget blanks the whole pageAdd granular boundaries around independent regions
Logging errors with no release, user id, or contextCannot reproduce or tell which deploy broke itAttach release, route, trace id, and breadcrumbs
Sending personal data or form contents in error reportsPrivacy and compliance violationsScrub in beforeSend; log ids, not content
Alerting on every error eventAlert fatigue; real incidents get ignoredAlert on new issues and rate changes after releases
Practice
  1. Add error boundaries at three levels (app, route, widget) and verify each by throwing inside it.
  2. Wire an error-monitoring SDK with releases and source maps, throw a test error, and confirm the stack trace shows original source.
  3. Add a request id to every API call and show it on the error UI, then trace one failure through to server logs.
Key takeaways
  • Handle errors in layers: boundaries for render, try/catch for handlers, the data layer for requests, and global handlers as a safety net.
  • Observability for front ends means errors, real-user performance, and breadcrumbs, tagged by release and trace id.
  • Alert on meaningful change, protect privacy, and give users a clear path forward.
