Feature-Based Architecture

In a large codebase, how files are organized determines how fast people can find, change, and delete things. Organizing by feature keeps related code together and makes the boundaries between parts of the product explicit.

§1From Layers to Features

A small app is often organized by layer: all components in one folder, all hooks in another, all API calls in a third. As the app grows, a single feature (say, checkout) is scattered across six folders, every change touches many places, and nobody knows what is safe to delete.

// by layer: one feature is spread everywhere
src/
  components/   CartItem.tsx  ProductCard.tsx  CheckoutForm.tsx  ...(200 files)
  hooks/        useCart.ts  useCheckout.ts  ...
  api/          cart.ts  products.ts  orders.ts
  utils/        ...

// by feature: a feature is a folder you can read, move, or delete
src/
  features/
    cart/        components/  hooks/  api.ts  store.ts  index.ts   <- public API
    checkout/    components/  hooks/  api.ts  schema.ts  index.ts
    products/    ...
  shared/        ui/  lib/  hooks/       <- used by many features, no feature knowledge
  app/           routes, providers, layout  <- wires features together

A feature is a slice of product behavior with a clear owner (search, cart, onboarding), not a technical category. The test: *can I describe it to a product manager?* Each folder contains everything that feature needs: UI, state, data access, types, and tests.

§2Boundaries and Dependency Rules

Folders alone do not create architecture; rules about who may import whom do. Without them, features quietly depend on each other's internals and the structure becomes decoration.

  • Direction of dependencies: app can import from features and shared; features can import from shared; shared imports from nothing above it. Features should not import from other features' internals.
  • Each feature exposes a public API through its index.ts. Other code imports only from that entry point, never from deep paths like features/cart/hooks/useCartInternal.
  • When two features need to cooperate, prefer composition at the app level (the page wires the cart button into the product card via props or slots) or a narrow, explicit interface, instead of one feature reaching into another.
  • Code used by two or more features moves to shared. Do not pre-emptively share: duplication is cheaper than the wrong abstraction.
  • shared must not know about any feature (no if (feature === "cart") in shared UI).
// features/cart/index.ts : the public surface
export { CartButton } from "./components/CartButton";
export { useCartCount } from "./hooks/useCartCount";
export type { CartItem } from "./types";
// everything else in cart/ is private

// app/ProductPage.tsx : composition at the app layer
import { CartButton } from "@/features/cart";
import { ProductDetails } from "@/features/products";
<ProductDetails renderActions={(p) => <CartButton productId={p.id} />} />

// enforce it with lint: eslint-plugin-boundaries or import/no-restricted-paths
// rule: features/* may not import from features/*/(components|hooks|...) of another feature

§3Making It Work Over Time

ConcernPractice
Finding codeName folders after the product domain, not technology
Deleting a featureRemove its folder and its few references from app/
OwnershipMap each feature folder to a team (CODEOWNERS)
Enforcing boundariesLint rules or tools (eslint-plugin-boundaries, Nx module boundaries, dependency-cruiser) that fail CI
Shared UIA design system or shared/ui with no business logic
Cross-feature stateLift to the app layer, or a small shared store with a narrow API
GrowthSplit a feature that gets large into sub-features, and promote shared pieces only when a second user appears
  • Colocate tests, styles, and types with the code they cover.
  • Keep routing thin: route files import from features and compose them, rather than holding logic.
  • Resist the urge to create a perfect structure up front. Start simple, reorganize as boundaries become clear, and use the dependency rules to guide the move.
  • Feature folders and domain-driven thinking help most when several teams work in the same repo; for a solo project, a flat structure can be perfectly fine.
  • Beware over-abstraction: a features/ folder with ten tiny features and elaborate indirection is as hard to navigate as the layered mess it replaced.
A boundary nobody enforces is a suggestion Folders express intent; lint rules and CI make it real. Add an automated check for the one rule that matters most: features do not reach into each other's internals.

§4Common Mistakes

MistakeWhat HappensFix
Organizing by file type in a large appOne change touches many folders; nothing is safely deletableGroup by feature and colocate
Features importing each other's internalsHidden coupling; changes ripple unpredictablyExpose a small public API and compose at the app layer
Moving everything to shared "in case"A dumping ground full of feature-specific codePromote only when a second feature needs it
Defining boundaries without enforcementThey erode within monthsAdd lint or tooling rules that fail CI
Practice
  1. Take a layered project and reorganize one feature (such as cart) into a feature folder with an index.ts public API.
  2. Add a lint rule that forbids importing from another feature's internal paths, and fix the violations it finds.
  3. Draw the dependency diagram of an app you know and mark every arrow that violates the intended direction.
Key takeaways
  • Organize large apps by product feature, with each folder holding its UI, state, data, and tests.
  • Define dependency directions and a public API per feature, and enforce them with tooling.
  • Share only when a second consumer exists, and keep shared free of feature knowledge.
