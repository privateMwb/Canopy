Route Handlers & API Design

Building REST endpoints inside the framework.

§1Route Handlers

Server Actions cover your own forms, but sometimes you need a real HTTP endpoint: for a mobile app, a webhook, a third-party integration, or a public API. In the App Router, a file named route.ts exports functions named after HTTP methods.

// app/api/tasks/route.ts
import { NextResponse } from "next/server";

export async function GET(request: Request) {
  const { searchParams } = new URL(request.url);
  const limit = Number(searchParams.get("limit") ?? 20);
  const tasks = await db.task.findMany({ take: Math.min(limit, 100) });
  return NextResponse.json({ data: tasks });
}

export async function POST(request: Request) {
  const body = await request.json().catch(() => null);
  const parsed = TaskSchema.safeParse(body);
  if (!parsed.success)
    return NextResponse.json({ error: parsed.error.flatten() }, { status: 400 });
  const task = await db.task.create({ data: parsed.data });
  return NextResponse.json({ data: task }, { status: 201 });
}

§2Designing a Good API

  • Nouns for resources, methods for actions: GET /api/tasks, POST /api/tasks, DELETE /api/tasks/42.
  • Correct status codes: 201 for created, 400 for bad input, 401 and 403 for auth, 404 for missing, 429 for rate limited.
  • Consistent shape: the same envelope for success and for errors, with a machine-readable code.
  • Pagination and limits: never return an unbounded list; cap limit on the server.
  • Validation and authorization on every handler, exactly as for Server Actions.
// A consistent error shape
{ "error": { "code": "validation_failed", "message": "Title is required", "fields": { "title": ["Required"] } } }

§3Server Actions or Route Handlers?

UseWhen
Server ActionYour own UI mutates data (forms, buttons)
Route HandlerAnything external needs a URL: webhooks, mobile clients, public or partner APIs, non-form clients
Server Component readYour own pages reading data; no endpoint needed

Note that whether GET handlers are cached by default has varied between versions. If a handler returns data that changes, make its caching behaviour explicit.

An API is a contract Once outside clients depend on a response shape, changing it breaks them. Design the contract deliberately, and add fields rather than altering or removing existing ones.

§4Common Mistakes

MistakeWhat HappensFix
Returning 200 for errorsClients and monitoring treat failures as successUse the proper 4xx and 5xx status codes
Unbounded list endpointsSlow responses and an easy denial-of-service pathPaginate and enforce a maximum page size
Leaking database fieldsInternal columns such as password hashes escapeMap to an explicit response shape instead of returning raw rows
Practice
  1. Build GET and POST handlers for a resource with validation, pagination, and a consistent error shape.
  2. Call your endpoints with curl and verify the status codes for success, invalid input, and a missing record.
Key takeaways
  • Use route handlers for external clients, and Server Actions for your own UI.
  • Design APIs with resource-oriented URLs, correct status codes, consistent errors, and pagination.
  • Validate, authorize, and map responses explicitly, and never return raw database rows.
