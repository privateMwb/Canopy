File Uploads & External Services

Storage, email, and payments integrations.

§1Files Don't Belong in Your Server's Memory

Serverless functions have request size limits and no persistent disk, so storing uploads on the server isn't an option. The standard pattern is object storage (S3, Cloudflare R2, Vercel Blob, Supabase Storage) with the browser uploading directly to it.

§2Presigned Uploads

  1. The client asks your server for permission to upload, sending the file's name, type, and size.
  2. Your server authenticates the user, validates type and size, and returns a short-lived presigned URL.
  3. The browser uploads the file straight to storage using that URL.
  4. The client (or a storage event) tells your server the upload finished; you save the object key in your database.
const url = await getSignedUrl(s3, new PutObjectCommand({
  Bucket: process.env.BUCKET,
  Key: `users/${user.id}/${crypto.randomUUID()}.png`,   // never trust a client-chosen name
  ContentType: "image/png",
}), { expiresIn: 60 });                                  // valid for one minute

§3Validate Everything About a File

  • Size limits enforced server-side, plus bucket limits.
  • Allowed content types by an allowlist, checked against actual content where it matters, since the declared type can be faked.
  • Generated key names, to prevent path tricks and overwrites.
  • Private by default: serve sensitive files through short-lived signed download URLs.
  • Scan or process untrusted files (for malware, or by re-encoding images) before using them.

§4Other External Services

Email (Resend, Postmark), payments (Stripe), and similar providers share common rules. Call them from the server with secrets kept in env variables. Set timeouts, handle failure explicitly, and keep your own record of what you asked for. Never put a secret API key in client code. Wrap each provider behind a small module of your own, so swapping vendors, or mocking in tests, touches one file.

Let the browser carry the bytes If a large file passes through your function, you pay for the bandwidth and time twice, and risk timeouts. Presigned uploads move the heavy transfer off your server entirely.

§5Common Mistakes

MistakeWhat HappensFix
Uploading large files through your own API routeSize limits, timeouts, and high costUse presigned URLs for direct-to-storage uploads
Using the client's filename as the storage keyOverwrites and path traversal attemptsGenerate a random key and store the original name separately
Making upload buckets publicPrivate user files become accessible to anyoneKeep buckets private and serve files via signed URLs
Practice
  1. Implement a presigned upload flow with a size limit and an allowed-types check, and save the resulting key in the database.
  2. Wrap an email or payment provider in a small module with a timeout and one clearly handled failure case.
Key takeaways
  • Use object storage with presigned URLs so uploads go directly from the browser to storage.
  • Validate size, type, and name on the server, and keep sensitive files private.
  • Keep provider calls on the server, with timeouts, error handling, and a thin wrapper module.
