Rate Limiting & Abuse Prevention

Protecting endpoints from misuse.

§1Every Public Endpoint Will Be Abused

Login forms get credential stuffing, signup forms get bots, expensive endpoints get scraped, and anything calling a paid API (such as an LLM) becomes a way to burn your money. Rate limiting caps how often a client may do something, and it's one of the cheapest, highest-value protections you can add.

§2Common Algorithms

AlgorithmBehaviourNotes
Fixed windowN requests per minute, counter resets on the minuteSimple, but allows bursts at window edges
Sliding windowN requests in any trailing minuteSmoother and fairer; slightly more state
Token bucketTokens refill steadily; each request spends oneAllows controlled bursts while enforcing an average

Serverless functions don't share memory, so counters need a shared fast store such as Redis (Upstash and similar services are popular). In-memory counters only work on a single long-lived server.

import { Ratelimit } from "@upstash/ratelimit";
import { Redis } from "@upstash/redis";

const limiter = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(10, "1 m"),     // 10 requests per minute
});

const key = userId ?? ip;                           // prefer user id over IP when known
const { success, reset } = await limiter.limit(`login:${key}`);
if (!success) {
  return new Response("Too many requests", {
    status: 429,
    headers: { "Retry-After": String(Math.ceil((reset - Date.now()) / 1000)) },
  });
}

§3Choosing What to Limit

  • Sensitive actions (login, password reset, MFA) get strict limits, ideally by account *and* IP.
  • Expensive operations (search, exports, AI calls) get limits sized to your costs.
  • Signup and messaging get limits plus bot protection such as CAPTCHA or proof-of-work where needed.
  • Respond with 429 and a Retry-After header so well-behaved clients can back off.

IP addresses are an imperfect identity: many users share one behind NAT, and attackers rotate them. Combine signals (account, IP, device) and keep the limits generous enough not to hurt real users.

Limits protect your wallet too Abuse isn't only a security issue. Unlimited access to a paid API from a public endpoint is an invitation for someone to run up your bill. Add limits and spending caps before launch.

§4Common Mistakes

MistakeWhat HappensFix
Counting requests in server memory on serverlessEach instance has its own counter, so limits are ineffectiveUse a shared store such as Redis
Limiting only by IPShared networks get blocked and attackers rotate addressesLimit by account where possible, and combine signals
No limit on login or password resetCredential stuffing and account lockoutsApply strict per-account and per-IP limits with backoff
Practice
  1. Add a sliding-window limit to a login endpoint and return a proper 429 with Retry-After.
  2. List your app's five most expensive or sensitive endpoints and choose a limit and an identity key for each.
Key takeaways
  • Rate limiting protects against credential stuffing, scraping, and cost abuse.
  • Serverless needs a shared store for counters; token bucket and sliding window are common algorithms.
  • Limit by meaningful identities, return 429 with Retry-After, and size limits to real usage.
