CI/CD & Environments

Pipelines, staging, and safe releases.

§1Automate the Safety Net

Continuous integration (CI) runs checks on every change, so problems are caught by a machine in minutes rather than by users in production. Continuous delivery (CD) then promotes passing builds to environments automatically.

# .github/workflows/ci.yml  (GitHub Actions)
name: CI
on: [pull_request]
jobs:
  checks:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_PASSWORD: postgres }
        ports: ["5432:5432"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npx tsc --noEmit        # type check
      - run: npm test                # unit + integration
      - run: npm run build
      - run: npx playwright install --with-deps && npx playwright test

Order checks from fastest to slowest so failures surface early, and run independent jobs in parallel.

Keep configuration per environment in variables, and keep environments as similar as possible so staging results mean something.

§3Safe Releases

  • Protected main: require passing checks and review before merge.
  • Small, frequent releases: smaller diffs mean easier diagnosis and rollback.
  • Feature flags: deploy code dark, then turn it on gradually, and off instantly if it misbehaves.
  • Fast rollback: keep previous deployments available and practise promoting one.
  • Migrations in two steps: make schema changes backwards compatible, so old and new code both work during the deploy (see lesson 3.2.3).
Fast feedback beats thorough feedback A pipeline that takes 40 minutes gets bypassed. Keep the pull-request path quick (aim for minutes), and run slower or broader suites on merge or on a schedule.

§4Common Mistakes

MistakeWhat HappensFix
Running checks only locallyBroken code reaches main when someone skips themEnforce checks in CI with required status checks
Sharing one database across environmentsTest runs corrupt staging or production dataGive each environment its own database and secrets
Deploying with no rollback planA bad release means a long outage while you improvisePractise rollbacks and use feature flags for risky changes
Practice
  1. Write a CI workflow that runs lint, type check, tests, and build on every pull request.
  2. Describe how you would roll back a bad deploy and how you would roll back a bad database migration, and compare the difficulty.
Key takeaways
  • CI runs lint, types, tests, and build on every change, ordered fast to slow.
  • Separate local, preview, staging, and production, each with its own data and secrets.
  • Release in small steps with protected branches, feature flags, and a practised rollback.
