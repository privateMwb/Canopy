Unit & Integration Testing

Testing components and server logic.

§1What to Test, and at Which Level

Tests trade cost for confidence. Unit tests are fast and precise, integration tests check that pieces work together, and end-to-end tests check whole user flows but are slower and more brittle. A healthy suite has many of the first, some of the second, and a few of the last.

LevelTestsSpeedExample
UnitOne function or component in isolationMillisecondsA price-formatting helper
IntegrationSeveral units plus real collaboratorsSecondsA server function against a test database
End to endThe deployed app through a browserMany secondsSign up, add item, check out

§2Unit and Component Tests

Vitest (or Jest) runs fast tests, and React Testing Library renders components and queries them the way a user would: by role and text, not by implementation details.

import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { LikeButton } from "./like-button";

test("toggles like state", async () => {
  render(<LikeButton id="1" />);
  await userEvent.click(screen.getByRole("button", { name: /like/i }));
  expect(screen.getByRole("button", { name: /unlike/i })).toBeInTheDocument();
});

async Server Components can't be rendered by most unit-test tooling yet. Extract their logic into plain functions and test those, and cover the full page in an end-to-end test.

§3Integration Tests for Server Logic

The server code that matters most (data access, authorization, business rules) deserves tests against a real database, such as a disposable Postgres in Docker, rather than heavy mocking. Mock only true boundaries like the network or the clock.

test("a user cannot read another user's task", async () => {
  const task = await seedTask({ ownerId: "alice" });
  await expect(getTask(task.id, { userId: "bob" })).rejects.toThrow(/not found/i);
});
Test behaviour, not implementation If renaming an internal variable breaks a test, the test is too coupled. Query by what users see and assert on outcomes, so refactors don't force test rewrites.

§4Common Mistakes

MistakeWhat HappensFix
Mocking everything including your own modulesTests pass while the real integration is brokenUse a real test database; mock only external boundaries
Querying by CSS class or test id firstTests don't reflect what users or assistive tech perceivePrefer getByRole, getByLabelText, and visible text
Trying to unit-test async Server Components directlyTooling errors and flaky setupsTest extracted logic, and cover pages end to end
Practice
  1. Write a component test for an interactive client component using Testing Library queries by role.
  2. Write an integration test proving that one user can't access another user's record.
Key takeaways
  • Balance fast unit tests, integration tests, and a few end-to-end tests.
  • Test components the way users interact with them, not by internal details.
  • Test server logic against a real database, and mock only genuine external boundaries.
