Partial Prerendering & Rendering Modes

Mixing static and dynamic content on one page.

§1The Static-or-Dynamic Dilemma

Many pages are mostly static with one personalised piece: a product page with a user-specific cart badge, or a blog with a logged-in greeting. Historically, one dynamic element forced the entire page to render per request. Partial prerendering (PPR) removes that trade-off.

§2A Static Shell with Dynamic Holes

With PPR, the framework prerenders a static shell at build time and serves it instantly from the edge. Dynamic parts are marked with <Suspense>, and their fallbacks are part of the shell. The dynamic content streams in from the server while the static part is already visible.

export default function ProductPage({ params }) {
  return (
    <>
      <ProductDetails />                        {/* static: in the shell */}
      <Suspense fallback={<CartSkeleton />}>
        <PersonalisedCart />                    {/* reads cookies → dynamic, streamed */}
      </Suspense>
    </>
  );
}

In recent Next.js versions this is delivered through Cache Components, where you explicitly opt content into caching with use cache and everything else is dynamic by default. This area has changed quickly between releases, so confirm the current flag names and behaviour in the documentation.

§3The Spectrum of Rendering Modes

ModeHTML producedBest for
Static (SSG)Build timeContent that rarely changes
Incremental / revalidatedBuild time, refreshed on a schedule or eventContent that changes occasionally
Dynamic (SSR)Every requestFully personalised or real-time pages
Partial prerenderingStatic shell at build, dynamic parts at requestMostly-static pages with personalised regions
Client-side renderingIn the browserHighly interactive widgets behind login

Choose per page, and per region within a page, not once for the whole app. The aim is to push as much as possible toward static while still delivering the personalised pieces.

Think in regions Instead of asking 'is this page static or dynamic?', ask 'which parts of this page depend on the request?' Wrap those parts in Suspense and let the rest be served from the edge.

§4Common Mistakes

MistakeWhat HappensFix
Reading cookies at the top of the page componentThe whole route becomes dynamic and the static shell is lostRead request data only inside the Suspense-wrapped component that needs it
Using full SSR for pages that are 90% staticSlow time to first byte for no benefitUse static or PPR with dynamic holes
Following a blog post for PPR flags from an older versionConfiguration doesn't match your framework versionCheck the docs for the version you run
Practice
  1. Take a page with one personalised element and restructure it so only that element is dynamic, then compare it with the fully dynamic version.
  2. Classify five pages in an app you know as static, revalidated, dynamic, or PPR, and justify each.
Key takeaways
  • PPR serves a static shell instantly and streams dynamic regions in afterwards.
  • Mark dynamic regions with Suspense and read request data only inside them.
  • Choose a rendering mode per page and per region, and verify against your framework version's docs.
