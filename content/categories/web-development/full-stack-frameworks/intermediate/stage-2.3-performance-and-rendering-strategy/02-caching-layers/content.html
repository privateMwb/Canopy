Caching Layers

Data cache, full-route cache, CDN, and invalidation.

§1Many Caches, Different Jobs

A request in a full-stack app can pass through several caches. When something looks stale, the first question is *which* layer is serving it. The exact set depends on framework and version; this lesson uses the Next.js model as the example.

LayerWhereCachesInvalidated by
Request memoizationServer, one render passDuplicate identical requests in one renderAutomatic; ends with the request
Data cacheServer, persistentResults of data fetchesTime (revalidate), tags, or paths
Full-route cacheServer / build outputRendered HTML and RSC payload for static routesRevalidation or a new deploy
CDN / edge cacheNetwork edgeResponses for repeated requestsTTL, purge, or Cache-Control rules
Client router cacheBrowser memoryVisited and prefetched route payloadsTime, refresh, or action revalidation
HTTP browser cacheBrowserFiles and responses per headersCache-Control, ETags, URL changes

§2Controlling the Edge and Browser

Headers tell shared caches and browsers what they may keep. Static assets with hashed filenames can be cached essentially forever, while HTML should be revalidated.

# Hashed JS/CSS: cache for a year, never revalidate
Cache-Control: public, max-age=31536000, immutable

# Dynamic page: CDN may keep it 60s and serve stale while refreshing
Cache-Control: public, s-maxage=60, stale-while-revalidate=300

# Personalised response: never store in a shared cache
Cache-Control: private, no-store

§3Invalidation Strategy

  • Tag data by what it represents (product:42, posts), and invalidate tags from the mutation that changes them.
  • Cache the right granularity: a whole page, a component, or a single query.
  • Never cache personalised responses in a shared cache, or one user may receive another's data.
  • Test freshness in production: the dev server hides most caching behaviour.

Phil Karlton's old joke still holds: the two hard problems are naming things and cache invalidation. Keeping a clear map of layers and tags is how you keep the second one manageable.

Debug stale data top-down Ask in order: is the browser caching it, is the CDN, is the framework's full-route cache, is the data cache? Bypass layers one at a time (hard refresh, curl the origin, check response headers) until the stale copy disappears.

§4Common Mistakes

MistakeWhat HappensFix
Caching a personalised page at the CDNUsers see each other's data, a serious privacy bugMark such responses private or no-store and vary correctly
Using one long TTL and no invalidationUpdates take hours to appearTag data and invalidate when it changes
Debugging staleness in dev modeProduction caches don't exist locally, so the bug is invisibleReproduce with a production build, and inspect response headers
Practice
  1. Use curl -I on a deployed page and static asset and explain each Cache-Control and CDN cache header you see.
  2. Draw the path of a request through every cache layer in your app, and mark where a stale copy could hide.
Key takeaways
  • Several caches stack (memoization, data, route, CDN, router, browser), each with its own invalidation rules.
  • Use Cache-Control to separate immutable assets, revalidated HTML, and private responses.
  • Tag data for precise invalidation, never cache personalised responses publicly, and debug layer by layer.
