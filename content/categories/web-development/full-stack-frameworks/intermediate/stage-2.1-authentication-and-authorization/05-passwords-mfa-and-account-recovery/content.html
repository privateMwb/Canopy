Passwords, MFA & Account Recovery

Doing the unglamorous parts safely.

§1The Parts Everyone Gets Wrong

Password handling, multi-factor authentication, and recovery flows are unglamorous and easy to break. If you manage credentials yourself, follow the rules below; if you use a provider, they handle most of this, but you still need to understand it.

§2Storing Passwords

  • Never store plain text, and never use fast hashes such as MD5 or plain SHA-256.
  • Use a slow, salted, purpose-built algorithm: Argon2id (preferred), scrypt, or bcrypt.
  • Each password gets its own random salt, which the library handles for you.
  • Compare using the library's verify function, not string equality.
import { hash, verify } from "@node-rs/argon2";

const stored = await hash(password);          // salted Argon2id hash
const ok = await verify(stored, attempt);     // constant-time comparison

Follow current NIST guidance: favour length over arbitrary complexity rules, allow long passphrases and paste, and check new passwords against lists of known breached passwords.

§3Multi-Factor Authentication

MFA adds a second proof. Strength varies: passkeys (WebAuthn) and hardware keys are phishing-resistant, authenticator-app codes (TOTP) are good, and SMS codes are the weakest because SIM swapping and interception exist. Offer recovery codes at enrolment, hashed in storage and single-use.

§4Account Recovery

Recovery is the back door to an account, so it must not be weaker than the front door. Use single-use, random, expiring reset tokens, store only their hash, send them by email, and invalidate all sessions after a reset. Return the same message whether or not the email exists, so attackers can't enumerate accounts.

// Always respond identically
return { message: "If that email exists, we've sent a reset link." };
Consider not storing passwords at all Passkeys and social or magic-link login remove the biggest liability. Fewer secrets in your database means a breach exposes less.

§5Common Mistakes

MistakeWhat HappensFix
Hashing with SHA-256 or MD5Passwords are cracked quickly after a leakUse Argon2id, scrypt, or bcrypt
Revealing whether an email is registeredAttackers can enumerate your user baseUse identical responses and similar timing
Reset tokens that don't expire or can be reusedOld emails become permanent account keysUse short-lived, single-use, hashed tokens
Practice
  1. Hash and verify a password with Argon2id, then show that the same password produces different hashes because of salting.
  2. Design a password-reset flow on paper and list three ways an attacker could abuse it and how you would prevent each.
Key takeaways
  • Hash passwords with Argon2id, scrypt, or bcrypt, never fast hashes.
  • Prefer phishing-resistant MFA such as passkeys; treat SMS as a fallback.
  • Recovery flows must be as strong as login: single-use tokens, expiry, and no account enumeration.
