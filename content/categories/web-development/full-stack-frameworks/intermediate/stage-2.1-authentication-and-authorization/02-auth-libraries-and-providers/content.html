Auth Libraries & Providers

Auth.js, Clerk, and OAuth flows.

§1Don't Hand-Roll Authentication

Password hashing, session rotation, OAuth flows, and account linking are easy to get subtly wrong. Most teams use a library or a hosted provider. The choice is mostly about control versus convenience.

OptionExamplesYou ownTrade-off
Library in your appAuth.js, Better Auth, Lucia-style patternsUser data and sessions in your databaseMore control, more to maintain
Hosted providerClerk, Auth0, WorkOS, Supabase AuthLittle; the vendor stores usersFast and polished, but vendor lock-in and cost at scale

Library features and project names change often. Check current documentation before choosing, and prefer one with active maintenance.

§2How OAuth Sign-In Works

'Sign in with Google' uses OAuth 2.0 with OpenID Connect. Your app never sees the user's Google password; it redirects them to Google, and Google redirects back with a short-lived code that your server exchanges for tokens.

  1. The user clicks 'Sign in with Google'; your app redirects to Google with a client_id, a redirect_uri, scopes, a state value, and a PKCE challenge.
  2. The user authenticates and consents on Google's domain.
  3. Google redirects back to your redirect_uri with a one-time code and your state.
  4. Your server verifies state, then exchanges the code (and PKCE verifier) for an ID token and access token.
  5. Your app reads the verified identity, creates or finds the local user, and starts its own session.

§3Configuration in Practice

// auth.ts (Auth.js-style configuration)
export const { handlers, auth, signIn, signOut } = NextAuth({
  providers: [Google, GitHub],
  session: { strategy: "database" },   // server-side sessions
  callbacks: {
    session({ session, user }) {
      session.user.role = user.role;    // expose only what the UI needs
      return session;
    },
  },
});

Register the exact redirect URIs with the provider for each environment (local, preview, production). Mismatched URIs are the most common reason sign-in fails after a deploy.

Identity is not the same as your user A provider tells you who someone is (an id and email). Your database still needs its own user record for roles, preferences, and data. Link the two with the provider's stable id rather than the email alone.

§4Common Mistakes

MistakeWhat HappensFix
Skipping the state parameter checkLogin CSRF: an attacker can bind their account to a victim's sessionAlways generate and verify state (libraries do this for you)
Matching accounts by email without verificationAccount takeover through an unverified email at another providerRequire a verified email, or link via explicit user action
Forgetting production redirect URIsSign-in works locally but fails when deployedRegister a URI for every environment
Practice
  1. Add Google or GitHub sign-in to a small app using an auth library and read the user on the server.
  2. Write the five steps of the OAuth code flow in your own words, and mark which steps happen in the browser and which on your server.
Key takeaways
  • Use a maintained library or hosted provider rather than writing authentication yourself.
  • OAuth with OpenID Connect delegates login while your app still creates its own session.
  • Register redirect URIs per environment and link provider identities to local users safely.
