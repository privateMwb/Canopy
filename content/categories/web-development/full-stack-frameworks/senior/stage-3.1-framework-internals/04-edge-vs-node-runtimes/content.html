Edge vs. Node Runtimes

Capabilities, limits, and cold starts.

§1Two Places Your Code Can Run

Serverless platforms offer two execution environments. The Node.js runtime is a full server-side JavaScript environment. The edge runtime is a lightweight, V8-isolate-based environment that starts almost instantly and runs in many locations, but supports only web-standard APIs.

PropertyNode.js runtimeEdge runtime
Cold startHundreds of milliseconds, more with large bundlesTypically a few milliseconds
GeographyOne or a few regions you chooseGlobally distributed
Available APIsFull Node API, native modules, filesystemWeb APIs (fetch, Request, Web Crypto, streams)
Bundle size limitsLarge (tens to hundreds of MB)Small (low single-digit MB on many platforms)
Execution limitsLonger timeouts and more memoryTight CPU and time limits
Database accessAny driver and connection poolingHTTP or edge-compatible drivers

§2Cold Starts

A cold start happens when a platform must create a new instance to serve a request: it loads your code, initialises modules, and may open connections. Cost grows with bundle size and top-level work. Mitigations include smaller bundles, lazy-loading heavy modules, avoiding expensive top-level initialisation, and platform features such as instance reuse or provisioned concurrency. Newer 'fluid' compute models reuse instances across concurrent requests to reduce how often cold starts occur, but they can't be eliminated.

// Slow cold start: heavy work at module load
const model = await loadHugeModel();            // runs on every new instance

// Better: defer until needed, then reuse
let model: Model | undefined;
export async function getModel() { return (model ??= await loadHugeModel()); }

§3Choosing a Runtime

  • Choose Node.js by default for anything touching a database, using npm packages, or doing real computation.
  • Choose edge for small, latency-critical logic: redirects, header manipulation, personalisation lookups against edge-friendly stores.
  • Co-locate compute with data. If the database is in one region, a function in that region usually beats edge compute making several cross-region round trips.
  • Check platform limits for timeouts, memory, and bundle size before you design around them.
Latency is a sum of round trips Edge placement shortens the first hop, but a request that then makes four sequential calls to a far-away database can lose all that gain. Count the network hops, not just where the code starts.

§4Common Mistakes

MistakeWhat HappensFix
Choosing edge for everything because it sounds fasterChatty database calls cross regions and total latency risesRun data-heavy code near the database, on Node
Heavy top-level initialisationEvery cold start pays the costDefer, lazy-load, and cache expensive setup
Exceeding edge bundle or API limits late in developmentLast-minute rewritesCheck limits before choosing the runtime for a route
Practice
  1. Measure the cold-start and warm latency of the same route on both runtimes (or in two regions) and explain the difference.
  2. For a route that does three database queries, estimate total latency for an edge function and for a function beside the database.
Key takeaways
  • Node.js offers full capability; the edge offers fast starts and global reach with strict limits.
  • Cold starts scale with bundle size and top-level work, so keep both small.
  • Place compute near its data, and choose edge only for light, latency-critical logic.
