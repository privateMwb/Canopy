Data Access Layers

Keeping database code out of components.

§1The Problem with Queries Everywhere

In a small app it's tempting to call the ORM directly from every component and action. As the app grows, the same query is copy-pasted with slight variations, authorization checks are forgotten in some places, and a schema change touches dozens of files. A data access layer (DAL) is a small set of server-only functions through which all data access flows.

§2What a DAL Looks Like

// lib/dal/tasks.ts
import "server-only";
import { cache } from "react";

// Authorization + shape live here, once
export const getTasksForCurrentUser = cache(async () => {
  const user = await requireUser();
  const rows = await db.task.findMany({
    where: { ownerId: user.id },
    select: { id: true, title: true, done: true },   // explicit, minimal shape
    orderBy: { createdAt: "desc" },
  });
  return rows satisfies TaskDTO[];
});

export async function completeTask(id: string) {
  const user = await requireUser();
  const result = await db.task.updateMany({ where: { id, ownerId: user.id }, data: { done: true } });
  if (result.count === 0) throw new NotFoundError();
}

Components and actions call getTasksForCurrentUser() rather than db.task.findMany(). The DAL guarantees that every caller gets authorized, minimal, correctly shaped data.

§3Design Principles

  • Server-only: mark the module with server-only so it can never be bundled for the browser.
  • Authorize inside: each function checks the current user's rights, so a forgotten check at the call site can't leak data.
  • Return DTOs, not rows: data transfer objects contain only fields the UI may see. Password hashes and internal flags never escape.
  • Express intent: name functions for business operations (completeTask, listInvoicesForOrg), not table operations.
  • One place for transactions and caching: wrap multi-step writes in transactions, and tag or memoize reads here.

Keep the layer thin. It isn't a place for a speculative repository abstraction over every table; it is a boundary that makes the rules enforceable and the code searchable.

Make the safe path the easy path If querying the database directly is easier than going through the DAL, people will. Make the DAL convenient, then enforce with lint rules that forbid importing the ORM outside it.

§4Common Mistakes

MistakeWhat HappensFix
Passing raw ORM rows to client componentsSensitive columns leak into the page payloadReturn explicit DTOs from the DAL
Authorization only at the page levelOther callers, such as actions and handlers, bypass itCheck inside each data function
Over-abstracting with generic repositories for every tableBoilerplate that hides what queries actually runKeep functions task-specific and small
Practice
  1. Refactor three direct ORM calls into DAL functions that authorize and return DTOs. Then add a lint rule forbidding the ORM import elsewhere.
  2. Write a test that proves the DAL denies access to another user's record for every function.
Key takeaways
  • A server-only data access layer centralises queries, authorization, and shaping.
  • Return DTOs, and name functions for business intent rather than table operations.
  • Enforce its use with lint rules so the safe path is the default.
