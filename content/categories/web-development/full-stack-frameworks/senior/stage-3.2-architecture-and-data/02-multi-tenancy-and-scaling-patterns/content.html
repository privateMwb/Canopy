Multi-Tenancy & Scaling Patterns

Isolating customers and growing safely.

§1Many Customers, One System

A multi-tenant application serves many customers (tenants) from one deployment. The central design question is how to keep one tenant's data invisible to the others while still sharing infrastructure for cost and operational simplicity.

ModelHow it worksIsolationCost and ops
Shared tables + tenant_idAll tenants in the same tables, filtered by a tenant columnLogical; relies on correct filteringCheapest and easiest to operate; noisy-neighbour risk
Schema per tenantEach tenant gets its own schema in one databaseStrongerMigrations run per schema; harder at thousands of tenants
Database per tenantEach tenant gets a separate databaseStrongest, easy per-tenant restoreHighest cost and operational overhead

Most SaaS products start with shared tables and a tenant_id, moving large or regulated customers to dedicated databases as needed.

§2Enforcing Isolation

With shared tables, a single forgotten WHERE tenant_id = ? is a data breach. Don't rely on developers remembering. Make isolation structural.

-- PostgreSQL Row-Level Security: the database enforces the filter
ALTER TABLE tasks ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON tasks
  USING (tenant_id = current_setting('app.tenant_id')::uuid);

-- Per request, inside a transaction:
-- SET LOCAL app.tenant_id = '<the signed-in user's tenant>';
  • Resolve the tenant from the verified session, never from a client-supplied header or form field.
  • Put tenant_id in every table, include it in unique constraints and indexes, and make it part of the DAL's required arguments.
  • Use row-level security or a query wrapper so queries without a tenant fail loudly.
  • Test cross-tenant access explicitly: tenant A must never read or write tenant B's rows.

§3Scaling Patterns

  • Noisy neighbours: apply per-tenant rate limits and quotas, so one customer can't starve others.
  • Sharding by tenant: when one database can't hold everyone, route tenants to shards by tenant_id.
  • Per-tenant features and config: keep plans, flags, and limits in data, not code branches.
  • Tenant-aware observability: tag logs and metrics with tenant ids to find who is affected.
  • Routing: tenants may arrive via subdomain (acme.app.com), path, or custom domain; resolve and verify early, in middleware plus a server check.
Isolation bugs are the worst bugs A normal bug annoys users. A tenant-isolation bug exposes one customer's data to another and can end the business relationship. Defence in depth (application checks plus database policies plus tests) is justified here.

§4Common Mistakes

MistakeWhat HappensFix
Trusting a tenant id sent from the clientA user can pass another tenant's id and read its dataDerive the tenant from the authenticated session
Unique constraints without tenant_idTenants collide on values like usernames or slugsScope uniqueness per tenant
No per-tenant limitsOne heavy customer degrades everyoneAdd quotas and rate limits keyed by tenant
Practice
  1. Add a tenant_id and a row-level security policy to one table, then write a test proving a second tenant can't see the first tenant's rows.
  2. Sketch how you'd migrate your largest customer to a dedicated database with minimal downtime.
Key takeaways
  • Choose shared tables, schema-per-tenant, or database-per-tenant by weighing isolation against cost.
  • Enforce isolation structurally with session-derived tenant ids, required DAL arguments, and row-level security.
  • Plan for noisy neighbours with quotas, tenant-aware monitoring, and a path to shard or isolate large tenants.
