What a Full-Stack Framework Gives You

Routing, rendering, data, and build tooling in one package.

§1What You'd Otherwise Assemble Yourself

A React app on its own is a view library. To ship a real product you also need a router, a way to render on the server for first paint and SEO, a bundler and compiler, a place for backend code, data fetching, caching, and a deployment story. A full-stack framework such as Next.js, Remix, Nuxt, or SvelteKit bundles those decisions into one coherent package.

ConcernPlain React (Vite)Full-stack framework
RoutingAdd a router library and configure itFolders and files define routes
RenderingClient-side only unless you build SSR yourselfServer, static, and client rendering built in
Backend codeA separate server projectRoute handlers and server functions in the same repo
Data loadinguseEffect plus a fetching libraryFetch in the server layer, close to the UI
Build and deployHand-tuned bundler configOne build command; the platform understands the output

§2Conventions Over Configuration

The framework trades flexibility for decisions already made. You put a file in a known place and it becomes a page, an API endpoint, or a layout. This course uses the Next.js App Router, but every framework here has an equivalent idea.

npx create-next-app@latest my-app    # scaffold a project
cd my-app && npm run dev            # dev server with hot reload
npm run build && npm start          # production build and server

The three commands you will use constantly are dev for development, build to compile for production, and start to serve the production build. Always test a production build before you deploy, because dev mode hides problems such as caching behaviour.

§3What You Give Up

Frameworks are opinionated. You accept their folder layout, their rendering model, and their upgrade schedule. Some features are tied to a hosting platform, and the framework's own abstractions (caching, server components) have to be learned in addition to React. That cost is usually worth paying, but it is a real cost, and Stage 3.4 returns to the question of when plain tools beat a framework.

The key insight A full-stack framework is not about writing less React. It's about the code around React: where it runs, when it runs, and how it reaches the browser. Learning those answers is the actual curriculum.

§4Common Mistakes

MistakeWhat HappensFix
Treating the framework as 'React with extras'You apply client-only habits (useEffect for everything) and lose server rendering benefitsAsk first: can this run on the server before the page is sent?
Judging the framework from the dev server onlyCaching, performance, and errors behave differently in productionRun build and start before you decide something works
Choosing a framework by popularity aloneYou inherit trade-offs that don't fit your appMatch the framework to your rendering, hosting, and team needs
Practice
  1. Scaffold a new Next.js app, run it in dev, then run a production build and read the build output. Which routes are marked static and which are dynamic?
  2. Pick one feature of a React app you've built (routing, data loading, or deployment) and list how the framework changes how you'd do it.
Key takeaways
  • A full-stack framework bundles routing, rendering, backend code, and build tooling into one convention-driven package.
  • Conventions replace configuration: files and folders in known places become pages, layouts, and endpoints.
  • The price is opinionated structure and framework-specific concepts you must learn.
