Caching & Revalidation

Time-based and on-demand revalidation.

§1Why Caching Matters

Rendering and fetching cost time and money. Caching stores a result so the next request can reuse it. The hard part isn't storing data; it's deciding when stored data is stale. Frameworks give you two main tools: time-based and on-demand revalidation.

Caching defaults have changed across Next.js releases (earlier versions cached fetch results aggressively, newer ones lean toward opt-in caching), so always read the docs for the version you run and set your intent explicitly.

§2Time-Based Revalidation

Tell the framework how long a result stays fresh. After that window, the next request triggers a regeneration in the background while the old copy is still served (stale-while-revalidate).

// Cache this fetch for 1 hour
const res = await fetch("https://api.example.com/products", {
  next: { revalidate: 3600 },
});

// Or for a whole route segment
export const revalidate = 3600;

§3On-Demand Revalidation

Time windows are guesses. If you know exactly when data changes, such as when an editor publishes a post, invalidate it then. Tag the data when you fetch it, and revalidate the tag or path inside a mutation.

// Reading: tag the cached data
await fetch(url, { next: { tags: ["posts"] } });

// Writing: invalidate it after a change
"use server";
import { revalidateTag, revalidatePath } from "next/cache";

export async function publishPost(data: FormData) {
  await savePost(data);
  revalidateTag("posts");        // everything tagged 'posts' becomes stale
  revalidatePath("/blog");       // or target a specific path
}

Newer versions also offer a use cache directive for caching functions and components explicitly, with cacheLife and cacheTag to control lifetime. The idea is the same: declare what is cacheable and how long it lasts.

Prefer on-demand over short timers A one-minute revalidate on a page that changes twice a month wastes work and still serves stale data. Tag your data and invalidate it at the moment it changes.

§4Common Mistakes

MistakeWhat HappensFix
Assuming data is cached (or not) without checkingStale pages, or needless load on your APIState your caching intent explicitly and verify in production
Mutating data without revalidatingUsers still see the old version after savingCall revalidateTag or revalidatePath after the write
Using very long revalidate windows for changing dataUsers see outdated informationUse on-demand revalidation for event-driven changes
Practice
  1. Build a blog list with revalidate: 60, change the underlying data, and watch when the page updates.
  2. Switch the same page to tag-based revalidation triggered by a Server Action and compare the behaviour.
Key takeaways
  • Caching trades freshness for speed, so decide explicitly how stale data may be.
  • Time-based revalidation regenerates after a window; on-demand revalidation invalidates when data changes.
  • Always check what your framework version caches by default.
