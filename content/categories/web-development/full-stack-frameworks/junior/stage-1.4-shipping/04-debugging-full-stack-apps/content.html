Debugging Full-Stack Apps

Logs, the network tab, and server errors.

§1Know Where the Code Ran

The hardest part of debugging a full-stack app is knowing where a failure happened. The same file may run at build time, on the server, or in the browser, and each has its own place to look.

SymptomLook here first
Page is blank or broken in the browserBrowser console for client errors
A request returns 4xx or 5xxNetwork tab: status, request body, and response
Server Component or action throwsTerminal (dev) or the platform's function logs (production)
Works in dev, fails after deployBuild logs and environment variables
Hydration warningMismatch between server HTML and client render

§2A Repeatable Process

  1. Reproduce the problem reliably, and note the exact steps.
  2. Locate the layer: build, server, network, or browser.
  3. Read the message. Errors usually name the file, the line, and often the cause.
  4. Narrow down by logging or bisecting until the failing line is isolated.
  5. Fix and verify, ideally with a test that would have caught it.
// Server code logs to the terminal / platform logs, NOT the browser console
console.error("createTask failed", { userId, error });

§3Common Culprits

  • Hydration mismatches: rendering Date.now(), random values, or window checks differently on server and client.
  • Missing environment variables: undefined in production because they were only set locally.
  • Stale cache: old data from a cache you forgot you had; test with a hard refresh and check revalidation.
  • Server-only code in a client file: build errors that name the offending import chain.
Production hides detail on purpose To avoid leaking internals, production error pages show a generic message and a digest. Search your server logs for that digest to find the real stack trace.

§4Common Mistakes

MistakeWhat HappensFix
Looking in the browser console for a server errorNothing is there, so you assume there is no errorCheck the terminal or platform function logs
Changing several things at onceYou can't tell which change matteredChange one variable at a time
Ignoring warnings in devThey become production failures laterTreat hydration and key warnings as bugs
Practice
  1. Introduce a hydration mismatch with new Date().toLocaleTimeString() in a component and fix it.
  2. Break an environment variable on purpose in a deployed preview, then find the failure using only the platform logs.
Key takeaways
  • First decide which layer failed: build, server, network, or browser.
  • Server errors appear in terminal or platform logs, not the browser console.
  • Reproduce, locate, read the message, narrow down, then fix and verify.
