Deploying to Vercel

Previews, production, and environment config.

§1From Git Push to Live URL

Vercel (built by the makers of Next.js) connects to your Git repository. Every push triggers a build, and the result is deployed automatically. Pushes to your production branch (usually main) go live; pushes to any other branch become preview deployments with their own URLs.

  1. Push your project to GitHub, GitLab, or Bitbucket.
  2. Import the repository in the Vercel dashboard. The framework is detected automatically.
  3. Add your environment variables before the first build.
  4. Deploy. Vercel runs next build and publishes the output globally.

§2Environments and Their Variables

Vercel has three environments: Production, Preview, and Development. Each can have different variable values, so previews can point at a staging database while production uses the real one. A variable that is set for the wrong environment is the most common cause of 'works locally, breaks in production.'

EnvironmentTriggered byTypical config
ProductionMerge or push to the production branchReal database, live API keys
PreviewAny other branch or pull requestStaging database, test API keys
Developmentvercel dev / vercel env pullLocal values
npm i -g vercel
vercel link             # connect this folder to a project
vercel env pull         # download development variables to .env.local
vercel --prod           # deploy from the CLI (usually Git does this)

§3What Gets Deployed

Static pages go to the CDN, and dynamic routes and Server Actions become serverless functions that scale on demand. You don't manage servers, but you do inherit platform limits such as function timeouts and memory, which Stage 3.1 and 3.4 examine. Other hosts (Netlify, Cloudflare, AWS, a Docker container) can run the same framework with differing levels of feature support.

Build locally first If npm run build fails on your machine, it will fail on the platform too. Type errors and lint errors that dev mode tolerated often surface only at build time.

§4Common Mistakes

MistakeWhat HappensFix
Forgetting environment variables on the platformThe build or runtime fails because configuration is missingAdd variables for each environment before deploying
Pointing previews at the production databaseTest activity corrupts real dataUse a separate staging database for the Preview environment
Never reading the build logsYou miss warnings that become production bugsRead the log when a deploy fails, and skim it when it succeeds
Practice
  1. Deploy your task manager to Vercel and add the database URL as an environment variable.
  2. Push a change on a new branch and find the preview URL that was generated for it.
Key takeaways
  • A Git push triggers a build; the production branch goes live and other branches get preview URLs.
  • Environment variables are set per environment, so verify each one.
  • Always run a production build locally before relying on the platform.
