The Critical Rendering Path

The critical rendering path is the sequence of work between receiving HTML and drawing the first pixels. Shortening it is how you get meaningful content on screen fast.

§1The Path, Step by Step

To show anything, the browser must complete a chain: parse HTML into the DOM, parse CSS into the CSSOM, combine them into a render tree, compute layout, and paint. Anything that delays one link delays first paint.

StepNeedsCan be delayed by
DOM constructionHTML bytesSlow response, blocking scripts
CSSOM constructionAll applicable CSSLarge or slow stylesheets
Render treeDOM and CSSOMWhichever finishes last
Layout and paintRender treeHeavy DOM, expensive styles

CSS is render-blocking because painting before styles arrive would flash unstyled content. Scripts can be parser-blocking, and a script that reads styles must wait for the CSSOM first. These interactions create the chains that matter.

§2Three Ways to Shorten It

Think in three quantities: critical resources (how many block rendering), critical bytes (how big they are), and critical path length (how many round trips in sequence).

  1. Send less critical data. Minify and compress CSS, and inline the above-the-fold rules so the first paint doesn't wait on a stylesheet request.
  2. Cut round trips. Avoid chains such as CSS importing more CSS (@import) or a stylesheet loading a font before text can render. Reference things directly in the HTML.
  3. Stop non-critical work blocking. Defer scripts, load below-the-fold CSS asynchronously, and keep large work out of the head.
/* Bad: a hidden chain. HTML -> main.css -> theme.css, in sequence */
@import url('theme.css');

<!-- Better: both discovered in the HTML, fetched in parallel -->
<link rel="stylesheet" href="main.css">
<link rel="stylesheet" href="theme.css">

§3Getting First Content Out Early

Besides shortening the path, deliver meaningful content early. A server can stream HTML, sending the head and the first part of the body while it is still working on the rest, so the browser starts discovering resources sooner.

  • Flush the <head> early so the browser can start fetching CSS and fonts while the server builds the page.
  • Put critical content in the initial HTML. A page that is an empty <div id="root"> has nothing to paint until JavaScript downloads, runs, and fetches data.
  • Keep the first screen simple: fewer elements means a cheaper layout.
<head>
  <meta charset="utf-8">
  <title>Shop</title>
  <style>/* critical CSS for the first screen */</style>
  <link rel="stylesheet" href="/rest.css" media="print" onload="this.media='all'">
  <script src="/app.js" defer></script>
</head>

Measure the effect with First Contentful Paint and LCP, and use the Performance panel's trace to confirm that the number of sequential steps actually shrank.

The key insight Performance of the first paint is mostly about dependency chains. Count how many requests must finish, in order, before the browser can draw, and try to make that number small.

§4Common Mistakes

MistakeWhat HappensFix
Using CSS @importCreates a sequential chain that delays renderingUse separate <link> tags, or bundle
Shipping an empty HTML shell for everythingNothing to paint until JavaScript runsRender critical content on the server or at build time
Inlining all CSSLarge HTML that can't be cached separatelyInline only the first screen's rules
Practice
  1. Open a trace of a page load. Count the requests that must complete, in order, before first paint.
  2. Remove a CSS @import chain from a test page and measure FCP before and after.
Key takeaways
  • The path runs DOM, CSSOM, render tree, layout, and paint, and CSS blocks rendering.
  • Shorten it with fewer critical resources, fewer critical bytes, and fewer sequential round trips.
  • Stream HTML early and put the first screen's content in the initial response.
