Server Response Time

Nothing renders until the HTML arrives. Time to First Byte sets the floor for every other metric, so a slow server limits everything built on top of it.

§1What TTFB Includes

Time to First Byte is measured from the start of the navigation to the first byte of the response. It includes more than your server's thinking time.

ComponentNotes
RedirectsEach redirect is a full extra round trip; chains add up
DNS, connect, TLSNetwork setup before any request
Request travelDistance to the server
Server processingYour code, database queries, and upstream calls
Response startThe first bytes returning

A good TTFB is often considered under about 800 ms at the 75th percentile, but since it sits at the start of the LCP budget, faster is better. The Server-Timing header lets your server report its own timings so you can see where the time went.

HTTP/1.1 200 OK
Server-Timing: db;dur=82, render;dur=34, cache;desc="miss"

§2Making the Server Faster

  • Cache at every layer. Cache full pages or fragments, query results, and computed data. A cache hit skips the expensive work.
  • Use a CDN for static and cacheable HTML so the response comes from a nearby edge.
  • Reduce redirects. Link to the final URL, including https:// and the canonical hostname.
  • Optimize the slow path. Find the slow queries, add indexes, avoid N+1 queries, and run independent calls in parallel.
  • Keep connections warm to databases and upstream services, using pooling.
  • Stream the response so the browser gets the head early while the rest is generated.
// Independent calls run in parallel, not one after another
const [user, cart, recs] = await Promise.all([
  getUser(id),
  getCart(id),
  getRecommendations(id),
]);

§3Edge Rendering and Stale Content

If a page is the same for most visitors, serve it from the edge and avoid your origin altogether. When content can be a little stale, two directives make that safe.

Cache-Control: public, s-maxage=60, stale-while-revalidate=300
# CDN serves a cached page for 60s; for the next 300s it serves the stale
# copy instantly while fetching a fresh one in the background

Running logic at the edge, on a CDN's compute platform, can personalize or assemble a response close to the user without a trip to a distant origin. It trades simplicity for speed, and makes data access harder, so use it where latency matters most.

Gotcha Measure TTFB from real users, not just from your own region. A server that responds in 100 ms to you can respond in 900 ms to someone across an ocean.

§4Common Mistakes

Testing TTFB only from your own locationDistant users are slower than you thinkCheck field TTFB by region
Practice
  1. Measure the TTFB of a page with curl -w '%{time_starttransfer}' and break it down using the timing fields.
  2. Add a Server-Timing header to one endpoint and read it in the Network panel's Timing tab.
Key takeaways
  • TTFB includes redirects, network setup, travel, and server processing, and it limits every later metric.
  • Cache, use a CDN, remove redirects, parallelize work, and stream the response.
  • Use stale-while-revalidate and edge delivery to answer fast without losing freshness.
