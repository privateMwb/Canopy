Statistics for Performance Data

Performance numbers are noisy and skewed. A few statistical habits stop you shipping a 'fix' that was just luck, and from missing a real regression.

§1Averages Lie, Percentiles Don't

Load times are not a bell curve. Most visits are fast, with a long tail of very slow ones. The mean gets dragged around by the tail and describes almost nobody's actual experience.

StatisticWhat it tells you
Median (p50)The typical visit: half are faster, half slower
p75The bar Core Web Vitals use
p95 / p99How bad the slow tail is
MeanEasily distorted. Rarely the right summary.
const sorted = [...samples].sort((a, b) => a - b);
const pct = p => sorted[Math.min(sorted.length - 1, Math.floor(p * sorted.length))];
console.log({ p50: pct(0.5), p75: pct(0.75), p95: pct(0.95) });

Always keep the full distribution in view. A histogram shows things a single number hides, such as two clusters of users, one on fast devices and one on slow.

§2Noise and Repeatability

Run the same lab test ten times and you'll get ten different answers. Network jitter, CPU load, background processes, and caching all move the numbers. A single before-and-after pair says almost nothing.

  • Run many iterations and compare medians, not single runs.
  • Control what you can: same machine, same throttling, same time of day, cold or warm cache consistently.
  • Look at the spread. If before and after ranges overlap heavily, you can't tell them apart.
  • Beware of warm-up effects. The first run is often an outlier.

§3Not Fooling Yourself

Field data adds its own traps. Visits change as traffic changes, so a metric can move without any code change.

TrapExampleDefense
Mix shiftA marketing push brings more slow-phone users, and p75 worsensSegment by device and country before blaming code
Small samplesp95 from 40 visitsRequire a minimum sample size
Cherry-pickingReporting the one run that looks goodDecide the metric and method before testing
Regression to the meanAn unusually bad day looks better the nextCompare over longer windows
Simpson-style effectsEvery segment improves but the total worsensCheck both the aggregate and the segments

The gold standard is an A/B test: randomly split users, change one thing, and compare the same metric across the groups over the same period. It controls for most of these effects.

Rule of thumb If you can't say how much the number varies when nothing changes, you can't tell whether a change did anything.

§4Common Mistakes

MistakeWhat HappensFix
Reporting the mean load timeThe long tail distorts itReport p50, p75, and p95
Concluding from one before-and-after testNoise may account for the differenceRepeat, and compare distributions
Blaming code for a field regression without segmentingThe audience mix may have changedSlice by device, country, and release
Practice
  1. Run a lab test ten times on the same page. Record the median and the range, and say how big a change you could detect.
  2. Take a field metric and compare its p75 against its mean. Explain why they differ.
Key takeaways
  • Performance data is skewed, so use percentiles and look at the distribution, not the mean.
  • Repeat lab tests, control conditions, and look at spread before claiming an improvement.
  • Watch for mix shift, small samples, and cherry-picking, and use A/B tests when you need proof.
