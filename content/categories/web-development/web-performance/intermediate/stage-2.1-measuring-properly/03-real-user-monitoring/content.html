Real User Monitoring

Lab tests tell you what could happen. Real user monitoring tells you what does. The web-vitals library makes collecting it straightforward.

§1Why Collect Your Own Field Data

Public datasets such as CrUX cover only some sites, are aggregated over a window, and can't be sliced by your own dimensions. Collecting your own field data lets you see metrics per page type, per country, per release, per device class, and in near real time.

  • Find which pages and user segments are slow.
  • Spot a regression within hours of a deploy.
  • Measure INP, which needs real interactions.
  • Connect performance to business metrics in your own analytics.

§2Collecting with web-vitals

Google's web-vitals library wraps the browser APIs and handles the awkward cases, such as pages loaded in the background, back-forward cache restores, and final values reported when the page is hidden.

import { onLCP, onINP, onCLS, onTTFB } from 'web-vitals/attribution';

function send(metric) {
  const body = JSON.stringify({
    name: metric.name,
    value: metric.value,
    rating: metric.rating,            // 'good' | 'needs-improvement' | 'poor'
    id: metric.id,
    page: location.pathname,
    attribution: metric.attribution,  // what element / what interaction
  });
  // sendBeacon survives page unload; fall back to fetch with keepalive
  (navigator.sendBeacon && navigator.sendBeacon('/rum', body)) ||
    fetch('/rum', { method: 'POST', body, keepalive: true });
}

onLCP(send); onINP(send); onCLS(send); onTTFB(send);

The attribution build adds the context that makes a poor number actionable: which element was the LCP, which interaction was the slowest INP, and which element shifted.

§3Analyzing the Data

Don't average. Performance data is skewed by a long tail of slow visits, so look at percentiles, especially the 75th, which is what Core Web Vitals use.

SELECT page,
       approx_percentile(value, 0.75) AS p75_lcp,
       COUNT(*)                       AS samples
FROM rum_events
WHERE name = 'LCP' AND ts > now() - interval '7 days'
GROUP BY page
HAVING COUNT(*) > 200          -- ignore pages with too few samples
ORDER BY p75_lcp DESC;
  • Segment by device class, connection type, country, and release.
  • Use a sampling rate if volume is large, but keep enough samples to be meaningful.
  • Respect privacy: don't collect personal data, and follow your consent rules.
Gotcha Different browsers support different metrics, so each number covers only the browsers that report it. State that when you compare your data to public datasets.

§4Common Mistakes

MistakeWhat HappensFix
Reporting averagesA long tail hides the pain of slow usersUse the 75th percentile and the full distribution
Sending with plain fetch on unloadBeacons are lost when the page closesUse sendBeacon or fetch with keepalive
Collecting the metric but not the attributionYou know it's slow but not whyUse the attribution build and send the culprit
Practice
  1. Add web-vitals to a page and send the four metrics to a simple logging endpoint. Open the page on a phone and inspect what arrives.
  2. Write a query for the 75th percentile LCP by page over the last week.
Key takeaways
  • Your own field data can be sliced by page, device, release, and country.
  • web-vitals handles edge cases, and its attribution build tells you what caused a poor value.
  • Analyze percentiles by segment, with enough samples and respect for privacy.
