Web Workers & Off-Main-Thread Work

The main thread handles input, layout, and paint, and your code competes with them. Moving heavy work to a worker keeps the interface responsive.

§1Why Move Work Off the Main Thread

JavaScript on the main thread blocks everything else. Parsing a large file, filtering a big dataset, image processing, or compression can easily take hundreds of milliseconds, freezing input and animation for that long. That directly hurts INP.

A Web Worker runs JavaScript on a separate thread, with its own event loop. It can't touch the DOM, but it can compute and send results back, so the main thread stays free to respond.

Good for workersPoor fit
Parsing or transforming large dataAnything that needs the DOM directly
Search, sort, and filter on big listsTiny tasks where messaging costs more than the work
Image, audio, and video processingWork that needs frequent synchronous access to main-thread state
Compression, crypto, and encodingWork that only waits on the network, which is already asynchronous

§2Using a Worker

// worker.js
self.onmessage = (e) => {
  const result = expensiveSearch(e.data.query, e.data.items);
  self.postMessage(result);
};

// main.js
const worker = new Worker(new URL('./worker.js', import.meta.url), { type: 'module' });
worker.onmessage = (e) => render(e.data);
searchInput.addEventListener('input', () => {
  worker.postMessage({ query: searchInput.value, items });
});

Messages are copied with the structured clone algorithm, which costs time for large data. For big binary data, use transferable objects such as ArrayBuffer, which move ownership to the worker without copying.

const buffer = new ArrayBuffer(50_000_000);
worker.postMessage({ buffer }, [buffer]);   // transferred, not copied: buffer is now unusable here

§3Making Workers Practical

  • Use a library such as Comlink to call worker functions like ordinary async functions, instead of hand-writing message protocols.
  • Reuse a worker instead of creating one per task, since startup has a cost.
  • Consider a worker pool for many parallel tasks, sized to the device's cores.
  • Share memory carefully. SharedArrayBuffer and Atomics allow shared state but require cross-origin isolation and careful synchronization.
  • Other off-main-thread options: OffscreenCanvas for rendering in a worker, and service workers for network handling (a different purpose).
import * as Comlink from 'comlink';
const api = Comlink.wrap(new Worker(new URL('./worker.js', import.meta.url), { type: 'module' }));
const result = await api.expensiveSearch(query, items);   // looks like a normal call

Measure before and after. A worker adds overhead for messaging and startup, so confirm in a trace that the long task has actually disappeared from the main thread.

The key insight A worker doesn't make computation faster, it makes it not block the interface. The result may arrive slightly later, but the page stays responsive meanwhile.

§4Common Mistakes

MistakeWhat HappensFix
Sending huge objects back and forthCloning costs more than the work savedUse transferables, or keep data in the worker
Creating a new worker for every small taskStartup overhead dominatesReuse a worker or a pool
Moving tiny tasks to a workerMessaging overhead outweighs the gainOnly move work over about 50 ms
Practice
  1. Take a function that blocks the main thread for 200 ms or more, move it into a worker, and show the long task gone in a trace.
  2. Rewrite your message passing using Comlink and compare the code.
Key takeaways
  • Workers run JavaScript on another thread, so heavy computation doesn't block input or paint.
  • Messages are copied unless you transfer ownership, so mind the data size.
  • Reuse workers, consider Comlink, and verify the improvement in a trace.
