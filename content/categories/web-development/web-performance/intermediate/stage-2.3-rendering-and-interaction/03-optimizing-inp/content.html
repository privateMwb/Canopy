Optimizing INP

INP measures how fast the page responds to every interaction. It is almost always poor because the main thread is busy when the user clicks.

§1The Three Parts of an Interaction

INP takes the slow interactions of a visit, and reports roughly the worst, from the moment of input until the browser paints the next frame. Each interaction breaks into three phases.

PhaseWhat it isCommon cause when long
Input delayWaiting for the main thread to become freeA long task already running, such as a timer or a script
Processing timeYour event handlers runningHeavy handlers, synchronous work, big re-renders
Presentation delayHandlers finish until the next frame paintsLarge DOM updates, expensive layout and paint

Good is 200 ms or less at the 75th percentile. Use web-vitals attribution to see which phase and which element hurt real users, and the Performance panel's Interactions track to reproduce it.

§2Breaking Up Long Tasks

The browser can't respond while a task runs, and any task over 50 ms is a long task. The core fix is to do less in one go, and yield to the browser so it can handle input and paint between chunks.

function yieldToMain() {
  if (globalThis.scheduler?.yield) return scheduler.yield();   // resumes with priority
  return new Promise(resolve => setTimeout(resolve, 0));        // older fallback
}

async function processAll(items) {
  let last = performance.now();
  for (const item of items) {
    handle(item);
    if (performance.now() - last > 40) {   // stay under ~50ms per chunk
      await yieldToMain();
      last = performance.now();
    }
  }
}
  • Do the essential visual update first, such as showing a spinner or toggling state, then yield and do the rest.
  • Defer non-urgent work, like analytics, with requestIdleCallback or after a yield.
  • Move heavy computation off the main thread into a Web Worker (next stage).

§3Cheaper Handlers and Updates

  • Avoid redundant work. Debounce input handlers that don't need to run on every keystroke, and throttle scroll handlers.
  • Limit what re-renders. In a framework, update only the affected components, and memoize expensive computations.
  • Reduce DOM size and complexity, since presentation delay grows with how much the browser must restyle and lay out.
  • Don't block on third parties. Their scripts add long tasks that delay your handlers.
button.addEventListener('click', async () => {
  button.disabled = true;           // 1. instant visual feedback
  spinner.hidden = false;
  await yieldToMain();              // 2. let the browser paint it
  const result = heavyWork();       // 3. then do the expensive part
  render(result);
});
The key insight INP is not about speed in general. It is about whether the main thread is free at the moment of interaction, so shorter tasks and earlier visual feedback are the levers.

§4Common Mistakes

MistakeWhat HappensFix
Running a large loop in one synchronous taskThe page freezes for the durationChunk it and yield between chunks
Doing all work before showing any feedbackThe interaction looks unresponsiveUpdate the UI first, then continue
Optimizing handler code when input delay is the problemThe thread was busy before the handler even beganCheck the phase breakdown first
Practice
  1. Record an interaction in the Performance panel and read the input delay, processing time, and presentation delay.
  2. Break one long-running handler into chunks that yield, and show the long task disappear in a new trace.
Key takeaways
  • INP covers input delay, processing time, and presentation delay for the worst interactions.
  • Break long tasks, yield, show feedback first, and move heavy work off the main thread.
  • Diagnose the phase before choosing a fix.
