Core Web Vitals

Three field metrics describe whether a page loads quickly, responds promptly, and stays visually stable.

§1The Three Metrics

Core Web Vitals are a small set of metrics, defined by Google and measured in real browsers, that focus on what users feel. Each has a threshold for 'good', judged at the 75th percentile of real visits. That means three quarters of visits must meet the bar.

MetricQuestion it answersGoodPoor
LCP: Largest Contentful PaintHow soon is the main content visible?≤ 2.5 s> 4 s
INP: Interaction to Next PaintHow quickly does the page respond to input?≤ 200 ms> 500 ms
CLS: Cumulative Layout ShiftDoes the page jump around?≤ 0.1> 0.25

INP replaced the older First Input Delay metric in 2024. FID only measured the delay before the first interaction. INP looks at the responsiveness of interactions across the whole visit.

§2What Each One Measures

LCP times when the largest image or block of text in the viewport finishes rendering. It's a proxy for 'the page looks loaded'. Typical culprits are a slow server, a render-blocking resource, or a hero image that was discovered late.

INP observes every click, tap, and key press, and measures the time from the input until the next frame is painted. The page reports roughly the worst interaction. It is poor when the main thread is busy with JavaScript and can't respond.

CLS sums up unexpected movement of visible elements. A shift is bad if it happens without user input, such as an image loading without reserved space and pushing the text down just as you go to tap.

import { onLCP, onINP, onCLS } from 'web-vitals';

onLCP(m => console.log('LCP', m.value));   // milliseconds
onINP(m => console.log('INP', m.value));   // milliseconds
onCLS(m => console.log('CLS', m.value));   // unitless score

§3Using the Vitals Well

The vitals are a diagnostic starting point, not the whole of performance. They don't cover everything, such as total JavaScript cost or how a single-page app behaves across navigations, but they target the common ways pages feel bad.

  • Pages are assessed on real-user data at the 75th percentile, so improving the typical visit isn't enough if a slow tail drags it down.
  • A fast LCP with a bad CLS is still a poor experience. Each metric covers a separate failure.
  • Other metrics, such as TTFB and FCP, help you diagnose why a vital is poor.
Remember the split LCP is about loading, INP is about responsiveness, and CLS is about stability. When one is poor, that tells you which kind of problem to hunt for.

§4Common Mistakes

MistakeWhat HappensFix
Reporting the average instead of the 75th percentileHides the slow visits that drag the page below the barLook at the 75th percentile, and the full distribution
Optimizing the score instead of the experienceTricks can hit the number and still feel slowVerify improvements by watching real loads
Assuming FID is still the responsiveness metricYou track a retired measureUse INP
Practice
  1. Add the web-vitals library to a test page and log LCP, INP, and CLS. Interact with the page and watch the values change.
  2. For each vital, name one thing on a page that would make it poor.
Key takeaways
  • LCP, INP, and CLS measure loading, responsiveness, and visual stability.
  • Thresholds are judged at the 75th percentile of real visits: 2.5 s, 200 ms, and 0.1.
  • The vitals point you toward a kind of problem, and other metrics help explain it.
