What Happens When You Load a Page

Between typing a URL and seeing a page, a chain of steps runs. Each one can be slow, and knowing the chain tells you where to look.

§1The Network Steps

When you navigate to https://example.com/, the browser can't ask for the page until it knows where the server is and has a secure channel to it.

  1. DNS lookup: turn the hostname into an IP address. Often cached, sometimes tens of milliseconds.
  2. TCP connection: a handshake to open a reliable channel. One round trip. (HTTP/3 uses QUIC instead, which merges this step with the next.)
  3. TLS handshake: agree on encryption and verify the certificate. One more round trip, often fewer on repeat connections.
  4. HTTP request and response: send the request, wait for the server, receive the first byte (TTFB), then the rest.

Each round trip costs the full network latency. On a 150 ms mobile connection, three round trips are nearly half a second before a single byte of HTML arrives. This is why servers close to users, connection reuse, and fewer origins matter.

§2The Browser Steps

The HTML response is only the start. The browser turns it into pixels in stages.

  • Parse HTML into the DOM. When the parser meets a stylesheet or script, it may have to wait for it.
  • Build the CSSOM from all the CSS. Rendering can't start until the CSS that applies is known.
  • Combine into a render tree, the elements that will actually be shown and their styles.
  • Layout: compute the size and position of everything.
  • Paint and composite: draw the pixels and layer them onto the screen.
<html>
  <head>
    <link rel="stylesheet" href="/app.css">   <!-- blocks first paint until loaded -->
    <script src="/app.js"></script>            <!-- blocks the parser while it downloads and runs -->
  </head>
  <body>
    <img src="/hero.jpg">                      <!-- discovered as the parser reaches it -->
  </body>
</html>

Images and fonts don't block the first render of text, but they arrive late and can shift the layout or delay the largest visible element. JavaScript can then change everything again.

§3Finding Where the Time Goes

The Network panel in DevTools shows the steps as a waterfall. For each request you can see the connection setup, the wait for the server, and the download.

Waterfall segmentWhat it meansCommon cause when long
DNS / Connect / SSLSetting up the connectionMany origins, no connection reuse
Waiting (TTFB)Server is workingSlow backend, no cache, distance
Content downloadBytes movingLarge files, no compression
Gap before a request startsThe browser didn't know about it yetResource discovered late
The key insight Slow means different things at different steps. A slow server, a heavy download, and a blocked render look similar to a user but need different fixes.

§4Common Mistakes

MistakeWhat HappensFix
Blaming 'the network' without looking at the waterfallYou optimize the wrong stepRead connection, wait, and download times separately
Loading assets from many different hostnamesEach new origin pays DNS, TCP and TLSConsolidate origins, or use preconnect for the necessary ones
Putting large scripts in the head with no deferThe parser stops and the page stays blankDefer non-critical scripts
Practice
  1. Load any page with DevTools open to the Network tab. Find the HTML request and read its connection, waiting, and download times.
  2. Find one resource that the browser discovered late (it starts well after the HTML arrives). Explain why it was discovered late.
Key takeaways
  • Before the first byte arrives, DNS, TCP, and TLS each add round trips.
  • The browser builds the DOM and CSSOM, then does layout, paint, and composite, and CSS and scripts can block that.
  • The waterfall shows which step is slow, which decides what to fix.
