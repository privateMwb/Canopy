Browser Cache vs. CDN Cache

A response can be cached in several places between your server and the user's screen. Each layer has a different owner, size, and way to clear it.

§1The Layers

On its way to the user, a response may pass through, and be stored by, several caches. A request is answered by the closest layer that has a usable copy.

LayerWhere it livesWho it servesControlled by
Browser cacheOn the user's deviceOnly that userCache-Control, user actions
CDN / edge cacheA server near the userMany users in a regions-maxage, CDN rules, purging
Origin cacheYour own app or proxyAll traffic reaching youYour application

A browser hit costs nothing at all. A CDN hit costs one short trip to a nearby server. A miss at every layer travels all the way to your origin, which is the slowest and most expensive path.

§2Same Headers, Different Audiences

Shared caches such as a CDN follow the same Cache-Control headers as browsers, with a few additions that let you treat them separately.

Cache-Control: public, max-age=60, s-maxage=600
# browsers: fresh for 60 seconds
# shared caches (CDN): fresh for 600 seconds
  • s-maxage applies only to shared caches, overriding max-age for them.
  • private keeps a response out of shared caches, which is essential for per-user data.
  • Vary lists request headers that change the response, such as Accept-Encoding, so each variant is stored separately.

Many CDNs also add headers such as Age and an X-Cache style field that report whether a response was a hit. Check your provider's documentation for the exact names.

§3Invalidation Is the Hard Part

Once a copy is cached, you can't reach into every user's browser to remove it. A CDN, though, usually offers a purge.

LayerHow you change what users see
Browser cacheChange the URL, or wait for expiry. You cannot purge it.
CDN cachePurge by URL, tag, or path, or change the URL
Origin cacheClear it from your own system

Because browsers can't be purged, the dependable way to ship changes is to change the URL. That idea, called fingerprinting, is the next lesson.

The key insight Think in layers. Decide what each layer may cache and for how long, and use private for anything personal so a shared cache never serves one user's data to another.

§4Common Mistakes

MistakeWhat HappensFix
Letting a CDN cache personalized responsesOne user may be served another's dataMark them private or no-store, and use Vary correctly
Relying on purging to update browsersPurging can't reach local cachesUse versioned URLs for assets
Forgetting Vary: Accept-EncodingA client may receive an encoding it can't decodeEnsure the cache keys on encoding
Practice
  1. Fetch the same asset twice through a CDN and read the Age header. Explain what it shows.
  2. Write the Cache-Control for an API response that should be cached by a CDN for 5 minutes but by browsers for 30 seconds.
Key takeaways
  • Responses can be cached in the browser, at a CDN edge, and at your origin, and the closest hit wins.
  • s-maxage, private, and Vary give shared caches separate rules from browsers.
  • Browsers can't be purged, so changing the URL is the reliable way to invalidate.
