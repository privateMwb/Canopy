HTTP Caching Headers

Caching is the fastest optimization there is: a request that never happens costs nothing. A few headers decide whether a response can be reused, and for how long.

§1Cache-Control

The Cache-Control response header tells browsers and shared caches how to treat a response. The most important directives:

DirectiveMeaning
max-age=3600The response is fresh for 3600 seconds. No request is made while fresh.
no-cacheMay be stored, but must be revalidated with the server before each reuse
no-storeNever store it. Use for sensitive data.
public / privateShared caches may store it / only the user's own browser may
immutableIt will not change while fresh, so skip revalidation even on reload
stale-while-revalidate=NMay serve a stale copy for N seconds while refreshing in the background

no-cache is badly named: it does not mean 'don't cache'. It means 'check before using'. The directive that forbids storing is no-store.

§2Validation: ETag and 304

When a cached response becomes stale, the browser can ask the server whether it changed instead of downloading it again. The server provides a validator, an ETag or Last-Modified, and the browser sends it back.

GET /logo.svg HTTP/1.1
If-None-Match: "a1b2c3"        # I have version a1b2c3, has it changed?

HTTP/1.1 304 Not Modified       # no body, reuse your copy
ETag: "a1b2c3"
Cache-Control: max-age=3600

A 304 still costs a round trip, but no body. That is far cheaper than a full download, though far worse than a fresh cache hit that needs no request at all.

§3Choosing Values

  • Fingerprinted assets like app.3f9a1c.js: public, max-age=31536000, immutable. A new version gets a new URL.
  • HTML documents: no-cache (revalidate), or a short max-age, so users see updates promptly.
  • Personalized or sensitive responses: private or no-store.
  • Rarely changing, unversioned files such as a logo: a moderate max-age plus an ETag.
# Inspect what a server actually sends
curl -sI https://example.com/app.3f9a1c.js | grep -i -E 'cache-control|etag|last-modified|age'

If you set no caching headers at all, browsers may apply heuristics, guessing a lifetime from Last-Modified. Don't rely on that. State your intent explicitly.

Gotcha max-age on a file whose URL never changes means users can be stuck on the old version until it expires. Long lifetimes are only safe when the URL changes with the content.

§4Common Mistakes

MistakeWhat HappensFix
Believing no-cache stops storageSensitive data gets stored and reused after revalidationUse no-store when data must never be kept
Long max-age on an unversioned fileUsers keep seeing the old file after a deployFingerprint the filename, or keep the lifetime short
No caching headers at allUnpredictable heuristic cachingSet Cache-Control explicitly on every response type
Practice
  1. Use curl -sI on three kinds of file on a site (HTML, a script, an image) and record each Cache-Control.
  2. Request a file with an If-None-Match header from its ETag and confirm the server answers 304.
Key takeaways
  • max-age makes a response fresh with no request, and no-store is the only directive that forbids storage.
  • Validators (ETag, Last-Modified) let a stale copy be reused through a body-less 304.
  • Pair long lifetimes with versioned URLs, and keep HTML revalidated.
