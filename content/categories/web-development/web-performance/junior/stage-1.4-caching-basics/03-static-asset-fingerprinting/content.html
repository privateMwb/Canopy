Static Asset Fingerprinting

Give a file a name that changes whenever its content does, and you can cache it essentially forever and still ship updates instantly.

§1The Problem

You want users to cache your JavaScript and CSS for a long time, so repeat visits are fast. But you also need to ship a bug fix and have everyone get it immediately. With a fixed filename like app.js, those two goals conflict: a long cache lifetime means stale code, and a short one means constant revalidation.

§2The Solution: Content Hashes in Filenames

Fingerprinting (or cache busting) puts a hash of the file's contents into its name. If the content changes, the hash and name change. If it doesn't, the name stays the same.

app.js           # before: the name never changes
app.3f9a1c7e.js  # after: the name is derived from the content

# deploy changes one line of code:
app.b81d04aa.js  # a new URL, so every browser fetches it fresh

Now the old URL can be cached for a year with no risk, because it will never be reused for different content. The HTML, which references the file, is the only thing that needs to stay fresh.

# Served for fingerprinted assets
Cache-Control: public, max-age=31536000, immutable

# Served for the HTML page that references them
Cache-Control: no-cache

§3How It Works in Practice

Modern bundlers do this for you. They hash each output file and rewrite the HTML or a manifest to point at the new names.

// vite.config.js - hashed filenames are the default for production builds
export default {
  build: {
    rollupOptions: {
      output: { entryFileNames: 'assets/[name].[hash].js' }
    }
  }
};
  • Hash the content, not the build time, so unchanged files keep their name and stay cached across deploys.
  • Keep the HTML short-lived. If it were cached for a year, it would keep pointing at old asset names.
  • Splitting code into separate chunks helps: a change to one chunk invalidates only that file.
  • Keep recently used old assets on the server for a while, so users with an open tab on the old HTML don't hit missing files.
Why this works Caching rules attach to a URL. Change the URL and you've created a new cache entry, so the old one can never serve stale content.

§4Common Mistakes

MistakeWhat HappensFix
Using ?v=2 query strings for versioningSome caches ignore or strip queries, and it's easy to forget to bumpPut the hash in the filename
Giving the HTML a long max-ageUsers never see new asset namesKeep HTML revalidated, no-cache or short
Deleting old assets immediately on deployOpen tabs break when they request old filesKeep previous versions for a grace period
Practice
  1. Build a small project with a bundler and confirm output files have content hashes. Change one source file and see which names change.
  2. Set the response headers for hashed assets and for HTML, then verify them with curl -sI.
Key takeaways
  • Put a content hash in the filename so each version has its own URL.
  • Cache fingerprinted assets for a year with immutable, and keep the HTML fresh.
  • Hash by content and keep old files briefly to avoid breaking open pages.
