Removing Unused Code

The fastest code is code that never ships. Find the JavaScript and CSS a page downloads but never uses, and cut it.

§1Where Unused Code Comes From

Sites accumulate dead weight. A framework is imported for one helper, a CSS library ships thousands of unused rules, and features are removed while their code stays. Users pay for all of it in download, parse, and execution time.

  • Whole libraries imported for a small part of their API.
  • Global CSS frameworks where a page uses a small fraction of the rules.
  • Old experiments, abandoned features, and duplicate dependencies.
  • Polyfills for browsers you no longer support.

§2Measuring It

Chrome's Coverage tool shows how much of each file ran during a page load. Open DevTools, then the Command Menu (Ctrl or Cmd + Shift + P), then 'Show Coverage', and reload.

What you seeHow to read it
Red barsBytes not executed or not applied during the recording
Blue or green barsBytes that were used
High unused % on a big fileA candidate for splitting or removal

Coverage has a limit: code that isn't used yet looks unused. A checkout flow's code won't run on the home page, but it is still needed on the checkout page. Use the tool to find candidates, then decide carefully.

# See what a bundle is made of
npx source-map-explorer dist/app.js
# or, with a Vite or Rollup project
npx vite-bundle-visualizer

§3Cutting It

  1. Remove dead features and unused dependencies outright.
  2. Import narrowly: import only the functions you use so tools can drop the rest.
  3. Split by route or interaction so code loads only when needed.
  4. Purge unused CSS with a build step, or use a utility or component approach that generates only what's used.
  5. Update your browser targets so you stop shipping polyfills and transforms for browsers nobody uses.
// Imports the entire library
import _ from 'lodash';
const a = _.debounce(fn, 200);

// Imports one function
import debounce from 'lodash/debounce';
const b = debounce(fn, 200);

Be careful with CSS purging. Classes added dynamically at runtime can be mistaken for unused and deleted. Safelist them, and test the real pages.

Gotcha Coverage records one page load. A route, a modal, or an error path that never ran during your recording will look entirely unused, so verify across real flows before deleting.

§4Common Mistakes

MistakeWhat HappensFix
Deleting code that Coverage marked unusedYou break a feature that runs later in the sessionCheck usage across the whole flow before removing
Importing a whole library for one helperA large bundle for little benefitImport the specific function, or use a smaller alternative
Purging CSS without a safelistDynamically added classes lose their stylesSafelist dynamic class names and test
Practice
  1. Open Coverage on a real page, reload, and note the unused percentage of the largest JavaScript and CSS files.
  2. Find one dependency imported whole but used for a single function, and replace it with a narrow import.
Key takeaways
  • Unused JavaScript and CSS still cost download, parse, and execution time.
  • Coverage and bundle analyzers find candidates, but 'not used yet' is not 'never used'.
  • Remove, import narrowly, split by route, and purge CSS carefully.
