Debugging Regressions

A metric got worse and no one knows why. Finding the cause is detective work: narrow the window, compare traces, and isolate the change.

§1Confirm and Characterize

Before hunting for a cause, be sure the regression is real and learn its shape. Many 'regressions' are noise, a traffic mix shift, or a measurement change.

  1. Confirm it is real. Does it appear in several runs or a large field sample, and beyond normal variation?
  2. Find when it started. Plot the metric over time, annotate deploys, and find the step.
  3. Find who is affected. Segment by page, device, browser, country, and connection. A regression concentrated in one segment points at a cause.
  4. Find which part of the metric moved. For LCP, check the phases. For INP, check input delay, processing, and presentation. For loading, check TTFB.
  5. Check non-code explanations. Traffic changes, third-party updates, CDN or infrastructure changes, and a different browser version.
PatternSuggests
Step change at a deploy timeA code or config change in that release
Gradual creepAccumulated small changes, growing data, or caches getting colder
Only one country or ISPCDN or routing issue
Only one browserBrowser update or a feature-specific code path
Only logged-in usersPersonalization code or heavier data

§2Isolating the Cause

Once you have a window, shrink it. The tool is bisection: halve the range of candidate changes until one remains.

# Bisect commits with an automated performance check
git bisect start HEAD v2.14.0
git bisect run ./scripts/perf-check.sh
# perf-check.sh builds, runs the lab test several times, and exits non-zero
# when the median LCP exceeds the threshold
  • Diff the traces. Record a trace from before and after, line them up, and look for the new long task, the new request, or the added delay.
  • Diff the waterfalls and bundles. A new dependency, a request chain, or a missing cache header are common.
  • Check configuration and infrastructure, not only code: headers, CDN rules, feature flags, and experiments.
  • Use feature flags to toggle suspects off in production and watch the metric.
  • Change one thing at a time when testing a hypothesis.

§3Fix, Verify, and Prevent

  • Fix the cause, not the symptom. Deleting the long task beats adding a loading spinner over it.
  • Verify in the same way you detected it: lab test first, then field data over enough time.
  • Write it down. A short post-incident note: what happened, how it was found, what fixed it.
  • Close the gap that let it through. Add a test, budget, or alert that would have caught it, because every regression shows a missing guardrail.
# Post-incident note template
Symptom:     p75 INP on /checkout rose 180 -> 340 ms on Oct 12
Detected by: RUM alert, 14 h after deploy
Cause:       new address-validation script ran 220 ms on each keystroke
Fix:         debounced and moved to a worker
Prevention:  added INP lab assertion for the checkout flow
The key insight Narrow first, then explain. Time, segment, and metric phase tell you where to look, and bisection and trace diffs tell you what changed.

§4Common Mistakes

MistakeWhat HappensFix
Jumping to a suspect without confirming the regressionHours spent on noise or a mix shiftConfirm, then find when and for whom
Changing several things while testingYou can't tell which one matteredChange one thing at a time
Fixing it and moving onThe same class of regression returnsAdd the guardrail that would have caught it
Practice
  1. Given a metric chart with a step change and a list of deploys, state the segmentation and trace comparisons you would run first.
  2. Write a short post-incident note for a regression you have seen or imagine, including the prevention step.
Key takeaways
  • Confirm the regression, then find when it started, who is affected, and which phase moved.
  • Bisect commits, diff traces and waterfalls, and toggle suspects with flags.
  • Verify the fix, document it, and add the guardrail that was missing.
