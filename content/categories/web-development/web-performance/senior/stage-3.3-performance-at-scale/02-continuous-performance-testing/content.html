Continuous Performance Testing

A performance test that runs once is a snapshot. One that runs on every change is a safety net. The trick is making it reliable enough that people trust it.

§1What to Run, and Where

LayerRunsCatches
Static checksEvery commitBundle size, request counts, forbidden dependencies
Lab testsEvery pull request or preview deployRegressions in LCP, TBT, CLS, transfer size on a controlled setup
Scheduled lab runsHourly or nightly against productionThird-party changes and infrastructure drift with no code change
Synthetic monitoringContinuously from several regionsAvailability and slowness from outside
Real-user monitoringAlwaysWhat actually reaches users, including things the lab misses

Each layer covers gaps in the others. Lab tests are repeatable but unrealistic. Field data is realistic but arrives after release and is noisy. Together they catch problems early and confirm them later.

§2Making Lab Tests Trustworthy

A flaky performance test gets ignored, so reducing noise is the main engineering problem.

  • Fix the environment. Same machine class, same throttling, same location, same browser version, pinned.
  • Run multiple times and use the median, typically 5 or more runs per URL.
  • Mock or stub what you can't control: third-party calls, time-varying data, and ads.
  • Use deterministic metrics where possible. Bytes and request counts don't fluctuate, so make them hard gates, and treat timings as softer thresholds.
  • Compare with a baseline from the main branch run under the same conditions, not with an absolute number alone.
  • Allow a tolerance. Fail only when a change exceeds the noise by a margin.
// lighthouserc.js (Lighthouse CI)
module.exports = {
  ci: {
    collect: { url: ['http://localhost:3000/', 'http://localhost:3000/product/1'], numberOfRuns: 5 },
    assert: {
      assertions: {
        'largest-contentful-paint': ['error', { maxNumericValue: 2500, aggregationMethod: 'median' }],
        'total-blocking-time':      ['warn',  { maxNumericValue: 300 }],
        'resource-summary:script:size': ['error', { maxNumericValue: 180000 }],
      },
    },
    upload: { target: 'temporary-public-storage' },
  },
};

§3Alerting and Closing the Loop

  • Alert the owner, not a shared channel. A regression should reach the team that can fix it.
  • Alert on sustained change, such as a rolling median shifting for several runs, not on a single bad run.
  • Link alerts to the cause: the commit range, deploy, or third-party change, plus a trace to open.
  • Track trends with a time-series chart of key metrics per page, annotated with deploys.
  • Reconcile lab and field. If the lab is green but field metrics regress, your tests are missing something, so add it.
  • Keep the suite fast. A test that takes an hour won't run on every pull request.
# A minimal CI step
- run: npm run build
- run: npx lhci autorun         # fails the job when budgets are exceeded
- run: node scripts/check-bundle-size.js
The key insight Trust is the product. A test suite that cries wolf is turned off, so invest first in stability: pinned environments, repeated runs, medians, and tolerances.

§4Common Mistakes

MistakeWhat HappensFix
Failing builds on a single noisy timingFlaky failures train people to ignore the checkUse medians over several runs and a tolerance
Testing only the labMisses third-party and real-device regressionsAdd scheduled synthetic runs and real-user monitoring
Sending alerts to a general channelNo one owns the responseRoute to the owning team with context
Practice
  1. Set up Lighthouse CI against a local build with five runs and median assertions. Deliberately add a large script and confirm it fails.
  2. Write down which of your metrics should be hard gates (deterministic) and which soft thresholds (noisy).
Key takeaways
  • Layer static checks, lab tests, scheduled runs, and real-user monitoring, because each covers the others' gaps.
  • Reduce noise with fixed environments, repeated runs, medians, and tolerances.
  • Route alerts to owners with context, and reconcile lab results with field data.
