Networking Deep Dive

Latency and bandwidth are not the same thing, and most page loads are limited by round trips. Understanding TCP, TLS, and QUIC explains why.

§1Latency, Bandwidth, and Round Trips

Bandwidth is how much data per second the link can carry. Latency is how long a signal takes to cross it. Typical pages are made of many small requests, so they are dominated by round trips, and you can't buy your way out of the speed of light by buying more bandwidth.

StepRound trips (typical, HTTPS over TCP)
DNS lookup (uncached)1 or more
TCP handshake1
TLS 1.3 handshake1 (0 with resumption and early data)
HTTP request and first byte1

On a link with 100 ms round-trip time, that is already 300 to 400 ms before the first byte of HTML. QUIC, the transport under HTTP/3, combines the transport and TLS handshakes, which cuts a round trip, and supports resumption for repeat visits.

§2TCP Slow Start and Congestion Control

A new TCP connection doesn't know how fast the path is, so it starts slow. It sends a small initial window of packets, typically around 10, then doubles per round trip until it detects loss or hits capacity. A 100 KB response over a fresh connection can therefore take several round trips just to ramp up.

# Rough shape on a fresh connection, initial window ~10 packets (~14 KB):
# RTT 1:  ~14 KB   RTT 2:  ~28 KB   RTT 3:  ~56 KB   RTT 4: ~112 KB ...
# A 100 KB file needs about 4 round trips even on a fast link.
  • This is why the first ~14 KB of a response is special: it can arrive within the first window. Keeping critical HTML and inline CSS compact helps.
  • Reusing a warm connection avoids the ramp-up cost, so fewer origins is better.
  • Loss triggers backoff. On mobile networks where loss is common, throughput can fall sharply.

§3Head-of-Line Blocking and QUIC

TCP delivers bytes strictly in order. If one packet is lost, everything behind it waits, even data belonging to unrelated requests. HTTP/2 multiplexes many requests over one TCP connection, so a single lost packet can stall them all: head-of-line blocking moved down a layer.

QUIC runs over UDP and implements streams itself. Loss on one stream blocks only that stream. It also supports connection migration, so a phone moving from wifi to cellular can keep its connection.

Protocol stackSetupLoss on one stream
HTTP/1.1 over TCP + TLSTCP and TLS handshakesBlocks only that connection (but only one request each)
HTTP/2 over TCP + TLSTCP and TLS handshakesStalls all streams on the connection
HTTP/3 over QUICCombined handshakeStalls only the affected stream

Practical consequences: use a CDN so connections terminate near users, enable HTTP/3, use preconnect for unavoidable third parties, and keep critical content small. Test on lossy, high-latency profiles, because that is where these differences show.

The key insight Think in round trips, not megabytes. Each avoidable handshake, redirect, or new origin costs a full round trip, which on mobile is a large fraction of your budget.

Practice
  1. Compute the time to first byte for a fresh HTTPS connection at 120 ms RTT using the round-trip table. Then recompute for a resumed HTTP/3 connection.
  2. Explain why a 100 KB file can take multiple round trips on a fast link.
Key takeaways
  • Page loads are bound by round trips, which handshakes, redirects, and extra origins all add to.
  • TCP slow start means new connections ramp up gradually, and the first ~14 KB matters.
  • QUIC removes TCP-level head-of-line blocking and shortens setup, and it helps most on lossy links.
