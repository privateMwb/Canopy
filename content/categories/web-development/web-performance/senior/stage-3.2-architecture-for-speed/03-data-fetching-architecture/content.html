Data Fetching Architecture

Many slow pages are slow because of when they ask for data, not how long the data takes. Request waterfalls are an architecture problem.

§1The Waterfall Problem

A request waterfall is a chain in which each request can only start once the previous one finishes, because it depends on its result, or because the code that makes it hasn't loaded or rendered yet. Each link adds a full round trip.

// Classic client-side waterfall
// 1. HTML arrives             (200 ms)
// 2. JavaScript downloads and runs   (400 ms)
// 3. App fetches /user      (250 ms)
// 4. Then renders <Orders>, which fetches /orders  (250 ms)
// 5. Then renders <OrderItem>, which fetches /items/:id  (250 ms each)
// Content appears after ~1.4 s, though no single request is slow.

Components that fetch their own data inside their children are the usual cause: the child doesn't exist until the parent has rendered, so its fetch can't start earlier.

§2Flattening the Chain

TechniqueHow it helps
Fetch in parallelStart independent requests together with Promise.all
Hoist fetching to the routeDecide what data a page needs before rendering components
Fetch on the serverData and HTML arrive together. The server is close to the data.
Batch requestsOne request for many items, instead of N+1 requests
Aggregate in a backend-for-frontendA single endpoint returns exactly what the screen needs
Preload the dataStart fetching on navigation intent, such as hover, before the page code even runs
Cache and deduplicateIdentical in-flight requests share one fetch
// Sequential: 750 ms
const user = await getUser();
const orders = await getOrders(user.id);
const recs = await getRecs(user.id);

// Parallel where possible: dependent step first, independents together
const user = await getUser();
const [orders, recs] = await Promise.all([getOrders(user.id), getRecs(user.id)]);

// Better: if the server can resolve it, one call
const page = await fetch('/api/dashboard');

§3Designing the Data Layer

  • Treat fetching as a design decision. Decide who fetches what, and when, rather than letting every component do its own.
  • Use a query cache (such as TanStack Query or SWR) for deduplication, background refresh, and sharing results between components.
  • Stream slower data separately, so fast data shows right away and slow parts fill in behind skeletons that reserve space.
  • Prefetch likely next requests when idle or on intent, and cancel stale ones.
  • Watch for over-fetching, such as giant payloads when the screen needs three fields. Shape responses to the view.
  • Think about GraphQL and BFFs as tools to reduce round trips, with the cost of their own caching complexity.
// Start fetching on intent, long before the click completes
link.addEventListener('pointerenter', () => queryClient.prefetchQuery(['order', id], () => getOrder(id)), { once: true });

To find waterfalls, read the request waterfall and ask of each late request: what had to happen before this could start? The answer shows what to hoist or parallelize.

The key insight The data that a page needs is usually known before the components that use it exist. Fetch it as early and as in parallel as possible, ideally on the server or at route level.

§4Common Mistakes

MistakeWhat HappensFix
Each nested component fetching its own dataA chain of sequential requestsHoist fetching to the route or the server
N+1 queries: one request per list itemDozens of round tripsBatch, or return the needed data in one call
Awaiting independent calls one after anotherLatency adds upUse Promise.all
Practice
  1. Read a page's request waterfall, identify the longest dependency chain, and say what each link waited for.
  2. Redesign that page's data fetching to remove at least two links in the chain, and estimate the saving.
Key takeaways
  • Waterfalls arise from dependent requests, often hidden in nested components.
  • Fetch in parallel, hoist to the route or server, batch, and prefetch on intent.
  • Shape and cache the data layer deliberately instead of leaving it to each component.
