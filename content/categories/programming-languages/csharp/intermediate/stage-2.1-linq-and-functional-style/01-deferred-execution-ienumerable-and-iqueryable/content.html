Deferred Execution, IEnumerable & IQueryable

A LINQ query is a description of work, not the work itself. Knowing exactly when it runs explains most surprising LINQ behavior, especially against a database.

§1Queries Run When You Enumerate Them

var numbers = new List<int> { 1, 2, 3 };
var query = numbers.Where(n => n > 1);   // nothing has run yet

numbers.Add(10);                          // change the source

foreach (var n in query)                  // runs now
    Console.Write(n + " ");               // 2 3 10

Where, Select, OrderBy, and similar operators are deferred: they build a pipeline and return immediately. The work happens when something enumerates the result, through foreach, ToList(), Count(), First(), and so on. Operators that return a single value or a collection (ToList, Sum, ToDictionary) are immediate.

§2Consequences

var query = orders.Where(o => ExpensiveCheck(o));

int a = query.Count();      // runs the whole pipeline
var list = query.ToList();  // runs it AGAIN: ExpensiveCheck called twice per item

var snapshot = orders.Where(o => ExpensiveCheck(o)).ToList(); // run once, reuse
  • Repeated enumeration repeats the work (and any side effects). Materialize with ToList() when you'll use the result more than once.
  • Changes to the source are visible to a query not yet run, as the first example shows.
  • Exceptions surface late: an invalid element throws when you enumerate, not where you wrote the query.
  • Streaming: Where and Select pass items through one at a time, so First() can stop early. OrderBy and GroupBy must read everything first.

§3IEnumerable vs. IQueryable

IEnumerable<T> runs in your process, with lambdas compiled to delegates. IQueryable<T>, which Entity Framework returns, takes expression trees instead, so a provider can translate the query into SQL and run it in the database.

IQueryable<Order> q = db.Orders.Where(o => o.Total > 100);   // becomes SQL WHERE
var page = q.OrderBy(o => o.Id).Take(20).ToList();              // SQL runs here

// Breaks translation: AsEnumerable() pulls every row into memory first
var bad = db.Orders.AsEnumerable().Where(o => o.Total > 100).ToList();

Keep the query as IQueryable for as long as you can so filtering, sorting, and paging happen in the database, and only call ToList() at the end. Returning IQueryable from a method leaks the database context to callers, so return a materialized list at the boundary.

The key insight A query variable holds a recipe, not results. Whenever behavior surprises you, ask: "when does this actually enumerate, and how many times?"

§4Common Mistakes

MistakeWhat HappensFix
Enumerating the same query repeatedlyWork and side effects repeat, and with a database, repeated queriesCall ToList() once and reuse the list
AsEnumerable() or ToList() before filtering an EF queryEntire tables load into memoryFilter and page on the IQueryable first, materialize last
Using a lazy query after its data source is disposedObjectDisposedException at enumeration timeMaterialize inside the scope that owns the source
Practice
  1. Write a query with a Select that prints in its lambda, enumerate it twice, and count how many times the print runs. Then fix it with ToList().
  2. Using EF Core's ToQueryString() or logging, compare the SQL for a filter placed before and after AsEnumerable().
Key takeaways
  • Deferred operators describe work; enumerating (or a terminal operator) runs it, every time.
  • Materialize with ToList() when you reuse results or need a snapshot.
  • IQueryable is translated to SQL, so keep it that way until the final step.
