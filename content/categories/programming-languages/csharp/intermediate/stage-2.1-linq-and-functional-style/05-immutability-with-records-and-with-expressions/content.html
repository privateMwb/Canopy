Immutability with Records & with-Expressions

Immutable objects never change after they're built, so they're safe to share and easy to reason about. Records and with make that style cheap.

§1Why Immutability

A mutable object can be changed by anyone holding a reference, at any time. That makes bugs hard to trace and sharing across threads dangerous. An immutable object is fully set when it's constructed, so you can pass it around freely, cache it, use it as a dictionary key, and never worry about a surprise change.

public record Money(decimal Amount, string Currency);

var price = new Money(10m, "EUR");
// price.Amount = 20m;                    // compile error: init-only
var sale = price with { Amount = 8m };   // new object; price is unchanged

§2Non-Destructive Mutation and Collections

public record Cart(IReadOnlyList<string> Items)
{
    public Cart Add(string item) => this with { Items = [.. Items, item] };   // spread into a new list
    public Cart Remove(string item) => this with { Items = Items.Where(i => i != item).ToList() };
}

var c1 = new Cart([]);
var c2 = c1.Add("Pen").Add("Ink");
Console.WriteLine(c1.Items.Count);   // 0
Console.WriteLine(c2.Items.Count);   // 2

Instead of mutating, each "change" returns a new object that shares unchanged parts. Note the trap: a record is only shallowly immutable. If a property holds a List<T>, anyone can still call Add on it. Expose IReadOnlyList<T> or ImmutableList<T> (from System.Collections.Immutable), and copy collections you receive.

§3Designing Around Immutable Models

  • Validate once, in the constructor or a factory, so every instance in existence is valid.
  • Model state changes as functions: (State, Event) -> State is easy to test and replay.
  • Use readonly and init for fields and properties, and sealed for types that aren't meant to be extended.
  • Know the cost: copying large structures on every change can be expensive. For hot loops or big buffers, local mutation inside a method is fine as long as the result you expose is immutable.
public record Account(decimal Balance)
{
    public Account Deposit(decimal amount) =>
        amount <= 0 ? throw new ArgumentOutOfRangeException(nameof(amount))
                    : this with { Balance = Balance + amount };
}
The key insight Immutability moves complexity from "who might change this, and when?" to "where was this value created?" The second question has a single, searchable answer.

§4Common Mistakes

MistakeWhat HappensFix
A record with a public List<T> propertyCallers mutate the list and break the immutability promiseExpose IReadOnlyList<T> or immutable collections
Using with to bypass validationThe copy can hold a combination the constructor would rejectPut validation in init accessors or the constructor, and re-validate in domain methods
Making everything immutable regardless of costAllocation churn in tight loopsMutate locally and freeze the result at the boundary
Practice
  1. Model an Order with line items as immutable records and write AddLine and RemoveLine methods that return new orders.
  2. Show that mutating a list inside a record changes the "immutable" original, then fix the record so it can't.
Key takeaways
  • Immutable objects are safe to share, cache, and use as keys.
  • with copies a record with changes, and records are only shallowly immutable.
  • Validate at creation and model changes as functions that return new values.
