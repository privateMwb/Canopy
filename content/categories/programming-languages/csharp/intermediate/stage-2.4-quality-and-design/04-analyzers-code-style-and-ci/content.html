Analyzers, Code Style & CI

Consistency and early warnings shouldn't depend on reviewers noticing. Analyzers and a CI pipeline enforce standards on every change, automatically.

§1.editorconfig and Code Style

# .editorconfig at the repository root
root = true

[*.cs]
indent_style = space
indent_size = 4
csharp_style_namespace_declarations = file_scoped:warning
csharp_style_var_for_built_in_types = false:suggestion
dotnet_style_qualification_for_field = false:suggestion
dotnet_diagnostic.IDE0005.severity = warning        # remove unnecessary usings
dotnet_diagnostic.CA2007.severity = none            # ConfigureAwait: not needed in this app

.editorconfig is read by Visual Studio, VS Code, Rider, and the compiler. Rules have a severity: none, suggestion, warning, or error. Check it into source control so every developer and the build agree. dotnet format applies the formatting and style rules to existing code.

§2Roslyn Analyzers and Warnings as Errors

<PropertyGroup>
  <Nullable>enable</Nullable>
  <AnalysisLevel>latest-recommended</AnalysisLevel>
  <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
  <TreatWarningsAsErrors Condition="'$(CI)' == 'true'">true</TreatWarningsAsErrors>
</PropertyGroup>
<!-- Third-party analyzers are added as PackageReference with PrivateAssets="all" and a pinned Version -->

Analyzers inspect your code during the build and report problems: possible null dereferences, undisposed objects, misuse of APIs, security flaws, and style issues. The .NET SDK includes the built-in CA (quality) and IDE (style) rules. TreatWarningsAsErrors makes warnings stop the build, so a warning can't be silently ignored. Enable it in CI first, or adopt it gradually by promoting one rule at a time. Suppress a rule only with a comment and a reason.

§3A CI Pipeline

# .github/workflows/ci.yml
name: ci
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: '10.0.x' }
      - run: dotnet restore
      - run: dotnet format --verify-no-changes --no-restore
      - run: dotnet build --no-restore -c Release -warnaserror
      - run: dotnet test --no-build -c Release --collect:"XPlat Code Coverage"

The pipeline runs the same commands you run locally: restore, check formatting, build with warnings as errors, and test with coverage. It runs on every push and pull request, and a failing step blocks the merge. Aim to keep it under a few minutes. Treat coverage as a way to find untested code, not a target to maximize: 100% coverage of trivial code tells you less than good tests of the payment logic.

The key insight Anything a human reviewer has to repeat (formatting, unused code, missing null checks) should be made a machine's job, so reviews can focus on design and correctness.

§4Common Mistakes

MistakeWhat HappensFix
Turning on warnings-as-errors for a large legacy codebase all at onceThe build breaks, and the team switches it offPromote rules gradually, fixing each batch, or baseline existing warnings
Suppressing warnings with #pragma and no explanationReal problems are hidden permanentlyFix them, or suppress narrowly with a comment stating why
CI that differs from local commands"Works on my machine" failuresRun the same dotnet commands locally and in CI
Practice
  1. Add an .editorconfig with at least three rules to a project, run dotnet format, and review the diff it produces.
  2. Write a CI workflow that restores, builds with -warnaserror, and runs tests. Introduce a warning on purpose and confirm the pipeline fails.
Key takeaways
  • .editorconfig plus dotnet format makes style consistent and automatic.
  • Analyzers find real problems at build time, and warnings-as-errors keep them from being ignored.
  • CI runs the same checks on every change, and coverage is a guide to untested code, not a goal.
