Testing Services

Unit tests check logic in isolation, and integration tests check that the pieces work together. A healthy suite has both, and knows which tool fits which question.

§1Fakes and Mocks

// A hand-written fake: simple, readable, reusable
public class FakeNotifier : IOrderNotifier
{
    public List<Order> Confirmed { get; } = new();
    public Task ConfirmAsync(Order o, CancellationToken ct) { Confirmed.Add(o); return Task.CompletedTask; }
}

[Fact]
public async Task Place_ValidOrder_SavesAndNotifies()
{
    var store = new InMemoryOrderStore();
    var notifier = new FakeNotifier();
    var sut = new OrderProcessor(store, notifier);

    await sut.PlaceAsync(new Order { Total = 50 }, CancellationToken.None);

    Assert.Single(store.Saved);
    Assert.Single(notifier.Confirmed);
}

// A mock with a library such as NSubstitute or Moq: verify an interaction
var notifier2 = Substitute.For<IOrderNotifier>();
await new OrderProcessor(store, notifier2).PlaceAsync(order, default);
await notifier2.Received(1).ConfirmAsync(order, Arg.Any<CancellationToken>());

A fake is a working lightweight implementation (an in-memory store). A mock is a generated stand-in you program and then verify calls on. Prefer fakes and assert on outcomes (what was saved) over mocks that assert on interactions (which methods were called), because interaction tests break whenever you refactor, even if behavior is unchanged. Time is a dependency too: inject TimeProvider instead of calling DateTime.UtcNow, and use FakeTimeProvider in tests.

§2Integration Tests with WebApplicationFactory

public class OrdersApiTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly HttpClient _client;

    public OrdersApiTests(WebApplicationFactory<Program> factory)
    {
        _client = factory.WithWebHostBuilder(b => b.ConfigureServices(services =>
        {
            // Replace real infrastructure with test doubles
            services.RemoveAll<IOrderNotifier>();
            services.AddSingleton<IOrderNotifier, FakeNotifier>();
        })).CreateClient();
    }

    [Fact]
    public async Task PostOrder_Valid_Returns201()
    {
        var response = await _client.PostAsJsonAsync("/orders", new { total = 25 });
        Assert.Equal(HttpStatusCode.Created, response.StatusCode);
    }

    [Fact]
    public async Task PostOrder_Invalid_Returns400()
    {
        var response = await _client.PostAsJsonAsync("/orders", new { total = -1 });
        Assert.Equal(HttpStatusCode.BadRequest, response.StatusCode);
    }
}

// Program.cs: expose the entry point to the test project
public partial class Program { }

WebApplicationFactory<Program> starts your real app in memory, with real routing, middleware, model binding, and serialization, and gives you an HttpClient. You can override services (for example replacing an email sender or pointing EF at a test database) in ConfigureServices. This catches the failures unit tests can't: wrong routes, missing registrations, a serialization mismatch, an authorization rule that isn't applied.

§3Choosing the Right Test

QuestionTest typeSpeed
Is this calculation or rule right?Unit test, no doubles neededMilliseconds
Does this service use its collaborators correctly?Unit test with fakesMilliseconds
Does the endpoint wire up end to end?WebApplicationFactory testTens of ms to seconds
Does the SQL work on a real database?Integration test with a real database (for example in a container)Seconds

Many fast unit tests, a smaller layer of integration tests, and a few end-to-end checks make a good balance. Don't test the framework (that [HttpGet] routes), and don't test EF Core against an in-memory provider and trust the result: its behavior differs from a real database, so use the same engine you deploy on for anything involving queries and constraints.

The key insight Test behavior through the public surface, and substitute only what's slow, nondeterministic, or external. The more a test knows about internals, the more it breaks without finding bugs.

§4Common Mistakes

MistakeWhat HappensFix
Mocking everything and asserting each callTests mirror the implementation and fail on harmless refactorsUse fakes and assert on resulting state or output
Using EF's in-memory provider as proof of correct queriesConstraints, translation, and transactions behave differentlyUse a real database engine for data-access tests
Shared state between integration testsOrder-dependent, flaky testsCreate fresh data per test or reset the database between tests
Practice
  1. Write a unit test for a service using a hand-written fake, then rewrite it with a mocking library. Compare how each reacts when you refactor the service internals.
  2. Add a WebApplicationFactory test that checks an endpoint returns 401 without a token and 200 with one.
Key takeaways
  • Prefer fakes and outcome assertions; use mocks sparingly to verify important interactions.
  • WebApplicationFactory runs the real app in memory for end-to-end API tests, with replaceable services.
  • Match the test to the question: logic with units, wiring with integration tests, SQL with a real database.
