Generics & Constraints

Beyond using List<T>, you'll write generic code of your own. Constraints, variance, and a few design rules keep it both flexible and safe.

§1Constraints in Depth

public interface IEntity<TKey> { TKey Id { get; } }

public class Repository<TEntity, TKey>
    where TEntity : class, IEntity<TKey>, new()
    where TKey : IEquatable<TKey>
{
    private readonly Dictionary<TKey, TEntity> _store = new();
    public void Add(TEntity e) => _store[e.Id] = e;
    public TEntity? Find(TKey id) => _store.GetValueOrDefault(id);
    public TEntity Create() => new();            // allowed because of new()
}

public static T Sum<T>(IEnumerable<T> xs) where T : INumber<T> =>
    xs.Aggregate(T.Zero, (a, b) => a + b);       // generic math: works for int, double, decimal

Each where clause names a type parameter and lists what it must satisfy: class, struct, new(), a base class, or interfaces. Newer .NET adds static abstract members in interfaces, so INumber<T> lets you write arithmetic that works across all numeric types. Constrain exactly as much as the body needs, because every constraint narrows who can use your type.

§2Variance: covariance and contravariance

// Covariant (out): a producer of T. IEnumerable<out T>
IEnumerable<string> strings = new List<string> { "a" };
IEnumerable<object> objects = strings;     // OK: every string is an object

// Contravariant (in): a consumer of T. Action<in T>, IComparer<in T>
Action<object> printAny = o => Console.WriteLine(o);
Action<string> printStr = printAny;        // OK: something that accepts any object accepts a string

// List<T> is invariant: it both reads and writes T
// List<object> l = new List<string>();    // compile error, and for good reason

Variance describes whether Generic<Derived> can be used as Generic<Base>. It's safe for an interface that only returns T (out, covariant) or only accepts T (in, contravariant). If an interface does both, it has to be invariant. You rarely declare variance yourself, but you benefit from it every time you pass a List<string> to a method taking IEnumerable<object>. Variance applies to interfaces and delegates, not classes, and only with reference types.

§3Design Rules for Generic Code

  • Start concrete. Write the code for one type, and generalize when a second real use appears.
  • Prefer generic methods over generic classes when state isn't needed, since callers get type inference.
  • Don't over-parameterize. Three or four type parameters usually signal a design that's doing too much.
  • Mind allocations. A generic method over a struct gets its own specialized code (no boxing), but an unconstrained T compared with == or cast to object may box.
  • Use default and EqualityComparer<T>.Default instead of assuming what T is.
public static bool IsDefault<T>(T value) => EqualityComparer<T>.Default.Equals(value, default);
The key insight A generic type's constraints are its requirements, and its variance is a promise about direction (only out, or only in). Get either wrong and the compiler, not production, tells you.

§4Common Mistakes

MistakeWhat HappensFix
Over-constraining a type parameterCallers who'd work fine can't use itAdd only constraints the code requires
Expecting List<Derived> to convert to List<Base>Compile errorUse IEnumerable<Base> or IReadOnlyList<Base>, which are covariant
Abstracting generically before there are two usesHard-to-read code solving a problem that doesn't existWrite the concrete version first and refactor when needed
Practice
  1. Write a generic MaxBy<T, TKey>(IEnumerable<T>, Func<T,TKey>) where TKey : IComparable<TKey> and test it with three different key types.
  2. Explain, in a sentence each, why IEnumerable<out T> is covariant and List<T> is invariant.
Key takeaways
  • Constraints state what a type parameter must support, and generic math uses interfaces like INumber<T>.
  • Covariance (out) fits producers, contravariance (in) fits consumers, and types that do both are invariant.
  • Write concrete code first, generalize when needed, and keep type parameters few.
