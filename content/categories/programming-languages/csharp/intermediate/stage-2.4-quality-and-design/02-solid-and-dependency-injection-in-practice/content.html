SOLID & Dependency Injection in Practice

SOLID is a set of heuristics for code that's easy to change. They're useful when applied to real pain, and harmful when applied by reflex.

§1The Five Principles, Concretely

PrinciplePlain meaningSmell it fixes
Single ResponsibilityA class has one reason to changeA class that validates, saves, emails, and logs
Open/ClosedAdd behavior by adding code, not editing working codeA growing switch on type in many places
Liskov SubstitutionSubtypes must work wherever the base type is expectedOverrides that throw NotSupportedException
Interface SegregationSmall interfaces focused on a client's needsImplementers stubbing out methods they don't use
Dependency InversionDepend on abstractions, and have the caller supply the implementationnew SqlRepository() buried in business logic

§2Refactoring a Real Service

// Before: does everything, impossible to test without SMTP and a database
public class OrderProcessor
{
    public void Place(Order o)
    {
        if (o.Total <= 0) throw new ArgumentException("Invalid");
        using var db = new ShopDb();
        db.Orders.Add(o); db.SaveChanges();
        new SmtpClient("mail").Send("shop@x.com", o.Email, "Thanks", "Order placed");
    }
}

// After: each dependency is an abstraction supplied from outside
public interface IOrderStore { Task SaveAsync(Order o, CancellationToken ct); }
public interface IOrderNotifier { Task ConfirmAsync(Order o, CancellationToken ct); }

public class OrderProcessor
{
    private readonly IOrderStore _store; private readonly IOrderNotifier _notifier;
    public OrderProcessor(IOrderStore store, IOrderNotifier notifier) { _store = store; _notifier = notifier; }

    public async Task PlaceAsync(Order o, CancellationToken ct)
    {
        if (o.Total <= 0) throw new ArgumentException("Invalid order", nameof(o));
        await _store.SaveAsync(o, ct);
        await _notifier.ConfirmAsync(o, ct);
    }
}

builder.Services.AddScoped<IOrderStore, EfOrderStore>();
builder.Services.AddScoped<IOrderNotifier, EmailOrderNotifier>();
builder.Services.AddScoped<OrderProcessor>();

The refactor pays off in a concrete way: OrderProcessor now contains only order rules, and a test can supply an in-memory store and a fake notifier. That's the benefit to aim for, so being able to test and change one part without touching another.

§3Noticing Over-Engineering

  • An interface with exactly one implementation and no test or boundary reason to exist is clutter. Add it when the second implementation or the test appears.
  • A class for every verb (OrderValidator, OrderValidatorFactory, OrderValidatorProvider) often moves complexity around without removing it.
  • If following a principle makes the code harder to follow for a small, stable feature, you're serving the principle instead of the code.
  • Ask of each abstraction: what change does this make cheap? If you can't name one, remove it.

The principles are tradeoffs. A short, direct method that does one clear thing in 20 lines beats five files and three interfaces. Reach for structure when a real change has hurt, not before.

The key insight Each abstraction should buy something specific: testability, a swappable implementation, or isolation of a volatile detail. If it buys nothing, it's cost.

§4Common Mistakes

MistakeWhat HappensFix
An interface for every class by defaultDouble the files with no benefitIntroduce an interface at real boundaries (I/O, external services) or when substitution is needed
A "god" service injected with ten dependenciesViolates single responsibility and is painful to testSplit it by responsibility; many dependencies are a design signal
Hiding new inside methodsDependencies are invisible and can't be replacedAccept dependencies through the constructor
Practice
  1. Take a class that touches a database, the clock, and the file system, and extract interfaces so a unit test can run without any of them. List which ones you did not extract, and why.
  2. Find an interface in a project that has only one implementation. Decide whether to keep it, and write down the reason.
Key takeaways
  • SOLID principles are heuristics that make change cheaper when applied to real problems.
  • Constructor injection of small abstractions at I/O boundaries makes code testable.
  • Add abstractions in response to pain, and remove those that buy nothing.
