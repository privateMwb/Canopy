Configuration, Logging & the Options Pattern

Applications need settings that change between environments and logs that explain what happened. ASP.NET Core provides both through layered configuration and structured logging.

§1Layered Configuration

// appsettings.json
{
  "ConnectionStrings": { "Shop": "Data Source=shop.db" },
  "Email": { "Host": "localhost", "Port": 25 },
  "Logging": { "LogLevel": { "Default": "Information" } }
}

// Program.cs
var cs = builder.Configuration.GetConnectionString("Shop");
var host = builder.Configuration["Email:Host"];            // ':' navigates sections

Configuration is built from several providers, and later ones override earlier ones: appsettings.json, then appsettings.{Environment}.json (for example Production), then user secrets (development only), then environment variables, then command-line arguments. Environment variables use __ for nesting, so Email__Port=587 overrides Email:Port. The environment itself comes from ASPNETCORE_ENVIRONMENT.

  • Never commit secrets such as passwords and API keys. Use user secrets locally (dotnet user-secrets set) and environment variables or a secret manager in deployment.

§2The Options Pattern

public class EmailOptions
{
    public const string Section = "Email";
    [Required] public string Host { get; set; } = "";
    [Range(1, 65535)] public int Port { get; set; } = 25;
}

builder.Services
    .AddOptions<EmailOptions>()
    .BindConfiguration(EmailOptions.Section)
    .ValidateDataAnnotations()
    .ValidateOnStart();                       // fail at startup, not at the first request

public class Mailer
{
    private readonly EmailOptions _opt;
    public Mailer(IOptions<EmailOptions> options) => _opt = options.Value;
}

Instead of reading strings from IConfiguration all over your code, bind a section to a class and inject it. You get type safety, defaults, and validation. Use IOptions<T> for values fixed at startup, IOptionsSnapshot<T> for per-request reloading, and IOptionsMonitor<T> to react to changes in singletons.

§3Structured Logging

public class OrderService
{
    private readonly ILogger<OrderService> _log;
    public OrderService(ILogger<OrderService> log) => _log = log;

    public void Ship(int orderId, string customer)
    {
        _log.LogInformation("Shipping order {OrderId} for {Customer}", orderId, customer);
        try { /* ... */ }
        catch (Exception ex)
        {
            _log.LogError(ex, "Failed to ship order {OrderId}", orderId);
            throw;
        }
    }
}

Write a message template with named placeholders and pass values as arguments. Don't use string interpolation ($"..."), because that flattens the data into text. A structured log sink stores OrderId and Customer as searchable fields, so you can query "all errors for order 42." Choose levels deliberately: Debug for developers, Information for normal events, Warning for recoverable problems, and Error for failures. Never log secrets or personal data.

The key insight Settings and logs are interfaces to operations. Make configuration typed and validated at startup, and make logs structured, so a problem at 3 a.m. can be diagnosed by querying fields rather than reading text.

§4Common Mistakes

MistakeWhat HappensFix
Committing secrets in appsettings.jsonCredentials leak through source controlUse user secrets, environment variables, or a vault
Logging with interpolated stringsNo searchable fields, and formatting cost even when the level is offUse message templates with named placeholders
Reading raw config strings throughout the codeTypos, no validation, and failures surface lateBind to options classes and use ValidateOnStart
Practice
  1. Create an options class for an email section with validation, bind it, and deliberately set an invalid port to see the startup failure.
  2. Override one setting with an environment variable in a launch profile, and show the value changed.
Key takeaways
  • Configuration layers from JSON files to environment variables, and later sources win.
  • Bind sections to validated options classes and inject them.
  • Log with message templates and levels so logs are queryable, and keep secrets out of both config files and logs.
