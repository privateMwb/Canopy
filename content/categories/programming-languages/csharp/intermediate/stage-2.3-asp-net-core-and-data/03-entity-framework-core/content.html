Entity Framework Core

EF Core maps C# classes to database tables and translates LINQ into SQL. Used well it removes boilerplate, used carelessly it generates slow queries.

§1Models and the DbContext

public class Customer
{
    public int Id { get; set; }
    public required string Name { get; set; }
    public List<Order> Orders { get; set; } = new();
}
public class Order
{
    public int Id { get; set; }
    public decimal Total { get; set; }
    public int CustomerId { get; set; }          // foreign key by convention
    public Customer Customer { get; set; } = null!;
}

public class ShopDb : DbContext
{
    public ShopDb(DbContextOptions<ShopDb> options) : base(options) { }
    public DbSet<Customer> Customers => Set<Customer>();
    public DbSet<Order> Orders => Set<Order>();

    protected override void OnModelCreating(ModelBuilder b) =>
        b.Entity<Customer>().Property(c => c.Name).HasMaxLength(100);
}

A DbSet<T> represents a table. Conventions infer keys (Id) and relationships from property names, and OnModelCreating (or attributes) overrides them. A DbContext is a lightweight unit of work that should live for one request, which is why it's registered as scoped.

§2Migrations and Queries

dotnet tool install --global dotnet-ef
dotnet ef migrations add InitialCreate    // generate a migration from model changes
dotnet ef database update                  // apply it to the database
var big = await db.Orders
    .Where(o => o.Total > 100)
    .OrderByDescending(o => o.Total)
    .Take(20)
    .Select(o => new OrderDto(o.Id, o.Customer.Name, o.Total))   // only the columns you need
    .ToListAsync();

db.Customers.Add(new Customer { Name = "Ada" });
await db.SaveChangesAsync();                // one transaction; INSERT/UPDATE/DELETE sent here

var c = await db.Customers.FirstAsync(x => x.Name == "Ada");
c.Name = "Ada L.";                          // change is detected
await db.SaveChangesAsync();

Migrations are versioned, reviewable C# files that evolve the schema. Commit them. Queries are IQueryable, so they translate to SQL when enumerated (ToListAsync, FirstAsync). Change tracking keeps the original values of loaded entities, so SaveChangesAsync knows what to write. For read-only queries, add .AsNoTracking() to skip that cost.

§3Loading Related Data and the N+1 Problem

// N+1: one query for customers, then one per customer for its orders (lazy loading or a loop)
var customers = await db.Customers.ToListAsync();
foreach (var c in customers)
    Console.WriteLine(c.Orders.Count);          // triggers a query each time with lazy loading

// Fix 1: eager load
var fixed1 = await db.Customers.Include(c => c.Orders).ToListAsync();

// Fix 2 (often best): project exactly what you need in one query
var fixed2 = await db.Customers
    .Select(c => new { c.Name, OrderCount = c.Orders.Count })
    .ToListAsync();

The N+1 problem is one query to get a list plus one extra query per item, which turns 100 rows into 101 round trips. Spot it by logging the SQL EF generates (LogTo(Console.WriteLine) or ToQueryString()) and seeing the same statement repeat. Fix it with Include or, better, a Select projection that returns only the columns required.

The key insight EF Core writes SQL for you, so you still own what it writes. Log the generated SQL in development, count the queries per request, and treat a repeating query as a bug.

§4Common Mistakes

MistakeWhat HappensFix
Loading whole entities when only a few columns are neededMore data transferred, plus change-tracking overheadProject to a DTO with Select, and use AsNoTracking for reads
Looping and touching navigation properties (N+1)Hundreds of round tripsUse Include or a projection to fetch in one query
Editing the database by hand while using migrationsThe model, migration history, and database drift apartMake every schema change through a migration
Practice
  1. Create a Customer/Order model with SQLite, add a migration, seed some data, and write a query returning each customer with their order count in one SQL statement.
  2. Provoke an N+1 with a loop, log the SQL to count the statements, then fix it two ways.
Key takeaways
  • A DbContext is a per-request unit of work; DbSets map to tables; migrations evolve the schema.
  • LINQ on IQueryable becomes SQL, and SaveChangesAsync writes tracked changes in one transaction.
  • Watch for N+1: fetch related data with Include or projections, and verify with logged SQL.
