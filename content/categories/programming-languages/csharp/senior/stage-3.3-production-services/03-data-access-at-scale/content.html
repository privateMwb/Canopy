Data Access at Scale

Most production slowdowns are database slowdowns. At scale, how you query, batch, cache, and scope transactions matters more than any micro-optimization in C#.

§1Query Performance in EF Core

// Read-only, projected, paged, no tracking
var page = await db.Orders
    .AsNoTracking()
    .Where(o => o.CustomerId == customerId && o.Status == OrderStatus.Open)
    .OrderByDescending(o => o.CreatedAt).ThenBy(o => o.Id)
    .Select(o => new OrderSummary(o.Id, o.Total, o.CreatedAt))
    .Take(50)
    .ToListAsync(ct);

// Keyset pagination: stable and fast on large tables (OFFSET gets slower the deeper you go)
var next = await db.Orders.AsNoTracking()
    .Where(o => o.CreatedAt < lastSeen)
    .OrderByDescending(o => o.CreatedAt).Take(50).ToListAsync(ct);

// Server-side bulk operations without loading entities
await db.Orders.Where(o => o.Status == OrderStatus.Expired).ExecuteDeleteAsync(ct);
await db.Products.Where(p => p.Stock == 0).ExecuteUpdateAsync(s => s.SetProperty(p => p.Active, false), ct);
  • Project only the columns you need, add AsNoTracking to reads, and always page large results.
  • Index the columns you filter and sort on, and check the execution plan in the database, because EF writes the SQL but the database decides how to run it.
  • Watch for N+1 queries and for client-side evaluation: log the SQL in development and in load tests.
  • AsSplitQuery() avoids the row explosion of multiple Include collections in one query, at the cost of several round trips.

§2Batching and Caching

// Batching: one round trip, many rows. SaveChanges already batches commands.
db.Orders.AddRange(newOrders);
await db.SaveChangesAsync(ct);

// Caching read-mostly data
var product = await cache.GetOrCreateAsync($"product:{id}", async entry =>
{
    entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
    entry.SetSize(1);
    return await db.Products.AsNoTracking().FirstOrDefaultAsync(p => p.Id == id, ct);
});

// .NET 9+: HybridCache combines in-memory (L1) and distributed (L2) with stampede protection
var item = await hybridCache.GetOrCreateAsync($"product:{id}", async token => await LoadAsync(id, token), cancellationToken: ct);

Cache data that is read often, changed rarely, and tolerates staleness. Every cache needs three decisions: a key that includes everything the value depends on (tenant, culture), an expiry or invalidation rule, and a size bound. Beware the cache stampede, where many requests miss at once and all hit the database, which is what HybridCache and per-key locking prevent. Use IMemoryCache for one instance, and a distributed cache (such as Redis) when several instances must share it.

§3Transaction Boundaries

// Default: one SaveChangesAsync = one transaction. Keep units of work small.
await using var tx = await db.Database.BeginTransactionAsync(ct);
var from = await db.Accounts.FindAsync([fromId], ct);
var to = await db.Accounts.FindAsync([toId], ct);
from!.Balance -= amount; to!.Balance += amount;
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);

// Optimistic concurrency: detect conflicting writes
public class Product { public int Id { get; set; } [Timestamp] public byte[] RowVersion { get; set; } = []; }
// SaveChangesAsync throws DbUpdateConcurrencyException if the row changed since it was read
  • Keep transactions short: never hold one open across a user interaction or a slow external call, because locks are held until commit.
  • Never call an HTTP API or message broker inside a transaction and assume it rolls back with the database. Use an outbox table for reliable side effects.
  • Use optimistic concurrency (row versions) so concurrent edits fail loudly instead of silently overwriting each other.
  • Pick the isolation level deliberately. The default (often Read Committed) is usually right, and Serializable costs throughput.
The key insight Make the database do less: fewer rows, fewer columns, fewer round trips, shorter transactions. Then measure with real data volumes, because a query that is fast on 1,000 rows can collapse on 10 million.

§4Common Mistakes

MistakeWhat HappensFix
OFFSET pagination on deep pagesEach page is slower than the lastUse keyset pagination with a stable ordering
A cache key missing a dimension such as tenant or cultureOne tenant sees another's dataInclude every input of the computation in the key
Calling external services inside a database transactionLong-held locks, and side effects that can't be rolled backCommit first, and use an outbox for reliable follow-up work
Practice
  1. Load-test a list endpoint with 1 million rows using OFFSET and then keyset pagination, and compare the SQL execution time of the last page.
  2. Add optimistic concurrency to an entity, simulate two simultaneous edits, and handle the DbUpdateConcurrencyException by returning a 409.
Key takeaways
  • Project, track nothing for reads, page with keysets, and use ExecuteUpdate and ExecuteDelete for bulk work.
  • Cache read-mostly data with correct keys, expiry, size limits, and stampede protection.
  • Keep transactions short, avoid external calls inside them, and use optimistic concurrency.
