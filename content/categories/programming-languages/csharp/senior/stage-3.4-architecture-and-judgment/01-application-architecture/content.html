Application Architecture

Architecture is the set of decisions that are expensive to change later. The goal isn't a fashionable diagram but a structure where the changes you expect are cheap.

§1Layers and Clean Architecture

In a layered or clean architecture, dependencies point inward toward the business rules, and outer details (web, database, message bus) plug into them.

src/
  Shop.Domain/          // entities, value objects, domain rules: references nothing
  Shop.Application/     // use cases, interfaces (IOrderStore): references Domain
  Shop.Infrastructure/  // EF Core, email, HTTP clients: implements Application interfaces
  Shop.Api/             // endpoints, DI composition root: references all of the above

The rule is that the domain never depends on infrastructure. Shop.Application declares IOrderStore, and Shop.Infrastructure implements it with EF Core. You can test the business rules with no database, and swap storage without touching them. The cost is ceremony: every feature touches several projects, and for a simple CRUD service that overhead buys little.

§2Vertical Slices

src/Shop.Api/Features/
  Orders/
    PlaceOrder.cs          // request, validator, handler, endpoint: all in one place
    GetOrder.cs
    CancelOrder.cs
  Catalog/
    SearchProducts.cs
public static class PlaceOrder
{
    public record Command(int CustomerId, List<Line> Lines);
    public record Line(int ProductId, int Qty);

    public static void Map(IEndpointRouteBuilder app) => app.MapPost("/orders", Handle);

    private static async Task<IResult> Handle(Command cmd, ShopDb db, CancellationToken ct)
    {
        if (cmd.Lines.Count == 0) return Results.BadRequest("No lines");
        // ...rules, persistence...
        return Results.Created("/orders/1", null);
    }
}

Vertical slices organize code by feature instead of by technical layer. Everything for "place an order" lives together, so a change touches one folder and slices can use different approaches (a complex slice can use a rich domain model, a simple one a direct query). The tradeoff is some duplication between slices, and it needs discipline to extract shared rules into the domain when two slices genuinely share them.

§3The Modular Monolith and Choosing

A modular monolith is one deployable application divided into modules with strict boundaries: each module owns its data, exposes a small public interface, and other modules may not reach into its internals or tables. You get most of microservices' organizational benefits (independent teams, clear ownership) without their operational cost (network calls, distributed transactions, many deployments).

  • Enforce boundaries mechanically: separate projects with internal types, and architecture tests (for example NetArchTest or ArchUnitNET) that fail the build when a module references another's internals.
  • Modules communicate through public interfaces or in-process events, so extracting one into a service later is possible.
  • Start with a modular monolith, and split a module into a service only when a concrete need justifies it: independent scaling, a different team and release cadence, or fault isolation.
SituationReasonable default
Small team, simple CRUD, uncertain requirementsOne project, vertical slices, minimal ceremony
Rich business rules, long-lived systemClean layers around a real domain model
Many teams in one codebaseModular monolith with enforced boundaries
Parts that must scale or deploy independentlyExtract those modules as services, with eyes open about the costs
The key insight Every boundary has a price in indirection. Draw one where it protects something real, such as a volatile dependency, a team boundary, or a rule that must stay testable, and nowhere else.

§4Common Mistakes

MistakeWhat HappensFix
Copying a full clean-architecture template for a simple serviceFour projects and many mappings for a handful of endpointsStart simple and add layers when complexity appears
Microservices before the need existsDistributed failures, versioning, and operations overhead for a small teamStart with a modular monolith and extract with evidence
Modules that read each other's database tablesHidden coupling; no module can change its schemaGive each module its own data and expose queries through its public interface
Practice
  1. Sketch the module boundaries for an e-commerce system (catalog, orders, payments, shipping). For each pair, write what they may call and what they may not.
  2. Add an architecture test that fails when Shop.Domain references Microsoft.EntityFrameworkCore.
Key takeaways
  • Clean architecture points dependencies at the domain, which makes rules testable at the cost of ceremony.
  • Vertical slices group by feature, so a change touches one place.
  • A modular monolith with enforced boundaries delivers most microservice benefits without their operational cost.
