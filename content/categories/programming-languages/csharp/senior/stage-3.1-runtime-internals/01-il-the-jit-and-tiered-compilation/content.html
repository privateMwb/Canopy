IL, the JIT & Tiered Compilation

Your C# doesn't run directly. It becomes IL, then machine code, and the choices .NET makes along the way explain its startup time and steady-state speed.

§1From C# to IL

The C# compiler (Roslyn) doesn't emit machine code. It emits IL (Intermediate Language, also called CIL), a stack-based, CPU-independent instruction set stored in the assembly along with metadata describing every type and member. You can inspect it with tools such as ildasm, ILSpy, or the Disassembly view in SharpLab.

// C#
static int Add(int a, int b) => a + b;

// IL (conceptually)
// ldarg.0     push a
// ldarg.1     push b
// add         pop both, push the sum
// ret         return the top of the stack

IL is verifiable and portable, which is why one build runs on x64, Arm64, Windows, Linux, and macOS. The cost is that something has to turn IL into native code before it can run.

§2The JIT and Tiered Compilation

The JIT (just-in-time compiler) translates a method's IL to machine code the first time that method is called, then reuses it. Fully optimizing everything up front would slow startup, so .NET uses tiered compilation:

  • Tier 0: a fast, minimally optimized compile so the app starts quickly. Methods are instrumented to count calls.
  • Tier 1: methods called often (about 30 calls) are queued and recompiled in the background with full optimizations: inlining, loop optimizations, and bounds-check elimination.
  • Dynamic PGO (profile-guided optimization): Tier 0 gathers data on which branches and types are common, so Tier 1 can optimize for them, for example by guarding a virtual call with a fast path for the most common type.
  • On-stack replacement (OSR): a long-running loop in a Tier 0 method can switch to optimized code mid-execution.

The consequence for you: the first calls of any method are slower, and a short benchmark can measure warm-up instead of real performance. This is why microbenchmarks must warm up, and why services have a brief period of higher latency after start.

§3ReadyToRun and Native AOT

ModeWhat it doesTradeoff
JIT (default)Compiles IL at run time, tiered, with PGOSlower start; best steady-state speed; full dynamic features
ReadyToRun (R2R)Precompiles to native code in the assembly, then still JITs hot methods to Tier 1Faster start, larger files; still needs the runtime
Native AOTCompiles everything to a standalone native executable ahead of timeFastest start, small footprint, no JIT; restricted reflection and dynamic code
<PropertyGroup>
  <PublishReadyToRun>true</PublishReadyToRun>   <!-- R2R -->
  <PublishAot>true</PublishAot>                 <!-- Native AOT: dotnet publish -->
  <TieredPGO>true</TieredPGO>
</PropertyGroup>

Native AOT suits CLI tools, serverless functions, and containers where startup time and memory matter. Because there is no JIT, code that generates types at run time, or relies on unrestricted reflection, doesn't work unless the compiler can see it ahead of time. Source generators (a later lesson) are how libraries stay AOT-friendly.

The key insight The same C# can run as unoptimized, optimized, precompiled, or ahead-of-time compiled code. When you measure performance, know which of these you're actually measuring.

§4Common Mistakes

MistakeWhat HappensFix
Benchmarking a method once or a few timesMeasures Tier 0 and JIT cost, not steady-state speedWarm up first, or use BenchmarkDotNet, which handles warm-up and tiering
Enabling Native AOT without checking reflection and dynamic-code usageTrim and AOT warnings, or runtime failuresResolve the analyzer warnings, use source generators, and test the published binary
Assuming Release and Debug differ only in symbolsDebug disables many optimizations and changes timingAlways measure with Release builds
Practice
  1. Paste a small method into SharpLab and compare the IL with its Debug and Release forms. What changed?
  2. Time the first and the hundredth call of a method in a loop with Stopwatch, and explain the difference using tiers.
Key takeaways
  • C# compiles to IL, and the JIT turns IL into machine code on first use.
  • Tiered compilation with dynamic PGO starts fast and then optimizes hot methods.
  • ReadyToRun improves startup, and Native AOT removes the JIT at the cost of dynamic features.
