Benchmarking with BenchmarkDotNet

Timing code with a stopwatch gives numbers that look precise and are usually wrong. BenchmarkDotNet handles warm-up, statistics, and the traps for you.

§1Why Hand-Rolled Timing Lies

  • JIT warm-up: the first calls run unoptimized Tier 0 code (the earlier lesson on tiering).
  • Dead-code elimination: if the result isn't used, the JIT may remove the work you meant to measure.
  • Noise: other processes, CPU frequency changes, and GC pauses vary run to run, so one number means little.
  • Debug builds: they disable optimizations, so the results don't reflect production.

A benchmark needs warm-up, many iterations, outlier handling, and a way to prevent the optimizer from discarding results. BenchmarkDotNet does all of that.

§2Writing a Benchmark

dotnet new console -o Bench && cd Bench
dotnet add package BenchmarkDotNet
[MemoryDiagnoser]                                // report allocations and GC counts
public class JoinBenchmarks
{
    private string[] _words = default!;

    [Params(10, 1_000)]                            // run every benchmark for each size
    public int Count;

    [GlobalSetup]
    public void Setup() => _words = Enumerable.Range(0, Count).Select(i => "word" + i).ToArray();

    [Benchmark(Baseline = true)]
    public string Concat()
    {
        var s = "";
        foreach (var w in _words) s += w;           // O(n^2) copying
        return s;                                    // returning the value keeps the work alive
    }

    [Benchmark]
    public string StringBuilderJoin()
    {
        var sb = new StringBuilder();
        foreach (var w in _words) sb.Append(w);
        return sb.ToString();
    }

    [Benchmark]
    public string StringJoin() => string.Join("", _words);
}

public class Program { public static void Main(string[] args) => BenchmarkRunner.Run<JoinBenchmarks>(); }
dotnet run -c Release                          // ALWAYS Release, and not under a debugger

Return values from benchmark methods (or consume them) so the work can't be optimized away. Keep setup out of the measured method with [GlobalSetup], and use [Params] to see how cost scales with input size, which often matters more than the single-size result.

§3Reading the Results

ColumnMeaning
MeanAverage time per operation, but look at the spread too
Error / StdDevConfidence interval and variation; a large StdDev relative to the mean means unstable results
RatioTime relative to the Baseline = true benchmark: 0.10 means ten times faster
Gen0 / Gen1 / Gen2Collections per 1,000 operations
AllocatedBytes allocated per operation

Compare with the Ratio and the Allocated column, not by eye. Allocation differences often explain the time differences. And remember what a microbenchmark can't tell you: it measures one method in isolation with warm caches, so a 20% win there may be invisible in the real application. Benchmark to choose between alternatives, and profile the real app to find where time actually goes.

The key insight A benchmark answers one narrow question under controlled conditions. Use it to compare two implementations, and use a profiler on the real system to decide what's worth comparing.

§4Common Mistakes

MistakeWhat HappensFix
Running benchmarks in Debug or with the debugger attachedNumbers are meaningless and BenchmarkDotNet will warnUse dotnet run -c Release without a debugger
Not using or returning the resultThe JIT eliminates the work and you measure nothingReturn the value from the benchmark method
Benchmarking only one input sizeMisses scaling behavior such as O(n²) growthUse [Params] with sizes that span the real range
Practice
  1. Benchmark three ways of summing a list of 1,000 ints (foreach, LINQ Sum, and span-based loop). Report Mean and Allocated, and explain the differences.
  2. Add [Params] to the string-joining benchmark and find the size at which the naive version becomes unusable.
Key takeaways
  • Hand-timing misleads because of warm-up, dead-code elimination, and noise.
  • BenchmarkDotNet needs Release builds, returned results, and [Params] for scaling.
  • Compare with Ratio and Allocated, and confirm a micro-win matters in the real application.
