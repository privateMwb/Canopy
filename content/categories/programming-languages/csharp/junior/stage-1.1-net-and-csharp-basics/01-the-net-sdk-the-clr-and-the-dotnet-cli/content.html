The .NET SDK, the CLR & the dotnet CLI

Create, build, and run a C# project from the command line, and understand what the SDK, the compiler, and the runtime each contribute.

§1The Pieces: SDK, Runtime, and Language

C# is the language. .NET is the platform it runs on. The .NET SDK is what you install to develop: it contains the dotnet command, the C# compiler (Roslyn), MSBuild, and the NuGet client. The runtime (the CLR plus the base class library) is what executes your program, and it's the only part your users need.

PieceWhat it doesYou meet it as
SDKBuilds, tests, and packages projectsdotnet build, dotnet test
Roslyn compilerTurns C# into IL (intermediate language) in a .dllCompiler errors and warnings
CLRLoads IL, JIT-compiles it to machine code, manages memory, enforces type safetyGarbage collection, exceptions, stack traces

§2Create, Build, Run

Check your install, then create a console project:

dotnet --version           // prints the SDK version
dotnet new console -o Hello  // scaffold a project in ./Hello
cd Hello
dotnet run                   // restore, build, then run

You get two files. Hello.csproj describes the project, and Program.cs holds the code. Modern templates use top-level statements, so there's no Main method to write by hand:

// Program.cs
Console.WriteLine("Hello, .NET");

Console resolves without a using because the template enables implicit usings for common namespaces. The project file shows that and the other settings that matter:

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>  <!-- match the SDK you installed -->
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>

§3What Happens When You Run It

dotnet run chains several steps. Restore fetches NuGet packages. Build compiles your C# to IL and writes it to bin/Debug/net10.0/Hello.dll. Then the dotnet host starts the CLR, which loads that DLL and JIT-compiles methods to native code as they're first called.

Because the output is IL rather than machine code, the same Hello.dll runs on Windows, Linux, and macOS wherever a compatible runtime is installed. Use dotnet build to compile without running, and dotnet build -c Release for an optimized build.

dotnet new list            // available templates
dotnet new classlib -o MyLib // other project types
dotnet build -c Release
dotnet clean
The key insight The compiler does not produce native code. It produces IL, and the CLR finishes the job at run time. That's why one build runs on any operating system, and why later lessons on the JIT and Native AOT matter for performance.

§4Common Mistakes

MistakeWhat HappensFix
Installing only the runtime and expecting dotnet new to workThe command isn't found, or only dotnet MyApp.dll worksInstall the SDK for development; users of your app only need the runtime
Setting a TargetFramework newer than the installed SDKRestore or build fails with an unsupported-framework errorRun dotnet --version and match the moniker, e.g. net10.0
Editing files inside bin/ or obj/Changes are overwritten on the next buildEdit only source files and the .csproj; treat bin/ and obj/ as disposable
Practice
  1. Create a console project, change the message to print your name, and run it with dotnet run. Then find the .dll it produced under bin/.
  2. Build the same project with -c Release and compare the two output folders. Which files differ?
Key takeaways
  • The SDK builds your code; the runtime (the CLR plus the base class library) runs it.
  • C# compiles to IL, and the JIT turns IL into machine code as methods are first called.
  • dotnet new, build, and run are the core loop, and the .csproj file controls the settings.
