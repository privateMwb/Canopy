Equality, ToString & the Object Contract

Every type inherits a few methods from object, and getting equality and hashing right is what makes your types work in dictionaries, sets, and comparisons.

§1Reference vs. Value Equality

For classes, the default Equals and == test reference equality: are these the same object? Strings, records, and structs are different: they compare values.

class Box { public int Size; }
var a = new Box { Size = 1 };
var b = new Box { Size = 1 };
Console.WriteLine(a == b);        // False: different objects
Console.WriteLine(a.Equals(b));   // False (default behavior)
Console.WriteLine(ReferenceEquals(a, a)); // True

§2Overriding Equals and GetHashCode

When two instances should be equal by their contents, override Equals and GetHashCode together, and implement IEquatable<T> to avoid boxing and casts.

public sealed class Isbn : IEquatable<Isbn>
{
    public string Value { get; }
    public Isbn(string value) => Value = value;

    public bool Equals(Isbn? other) =>
        other is not null && Value == other.Value;
    public override bool Equals(object? obj) => Equals(obj as Isbn);
    public override int GetHashCode() => Value.GetHashCode();
    public override string ToString() => Value;
}

The contract is simple but strict: if two objects are equal, they must have the same hash code. Hash-based collections use the hash to pick a bucket and then Equals to confirm, so a violation makes items vanish from dictionaries. Combine several fields with HashCode.Combine(a, b).

§3ToString and the Easy Way Out

ToString() defaults to the type name, which is useless in logs. Override it to show the values you'd want to see while debugging. The easiest way to get all of this correct is to avoid writing it by hand:

public record Isbn(string Value);                  // equality, hash, ToString: done
public readonly record struct Point(int X, int Y); // same for value types

Hand-written Equals is for the rare class that needs custom rules, for example comparing only an ID. Whatever you compare in Equals must be exactly what you hash, and neither should change while the object sits inside a HashSet or Dictionary key.

The key insight Equals and GetHashCode are a pair. Override both, base both on the same immutable fields, or let a record do it for you.

§4Common Mistakes

MistakeWhat HappensFix
Overriding Equals but not GetHashCodeEqual objects land in different buckets, so dictionary lookups failAlways override both (the compiler warns)
Hashing a mutable fieldThe object can't be found after it changesBase hashing on immutable data only
Comparing floating-point fields with == in EqualsTiny rounding differences make equal values unequalCompare with a tolerance, or use decimal
Practice
  1. Put two Isbn objects with the same value into a HashSet<Isbn> with and without the GetHashCode override, and count the items.
  2. Replace the hand-written Isbn class with a record and confirm the tests you wrote still pass.
Key takeaways
  • Classes compare by reference by default; records and structs compare by value.
  • Override Equals and GetHashCode together and base both on immutable fields.
  • Prefer records for value-like types, and override ToString so debugging output is readable.
