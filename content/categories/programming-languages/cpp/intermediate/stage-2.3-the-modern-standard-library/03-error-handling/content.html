Error Handling

C++ gives you several ways to report failure, and choosing the right one per situation matters more than choosing a favorite.

§1Exceptions

An exception unwinds the stack from the throw to the nearest matching catch, running destructors on the way, which is why RAII and exceptions work together.

#include <stdexcept>
int parsePort(const std::string& s) {
    int p = std::stoi(s);                           // throws std::invalid_argument
    if (p < 1 || p > 65535) throw std::out_of_range{"port out of range"};
    return p;
}
try {
    int port = parsePort(input);
} catch (const std::out_of_range& e) {
    std::cerr << "bad port: " << e.what() << '\n';
} catch (const std::exception& e) {                 // always catch by const reference
    std::cerr << e.what() << '\n';
}

Throw by value, catch by const&. Exceptions suit exceptional, rare failures that the immediate caller can't handle, because they keep the success path clean. The thrown path is slow, and not zero cost in code size.

§2Error Codes and Optional

When failure is expected and common, such as "user typed a bad number" or "key not found," return it as a value instead.

std::optional<int> tryParse(std::string_view s);       // nullopt on failure
std::error_code ec;
std::filesystem::remove("x", ec);                      // overloads that report via ec
if (ec) { /* handle */ }

optional says only *that* it failed, and error codes say *why*, but they are easy to ignore.

§3std::expected (C++23)

std::expected<T, E> holds either a value or an error, forcing callers to look at both.

#include <expected>
std::expected<int, std::string> parse(std::string_view s) {
    int v{};
    auto [ptr, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    if (ec != std::errc{}) return std::unexpected{"not a number"};
    return v;
}
if (auto r = parse("42")) std::cout << *r << '\n';
else                       std::cerr << r.error() << '\n';
auto doubled = parse("21").transform([](int x) { return x * 2; });   // monadic chaining

§4noexcept and Termination

noexcept promises a function won't throw. If one does, std::terminate is called immediately. Mark destructors, moves, and swaps noexcept. Programmer errors (violated preconditions) are better caught by assert, since no caller can recover from "my code is wrong."

§5Exception Safety Levels

  • No-throw: never fails (swap, moves, destructors).
  • Strong: if it throws, nothing changed (copy-and-swap).
  • Basic: if it throws, nothing leaks and invariants hold, but values may have changed.

RAII provides the basic guarantee almost for free.

The key insight Pick by how routine the failure is. Rare and unrecoverable locally: exception. Common and expected: optional or expected. Bug in the caller: assert.

§6Common Mistakes

MistakeWhat HappensFix
Catching ... and swallowing the errorHides real bugsCatch specific types, and log or rethrow
Throwing from a destructorterminate if already unwindingNever let exceptions escape destructors
Catching exceptions by valueSlices derived exceptions and copiesCatch by const&
Practice
  1. Write the same parseInt three ways: throwing, optional, and expected. Compare call sites for a bad input.
  2. Mark a function noexcept that calls something throwing, and observe the program terminate.
Key takeaways
  • Exceptions fit rare, non-local failures; optional/expected fit common, expected ones.
  • Throw by value, catch by const&, and never throw from destructors.
  • noexcept is a promise; breaking it terminates the program.
