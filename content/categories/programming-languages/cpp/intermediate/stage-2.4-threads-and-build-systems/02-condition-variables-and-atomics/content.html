Condition Variables & Atomics

A condition variable lets a thread sleep until another thread signals that something changed, and an atomic is the lightweight tool for a single shared variable.

§1Waiting Without Spinning

Polling a flag in a loop wastes CPU, and sleeping a fixed time wastes latency. A std::condition_variable blocks a thread until another notifies it, with a mutex protecting the condition.

std::mutex m;
std::condition_variable cv;
std::queue<int> jobs;
bool done{false};

void producer() {
    for (int i = 0; i < 5; ++i) {
        { std::lock_guard lock{m}; jobs.push(i); }
        cv.notify_one();
    }
    { std::lock_guard lock{m}; done = true; }
    cv.notify_all();
}
void consumer() {
    std::unique_lock lock{m};
    while (true) {
        cv.wait(lock, [] { return !jobs.empty() || done; });   // releases m while sleeping
        while (!jobs.empty()) { int j = jobs.front(); jobs.pop(); /* process j */ }
        if (done) break;
    }
}

wait atomically unlocks the mutex and sleeps; when woken it re-locks and re-checks the predicate.

§2Always Use a Predicate

Waiting can end spuriously, and a notification sent before a thread starts waiting is lost. The predicate form wait(lock, pred) loops until the condition is truly true, and handles both problems. The condition itself (jobs, done) must only be changed while holding the same mutex.

§3std::atomic

For one simple shared variable, a mutex is heavier than needed. std::atomic<T> makes individual operations indivisible.

#include <atomic>
std::atomic<int> counter{0};
auto inc = [&] { for (int i = 0; i < 100000; ++i) ++counter; };   // thread-safe
std::atomic<bool> stop{false};
// worker: while (!stop.load()) { ... }       main: stop.store(true);
counter.fetch_add(5);
int expected = 3;
counter.compare_exchange_strong(expected, 10);   // set to 10 only if currently 3

The default ordering is the strongest (seq_cst), which is always correct. Weaker orderings are an advanced topic for Level 3.

§4Atomic or Mutex?

An atomic protects one variable. As soon as an invariant spans two or more variables (a queue plus a count, a balance and a log), use a mutex, because two separate atomic updates are not one atomic operation.

std::atomic<int> a{0}, b{0};
// a.store(1); b.store(1);     // another thread can see a=1, b=0: no combined atomicity
The key insight Condition variables wait for a *state* guarded by a mutex; they don't carry the information themselves. Always write the state change, then notify, and always wait on a predicate.

§5Common Mistakes

MistakeWhat HappensFix
Calling wait without a predicateSpurious wakeups or lost notifications cause hangs or wrong behaviorUse cv.wait(lock, predicate)
Changing the condition variable's state without the mutexA race between the check and the wait, so a wakeup is missedModify shared state while holding the lock
Using several atomics to protect one invariantOther threads see inconsistent intermediate statesUse a mutex
Practice
  1. Build a producer/consumer pair with a bounded queue using a mutex and two condition variables (not empty, not full).
  2. Replace a std::atomic<bool> stop flag with a plain bool and run ThreadSanitizer to see the report.
Key takeaways
  • Condition variables let a thread sleep until a guarded condition holds; always use a predicate.
  • std::atomic is right for one independent variable, such as a counter or a flag.
  • Multi-variable invariants need a mutex.
