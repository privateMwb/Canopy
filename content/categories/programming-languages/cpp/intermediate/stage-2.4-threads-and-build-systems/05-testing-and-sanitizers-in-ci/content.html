Testing & Sanitizers in CI

Automated tests and sanitizer builds that run on every commit turn "it worked on my machine" into a checked guarantee.

§1Unit Tests with GoogleTest

A test framework gives you test discovery, assertions, and readable failures. GoogleTest integrates with CMake through FetchContent and gtest_discover_tests.

// tests/stack_test.cpp
#include <gtest/gtest.h>
#include "myapp/stack.h"

TEST(StackTest, StartsEmpty) {
    Stack<int> s;
    EXPECT_TRUE(s.empty());
}
TEST(StackTest, PopReturnsLastPushed) {
    Stack<int> s;
    s.push(1); s.push(2);
    EXPECT_EQ(s.pop(), 2);          // EXPECT continues on failure
    ASSERT_FALSE(s.empty());        // ASSERT aborts the test on failure
}
TEST(StackTest, PopOnEmptyThrows) {
    Stack<int> s;
    EXPECT_THROW(s.pop(), std::out_of_range);
}
enable_testing()
FetchContent_Declare(googletest URL https://github.com/google/googletest/archive/refs/tags/v1.14.0.zip)
FetchContent_MakeAvailable(googletest)
add_executable(tests tests/stack_test.cpp)
target_link_libraries(tests PRIVATE GTest::gtest_main)
include(GoogleTest)
gtest_discover_tests(tests)

Run with ctest --test-dir build --output-on-failure. Catch2 offers a similar experience with a lighter syntax (TEST_CASE, REQUIRE). Test behavior through the public interface, give tests descriptive names, and keep each test about one thing.

§2Which Sanitizer Finds What

  • ASan (address): out-of-bounds, use-after-free, double free, leaks.
  • UBSan (undefined): overflow, bad shifts, null dereferences, misalignment.
  • TSan (thread): data races and some lock-order problems.
  • MSan (memory, Clang only): reads of uninitialized memory.

ASan and TSan cannot be combined, so you build and run the test suite once for each: one job for address,undefined, one for thread.

§3Continuous Integration

A CI configuration builds and tests on every push, with each sanitizer as its own job. A minimal GitHub Actions example:

name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        san: ["address,undefined", "thread"]
    steps:
      - uses: actions/checkout@v4
      - run: cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_CXX_FLAGS="-fsanitize=${{ matrix.san }} -fno-omit-frame-pointer"
      - run: cmake --build build -j
      - run: ctest --test-dir build --output-on-failure

Sanitizers abort with a non-zero exit code on a finding, so the job fails, which is the point. Treat a red build as a stop sign, not a suggestion.

The key insight A sanitizer only finds bugs on paths your tests actually execute. The tests supply the coverage, and the sanitizers supply the detection, so you need both.

§4Common Mistakes

MistakeWhat HappensFix
Running sanitizers only by handRegressions slip in between runsMake them a required CI job
Combining address and thread in one buildIncompatible; the build or run failsUse separate build configurations
Testing only the happy pathEdge cases and error paths stay unverifiedAdd tests for empty, boundary, and failing inputs
Practice
  1. Add GoogleTest to your CMake project with three tests, and run them with ctest.
  2. Write a GitHub Actions (or equivalent) file that builds with ASan+UBSan and a second job with TSan.
Key takeaways
  • Tests give coverage, and sanitizers detect memory and threading bugs on the code paths that tests exercise.
  • Run ASan/UBSan and TSan as separate builds, because they can't be combined.
  • CI should fail the build on any test failure or sanitizer finding.
