Cache-Friendly Design & Data Layout

On modern CPUs the cost of a program is often set by how many cache lines it touches, so data layout can matter more than the algorithm's instruction count.

§1The Memory Hierarchy

A load from L1 cache costs about a nanosecond or less, while a load from main memory costs on the order of 100 ns, a gap of roughly 100x. The CPU fetches memory in cache lines (64 bytes on x86-64 and most ARM chips), so touching one byte pulls in its neighbors, and sequential access is nearly free while random access stalls.

std::vector<int> v(1 << 24);
long long sum = 0;
for (int x : v) sum += x;                       // sequential: prefetcher streams it in
// Walking a std::list<int> of the same size is often 10x or more slower: each node is separate

This is why std::vector beats node-based structures at small and medium sizes despite worse big-O on paper: contiguous elements are cache-friendly.

§2Array of Structs vs. Struct of Arrays

How you group fields decides which bytes share a cache line.

struct Particle { float x, y, z; float vx, vy, vz; int id; int flags; };   // 32 bytes
std::vector<Particle> aos;                      // AoS: whole particles together

struct Particles {                              // SoA: each field in its own array
    std::vector<float> x, y, z, vx, vy, vz;
    std::vector<int> id, flags;
};

If a hot loop updates only positions, AoS loads the unused id and flags into cache with every particle, wasting bandwidth. SoA reads only the arrays the loop uses and also vectorizes well. If code usually needs whole objects, AoS is simpler and just as fast. Choose by access pattern.

§3Struct Size, Padding, and False Sharing

Compilers insert padding to align members, so field order changes sizeof.

struct A { char c; double d; char e; };     // 24 bytes with padding
struct B { double d; char c; char e; };     // 16 bytes: sort members by size, largest first
static_assert(sizeof(B) == 16);

Two threads writing to different variables that share a cache line cause false sharing: the line ping-pongs between cores. Separate hot per-thread data with alignas(64) (or std::hardware_destructive_interference_size).

struct alignas(64) PerThreadCounter { std::atomic<long> n{0}; };

§4Practical Rules

  • Prefer contiguous containers (vector, array, flat sorted vectors) over pointer-chasing ones.
  • Keep hot fields together and cold fields apart; split a struct if a loop uses a third of it.
  • Avoid std::vector<std::unique_ptr<T>> for hot loops; store values inline when possible.
  • Process data in the order it sits in memory.
The key insight Think in cache lines, not objects. The question for a hot loop is "how many bytes did I pull in per byte I used?" Layout changes that ratio without changing the algorithm.

§5Common Mistakes

MistakeWhat HappensFix
Choosing a linked list for "fast insertion"Cache misses on every node make it slower than a vector in nearly all workloadsUse vector and measure
Optimizing layout without measuringEffort goes to code that isn't hotProfile first (a later lesson)
Per-thread counters packed in one arrayFalse sharing slows every threadPad each to a cache line
Practice
  1. Write a loop summing one field of a 10-million-element AoS and the same field in SoA form, and time both.
  2. Reorder the members of a struct to minimize sizeof, and confirm with static_assert.
Key takeaways
  • Memory access, not arithmetic, usually dominates, and contiguous sequential access is fastest.
  • Choose AoS or SoA by what the hot loop actually touches.
  • Member order, padding, and false sharing are all measurable layout effects.
