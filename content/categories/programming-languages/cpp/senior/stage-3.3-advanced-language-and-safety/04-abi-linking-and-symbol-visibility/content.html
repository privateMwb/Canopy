ABI, Linking & Symbol Visibility

The ABI is the binary-level contract between compiled code, and changing it without recompiling every user breaks programs in ways the compiler can't warn you about.

§1API vs. ABI

The API is what source code sees: function names and types. The ABI (Application Binary Interface) is what compiled code depends on: struct layouts and sizes, calling conventions, vtable layouts, name mangling, and the standard library's own internals. A change that is source-compatible can still be ABI-breaking.

// v1:  struct Config { int a; };            // sizeof == 4
// v2:  struct Config { int a; int b; };     // sizeof == 8
// A binary compiled against v1 that links to v2 reads and writes the wrong layout. No error.

Adding a data member, reordering members, adding a virtual function, or changing an inline function's body (which was copied into callers) all change the ABI.

§2Name Mangling

C++ allows overloading, so the compiler encodes parameter types (and namespaces) into each symbol's name. int f(double) becomes something like _Z1fd under the Itanium ABI.

nm -C libfoo.so              # list symbols, demangled
nm libfoo.so | grep _Z       # raw mangled names
c++filt _Z3addii             # add(int, int)

Mangling differs between compilers (Itanium on Linux/macOS, MSVC's scheme on Windows) and encodes enough that mixing mismatched declarations usually becomes a linker error, a good outcome. The dangerous cases are the ones that link fine but disagree about layout.

§3Shared Libraries and Visibility

By default on Linux, every non-static symbol in a shared library is exported, which bloats the library, slows loading, and freezes internal details into your ABI. Hide by default and export deliberately.

g++ -shared -fPIC -fvisibility=hidden -o libfoo.so foo.cpp

#define FOO_API __attribute__((visibility("default")))
FOO_API int publicFunction(int);         // exported
int internalHelper(int);                 // hidden

On Windows use __declspec(dllexport) / dllimport. Fewer exported symbols means a smaller ABI surface to maintain.

§4Keeping an ABI Stable

  • Expose a C interface (extern "C") or opaque handles: struct Foo; Foo* foo_create(); void foo_destroy(Foo*);.
  • The pimpl idiom hides data members behind a pointer, so layout changes don't affect callers.
  • Don't expose standard library types across a DLL boundary if the library and caller might use different standard library versions or settings.
  • Avoid inline and template code in public headers when you want to change it without recompiling callers.
  • Use inline namespaces or versioned symbols when you must evolve.

The standard library has its own ABI hazards, such as the libstdc++ dual ABI for std::string (_GLIBCXX_USE_CXX11_ABI), where mismatched settings give mysterious link errors.

The key insight ABI breaks are silent because nothing checks them: the program links and then misbehaves. Treat anything in a public header as frozen once shipped, and keep implementation details behind opaque pointers.

§5Common Mistakes

MistakeWhat HappensFix
Adding a data member or virtual function to a public class in a minor releaseOld binaries read the wrong layoutUse pimpl, or bump the major version and require a rebuild
Exporting every symbolBloat, and internals become de-facto APIUse -fvisibility=hidden and annotate the public API
Passing std::string or std::vector across a plugin boundaryDiffering allocators and ABIs corrupt the heapUse C types and let one side own allocation
Practice
  1. Build a small shared library with -fvisibility=hidden and an exported function, and verify what nm -D shows.
  2. Convert a class with private data members into a pimpl, and demonstrate that adding a member no longer changes sizeof for callers.
Key takeaways
  • The ABI is layouts, calling conventions, and mangled names, and changes can be invisible to source-level checks.
  • Hide symbols by default, and export a deliberate, small API.
  • C interfaces, opaque handles, and pimpl are the tools for stable binary interfaces.
