Hardening & the Core Guidelines

You can't eliminate undefined behavior by trying harder, but you can shrink the room it has to occur by using safe idioms, hardening flags, and static analysis.

§1The C++ Core Guidelines

The Core Guidelines (by Stroustrup and Sutter) are a large, searchable rule set with rationale, and many are checkable by tools. The ones that remove the most bugs:

  • R: resource management. Use RAII; no owning raw pointers; make_unique.
  • ES: expressions. Initialize every variable, avoid casts, prefer const.
  • C.21: the Rule of Zero/Five, and C.35 virtual destructors in bases.
  • I: interfaces. Make them explicit, strongly typed, and with clear ownership.
  • Bounds: use span, containers, and at, not pointer arithmetic.

Treat them as defaults with reasons rather than law, and annotate or suppress deliberately where you break one.

§2Static Analysis

Static analyzers examine code without running it. Use several, because each finds different things.

clang-tidy -checks='bugprone-*,cppcoreguidelines-*,modernize-*,performance-*' file.cpp -- -std=c++20
cppcheck --enable=all --inconclusive src/
g++ -fanalyzer file.cpp         # GCC's built-in analyzer

clang-tidy can also auto-fix (-fix) many modernizations. Run analyzers in CI, start with a small set of checks you're willing to fix, and expand. A baseline of "zero new warnings" works better than an all-at-once cleanup.

§3Compiler Hardening

Turn on warnings and run-time mitigations, which are cheap defenses against exploitation of memory bugs.

-Wall -Wextra -Wpedantic -Wconversion -Wshadow -Wnull-dereference -Werror
-D_GLIBCXX_ASSERTIONS            # bounds checks in libstdc++ containers
-D_FORTIFY_SOURCE=3              # checks for common C library misuse
-fstack-protector-strong -fstack-clash-protection -fcf-protection
-fPIE -pie -Wl,-z,relro,-z,now   # position-independent code, hardened linking
-ftrivial-auto-var-init=zero     # zero-initialize stack variables

libc++ and libstdc++ both offer hardened modes that turn undefined out-of-bounds accesses in vector, span, and others into controlled aborts. The performance cost is small for most programs.

§4Making Whole Bug Classes Impossible

Aim for designs where the bug can't be written, not code where it's merely unlikely.

  • Use std::span and .at() instead of pointer-plus-length for buffers.
  • Use std::optional, std::variant, and strong types instead of sentinels and ints for IDs and units.
  • Use std::unique_ptr and containers so ownership is never manual.
  • Use enum class, explicit, and [[nodiscard]] so misuse fails to compile or warns.
  • Use gsl::not_null, std::string_view carefully, and gsl::owner annotations where raw pointers remain.
  • Fuzz parsers and anything that handles untrusted input (libFuzzer, AFL++) with sanitizers on.
The key insight Safety is cumulative: language-level idioms prevent bugs, hardening flags limit the damage when a bug slips through, and analyzers, sanitizers, and fuzzers find what remains. No single layer is enough.

§5Common Mistakes

MistakeWhat HappensFix
Enabling a pile of warnings then ignoring themWarning fatigue hides real problemsFix them, or turn off ones the team won't act on, and use -Werror in CI
Suppressing analyzer findings without explanationThe real bug staysSuppress narrowly with a comment, and review suppressions
Trusting hardening to replace correctnessMitigations reduce exploitability but don't fix logicCombine them with sanitizers and tests
Practice
  1. Run clang-tidy with the bugprone and cppcoreguidelines checks on a project and triage the first 20 findings by severity.
  2. Build one project with -D_GLIBCXX_ASSERTIONS and a hardened set of flags, and measure the run-time overhead.
Key takeaways
  • The Core Guidelines supply checkable default rules, especially for ownership, bounds, and initialization.
  • Combine warnings, static analyzers, sanitizers, fuzzing, and hardening flags, because each finds different bugs.
  • Prefer APIs that make a bug impossible to write over APIs that merely discourage it.
