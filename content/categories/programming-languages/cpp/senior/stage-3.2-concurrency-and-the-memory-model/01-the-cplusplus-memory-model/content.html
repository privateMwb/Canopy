The C++ Memory Model

The memory model defines which values a thread may see when other threads write, and it is what makes lock-free code either correct or silently broken.

§1Why Ordering Is a Question at All

Compilers and CPUs reorder memory operations for speed, and each core has store buffers and caches. Without rules, one thread's writes can appear to another in a different order than the code wrote them. The model defines the guarantees through happens-before: if A happens-before B, then B sees A's effects. Mutexes, thread creation and join, and atomics with suitable orderings all create happens-before edges.

int data{0};
std::atomic<bool> ready{false};
// Thread 1:                      // Thread 2:
data = 42;                        while (!ready.load()) {}
ready.store(true);                std::cout << data << '\n';   // must print 42

With the default atomics this is guaranteed to print 42. With a plain bool it's a data race and undefined behavior.

§2The Memory Orders

Every atomic operation accepts a std::memory_order.

  • memory_order_seq_cst (the default): all threads agree on one total order of all seq_cst operations. Simplest to reason about and the most expensive on some CPUs.
  • memory_order_acquire (loads) and memory_order_release (stores): a release store makes everything before it visible to a thread whose acquire load reads that value.
  • memory_order_acq_rel: for read-modify-write operations, acting as both.
  • memory_order_relaxed: atomicity only; no ordering with other variables.
// Release/acquire handoff: the same flag example, with weaker, cheaper ordering
data = 42;
ready.store(true, std::memory_order_release);         // publishes data

while (!ready.load(std::memory_order_acquire)) {}     // synchronizes-with the store
use(data);                                            // sees 42

Release/acquire pairs are enough for "publish data, then flag it" patterns such as spinlocks, queues, and once-flags.

§3Relaxed Operations

Relaxed atomics are correct when nothing else depends on the ordering, such as a statistics counter that is only read at the end.

std::atomic<long> hits{0};
hits.fetch_add(1, std::memory_order_relaxed);        // just needs to be atomic

Relaxed is not appropriate for a flag guarding other data, because the reader may see the flag set but the data stale.

§4Fences and Reality Checks

std::atomic_thread_fence provides ordering without tying it to one variable, and is rarely needed. On x86, loads and stores already have acquire/release-like behavior, so bugs from too-weak orderings can hide until the code runs on ARM, where reordering is more aggressive. Test on weakly ordered hardware and with ThreadSanitizer.

The key insight Start with the default seq_cst. Weaken an ordering only when a profile shows the atomics are a bottleneck, and only after you can state the happens-before edge you're relying on.

Practice
  1. Implement a one-shot publish with plain data and an atomic<bool>, using release/acquire. Explain which edge makes the data visible.
  2. Write a spinlock with std::atomic_flag (acquire on lock, release on unlock), and justify each ordering.
Key takeaways
  • Happens-before decides what values a thread may see, and data races without it are undefined behavior.
  • Release/acquire is the standard publish pattern, relaxed is for independent counters, and seq_cst is the safe default.
  • Weak-ordering bugs hide on x86, so test on ARM and with TSan.
