Finding Races with ThreadSanitizer

ThreadSanitizer detects data races at run time, and learning to read its report is the fastest way to find concurrency bugs that tests alone miss.

§1Using TSan

Compile and link with -fsanitize=thread, with optimization and symbols, and run the program or test suite. TSan instruments every memory access and tracks happens-before between threads, reporting any pair of conflicting accesses that aren't ordered.

g++ -std=c++20 -g -O1 -fsanitize=thread -fno-omit-frame-pointer race.cpp -o race -pthread
./race

It slows the program by 5 to 15x and uses much more memory, and it cannot be combined with ASan. It finds races that actually execute in that run, regardless of whether the bad interleaving happened to occur, which is far better than hoping a test fails.

§2Reading a Report

int counter = 0;
void work() { for (int i = 0; i < 1000; ++i) ++counter; }
// main starts two threads running work(), then joins them
WARNING: ThreadSanitizer: data race (pid=4711)
  Write of size 4 at 0x000000c0a2b0 by thread T2:
    #0 work() race.cpp:2
  Previous write of size 4 at 0x000000c0a2b0 by thread T1:
    #0 work() race.cpp:2
  Location is global 'counter' of size 4
  Thread T2 created by main thread at: ...

Read it in this order: the kind of access (read or write) for both threads, the memory location (the variable name, or a heap block with its allocation stack), the two stacks showing the conflicting code, and where each thread was created. Two accesses, at least one a write, with no synchronization between them: that is the definition of the race.

§3Common Findings and Fixes

  • Unprotected shared variable: add a mutex, make it atomic, or stop sharing it.
  • Mutex missing on one code path: a getter reads without locking while a setter locks; take the lock in both.
  • Lock-order inversion (reported as a potential deadlock): make all threads take mutexes in the same order, or use std::scoped_lock.
  • Race on destruction: a thread uses an object while another destroys it; fix ownership with shared_ptr or join threads first.
  • Plain bool stop flag: use std::atomic<bool> or std::stop_token.

§4Suppressions and Limits

TSan sometimes flags code in third-party libraries; a suppression file (TSAN_OPTIONS=suppressions=tsan.supp) can silence a known-benign report, but treat it as a last resort and with a comment. TSan does not understand custom synchronization built from inline assembly or non-standard primitives, and it can't prove the absence of races, only find those on executed paths. Combine it with stress tests that run the concurrent code many times with varied timing.

The key insight A race that appears once in a million runs in production will be reported on the first run under TSan. "It never fails" is not evidence of correctness, but "TSan is clean on a good stress test" is real evidence.

§5Common Mistakes

MistakeWhat HappensFix
Dismissing a report as "benign"Compilers may assume no races and break the code in new waysFix every report, or prove it with proper atomics
Running TSan on code that doesn't exercise concurrencyNothing to detectWrite tests that actually run multiple threads
Mixing ASan and TSan flagsWon't build or runUse separate configurations
Practice
  1. Write the racy counter above, run it under TSan, and fix it first with a mutex, then with std::atomic.
  2. Introduce a lock-order inversion between two mutexes and read TSan's deadlock report.
Key takeaways
  • TSan reports races that ran, even if they didn't corrupt anything this time.
  • Read the access kinds, location, and both stacks; then add synchronization or remove the sharing.
  • Run TSan over a concurrent stress test in CI, as its own build.
