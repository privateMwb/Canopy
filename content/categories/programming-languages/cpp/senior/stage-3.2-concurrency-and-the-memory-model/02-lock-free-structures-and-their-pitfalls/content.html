Lock-Free Structures & Their Pitfalls

Lock-free structures use atomic compare-and-swap instead of mutexes, and they are far harder to get right than they look.

§1Compare-and-Swap

compare_exchange_weak(expected, desired) atomically sets the variable to desired only if it currently equals expected; otherwise it loads the current value into expected and fails. Retrying in a loop is the basic pattern.

std::atomic<int> maxSeen{0};
void update(int v) {
    int cur = maxSeen.load();
    while (v > cur && !maxSeen.compare_exchange_weak(cur, v)) {
        // on failure cur holds the latest value: loop re-checks it
    }
}

weak may fail spuriously (cheaper on some CPUs) and so belongs in a loop; strong doesn't fail spuriously.

§2A Lock-Free Stack

template <typename T>
class LockFreeStack {
    struct Node { T value; Node* next; };
    std::atomic<Node*> head_{nullptr};
public:
    void push(T v) {
        Node* n = new Node{std::move(v), head_.load(std::memory_order_relaxed)};
        while (!head_.compare_exchange_weak(n->next, n,
                   std::memory_order_release, std::memory_order_relaxed)) {}
    }
    bool pop(T& out) {
        Node* h = head_.load(std::memory_order_acquire);
        while (h && !head_.compare_exchange_weak(h, h->next,
                   std::memory_order_acquire, std::memory_order_acquire)) {}
        if (!h) return false;
        out = std::move(h->value);
        // delete h;   // UNSAFE: another thread may still be reading h->next
        return true;
    }
};

The commented-out delete shows the central difficulty.

§3The ABA Problem

Thread 1 reads head A (with A->next = B) and gets interrupted. Meanwhile thread 2 pops A, pops B, frees them, and pushes a new node that happens to reuse A's address. Thread 1 resumes and its CAS sees head == A and succeeds, installing the stale pointer to B, a freed node. The value looks unchanged but the world changed. Fixes:

  • Tagged pointers: pair the pointer with a version counter and CAS both together (double-width CAS).
  • Hazard pointers: threads publish what they're reading, and nodes are freed only when no hazard references them.
  • Epoch-based reclamation and RCU: defer frees until all threads pass a safe point.
  • Never free; use a pool (leaks memory, but sidesteps the problem).

C++26 adds std::hazard_pointer and RCU in the standard library, and many production libraries (Folly, libcds, boost.lockfree) provide tested implementations.

§4Lock-Free Is Not "Faster"

Lock-free means some thread always makes progress, without a thread being stuck behind a lock-holder that was descheduled. It doesn't mean faster: contended CAS loops retry and bounce cache lines, and an uncontended mutex is only tens of nanoseconds. Use lock-free structures when you need to avoid blocking (real-time threads, signal handlers) or measurements show lock contention is your bottleneck. Alternatives to try first: reduce sharing, shard the data per thread, batch updates, use a read-write lock, or use a well-tested concurrent queue.

The key insight The hard part of lock-free programming isn't the CAS, it's memory reclamation: knowing when it's safe to free a node that another thread may still be examining.

§5Common Mistakes

Key takeaways
  • A CAS loop retries until the value it based its decision on is still current.
  • ABA and memory reclamation are the real difficulties of lock-free structures.
  • Lock-free means non-blocking, not automatically faster; measure before choosing it.
