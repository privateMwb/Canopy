Interoperating with C & Other Languages

The common ground between languages is the C ABI, so crossing a language boundary means exposing a C-shaped interface and carefully handling ownership, errors, and strings.

§1extern "C"

C++ mangles names, so other languages can't find your functions. extern "C" gives a function C linkage: an unmangled name and the C calling convention.

// mylib.h: usable from both C and C++
#ifdef __cplusplus
extern "C" {
#endif
typedef struct Counter Counter;                   // opaque handle
Counter* counter_create(void);
void     counter_add(Counter*, int);
int      counter_value(const Counter*);
void     counter_destroy(Counter*);
#ifdef __cplusplus
}
#endif
// mylib.cpp
struct Counter { int n{0}; };
extern "C" Counter* counter_create() { return new Counter; }
extern "C" void counter_add(Counter* c, int x) { c->n += x; }
extern "C" int counter_value(const Counter* c) { return c->n; }
extern "C" void counter_destroy(Counter* c) { delete c; }

The inside can be rich C++, and the outside is a plain C interface.

§2Rules at the Boundary

  • Only C types cross: integers, floats, pointers, plain structs, function pointers. No std::string, std::vector, references, or classes.
  • No exceptions may escape: catch everything at the boundary and convert to error codes. An exception propagating into C or another runtime is undefined behavior or a crash.
  • Ownership must be explicit: whoever allocates must free, ideally with a matching _destroy or _free function from the same library, so allocators match.
  • Strings: pass const char* plus length (or null-terminated) and document encoding (UTF-8) and who owns the memory.
  • Fixed-width types (int32_t) and explicit struct packing avoid size surprises.
extern "C" int counter_parse(Counter* c, const char* text) noexcept {
    try { c->n = std::stoi(text); return 0; }
    catch (const std::exception&) { return -1; }
    catch (...) { return -2; }
}

§3Calling C from C++

Wrap C library handles in RAII types immediately so every exit path releases them, as in the RAII lesson.

using FilePtr = std::unique_ptr<std::FILE, decltype(&std::fclose)>;
FilePtr f{std::fopen("x.txt", "r"), &std::fclose};

§4Python Bindings

Pybind11 and nanobind expose C++ functions and classes to Python with very little code, and handle type conversion, reference counting, and exceptions.

#include <pybind11/pybind11.h>
namespace py = pybind11;
int add(int a, int b) { return a + b; }
PYBIND11_MODULE(example, m) {
    m.def("add", &add, "Add two integers");
    py::class_<Counter>(m, "Counter")
        .def(py::init<>())
        .def("add", &Counter::add)
        .def_property_readonly("value", &Counter::value);
}

Consider the GIL: release it (py::gil_scoped_release) around long computations, and be careful about object lifetimes shared with Python. Other routes: ctypes and cffi on a C interface, SWIG, and for Rust, the cxx crate or cbindgen.

The key insight A language boundary is a trust boundary. Treat everything crossing it as untrusted input: validate sizes and pointers, never let exceptions through, and make ownership impossible to misread.

§5Common Mistakes

MistakeWhat HappensFix
Letting a C++ exception propagate through a C callback or FFI callCrash or undefined behaviorCatch all exceptions at the boundary and return an error code
Freeing memory with a different allocator than the one that allocated itHeap corruptionProvide the library's own destroy function
Exposing std::string or a class in a C interfaceLayout and ABI mismatchUse const char* plus length, and opaque handles
Practice
  1. Wrap a small C++ class in a C interface, then call it from C and from Python with ctypes.
  2. Write a pybind11 module exposing a function and a class, and release the GIL during a long loop.
Key takeaways
  • extern "C" plus plain C types gives a stable, language-neutral boundary.
  • Catch every exception, make ownership explicit, and validate all inputs at the boundary.
  • Wrap C handles in RAII on the C++ side, and use pybind11 or nanobind for Python.
