Undefined Behavior & Sanitizers

Undefined behavior means the language places no requirements on what happens, so a program that "works" may still be broken, and sanitizers are how you find out.

§1What Undefined Behavior Is

The standard says some operations have no defined result: the program may crash, give a wrong answer, appear to work, or behave differently after an unrelated change. The compiler is allowed to assume UB never happens and optimizes accordingly.

int a[3]{};
int i = 3;
a[i] = 1;                 // out-of-bounds write: UB

int x = std::numeric_limits<int>::max();
x + 1;                    // signed overflow: UB

int* p = nullptr;
*p;                       // null dereference: UB

int u;
std::cout << u;           // read of uninitialized int: UB

Others include use after free, data races, and reading an object after its lifetime ends. UB is not "the same as a crash": the dangerous cases are the silent ones.

§2Why Testing Alone Fails

UB can pass every test, then break with a new compiler version, optimization level, or platform. Because the optimizer assumes no UB, it may delete a null check that comes *after* a dereference. "It runs fine on my machine" is not evidence that code is correct.

§3Sanitizers

Sanitizers instrument your program to detect bugs while it runs. Enable them with compiler flags in a debug build:

g++ -std=c++20 -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer main.cpp -o app
./app
  • AddressSanitizer (ASan) catches heap/stack out-of-bounds, use after free, double free, and leaks.
  • UndefinedBehaviorSanitizer (UBSan) catches signed overflow, bad shifts, null dereference, misaligned access, and more.

A typical report names the bug type, the line that triggered it, and where the memory was allocated and freed, so read it from the top.

==1234==ERROR: AddressSanitizer: heap-use-after-free on address 0x602000000010
READ of size 4 at 0x602000000010 thread T0
    #0 0x4011a3 in main main.cpp:9

Sanitizers slow a program by roughly 2x or more, so use them in tests and development, not production. Run them over your whole test suite regularly.

The key insight A bug you can't see is still a bug. Make sanitizers part of the normal build, so every run is a chance to catch UB rather than hoping the program crashes.

§4Common Mistakes

MistakeWhat HappensFix
Concluding "no crash means no bug"UB hides until the build or input changesRun the program under ASan and UBSan
Combining ASan with TSan in one buildThey are incompatibleBuild separately, one sanitizer family per binary
Ignoring a sanitizer warning because the output was rightThe bug is still thereTreat every report as a real defect
Practice
  1. Write a program that writes one element past a std::vector's end, build it with -fsanitize=address, and read the report.
  2. Add signed overflow to a program and confirm UBSan reports it with a line number.
  3. List three kinds of UB and write the shortest program for each.
Key takeaways
  • Undefined behavior means no guarantees at all, and the optimizer relies on its absence.
  • A program that appears to work can still contain UB.
  • Build and test with -fsanitize=address,undefined and treat every report as a bug.
