The Call Stack, Tasks & Microtasks

The event loop runs one piece of code at a time, and the order is always the same: the stack empties, then all microtasks run, then the next task starts.

§1The Model

JavaScript has a call stack (the code running now), a task queue (timers, I/O, UI events), and a microtask queue (promise reactions, queueMicrotask). The loop takes one task, runs it to completion, drains the entire microtask queue, may render, then takes the next task. Code is never interrupted midway.

  • Tasks (macrotasks): setTimeout, setInterval, DOM events, message events, I/O callbacks.
  • Microtasks: .then/.catch/.finally callbacks, code after await, queueMicrotask, MutationObserver.
  • After every task, *all* microtasks run — including ones queued by other microtasks — before anything else.

§2Predicting the Order

This classic snippet shows the rule. Synchronous code first, then microtasks, then the next task — even with a delay of 0.

console.log("A");
setTimeout(() => console.log("B (task)"), 0);
Promise.resolve().then(() => console.log("C (microtask)"));
queueMicrotask(() => console.log("D (microtask)"));
console.log("E");
// A, E, C (microtask), D (microtask), B (task)

Everything inside an async function before the first await runs synchronously. The code after await is a microtask continuation.

async function f() {
  console.log("1 sync");
  await null;
  console.log("3 after await");     // microtask
}
f();
console.log("2 sync, after f() returned");
// 1, 2, 3

§3Why It Matters

Because the loop only moves on when the stack is empty, a long synchronous loop blocks timers, clicks, and rendering. And because microtasks drain completely, a promise chain that keeps queueing microtasks can starve the page — nothing else gets to run.

setTimeout(() => console.log("timer"), 0);

function spin() { Promise.resolve().then(spin); }  // microtask forever
// spin();   // the timer never fires, and the page freezes

const start = Date.now();
while (Date.now() - start < 2000) {}               // blocks everything for 2s

A setTimeout delay is a *minimum*, not a guarantee. The callback runs only after the delay has passed and the stack is clear.

The one rule Stack empties → run all microtasks → (render) → next task. If you remember only this, you can predict most async-ordering puzzles.

§4Common Mistakes

MistakeWhat HappensFix
Expecting setTimeout(fn, 0) to run immediatelyIt runs after the current code and all microtasksUse queueMicrotask for "as soon as the stack clears"
Queueing microtasks recursivelyStarves timers, input, and renderingSchedule recurring work with a task (setTimeout)
Assuming await yields to the browser for renderingOnly microtasks run; the page does not repaintawait a timer or requestAnimationFrame if you need a paint
Practice
  1. Predict the output of a snippet mixing setTimeout, Promise.then, and await, then run it to check yourself.
  2. Write a loop that processes 10,000 items in a way that blocks the UI, then change it so the page stays responsive.
Key takeaways
  • One task runs to completion; then every microtask runs; then the next task.
  • Promise callbacks and post-await code are microtasks; timers and events are tasks.
  • Blocking the stack — or flooding microtasks — freezes timers, input, and rendering.
