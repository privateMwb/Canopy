npm, package.json & Semver

npm installs your dependencies, package.json describes them, and semantic-version ranges decide which exact versions you actually get.

§1package.json

package.json is the manifest: name, version, entry points, scripts, and dependencies. dependencies ship with your app; devDependencies (test runners, bundlers, types) are only needed to build and test.

{
  "name": "my-api",
  "version": "1.0.0",
  "type": "module",
  "engines": { "node": ">=20" },
  "scripts": {
    "dev": "node --watch src/server.js",
    "test": "node --test",
    "build": "tsc"
  },
  "dependencies": { "express": "^4.19.2" },
  "devDependencies": { "typescript": "^5.4.0" }
}
# npm install express            # add a dependency
# npm install -D vitest          # add a dev dependency
# npm run dev                    # run a script
# npm ci                         # clean, exact install from the lockfile (use in CI)
# npx tsc --noEmit               # run a locally installed binary

§2Semantic Versioning

Versions are MAJOR.MINOR.PATCH. By convention: a patch fixes bugs, a minor adds features compatibly, and a major may break things. Ranges in package.json say which upgrades you accept automatically.

"^4.19.2"   // >=4.19.2 <5.0.0  — minor and patch updates (the default)
"~4.19.2"   // >=4.19.2 <4.20.0 — patch updates only
"4.19.2"    // exactly this version
"*"         // anything — avoid
"^0.3.1"    // for 0.x, ^ allows only patch changes: >=0.3.1 <0.4.0

Semver is a promise by maintainers, not a guarantee; breaking changes still slip into minors. That is what lockfiles are for.

Commit the lockfile package-lock.json pins the exact version of every direct and transitive dependency. Commit it, and use npm ci in CI and deploys so every environment installs identical code.

§3Common Mistakes

MistakeWhat HappensFix
Not committing package-lock.jsonDifferent machines resolve different versionsCommit it; install with npm ci in CI
Putting test tools in dependenciesBloats production installsUse npm install -D
Using * or latest as a versionAny release can break your buildUse a caret range and a lockfile
Practice
  1. Create a project with npm init -y, add one dependency and one dev dependency, and add scripts for dev and test.
  2. Explain what versions ^1.4.2, ~1.4.2, and ^0.4.2 allow, then confirm with npm view <pkg> versions.
Key takeaways
  • package.json lists dependencies, dev dependencies, and scripts.
  • ^ allows minor and patch updates, ~ allows patches only; 0.x is stricter.
  • Commit the lockfile and use npm ci for reproducible installs.
