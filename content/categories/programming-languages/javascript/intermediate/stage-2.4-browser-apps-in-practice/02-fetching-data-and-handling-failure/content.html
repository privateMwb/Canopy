Fetching Data & Handling Failure

Every request is in one of several states — loading, success, error, or stale — and a UI that handles only the success case is broken the first time the network misbehaves.

§1The States of a Request

Model the request explicitly. A discriminated shape makes impossible states impossible, and forces you to render something for every case — including *empty*.

function useData(url) {
  const [state, setState] = useState({ status: "loading" });

  useEffect(() => {
    const controller = new AbortController();
    setState({ status: "loading" });
    fetch(url, { signal: controller.signal })
      .then((r) => { if (!r.ok) throw new Error(`HTTP ${r.status}`); return r.json(); })
      .then((data) => setState({ status: "success", data }))
      .catch((error) => { if (error.name !== "AbortError") setState({ status: "error", error }); });
    return () => controller.abort();          // cleanup: no stale responses after unmount/url change
  }, [url]);

  return state;
}

§2Caching, Staleness, and Retries

Fetching on every render or mount wastes bandwidth and flashes spinners. A cache serves the last result immediately, then revalidates in the background (stale-while-revalidate). Libraries like TanStack Query and SWR implement caching, deduping, and retries so you don't write them by hand.

import { useQuery } from "@tanstack/react-query";

function Profile({ id }) {
  const { data, error, isPending, isFetching, refetch } = useQuery({
    queryKey: ["user", id],                   // the cache key
    queryFn: () => getJson(`/api/users/${id}`),
    staleTime: 60_000,                        // fresh for a minute: no refetch
    retry: 2,                                 // retry transient failures with backoff
  });
  if (isPending) return <Skeleton />;
  if (error) return <ErrorMessage onRetry={refetch} />;
  return <Card user={data} refreshing={isFetching} />;
}

§3Handling Failure Well

Retry only what's safe to retry (idempotent reads, or writes with an idempotency key), back off between attempts, and give up. Tell the user what happened and what they can do. Distinguish *can't reach the server* from *the server said no*.

async function fetchWithRetry(url, { retries = 3, signal } = {}) {
  for (let attempt = 0; ; attempt++) {
    try {
      const res = await fetch(url, { signal });
      if (res.status >= 500 && attempt < retries) throw new Error("server error");
      return res;                              // 4xx are the caller's problem: don't retry
    } catch (e) {
      if (e.name === "AbortError" || attempt >= retries) throw e;
      await new Promise((r) => setTimeout(r, 2 ** attempt * 300 + Math.random() * 100));  // backoff + jitter
    }
  }
}

// Optimistic update: show the change now, roll back if it fails
setTodos(next);
try { await api.save(next); } catch { setTodos(previous); toast("Couldn't save — reverted"); }

A good error state names the problem in plain words, keeps the user's input, and offers a retry.

Always render all four For each piece of remote data, decide what shows while loading, on error, when empty, and when success. If any is a blank screen, the app will feel broken in real conditions.

§4Common Mistakes

MistakeWhat HappensFix
Rendering only the success caseBlank page or crash on slow/failed requestsHandle loading, error, and empty explicitly
Retrying non-idempotent writes blindlyDuplicate orders or paymentsRetry only safe requests, or use idempotency keys
Not aborting on unmount or input changeA stale response overwrites newer stateAbort in the effect cleanup
Practice
  1. Wrap a fetch in a hook or function that returns { status, data, error }, and render all three states for a user-profile card.
  2. Add retry with exponential backoff and jitter to a fetch helper, and show a "Retry" button after the final failure.
Key takeaways
  • Model request status explicitly: loading, success, error, and empty.
  • Cache and revalidate (SWR, TanStack Query) instead of refetching blindly; abort stale requests.
  • Retry only safe operations with backoff, and give users clear recovery options.
