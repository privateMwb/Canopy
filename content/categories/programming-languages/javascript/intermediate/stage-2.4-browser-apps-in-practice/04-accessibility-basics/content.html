Accessibility Basics

An accessible page works with a keyboard, a screen reader, and zoom — and most of it comes free from using the right HTML elements.

§1Semantic HTML First

A <button> is focusable, activates with Enter and Space, and is announced as a button. A <div onclick> is none of those until you re-implement all of it badly. Use real elements for what they are: headings in order, lists, <nav>, <main>, <label>, <a href> for navigation and <button> for actions.

<!-- Bad: not focusable, no role, no keyboard support -->
<div class="btn" onclick="save()">Save</div>

<!-- Good -->
<button type="button" onclick="save()">Save</button>

<label for="email">Email</label>
<input id="email" type="email" autocomplete="email" required>

<img src="chart.png" alt="Sales rose 20% from March to June">
<img src="divider.png" alt="">         <!-- decorative: empty alt -->

§2Keyboard and Focus

Everything clickable must be reachable and operable by keyboard, in a logical order, with a visible focus indicator — never outline: none without a replacement. When you open a dialog, move focus into it, keep it there, and return it on close.

button:focus-visible { outline: 3px solid #1D4ED8; outline-offset: 2px; }

const dialog = document.querySelector("dialog");
const opener = document.activeElement;
dialog.showModal();                  // native <dialog> traps focus and handles Escape
dialog.addEventListener("close", () => opener.focus());   // restore focus

// Avoid positive tabindex. tabindex="0" makes something focusable;
// tabindex="-1" makes it focusable by script only (e.g., a heading after navigation).
// After a client-side route change, move focus to the new page's <h1>.

§3ARIA, Sparingly

ARIA adds meaning HTML lacks, but it changes only what assistive technology is *told* — not behavior. The first rule of ARIA: don't use it if a native element does the job. Use it for live announcements and for state of custom widgets.

<button aria-expanded="false" aria-controls="menu">Menu</button>
<ul id="menu" hidden>...</ul>

<div role="status" aria-live="polite" id="status"></div>   <!-- announce updates -->

button.addEventListener("click", () => {
  const open = button.getAttribute("aria-expanded") === "true";
  button.setAttribute("aria-expanded", String(!open));
  menu.hidden = open;
});
status.textContent = "3 results found";   // screen readers announce this

/* Also: color contrast >= 4.5:1 for body text; never convey meaning by color alone */

Test with the keyboard alone (Tab, Shift+Tab, Enter, Space, Escape), a screen reader such as VoiceOver or NVDA, and an automated checker like axe or Lighthouse — which catches only a fraction of issues.

Automated tools find ~30% Linters and checkers catch missing alt text and contrast. They can't tell whether the tab order makes sense or a dialog traps focus. Unplug the mouse and use your app.

§4Common Mistakes

MistakeWhat HappensFix
Clickable <div> or <span>Not keyboard-accessible or announced properlyUse <button> or <a href>
outline: none with no replacementKeyboard users can't see where they areStyle :focus-visible instead
Placeholder text as the only labelDisappears when typing; poorly announcedUse a visible <label>
Practice
  1. Navigate one of your own pages using only the keyboard and list every place you get stuck or lose track of focus.
  2. Convert a <div>-based menu button to a real <button> with aria-expanded, and confirm it works with Enter, Space, and Escape.
Key takeaways
  • Native HTML elements provide keyboard support and semantics for free — use them first.
  • Keep focus visible and managed, especially around dialogs and route changes.
  • Use ARIA sparingly, and verify with a keyboard, a screen reader, and automated checks.
