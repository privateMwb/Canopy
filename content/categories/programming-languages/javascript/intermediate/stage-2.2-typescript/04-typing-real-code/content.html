Typing Real Code

Real adoption means configuring the compiler, turning on strict mode, adding type definitions for libraries, and migrating one file at a time.

§1tsconfig and Strict Mode

tsconfig.json controls what TypeScript checks. Turn on strict: it enables strictNullChecks (no accidental null/undefined), noImplicitAny, and several more. These are the checks that catch the bugs types exist to catch.

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,   // arr[i] is T | undefined
    "noEmit": true,                     // a bundler or Node does the emitting
    "skipLibCheck": true,
    "allowJs": true, "checkJs": false   // allow a gradual migration
  },
  "include": ["src"]
}
const el = document.querySelector("#name");   // Element | null
el.value;                                     // Error under strictNullChecks
if (el instanceof HTMLInputElement) el.value; // narrowed: OK

§2Third-Party Types

Packages ship their own types (a types field or .d.ts files) or have community types published as @types/<name>. Install them as dev dependencies. For an untyped package, a one-line declaration is a temporary fix.

// npm install --save-dev typescript @types/node @types/express
// npm install --save-dev @types/lodash

// types/untyped-lib.d.ts   — a stopgap for a package with no types
declare module "untyped-lib";

// A more honest stopgap
declare module "untyped-lib" {
  export function doThing(input: string): number;
}

§3Migrating Gradually

You don't have to convert everything at once. Rename one file from .js to .ts, fix what the compiler finds, repeat — starting with leaf modules and shared utilities. Use JSDoc type comments for files you aren't ready to rename.

// @ts-check
/** @param {number[]} nums @returns {number} */
export function sum(nums) { return nums.reduce((a, b) => a + b, 0); }

// Last-resort escapes — each should be rare, specific, and explained
// @ts-expect-error — library types are wrong here (fails if the error goes away)
badCall();
const x = value as unknown as Target;   // double assertion: a code smell

Prefer @ts-expect-error to @ts-ignore: it fails when the error disappears, so stale suppressions don't pile up.

Strict from day one It's far cheaper to start strict than to turn it on later. For a migration, enable strict for new files or directories first, then widen the net.

§4Common Mistakes

MistakeWhat HappensFix
Leaving strict off "for now"null/undefined bugs and implicit any slip throughEnable strict and fix errors file by file
Scattering as assertions to get green buildsCompiler trust replaced by wishesNarrow with checks or fix the type
Forgetting @types/* for a JS libraryEverything from it is any or an errorInstall the matching @types package
Practice
  1. Create a minimal tsconfig.json with strict on, then run tsc --noEmit on a small project and list the first five errors you see.
  2. Take one .js file, add // @ts-check and JSDoc types, then rename it to .ts and tighten the types.
Key takeaways
  • Enable strict (including strictNullChecks) — it's where most of the value comes from.
  • Install @types/* or bundled types for libraries; use targeted declarations for untyped ones.
  • Migrate incrementally with allowJs, @ts-check, and @ts-expect-error for known exceptions.
