Unions, Narrowing & Generics

Union types describe values that can be one of several shapes, narrowing lets the compiler follow your checks, and generics keep functions reusable without losing type information.

§1Unions and Literal Types

A union A | B means the value is one of them. Combined with literal types, you can model a closed set of states precisely and let the compiler reject everything else.

type Status = "idle" | "loading" | "error";
let s: Status = "idle";
s = "done";                          // Error — not in the union

function format(v: string | number) {
  return v.toFixed(2);               // Error: toFixed doesn't exist on string
}

§2Narrowing and Discriminated Unions

Checks like typeof, instanceof, in, equality, and truthiness narrow a union inside the branch. For object shapes, give each variant a shared literal field (a *discriminant*). The compiler then knows exactly which fields exist in each case — and can warn you when you miss one.

function format(v: string | number) {
  if (typeof v === "number") return v.toFixed(2);   // v: number here
  return v.trim();                                   // v: string here
}

type Result =
  | { status: "ok"; data: string[] }
  | { status: "error"; message: string };

function show(r: Result) {
  switch (r.status) {
    case "ok": return r.data.join(", ");     // r.data is available
    case "error": return r.message;
    default: {
      const _exhaustive: never = r;          // adding a new variant breaks the build here
      return _exhaustive;
    }
  }
}

§3Generics

A generic is a function or type parameterized by another type, so it works for many types while keeping the relationship between input and output. T is just a placeholder name, chosen by inference at each call.

function first<T>(items: T[]): T | undefined {
  return items[0];
}
first([1, 2, 3]);          // number | undefined
first(["a", "b"]);         // string | undefined

type ApiResponse<T> = { data: T; error: null } | { data: null; error: string };

function pick<T, K extends keyof T>(obj: T, key: K): T[K] {   // constrain K to real keys
  return obj[key];
}
pick({ id: 1, name: "Ana" }, "name");   // string
pick({ id: 1 }, "oops");                // Error

Use generics when a type *relates* inputs to outputs. If a type parameter appears only once in a signature, you probably don't need it.

Make impossible states unrepresentable Instead of { loading: boolean; data?: X; error?: Error } (which permits loading: true *and* error), use a discriminated union. Each state then carries exactly the fields that make sense.

§4Common Mistakes

MistakeWhat HappensFix
Optional fields to model states (data?, error?)Invalid combinations compile fineUse a discriminated union keyed by status
Missing a default/exhaustiveness check in a switch over a unionNew variants are silently unhandledAssign to never in the default branch
Over-constraining or over-using genericsHard-to-read signaturesAdd a type parameter only when it links types
Practice
  1. Model a Shape as a discriminated union of circle and rectangle, and write area(shape) with an exhaustiveness check.
  2. Write a generic groupBy<T, K extends PropertyKey>(items: T[], key: (item: T) => K) returning Record<K, T[]>.
Key takeaways
  • Unions + literal types describe exactly the values allowed.
  • Narrowing (typeof, in, discriminants) lets the compiler follow your checks; use never for exhaustiveness.
  • Generics preserve the relationship between input and output types.
