Resilient Async Design

Networks fail in the middle of operations, so reliable systems combine timeouts, careful retries, idempotency, and clear failure semantics.

§1Timeouts Everywhere

Without a timeout, a hung dependency becomes a hung request, then a hung server. Every outbound call needs a deadline, and the deadlines should nest: the total budget for the operation must be smaller than what the caller will wait for.

async function callApi(url, { timeoutMs = 3000, signal } = {}) {
  const combined = AbortSignal.any([AbortSignal.timeout(timeoutMs), ...(signal ? [signal] : [])]);
  const res = await fetch(url, { signal: combined });
  if (!res.ok) throw Object.assign(new Error(`HTTP ${res.status}`), { status: res.status });
  return res.json();
}

// Budget the whole operation, then pass what's left to each step
const deadline = Date.now() + 8000;
const remaining = () => Math.max(0, deadline - Date.now());
await callApi(a, { timeoutMs: remaining() });

§2Retries, Backoff, and Idempotency

Retrying makes transient failures invisible — and makes permanent ones worse if done badly. Retry only transient errors (network failures, 502/503/504, 429 honoring Retry-After), use exponential backoff with jitter, cap attempts, and never retry a non-idempotent operation unless the server can deduplicate it. An idempotency key lets a server recognize a repeated request and return the original result instead of charging twice.

async function retry(fn, { retries = 4, base = 200, max = 5000, shouldRetry = isTransient } = {}) {
  for (let attempt = 0; ; attempt++) {
    try { return await fn(attempt); }
    catch (err) {
      if (attempt >= retries || !shouldRetry(err)) throw err;
      const delay = Math.min(max, base * 2 ** attempt) * (0.5 + Math.random() / 2);  // jitter
      await new Promise((r) => setTimeout(r, delay));
    }
  }
}
const isTransient = (e) => !e.status || [429, 502, 503, 504].includes(e.status);

const key = crypto.randomUUID();                    // same key on every retry of ONE logical action
await retry(() => fetch("/payments", {
  method: "POST",
  headers: { "Idempotency-Key": key, "Content-Type": "application/json" },
  body: JSON.stringify(order),
}));

§3Failing Well

When a dependency is down, hammering it makes recovery harder. A circuit breaker stops calling a failing service for a cool-down period and fails fast. Limit concurrency with a bulkhead so one slow dependency can't use all your capacity. Decide per feature whether to degrade (serve cached/partial data) or fail.

class CircuitBreaker {
  #failures = 0; #openUntil = 0;
  constructor(fn, { threshold = 5, coolDownMs = 10_000 } = {}) { Object.assign(this, { fn, threshold, coolDownMs }); }
  async call(...args) {
    if (Date.now() < this.#openUntil) throw new Error("circuit open: failing fast");
    try {
      const result = await this.fn(...args);
      this.#failures = 0;
      return result;
    } catch (err) {
      if (++this.#failures >= this.threshold) this.#openUntil = Date.now() + this.coolDownMs;
      throw err;
    }
  }
}

const results = await Promise.allSettled([getProfile(), getRecommendations()]);   // degrade: recommendations are optional

Retry layering multiplies: three layers that each retry three times produce up to 27 attempts. Retry at one layer, and propagate failure from the rest.

Idempotency is the foundation Retries are only safe on operations that can be repeated without changing the result. Design endpoints and handlers so that doing the same thing twice is harmless, then retries become a simple tool instead of a risk.

§4Common Mistakes

MistakeWhat HappensFix
No timeout on outbound callsA hung dependency hangs your own requestsSet a deadline on every call, with a total budget
Retrying immediately and in lockstepThundering herd hammers the recovering serviceExponential backoff with jitter
Retrying non-idempotent writes without a keyDuplicate charges or recordsSend an idempotency key; dedupe on the server
Practice
  1. Implement retry with backoff and jitter, then test it against a fake function that fails twice before succeeding, asserting call counts and delays.
  2. Design the idempotency-key flow for a POST /orders endpoint: what does the server store, and what does it return on a repeated key?
Key takeaways
  • Put a timeout on every outbound call and budget deadlines end to end.
  • Retry only transient failures, with backoff and jitter, at a single layer — and make writes idempotent.
  • Fail fast with circuit breakers and degrade gracefully when optional dependencies are down.
