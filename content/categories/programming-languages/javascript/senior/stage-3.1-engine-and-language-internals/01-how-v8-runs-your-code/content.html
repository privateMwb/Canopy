How V8 Runs Your Code

V8 doesn't interpret JavaScript line by line forever — it parses, runs bytecode, watches what is hot, and recompiles that code to optimized machine code based on what it has observed.

§1The Pipeline

V8 (Chrome, Node, Deno) turns source into running code in stages. It parses the source into an abstract syntax tree (lazily — functions that haven't run yet are only pre-parsed), then Ignition, the interpreter, generates compact bytecode and runs it immediately. Startup is fast because nothing is optimized yet.

// See what V8 does with a function (Node):
// node --print-bytecode --print-bytecode-filter=add file.js
function add(a, b) { return a + b; }

// Roughly what Ignition generates (a register machine):
//   Ldar a1          ; load argument b into the accumulator
//   Add a0, [0]      ; add argument a; slot [0] records type feedback
//   Return

§2Tiers and Feedback

While running, Ignition collects type feedback: for a + b, were both operands always small integers? When a function gets hot, tiers of compilers take over: Sparkplug (a fast baseline compiler), Maglev (a mid-tier optimizer), and TurboFan (the top-tier optimizer). TurboFan assumes the feedback will keep being true and generates machine code specialized to it.

function sum(arr) {
  let s = 0;
  for (let i = 0; i < arr.length; i++) s += arr[i];   // feedback: arr is packed SMIs
  return s;
}
for (let i = 0; i < 1e5; i++) sum([1, 2, 3, 4]);       // hot -> optimized

// Watch tier-ups and deopts:
// node --trace-opt --trace-deopt file.js

Optimizations are speculative. TurboFan inserts cheap checks ("is this still an integer?") that guard the fast path. If a check fails, V8 deoptimizes — throws away the machine code and returns to the interpreter — and tries again later with new feedback.

What this means in practice Most JavaScript is already fast. Predictable code — stable types, consistent object shapes, small hot functions — is what lets the optimizer's assumptions hold. Write for clarity first; profile before applying engine-level tricks.

§3Common Mistakes

MistakeWhat HappensFix
Micro-benchmarking a function called once or twiceYou measure interpreter startup, not steady-state speedWarm up with many iterations and use a benchmarking tool
Writing "clever" code for the optimizer without profilingHurts readability for no measurable gainProfile; optimize only measured hot paths
Assuming optimization is permanentA type change can trigger deoptimization laterKeep hot-path types stable
Practice
  1. Run a hot function with node --trace-opt --trace-deopt and identify when it was optimized and whether it ever deoptimized.
  2. Benchmark one function when called with only numbers, then after a call passes a string; compare timings.
Key takeaways
  • V8 parses, interprets with Ignition, and recompiles hot code through baseline and optimizing tiers.
  • Optimizations are speculative, based on collected type feedback, and guarded by checks.
  • A failed assumption deoptimizes the function — stable types keep code on the fast path.
