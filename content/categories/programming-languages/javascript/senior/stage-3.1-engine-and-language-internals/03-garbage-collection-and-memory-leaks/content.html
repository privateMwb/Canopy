Garbage Collection & Memory Leaks

JavaScript frees memory automatically, but only when nothing reachable still points to an object — so leaks are almost always something you're accidentally still holding.

§1How the Collector Works

V8's garbage collector frees objects that are unreachable from the roots (globals, the stack, active closures). It is *generational*, based on the observation that most objects die young. New objects go into a small young generation cleaned frequently by a fast copying collector (the *scavenger*). Survivors are promoted to the old generation, cleaned less often by a concurrent, incremental mark-and-sweep (with compaction when needed).

function handle() {
  const big = new Array(1e6).fill(0);   // reachable only inside this call
  return big.length;
}                                       // after return, big is unreachable -> collectable

let cache = new Map();
cache.set("k", new Array(1e6));         // reachable via the global `cache` -> stays alive

// Inspect memory
console.log(process.memoryUsage().heapUsed / 1e6, "MB");   // Node
// node --expose-gc ; global.gc() forces a collection, for experiments only

§2Common Leak Patterns

A leak is memory that stays reachable but is never used again. The usual suspects are always the same handful:

  • Unbounded caches and maps keyed by ids that are never evicted.
  • Forgotten listeners and timers: addEventListener, setInterval, and subscriptions that are never removed.
  • Closures capturing large scope that outlives its usefulness.
  • Detached DOM nodes removed from the page but still referenced from JavaScript.
  • Accidental globals and growing module-level arrays or logs.
// Leak: the interval keeps the closure — and `bigData` — alive forever
function start(bigData) {
  setInterval(() => report(bigData.length), 1000);   // never cleared
}

// Fix: keep the handle, and clean up
const id = setInterval(tick, 1000);
clearInterval(id);

el.addEventListener("click", onClick, { signal: controller.signal });   // abort() removes it
controller.abort();

§3Weak References

WeakMap and WeakSet hold their keys weakly: if nothing else references the key object, it can be collected along with its entry. Use them to attach metadata to objects you don't own without keeping them alive. WeakRef and FinalizationRegistry exist but are unpredictable — prefer explicit cleanup.

const meta = new WeakMap();
function track(node) { meta.set(node, { clicks: 0 }); }   // entry vanishes with node

// A cache that doesn't keep values alive forever:
class WeakCache {
  #m = new Map();
  get(k) { return this.#m.get(k)?.deref(); }
  set(k, v) { this.#m.set(k, new WeakRef(v)); }
}

Weak collections aren't enumerable (no .size, no iteration), precisely because the collector may remove entries at any time.

Not a leak A heap that grows then drops is the GC doing its job. A leak is a sawtooth whose floor keeps rising: after each full collection, memory used is higher than the last time.

§4Common Mistakes

MistakeWhat HappensFix
An in-memory cache with no size limitMemory grows with every unique keyAdd LRU eviction, TTL, or a WeakMap
Adding listeners/intervals without removing themCallbacks and everything they capture stay aliveRemove on teardown; use AbortController signals
Keeping references to removed DOM nodesDetached nodes (and subtrees) can't be freedNull out references when removing elements
Practice
  1. Write a function that leaks via an uncleared setInterval; observe growth in process.memoryUsage() and then fix it.
  2. Replace a Map<HTMLElement, data> with a WeakMap and explain what changes about its lifetime.
Key takeaways
  • Objects are freed when unreachable; V8 uses a generational GC with a fast scavenger for young objects.
  • Leaks are references you forgot: caches, listeners, timers, closures, detached nodes.
  • WeakMap/WeakSet tie metadata to an object's lifetime — but prefer explicit cleanup.
