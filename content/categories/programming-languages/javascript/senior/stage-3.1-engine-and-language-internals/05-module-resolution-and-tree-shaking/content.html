Module Resolution & Tree Shaking

How a module specifier turns into a file differs between Node ESM, CommonJS, and bundlers — and tree shaking only works when your code makes its dead branches provable.

§1How Imports Are Resolved

Relative specifiers (./a.js) map to files. Bare specifiers (lodash) are looked up in node_modules and resolved through the package's exports map (or main as a fallback). Node's ESM requires explicit file extensions and exact paths; CommonJS adds extension guessing and directory index.js lookup. Bundlers and TypeScript each add their own resolution modes, which is why moduleResolution matters.

// package.json of a library
{
  "name": "lib",
  "exports": {
    ".": {
      "import": "./dist/index.mjs",       // used by ESM importers
      "require": "./dist/index.cjs",      // used by CommonJS
      "types": "./dist/index.d.ts"
    },
    "./utils": "./dist/utils.mjs"          // only these subpaths are importable
  }
}

import lib from "lib";           // -> import condition
require("lib");                  // -> require condition
import x from "lib/internal.js"; // ERR_PACKAGE_PATH_NOT_EXPORTED: not in the map

§2Interop Traps

Mixing systems is where most module errors come from. ESM can import CommonJS (module.exports becomes the default export), but named-import detection from CJS is best-effort. CommonJS require of ESM has historically failed, and the "dual package hazard" — loading both the ESM and CJS builds of one package — creates two separate copies with separate state.

// ESM importing CJS: the safest form
import pkg from "cjs-package";           // module.exports
const { thing } = pkg;                   // destructure after import

// A CJS-only __dirname equivalent in ESM
import { fileURLToPath } from "node:url";
const __filename = fileURLToPath(import.meta.url);

// Dynamic import works from both worlds
const mod = await import("./maybe-esm.mjs");
// "default" confusion: import x from "cjs" may give { default: ... } under some tools — check interop settings

§3Tree Shaking

Tree shaking removes exports that are never used — but only if the bundler can prove it's safe. ESM's static import/export makes unused exports visible. It fails when modules have side effects at load time, when code uses CommonJS, or when exports are accessed dynamically. Library authors declare purity with "sideEffects": false in package.json.

// Shakeable: named ESM imports from a library that's marked side-effect free
import { debounce } from "lodash-es";           // only debounce ends up in the bundle

import _ from "lodash";                         // CJS build: the whole library is included

// Side effects block removal
export const registry = new Map();
registry.set("a", 1);                           // top-level work: can't be dropped safely

// package.json: "sideEffects": false   (or ["./polyfill.js"] for exceptions)
// Verify, don't hope: analyze the bundle (vite-bundle-visualizer, source-map-explorer, esbuild --metafile)

Barrel files (index.js re-exporting everything) can pull in whole directories when a bundler can't prove the unused parts are side-effect free. Import from the specific file in performance-sensitive code.

Check the output Whether tree shaking worked is an empirical question. Look at the bundle analysis; if a library you imported one function from is 70 KB in the output, shaking didn't happen.

§4Common Mistakes

MistakeWhat HappensFix
Importing a deep path not listed in exportsERR_PACKAGE_PATH_NOT_EXPORTEDUse a documented subpath export or ask the maintainer
Importing from a CommonJS build of a library for the browserWhole library bundled; no tree shakingUse the ESM build (lodash-es) with named imports
Top-level side effects in a utility moduleBundler must keep the module even if unusedMove side effects into explicit functions; mark sideEffects accurately
Practice
  1. Create a small package with an exports map providing import and require entry points, and consume it from both a .mjs and a .cjs file.
  2. Bundle a page that imports debounce from lodash versus lodash-es and compare the output sizes with a bundle analyzer.
Key takeaways
  • Resolution differs by system; the exports map is the authoritative entry point for packages.
  • ESM/CJS interop and dual-package state are the main sources of module bugs.
  • Tree shaking needs static ESM and side-effect-free modules — verify with a bundle analysis.
