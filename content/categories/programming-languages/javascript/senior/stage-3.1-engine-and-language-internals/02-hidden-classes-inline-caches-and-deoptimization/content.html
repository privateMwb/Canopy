Hidden Classes, Inline Caches & Deoptimization

V8 makes property access fast by giving objects with the same shape the same hidden class — and code loses that fast path when object shapes and types become unpredictable.

§1Hidden Classes (Shapes)

A JavaScript object is a dynamic dictionary in theory, but V8 doesn't treat it that way. Each object has a hidden class (also called a *shape* or *map*) describing which properties it has and where they sit in memory. Objects created the same way share a hidden class, so obj.x becomes a fixed memory offset instead of a hash lookup.

function Point(x, y) { this.x = x; this.y = y; }
const a = new Point(1, 2);
const b = new Point(3, 4);       // same hidden class as a: fast

const c = { x: 1, y: 2 };
const d = { y: 2, x: 1 };        // different property ORDER -> different hidden class

const e = { x: 1 };
e.y = 2;                         // adding properties transitions the hidden class
delete e.x;                      // delete can push the object into slow dictionary mode

§2Inline Caches

At each property access site (p.x), V8 keeps an inline cache remembering which hidden class it saw and the offset it found. The states matter: *monomorphic* (one shape — fastest), *polymorphic* (2–4 shapes), and *megamorphic* (many shapes — falls back to a slow global lookup).

function getX(p) { return p.x; }

getX({ x: 1, y: 2 });
getX({ x: 3, y: 4 });            // monomorphic: always the same shape

getX({ x: 1 });
getX({ x: 1, z: 9 });
getX({ a: 0, x: 5 });            // more shapes -> polymorphic, then megamorphic

// A function handling many different object shapes is the usual megamorphic culprit:
// keep hot functions fed with objects built the same way.

§3Writing Shape-Friendly Code

You don't need to think about this everywhere — only in hot paths that profiling has pointed at. The guidelines are simple: initialize all properties in the constructor, in the same order; don't add or delete properties later; keep arrays holding one element type.

class Particle {
  constructor(x, y) {
    this.x = x; this.y = y;
    this.vx = 0; this.vy = 0;       // all fields set up front, same order
    this.active = true;             // not added later
  }
}

const arr = [1, 2, 3];              // packed small integers: the most compact, fastest kind
arr.push(1.5);                      // transitions to a double array
arr.push("x");                      // transitions again to a generic array — never goes back
// Avoid holes: new Array(1000) is HOLEY; build with push or Array.from instead

obj.maybe = cond ? value : undefined;   // better than adding the property only sometimes
Verify, don't assume Use --trace-deopt, %HaveSameMap(a, b) (with --allow-natives-syntax), and DevTools profiles to confirm a shape problem exists before restructuring code around it.

§4Common Mistakes

MistakeWhat HappensFix
Adding properties to objects after construction in hot codeMany hidden-class transitions; megamorphic access sitesInitialize every field in the constructor
Using delete on objects in hot pathsMay switch object to slow dictionary modeSet the property to undefined or null instead
Mixing numbers, strings, and objects in one hot arrayArray loses its specialized, fast representationKeep hot arrays homogeneous
Practice
  1. Create two objects with the same properties in a different order and confirm with %HaveSameMap that they have different hidden classes.
  2. Benchmark a loop over 1M objects built consistently versus objects built with randomly omitted properties.
Key takeaways
  • Objects built the same way share a hidden class, turning property reads into fixed offsets.
  • Inline caches are fast for one shape and degrade as an access site sees more shapes.
  • In measured hot paths: consistent construction, no delete, homogeneous arrays.
