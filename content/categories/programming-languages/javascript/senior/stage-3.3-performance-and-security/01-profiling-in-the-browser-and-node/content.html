Profiling in the Browser & Node

Profiling replaces guessing with evidence: a CPU profile shows which functions actually consume the time, and a flame graph makes the answer visible at a glance.

§1The Browser Performance Panel

Open DevTools → Performance, click record, perform the slow interaction, and stop. You get a timeline of main-thread activity, network, frames, and layout. Long tasks are flagged with red corners. Throttle the CPU (4x or 6x) to approximate a mid-range phone — your developer machine hides problems.

// Add your own marks so your code appears on the timeline
performance.mark("render-start");
renderList(items);
performance.mark("render-end");
performance.measure("render list", "render-start", "render-end");
console.log(performance.getEntriesByName("render list")[0].duration);

console.time("sort"); data.sort(cmp); console.timeEnd("sort");
// Prefer performance.now() for timing: monotonic and sub-millisecond

§2Reading a Flame Graph

A flame graph stacks the call stack over time: the x-axis is time (or sample count), the y-axis is call depth, and width is cost. Look for wide boxes. *Self time* is time spent in the function itself; *total time* includes everything it called. Work down from the widest top-level function to the widest child until you reach code you own and can change.

  • Wide and flat on top = a function doing a lot of work by itself — optimize or avoid it.
  • Many narrow identical stacks = a small function called very many times — reduce calls.
  • Tall and thin = deep recursion or framework layers — usually not the problem.
  • Purple/green bars in the browser = layout and paint — likely forced reflows or large DOM.

§3Profiling Node

Node can write a CPU profile, or you can attach Chrome DevTools to it. Use --cpu-prof for a file, or --inspect and open chrome://inspect. In production, use a sampling profiler with low overhead, and profile under realistic load.

# node --cpu-prof app.js            # writes CPU.<date>.cpuprofile; open in DevTools
# node --inspect app.js             # attach Chrome DevTools: Profiler / Memory tabs
# node --prof app.js && node --prof-process isolate-*.log    # V8's built-in tick profiler
# npx autocannon -c 50 -d 20 http://localhost:3000/slow      # generate load while profiling
# npx 0x app.js                     # one-command flame graph

Change one thing, then profile again. Record the before and after numbers — an optimization with no measurement is a guess, and sometimes a regression.

Optimize the right thing Amdahl's law applies: speeding up something that takes 2% of the time can't improve the total by more than 2%. The profile tells you where the other 98% is.

§4Common Mistakes

MistakeWhat HappensFix
Profiling on a fast laptop with no throttlingReal-device bottlenecks are invisibleThrottle CPU and network; test on a real mid-range device
Profiling a development buildIncludes dev-mode checks and unminified frameworksProfile production builds
Optimizing before measuringTime wasted on code that isn't slowProfile, fix the widest bar, re-measure
Practice
  1. Record a Performance profile of a slow interaction with 4x CPU throttling, identify the widest function, and write down its self time.
  2. Run a Node server under autocannon with --cpu-prof, find the hottest function, optimize it, and report requests per second before and after.
Key takeaways
  • Profile first: the Performance panel, --cpu-prof, and --inspect show where time really goes.
  • In a flame graph, width is cost — follow the widest boxes down to code you own.
  • Profile production builds under realistic throttling and load, and re-measure after every change.
