Wildcards, Bounds & Type Erasure

Wildcards let a method accept a family of generic types safely, the PECS rule tells you which wildcard to use, and type erasure explains why some things generics simply can't do.

§1Why List<Integer> Isn't a List<Number>

Generics are invariant: List<Integer> is not a subtype of List<Number>, even though Integer is a Number. If it were, this would compile and corrupt the list:

List<Integer> ints = new ArrayList<>();
// List<Number> nums = ints;          // compile error, and rightly so
// nums.add(3.14);                    // would put a Double into a list of Integers

So a method declared as double sum(List<Number> list) can't be called with a List<Integer>. Wildcards solve this.

§2Upper-Bounded: ? extends T

List<? extends Number> means "a list of some unknown type that is Number or a subtype". You can read elements as Number, but you can't add anything (except null), because the compiler doesn't know the actual element type.

static double sum(List<? extends Number> list) {
    double total = 0;
    for (Number n : list) total += n.doubleValue();     // reading is fine
    return total;
}
sum(List.of(1, 2, 3));            // List<Integer>
sum(List.of(1.5, 2.5));           // List<Double>
// list.add(1);                   // compile error inside sum: unknown type

§3Lower-Bounded: ? super T

List<? super Integer> means "a list of Integer or any supertype of it". You can safely add Integers, because whatever the list holds can accept an Integer. Reading gives you only Object.

static void fillWithInts(List<? super Integer> sink) {
    for (int i = 0; i < 3; i++) sink.add(i);            // writing is fine
    Object o = sink.get(0);                             // reading yields only Object
}
fillWithInts(new ArrayList<Integer>());
fillWithInts(new ArrayList<Number>());
fillWithInts(new ArrayList<Object>());

§4PECS: Producer Extends, Consumer Super

The rule of thumb: if a parameter produces values you read, use extends; if it consumes values you write, use super; if both, use an exact type with no wildcard. The classic example is Collections.copy-style code:

static <T> void copy(List<? extends T> src, List<? super T> dst) {
    for (T item : src) dst.add(item);                   // src produces, dst consumes
}
List<Integer> a = List.of(1, 2);
List<Number> b = new ArrayList<>();
copy(a, b);                                              // works: Integer -> Number

Comparators show the same idea: Comparator<? super T> accepts a comparator for any supertype of T, so a Comparator<Object> can sort Strings. An unbounded List<?> means "a list of anything", useful for methods that don't care about the element type, such as printing the size. Prefer a named type parameter instead when you need to relate types (<T> void swap(List<T> l, ...)).

§5Type Erasure

Generics exist at compile time. The compiler checks them, inserts casts, then erases the type arguments, so at runtime a List<String> and a List<Integer> are both just List. This kept old code compatible, and it has consequences.

List<String> a = new ArrayList<>();
List<Integer> b = new ArrayList<>();
System.out.println(a.getClass() == b.getClass());       // true

// if (obj instanceof List<String>) { }                  // illegal: type argument erased
// T t = new T();                                        // illegal: T is unknown at runtime
// T[] arr = new T[10];                                  // illegal: generic array creation
// static T field;                                       // illegal: T belongs to instances

Workarounds: pass a Class<T> token (clazz.getDeclaredConstructor().newInstance()), pass a Supplier<T> or IntFunction<T[]>, or capture a generic type with a subclass trick (as libraries like Jackson's TypeReference do). Two overloads that differ only in generic arguments have the same erasure and won't compile. Mixing raw types with generics causes heap pollution: a ClassCastException at a place far from the real mistake.

Get and Put Principle ? extends is for getting values out; ? super is for putting values in. If you try to do both with one wildcard, the compiler will stop you, and that is the compiler telling you to use an exact type.

§6Common Mistakes

MistakeWhat HappensFix
Writing List<Number> parameters for read-only methodsCallers with List<Integer> can't use itUse List<? extends Number>
Trying to add to a List<? extends T>Compile errorUse ? super T for writing, or an exact type
Using ? super and expecting typed readsYou only get ObjectUse ? extends for reading
Writing new T() or new T[n]Compile error, due to erasurePass a Supplier<T> or Class<T>
Checking instanceof List<String>Compile errorCheck against List<?> and inspect elements
Mixing raw and generic typesUnchecked warnings, then a distant ClassCastExceptionNever use raw types; fix warnings rather than suppressing them
Practice
  1. Write static double maxOf(Collection<? extends Number> c) and call it with lists of Integer and Double.
  2. Write static void addDefaults(Collection<? super String> c) and call it with a List<Object>.
  3. Write a generic factory static <T> T[] makeArray(IntFunction<T[]> maker, int n) and use it to build a String[].
Key takeaways
  • Generics are invariant, so use ? extends to read from a family of types and ? super to write into one (PECS).
  • Type arguments are erased at runtime, which rules out new T(), generic arrays, and instanceof with type arguments.
  • Use Class<T> tokens or suppliers to recover runtime type information, and avoid raw types.
