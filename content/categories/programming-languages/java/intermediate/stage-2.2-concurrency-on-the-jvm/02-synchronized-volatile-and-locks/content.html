synchronized, volatile & Locks

When threads share mutable data, you need rules for who may touch it and when changes become visible, and Java gives you synchronized, volatile, and explicit locks, each guaranteeing something different.

§1The Problem: Races and Visibility

Two threads incrementing a shared counter can lose updates, because count++ is really three steps (read, add, write). That is a race condition. A second, subtler problem is visibility: without proper synchronization, one thread may never see another thread's write, because of CPU caches and compiler reordering.

class Counter {
    private int count = 0;
    void inc() { count++; }              // not atomic: two threads can both read 5 and both write 6
    int get() { return count; }
}
// 2 threads x 100,000 inc() calls usually give a total below 200,000

§2synchronized

A synchronized method or block acquires a monitor lock on an object. Only one thread at a time can hold a given lock, and releasing it makes all changes visible to the next thread that acquires the same lock. That gives you both mutual exclusion and visibility.

class SafeCounter {
    private int count = 0;
    synchronized void inc() { count++; }           // locks on 'this'
    synchronized int get() { return count; }       // reads need the lock too, for visibility
}

private final Object lock = new Object();           // a private lock is safer than 'this'
void transfer() {
    synchronized (lock) {
        // critical section: keep it as short as possible
    }
}

The lock is reentrant: a thread already holding it can enter another synchronized block on the same object. Everything that touches the shared data must use the same lock, or the protection means nothing. Locking on a public object, or on a string literal or boxed number, invites unrelated code to contend with you.

§3volatile

A volatile field guarantees visibility and ordering for reads and writes of that one variable, but it does not make compound operations atomic. It is the right tool for a simple flag written by one thread and read by others.

private volatile boolean running = true;
void stop() { running = false; }                    // visible to the worker immediately
void work() { while (running) { doStep(); } }

private volatile int hits;
void bad() { hits++; }                              // still a race: read-modify-write

§4Explicit Locks

java.util.concurrent.locks.ReentrantLock offers what synchronized cannot: attempting the lock without blocking, timing out, and being interruptible, plus separate Conditions and read/write locking. The cost is that you must release the lock yourself, always in a finally.

private final ReentrantLock lock = new ReentrantLock();

void update() {
    lock.lock();
    try {
        // critical section
    } finally {
        lock.unlock();                              // must happen even on exception
    }
}

if (lock.tryLock(100, TimeUnit.MILLISECONDS)) {     // give up instead of waiting forever
    try { /* ... */ } finally { lock.unlock(); }
}

ReentrantReadWriteLock allows many concurrent readers or one writer, which helps for read-heavy data. For the simplest cases, AtomicInteger (next lesson) is better than either.

§5Deadlock

If thread A holds lock 1 and wants lock 2 while thread B holds lock 2 and wants lock 1, both wait forever. Avoid it by always acquiring multiple locks in the same global order, by holding locks for as short a time as possible, and by never calling unknown code (callbacks, overridable methods) while holding a lock.

Visibility and atomicity are different guarantees volatile gives visibility only. synchronized and locks give both visibility and atomicity for the code inside them. Ask which one your problem actually needs.

§6Common Mistakes

MistakeWhat HappensFix
Using volatile for a counterLost updates, because ++ is still three stepsUse AtomicInteger, or synchronized
Synchronizing the writer but not the readerThe reader can see stale valuesUse the same lock for every access
Forgetting unlock() in a finallyOne exception leaves the lock held foreverAlways try { ... } finally { lock.unlock(); }
Locking on this or a string literalUnrelated code can contend on the same lockUse a private final lock object
Acquiring two locks in different ordersDeadlockDefine one global lock order
Calling a callback while holding a lockThe callback may take another lock and deadlockRelease the lock first, or copy the data out
Practice
  1. Write the unsafe Counter, run it with two threads for 100,000 increments each, and observe the wrong total. Fix it with synchronized, then with AtomicInteger.
  2. Write a worker loop that stops via a volatile boolean, then remove volatile and see whether it still stops (it may not).
  3. Construct a deliberate deadlock with two locks and two threads, then fix it by ordering the locks.
Key takeaways
  • Shared mutable state needs both mutual exclusion and visibility.
  • synchronized and locks provide both; volatile provides visibility only and doesn't make x++ atomic.
  • Always release locks in finally, keep critical sections small, and acquire multiple locks in a fixed order.
