java.util.concurrent

The java.util.concurrent package provides ready-made, well-tested building blocks, so you rarely need to write your own locking for common patterns.

§1Concurrent Collections

Ordinary collections like HashMap and ArrayList are not thread-safe. Wrapping them with Collections.synchronizedMap locks every call but doesn't make compound operations (check-then-act) safe. The concurrent collections are designed for multi-threaded access.

ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();
counts.merge("apple", 1, Integer::sum);              // atomic increment
counts.computeIfAbsent("pear", k -> expensive(k));   // atomic: computed once per key
counts.putIfAbsent("fig", 0);

if (!counts.containsKey("x")) counts.put("x", 1);    // BUG: another thread can insert between the two calls
counts.putIfAbsent("x", 1);                          // correct: one atomic step

CopyOnWriteArrayList<Listener> listeners = new CopyOnWriteArrayList<>();
// safe to iterate while others add; each write copies the array, so use for read-heavy, rare-write lists

Individual operations on a ConcurrentHashMap are atomic, but a sequence of separate calls isn't, so use the atomic compound methods (merge, compute, putIfAbsent). Also note that ConcurrentHashMap forbids null keys and values.

§2Atomics

AtomicInteger, AtomicLong, AtomicReference, and friends provide lock-free atomic updates using CPU compare-and-swap instructions. For counters under heavy contention, LongAdder scales better than AtomicLong.

AtomicInteger hits = new AtomicInteger();
hits.incrementAndGet();
hits.addAndGet(5);
hits.compareAndSet(6, 100);                          // set only if the current value is 6
hits.updateAndGet(x -> Math.min(x, 50));

LongAdder total = new LongAdder();                   // better for many writers, occasional reads
total.add(3);
long sum = total.sum();

§3Producer-Consumer with Blocking Queues

A BlockingQueue lets threads hand work to each other. put blocks when full and take blocks when empty, which gives you natural backpressure: a fast producer is slowed down to the consumer's pace.

BlockingQueue<String> queue = new ArrayBlockingQueue<>(100);     // bounded: always prefer this

Thread producer = new Thread(() -> {
    try { for (int i = 0; i < 1000; i++) queue.put("job-" + i);   // blocks when full
          queue.put("DONE"); }                                    // poison pill to signal the end
    catch (InterruptedException e) { Thread.currentThread().interrupt(); }
});
Thread consumer = new Thread(() -> {
    try {
        for (String job; !(job = queue.take()).equals("DONE"); ) process(job);
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
});

offer and poll with a timeout let you give up instead of blocking forever. An unbounded LinkedBlockingQueue can eat all your memory if consumers fall behind.

§4Coordination Tools

CountDownLatch ready = new CountDownLatch(3);       // one-shot: wait until 3 events occur
// workers call ready.countDown(); the coordinator calls ready.await();

Semaphore permits = new Semaphore(5);               // allow at most 5 concurrent users
permits.acquire(); try { callRateLimitedApi(); } finally { permits.release(); }

CyclicBarrier barrier = new CyclicBarrier(4);       // N threads wait for each other, reusable

Prefer these higher-level tools to wait/notify, which are easy to get wrong.

Atomic methods, not atomic calls Every method on a concurrent map is thread-safe by itself, but two calls in a row are not. If your logic is "check, then act", find the single atomic method that does both.

§5Common Mistakes

MistakeWhat HappensFix
Using HashMap from multiple threadsLost entries, corrupted state, or even infinite loops in old JDKsUse ConcurrentHashMap
containsKey then put on a concurrent mapRace: two threads both insertUse putIfAbsent, computeIfAbsent, or merge
An unbounded queue between fast producers and slow consumersMemory grows until the process diesUse a bounded ArrayBlockingQueue
Using CopyOnWriteArrayList for write-heavy dataEach write copies the whole arrayUse it only for read-mostly lists
Forgetting a stop signal for consumer threadsConsumers block forever on take()Use a poison pill, or interrupt the threads
Practice
  1. Count word frequencies across several files in parallel, using a thread pool and a shared ConcurrentHashMap with merge.
  2. Build a producer and two consumers connected by a bounded ArrayBlockingQueue. Make the consumers slower and watch the producer block.
  3. Use a Semaphore(3) to limit how many of ten tasks run at the same time, and log the concurrency.
Key takeaways
  • Use ConcurrentHashMap and its atomic compound methods; plain collections are not thread-safe.
  • Atomics provide lock-free single-variable updates, and LongAdder suits heavy contention.
  • Bounded blocking queues give backpressure, and latches, semaphores, and barriers coordinate threads without wait/notify.
