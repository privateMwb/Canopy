CompletableFuture

CompletableFuture lets you describe a chain of asynchronous steps, with error handling, so the result of one step feeds the next without any thread sitting blocked waiting for it.

§1From Future to CompletableFuture

A plain Future can only be polled or blocked on with get(). A CompletableFuture<T> is a future you can attach continuations to, so you say what should happen when the result arrives.

ExecutorService io = Executors.newFixedThreadPool(8);

CompletableFuture<String> user = CompletableFuture.supplyAsync(() -> fetchUser(42), io);

CompletableFuture<Void> done = user
    .thenApply(u -> u.toUpperCase())                 // transform the result
    .thenAccept(u -> System.out.println("got " + u)); // consume it

String blocking = user.join();                        // like get(), but throws unchecked exceptions

supplyAsync runs a task that returns a value; runAsync runs one that doesn't. Always pass your own executor for blocking work: without one, tasks run on the shared ForkJoinPool.commonPool(), which is sized for CPU-bound work and is easily starved by blocking calls.

§2Composing Steps

The key methods differ by what the function returns. This mirrors map and flatMap.

MethodUse when the next step...
thenApply(f)is a plain function: T -> U
thenCompose(f)itself returns a CompletableFuture (like flatMap)
thenCombine(other, f)needs the results of two independent futures
thenAccept / thenRunonly has a side effect
CompletableFuture<Order> order = CompletableFuture
    .supplyAsync(() -> fetchUser(42), io)
    .thenCompose(u -> CompletableFuture.supplyAsync(() -> fetchLastOrder(u), io));   // sequential, dependent

CompletableFuture<Price> price = supplyAsync(() -> priceFor(id), io);
CompletableFuture<Stock> stock = supplyAsync(() -> stockFor(id), io);
CompletableFuture<String> summary = price.thenCombine(stock, (p, s) -> p + " / " + s);   // run in parallel

To wait for many futures, use allOf (completes when all finish) or anyOf (first to finish). allOf returns CompletableFuture<Void>, so collect the results from the individual futures afterward.

List<CompletableFuture<Page>> pages = urls.stream()
    .map(u -> CompletableFuture.supplyAsync(() -> download(u), io)).toList();
CompletableFuture.allOf(pages.toArray(CompletableFuture[]::new)).join();
List<Page> all = pages.stream().map(CompletableFuture::join).toList();

§3Error Handling and Timeouts

If a stage throws, the exception travels down the chain and later thenApply stages are skipped. Handle it with exceptionally, handle (both result and error), or whenComplete (observe without changing). Exceptions are usually wrapped in a CompletionException.

CompletableFuture<String> safe = supplyAsync(() -> riskyCall(), io)
    .exceptionally(ex -> "fallback")                 // recover with a default
    .orTimeout(2, TimeUnit.SECONDS);                 // fail with TimeoutException if too slow

CompletableFuture<Integer> both = supplyAsync(() -> compute(), io)
    .handle((value, ex) -> ex != null ? -1 : value);

completeOnTimeout(default, 2, SECONDS) supplies a value instead of failing. Cancelling a CompletableFuture does not interrupt the underlying running task.

§4Avoiding Blocked Pools

The usual pitfall is calling join() or get() inside a task running on the same pool, which can use up all the threads waiting on work that is queued behind them, so nothing ever finishes. Keep the chain asynchronous, using thenCompose rather than blocking in the middle, and block only at the very edge of your program. Also, thenApply runs on whichever thread completed the previous stage; use the ...Async variants with an executor if a continuation is slow.

Async is not the same as parallel A chain of thenApply steps runs one after another; the benefit is that no thread waits while a step is pending. Parallelism comes from starting independent futures and combining them.

§5Common Mistakes

MistakeWhat HappensFix
Using thenApply with a function returning a CompletableFutureA nested CompletableFuture<CompletableFuture<T>>Use thenCompose
Running blocking I/O on the common poolThe shared pool stalls, and unrelated work slows downSupply a dedicated executor
Calling join() inside a pool taskThread starvation and deadlockCompose with thenCompose, and block only at the edge
Ignoring exceptionsFailures are silent unless something calls join()Add exceptionally, handle, or whenComplete
Expecting cancel(true) to stop the taskThe task keeps runningBuild cooperative cancellation into the task
No timeoutA slow dependency hangs the chainUse orTimeout or completeOnTimeout
Practice
  1. Simulate two slow services (500 ms sleeps), call them in parallel with thenCombine, and show that the total time is about 500 ms, not 1,000 ms.
  2. Use allOf to fetch ten items and print the results in order, tolerating a failure in any one with exceptionally.
  3. Write a chain that fails midway and use handle to log the error and return a default.
Key takeaways
  • Chain asynchronous steps with thenApply, thenCompose, and thenCombine instead of blocking.
  • Handle errors explicitly with exceptionally or handle, and add timeouts.
  • Use a dedicated executor for blocking work, and never block pool threads waiting on the same pool.
