Configuration, Logging & Packaging

A service has to run unchanged in development, staging, and production, which means externalized configuration, useful structured logs, and a build that produces one runnable artifact.

§1Externalized Configuration and Profiles

Code should not change between environments; configuration should. Spring Boot reads settings from several places in a defined order, with later, more specific sources overriding earlier ones: defaults packaged in application.yml, then profile-specific files, then environment variables, then command-line arguments.

# application.yml (defaults)
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/app
    username: app
app:
  feature-x: false
---
spring:
  config:
    activate:
      on-profile: prod
app:
  feature-x: true
SPRING_PROFILES_ACTIVE=prod \
SPRING_DATASOURCE_PASSWORD=$(cat /run/secrets/db) \
java -jar app.jar --server.port=9000

Environment variables map automatically (SPRING_DATASOURCE_URL overrides spring.datasource.url). Use profiles sparingly, for genuinely different wiring such as a test stub vs. a real client, and prefer plain configuration values for ordinary differences. Never commit secrets; inject them at runtime from environment variables or a secrets manager.

§2Logging

Log through an abstraction (SLF4J, with Logback as Boot's default), not System.out. Use levels deliberately: ERROR for failures needing attention, WARN for recoverable oddities, INFO for significant business events, DEBUG for diagnosis, TRACE rarely.

private static final Logger log = LoggerFactory.getLogger(OrderService.class);

log.info("order placed id={} customer={} total={}", order.id(), order.customer(), order.total());
log.debug("pricing details: {}", details);              // placeholders avoid building the string if disabled
log.error("payment failed for order {}", orderId, ex);   // pass the exception LAST to get the stack trace

Use {} placeholders rather than string concatenation, and pass the exception as the final argument so the stack trace is logged. Never log passwords, tokens, or full personal data. In production, emit structured logs (JSON, with fields like orderId and a request or trace id) so a log platform can filter and aggregate them; recent Spring Boot versions can do this with a simple property. Use MDC (a per-thread context map) to attach a correlation id to every log line within a request.

MDC.put("requestId", requestId);
try { chain.doFilter(req, res); } finally { MDC.clear(); }

Also set log levels per package in configuration (logging.level.com.example=DEBUG), so you can turn on detail without redeploying.

§3Packaging

mvn package or ./gradlew bootJar produces an executable jar (a "fat jar") containing your classes and all dependencies, runnable with one command.

./mvnw -DskipTests package
java -jar target/app-1.0.0.jar

Production deployments commonly use a container image. Boot can build one without a Dockerfile using Cloud Native Buildpacks (./mvnw spring-boot:build-image), or you can write a Dockerfile; a layered jar and a multi-stage build keep rebuilds fast, because dependencies change less often than your code.

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY target/app-1.0.0.jar app.jar
USER 1000
ENTRYPOINT ["java", "-jar", "app.jar"]

Run as a non-root user, use a slim JRE base image, and expose health endpoints (Actuator's /actuator/health) so the platform can check readiness and liveness. Handle shutdown gracefully (server.shutdown=graceful) so in-flight requests finish when the container receives a stop signal.

Build once, configure everywhere The same artifact should run in every environment, with only environment variables and mounted secrets differing. If you rebuild per environment, you are no longer testing what you ship.

§4Common Mistakes

MistakeWhat HappensFix
Committing passwords or API keys in config filesSecrets leak through version controlSupply secrets through env vars or a secrets manager
Building a different artifact per environmentWhat you test isn't what you deployBuild once and externalize configuration
Using System.out.println for loggingNo levels, no routing, no structureUse SLF4J with placeholders
Logging "failed: " + e.getMessage()The stack trace is lostPass the exception as the last argument
Logging sensitive dataCompliance and security incidentsRedact or omit secrets and personal data
Running the container as root with no health checkA larger attack surface and no readiness signalUse a non-root user and health endpoints
Many overlapping profilesConfusing, untested combinationsUse few profiles, and plain config for simple differences
Practice
  1. Add a prod profile that changes one setting, then run the jar with the profile selected through an environment variable.
  2. Add a log statement with placeholders and an exception, and confirm the stack trace appears. Then add a request-id via MDC.
  3. Build a container image (with Buildpacks or a Dockerfile) and run it, overriding the database URL with an environment variable.
Key takeaways
  • Externalize configuration through profiles and environment variables, and never commit secrets.
  • Log with SLF4J placeholders and include the exception, prefer structured logs, and attach correlation ids.
  • Package as one executable jar or container image, run as non-root, and expose health checks.
