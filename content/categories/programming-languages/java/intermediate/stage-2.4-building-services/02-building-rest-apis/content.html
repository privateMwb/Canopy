Building REST APIs

A well-built REST controller maps HTTP to your code, validates input at the boundary, and reports failures with the right status codes and a consistent error shape.

§1Controllers and Resources

Model your API around resources (nouns) and use HTTP methods for the verbs: GET reads, POST creates, PUT replaces, PATCH partially updates, DELETE removes.

@RestController
@RequestMapping("/api/books")
class BookController {
    private final BookService service;
    BookController(BookService service) { this.service = service; }

    @GetMapping
    List<BookDto> list(@RequestParam(defaultValue = "0") int page,
                       @RequestParam(defaultValue = "20") int size) {
        return service.list(page, size);
    }

    @GetMapping("/{id}")
    BookDto get(@PathVariable long id) { return service.get(id); }       // 404 handled below

    @PostMapping
    ResponseEntity<BookDto> create(@Valid @RequestBody CreateBook req) {
        BookDto created = service.create(req);
        return ResponseEntity.created(URI.create("/api/books/" + created.id())).body(created);   // 201 + Location
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    void delete(@PathVariable long id) { service.delete(id); }
}

Use separate DTOs (data transfer objects) for the request and response rather than exposing your database entities directly. Otherwise a schema change breaks the API, and you risk leaking fields like password hashes. Records make excellent DTOs.

§2Validation

Declare constraints on the input type and add @Valid; Spring rejects bad input before your code runs. Add spring-boot-starter-validation to enable it.

record CreateBook(
    @NotBlank @Size(max = 200) String title,
    @NotBlank String author,
    @Min(1) @Max(5000) int pages,
    @Email String contactEmail) { }

Validation at the boundary guards against malformed input; business rules ("this ISBN already exists") belong in the service layer, because they depend on state.

§3Error Handling

Throw meaningful exceptions from the service layer and translate them into HTTP responses in one place with @RestControllerAdvice. Return a consistent body; Spring supports the standard ProblemDetail (RFC 9457) format.

class BookNotFoundException extends RuntimeException {
    BookNotFoundException(long id) { super("book " + id + " not found"); }
}

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(BookNotFoundException.class)
    ProblemDetail notFound(BookNotFoundException e) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    }
    @ExceptionHandler(MethodArgumentNotValidException.class)
    ProblemDetail invalid(MethodArgumentNotValidException e) {
        var pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "validation failed");
        pd.setProperty("fields", e.getBindingResult().getFieldErrors().stream()
            .collect(Collectors.toMap(FieldError::getField, FieldError::getDefaultMessage, (a, b) -> a)));
        return pd;
    }
}

Never return a stack trace or internal details to clients; log them on the server and send a generic message for unexpected errors.

§4Status Codes

Use them precisely: 200 OK, 201 Created (with a Location header), 204 No Content, 400 malformed or invalid input, 401 not authenticated, 403 authenticated but not allowed, 404 not found, 409 conflict (duplicate, version mismatch), 422 semantically invalid, 429 too many requests, 500 an unexpected server bug. Don't return 200 with an error in the body. Make PUT and DELETE idempotent (repeating them has the same effect as doing them once), and consider an idempotency key for POST operations like payments that a client may retry.

§5Pagination and Evolution

Never return an unbounded list. Accept page/size or a cursor and cap the maximum. Treat the contract as public: adding optional fields is safe; renaming, removing, or changing the meaning of a field breaks consumers, so version the API before you do that.

The controller is thin A controller should translate HTTP in and out: parse, validate, call a service, and shape the response. If it contains business logic or database calls, move them down a layer so they can be tested without HTTP.

§6Common Mistakes

MistakeWhat HappensFix
Returning JPA entities directly from endpointsSchema changes break clients, and sensitive fields can leakUse separate DTOs
Skipping @Valid and checking input manually in each methodInconsistent validationDeclare constraints and handle failures centrally
Returning 200 with {"error": ...}Clients and proxies misread failuresUse the proper 4xx/5xx status
Different error formats from different endpointsClients need special casesUse one @RestControllerAdvice and ProblemDetail
Unbounded list endpointsMemory and latency blow up as data growsPaginate with a maximum page size
Exposing stack traces in responsesInformation disclosureLog server-side, return a generic message
Practice
  1. Build CRUD endpoints for a Book resource with DTO records, validation, 201 with Location, and 404 for missing ids.
  2. Add a @RestControllerAdvice that returns ProblemDetail for validation errors and for your not-found exception.
  3. Add pagination with a maximum size of 100, and test what happens when a client asks for 10,000.
Key takeaways
  • Model resources with the right HTTP verbs, use DTOs, and keep controllers thin.
  • Validate input with annotations at the boundary and translate exceptions centrally into consistent error bodies.
  • Use precise status codes, paginate lists, and treat the API as a public contract.
