Data Access at Scale

At scale, the database is usually the first thing to saturate, so the work is managing connections, keeping transactions short, caching safely, and avoiding contention instead of writing faster queries alone.

§1Connection Pools Are a Bottleneck by Design

A database connection is expensive, and a database can serve only a limited number at once, so applications share a pool (HikariCP in Spring Boot). The pool size is a throttle, and getting it wrong in either direction hurts.

  • Too small: requests queue up waiting for a connection, and latency rises while the database sits idle.
  • Too large: many concurrent queries thrash the database (CPU, I/O, lock contention), making every query slower, and total connections across all service instances can exceed what the database allows.

Counterintuitively, a small pool is often faster than a big one; a common starting point is around (cores x 2) + effective disks connections for the database, and then a per-instance size that, multiplied by the number of instances, stays under that budget.

spring:
  datasource:
    hikari:
      maximum-pool-size: 20          # per instance: multiply by instance count!
      connection-timeout: 2000        # fail fast instead of waiting forever for a connection
      max-lifetime: 1800000

A request that holds a connection while waiting on something slow (an HTTP call, a sleep) wastes the scarcest resource. Watch the pool's metrics: active, idle, and pending connections and the time spent waiting for one. Pending requests with an idle database signal a pool problem; a saturated database signals a query or capacity problem. When many instances overwhelm the database, put a server-side pooler (such as PgBouncer) in front.

§2Transaction Boundaries

A transaction holds locks and a connection for as long as it is open. Keep them as short and narrow as possible: do slow work (remote calls, file I/O, computation) before or after, not inside.

// Bad: holds a transaction and connection across a remote call
@Transactional
void checkout(Order o) {
    orderRepo.save(o);
    paymentClient.charge(o);          // seconds if the gateway is slow, locks held throughout
    orderRepo.markPaid(o);
}
// Better: separate the phases; use a status and idempotent retries or the outbox pattern

Prefer fewer round trips: batch inserts and updates, fetch what you need in one query, and avoid N+1 patterns. Understand your isolation level and which anomalies you accept, and choose optimistic or pessimistic locking deliberately.

§3Contention and Hot Rows

Many transactions updating the same row (a global counter, an account balance, an inventory count) serialize on that row's lock, and throughput collapses no matter how many instances you add. Remedies: optimistic locking with a version column (@Version) and retry on conflict, atomic updates done in SQL (UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0) instead of read-modify-write in Java, splitting a hot counter into several rows summed on read, and redesigning so writes are append-only (insert events rather than updating a total). Always acquire row locks in a consistent order to avoid deadlocks, and retry transactions that the database aborts as deadlock victims.

@Entity class Product {
    @Id Long id;
    @Version long version;            // Hibernate adds "where version = ?" and fails on conflict
    int stock;
}
// Catch OptimisticLockingFailureException and retry, a limited number of times.

§4Caching

A cache removes load from the database and cuts latency, at the price of staleness and a new failure mode. Decide for each piece of data: how stale may it be, and what invalidates it? Common patterns are cache-aside (read the cache, on miss load from the database and populate), TTLs (a time-based expiry), and explicit invalidation on writes. Use a local cache (Caffeine) for per-instance, read-heavy data, and a shared cache (Redis) when instances must agree. Watch for:

  • Stampedes: when a popular key expires and hundreds of requests all hit the database at once. Use request coalescing, jittered TTLs, or refresh-ahead.
  • Unbounded caches, which are memory leaks; always set a maximum size and expiry.
  • Caching errors or empty results unintentionally.
  • Consistency: after a write, other instances may serve the old value until it expires.

Read replicas offer another scaling lever for reads, with the cost of replication lag: a user who writes and then immediately reads from a replica may not see their own write.

§5Measure at the Database

Look at slow query logs, EXPLAIN plans, and statistics such as pg_stat_statements. A missing index or a query that fetches too much frequently beats any application-level tuning. Fix the query, then the pool, then add caching.

Scale is mostly about waiting Under load, requests wait for connections, locks, and I/O. Shorter transactions, fewer round trips, smaller critical sections, and less contention are what raise throughput, usually more than faster code does.

§6Common Mistakes

MistakeWhat HappensFix
A huge connection pool "for performance"Database thrashing and exceeding its connection limit across instancesSize the pool against the database's capacity, then divide by instances
Holding a transaction during a remote callLocks and connections held for secondsDo slow work outside the transaction
Read-modify-write on a hot row in JavaLost updates or heavy lock contentionUse atomic SQL updates or optimistic locking with retries
A cache with no size limit or expiryMemory leak and stale dataSet maximum size and TTL
Cache stampede on a popular keyDatabase spike when it expiresCoalesce requests, add jitter, or refresh ahead
Reading your own write from a lagging replicaUsers see old dataRoute read-after-write to the primary
Caching before fixing a slow queryHides a problem that returns on a missCheck the query plan and indexes first
Practice
  1. Run a load test against a service with a pool of 5, 20, and 100 connections and plot throughput and latency, explaining the shape.
  2. Implement a stock decrement three ways (read-modify-write, @Version with retry, atomic SQL) and compare correctness and throughput under concurrency.
  3. Add a Caffeine cache with a size limit and TTL in front of a slow lookup, and measure the hit rate and what happens when a hot key expires.
Key takeaways
  • The pool size is a throttle: size it for the database, not for the application, and measure pending waits.
  • Keep transactions short, avoid holding them across remote calls, and fix hot-row contention with atomic updates or optimistic locking.
  • Caches trade staleness for speed, so bound them, handle stampedes, and fix slow queries first.
