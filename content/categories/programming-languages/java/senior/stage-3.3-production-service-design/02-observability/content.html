Observability

Observability means being able to ask new questions of a running system from the data it emits, and for a Java service that data is metrics, traces, and structured logs, tied together by shared context.

§1Three Signals, Three Questions

  • Metrics are numbers aggregated over time (request rate, error rate, latency percentiles, heap usage). They are cheap and answer "is something wrong, and since when?"
  • Traces follow one request across services and show where its time went. They answer "where is this request slow?"
  • Logs are discrete events with detail. They answer "what happened in this particular case?"

Each is weak alone. A metric tells you the p99 latency spiked, a trace points at the inventory call, and a log line for that trace shows the exact error. Linking them is the point.

§2Metrics

Instrument what users and operators care about. A good default is the RED method for services (Rate, Errors, Duration of requests) and the USE method for resources (Utilization, Saturation, Errors). In Spring Boot, Micrometer is the metrics facade, and Actuator exposes it to systems such as Prometheus.

@Service
class CheckoutService {
    private final Counter orders;
    private final Timer latency;

    CheckoutService(MeterRegistry registry) {
        this.orders = Counter.builder("orders.placed").tag("channel", "web").register(registry);
        this.latency = Timer.builder("checkout.duration").publishPercentileHistogram().register(registry);
    }
    Order checkout(Cart cart) {
        return latency.record(() -> { Order o = doCheckout(cart); orders.increment(); return o; });
    }
}

Be deliberate about cardinality: every distinct combination of tag values creates a new time series. Tagging by status or endpoint is fine; tagging by userId or orderId can create millions of series and take down your metrics system. Prefer percentiles and histograms over averages, since averages hide the slow tail where users actually suffer. Include JVM metrics (heap, GC pauses, threads, pool sizes) so you can see resource problems next to application ones.

§3Distributed Tracing

A trace is a tree of spans, each a timed operation (an incoming request, a database query, an outgoing call). A trace id is created at the edge and propagated to every downstream service in request headers (the standard is the W3C traceparent header). OpenTelemetry is the vendor-neutral standard for generating and exporting traces, metrics, and logs, and the OpenTelemetry Java agent can instrument common frameworks and libraries automatically with no code change.

java -javaagent:opentelemetry-javaagent.jar \
     -Dotel.service.name=checkout \
     -Dotel.exporter.otlp.endpoint=http://collector:4317 \
     -jar app.jar

Add custom spans around meaningful business operations, and attach useful attributes (but not secrets or high-volume personal data).

Span span = tracer.spanBuilder("price-calculation").startSpan();
try (Scope scope = span.makeCurrent()) {
    span.setAttribute("cart.items", cart.size());
    return calculate(cart);
} catch (Exception e) {
    span.recordException(e);
    span.setStatus(StatusCode.ERROR);
    throw e;
} finally {
    span.end();
}

Tracing everything at full volume gets expensive, so use sampling (a percentage of requests, or tail-based sampling that keeps slow and failed traces).

§4Structured Logging with Correlation

Log as JSON with named fields rather than free text, so a platform can filter and aggregate by field. Include the trace id and span id in every line (OpenTelemetry and Micrometer Tracing put them into the logging context for you), which lets you jump from a trace to the logs for exactly that request, and the reverse. Keep the message constant and the data in fields, and log at boundaries (a request arrived, an order was placed, a dependency failed) rather than inside every loop.

{"ts":"2026-03-04T10:15:02Z","level":"WARN","service":"checkout","traceId":"4bf92f35...","msg":"inventory call slow","durationMs":1840,"sku":"A-17"}

§5Alerts and Dashboards

Alert on symptoms users feel (error rate, latency above an objective), not every internal cause (high CPU alone is rarely a reason to wake someone). Define service level objectives (for example, 99.9 percent of requests under 300 ms) and alert when you are burning through the error budget. Build dashboards in layers: a service overview with the RED signals, then drill-downs for dependencies, JVM, and database. Every alert should link to a runbook describing first steps.

Connect the three signals The most useful thing observability gives you is a path: from a metric alert, to the slow trace, to the log lines of that exact request. Without a shared trace id, you have three disconnected piles of data.

§6Common Mistakes

MistakeWhat HappensFix
Tagging metrics with unbounded values (user id, URL with ids)Cardinality explosion that overloads the metrics systemUse bounded tags such as status, method, route template
Alerting on averagesThe slow tail is hiddenAlert on percentiles and error rates
Logs with no correlation idImpossible to follow a request across servicesInclude trace and span ids in each line
Free-text logs with data in the messageCan't filter or aggregateLog structured fields with a constant message
Not propagating trace context to async workTraces break into disconnected piecesUse instrumented executors and propagate context
Logging secrets or full personal data in spans or logsSecurity and compliance incidentsRedact, hash, or omit sensitive fields
Alerting on every internal metricAlert fatigue, so real alerts are ignoredAlert on user-visible symptoms and SLOs
Practice
  1. Add a Micrometer counter and timer to one endpoint, expose them through Actuator, and read the p95 latency.
  2. Attach the OpenTelemetry Java agent to two small services where one calls the other, and confirm that a single trace spans both.
  3. Switch an application to JSON logs and verify that the trace id in a log line matches the trace in the tracing UI.
Key takeaways
  • Metrics say something is wrong, traces say where, and logs say what; they are most useful when linked by trace ids.
  • Instrument RED and USE signals with bounded cardinality, use percentiles, and prefer structured logs.
  • OpenTelemetry offers vendor-neutral, mostly automatic tracing, and alerts should follow user-visible symptoms and SLOs.
