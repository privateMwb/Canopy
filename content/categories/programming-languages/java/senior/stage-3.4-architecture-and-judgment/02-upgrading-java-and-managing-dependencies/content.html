Upgrading Java & Managing Dependencies

Staying current on Java and on your libraries is a continuous, low-drama practice that costs far less than the occasional emergency upgrade after years of neglect.

§1Why Upgrade Regularly

Running an old JDK means missing security patches, slower garbage collectors and runtime, and newer language features, and it eventually blocks your frameworks, which raise their minimum Java version over time. Because each LTS is supported for years, teams are tempted to stay put, and the longer they wait, the bigger the jump and the riskier it becomes. Upgrading every LTS (and applying quarterly security updates within a version) keeps each step small. Java's strong backward compatibility helps: most application code compiles and runs unchanged on newer versions.

§2What Breaks Between Versions

The usual suspects when moving across LTS versions:

  • Removed or encapsulated JDK internals: code or libraries using sun.misc.Unsafe, sun.* packages, or reflective access into java.* internals. Java 17 made strong encapsulation of internals the default, so libraries that "worked" via --illegal-access in Java 8 and 11 fail until updated or given --add-opens.
  • Removed modules and APIs: Java EE and CORBA modules left the JDK in Java 11 (so JAXB, javax.annotation, and others need explicit dependencies); the Security Manager has been removed; some deprecated methods eventually vanish.
  • The javax to jakarta rename: Jakarta EE 9 and newer (and Spring Boot 3 and newer) use jakarta.* packages, so servlet, persistence, and validation APIs change imports, and every library must match.
  • Behavior changes: default garbage collector, default charset (UTF-8 by default since Java 18), locale data, TLS defaults and disabled algorithms, and stricter parsing.
  • Bytecode level and tooling: older Lombok, ASM-based agents, Mockito, bytecode manipulators, and build plugins may not understand new class file versions.

Read each release's migration guide and release notes, and use jdeps --jdk-internals and jdeprscan to find uses of internal and removed APIs in your own code and jars.

jdeps --jdk-internals --multi-release 21 -cp 'libs/*' app.jar    # which code reaches into JDK internals?
jdeprscan --release 21 app.jar                                   # which deprecated or removed APIs does it call?

§3A Safe Upgrade Process

  1. Upgrade dependencies first, on the current JDK where possible, since most breakage comes from old libraries. Update frameworks, test libraries, and build plugins to versions that support the target JDK.
  2. Build and test on the new JDK in CI while still compiling for the old target (--release 17), and fix failures in small steps.
  3. Then switch the runtime and eventually the --release level, in a staging environment under realistic load.
  4. Compare behavior, not just whether tests pass: startup time, memory, GC logs, latency percentiles, and error rates. A different default GC or JIT can change performance characteristics.
  5. Roll out gradually (a canary or a small share of traffic) with an easy rollback.

Keep CI running against two JDK versions during a transition. And remember toolchain pinning: configure the JDK version explicitly in the build (Gradle toolchains, Maven release), so a developer's machine and CI agree.

§4Managing Dependencies

Every dependency is code you run and a trust relationship you have accepted. A healthy practice:

  • Know what you depend on, including transitive dependencies: mvn dependency:tree, ./gradlew dependencies.
  • Resolve conflicts deliberately. When two libraries want different versions of a third, the build tool silently picks one (Maven: nearest definition wins; Gradle: the highest version), which can produce NoSuchMethodError at runtime. Use a BOM (bill of materials, such as Spring Boot's) or dependency management to pin a coherent set, and Gradle's dependency locking or dependencyInsight to see why a version was chosen.
  • Update continuously and in small steps with automation (Dependabot or Renovate) and a good test suite, which turns upgrades into routine small pull requests rather than annual crises.
  • Scan for vulnerabilities (OWASP Dependency-Check, GitHub advisories, Snyk) and have a plan for how quickly each severity must be fixed, including for transitive ones.
  • Prefer fewer, well-maintained dependencies. Before adding a library, check its maintenance, license, size, transitive footprint, and whether the JDK already does the job.
  • Pin versions for reproducible builds, and use checksums or a repository manager for supply-chain control.
mvn dependency:tree -Dincludes=com.fasterxml.jackson.core        # why is this version on my classpath?
./gradlew dependencyInsight --dependency jackson-databind
mvn versions:display-dependency-updates

§5Reducing Upgrade Risk Over Time

The cheapest upgrades are on codebases that were prepared for them: good automated tests, no reliance on JDK internals, thin use of reflection, dependencies kept near-current, and a build that already runs on the next JDK in CI. Treat "can we build and test on the latest JDK?" as a standing check that you run all the time.

Upgrade early, upgrade small The pain of an upgrade grows faster than linearly with how long you've waited. Smaller, more frequent steps are cheaper, safer, and keep your options open.

§6Common Mistakes

Practice
  1. Run jdeps --jdk-internals and jdeprscan on one of your own applications, and list what each reports.
  2. Add a second CI job that builds and tests on the next JDK while still compiling to the current release, and fix what fails.
  3. Pick one conflicting transitive dependency in a project, find out why that version was chosen, and pin it with a BOM or constraint.
Key takeaways
  • Upgrade every LTS in small steps; breakage comes mostly from removed internals, the javax-to-jakarta rename, and old libraries.
  • Update dependencies first, test on the new JDK in CI, compare real behavior, and roll out gradually.
  • Know your dependency tree, resolve conflicts deliberately, automate updates, and scan for vulnerabilities.
