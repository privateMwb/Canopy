Modules & Large Codebases

As a codebase grows, the structure of its dependencies matters more than any single class, and the goal is to keep dependencies pointing in one direction so that parts can change, build, and be understood independently.

§1Why Structure Matters

In a small project everything can see everything, and that's fine. In a large one, unrestricted visibility means any code can depend on any other, so the dependency graph becomes a tangle: a change in one corner breaks distant code, builds can't be parallelized or cached, a cyclic dependency makes it impossible to extract or test a part alone, and nobody can say which code is safe to delete. The remedy is enforced boundaries: units with a small public surface and explicit, directional dependencies.

§2Multi-Module Builds

Both Maven and Gradle can split a project into modules (subprojects), each built into its own jar, with declared dependencies on the others.

shop/
  pom.xml  (or settings.gradle)
  shop-domain/        pure business rules; depends on nothing internal
  shop-persistence/   depends on shop-domain
  shop-api/           depends on shop-domain
  shop-app/           wires everything; depends on all of the above

The build tool refuses cyclic module dependencies, which makes the boundary real, and it builds only what changed (with Gradle's caching, only what changed and what depends on it). The principle to apply is the dependency rule: dependencies point inward, toward the stable core. The domain doesn't know about the web framework or the database; the outer layers know about the domain. If shop-domain needs to save something, it defines an interface that shop-persistence implements (dependency inversion).

// shop-api/build.gradle
dependencies {
    implementation project(':shop-domain')       // 'implementation' hides it from consumers of this module
    api 'com.fasterxml.jackson.core:jackson-annotations:2.17.0'   // 'api' exposes it in this module's own public API
}

Prefer implementation over api so transitive dependencies don't leak into every consumer's compile classpath. Keep a module's public API small: put most classes in a package that isn't meant for others and, ideally, make that unreachable.

§3The Java Platform Module System (JPMS)

Since Java 9, a module is a named group of packages described by module-info.java. It states which packages it exports and which modules it requires. Unexported packages are inaccessible even through reflection (unless explicitly opened), which gives the language itself strong encapsulation.

module com.shop.domain {
    requires java.logging;
    exports com.shop.domain.model;              // public API
    // com.shop.domain.internal is NOT exported: no one else can touch it
}

module com.shop.persistence {
    requires com.shop.domain;
    provides com.shop.domain.OrderStore with com.shop.persistence.JdbcOrderStore;   // service provider
}

The JDK itself is modularized (java.base, java.sql, and so on), and jlink can build a minimal runtime image containing only the modules an application needs. In practice, many application codebases use JPMS little or not at all: much of the ecosystem still uses the classpath, and frameworks that rely on reflection need packages opens-ed to them. It is most valuable for libraries and platforms that want hard encapsulation and for building trimmed runtimes. For most services, build-tool modules plus package conventions give most of the benefit with less friction.

§4Enforcing Architecture

Boundaries erode unless a tool defends them. Options: separate build modules (the strongest and simplest), ArchUnit tests that fail the build when a rule is broken, and static analysis for cycles.

@AnalyzeClasses(packages = "com.shop")
class ArchitectureTest {
    @ArchTest
    static final ArchRule domainIsIndependent = noClasses().that().resideInAPackage("..domain..")
        .should().dependOnClassesThat().resideInAnyPackage("..persistence..", "..api..", "org.springframework..");

    @ArchTest
    static final ArchRule noCycles = slices().matching("com.shop.(*)..").should().beFreeOfCycles();
}

§5Modular Monolith or Microservices?

A large codebase doesn't have to be split into separate services. A modular monolith, with strict internal modules in one deployable, gives most of the organizational benefits (clear ownership, independent evolution, testability) without the network, deployment, and consistency costs of distributed services. Extract a module to its own service only when it needs independent scaling, release cadence, or fault isolation. If a codebase can't be cleanly split into modules, splitting it into services only turns the tangle into a distributed one, which is much harder to fix.

Architecture is the rules you enforce A diagram that nobody checks will drift. Boundaries only exist if the build or a test fails when someone crosses them.

§6Common Mistakes

MistakeWhat HappensFix
One giant module where everything can see everythingA tangled dependency graph, slow builds, and no ownershipSplit by responsibility into modules with directional dependencies
Cyclic dependencies between modules or packagesCan't extract, test, or understand parts aloneBreak the cycle with an interface or by moving shared code down
Using api everywhere in GradleTransitive dependencies leak into every consumerUse implementation unless the type is part of your public API
A domain module depending on web or database frameworksThe core can't be tested or reused without infrastructureInvert the dependency with interfaces
Adopting JPMS everywhere without a reasonFriction with reflection-heavy frameworks and librariesUse it where strong encapsulation or jlink images pay off
Splitting into microservices to fix a tangled codebaseA distributed tangle that is harder to debugModularize inside the monolith first
Documenting rules but not testing themRules erode silentlyAdd ArchUnit tests or build-enforced modules
Practice
  1. Split a small single-module application into domain, persistence, and app modules, and observe the build failing when you introduce a cyclic dependency.
  2. Write two ArchUnit rules: one forbidding the domain package from depending on the web layer, and one forbidding cycles. Break each on purpose.
  3. Add a module-info.java to a small library, export only its public package, and show that code in another module can't reach the internal package.
Key takeaways
  • Keep dependencies directional, with the stable domain at the center, and let the build refuse cycles.
  • Build-tool modules give most of the benefit; JPMS adds strong encapsulation and jlink where it pays off.
  • Enforce the architecture with modules and ArchUnit tests, and prefer a modular monolith before microservices.
