Enums, Optional & Null Handling

Enums model a fixed set of values safely, and Optional makes "this might be absent" visible in a method's signature instead of waiting to crash with a NullPointerException.

§1Enums

An enum is a type with a fixed set of named instances. It beats strings and magic numbers because a typo is a compile error and a switch over it can be checked for completeness. Enums can have fields, constructors, and methods, and each constant can even override behavior.

public enum Status { PENDING, ACTIVE, CLOSED }

public enum Planet {
    MERCURY(3.303e+23, 2.4397e6),
    EARTH(5.976e+24, 6.37814e6);

    private final double mass, radius;
    Planet(double mass, double radius) { this.mass = mass; this.radius = radius; }
    public double surfaceGravity() { return 6.67300E-11 * mass / (radius * radius); }
}

Status s = Status.valueOf("ACTIVE");        // throws IllegalArgumentException if not found
s.name();                                   // "ACTIVE"
s.ordinal();                                // 1 (avoid persisting this: it changes if you reorder)
for (Status each : Status.values()) { }

String label = switch (s) {
    case PENDING -> "waiting";
    case ACTIVE -> "running";
    case CLOSED -> "done";                  // adding a new constant breaks this until handled
};

Compare enums with ==; there is exactly one instance of each constant. Use EnumMap and EnumSet for fast, compact collections keyed by enums.

§2The Problem with null

null means "no object", and calling a method on it throws NullPointerException. The trouble is that nothing in a method's signature says whether null may come back. Optional<T> is a container that either holds a value or is empty, and it forces the caller to deal with absence.

static Optional<User> findByEmail(String email) {
    User u = db.get(email);                   // may be null
    return Optional.ofNullable(u);            // wraps null into an empty Optional
}

Optional<User> found = findByEmail("ada@example.com");
found.isPresent();                            // true or false
String name = found.map(User::name).orElse("guest");          // transform, with a default
User u = found.orElseThrow(() -> new NoSuchElementException("no such user"));
found.ifPresent(user -> System.out.println(user.name()));
String shout = found.map(User::name).filter(n -> !n.isBlank()).map(String::toUpperCase).orElse("?");

§3Using Optional Well

Optional is designed for return types of methods that may legitimately find nothing. Avoid it elsewhere: not for fields, not for method parameters, and not inside collections (return an empty collection instead of null or Optional<List>). Avoid calling get() without checking; orElseThrow() says the same thing more honestly.

For the rest of your null handling, a few habits go a long way. Validate arguments at the boundary with Objects.requireNonNull(x, "x") to fail fast with a clear message. Return empty collections, never null. Put the literal first in comparisons ("yes".equals(s)). And use Objects.equals(a, b) when either side may be null.

public Order(String id, List<Item> items) {
    this.id = Objects.requireNonNull(id, "id");
    this.items = List.copyOf(items);          // also rejects null elements
}
Absence should be part of the type If a method can return nothing, say so with Optional. If it can't, never return null. Then a reader knows from the signature alone where to expect trouble.

§4Common Mistakes

MistakeWhat HappensFix
Using ordinal() to store or compare enumsReordering constants silently corrupts dataStore name() or an explicit code field
Calling Optional.get() blindlyNoSuchElementException, just like a null crashUse orElse, orElseThrow, or ifPresent
Using Optional for fields and parametersAwkward, and callers can still pass nullUse it only as a return type
Returning null from a method returning a collectionEvery caller needs a null checkReturn an empty collection
Optional.of(maybeNull)NullPointerException right thereUse Optional.ofNullable
Practice
  1. Model a TrafficLight enum with a next() method and a durationSeconds field, and use it in a switch expression.
  2. Write Optional<Integer> parseInt(String s) that returns empty instead of throwing, then chain map and orElse on its result.
  3. Replace one null-returning lookup in your own code with Optional, and update the callers.
Key takeaways
  • Enums give a closed, type-safe set of values, compare with ==, and work well in switch expressions.
  • Optional makes absence explicit in return types; avoid it for fields, parameters, and collections.
  • Fail fast with requireNonNull, and return empty collections rather than null.
