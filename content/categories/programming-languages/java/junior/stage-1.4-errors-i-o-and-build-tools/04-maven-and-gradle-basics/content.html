Maven & Gradle Basics

Maven and Gradle compile your code, download dependencies, run tests, and package a jar from one declarative file, replacing the hand-built javac commands.

§1Why a Build Tool

Once a project has several packages, tests, and third-party libraries, nobody wants to maintain the javac -cp ... command by hand. A build tool gives you a standard layout, dependency management with transitive dependencies resolved for you, repeatable builds from the command line and from CI, and plugins for tests and packaging.

§2Standard Layout

Both tools expect the same directory structure:

my-app/
  pom.xml (Maven)  or  build.gradle (Gradle)
  src/
    main/java/com/example/App.java          production code
    main/resources/                         config files, bundled in the jar
    test/java/com/example/AppTest.java      tests
    test/resources/
  target/ (Maven)  or  build/ (Gradle)      generated output: never commit

§3Maven

Maven describes the project in XML in pom.xml. Each dependency is identified by groupId, artifactId, and version ("coordinates") and is downloaded from Maven Central into a local cache.

<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.example</groupId>
  <artifactId>my-app</artifactId>
  <version>1.0.0</version>
  <properties>
    <maven.compiler.release>21</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>
  <dependencies>
    <dependency>
      <groupId>com.google.code.gson</groupId>
      <artifactId>gson</artifactId>
      <version>2.11.0</version>
    </dependency>
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>5.11.0</version>
      <scope>test</scope>
    </dependency>
  </dependencies>
</project>
mvn compile          # compile src/main
mvn test             # compile and run tests
mvn package          # build target/my-app-1.0.0.jar
mvn clean verify     # delete target/, then build and run all checks

Maven runs a fixed lifecycle (validate, compile, test, package, verify, install, deploy), and running a phase runs every phase before it.

§4Gradle

Gradle uses a Groovy or Kotlin script, which is more flexible and often faster thanks to incremental builds and caching. The same project looks like this:

plugins { id 'java' }

repositories { mavenCentral() }

java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }

dependencies {
    implementation 'com.google.code.gson:gson:2.11.0'
    testImplementation 'org.junit.jupiter:junit-jupiter:5.11.0'
    testRuntimeOnly 'org.junit.platform:junit-platform-launcher'
}

tasks.named('test') { useJUnitPlatform() }
./gradlew build      # compile, test, and package into build/libs/
./gradlew test
./gradlew dependencies

Always use the wrapper (mvnw/gradlew) checked into the repository, so everyone, including CI, builds with the same tool version.

§5Dependencies and Scopes

Declaring a library pulls in the libraries it depends on too (transitive dependencies). Scopes control where a dependency is available: compile or implementation for production code, test/testImplementation for tests only. Pin versions explicitly; a floating version makes builds irreproducible. A plain jar doesn't contain its dependencies, so to run it you need them on the classpath or a "fat jar" built by a plugin.

Commit the wrapper, never the output Check in pom.xml, build.gradle, and the wrapper scripts. Add target/ and build/ to .gitignore. A fresh clone should build with a single command.

§6Common Mistakes

MistakeWhat HappensFix
Files in the wrong directory (such as tests under src/main)The tool ignores them, or ships test code in the jarFollow the standard layout exactly
Committing target/ or build/Huge diffs and stale artifactsAdd them to .gitignore
Using a version range or LATESTDifferent builds on different daysPin exact versions
Running a globally installed Maven or GradleVersion differences between machinesUse ./mvnw or ./gradlew
Expecting mvn package to produce a runnable jar with dependenciesNoClassDefFoundError at startupUse a shade/assembly plugin, or run with the classpath
Practice
  1. Create a Maven or Gradle project with one class and one dependency (such as Gson). Build it and run the produced jar.
  2. Add a test-scope dependency and confirm it is not available to code in src/main.
  3. Delete the build output directory, rebuild from scratch, and note how long it takes with and without the cache.
Key takeaways
  • Maven and Gradle share the same layout and dependency model; the config file differs (XML vs. a script).
  • Dependencies are identified by coordinates, resolved transitively, and limited by scope.
  • Use the wrapper, pin versions, and keep generated output out of version control.
