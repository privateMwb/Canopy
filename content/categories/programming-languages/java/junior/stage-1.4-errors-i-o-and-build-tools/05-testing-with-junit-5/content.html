Testing with JUnit 5

JUnit 5 lets you write small automated tests that run in seconds, so you find out immediately when a change breaks something that used to work.

§1Your First Test

Tests live under src/test/java, mirror the production package, and are ordinary methods marked with @Test. Each test builds a situation, calls the code, and asserts the result.

package com.example;

import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class PriceCalculatorTest {

    @Test
    void appliesTenPercentDiscount() {
        var calc = new PriceCalculator();
        assertEquals(900, calc.discounted(1000, 10));
    }

    @Test
    void rejectsNegativePrice() {
        var calc = new PriceCalculator();
        var ex = assertThrows(IllegalArgumentException.class,
                              () -> calc.discounted(-1, 10));
        assertTrue(ex.getMessage().contains("negative"));
    }
}

Run them with mvn test or ./gradlew test. Tests should be independent, fast, and repeatable: the same result in any order, with no network or shared state unless you are deliberately writing an integration test. Test classes and methods don't need to be public.

§2Assertions

The commonly used assertions are assertEquals(expected, actual) (expected first), assertTrue, assertFalse, assertNull, assertNotNull, assertThrows, and assertAll to group several checks so you see every failure rather than just the first. For floating point, pass a tolerance: assertEquals(0.3, 0.1 + 0.2, 1e-9). Many teams add AssertJ for more readable, fluent assertions.

assertAll("order totals",
    () -> assertEquals(3, order.itemCount()),
    () -> assertEquals(2500, order.totalCents()));

§3Setup, Organization, and Naming

Lifecycle annotations prepare each test: @BeforeEach runs before every test (create fresh objects here), @AfterEach after, and @BeforeAll/@AfterAll once per class (they must be static). Use @DisplayName for readable reports, @Nested classes to group related cases, and @Disabled sparingly with a reason.

class StackTest {
    private Stack<Integer> stack;

    @BeforeEach void setUp() { stack = new Stack<>(); }

    @Nested @DisplayName("when empty")
    class WhenEmpty {
        @Test void popThrows() { assertThrows(EmptyStackException.class, stack::pop); }
        @Test void isEmpty() { assertTrue(stack.isEmpty()); }
    }
}

A good test name says what behavior is being checked, such as rejectsNegativePrice, not test1. Follow arrange, act, assert: set up, call once, then verify.

§4Parameterized Tests

When the same logic should hold for many inputs, a parameterized test avoids copy-pasting. This needs the junit-jupiter-params module, which the junit-jupiter aggregate includes.

@ParameterizedTest
@CsvSource({ "0, 0", "1, 1", "5, 120", "10, 3628800" })
void factorial(int n, long expected) {
    assertEquals(expected, MathUtil.factorial(n));
}

@ParameterizedTest
@ValueSource(strings = { "", " ", "\t" })
void blankIsRejected(String input) {
    assertThrows(IllegalArgumentException.class, () -> Parser.parse(input));
}

Test the edges, not just the happy path: empty, one element, boundary values, null, and error cases. A test you have never seen fail may not be testing anything, so briefly break the code on purpose to confirm the test goes red.

Tests are documentation that runs A well-named test shows exactly how the code is meant to behave, and unlike a comment it fails when it goes out of date.

§5Common Mistakes

MistakeWhat HappensFix
Swapping expected and actual in assertEqualsFailure messages are misleadingAlways pass (expected, actual)
Tests that depend on each other or on orderRandom failures when run singly or in another orderCreate fresh state in @BeforeEach
Testing only the happy pathBugs hide at the edgesAdd empty, null, boundary, and error cases
Asserting several unrelated things in one testThe first failure hides the rest, and the cause is unclearOne behavior per test, or use assertAll
Using Thread.sleep or real clocks in testsSlow, flaky testsInject a clock, or poll with a timeout
Practice
  1. Write tests for a fizzBuzz(int) method, including a parameterized test covering several inputs.
  2. Write a test for a method that should throw on invalid input, and assert on the exception message.
  3. Deliberately introduce a bug in your code and confirm that at least one test fails.
Key takeaways
  • Tests are @Test methods in src/test/java that arrange, act, and assert, and they should be independent and fast.
  • Use lifecycle annotations for setup, @Nested for grouping, and @ParameterizedTest for many inputs.
  • Test edges and failure cases, and check that a test can fail.
