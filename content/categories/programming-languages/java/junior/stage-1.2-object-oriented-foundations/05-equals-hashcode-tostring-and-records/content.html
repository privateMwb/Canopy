equals, hashCode, toString & Records

Every Java object inherits three methods that define how it prints, how it compares, and how it hashes, and records let you get all three correct for simple data classes with one line.

§1The Object Contract

Every class extends Object, which defines toString, equals, and hashCode. The defaults are rarely what you want: toString prints something like Point@1b6d3586, and equals compares identity (==).

Point p = new Point(1, 2);
Point q = new Point(1, 2);
System.out.println(p == q);          // false: different objects
System.out.println(p.equals(q));     // false with the default equals
System.out.println(p);               // Point@1b6d3586

Override equals to define value equality: two objects are equal when their meaningful fields match.

public final class Point {
    private final int x, y;
    public Point(int x, int y) { this.x = x; this.y = y; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point other)) return false;     // also handles null
        return x == other.x && y == other.y;
    }
    @Override public int hashCode() { return java.util.Objects.hash(x, y); }
    @Override public String toString() { return "Point[x=" + x + ", y=" + y + "]"; }
}

§2The Contract Between equals and hashCode

The rules are strict. equals must be reflexive, symmetric, transitive, consistent, and x.equals(null) must be false. And: if two objects are equal, they must return the same hashCode. Hash-based collections like HashMap and HashSet use the hash to choose a bucket, then equals to confirm a match. If you override equals but not hashCode, equal objects land in different buckets and lookups fail.

java.util.Set<Point> set = new java.util.HashSet<>();
set.add(new Point(1, 2));
System.out.println(set.contains(new Point(1, 2)));   // true only if both methods are overridden

Don't use mutable fields in hashCode; changing a field after inserting the object into a HashSet makes it unfindable.

§3Records

A record is a concise, immutable data carrier. The compiler generates the constructor, accessors, equals, hashCode, and toString from the component list.

public record Point(int x, int y) { }

Point p = new Point(1, 2);
p.x();                                   // accessor: x(), not getX()
p.equals(new Point(1, 2));               // true
System.out.println(p);                   // Point[x=1, y=2]

public record Range(int lo, int hi) {
    public Range {                       // compact constructor: validate here
        if (lo > hi) throw new IllegalArgumentException("lo > hi");
    }
    public int length() { return hi - lo; }    // records can have methods
}

Records are shallowly immutable: fields are final, but a record holding a List still lets that list be mutated unless you copy it. They can implement interfaces but cannot extend other classes.

When to reach for a record If a class is just "these fields, compared by value", make it a record. If it has identity, mutable state, or behavior that depends on a lifecycle (like an Account), keep it a normal class.

§4Common Mistakes

MistakeWhat HappensFix
Overriding equals without hashCodeEqual objects behave as different keys in HashMap and HashSetAlways override both together
Using == to compare objectsCompares identityUse equals
Hashing a mutable fieldThe object is lost in a hash set after it changesBase hashCode on immutable fields
Writing equals(Point p) instead of equals(Object o)It overloads rather than overrides, so collections ignore itUse the Object parameter and @Override
Assuming a record deeply protects a List componentCallers can still mutate the listCopy defensively in the compact constructor
Practice
  1. Write a Money class with currency and cents, implementing equals, hashCode, and toString. Test it as a HashMap key.
  2. Rewrite Money as a record and confirm that its behavior is identical.
  3. Insert a mutable object into a HashSet, change a field used in hashCode, and show that contains now fails.
Key takeaways
  • Override equals, hashCode, and toString for value-like classes, and always override the first two together.
  • Equal objects must have equal hash codes, or hash-based collections break.
  • Records generate all three for immutable data and support validation in a compact constructor.
