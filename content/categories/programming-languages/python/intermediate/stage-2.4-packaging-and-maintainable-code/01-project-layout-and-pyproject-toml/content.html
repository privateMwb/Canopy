Project Layout & pyproject.toml

A standard project layout plus one pyproject.toml file declares your package's name, dependencies, and tools in a form every modern Python tool understands.

§1The src Layout

Put importable code in a src/ directory, with tests beside it rather than inside the package.

myapp/
    pyproject.toml
    README.md
    src/
        myapp/
            __init__.py
            cli.py
            core.py
    tests/
        test_core.py

The src layout prevents a common trap: with code at the project root, import myapp works in tests because the current directory is on the path, even if the package is broken once installed. With src/, tests can import your code only after it's installed, which is how users will get it.

§2pyproject.toml

This single TOML file replaces the older setup.py, setup.cfg, and scattered tool configs.

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "myapp"
version = "0.1.0"
description = "Summarize log files."
readme = "README.md"
requires-python = ">=3.10"
license = "MIT"
dependencies = [
    "requests>=2.31",
    "rich>=13",
]

[project.optional-dependencies]
dev = ["pytest>=8", "ruff", "mypy"]

[project.scripts]
myapp = "myapp.cli:main"

[tool.pytest.ini_options]
testpaths = ["tests"]
  • [build-system] says which tool builds the package (hatchling, setuptools, flit, and others all work).
  • [project] holds metadata, and dependencies lists what users need.
  • [project.scripts] creates a command named myapp that calls main() in myapp/cli.py.
  • [tool.*] sections configure tools like pytest, ruff, and mypy.

§3Installing for Development

An editable install links your source into the environment, so changes take effect immediately.

python -m venv .venv && source .venv/bin/activate
python -m pip install -e ".[dev]"
myapp --help            # the script entry point now exists
pytest

§4Versions and Dependency Specifiers

Use ranges for libraries (requests>=2.31,<3) so users can combine your package with others. For applications, you also want exact pins (a lock file) so deployments are reproducible. Libraries declare what they accept; applications pin what they run.

The key insight pyproject.toml separates *what your project is* from *how it's built*. Any compliant tool (pip, uv, build, poetry) can read it, so you're not locked into one workflow.

§5Common Mistakes

MistakeWhat HappensFix
Putting code at the repository root and importing it in testsTests pass against local files but the installed package is brokenUse src/ layout and test an installed copy
Pinning exact versions in a library's dependenciesUsers hit conflicts with their other packagesUse lower bounds and a sensible upper bound
Forgetting requires-pythonInstalls on unsupported versions and fails at runtimeDeclare the minimum version you test
Practice
  1. Convert a script folder of yours to the src layout with a pyproject.toml, and install it with pip install -e ..
  2. Add a [project.scripts] entry and confirm that the command works from any directory.
Key takeaways
  • src/ layout plus pyproject.toml is the standard, tool-neutral project shape.
  • [project] declares metadata and dependencies; [project.scripts] creates commands.
  • Use pip install -e . for development; libraries use ranges, applications use lock files.
