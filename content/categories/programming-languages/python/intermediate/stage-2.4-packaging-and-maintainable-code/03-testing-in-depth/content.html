Testing in Depth

Real code touches files, clocks, and networks, and good tests isolate those dependencies, measure coverage, and stay fast and reliable.

§1Fixtures Beyond the Basics

Fixtures can set up and tear down resources, and widen their scope to share expensive setup.

import pytest, sqlite3

@pytest.fixture(scope="module")          # created once per test file
def db():
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE users (id INTEGER, name TEXT)")
    yield conn                            # tests run here
    conn.close()                          # teardown after the last test

@pytest.fixture
def clean_db(db):
    db.execute("DELETE FROM users")
    return db

Built-ins worth knowing: tmp_path (temporary directory), monkeypatch (temporarily change attributes, env vars, or the working directory), capsys (capture printed output), and caplog (capture log records).

def test_reads_config(tmp_path, monkeypatch):
    cfg = tmp_path / "app.ini"
    cfg.write_text("debug = 1\n")
    monkeypatch.setenv("APP_CONFIG", str(cfg))
    assert load_config().debug is True

§2Mocking

Replace slow or non-deterministic collaborators with fakes using unittest.mock. Patch the name where it is used, not where it's defined.

from unittest.mock import patch, Mock

# weather.py
#   import requests
#   def current_temp(city):
#       return requests.get(f"https://api.example/{city}").json()["temp"]

def test_current_temp():
    fake = Mock()
    fake.json.return_value = {"temp": 21}
    with patch("weather.requests.get", return_value=fake) as get:
        assert current_temp("oslo") == 21
        get.assert_called_once_with("https://api.example/oslo")

def test_network_failure():
    with patch("weather.requests.get", side_effect=ConnectionError):
        with pytest.raises(ConnectionError):
            current_temp("oslo")

Mock sparingly. Over-mocked tests verify your mocks rather than your code. Prefer a fake (a small in-memory implementation) or inject the dependency as a parameter, which needs no patching at all.

§3Parametrization and Markers

@pytest.mark.parametrize("text, expected", [
    ("", 0),
    ("a", 1),
    ("a b  c", 3),
], ids=["empty", "single", "extra-spaces"])
def test_word_count(text, expected):
    assert word_count(text) == expected

@pytest.mark.slow
def test_full_import(): ...

Run subsets with pytest -m "not slow" or pytest -k word_count. Use -x to stop at the first failure and --lf to rerun only the last failures.

§4Coverage

python -m pip install pytest-cov
pytest --cov=myapp --cov-report=term-missing

The report lists lines that never ran. Use it to find untested code, not as a goal: 100% coverage can still miss logic errors, and chasing the number invites meaningless tests. Consider --cov-fail-under=80 in CI as a floor.

§5Testing Properties

For code with many valid inputs, libraries such as Hypothesis generate cases for you and shrink failures to the smallest example, which finds edge cases you wouldn't write by hand.

The key insight If code is hard to test, the design is usually the problem. Passing dependencies in (a clock, a client, a path) makes tests simple and avoids patching altogether.

§6Common Mistakes

MistakeWhat HappensFix
Patching where an object is defined (patch("requests.get")) while the code uses from requests import getThe patch has no effectPatch the name in the module that uses it
Tests that hit the real network or clockSlow, flaky failuresFake the dependency, and inject a time source
Chasing 100% coverageLow-value tests, false confidenceCover meaningful behavior and use the report to find gaps
Practice
  1. Write a test for a function that reads os.environ["API_KEY"] using monkeypatch, including the missing-variable case.
  2. Take a function that calls requests.get, test it with unittest.mock.patch, and then refactor it to accept the client as a parameter and test it without patching.
Key takeaways
  • Fixtures handle setup and teardown with yield; tmp_path and monkeypatch isolate the disk and environment.
  • Mock external boundaries sparingly, patching where the name is used; prefer injecting dependencies.
  • Coverage shows what never ran; it doesn't prove the tests are good.
