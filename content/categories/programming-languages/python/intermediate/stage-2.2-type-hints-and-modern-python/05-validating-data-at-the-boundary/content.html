Validating Data at the Boundary

Type hints don't protect you from bad input, so convert untrusted data into trusted objects once, at the edge of your program.

§1The Boundary Problem

Data arriving from JSON, forms, files, or APIs is just dicts and strings, whatever your annotations claim. If you let it flow inward unchecked, errors surface far from the cause.

import json

raw = json.loads('{"name": "Ana", "age": "thirty"}')
age = raw["age"] + 1          # TypeError, deep inside unrelated code

The fix is to validate and convert once, at the boundary, and use well-typed objects everywhere else.

§2Plain Dataclasses

You can do this by hand with a dataclass and __post_init__, with no dependencies.

from dataclasses import dataclass

@dataclass(frozen=True)
class User:
    name: str
    age: int

    def __post_init__(self):
        if not isinstance(self.age, int) or self.age < 0:
            raise ValueError(f"invalid age: {self.age!r}")
        if not self.name.strip():
            raise ValueError("name is required")

def parse_user(data: dict) -> User:
    return User(name=str(data["name"]), age=int(data["age"]))

This is explicit and fine for small cases, but grows tedious with nested data, optional fields, and error reporting.

§3Pydantic

Pydantic (a third-party library) reads your annotations and validates and converts input, collecting all errors with clear paths.

from pydantic import BaseModel, Field, ValidationError

class Address(BaseModel):
    city: str
    zip_code: str = Field(pattern=r"^\d{5}$")

class User(BaseModel):
    name: str
    age: int = Field(ge=0, le=150)
    email: str | None = None
    address: Address

try:
    user = User.model_validate({"name": "Ana", "age": "31",
                                "address": {"city": "Oslo", "zip_code": "0150"}})
except ValidationError as err:
    print(err)               # which fields failed and why

ok = User.model_validate({"name": "Ana", "age": "31",
                          "address": {"city": "Oslo", "zip_code": "01500"}})
print(ok.age + 1)            # 32: the string "31" was converted to int

By default Pydantic coerces compatible values ("31" becomes 31); use strict mode if you want exact types. These examples use Pydantic v2 (model_validate, model_dump).

§4Choosing a Tool

  • dataclass: internal data that's already trusted; no dependencies.
  • attrs: dataclass-like with validators and converters built in.
  • Pydantic: untrusted external input, nested structures, API schemas, and settings loaded from the environment.

Whichever you pick, the rule is the same: parse, don't validate-and-forget. Return a new, typed object instead of checking a dict and passing the same dict onward.

The key insight Validation belongs at the edge. Once data has become a User, the rest of the code can trust it, and the number of places that can fail on bad input drops to one.

§5Common Mistakes

MistakeWhat HappensFix
Trusting JSON because the function is annotated -> UserAnnotation is a promise, not a checkBuild the object through a validating constructor
Validating deep inside business logicErrors appear far from the source, with unclear messagesValidate once at the entry point
Assuming Pydantic rejects "31" for an int fieldIt silently convertsEnable strict mode when you need exact types
Practice
  1. Write a parse_order(data: dict) function that returns a frozen dataclass and raises ValueError with a clear message for each missing or invalid field.
  2. Define a Pydantic model for a config file with a port (1 to 65535), a host, and a debug flag, and feed it deliberately bad data.
Key takeaways
  • Annotations don't validate; convert untrusted input into typed objects at the boundary.
  • Dataclasses suit small, trusted cases; Pydantic handles nested, external data with full error reporting.
  • Parse once at the edge and pass the typed object inward.
