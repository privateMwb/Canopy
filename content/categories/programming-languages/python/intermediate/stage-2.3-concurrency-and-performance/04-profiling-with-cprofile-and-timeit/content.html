Profiling with cProfile & timeit

Measure where time actually goes before optimizing, because the real bottleneck is almost never where you'd guess.

§1Timing Small Snippets

timeit runs a snippet many times and reports the total, which smooths out noise. It's the right tool for comparing two small alternatives.

import timeit

a = timeit.timeit("sum(x * x for x in range(1000))", number=2000)
b = timeit.timeit("sum([x * x for x in range(1000)])", number=2000)
print(f"generator: {a:.3f}s  list: {b:.3f}s")
python -m timeit -s "data = list(range(1000))" "999 in data"
python -m timeit -s "data = set(range(1000))" "999 in data"

For a quick wall-clock measure around a block, use time.perf_counter(). Run measurements several times and prefer the minimum; the system adds noise, never subtracts it.

§2Profiling a Whole Program

cProfile records how many times each function was called and how long it took.

python -m cProfile -s cumulative script.py | head -20
python -m cProfile -o out.prof script.py        # save for later analysis
import cProfile, pstats

with cProfile.Profile() as pr:
    main()
stats = pstats.Stats(pr).sort_stats("cumulative")
stats.print_stats(10)

Key columns:

ColumnMeaning
ncallsnumber of calls
tottimetime spent in the function itself, excluding subcalls
cumtimetime including everything it called
percallthe above divided by calls

Sort by cumulative to see which high-level operations dominate, and by tottime to find the functions that burn the cycles themselves.

§3Reading the Result

   ncalls  tottime  percall  cumtime  percall filename:lineno(function)
        1    0.002    0.002    4.810    4.810 report.py:12(build_report)
    20000    0.050    0.000    4.700    0.000 report.py:30(find_customer)
 20000000    4.600    0.000    4.600    0.000 report.py:35(<genexpr>)

Here find_customer does a linear scan 20,000 times: the cost sits in a generator expression called twenty million times. The fix is structural (build a dict once), not micro-tuning. Visual tools such as snakeviz display profiles as flame-style charts.

§4A Disciplined Process

  • Write a benchmark or a realistic input first, so you can repeat the measurement.
  • Profile, and fix the largest cost, not the one that looks ugly.
  • Measure again. If the gain isn't real, revert.
  • Stop when it's fast enough.
The key insight Profilers add overhead and slow the program down, so read them for proportions, not absolute times. If one function owns 80% of the cumulative time, that's where to look; no other change can give a large win.

§5Common Mistakes

MistakeWhat HappensFix
Optimizing without measuringEffort goes to code that takes 1% of the timeProfile first and target the top entry
Timing a snippet onceNoise and caching dominate the resultUse timeit with many repetitions, and take the best
Profiling toy inputThe bottleneck shifts at real scaleProfile with realistic data sizes
Practice
  1. Profile a script that processes a few hundred thousand records, and name the top three functions by cumulative time.
  2. Use timeit to compare string building with += and "".join at 10, 1,000, and 100,000 pieces.
Key takeaways
  • timeit compares small snippets; cProfile finds hot spots in a whole program.
  • Sort by cumulative for the big picture and tottime for the functions doing the work.
  • Measure, change one thing, and measure again.
