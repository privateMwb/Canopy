Plugin Architectures & Entry Points

Entry points let other packages extend your program just by being installed, with no forking and no edits to your code.

§1Why Plugins

A plugin system lets third parties add formats, commands, or backends without changing your core. Tools such as pytest, Flask extensions, and many CLIs work this way. The design question is how the core discovers extensions.

§2Registration Options

  • Explicit registration: users import a plugin and pass it in, or call register(). Simple and obvious, but requires user code to run first.
  • Subclass registration: __init_subclass__ records subclasses automatically, but only for modules that have already been imported.
  • Entry points: installed packages declare plugins in their metadata, and the core finds them by name at runtime, with no import of the plugin required until it's loaded.
# Explicit
registry: dict[str, type] = {}

def register(name):
    def deco(cls):
        registry[name] = cls
        return cls
    return deco

@register("csv")
class CsvExporter: ...

§3Entry Points

A plugin package advertises its plugin in pyproject.toml under a group name that your project defines.

# plugin package: acme-exporters/pyproject.toml
[project]
name = "acme-exporters"

[project.entry-points."mytool.exporters"]
parquet = "acme_exporters.parquet:ParquetExporter"
xml = "acme_exporters.xml_export:XmlExporter"

The host program looks them up with importlib.metadata.

from importlib.metadata import entry_points

def load_exporters():
    exporters = {}
    for ep in entry_points(group="mytool.exporters"):     # Python 3.10+ API
        try:
            exporters[ep.name] = ep.load()                # imports the object lazily
        except Exception as err:
            log.warning("plugin %s failed to load: %s", ep.name, err)
    return exporters

exporters = load_exporters()
exporters["parquet"]().export(data, "out.parquet")

pip install acme-exporters is all a user needs; parquet becomes available in your tool. The same mechanism creates console scripts ([project.scripts] is a special entry-point group).

§4Designing the Plugin Contract

  • Define a small interface: a Protocol or abstract base class describing methods and attributes plugins must supply.
  • Version the contract (a plugin_api_version attribute, or a documented interface version) so you can evolve it.
  • Isolate failures: a broken plugin shouldn't crash the host. Catch load errors, log them, and carry on, or offer a strict mode.
  • Define ordering and conflicts: what happens if two plugins claim the same name?
  • Provide a testing helper and docs so plugin authors can verify compatibility, such as a base test class.
  • Remember plugins run with the host's full privileges. Installing one is a trust decision.
The key insight An entry point turns "installed" into "enabled." The plugin never needs a code path in your repository, and you never need to know it exists.

§5Common Mistakes

MistakeWhat HappensFix
Importing every plugin eagerly at startupSlow start, and one bad plugin breaks everythingLoad lazily with ep.load() and handle failures
Letting plugins depend on your internalsYour refactors break the ecosystemExpose a small, versioned, documented plugin interface
Using old entry_points() return shapesCode breaks across Python versionsUse entry_points(group=...) (3.10+), or the importlib_metadata backport for older versions
Practice
  1. Create two tiny packages: a host exposing a greeters group, and a plugin that registers a greeter. Install both in editable mode and list the discovered plugins.
  2. Add a failing plugin and make the host log the error and continue.
Key takeaways
  • Entry points let installed packages register plugins under a named group in pyproject.toml.
  • Discover with importlib.metadata.entry_points(group=...) and load lazily.
  • Define a small versioned plugin interface, isolate plugin failures, and treat plugins as trusted code.
