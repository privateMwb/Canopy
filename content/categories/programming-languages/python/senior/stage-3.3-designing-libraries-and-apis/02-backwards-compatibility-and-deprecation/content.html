Backwards Compatibility & Deprecation

Users trust a library that changes predictably, so version meaningfully, warn before you break, and give people time and a path to migrate.

§1Semantic Versioning

SemVer numbers releases MAJOR.MINOR.PATCH:

BumpWhenExample
PATCHbug fixes only, no API change1.4.2 to 1.4.3
MINORnew, backward-compatible features1.4.3 to 1.5.0
MAJORany breaking change1.5.0 to 2.0.0

Below 1.0.0, anything may change, which is why serious libraries reach 1.0 once they have users. A "breaking change" includes more than removed functions: changed defaults, new required arguments, changed return types, different exception types, and raised minimum Python versions. Some projects follow CalVer or their own scheme, and the key point is stating the policy plainly.

§2Deprecate Before You Remove

Give users a visible warning for at least one release cycle before removal, naming the replacement and the version in which it will go away.

import warnings

def fetch(url, timeout=None):
    ...

def get(url, timeout=None):
    """Deprecated: use fetch()."""
    warnings.warn(
        "get() is deprecated and will be removed in 3.0; use fetch() instead",
        DeprecationWarning,
        stacklevel=2,          # point at the CALLER's line, not this one
    )
    return fetch(url, timeout)

stacklevel=2 is the detail people miss: without it, the warning points inside your library, where the user can't act on it. Python 3.13 also adds warnings.deprecated (and typing_extensions.deprecated for older versions), a decorator that marks the function for type checkers as well.

from warnings import deprecated      # 3.13+

@deprecated("use fetch() instead")
def get(url): ...

DeprecationWarning is hidden by default outside code run as __main__ and test runners, so tests should turn it into an error: pytest -W error::DeprecationWarning or filterwarnings = ["error::DeprecationWarning"]. Use FutureWarning for warnings meant for end users of applications.

§3Changing Signatures Safely

_MISSING = object()

def connect(host, *, timeout=30.0, ssl=_MISSING):
    if ssl is not _MISSING:
        warnings.warn("'ssl' is deprecated; use 'tls'", DeprecationWarning, stacklevel=2)
  • Add new parameters with defaults, and as keyword-only.
  • To rename, accept both for a while, and warn on the old one.
  • To change behavior, introduce the new behavior behind an opt-in first, make it the default in a major release, and keep a way to restore the old one temporarily.
  • Moved modules can leave a shim that re-exports from the new location and warns.

§4Communicating

  • Keep a changelog with sections for Added, Changed, Deprecated, Removed, Fixed, and Security.
  • State the support policy: which Python versions and how long old majors get fixes.
  • Test compatibility: run your suite against the previous release's public examples, and consider tools that detect API changes between versions.
The key insight Every removal is a negotiation with people you can't talk to. A warning, a replacement, a timeline, and a changelog entry are the only channels you have.

§5Common Mistakes

MistakeWhat HappensFix
Removing a function in a minor releaseUsers' code breaks on a routine upgradeDeprecate first; remove only in a major release
Omitting stacklevel=2 in warnings.warnWarnings point at library internalsSet stacklevel=2 so users see their own line
Never turning warnings into errors in your own testsYou miss deprecations from your dependencies and yourselfConfigure the test runner to error on DeprecationWarning
Practice
  1. Deprecate a function in a toy library with the correct stacklevel, then write a test asserting the warning with pytest.warns(DeprecationWarning).
  2. Write a short versioning and support policy (a few sentences) for your library, including what counts as a breaking change.
Key takeaways
  • Use SemVer: breaking changes require a major version, and the definition of "breaking" is broad.
  • Deprecate with warnings.warn(..., stacklevel=2) first, naming the replacement and removal version.
  • Publish a changelog and support policy, and run your tests with deprecation warnings as errors.
