Native Extensions

When Python itself is too slow or you need a C or Rust library, you cross into native code, and each way of doing it trades effort, speed, and safety.

§1First, Decide Whether You Need It

Native code is the last rung of the performance ladder. Try algorithms, vectorization (NumPy), and existing compiled libraries first. Cross the boundary when a small, hot function dominates the profile, or when you need to call an existing C/C++/Rust library.

§2ctypes and cffi: Call Existing Libraries

ctypes is in the standard library and loads shared libraries at runtime with no compilation step. You declare the function signatures yourself.

import ctypes, ctypes.util

libm = ctypes.CDLL(ctypes.util.find_library("m"))
libm.cos.argtypes = [ctypes.c_double]
libm.cos.restype = ctypes.c_double
print(libm.cos(0.0))                 # 1.0

Declaring argtypes and restype matters: without them, ctypes assumes int, and a wrong declaration can silently corrupt data or crash. cffi parses C declarations for you and offers a cleaner API, and it works well with PyPy.

§3Cython: Typed Python Compiled to C

Cython compiles Python-like code with optional C type annotations into a C extension.

# fib.pyx
def fib(int n):
    cdef long a = 0, b = 1
    cdef int i
    for i in range(n):
        a, b = b, a + b
    return a

Once built (via pyproject.toml and a build backend such as setuptools), the loop runs at C speed because the types are known. Cython suits gradual speedups of numerical hot loops and wrapping C libraries. The cost is a build step and a separate language dialect.

§4Rust with PyO3

PyO3 lets you write extensions in Rust, and maturin builds and publishes them as wheels.

use pyo3::prelude::*;

#[pyfunction]
fn count_primes(limit: u64) -> u64 {
    (2..limit).filter(|n| (2..).take_while(|d| d * d <= *n).all(|d| n % d != 0)).count() as u64
}

#[pymodule]
fn fastmath(m: &Bound<'_, PyModule>) -> PyResult<()> {
    m.add_function(wrap_pyfunction!(count_primes, m)?)
}

Rust gives speed with memory safety and a good packaging story, and many popular tools (such as Pydantic's core and ruff) use it. The cost is learning Rust and maintaining two toolchains.

§5The Costs of the Boundary

  • Call overhead: crossing the boundary costs time, so move whole loops into native code, not one tiny function called a million times.
  • Data conversion: copying between Python objects and native structures can erase the gain. Share buffers instead (NumPy arrays, the buffer protocol, memoryview).
  • The GIL: native code can release it for long computations, allowing real parallelism, but must then take care not to touch Python objects.
  • Safety: a bug in native code can crash the entire interpreter (segfault), with no traceback.
  • Distribution: you now ship per-platform wheels, built for several operating systems and Python versions, typically in CI.
  • ABI: the stable ABI (abi3) lets one wheel work across Python versions, with some performance and feature limits.
The key insight The boundary is the cost center. A native function called once on a million-item buffer is a win; called a million times on one item each, it can be slower than pure Python.

§6Common Mistakes

MistakeWhat HappensFix
Rewriting in C or Rust before profilingEffort spent on code that wasn't the bottleneckProfile first, and isolate the hot function
Omitting argtypes/restype in ctypesWrong results or segmentation faultsDeclare every signature explicitly
Calling a tiny native function in a tight Python loopBoundary overhead dominatesPush the loop inside the native function
Practice
  1. Use ctypes to call strlen or qsort from the C library, declaring signatures, and compare a pure-Python alternative.
  2. Choose a hot function from a project and write a one-paragraph justification for or against going native, naming the boundary costs.
Key takeaways
  • Try algorithms and vectorized libraries before native code; then choose ctypes/cffi, Cython, or Rust (PyO3) by need.
  • Boundary crossings and data copies are the main costs; batch work and share buffers.
  • Native code brings crash risk and per-platform packaging, so weigh them against the gain.
