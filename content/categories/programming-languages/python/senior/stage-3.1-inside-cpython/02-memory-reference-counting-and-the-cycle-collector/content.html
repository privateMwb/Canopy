Memory: Reference Counting & the Cycle Collector

CPython frees most objects the instant their reference count hits zero, and a separate cycle collector reclaims objects that only reference each other.

§1Reference Counting

Every object carries a count of how many references point to it. Binding a name, adding to a list, or passing an argument increments it, and the matching removal decrements it. At zero, the object is freed immediately.

import sys

a = []
print(sys.getrefcount(a))     # 2: the name `a` plus the temporary argument
b = a
print(sys.getrefcount(a))     # 3
del b
print(sys.getrefcount(a))     # 2

This makes cleanup deterministic: when the last reference disappears, __del__ (if any) runs and memory is released, right then. It's why with open(...) isn't strictly needed for CPython to close a file when the variable goes out of scope, though relying on that is non-portable (PyPy, for instance, doesn't behave this way).

§2Reference Cycles

Reference counting can't free a cycle, because each object keeps the others' counts above zero.

import gc

class Node:
    def __init__(self):
        self.other = None

a, b = Node(), Node()
a.other, b.other = b, a       # a cycle
del a, b                       # counts drop to 1 each, not 0: unreachable but not freed

print(gc.collect())            # the cycle collector finds and frees them

The cycle collector (the gc module) periodically traverses container objects that could participate in cycles, finds groups unreachable from outside, and frees them. It's generational: new objects are examined often, and survivors are checked less frequently, controlled by thresholds you can see with gc.get_threshold(). Collection strategy details are tuned from release to release.

§3Why Leaks Still Happen

Garbage collection frees *unreachable* objects. A "leak" in Python is almost always an object that's still reachable when you don't expect it to be:

  • Module-level or class-level caches and registries that grow forever (_cache = {}).
  • Lists of results, or listeners and callbacks that are added and never removed.
  • Closures, exception tracebacks, or frames holding references to large objects.
  • Cycles with the collector disabled (gc.disable()), or frozen (gc.freeze()).
  • Memory leaked by C extensions that mismanage their own references, which no Python tool can see.

Also, freed memory isn't always returned to the operating system: Python's allocator keeps arenas around, so resident memory may stay high even when objects were freed.

§4Finding Out

import tracemalloc, gc

tracemalloc.start()
run_workload()
snap = tracemalloc.take_snapshot()
for stat in snap.statistics("lineno")[:5]:
    print(stat)                    # top allocation sites

print(gc.get_count(), len(gc.get_objects()))
gc.set_debug(gc.DEBUG_SAVEALL)     # keep unreachable objects in gc.garbage to inspect

Compare two snapshots (snap2.compare_to(snap1, "lineno")) to see what grew. weakref lets you reference an object without keeping it alive, which breaks accidental ownership in caches and observer lists.

The key insight Ask "who still holds a reference?" not "why didn't the collector run?" gc.get_referrers(obj) and tracemalloc snapshots answer the question directly.

§5Common Mistakes

MistakeWhat HappensFix
Assuming the garbage collector prevents all leaksReachable-but-unneeded objects accumulateBound caches (lru_cache(maxsize=...)), remove listeners, and use weakref where appropriate
Disabling gc for speed without understanding cyclesMemory grows unboundedly if cycles existKeep it on, or call gc.collect() at known safe points
Relying on __del__ for cleanupTiming is unreliable outside CPython's refcountingUse with and context managers for resources
Practice
  1. Create a cycle of two objects with gc.disable(), observe memory or object counts grow, then call gc.collect() and see them reclaimed.
  2. Use tracemalloc snapshots before and after a function runs 1,000 times to find the line that retains memory.
Key takeaways
  • Reference counts free most objects immediately; the generational cycle collector handles unreachable cycles.
  • Most Python leaks are still-reachable objects such as unbounded caches and forgotten callbacks.
  • tracemalloc, gc.get_referrers, and weakref are the main tools for finding and preventing them.
