How CPython Runs Your Code

CPython compiles source into bytecode and runs it in a stack-based evaluation loop, and the dis module lets you read exactly what it generated.

§1From Source to Bytecode

CPython, the reference implementation, works in stages: parse the source into an abstract syntax tree (AST), compile the tree to bytecode stored in code objects, and execute that bytecode in the evaluation loop. Compiled modules are cached as .pyc files in __pycache__, keyed by the interpreter version.

import ast, dis

src = "total = price * qty + 1"
print(ast.dump(ast.parse(src), indent=2)[:120])   # the tree

def add(a, b):
    return a + b

dis.dis(add)
  RESUME        0
  LOAD_FAST     0 (a)
  LOAD_FAST     1 (b)
  BINARY_OP     0 (+)
  RETURN_VALUE

The exact instructions change between Python versions (this is 3.12-style output), so treat bytecode as an implementation detail, not an API. A function's code object is available as add.__code__, with co_code, co_consts, co_varnames, and co_names.

§2A Stack Machine

Each instruction operates on a value stack inside a frame. LOAD_FAST pushes a local variable, BINARY_OP pops two values and pushes the result, and RETURN_VALUE pops the top and returns it. Each function call creates a frame holding the locals, the stack, and the current instruction position. That's what tracebacks display, and why deep recursion raises RecursionError (see sys.getrecursionlimit()).

§3Reading dis to Learn Costs

dis explains performance questions with evidence.

def f1(items):
    out = []
    for x in items:
        out.append(x * 2)        # attribute lookup + call on every iteration
    return out

def f2(items):
    return [x * 2 for x in items]

dis.dis(f1)
dis.dis(f2)

It also shows scoping directly: names assigned in a function compile to LOAD_FAST/STORE_FAST (a fast array slot), while module-level and built-in names use LOAD_GLOBAL, a dictionary lookup. Constants like 2 * 3 are folded at compile time into 6.

§4The Adaptive Interpreter

Since Python 3.11, CPython specializes hot bytecode at runtime. After an instruction runs a few times with the same operand types, the interpreter swaps it for a faster variant (for example, integer addition or a cached attribute load), and reverts if the types change. You can see the result with dis.dis(add, adaptive=True) after calling the function many times. This is a large reason newer versions run the same code faster, with no changes on your part.

The key insight Python isn't "interpreting text." It's executing compact bytecode on a stack machine whose hot paths specialize themselves. When performance puzzles you, dis and a profiler beat folklore.

§5Common Mistakes

MistakeWhat HappensFix
Relying on exact bytecode in tests or toolsBreaks on every Python upgradeTreat bytecode as version-specific; use the AST or public APIs
Distributing only .pyc files as "protection"Trivially decompiled and tied to one versionDon't depend on .pyc for secrecy; use a license and a server boundary instead
Assuming the global lookups in a hot loop are freeEach LOAD_GLOBAL costs a dict lookup (cached in recent versions, but still not free)Profile first; bind locals only where measurement shows a gain
Practice
  1. Use dis.dis on a function with a for loop and one with a list comprehension, and identify which instructions are per-iteration.
  2. Compile x = 2 ** 10 + 1 with dis and explain why there's no arithmetic at runtime.
Key takeaways
  • CPython parses to an AST, compiles to bytecode in code objects, and executes it on a stack machine in frames.
  • dis shows the bytecode, but its details change per version.
  • The 3.11+ adaptive interpreter specializes hot instructions, so upgrading Python alone can speed up code.
