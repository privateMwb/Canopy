Testing with pytest

pytest finds functions named test_*, runs them, and reports failures from plain assert statements.

§1Your First Tests

Put tests in files named test_*.py and functions named test_*. Use a plain assert; on failure, pytest shows the values on both sides.

# calc.py
def add(a, b):
    return a + b

def divide(a, b):
    if b == 0:
        raise ZeroDivisionError("b must not be zero")
    return a / b
# test_calc.py
import pytest
from calc import add, divide

def test_add():
    assert add(2, 3) == 5

def test_divide():
    assert divide(10, 4) == 2.5

def test_divide_by_zero():
    with pytest.raises(ZeroDivisionError):
        divide(1, 0)

Install with python -m pip install pytest and run pytest (or pytest -v, or pytest test_calc.py::test_add for one test).

§2Fixtures

A fixture is a function that prepares something tests need. Declare it with @pytest.fixture, and a test requests it by naming it as a parameter.

import pytest
from inventory import Inventory

@pytest.fixture
def inv():
    i = Inventory()
    i.add("pen", 10)
    return i

def test_remove_reduces_count(inv):
    inv.remove("pen", 3)
    assert inv.count("pen") == 7

def test_cannot_remove_more_than_stock(inv):
    with pytest.raises(ValueError):
        inv.remove("pen", 99)

Each test gets a fresh fixture by default, so tests don't affect each other. Fixtures shared across files go in conftest.py. The built-in tmp_path fixture gives a temporary directory.

§3Parametrization

Run one test body against many inputs.

@pytest.mark.parametrize("a, b, expected", [
    (1, 1, 2),
    (0, 0, 0),
    (-1, 1, 0),
])
def test_add_cases(a, b, expected):
    assert add(a, b) == expected

Each row reports as its own test, so one failing case doesn't hide the others.

§4What to Test

Test behavior through the public interface: normal cases, edge cases (empty, zero, one, maximum), and failure cases. A good test fails for one reason and has a name that describes the behavior, like test_cannot_remove_more_than_stock.

The key insight Tests are what let you change code with confidence. If you refactor and the suite stays green, you didn't break behavior; if it goes red, the failure points at what you did.

§5Common Mistakes

MistakeWhat HappensFix
Tests that depend on each other's orderFailures that appear only in some runsMake each test set up its own state, usually with a fixture
Asserting too much in one testA failure doesn't tell you what brokeOne behavior per test, with a descriptive name
Using assert on floats with ==Rounding errors cause flaky failuresUse pytest.approx(0.3)
Practice
  1. Write tests for a fizzbuzz(n) function using parametrize to cover 3, 5, 15, and a plain number.
  2. Create a fixture that writes a temporary CSV file with tmp_path, and test a function that reads it.
Key takeaways
  • pytest discovers test_* functions and uses plain assert with detailed failure output.
  • Fixtures prepare fresh test state; parametrize runs the same test over many cases.
  • Test behavior through the public interface, including edge cases and expected errors.
