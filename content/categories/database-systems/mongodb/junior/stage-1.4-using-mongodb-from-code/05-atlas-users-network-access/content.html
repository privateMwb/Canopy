Atlas, Users & Network Access

A reachable database must be locked down: give each application a least-privilege user and allow connections only from places that need them.

§1Least-Privilege Users

Create separate database users for separate jobs, and give each only the role it needs.

RoleAllowsTypical use
readRead one databaseReporting, analytics
readWriteRead and write one databaseAn application
dbAdminManage indexes and collectionsMigration scripts
atlasAdminEverythingAlmost never
// self-managed server, in mongosh
db.getSiblingDB("shop").createUser({
  user: "shop_app", pwd: passwordPrompt(),
  roles: [ { role: "readWrite", db: "shop" } ]
})

In Atlas, you create the same users in the Database Access page and scope them to specific databases or clusters.

§2Network Access

Atlas only accepts connections from addresses on its IP access list. For development, add your own IP. For production, add the fixed addresses of your servers, or use private networking such as VPC peering or a private endpoint, so traffic never crosses the public internet.

Allowed:   203.0.113.10/32    (your office)
Allowed:   10.8.0.0/16        (peered network)
Avoid:     0.0.0.0/0          (the whole internet)

Using 0.0.0.0/0 makes the cluster reachable from anywhere, so a leaked password becomes a breach.

§3Other Basics

  • Always connect over TLS, which Atlas requires.
  • Use strong generated passwords and rotate them when someone leaves.
  • Keep separate clusters or databases and credentials for development, staging, and production.
  • Turn on auditing and alerts for production clusters where your tier allows it.
The key insight Two independent locks protect the database: who you are (credentials with a narrow role) and where you connect from (the access list). Use both.

§4Common Mistakes

MistakeWhat HappensFix
One admin user shared by every serviceA leak gives full controlCreate one least-privilege user per application
Allowing 0.0.0.0/0 "to make it work"Anyone on the internet can try to connectAllow specific addresses or use private networking
Using production credentials in developmentTest code can modify real dataSeparate users, clusters, and strings per environment
Practice
  1. Create a read-only reporting user and a read-write application user, and confirm that the reporting user cannot write.
  2. Write down the IP access list you would use for production and how each entry would be justified.
Key takeaways
  • Give each application a user with only the roles it needs.
  • Restrict network access to known addresses or private networking, and never leave it open to the world.
  • Separate credentials per environment limit the damage of any leak.
