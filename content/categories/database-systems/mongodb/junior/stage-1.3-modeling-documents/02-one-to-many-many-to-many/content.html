One-to-Many & Many-to-Many

Relationships come in different sizes, and each size has a shape that works and a shape that eventually fails.

§1One-to-Few: Embed

When the many side is small and bounded, put it in an array of subdocuments.

{ _id: 1, name: "Ada",
  phones: [ { type: "mobile", number: "555-0100" }, { type: "work", number: "555-0111" } ] }

§2One-to-Many: Reference From the Child

When the many side is large or independent, give each child a pointer to its parent.

// authors
{ _id: 1, name: "Ada" }
// posts
{ _id: 10, authorId: 1, title: "Notes", createdAt: ISODate("2026-02-01") }

db.posts.createIndex({ authorId: 1, createdAt: -1 })        // the pointer must be indexed
db.posts.find({ authorId: 1 }).sort({ createdAt: -1 }).limit(10)

Keeping the reference on the "many" side avoids an array of ids that grows forever inside the parent. A parent-side array of ids is fine only when the list is small and bounded.

§3Many-to-Many

A student takes many courses and a course has many students. Options:

  • Array of ids on one side, when one side is small: { _id: "s1", courseIds: ["c1", "c2"] }, indexed with a multikey index.
  • Arrays on both sides, to read either direction cheaply, at the cost of keeping two lists in sync.
  • A join collection (enrollments), when the relationship itself has data such as a grade or a date.
db.enrollments.insertOne({ studentId: "s1", courseId: "c1", grade: "A", enrolledAt: new Date() })
db.enrollments.createIndex({ courseId: 1, studentId: 1 }, { unique: true })
The key insight Ask which side is bounded and which direction you query most. Put the pointer on the side that stays small, and index it.

§4Common Mistakes

MistakeWhat HappensFix
An array of child ids inside a parent with millions of childrenThe parent document keeps growingStore parentId on each child instead
Forgetting to index the reference fieldEvery lookup scans the child collectionIndex authorId, courseId, and similar fields
Two-sided arrays updated in separate writesThe two lists drift apartWrite one side only, or use a transaction when you must keep both
Practice
  1. Model users and followers where some users have millions of followers, and explain which side holds the reference.
  2. Model students, courses, and grades, and justify whether you need a join collection.
Key takeaways
  • Embed one-to-few, reference from the child for one-to-many, and use arrays or a join collection for many-to-many.
  • The side that can grow without bound should never be an array inside the other document.
  • Always index the field you use to follow a reference.
