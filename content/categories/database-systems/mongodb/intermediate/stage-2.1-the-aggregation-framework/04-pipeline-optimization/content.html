Pipeline Optimization

A pipeline is fast when it uses an index early, shrinks the data quickly, and avoids stages that must hold everything in memory, and explain shows whether it does.

§1Order Matters

The server reorders some stages automatically, but you should still write them in a good order.

  • Start with $match (and $sort that an index can serve) so the pipeline uses an index.
  • Use $project or $unset early to drop large fields you do not need.
  • Put $limit right after $sort so the server only keeps the top N.
  • Avoid $lookup and $unwind on data you have not yet filtered.
// good: filter, then group
db.orders.aggregate([
  { $match: { status: "paid", placedAt: { $gte: start } } },
  { $group: { _id: "$customerId", total: { $sum: "$total" } } }
])

An index on { status: 1, placedAt: 1 } can serve that $match. A $match that comes after a $group filters the grouped output and cannot use the collection's indexes.

§2Reading explain for Pipelines

db.orders.explain("executionStats").aggregate([ /* pipeline */ ])

Look at the first stage in the output. IXSCAN means an index served the leading $match, while COLLSCAN means a full scan. Compare totalDocsExamined to the number of documents that actually matter.

§3Memory Limits

Each blocking stage ($group, $sort without an index) may use up to 100 MB of RAM. Beyond that the stage fails unless you allow spilling to disk.

db.orders.aggregate(pipeline, { allowDiskUse: true })     // disk spilling is the default in recent versions

Spilling to disk keeps a big job from failing, but it is much slower, so shrink the data first when you can.

The key insight A pipeline that reads a million documents to return ten is slow no matter how clever the later stages are. The first $match decides most of the cost.

§4Common Mistakes

MistakeWhat HappensFix
Leading with $project or $addFields instead of $matchThe index goes unusedPut the filter first
Sorting a large unindexed set and then limitingA huge in-memory sortIndex the sort, and keep $limit next to $sort
Never checking explainFull scans go unnoticedCheck the first stage and totalDocsExamined
Practice
  1. Take a slow pipeline, run explain("executionStats"), and rewrite it so its first stage uses an index.
  2. Add allowDiskUse to a large $group, and compare the timing with a version that has a $match first.
Key takeaways
  • Begin with an indexed $match, drop unneeded fields early, and keep $limit next to $sort.
  • Use explain("executionStats") to see whether the first stage uses an index.
  • Blocking stages have a memory limit, and spilling to disk is a slow safety net.
