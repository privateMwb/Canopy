Choosing a Shard Key

The shard key controls distribution, query efficiency, and growth for a collection, and it is the hardest decision to reverse, so it deserves the most care.

§1What Makes a Good Key

Judge a candidate key on four properties.

PropertyQuestionBad example
CardinalityAre there many distinct values?status (only a few values, so few chunks)
FrequencyIs any value very common?country where most users are in one country
MonotonicityDoes the value always increase?_id as an ObjectId, or a timestamp
Query fitDo common queries include it?A field no query filters on

Low cardinality limits how many chunks can exist. High frequency of one value creates a jumbo chunk that cannot be split. A monotonically increasing key sends every new insert to the last chunk, so one shard takes all the writes.

§2Hashed and Compound Keys

A hashed key fixes monotonic writes by scattering inserts across shards, at the cost of efficient range queries on that field.

A compound key can combine properties: a field you query by plus one that adds cardinality.

sh.shardCollection("shop.orders", { customerId: "hashed" })           // even write spread
sh.shardCollection("shop.events", { tenantId: 1, deviceId: 1 })       // targets by tenant, spreads within it
sh.shardCollection("logs.entries", { source: 1, ts: 1 })              // group by source, then time

Using { tenantId: 1, _id: 1 } keeps a tenant's data together while giving every document a unique, high-cardinality tail.

§3The Cost of a Wrong Choice

A poor key causes hotspots, where one shard takes most of the load, and scatter-gather queries that touch every shard. Since MongoDB 5.0 you can reshard a collection, and from 4.4 you can refine a key by adding a suffix, but both are heavy operations on a live cluster. Pick carefully up front, and test the key against a realistic workload before production.

The key insight Start from your most frequent queries and writes. A good key appears in them, spreads writes evenly, and has plenty of distinct values.

§4Common Mistakes

MistakeWhat HappensFix
Sharding on a timestamp or ObjectIdAll inserts land on one shardUse a hashed key, or a compound key with a well-spread prefix
Low-cardinality keyFew chunks, uneven data, and jumbo chunksAdd a high-cardinality field to a compound key
A key no query usesEvery query is scatter-gatherChoose a key found in your main filters
Practice
  1. Evaluate userId, createdAt, _id, and { tenantId, _id } for a multi-tenant events collection against the four properties.
  2. Pick a shard key for a chat application and defend it against hotspots and scatter-gather queries.
Key takeaways
  • Judge a key by cardinality, frequency, monotonicity, and fit with queries.
  • Monotonic keys create write hotspots, and hashed or compound keys spread them.
  • A wrong key is costly to fix, so test it against the real workload first.
