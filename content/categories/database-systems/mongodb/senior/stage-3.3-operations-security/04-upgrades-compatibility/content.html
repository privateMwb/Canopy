Upgrades & Compatibility

MongoDB upgrades follow a defined path, one release at a time, with a feature compatibility version that lets you roll back until you commit.

§1Release Rules

MongoDB releases come as major versions (such as 7.0 and 8.0). You upgrade one major version at a time, and must be on the latest patch of the current version first. Each version has an end-of-life date, after which it no longer receives fixes, so plan upgrades before then.

Before you start, read the release notes for compatibility changes, removed commands, changed defaults, and driver requirements.

§2Feature Compatibility Version

The feature compatibility version (FCV) controls which features are enabled, and it is separate from the binary version. After you replace the binaries with the new version, the cluster still runs with the old FCV, and new features that would make the data incompatible with the older version stay off.

db.adminCommand({ getParameter: 1, featureCompatibilityVersion: 1 })
db.adminCommand({ setFeatureCompatibilityVersion: "7.0", confirm: true })      // commit the upgrade

While the FCV is still the old one, you can downgrade the binaries if something is wrong. Setting the FCV commits you to the new version's data features.

§3A Rolling Upgrade

For a replica set, upgrade without downtime.

  1. Take and verify a backup, and test the upgrade in a staging copy of production.
  2. Upgrade the secondaries one at a time: stop, replace the binary, start, wait until it is healthy and caught up.
  3. Step down the primary, and upgrade it as a secondary.
  4. Run the application on the new version for a soak period while the FCV is old.
  5. Set the FCV to the new version.

For a sharded cluster, disable the balancer, upgrade the config servers, then the shards, then the mongos routers, and re-enable the balancer.

rs.stepDown(120)          // ask the primary to step down and not seek election for 120 seconds

§4Compatibility Checks and Rollback Plan

  • Check driver compatibility with the new server version, and upgrade drivers first if required.
  • Run your test suite and a load test against the new version.
  • Write the rollback plan before you begin: downgrade the binaries while the FCV is old, or restore from the backup.
The key insight The FCV split gives you a reversible stage. Soak on the new binaries with the old FCV, and commit only when you are confident.

§5Common Mistakes

MistakeWhat HappensFix
Skipping a major versionUnsupported path, and failure to startUpgrade one version at a time
Setting the FCV immediatelyNo easy rollbackSoak first, then commit
No tested rollback or backupA failed upgrade becomes an outagePrepare and rehearse the rollback
Practice
  1. Write the exact step list for upgrading a three-member replica set from one major version to the next.
  2. Explain what you can and cannot do if a problem appears before and after the FCV change.
Key takeaways
  • Upgrade one major version at a time, after reading the compatibility notes.
  • The feature compatibility version separates the binary upgrade from the irreversible step.
  • Rehearse the upgrade, and write the rollback plan before you start.
