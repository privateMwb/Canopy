The Query Planner & Plan Cache

For each query shape, MongoDB tries candidate indexes, picks a winner, and caches that decision, so a stale cached plan can quietly slow a query down.

§1Choosing a Plan

When a query could use several indexes, the planner builds candidate plans and runs them in a short trial period, all competing in parallel. The plan that returns results first, or makes the most progress, wins and finishes the query.

db.orders.find({ status: "paid", customerId: 42 }).explain("allPlansExecution")
// winningPlan:  IXSCAN { customerId: 1, placedAt: -1 }
// rejectedPlans: [ IXSCAN { status: 1 } ]

Plans are scored on how much work they do per result, with a bonus for avoiding a blocking sort.

§2The Plan Cache

Running the trial for every query would be wasteful, so the winner is stored in the plan cache, keyed by the query shape: the structure of the filter, sort, and projection with literal values removed. The next query with the same shape uses the cached plan right away.

db.orders.getPlanCache().list()               // inspect cached plans
db.orders.getPlanCache().clear()              // clear them

A cached plan is monitored. If it performs much worse than when it was chosen, the planner replans, and the cache entry is invalidated by events such as index creation or removal, a collection drop, and a server restart. In newer versions entries are also evicted when the collection changes significantly.

§3When a Good Plan Goes Bad

The winner for one value may be a poor choice for another. For example { status: "paid" } matches almost everything, while { status: "refunded" } matches almost nothing. A plan picked for one can slow down the other. Warning signs are the same query shape with wildly different times and large differences between examined and returned counts.

  • Build compound indexes that make the best plan obvious.
  • Use hint() to force an index while diagnosing, or in rare cases permanently.
  • Use index filters or query settings to pin a plan when no better fix exists.
db.orders.find({ status: "refunded" }).hint({ status: 1, placedAt: -1 })
The key insight The planner chooses by trial, not by statistics on your data distribution. A good compound index removes the ambiguity, and that is more reliable than overriding the planner.

§4Common Mistakes

MistakeWhat HappensFix
Leaving a hint() in code after the data changesA forced plan that is no longer bestRe-evaluate hints regularly, and prefer fixing the index
Blaming MongoDB when one value is slowCached plan suits another valueCheck explain for that specific value, and improve the compound index
Overlapping single-field indexesThe planner has weak choicesReplace them with a compound index
Practice
  1. Create two overlapping indexes, run the same query shape with a common and a rare value, and compare plans.
  2. Use getPlanCache().list() to find the cached plan for a shape, then clear it and observe what changes.
Key takeaways
  • The planner trials candidate plans and caches the winner by query shape.
  • A cached plan can be wrong for some values, and the planner replans only if it degrades badly.
  • Compound indexes that match the query remove ambiguity, and hint() is for diagnosis.
