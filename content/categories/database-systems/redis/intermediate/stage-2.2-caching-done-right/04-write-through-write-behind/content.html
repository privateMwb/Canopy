Write-Through & Write-Behind

Write-through and write-behind keep the cache and database in step, with very different failure behavior.

§1Write-Through

The application writes to the cache and the database together, and returns once both are done.

await db.upsert(product);                                // source of truth first
await redis.set(`cache:product:${id}`, JSON.stringify(product), { EX: 3600 });

Reads are always warm, but writes are slower, and the two writes can disagree if one fails. If the cache write fails after the database commit, the cache holds old data until the TTL.

§2Write-Behind

The application writes to Redis and returns immediately; a background worker writes to the database later.

await redis.xadd("pending:writes", "*", "id", id, "data", JSON.stringify(product));
// a worker drains the stream into the database in batches

Writes are very fast and can be batched, but the data exists only in Redis until the worker catches up. A crash, eviction, or failover in that window loses writes.

§3Comparing

  • Cache-aside is simplest and tolerates cache loss.
  • Write-through keeps reads fresh at the cost of write latency.
  • Write-behind maximizes write speed and demands durable queuing, retries, and monitoring of the backlog.

If you use write-behind, use a stream with acknowledgements and AOF persistence, not a plain list.

Gotcha With write-behind, the cache becomes the system of record for the pending window. Treat it with the same care as a database.

§4Common Mistakes

MistakeWhat HappensFix
Write-behind with no persistenceA restart loses acknowledged writesEnable AOF and use streams with acknowledgement
Writing the cache before the database in write-throughA failed database write leaves cached data that never existedWrite the database first
Not monitoring the write-behind backlogThe database falls far behind unnoticedAlert on queue length and age
Practice
  1. Sketch what happens to each pattern if Redis restarts in the middle of a write.
  2. Implement write-behind with a stream and a worker that retries on failure.
Key takeaways
  • Write-through is simple and fresh; write-behind is fast and risky.
  • Write-behind data lives only in Redis until flushed.
  • Use durable queues and monitor backlog if you choose it.
