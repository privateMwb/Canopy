Job Queues & Reliable Processing

A reliable queue never loses a job when a worker dies mid-task, which a plain list pop cannot promise.

§1Why a Simple Pop Loses Jobs

RPOP jobs removes the job from Redis before the worker has done anything. If the worker crashes next, the job is gone.

§2Reliable Queue With a Processing List

LMOVE moves an item atomically from one list to another, so a job is always in exactly one place.

LMOVE jobs processing RIGHT LEFT          # take a job and park it
# ...do the work...
LREM processing 1 "job-payload"           # remove on success

A janitor process finds jobs stuck in processing too long and moves them back.

§3Reliable Queue With Streams

Streams do this natively: XREADGROUP delivers a job, and until XACK it stays pending and claimable.

XREADGROUP GROUP workers w1 COUNT 1 BLOCK 5000 STREAMS jobs >
XACK jobs workers 1715680000000-0
XAUTOCLAIM jobs workers w2 60000 0-0 COUNT 10     # steal jobs idle over 60 s

§4Retries and Dead Letters

Count attempts per job. After a limit such as 5, move the job to a dead-letter stream or list for inspection instead of retrying forever.

if (attempts >= 5) await redis.xAdd("jobs:dead", "*", { id, error: String(err) });
else await redis.xAdd("jobs", "*", { id, attempts: attempts + 1 });

Use exponential backoff between retries, for example with a sorted set scored by the next attempt time.

The key insight Delivery is at-least-once, so a job can run twice. Make jobs idempotent, or you will charge a customer twice.

§5Common Mistakes

MistakeWhat HappensFix
RPOP for important jobsA crash loses the jobUse LMOVE or streams with acknowledgement
Retrying foreverA poisonous job loops and blocks resourcesCap attempts and use a dead-letter store
Non-idempotent job handlersDuplicate deliveries cause duplicate effectsUse an idempotency key per job
Practice
  1. Build a worker, kill it with kill -9 mid-job, and confirm another worker finishes the job.
  2. Add a retry limit and a dead-letter stream.
Key takeaways
  • Use LMOVE or streams so a job is never in limbo.
  • Cap retries and send failures to a dead-letter store.
  • Delivery is at least once, so make handlers idempotent.
