Naming Keys & Key Design

Redis has one flat keyspace, so a consistent naming scheme is the only organization you get.

§1Namespaces by Convention

Redis has no tables or folders. By convention, keys use colons to build a hierarchy that humans and tools can read.

user:1001:profile
user:1001:sessions
order:2024-05:count
cache:product:77
rate:ip:203.0.113.5:minute

A good key says what kind of thing it is, which one, and sometimes which attribute. Tools such as redis-cli and GUI clients group keys by colon.

§2Rules That Keep a Keyspace Healthy

  • Start with a prefix per feature or service (cache:, sess:, rate:) so you can find and clean up one feature's keys.
  • Keep keys short enough to be cheap, but readable. Millions of keys multiply every extra byte.
  • Include a version when the stored format may change, such as cache:v2:product:77.
  • Never build keys from raw user input without limiting length and characters.
SCAN 0 MATCH cache:product:* COUNT 500    # find one feature's keys

§3Planning for Deletion and Scale

Decide up front how keys die. Cache and session keys should carry a TTL. Keys that must live forever should be few and documented. Later, when you move to Redis Cluster, a hash tag in curly braces ({user:1001}:cart) controls which keys live together, so thinking about key shape early pays off.

The key insight A key name is a tiny schema. Write down the patterns your team uses, the way you would document table names.

§4Common Mistakes

MistakeWhat HappensFix
Keys like data1, tmp, xNobody knows what they hold or who owns themUse feature:entity:id:attribute
Putting a whole user-supplied string in the keyHuge or hostile keys waste memory and can collideValidate and bound the input, or hash it
Mixing cache keys and permanent data with no prefixA cleanup or flush removes the wrong thingsSeparate by prefix, and use TTLs on all cache keys
Practice
  1. Write the key patterns for a small shop: user profiles, carts, product cache, and a per-IP login rate limit.
  2. Add a version segment to one pattern and describe how you would roll out a format change.
Key takeaways
  • Redis has a flat keyspace, so naming is your structure.
  • Use feature:entity:id:attribute with consistent prefixes and TTLs.
  • Keep keys readable, bounded, and versioned where formats may change.
