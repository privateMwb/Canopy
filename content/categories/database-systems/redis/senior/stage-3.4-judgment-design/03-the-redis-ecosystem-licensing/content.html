The Redis Ecosystem & Licensing

Redis licensing changed in recent years, which led to community forks and made it worth checking what you are actually running and agreeing to.

§1What Happened

Redis began under a permissive BSD license. In 2024 the project moved to dual source-available licenses (RSALv2 and SSPLv1) for newer versions. That change prompted the Linux Foundation to host Valkey, a fork of the last BSD-licensed code, backed by major cloud providers. In 2025, Redis 8 added the AGPLv3 as a license option alongside the others. Check the current license terms of the exact version and distribution you use, because they differ.

§2The Alternatives

  • Valkey: a drop-in compatible fork under a permissive license. It has diverged with its own features and performance work, so compatibility with newer Redis features should be checked.
  • Redis (official): the reference implementation with newer modules and features, under its current license terms.
  • Memcached: a simple, multithreaded cache with only strings. It is a good fit for pure caching but offers no data structures, persistence, or replication built in.
  • Managed or compatible services: cloud providers offer their own Redis-compatible engines, with differing feature coverage.
  • KeyDB, Dragonfly, and similar: compatible or multithreaded alternatives with varying maturity and licensing.

§3How to Decide

Check license terms against how you deploy (internal use, offering Redis as a service, redistributing), confirm which commands and modules your application needs, and test compatibility with your client library. Avoid depending on a vendor-only feature without noting it.

Gotcha "Redis-compatible" varies. Test your actual command mix, scripts, and modules, not just the basics.

Key takeaways
  • Redis licensing changed, and forks such as Valkey emerged.
  • Alternatives differ in features, compatibility, and license.
  • Verify the license and compatibility for your exact version and use.
