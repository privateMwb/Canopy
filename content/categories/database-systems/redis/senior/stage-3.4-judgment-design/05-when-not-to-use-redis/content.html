When Not to Use Redis

Redis is a superb tool for a fairly narrow set of jobs, and recognizing the others early saves you a painful migration later.

§1Poor Fits

  • Large datasets with flexible queries: memory is costly and there is no query language or joins. Use a database.
  • Strong durability and transactions across keys: there is no rollback and no multi-statement isolation beyond MULTI.
  • Complex reporting and analytics: use a warehouse or an analytical database.
  • Message queues needing rich routing, large backlogs, or long retention: a broker such as Kafka or RabbitMQ is built for that.
  • Big blobs: storing multi-megabyte values wastes memory and blocks the loop.
  • Global distribution with strong consistency: a single-leader replicated store cannot give it.

§2Warning Signs

  • You are writing scripts that reimplement database queries.
  • Memory cost grows faster than the value of the data.
  • You rely on WAIT and persistence to protect important records.
  • You keep adding client-side logic to compensate for missing indexes.

§3Better Alternatives, by Need

  • Relational integrity and ad-hoc queries: PostgreSQL.
  • Document storage with rich queries: MongoDB.
  • Embedded, single-file storage: SQLite.
  • Durable, high-volume event logs: Kafka or a similar log.
  • Blobs: object storage.

§4Keep Redis for What It Does Best

Speed for small operations, atomic counters, ephemeral state, rankings, and shared coordination.

The key insight Redis's strengths come from its constraints. If you keep fighting those constraints, you have picked the wrong tool for that data.

§5Common Mistakes

MistakeWhat HappensFix
Treating Redis as a general databaseCost and risk grow with the dataUse it as an accelerator next to a real database
Using it as a long-retention message logMemory fills, and replay is limitedUse a log system built for retention
Storing large blobs in valuesMemory waste and latencyStore them in object storage and cache references
Practice
  1. Choose three features from a real product and name the best store for each, including at least one where Redis is the wrong answer.
  2. List the warning signs that would make you start planning a migration away from Redis for a given dataset.
Key takeaways
  • Redis is weak at big data, rich queries, strict durability, and long-retention logs.
  • Warning signs include re-implementing database features in scripts.
  • Match each workload to the store whose strengths fit it.
