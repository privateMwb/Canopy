Validating Data in Rules

Ownership rules stop the wrong person writing. Validation rules stop anyone writing the wrong data.

§1Types and Required Fields

Check the incoming document in request.resource.data.

function validPost(d) {
  return d.keys().hasAll(['title', 'body', 'authorId', 'createdAt'])
      && d.keys().hasOnly(['title', 'body', 'authorId', 'createdAt', 'tags'])
      && d.title is string && d.title.size() > 0 && d.title.size() <= 120
      && d.body is string && d.body.size() <= 5000
      && d.authorId == request.auth.uid
      && d.createdAt == request.time
      && (!('tags' in d) || (d.tags is list && d.tags.size() <= 10));
}

match /posts/{id} {
  allow create: if request.auth != null && validPost(request.resource.data);
}

hasOnly blocks extra, unexpected fields, which stops clients from attaching arbitrary data. Comparing createdAt with request.time means the field must be serverTimestamp().

§2Controlling What Can Change

On update, decide which fields a user may touch.

allow update: if isOwner(resource.data.ownerId)
  && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['title', 'body', 'updatedAt']);

diff(...).affectedKeys() lists the fields that changed. This prevents a user from editing protected fields such as ownerId, role, or createdAt.

§3Immutable and Computed Values

// createdAt can never change after creation
request.resource.data.createdAt == resource.data.createdAt

// a counter may only move up by one
request.resource.data.likeCount == resource.data.likeCount + 1

Rules cannot loop or call outside services, so complex validation (like checking a value against a list in another system) belongs in a Cloud Function.

Validate what the client could lie about Every field arrives from code the user controls. Assume a hostile client and check types, sizes, allowed keys, and protected fields in rules, because client-side validation is only a convenience.

§4Common Mistakes

MistakeWhat HappensFix
No hasOnly on createClients add arbitrary fields or oversized dataList the exact allowed keys
Allowing updates to any fieldUsers promote themselves or change ownersRestrict with affectedKeys().hasOnly([...])
Trusting client timestampsUsers backdate recordsRequire request.time or serverTimestamp()
Practice
  1. Write a validPost function and tests that reject a missing title, an oversized body, and an extra field.
  2. Make createdAt immutable and test that an update changing it is denied.
Key takeaways
  • Validate types, sizes, and allowed keys on every write.
  • affectedKeys() restricts which fields an update may change.
  • Complex validation that rules cannot express belongs on the server.
