Idempotency, Retries & Errors

Event delivery is at-least-once, so a function can run twice for one event. Making it idempotent means a repeat changes nothing.

§1Why Duplicates Happen

Event-driven functions can be retried after a failure and, occasionally, delivered twice even without one. If your function charges a card or sends an email, a repeat is a real problem. Enable retries only for functions that are safe to run again.

export const onPaid = onDocumentUpdated({ document: "orders/{id}", retry: true }, handler);

With retry: true, a thrown error causes redelivery for up to about a week with backoff. Without it, a failure is dropped.

§2Making Handlers Idempotent

Record that an event was handled, in the same transaction as the effect, keyed by the unique event ID.

export const onOrderCreated = onDocumentCreated({ document: "orders/{id}", retry: true }, async (event) => {
  const db = getFirestore();
  const doneRef = db.doc(`processedEvents/${event.id}`);

  await db.runTransaction(async (tx) => {
    if ((await tx.get(doneRef)).exists) return;          // already handled
    tx.update(db.doc(`users/${event.data.data().userId}`), { orderCount: FieldValue.increment(1) });
    tx.set(doneRef, { at: FieldValue.serverTimestamp() });
  });
});

Other approaches: use deterministic document IDs so a repeated set writes the same document, and pass an idempotency key to payment providers so they ignore repeats.

§3Retryable vs Permanent Errors

Retry only errors that may succeed later, such as a timeout or a rate limit. For permanent errors like invalid data, log the problem and return normally so the event is not retried forever. Store failures in a dead-letter collection so you can inspect and replay them.

Assume every function runs twice If a second run of your function would hurt, make it safe: record the event ID, use deterministic IDs, or pass idempotency keys.

§4Common Mistakes

MistakeWhat HappensFix
Enabling retry on a non-idempotent functionDuplicate emails or double chargesMake the function idempotent before enabling retries
Throwing on invalid data with retries onAn endless retry loopLog and return for permanent errors
Using add() for results keyed to an eventEach retry creates another documentUse a deterministic ID such as the event ID
Practice
  1. Make an order trigger idempotent using the event ID, then redeliver the same event in a test and check nothing doubles.
  2. Add a dead-letter collection and write failed events there.
Key takeaways
  • Event delivery is at-least-once, so duplicates are possible.
  • Use event IDs, deterministic document IDs, and idempotency keys.
  • Retry transient errors; log and stop on permanent ones.
