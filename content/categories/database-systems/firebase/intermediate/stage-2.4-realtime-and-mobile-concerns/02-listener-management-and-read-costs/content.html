Listener Management & Read Costs

Real-time listeners feel free, but each one bills for the data it delivers, so managing them is a cost and a performance issue.

§1How Listeners Are Billed

In Firestore, a listener is billed for one read per document in its initial result, and then one read each time a document in the result changes (an added, modified, or removed document). A single live query on a busy collection can therefore generate a huge number of reads with no extra code.

  • Listening to a whole collection to show 10 items bills for every document returned
  • A limit bounds the initial reads, and only changes inside the window bill afterward
  • If a listener is disconnected for more than about 30 minutes and reconnects, its initial results are billed again

§2Detaching Properly

// React example
useEffect(() => {
  const unsubscribe = onSnapshot(q, (snap) => setItems(snap.docs.map((d) => d.data())));
  return unsubscribe;                    // runs when the component unmounts
}, [roomId]);

Common leaks: forgetting the cleanup, attaching a new listener on every render, and leaving listeners on screens that are no longer visible. In the emulator or console you can watch the number of active listeners to spot a leak.

§3Reducing the Bill

  • Use getDocs for data that rarely changes, and listeners only for what must be live
  • Add limit and filters to every listener
  • Share one listener across components through a store, instead of one per component
  • Prefer an aggregate document (like a summary with counts) over listening to a whole collection
  • Use the usage dashboard in the Firebase console to see reads per day and find the spike
Live data costs per change A listener is a subscription that pays on every change. Use it where the freshness is worth the price, and use one-time reads everywhere else.

§4Common Mistakes

MistakeWhat HappensFix
One listener per list item componentHundreds of listeners and repeated readsQuery once and pass the data down
No limit on a listener over a growing collectionReads and load time grow foreverLimit and paginate
Ignoring the usage dashboardSurprise bills with no clue where they came fromCheck reads per day weekly and after releases
Practice
  1. Count the active listeners in one screen of your app and remove one unnecessary one.
  2. Replace a collection listener that feeds a counter with a single summary document.
Key takeaways
  • A listener bills per initial document and per later change.
  • Always unsubscribe on cleanup and share listeners where possible.
  • Use limits, summaries, and one-time reads to cut costs.
