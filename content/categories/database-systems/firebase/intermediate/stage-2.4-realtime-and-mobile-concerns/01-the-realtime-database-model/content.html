The Realtime Database Model

The Realtime Database is one big JSON tree synced to every client, and it stays the better choice for a few specific jobs.

§1Structuring the Tree

Because reading a node downloads everything below it, keep the tree shallow and flat and link by ID.

{
  "users":    { "alice": { "name": "Alice" } },
  "rooms":    { "r1": { "title": "General" } },
  "messages": { "r1": { "m1": { "from": "alice", "text": "hi", "ts": 1700000000000 } } },
  "members":  { "r1": { "alice": true } }
}

Messages are grouped by room so one listener on messages/r1 fetches only that room. Lists of IDs are stored as keys set to true, because the database has no arrays.

§2Querying

You can order and filter on one property at a time.

import { ref, query, orderByChild, orderByKey, limitToLast, startAt, endAt, equalTo, onValue } from "firebase/database";

const q = query(ref(db, "messages/r1"), orderByChild("ts"), limitToLast(50));
onValue(q, (snap) => snap.forEach((child) => console.log(child.key, child.val())));

Filtering and ordering happen on the server, but you must tell the rules to index the field with .indexOn or large queries download everything and filter on the client.

{ "rules": { "messages": { "$room": { ".indexOn": ["ts"] } } } }

§3Where It Still Wins

  • Presence: the onDisconnect() hook sets a value when a client drops, ideal for online status
  • Very frequent tiny updates: cursors, typing indicators, game state, with low latency
  • Bandwidth-based pricing: cheap when you move many small values but store little
  • Simple tree data where the whole subtree is read together anyway
import { onDisconnect, set } from "firebase/database";
const presence = ref(db, `status/${uid}`);
await set(presence, "online");
onDisconnect(presence).set("offline");
Rules cascade in this database A .read or .write that grants access at a node grants it for everything beneath, and deeper rules cannot take it back. Put permissions low in the tree, not high.

§4Common Mistakes

MistakeWhat HappensFix
Nesting messages inside the room objectLoading the room downloads every messageKeep messages in a separate top-level node
Filtering on a field with no .indexOnThe client downloads all data to filter itDeclare .indexOn for queried fields
Granting .read high in the treeEverything below is readable and cannot be restrictedGrant access at the narrowest node
Practice
  1. Build a presence indicator with onDisconnect and watch it flip when you close the tab.
  2. Restructure a nested chat tree into separate rooms and messages nodes.
Key takeaways
  • Keep the Realtime Database tree flat and link by IDs.
  • Queries sort or filter on one property and need .indexOn.
  • It excels at presence and rapid tiny updates.
