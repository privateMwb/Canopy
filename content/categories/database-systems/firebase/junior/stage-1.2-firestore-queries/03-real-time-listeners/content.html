Real-Time Listeners

onSnapshot keeps a query or document open and calls your function every time the data changes, including changes you make yourself before the server confirms them.

§1Listening

import { onSnapshot, query, collection, where } from "firebase/firestore";

const q = query(collection(db, "messages"), where("room", "==", "general"));

const unsubscribe = onSnapshot(q, (snap) => {
  const messages = snap.docs.map((d) => ({ id: d.id, ...d.data() }));
  render(messages);
}, (error) => console.error("listener failed", error));

// later, when the screen goes away
unsubscribe();

The callback fires once with the current results, then again on every change. Always keep the unsubscribe function and call it when the component unmounts, or the listener keeps running and keeps billing.

§2Local Writes and Metadata

When your app writes data, the listener fires immediately with the new data, before the server has confirmed it. Each snapshot tells you where the data came from:

onSnapshot(q, (snap) => {
  const fromCache = snap.metadata.fromCache;            // true = not yet from the server
  snap.docs.forEach((d) => {
    if (d.metadata.hasPendingWrites) {/* show a "sending..." state */}
  });
});

If the server rejects the write (for example, rules deny it), the listener fires again and the local change disappears.

§3Reading Only What Changed

Use docChanges() to see which documents were added, modified, or removed since the last snapshot, instead of re-rendering everything.

snap.docChanges().forEach((change) => {
  if (change.type === "added") add(change.doc);
  if (change.type === "modified") update(change.doc);
  if (change.type === "removed") remove(change.doc.id);
});
Listeners are billed per change You pay for the initial results of a listener and then one read per document that changes. A listener on a busy collection with no limit can cost far more than occasional getDocs calls.

§4Common Mistakes

MistakeWhat HappensFix
Never calling unsubscribeListeners pile up and keep billing after the user leavesUnsubscribe when the view is destroyed
Ignoring the error callbackA rules failure silently stops updatesPass an error handler and surface it
Listening to a huge collection without limitSlow first load and large billsFilter and limit listener queries
Practice
  1. Open the same app in two browser tabs and watch a message appear in both when added in one.
  2. Show a "sending..." indicator on messages whose hasPendingWrites is true.
Key takeaways
  • onSnapshot delivers initial results and then every change, returning an unsubscribe function.
  • Local writes show up immediately and are corrected if the server rejects them.
  • Always unsubscribe, and limit what a listener watches.
