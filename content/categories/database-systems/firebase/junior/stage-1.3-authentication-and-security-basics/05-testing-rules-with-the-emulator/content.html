Testing Rules with the Emulator

The Firebase Emulator Suite runs Firestore and Auth on your machine so you can test rules without touching real data.

§1Starting the Emulators

firebase init emulators          # choose Firestore and Authentication
firebase emulators:start

The Emulator UI appears at localhost:4000. By default Firestore runs on port 8080 and Auth on 9099. Data is stored in memory and discarded when you stop, which is exactly what you want for tests.

§2Automated Rules Tests

The @firebase/rules-unit-testing package lets you act as different users and assert what succeeds or fails.

import { initializeTestEnvironment, assertSucceeds, assertFails } from "@firebase/rules-unit-testing";
import { readFileSync } from "fs";
import { doc, getDoc, setDoc } from "firebase/firestore";

const env = await initializeTestEnvironment({
  projectId: "demo-test",
  firestore: { rules: readFileSync("firestore.rules", "utf8") },
});

const alice = env.authenticatedContext("alice").firestore();
const bob = env.authenticatedContext("bob").firestore();
const anon = env.unauthenticatedContext().firestore();

await assertSucceeds(setDoc(doc(alice, "notes/n1"), { ownerId: "alice", text: "hi" }));
await assertSucceeds(getDoc(doc(alice, "notes/n1")));
await assertFails(getDoc(doc(bob, "notes/n1")));
await assertFails(getDoc(doc(anon, "notes/n1")));

await env.clearFirestore();

Use env.withSecurityRulesDisabled(...) to seed data that your test needs but your rules would not let a user create.

§3Running in One Command

firebase emulators:exec --only firestore "npm test"

emulators:exec starts the emulator, runs your command, and shuts it down, which makes it easy to run in continuous integration. A project ID starting with demo- guarantees the emulator never talks to a real project.

Test the denials A passing "allowed" test only proves the happy path. Most security bugs are a missing "denied" test, so write at least one assertFails for every rule.

§4Common Mistakes

MistakeWhat HappensFix
Testing only what should workA hole in the rules goes unnoticedAdd an assertFails for every user and operation that must be blocked
Using a real project ID in testsRisk of reading or changing production dataUse a demo- project ID with the emulator
Forgetting clearFirestore between testsLeftover data makes tests pass or fail by accidentClear data before each test
Practice
  1. Start the emulators and use the UI to create a user and a document.
  2. Write three tests: owner can read, another user cannot read, and signed-out visitors cannot read.
Key takeaways
  • The emulator runs Firestore and Auth locally with throwaway data.
  • assertSucceeds and assertFails act as different users to prove what rules allow.
  • Test denials as carefully as approvals.
