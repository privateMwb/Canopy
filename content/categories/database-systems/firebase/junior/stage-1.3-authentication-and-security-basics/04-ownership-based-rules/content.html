Ownership-Based Rules

The most common rule pattern ties each document to the user who owns it and compares that to request.auth.uid.

§1Rules by Document ID

When the document ID is the user's uid, the rule is short.

match /users/{userId} {
  allow read, write: if request.auth != null && request.auth.uid == userId;
}

The path variable {userId} captures the document ID, and request.auth.uid is the signed-in user's uid. They must match.

§2Rules by an Owner Field

For documents with their own IDs, store the owner on the document and check it.

match /notes/{noteId} {
  // reading and deleting use the stored document
  allow read, delete: if request.auth != null && resource.data.ownerId == request.auth.uid;

  // creating checks the incoming data
  allow create: if request.auth != null && request.resource.data.ownerId == request.auth.uid;

  // updating checks both, and stops the owner field from being changed
  allow update: if request.auth != null
    && resource.data.ownerId == request.auth.uid
    && request.resource.data.ownerId == resource.data.ownerId;
}

resource.data is the document as it is stored now. request.resource.data is the document as it would be after the write. Creates have no existing document, so they use the second.

§3Matching Queries to Rules

Because rules are not filters, the client query must include the same constraint.

const q = query(collection(db, "notes"), where("ownerId", "==", auth.currentUser.uid));

Without the where, the query could return other people's notes and Firestore rejects it outright.

Never trust a client-provided owner On create, force the owner field to equal request.auth.uid. Otherwise a user can create documents that claim to belong to someone else.

§4Common Mistakes

MistakeWhat HappensFix
Checking only resource.data on createCreates have no stored document, so they are denied or the rule errorsUse request.resource.data for create
Letting updates change ownerIdA user can hand a document to another user or steal oneRequire the owner field to stay the same
Querying without the ownerId filterPermission denied even for the user's own notesAdd the matching where clause
Practice
  1. Write rules so that a user can read, create, edit, and delete only notes whose ownerId is their uid.
  2. Try to create a note with someone else's uid as the owner and confirm it is rejected.
Key takeaways
  • request.auth.uid is the caller's identity; compare it to the path ID or an owner field.
  • resource.data is stored data and request.resource.data is the incoming data.
  • Match your queries' where clauses to what the rule requires.
