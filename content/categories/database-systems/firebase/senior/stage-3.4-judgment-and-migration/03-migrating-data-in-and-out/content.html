Migrating Data In and Out

A migration is a pipeline: export, transform, load, verify, and switch over, with a plan for changes that happen while it runs.

§1Moving Data Out of Firestore

Options for getting data out:

  • Managed export to Cloud Storage: fast and complete, but in a Google-specific format, best used to import into BigQuery or another Firestore database
  • Scripts using the Admin SDK that page through collections and write JSON or load into a target database
  • The BigQuery export extension, then SQL to transform and unload
// stream a collection out in pages
let last = null;
while (true) {
  let q = db.collection("orders").orderBy("__name__").limit(500);
  if (last) q = q.startAfter(last);
  const snap = await q.get();
  if (snap.empty) break;
  for (const d of snap.docs) await target.upsert(d.id, transform(d.data()));
  last = snap.docs[snap.docs.length - 1];
}

Throttle the reads, since they are billed and share capacity with live traffic.

§2Transforming Documents to Tables

Documents are denormalized, so moving to SQL means splitting copies, deriving foreign keys, and normalizing arrays into join tables. Convert timestamps and references into plain types, and decide what to do with schemaless variation. Write the mapping explicitly and test it on a sample, and track row counts and checksums per collection to verify the result.

§3Zero-Downtime Cutover

1. Backfill a copy of the data into the new system 2. Dual write or stream changes (via a trigger or the BigQuery changelog) so the copy stays current 3. Verify by comparing counts and sampling records, and shadow-read from the new system 4. Switch reads, then writes, gradually with a flag 5. Keep the old system read-only for a rollback window, then decommission

Moving into Firestore follows the same pipeline in reverse, with extra care for document size limits and the one-write-per-second rule during bulk load.

Migrate in reversible steps Dual writes, verification, and a rollback window turn a risky weekend cutover into a series of small, checkable moves.

§4Common Mistakes

MistakeWhat HappensFix
Exporting everything in one unthrottled runA huge read bill and slower productionThrottle and page the export
Switching over without verificationMissing or wrong data is found by usersCompare counts, checksums, and samples first
Cutting over all at onceNo rollback pathMove reads and writes in stages behind flags
Practice
  1. Write an export script that streams one collection to JSON files with throttling.
  2. Design the dual-write and verification steps for migrating one collection to Postgres.
Key takeaways
  • Migration is export, transform, load, verify, and switch.
  • Use dual writes and staged cutover with rollback.
  • Throttle bulk reads and verify with counts and checksums.
