Vendor Lock-in & Exit Strategy

Every managed platform couples you to it somewhat, and the goal is to know exactly how much and keep the cost of leaving reasonable.

§1What Is and Isn't Portable

Fairly portable: your data (it can be exported), your business logic if kept in plain functions, Cloud Storage files (also accessible as Google Cloud Storage), and standard web code.

Tightly coupled: - The Firestore data model and query semantics, plus the client SDK calls spread through your UI - Security rules, which have no equivalent elsewhere and must be reimplemented as server authorization - Real-time listeners and offline sync, which other backends do not provide the same way - Firebase Authentication: users can be exported, but password hashes use a specific scheme that the new system must be able to verify, and sessions and tokens will change - Cloud Functions triggers that react to Firestore events

§2Reducing Lock-in Cheaply

  • Put Firebase calls behind a repository layer, so only one module knows about Firestore
  • Keep business logic in plain functions with your own interfaces, not inside trigger handlers
  • Avoid unusual Firestore-only features unless they pay off
  • Keep schemas documented and exportable, with scheduled exports to a bucket you control
  • Use standard OIDC claims and keep your own users table of IDs and emails
// UI code calls this, never Firestore directly
export const notesRepo = {
  list: (uid) => /* Firestore today, SQL API tomorrow */,
  create: (uid, note) => /* ... */,
};

§3Writing an Exit Plan

A short document answering: what data would we export and how, how would users log in on the new system (hash export and import, or forced password reset), what replaces rules, listeners, and functions, how long it would take, and what it would cost. Written when things are calm, it turns "we're stuck" into a project with an estimate.

Lock-in is a cost to size Don't avoid managed services out of fear, and don't ignore the coupling. Estimate the exit cost once, keep it from growing needlessly, and revisit it yearly.

§4Common Mistakes

MistakeWhat HappensFix
Calling Firestore directly from hundreds of UI componentsA migration means rewriting the whole front endPut data access behind a repository layer
Not knowing how auth would be migratedYou discover hash and token issues mid-migrationTest an auth export and import early
Believing lock-in is zero or totalYou either over-engineer or under-planEstimate the actual exit effort
Practice
  1. List every place your UI calls Firestore directly and design a repository interface to replace them.
  2. Write a one-page exit plan covering data, auth, and rules for your app.
Key takeaways
  • Data and plain logic are portable; rules, listeners, auth hashes, and triggers are not.
  • Wrap data access in a repository layer and keep business logic independent.
  • Write and update an exit plan.
