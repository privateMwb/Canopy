Hotspots & Write Limits

Firestore scales by spreading data across servers, and certain key and index patterns concentrate traffic on one server, which slows or fails writes.

§1Per-Document and Per-Index Limits

A single document sustains only about one write per second, with short bursts allowed. That is why a global counter in one document fails under load. The same idea applies to index ranges: indexed values that are adjacent in sorted order live together, so a stream of writes with sequential values hits the same place.

Common hotspots:

  • Document IDs that are monotonically increasing, such as timestamps or incrementing numbers
  • An indexed field that always holds the current time (createdAt) on a very high write rate collection
  • Many writes to one parent document, like a total or a lastActive field

§2Avoiding Them

  • Use Firestore's automatic IDs, which are random and spread evenly
  • If you need ordering by time, store the timestamp as a field but accept the sort order cost, or add a random shard prefix for extreme rates
  • Shard hot counters across several documents
  • Batch rarely needed updates instead of writing on each event
// bad: sequential IDs at high rate
setDoc(doc(db, "events", String(Date.now())), data);

// good: random auto-ID
addDoc(collection(db, "events"), data);

§3Ramping Up Traffic

A new collection or fresh index needs time to split across servers. Google's guidance, the 500/50/5 rule, is to start at no more than about 500 operations per second to a new collection and increase by 50% every 5 minutes. Launching a viral campaign or a bulk import at full speed into an empty collection can cause contention errors and latency even though the steady-state load would be fine.

Randomness spreads load Random IDs and sharded counters turn one hot spot into many warm ones. Sequential values are convenient to humans and expensive for distributed databases.

§4Common Mistakes

MistakeWhat HappensFix
Using timestamp-based document IDs under heavy write loadWrites concentrate on one range and slow or failUse auto-IDs and store the time as a field
Importing millions of documents at full speedContention errors and retriesRamp up gradually following the 500/50/5 rule
Updating one summary document on every eventIt exceeds about one write per secondShard it or aggregate in batches
Practice
  1. Find one document in your design that many users write to and describe how you would shard it.
  2. Write an import script that ramps up its write rate over several minutes.
Key takeaways
  • A document sustains about one write per second; sequential keys and indexes concentrate load.
  • Prefer random IDs and sharding.
  • Ramp traffic into new collections gradually.
