Threat Modeling for Rules

A security review of rules asks what each kind of attacker could do, not whether the happy path works.

§1The Attacker Checklist

For every collection and operation, ask:

  • Can a signed-out visitor read or write anything?
  • Can user A read user B's data, directly or by a broad list query?
  • Can a user create a document that claims another owner, tenant, or role?
  • Can a user update a protected field such as role, ownerId, or price?
  • Can they delete things they should only create?
  • Can they write oversized, malformed, or extra data?
  • Can they enumerate IDs, emails, or private metadata through a readable collection?
  • Can they make an expensive query or upload to hurt the bill?

§2Common Holes Found in Reviews

// 1. Any signed-in user can read all users, including emails
match /users/{id} { allow read: if request.auth != null; }

// 2. Role stored on a user-writable document
match /users/{id} { allow write: if request.auth.uid == id; }   // user can set role: "admin"

// 3. Owner not forced on create
allow create: if request.auth != null;                          // anyone can create for anyone

// 4. A forgotten catch-all
match /{document=**} { allow read, write: if request.auth != null; }

Fixes include splitting public and private profile data into separate documents, validating with affectedKeys().hasOnly(...), forcing owner and tenant fields, and removing catch-all rules.

§3Make Review Routine

Do a rules review for every new collection, in pull requests, using a checklist like the one above. Run a periodic adversarial pass: write tests as an attacker, signing in as a normal user and trying every forbidden thing. Use the emulator's rules coverage report to find rules never exercised. Keep a list of past findings and add a test for each.

Think like the person trying to break it Reviewing rules for correctness is not the same as reviewing for abuse. Assume the client is hostile and the user is curious.

§4Common Mistakes

MistakeWhat HappensFix
Allowing all signed-in users to read the users collectionEmails and private data are exposedSplit public profile fields from private ones
Leaving a catch-all wildcard match inIt overrides all your careful rulesSearch for {document=**} in every review
Reviewing only the allowed pathHoles in the denied paths go unnoticedTest each forbidden action as an attacker
Practice
  1. Run the attacker checklist against your own rules file and write down every "yes".
  2. Write an adversarial test file that tries ten forbidden actions as a normal user.
Key takeaways
  • Review rules by asking what an attacker can read, create, change, and delete.
  • Typical holes: broad reads, user-editable roles, unforced owners, catch-alls.
  • Make adversarial testing a routine part of changes.
