Disaster Recovery

A managed database survives hardware failures, but it will not save you from your own mistakes or from a missing plan.

§1What Google Handles and What It Doesn't

Google replicates your data, and a multi-region Firestore database tolerates the loss of a region. That covers infrastructure failure. It does not cover:

  • A bug or script that deletes or corrupts data (replicated instantly)
  • A bad deploy of rules that opens or locks everything
  • A compromised account or leaked key
  • A deleted project or revoked billing that suspends service
  • A function loop that overwrites good data

§2Building a Recovery Plan

Define two numbers: RPO, how much data you can afford to lose, and RTO, how long you can be down. Then choose tools to meet them.

  • PITR for recovering from mistakes within the last week, with minute granularity
  • Scheduled backups with a retention period suited to your needs
  • Cross-project exports to a separate project or bucket that production credentials cannot delete
  • Auth user export (firebase auth:export users.json) and Storage backups, since Firestore backups do not include them
  • Infrastructure as code: rules, indexes, functions, and config in git so you can rebuild the project
firebase auth:export users.json --format=json --project prod

§3Drills and Runbooks

Write a runbook for the scenarios above: who decides, which command restores what, how to switch the app to the restored database, how to tell users. Practice at least one full restore into a fresh project and time it. Note that restores create a new database, so clients may need a config change or you need to copy data back.

Replication is not backup Replication copies mistakes as quickly as it copies data. Only versioned, isolated backups let you go back in time.

§4Common Mistakes

MistakeWhat HappensFix
Relying on multi-region as a backupA bad delete is replicated everywhere instantlyEnable PITR and scheduled backups
Backing up Firestore but not Auth or StorageA restore leaves users and files missingExport users and files too
No restore drillRTO is a guess and steps are unknownPractice a restore and write the runbook
Practice
  1. Define an RPO and RTO for your product and check that your backups meet them.
  2. Restore a backup into a new database in a test project and measure how long it takes.
Key takeaways
  • Managed replication does not protect against bad deletes, bad deploys, or compromised access.
  • Combine PITR, scheduled and cross-project backups, and exports of Auth and Storage.
  • Write a runbook and practice restores.
