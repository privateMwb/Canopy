Streaming Replication

Streaming replication ships the primary's WAL to standbys that replay it continuously, giving you copies for failover and for read traffic.

§1How It Works

A standby is a server that starts from a copy of the primary and then continuously replays WAL streamed over a normal connection. It is a byte-level, physical copy: the same major version, the same architecture, the entire cluster. A WAL sender process on the primary feeds a WAL receiver on the standby. With hot_standby = on (the default), the standby accepts read-only queries while it replays.

primary                                standby
  backend writes WAL  ->  walsender  ->  walreceiver  ->  WAL on disk  ->  startup process replays

Physical replication copies everything, including bloat and any data you do not need, and the standby cannot have different indexes or extra tables. In exchange it is simple, fast, and exact.

§2Setting One Up

Configure the primary, create a replication role, allow it in pg_hba.conf, and clone with pg_basebackup.

# primary: postgresql.conf
wal_level = replica
max_wal_senders = 10
max_slot_wal_keep_size = 50GB        # cap WAL a lagging slot may pin

-- primary
CREATE ROLE replicator REPLICATION LOGIN PASSWORD '...';
SELECT pg_create_physical_replication_slot('standby1');

# pg_hba.conf
host replication replicator 10.0.0.0/24 scram-sha-256

# standby: clone and start (-R writes standby.signal and primary_conninfo)
pg_basebackup -h primary -U replicator -D /var/lib/postgresql/data -R -X stream -S standby1 -P

A replication slot makes the primary retain WAL until the standby has received it, so a standby that falls behind does not lose its place. The danger is the flip side: an abandoned slot makes WAL pile up until the disk fills, so monitor slots and set max_slot_wal_keep_size.

§3Synchronous vs Asynchronous, and Lag

By default replication is asynchronous: the primary commits without waiting for the standby, which is fast but can lose the most recent commits if the primary dies before they reach a standby. For synchronous replication, name standbys in synchronous_standby_names, and synchronous_commit decides how far the standby must get before the commit returns: remote_write (received), on (flushed to disk), or remote_apply (replayed and visible to queries).

SELECT application_name, state, sync_state,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS bytes_behind,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;          -- run on the primary

SELECT now() - pg_last_xact_replay_timestamp() AS replay_delay;   -- run on a standby

Synchronous replication buys zero data loss at the price of write latency and an availability risk: if the sync standby is down, writes stall unless you configure a quorum such as ANY 1 (s1, s2). Decide by the cost of lost commits versus the cost of slower, riskier writes.

The key insight Replication is a trade between durability, latency, and availability. Asynchronous favors speed and may lose recent commits; synchronous favors safety and can stall writes.

§4Common Mistakes

MistakeWhat HappensFix
Creating a replication slot and then abandoning the standbyWAL accumulates on the primary until the disk is fullDrop unused slots, set max_slot_wal_keep_size, and alert on slot lag
Assuming asynchronous replication is losslessA primary failure loses commits not yet shippedUse synchronous or quorum commit where loss is unacceptable
Treating a standby as a backupA bad DROP TABLE replicates instantly to every standbyKeep real backups and PITR in addition to replicas
Practice
  1. Build a primary and one standby locally (containers work well) using pg_basebackup -R, and confirm writes on the primary appear on the standby.
  2. Query pg_stat_replication while generating load and read the lag columns.
  3. Make the standby synchronous, stop it, and observe what happens to commits on the primary.
Key takeaways
  • A standby is a physical copy that replays the primary's streamed WAL, optionally serving read-only queries.
  • Replication slots prevent lost WAL but can fill the primary's disk if abandoned.
  • Choose synchronous or quorum replication to avoid data loss, accepting latency; replicas are not backups.
