Failover & Switchover

Failover promotes a standby when the primary fails, and the hard part is making sure the old primary can never accept writes again.

§1Switchover and Failover

A switchover is a planned role swap, for maintenance or upgrades: stop writes, let a standby catch up fully, promote it, and demote the old primary to a standby. No data is lost. A failover is unplanned: the primary is gone, you promote the best remaining standby, and any commits not yet replicated are lost (with asynchronous replication).

SELECT pg_promote();                  -- on the standby: becomes a writable primary
-- or from the shell:  pg_ctl promote -D $PGDATA

SELECT pg_is_in_recovery();           -- true on a standby, false on a primary

Promotion creates a new timeline: a new branch of WAL history. Other standbys must switch to follow the new primary's timeline, and the old primary cannot simply rejoin because its history has diverged.

§2Split-Brain

Split-brain is two servers both believing they are the primary and accepting writes. The data diverges and cannot be merged automatically. It happens when a failover is triggered by a network partition, but the old primary is alive and still reachable by some clients.

Preventing it requires fencing: before promoting a standby, make certain the old primary is down, by powering it off (STONITH, "shoot the other node in the head"), revoking its network or storage access, or relying on a consensus system so only a node holding a leader lease may accept writes. Never run a failover script that promotes a standby merely because a ping failed.

To bring a former primary back as a standby, use pg_rewind, which rewinds its data directory to the point where the timelines diverged and then applies the new primary's changes, instead of a full re-clone.

§3Automation and Routing

Because correctness depends on agreement among nodes, use a proven tool rather than a home-made script. Patroni (with etcd, Consul, or ZooKeeper as a distributed store holding the leader key), repmgr, and pg_auto_failover each detect failure, elect a standby, fence the old primary, and reconfigure the others. Managed cloud services provide this behind a single endpoint.

Applications must find the new primary. Common approaches: a virtual IP, a load balancer such as HAProxy that health-checks each node's role, DNS updates (beware of TTLs), or client-side multi-host connection strings.

postgresql://db1,db2,db3/shop?target_session_attrs=read-write

libpq tries each host in turn and connects to the one that accepts writes. Applications must also handle reconnects: connections break during failover, in-flight transactions are lost, and writes need retries with idempotency. Practice failovers regularly; the first real one should not be the first one.

The key insight Promotion is easy; safety is not. A failover system is only correct if it can guarantee that at most one node is a writable primary at any moment.

§4Common Mistakes

MistakeWhat HappensFix
Promoting a standby on a failed health check aloneThe old primary may still be alive, leading to split-brainFence the old primary or use a consensus-based tool like Patroni
Re-attaching the old primary without checking timelinesDiverged data and replication errorsUse pg_rewind or re-clone it as a standby
Never rehearsing failoverUnknown recovery time, broken application reconnects, surprises under pressureRun planned switchovers and game days regularly
Practice
  1. Promote a standby with pg_promote(), then use pg_rewind to turn the old primary into a standby of the new one.
  2. Describe the sequence of events that could cause split-brain in a network partition and what fencing would prevent it.
  3. Use a multi-host connection string with target_session_attrs=read-write and observe which host is chosen before and after a switchover.
Key takeaways
  • Switchover is planned and lossless; failover is unplanned and may lose unreplicated commits.
  • Split-brain is the main danger; fencing and consensus-based leadership prevent it.
  • Use proven tooling for automation, make clients reconnect and retry safely, and rehearse failovers.
