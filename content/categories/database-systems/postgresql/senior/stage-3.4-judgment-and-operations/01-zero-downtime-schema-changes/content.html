Zero-Downtime Schema Changes

Changing a big, busy table without downtime means splitting each change into small, compatible steps and controlling the locks every step takes.

§1Know the Lock and the Rewrite

Two things make a schema change dangerous on a large table: the lock it takes and whether it rewrites the table. Even a change that is instant on disk needs a brief ACCESS EXCLUSIVE lock, and if a long query holds the table, your ALTER waits, and every query behind it waits too (Lesson 2.3.3).

ChangeBehavior on a large table
ADD COLUMN (nullable, or with a constant default)Metadata only since PostgreSQL 11; instant
ADD COLUMN with a volatile default (random())Rewrites the table
ALTER COLUMN TYPEUsually rewrites the table (a few binary-compatible changes do not)
SET NOT NULLScans the table under a strong lock, unless a validated CHECK (col IS NOT NULL) exists (PostgreSQL 12+)
ADD FOREIGN KEY / ADD CHECKScans; use NOT VALID, then VALIDATE CONSTRAINT with a weaker lock
CREATE INDEXBlocks writes; use CONCURRENTLY
DROP COLUMNInstant, but the application must have stopped using it
SET lock_timeout = '3s';          -- give up rather than queue behind a long query
SET statement_timeout = '15min';
ALTER TABLE orders ADD COLUMN currency text NOT NULL DEFAULT 'USD';   -- fast (constant default)

Wrap risky ALTERs in a retry loop with a short lock_timeout, so that a failure costs nothing and the next attempt tries again.

§2Expand and Contract

The reliable pattern for changes that are not instant (renaming a column, changing a type, splitting a table) is expand, migrate, contract. At every step the old and new application versions both work.

  1. Expand: add the new column or table alongside the old (nullable, no rewrite).
  2. Dual-write: deploy application code that writes both old and new (or a trigger keeps them in sync).
  3. Backfill existing rows in small batches, outside one giant transaction.
  4. Switch reads to the new column; verify.
  5. Contract: stop writing the old column, then drop it in a later release.
-- Step 3: batched backfill, small transactions, each one commits quickly
UPDATE orders SET amount_cents = (total * 100)::bigint
WHERE id >= 100000 AND id < 110000 AND amount_cents IS NULL;
-- repeat for the next id range, pausing briefly between batches to let replicas keep up

Each step is a separate deploy, and each is individually reversible. A rename is then not RENAME COLUMN (which breaks running code instantly) but add, copy, switch, drop.

§3Safe Constraints and Indexes

Add constraints in two phases so the expensive validation runs with a light lock.

-- 1. Enforce for new rows only (brief lock)
ALTER TABLE orders ADD CONSTRAINT orders_customer_fk
    FOREIGN KEY (customer_id) REFERENCES customers (id) NOT VALID;
-- 2. Validate existing rows (does not block normal reads and writes)
ALTER TABLE orders VALIDATE CONSTRAINT orders_customer_fk;

-- NOT NULL without a long scan under lock:
ALTER TABLE orders ADD CONSTRAINT orders_cust_nn CHECK (customer_id IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_cust_nn;
ALTER TABLE orders ALTER COLUMN customer_id SET NOT NULL;     -- fast: uses the validated check
ALTER TABLE orders DROP CONSTRAINT orders_cust_nn;

-- Unique constraint from an index built concurrently
CREATE UNIQUE INDEX CONCURRENTLY orders_ref_uq ON orders (ref);
ALTER TABLE orders ADD CONSTRAINT orders_ref_uq UNIQUE USING INDEX orders_ref_uq;

Tools such as pgroll, reshape, and online schema-change utilities automate parts of this, but understanding the underlying lock behavior lets you review what they do. Rehearse every migration on a production-sized copy and measure the lock time.

The key insight On a large table, the question is never only "is this ALTER fast?" but "what lock does it need, and what will queue behind it?" Short lock timeouts and small compatible steps make changes boring.

§4Common Mistakes

MistakeWhat HappensFix
Running ALTER TABLE with no lock_timeout on a busy tableIt queues behind a long query and blocks everythingSet lock_timeout and retry
Renaming or retyping a column in one stepRunning application code breaks, or the table is rewritten under a lockUse expand and contract in separate deploys
Backfilling millions of rows in one UPDATELong transaction, bloat, replica lag, and held locksBackfill in small batches with pauses
Practice
  1. On a million-row table, compare the time of ADD COLUMN ... DEFAULT 'x' with ALTER COLUMN TYPE and explain the difference.
  2. Add a foreign key using NOT VALID and VALIDATE and watch the lock types in pg_locks at each stage.
  3. Plan an expand-and-contract migration to rename total to amount_cents, listing each deploy.
Key takeaways
  • Evaluate every change by the lock it takes and whether it rewrites the table.
  • Use lock_timeout, retries, NOT VALID then VALIDATE, and CONCURRENTLY to keep locks short.
  • Expand, dual-write, backfill in batches, switch, then contract: each step compatible with old and new code.
