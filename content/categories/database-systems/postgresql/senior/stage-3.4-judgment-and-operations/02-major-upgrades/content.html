Major Upgrades

A major-version upgrade is a planned project with a tested path forward and a decided way back.

§1Minor vs Major Upgrades

Postgres releases a major version about once a year (such as 17 to 18) and supports each for five years. Minor releases (18.5 to 18.6) contain only bug and security fixes, never format changes: stop and start the server with the new binaries, no migration needed. Apply them promptly, and keep a regular patching routine.

A major upgrade changes the on-disk format and system catalogs, so the data directory cannot simply be opened by new binaries. Your options:

MethodDowntimeNotes
pg_dump / pg_restoreProportional to database sizeSimple and clean; fine for small databases
pg_upgradeMinutes, mostly independent of size (with --link)The standard in-place method
Logical replicationSeconds at cutoverMost flexible; needs more setup (Lesson 3.2.3)

§2pg_upgrade in Practice

pg_upgrade creates a new cluster with the new binaries and transfers the data and catalogs. With --link it hard-links data files instead of copying them, which is very fast and needs no extra space, but means the old cluster cannot be safely started once the new one has run. --clone (on file systems that support it) and --copy are alternatives with different trade-offs.

pg_upgrade --check \
  -b /usr/lib/postgresql/17/bin  -B /usr/lib/postgresql/18/bin \
  -d /var/lib/postgresql/17/main -D /var/lib/postgresql/18/main      # dry run: finds problems

pg_upgrade --link  ...same arguments without --check...

vacuumdb --all --analyze-in-stages          # rebuild planner statistics after the upgrade

Before PostgreSQL 18, pg_upgrade did not carry over planner statistics, so queries could be slow until ANALYZE finished; newer versions preserve most of them, but still verify. Also update extensions (ALTER EXTENSION ... UPDATE), check that every extension has a build for the new version, and reindex any indexes the release notes flag.

§3Plan the Way Back

Decide before the upgrade day what happens if it goes wrong, and test that path too.

  • Rehearse on a production-sized copy with real extensions and the real application; time every step and record it.
  • Read the release notes for each version you cross: removed features, changed defaults, and incompatibilities in queries, drivers, and extensions.
  • Back up immediately before starting, and keep it. With --link, once the new cluster has started, the old directory is not a valid fallback.
  • Rollback options: restore the backup (slow, loses data written after the upgrade), or use logical replication in reverse, keeping the old cluster as a subscriber of the new one so you can switch back with little loss.
  • Application readiness: drivers, ORMs, and SQL that depends on version-specific behavior must be tested against the new version first.
  • Define success and a deadline: specific checks, a rollback decision point, and who makes the call.

A well-run upgrade is dull because every surprise was found in rehearsal.

The key insight The upgrade method matters less than the rehearsal and the rollback plan. If you cannot describe how you would go back, you are not ready to go forward.

§4Common Mistakes

MistakeWhat HappensFix
Upgrading production first, and testing laterIncompatible extensions or queries are found during the outageRehearse on a production-sized copy, including the application
Using pg_upgrade --link without a backupNo fallback once the new cluster startsTake and verify a backup before the upgrade
Skipping ANALYZE after the upgradeMissing statistics produce terrible plans until autovacuum catches upRun vacuumdb --analyze-in-stages and verify key queries
Practice
  1. Run pg_upgrade --check between two major versions on a test cluster and read the report.
  2. Write an upgrade runbook with steps, expected durations, success checks, and the rollback decision point.
  3. Outline how you would upgrade with logical replication, and how you would keep a reverse path open.
Key takeaways
  • Minor releases are drop-in fixes; major releases need pg_upgrade, dump and restore, or logical replication.
  • pg_upgrade --link is fast but removes the old cluster as a fallback; back up first and analyze after.
  • Rehearse, read the release notes, and plan rollback before the day.
