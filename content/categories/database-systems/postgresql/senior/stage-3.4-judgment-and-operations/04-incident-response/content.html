Incident Response

Most Postgres emergencies are one of a few recurring shapes, and calm diagnosis with a few known queries beats improvising under pressure.

§1Runaway Queries and Lock Pileups

Symptoms: high CPU or load, requests timing out, connections piling up. First move: look at what is running and what is blocked.

SELECT pid, now() - query_start AS runtime, state, wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blocked_by, left(query, 100) AS query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY runtime DESC;

For a runaway query, cancel it with pg_cancel_backend(pid), and use pg_terminate_backend(pid) if that is not enough. For a lock pileup, find the *root* blocker (a session that blocks others but is not itself blocked, often idle in transaction) and end that one. Killing the many victims changes nothing. Afterwards, add statement_timeout, lock_timeout, and idle_in_transaction_session_timeout for the application roles so it cannot recur silently. Capture a snapshot of pg_stat_activity *before* killing anything, for the postmortem.

Too many connections (FATAL: sorry, too many clients already) calls for the same triage plus pooling: find who holds the connections, then fix pool sizes or add PgBouncer.

§2Disk Full

When the disk fills, Postgres stops accepting writes and may shut down. The usual culprits:

  • WAL in pg_wal: a stuck replication slot, an abandoned standby, or a failing archive_command.
  • Temporary files from huge sorts or runaway queries.
  • Bloat or rapid growth from a large load or a long transaction blocking vacuum.
  • Logs that grew without rotation.
SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots ORDER BY pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) DESC;

SELECT pg_drop_replication_slot('abandoned_slot');     -- if truly unused
SELECT * FROM pg_stat_archiver;                         -- is archiving failing?

Never delete files from pg_wal by hand: the server may need them for crash recovery, and removing the wrong ones corrupts the cluster. Free space by removing unrelated files (old logs, backups), dropping a dead slot, or adding disk, then fix the cause. Prevent it with alerts at 70 and 85 percent usage, max_slot_wal_keep_size, and monitoring of slot lag.

§3Transaction ID Wraparound and the Runbook

Transaction IDs are 32-bit, and vacuum must freeze old rows to avoid wraparound (Lesson 2.4.4). If freezing falls far enough behind, Postgres first logs warnings ("database must be vacuumed within N transactions") and finally refuses to start new transactions that need an ID, effectively stopping writes to protect the data.

SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;
-- Find what blocks freezing: old transactions, prepared transactions, stale slots
SELECT * FROM pg_prepared_xacts;
SELECT slot_name, xmin, catalog_xmin FROM pg_replication_slots;

Remove whatever holds the horizon, then run VACUUM (FREEZE, VERBOSE) on the oldest tables, starting with the largest age(relfrozenxid); follow the exact HINT in the error message for your version. The best response is prevention: alert far earlier, at around a billion of age.

Keep a written runbook for each emergency above: the diagnostic queries, who has authority to terminate sessions, how to communicate status, and where the dashboards are. During an incident, stabilize first, diagnose second, fix the root cause third, and hold a blameless postmortem afterwards.

The key insight In an emergency, find the root cause before killing anything: the session at the head of the blocking chain, the oldest transaction, or the stuck slot. Treat symptoms and the cause returns in minutes.

§4Common Mistakes

MistakeWhat HappensFix
Deleting WAL files to free disk spacePossible unrecoverable corruption of the clusterFix the cause (slot or archive) and let Postgres remove WAL itself
Terminating blocked sessions instead of the blockerThe blocker keeps its locks and the queue refillsTrace pg_blocking_pids() to the root
Having no runbook until the first incidentSlow, inconsistent response under stressWrite and rehearse runbooks for the common failure shapes
Practice
  1. Create a lock pileup with three sessions, then locate and end the root blocker using only pg_stat_activity.
  2. Create a replication slot, stop consuming it, generate WAL, and observe retained WAL growth; then drop the slot.
  3. Write a one-page runbook for "disk is 95% full" with commands and decision points.
Key takeaways
  • Start with pg_stat_activity and pg_blocking_pids; kill the root blocker, not the victims.
  • Disk-full incidents usually come from stuck slots, failing archiving, temp files, or bloat; never delete pg_wal files by hand.
  • Alert early on connections, disk, slot lag, and transaction ID age, and keep rehearsed runbooks.
