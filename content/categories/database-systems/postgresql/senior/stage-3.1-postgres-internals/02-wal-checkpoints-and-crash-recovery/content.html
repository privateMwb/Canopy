WAL, Checkpoints & Crash Recovery

Postgres writes every change to a sequential log before touching data files, so after a crash it can replay the log and recover exactly what was committed.

§1Write-Ahead Logging

Changes to data pages happen in memory (the buffer cache), and writing each modified page to disk at commit time would be slow and random. Instead, the rule is write-ahead: before a modified page may reach disk, a record describing the change must be safely in the WAL, an append-only log in pg_wal. At COMMIT, Postgres flushes the WAL up to that transaction's commit record (an fsync), and only then reports success. Sequential appends are fast, and the data pages can be written later, in the background.

SELECT pg_current_wal_lsn();                      -- current position in the log
SELECT pg_walfile_name(pg_current_wal_lsn());     -- which 16 MB segment file
SHOW synchronous_commit;                          -- on (default), off, local, remote_write, remote_apply

That flush is what durability means in practice. Setting synchronous_commit = off skips waiting for the flush: it can lose the last few moments of commits after a crash, but never corrupts the database, and is a legitimate trade for some workloads.

§2Checkpoints

A checkpoint forces all dirty pages that were modified before a certain point to be written to the data files, then records that point in the WAL. It bounds recovery time: after a crash, replay need only begin at the last checkpoint's redo point.

checkpoint_timeout = 5min        # time-based trigger
max_wal_size = 4GB               # size-based trigger
checkpoint_completion_target = 0.9   # spread the writes across the interval

SELECT * FROM pg_stat_checkpointer;   -- PostgreSQL 17+; older: pg_stat_bgwriter

Checkpoints are expensive: a flood of writes can cause latency spikes. Postgres spreads the I/O across most of the interval. After a checkpoint, the first change to each page writes the entire page image to the WAL (full-page writes), protecting against torn pages from a crash mid-write, which is why WAL volume jumps right after checkpoints. Tune with max_wal_size (fewer, larger-interval checkpoints) and watch with log_checkpoints = on.

§3Crash Recovery and Replication

After an unclean shutdown, Postgres starts in recovery: it finds the last checkpoint, then replays every WAL record after the redo point, reapplying changes to data pages that were lost from memory. Transactions without a commit record in the log are simply treated as aborted, and MVCC hides their row versions. No manual repair is needed, and nothing committed is lost, provided the disk honored its flush promises.

The same mechanism powers other features: a standby is a server continuously replaying WAL from a primary (streaming replication, Stage 3.2), PITR replays archived WAL (Stage 2.4), and logical replication decodes WAL into row changes. Since WAL is the source of truth for everything that changes, its volume, retention, and the disk it lives on deserve attention. A full pg_wal volume stops the database, usually because of a failing archive command or a stalled replication slot.

The key insight The WAL is the database's real commit point. The data files can be behind, even inconsistent, at any moment; the log is what guarantees the result is correct after a crash.

§4Common Mistakes

MistakeWhat HappensFix
Disabling fsync to speed things upA crash or power loss can corrupt the entire clusterLeave fsync on; use synchronous_commit = off if you can tolerate losing recent commits
Letting pg_wal live on a small volumeA stalled archive or replication slot fills the disk and stops the serverSize it generously and alert on usage and slot lag
Setting max_wal_size too lowFrequent forced checkpoints and write spikesRaise it until most checkpoints are time-triggered
Practice
  1. Insert rows and compare pg_current_wal_lsn() before and after to measure WAL generated; use pg_wal_lsn_diff.
  2. Enable log_checkpoints and generate load to see whether checkpoints are time- or size-triggered.
  3. Kill a test server with kill -9, restart it, and read the recovery messages in the log.
Key takeaways
  • WAL records are flushed to disk before a commit returns; data pages are written later.
  • Checkpoints bound recovery time and cause bursts of writes, with full-page images following each one.
  • Crash recovery replays WAL from the last checkpoint, and the same log drives standbys, PITR, and logical replication.
