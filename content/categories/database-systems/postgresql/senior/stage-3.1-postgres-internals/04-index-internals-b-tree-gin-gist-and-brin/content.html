Index Internals: B-tree, GIN, GiST & BRIN

Postgres ships several index types, each laid out differently on disk and built for a different shape of query.

§1B-tree and Hash

B-tree is the default and the only type that supports ordering and unique constraints. Pages form a tree: a root page, internal pages of separator keys, and leaf pages holding the key and the heap pointer. Leaves are linked, so range scans walk sideways. Page splits keep the tree balanced, and deduplication (since PostgreSQL 13) shrinks indexes with many repeated keys.

Hash indexes support only equality (=). Since PostgreSQL 10 they are crash-safe and WAL-logged. They are rarely faster than a B-tree in practice and offer no ordering or uniqueness, so they are a niche choice.

CREATE INDEX ON events USING btree (created_at);
CREATE INDEX ON sessions USING hash (token);
\di+                        -- sizes

§2GIN and GiST

GIN (Generalized Inverted Index) maps each *element* inside a value to the rows containing it, like the index at the back of a book. It suits values that contain many keys: arrays, jsonb, and full-text tsvector. Lookups are fast, while updates are slower; GIN buffers new entries in a pending list (fastupdate) and merges them later.

GiST (Generalized Search Tree) is a framework for tree indexes over data with no total order: geometric shapes (PostGIS), ranges, nearest-neighbor search, and trigram similarity. It supports operators like "overlaps", "contains", and "distance".

CREATE INDEX ON articles USING gin (tags);                       -- text[] containment: tags @> ARRAY['db']
CREATE INDEX ON places    USING gist (location);                 -- geometry / spatial
CREATE INDEX ON bookings  USING gist (room_id, during);          -- range overlap (with btree_gist)
ALTER TABLE bookings ADD EXCLUDE USING gist (room_id WITH =, during WITH &&);   -- no double booking

The exclusion constraint above uses a GiST index to forbid overlapping reservations for the same room, something a unique B-tree cannot express.

§3BRIN and SP-GiST, and Choosing

BRIN (Block Range Index) stores only a summary (such as min and max) for each range of table pages, so the index is tiny. It works when the column's value correlates with the physical row order, for example an append-only table with an increasing timestamp. It narrows a search to a few page ranges, then the rows are checked.

SP-GiST supports space-partitioned structures such as tries and quadtrees, useful for IP ranges, phone-prefixes, and points.

CREATE INDEX events_ts_brin ON events USING brin (created_at) WITH (pages_per_range = 64);
-- tens of KB for a billion-row table, versus gigabytes for a B-tree

SELECT correlation FROM pg_stats WHERE tablename = 'events' AND attname = 'created_at';
WorkloadIndex
Equality, ranges, ordering, uniquenessB-tree
Elements inside arrays, jsonb, full textGIN
Geometry, ranges, nearest neighbor, exclusionGiST
Huge, naturally ordered, append-only tablesBRIN

Match the index to the *operators* your queries use; a plain B-tree cannot answer @> or &&.

The key insight An index type is a data structure paired with a set of operators. Pick the structure whose operators match the question your query asks.

§4Common Mistakes

MistakeWhat HappensFix
Creating a B-tree on a jsonb or array column and using @>The index is not usable for containmentUse a GIN index with the matching operator class
Using BRIN on a column unrelated to physical orderEvery range matches, so the index narrows nothingCheck correlation in pg_stats; use B-tree otherwise
Expecting a GIN index to update as quickly as a B-treeSlower inserts and bursts of pending-list mergingAccept the trade-off, or tune gin_pending_list_limit and fastupdate
Practice
  1. Create GIN and B-tree indexes on a text[] column and use EXPLAIN to show which operators each supports.
  2. Build a BRIN index on a time-ordered table and compare its size with a B-tree on the same column.
  3. Add an exclusion constraint with a GiST index to prevent overlapping bookings.
Key takeaways
  • B-tree handles ordering and equality; GIN indexes elements inside values; GiST handles geometry, ranges, and exclusion.
  • BRIN is tiny and effective only when values correlate with physical order.
  • Choose the index type by the operators your queries use.
