Foreign Data Wrappers & Analytics Patterns

Foreign data wrappers let Postgres query other systems as if they were tables, and a few patterns shape data for reporting without a separate warehouse.

§1Foreign Data Wrappers

A foreign data wrapper (FDW) teaches Postgres to read, and sometimes write, an external data source through ordinary SQL. postgres_fdw connects to another Postgres server, file_fdw reads CSV files, and third-party wrappers reach MySQL, Oracle, MongoDB, S3-hosted files, REST APIs, and more.

CREATE EXTENSION postgres_fdw;

CREATE SERVER reporting_srv FOREIGN DATA WRAPPER postgres_fdw
    OPTIONS (host 'reports.internal', dbname 'warehouse', port '5432');

CREATE USER MAPPING FOR app_user SERVER reporting_srv
    OPTIONS (user 'reader', password '...');

IMPORT FOREIGN SCHEMA public LIMIT TO (sales_summary)
    FROM SERVER reporting_srv INTO staging;

SELECT * FROM staging.sales_summary WHERE day >= current_date - 7;

This lets you join local and remote data in one query, migrate data between systems with INSERT ... SELECT, or expose a legacy database during a transition.

§2Pushdown and Its Limits

A foreign scan is only fast when the work happens remotely. postgres_fdw can push WHERE conditions, some joins between tables on the same server, sorts, and aggregates down to the remote side, so only the needed rows travel. The plan shows what was sent.

EXPLAIN (VERBOSE) SELECT * FROM staging.sales_summary WHERE day >= '2026-10-01';
 Foreign Scan on staging.sales_summary
   Remote SQL: SELECT day, total FROM public.sales_summary WHERE ((day >= '2026-10-01'::date))

Conditions that call local-only functions, or joins between tables on different servers, cannot be pushed, so Postgres fetches all the rows and processes them locally, which can be very slow. Foreign tables also have no local indexes or statistics unless you run ANALYZE on them, and each query pays network latency. Use FDWs for convenience, occasional queries, and migrations, not as a high-throughput data path.

§3Analytics Patterns Inside Postgres

Many teams run reporting on their operational Postgres, and a few patterns keep that sustainable:

  • Run it on a replica (Lesson 3.2.5) so heavy queries do not compete with transactions.
  • Pre-aggregate: materialized views or rollup tables (daily_sales) refreshed on a schedule or incrementally with INSERT ... ON CONFLICT DO UPDATE.
  • Partition fact tables by time and use BRIN indexes on append-only timestamps for cheap range scans.
  • Shape data for questions: a star schema (a central fact table with dimension tables) makes reporting queries simple and fast.
  • Parallel query (max_parallel_workers_per_gather) accelerates large scans and aggregates.
INSERT INTO daily_sales (day, orders, revenue)
SELECT date_trunc('day', placed_at)::date, count(*), sum(total)
FROM orders WHERE placed_at >= current_date - 1 AND placed_at < current_date
GROUP BY 1
ON CONFLICT (day) DO UPDATE SET orders = EXCLUDED.orders, revenue = EXCLUDED.revenue;

When data volume, query complexity, or the number of analysts outgrows this, a columnar warehouse or lakehouse is the better tool. Extensions for columnar storage and time series exist, and some cloud services bundle them; evaluate them with Lesson 3.3.1's checklist.

The key insight An FDW makes remote data look local, but it does not make it fast. Always check EXPLAIN VERBOSE to see what was pushed down and what was dragged across the network.

§4Common Mistakes

MistakeWhat HappensFix
Joining two large foreign tables from different serversAll rows are pulled over the network and joined locallyCopy the data locally, or run the join on one server
Running heavy reports on the primaryAnalytic scans compete with transactions and slow the applicationUse a replica and pre-aggregated tables
Using an FDW as a permanent high-volume pipelineLatency and fragility on every queryReplicate or load the data (logical replication, ETL) instead
Practice
  1. Set up postgres_fdw between two databases and use EXPLAIN (VERBOSE) to see the remote SQL for a filtered query.
  2. Build a daily_sales rollup table and a job that refreshes yesterday's row idempotently.
  3. Compare the time of an aggregate over a raw fact table with the same query against its rollup.
Key takeaways
  • FDWs expose external data as tables; postgres_fdw can push filters, joins, and aggregates to the remote server.
  • Check Remote SQL in EXPLAIN VERBOSE; cross-server joins and local-only functions are not pushed down.
  • For reporting, use replicas, rollups, time partitioning, and a star-schema shape, and move to a warehouse when you outgrow them.
