PostGIS & Geospatial Data

PostGIS adds geometry and geography types, spatial functions, and GiST indexes, which turn "find things near here" into an indexed query.

§1Geometry and Geography

PostGIS is the standard extension for geospatial data in Postgres. It provides two key types: geometry (planar coordinates; fast, with many functions) and geography (coordinates on the earth's surface, with distances in meters). Every value carries an SRID, a number naming its coordinate reference system; 4326 is the familiar GPS longitude/latitude (WGS 84).

CREATE EXTENSION postgis;

CREATE TABLE places (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name     text NOT NULL,
    location geography(Point, 4326) NOT NULL
);

INSERT INTO places (name, location)
VALUES ('Wellington Station', ST_SetSRID(ST_MakePoint(174.7807, -41.2787), 4326)::geography);

Argument order is longitude, then latitude (x, y). Reversing them is the most common PostGIS bug and silently places points on the wrong side of the world.

§2Spatial Queries and Indexes

Spatial indexes use GiST, which indexes the bounding box of each shape. Functions that are index-aware (ST_DWithin, ST_Intersects, ST_Contains) use it; computing ST_Distance(...) < x does not.

CREATE INDEX places_location_gix ON places USING gist (location);

-- Everything within 500 metres of a point (index-assisted)
SELECT name
FROM places
WHERE ST_DWithin(location, ST_SetSRID(ST_MakePoint(174.78, -41.29), 4326)::geography, 500);

-- Five nearest places, using the KNN distance operator <-> with the index
SELECT name, location <-> ST_SetSRID(ST_MakePoint(174.78, -41.29), 4326)::geography AS metres
FROM places
ORDER BY location <-> ST_SetSRID(ST_MakePoint(174.78, -41.29), 4326)::geography
LIMIT 5;

-- Which district contains this point?
SELECT d.name FROM districts d WHERE ST_Contains(d.boundary, some_point_geom);

Distances on geography are in meters on the spheroid. For heavy local analysis, store geometry in a projected system suited to your region (ST_Transform) so planar math is accurate and fast. Never mix SRIDs in one query without transforming.

§3Choosing PostGIS

PostGIS handles points, lines, polygons, rasters (with an extension), routing (with pgRouting), and vector tiles for maps. It is the right tool when location is part of your relational data: stores near customers, delivery zones, parcels, geofences, tracking, region lookups. Because the data lives beside your other tables, you can join spatial and business data in one query, in one transaction.

Plan for data size: geometry with many vertices (detailed coastlines) is large, so simplify (ST_Simplify) for display and index only what you query. For simple needs, such as nearest point by latitude/longitude on a small table, built-in types with cube and earthdistance can suffice, but PostGIS is the safer long-term choice once spatial requirements appear. Keep an eye on extension versioning during major upgrades; PostGIS ships its own libraries (GEOS, PROJ, GDAL) that must match.

The key insight Use index-aware predicates: ST_DWithin for "within distance" and ORDER BY <-> for nearest neighbors. Writing the same question as ST_Distance(a, b) < x forces a scan.

§4Common Mistakes

MistakeWhat HappensFix
Passing latitude first to ST_MakePointPoints land in the wrong placeUse ST_MakePoint(longitude, latitude)
Filtering with ST_Distance(...) < xNo index use, so a full scanUse ST_DWithin
Mixing SRIDs in one queryErrors or meaningless resultsTransform to a common SRID with ST_Transform
Practice
  1. Load 10,000 random points, add a GiST index, and compare EXPLAIN ANALYZE for ST_DWithin against ST_Distance < x.
  2. Find the five nearest points to a location with the <-> operator.
  3. Create a polygon table of regions and join points to the region containing each one.
Key takeaways
  • PostGIS adds geometry and geography types, each value tagged with an SRID; coordinates are longitude then latitude.
  • GiST spatial indexes accelerate ST_DWithin, ST_Intersects, ST_Contains, and <-> nearest-neighbor ordering.
  • Spatial data joins naturally with relational data, but mind SRIDs, geometry size, and extension versions.
