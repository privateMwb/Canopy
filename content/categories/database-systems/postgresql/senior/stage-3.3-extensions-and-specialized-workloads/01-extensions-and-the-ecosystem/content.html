Extensions & the Ecosystem

Extensions add types, functions, index methods, and whole features to Postgres, and choosing which ones to depend on is an engineering decision, not just a convenience.

§1Installing and Managing Extensions

An extension is a packaged set of SQL objects, and sometimes compiled code, that you install into a database with one command. Postgres ships dozens of them in its contrib collection, and a large ecosystem provides more.

SELECT name, default_version, installed_version, comment
FROM pg_available_extensions WHERE name LIKE 'pg_%' ORDER BY name;

CREATE EXTENSION IF NOT EXISTS pg_trgm;
ALTER EXTENSION pg_trgm UPDATE;
\dx                                  -- list installed extensions
DROP EXTENSION pg_trgm;               -- fails if objects depend on it, unless CASCADE

Extensions install per database, not per cluster. Creating one normally needs superuser, except extensions marked trusted (since PostgreSQL 13), which a user with CREATE privilege on the database may install. Managed services offer a fixed list, so check availability before you design around one.

Some extensions load code at server start and need shared_preload_libraries plus a restart; others are pure SQL and install instantly.

§3Evaluating a Third-Party Extension

An extension runs inside the database server, often as compiled C with full access to memory, so a bad one can crash or compromise the cluster. Treat the decision like adopting any critical dependency.

  • Maintenance: is it actively maintained, with releases for each new Postgres major version? Upgrades are blocked until it supports the target version.
  • Availability: is it offered by your managed provider, and at which version? Self-hosting an unsupported one may mean running your own servers.
  • License and governance: what is the license, and who controls the project?
  • Upgrade story: does ALTER EXTENSION UPDATE work smoothly, and does pg_upgrade handle it?
  • Blast radius: does it need shared_preload_libraries, superuser, or hooks into the planner? Those raise the risk.
  • Alternative: can plain SQL, a built-in feature, or an external service do the job with less coupling?

Pin and record extension versions in your infrastructure code, and test extension upgrades alongside major-version upgrades.

The key insight Extensions are Postgres's superpower and its biggest coupling risk. Every one you adopt becomes a constraint on upgrades, hosting, and recovery.

§4Common Mistakes

MistakeWhat HappensFix
Adding an extension without checking the managed service's listYou cannot install it in productionVerify availability and version before designing around it
Assuming CREATE EXTENSION is cluster-wideIt is missing in other databases and in new onesInstall it in each database that needs it, via migrations
Depending on an abandoned extensionIt blocks the next major-version upgradeCheck release history and maintainers first, and have an exit plan
Practice
  1. List installed and available extensions in your database and note which are trusted.
  2. Install pg_trgm and use it to index and search LIKE '%term%' queries; compare EXPLAIN before and after.
  3. Pick one third-party extension and write a half-page evaluation using the checklist above.
Key takeaways
  • Extensions package new types, functions, and index methods; they are installed per database.
  • contrib and the third-party ecosystem cover many needs, but each choice couples you to upgrades and hosting.
  • Evaluate maintenance, availability, upgrade path, and blast radius before depending on one.
