Covering Indexes & Index-Only Scans

A covering index carries extra columns so the query never visits the table, and an index-only scan is only as good as the visibility map.

§1Index-Only Scans

Normally an index lookup finds the matching row's location, then fetches the row from the table (the heap) to read other columns. If the index already contains every column the query needs, Postgres can answer from the index alone: an Index Only Scan.

CREATE INDEX orders_cust_total_idx ON orders (customer_id, total);

EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, total FROM orders WHERE customer_id = 42;

 Index Only Scan using orders_cust_total_idx on orders
   Index Cond: (customer_id = 42)
   Heap Fetches: 0

Skipping the heap saves random page reads, which is often the dominant cost for queries that return many rows.

§2INCLUDE Columns

You might want a column in the index only so it can be returned, not searched or sorted. INCLUDE adds such payload columns without making them part of the sort key, which keeps the key small and allows types without a B-tree ordering.

CREATE INDEX orders_cust_inc_idx ON orders (customer_id) INCLUDE (total, status);

SELECT total, status FROM orders WHERE customer_id = 42;     -- covered

CREATE UNIQUE INDEX users_email_inc ON users (email) INCLUDE (name);
-- uniqueness applies to email only; name rides along

Each included column makes the index bigger and every write more expensive. Cover only the hot, narrow, high-frequency queries; do not add columns speculatively.

§3The Visibility Map and Heap Fetches

Because of MVCC (Stage 2.3), an index entry alone does not say whether the row is visible to your transaction. Postgres consults the visibility map, which marks pages where every row is visible to everyone. For such pages it can trust the index; for others it must visit the heap anyway, shown as Heap Fetches in the plan.

The visibility map is maintained by VACUUM. A table that is updated heavily and not vacuumed recently will show many heap fetches, and an "Index Only Scan" will behave like a normal one.

VACUUM (ANALYZE) orders;       -- refreshes the visibility map and statistics

SELECT relname, relpages, relallvisible FROM pg_class WHERE relname = 'orders';

Mostly-append, rarely-updated tables benefit most. A very low Heap Fetches figure means the covering index is paying off.

The key insight An index-only scan is a promise the visibility map has to keep. If Heap Fetches stays high, vacuum the table, or accept that the table is too write-heavy for the technique.

§4Common Mistakes

MistakeWhat HappensFix
Adding wide columns to many indexes for coverageLarge indexes and slow writesCover only a few proven hot queries, with narrow columns
Expecting an Index Only Scan on a table that is never vacuumedHeap Fetches remain high and the benefit disappearsEnsure autovacuum keeps up, or run VACUUM after bulk loads
Selecting * from a table with a covering indexThe query needs columns the index lacks, so it reads the heapSelect only the columns the index includes
Practice
  1. Create a covering index with INCLUDE, run EXPLAIN (ANALYZE, BUFFERS), and read Heap Fetches.
  2. Update a large share of rows, re-run the query, and watch heap fetches rise; then VACUUM and re-test.
  3. Compare the size of an index with and without an INCLUDE column.
Key takeaways
  • An index-only scan answers the query from the index without visiting the table.
  • INCLUDE adds payload columns without making them part of the sort key.
  • The visibility map, kept up by VACUUM, determines how often heap fetches are still needed.
