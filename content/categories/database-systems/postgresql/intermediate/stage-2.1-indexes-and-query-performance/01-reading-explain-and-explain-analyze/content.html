Reading EXPLAIN & EXPLAIN ANALYZE

EXPLAIN shows the plan Postgres chose, and EXPLAIN ANALYZE runs the query so you can compare the plan's estimates with what actually happened.

§1Reading a Plan

A plan is a tree of nodes. Data flows from the leaves (scans) up to the root (the final result). Each node shows an estimated cost as startup..total in arbitrary planner units, the estimated rows, and the average row width in bytes.

EXPLAIN SELECT * FROM orders WHERE customer_id = 42;

 Index Scan using orders_customer_id_idx on orders  (cost=0.43..8.45 rows=1 width=40)
   Index Cond: (customer_id = 42)

Indentation shows nesting; the most indented nodes run first. Common nodes: Seq Scan (read the whole table), Index Scan and Index Only Scan, Bitmap Heap Scan (collect matching row locations, then read pages in order), Nested Loop / Hash Join / Merge Join, Sort, Aggregate. Plain EXPLAIN does not run the query, so it is safe on anything.

§2EXPLAIN ANALYZE

EXPLAIN ANALYZE executes the query and adds real measurements next to the estimates: actual time (milliseconds, startup..total, per loop), actual rows, and loops.

EXPLAIN (ANALYZE, BUFFERS)
SELECT c.email, count(*)
FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE o.placed_at >= now() - interval '7 days'
GROUP BY c.email;

 HashAggregate  (cost=...) (actual time=41.2..41.9 rows=830 loops=1)
   ->  Hash Join  (actual time=3.1..35.6 rows=9120 loops=1)
         ->  Seq Scan on orders o  (actual time=0.02..28.4 rows=9120 loops=1)
               Filter: (placed_at >= ...)
               Rows Removed by Filter: 990880
               Buffers: shared hit=6120 read=1210

It really runs the statement. For INSERT, UPDATE, or DELETE, wrap it: BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;. BUFFERS reports how many 8 kB pages came from cache (hit) versus disk or the OS (read); on PostgreSQL 18 it is included automatically with ANALYZE. Multiply a node's actual time by its loops to get its total time.

§3Finding Where the Time Goes

Read the plan with three questions:

  1. Which node has the largest actual time (after accounting for loops, and subtracting its children's time)?
  2. Do estimates match reality? A node with rows=1 estimated but rows=250000 actual means the planner chose its strategy on bad information, which is the usual root cause of a slow plan (see the statistics lesson).
  3. Is a scan reading far more than it returns? Rows Removed by Filter: 990880 on a node that returns 9,120 rows suggests an index on the filter column.

A Seq Scan is not automatically bad: reading most of a table sequentially is the fastest plan. It becomes a problem when it throws away almost everything it reads. Always check Execution Time at the bottom and compare runs; the first run may be slow because the cache was cold.

The key insight The biggest estimate-versus-actual gap in a plan is usually where the problem began. Fix the statistics or the query shape there, rather than tuning the slow node downstream.

§4Common Mistakes

MistakeWhat HappensFix
Running EXPLAIN ANALYZE on a DELETE or UPDATE without a transactionThe change is really appliedWrap it in BEGIN; ... ROLLBACK;
Judging by cost numbers aloneCosts are planner estimates in arbitrary units, not millisecondsCompare actual time and buffers
Timing a query onceCache state skews the first runRun it several times and compare, noting cold versus warm
Practice
  1. Run EXPLAIN (ANALYZE, BUFFERS) on a join query and mark the node with the largest self time.
  2. Find a node where estimated rows and actual rows differ by 10x or more.
  3. Run EXPLAIN ANALYZE on an UPDATE safely inside a rolled-back transaction.
Key takeaways
  • A plan is a tree: data flows from the most indented scans upward, and plain EXPLAIN does not execute the query.
  • EXPLAIN (ANALYZE, BUFFERS) runs the statement and shows actual time, rows, loops, and cache hits.
  • Look for large estimate-versus-actual gaps and scans that discard most of what they read.
