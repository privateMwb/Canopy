Statistics, ANALYZE & the Planner

The planner chooses plans from statistics about your data, so stale or missing statistics are a leading cause of surprisingly bad plans.

§1How the Planner Estimates

For each possible plan, Postgres estimates how many rows each step produces and prices the work. Those row counts come from statistics gathered by ANALYZE: the number of distinct values, the most common values and their frequencies, a histogram of the rest, the fraction of NULLs, and how well the physical row order correlates with the column order.

SELECT attname, n_distinct, null_frac, most_common_vals, correlation
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';

The estimated rows for WHERE status = 'new' is roughly (frequency of 'new') times (number of rows in the table). If those numbers are wrong, every later decision (join order, join method, index versus sequential scan) can be wrong too.

§2ANALYZE and Autovacuum

Autovacuum runs ANALYZE automatically when enough rows have changed, but it is not instant. After a bulk load, a big delete, or a migration that rewrites a table, run ANALYZE yourself.

ANALYZE orders;                       -- refresh statistics for one table
ANALYZE VERBOSE;                      -- whole database

SELECT relname, last_analyze, last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables ORDER BY n_mod_since_analyze DESC;

ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;   -- finer histogram
ANALYZE orders;

default_statistics_target (default 100) controls how detailed the samples are. Raising it for a skewed, important column gives better estimates at the cost of slightly slower ANALYZE and planning. Cost settings matter too: on SSDs, lowering random_page_cost from its default of 4 toward 1.1 tells the planner that index lookups are cheaper than it assumed.

§3Extended Statistics

By default the planner treats columns as independent and multiplies their selectivities. When columns are correlated (city and zip, country and currency), that product badly underestimates the rows, which leads to nested loops where a hash join would win.

CREATE STATISTICS addr_stats (dependencies, ndistinct, mcv)
    ON city, zip FROM addresses;
ANALYZE addresses;

SELECT * FROM pg_stats_ext WHERE statistics_name = 'addr_stats';

dependencies captures that one column determines another, ndistinct improves estimates for GROUP BY on several columns, and mcv records the most common *combinations*. Use extended statistics when EXPLAIN ANALYZE shows a multi-column filter estimated far too low.

The key insight When a plan is bad, ask first whether the planner was lied to. Check pg_stats, run ANALYZE, and compare estimated rows with actual rows before reaching for hints or rewrites.

§4Common Mistakes

MistakeWhat HappensFix
Bulk loading or deleting a large share of a table and moving onStatistics are stale and plans degrade until autovacuum catches upRun ANALYZE right after the change
Leaving random_page_cost at 4 on SSD storageThe planner overestimates index cost and picks sequential scansTune it from evidence, commonly toward 1.1 on SSDs
Assuming columns are independent when they are correlatedRow estimates are far too low and plans use the wrong join methodCreate extended statistics on the correlated columns
Practice
  1. Load a table, check pg_stats for a skewed column, and compare estimated versus actual rows on WHERE col = 'rare' and 'common'.
  2. Bulk-delete half a table, check n_mod_since_analyze, then ANALYZE and observe how the plan changes.
  3. Create extended statistics on two correlated columns and compare the row estimate before and after.
Key takeaways
  • Plans are chosen from estimated row counts that come from ANALYZE statistics in pg_stats.
  • Run ANALYZE after bulk changes; raise the statistics target on important skewed columns.
  • Extended statistics fix estimates for correlated columns that the planner would otherwise multiply as independent.
