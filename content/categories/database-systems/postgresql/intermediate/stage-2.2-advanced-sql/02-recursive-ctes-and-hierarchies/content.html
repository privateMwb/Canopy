Recursive CTEs & Hierarchies

A recursive CTE repeatedly joins its own output to a table, which is how plain SQL walks trees, org charts, and graphs.

§1The Shape of a Recursive CTE

Hierarchies store a parent pointer in each row: employees(id, name, manager_id). Finding everyone below a manager at any depth needs repetition, which WITH RECURSIVE provides. It has an anchor query (the starting rows) and a recursive query that references the CTE itself; they are combined with UNION ALL.

WITH RECURSIVE reports AS (
    SELECT id, name, manager_id, 1 AS depth
    FROM employees
    WHERE id = 7                                    -- anchor: start at employee 7

    UNION ALL

    SELECT e.id, e.name, e.manager_id, r.depth + 1
    FROM employees e
    JOIN reports r ON e.manager_id = r.id           -- recursive step
)
SELECT * FROM reports ORDER BY depth, name;

Postgres runs the anchor, then repeatedly runs the recursive part against only the rows produced by the previous round, and stops when a round produces no new rows.

§2Paths, Ancestors, and Aggregates

Walking *up* a tree is the same pattern pointing the other way. Carry an array of the path to display it or to sort in tree order.

WITH RECURSIVE chain AS (
    SELECT id, name, manager_id, ARRAY[name] AS path
    FROM employees WHERE manager_id IS NULL         -- the root(s)
    UNION ALL
    SELECT e.id, e.name, e.manager_id, c.path || e.name
    FROM employees e JOIN chain c ON e.manager_id = c.id
)
SELECT repeat('  ', cardinality(path) - 1) || name AS tree
FROM chain
ORDER BY path;

The same technique computes bills of materials (assemblies made of parts made of parts), category trees, thread replies, and folder sizes. You can aggregate over the result as with any CTE, for example sum(salary) for an entire subtree.

§3Cycles and Graphs

If the data contains a cycle (A reports to B, B to A), the recursion never ends. Protect against it. Since PostgreSQL 14, the CYCLE clause does this declaratively, and SEARCH controls depth-first or breadth-first ordering.

WITH RECURSIVE walk(node, next) AS (
    SELECT from_id, to_id FROM edges WHERE from_id = 1
    UNION ALL
    SELECT e.from_id, e.to_id FROM edges e JOIN walk w ON e.from_id = w.next
)
CYCLE node SET is_cycle USING path
SELECT * FROM walk WHERE NOT is_cycle;

Using UNION (not UNION ALL) also removes repeated rows, which can stop some cycles, but it costs a deduplication pass. For deep hierarchies that you query constantly, consider a materialized path column or the ltree extension; for very graph-heavy workloads, weigh Stage 3.4's "right tool" discussion.

The key insight Recursion needs a base case and a progress guarantee. The anchor is your base, and the join must move toward fewer remaining rows, or a CYCLE check must stop it.

§4Common Mistakes

MistakeWhat HappensFix
No protection against cycles in the dataThe query runs until memory or time runs outUse the CYCLE clause, a depth limit, or an explicit visited-path check
Putting the anchor and recursive parts in the wrong order or using UNION unintentionallyWrong results or unnecessary deduplication costAnchor first, then UNION ALL the recursive step
Recomputing a deep tree on every page viewRepeated heavy queriesCache the result or store a materialized path for hot hierarchies
Practice
  1. Create an employees table with manager_id and list every direct and indirect report of one manager with their depth.
  2. Print an indented tree by carrying a path array and ordering by it.
  3. Add a cycle to the data and use the CYCLE clause to prevent endless recursion.
Key takeaways
  • WITH RECURSIVE pairs an anchor query with a recursive step joined by UNION ALL.
  • Carry a path or depth column to display trees and to detect cycles.
  • Always guard recursion against cyclic data with CYCLE, a depth cap, or a visited check.
