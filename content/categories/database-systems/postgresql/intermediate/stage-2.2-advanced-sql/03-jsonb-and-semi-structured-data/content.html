JSONB & Semi-Structured Data

jsonb stores documents inside a relational row, with operators to query them and GIN indexes to make those queries fast.

§1json vs jsonb and the Core Operators

Postgres has two JSON types. json stores the exact text; jsonb stores a decomposed binary form that is faster to query, supports indexing, and drops duplicate keys and whitespace. Use jsonb almost always.

CREATE TABLE events (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    kind    text NOT NULL,
    payload jsonb NOT NULL
);

SELECT payload -> 'user'              FROM events;    -- jsonb value
SELECT payload ->> 'user'             FROM events;    -- as text
SELECT payload #>> '{user,address,city}' FROM events; -- nested path as text
SELECT * FROM events WHERE payload @> '{"plan": "pro"}';   -- contains
SELECT * FROM events WHERE payload ? 'coupon';             -- has top-level key

-> returns jsonb (so you can keep digging), ->> returns text. Cast to compare numbers: (payload ->> 'amount')::numeric > 100. The containment operator @> is the most useful for filtering and the one that indexes best.

§2Updating and Building JSON

jsonb values are replaced as a whole when stored, but you can change parts using functions and operators, then assign the result.

UPDATE events SET payload = payload || '{"seen": true}'                 WHERE id = 1;  -- merge keys
UPDATE events SET payload = jsonb_set(payload, '{user,name}', '"Ada"')  WHERE id = 1;  -- set a path
UPDATE events SET payload = payload - 'coupon'                          WHERE id = 1;  -- remove a key

SELECT jsonb_build_object('id', id, 'kind', kind) FROM events;
SELECT jsonb_agg(jsonb_build_object('id', id)) FROM events;             -- rows to a JSON array
SELECT jsonb_array_elements(payload -> 'items') FROM events;            -- array to rows

Postgres 17 added SQL/JSON query functions such as JSON_TABLE, JSON_QUERY, and JSON_VALUE, which map documents directly to relational rows. The older jsonb_path_query functions with SQL/JSON path syntax work on earlier versions.

§3Indexing with GIN, and When Not to Use JSONB

A GIN (Generalized Inverted Index) on a jsonb column indexes every key and value, so containment and key-existence queries avoid a sequential scan.

CREATE INDEX events_payload_gin ON events USING gin (payload);                  -- @>, ?, ?|, ?&
CREATE INDEX events_payload_path ON events USING gin (payload jsonb_path_ops);  -- smaller, faster, @> only

-- For one hot field, a plain expression index is often better:
CREATE INDEX events_plan_idx ON events ((payload ->> 'plan'));

A good rule: use regular columns for data you filter, join, constrain, or report on, and jsonb for the leftover that really varies per row (third-party webhook bodies, user preferences, sparse attributes). Documents give up foreign keys, NOT NULL, and type checking for the fields inside them, and updating one field rewrites the entire value. If every row has the same keys, they should be columns.

The key insight jsonb is an escape hatch, not a replacement for tables. Promote any field you filter or join on into a real column, and keep the flexible remainder in the document.

§4Common Mistakes

MistakeWhat HappensFix
Storing everything in one jsonb blobNo constraints, no foreign keys, and slow, awkward queriesUse columns for stable fields and jsonb for the variable part
Querying with ->> equality on an unindexed fieldA sequential scan over every documentAdd an expression index, or use @> with a GIN index
Comparing JSON numbers as text'9' sorts after '10'Cast: (payload ->> 'n')::numeric
Practice
  1. Store webhook-style events in a jsonb column and query by nested fields using ->, ->>, and @>.
  2. Add a GIN index and confirm with EXPLAIN that a containment query uses it.
  3. Use jsonb_set and || to update fields, and jsonb_array_elements to explode an array into rows.
Key takeaways
  • Use jsonb over json; -> keeps JSON, ->> gives text, @> tests containment.
  • A GIN index makes containment and key-existence queries fast; expression indexes serve single hot fields.
  • Keep relational data in columns; use jsonb only for genuinely variable attributes.
