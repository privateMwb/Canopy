Vacuum & Autovacuum

Autovacuum reclaims dead rows, refreshes statistics, and prevents transaction ID wraparound, and busy tables often need it tuned per table.

§1What Vacuum Does

VACUUM has four jobs: it marks space from dead tuples as reusable, updates the visibility map (enabling index-only scans), freezes old rows to prevent transaction ID wraparound, and, with ANALYZE, refreshes planner statistics. Plain VACUUM runs alongside normal traffic and does not shrink the file in most cases; the space is reused by later inserts and updates. VACUUM FULL rewrites the table to a smaller file but takes an exclusive lock, so avoid it on live tables.

VACUUM (VERBOSE, ANALYZE) orders;

You rarely run it by hand. The autovacuum launcher starts worker processes that vacuum tables automatically once enough rows have changed.

§2Autovacuum Triggers and Throttling

A table is vacuumed when dead tuples exceed autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * rows, by default 50 + 20% of the table. For a table with 100 million rows, that means waiting for 20 million dead rows before cleaning, which is far too late. Autovacuum is also throttled by cost settings so that it does not overwhelm the disks.

-- Tune a hot, large table individually
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor  = 0.01,     -- 1% instead of 20%
    autovacuum_analyze_scale_factor = 0.005,
    autovacuum_vacuum_cost_limit    = 2000      -- allow more work per cycle
);

-- Is autovacuum keeping up?
SELECT relname, n_dead_tup, last_autovacuum, autovacuum_count
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;

Global levers include autovacuum_max_workers (default 3), autovacuum_naptime, and the cost limit and delay. With log_autovacuum_min_duration set, the log shows how long each run took and how many tuples it removed or could not remove, a clue that a long transaction is holding things back.

§3Freezing and Wraparound

Transaction IDs are 32-bit numbers, and Postgres compares them circularly. Rows older than about two billion transactions would suddenly appear to be in the future unless they are frozen, marked as visible to everyone. Vacuum freezes old rows; autovacuum_freeze_max_age (default 200 million) forces an anti-wraparound vacuum on tables that approach the limit.

SELECT datname, age(datfrozenxid) AS xid_age FROM pg_database ORDER BY 2 DESC;
SELECT relname, age(relfrozenxid) FROM pg_class
WHERE relkind = 'r' ORDER BY 2 DESC LIMIT 10;

If freezing falls too far behind, Postgres eventually refuses new writes to protect data (Stage 3.4 covers the incident). Monitor age(datfrozenxid), alert well before one billion, and treat a long-running transaction or an abandoned replication slot as the usual cause when it keeps rising.

The key insight Scale factors that are fine for small tables are far too lax for large ones. Give big, hot tables their own autovacuum settings and watch that vacuum is finishing, not just starting.

§4Common Mistakes

MistakeWhat HappensFix
Disabling autovacuum because it "uses resources"Bloat, stale statistics, and eventually wraparound troubleTune its settings, never turn it off
Running VACUUM FULL on a busy tableAn exclusive lock blocks all access during the rewriteUse plain VACUUM, or an online tool like pg_repack
Leaving the default 20% scale factor on a 500-million-row tableVacuum starts only after 100 million dead rowsSet a small per-table scale factor, such as 0.01 or a fixed threshold
Practice
  1. Generate many updates on a table and watch n_dead_tup and last_autovacuum in pg_stat_user_tables.
  2. Set per-table autovacuum parameters for a large table and compare the vacuum frequency.
  3. Query age(datfrozenxid) for each database and describe what number would worry you.
Key takeaways
  • Vacuum reclaims dead tuples, updates the visibility map, freezes old rows, and ANALYZE refreshes statistics.
  • Default thresholds are proportional to table size; tune hot, large tables with per-table settings.
  • Never disable autovacuum; monitor transaction ID age to stay far from wraparound.
