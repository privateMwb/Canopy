WAL Archiving & Point-in-Time Recovery

A base backup plus a continuous archive of write-ahead log files lets you restore the database to any moment, such as the minute before a bad DELETE.

§1How Point-in-Time Recovery Works

Every change is first written to the write-ahead log (WAL). If you keep a physical base backup (a copy of the data directory) and every WAL file generated after it, you can restore the base backup and replay WAL up to a chosen moment. That is point-in-time recovery (PITR).

Logical dumps (pg_dump) restore only to the instant they were taken. PITR gives you a recovery point that is seconds old, and it lets you stop just *before* an accident.

base backup (Sunday 02:00) + WAL archive (continuous) -> restore to Tuesday 14:07:30

It also underpins standbys and is the standard answer to "someone ran DELETE without WHERE at 14:08".

§2Setting Up Archiving

Enable WAL archiving on the primary, then take base backups.

# postgresql.conf
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'   # example only

# base backup
pg_basebackup -D /backups/base_2026-10-29 -Ft -z -P

The archive_command must return success only after the file is safely stored, and a failing command makes WAL pile up on the primary until the disk fills. In practice, use a purpose-built tool instead of hand-written commands: pgBackRest, Barman, or WAL-G handle compression, encryption, retention, parallelism, verification, and storage in object stores such as S3. Monitor pg_stat_archiver for failures and growing lag.

§3Performing a Restore

To recover to a point in time, restore a base backup into an empty data directory, tell Postgres how to fetch archived WAL, set the target, and start.

# postgresql.conf (restore side)
restore_command = 'cp /archive/%f %p'
recovery_target_time = '2026-10-29 14:07:30+00'
recovery_target_action = 'promote'

# then create the signal file and start the server
touch $PGDATA/recovery.signal
pg_ctl start

Postgres replays WAL until the target, then promotes itself to a normal server. Check the data, and if the target was wrong, restore again with a different one. The hard part is not the commands but the rehearsal: restore regularly to a scratch machine, time it, and write down the procedure, because you will be doing it under pressure. Keep enough WAL and backup generations to cover your recovery window, and store them away from the primary.

The key insight A base backup is the starting point and the WAL archive is the timeline. Lose either one and you cannot reach the moment you need, so monitor the archive as closely as the database.

§4Common Mistakes

MistakeWhat HappensFix
Setting up archiving and never restoring from itThe first real restore reveals a missing WAL file or a wrong settingRehearse PITR on a schedule and time it
Ignoring archive_command failuresWAL accumulates on the primary until the disk is full and the server stopsAlert on pg_stat_archiver.failed_count and archive lag
Writing archive scripts by handSubtle bugs: partial files, no verification, no retentionUse pgBackRest, Barman, or WAL-G
Practice
  1. Enable archiving on a test server, take a base backup, make changes, and note a timestamp before a deliberate DROP TABLE.
  2. Restore the base backup to a new directory and recover to just before the drop; confirm the table is back.
  3. Check pg_stat_archiver and describe what you would alert on.
Key takeaways
  • PITR = a physical base backup plus continuous WAL archiving, replayed up to a chosen target.
  • Use a proven tool such as pgBackRest, Barman, or WAL-G, and monitor archive health.
  • Rehearse restores regularly; recovery time and procedure matter as much as the backup itself.
