Configuration That Matters

A handful of Postgres settings account for most tuning gains, and each one should be changed because a measurement says so.

§1Where Settings Live

Settings come from postgresql.conf, postgresql.auto.conf (written by ALTER SYSTEM), per-database and per-role overrides, and the session. The pg_settings view shows the current value, its source, and whether a change needs a reload or a restart.

SHOW shared_buffers;
SELECT name, setting, unit, source, context FROM pg_settings WHERE name = 'work_mem';

ALTER SYSTEM SET work_mem = '32MB';
SELECT pg_reload_conf();                       -- enough for context = 'sighup' or 'user'

ALTER ROLE report_user SET work_mem = '256MB'; -- override for one role
SET LOCAL work_mem = '256MB';                  -- for one transaction

A context of postmaster means a restart is required (for example shared_buffers). Keep configuration in version control or configuration management so changes are reviewed and reproducible.

§2The Settings That Matter Most

SettingWhat it doesStarting point
shared_buffersPostgres's own page cacheAbout 25% of RAM on a dedicated server
effective_cache_sizePlanner's guess of total cache (Postgres plus OS)50 to 75% of RAM
work_memMemory per sort or hash operation, per node, per connection4 to 64 MB; raise for specific roles
maintenance_work_memMemory for VACUUM and CREATE INDEX256 MB to 2 GB
max_wal_sizeHow much WAL accumulates between checkpointsRaise (e.g. 4 to 16 GB) if checkpoints fire too often
random_page_costPlanner's cost of non-sequential readsAbout 1.1 on SSDs
max_connectionsHard limit on connectionsKeep modest; use a pooler

Mind the multiplication in work_mem: a complex query can use it several times, and with 200 connections the total can far exceed RAM. Raise it carefully, for the roles or transactions that need it, and look for Sort Method: external merge Disk in EXPLAIN ANALYZE to see when it is too small.

§3Tune from Evidence

Settings advice on the internet is a starting point, not an answer. Make one change at a time and measure with a realistic workload.

  • Check log_checkpoints and the pg_stat_checkpointer view (pg_stat_bgwriter before PostgreSQL 17): checkpoints triggered by size rather than time mean max_wal_size is too low.
  • Check cache hit ratios in pg_stat_database and per-query shared_blks_read in pg_stat_statements.
  • Check EXPLAIN (ANALYZE, BUFFERS) for disk-based sorts and hashes before touching work_mem.
  • Use log_min_duration_statement to log slow queries, then fix the queries first. Bad queries cost more than bad settings.

Tools like PGTune produce reasonable first values from your hardware, but they cannot see your workload. Record what you changed, why, and the before-and-after numbers.

The key insight Queries and indexes usually matter more than settings. Tune configuration after you have found a measured bottleneck, and change one thing at a time.

§4Common Mistakes

MistakeWhat HappensFix
Raising work_mem globally to a large valueMany concurrent sorts and hashes exhaust memory and the server is killedRaise it per role or per transaction, and size for connections times operations
Changing many settings at once from a blog postYou cannot tell which change helped or hurtChange one thing, measure, and record the result
Editing postgresql.conf and not reloading, or needing a restart and not planning itSettings silently stay unchanged, or an unplanned restart interrupts serviceCheck pg_settings.context and pending_restart
Practice
  1. Query pg_settings for the table's settings, and note which need a restart.
  2. Run a sort-heavy query with a small and then larger work_mem and compare the plans and times.
  3. Enable log_min_duration_statement = 500 and review the slow queries your workload produces.
Key takeaways
  • Settings can be set globally, per role, or per transaction; pg_settings shows the source and whether a restart is needed.
  • The core knobs are shared_buffers, effective_cache_size, work_mem, maintenance_work_mem, max_wal_size, and random_page_cost.
  • Change one setting at a time, from measurements, and fix slow queries before fiddling with configuration.
