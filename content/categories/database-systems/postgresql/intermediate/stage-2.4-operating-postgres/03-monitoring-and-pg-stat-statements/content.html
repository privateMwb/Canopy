Monitoring & pg_stat_statements

pg_stat_statements shows which queries consume the most time, and good logging catches the rest.

§1Enabling pg_stat_statements

The pg_stat_statements extension records execution statistics for every distinct normalized query: how often it ran, total and mean time, rows returned, and buffer usage. It is the single most useful monitoring tool in Postgres.

-- postgresql.conf (requires a restart)
shared_preload_libraries = 'pg_stat_statements'

-- then, in each database where you want to query it:
CREATE EXTENSION pg_stat_statements;

Queries are normalized: constants are replaced with placeholders (WHERE id = $1), so thousands of executions with different values collapse into one row. Reset the counters with SELECT pg_stat_statements_reset(); before a test to measure just that period.

§2Finding the Worst Queries

Different sort orders answer different questions.

-- Where does the database spend its time overall?
SELECT round(total_exec_time::numeric, 0) AS total_ms, calls,
       round(mean_exec_time::numeric, 2)  AS mean_ms, rows,
       left(query, 80) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 10;

-- Which queries are slow per call?          ORDER BY mean_exec_time DESC
-- Which read the most from disk?            ORDER BY shared_blks_read DESC
-- Which are simply called the most?         ORDER BY calls DESC

A query that takes 2 ms but runs 5 million times an hour can cost more than a 3-second report that runs once. Sort by total time first, then investigate the top entries with EXPLAIN (ANALYZE, BUFFERS) using realistic parameter values. Fix the top three and measure again.

§3Logs and Live Views

Statistics show aggregates; logs show individual events. Turn on logging that earns its keep.

log_min_duration_statement = 500     # log queries slower than 500 ms
log_lock_waits = on                  # log waits longer than deadlock_timeout
log_checkpoints = on                 # checkpoint frequency and cost
log_temp_files = 0                   # log every spill to disk
log_autovacuum_min_duration = 0      # log autovacuum activity
log_line_prefix = '%m [%p] %u@%d '   # timestamp, pid, user, database

For live diagnosis, query pg_stat_activity (what is running now and for how long), pg_stat_database (commits, rollbacks, deadlocks, temp files), and pg_stat_user_tables (scans, dead tuples, vacuum times). The auto_explain module logs the actual plan of slow queries, which is invaluable when a query is slow only occasionally. Ship logs and metrics to a central system and alert on trends such as connection count, replication lag, oldest transaction, and disk space.

The key insight Optimize what the database actually spends time on. Rank queries by total time in pg_stat_statements; intuition about which query is slow is wrong surprisingly often.

§4Common Mistakes

MistakeWhat HappensFix
Optimizing the query someone complained about without measuringEffort goes into a rare query while the real load is elsewhereRank by total time in pg_stat_statements first
Forgetting shared_preload_libraries and the restartCREATE EXTENSION works but the view errors on queryAdd the library, restart, then create the extension
Logging every statement in productionHuge logs and measurable overheadLog slow statements with log_min_duration_statement instead
Practice
  1. Enable pg_stat_statements, run a mixed workload, and list the top five queries by total time.
  2. Take the top query and examine its plan with EXPLAIN (ANALYZE, BUFFERS); propose a fix.
  3. Turn on log_lock_waits and log_min_duration_statement, create a lock wait, and find it in the log.
Key takeaways
  • pg_stat_statements aggregates normalized queries; sort by total time, then by mean time and I/O.
  • Use targeted logging for slow statements, lock waits, checkpoints, and temp files.
  • Combine live views (pg_stat_activity) with trends and alerts on connections, lag, oldest transaction, and disk.
