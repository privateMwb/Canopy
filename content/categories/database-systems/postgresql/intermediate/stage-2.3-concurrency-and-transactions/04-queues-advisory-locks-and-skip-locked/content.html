Queues, Advisory Locks & SKIP LOCKED

SELECT ... FOR UPDATE SKIP LOCKED turns a table into a safe job queue, and advisory locks coordinate work that has no row to lock.

§1A Queue in a Table

Many systems need a work queue, and Postgres can serve small and medium ones without extra infrastructure. The challenge: several workers must each claim a different job, never the same one twice. SKIP LOCKED solves this: a worker locks the first available job and other workers simply skip locked rows instead of waiting.

CREATE TABLE jobs (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payload    jsonb NOT NULL,
    state      text NOT NULL DEFAULT 'queued',
    attempts   int  NOT NULL DEFAULT 0,
    run_after  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX jobs_ready_idx ON jobs (run_after) WHERE state = 'queued';

The partial index keeps the "ready" set small however many finished jobs the table holds.

§2Claiming Work Safely

Claim and mark a job in one statement so a crash cannot lose or duplicate it.

WITH next AS (
    SELECT id FROM jobs
    WHERE state = 'queued' AND run_after <= now()
    ORDER BY run_after, id
    LIMIT 1
    FOR UPDATE SKIP LOCKED
)
UPDATE jobs j
   SET state = 'running', attempts = attempts + 1
  FROM next
 WHERE j.id = next.id
RETURNING j.id, j.payload;

After the work, update the job to done or schedule a retry by setting state = 'queued' and a later run_after. For crash recovery, also record when a job started and let a sweeper requeue jobs that have been running too long. Delivery is therefore at least once: handlers must be idempotent (Lesson 2.2.5). Keep the claiming transaction short and do not hold it open during the work itself; claim, commit, work, then update.

§3Advisory Locks

Advisory locks are locks on an arbitrary number that *your application* defines the meaning of. Postgres tracks and enforces them but does not tie them to any table. Use them to ensure only one process runs a task, such as a nightly job or a migration.

SELECT pg_try_advisory_lock(42);          -- true if acquired, false if someone has it
SELECT pg_advisory_unlock(42);

BEGIN;
SELECT pg_advisory_xact_lock(hashtext('nightly-report'));   -- released at COMMIT/ROLLBACK
-- do exclusive work
COMMIT;

Session-level locks (pg_advisory_lock) persist until released or the connection closes, which makes them risky with connection pools in transaction mode; prefer the transaction-scoped pg_advisory_xact_lock form. When queue volume or latency needs outgrow a table (very high throughput, fan-out, or complex routing), a dedicated broker is the better tool, as Stage 3.4 discusses.

The key insight FOR UPDATE SKIP LOCKED replaces "who has the lock?" waiting with "give me whatever nobody has", which is exactly what a pool of workers wants.

§4Common Mistakes

MistakeWhat HappensFix
Workers selecting a job and updating it in two separate statementsTwo workers claim the same jobClaim and mark it in one statement using FOR UPDATE SKIP LOCKED
Holding the claim transaction open while doing the workLong transactions, bloat, and lost jobs when a worker diesCommit the claim, do the work, then record the result
Using session-level advisory locks behind a transaction-mode poolerThe lock stays with a server connection another client may reuseUse pg_advisory_xact_lock or a session-mode connection
Practice
  1. Create the jobs table, enqueue 100 jobs, and run three worker sessions claiming jobs with SKIP LOCKED; verify none are claimed twice.
  2. Add retry with backoff by requeueing failed jobs with a later run_after.
  3. Use pg_try_advisory_lock to make sure only one copy of a scheduled task runs at a time.
Key takeaways
  • FOR UPDATE SKIP LOCKED lets many workers claim different rows without waiting on each other.
  • Claim in one statement, commit, do the work, then record the result; delivery is at least once, so handlers must be idempotent.
  • Advisory locks coordinate application-defined critical sections; prefer the transaction-scoped form.
