Transactions & ACID Basics

A transaction groups statements into one all-or-nothing unit, and ACID describes the guarantees that make it trustworthy.

§1BEGIN, COMMIT, ROLLBACK

By default each statement in Postgres is its own transaction. To group several, wrap them explicitly. Nothing is visible to other sessions until COMMIT, and ROLLBACK discards everything.

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

If any statement errors inside a transaction, the transaction enters an aborted state: every later statement fails until you ROLLBACK. Savepoints let you recover part-way without losing everything.

BEGIN;
INSERT INTO log (msg) VALUES ('start');
SAVEPOINT try_it;
INSERT INTO accounts (id) VALUES (1);     -- fails: duplicate key
ROLLBACK TO try_it;                       -- undo just that step
COMMIT;

§2What ACID Promises

  • Atomicity: all the statements take effect, or none do. A crash mid-transaction leaves no half-applied change.
  • Consistency: a transaction moves the database from one valid state to another; constraints are checked and violations abort the transaction.
  • Isolation: concurrent transactions do not see each other's uncommitted work. How strictly is a setting (Stage 2.3).
  • Durability: once COMMIT returns, the change survives a crash, because the commit record is flushed to the write-ahead log on disk (Stage 3.1).

DDL is transactional in Postgres: CREATE TABLE, ALTER TABLE, and DROP can be rolled back, which makes migrations safer than on many databases.

BEGIN;
ALTER TABLE books ADD COLUMN subtitle text;
DROP TABLE old_books;
ROLLBACK;            -- both undone

§3Using Transactions Well

Keep transactions short. An open transaction holds locks and prevents cleanup of old row versions, so a transaction left open while waiting for a user or a slow API call harms the whole database (Stage 2.3).

Do the thinking outside the transaction: gather input, validate, then BEGIN, write, COMMIT. Handle failures by retrying the whole transaction when the error is a serialization failure or deadlock, and by reporting constraint violations to the user.

Application drivers usually start a transaction implicitly for you and commit at the end of a block; learn what your library does, and never assume that code running in a handler is atomic unless a transaction wraps it.

The key insight Atomicity is about failure, not concurrency. A transaction guarantees you never see a half-completed transfer, even if the server dies between the two UPDATEs.

§4Common Mistakes

MistakeWhat HappensFix
Running related writes as separate autocommit statementsA failure between them leaves inconsistent dataWrap them in one transaction
Continuing after an error inside a transactionEvery later statement fails with "current transaction is aborted"Roll back, or use a savepoint to recover
Holding a transaction open across user input or network callsLocks held and cleanup blocked for a long timeOpen the transaction only around the database work
Practice
  1. Run a two-statement money transfer in a transaction and verify a ROLLBACK restores both balances.
  2. Cause an error mid-transaction, observe the aborted state, and recover using a savepoint.
  3. Drop a table and roll it back to confirm DDL is transactional.
Key takeaways
  • A transaction makes several statements atomic: COMMIT keeps them all, ROLLBACK discards them all.
  • ACID: atomicity, consistency, isolation, durability; durability comes from the write-ahead log.
  • Keep transactions short and retry them on serialization failures and deadlocks.
