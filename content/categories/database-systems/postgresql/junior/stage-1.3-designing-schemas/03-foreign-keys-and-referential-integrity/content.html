Foreign Keys & Referential Integrity

Foreign keys make the database refuse orphan rows, and ON DELETE rules decide what happens to children when a parent goes away.

§1Declaring a Foreign Key

A foreign key says that a column's value must exist in another table's key. Postgres checks it on every insert and update to the child, and on every update or delete of the parent.

CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES customers (id) ON DELETE RESTRICT
);

INSERT INTO orders (customer_id) VALUES (999);
-- ERROR: insert or update on table "orders" violates foreign key constraint
-- DETAIL: Key (customer_id)=(999) is not present in table "customers".

The referenced column must be unique (usually the primary key). Without a foreign key, nothing stops application bugs, manual fixes, and half-finished deletes from leaving orphan rows that join to nothing.

§2ON DELETE and ON UPDATE Actions

When a parent row is deleted, the foreign key's action decides what happens to children.

ActionBehaviorTypical use
NO ACTION (default)Error at the end of the statement if children existGeneral safety
RESTRICTError immediately if children existStrict, non-deferrable check
CASCADEDelete the children tooOwned data: order items with an order
SET NULLSet the child's column to NULLOptional links; column must be nullable
SET DEFAULTSet the child's column to its defaultRare
CREATE TABLE order_items (
    order_id   bigint NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
    product_id bigint NOT NULL REFERENCES products (id) ON DELETE RESTRICT,
    PRIMARY KEY (order_id, product_id)
);

Choose CASCADE only for data that has no meaning without its parent. Cascading from a core table like customers can erase a surprising amount of history with one statement.

§3Indexes, Deferral, and Existing Data

Postgres does not automatically index the referencing (child) column. Parent deletes must find matching children, so without an index on orders.customer_id each delete scans the whole child table. Add the index yourself.

CREATE INDEX ON orders (customer_id);

-- Check constraints later, at COMMIT, e.g. to insert two rows that reference each other
ALTER TABLE a ADD CONSTRAINT a_b_fk FOREIGN KEY (b_id) REFERENCES b (id)
    DEFERRABLE INITIALLY DEFERRED;

-- Adding to a big table without a long lock: add unvalidated, then validate
ALTER TABLE orders ADD CONSTRAINT orders_cust_fk
    FOREIGN KEY (customer_id) REFERENCES customers (id) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_cust_fk;

NOT VALID enforces the rule for new rows immediately and lets you check old rows later with a lighter lock, which is the safe pattern on large production tables.

The key insight Let the database enforce what the code assumes. The cost of a foreign key is a small amount of write overhead; the cost of orphan data is paid in bugs, forever.

§4Common Mistakes

MistakeWhat HappensFix
Skipping foreign keys "for performance"Orphan rows accumulate and joins return wrong resultsKeep them; index the child column to keep writes fast
Using ON DELETE CASCADE on a core business tableOne delete removes years of dependent historyUse RESTRICT or soft deletion; cascade only for owned children
Not indexing the foreign key columnParent deletes and joins scan the child tableAdd an index on every foreign key column that is queried or cascaded
Practice
  1. Create customers and orders with a foreign key and try inserting an order for a missing customer.
  2. Delete a customer under RESTRICT, then under CASCADE, and compare the outcomes.
  3. Use EXPLAIN on a parent delete with and without an index on the child column.
Key takeaways
  • Foreign keys stop orphan rows; the referenced column must be unique.
  • Pick ON DELETE actions per relationship: CASCADE for owned children, RESTRICT otherwise.
  • Index referencing columns yourself, and use NOT VALID then VALIDATE to add keys to large tables safely.
