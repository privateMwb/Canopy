Data Types That Matter

Choosing the right column type is the cheapest correctness and performance win in Postgres, and a few popular choices cause quiet bugs.

§1The Everyday Types

Most schemas are built from a short list. Pick the most specific type that fits the data, because the type is also a constraint.

NeedTypeNotes
Whole numbersinteger, bigintinteger tops out near 2.1 billion; use bigint for IDs that may grow
Exact decimalsnumeric(p,s)Money, quantities, anything where rounding matters
TexttextNo length penalty versus varchar(n); add a CHECK if you need a limit
True/falsebooleanAccepts true/false, t/f, yes/no
Point in timetimestamptzStored as UTC, displayed in the session time zone
Calendar datedateNo time or zone
Unique IDuuidRandom or time-ordered, generated in the database
Flexible documentsjsonbCovered in Stage 2.2
SELECT 7 / 2, 7 / 2.0, 7::numeric / 2;      -- 3, 3.5000..., 3.5000...
SELECT 0.1::float8 + 0.2::float8;            -- 0.30000000000000004
SELECT 0.1::numeric + 0.2::numeric;          -- 0.3

§2Time and UUIDs

Use timestamptz for events. Despite the name, it does not store a zone: it stores an absolute instant and converts to the session's TimeZone on output. Plain timestamp (without time zone) stores whatever wall-clock value you hand it, which becomes ambiguous the moment two servers or users are in different zones.

SET TimeZone = 'America/New_York';
SELECT now();                                   -- instant, shown in New York time
SELECT '2026-03-08 02:30'::timestamptz;         -- interpreted in the session zone
SELECT now() AT TIME ZONE 'UTC';                -- convert for display as a plain timestamp

For uuid, gen_random_uuid() is built in and produces random version-4 values. PostgreSQL 18 adds uuidv7(), which produces time-ordered values that index better because new rows land near each other.

§3Types That Cause Quiet Bugs

  • float4 / float8 are binary floating point and cannot represent most decimals exactly. Never use them for money.
  • money is locale-dependent and awkward; prefer numeric with an explicit scale.
  • timestamp without time zone hides zone errors until daylight saving time or a second region exposes them.
  • char(n) pads with spaces and gains nothing over text in Postgres.
  • serial is an older shorthand for an integer plus a sequence; Lesson 1.3.5 covers the modern identity column.
  • Integer overflow on integer IDs is a real production outage, because changing the type later rewrites the table.
SELECT 2147483647 + 1;                       -- ERROR: integer out of range
SELECT '2026-02-30'::date;                   -- ERROR: date/time field value out of range

Postgres rejects invalid values at the type level, which is exactly what you want.

Rule of thumb bigint for keys, numeric for money, text for strings, timestamptz for instants. Deviate only when you can say why.

§4Common Mistakes

MistakeWhat HappensFix
Storing prices in float8Totals drift by fractions of a cent and reports will not reconcileUse numeric(12,2) or store integer minor units
Using timestamp for event timesValues mean different things in different zones, and daylight saving shifts them silentlyUse timestamptz and convert at the edges
Choosing integer for an ID column on a growing tableOverflow after about 2.1 billion rows forces a painful table rewriteUse bigint from the start
Practice
  1. Run the 0.1 + 0.2 example with float8 and with numeric and explain the difference.
  2. Set the session time zone to two different zones and compare SELECT now(); and SELECT now() AT TIME ZONE 'UTC';.
  3. Generate five UUIDs with gen_random_uuid() and note their ordering; if you are on PostgreSQL 18, compare with uuidv7().
Key takeaways
  • The type is a constraint: pick the most specific one that fits.
  • Use numeric for exact decimals and timestamptz for points in time.
  • Avoid float for money, char(n), and plain timestamp; plan for ID growth with bigint.
