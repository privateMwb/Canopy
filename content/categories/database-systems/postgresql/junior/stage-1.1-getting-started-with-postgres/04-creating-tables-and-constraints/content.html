Creating Tables & Constraints

Constraints turn rules about your data into rules the database enforces, so invalid rows are rejected no matter which application sends them.

§1CREATE TABLE and Primary Keys

A table is a set of named, typed columns. Almost every table should have a primary key: a column (or set of columns) that is unique and never NULL, and that identifies one row.

CREATE TABLE books (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    isbn        text NOT NULL UNIQUE,
    title       text NOT NULL,
    price       numeric(8,2) NOT NULL,
    in_stock    boolean NOT NULL DEFAULT true,
    created_at  timestamptz NOT NULL DEFAULT now()
);

PRIMARY KEY creates a unique index automatically. GENERATED ALWAYS AS IDENTITY produces sequential values for you (Lesson 1.3.5 explains how it works). DEFAULT supplies a value when the INSERT omits the column.

§2NOT NULL, UNIQUE, and CHECK

Each constraint answers a different question about a column.

  • NOT NULL: a value must be present.
  • UNIQUE: no two rows may share this value (NULLs are allowed and do not conflict, unless you write NULLS NOT DISTINCT on Postgres 15+).
  • CHECK (expr): the row is rejected unless the expression is true.
  • DEFAULT expr: not a restriction, but it removes a reason to leave a column empty.
ALTER TABLE books
    ADD CONSTRAINT price_nonneg CHECK (price >= 0),
    ADD CONSTRAINT title_not_blank CHECK (length(btrim(title)) > 0);

INSERT INTO books (isbn, title, price) VALUES ('978-0', 'Dune', -5);
-- ERROR: new row for relation "books" violates check constraint "price_nonneg"

Name your constraints. The auto-generated names are cryptic in error messages and awkward to drop later.

§3Multi-Column Constraints and Altering Tables

Some rules involve more than one column. Define them at the table level.

CREATE TABLE reservations (
    room_id   int NOT NULL,
    day       date NOT NULL,
    guest     text NOT NULL,
    PRIMARY KEY (room_id, day),
    CHECK (guest <> '')
);

ALTER TABLE books ADD COLUMN language text NOT NULL DEFAULT 'en';
ALTER TABLE books RENAME COLUMN title TO name;
ALTER TABLE books DROP COLUMN language;
DROP TABLE reservations;

Adding a constraint to an existing table checks every existing row first, so it fails if the data already violates the rule. Fix or remove the bad rows, then add the constraint.

The key insight Application validation can be bypassed by a second service, a script, or a bug. A constraint in the table cannot be, which is why "make bad data impossible" belongs in the schema.

§4Common Mistakes

MistakeWhat HappensFix
Leaving columns nullable by defaultNULLs creep in and every query must handle themWrite NOT NULL unless absence is a real, meaningful state
Relying on application code alone for uniquenessTwo concurrent requests both pass the check and insert duplicatesAdd a UNIQUE constraint and handle the violation error
Using varchar(255) out of habitArbitrary limits that reject valid data or hide nothingUse text and a CHECK if a real limit exists
Practice
  1. Create books as above and try to insert a negative price, a blank title, and a duplicate ISBN. Read each error message.
  2. Add a CHECK that isbn matches a length of 10 or 13 characters once hyphens are removed.
  3. Create a table with a composite primary key and show that a duplicate pair is rejected while a partial match is accepted.
Key takeaways
  • Every table gets a primary key; every column that must have a value gets NOT NULL.
  • UNIQUE and CHECK enforce rules in the database itself, regardless of which client writes.
  • Name constraints so error messages and later migrations stay readable.
