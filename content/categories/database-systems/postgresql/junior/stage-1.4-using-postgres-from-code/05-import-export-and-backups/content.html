Import, Export & Backups

COPY moves data in and out fast, pg_dump and pg_restore back up a database, and a backup you have never restored is only a hope.

§1COPY: Bulk Import and Export

COPY reads or writes whole tables (or query results) far faster than row-by-row INSERTs. The server-side COPY reads files on the *server*; psql's \copy reads and writes files on *your* machine, which is usually what you want.

\copy books (isbn, title, price) FROM 'books.csv' WITH (FORMAT csv, HEADER)
\copy (SELECT * FROM books WHERE in_stock) TO 'stock.csv' WITH (FORMAT csv, HEADER)

Load order for big imports: create the table, COPY the data, *then* create indexes and add foreign keys. Building an index once over loaded data is much faster than maintaining it row by row. Wrap the load in a transaction so a bad file does not leave partial data.

§2pg_dump and pg_restore

pg_dump takes a consistent snapshot of one database while it is in use. The custom format (-Fc) is compressed and lets pg_restore pick objects and run in parallel.

pg_dump -Fc -d shop -f shop.dump                   # logical backup of one database
pg_dump -Fd -j 4 -d shop -f shop_dir               # directory format, 4 parallel jobs
pg_dumpall --globals-only > globals.sql            # roles and tablespaces

createdb shop_restored
pg_restore -d shop_restored -j 4 shop.dump         # restore, 4 parallel jobs

A logical dump is portable across versions and platforms and is ideal for small to mid-sized databases, moving data between environments, and upgrades. It restores to a single point in time (the moment the dump began). For large databases that need minute-level recovery, you also need physical backups and WAL archiving, covered in Stage 2.4.

§3Prove the Backup Works

A backup is real only after a restore test. Make this routine: restore to a scratch server, then check basic facts.

pg_restore -d scratch --exit-on-error shop.dump
psql -d scratch -c "SELECT count(*) FROM orders;"
psql -d scratch -c "SELECT max(placed_at) FROM orders;"      -- is it recent enough?

Practical rules: store backups on different storage than the database, encrypt them, keep several generations, monitor that the job ran *and* succeeded, and write down the restore steps and expected time. Decide in advance how much data loss (RPO) and downtime (RTO) the business can accept, then pick a backup method that meets those numbers.

The key insight The only backup that counts is one you have restored successfully. Schedule restore tests, not just dumps.

§4Common Mistakes

MistakeWhat HappensFix
Importing with row-by-row INSERTsAn import that should take seconds takes hoursUse COPY or \copy, and create indexes after loading
Never testing a restoreThe backup turns out to be empty, corrupt, or missing roles when you need itRestore to a scratch server on a schedule and check row counts
Keeping backups on the same disk or server as the databaseOne failure destroys bothCopy backups off-host to separate storage
Practice
  1. Export a table to CSV with \copy, truncate it, and import it back; compare row counts.
  2. Dump a database with pg_dump -Fc, restore it into a new database with pg_restore, and diff row counts per table.
  3. Write down an RPO and RTO for a small shop and decide whether nightly dumps satisfy them.
Key takeaways
  • COPY and \copy are the fast way to load and export data; build indexes after the load.
  • pg_dump -Fc plus pg_restore gives portable logical backups; globals need pg_dumpall.
  • Restore tests, off-host storage, and agreed RPO and RTO are what make a backup trustworthy.
