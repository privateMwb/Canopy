Connections, Roles & Authentication

An application connects with a URL, authenticates as a role, and is allowed in only if pg_hba.conf says so, so least privilege starts here.

§1Connection Strings

Almost every driver accepts a connection URI or the equivalent key/value pairs. Both describe the same five things: host, port, database, user, and password, plus options such as TLS.

postgresql://app_user:s3cret@db.internal:5432/shop?sslmode=verify-full

host=db.internal port=5432 dbname=shop user=app_user sslmode=verify-full

Keep the password out of source control: read the whole URL (or its parts) from an environment variable or a secrets manager. Use sslmode=verify-full for any connection that crosses a network you do not fully control; plain require encrypts but does not verify the server's identity. A ~/.pgpass file or a service file (pg_service.conf) keeps credentials out of command lines for humans.

§2Least-Privilege Roles

The application should connect as a role that can do only what the application does. Separate the owner of the schema (used by migrations) from the role the running service uses.

CREATE ROLE shop_owner LOGIN PASSWORD '...';          -- runs migrations
CREATE ROLE shop_app   LOGIN PASSWORD '...';          -- runs the service

GRANT CONNECT ON DATABASE shop TO shop_app;
GRANT USAGE ON SCHEMA public TO shop_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO shop_app;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO shop_app;

ALTER DEFAULT PRIVILEGES FOR ROLE shop_owner IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO shop_app;

With this split, a SQL injection flaw in the service cannot drop tables or change roles. Reporting tools get a separate read-only role.

§3pg_hba.conf and Authentication

pg_hba.conf (host-based authentication) is a list of rules, read top to bottom; the first match decides. Each line names a connection type, database, role, client address, and authentication method.

# TYPE  DATABASE  USER      ADDRESS         METHOD
local   all       postgres                  peer
host    shop      shop_app  10.0.0.0/16     scram-sha-256
hostssl all       all       0.0.0.0/0       scram-sha-256
host    all       all       0.0.0.0/0       reject

scram-sha-256 is the standard password method and the default for new installs; avoid md5 and never use trust outside a throwaway local machine. peer maps the operating system user to the database role for local socket connections. After editing, reload with SELECT pg_reload_conf();. Also check listen_addresses in postgresql.conf: the server only listens where you tell it to.

The key insight Two separate gates apply: the network and pg_hba.conf decide whether you may connect and how you must prove who you are; role privileges decide what you can do afterwards.

§4Common Mistakes

MistakeWhat HappensFix
Using the postgres superuser in the application's connection stringAny injection flaw has full control of the serverCreate a role with only the table privileges the service needs
Committing the connection string or password to GitCredentials leak and must be rotated everywhereLoad them from the environment or a secrets store
Setting trust or 0.0.0.0/0 with weak methodsAnyone who can reach the port can log inUse scram-sha-256 with TLS, narrow address ranges, and a firewall
Practice
  1. Create shop_owner and shop_app roles and confirm the app role cannot DROP TABLE or CREATE TABLE.
  2. Read the pg_hba.conf of a local install (SHOW hba_file;) and explain each active line.
  3. Connect using a URI with sslmode set and verify with SELECT ssl FROM pg_stat_ssl WHERE pid = pg_backend_pid();.
Key takeaways
  • A connection URI carries host, port, database, user, password, and TLS options; keep secrets out of code.
  • Use separate roles for migrations and for the running service, each with minimal privileges.
  • pg_hba.conf is evaluated first-match-wins; prefer scram-sha-256 over md5 and never trust in production.
