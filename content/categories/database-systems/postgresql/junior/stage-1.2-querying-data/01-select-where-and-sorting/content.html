SELECT, WHERE & Sorting

SELECT chooses columns, WHERE chooses rows, and ORDER BY and LIMIT decide which rows you see first.

§1Projecting and Filtering

A query reads from a table, filters rows with WHERE, and then returns the columns you list. The examples in this stage use a small bookstore: books(id, title, author_id, price, published, in_stock).

SELECT title, price
FROM books
WHERE in_stock AND price < 15
  AND published >= '2020-01-01';

Common predicates: comparison (=, <>, <, >=), ranges (BETWEEN 5 AND 10, inclusive at both ends), sets (IN ('a','b')), patterns (LIKE 'The %', case-insensitive ILIKE), and IS NULL for missing values. Combine them with AND, OR, and NOT; use parentheses whenever you mix AND and OR, because AND binds tighter.

Prefer naming columns over SELECT * in application code. It keeps results stable when the schema changes and avoids fetching data you do not need.

§2Sorting and Limiting

Rows come back in no guaranteed order unless you say so. ORDER BY sorts by one or more expressions, each ascending (the default) or descending.

SELECT title, price
FROM books
ORDER BY price DESC, title ASC
LIMIT 10 OFFSET 20;       -- page 3 when pages hold 10 rows

NULLs sort last in ascending order and first in descending order by default; override with NULLS FIRST or NULLS LAST. DISTINCT removes duplicate result rows, and DISTINCT ON (author_id) keeps the first row per author according to your ORDER BY, a Postgres-specific shortcut for "latest per group".

SELECT DISTINCT ON (author_id) author_id, title, published
FROM books
ORDER BY author_id, published DESC;      -- newest book per author

§3Pagination

LIMIT ... OFFSET ... is simple, but the database must still walk past every skipped row, so deep pages get slower. For large tables, use keyset pagination: remember the last row you showed and ask for rows after it.

SELECT id, title
FROM books
WHERE id > 1042            -- last id from the previous page
ORDER BY id
LIMIT 20;

Keyset pagination stays fast with an index on the sort column and does not skip or repeat rows when data is inserted between requests. Whatever you use, always include ORDER BY with a unique tiebreaker such as id, or pages can overlap.

The key insight A table has no inherent row order. If the order matters to the reader or to pagination, it must be in the query as ORDER BY, ending with a unique column as a tiebreaker.

§4Common Mistakes

MistakeWhat HappensFix
Mixing AND and OR without parenthesesa OR b AND c means a OR (b AND c), returning surprising rowsAdd explicit parentheses
Paginating with LIMIT and no ORDER BYRows can repeat or vanish between pagesOrder by a unique key on every paginated query
Writing WHERE col = NULLAlways returns no rows, since NULL is not equal to anythingUse IS NULL or IS NOT NULL
Practice
  1. Write a query for in-stock books under 20, sorted by price descending then title, limited to 5 rows.
  2. Use DISTINCT ON to return the most recent book for each author.
  3. Rewrite a deep OFFSET 100000 page query as a keyset query and compare timings with \timing.
Key takeaways
  • WHERE filters rows; the select list picks columns; name columns rather than using * in application code.
  • Without ORDER BY there is no order, and pagination needs a unique tiebreaker.
  • Keyset pagination scales better than large OFFSET values.
