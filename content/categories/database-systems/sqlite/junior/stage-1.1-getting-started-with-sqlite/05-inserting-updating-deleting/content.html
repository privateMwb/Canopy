Inserting, Updating & Deleting

INSERT, UPDATE, and DELETE change data, and checking what changed is what separates a careful edit from a destructive one.

§1Insert

INSERT INTO product (name, price_cents) VALUES ('Pen', 120);
INSERT INTO product (name, price_cents) VALUES ('Pad', 450), ('Ink', 800);
INSERT INTO archive SELECT * FROM product WHERE price_cents > 500;
SELECT last_insert_rowid();       -- id of the row just inserted

§2Update and Delete

UPDATE product SET price_cents = price_cents + 10 WHERE name = 'Pen';
DELETE FROM product WHERE id = 3;
SELECT changes();                 -- rows affected by the last statement

Omit the WHERE clause and every row is changed or removed.

§3Conflict Handling

INSERT OR IGNORE INTO account (email) VALUES ('a@x.com');     -- skip duplicates
INSERT OR REPLACE INTO account (id, email) VALUES (1, 'b@x.com');   -- delete and reinsert
INSERT INTO account (email) VALUES ('a@x.com')
  ON CONFLICT (email) DO UPDATE SET age = excluded.age;       -- upsert

OR REPLACE deletes the old row first, so columns you do not mention reset to defaults and delete triggers can fire. An ON CONFLICT ... DO UPDATE upsert is usually safer.

§4Return What Changed

UPDATE product SET price_cents = 999 WHERE id = 1 RETURNING id, price_cents;

RETURNING is available since 3.35 and shows exactly which rows were affected.

§5Wrap Risky Edits in a Transaction

BEGIN;
DELETE FROM product WHERE price_cents < 100;
SELECT changes();       -- check the count, then:
ROLLBACK;               -- or COMMIT;
The key insight Run the same WHERE as a SELECT first, then inside a transaction check changes() before you commit.

§6Common Mistakes

MistakeWhat HappensFix
UPDATE or DELETE with no WHEREEvery row is changed or lostTest with SELECT and use a transaction
Using INSERT OR REPLACE as an updateUnmentioned columns are resetUse ON CONFLICT DO UPDATE
Ignoring changes()A wrong filter silently affects zero rowsCheck the count in code
Practice
  1. Insert five products, raise one price with RETURNING, and delete one inside a transaction that you roll back.
  2. Write an upsert that adds to a counter column if the row already exists.
Key takeaways
  • INSERT, UPDATE, and DELETE take a WHERE clause, and omitting it affects every row.
  • Upserts use ON CONFLICT DO UPDATE, and RETURNING shows changed rows.
  • Check changes() and use transactions for risky edits.
