WAL Internals & Checkpointing

In WAL mode, committed changes sit in a log file with an index in shared memory, and checkpoints move them into the main database.

§1The Files

  • db-wal: a 32-byte header, then a series of frames. Each frame is a page image preceded by a 24-byte frame header with the page number, the database size after commit, a salt, and a checksum.
  • db-shm: the wal-index, a shared-memory hash table that maps page numbers to the newest frame that holds them.

§2Commit

A write appends frames for the changed pages. The transaction commits when the last frame is marked as a commit frame (the header records the database size). Nothing in the main file changes, which is why a commit can be a single sequential append and, optionally, one sync.

§3Reading

A reader records the end mark, the last committed frame at its start. For each page it needs, it looks in the wal-index for the newest frame at or before that mark, and otherwise reads the main file. Readers therefore see a consistent snapshot and never block the writer.

PRAGMA wal_checkpoint(PASSIVE);     -- copy what it can without blocking
PRAGMA wal_checkpoint(FULL);        -- wait for writers, then copy everything
PRAGMA wal_checkpoint(RESTART);     -- also wait so the next writer restarts the log
PRAGMA wal_checkpoint(TRUNCATE);    -- RESTART plus truncate the file to zero bytes

§4Checkpointing

A checkpoint copies the newest version of each page in the log into the database file, and can only copy frames older than the oldest active reader's end mark. After a full checkpoint, the writer can start over at the beginning of the log and reuse the space.

§5Why a WAL Can Grow

A long-lived reader keeps an old end mark, so the checkpoint cannot pass it, and the writer must keep appending. Or checkpoints are starved by constant activity. Watch the -wal size, keep read transactions short, and run a TRUNCATE checkpoint during quiet periods.

PRAGMA wal_autocheckpoint = 1000;
PRAGMA journal_size_limit = 67108864;

§6Recovery

On opening after a crash, SQLite rebuilds the wal-index from the WAL by validating frame checksums, and ignores anything after the last valid commit.

The key insight WAL turns commits into appends and snapshots into frame lookups. The cost is the checkpoint, which has to keep up with the writer.

§7Common Mistakes

MistakeWhat HappensFix
A reader that never endsThe WAL grows without boundBound the lifetime of read transactions
Deleting the -shm file while connections existReaders lose the shared indexLet SQLite manage it, and close all connections first
Running a FULL checkpoint in a busy system with long readersIt waits and blocks writersUse PASSIVE regularly and TRUNCATE at quiet times
Practice
  1. Observe the WAL grow while a reader holds a transaction, then checkpoint after it ends.
  2. Run each checkpoint mode and read the three numbers it returns.
Key takeaways
  • WAL frames hold page images, and the wal-index maps pages to frames.
  • Readers take a snapshot end mark, so they never block the writer.
  • Checkpoints merge the log into the database, and long readers can prevent that.
