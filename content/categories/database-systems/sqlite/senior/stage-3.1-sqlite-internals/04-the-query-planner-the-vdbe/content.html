The Query Planner & the VDBE

SQLite compiles every SQL statement into bytecode for a small virtual machine, and reading that bytecode explains why queries perform as they do.

§1From SQL to Bytecode

The tokenizer and parser produce a parse tree, the planner chooses how to access each table, and the code generator emits a program for the VDBE (virtual database engine).

EXPLAIN SELECT name FROM product WHERE id = 7;
addr  opcode       p1  p2  p3
0     Init         0   9   0
1     OpenRead     0   2   0      -- open a cursor on the table's B-tree
2     Integer      7   1   0
3     SeekRowid    0   8   1      -- jump to the row with that id
4     Column       0   1   2      -- read column 1
5     ResultRow    2   1   0
...

Opcodes such as OpenRead, Rewind, Next, SeekGE, Column, and ResultRow open cursors on B-trees, move them, and read data. Loops are Rewind/Next pairs, so more nested loops means more of them.

§2Reading It

You rarely need the details, but a few patterns are informative:

  • A Rewind followed by Next over a table with no Seek* is a full scan.
  • SeekGE or SeekRowid is an index or rowid lookup.
  • SorterOpen and SorterInsert mean an explicit sort.
  • OpenEphemeral creates a temporary B-tree, for example for DISTINCT or IN.

§3The Query Planner

For each table in a join, the planner estimates the cost of each access path from statistics and index information, and picks the cheapest ordering of loops. SQLite always uses nested loops: for each row of the outer table, it searches the inner table, ideally by index. It can also build an automatic index on the fly when it expects that to be cheaper than repeated scans.

SEARCH a USING INDEX ...
SEARCH b USING AUTOMATIC COVERING INDEX (a_id=?)    -- the planner built a temporary index

An automatic index in your plan is a hint that you should create a real one.

§4Statement Reuse

Compilation costs time. A prepared statement compiled once and run many times avoids repeating it, which is why drivers expose prepared statements and caches.

The key insight EXPLAIN QUERY PLAN answers "how", and EXPLAIN bytecode answers "exactly what". Reach for bytecode only after the plan does not explain the behavior.

§5Common Mistakes

MistakeWhat HappensFix
Ignoring AUTOMATIC INDEX in a planEvery execution rebuilds a temporary indexCreate the permanent index
Re-parsing the same SQL on every callWasted CPUReuse prepared statements
Reading bytecode before reading the planToo much detailStart with EXPLAIN QUERY PLAN
Practice
  1. Run EXPLAIN on a join and identify each loop's Rewind and Next.
  2. Find a query whose plan includes an automatic index and create the real one.
Key takeaways
  • SQL is compiled into VDBE bytecode that drives B-tree cursors.
  • Joins use nested loops, and the planner picks the order from cost estimates.
  • Automatic indexes and sorters in the plan point to missing indexes.
