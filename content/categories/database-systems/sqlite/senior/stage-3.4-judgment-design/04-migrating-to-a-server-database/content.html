Migrating to a Server Database

Planning a path to a server database before you need it turns a future emergency into a routine project.

§1Know Your Trigger

Define measurable signs: sustained SQLITE_BUSY rates, write queue latency above a threshold, need for a second application host, database size making restores too slow, or new requirements such as row-level security. Review them on a schedule.

§2Keep the Door Open

  • Use standard SQL where you can, and isolate SQLite-specific features (such as flexible typing, INSERT OR REPLACE, GLOB, and rowid reliance) behind a data-access layer.
  • Use STRICT tables and explicit types, which map more cleanly to a server database.
  • Store dates in one consistent format, and money as integers.
  • Avoid depending on implicit rowid and on case-insensitive LIKE behavior.
  • Keep the schema in migrations that you can translate.

§3The Migration Steps

1. Stand up the target and translate the schema (types, constraints, sequences, indexes).

2. Copy data with a tool or script, using CSV or batch inserts, fixing values that violate stricter types.

3. Verify: compare row counts, checksums, and sample queries.

4. Run in parallel: write to both, or replicate changes, and compare results.

5. Cut over during a quiet period, with a rollback plan to the SQLite file.

pgloader app.db postgresql:///target       # one example tool
sqlite3 app.db ".mode csv" ".headers off" ".once orders.csv" "SELECT * FROM orders;"

§4Differences to Test

Typing and coercion, NULL ordering, case sensitivity, date handling, integer division, AUTOINCREMENT versus sequences, boolean values, and concurrency behavior. Run your test suite against the target engine.

§5Rehearse

Time the full migration on a copy of production data, and measure downtime. If it needs hours, plan an incremental approach with change capture.

The key insight The cost of leaving is set by how many SQLite-specific assumptions are in your code. Reduce them while it is cheap.

§6Common Mistakes

MistakeWhat HappensFix
Never rehearsing a migrationCutover day reveals data problemsPractice on a production copy
Leaning on SQLite-only behaviors everywhereA rewrite instead of a migrationIsolate them behind a data layer
Cutting over with no rollbackA bad result is irreversibleKeep the SQLite file and a way back
Practice
  1. List the SQLite-specific behaviors your application relies on and mark which would break on PostgreSQL.
  2. Migrate a sample database to PostgreSQL, fix type errors, and compare checksums.
Key takeaways
  • Define measurable triggers for moving to a server database.
  • Reduce SQLite-specific assumptions and use explicit, strict schemas.
  • Rehearse data copy, verification, parallel running, and rollback.
